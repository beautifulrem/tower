## 1. 总评

**第 82 轮的 1 条重要、8 条次要条目全部关闭**（R82-D5-01 就所问的三处关闭，但 ADR-210 的 “一律不调用 Host 的 `getAgentDir()`” 对 MCP 与设置不成立，另列 R83-D5-01）。§5 的 11 条观察中，10 条落地或随删除失效，观察 9 部分落地。核对见 §3。

**ADR-210 的主体成立**（§3.3）：
- **准备命令的删除**：
  - 命令、远程矩阵一行与 `16` §16.5 一行都已撤除；
  - `00` §0.5.1、`10` §10.8.4 第 2 步、`04` §4.6.7、G37 与 T31 都如实写成 “由人在自己的终端中运行”；
  - M2 的两个前提写在唯一定义处。
  - 只残留 `12` L418 一处 “按钮在目标页人工编辑面板”，lint (d) 按名字匹配，拦不到（并入 R83-D15-01）。
- **非回合检查点照常记 `checkpoint.created`**：
  - 事件消费者（`10` L1320 的时间线、恢复与指纹；`05` L1093 的映射只针对回合检查点）都不受影响；
  - I4(b) 不变，归因窗口按序号取检查点的前提得以成立。
  - 带出一处原有的空白：settle 时 `agent_bg_done` 检查点会因去重不建（R83-D6-01）。
- **“当前 pin 的检查点”**：树与 L 都相等的最近检查点，没有时取 pin 本身。与归因表第 4 行、I2 与交还第 6 步用同一个 L，成立。
  - `externalChange.baselineCps` 的类型容不下 “pin 本身”。这一点在 ADR-210 之前已存在，记为观察 5。
- **`info/exclude` 的刷新时机**：唯一定义（`10` L183）、用户说明（`10` L184、`04` L1313）与 G46 第八组一致。
  - “Run 开始” 覆盖暂停后继续、自动返工、`request_changes`、`retry_after_human_change`；`retry_verify` 与 settle 续跑不开 Run，所以不刷新，与说明相符。
  - 但刷新把 “忽略规则在 Goal 进行中变化” 从少见变为常规，暴露了影子索引的一个原有问题：“同一内容与同一个 L 总得到同一棵树，与索引的历史无关” 并不成立（R83-D13-01）。
- **G21 的改写**：用例本身改为 M1 中存在的路径，成立。但 G21 仍在 B1（第 11 周，只依赖 W7-core），而交还写回到第 22 周才完成（R83-D14-01）。

**全范围扫描**在 ADR-210 之外新发现以下问题：
- **Pi 在加载资源时自动安装用户设置中缺失的包**：发生在 Host 中、沙箱之外，含包的生命周期脚本与网络访问。静态清单只对 “已安装包的目录” 求哈希，正文对这一行为只字未提。这违反 “静态清单，确认之前不加载、不执行任何代码”（R83-D11-01，**重要**）。
- **内置 MCP 扩展按 Host 自己的 `getAgentDir()` 读取 `mcp.json`**：用户设置了 `PI_CODING_AGENT_DIR` 时，实际启动的 MCP 服务器可以不在确认过的清单里（R83-D5-01，**重要**）。
- 检验带回的检查点没有 landmark 与 `humanPaths` 的规定，人带回的改动可能被归为 Agent（R83-D7-01）；
- 评论 “未送达” 的两个按钮没有命令（R83-D8-01），与 R80–R82 的 D8 条目同类；
- “人工编辑检出已丢失” 的 Needs-You 没有 kind、去重键与出口分类（R83-D8-02）；
- `run.rewind`、`run.fork_goal`、`goal.rewind`/`goal.fork` 与诊断视图的回退和分叉动作在 `06`、`08`、`16` 中未标 M2（R83-D15-01）。

### D11 安全与自主度

**R83-D11-01｜重要**（Pi 加载资源时在 Host 中自动安装用户设置里缺失的包，静态清单不覆盖）

- **问题**：
  - `05` L1328 与 `11` L607 的不变式：“**静态清单，确认之前不加载、不执行任何代码**”。清单的组成是：用户 agentDir 下的 `extensions/`、用户 `settings.json` 中 `extensions`/`packages` 指向的本地路径、**已安装包的目录**、用户级 `mcp.json` 中的服务器条目。
  - Pi v1.2.0 中，`createAgentSessionServices` 构造资源加载器后立即 `reload()`。`reload()` 无条件调用 `packageManager.resolve()`，不带 `onMissing`（`core/resource-loader.ts:529`）。
  - `resolve()` 对 `settings.json` 中 `packages` 的每个 npm/git 来源判定。来源**未安装**，或已安装版本与配置的版本**不符**（`core/package-manager.ts:1323`），并且没有 `onMissing` 时，它在 Host 进程中直接安装（`:1308-1318`）：
    - 运行包管理器或克隆仓库，有网络访问；
    - 包的生命周期脚本照常执行；
    - 安装位置在 agentDir 之下（`:2090-2099`）。
    - 随后该包的扩展被加载。
    - 唯一的关闭开关是环境变量 `PI_OFFLINE`（`:60-63`）。
  - 正文没有任何地方提到这一行为。Host 的环境白名单（`11` L507、`05` L447）不含 `PI_OFFLINE`。
  - 于是，用户设置中列出、但本机尚未安装或版本已变的包：
    - 不在确认过的清单中（清单只对已安装包的目录求哈希）；
    - 却在 Host 启动时由 Tower 发起下载、以用户权限在沙箱外执行安装脚本，再作为扩展加载。
    - 这正是该不变式要排除的那一类后果：**未经确认的沙箱外代码在确认之前执行**。另外 Tower 因此写入了用户自己的 Pi 目录，这与 “从存储层面杜绝写入用户 Pi 配置”（`05` §5.3.3）的取向相反。
  - `noExtensions` 只在 `resolve()` 之后过滤扩展路径（`resource-loader.ts:577-578`），所以隔离模式同样会触发安装，取决于隔离模式读哪一份设置（见 R83-D5-01 (b)）。
  - 触发条件并不罕见：用户在新机器上同步了 `settings.json`、手工编辑了 `packages`，或把某个包固定到新版本而尚未在终端中运行过 `pi`。
- **为什么是重要**：照正文实现（`05` §5.3.5 的骨架），这个不变式在上述常见情形下必然被违反，后果是来自网络的、未经确认的代码以用户权限在沙箱外执行。
- **文档位置**：`05` L343–L352、L447、L1328；`11` L507、L607、T16（L692）；`14` A11、C 类契约测试。
- **期望的回答形态**：在 `05` §5.3.6 的 Host 环境（唯一定义）加一条，`11` §11.8.2 引用：
  - Host 环境恒设 `PI_OFFLINE=1`，Tower 从不经 Pi 安装或更新包；
  - 静态清单把 “`settings.json` 的 `packages` 中列出、但未安装或版本不符” 的来源单列为 “未安装：Tower 不安装、不加载，请在终端中运行 `pi` 安装后重新确认”；
  - 补一条契约测试：设置中列出一个未安装的包，Host 启动后没有网络请求、没有安装目录生成、该包未加载。
  - 若不取 `PI_OFFLINE`，另一种取法是自建资源加载流程并传入 `onMissing: "skip"`。但 `reload()` 不接受这个参数，需要登记为依赖项。

### D5 Agent 架构与 Pi 集成

**R83-D5-01｜重要**（“一律不调用 Host 的 `getAgentDir()`” 对内置 MCP 扩展与设置不成立）

- **问题**：
  - **(a) MCP**：
    - ADR-210 在 `05` L459 写明：同一个用户 agentDir 用于全部用户级 Pi 资源，一律不调用 Host 的 `getAgentDir()`；“清单枚举的目录就是 Pi 实际加载扩展的目录”。
    - 但 `05` L343 只向 `createMcpExtension` 传入 `createTransport`。Pi 内置 MCP 扩展缺省时：
      - 以 `loadMcpConfig({agentDir: getAgentDir(), …})` 读 `mcp.json`（`extensions/mcp/index.ts:1344`）；
      - OAuth 凭据存储 `mcp-auth.json` 及其锁目录取 `getAgentDir()`（`extensions/mcp/oauth.ts:147-148`）；
      - `mcp.log` 同样取 `getAgentDir()`（`index.ts:370`）。
    - `getAgentDir()` 读 Host 进程自己的环境，而 Host 的环境白名单不含 `PI_CODING_AGENT_DIR`（ADR-209 正是因为从 Dock 启动时拿不到它才另行求值）。
    - 所以用户设置了 `PI_CODING_AGENT_DIR` 时：
      - 静态清单枚举的是用户 agentDir 中的 `mcp.json`，Pi 实际连接的却是默认目录中的 `mcp.json`（会话开始即连接，`index.ts:1114` 起）。默认目录中若留有旧配置，其中的服务器**不经确认即在沙箱外启动**，违反 `05` L1328、`11` L607 的不变式；
      - 默认目录中没有配置时，用户的 MCP 服务器在 Tower 中全部不可用，而确认卡片仍列出它们；
      - MCP OAuth 登录写入另一份 `mcp-auth.json`，与用户自己的 `pi` 分处两个文件、两把锁。这与 ADR-208 为 `auth.json` 消除的分裂是同一类问题。
  - **(b) 设置**：
    - `05` L459 写 “Pi 以它（传入的 `agentDir`）定位全局 `settings.json`”。但 Tower 自己传入 `settingsManager`（`05` L348），`createAgentSessionServices` 只在缺省时才 `SettingsManager.create(cwd, agentDir)`（`core/agent-session-services.ts:147`）。
    - 全局设置文件的位置因此由 `ReadThroughSettingsStorage` 的 `globalPath` 决定，而 `05` L296–L309 没有为两种模式定义它。
    - 按 “文中 `~/.pi/agent` 均指用户 agentDir” 的统一读法，实现者会在隔离模式下也读用户的 `settings.json`。这与 `05` L459 “隔离的……settings 与 MCP 的加载目录” 相反，并使隔离模式的包解析取用户的 `packages`。隔离 agentDir 下这些包都 “未安装”，于是每个高风险 Goal 启动时都会触发 R83-D11-01 的安装。
- **为什么是重要**：(a) 照正文的骨架实现，在用户自定义了 Pi 目录时必然违反 “确认之前不加载、不执行任何代码”。触发需要非默认配置，但这正是 ADR-209/210 专门要支持的配置，而且 ADR-210 明确断言这一不变式 “仍由构造保证”。(b) 本身是定义缺口，与 R83-D11-01 叠加后放大。

- **期望的回答形态**：在 `05` §5.3.6 “用户 agentDir 的取值” 一段（唯一定义）二选一：

### D13 隔离、git 与并发

**R83-D13-01｜次要**（影子索引的历史影响快照：此前收入、此后被忽略的非 base 路径）

- **问题**：
  - `10` L746 与 `07` L285 断言：“同一工作区内容与同一个 L 总得到同一棵树，不依赖索引的历史 / 与影子索引的历史无关”。
  - 但决定性指纹在持久的影子索引上做 `add -A`（`10` L745–L746）。`add -A` 不会移除已在索引中、现在匹配忽略规则的条目。`10` L740 只对 (b) gitlink 与 (d) 本地文件排除集先 `--force-remove`。
  - 而 `full` 闸口的 “全新临时索引” 一律以 `read-tree <baseCommit>` 初始化（`10` L211），只保住 base 中被跟踪的条目。
  - 于是，一个**不在 base 中**、此前已被某个检查点收入、之后才被忽略的路径：
    - 留在决定性快照、pin 与之后的检查点中；
    - 不在 `full` 的快照中。
  - 这类路径有两个来源：
    - Agent 在 `.gitignore` 中加入它此前生成并已被快照的目录（常见）；
    - ADR-210 起每次 Run 开始从用户仓库刷新 `info/exclude`，人在其中加了一行。
  - 后果：
    - 验收或 seal 时 `full ≠ decisive`，记 `stat_cache_mismatch`（`07` L281）。随后 “变化的路径按归因表分类”，而这些路径没有任何写入者，内容也没有变化，归因表第 1–4 行都不对应。实现者可能送进 `verifying`、送进 `paused(external_change)`，或要求人 “采纳” 一个没有人动过的路径。
    - 同一节又说只经 `info/exclude` 忽略的文件 “不会进入检查点、pin 与 seal”（`10` L183）。对上述路径，这句话不成立。
  - 同类的问题在 “清空该 Goal 的影子索引”（`07` L281）之后也存在：清空后若从空索引开始 `add -A`，连 base 中被跟踪而匹配忽略规则的文件也会从快照中消失。L211 只为 `full` 写了 `read-tree <baseCommit>`。
- **为什么是次要**：不丢数据，文件仍在卫星中。但验收闸口会出现没有来源的不一致，后续去向取决于实现者自选；而且正文的两处断言照字面不成立。
- **文档位置**：`10` L183、L211、L740、L745–L746；`07` L281、L285；`16` §16.2.6。
- **期望的回答形态**：在 `10` §10.7.1 第 1 步（唯一定义）二选一：
  - **忽略规则不追溯**：`full` 与重置后的影子索引都以 “当前 pin（或最近检查点）的树” 初始化，而不是 `baseCommit`。这与 git 自身 “已跟踪的文件不因加入忽略规则而消失” 一致；`10` L183 的那句改为 “不会**新**进入”；
  - **忽略规则追溯**：`add -A` 之前对 “不在 `baseCommit` 中、当前匹配忽略规则” 的索引条目先 `--force-remove`，并写明由此产生的删除按谁归属（例如按引起忽略变化的一方：`.gitignore` 的改动随回合归 Agent；`info/exclude` 的刷新按 `safety` 检查点记 `mixedPaths`）。
  - 两种取法都要把 “清空影子索引” 之后的初始化写成同一规则，并修正 `10` L746、`07` L285 的断言。
