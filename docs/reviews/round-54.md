**全范围扫描找到此前各轮没有覆盖的问题，集中在四类地方**：
- **交还第 5 步的短路越过了第 6 步对外部写入的处置**：人没有改动、但接管期间有来源不明的写入时，外部写入会进入 `author:"human"` 的检查点；选 `take_human` 时 `external_change` 还会被解除。这违反 `10` L902“任何选项都不会把外部写入记为人的改动”（R54-D13-01，**重要**）。
- **卫星重建中的 `restoreCheckpoint` 第 0 步**：它会对刚检出 base 的卫星做一个 safety 检查点，打断检查点链，影响归因基线、交还归因与崩溃后的重建来源（R54-D13-02）。
- **自主度的几处派生效果**：
  - web 允许的范围缩小会被计划编译撤销；`testPathOverrides.add` 会经分类器顺序改变范围外路径的动作类（R54-D11-01）；
  - S0 授权“至合同修订”的失效没有落点（R54-D11-02）；
  - 运行时授权与 `forbid`、单向门的关系，以及撤销路径，都没有定义（R54-D11-03）。
- **Pi 与可靠性**：OAuth 刷新失败在网络或超时原因下会被 Pi 重试（R54-D5-01）；自动重建在 `rename` 之后崩溃会让 Goal 永久卡在“正在重建”（R54-D6-01）。

每一条都回到正文核对过，不是推测。

### D11 安全与自主度

**R54-D11-01｜次要**（封闭表的两处派生效果：web 允许的范围缩小会被计划编译撤销；`testPathOverrides.add` 会经分类器顺序改变范围外路径的动作类）

- **问题**：
  - **范围与计划编译**：
    - `16` L1002 允许 web 缩小 `scope.include`，L1006 规定 `scope.includeOrigin` 的任何改动仅本机，L1014 允许 web 把计划步骤设为 `needsDecision:true`。

    - 正文没有写明三件事：
      - 人编辑 `include` 时 `includeOrigin` 是否变为 `explicit`。若变，web 的每次缩小都会因 `includeOrigin` 仅本机而被拒绝，web 允许的方向形同虚设；若不变，下一次触发编译的修订就会把范围重置为 `∪touches`。
      - 一次只改步骤标题或 `needsDecision` 的修订是否算“批准计划”。
      - 判别原则（L986）比较的是提交的字段差异，还是编译后的合同。
    - 按“比较提交差异、`includeOrigin` 不变”这一字面读法，两次各自合规的 web 修订（先缩小 `include`，再设 `needsDecision:true`）合起来会把范围放宽到上一版之外，违反 L986 的“放宽……范围的改动都属放宽”。
  - **`testPathOverrides.add` 与分类器顺序**：
    - `16` L1038 允许 web 新增 `testPathOverrides.add` 条目。
    - 文件类分类（`11` L147–149）先判 `isTestPath`，再判范围：范围外但在测试路径集合中的路径被归为 `edit.tests`，而不是 `edit.out_of_scope`。

    - 这也与 `02` L311、`11` L212 的“同一路径命中多条规则时取最严格者”不一致。
- **为什么是次要**：属于 M2 `serve`，S2 沙箱仍然生效，放宽的上限是本机曾批准过的计划范围或 `allowTestEdits` 级别。但这两处都让封闭表自身的判别原则在派生层面失效，实现会分歧。
- **文档位置**：`16` L986、L1002、L1006、L1014、L1038；`02` L299–301、L311、L350–352；`04` L1125；`11` L147–149、L212。
- **期望的回答形态**：
  - 写明人编辑 `include` 时 `includeOrigin` 的去向（建议一律变为 `explicit`，并把“web 缩小 `include` 同时把 `includeOrigin` 置为 `explicit`”列为 web 允许的唯一联动）；写明判别原则以**编译后的合同**与上一版比较。

**R54-D11-02｜次要**（S0 执行授权的“至合同修订 / 测试构建配置改变”失效没有写入点；`16` L941 与 `11` 相反）

- **问题**：
  - `11` L106 与 `05` L968 规定，S0 执行授权“有效期至合同修订、或 `scope.protected` 中的测试/构建配置改变为止”。`06` L858 也以它存在为前提（“不使 S0 授权的‘至合同修订’到期”）。
  - 但没有任何一处写这次失效：
    - `contract.amend` 的效果（`06` L867）清除 `until_amend` 静默、重算三要素，不改 `s0_grant`；
    - `s0_grant_expires_on`（`06` L479，`02` L185）只取 `run_end`/`next_run_start`；
    - “测试/构建配置改变”由谁、在什么时点检测，也没有定义。
  - 表示也不一致：
    - `16` L253 说 S0 授权“是 `Grant{class: exec.test|exec.build}`，决定为 `grant_s0_exec`”；
    - 而 `02` L322–327 的 `Grant`（ADR-180 唯一定义）只存于 `approve_action` 决定的 `payload.grant`，且“只在本机批准时产生”。S0 授权却可以远程批准（`16` L941），实际由 `Goal.s0Grant` 状态表示（`02` L184）。
  - `16` L941 写远程批准的 `s0.grant` “不取 `11` §11.2 的‘至合同修订’”。`11` L106、L580 与 `16` L33 都写“取先到者”。
- **违反的不变式**：`11` §11.2：在无沙箱下运行 Agent 写的代码，其同意在合同或测试/构建配置改变后失效，需要重新同意。
- **为什么是次要**：只在 S0（SP6 未通过的 macOS）下相关，S0 下的其他告知仍在。但照 `06` 的命令表与 `16` L941 实现，同意会在合同修订后继续有效，Agent 写的代码继续以用户权限运行。这一类后果正是这条规则要防的。
- **文档位置**：`02` L184–185、L322–327；`05` L966–968；`06` L479、L858、L867；`11` L106、L580；`16` L33、L253、L941。
- **期望的回答形态**：
  - 在 `contract.amend` 的效果中写明“`s0_grant = granted` 时回到 `none`、清除 `s0_grant_expires_on`，同一事务”。定义“测试/构建配置改变”的检测点（例如每个检查点比较 `scope.protected` 中测试/构建配置路径的树哈希）。

**R54-D11-03｜次要**（运行时授权与 `forbid`、单向门、合同收紧的关系没有定义，项目级授权没有撤销路径）

- **问题**：
  - `11` L226 的 `applyGrants(m.levels[k], k, c.subjects, g)` 在任何文档中都没有定义：授权能否越过合同的 `forbid`？能否越过之后的合同收紧或自适应自主度的自动降级（`11` L304）？
  - “本项目内同类”授权（`02` L322–327，30 天）在每个 Run 开始时编入该项目**所有** Goal 的 `policy.json`。其中可能有合同把该类设为 `forbid` 的 Goal，例如 `生产热修` 的 `dep.add`、`edit.out_of_scope`。web 允许的“`autonomy.levels` 收紧”（`16` L1009）也可能被已有的项目级授权抵消。
  - 单向门：`11` L115–116 与 `16` L233 写单向门不能形成 Goal/项目级授权；`11` L298 与 `09` L423 写“单向门最高只能到 `ask` + 项目级授权”。
  - 撤销：运行时授权存于不可变决定的 `payload`（`06` L626–643 的触发器禁止更新与删除）；`autonomy.revoke`（`06` L931）的参数是 `{projectId, class, level}`，改的是级别，不撤销某条授权。人发现某条 30 天的项目级授权不妥时，没有收回它的路径。`02` §2.7 的 `HumanDecision` 类型也没有 `grant` 键（只有 DDL 有 `payload` 列）。
- **为什么是次要**：运行时授权只在本机由人选择。但授权的作用范围跨越 Goal 与合同；照字面实现时，有人会让授权一律降为 `silent`，有人会让它止于 `ask`，结果是同一项目中一个 Goal 的批准可能放宽另一个 Goal 合同明确禁止的动作。
- **文档位置**：`02` L322–327、§2.7；`06` L626–643、L931；`09` L423；`11` L113–118、L226、L298、L304；`16` L233、L254、L1009。
- **期望的回答形态**：
  - 在 `11` §11.3.5 定义 `applyGrants`：授权只能把 `ask` 降到 `notify`/`silent`，不越过 `forbid`，也不越过硬底线与单向门下限；项目级授权不作用于合同把该类设为 `forbid` 的 Goal。
  - `11` L298 与 `09` L423 改为“单向门最高只能到 `ask`，不能形成授权”。
  - 增加撤销：例如 `autonomy.revoke_grant{grantedBy}` 记一条决定，编译 `policy.json` 时排除被撤销的授权；或者写明不提供撤销的理由。`02` §2.7 补 `grant?: Grant` 键。

### D5 Agent 架构与 Pi 集成

**R54-D5-01｜次要**（OAuth 刷新失败在原因含网络、超时字样时会被 Pi 重试；压缩路径中的刷新失败不产生 F7 的检测键）

- **问题**：
  - D58（`05` L1362）、F7（`06` L1171）与 ADR-180 都写：刷新失败的错误消息“不匹配可重试模式”“Pi 不重试”。
  - v1.2.0 源码：
    - `ModelsError` 把原因拼进 `message`（`ai/src/utils/models-error.ts:9-20`，`${message}: ${detail}`），所以 `errorMessage` 是 `OAuth refresh failed for <provider>: <原因文本>`。
    - 可重试判定（`retry.ts:3-5`）是不加锚点、不区分大小写的正则，含 `fetch failed`、`timeout`、`timed? out`、`terminated`、`ENOTFOUND`、`5xx`、`429` 等（`:30-75`）。
    - 网络不可用时原因含 `fetch failed`；刷新超时（`resolve.ts:140` 的 15 s `AbortSignal.timeout`）时原因含 `timeout`。这两种情况下 `isRetryableAssistantError` 返回真，`_isRetryableError`（`agent-session.ts:3734-3737`）让 Pi 按 `maxRetries: 3`（`settings-defaults.ts:19`）重试，先发出 `auto_retry_start`/`end`，也就是 F6 的检测键 `retry.*`。
  - 这正是 F7 自己承认“不区分刷新令牌失效与网络不可用”的那一类。最终失败的消息仍以 F7 的前缀开头，所以检测键本身可用。但若实现者在第一条失败消息上就生成 F7，就会与仍在进行的 Pi 重试并存：重试成功后留下一张陈旧的“去登录”卡片；或者 F6 先按 `retry.*` 开始根因合并。
  - 另外，压缩与摘要请求经 `_getRequiredRequestAuth`（`agent-session.ts:532-569`）取认证，刷新失败在这里直接抛出，不成为 assistant 消息。F7 的检测键 ① 覆盖不到它，它会以 `compaction.end{error}` 出现；同一函数中还有一支实际可达的 “Run '/login …'” 文本（`:561-566`）。
- **为什么是次要**：认证过期是必然会走到的路径。检测键成立，但关于重试的断言写进了“v1.2.0 直接核实”的 D58 与 C39 的期望，照它实现 F6/F7 的时序会分歧。
- **文档位置**：`05` L1362（D58）、L1411（C39）；`06` L1170–1171（F6、F7）；`15` ADR-180 R53-D5-01。
- **期望的回答形态**：
  - D58、F7 改为：原因文本含网络或超时字样时 Pi 会重试，F7 只在 `agent.end`（`willRetry:false`）的最终错误上判定；F6 对 `errorMessage` 以 `OAuth refresh failed for` 开头的 `retry.*` 不开始根因合并。
  - C39(c) 增加一组“刷新以网络错误失败”，断言 Pi 重试、最终仍按 F7 归类。
  - F7 补压缩路径：`compaction.end` 的 `error` 以同一前缀开头时同样按 F7 处理（或写明不处理的理由）。

### D6 系统架构与可靠性

**R54-D6-01｜次要**（自动重建在 `rename` 之后、提交之前崩溃，重启后无规则处理，`satellite_rebuilding=1` 永久保留）

- **问题**：
  - ADR-181 为**人选的**重建补了这一窗口（`06` L140：已存在的卫星移入旁路目录后，按 `checkpointN` 续做）。**自动**重建没有对应规则：
    - `06` L139 只在“卫星的工作目录或 `_gitdirs/<goalId>` 不存在”时触发。自动重建已原子 `rename` 到位、提交事务未完成时，目录存在，本行不触发。
    - L140 要求“最近一条 `human.decision{rebuild_satellite}` 晚于本次进入 `satellite_missing`”，自动重建没有这条决定，本行也不适用。
    - 结果是 `satellite_rebuilding=1` 永久保留，`satellite.recovered` 永远不会记录。该标志使 `goal.resume`、`take_over`、`hand_back`、`discard_human_edits` 返回 `E_STATE`，`goal.rebuild_satellite` 返回 `E_BUSY`（`06` L870、L892–895、L921）。Goal 只剩“放弃”一个出口；在 `running` 中丢失的，还同时停在 `paused(satellite_missing)`。
  - 相邻的窗口：`06` L921 写明 `running` 中丢失时，`satellite_missing` 在自动重建开始**之前**就已写入。没有任何一处要求它与 `satellite_rebuilding=1` 在同一事务中写入。两者之间崩溃时，重启后 ADR-181 的新规则（L139：“已带 `satellite_missing` 且 `satellite_rebuilding=0` 的 Goal 不触发本行”）会把它当作“之前的重建已失败”，不再自动重建。而失败的 Needs-You 只在重建失败时生成（L139 末尾），此时并不存在，“保持打开”的前提不成立。
- **为什么是次要**：崩溃窗口窄，内容在影子中。但第一种情形照文实现会卡死 Goal，人只能放弃，这是 ADR-181 刚为手动路径关闭的同一类问题。
- **文档位置**：`06` L139、L140、L870、L892–895、L921；`10` L1174。
- **期望的回答形态**：
  - 在 `06` §6.1.6 增加一行（或扩大 L140）：`satellite_rebuilding=1` 而没有对应的人选决定时，按自动重建处理，已存在的卫星同样先移入旁路目录，再从最新的检查点或 pin 续做。
  - 写明 `running` 中丢失时 `satellite_missing`、继续目标与 `satellite_rebuilding=1` 在同一事务写入；或者把 L139 的豁免条件改为“已带 `satellite_missing`、`satellite_rebuilding=0` **且**已有失败的 Needs-You”。

### D7 诚实与验证

**R54-D7-01｜次要**（链接检查器对“重定向到允许范围外的主机”与“超过 3 跳”的结论未定义）

- **问题**：
  - ADR-181 的地址规则（`07` L922）写：“不自动跟随重定向：每一跳的目标按同一规则检查通过**且主机在 `network` 允许范围内**才请求，跳数上限 3。被拒绝的链接既不算可达也不算失败……该检查为 `skipped`（`address_refused`）”。
  - 但“被拒绝”只明确指地址规则命中的情形。以下两种情形是记为 `address_refused`（`skipped`，有保留的通过），还是记为不可达（失败），没有写：
    - 重定向到公网上、但不在 `network` 允许范围内的主机；
    - 超过 3 跳。
  - `checkLinks`（`07` L910）也没有返回这两类结果。
- **为什么是次要**：属于验证结论。同一份文档在两种实现中一个是“失败、触发返工”，一个是“有保留的已验证”，属于实现会分歧的结论差异。
- **文档位置**：`07` L910、L917、L922；`11` T34。
- **期望的回答形态**：二选一并写进 `07` §7.4.9：允许范围外的重定向目标与超出跳数都按“被拒绝”计（`skipped`，`detail` 分别为 `redirect_outside_network` 与 `too_many_redirects`）；或者都按不可达计（失败），并说明理由。

### D8 注意力与交互

**R54-D8-01｜次要**（`X`（`needs_you.dismiss`）对阻塞类条目的效果没有定义）

- **是否还有可追问的问题：有。** 新增共 **13** 条：阻断 0、**重要 1**、次要 12。
  - **第 53 轮核验**：16 条中已解决 12、部分 4（R53-D13-01、R53-D5-01、R53-D9-01、R53-D12-01），未解决 0。第 52 轮三条“部分”全部关闭。ADR-181 的 15 条观察中已解决 14、部分 1（`06` L917 的重新 seal 判定）。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 181，(v) 96 条命令，(e) 151 对，(r′) 32 对，(p) 10 格，(P) 8 格，(i) 31 个名称，(D) 46 个短语，(o) 8 行）；
    - Pi v1.2.0 复核约 35 条，被源码否定的只有“OAuth 刷新失败不重试”一条断言；
    - 排期结论成立：WBS 122.16；各线 26.28 / 26.35 / 27.64 / 28.42 / 13.47；余量 0.53 / 0.12 / 0.58 / 1.04 / 0.46；依赖链 19.7；增人 128.00、T 23.64、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    - **倒计时表**（`08` L442–448）的五种情形不含 `stalled` 的默认暂停（`07` L1347、`16` L590：`use_defaults` 下 1800 s 后暂停），`08` §8.8 的 `stalled` 行也没有 `timeout` 一类；反过来，`verify_failed` 行有“超时 → `timeout`”，却没有任何计时。照现有文案，实现者大概会写“30 分钟后 → 暂停”。
    - **`reverted` 标记**：`16` L52 “只在 Goal 不处于 `integrated` 时显示”且从不清除。撤销后又经返工、再次合入并归档的 Goal，在归档中仍显示 `reverted`；`04`、`12` 也没有规定它的字形与位置。连续两次撤销后，`integrationRevertedSeal` 只记最后一次，第一次被撤销的 seal 不再被忽略。若合入观测按状态（而非按变化）触发，`accepted` 的 Goal 可能按 `10` L1108 (ii) 被降回 `in_review`。
    - **`prepareTimeoutSec`**（`16` L1029）：web 允许“任何方向”，而判别原则把“使原本执行的检查不再执行”列为放宽。降低时限会使检查以 `verify_env_error` 告终，不会通过，只影响可用性；可在该行注明它为什么不属判别原则所指的情形。
    - **规则 5 的措辞与 lint**：规则 5 要求每个副本列写明“规则 5”，gitconfig、Rust、uv、pip 各行没有写，(p)/(P) 以两个关键词放行。gitconfig 行（`16` L1184）是“凭据判定命中即剔除”，没有“先剥除 userinfo”一步。白名单中几乎没有 URL 值，两种顺序的结果只在少数 `alias.*` 上不同。`16` §16.8.3 的 uv/Poetry 草案在槽位内 `sync`，与“V 绝不执行 install”不符（M2 草案）。
    - **`SessionManager.open` 的副作用**：v1.2.0 中打开源会话文件时，若末尾没有换行会追加一个，0 字节文件会被写入头部（`session-manager.ts:665`、`:1035-1045`）。“分叉为新 Goal”在源 Goal 的 Host 仍在写同一文件时打开它，可能与写入交错；建议写明分叉前源 Run 空闲（与回退的前提相同）。
    - **`goal.discard_human_edits` 与接管期间的修订**：`16` L43 写“→ 回到 `takeoverFrom`”，但接管期间若修订了标准，继续目标已被改写为 `verify{pin}`。实际去向由 `onAllReasonsCleared()` 决定（`10` L952 写的正是这一机制），`16` 的简写可改为引用它。
    - **卡片上的问题标题**：`04` L233 说 `waiting_human` 下的问题标题是说法、以 `┆` 标出；`12` L378 的实况行定义与 `04` 各线框都写作 `◆ 等你 · 问题 · …`，没有 `┆`。
    - **图例中的 `■`**：`04` L22 写“异常 / 验证器失败 / 已拒绝”，`12` L335 只写“异常与阻断哨兵”；验证器失败的字形是 `✕`/`▫`。
    - **调研类 Goal 出现在 M1 线框中**：G-0145（`04` L168 等）是调研类，按 `14` L189 不在 M1，线框没有标注。
    - **`09` 的两处里程碑**：`09` L21 把“过期复审”列为 M1，而复审批次经站会摘要投递（`09` L162），站会摘要属 M2（`16` L667）。`09` L480 的“证据摘录 ≤ 64 KB 永久保留”与 `07` L474–486 的重放包上限（每条标准 ≤ 2 MB）口径不同。
    - **试运行结果的标签**：`04` L1096 只定义了通过与失败；base 上的 `vacuous`、`timeout`、`unparseable` 显示为什么、是否算红灯，没有写。
- **设计是否完成：主干已收敛。剩下的是步骤之间的控制流边角、几处派生效果，以及唯一定义改动后的复述残留。**
