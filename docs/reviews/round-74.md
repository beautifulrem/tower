**ADR-201 的主干成立**：
- **不加载的机制**：
  - SDK 下 `resolveProjectTrust` 返回假，经 `setProjectTrusted(false)` 使项目设置为 `{}`。项目扩展、技能、提示、主题，以及祖先目录的 `.agents/skills`、`SYSTEM.md`/`APPEND_SYSTEM.md`、`.pi/mcp.json` 都不收集。
  - 判定之前的引导加载本就强制不信任（`resource-loader.ts:505-511`），不会先执行项目代码。
  - RPC 下 `--no-approve` 优先于扩展的 `project_trust` 与 `trust.json`。
  - “连 base 版本也不加载” 是 Pi 一次判定整个项目的直接结果，正文如实写明。
- **不误伤 base 中未改动的配置**：路径未改动时复核为信任，Pi 从卫星加载与 base 相同的内容。Pi 自己写入的安装根（`.pi/npm`、`.pi/git`）自带 `*` 的 `.gitignore`，不进入快照，因此 Pi 自己安装项目包不会让下一个 Run 变成不信任。
- **每个 Run 启动时求值**：`cmd:start(RunSpec)` 每次都以 `resolveProjectTrust` 新建 services（`05` L256–L262），Host 在 5 分钟内复用时也成立。M1 的 SDK 拒绝 `ctx.reload()`（`05` L390），Run 中途不会重新加载；RPC 的重载属 M2，ADR-201 已列为推迟项。
- **事后检测交给验证时的哨兵**：
  - 运行中只在检查点事务使 S0 授权失效，与 §11.2 失效条件 (ii) 一致。
  - `protected_path` 在 `07` §7.6.1 由 base..pin 推导；未经批准的写入为 severity 3，阻止进入 `in_review`。
  - 卡片写 “改动已发生”，停止条件卡片的 “该改动没有发生” 只用于执行前的拒绝，两处不再冲突。
  - `07` §7.6 段首 “默认 L-b 与 L-c 两层运行”，被 `16` L163 与 `07` L1485 的 “pin” 列作为特别说明覆盖，不矛盾。
- **`tower_data` 按种类判定**（`16` L174）：
  - 判定顺序不变。`user_checkout` 与 `<wtRoot>` 互不包含，不会抢先命中。
  - 本 Goal 自己的允许项不会被拒绝。
  - 判例覆盖默认位置。
- **drain 进行中卫星丢失**（`06` L139）：先按 L146 结束 drain，再按叠加态重建。四种目标的结果都有定义；`CHECK`（`draining_for` 只在 `running`，`external_change` 的双向约束）成立；人的暂停保留。G35e(n) 覆盖运行时与重启两条路径。

**全范围扫描新发现 1 条：重要 1、次要 0。**

### D11 安全与自主度

**R74-D11-01｜重要**（信任复核只比较 `.pi`、`.agents`，而 Pi 在信任下于宿主中、在沙箱外执行的代码，可以来自卫星中 Agent 在 S2 下可写、默认也不受保护的其他路径。跨 Run 的沙箱外执行因此没有被挡住）

- **问题**：
  - **正文的不变式**：
    - `11` L563：`trusted` 当且仅当 `Project.trust == trusted`，且卫星中 `.pi`、`.agents` 相对 baseCommit 无变化，且祖先目录检查通过。
    - 末句的理由：Agent 在 Run 1 写入的扩展若在 Run 2 以信任加载，“将在宿主进程中以用户权限运行、完全绕过 S2 沙箱”。
    - T4（`11` L647）因 “默认 protected；S2 写拒绝；每个 Run 复核信任” 把这一威胁评为 **低**。
    - `00` L67、L104 对用户承诺：仓库内 `.pi/` 资源只在未被修改时加载。
    - 这些缓解措施都隐含一个前提：信任下会执行的代码全部位于 `.pi/**`、`.agents/**`。前者在 S2 下写拒绝（`11` L350），并且默认受保护（`02` L307）。
  - **Pi v1.2.0 的实际范围**：项目受信任时，会在宿主中或作为其子进程执行的代码还包括以下三类，都不在 `.pi`、`.agents` 之内：
    1. **项目设置引用的本地扩展与包**：
       - 项目 `settings.json` 的 `extensions`、`packages` 等条目以 `.pi` 为基准解析（`package-manager.ts:945-961`、`:1302-1305`）；
       - Pi 文档写明支持相对路径、绝对路径与 `~`（`docs/settings.md:149`），本地包 “从解析出的路径加载，不复制”（`docs/packages.md:36,40`）；
       - 因此 base 中未改动的 `.pi/settings.json` 可以指向仓库中 `.pi` 之外的目录。
    2. **项目 `mcp.json` 启动的服务器**：
       - 受信任时读取 `<cwd>/.pi/mcp.json`（`mcp/config.ts:145-149`）；
       - stdio 服务器以用户权限、在 S2 之外运行（`11` §11.8.2）；
       - 它的命令行常常运行仓库中的脚本。`mcp.json` 本身未改动，脚本可以已被改动。
    3. **未改动的项目扩展所导入的模块**：
       - 扩展经 jiti 按常规模块解析加载（`extensions/loader.ts:567-581`），可以导入仓库中 `.pi` 之外的文件；
       - 导入的第三方包按 Node 的规则向上解析，可能落到卫星的依赖目录中。
  - **Agent 能否写这些路径**：
    - 能。上面三类目标都在卫星工作区中，S2 写允许覆盖整个卫星工作区；
    - 写拒绝只针对 `.git` 名字与 `.pi/**`、`.agents/**`、`AGENTS*.md`、`CLAUDE.md`（`11` L350）；
    - 默认 `protected` 不含这些路径（`02` L307），bash 的写入也只在事后检测中按 `protected` 判断（`11` L289）；
    - 依赖目录被 git 忽略，不进入检查点与 pin（`07` L297），验证时的 `scope_breach` 看不到它。
  - **另一处只在 S0 下存在的缺口**：
    - 快照不含被忽略的文件。Pi 的自动发现只读取被扫描目录**之内**的忽略文件（`package-manager.ts:267-285`、`:599-611`）；
    - 因此 `.pi` 或 `.agents` 之下、被其外部的忽略规则忽略的新文件，git 快照看不到，Pi 却会加载。项目包的安装根 `.pi/npm`、`.pi/git` 也是这样：自带忽略规则，内容在信任下执行；
    - S2 下 `.pi/**` 写拒绝，这一缺口关闭。S0 下没有关闭，而祖先目录检查一句写明它 “主要防护 S0”，说明 S0 在设计的考虑之内。
  - **照字面实现**：Tower 只对 `.pi`、`.agents` 求差异。同一 Goal 的下一个 Run 复核为信任，Pi 于是在宿主中加载 Agent 上一个 Run 改动过的代码，或以 MCP 子进程运行它。
    - 静态清单确认（`05` L1316、`11` L574）也挡不住：它只列 “受信任项目的 `.pi/extensions/`”；MCP 只对命令行与可执行文件求哈希，不对脚本参数求哈希。
    - 验证时这些改动可能不受保护（第 1、2 类），也可能根本不在 pin 中（第 3 类中的依赖目录），人在评审中未必看到。
  - **相关的未写明之处**：
    - 受信任项目设置中的 `packages`（npm/git）缺失时，Pi 在宿主中自动安装（`resource-loader.ts:529` 调用 `resolve()` 不带 `onMissing`，`package-manager.ts:1308-1312`），安装目标在 Agent 可写的卫星之内。
    - 这与人批准项目信任时看到的 base 声明一致，本身不越界。但信任提示（`11` L562）没有列出 “项目包会在启动时被安装并执行”。
- **所放进的后果类别**：
  - 提示注入或越权的 Agent 可以把代码留在一个 Agent 可写、不受保护的位置，它在同一 Goal 的后续 Run 中以用户权限、在沙箱之外执行。这是 T4/T16 防范的跨 Run 持久化与沙箱逃逸。
  - 前提只有两个：项目受信任，且 base 中的项目配置使用了上述常见写法（引用本地包、在 `mcp.json` 中运行仓库脚本、扩展导入仓库模块或第三方包）。都不需要人做任何额外的批准。
- **为什么是重要**：
  - 照正文实现会违反 `11` L563 末句与 T4、T16 写明的不变式；
  - `00` §0.5 对用户的承诺（`.pi/` 资源未被修改时才加载）在字面上成立，实际保护却落空；
  - 越界执行是用户权限下的任意代码，正落在安全边界最核心的一类。
- **文档位置**：`11` L558、L562–L563、L574（§11.8.2）、L289、L350、T4（L647）、T16（L659）；`05` L311、L479、L1256、L1316；`02` L93（`resourcesSeen`）、L307；`07` L297；`00` L67、L104；`15` ADR-004、ADR-201。
- **期望的回答形态**：在 `11` §11.8.1（唯一定义）先写出不变式：“在信任下由 Pi 于宿主中或作为其子进程执行的任何代码，都不得解析到 Agent 可写的位置，除非其内容已被证明等于人批准信任时的内容”。然后二选一：
  - **M1 取严格的一边**：
    - base 中项目配置含会执行代码的资源时，M1 一律以不信任启动。会执行代码的资源包括项目扩展、`packages`、`extensions` 条目，以及 `mcp.json` 中的 stdio 服务器。
    - Pi 一次判定整个项目，SDK 的 `extensionsOverride` 又在加载之后才过滤，无法只放行声明性资源。因此只含声明性资源（设置、技能、提示、主题、`SYSTEM.md`）的项目照常复核。
    - 在 `00` §0.5.1 登记这一差异，并在信任提示中说明。G46 补一组：受信任项目的 `.pi/mcp.json` 或项目扩展引用仓库中的代码时，任何 Run 都以不信任启动。
  - **或扩大比较范围，并如实登记残余**：
    - 批准信任时与每个 Run 启动时，按 Pi 的解析规则静态解析 base 项目设置中的本地路径、`mcp.json` 命令行中指向仓库的路径，把它们并入复核的路径集合（同时并入默认 `protected`）。仓库外的路径按祖先目录的做法记录哈希。
    - S0 下的比较须包括 `.pi`、`.agents` 之下被忽略的文件。
    - 扩展导入图（含依赖目录）这一残余无法静态封闭，须在 T4/T16 中如实提高评级，并写进信任提示。
    - G46 补对应的一组。

    2. **运行时卫星丢失时的 drain 结束**：
       - `06` L139 规定先按 drain 恢复行结束 drain。
       - 正常的 drain 结束会记录回合检查点，这时卫星已不在，无法记录；可用的最新检查点仍在影子中，重建从它开始，不丢数据。
       - 实现者自然会跳过这一步，建议写半句。
    3. **归档续做的范围**：`10` L442 写 “对卫星仍在或仍有待删分支的 `archived` Goal 续做”。按删除条件保留的分支（例如 “可能含你的提交”）也是 “未删除的分支”，每次重启都会重新判定一次。删除以 CAS 守卫，条件不满足时照旧保留，没有危害；建议写明 “重新判定” 是有意为之，或只续做尚未判定过的分支。
    4. **已结束 Run 的存活者**：`06` L145 起，重启时也终止已结束 Run 的存活者，并 “对所属 Goal 补 `agent_bg_done` 检查点”。这样的 Goal 若已不再有卫星（例如在宽限期后已归档），检查点无从记录。终止照常进行，跳过检查点不丢数据；建议写半句。

  - 信任复核按 “Pi 读取哪些配置文件” 划定比较范围，而安全不变式关心的是 “Pi 在信任下会执行哪些代码”。
  - 两者在常见的项目配置写法下并不相同。
  - 关闭它需要先在 `11` §11.8.1 写出以代码为单位的不变式，再选择 “M1 严格不加载” 或 “扩大范围并如实登记残余”。
- **下一轮建议**：
  1. **R74-D11-01**：写出信任下执行代码的不变式，二选一关闭，同步 T4/T16 的评级、`00` §0.5.1 与信任提示，G46 补一组。
  2. §5 的四条观察各补半句。

  **工时与排期**：约 0.02–0.1 人周，落在安全线或 Agent 线，不在依赖链上；预计 M1 仍可维持 38 周（2027-07-30）。
