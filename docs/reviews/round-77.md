## 1. 总评

**第 76 轮的 7 条与 §5 的 8 条观察都已在唯一定义处落地**，核对见 §3：
- 名字比较规则推广到全部 `protected` 模式与 `07` §7.6.3（`16` L287，`02` L308，`11` L150、L208，`07` L1249、L1273、L1275）；
- 祖先 `.agents/skills` 的记录与重新枚举删除，范围改为 “与用户在检出中运行 Pi 相同”（`11` L584）；
- `read.pi_resources` 补技能 `baseDir`（`16` L251，`11` L30）；

- `symlink_escape` 一行改为现行规则摘要（`16` L176）。
- lint 的 DELETED 与 (D) 各补一项，已正向核对。

**关于 “Run 的 cwd = 用户检出的仓库根” 这一前提（本轮重点 2）**：
- **M1 中成立**：
  - Project 的身份是整个仓库（规范根提交，`02` §2.3），`WorkspaceBinding` 没有子路径字段（`02` L228–L241）。
  - 卫星是整个仓库的克隆，`RunSpec.cwd` 是主 binding 的卫星根（`05` L83）。
  - 多仓库 Goal 属 M3（`14` L18、L464；`04` L144），其 cwd 为工作区目录，这一点已登记为 M3 待定（`10` L1185）。
  - monorepo 在 M1 中只表现为 `scope.include` 指向子包（`10` L1194），cwd 仍是仓库根。
- 因此 `contextFiles()`、`.agents/skills` 的范围与祖先差异的公式在 M1 中都成立。
- 前提的边界只有一处：“与用户自己运行 Pi 一致” 默认用户在仓库根运行 Pi。monorepo 用户若习惯在子包中运行 Pi，子包中的 `AGENTS.md` 与 `.agents/skills` 会被自己的 Pi 加载，Tower 的 Run 不加载。规则本身无歧义，但限制清单没有写，记为观察（§5 观察 2）。
- 真正受前提影响的是导出目标：ADR-204 把 “Pi 在 Run 的 cwd 实际加载的那个文件” 与 “`contextFiles(用户检出)` 中仓库根那一项” 写成同一个东西。前者在卫星（由 base 树检出）上求值，后者在用户检出（含未跟踪文件、可能在其他分支）上求值，两者并不总是相同（R77-D12-01）。

**其余三个探查点**：
- **合同中写的模式也折叠**：只会多报，不会漏报。`scope.include`/`exclude` 不折叠是有意的，写在 `16` L287：
  - 大小写不敏感卷上，只差大小写的路径可能在写入时算范围内、验证时（git 的路径）算越界；
  - 这在 ADR-204 之前就如此，验证会兜住，不破坏不变式。
  - 授权匹配器仍区分大小写，只会多问一次，方向安全。
- **以小写 `agents.md` 为导出目标**：“以磁盘上的实际名字写入” 与 Pi 在本机的加载一致；大小写敏感的系统上 Pi 不加载 `agents.md`，那是仓库自身的约定，不归 Tower 管。不构成问题。
- **`--no-renames`**：两种复核都已改用。改名为上下文文件或受保护名字的条目以 `A` 出现，改名移出的以 `D` 出现，两种都被筛出。成立。

**全范围扫描新发现 5 条：阻断 0，重要 0，次要 5。** 都已对照原文复核。
- **ADR-204 新文字带出的两处**：
  - 导出目标的两种求值方式不同，且导出的推荐路径（docs Goal）不在 M1（R77-D12-01）；
  - `engine_crash` 的唯一定义引入 “`autoResume` 为假”“自动恢复失败” 两个分支，正文没有给出它们何时成立；它们与启动时自动解除的关系也未定义（R77-D8-01）。
- **前几轮未发现的三处**：
  - 回退位置的祖先差异，`09` 与 `10` 在何时计算、比较什么、内容放到哪里三点上不一致。ADR-204 只统一了 “用同一个函数”（R77-D13-01）。
  - 三处文档建议把未跟踪的 `AGENTS.md` 加入 “本地文件” 清单，但清单的设计假定条目被 git 忽略，`add` 时不检查。未被忽略的条目播种后会进入检查点、pin 与 seal（R77-D13-02）。
  - `provider_unavailable` 暂停时实况行写 `◇`，而此时已有一条不可关闭的 `stalled{engine_error}` 条目，与 `12` 自己的字形规则矛盾（R77-D9-01）。

### D8 注意力与交互

**R77-D8-01｜次要**（`engine_crash` 唯一定义中的两个分支没有成立条件，与启动时自动解除的关系未定义）

- **问题**：
  - **`08` L386（唯一定义）**：自动 “重启并恢复” 进行期间不生成条目；“自动恢复不进行（10 分钟内重复崩溃、`autoResume` 为假）或失败时” 才生成 `stalled{unresponsive|crashed}`（L3）；“恢复成功则不生成，因此不存在要随自动恢复关闭的条目”。
  - **“`autoResume` 为假” 没有来源**：
    - `06` L64 进入 `engine_crash` 时一律写 `autoResume:true`；
    - `06` L148 只写 “`autoResume` 按原因决定”；
    - 正文没有一处在 `engine_crash` 上写 `autoResume:false`。
    - 实现者可能把 “第二次崩溃起改为等待人工处理”（`06` L64）实现为写 `autoResume:false`，也可能保持 `true` 只是不再自动重启。
  - **“自动恢复失败” 没有判定点**：
    - 自动恢复是解除 `engine_crash` 后再开 Run。按 `06` L298，这必须经过准入闸口，也就是准备阶段。
    - 准备阶段中，Host 握手失败或超时是 `prepare_failed`，有自己的 `stalled{prepare_failed}`（`03` L97，`06` L1180 F4b；`08` L209 写明它 “不是 `engine_crash`”）。`ensureSatellite` 失败归 `satellite_missing`（`06` L1190 F14）。
    - 所以 “失败” 要么已由别的原因与条目表达，要么只剩 “恢复后的 Run 在 10 分钟内再次崩溃”，而后者已是 “不进行” 分支。
    - 照字面实现，有人会在重启失败时再生成一条 `stalled{crashed}`，与 `stalled{prepare_failed}` 并存；此时 `engine_crash` 已不在暂停原因中，这条条目没有可以解除的原因。
  - **与启动时自动解除的关系**：
    - `06` L101：`resumeOnLaunch` 打开（默认）时，`app_quit`/`engine_crash` 在启动时自动解除，没有例外。
    - 于是一个已 “等待人工处理”、带着 `stalled{crashed}` 的 Goal，在下次启动时会被自动重启，条目按 `08` L526 以 `obsolete` 关闭。
    - 若实现者按上一点把重复崩溃写成 `autoResume:false`，又可能认为启动时不该解除它。两种实现用户可见的行为不同（重复崩溃的 Goal 下次启动是否自动重启），正文没有裁决。
- **为什么是次要**：
  - ADR-204 刚把这里定为唯一定义，新加的两个分支却没有成立条件，实现会在 “是否生成条目”“是否自动重启” 上分化。
  - 危害有界：最坏是多一条 L3 打扰，或每次启动多一次崩溃。
- **文档位置**：`08` L386、L526；`06` L64、L101、L148、L298、L1179、L1180、L1190；`03` L96、L97；`12` L406、L430；`16` L195。
- **期望的回答形态**：在 `08` L386 或 `06` L64 补一句即可。
  - “`autoResume` 为假” 的含义：例如 “第二次崩溃时写 `autoResume:false`”，或删去这一分支；
  - “失败” 的含义：例如 “恢复出的 Run 在 10 分钟内再次崩溃”；重启前的失败按 `prepare_failed`/`satellite_missing` 处理，不另生成 `stalled{crashed}`；
  - `06` L101 的启动自动解除是否看 `autoResume`。

     - `10` L528：“把缺失的祖先上下文文件以 Tower 注入的形式（Trace 可见）补入简报”。
     - `05` L1297 与 `09` 一致（“在系统段中提示”）。`16` L508 登记的被取代说法只涉及导入哪些文件，没有涉及去向。
- **为什么是次要**：
  - 同一步骤，两份文档给出三处不同的规则。照 `10` 实现，人设置 `worktreeRoot` 后不再提示 “Agent 看到的上下文文件与你本地 Pi 不同”，文件变化也不重新提示。照 `10` 把内容放进简报，会占用 ADR-009 的常驻预算。
  - 只在非默认位置发生，不涉及沙箱。
- **文档位置**：`09` L460–L463；`10` L514、L516–L528；`05` L1297；`16` L508；`15` ADR-008、ADR-178。
- **期望的回答形态**：
  - `10` L525–L528 只保留 “回退时按 `09` §9.11 计算并处理祖先上下文差异”，何时计算、比较范围与去向都以 `09` 为唯一定义；
  - 或把 `09` 改为与 `10` 一致，并说明人设置 `worktreeRoot` 时为何不提示。

**R77-D13-02｜次要**（“本地文件” 清单假定条目被 git 忽略，但 `add` 不检查；三处文档建议把未跟踪的 `AGENTS.md` 加入清单）

- **问题**：
  - **清单的前提**：
    - “本地文件” 是 “被 git 忽略、但运行所需的文件”（`11` L355，`06` L890 `project.local_files.add`，`07` L516）。
    - `16` L702 的 `mark_secret` 一段直接依赖这一点：“该路径被 git 忽略，不改变指纹与 diff”。
    - 检查点与 pin 的树只排除 `.git` 与 gitlink，靠忽略规则挡住被忽略的文件（`10` L183、L737–L739）。播种的普通本地文件没有另外排除（`10` L371）。只有交还时排除机密本地文件（`10` L947）。
  - **`add` 不检查**：`06` L890 与 `16` L702 都没有要求加入时确认路径被忽略。
  - **文档的建议直接导向未被忽略的情形**：
    - `00` L89：“用户主检出中**未被 git 跟踪**的 `AGENTS.md`/`CLAUDE.md` 不在卫星中……需要时把它加入项目的‘本地文件’清单”；
    - `11` L349、`09` L463 同样建议。
    - “未跟踪” 包含 “未跟踪且未被忽略”。
  - **照字面实现的后果**：
    - 这样的文件经批准播种进卫星后不被忽略，第一个检查点就把它收进树中，在 base→pin 的差异中以新增出现。
    - 它是上下文文件，命中 `protected_path`（severity 3，阻止进入评审，`07` L1249），而 Agent 从未写过它。上下文文件复核也会每个 Run 报告它（`11` L598）。
    - 若人在评审中放行，它随 seal 进入用户仓库的分支，把一份个人文件带进仓库历史；集成回用户检出时又与那个未跟踪文件冲突。
    - 不是上下文文件的未忽略本地文件，同样会进入 seal。
- **为什么是次要**：
  - 一条设计前提（本地文件被 git 忽略）只是假定、没有检查，而文档自己的建议恰好违反它。实现者不会想到要补检查或排除，结果是阻断与误提交。
  - 人在评审中能看到这个文件，危害有界。
- **文档位置**：`00` L89；`11` L349、L355；`09` L463；`06` L890；`07` L516、L1249；`10` L183、L371、L737–L739、L947；`16` L702。
- **期望的回答形态**，二选一，一句即可：
  - `project.local_files.add` 要求路径在用户检出中被忽略（例如 `git check-ignore` 为真），否则提示 “先把它加入 `.git/info/exclude`”。三处建议同步写成 “加入 `info/exclude` 后再加入本地文件清单”（影子已复制 `info/exclude`，`10` L183）。
  - 或者影子在快照时排除全部已播种的本地文件路径，与交还时排除机密本地文件的做法相同。
