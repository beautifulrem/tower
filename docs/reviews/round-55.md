  - `06` 只引用 `10`。
- 第 53 轮带来的四条“部分”与 ADR-181 观察 2 都已关闭。
- 第 54 轮 §5 的 11 条观察都已落地。其中两条修复各自带出了新问题：
  - “每个 seal 只判定一次”，见 R55-D13-02；
  - 倒计时表新列的停滞默认暂停没有暂停原因，见 R55-D8-01。

**全范围扫描找到此前 54 轮都没有覆盖的问题，集中在五类地方**：
- **验证器的缓存路径（R55-D7-01，重要）**：
  - 正式验证（`claimed` 等）在 exec 标准全部命中缓存时，在取槽位之前就调用 `decide()`。
  - 验证时的 L-c 哨兵与测试清单只在取槽位之后运行，因此都被跳过。
  - 机会式验证照常写入可被缓存命中的 `criterion_check`。最常见的路径——机会式验证在 T 上通过、Agent 不再改动就提交——会让 `claimed` 的验证完全不做测试清单比对（R-T5，severity 3、阻断）就判为“已验证”。
- **接管期间从更早检查点重建卫星后的交还（R55-D13-01，重要）**：
  - `keep_both` 的不相交判定按 T0→T1，写回却按 B→T1（B = 重建所用的树）；
  - B→T0 路径上的外部写入会被覆盖，而且不在任何检查点中；
  - 第 8 步的 `human_edit` 检查点还会把 B→T0 的 Agent 工作记为人的改动。
- **ADR-182 的几处派生效果**：
  - 每个合同版本都执行计划编译，没有计划的快速路径合同会把 `scope.include` 编译为空集（R55-D4-01）；
  - “每个 seal 只判定一次”使临时条件下观测到的合入永远不再判定（R55-D13-02）；
  - 阻塞类条目规则漏掉 drain 窗口（R55-D8-01）；
  - `applyGrants` 的排除 (c) 没有时间顺序，运行时授权在 M1 没有列出与撤销的入口（R55-D11-02）。
- **进程与时序**：
  - 开场队列在 `run.started` 消费与经 `RunSpec` 先行投递两种写法矛盾（R55-D6-01）；
  - Host 中的扩展与 Supervisor 两个进程写同一影子索引与 `cp/<n>` 引用，没有跨进程互斥（R55-D6-02）。
- **其余**：
  - 合同字段 `repeat` 没有判定规则；`anyQualified` 少列多种保留条件（R55-D7-03）；
  - 可由被测代码输出触发的自动学习规则会去掉零分母保护（R55-D12-01）；
  - `G46` 中标为 M1 的组含 M2 的 `serve` 部分（R55-D14-01）；
  - 几处复述残留（R55-D15-01）。

每一条都回到正文核对过，不是推测。

### D13 隔离、git 与并发

**R55-D13-01｜重要**（接管期间从更早的检查点重建卫星后交还：`keep_both` 会覆盖外部写入，B→T0 的 Agent 工作被记为人的改动）

- **触发条件**：
  - 接管期间卫星丢失、自动重建失败后，人可以选择“从更早的检查点重建”（`goal.rebuild_satellite{checkpointN}`，`06` L921；守卫只要求 `satellite_missing`）。
  - 成功后 `humanCheckout.rebuiltTree` = 检查点 m 的树，记为 B ≠ T0。重建同时记录 B 的 `safety` 检查点（`10` L1180，ADR-182）。
- **问题**：
  - **(a) 外部写入被覆盖**：
    - 第 6 步 `keep_both`“只在 E 与人改动的路径（T0→T1）不相交时提供”（`10` L915）；
    - 第 7 步的写回集合却是 `git diff B T1`（L920），包含 B→T0 的全部路径（m 之后 Agent 的工作）；
    - 重建后有来源不明的写入落在某条 B→T0 路径 p 上、p 不在 T0→T1 中时，`keep_both` 会被提供，写回又用 T1 的版本覆盖 p；
    - 该外部内容不在任何检查点中：`keep_both` 不像 `take_human` 那样先做 safety 检查点（L909）；
    - 第 8 步的检查点仍对 p 记 `externalPaths`，`external_change` 也保留。之后 `keep` 会把 Agent 的内容当作“采纳为我的改动”，`revert` 把 p 恢复为基线版本，原外部内容再也找不回来。
  - **(b) 归因错误**：
    - 第 8 步的 `human_edit` 检查点紧接在 B 的 `safety` 检查点之后（L934）。评审单元按“最后改动该路径的检查点的作者”归因（`10` L730–733，`02` L548），所以 B→T0 的 Agent 工作全部成为 `author:"human"`。
    - 后果：seal 带 `Tower-Human-Edit`；`tower.handback` 把这些文件列为“人改过的、不得回退”；验证失败因人的改动不自动返工。
    - 这与同一步骤的“T0→T1 归因为 human”（L909）和 L409“交还（T0→T1 的路径）”相反。
- **违反的不变式**：
  - `10` L916：`keep_both` 时“外部写入保留 `external_change`，等待 keep / revert”；
  - L908：任何选项都不改变外部写入的归属；
  - L409：`Tower-Human-Edit` 只覆盖 T0→T1。
- **为什么是重要**：触发链较长（接管、卫星丢失、自动重建失败、人选更早的检查点）。但照文实现时，`keep_both` 会静默丢掉一份来源不明的内容（可能是人自己在 IDE 中的修改），没有任何检查点保存它，属于“丢失用户数据”一类。归因错误则让 Agent 的代码以人的名义进入 seal。
- **文档位置**：`02` L548；`06` L893、L921；`10` L409、L730–733、L905–922、L934、L1180。
- **期望的回答形态**：
  - `keep_both` 的不相交判定改为“E 与写回集合 B→T1 不相交”。或者在第 7 步写回之前，对 E 中的路径先做 `safety` 检查点（与 `take_human` 相同）。
  - 交还的归因只把 T0→T1 记为人。例如 `rebuiltTree ≠ T0` 时，先写回 B→T0 并记一个 `author:"agent"`、树为 T0 的检查点，再写回 T0→T1 并记 `human_edit`。或者 `human_edit` 检查点逐路径记作者。
  - G46(as) 补一组：接管期间从更早的检查点重建，重建后外部写一条 B→T0 路径，人改另一条路径，以 `keep_both` 交还。

**R55-D4-01｜次要**（每个合同版本都执行计划编译：没有计划或步骤没有 `touches` 时 `include` 被编译为空集；编译生成的停止条件与 web 允许的步骤标题修改冲突）

### D6 系统架构与可靠性

**R55-D6-01｜次要**（开场队列在 `run.started` 消费，又经 `RunSpec` 在它之前投递；`withdraw` 的承诺与崩溃语义因此不确定）

- **问题**：
  - **一种写法：在 `run.started` 消费**：
    - `05` L100：“队列在 run.started 事件的同一事务中被消费（之后撤回该 id 返回 `already_delivered`）”；
    - `06` L853：“任何 Run 开始……都在 `run.started` 事件的同一事务中按追加顺序消费并清空 `pending_openings`、组装开场”。
  - **另一种写法：在 `run.started` 之前投递**：
    - `RunSpec.opening` 是 `start()` 的输入（`05` L88）；
    - 启动时序图（`06` L331–339）先 `cmd:start(RunSpec)`，收到 `run.ready, agent.start …` 后才记 `run.started`；
    - 准备第 ③ 步“Host 握手与开场组装”在 `run.started` 之前，限时 120 s（`16` L23，`06` L1168 F4b）。
  - **两种实现各有一个洞**：
    - **按时序图实现**：第 ③ 步中，开场已组装进 `RunSpec`，队列尚未消费。`goal.openings.withdraw`（`06` L871，允许远程）此时仍成功，Agent 却会收到被撤回的条目，违反“撤回后 Agent 不会收到它”。崩溃于 `run.started` 之前则按准备阶段恢复、重新投递，同一会话中出现重复的开场。
    - **按“先消费再投递”实现**：提交之后、Pi 写入之前崩溃，开场丢失。`tower.*` 注入不经 `engine_outbox`（`06` L699 的 `op` 没有 `inject`），“Run 中崩溃”行的继续目标 `run` 面对的是空队列，只得到 `tower.resume`；人的回答、note 与 `tower.external_resolved` 都不再送达，`withdraw` 却报告 `already_delivered`。
- **为什么是次要**：内容在决定记录中，不丢失；窗口限于准备第 ③ 步与崩溃。但人撤回的条目仍被投递，或人的指示没有送达而界面称已发送，两种实现会分歧。
- **文档位置**：`05` L88、L100、L1412（C38）；`06` L126、L146、L331–339、L699、L853、L871、L1168；`16` L23。
- **期望的回答形态**：
  - 写明唯一的消费点。例如组装时在同一事务中把条目标为 `in_flight`：期间 `withdraw` 返回 `already_delivered`；准备失败或崩溃且 Pi 未确认时按原顺序放回；重启后按 `details.key` 对 JSONL 去重（推广 §5.6.5 ② 的做法）。
  - 或者让注入经 `engine_outbox`，按键对账。

**R55-D6-02｜次要**（Host 中的扩展与 Supervisor 两个进程写同一影子索引与 `cp/<n>` 引用，没有定义跨进程互斥）

- **问题**：
  - **Host 侧写影子**：
    - `05` L1016：`captureCheckpoint` 是共享模块 `@tower/checkpoint`，“GitService 也使用它”；
    - L1026–1031：扩展在 Host 中以 `node:child_process.execFile` 执行，只用进程内的 `cpQueue` 串行。
  - **Supervisor 侧也写同一影子**：
    - `10` L756：检查点“由 Supervisor 在影子上下文中异步执行……每个卫星 + 影子互斥”；
    - `06` L241：GitService 每个卫星一把锁；
    - Supervisor 自己写 pin、`agent_bg_done`、`safety`、`human_edit` 与重建检查点。两边都用 `GIT_INDEX_FILE=<SH>/index` 与 `update-ref refs/tower/<goalId>/cp/<n> C ""`（`10` L702、L710）。
  - **两者会并发**：
    - 机会式验证对 `running` 的 Goal 生成 pin（`06` L325）；
    - settle 时扩展只等 `cpQueue` 最长 5 s（`05` L1041），之后 Supervisor 即取 `agent_bg_done` 检查点与 pin。在单次检查点 0.3–1.5 s 以上的仓库（`10` L752–754）中，排队的 Host 检查点会与它并发。
  - **结果**：`index.lock` 冲突使一方失败；`cp/<n>` 编号冲突（CAS 失败）；较晚完成的 `tower.checkpoint` 落在 `agent.settled` 之后，与 L1041“一定排在 `agent.settled` 之前”相反。失败时检查点或 pin 怎样处理也没有定义。
- **为什么是次要**：git 的锁使冲突以失败告终，不会写坏影子；损失的是某个回合的检查点或一次 pin 的重试。但单一写者是 `06` 的基本原则，实现会分歧。
- **文档位置**：`05` L1016–1041；`06` L241、L325；`10` L702–711、L752–756。
- **期望的回答形态**：二选一并写进 `10` §10.7.2：
  - 扩展只发出请求，由 Supervisor 的 git worker 持 `wtLock` 执行；
  - 或者定义所有写者都取的 `<SH>` 跨进程文件锁与编号分配方式。
  - 同时写明 `cpQueue` 超过 5 s 时 settle 怎样处理。

### D11 安全与自主度

**R55-D11-01｜次要**（分类器在 `protected` 处截断，“取最严格者”只修了测试与范围外一对；`07` 与 `11` 对受保护路径的级别相反）

- **问题**：
  - `11` L146–150 的 `elif` 链先判 `match(scope.protected) → edit.protected`，命中后不再判测试路径与范围。ADR-182 只让“测试路径且范围外”同归两类。
  - **受保护且是测试路径**：快照 `**/__snapshots__/**`、`*.snap` 既在默认 `protected` 中，也在测试路径集合中。
    - 标准预设下 `edit.protected` 为 `ask`（`11` L81）。合同把 `allowTestEdits` 收紧为 `forbid` 后（web 允许），快照仍按 `edit.protected` 得到 `ask`：可以批准，也可以被授权降为 `notify`。
  - **受保护且在范围外**：合同逐格把 `edit.out_of_scope` 设为 `forbid` 而 `edit.protected` 为 `ask` 时，范围外的受保护路径仍是 `ask`。
  - **两处级别相反**：`07` L1208 写“`ScopeFence.protected` 与 `allowTestEdits` 同时作用时……protected 中的路径一律视作 `forbid`”，与 `11` §11.2 各预设中 `edit.protected` 为 `ask` 相反。
- **为什么是次要**：受保护路径仍至少为 `ask`，事后检测（`11` §11.4）照常；但“同一路径命中多条规则时取最严格者”（`02` L312、`11` L213）在这几种组合下不成立，两处级别也相反，实现会分歧。
- **文档位置**：`02` L312；`07` L1196–1208；`11` L80–82、L146–150、L213。
- **期望的回答形态**：
  - 文件类分类收集全部适用的类（`edit.protected`、`edit.tests`、`edit.out_of_scope`），`decide` 取最严格者。
  - `07` L1208 改为与 `11` 一致的说法：受保护的测试路径取 `edit.protected` 与 `allowTestEdits` 对应级别中较严者。

**R55-D11-02｜次要**（`applyGrants` 的三处边界：排除 (c) 没有时间顺序；多类审批的授权只记一类；M1 没有列出与撤销运行时授权的入口）

- **问题**：
  - **(c) 无时间顺序**：
    - 排除 (c) 写“本 Goal 的合同修订把该类收紧过的……该类的全部授权不作用于本 Goal”（`11` L244），理由却是“不被**此前的**授权抵消”。
    - 收紧之后，人在同一类的 `ask` 上选“本 Goal 内同类”，这条授权在当前 Run 中立即生效（`11` L263 `goalCtx().grants.push(d.grant)`），到下一个 Run 编译时又被静默排除，重新出现授权本来要消除的重复审批。
  - **多类审批**：
    - ADR-182 让范围外的测试路径同时归两类，bash 本来就有多类调用。`Grant` 只有一个 `class`（`02` L325），`applyGrants` 逐类判定（`11` L227）。
    - 一次多类 `ask` 的批准生成的授权只降其中一类，另一类仍为 `ask`，授权实际无效。实现会在“一类一条”“只取主类”“不提供授权选项”之间分歧。
  - **M1 无撤销入口**：
    - `autonomy.revoke` 省略 `level`（`06` L931）的唯一界面入口是 `11` L311 的“已获得的自主度”面板，它在 §11.5 自适应自主度之下（M3，默认关，`16` L1082，`04` L1278）。
    - `04` §4.16 设置页的“自主度预设”只列矩阵与 S0 授权记录。M1 能产生 30 天的项目级授权（`11` L116，W10），却看不到也收不回。这是 R54-D11-03 期望的撤销路径在 M1 界面上的缺口。
- **为什么是次要**：授权只把 `ask` 降到 `notify`，不越过 `forbid`。但三处都让授权的实际效果取决于实现者的选择。
- **文档位置**：`02` L323–330；`04` L1267、L1278；`06` L931；`11` L114–118、L227–244、L263、L311；`16` L1082。
- **期望的回答形态**：
  - (c) 只排除收紧之前产生的授权（与 (b) 的写法一致）；或者收紧过的类不再提供授权选项。
  - 写明多类 `ask` 的授权：例如为每个处于 `ask` 的类各生成一条同匹配器的授权，或者多类时只提供“仅这一次”。
  - M1 设置页“自主度预设”下增加“本项目仍有效的运行时授权”列表与撤销入口（不依赖自适应自主度面板）。

### D12 记忆与学习

**R55-D12-01｜次要**（自动关闭 reporter 注入的学习规则可由被测代码的输出触发，并去掉零分母保护）

- **问题**：
  - `09` L380：“注入导致 `Unknown option` 失败 1 次 → 对该 runner 关闭注入”，应用方式“自动（仅影响性能和信息量，不影响判定）”。
  - 判定条件是“退出码 ≠ 0 且输出含 `Unknown option`”（`07` L779），而输出来自验证槽位中运行的、Agent 写的测试代码。这条项目级、持久的学习规则因此可以由被测代码触发。
  - 关闭注入后结果为 `source="none"`，没有计数。`verdictOf` 的零分母（`vacuous`）、`minTests`、`maxFailures` 分支都依赖计数（`07` L790–794），只有合同写了 `minTests` 时才会得到 `unparseable`。之后“全部跳过”的运行可以在没有分母的情况下判为 `pass`。
  - 所以“不影响判定”不成立，它与 H10（`07` L33）及 `09` L387 的原则（“凡是可能让判定变宽松的调整都需要人批准”）相反。
- **违反的不变式**：`09` L387；`07` H10（零分母不算通过）。
- **为什么是次要**：多数运行器在零用例时本就以非零码退出，R-T2 也会标出新增的跳过；但这是一条无需人批准、可由被测代码触发、作用于整个项目的放宽，实现会分歧。
- **文档位置**：`07` L33、L775–797；`09` L380、L387。
- **期望的回答形态**：
  - 这条规则改为需批准；或者关闭注入后以正则兜底计数并标“计数为估计”，没有计数时按 `unparseable` 处理。
  - 写明触发判据只在 Tower 自己的探测运行（例如对 runner 的 `--help` 探测）中计算，不取被测代码的输出。

**R55-D12-02｜次要**（网络学习的建议目标与 ADR-178 相反；彻底清除的墓碑不在同步合并算法中）

- **问题**：
  - **网络学习**：`09` L381 建议“在标准中声明所需主机”。按 ADR-178，合同中没有可放行执行阶段网络的字段，唯一来源是 `VerifyProfile.env.network`，且只能在本机修改（`07` L748，`16` L1047）；artifact 标准的 `network` 只供链接检查器。照文实现的建议无处落地，或被误写进 artifact 的 `network`。
  - **墓碑（M2–M3）**：
    - 彻底清除写墓碑 `{"id", "purged": true}`（`09` L521），不带版本向量与签名；合并算法（L526–534）没有墓碑一支。
    - 另一台仍持有该条目的机器按“`vv(L)` 支配 → keep L、下次写出时覆盖远端”处理，执行清除的机器之后按 `!L → take R` 把它取回，被清除的记忆复活。
    - 同步目录为 git 仓库时，历史中仍保留原文（L517），清除界面没有说明。
- **违反的不变式**：`09` §9.12.4“删除全部版本”。
- **为什么是次要**：同步属 M2、可选；网络建议需人批准。但前者会让隐私清除在多机下失效，后者的建议对象不存在，实现会分歧。
- **文档位置**：`07` L748；`09` L381、L517–534、L545；`16` L1047。
- **期望的回答形态**：
  - L381 的建议改为“`VerifyProfile.env.network`（仅本机）或给测试加 mock”。
  - 墓碑带 HMAC 与支配性的版本向量，合并算法中墓碑优先；清除界面说明同步仓库历史中的副本。
