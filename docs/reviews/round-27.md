### D11 安全与自主度

**R27-D11-01｜重要**（从 base 的 `.lfsconfig` 提升为 `-c` 的键没有白名单，绕过了 git-lfs 自带的安全子集）

- **问题**：
  - **规则现状**：ADR-152 规定，Tower 读取 base 的 `.lfsconfig`，“算出有效端点与相关键，**全部**以命令行 `-c` 显式传给这条 `git lfs fetch`”。出处：`15` L1244，`10` L207–209，`06` L239，`16` L468。
  - **这条命令的特殊性**：它是加固清单的**唯一例外**（`10` L54）。它在 Agent 沙箱之外、以用户身份运行，用户的凭据配置照常生效，网络不限主机。例外的理由是“它不处理任何 Agent 可控的内容”。
  - **安全子集被绕过**：
    - git-lfs 自己读 `.lfsconfig` 时只接受一个固定的键子集，文档注明“restricted for security reasons”。原因是 `.lfsconfig` 是**仓库内容**，任何贡献者都能写。
    - 通过 `-c` 传入的值属于 git 配置，不受这一限制。git 与 git-lfs 及其子进程会照常使用这些值，包括 `16` L602 登记的“可执行或重定向的 git 配置键”一类。
    - 文档没有任何一处说“只提升 git-lfs 允许的键”。“相关键”没有定义，“全部”一词还会引导实现者把解析出的键原样传入。
  - **例外理由的前提被削弱**：
    - base 中的 `.lfsconfig` 不一定出自用户本人。它可能来自上游贡献者，也可能来自以前某个 Goal 中由 Agent 写入、经人验收并合入 base 的改动。文档没有把 `.lfsconfig` 列为受保护路径，评审中它也只是一个普通的小文件。
    - 因此“Agent 不能影响这条命令的任何输入”（`10` L211，`11` L372）只在键受白名单约束时成立。
  - 上轮 R26-D13-01 的期望写有“只保留 git-lfs 允许的键”，回应没有采纳，也没有给出不采纳的理由。
- **为什么重要**：
  - 这一类后果是：仓库内容经 Tower 提升为命令行配置，在沙箱外以用户身份触发进程执行或凭据路由的改变。整套 §10.1.2 加固清单正是为了防止这一类后果。
  - ADR-152 之前，`.lfsconfig` 由 git-lfs 自己读取，安全子集自然生效。ADR-152 把读取移到 Tower，却没有把这条不变式一起带过来，所以这是一处回归。
  - 修订只需要一句规则，加一组用例。
- **文档位置**：`10` L54、L206–211；`06` L239；`11` L372；`15` ADR-152 L1244；`16` L468、L602；`14` G43(b)（L129）。
- **期望的回答形态**：
  - 在 `10` 步骤 2a（以及 `16` L468 的规则行）写明以下不变式：
    - 从 base `.lfsconfig` 提升的键**只限于 git-lfs 对 `.lfsconfig` 允许的子集**，以白名单列出或直接引用 `git-lfs-config(5)` 的 LFSCONFIG 一节；
    - 子集之外的键一律丢弃，并在诊断日志中记录被丢弃的键名，不记值；
    - Tower 解析 `.lfsconfig` 时不处理 `include`/`includeIf`。
  - 同样写明：从用户主检出的**本地** git 配置复制的键也只限于同一子集，再加 `remote.<r>.url`。其余由用户的全局与系统配置照常提供。
  - 把 `10` L211、`11` L372 中“Agent 不能影响这条命令的任何输入”改为带前提的表述，例如“base 的仓库内容只能经白名单键影响端点与获取范围”。
  - 用例（并入 G43(b)）：base 的 `.lfsconfig` 除 `lfs.url` 外还含一条子集之外的键。期望该键不出现在命令行配置中，诊断日志只记录它被丢弃，获取照常完成。

### D13 隔离、git 与并发

**R27-D13-01｜次要**（“按 git-lfs 的优先级”写错；镜像 `HEAD` 的残余键、远端名，以及 `fetchinclude`/`fetchexclude` 与“缺失”判定的关系没有定义。R26-D13-01 残留）

- **问题**：
  1. **优先级与 git-lfs 不符。**
     - 文中的顺序是“用户主检出的 git 配置 `lfs.url` / `remote.<name>.lfsurl` 优先，其次 base 的 `.lfsconfig`，再次由远端 URL 推导”（`10` L208，`06` L239，`11` L372，`16` L359、L468，`15` L1244）。这是**先按来源**排序。
     - git-lfs 实际上**先按键**，同一个键内才是 git 配置覆盖 `.lfsconfig`：先找 `lfs.url`（git 配置或 `.lfsconfig`），再找 `remote.<r>.lfsurl`，最后由远端 URL 推导。
     - 本机 git-lfs 3.8.0 实测：`.lfsconfig` 设 `lfs.url`、本地 git 配置设 `remote.origin.lfsurl` 时，生效的是 `.lfsconfig` 的 `lfs.url`。按文中的顺序，Tower 会选 `remote.origin.lfsurl`。
     - 结果是这一配置组合下，Tower 与用户自己执行 `git lfs pull` 访问不同的端点，与“与用户自己执行 `git lfs pull` 相同”的论证相反。G43(b) 只测了 `lfs.url` 对 `lfs.url`，测不出这一点。
  2. **镜像 `HEAD` 的状态没有定义。**
     - `-c` 只覆盖传入的键。镜像 `HEAD` 所指提交中的 `.lfsconfig` 若含 Tower 没有传入的键（例如 `lfs.fetchexclude`、`lfs.<url>.access`），git-lfs 仍会读到。
     - 因此“镜像的 `HEAD` 与其中任何配置都不参与”在机制上没有保证。镜像由 CoW 复制对象库、ref 在 `refs/user/*` 下建立（`10` L22、L201），`HEAD` 很可能是未诞生的分支，但文档没有写。
     - `10` L206“仓库级配置不读镜像中的任何内容”的措辞仍未修正，而 git 必然读取镜像自己的 `config`，只是那份配置由 Tower 写入。
  3. **远端名与推导。**
     - `remote.<name>.lfsurl` 中的 `<name>` 怎样选，“由远端 URL 推导”用哪个远端，都没有写。git-lfs 的规则是 `remote.lfsdefault`，未设置时只有一个远端就用它，否则用 `origin`。
     - 镜像本身没有指向项目远端的 remote（它从用户检出 fetch）。所以推导所需的远端 URL 也必须由 Tower 显式传入。SSH 远端的认证还依赖“端点来自 ssh 形式的 URL”这一点。
  4. **`fetchinclude`/`fetchexclude` 与“缺失”判定。**
     - 这两个键在 `.lfsconfig` 的允许子集内。用它们排除大体量可选资产，是 LFS 项目的常见做法。
     - 文档对“base 所需的对象”（`10` L204）与“仍缺的对象 → `prepare_failed`”（L215）的定义没有考虑它们。若 Tower 传入 `fetchexclude`、却按全部指针判定缺失，这类项目每次都会进入 `prepare_failed`，重试无效。若不传入，就会下载用户刻意排除的资产，可能超过 15 分钟。
     - 用户自己的主检出中，这些路径本来就是指针文件。
- **为什么重要**：
  - 第 1、4 项会让一部分真实配置的项目访问错误的端点，或者无法开始 Goal，属于上轮要防止的“重试无效”。
  - 第 2、3 项是声称的结果没有机制，实现者要自己补设计。
  - 修订只是写清规则，不需要新架构。
- **文档位置**：`10` L22、L201、L204–215；`06` L239；`11` L372；`16` L359、L468；`15` ADR-152 L1244；`14` G43(b)（L129）。
- **期望的回答形态**：
  - 把优先级改为与 git-lfs 一致的**逐键合并**：对白名单中的每个键，用户主检出的 git 配置（含全局与系统）中有就取它，否则取 base `.lfsconfig` 中的值。合并结果全部以 `-c` 传入，另传 `remote.<r>.url`（取自用户主检出），由 git-lfs 自己按键序决定端点。
  - 也可以由 Tower 按“`lfs.url` → `remote.<r>.lfsurl` → 推导”的键序自行计算，但必须写明是逐键。
  - 写明镜像 `HEAD` 的状态，例如：始终指向一个不存在的 ref，使 git-lfs 在镜像中找不到任何 `.lfsconfig`。也可以换成等价的保证。同时把 `10` L206 改为准确的措辞。
  - 写明远端名按 git-lfs 规则取自用户主检出（`remote.lfsdefault` → 唯一远端 → `origin`）。
  - 写明“base 所需的对象”= base 树中的 LFS 指针，经合并后生效的 `fetchinclude`/`fetchexclude` 过滤。被排除的路径在卫星中保持指针文件，与用户主检出一致，不计入“缺失”。卡片或 Live Line 以 Fact 标注“按项目配置排除 N 个 LFS 对象”。
  - 用例（并入 G43(b)）：
    - `.lfsconfig` 的 `lfs.url` 对用户本地的 `remote.origin.lfsurl`，期望用 `.lfsconfig` 的 `lfs.url`；
    - 镜像 `HEAD` 所指提交的 `.lfsconfig` 含 `fetchexclude`，而 base 中没有，期望该键不生效；
    - base 的 `.lfsconfig` 含 `fetchexclude`，期望被排除的对象不获取、不判缺失，Goal 照常开始。

### D4 领域模型与生命周期

**R27-D4-01｜次要**（`ready` 中外部写入的前提只在 `16` 中改为检出标记；归因的唯一定义与写回窗口没有同步。R26-D4-01 残留）

- **问题**：
  - **写法不一致**：
    - `16` L23 已写“`ready` 中检测到来源不明的写入（**检出完成标记存在时**）→ `paused(external_change)`”。

  - **G42(y) 的重试会被误判**：
