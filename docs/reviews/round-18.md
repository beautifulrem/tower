### 3.1 删减的回归检查

|---|---|---|---|
| `run.openings`、`settle.adoptedHuman` → `pendingOpenings` | 人写的转向与“不要回退”不丢 | 独立队列，任何 Run 开始时消费 | ✓。改写与交还都不再丢载荷。新代价：队列可能跨越多次验证与评审，人写文字在很久之后以“你”发出，而且看不到、撤不回（R18-D8-01） |

### D4 领域模型与生命周期

**R18-D4-01｜重要**（按归因决定是否返工：引用不存在的值、边界有歧义，且一旦人改过就“粘住”）

- **问题**：
  1. **`mixed` 不是 `Checkpoint.author` 的取值。**
     - 规则写的是“存在 `author:"human"` 或 `mixed` 的检查点”（`03` L71、L85，`06` L261、L818，`07` L1426–1427、L1471，`16` L31、L331，ADR-140）。`07` 的 `decide()` 以 `cp.author === "mixed"` 判定。
     - 但 `Checkpoint.author` 只有 `agent | human`（`10` L556，`06` DDL L557 `CHECK (author IN ('agent','human'))`，`16` L169、L269）。`mixed` 只是路径级的标注 `Checkpoint.mixedPaths`，或评审单元的 `author`（`02` L491）。
     - 实现者只能二选一：
       - (a) 这一分支是死代码；
       - (b) 理解为“`mixedPaths` 非空的检查点”。
     - 按 (b)，`running` 中检测到外部写入后，drain 期间的回合检查点是 `author:"agent"` 且带 `mixedPaths`（`10` L240）。人选择 `revert` 后，这些路径上 Agent 与外部的编辑都已被撤销，卫星中没有任何人的内容，但该检查点仍在链上。此后每一次验证失败都会进入 `human_change_verify_failed`，卡片还会把它列为“你采纳或修改的内容”（`04` L944）。
  2. **“上一个已验证 pin”有两种读法。**
     - `03`/`06`/`07`/`16` 写“已验证 pin”（`07` 为 `lastVerifiedPin(goal)`，未定义）。它可以指“跑过验证的 pin”，也可以指“验证通过的 pin”。
     - `04` L942 与 `12` L407 写的是“自上一次**验证通过**的版本以来”。
     - G33e(e) 的期望也只与“通过”的读法一致：“上一个已验证 pin 之后人 `keep` 过一次外部改动，随后 Agent 又返工一轮，新 pin 验证失败 → 不自动返工”。
  3. **按“通过”的读法，规则会粘住，且出路都不能解除它。**
     - 一个 Goal 在首次通过之前只要出现过一次人的检查点，此后直到某次验证通过，每一次失败都进入 `paused(human_change_verify_failed)`。例如：
       - `keep` 了一次格式化工具或 `git pull` 带来的改动；
       - 接管修了一行；
       - 在 settle 中采纳了外部写入。
     - `human_change_verify_failed` 的三个出口都不能解除这种状态：
       - **“交给 Agent”**（`retry_after_human_change`，`03` L85，`06` L844）：Agent 改完提交，验证失败，又回到同一张卡片；
       - **交还选“交给 Agent 继续”**：结果同上；
       - **“撤销人的改动后 `retry_verify`”**：人的检查点仍在链上，结果同上。
     - 后果：
       - 每一轮都要人点一次，I6 的 `maxReworkCycles` 不再起作用，因为计数不增加；
       - 在此之前（ADR-099/137），“交给 Agent”之后 Agent 的失败按 Agent 路径自动返工。这是 R5（例外管理）意义上的回归。
- **为什么重要**：
  - 这条是 ADR-140 新设的唯一规则，位于核心循环“验证失败 → 谁来修”上。
  - 照文实现会出现三种互不兼容的行为。按 `04`/G33e 的读法，第一次人的介入之后，“监督而不陪跑”就退化为每轮人工放行。
  - 诚实语法也受影响：Agent 的检查点会被标成“你的改动”。
- **文档位置**：`03` L71、L85、L112；`04` L942–946；`06` L261、L818、L844；`07` L1426–1440、L1471、L1474；`10` L240、L556；`06` L557；`16` L31、L169、L269、L331；`12` L407；`14` G33e；`15` ADR-140。
- **期望的回答形态**：
  - 条件只看 `author:"human"`，删去 `mixed`。`keep` 产生的检查点本来就是 `human`，`mixedPaths` 只用于显示。或者明确定义“`mixedPaths` 中仍有未被 `revert` 撤销的路径”。二选一，并让 lint (s) 检查规则中引用的枚举值。
  - 把边界定义为以下两者中**较晚**的一个：
    - 上一个**验证通过**的 pin（没有则 base）；
    - 上一个把内容所有权显式交给 Agent 的人的决定：`retry_after_human_change`、`hand_back{continue_agent}`，以及 `human_change_verify_failed` 中带转向的 `resume`（如果允许）。

    这样，人“交给 Agent”之后，Agent 自己的失败恢复自动返工；人未表态之前，仍不自动改人的代码。
  - `lastVerifiedPin` 写入 `16` 的唯一定义；`04` L942 的文案同步。
  - 增加 G33e：
    - (f) `retry_after_human_change` 之后 Agent 的失败自动返工；
    - (g) running 中检测、drain 有 mixed 路径、`revert` 之后 Agent 的失败自动返工；
    - (h) 撤销人的改动后 `retry_verify` 失败的去向。

**R18-D4-02｜次要**（硬上限守卫让 `verifying` 成为 `budget_hard_cap` 的新入口，但没有定义）

- **问题**：
  1. **入口未登记。** `decide()` 在验证失败、按 Agent 路径且已达硬上限时，直接从 `verifying` 进入 `paused(budget_hard_cap)`（`07` L1437–1438、L1471；`03` L71；G33c(b)）。但 `03` L80 的入口只写 `running（达硬上限，drain 后）`，`03` L58 的 `verifying` 出口也没有这一条。
  2. **继续目标会把 Goal 带回同一个失败的 pin。**
     - 按 `03` L68，从 `verifying` 第一次进入 `paused` 写 `verify{pin}`。
     - 人 `budget.extend` + `resume` 之后，`onAllReasonsCleared()` 会以**同一个已失败的 pin** 重跑验证（可能耗时数分钟），再失败才开返工 Run。
     - 而 `decide()` 已经把返工证据放进了 `pendingOpenings`，`buildReworkMessage` 又会再生成一份，开场中出现两份返工证据。
     - 若人选 `claim_on_behalf`：`claim` → `claimed` → 以同样的内容验证 → 同样失败 → 再次 `budget_hard_cap`，没有终点提示。
  3. **类型不符。** `pendingOpenings: DecisionId[]`（`02` L179，`06` L452），返工证据不是决定，`appendOpening: reworkEvidence(goal, pin)` 放不进去。
- **为什么重要**：
  - 这是新规则在唯一来源 `03` 中的状态机缺口。实现者要么照 `03` 重跑失败的验证，要么自行改写继续目标；
  - 开场中的重复证据会浪费 Agent 的上下文。
- **文档位置**：`03` L58、L68、L71、L80；`07` L1437–1438、L1471；`02` L179；`06` L306、L452；`14` G33c(b)。
- **期望的回答形态**：
  - `decide()` 的硬上限分支写明继续目标为 `{kind:"run"}`（失败已判定，解除后直接返工），返工证据不进队列，而在 Run 开始时由 `buildReworkMessage` 依据最近一次失败的验证生成；
  - 或者给 `pendingOpenings` 增加非决定类条目 `{kind:"rework", verifyId}`。二选一；
  - `03` L80 的入口与 L58 的出口补上 `verifying`；
  - G33c(b) 增加“提高硬上限并 `resume` 后直接开返工 Run、不重跑验证、开场只有一份返工证据”的断言。

### D5 Agent 架构与 Pi 集成

**R18-D5-01｜次要**（`user_bash` 拿不到令牌；nudge 起点仍按 Pi agent run 计）

- **问题**：
  1. **`user_bash` 不经过 `spawnHook`**（文首核对）。
     - `05` L372 说令牌写在 `spawnHook`（`bashEnv`）中，并且“`user_bash`（同样走 `sandboxedOps`）派生的每条命令及其子孙都继承它”。
     - 但 v1.2.0 的 `user_bash` → `executeBash` → `executeBashWithOperations` 以 `operations.exec(command, cwd, {onData, signal})` 调用，**没有 `env`**（`bash-executor.ts` L121）。
     - 因此 `sandboxedOps.exec` 收到的 `env` 为空。按 Pi 自己的约定，它会回落到进程环境（`tools/bash.ts` L115），令牌与 `bashEnv` 的白名单剥离都不会生效。
     - M1（SDK）没有这条路径（`05` L380），影响在 M2 的 RPC 模式。
     - 设计须先决定人经 Pi 输入的命令派生的进程应不应当被视为 Agent 进程：要不要在 settle 时终止它们，它们的写入归谁。然后让实现与之一致。
     - C31 只断言“在 S2 中执行”，C28a 只覆盖工具路径，都测不到这一点。
  2. **nudge 起点。**
     - `tower.run_start` 在**每个** `before_agent_start` 写入（`05` L919），重建时取分支上“最后一个”（`05` L1059）。
     - 一个 Tower Run 里可能有多个 Pi agent run：宽限失败后由扩展定时器引起的新 run；撤回后的新 run。所以起点仍是最近一次 Pi agent run，与 Supervisor I4 的“本 Run”（Tower Run）不同。这正是 R17-D5-01 第 3 项后半的问题。
     - 后果：前一个 agent run 已有效 `submit`，后一个 agent run 只读不写时，tower-goal 看不到起点之后的 `submit`，会多 nudge 一次（多一次 LLM 调用），而 I4 认为提交有效。
- **为什么重要**：
  - 第 1 项是 Pi 事实与文档相反，正落在本轮新增机制的前提上；
  - 第 2 项照文实现会产生多余的模型调用。
- **文档位置**：`05` L350–372、L380、L392、L919、L1059、L1335（D38）、L1347（D50）、L1392（C28a）、L1394（C31）、L1400（C37）；`06` L187；`10` L267。
- **期望的回答形态**：
  - `createSandboxedBashOperations.exec` 不依赖调用方传入的 `env`：在 `env` 缺省时自行以 `bashEnv(getShellEnv())` 加令牌构造环境。或者在 `user_bash` 处理器返回的 `operations` 中包一层注入。二者都在 Tower 自己的代码中，不改 Pi。
  - 明确人经 Pi 输入的命令是否带令牌，并在 `10` 归因表中写明其写入归属；
  - D38/D50 行登记“`executeBashWithOperations` 不传 `env`”（`bash-executor.ts` L121）；
  - C31 增加：RPC `bash` 命令派生的后台进程环境中的令牌（按所选语义断言有或无），以及凭据变量不可见。
  - `tower.run_start` 只在分支上还没有同一 `runId` 的条目时写入（即本 Tower Run 的第一个 `before_agent_start`）；
  - C37 增加两例：同一 Tower Run 内第二个 Pi agent run；`fork` 后重建。

### D6 系统架构与可靠性

**R18-D6-01｜重要**（drain 的非 `pause` 目的与并入原因的组合未定义；settle 序列中崩溃的恢复）

- **问题**：ADR-141 规定“drain 期间到达的暂停请求只并入 `reasons`”。但结束时与崩溃时怎样处理 `reasons`，只对 `target = pause` 写了（`06` L96、L140，`16` L32，`10` L267）。另外三种目的分别有以下问题。
  1. **正常结束时，并入的原因没有去向。**
     - **`take_over` + `external_change`**：`take_over` 的前置条件是 `external_change` 已解除，否则 `E_STATE`（`06` L842，`03` L78）。drain 结束时，接管是执行、拒绝还是改为 `paused(external_change)`，没有规定。
     - **`rewind` + `external_change`**：`navigate` + `restoreCheckpoint` 会以 Tower 写回覆盖卫星（`06` L856），E 中的来源不明内容未经 keep/revert 就被覆盖。这与“来源不明的内容要么被撤销、要么经 `keep` 成为人的改动，且必须由人决定”（`07` L1485、`10` L255）相违，`externalChange` 列也没有清除点。
     - **`dependency` + `human` 或 `external_change`**：结束时进入 `ready{dependency}`（`06` L140），人的暂停丢失。依赖恢复后会自动开 Run，违背人的暂停。
     - **`dependency` + `external_change`**：`ready` 中 `externalChange` 非空，违反 `06` L481–482 的 `CHECK`（`ready` 既没有 `pause_reason`，也没有 `also_applies`）。
  2. **崩溃恢复丢弃 `reasons`。**
     - `take_over`/`rewind` → `paused(human)`；`dependency` → `ready`（`06` L140，ADR-141）。都没有说 `reasons` 并入 `alsoApplies`。
     - `reasons` 含 `external_change` 时，恢复事务要么违反 `CHECK`，要么清掉 E，又回到 R16-D6-01/R17-D6-01 关闭过的“来源不明的内容失去保护”。
     - G35e(e)(f) 只测了单独的 `take_over`/`rewind`/`dependency`。
  3. **目的之间的冲突。**
     - `pause` 的 drain 中人又按“我来改”，或 `take_over` 的 drain 中发生依赖回退：`target` 是只取先到者、被覆盖，还是拒绝后到的命令，都未定义。
     - `16` L32 的“只并入”只覆盖“暂停请求”。
  4. **settle 序列中直接崩溃（没有 drain）。**
     - `06` L140 末句把“`draining_for` 为空”一律按“Run crashed”处理，即 `paused{app_quit|engine_crash}`，继续目标按 `running` 写为 `run`。
     - G35c(o) 却断言“继续目标 `settle`”，`03` L68 也要求 settle 序列中的任何暂停都写 `settle`。
     - 恢复所需的判据（Run 已 `agent_settled`、有效提交已记录、尚未 `claimed`）没有写进恢复表。R17-D4-03 第 4 项末句建议的 settle 阶段持久化没有落地。
- **为什么重要**：
  - 第 1、2 项都会在不常见但完全可预见的时序下（检测到外部写入恰好发生在接管、回退或依赖回退的 drain 中）静默改写人的决定或来源不明的内容，并且与 DDL 冲突；
  - 第 4 项使一条测试的期望无法从正文推出。
- **文档位置**：`02` L175–178；`03` L55、L68、L78；`06` L90–96、L140、L458、L477、L481–482、L842、L856；`07` L1485；`10` L240、L255、L267；`16` L32；`14` G35c(o)、G35e。
- **期望的回答形态**：
  - 规定唯一规则：drain 结束或崩溃恢复时，`reasons` 总是并入结果状态的原因集合。若结果状态不能承载原因（`ready`），则改为进入 `paused`：
    - `dependency` + 非空 `reasons` → `paused(<最高者>)`，`dependency` 记为解除后的去向，或者作为 `ready` 的前置条件；
    - `take_over` + `external_change` → 不执行接管，进入 `paused(external_change)`，提示“先处理外部改动，再接管”；
    - `rewind` + `external_change` → 同上，不执行回退。
  - 目的冲突：drain 进行中，`take_over`/`rewind` 命令返回 `E_STATE`（“正在暂停，请稍后”）；依赖回退在 drain 中只并入一个 `dependency` 标记，结束后按上一条处理。
  - 恢复表增加一行“settle 序列中（`runs` 已记 `agent_settled`、未 `claimed`、无 `draining_for`）”→ 继续目标 `settle`，与 G35c(o) 一致。所需判据持久化为 `runs.settled_at` 或类似列。
  - G35e 增加：
    - (h) `take_over` 的 drain 中检测到外部写入，分别正常结束与崩溃；
    - (i) `rewind` 同上；
    - (j) 依赖回退的 drain 中人暂停。

**R18-D6-02｜次要**（令牌识别的运行期枚举：频率、成本、存活者退出与残余窗口）

- **问题**：ADR-142 删除了“随进程进出写事件”，但以下功能仍需要知道“本 Run 的进程此刻是否存活、是哪些”。它们没有重新规定机制：
  1. **归因表第 2 行**（`10` L232）：`running` 中每批文件事件都要判断“本 Run 的进程中仍有存活者”。在 macOS 上，这意味着对同一用户的全部进程读一次环境（`13` L314：≤ 40 ms/次）。开发服务器持续写 `dist/` 时可能每秒一次、每个 Goal 一次。`13` L319 仍写“检测复用指纹的 stat 检查，**无新增**”。
  2. **进程树清空时的 `agent_bg_done`**（`10` L526，G35b），以及**每 Goal 进程树的内存上限**（`13` L190：超过时“杀掉最大子进程组”），都需要持续采样成员与 RSS。采样频率、是否与第 1 项共用一次扫描，都未规定。
  3. **`bg_process_survived` 的“进程自行退出 → `obsolete`”**（`08` L486），以及它决定的归因窗口（`10` L233 的“未解决期间”），需要有人发现存活者已退出。
     - 现在既没有退出事件，重启后的扫描也只覆盖“未结束 Run 的令牌”（`06` L190，`13` L315）。存活者属于已结束的 Run，重启后不再被检查。
     - 于是“未解决”期间可能无限延长，已知误判 (c)（人的保存被记为 Agent）随之延长。
  4. **残余窗口的描述。**
     - “范围小于此前的 `setsid` 脱组窗口”（`06` L189，`10` L267，ADR-142）没有论证。两者是不同的窗口：
       - 令牌方案漏掉的是**构造全新环境**派生的子进程。很多测试框架与构建工具会显式传入环境对象，`env -i` 只是其中最显眼的一种。
       - 进程组方案能捕获这类子进程，只要它们没有脱组。
     - G35c(j″) 只覆盖了 `env -i`。
- **为什么重要**：
  - 第 1、2 项是新方案在 macOS 上的常驻成本，没有预算，也没有降级策略；
  - 第 3 项使一个已登记的误判窗口失去上界；
  - 第 4 项是没有证据的比较性断言。
- **文档位置**：`06` L187–190；`08` L486；`10` L232–233、L267、L526；`13` L190、L314–315、L319；`15` ADR-142；`14` G35b、G35c(j″)。
- **期望的回答形态**：
  - 规定一次共享的周期扫描。例如每 2 s 对所有活跃 Run 与未解决 `bg_process_survived` 的令牌做一次全进程环境扫描，结果供第 1–3 项共用。文件事件批次只读最近一次扫描结果，不另扫。在 `13` 登记成本（≤ 40 ms / 2 s / 全部 Goal）与降级（负载高时降到 5 s）。
  - `bg_process_survived` 在周期扫描中找不到该令牌的进程时自动以 `obsolete` 关闭；重启扫描覆盖“未结束 Run **以及**未解决 `bg_process_survived` 的 Run”。
  - 把残余窗口改写为“不继承环境派生的进程（显式构造环境、`env -i`、经 launchd 等启动）”，删去“范围更小”的比较，或者给出依据。是否以进程组作为辅助识别（同组即属于该 Run），记为权衡。
  - G35c 增加：(q) 测试运行器以显式环境派生 worker；(r) 存活者在 Run 结束后自行退出，断言条目以 `obsolete` 关闭。

### D8 注意力与交互

**R18-D8-01｜次要**（排队的开场不可见、不可撤回；残留的 UI 文案）

- **问题**：
  1. **`pendingOpenings` 只在“下一次任何 Run 开始时”消费**（`03` L69–70，`16` L29），验证、评审都不消费。
     - 队列可以跨越多次验证、评审，甚至跨天。例如：
       - 在验证中暂停后 `resume{note}`；
       - 交还选“直接重新验证”时写的意图；
       - 验证通过进入 `in_review`，几天后 `request_changes`。
     - 此时这些人写的文字会以 user 角色、在 Trace 中以“你”的身份发出（`04` L932，`06` L835）。
     - 但 `04` 没有任何位置显示“下次运行时将告诉 Agent：n 条”，也没有撤回或编辑的命令。评论有回执与“未送达”的处理（`04` L497、L1235），这里没有。
  2. **`04` L880**：`bg_process_survived` 卡片的“再次终止”说明仍是“以 (启动时间, pid) 确认身份后再发信号”，与 ADR-142 及 `06` L873 相反。
- **为什么重要**：
  - 第 1 项是一条“UI 没有命令”的缺口：人不知道、也改不了即将以自己名义发出的话。Trace 中这条 user 消息的时间也不是人写下它的时间，与 Fact/Claim/Human 的时间语义不符。
  - 第 2 项是对用户可见的错误说明。
- **文档位置**：`03` L69–70；`04` L497、L880、L932、L1235；`06` L835、L873；`16` L29。
- **期望的回答形态**：
  - Goal 页与暂停卡片显示 `下次运行时将送出：<条目摘要>`，每条可撤回；新增命令 `goal.opening.withdraw{decisionId}`（scope `decide`），写入 §6.4.3 与 lint (v) 的覆盖矩阵；
  - 人写文字发出时附原决定的时间（例如 Tower 标记行写“你于 <时间> 写下”）；
  - 修正 `04` L880；
  - 用例：G33d(e) 验证通过后再 `request_changes`，断言 UI 事先显示了排队内容，撤回后不发出。

### D11 安全与自主度

**R18-D11-01｜次要**（读取全部进程环境的处理不变式）

- **问题**：
  - ADR-142 让 Supervisor 在 settle、重启以及（按 R18-D6-02）运行期间，对**同一用户的全部进程**读取环境（`KERN_PROCARGS2`）。用户终端、其他应用的环境中常有云凭据、令牌与密码。
  - `11` L350 只论证了令牌本身不是凭据，没有规定 Tower 对读到的其他环境内容怎样处理：
    - 只在内存中做子串匹配；
    - 不写日志；
    - 不进入 Trace、事件、诊断包与崩溃转储；
    - 读完即丢弃。
  - 实现者为排查识别失败而记录环境，是很自然的调试动作。一旦这样做，密钥就会进入 Tower 的诊断导出（`06` §6.1.7 的“导出诊断包”）。
- **为什么重要**：

  - 两个重要项实现时会直接表现为：
    - 人一旦采纳或修改过内容，直到下一次验证通过前，Agent 的每一次失败都要人手动放行，“交给 Agent”也不能恢复；或者实现者按另一种读法写出不同的行为。Agent 的检查点可能被标成“你的改动”；
    - 接管、回退或依赖回退的 drain 中检测到外部写入（或收到人暂停）时，来源不明的内容被回退覆盖、人的暂停被丢弃，或者恢复事务违反 `CHECK`。
  - 两项都可以用一段规则关闭：
    - 归因只看 `author:"human"`，边界取“上一个通过的 pin”与“上一次交给 Agent 的决定”中较晚者；
    - drain 结束或崩溃时，`reasons` 一律并入结果状态；无法承载时进入 `paused`，并且外部写入未解除时不执行接管或回退。
  - 其余次要项多为接线、成本登记、可见性、用例与文字残留，范围有限。
- **下一轮建议按以下顺序修订**：
  1. 修正归因规则：删去 `mixed`，定义 `lastVerifiedPin` 为“通过”，加入“交给 Agent”边界，增加 G33e(f)–(h)（R18-D4-01，影响核心循环，优先）；

  3. 定义 `decide()` 硬上限分支的继续目标与返工证据的来源，补 `03` 的入口与出口（R18-D4-02）；
  4. 让 `sandboxedOps` 自行构造环境与令牌，决定 `user_bash` 的语义，`tower.run_start` 每个 Tower Run 只写一次（R18-D5-01）；
  5. 规定共享的周期扫描及其预算、存活者退出检测与重启覆盖范围，改写残余窗口的描述，并加上读取进程环境的不变式（R18-D6-02、R18-D11-01）；
