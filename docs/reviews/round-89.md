## 1. 总评

**第 88 轮的 4 条次要条目都已按所问关闭**（核对见 §3）。§5 的 14 条观察全部落地；回应 “偏离与未决” 的五条中四条接受，一条接受其方向，但它带出了 R89-D11-01。

**ADR-216 的主体成立**（§3.3）：
- **每个 Host 一个空目录**：默认模式下并发的 Goal 不再互相删除对方的目录，启动失败的窗口消失；Supervisor 重启时 Host 仍在运行（Host 是 main 的子进程，`06` L40），清理只删除不属于存活 Host 的残留。`hostId` 跨进程复用带来的先后问题见观察 1。
- **置灰的范围**：唯一定义移到 `03` L74，只列 `take_over` 与 `claim_on_behalf` 两项，`06` L882、L902，`16` L45，`04` L664、L933，`07` L1518，`14` G26c、G32 一致。解除原因的命令一律可用，`nested_repo_live` 与被保留的 `input_mutated_after_gate` 都不再只剩放弃。
- **`claim_on_behalf` 改为 `E_STATE`**：硬上限在交还时保留（`16` L31），`budget.extend` 没有 `pendingHandBack` 守卫（`06` L940），“先提高预算再 `resume`” 可走通；交还 `continue_agent` 开 Run 时才遇到硬上限的，第 ① 步已清除 `pendingHandBack`，`claim_on_behalf` 重新可用。规则自洽。
- **`reverify` → `continue_agent` 的置换**：只在附转向解除 `nested_repo_live` 时发生（`note` 必填，不附转向是 `E_STATE`）；转向照常进入 `pendingOpenings`（ADR-140）；路径不经 `verify_new`，残留的 `returnTo` 无害（ADR-143）；DDL 对该列只有 `json_valid` 与 `state='paused'` 两条约束（`06` L480、L501）；置换由 `human.decision{resume}` 在同一事务写出，重放可以复现。
- **重建**：字段粒度、墓碑行沿用、写入新库后替换。CHECK 只作用于合并后的最终行，旧库一致时最终行与旧库相同；旧库不一致时重建中止、旧库不变，有界。

**ADR-216 带出的新问题**：
- **门禁不再以服务器实际的工作目录为基准**（R89-D11-01）：
  - 为消除 R88-D11-02 的误判，ADR-216 把空目录整个移出了解析基准；
  - 但未写 `cwd` 的服务器正是按这个目录解析相对参数的。以 `..` 越出空目录的相对路径，结果可以落在第 3 条硬底线中的位置（影子目录、安装器目录、其他 Host 的空目录、用户主检出），门禁却按卫星求值，只 ask，一次批准即可放行；
  - ADR-216 写下的残余 “只写进本 Host 的空目录……从不跨 Host” 因此不成立；`05` L439 “相对的 `config.cwd` 实际只有 `.` 可用” 对含 `..` 的值也不成立，而这时门禁同样没有该基准。
- **置换后的 `resume` 不移动归因窗口的起点**（R89-D4-01）：
  - 窗口起点的决定列表是封闭的三项（`03` L75，`16` L38，`07` L1591、L1599）；交还决定仍记为 `reverify`，置换它的 `resume` 不在列表中；
  - 于是交还的 `human_edit` 检查点仍在窗口内，Agent 此后第一次验证失败进入 `paused(human_change_verify_failed)`，而不是按 “交给 Agent 继续” 自动返工。这与 `03` L74 的 “人的新选择取代交还时的选择” 和 `04` L664 的卡片文字不符。

**全范围扫描**在 ADR-216 之外新发现：
- **路径扫描不认 `file:` URI**（R89-D11-02）：`11` L221 (1) 只检查绝对路径与 `~` 路径，(3) 又把 `<scheme>://` 开头的值排除在相对路径之外；以 `file:` URI 指向的本地文件因此既不受硬底线 forbid，也不触发 `secrets.access`，在按工具名的 Goal 级授权之下只是 `notify`。这是第 3、4 轮起就有的规则，此前各轮都没有发现。

### D11 安全与自主度

**R89-D11-01｜次要**（门禁不以服务器实际的工作目录为基准：以 `..` 越出空目录的相对路径、含 `..` 的相对 `config.cwd`，都能使硬底线中的位置只 ask；ADR-216 写明的残余 “只写进本 Host 的空目录……从不跨 Host” 不成立）

- **问题**：
  - **服务器怎样解析相对参数**：
    - 未写 `cwd` 的 stdio 服务器，进程的工作目录是本 Host 的空目录 `~/.tower/mcp-cwd/<hostId>/`（`05` L439，`11` L222 (a)）；
    - 服务器按自己的工作目录解析相对参数（Pi 的 stdio 传输以该 `cwd` 启动子进程，`runtime.ts:118`）；`roots` 另行给出，只有自己按 `roots` 解析的服务器（代码智能类）才以卫星为基准。
  - **门禁怎样解析**：
    - `11` L222 (b)：以 `roots`（卫星）解析，写了绝对 `cwd` 时再以它解析，“**Tower 的空目录不作基准**”。
  - **两者不一致的后果**：
    - 以 `..` 开头、越出空目录的相对路径，按服务器实际的工作目录求出的位置可以在 `~/.tower/` 之下或之外的任意处，包括第 3 条硬底线中的影子目录、安装器私有目录、其他 Host 的空目录与用户主检出（`11` L212）；
    - 而门禁按卫星求出的位置与之无关，通常不在硬底线内，于是只 ask。一次批准即可放行，而硬底线本应 “不可授权覆盖”；
    - 写明的残余因此不成立：`11` L222 (b) “这样一次经人批准的调用可以写进本 Host 的空目录，按 (a) 只影响同一 Host 进程中之后启动的服务器……从不跨 Host”，ADR-216 与 `00` L99（“空目录按运行进程分开……写进去的东西不越过这个运行进程”）同此。
  - **ADR-215 曾挡住这一类**：ADR-215 以空目录为基准，越出它而落在硬底线的结果会被 forbid。R88-D11-02 只要求消除 “空目录本身在写入硬底线中” 引起的误判；ADR-216 把空目录整个移出基准，也移走了对越出它的检查。回应 “偏离与未决” 只权衡了 “以 `..` 越出卫星”。
  - **相对的 `config.cwd`**：
    - `05` L439 “相对的 `config.cwd` 实际只有 `.` 可用……其他相对值求出的都是其中不存在的子目录”（ADR-216 观察 4 同此）。对含 `..` 的值不成立：它们可以求出空目录之外、既不在 Agent 可写位置也不在 Tower 数据目录之下的目录（例如用户主目录中的某个仓库检出），服务器照常启动；
    - 这时门禁同样不以该目录为基准（(b) 只加 “写了绝对 `cwd`” 一侧），而同一目录写成绝对路径时，落在其中的相对路径会被 forbid（`11` L222 (b) 的例子）。两种写法得到不同的保护，且与 `05` L439 的陈述矛盾。
  - **后果的类别**：经人批准的一次沙箱外调用写进 Tower 的完整性存储（影子目录中的检查点、pin 与 seal 所在处）或另一个 Host 的空目录，跨越 ADR-216 声称的 Host 边界与硬底线。
- **为什么是次要**：与 R87-D11-02 同一口径——需要人对一次相对路径调用逐次批准（相对路径恒为 `opaque`、至少 ask，按工具名的 Goal 级授权也不放行，`11` L219），审批卡显示以 `..` 开头的参数；`11` L221 末句把沙箱外工具的路径扫描定为尽力而为，T7/T26 按 “是否加载了能写文件系统的沙箱外工具” 分档。但 ADR-216 对这一缺口写下了一条不成立的残余，并且移走了 ADR-215 已有的检查；实现者按 (b) 实现时不会检查这一类，按 (a) 的残余理解时会以为它被挡住。
- **文档位置**：`00` L99；README L19；`05` L439、L1461（C21）；`11` L212、L219、L221、L222；`14` L134（G46 (bk)）；`15` ADR-216 R88-D11-02 一条。
- **期望的回答形态**：在 `11` L222 (b)（唯一定义）加一句，`05` L439 改一句：
  - **以 Tower 求出的实际工作目录为第三个基准，但只检查越出它的结果**：对经 `towerMcpTransport` 启动的服务器，相对路径也以它的实际工作目录（`05` L439 求出的 `cwd`，不论来自空目录、相对或绝对的 `config.cwd`）解析；结果在本 Host 的空目录之内的不因此 forbid（保留 ADR-216 的取舍，`owner/repo` 一类照旧 ask），越出它而落在第 3 条硬底线中的 forbid、命中密钥路径表的按 (2) 处理。这样 R88-D11-02 的误判不会回来（不以 `..` 开头的值求出的结果都在空目录之内）；
  - 或者明写不这样做，并把残余如实改为 “以 `..` 越出空目录的相对路径只 ask，一次批准可以写进硬底线中的位置”，`00` L99 与 T7/T26 同步；
  - `05` L439 的 “只有 `.` 可用” 改为与规则一致的说法（例如把含 `..` 的相对 `config.cwd` 一并按同一句文字不启动，或删去该句）；
  - G46 (bk) 补一组只写期望：未写 `cwd` 的服务器收到以 `..` 越出空目录、指向硬底线位置的参数时被 forbid（若取第一支）。

**R89-D11-02｜次要**（路径扫描不认 `file:` URI：以 URI 形式出现的本地路径既不受硬底线 forbid，也不触发 `secrets.access`）

- **问题**：
  - **规则**：`11` L221 对沙箱外工具参数中的字符串值：(1) “绝对路径与 `~` 路径” 落在硬底线 forbid；(2) 命中密钥路径表 → `secrets.access`；(3) 相对路径的定义明确排除 “以 `<scheme>://` 开头” 的值。
  - **`file:` URI 不属于其中任何一类**：它不以 `/` 或 `~` 开头，又以 `<scheme>://` 开头，按字面实现既不是绝对路径也不是相对路径，只是普通字符串。
  - **而这正是 MCP 中本地文件最常见的写法**：MCP 资源以 URI 标识，文件系统类服务器的资源是 `file:` URI，资源工具 `read_mcp_resource` 以 URI 为参数（`11` L220）；代码智能类工具也以文件 URI 指明文档。
  - **后果**：
    - 指向用户主检出、影子目录等硬底线位置的 `file:` URI 不被 forbid；
    - 指向密钥路径表中文件的 `file:` URI 不另加 `secrets.access`，“一次审批命中两个 ask 类，只有‘仅这一次’”（`11` L219）不生效；
    - 人对该工具授予 “本 Goal 内同类” 之后（资源工具为所有服务器只注册一次，授予一次即覆盖全部服务器），这类调用只是 `notify`。
  - **后果的类别**：沙箱外工具在按工具名的授权之下读取或改写硬底线与密钥位置，而 `11` §11.3.4 对路径参数承诺的两条检查都不适用。
- **为什么是次要**：需要用户自己配置了接受 `file:` URI 的服务器，并由人授予过授权或逐次批准；路径扫描本是尽力而为。但这不是 “工具根据非路径参数自行决定位置” 那一类已登记的限制：值本身就是一个本地绝对路径，只是换了写法；实现者按字面会全部漏掉，按语义会解码检查，两种实现的保护差别很大。
- **文档位置**：`11` L219、L220、L221、L684（T7）、L703（T26）。
- **期望的回答形态**：在 `11` L221 (1) 补半句：`file:` URI（含 `file://localhost/`）按 RFC 8089 解码百分号转义后视为绝对路径，照 (1)(2) 检查；其他 scheme 照旧不视为路径。G46 或相应的 C 类补一组只写期望：资源工具以 `file:` URI 读取密钥路径表中的文件时出现 `secrets.access` 的审批卡，指向主检出时被 forbid。

  - **归因窗口的起点是封闭列表**：
    - `03` L75（唯一规则）：起点 = 最近一次通过的验证的 pin 与 “人最近一次明确把工作交给 Agent 的决定（`hand_back{continue_agent}`、`retry_after_human_change`、`request_changes`）” 中较晚者；
    - `16` L38 与 `07` L1591、L1599（`lastHandToAgentDecisionSeq`）以同一形状复述，`07` L1671 写明 “人随后以 `hand_back{continue_agent}`……把工作交给 Agent，窗口从该决定事件之后起算”。
  - **置换之后**：
    - 交还决定事件仍记为 `reverify`（事件不可改），置换它的 `human.decision{resume}` 不在列表中；
    - 交还的 `human_edit` 检查点（`author:"human"`）在上一次起点之后，仍在窗口内；
    - 所以 Agent 删除条目、提交之后，第一次验证失败进入 `paused(human_change_verify_failed)`，而不是按 Agent 路径自动返工。若交还时直接选了 “交给 Agent 继续”，同样的失败会自动返工（ADR-145：交还的 `human_edit` 检查点不在由该交还开启的窗口内）。
  - **两种读法**：照封闭列表实现，不自动返工；照 “取代交还时的选择” 的语义实现，把这次 `resume` 当作交给 Agent 的决定，自动返工。两者的去向不同，`14` G26c (b) 的 `reverify` 一组只写到 “进入 `running`、不先验证”，没有失败一支可以裁决。
- **为什么是次要**：不丢数据，照列表实现的结果偏保守（多一次人工确认，`retry_after_human_change` 即可交回）。但这是 ADR-216 刚定义的分支，它的文字承诺与唯一规则的结果不一致，实现会分叉；失败卡片还会把 Agent 的失败标为 “包含你的改动”。
- **文档位置**：`03` L74、L75；`04` L664、L933；`06` L882；`07` L1591、L1599、L1671；`14` L91（G26c）；`16` L38、L45。
- **期望的回答形态**：在 `03` L75（唯一规则）二选一：
  - **列入**：起点列表补一项 “置换 `pendingHandBack.mode` 为 `continue_agent` 的 `resume`（ADR-216）”，或把这一项概括为 “其执行开出 `handback` Run 的决定”；`16` L38、`07` L1591/L1599 与 L1671 同步；
  - **或如实写明不列入**：置换之后的第一次失败仍按 “窗口内有人的改动” 处理，`04` L664 的卡片文字与 `03` L74 的 “取代” 改为不承诺等同于交还时选择 “交给 Agent 继续”；
  - G26c (b) 的 `reverify` 一组补失败一支，只写期望。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D5、D6、D7、D8、D9、D10、D12、D13、D14、D15、D16 共十四个维度为 100，在这些维度上没有可追问的实质问题。
  - D4 为 95；D11 为 90。
- **是否还有可追问的问题：有。** 新增共 **3** 条：阻断 0、重要 0、**次要 3**。
  - **D11**：R89-D11-01、R89-D11-02。
  - **D4**：R89-D4-01。
  - **第 88 轮核验**：
    - 4 条全部按所问关闭，其中 R88-D11-02、R88-D4-01 各带出新条目；
    - §5 的 14 条观察全部落地，观察 3 带出本轮观察 2，观察 4 的一句并入 R89-D11-01；
    - 回应的五条偏离与未决全部接受，第一条附带 R89-D11-01。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 216，section_refs 7878，(v) 98 条命令，(e) 219 对，(i′) 5 个事件，(D) 357 个短语，(z′) 53 处，(C) 19 行并覆盖 §14.8），与第 88 轮记录逐行一致。
    - Pi v1.2.0：ADR-216 的引文为原文，行号差一处（观察 10）；默认工厂与 stdio 传输的工作目录、`roots` 的来源、重新连接的路径都已逐个核实（见文首）。
    - 排期结论成立：WBS 123.38；余量 0.12 / 0.15 / 0.36 / 0.48 / 0.12；依赖链 19.91；增人 129.33、T 23.88、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **`hostId` 与 “每个 Host 进程一个”**：`hostId` 跨进程复用（`05` L192 `hostEpoch` “Host 每次进程启动 epoch+1”，`06` L390、L1140 的幂等键），而目录以 `<hostId>` 命名。F4 的自动 “重启并恢复”（`06` L1184）或挂死后强杀时，旧进程的退出清理若晚于新进程的创建，会删掉新进程正在用的目录。`11` L222 “已存在时先删除” 表明意图是按进程，实现者会这样做，但宜写明 “以 `<hostId>-<hostEpoch>` 命名” 或 “退出清理只删除为该进程创建的目录”；同时写明启动恢复的清理排在 main 交回存活 Host 的端口之后（`06` L63），以及路径怎样交给 Host（`RunSpec` 或 Host 环境）。
    2. **交接时自检失败的出口**：`05` L434 “交接与恢复时运行时重建，这一检查随之再跑”，C21 期望交接时取代者出现则 `paused(prepare_failed)`；但 `03` L98 的 `running` 入口只列 ADR-188（Run 中途同名工具），F4b（`06` L1185）只列 “Host 启动自检”，`04` L974 只有 `启动失败：…` 的卡片。结果状态、继续目标与 “重试是开新的运行” 都已由 `prepare_failed` 行与 F4b 确定，宜在 `03` L98 与 F4b 各补半句，卡片沿用 ADR-188 那一支的 “运行已停止” 文字。
    3. **目标页 `继续` 按钮的改名**：`04` L664 写 `pendingHandBack` 期间目标页的 `继续` 改为 “重新验证” 或 “交给 Agent 继续”；`nested_repo_live` 在 `reverify` 模式下的附转向 `继续` 实际是 “改为交给 Agent 继续”，卡片文字已写，按钮的改名规则宜同列这一例外。
    4. **硬上限卡片的列举**：`04` L1508 与 `12` L439 列出 `claim_on_behalf` 而未注明 `pendingHandBack` 期间置灰（`04` L664 是引用点，`12` L424 已同步 ADR-215）；宜各补半句，并在置灰提示中点明 “先扩展预算，再继续”。
    5. **G32 区分不出新守卫**：G32（`14` L108）在 `paused(sentinel_high)` 中期望 `claim_on_behalf` 返回 `E_STATE`，而该命令本来只接受 `idle_without_submit|budget_hard_cap`（`06` L902），去掉新守卫也是 `E_STATE`。新守卫只在 G33（L110，硬上限 + `pendingHandBack`）的情形中起作用，宜把这一期望移到 G33。
    6. **`HumanDecision.handBack` 缺 `mode`**：`02` L527–L530 的 `handBack` 只有 `externalResolution` 与 `resolvePinHits`，而归因窗口按 `hand_back{continue_agent}` 读取决定，`06` L905 “③ 写决定时由它生成” 也暗示决定带 `mode`；宜在 `02` §2.7 补上。
    7. **被清除 Goal 在其他重放表中的行**：清除一个 Goal 时删除其 runs、checkpoints、facts、claims、contracts、comments 等行并墓碑化事件（`09` L565）；`06` L221 (a) 只写了 `goals` 与 `decisions` 的墓碑行，“跳过载荷已墓碑化的事件” 是隐含的，与 “事件产生而旧库没有该行即中止” 合读时可能被误解；宜补半句。被清除 Goal 名下的 `goal_deps` 行同理（依赖主要属 M2）。投影版本迁移改动普通行的非事件列时，其值的来源也宜与墓碑行同一句写明。
    8. **最后一次由非事件写入的字段**：`06` L144 在人工编辑检出丢失时清除 `human_checkout`，没有指定事件；字段粒度的重放会由 `human_checkout.created` 重新写出 `path`、`baseTree`，使已清除的检出 “复活”，下一次启动恢复再按 L144 清除，不丢数据。宜写 “最后一次写入不是事件的字段取旧库的值”，或为这次清除指定事件。
    9. **`inspect.bring_back` 写回期间的并发命令**：写回跨多个异步批次保持 `syncing`（`06` L914），CHECK（L499–L500）只在该期间允许 `in_review`/`accepted` 下 `human_checkout` 非空；这期间 `goal.abandon`、`request_changes`、`contract.amend` 没有定义 `E_BUSY`，交错时以 CHECK 失败的内部错误告终。CHECK 防止了损坏，宜在一处写 “带回进行中 → `E_BUSY`”。这是 ADR-105 以来的旧问题。
    10. **Pi 引文**：ADR-216 与回应的 `runtime.ts:342` 应为 `:343`；“stdio 服务器启动失败后在该会话中一直是 `failed`” 只对首次连接失败的服务器成立（其工具从未注册），以参数指明服务器的资源工具会经 `getClient()` 重新打开（`runtime.ts:237-243`、`:278-300`）。不影响 R88-D11-01 的结论。
    11. **Host 被强杀后的 stdio 服务器**：Pi 只在进程的 `exit` 钩子中终止 stdio 子进程组；Host 被强杀或因内存上限被杀时，服务器可能比 Host 活得久（多数在 stdin 关闭后退出），其工作目录随后被 Supervisor 删除。有界，宜在 `11` L222 (a) 或 `06` §6.1.3 的 Host 一行写一句 “Host 退出后其进程组中残留的 MCP 服务器一并终止” 或登记为残余。
    12. **`GIT_CEILING_DIRECTORIES` 的旧写法**：`11` L693（T16）、L706（T29）仍写 `<wtRoot>`，唯一定义是 `<全部 wtRoot>`（`05` L466，`10` L29）；措辞差异，打包模式下可能让实现者只列一个根。
- **设计是否完成：ADR-216 正确地关闭了第 88 轮的四条次要条目。**
  - 空目录按 Host 分开，并发的 Goal 不再互相删除；置灰的范围收为两项并有唯一定义；`claim_on_behalf` 与 `take_over` 同一守卫；重建以字段为粒度、墓碑行沿用、写入新库后替换。
  - 本轮没有重要条目。3 条次要条目分两类：
    - **ADR-216 的新规则在相邻情形下的后果**：R89-D11-01（空目录移出基准之后，越出它的相对路径与含 `..` 的相对 `cwd` 只 ask）、R89-D4-01（置换与归因窗口）；
    - **此前各轮未发现的旧规则缺口**：R89-D11-02（`file:` URI）。
- **下一轮建议**：
  1. **R89-D11-01**：以实际工作目录为第三个基准、只检查越出空目录的结果；或如实改写残余。`05` L439 的 “只有 `.` 可用” 与规则对齐。
  2. **R89-D11-02**：`file:` URI 解码后按绝对路径检查。
  3. **R89-D4-01**：起点列表补置换的 `resume`，或如实写明不补；G26c (b) 补失败一支。
  4. §5 的十二条观察各补半句。

  **工时与排期**：约 0.02–0.03 人周，不在依赖链上。系统线与安全线余量都是 0.12、都在改派阈值上，本轮可能落在这两条线上的增量（R89-D11-01、R89-D11-02 在 W10；R89-D4-01 在 W3/W9）都须先按 ADR-136 改派（§3.2）。预计 M1 仍可维持 38 周（2027-07-30）。
