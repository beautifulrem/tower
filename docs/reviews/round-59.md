### D7 诚实与验证

**R59-D7-01｜次要**（`07` L500 的唯一定义同时写“只有走到槽位路径的验证才有重放包”与“验收与 seal 时的完整重哈希验证永久保留”。后者是指纹闸口，不是 `verify()` 的运行，没有写重放包的位置、`verifyId` 与保留 ref 的目标；缓存命中的前提也有两种写法）

- **问题**：
  1. **完整重哈希不是验证运行**：
     - `07` L500：“只有决定性验证永久保留：导致 `in_review` / `accepted` 的验证，以及验收与 seal 时的完整重哈希验证；镜像保留 ref 只为这些重放包而写。只有走到槽位路径的验证才有重放包（`verify()` 中的 `writeReplayBundle`，唯一定义，ADR-186）”。
     - 但验收与 seal 时的完整重哈希是指纹模式：`07` L274 写“`accept` 动作、seal | `full`（全新临时索引，完整重哈希）”；`10` L210、L648 也只说它是闸口处的指纹确认。
     - 它不经过 `verify()`，`VerifyTrigger` 中没有 accept 或 seal，因此按同一行的唯一定义，它不可能有重放包。
     - 同一子句被复述于 `06` L1114、`10` L1249（“永久重放包写入时”写保留 ref）、`13` L361、`16` L479。
     - **两种实现**：
       - 什么也不写（子句成为死文）；
       - 在验收或 seal 时另造一个重放包与保留 ref（指向已验收的 pin 还是 seal 提交、用哪个 `verifyId`，都没有定义）。
     - ADR-186 的目标是“只承诺真实的范围”，这一句恰好是唯一定义中仍然无法为真的承诺。
  2. **缓存命中的前提有两种写法**：
     - `07` L403 与 `07` L897：命中要求“原日志**与**原重放包仍在”，“原日志**或**原重放包已被清理时不算命中”；
     - `07` L500（唯一定义）与 ADR-186（`15` L2290）：只要求“原日志仍在”。
     - 磁盘压力清理同时删除两者（`10` L442），所以只在原重放包目录被单独删除时分歧。但“原日志”本身也有两个对象：§7.4.4 的完整日志（`verify/<verifyId>/…log`），以及重放包内的脱敏验证日志（L497 ①）。实现者对“命中时要检查哪个文件”会有不同答案。
- **为什么是次要**：判定与验收不受影响。但唯一定义的一行内部自相矛盾，永久证据的范围（以及镜像保留 ref 的写入点）会因实现而异。
- **文档位置**：`06` L1114；`07` L274、L363–370、L403、L497、L500、L897；`10` L210、L442、L648、L1249；`13` L361；`16` L479；`15` L2290。
- **期望的回答形态**：在 `07` L500 中二选一：
  - **删除**“以及验收与 seal 时的完整重哈希验证”（验收要求指纹等于决定性验证的 pin，后者有包时已永久保留），并在 `06`、`10`、`13`、`16` 的复述处同步删除；
  - **或写明**验收与 seal 闸口写什么：例如只写一条 Fact 并为已验收的 pin 写保留 ref，不写重放包；给出 ref 名。
  - 同时把缓存命中的前提统一为一种写法，并指明是哪一个日志文件（例如“§7.4.4 的完整日志仍在”），`07` L403、L897 改为引用。

**R59-D7-02｜次要**（覆盖哨兵使 Goal 经继续目标 `review{in_review, pin}` 进入 `in_review` 时，这次验证的结论标签没有写入点，也没有写它是否算归因窗口中的“通过”）

- **问题**：
  1. **标签没有写入点**：
     - `07` L1616–1620：有阻断命中时，`decide()` 在计算 `label` 之前就返回 `paused(sentinel_high)`。
     - 覆盖后，`06` L928 把继续目标改写为 `review{in_review, pin}`；`07` L1678 规定该目标“回到 `state`，不验证”。全程没有任何一步计算或存储 `label`。
     - **但标签有消费者**：
       - 徽章（`12` L245：⑦“哨兵已覆盖”对应 `▲*`）；
       - 验收闸的书面确认（⑦ 属于需要确认的条件）；
       - seal trailer：只有 `verified`/`verified_qualified` 写 `Tower-Verified-At`，其余写 `Tower-Not-Machine-Verified`（`10` L636、`06` L132）。
     - `04` L1371 只在“全部通过”的情形下写“进入 `in_review`，显示 `▲*`”。`sentinel_high` 同样可以在 `no_machine_criteria`、`exec_not_run` 时进入（`07` L1615），这时应为 `◬`“未经机器验证”，正文没有写。
  2. **是否算“通过”**：
     - 归因窗口的起点是“最近一次通过的验证——该次验证的结果使 Goal 进入 `in_review`”（`03` L71、`16` L38、`07` L1651；`07` L1587 的 `lastPassedVerifySeq` 没有定义）。
     - 被覆盖的验证本身的结果是 `paused`，是之后的决定使 Goal 进入 `in_review`。它算不算通过，决定了之后一次失败是自动返工，还是 `human_change_verify_failed`。
     - `s0.deny` 改写为 `review{in_review}` 的路径（`06` L899）也有同样的问题。
  - **两种实现**：
    - 覆盖时按“去掉已覆盖命中后的 `decide()`”计算标签并存储；
    - 不存储标签，界面按 `▲*` 一律显示。
    - 后者在 `exec_not_run` 的情形下，会让未经机器验证的 Goal 显示有保留的已验证字形，并写入 `Tower-Verified-At`。这与 `07` L953（只有 human 标准的 Goal “永远不显示已验证”）及 ADR-108 的 trailer 规则相悖。
- **为什么是次要**：多数实现者会自然地按 ⑦ 与 outcome 计算标签。触发需要“阻断哨兵 + 人覆盖”，且后果限于显示与 trailer，不越过验收闸。但它是一个缺失的写入点，并且一种读法会让诚实语法失真。
- **文档位置**：`03` L71、L84；`04` L1371；`06` L132、L899、L928；`07` L953、L1587、L1615–1627、L1638、L1651、L1678；`10` L636；`12` L245；`16` L38、L53。
- **期望的回答形态**：
  - 在 `07` §7.10.3（唯一定义）写明：
    - 覆盖使最后一个阻断命中解除时，同一事务按该次验证的 outcome 计算并存储 `label`：`pass` → `verified_qualified`（⑦ 成立）；`no_machine_criteria`/`exec_not_run` → `not_machine_verified{…}`。
    - 这次验证按“通过”计入归因窗口，序号取覆盖决定的事件序号或该次验证的序号，二选一写明。
    - `s0.deny` 路径同理。
  - `06` L928 与 `04` L1371 改为引用。

### D8 注意力与交互

**R59-D8-01｜次要**（`08` §8.8 的结果定类：ADR-186 在 `budget` 行把“放弃”同时放进 actionable 与 informative 两栏；新加的通用放弃规则与 `verify_failed` 行的“选择任意处置选项 → actionable”冲突；另有几个出口在任何一行中都没有定类）

  1. **`budget` 行（`08` L502）两栏并列**：

  3. **没有定类的出口**：

  - **其他核对**：
    - lint 全部通过（exit 0；ADR 186，(v) 96 条命令，(e) 165 对，(D) 118 个短语，(z′) 19 处，(T) 8 种，(F) 1 条，(M) 1 个）。

  - **不扣分的观察**：
    1. **内存算例与公式**：
       - `07` L965 的重项目一行仍写“3.6 + 0.6 + 2 × 4.6 = 13.4 GB”，应为 0.65 与 13.45（结论 c = 1 不变）；
       - `07` L961–962 的公式只计“Σ Goal 进程树预算 + Tower 本体”，而 `13` L194 的每 Goal 预留是 Host `h` + `p90_g`，L964 的算例也未计 `h`。参考配置下 3 × 0.12 GB 不改变结论，E6 回填时建议一并对齐。
    2. **开场触发列表**：`07` L1685 仍写“任何 Run 开始时（由 `run` 目标或 `pendingHandBack{continue_agent}` 触发）”，没有自动返工与 `request_changes`。总规则在 `06`、`16`，建议改为引用。
    3. **单向门确认摘要**：`16` L914 的 `⌘↩` 行仍只写“按住确认 1.5 s 或输入目标名”，没有动作类名的回退（同节 L949 已有）。
    4. **重放保留的复述**：
       - `14` L215 的第 58 轮增量段写“缓存命中引用的原日志按非永久规则保留”，`07` L500 与 `16` L558 写“按原验证的保留期保留”（原验证为决定性时是永久的）；
       - `06` L1114 的非永久列表漏了“以阻断结束的验证”（括注已说明）。
    5. **`03` 正文中未标 M2 的残留**：L78（从 `accepted` 接管后“不重新进入合并队列”）、L110（I2 中的“合并队列的重放”）、L147（验证步骤中的“冲突雷达”）。(z′) 不覆盖 `03` 的正文。
    6. **`07` §7.11.3 的里程碑**：检测器的自动降级与两类豁免提议没有 M2/M3 标记，`16` L707 也没有。`14` L189 的范围规则与 `08` L552 已把自动调节排除在 M1 之外，`07` L1737 已把项目豁免标为 M3。建议在 §7.11.3 标题处补标。
    7. **诊断视图的按键**：`04` L697–704 的诊断视图使用 `/`、`O`、`↩`，`16` §16.3 中 `/` 只登记“列表”，`O` 与 `↩` 没有轨迹 / 诊断作用域；`04` L1420 说“线框中的按键提示均取自该表”。与第 58 轮观察 10 同类。
    8. **⑨ 的措辞**：
       - `07` L1621 写“只作徽章”；L1632、L1634 与 `04` L540 写“只作标签”。而 `label` 是一个具体字段，延续回到 `accepted` 时为 `verified`。
       - `12` L245 把“延续验收”列在“有保留的已验证”的徽章中，显示由 `12` L248 的 `●*` 规则决定。
       - 建议统一为“徽章”。
    9. **来源计数**：`11` L218 写“只有四种来源”，列出的是四组、五个来源（`builtin:codemode` 与 `builtin:tool-search` 合为一组）；ADR-186 写“五种”。措辞问题。
    10. **合同编辑器的有效级别**：`floor` 使合同中低于下限的值“不生效”（`02` L318、`11` L103）。建议合同编辑器在这些格上显示有效级别 `ask`，或禁用更低的选项，以免人以为放宽已生效。
    11. **空匹配器的授权**：`11` L242 规定空匹配器不匹配。Harness 生成不出匹配器时（例如程序位置是变量的 `opaque` 调用），“本 Goal 内同类”给出的授权永远不会生效。建议此时只提供“仅这一次”。
    12. **变更类判定信任注解**：`16` L122 的只读白名单仍接受“声明 `readOnlyHint:true` 且通过路径检查的工具”，而 ADR-186 的门禁不看注解。两者用途不同（提交有效性与检查点预筛，不是授权），验证针对的是 pin，诚实性的影响有界。建议写一句说明这一不对称。
    13. **终态 Goal 的开场队列**：队列在归档或放弃后保留（`16` L36），`04` L1017 只以 N > 0 决定是否显示，`06` L873 的撤回命令没有状态守卫。终态卡片上 `下次运行时送出` 不再成立，建议终态时隐藏该行或改为“未送达”。
    14. **阶段与 drain 中的来源豁免**：`11` L254 的 `towerLevelBySource` 在阶段检查与 draining 分支之前返回。因此塑形或评审阶段中，`tool_search` 仍可改变可见工具集；codemode 容器可以启动，但它的嵌套调用照常被拒绝。没有越权，建议在 `05` §5.6.5 第 1 步注明。
    15. **取舍判断**：ADR-186 的重放证据改弱、开场队列保留、`tool.external` 非单向门与名字授权，都写得诚实、方向偏严，可以接受，判断见 §3.3。
- **设计是否完成：主干已收敛。** 第 58 轮的全部条目与观察都已落地，ADR-186 的“改弱但为真、删除机制、单一守卫”在各文档中一致，没有引入状态、事件或表。剩下 7 条次要条目分两类：
  - **ADR-186 的衍生后果**：按来源判定对 Tower 自身协议与差异表的影响（R59-D5-01、R59-D1-01）；唯一定义中残留的不可能承诺（R59-D7-01）；§8.8 的双重定类（R59-D8-01）。
  - **前几轮没扫到的旧处**：验收但不合并的命令（R59-D4-01）；`request_changes` 的 run 类守卫（R59-D6-01）；覆盖后的标签写入点（R59-D7-02）。
  - 都可以用一条规则、一处守卫、一个命令或一处删除关闭，不需要改变架构。
- **下一轮建议**（按优先级）：
  1. **R59-D5-01、R59-D1-01**：Tower 工具生效来源的启动自检、以来源指称内置工具；`00` §0.5.1 补两行。
  2. **R59-D7-02、R59-D7-01**：覆盖时存储标签并定义“通过”；删除或定义验收与 seal 的重放包子句，统一缓存命中前提。
  3. **R59-D6-01、R59-D4-01、R59-D8-01**：run 类阻断守卫；归档命令；§8.8 定类。

  **工时与排期**：W3、W6、W9b 各约 0.01，其余不足 0.01 或为 0。W3 落在系统线上（余量 0.12），应按 ADR-136 改派。预计 M1 仍可维持 38 周（2027-07-30），以修订后的 ADR-133 补记为准。
