# 对抗评审 · 第 7 轮

> **评审者**：独立对抗 Agent，未参与写作。
>
> **评审对象**：`docs/00`–`docs/16`、`README.md`、`research/pi-release-diff.md`、`research/git-isolation-experiment.md`；`reviews/round-6.md`、5 份第 6 轮回应、`round-6-lint.md`。
>
> **核对依据**：
> - Pi 发布标签 `v1.2.0`（`git -C research/pi-mono show v1.2.0:<path>`）：`core/package-manager.ts`、`core/resource-loader.ts`、`core/settings-manager.ts`、`extensions/mcp/runtime.ts`。
> - 本机最小核对（git 2.56.0、APFS、macOS `sandbox-exec`，均在 `/tmp` 中完成并已删除）。只核对防御机制的前提是否成立，正文只写结论：
>   1. 设置了 `GIT_CEILING_DIRECTORIES` 时，位于天花板**之下**、具有裸仓库布局的子目录仍会被 git 识别为仓库（天花板只阻止越过它向上发现）。
>   2. git 为它派生的子进程（别名、`rebase -x`、`bisect run`、钩子）把自身的 exec-path 放在 `PATH` 首位，而该目录中有 `git` 可执行文件。
>   3. 对照项（不构成问题）：在大小写不敏感的 APFS 卷上，Seatbelt 的 `regex` 拒绝规则对名称的大小写变体同样生效，所以“任意深度不可创建 `.git`”在 macOS S2 下没有大小写旁路。
>
> 本文只在设计层面描述问题：涉及哪条边界、需要什么前提、会有什么后果、期望怎样缓解。不包含复现步骤。行号以本轮读到的文件为准。

## 1. 总评

第 6 轮的三条实测问题都已实质处理：

- ADR-089 取消了 gitdir 写入白名单，G24 覆盖常用 git 操作全集。
- `10` §10.1.3 把 Tower 对 Agent 可写路径的原始文件操作收敛为“创建 / 整体删除 / 整体重建 + 不跟随符号链接”。
- 安装器拆成四段，depcache 的来源记录入库；重放包分层保留，并计入磁盘预算。
- `goal.resume` 的分派以 `03` 为唯一来源。

本轮没有阻断级问题，但有两条新的设计前提不成立：

- **ADR-089 的边界前提过强**。它认为“只要工作目录中没有 `.git`，S2 下就不存在可被沙箱外发现的仓库”，但这一前提忽略了 git 的裸仓库发现。
- **ADR-090 假定 git 的嵌套调用会经过垫片**。实际上 git 会把自身的 exec-path 放在子进程 `PATH` 首位，嵌套调用不经过垫片。

另有几处缺口：

- 安装阶段对共享缓存的写范围，与 ADR-092 的“只写暂存目录”矛盾。
- 运行器身份只校验“内容来自某个注册表 tarball”，不校验“是不是同一个包”。
- “我来改”从评审中发起后，放弃改动没有回到评审的路径。
- Pi 包内的技能仍不可读。

### D2 Pi 哲学契合度

**R7-D2-01｜重要**（R6-D2-01 的残留）

- **问题**：ADR-091 的读允许列表只覆盖 `~/.pi/agent/{skills,prompts,extensions}` 与 `~/.agents/skills`。Pi v1.2.0 中技能还有三个来源，都不在列表内：
  - 用户级 **Pi 包**：npm 包在 `~/.pi/agent/npm/`，git 包在 `~/.pi/agent/git/<host>/<path>`；临时包在 `~/.pi/agent/tmp/`。
  - settings 中 `skills` 数组声明的**任意路径**（`settings-manager.ts` L1109）。
  - 受信任项目的 `.pi/npm`、`.pi/git`：它们在卫星内，可读。
- **后果**：
  - 对包内技能，`read` 加载 `SKILL.md` 会被归为 `read.external`（标准修复预设下为 ask），技能脚本在 S2 中会被读拒绝。这正是第 6 轮指出的“技能静默失效或刷屏 ask”，只是换成了包分发的技能。
  - `00` §0.5.1 的差异行只写了两个目录，没有登记这一点；`05` L1232 仍写“技能在 S2 下照常可用”。
- **为什么重要**：Pi 包是 Pi “Adapt Pi to your workflows”的正式分发途径。包内技能失效与 README 第 8 点的承诺不符。
- **文档位置**：`15` ADR-091；`11` §11.1 L30、§11.6.2 L333；`05` L387、L1232；`00` §0.5.1 L86；`14` A11。
- **期望的回答形态**：
  - 允许列表按 Pi 资源加载器实际解析出的技能目录生成：会话启动时由 Host 枚举已启用技能的 `baseDir`，取 `realpath` 后加入只读允许列表。这样比维护固定目录清单更贴近 Pi 的行为。
  - 或者在 §0.5.1 如实登记“包内技能与自定义路径技能不可用”。
  - A11 增加“npm 包内技能”“settings 自定义路径技能”两个用例。

### D4 领域模型与生命周期

**R7-D4-01｜重要**

- **问题**：ADR-094 的转移只覆盖了“交还”这一条出路。
  - **(a) 放弃改动后回不去**：从 `in_review`/`accepted` 接管后，如果人选择“放弃改动”，Goal 会回到 `paused(human)`（`10` L585、`04` L581：“可直接继续”）。而 `human` 原因的出口只有 `→ running`（`resume`，开一个 Agent Run）与 `→ verifying`（`hand_back`，要求 `humanCheckout` 存在，`06` L780）。`takeoverFrom` 被记录了，却不作为出口（`02` L146 写它只“用于展示与审计”）。结果是：评审者打开“我来改”看了一眼后放弃，Goal 就离开了评审，只能让 Agent 再跑一轮，或者对未变化的内容重新验证。
  - **(b) 检验检出的“带回”没有命令与转移**：`10` §10.8.3 第 7 步与 `04` §4.6.6 第 6 步规定“作为人工改动带回目标（走 §10.8.4 第 5–8 步）”。但第 5–8 步的前提是 `paused(human)` 加上 `humanCheckout`，而检验期间 Goal 仍在 `in_review`。`06` §6.4.3 没有对应命令，`HumanDecision.kind` 中也没有对应值，从 `in_review` 出发的这条转移未定义。
  - **(c) 交还后，与旧 pin 绑定的叠加原因会过期**：`take_over` 会把原暂停原因放进 `also_applies`（`06` L779），交还后“`also_applies` 非空时 Goal 保持 paused”（`06` L780）。但 `sentinel_high`、`verify_failed_limit`、`verify_env_error`、`s0_grant_pending`、`human_change_verify_failed` 都是针对旧 pin 的判定。人的改动写回卫星后，这些原因已经过期。此时：
    - Goal 停在一个指向旧 pin 的原因上；
    - 人在交还对话框中选择的“直接重新验证”被吞掉。
  - **(d) 接管期间的系统动作**：`humanCheckout` 存在期间，`10` §10.10 的“Run 空闲点”（含 `paused`）自动 rebase 是否暂停没有写明；从 `accepted` 接管时，Goal 若已在合并队列中，是否出队也没有写明。按现规格，自动 rebase 会改写卫星，交还时第 6 步因此报出“卫星在你编辑期间被改动”。
- **为什么重要**：这些都是 `transitions.ts` 必须实现的边，而“我来改”是最常用的交接动作之一。(a) 还会在用户没有要求的情况下开出 Agent Run，违背 Needs-You 纪律。
- **文档位置**：`03` §3.2.1 L68；`06` L136、L779–780；`10` §10.8.3 第 7 步、§10.8.4 L585、§10.10、§10.11；`04` §4.6.6 第 6 步、§4.6.7 L581；`02` L146。
- **期望的回答形态**：
  - 增加 `goal.discard_human_edits` 命令：若 `takeoverFrom ∈ {in_review, accepted}` 且卫星树仍等于 pin 的树，直接回到 `takeoverFrom`（I2 不触发）；否则按现规则处理。
  - 为“检验带回”定义命令，例如 `inspect.bring_back`：`in_review/accepted → verifying{human_change}`，以 `T_pin` 为基线。
  - 规定交还时与 pin 绑定的 `alsoApplies` 原因一律清除（新 pin 会重新判定），只保留与 pin 无关的原因（如 `budget_*`、`app_quit`）。
  - `humanCheckout` 存在期间暂停自动 rebase，并把 Goal 移出合并队列。
  - `03` §3.2.1 的 `human` 行补上这些出口。

### D5 Agent 架构与 Pi 集成

**R7-D5-01｜次要**（自第 5 轮起的残留）

- **问题**：
  - `05` L373 写“HTTP 服务器沿用 `StreamableHttpTransport`”。但 v1.2.0 的默认传输工厂会向 HTTP 传输传入 `authProvider`（`extensions/mcp/runtime.ts` L59–63、L99–121、L187），Tower 的 `createTransport` 骨架没有写明这一点。需要 OAuth 的 MCP 服务器在 SDK 宿主下会因此失效。

- **期望的回答形态**：骨架中写明 HTTP 分支透传 `authProvider`（复用 Pi 的 OAuth 存储），C21 增加一个 OAuth MCP 用例；ADR-065 正文加修订注。

### D6 系统架构与可靠性

**R7-D6-01｜次要**

### D7 诚实与验证

**R7-D7-01｜重要**

- **问题**：ADR-092 的基准只证明运行器文件“等于 lockfile 中记录的那个注册表 tarball”，不证明这个 tarball 就是“项目一直使用的那个运行器”。下面几种改向都不在 (a') 的检测范围与 protected 默认值内：
  - **(a) 包名别名**：lockfile 或 `package.json` 把运行器名映射到注册表上另一个包（`npm:` 别名）。integrity 校验能通过，基准也来自这个 tarball，`runner_tampered` 与 `runner_patched` 都不会触发。
  - **(b) `pnpm-workspace.yaml` 中的设置**：pnpm 10 起，`overrides`、`patchedDependencies`、`packageExtensions` 等可以写在 `pnpm-workspace.yaml` 中（请以 SP6c 的版本矩阵核实）。`02` L248、`11` L206 只保护 `package.json` 中的同名键；(a') 的措辞也没有指明文件。`pnpm-workspace.yaml` 进入了 `depsKey`，但它不是 protected。
  - **(c) 非注册表 tarball URL**：lockfile 中的 `resolution.tarball` 指向任意 HTTPS 地址。拉取阶段的网络限制会使其失败，这一点值得写明作为依据；但如果用户的注册表允许列表包含通用代码托管域名，就挡不住。
  - **(d) `allowNewDependencies=true` 时运行器版本的变化**：只记 severity 1 的 `lockfile_drift`。
- **为什么重要**：运行器完整性是“Verified 可信”的根。这些改向不需要任何沙箱逃逸，也不会被哈希比对发现。
- **文档位置**：`07` §7.4.3 L469–470、(a)(a') L506–515；`02` §2.5 L248；`11` §11.3.3 L206；`15` ADR-092；`14` P32/P33。
- **期望的回答形态**：
  - 运行器身份 = (包名, 注册表来源, 版本)，以 base 的 lockfile 为参照：运行器集合中任何包出现别名、来源不是已配置的注册表、或版本相对 base 变化，都记 `runner_patched`（版本变化可以降为提示，但必须显示）。
  - protected 默认值加入 `pnpm-workspace.yaml` 中影响解析的键。
  - SP6c 增加“`npm:` 别名运行器”与“`pnpm-workspace.yaml` overrides”两个用例。

**R7-D7-02｜重要**

- **问题**：ADR-092 规定安装阶段（I-install）只写本次运行的暂存目录，`$VS` 其余部分只读。但：
  - **(a) 唯一来源仍写着读写**：`16` §16.8.1 的 I 列把 `$VS/pnpm-store`、`pnpm-cache`、`pnpm-state`、`npm-cache` 标为“读写”；`$VS/xdg` 一行明写“读写（安装阶段）”；`$SH/node-gyp` 标为“读写”。§16.8 的角色说明用一句“凡涉及写 `$VS` 的在 I-install 中只指暂存目录”笼统覆盖，没有逐行说明 store、XDG 与 node-gyp 目录在 I-install 中实际指向哪里。`$SH/node-gyp` 也不在 `$VS` 之下，这句覆盖不到它。
  - **(b) pnpm store 是跨 depsKey 共享的唯一安装输入**：pnpm 在构建依赖后，默认会把构建结果作为副作用缓存写回 store，后续安装会直接复用。
    - 如果 I-install 对 store 可写，一次安装中运行的第三方构建脚本或 `.pnpmfile.cjs` 就能影响其他 depsKey 的安装结果。这正是 R6-D7-02 要消除的跨 Goal 投毒路径，只是换成了 store。
    - 如果 store 只读，`pnpm install --offline` 与 `rebuild` 在只读 store 上能否成功，又是一个未登记的前提。
  - `$SH/node-gyp` 同理：它被所有 depsKey 的原生构建以及 Agent 读取。
- **为什么重要**：depcache 是验证器的信任根。ADR-092 把边界收窄到暂存目录，但共享输入缓存这一侧没有闭合。
- **文档位置**：`16` §16.8 角色说明 L828、§16.8.1 L844–L863；`07` §7.4.3 L476–493；`15` ADR-092；`11` T7。
- **期望的回答形态**：
  - 按 I-fetch / I-prefetch / I-install 三列重写 §16.8.1 中涉及写入的行。
  - I-install 对 store、`$SH`、`$VS/xdg` 只读，并关闭副作用缓存（或使用本次运行私有的 store 叠加层，随暂存目录一起丢弃）。
  - P34 的验收增加“安装前后 `$VS/pnpm-store`、`$SH` 的树哈希不变”。
  - 在 SP6c 中实测只读 store 下的离线安装与 rebuild。

### D11 安全与自主度

**R7-D11-01｜重要**

- **问题**：ADR-089 把沙箱外不可发现的边界建立在“工作目录任意深度不可创建 `.git`”加上 `GIT_CEILING_DIRECTORIES=<wtRoot>` 之上，并据此断言“S2 下不存在嵌套仓库，也不存在可被沙箱外发现的仓库”（`10` L28）。这个前提不完整：
  - git 的发现不只认名为 `.git` 的条目。一个本身具有裸仓库布局的目录，也会被识别为仓库；而 git 默认允许裸仓库发现。
  - `GIT_CEILING_DIRECTORIES` 只阻止越过天花板向上发现，对天花板之下的目录不起作用。本轮已用最小实验确认：天花板之下的裸仓库布局目录仍被识别。
  - 因此，Agent 可以在卫星中写出不含任何 `.git` 条目、却能被 git 当作仓库的目录。凡是沙箱外的进程以该目录（或其子目录）为工作目录运行 git，都会读取其中 Agent 可控的配置——这正是 ADR-081 要消除的那一类问题。可能这样做的进程有：
    - 用户扩展的 `pi.exec` 与 MCP git 服务器：它们的路径参数常由 Agent 给出；
    - 人在人工编辑检出、检验检出中的终端提示符与 IDE：两种检出都会复制这个目录；`10` L566 与 ADR-081 第 4 点“人的 IDE 与 shell 在其中运行 git 是安全的”只对检出的根目录成立；
    - 集成之后用户自己的主检出。
  - ADR-071 的嵌套仓库扫描、`nested_repo` 哨兵与 T29 都只按名为 `.git` 的条目判定。ADR-072 第 4 点注入的 `GIT_CONFIG_*` 只中和了两个键，`05` 也已明确它“不是安全边界”。
- **为什么重要**：这条缺口与 R5-D11-01 属于同一类，只是前提更窄（需要沙箱外的进程在子目录中运行 git）。它使 ADR-089 的核心不变式在 S2 下也不成立；而缓解成本很低。
- **文档位置**：`15` ADR-081 第 2、4 点，ADR-089 第 2 点；`10` §10.1 L28–29、§10.1.2 L74、L76、§10.3.1 L199、§10.8.3、§10.8.4 L566；`11` T29 L545、T31；`05` §5.3.5 L373；`14` G26。
- **期望的回答形态**：
  - 所有由 Tower 构造环境的沙箱外 git 使用者，都在受保护的配置作用域（命令行 / `GIT_CONFIG_*`，属于 git 认可的受保护作用域）中设置“只允许显式指定的裸仓库”（`safe.bareRepository=explicit`，git ≥ 2.38，最低版本 2.40 已满足）。这些使用者包括：Host 及其派生进程、MCP 传输的基础环境、检验终端与人工编辑终端的白名单环境。
  - 把“嵌套仓库”的定义从“名为 `.git` 的条目”扩展为“git 会识别为仓库的任何目录”（含裸仓库布局）。ADR-071 的扫描按这一定义判定，命中即记 `nested_repo` 并在评审中列出；交接前的信任提示也列出这类目录。
  - 在 `00` §0.5.1 或信任提示中建议用户在全局配置中启用同一设置，因为集成后的用户检出不在 Tower 的控制之下。
  - SP6b 增加一个用例：在 S2 下写出裸仓库布局目录后，扩展与 MCP 环境中的 git、两种检出中的终端，都不会把它当作仓库。

**R7-D11-02｜次要**

- **问题**：
  - **(a) GitRunner 读取 Agent 拥有的 gitdir**：`10` §10.1.3 L90 规定 Tower 在“只允许执行 git”的沙箱中，以 `--git-dir=<卫星 gitdir>` 运行 `rev-parse` 与 `log`，并限定了写范围为空、无网络。但读范围没有限定，而这时 git 会读取该 gitdir 中 Agent 可控的本地配置（包括 include 指令）与 `objects/info/alternates`。第 6 轮曾提醒“Tower 若经 alternates 读卫星对象，git 会递归跟随”；ADR-089 让 alternates 成为 Agent 可写之后，这一读取路径的读范围就需要明确。产出（seal 说明中的提交信息）会进入用户仓库与 PR 正文。
  - **(b) 扩展目录对 Agent 静默可读**：ADR-091 把 `~/.pi/agent/extensions/**` 也设为 silent 可读，但 Agent 并不需要读取扩展源码——扩展由 Host 加载。用户扩展目录中常有该扩展自己的配置或密钥。这一项扩大了读面，却没有说明用途，也没有说明是否做密钥扫描。
- **为什么重要**：(a) 是 Tower 进程作用于 Agent 可控元数据的最后一处；(b) 与 ADR-082 收紧读权限的方向相反。
- **文档位置**：`10` §10.1.3 L90；`15` ADR-089 第 3 点、ADR-091；`11` §11.6.2 L333。
- **期望的回答形态**：
  - (a) 这两次读取的沙箱读范围 = 该 gitdir 加镜像的 `objects/`，并说明本地配置中的 include 与 alternates 如何被中和（或改为由 Tower 自己解析 `HEAD`，只读普通文件、带大小上限）。
  - (b) 从允许列表中移除 `extensions/**`，或说明用途并对其中的文件施加密钥扫描与读拒绝规则。

### D13 隔离、git 与并发

**R7-D13-01｜重要**

- **问题**：ADR-090 的剥离规则依赖“嵌套的 `git` 调用会再次经过 `PATH` 首位的垫片”。但 git 在派生子进程（`rebase -x`/`--exec`、`bisect run`、钩子、`!` 别名、外部 diff 与 difftool）时，会把自身的 exec-path 放在 `PATH` 首位，而该目录中有 `git` 可执行文件。本轮已用最小实验确认这一顺序。
  - 因此，在 ADR-090 列举的典型场景中，嵌套的 `git` 直接解析为真实 git，继承来的 `GIT_DIR`/`GIT_WORK_TREE` 没有被剥离。
  - ADR-088 要消除的问题（测试夹具中的 `git init`/`commit` 作用到卫星 gitdir、污染卫星分支）在这些路径上依然存在。
  - 后果限于本 Goal 自己的卫星，不越过沙箱边界。但 `10` §10.6.1 L378 的例子与 G20 的验收预期（“`/tmp/x` 成为独立仓库，卫星 gitdir 未被重新初始化”）是按“垫片生效”写的。G20 会失败，而设计没有备选方案。
- **为什么重要**：这是第 6 轮实测问题的修复，修复依赖的机制前提与 git 的已知行为相反；G20 失败会阻塞 M1 冻结（`14` L31）。
- **文档位置**：`15` ADR-088、ADR-090；`10` §10.6.1 L373–388；`00` §0.5.1 L84；`14` G20、K22；`16` §16.8 `PATH` 行。
- **期望的回答形态**：
  - 选定一种不依赖 `PATH` 顺序的机制并论证。例如：垫片执行真实 git 时把 `GIT_EXEC_PATH` 指向 Tower 生成的 exec-path 覆盖层（与 git-core 内容相同，只把 `git` 换成垫片）；或用其他方式保证 git 派生的子进程仍先解析到垫片。
  - 写明该机制在 git 2.40、Apple 自带版本与最新版上的验证方式。
  - 如果最终放弃拦截，就在 §0.5.1 与 K22 如实登记“git 派生的子进程中的 `git init`/`commit` 会作用到卫星”，并修改 G20 的验收预期。

**R7-D13-02｜次要**

- **问题**：多仓库回退（lint U1 的裁决）只写在 `06` L790–791：
  - **(a) 没有检查点祖先的仓库**：某个仓库在该 `piEntryId` 路径上没有任何带检查点的祖先时（例如它的第一次改动发生在该条目之后），应恢复到 `baseCommit`，但没有写明。
  - **(b) `10` 未同步**：`10` §10.13 与 §10.8 没有同步这条规则，而 `06` 声称引用的正是 §10.13。
  - **(c) 降级档位下的语义**：在 `10` §10.7.2 的降级档位（每 3 个有变更回合才打一次检查点）下，“最近的带检查点祖先”不再等于该条目时刻的代码状态。回退界面没有提示这一近似。
  - **(d) 多仓库下的上下文与信任**：多仓库 Goal 的 Pi cwd 是 `~/.tower/goals/<goalId>/ws/`（`10` §10.13），各仓库的 `AGENTS.md` 不在它的祖先链上，ADR-091 的祖先上下文规则因此不覆盖它们；项目信任的复核在单一 cwd 下按哪个 binding 求值也没有写。这些属于 M3。
- **为什么重要**：回退是“看见 Agent 做了什么并撤销”的核心动作；近似必须如实呈现。
- **文档位置**：`06` L790–791；`10` §10.7.1、§10.7.2、§10.8、§10.13；`15` ADR-091。
- **期望的回答形态**：在 `10` §10.13 写出逐仓库的恢复规则（含回落到 `baseCommit`）；降级档位下回退界面标注“恢复到第 n 回合的最近快照”；在 M3 范围说明中登记多仓库下的上下文文件与信任求值规则。
