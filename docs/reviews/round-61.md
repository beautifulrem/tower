**ADR-188 的主干没有引入回归**：
- **S0 拒绝走 `decide()`**：
  - `07` L416–419（`verify()`）与 L1572–1575（`decide()` 注释，唯一定义）给出同一条路线：拒绝只解除本原因，继续目标仍为 `verify{pin}`；重新验证经 `denied` 分支，以 `{execSkipped:"s0_denied", by}` 回到 `decide()`，失败与阻断都在 `in_review` 之前判定。
  - `03` L58、L87，`06` L271、L899，`05` L990，`08` L448，`04` L832–834、L1500，`12` L456，`16` L32、L53 都改为引用这一定义；`16` L573 登记了被取代的说法。
  - 逐条探查了以下路径，结论都是**没有**一条路线能让带未覆盖阻断命中的 pin 进入 `in_review` 或 `accepted`：
    - **另有原因**：拒绝时 `s0_grant_pending` 只在 `alsoApplies` 中，继续目标照样不变。
    - **其他原因改写继续目标**：`keep` 改写为 `verify_new`，以新 pin 经同一 `denied` 分支验证；`revert` 不改写；修订标准只改写 `review`；交还删除 `s0_grant_pending`，新 pin 在 `s0Grant=pending` 时重新进入等待；放弃改动不改写。
    - **覆盖哨兵**：`override_sentinel` 只在 `paused(sentinel_high)` 中把继续目标改写为 `review`。`sentinel_high` 不会与 `s0_grant_pending` 同时成立：`decide()` 在 S0 等待处提前返回；`nested_repo_live` 不可覆盖。
    - **崩溃恢复**：`06` §6.1.6 的 `verifying` 行以同一 pin 重跑，仍走 `denied` 分支。
    - **缓存**：`07` L404–405 规定 S0 的两处返回都不记录命中。重新验证不复用 exec 结果；全部命中且 `runnable` 为空时在 S0 判定之前返回，本来也不执行 exec。
    - **标签**：`by` 由 `s0Grant` 推出，`denied_timeout` → `timeout`。验收延续要求 `outcome == pass`，所以从 `accepted` 来的这次验证总是进入 `in_review`。
    - **归因**：失败时按窗口判定。G46(bf)(1) 的四组期望与 `decide()` 一致。
- **Tower 工具来源自检**：

**新发现 5 条：重要 1，次要 4**：
- **重要**：
  - Pi v1.2.0 另有一个内置 shell 工具 `powershell`，默认不经沙箱执行。用户的默认工具设置包含它时，`running` 阶段保留它（`05` L679）。门禁按来源把它当作 Pi 内置工具，按 `bash` 的规则、以 Goal 的沙箱档位求值（`11` §11.3.2 标题“`bash`（及 `powershell`）”、L218、L257，`16` L259）。所以 S2 下 `exec.test`/`exec.build` 为 silent，而实际在沙箱之外运行 Agent 写的代码，也不经 S0 授权（R61-D11-01）。
- **次要**：
  - SDK 下传给 `bindExtensions` 的 `commandContextActions` 没有定义。扩展可以在 Run 中途触发自己的命令，调用重载或替换会话；Run 开始时的各项复核不会重做（R61-D5-01）；
  - M1 验收写分支失败时没有去向：Goal 已在 `accepted`，从 `accepted` 归档的前提“seal 分支已写”没有守卫。ADR-188 承诺的“已验收的改动总能从用户仓库取回”因此在失败时不成立（R61-D13-01）；
  - `prepare_failed` 的新来源 `running` 没有进入 `16` §16.1.1 注册表、`stalled` 子类型行、`08` §8.6.5 自称“统一”的定义和 `06` F4b。中途被遮蔽时卡片沿用“启动失败 / 重试（从已完成的步骤继续）”（R61-D15-01）；
  - 线框按键提示与 `16` §16.3 不一致：评审模式写 `E 我来改（M2）`，注册表为 M1；目标页 `[交还 ⌘↩]` 的作用域没有登记（R61-D15-02）。

### D5 Agent 架构与 Pi 集成

**R61-D5-01｜次要**（SDK 下传给 `bindExtensions` 的 `commandContextActions` 没有定义；扩展可以在 Run 中途触发自己的命令，调用 `reload`、`newSession`、`fork`、`switchSession`。Tower 对此没有规则，Run 开始时的复核不会随之重做）

- **问题**：
  - **正文**：
    - `05` L265 与 L376 的骨架把 `commandContextActions` 传给 `bindExtensions`，全文没有定义它的内容；
    - `05` L280 只规定 **Tower 自己**替换 runtime 后要重新绑定；L949 的 `/tower-nav`、`/tower-fork` 只用于 RPC。
  - **Pi 的行为**（v1.2.0，文首核实）：
    - 这些动作由宿主提供，不传时为空操作（`runner.ts:553-570`）。Pi 自己的 RPC 模式把它们接到真实的重载与 runtime 替换（`rpc-mode.ts:322-343`）；Tower 传的 `mode:"rpc"` 与这种接法同形，照抄 RPC 模式是自然的实现。
    - 扩展可以经 `sendUserMessage` 触发自己的命令，命令在流式中也立即执行（`agent-session.ts:2053-2068, 2390-2420`）。官方示例中就有可被模型调用的工具排队触发重载（`examples/extensions/reload-runtime.ts`），以及调用 `ctx.newSession` 的扩展（`handoff.ts:177`）。
    - `reload()`（`agent-session.ts:3685-3721`）会重读设置与资源、重建扩展运行器并再次发出 `session_start`。
  - **缺失的规则**：
    - Run 开始时的复核都只对 Tower 启动的那个会话成立：静态清单的哈希确认（`05` L1292“确认之前不加载”）、项目信任的复核（`11` L563，`resolveProjectTrust` 读的是 Run 开始时求得的 `spec.projectTrust`，`05` L352）、沙箱 bash 与 Tower 工具的来源自检、处理器顺序；
    - 如果这些动作接到真实实现，Run 中途的重载会以过时的信任结论加载资源，加载确认之后才出现或改动的扩展代码，并重建 tower-goal 实例（gate 的内存状态，例如 `approvedInput`，随之丢失）；会话替换会让 Tower 的会话记账与实际会话脱节；
    - 如果接成空操作，扩展会在没有提示的情况下“成功”返回，行为也没有写明。
  - **两种实现**：照抄 Pi 的 RPC 模式接到真实动作；或接成空操作或拒绝。两者的安全性质不同，正文都允许。
- **为什么是次要**：
  - 触发需要一个会调用这些动作的用户扩展；用户扩展本来就以用户权限在宿主中运行，是经确认的代码；
  - 要把 Agent 写的扩展代码加载进来，还需要沙箱外的写入（S0 且受保护路径的写入经批准）。
  - 但这是一条“运行中改变 Run 开始时前提”的路线，正文对它没有任何规则，而且 Pi 的官方示例把它当作正常用法。
- **文档位置**：`05` L264–265、L280、L352、L374–383、L459、L949、L1292；`11` L562–563；Pi `extensions/types.ts:2239-2259`、`extensions/runner.ts:553-570`、`modes/rpc/rpc-mode.ts:322-343`、`agent-session.ts:2053-2068, 2390-2420, 3685-3721`、`examples/extensions/reload-runtime.ts`、`handoff.ts:177`。
- **期望的回答形态**：在 `05` §5.3.5 骨架处唯一定义 SDK 的 `commandContextActions`：
  - `reload`、`newSession`、`fork`、`switchSession` 不执行，返回 `{cancelled:true}` 或抛错，并 `appendEntry` 一条审计；
  - 或者把它们视为 Run 边界：drain 后暂停，下一次 Run 开始时重做全部复核；
  - `waitForIdle`、`navigateTree` 写明 Tower 的接法；
  - `00` §0.5.1 加一行能力差异；C28a 或新契约测试补一组“扩展命令调用 `ctx.reload()`”。

### D11 安全与自主度

**R61-D11-01｜重要**（Pi v1.2.0 的内置 `powershell` 工具默认不经沙箱执行；`running` 阶段保留用户的默认工具，门禁却按来源把它当作 Pi 内置工具、按 `bash` 的规则以 Goal 的沙箱档位求值。S2 下测试与构建类命令因此为 silent，实际在沙箱外以用户权限运行 Agent 写的代码，也不经 S0 授权）

  - **不扣分的观察**：
    1. **`07` L1682 `review` 行的措辞**：括注写“S0 拒绝不改写继续目标，不经本行”。但 S0 拒绝后若进入 `sentinel_high` 再被覆盖，Goal 会经本行进入评审，此时 outcome 为 `exec_not_run`，标签原因应沿用 `s0_denied{by}`。本行只写“`exec_not_run` → `not_machine_verified`”，没写原因取自该次验证。多数实现者会取最近一次 `decide` 的 `opts`，建议改为“不经本行改写；拒绝后经覆盖进入时原因沿用 `s0_denied{by}`”。
    2. **gate 的分类对象与实际执行的工具**：Pi 在 `beforeToolCall` 之前就取定要执行的工具（`agent-loop.ts:708-729`），gate 按名字查当时的注册表。同一回合内有扩展注册了覆盖内置名的工具时，内置工具这次调用会被归为 `tool.external`（ask，参数路径扫描照常），而不按文件类工具的范围规则判定。方向偏严，触发需要回合内的覆盖注册，记为已知窗口即可。会话重载使两者反向不一致的情形归 R61-D5-01。
    3. **`12` §12.6.5 的 `◆`**：L406 规定“需要人的原因同时存在一条 Needs-You，由 `◆` 表达”。`provider_unavailable` 写 `◇`，`nested_repo_live` 行只有 `■`，而 `16` L194 为前者映射了 `stalled` 条目（重试耗尽后），后者属于 `sentinel_high` → `sentinel`。lint (w′) 只检查 `◆` → kind 的方向。建议补 `◆` 或注明例外。
    4. **依赖的里程碑**：`04` L143 把“子目标与依赖”列为 M2，`14` L189 规定 ADR-059 未列者不在 M1；但 `12` §12.6.5（标 M1）的 wait `dependency` 行、`04` L173、L256 的 M1 总览线框、`06` L862 `goal.add_dependency` 都没有 M2 标记。以 `14` L189 为准不会实现错，建议补标。
    5. **`00` L66“提供‘使用我安装的 pi’模式”** 没有 M2 标记（`04` L1263、`11` L277 已标）。
    6. **需要你线框的“不会超时”**：`04` L752–753 把“不会超时”解释为“高风险目标的问题不自动作答”。按 `08` §8.7.1，“不会超时”只取决于 `unattended:"wait"`；`use_defaults` 下高风险问题显示“超时后暂停”。示例本身可以成立，解释句会误导倒计时文案的实现。
    7. **嵌套调用的发起者**：Pi v1.2.0 中任何工具的 `execute` 都有 `ctx.executeTool`（`extensions/types.ts:366-392`），不只 codemode。已批准的沙箱外工具因此可以嵌套调用 Tower 工具，gate 第 1 步按来源放行（在 drain 分支之前）。后果限于“非模型选择的提交或日志”，提交之后仍由验证裁决，不越权。建议在 `11` §11.3.4 注明，或对 Tower 工具要求父调用为空或来自 `builtin:codemode`。
    8. **G46(bf)(2) 与 C28a 的“Run 中途经扩展命令注册”**：SDK 下 Tower 不提供 `!cmd` 与斜杠命令入口，转向走 `steer`，不执行扩展命令。测试需由扩展自己经 `sendUserMessage` 触发，或在 `tool_call`、`turn_start` 处理器中注册。属于测试写法，建议注明触发方式。
    9. **取舍判断**：ADR-188 的三处删除、一条守卫、一个字段都写得诚实，方向偏严或中性，判断见 §3.3。
