## 1. 总评

**第 102 轮的 8 条条目都按所问关闭**（核对见 §3）：
- 8 条都在唯一定义处落地，引用处改为引用。
- 其中四处修法本身带出新的分支：
  - R102-D5-01 的 “有存储的凭据就不注入”，没有区分 `auth.json` 中以 `$ENV` 引用或以命令给出的条目，与 ADR-049 类型表 “配置中的 `$ENV` 引用按类别处理” 一行相撞；也没有覆盖 Pi 先后顺序中 `models.json` 的密钥一层（R103-D5-01）。
  - R102-D6-01 让 `hostExpected` 在 Run 结束时清除，但 “只重启 Supervisor 后重新接上” 这一置位分支不限于有 Run 在进行的 Goal，同一条新写的不变式在这一支上不成立（R103-D6-01）。
  - R102-D13-02 补了关闭与带回，没有补打开：使用中而目录已不存在时，`inspect.open` 照字面会在旧检验仍打开时新建一个（R103-D13-01）。
  - R102-D15-01 把 Host 环境合为一处，但 `06` L323 仍在同一句中复述并列入了端口段（R103-D15-01 (a)）。
- §5 的 10 条观察全部落地。

**对本轮重点问题的回答**：

- **工具链变量改为封闭列表：接受**。
  - 七个变量与 `16` §16.8 同一组，唯一定义写明 “其他工具链变量不传入，Host 派生的 MCP 服务器与扩展子进程看不到它们，偏严”（`05` L472）。属于已写明、合理的取舍：
    - Host 的 `PATH` 取自登录 shell，多数工具的 shim 不依赖额外变量；
    - MCP 服务器可以在 `mcp.json` 的 `env` 中写明取值。
  - 剩下三件事：
    - **用户看不到这条取舍**：`00` §0.5.1 的能力差别表与静态清单的确认卡片都没有写，记为观察 1。
    - **列表漏了 CA 证书变量**：Tower 明确让 Host 直接使用企业代理发出模型请求（`05` L474，ADR-079），而 TLS 拦截的代理需要 `NODE_EXTRA_CA_CERTS` 一类变量。封闭列表把它排除在外，这一类用户在 Tower 中的模型请求全部失败，终端中正常（R103-D5-02）。
    - **① 中工具链变量的取值来源**：首次运行记录的值与 “重新读取” 替换的值都没有列出它们（R103-D15-01 (b)）。
- **`listedAt`：接受**。
  - 它是在已有命令上加的一个字段，守卫对所针对的情形成立（见文首 “经复核不成立” 第二条）。
  - 取值是求值开始还是结束的时刻，以及建立时间在非 APFS 卷上是否可得，没有写，记为观察 2。代价只是一次多余的重新求值，不会误删。
- **存储凭据的检查与 OAuth**：成立。
  - 存储了 OAuth 凭据时 Tower 不注入。刷新或过期失败时，Pi 不回落到环境变量（`resolve.ts:27-31`），Tower 与终端同样失败，按 F7 处理。
  - ADR-230 之前导入的密钥会掩盖过期的登录，现在不会，这是改进。
- **一个 Host 承载多个 Goal**：不成立的是一句描述。
  - 正文没有写 `ModelRuntime` 是每个 Host 一个还是每个 Run 一个（`05` L486）。照 “每次 `host.spawn` 与每个 Run 之前检查” 的写法，它是每个 Host 一个。
  - 打包模式下，一个 Goal 的 Run 开始时调用 `removeRuntimeApiKey`，会使同一 Host 中另一个 Goal 进行中的 Run 从下一次请求起改用存储的凭据（Pi 每次请求都重新求凭据，`model-runtime.ts:658-697`）。这与 “正在进行的 Run 仍用已注入的密钥” 不符。
  - 后果本身无害：改用的正是终端所用的凭据。并入 R103-D5-01 (c)。
- **`removeRuntimeApiKey` 的时机与进行中的请求**：
  - 已在流式传输中的请求保留发出时的凭据，只影响之后的请求。
  - 反方向没有写：Host 运行中你在终端 `/logout`，而这次 Run 没有注入，下一次请求就判为未配置，直到下一个 Run。G46 (d) 第八组只测了下一个 Run。并入 R103-D5-01 (c)。
- **按 Run 的变量移出 Host 环境**：成立。
  - 各文档都没有写扩展、MCP 服务器或 tower-goal 从 Host 环境读 `TOWER_GOAL_ID`、`TOWER_RUN_ID` 或端口；`10` §10.19 一致，只注入 Agent 的 bash 与验证器。
  - 只有 `06` L323 的复述仍把端口段列在 Host 环境中（R103-D15-01 (a)）。

**ADR-230 的其余结构性写法成立**（§3.3）：
- 先后规则的 Pi 依据；
- bearer 令牌与原始密钥并存时只注入令牌；
- `ANTHROPIC_AUTH_TOKEN` 与 `ANTHROPIC_API_KEY` 并存时的标注；
- 存储提示的界面状态、`system` 主题、单枚 `◇` 与 `◇ N 项`；
- F8 是应用级横幅；
- 交还对话框进入加固清单；
- 按已知提交 id 停止（不取 H/.git 可改写的 reflog）、`至少 N`、`200+`；
- 求值失败的 `仍然删除`；
- `来源未知` 一类的校验；
- 使用中而检验目录已不存在时的关闭与带回；
- `mcp.log` 的登记；
- 估计独占大小的限定与求值时机；
- E6 的窗口。

**本轮扫描发现的新问题**（全部为次要）：
- **存储凭据检查的三处分支**（R103-D5-01）：
  - `auth.json` 中以 `$ENV` 引用或以 `!` 命令给出的密钥被当作 “有存储的凭据”。前者在白名单 Host 环境中解析不出，请求以 “未配置” 失败，与 ADR-049 类型表相撞，也是相对 ADR-229 的回退；
  - `models.json` 的 `apiKey` 一层：Pi 中它先于环境变量，Tower 的注入压过它；
  - 进行中的 Run：打包模式与 `/logout`。
- **Host 环境的封闭列表没有 CA 证书变量**（R103-D5-02）：TLS 拦截的企业代理下 Tower 的模型请求失败，`00` §0.5.1 只为 S2 登记了这一类。
- **重新接上的 Host 使 `hostExpected` 在没有 Run 时置位**（R103-D6-01）：Supervisor 单独重启时暂停中的 Goal 的下一个 Run 仍按 30 s 判挂死。
- **F8 的 drain 去向与只读状态的解除没有定义**（R103-D6-02）：没有对应的暂停原因，只读的数据库写不进 drain；“直到条件解除” 没有判定；横幅没有视觉定义，也没有测试。
- **使用中而检验目录已不存在时的 `inspect.open`**（R103-D13-01）。
- **另一个 Tower 安装持有租约时，`<wtRoot>` 中的目录被标为 `来源未知（清除全部后遗留）` 并可删除**（R103-D13-02）。
- **`06` L323 的复述与 ① 中工具链变量的取值来源**（R103-D15-01）。

### D5 Agent 架构与 Pi 集成

**R103-D5-01｜次要**（存储凭据的检查把 `$ENV` 与命令形式的条目当作已有凭据、漏了 `models.json` 的密钥一层；进行中的 Run 的描述在打包模式与 `/logout` 时不成立）

- **问题**：
  - **(a) 条目的形式**：
    - `11` L517：“以 `readStoredCredential(provider, authPath)` 检查，有存储的凭据（`/login` 的订阅或密钥）时不调用 `setRuntimeApiKey`……Pi 用存储的凭据——用哪份凭据、由谁计费与终端相同”。
    - Pi v1.2.0 中，`auth.json` 的 `api_key` 条目可以把 `key` 写为 `$VAR` 引用或以 `!` 开头的命令（`coding-agent/docs/providers.md:71-84`；`core/resolve-config-value.ts:145-151`）。`readStoredCredential` 返回原始条目、不解析（`core/auth-storage.ts:497-507`），所以这两种条目都判为 “有存储的凭据”。
    - 请求时 `AuthStorage.read` 才解析（`auth-storage.ts:442-447`）：`$VAR` 只取条目自己的 `env` 或进程环境（`resolve-config-value.ts:88-89`）。Host 环境是白名单，模型密钥不在其中，于是 `key` 为空，Anthropic 一类 provider 回落到同样为空的环境变量（`ai/src/providers/anthropic.ts:28-46`），请求以 `Provider is not configured` 失败。终端中同一份 `auth.json` 正常。
    - 这与 ADR-049 类型表 “配置中的 `$ENV` 引用：首次运行解析出引用的变量名，按上表类别处理”（`15` L339）、`05` L475 同句相撞。按该表，API Key 一类导入并以运行时注入提供，ADR-229 之前也确实可用；ADR-230 的检查使它失效，首次运行却标注 `已有 pi /login 的凭据，Tower 用它`。
    - 以 `!` 开头的命令在 Host 进程中以 shell 执行（`resolve-config-value.ts:185-196`），环境是 Host 的白名单。依赖其他会话变量的命令（如密码管理器的会话变量）会得到空值，终端中正常；这一点也没有写。
  - **(b) `models.json` 的一层**：
    - Pi 的先后是运行时 `--api-key`、存储的凭据、`models.json` 的 `apiKey`、环境变量（`docs/models.md:23`；`core/provider-composer.ts:457-473` 在没有存储凭据时先取 `rawKey`）。
    - 运行时覆盖经 `RuntimeCredentials.read` 以存储凭据的身份出现，因而先于 `models.json` 的 `apiKey`。
    - 所以没有 `/login`、但在 `models.json` 中为该 provider 配了 `apiKey`、shell 中又有该 provider 的环境变量时，终端用 `models.json` 的密钥，Tower 导入环境变量并注入，用的是另一份密钥、另一个账户。“与终端相同” 对这一层不成立。
  - **(c) 进行中的 Run**：
    - “Host 运行中你在终端 `/login` 时，正在进行的 Run 仍用已注入的密钥，下一个 Run 起改用存储的凭据”。
    - Pi 每次请求都重新求凭据（`core/model-runtime.ts:658-697`），覆盖是每个 `RuntimeCredentials` 一张表。正文没有写 `ModelRuntime` 是每个 Host 一个还是每个 Run 一个（`05` L486）；照 “每次 `host.spawn` 与每个 Run 之前检查” 的写法是每个 Host 一个。
    - 那么在打包模式（`06` L42）下，一个 Goal 的 Run 开始时移除覆盖，同一 Host 中另一个 Goal 进行中的 Run 从下一次请求起就改用存储的凭据。
    - 反方向没有写：Run 开始时有存储的凭据、Tower 没有注入，Run 中途你在终端 `/logout`，这次 Run 之后的请求判为未配置，要到下一个 Run 才注入。G46 (d) 第八组（`14` L134）只断言 “`/logout` 之后的下一个 Run 用导入的密钥”。
- **为什么是次要**：没有机密进入 Agent 可影响的进程，也不丢数据，失败都以 provider 错误显现。但 (a) 是 ADR-230 的新规则与 ADR-049 已有规则之间的冲突，并使一种原先可用的配置失效；(b) 使 ADR-230 自称的 “由谁计费与终端相同” 在一种配置下不成立；(c) 的描述与实现必然的行为不符。
- **后果的类别**：
  - 在 `auth.json` 中以环境变量引用密钥的用户，Tower 中无法运行，而界面说 Tower 用的是他们的登录；
  - 在 `models.json` 中配了密钥的用户，Tower 中的花费落到另一个账户；
  - 打包模式下一个 Goal 的 Run 中途换了凭据，或 `/logout` 使进行中的 Run 失败，排障时与文档的描述对不上。
- **文档位置**：`11` L517；`05` L475、L486、L489；`15` L339（ADR-049 类型表）；`04` L1459；`14` L134（G46 (d) 第八组）；`06` L42。
- **期望的回答形态**：在 `11` L517 “与 `pi /login` 存储的凭据的先后” 的唯一定义中补三句：
  - (a) “有存储的凭据” 按条目形式判定，例如：`oauth` 条目与字面 `key` 算有；`key` 只是 `$VAR` 引用的条目算没有（照 ADR-049 类型表导入该变量并注入，与终端结果相同）；`!` 命令的条目交给 Pi 并写明它以 Host 的白名单环境执行。也可以改为如实登记。
  - (b) 该 provider 在 `models.json` 中配了 `apiKey` 时同样不注入（检查时读同一份 `modelsPath`），或登记这一差别。
  - (c) 写明 `ModelRuntime` 的范围；若为每个 Host 一个，打包模式下 “进行中的 Run 仍用已注入的密钥” 改为只对专用 Host 成立，或移除只在该 Host 上没有其他用该 provider 的 Run 时进行；写明 Run 中途 `/logout` 的结果（provider 错误、按 F7 处理，下一个 Run 起注入）。
  - G46 (d) 第八组补 `$VAR` 条目与 `models.json` 两组。

**R103-D5-02｜次要**（Host 环境的封闭列表没有 CA 证书变量，TLS 拦截的企业代理下 Tower 的模型请求失败）

- **问题**：
  - `05` L474：Host 与 Supervisor “**直接**使用用户代理（ADR-079）：模型请求、`git push`……都如此”；`05` L472 ⑤ 把代理变量列入 Host 环境。
  - 企业代理常做 TLS 拦截。这时 Node 进程要信任企业的根证书，通常靠 `NODE_EXTRA_CA_CERTS`：Node 默认不读 macOS 钥匙串中的证书，Pi 的 provider 请求在 Host 的 Node 进程中发出。
  - ADR-230 把 Host 环境改为封闭列表，① 至 ⑦ 中都没有这类变量，“此外一律删除”。所以设了 `NODE_EXTRA_CA_CERTS` 的用户，终端中的 `pi` 正常，Tower 中每个模型请求都以 TLS 错误失败。Host 派生的 MCP 服务器与扩展子进程同样如此。
  - `00` L113 只为 S2 下的 Agent 与安装器登记了 “企业代理的 CA 文件不生效”，没有说 Host 自己的模型请求也会失败；首次运行 “代理变量自动透传并告知”（`05` L489）也没有提到它。
- **为什么是次要**：失败明确可见，不丢数据，也不放宽任何沙箱；但它让一类已声明支持的配置（企业上游代理，ADR-067/079）在 M1 中完全不能用，且没有任何地方告知。照封闭列表实现正是这个结果，不需要实现者犯错。
- **后果的类别**：企业网络中的用户完成首次运行后，第一个 Goal 就以 provider 错误失败，而终端中一切正常；排障时没有线索指向被删掉的变量。
- **文档位置**：`05` L472、L474、L489；`00` L113；`11` L363、L516；ADR-079。
- **期望的回答形态**：二选一：
  - 在 `05` L472 ⑤ 加上 `NODE_EXTRA_CA_CERTS`（值取自登录 shell、首次运行记录，与代理同样告知）。它指向的文件同样受 “Host 环境不引用任何 Agent 可写的位置” 约束：落在该集合之内时不传入，并写明原因。它是否进入 `mcpBaseEnv`，一并写明。
  - 或如实登记为限制：`00` §0.5.1 L113 一行扩到 Host，首次运行检测到该变量时在代理的告知中写明 “Tower 中的模型请求不使用它，TLS 拦截的代理下会失败”。

### D6 系统架构与可靠性

**R103-D6-01｜次要**（只重启 Supervisor 后重新接上的 Host 在没有 Run 时也置位 `hostExpected`，下一个 Run 的准备阶段仍按 30 s 判挂死）

- **问题**：
  - `08` L365 的置位有两个分支：“完成该 Goal 本次 Run 准备阶段的握手（该 Run 的 `run.started`……每个 Run 重新置位，ADR-230）”，“或只重启 Supervisor 后重新接上了 main 交回的存活 Host”。清除条件为 “该 Goal 的 Run 结束（`run.ended`），或该 Host 进程退出”。
  - 第二个分支不要求有 Run 在进行。Host 在 `paused` 不足 5 分钟时保留（`06` L169），Supervisor 单独重启后 main 交回每个存活的 Host（`06` L63）。这时暂停中的 Goal 没有 Run：重新接上时 `hostExpected` 置位，却不会有 `run.ended` 来清除它。
  - 于是人在 5 分钟内继续时，下一个 Run 在复用的 Host 上准备，`hostExpected` 已置位，会话创建中超过 30 s 的同步阻塞被判挂死：SIGKILL，进入 `engine_crash`；打包模式下同一 Host 的其他 Goal 一并终止。
  - 这正是 ADR-230 在 `08` L393 新写的一句所排除的：“同一 Goal 下一个 Run 的准备阶段同样只由 120 s 准备时限判定”。Supervisor 在某个 Run 的准备阶段中途重启（`run.started` 之前）是同一类。
- **为什么是次要**：去向有定义（`engine_crash` 自动重启一次），不丢数据；需要 Supervisor 单独重启这一前提。但这是同一条刚修订的规则在另一个置位分支上的落点，照字面实现会违反同一行新写的不变式。
- **后果的类别**：全局根查询较慢的机器上，Supervisor 崩溃恢复后的第一个 Run 被误判挂死；同一 Host 的其他 Goal 随之中断。
- **文档位置**：`08` L365、L393；`06` L63、L169（§6.1.8）、§6.1.3；`14` L118（G35c (x)）。
- **期望的回答形态**：在 `08` L365 的第二个置位分支加半句：“只对在该 Host 上有已过 `run.started`、尚未 `run.ended` 的 Run 的 Goal 置位；其余 Goal 等其下一个 Run 的 `run.started`”。G35c (x) 补一组：暂停不足 5 分钟、Supervisor 单独重启后继续，新 Run 的会话创建阻塞 45 s 不判挂死。

**R103-D6-02｜次要**（F8 的 drain 去向、只读状态的解除与横幅的定义）

- **问题**：
  - `06` L1197 F8：“停止准入新 Run；对活跃 Run 走 drain；数据库切换为只读”。`08` L38（ADR-230）：应用级横幅 “显示在主窗口顶部直到条件解除……数据库此时只读”。
  - **drain 的去向**：drain 结束时要以 `reasons` 进入 `paused`（`06` L146），而暂停原因的集合中没有与磁盘相关的一项（`02` L153–L162，`16` L30）。用哪一个原因、`goals.draining_for` 与暂停怎样写进一个正在切换为只读的数据库，都没有写。
  - **只读的解除**：“直到条件解除” 没有判定。可以是定时复查可用空间、人删除之后复查、还是要重启 Tower，没有写；数据库何时恢复可写、恢复后被 drain 的 Goal 怎样继续，也没有写。
  - **呈现与测试**：
    - `12` 只定义了 L3 的断点提示条与 Watch 视图内横幅（`12` L521），没有应用级横幅的颜色与位置；`04` 也没有。
    - `04` §4.18.3 没有磁盘满一行；`14` 没有 ENOSPC 或 F8 的测试组。
  - ADR-229/230 把磁盘满时的告知与人释放空间的途径都落在 F8 上，这一行因此成为它们的依赖。
- **为什么是次要**：磁盘满时数据本身不因 Tower 的写法丢失（卫星的文件仍在磁盘上，`goal.delete_kept` 不写事件、只读下仍可用）；但新机制依赖的一行有三个未定义分支，实现会在 “沿用哪个暂停原因”“自动恢复还是要求重启” 之间分叉，且 M1 中没有测试覆盖。
- **后果的类别**：人释放空间之后横幅不消失、数据库不恢复，或 Goal 以误导的原因暂停；不同实现对同一次磁盘满给出不同的恢复路径。
- **文档位置**：`06` L1197、L146、§6.6.4；`08` L38；`02` L153–L162；`16` L30；`12` L521；`04` §4.18.3；`14` §14.3.5。
- **期望的回答形态**：在 `06` L1197 F8 一行（唯一定义）加两句：
  - drain 的去向：例如沿用已有原因中的一个（并写明理由），或不写暂停、按启动恢复的规则处理被中断的 Run；写明只读切换与 drain 写入的先后。
  - 解除条件：例如每 N 秒复查可用空间高于某个阈值时恢复可写并撤下横幅，或明确要求重启 Tower。
  - 另在 `12` 写明应用级横幅引用哪一种已有组件与颜色语义；`14` 补一组 ENOSPC 测试。

### D13 隔离、git 与并发

**R103-D13-01｜次要**（使用中而检验目录已不存在时，`inspect.open` 照字面在旧检验仍打开时新建一个）

- **问题**：
  - ADR-230 为 “使用中而检验目录已不存在” 补了 `inspect.close` 与 `inspect.bring_back` 的去向（`10` L255）。
  - `inspect.open` 的判定仍以路径存在为前提：`10` L255 “路径已存在时：若它使用中……打开检验返回 `E_STATE`”；`10` L891 “路径已存在时按 §10.2 处理——仍在使用中返回 E_STATE”；`06` L899 “已存在且仍在使用中时同样返回 `E_STATE`”。
  - 检验打开中（服务在运行、端口段已分配），或以 `keep` 关闭待处理，而人删掉或移走了检验目录时，`inspect.open` 不返回 `E_STATE`，而是独占新建一个检验目录并打开新的检验。旧检验的服务与端口段、以及 `◇ 检验目录有未处理的修改` 卡片的去向都没有定义。
- **为什么是次要**：由人删除目录这一外部操作触发，不丢失人的工作；但这是 R102-D13-02 修法留下的同类分支，同一状态下关闭与打开的判定不一致，实现会分叉。
- **后果的类别**：同一 Goal 同时有两个 “打开中” 的检验，或两套服务争用同一端口段；`keep` 待处理的状态在新检验打开后仍挂着。
- **文档位置**：`10` L255、L891、§10.8.3 第 7 步；`06` L899、L918、L919。
- **期望的回答形态**：在 `10` L255 “使用中而检验目录已不存在” 一句后补半句：“`inspect.open` 按状态判定——检验仍在使用中（不论目录是否存在）时返回 `E_STATE`，界面指向 `inspect.close`”；或写明它先隐式结束旧检验（停止服务、回收端口段）。`06` L899 同步。G46 的同一组补打开一步。

**R103-D13-02｜次要**（另一个 Tower 安装持有租约时，`<wtRoot>` 中它的目录被标为 `来源未知（清除全部后遗留）` 并可删除）

- **问题**：
  - `<wtRoot>` 默认在用户检出旁边（`<checkoutParent>/.tower-wt.noindex/<repoName>`，`10` L23、L239），两个 Tower 安装操作同一个检出时共用它。`06` L184 与 F25（`06` L1214）为此设了租约：后来者对该 Project 只读，“不创建 worktree、不写 `refs/tower/*`、不启动 Run”。
  - 列出的来源是按每个已知 Project 的 `<wtRoot>` 扫描（`10` L259）。ADR-230 让没有 Goal 行的目录标为 `来源未知（清除全部后遗留）`，`goal.delete_kept` 对它们 “只校验路径在某个已知 Project 的 `<wtRoot>` 之下、名字为所列形状”（`10` L259，`06` L911）。
  - 于是持有租约的另一个安装正在使用的 `_human/<goalId>` 与 `_inspect/<goalId>`，在后来者的存储面板中被标为清除全部的遗留，可以删除；其中可能是对方的人尚未交还的改动。只读状态的范围没有包括这条命令。
  - `_owner` 的 `hostname` 与本机相同时，Needs-You 文案本身就写 “可能是本机此前的安装（如‘清除全部’之后）”，与 `来源未知` 的标注一起，更容易让人把对方正在使用的目录当成遗留。
- **为什么是次要**：删除由人显式发起，确认框先列出将丢失的内容；前提是两个安装操作同一个检出，租约已生成 Needs-You。但标注给出的来源可能是错的，而 “Tower 从不悄悄破坏另一个安装” 正是租约要保证的。
- **后果的类别**：人按 “清除全部后遗留” 删除了另一个 Tower 安装中尚未交还的人工编辑检出。
- **文档位置**：`10` L23、L239、L259；`06` L184、L911、L1214；`09` §9.12.4。
- **期望的回答形态**：在 `10` L259 `来源未知` 一句后补一句：该 Project 因另一个安装的租约而只读时，其 `<wtRoot>` 中没有本机 Goal 行的目录标为 `可能属于另一个 Tower 安装`，`goal.delete_kept` 对它们返回 `E_STATE`（租约过期或被接管之后照常）。`06` L184 只读的范围补 “不删除 `<wtRoot>` 中的目录”。

### D15 文档一致性与可执行性

**R103-D15-01｜次要**（`06` L323 在 “端口不在其中” 的同一句中把端口段列入 Host 环境；① 中工具链变量的取值不在首次运行记录与 “重新读取” 的范围中）

- **问题**：
  - **(a) 残留的复述**：
    - `06` L323 准入链：“拼装 Host 环境（变量的完整列表只按 `05` §5.3.6 ‘Host 环境的变量’，端口与 Tower 标识不在其中，ADR-230；……白名单 + 最近一次读到的登录 shell `PATH`……+ 代理 + ADR-049 的凭据类别 + **ADR-055 的端口段与 `${port:N}` 模板** + Pi 运行开关……）”。
    - 同一句先声明只引用唯一定义、端口不在其中，随后又复述一遍并列入端口段，正是 R102-D15-01 要消除的那类复述。照这一句拼装 Host 环境，打包模式下一个 Goal 的端口会进入同一 Host 中其他 Goal 的扩展与 MCP 子进程。
  - **(b) 工具链变量的取值来源**：
    - `05` L472 ①：工具链变量 “取自登录 shell，有值才传入”。
    - 但首次运行写明从登录 shell “只取变量名……另取……`PI_CODING_AGENT_DIR` 的值……以及 `PATH` 与包管理器位置变量的值，供 Host 环境使用”（`05` L489）；设置页显示与 “重新读取” 只替换 “这些值与记入密钥库的上述非机密变量的值”。七个工具链变量都不在其中。
    - 从 Dock 启动的 Tower 自己的进程环境中没有它们（`05` L486 “从 Dock 启动时它拿不到 shell 环境”）。所以照字面，Host 中没有这些值。实现会在 “首次运行一并记录”“每次 spawn 重新运行登录 shell”（与 “Tower 不自动重新读取” 不符）与 “取 Tower 自己的环境” 之间分叉。
    - `16` L1368 说角色 A 经 Host 白名单继承它们，所以这也决定 Agent 的 bash 中有没有 `JAVA_HOME` 等。
    - `PNPM_HOME` 同时列在 ① 与 ④ 中，只有 ④ 写了取值规则（“Host 环境不引用 Agent 可写的位置”）。
- **为什么是次要**：(a) 有唯一定义可循，同一句的前半已指向它；(b) 一位称职的实现者多半会在首次运行时一并记录。但 (a) 是 ADR-230 刚合为一处的列表在另一处的残留；(b) 是唯一定义与首次运行的枚举之间的空档，影响 Agent 的构建环境。
- **后果的类别**：打包模式下端口泄到其他 Goal 的子进程；或 Agent 的 bash 中没有工具链变量，非 Node 项目的构建在 Tower 中失败而终端中正常。
- **文档位置**：`06` L323；`05` L472、L486、L489；`16` L1368。
- **期望的回答形态**：
  - (a) `06` L323 删去括号中的复述，只留 “变量的完整列表只按 `05` §5.3.6 ‘Host 环境的变量’”；可在 `16` §16.1.13 第 102 轮一行补登这一写法，由 (D) 检查。
  - (b) `05` L489 “另取” 的列举补上 ① 中的工具链变量（与 `PATH` 同样显示在设置页、随 “重新读取” 替换），`PNPM_HOME` 只留在一处并写明取值规则。

### 不扣分的观察

1. **封闭的工具链变量对用户不可见**：
   - `05` L472 写明 “其他工具链变量不传入……偏严”，ADR-230 又删去了用户放行的一类。但 `00` §0.5.1 的能力差别表与静态清单的确认卡片都没有写。
   - 受影响的是扩展经 `pi.exec` 启动的子进程（如依赖 `PYENV_ROOT`、`GOROOT`、`SDKMAN_DIR`、`ASDF_*` 的工具），它们没有出路；MCP 服务器可以在 `mcp.json` 的 `env` 中写字面值，但写成 `$NAME` 引用 shell 变量的会解析不出。
   - 宜在 `00` §0.5.1 补一行，并在静态清单中加载了扩展或 MCP 的确认卡片上写一句。
2. **`listedAt` 的取值时刻与建立时间**：
   - 宜写明 `listedAt` 取求值开始、第一次读取之前的时刻。
   - `<wtRoot>` 可以在非 APFS 或网络卷上（`10` L22、L382），那里建立时间可能不可得；宜写明不可得时的退路（如改比较设备号与 inode，改名保留它们）。
   - 最坏的结果只是一次多余的重新求值，不会误删。
3. **交还对话框中提交数的写法**：
   - `04` L635 与 G46 写 “1 个提交”。`10` L53 的 `至少 N`、`200+` 只对确认框写明；解析失败时 `10` L227 “省略该信息”，对话框的这一行随之消失，像是没有提交被忽略。
   - `ignoredCommits` 在上限与失败时的取值也没有写。
   - 宜补半句：交还对话框用同一写法，失败时写 `无法计算`，字段为数字或 `null`。H 原样保留，不丢数据。
4. **“含本地机密文件的副本” 的标注来源**（`10` L259，`09` L561）：
   - 唯一的记录是 `HumanDecision{inspect_with_secrets}`，没有写它怎样对应到 `_inspect/<goalId>` 与其后改名的 `.kept-*`；对 `（已清除）` 与 `来源未知` 的目录更求不出，而那正是隐私上要紧的情形。
   - 清除那一刻的结果已经注明。宜改为由目录本身求出（检查已知 Project 的机密本地文件路径是否存在于其中），或在没有记录时保守地写 `可能含`。
5. **存储提示按条件的已查看与 48px 细栏**：
   - `08` L38 的四类条件共用一枚 `◇ 存储`，“条件解除之后再次成立时重新显示” 只覆盖同一条件；看过人的工作现场的提示后磁盘压力才成立时是否重新显示，没有写。宜按条件记已查看。
   - 细栏不显示设置入口的 `◇`，而窗口不足 1100px 时侧栏固定为细栏（`04` L74、L1538）。这时存储提示与项目级通知只在设置页中可见，项目级通知此前就是如此；磁盘满另有 F8 横幅。宜在 `04` §4.3.2 注明，或给细栏的设置图标一个不带文字的 `◇`。
6. **提交遍历的细节**（`10` L53）：
   - “沿父链” 是只沿第一父还是全部父提交，没有写；每个 stash 因此计为 2 或 3 个提交，`至少` 覆盖了这一点。
   - `H/.git/worktrees/*` 下各工作树的 `HEAD` 不在遍历中；指向附注标签或非提交对象的 ref 怎样处理，没有写。
   - “`repack` 之后结果不变” 对以镜像中的提交为起点的 ref（人从 base 的祖先新建分支）略强：`repack` 之前在对象缺失处停止，之后会数进上游历史；偏保守的一边。
   - 保留目录在每次产生或删除之后重新扫描 `mtime`（`10` L568），其中可能有 `node_modules`，`13` 没有给出这一扫描的成本界限。
   - 人在检验目录中自建的 `.git` 或 H 中的嵌套克隆被排除在比较之外，确认框不列出，却会随之删除；属于人自己的少见操作。
7. **`readStoredCredential` 吞掉读取错误**：
   - 它在读不出或解析失败时返回 `undefined`（`auth-storage.ts:501-506`），而 Pi 写 `auth.json` 不是原子的（`:107`、`:188`）。
   - 检查恰好与一次刷新交错时，该 Run 会注入导入的密钥，只影响这一个 Run。宜在定义中注明 “读不出时按没有存储的凭据处理”。
8. **Host 环境的几处复述与开放项**：

   - `16` L1353 仍指向 “工具链变量（`11` §11.7.1，如 …）”，宜改为 `05` §5.3.6。
9. **同步与指向**：
