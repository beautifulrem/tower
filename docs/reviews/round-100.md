## 1. 总评

**第 99 轮的 7 条次要条目中，6 条按所问关闭，1 条部分关闭**（核对见 §3）。§5 的 9 条观察全部落地。回应 “偏离与未决” 的判断如下：
- 四条接受；
- 一条部分接受：**R99-D11-01 取 “不提供”**。安全方向成立，与 `11` 中 “无法判定取更严” 的取向一致；但它把加载了 MCP 服务器的每个 Goal 上的每次 MCP 调用都变成逐次批准，这一代价只写在回应中，正文没有登记，`08` 的告警纪律、M1 门槛与 E3 也没有为它留出口（R100-D8-01）；
- 一条接受方向、实现有缺口：**R99-D13-01 (a) “保留并列出”**。按 “整个目录” 比较的定义在被忽略目录已存在于主检出的常见布局下不生效（R100-D13-01）。

**对本轮重点问题的回答（逐次批准）**：
- **是否与 `00`/README 一致**：在**规则**层面一致。`00` L102 与 `01` L77 都如实写了 “加载了 MCP 服务器即如此”“每次调用都要人批准”，`04` L1112、`12` L735 与 `11` §11.3.4 一致。README 第 8 条的例外列表以 “例如” 开头，没有列出这一条，记为观察。
- **是否与 `08` 的打扰预算、E3 与可用性承诺一致**：不一致，而且没有写明。
  - 每次 MCP 调用产生一条 `approval`，`agent_blocked`、基础级别 L3（`08` L21–L28）。Goal 桶默认 3/h（`08` L267），取空后降为 L2，Agent 阻塞等人。
  - README 第 5 条（L16）承诺 “只在需要人时打扰人，并像工业报警系统一样度量每次打扰是否值得”；`08` L12 把 93–97% 的权限弹窗批准率称为典型的滋扰告警；`11` L328 把 “批准率持续 > 97%” 的闭环交给晋升机制。
  - 对加载了 MCP 的 Goal 上的 `tool.external`，这条闭环的两个出口都关了：按工具名授权不提供（ADR-227），晋升受级别下限 ask 所限（`11` L226、§11.5）。
  - M1 门槛的 “打扰率（含审批）”（`14` L436）、E3 的 “中位 ≤ 6 条/小时”（`14` L541）与 §14.6.2 的 “打扰率 L2+ ≤ 6”（`14` L667）都会被这一类审批推高，而没有一处单独报告它。
- **是否如实写为代价**：没有。ADR-227 与 `11` §11.3.4 只写了理由，没有写代价；回应 L295 的 “更吵” 是唯一的一处。
- **安全论证的一处张力**：`01` #9 与 T16 都说 “这一面由逐次 ask 承担”。而 T10（`11` L697）列出的 “审批疲劳导致盲批” 的缓解中，“授权” 与 “自适应晋升” 对这一类都不可用。逐次 ask 是否仍是有效的闸门，取决于它不被习惯性地点过；文档没有为此给出度量或复审点。

**ADR-227 的结构性写法成立**（§3.3）：
- **运行中的终止一轮**：范围限于该 Host 承载的 Run，第二类令牌以带 `runId` 的 `agent_bg_done` 检查点移出范围；`清理中` 与 `E_BUSY` 对运行中的一轮同样适用。`06` L64、L145、L196、L298、L320、L907，`10` L735，`12` L390，`16` L293 一致。
- **云 SDK 凭据**：总带 `AWS_PROFILE`、配套变量原样传入、缺区域时补 `us-east-1`，与 Pi 的判定与回落等价（单一来源的情形）。
- **按工具名授权的条件**：唯一定义在 `11` L226，§11.2、§11.3.5 (d)、§11.8、T16、`00`、`01`、`02`、`04`、`12`、`16` 只引用。
- **心跳起点与挂死的定义**：只重启 Supervisor 时不再以持久化的心跳为起点，第 99 轮观察 1 的风险已排除。
- **M3 的日期与 lint (C)**：成立，变异检查记录可信。

**ADR-227 带出、或本轮扫描发现的新问题**：
- **人新建的被忽略文件按整个目录比较**（R100-D13-01，重要）：被忽略的目录在主检出中已存在时（这正是它被忽略的常见原因），人在其中新建的文件不列出、不保留、随副本删除；`04` L660 的示例 `certs/dev.key` 正落在这一情形。反过来，Tower 自己物化的依赖目录与构建产物会使副本例行改名保留。第 8 步删除前比较的唯一定义也看不到第 5 步的 “按不同处理”。
- **AWS 规则与首次运行**（R100-D5-01）：`AWS_PROFILE` 与原始密钥并存时与终端中的 Pi 用不同的身份；Tower 写入的 profile 名未定；区域判定读哪个文件、何时判定未写；首次运行 “只取变量名、不记录值” 与 “原样传入” 冲突；API Key 类 provider 的非机密配置被删除。
- **挂死的计时与准备时限**（R100-D6-01）：`hostExpected` 自 spawn 起，Host 启动中的同步查询超过 30 s 即判挂死，与 “由 120 s 的准备时限兜底，进入 `prepare_failed`”（`13` L129、`05` L253）相撞。
- **逐次批准的代价**（R100-D8-01）：见上；另有条件成立时审批卡与合同编辑器不说明、按 (d) 失效的授权仍列为 “仍有效”。
- **终止一轮完成之前的写入**（R100-D13-02）：Goal 已进入 `paused`，残留进程的写入不满足归因表第 2、3 行，按第 4 行记为外部写入。
- **复述未同步**（R100-D15-01）：`06` L323 的 Host 环境拼装仍写 “只传指向文件的变量”；`10` L752 第 2 步的去重例外漏了本轮新增的检查点。

    - `11` L518 写 “凡以凭据文件提供 AWS 凭据，总带 `AWS_PROFILE`——你设了的取你的值”，原始密钥 “从不传入”；只在 “用户的配置只提供原始变量时” 写入投递文件。
    - 终端中的 Pi 在环境里同时有 `AWS_PROFILE` 与原始密钥对时，用的是原始密钥：只有经 `options` 或存储凭据的 `env` 给出的 profile 才优先，环境中的 `AWS_PROFILE` 不阻止 `config.credentials` 取原始密钥（`bedrock-converse-stream.ts:162-164, 215-217`）。
    - 照 `11` 实现，Tower 只传 profile，与终端中的 Pi 用不同的身份（可能是另一个账号，或 profile 无效时请求失败）；另一种实现把原始密钥也写进投递文件、以 `AWS_SHARED_CREDENTIALS_FILE` 指向它，又会遮住 `~/.aws/credentials` 中的 profile。两种都能从文字读出。
  - **(b) 写入的 profile 名**：
    - “Tower 写入的投递文件取写入时所用的 profile 名” 没有限定名字。Host 保留真实的 `HOME`（`11` L516），SDK 会把投递文件与 `~/.aws/config` 中同名的段合并。
    - 取 `default` 时，用户 `~/.aws/config [default]` 中的角色、SSO 或 `credential_process` 设置会参与解析；“该 profile 的配置中有无区域” 一句读到的也是一个 Tower 没有写过的段。
  - **(c) 区域判定的来源与时机**：没有写读 `AWS_CONFIG_FILE` 还是 `~/.aws/config`、在首次运行时还是每次 `host.spawn` 时判定。若只在首次运行时判定并补 `AWS_REGION=us-east-1`，之后用户在 profile 中加的区域会被这个环境变量盖住。
  - **(d) 首次运行只取变量名**：
    - `05` L489：“`$SHELL -ilc env`，只取变量名并与 provider 对应，不记录值”，例外只有 `PI_CODING_AGENT_DIR`、`PATH` 与包管理器位置变量；“重新读取” 也只替换这些值。
    - ADR-227 要求把 `AWS_PROFILE`、`AWS_REGION`、`AWS_CONFIG_FILE`、`GOOGLE_APPLICATION_CREDENTIALS`、`GOOGLE_CLOUD_PROJECT`、`GOOGLE_CLOUD_LOCATION` 的**值**原样传入 Host。这些值在哪里取得、存在哪里、“重新读取” 是否刷新它们，都没有写。用户换了 profile 或区域之后，Tower 没有写明的更新途径（这一点在 ADR-227 之前就隐含存在，ADR-227 使它的范围变大）。
  - **(e) API Key 类 provider 的非机密配置**：
    - `11` L516 的白名单之外 “其余一律删除”，例外只有云 SDK 凭据链。
    - Pi 的 Azure OpenAI 缺 `AZURE_OPENAI_BASE_URL`、`AZURE_OPENAI_RESOURCE_NAME` 与 `model.baseUrl` 时抛出（`azure-openai-config.ts:74-89`）；Cloudflare 缺 `CLOUDFLARE_ACCOUNT_ID`（AI Gateway 另缺 gateway id）时判为未配置（`cloudflare-auth.ts:37-42`），运行时注入的 API Key 不带这些值。
    - 这与 R99-D5-01 (b) 的 Vertex location 是同一类。ADR-049 的类型表（`15` L330）没有 “API Key 加非机密配置” 这一类；ADR-227 把 `env-api-keys.ts` 移出判定路径之后，正文也不再引用任何 “变量 → provider” 的对应来源。
- **为什么是次要**：没有机密进入 Agent 可影响的进程，也不丢数据；后果是某些配置在终端中可用、在 Tower 中失败或用错身份，界面只显示通用的 provider 错误。但 (a)(b)(c)(e) 都能导出实质不同的实现。
- **后果的类别**：混用来源的 Bedrock 用户在 Tower 中以另一个身份发请求，或失败；写入的 profile 与用户配置同名时凭据解析走向用户的角色或 SSO 设置；用户之后改的区域不生效；Azure、Cloudflare 一类用户一个请求也发不出去。
- **文档位置**：`11` L460、L516、L518；`05` L475、L489、D62（L1448）、C29（L1498）；`16` L722；`15` ADR-049（L330）；`14` G46 (d)。
- **期望的回答形态**：在 `11` L518 的唯一定义处补以下几句，G46 (d) 补 “两者并存” 一组：
  - 环境中同时有 `AWS_PROFILE` 与原始密钥对时取哪一个，并写明是否与终端中的 Pi 相同（取原始密钥则写投递文件且不传用户的 profile）；
  - 投递文件使用 Tower 保留的 profile 名（如 `tower-<hostId>`），不与用户配置中的段同名；
  - 区域判定读哪个文件、在每次 `host.spawn` 时进行；
  - `05` L489 的 “另取……的值” 加入这些非机密变量，写明存放位置，并列入 “重新读取” 替换的集合；
  - API Key 类 provider 的非机密配置变量（Azure 的端点、Cloudflare 的账号与 gateway id）原样传入 Host、不进入 bash，或登记为已知限制并给出 `pi /login`（存储凭据带 `env`）的替代；“变量 → provider” 的对应以各 provider 的 `resolve` 及其读取的配置变量为准。

### D6 系统架构与可靠性

**R100-D6-01｜次要**（挂死的计时自 spawn 起，与 120 s 准备时限及 `prepare_failed` 相撞）

- **问题**：
  - `08` L363 定义 `hostExpected` 自 “本 Supervisor 进程 spawn 了该 Goal 的 Engine Host” 起置位；L391 的挂死唯一定义为 “自 `hostExpected` 置位的时刻或最后一次心跳起已超过 30 s 没有心跳”，“两种情况都按 `06` §6.1.3 Engine Host 一行进入 `paused{engine_crash}`”，`06` L64 据此以 SIGKILL 终止并自动 “重启并恢复” 一次。
  - 心跳定时器与 Agent 循环共享 Host 的事件循环（`08` L390）。Host 创建会话时，用户级 npm 来源不在 `<agentDir>/npm/` 下就同步运行包管理器的全局根查询、没有超时（`05` L1431 D45，`core/package-manager.ts:2102-2130`）。
  - 而 `13` L129 写 “你配置的包装命令挂起时，会话创建由 120 s 的准备时限兜底，进入 `paused(prepare_failed)`”；`05` L253 与 `06` L1192（F4b）把 Host 握手与开场组装在 120 s 内没有 `run.started` 归为 `prepare_failed`、“不是 `engine_crash`”；`06` L64 又写挂死一行 “只影响 running 的 Goal”。
  - ADR-227 之前 `hostExpected` 没有定义，准备阶段是否计入看门狗可以按 `13` 读。现在定义自 spawn 起，准备阶段中超过 30 s 的阻塞同时满足两条：照 `08` 是挂死 → SIGKILL → `engine_crash`（自动重启一次，10 分钟内再犯才出条目）；照 `13`/`05`/F4b 是 `prepare_failed`（不自动重启，直接出 `stalled{prepare_failed}`）。而这时 Goal 还在 `ready` 的准备阶段，`03`/`06` 也没有从准备阶段进入 `paused(engine_crash)` 的转移。
- **为什么是次要**：两种去向都暂停、都告知人，不丢数据；但出口、自动重启与 Needs-You 的类别不同，实现会分叉。
- **后果的类别**：启动慢的 Host 被强杀并自动重试一次，再以 `stalled{crashed}` 而不是 `prepare_failed` 告知；或者在准备阶段的状态上执行一条未定义的转移。
- **文档位置**：`08` L363–L364、L390–L391；`06` L64、L1191–L1192（F4、F4b）；`05` L253、L540（RPC 握手 20 s）；`13` L129。
- **期望的回答形态**：在 `08` L391 的挂死唯一定义处加一句，二选一：
  - 准备阶段（`run.started` 之前）不计入看门狗，Host 启动中的阻塞只由 120 s 准备时限判定为 `prepare_failed`，`hostExpected` 的起点改为握手完成；或
  - 准备阶段计入看门狗，挂死时按 `prepare_failed` 处理（照常终止进程、不进入 `engine_crash`），`13` L129 与 F4b 同步。

### D8 注意力与交互

**R100-D8-01｜次要**（MCP 工具逐次批准的代价没有登记，也不在度量与告警纪律之内；条件成立时审批卡与合同编辑器不说明，按 (d) 失效的授权仍显示为有效）

- **问题**：
  - **(a) 代价未登记**：
    - ADR-227 之后，配置了 MCP 服务器的用户的每个 Goal 上，不可信内容与对外通信恒为真（`11` L545–L546，判定按 “是否配置”，L562），所以每个沙箱外工具（MCP 工具，以及同一用户的扩展工具）的每次调用都出一张只有 “仅这一次” 的审批卡（`11` L226）。
    - 每张卡是 `approval`、`agent_blocked`，基础级别 L3（`08` L21–L28）；Goal 桶默认 3/h、容量 2（`08` L267），取空后降为 L2 进收件箱，Agent 阻塞等人。代码智能类 MCP（`11` L228 提到的这类）在一个 Run 中被调用几十次是常见的。
    - 正文写了**规则**（`00` L102、`01` L77），没有写**代价**：ADR-227 与 `11` §11.3.4 的 “理由” 只论证安全，回应 L295 的 “更吵” 是唯一的一处。
  - **(b) 告警纪律没有出口**：
    - README 第 5 条（L16）、`08` L12（93–97% 的批准率是滋扰告警，ADR-010）、`11` L320 与 L328（反射批准率高 → 晋升评估，“这也是告警纪律的闭环”）。
    - 对这一类，两个出口都关了：按工具名授权不提供；晋升受级别下限 ask 所限（§11.5 只建议 `ask → notify`，而 `decide()` 先钳到下限）。人能做的只有逐次批准、把该类设为 `forbid`，或不配置 MCP。
    - T10（`11` L697）的缓解列出 “授权；自适应晋升”，对这一类都不可用；而 `01` #9 与 T16 正以 “这一面由逐次 ask 承担” 作为安全论证。逐次 ask 被习惯性点过时，这道闸就不再承担。
  - **(c) 度量**：
    - M1 门槛 “打扰率（含审批）”（`14` L436，团队 ≤ 8、非团队 ≤ 10，“审批增加的部分单独报告”）、注意力行的 “每小时打扰中位数”（L426）、E3 的 “中位 ≤ 6 条/小时”（L541）与 §14.6.2 的 “打扰率 L2+ ≤ 6”（L667），都会被这一类审批推高。
    - 没有一处按 “是否加载了 MCP” 或按 `tool.external` 单独报告，也没有复审点。M1 自用期中 MCP 用户使门槛不达标时，无法从数据看出原因。
  - **(d) 条件成立时的界面**：
    - **审批卡**：`12` L735 的 `ExternalToolNote` 在 “本 Goal 内同类” 不提供时不显示，`04` L1112 只写 “只有‘仅这一次’”。正是每次都要批准的这一情形，卡片上没有一句说明为什么没有放行、之后还会一直询问。
    - **合同编辑器**：`11` L226 的半句 “授权后该工具的调用不再逐次询问” 写在 “条件不成立” 一支；条件成立时，带 `tool.external` 授权的合同（按 (d) 不会编入）显示什么，没有写。照字面把半句也放在这里，就是一句不实的说明。
    - **Goal 页右栏**（`04` L354）列 “本目标仍有效的‘本 Goal 内同类’授权”。按 (d) 不编入的授权是否列出、怎样标注，没有写；G46 (bn) 第三组中 `net.other` 授权使扩展工具的授权失效，`net.other` 的审批卡上也不说明这一后果（私有数据为 “未知”，ADR-201 的三要素警告不出现）。
- **为什么是次要**：安全方向是收紧，所有分叉都是 “多问”，不放宽访问、不丢数据；但 (a)(b)(c) 是一个按 README 与 `08` 的标准衡量的、实质的可用性代价，正文既没有登记也没有度量，(d) 的界面实现会分叉。
- **后果的类别**：MCP 重度用户的 Agent 频繁阻塞在审批上，打扰预算被这一类耗尽，批准退化为反射式点击；M1 门槛与 E3 的数据被一个没有单独报告的来源推高；人看到的授权状态与实际编入的不符。
- **文档位置**：`11` L226、L254、L320、L328、L545–L546、L558、L562、L697（T10）、L703（T16）；`08` L12、L21–L28、L264–L270；`14` L426、L436、L540–L541、L667、G46 (bn)；`04` L354、L1112；`12` L735；`00` L102；`01` L77；README L16；`15` ADR-227。

### D13 隔离、git 与并发

**R100-D13-01｜重要**（人新建的被忽略文件按 “整个目录” 与卫星、主检出比较：常见布局下随副本删除而不列出；Tower 自己物化的目录使副本例行保留；第 8 步的唯一定义看不到 “按不同处理”）

- **问题**：
  - **(a) 漏判，丢失人的文件**：
    - `10` L972（ADR-227）：“人新建的被忽略文件”= “H 中被 git 忽略、而卫星工作目录与主检出中都没有同一路径的条目（git 按目录汇报的被忽略目录按整个目录计……）”。
    - 被忽略的目录在主检出中已存在时——这正是它被忽略的常见原因，例如放本地证书的 `certs/`、放本地密钥的 `secrets/`——人在 H 的同一目录中新生成的文件，按目录汇报为 `certs/`；主检出中有 `certs/`，这个条目就不在集合之内：不列出、不触发第 8 步的 “不同”、H 照常删除，文件随之丢失。
    - `04` L660 的示例写的正是这一情形：“你在副本中新建、被 git 忽略、而主检出与工作目录中都没有的文件（如在被忽略的 `certs/` 中新生成的 `dev.key`）”。`04` 按文件说，`10` 按目录判，两处不一致；照 `10` 实现，示例中的文件被删除。
    - G46 (bl) 的 ADR-227 一组用的是 “主检出中没有的 `keys/` 目录”（`14` L134），恰好避开了这一情形。
    - ADR-227 自己的理由是 “这是人的工作，可能是刚生成、无法重新得到的密钥”（回应 L158），这一情形正是它要保护的。
  - **(b) 误判，副本例行保留**：
    - 同一判定把 “另两处没有” 当作 “人新建”。H 中由 Tower 自己物化、而卫星与主检出中恰好没有的被忽略目录也会落入：例如依赖在 H 中经 depcache 物化（`10` §10.8.4 第 2 步），而卫星的依赖目录已被磁盘压力清理、主检出从未安装；以及人按第 2 步的提示在 H 中运行准备步骤或构建而生成、两处都没有的产物目录（`dist/`、`.next/`、`coverage/` 一类）。
    - 每次这样的交还都使整个 H（含依赖目录）改名保留。改名保留的目录 Tower 从不删除、此后不再管理（`10` L256），对话框中也只给出 “副本将改名保留”，没有选择。回应对检验目录不采用这一条的理由（“多是运行与构建的产物”），对人在 H 中运行过的东西同样成立。
  - **(c) 第 8 步的唯一定义**：
    - 第 5 步写 “第 8 步删除前的比较按‘不同’处理，H 改名保留”（ADR-226 的凭据形文件与 ADR-227 的被忽略新文件两处）。
    - 而第 8 步 “删除来源目录之前的比较”（唯一定义，L1014–L1016）只写 “以求 T1 的同一规则……对该目录重新求树，与 T1 比较树 id：相同才删除”。这两类路径按构造都不在 T1 中，按同一规则重新求树也看不到它们，树 id 相同。
    - `06` L144 的启动续写引用的正是第 8 步（“与 T1 不同……来源目录只在写回成功、且其内容仍等于 T1 时删除”）。只照第 8 步或 `06` L144 实现时，崩溃之后续写完成即删除 H。
- **为什么是重要**：照 `10` L972 与 L1014–L1016 的文字实现，人在副本中新生成、没有其他副本的文件（含刚生成的密钥）会在交还后被删除，事先不列出、事后也不在结果中。这正是 ADR-227 明文承诺保护的对象，`04` 给出的示例本身就落在漏判之中。这符合 “照文字实现会丢失人的工作” 的标准。第 99 轮把同类丢失定为次要，理由是 “被忽略的文件不同步是写明的规则、缺的是告知”；ADR-227 之后，正文写的规则已是 “列出并保留”，丢失与写明的规则相悖。
- **后果的类别**：人的新文件随副本静默删除；同时，没有人的工作的交还也例行留下完整副本，“保留的目录” 与对话框中的灰字被人习惯性忽略，真正需要保留的情形因此被稀释。
- **文档位置**：`10` L256、L972、L1014–L1016；`06` L144；`04` L660、L668；`12` L683；`14` G46 (bl)（L134）；`15` ADR-227（L4533）。
- **期望的回答形态**：在 `10` L972 的唯一定义处改判定，并让第 8 步引用它：
  - “人新建” 相对 **Tower 写入 H 的内容**判定，而不是相对卫星与主检出：不在 T0 的物化、播种的本地文件与 Tower 物化的依赖目录之中的被忽略路径；
  - 按文件比较（对被忽略目录逐文件列出，例如以 `--ignored=matching` 求出，Tower 物化的依赖目录整体排除）；
  - 第 8 步删除前比较的唯一定义写明 “第 5 步列为‘按不同处理’的路径存在时不删除”，`06` L144 随之引用；
  - 对构建产物一类的误判，二选一：在对话框中提供 “随副本删除” 的选择（只对这一类），或在结果与 Goal 页给出删除保留副本的入口；
  - G46 (bl) 补一组：在主检出中已存在的被忽略目录（如 `certs/`）中新生成文件后交还，期望列出并保留；另补一组：只有依赖目录与构建产物时，期望不保留（或按所选写期望）。

**R100-D13-02｜次要**（Host 退出或挂死之后、终止一轮完成之前，残留进程的写入按外部写入归因）

- **问题**：
  - Host 退出或被判挂死时，Goal 立即进入 `paused{engine_crash}`（`06` L64）；它以 `detached` 派生、带 Run 令牌的后台进程（开发服务器、`--watch` 编译器）在终止的一轮发完信号、等待、到时 SIGKILL 之前仍可能写卫星。冷启动时同理：Host 已不存在的未结束 Run 在启动时记为 `crashed`，Goal 处于 `paused`，终止的一轮在后台执行（`06` L145）。
  - 归因表（`10` L391–L395）：第 2 行要求 `running`；第 3 行要求 “settle 之后存在未解决的 `bg_process_survived`”。这一窗口两者都不满足，写入落到第 4 行 “外部候选” → `external_change` 记入 `alsoApplies`（`10` L403）。
  - 结果是：自动 “重启并恢复” 被一个需要人 keep/revert 的 `external_change` 挡住；人选 keep 时，Agent 进程的写入被记为人的改动（`external_change_kept`，`author:"human"`）。`06` L145 的 “之后仍存活的已按下一类处理” 只覆盖一轮完成之后。
  - 这在 ADR-226 引入运行中的一轮时就存在，ADR-227 把运行中的一轮写成唯一定义而没有补这一句；settle 序列中同类的窗口登记为 “已知误判 (a)”（`10` L402），这里没有登记。
- **为什么是次要**：窗口只有一轮终止的时长，多数后台进程在 Agent 停止后不再写被跟踪的文件；后果是一次多余的人工处置或一次归因错误，经人的决定发生，不丢数据。但实现者可能把第 2 行的 “本 Run 的进程” 延伸到这一窗口，也可能不延伸，结果不同。
- **后果的类别**：崩溃后的自动恢复被不必要地挡住；Agent 后台进程的写入可能经人的 keep 记为人的改动，影响归因窗口与自动返工（`03` §3.2.1）。
- **文档位置**：`10` L391–L395、L402、L403；`06` L64、L145；`03` §3.2.1。
- **期望的回答形态**：在 `10` 归因表第 3 行加一句：终止的一轮（`06` §6.1.6，冷启动与运行中）完成之前，范围内仍有令牌已确认的存活者时，写入按本行归为 `agent_bg`；或在 `10` L402 的已知误判中登记这一窗口及其处置。

### 不扣分的观察

1. **README 第 8 条的例外列表**：以 “例如” 列出与 Pi 的差异，没有列 “配置了 MCP 时外部工具每次调用都要批准”。这是 MCP 用户最先感到的差异，宜随 R100-D8-01 补半句。
2. **检验目录的告知不均**：人新建的被忽略文件只在带回时列出（`10` L972）；`inspect.close`、验收与放弃删除检验目录时（`04` L589 第 6 步）不列出。取舍已写明，宜在第 6 步的 “删除目录” 处补半句 “其中被 git 忽略的文件一并删除”。
3. **没有卫星而未归档的 Goal 的第二类令牌**：`06` L145 只豁免 “已归档、没有卫星的 Goal”，而同一行右栏对一切没有卫星的 Goal 跳过检查点。卫星在 7 天无访问后删除的 `abandoned`、重建失败的 `satellite_missing`，令牌留在范围内，每次冷启动多做一轮、短时 `清理中`。有界，宜把豁免写为 “或没有卫星”。
4. **打包模式下挂死 Host 的后代树**：后代树中可能有范围之外的 Goal 的带令牌进程（例如此前在同一 Host 上运行、现处于 `in_review` 的 Goal 的存活者）。它们随后代树终止，而所属 Goal 不在范围中、不补检查点、不告知，其 `bg_process_survived` 在下次复查时以 `obsolete` 关闭。宜写一句归属。
5. **一轮完成与补检查点之间的崩溃**：下次冷启动再做一轮，幂等；但 “有进程被终止” 不持久化，恢复开场的 `tower.processes_terminated` 可能丢失。属于告知的完整性，宜如实登记。
6. **“打扰率” 的口径**：§14.6.2 定义为 “每用户每小时 L2+ 条目”（`14` L667），`08` 的打扰预算只对 L3/L4 扣令牌（`08` L784），M1 门槛与 E3 只写 “打扰” 不注级别。按 §14.6.2 读是一致的，宜在处理 R100-D8-01 的度量时注明引用同一口径。
7. **`12` L390 的 “只在双重故障中同时出现”**：运行中的一轮不阻挡 `goal.hand_back`，`写回中` 与 `清理中` 现在也可能在运行时同时出现；两者经 `wtLock` 串行，只是措辞。
8. **措辞与登记**：
   - `11` L720（T33）写 “云 SDK 凭据只以指向文件的变量传入 Host”，在讨论机密的语境中成立（配套变量不是机密），宜改为 “机密只以文件路径传入”；
   - `16` L394（§16.1.13 的历史行）现行一列仍是 ADR-158 时的写法，属于历史文字；
   - `04` L660 用 `certs/dev.key` 同时举 “不被忽略的凭据形文件” 与 “被忽略目录中的新文件” 两类，易混，宜换一个名字（随 R100-D13-01 修改时一并处理）；
   - `16` L722 的配套变量列出 `GOOGLE_CLOUD_PROJECT` 而没有 `GCLOUD_PROJECT`，`11` L518 两者都有。
9. **合同编辑器 “批准” 上方的多行说明**：致命三要素决策块、本地机密文件说明与 `ExternalToolNote` 的上下顺序没有写，宜在 `12` §12.12 补一句。
