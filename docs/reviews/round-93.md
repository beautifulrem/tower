## 1. 总评

**第 92 轮的 3 条重要条目都已按所问关闭**（核对见 §3）。§5 的 14 条观察全部落地。回应 “偏离与未决” 的六条全部接受，其中 “上下文文件更严” 带出两处未同步的验收期望（R93-D14-01）与一处注意力上的后果（R93-D8-01）。

**ADR-220 的主体成立**（§3.3）：
- **使用时强制**：三个工厂确实把求出的绝对路径交给 `operations`，Tower 的辅助进程在 S2 中执行，分类之后换上的路径分量不能把访问带出 S2。`operations` 之外只剩两处元数据访问：已登记的变体探测，以及未登记的 `withFileMutationQueue` 的 `realpath`（观察 1）。`<sdk:name>` 压过内置与扩展，自检是回归保护，成立。
- **删除目录型工具**：M1 中没有阶段需要它们，Pi 的系统提示词在三者都不在时自动改为让模型用 bash，技能经 `read` 加载不受影响。
- **写回失败**：任何分支都不留下 `syncing`；保留检出、还原未完成时转入情形 E，命令与自动转移不再落在 CHECK 之外；启动续写在删除前比较来源目录。

**ADR-220 带出的新问题**（都是次要）：
- **文件辅助进程的规格**（R93-D5-01、R93-D10-01）：“带大小上限与超时” 没有取值，而 Pi 的 `read`/`edit` 整读整写，取 `10` §10.1.3 的 “例如 1 MB、2 s” 会使大文件（常见的锁文件）不能读、不能改；它的内存 “计入 Engine Host 一行”，但 SP2、E6 与准入模型的 `h` 都只量 Host 进程，打包时 15 MB/Goal 的预算放不下一个独立进程。
- **Pi 的完整输出文件读不到**（R93-D5-02）：Pi 把截断输出的全文写在 Host 的 `os.tmpdir()` 并让模型 `read` 它；ADR-220 之后 `read` 在 S2 中执行，该位置不在读允许列表中；`11` L522 说它在 `$TMPDIR/tower-<goalId>/`，与 `05` L465 的唯一定义矛盾。
- **注定失败的审批**（R93-D8-01）：S2 必然拒绝的访问仍出审批卡，凭据读取被批准后再以 severity 2 的 “可能表明提示注入” 告警，不可标为良性。
- **写回失败处理自身的中途崩溃与 “改名保留”**（R93-D6-01）：① 的重新物化不是原子的；③ 置 `satellite_rebuilding=1` 后、移开旧卫星之前崩溃，`06` L140 会在重建成功后删除它；“按 `10` §10.2 改名保留 / 移到一边” 指向的机制在 `10` §10.2 中不存在（该节写 Tower “不自行改名”）。
- **“删除前比较” 的适用范围**（R93-D6-02）：`06` L144 末句与 `04` L667 写成一般规则（“只在写回成功、且内容仍等于 T1 时删除”），而本进程中的交还第 8 步、带回完成步骤仍不比较就删除。
- **G46 的两组期望与 ADR-220 相反**（R93-D14-01）。

**排期**：

- 余量：系统 0.12、Agent 0.14、桌面 0.25、设计 0.30、安全 0.12。

### D5 Agent 架构与 Pi 集成

**R93-D5-01｜次要**（文件辅助进程的回复上限与超时没有取值，与 Pi 整读整写的语义相撞；辅助进程崩溃后怎样处理未定）

- **问题**：
  - `11` L160 只写 “带大小上限与超时，超出即该次操作失败”，`16` 中没有对应的默认值。
  - Pi 的 `read` 先 `ops.readFile` 整个文件再按行截断或取 `offset`/`limit`（`read.ts:135, 155`）；`edit` 整读整写（`edit.ts:186, 198`）。所以上限低于某个文件的大小时，该文件**无论怎样分段都读不了、改不了**，Pi 自己的 “Use offset=… to continue” 提示也无效。
  - 文档中离这里最近的数值是 `10` §10.1.3 的 “例如 1 MB、2 s”（L222，Tower 自己读 Agent 可写文件的规则）。照搬它时，常见的锁文件、生成的夹具都会超出。
  - 生命周期：辅助进程与 Agent 的进程同在一个沙箱、同一用户，可能被终止或卡在某个文件上；文字没有说崩溃或超时之后是否重启、是否把卡住的进程杀掉，也没有说它在 settle 第 3 步之前停止（超时被报告为失败的写入可能在之后才落盘，`edit.ts:164-167` 的注释说明进行中的文件操作可能完成）。
- **后果的类别**：实现分叉——有的实现取小上限，使 Agent 不能编辑大文件；有的不设上限，大文件在辅助进程与 Host 中各占一份内存；辅助进程死掉之后，有的实现让本 Run 余下的文件工具全部失败。
- **文档位置**：`11` L160；`05` L386-L395；`16` 默认值各节；`13` §13.8.1。
- **期望的回答形态**：在 `11` L160（唯一定义）补一句：上限与超时的取值（例如上限不低于 Host 可承受的单文件大小，并登记在 `16`）；超出时工具结果的文字（例如 “文件超过 N MB，请用 bash 分段处理”）；辅助进程退出或超时后杀掉并在下一次操作时重启；Run 结束时在 settle 第 3 步之前停止。

**R93-D5-02｜次要**（Pi 的完整输出文件写在 Host 的临时目录，ADR-220 之后 `read` 在 S2 中读不到它；`11` L522 的说法与 `05` L465 矛盾）

- **问题**：
  - Pi 把截断的 bash 输出全文、MCP 二进制资源与 codemode 的图像都写在 `os.tmpdir()`（`utils/output-files.ts:17-27`），并在工具结果中写 “Full output: <path>”，引导模型去读（`bash.ts:343-352`）。

### D6 系统架构与可靠性

**R93-D6-01｜次要**（写回失败处理自身的中途崩溃：① 的物化不是原子的，③ 置重建标记后、移开旧卫星之前崩溃会删除旧卫星；“按 `10` §10.2 改名保留 / 移到一边” 指向不存在的机制）

- **问题**：
  - **① 中途崩溃**：① 在原路径以 T1 重新物化来源目录（`06` L914，按 `10` §10.8.4 第 2–3 步或 §10.8.3 第 1 步），这两步都是在目标路径上直接写出，不经旁路目录。此时 `syncing` 仍在（③ 尚未执行）。崩溃之后重启续写；续写若再次失败，① 的条件 “来源目录已不存在” 不成立（残缺的目录在），于是跳过物化，③ 清除 `targetTree`。残缺的目录从此被当作人的副本：人再交还时从它算出 T1′，写回集合 B→T1′ 会删除没有物化出来的文件。T1 只剩在影子对象中，失败处理 “不写决定”，没有任何记录引用它。
  - **③ 之后、移开旧卫星之前崩溃**：③ 在同一事务中置 `satellite_rebuilding=1`，并写明 “仍在的卫星先……移到一边、不删除”。若在移开之前崩溃，重启时 `06` L140（重建中途崩溃）把仍在原位的卫星当作 “原子 `rename` 之后、提交事务之前” 的产物，移入旁路目录、“续做成功后删除”。与 ③ 的 “不删除” 相反；只存在于旧卫星中的内容（如 `keep_both` 时保留在卫星中、尚无检查点的外部写入 E）随之删除。
  - **“改名保留 / 移到一边” 没有定义**：`06` L144（续写删除前比较不同）与 L914 ③ 都写 “按 `10` §10.2”，但 `10` §10.2（L254）写的是 `_human/<goalId>`、`_inspect/<goalId>` “不写出、不覆盖、不删除，Tower 也不自行改名”，唯一的改名是人点击的 `goal.take_over{moveAside}` → `_human/<goalId>.kept-<时间>`；卫星与 `_inspect` 没有对应的命名、`_gitdirs/<goalId>` 怎样处理、谁清理，都没有写。
  - **② 的还原范围**：② 只还原 `written` 中的路径，而 `written` 是批量提交的（`10` L993）。崩溃之后续写再失败时，崩溃前已写而未记入 `written` 的路径不被还原，还原却被判为 “完成”；交还侧随后第 6 步把这些 Tower 自己的写入当作 “卫星在你编辑期间被改动”，带回侧则触发 I2。
- **后果的类别**：在 “写回失败 + 崩溃” 的窗口中，人的改动可能只剩在一个残缺的目录里，之后的交还删除未物化的文件；旧卫星中尚无检查点的内容被删除；Tower 自己的写入被归为来源不明。窗口窄（需要两次故障），但都发生在 ADR-220 新增的步骤上。
- **文档位置**：`06` L140、L144、L914；`10` L254、L885、L946、L993、L1259。
- **期望的回答形态**：在 `06` L914（唯一定义）补：
  - ① 在旁路目录中物化完毕后再改名到原路径（与情形 E 的 “旁路目录 + `renameat`” 相同），或在 ① 之前先在同一事务中记一个 “正在重新物化” 标记，重启时据此重做；
  - ③ 先把旧卫星移开、再在事务中置 `satellite_rebuilding=1`（或在 `06` L140 中区分 “写回失败转入的重建”），使 “不删除” 在崩溃后同样成立；
  - ② 还原整个写回集合（幂等），或还原后比较卫星树与还原目标再判定 “完成”；
  - 在 `10` §10.2 定义 Tower 自动改名保留的命名（例如与 `moveAside` 同形的 `.kept-<时间>`）、它们不再被管理、在 Goal 页列出，或改为不改名、只在结果中列出路径。
  - G31 补一组只写期望：① 物化到一半时杀掉 Tower 并让续写再失败 → 人的改动不丢、条目写明。

**R93-D6-02｜次要**（“只在写回成功、且内容仍等于 T1 时删除来源目录” 写成一般规则，而本进程中的完成步骤不比较就删除；比较的口径未定）

- **问题**：
  - `06` L144 在启动续写一行的末尾写 “来源目录只在写回成功、且其内容仍等于 T1 时删除（ADR-220）”，`04` L667 对用户写 “Tower 只在写回成功、且副本内容与交还时相同时才删除它”。两处读起来都是一般规则。

  - 比较的口径写为 “按 `10` §10.8.4 第 5 步（带回按 §10.8.3 第 7 步）同一规则对目录求树，与 T1 比较树 id”。

### D8 注意力与交互

**R93-D8-01｜次要**（S2 必然拒绝的访问仍出审批卡；凭据读取在人批准之后又以 severity 2 告警）

- **问题**：
  - ADR-220 之后，S2 下 `read`/`edit`/`write` 的权限不超过沙箱 bash：读允许列表之外的 `read.external`、密钥路径表、上下文文件名的写入 “即使经批准也会失败”（`11` L160）。这些类在多数预设中仍是 ask（`11` §11.2；`secrets.access` 是单向门、需要双确认）。
  - 是否为 “必然被拒” 的调用出审批卡，正文没有写；“分类与审批卡照旧” 只出现在回应文件中。`04` L1133 把 M1 的凭据审批卡当作一种卡片描述，没有区分沙箱外工具（批准后能读）与 S2 下的 `read`（批准后必然失败）。
  - 批准之后的拒绝按 `11` L371 记 `sandbox_violation`；凭据读取属 `credential` 类，是 severity 2 的 Needs-You，措辞为 “可能表明提示注入或越权意图”，不能标为良性、永不降级。人刚刚亲手批准的动作因此再生成一条告警。
  - 审批期间 Agent 处于 `blocked_guard`，等待一个结果已知的决定。
  - ADR-220 之前 bash 已有同样的分支，但 `read` 是 Agent 读文件的主要途径，此后这类卡片会常见得多。
- **后果的类别**：违背 “只在需要人时打扰人” 的原则：人被要求做一个不起作用的决定（凭据一类还要双确认），之后又收到针对自己决定的告警；实现会分叉（有的直接拒绝，有的出卡片，有的在批准之后抑制哨兵）。
- **文档位置**：`11` L160、L371、§11.2、§11.3.5；`04` L1133；`08` §8.4；`16` §16.1.6。
- **期望的回答形态**：在 `11` §11.3.5 或 L160 写一条：S2 下，分类时已知必然被沙箱拒绝的文件工具访问（求出的路径不在读允许列表中、命中密钥路径表、写上下文文件名）按 forbid 处理，返回给模型的文字说明 “沙箱不允许，改用 `ask_user`”，不出审批卡；或者保留卡片，但卡片写明 “S2 下批准后仍会被拒绝”，且对已批准调用的拒绝只记审计、不另生成 severity 2 的 Needs-You。bash 一侧按同一原则写明是否适用。

### D10 性能

**R93-D10-01｜次要**（辅助进程的内存 “计入 Engine Host 一行”，但没有任何测量覆盖它；打包时 15 MB/Goal 放不下一个独立进程）

- **问题**：
  - `13` L173：Engine Host “目标 ≤ 60 MB；……打包时 ≤ 15 MB/Goal”，“该 Goal 的文件工具辅助进程……计入本行”。
  - 但 Host 的每一种测量都只看 Host 进程本身：`13` §13.1 的 Host 预算不含工具子进程；§13.12.3 以 `process.memoryUsage()` 采集；SP2（`14` L26）与 Host 粒度回退规则（`16` L866）以 “独占 Host 稳态 RSS p95” 判定；§13.8.3 准入模型的 `h` 取自 SP2。SP2 在 M0 进行，辅助进程在 M1 的 W4 中才出现。
  - 文字只说它是 “只做文件读写的小程序（不加载 Pi）”，没有说形态。以 Electron 自带的 Node 运行一个脚本是最省事的做法，单独一个进程的常驻内存就以数十 MB 计，打包时的 15 MB/Goal 无法成立；写成原生小程序则需要另一个构建目标。
- **后果的类别**：预算与准入模型系统性低估每个运行中 Goal 的内存；E6 与 CI 的 Host 内存门槛测不到它，超出时不会被发现；实现形态分叉。
- **文档位置**：`13` L36、L173、§13.8.3、§13.12.3；`14` L26；`16` L866、§16.2.6；`11` L160。
- **期望的回答形态**：在 `13` §13.8.1（唯一定义）为辅助进程单列一行（形态、常驻内存上限），或明写 “计入本行” 时测量取 Host 与其辅助进程 RSS 之和，SP2 与 E6 同步采集；准入模型的 `h` 写明是否含它；若定为原生小程序，W4 的估计与 `00` §0.5.1 的平台说明同步。

    6. **`04` L667 带回一侧的措辞**：重建期间的提示 “完成后可再次交还或放弃改动” 没有带回的写法（带回的出口是再次带回或关闭检验，`08` L516）；第一条提示已有括注，宜同样处理。

    8. **出口与验收组**：`08` L516 的出口未列 `goal.abandon`（`06` L914 写明照常可用）；G31 “不可写” 一组没有断言出现 `write_back_failed` 条目。
    9. **条目与 ③ 不在同一事务**：④ 的 Needs-You 在 ③ 的事务之外生成，两者之间崩溃时，“写回未完成”“Tower 已重新建立你的副本” 的告知丢失。宜在 ③ 的事务中写入。
    10. **重建来源的措辞**：交还失败转入重建时只用检查点 k，而第 6、7 步可能已在链上建了 safety 或 `agent_bg_done` 检查点，`10` L974 “接管期间它就是第 1 步的检查点 k” 不再总成立；情形 E 随后的告知 “检查点 n 之后的改动无法恢复” 在这里不准确（内容在检查点 n 中）。宜写 “未进入工作目录，仍在检查点 n 中”。
