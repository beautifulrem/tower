### D13 隔离、git 与并发

**R24-D13-01｜重要**（LFS 对象由谁、何时、以什么凭据取进镜像，没有定义；现文的先后不可能成立）

- **问题**：
  1. **先后矛盾。**
     - `10` §10.3.1 步骤 2（L210）规定，检出时 `GIT_LFS_SKIP_SMUDGE=1`，随后“由 Tower 从镜像的 LFS 存储 smudge 受跟踪文件”。步骤 2 属于 ①，计入 120 s，失败即 `prepare_failed`（`10` L223）。
     - 对象从哪里来，ADR-074（`15` L509）与 `10` §10.14（L941）的回答是：“LFS 对象由**安装器步骤**预取到镜像的 LFS 存储（网络只允许 LFS 端点）”。
     - 但安装器属于步骤 5（②），在步骤 2 之后，而 ADR-149 刚把这个顺序写成唯一定义。于是一个 LFS 项目的第一个 Goal 在步骤 2 时，镜像的 LFS 存储必然是空的。
  2. **安装器里也没有这一步。**
     - 安装器各阶段的唯一定义（`07` §7.4.3，摘要在 `10` L321、L329）是拉取 → 预取 → 安装 → 发布。拉取只连注册表；预取只放浏览器、引擎与 Node 头文件。没有任何阶段取 LFS 对象。
     - M1 中非 Node 项目没有验证器安装器（`10` L302、L332）。可是 LFS 支持并不限于 Node 项目（`10` L186、L941）。
  3. **凭据与网络没有写。**
     - 私有仓库的 LFS 端点需要用户的 git 凭据（凭据助手）。拉取阶段持有的是注册表令牌 `$TI`，不是 git 凭据。
     - 镜像上下文只对用户检出做本地 fetch（`10` L51）。
     - 这一步该在哪个上下文、持有哪类凭据、走哪条网络策略，是安全边界的选择，实现者无法从现文推出。`11` L336 只提到 PAC 解析会覆盖 LFS 端点。
- **为什么重要**：
  - LFS 是 M1 明确支持的仓库类型（只读，用例 G13，风险 K12）。
  - 照现文实现，每个 LFS 项目的首个 Goal 有两种结局：在步骤 2 失败进入 `prepare_failed`，而“重试”必然再失败；或者卫星里留下指针文件，Agent 与验证都在错误的内容上工作。
  - 验证槽位“从中 smudge”（`10` L941），同样没有来源。
  - 凭据归属不写，实现者可能把 git 凭据交给不该持有它的进程。
- **文档位置**：`10` L51、L186、L196–216（尤其 L210）、L221–223、L302、L321、L329、L332、L941；`15` ADR-074 L509；`07` §7.4.3；`11` L336；`14` G13（L74）、K12（L696）。
- **期望的回答形态**：
  - 写明 LFS 对象进入镜像 LFS 存储的**唯一步骤**及其位置。例如放在步骤 1 的镜像上下文中：首先从用户检出的本地 LFS 存储以 CoW 复制；缺的对象再在用户仓库上下文中、以用户自己的凭据取回，然后复制进镜像。
  - 写明这一步的凭据类别与网络策略，确认它不进入任何沙箱角色的环境。
  - 写明它是否计入 120 s；若可能很大（数 GB），给出单独的时限、进度子状态（`12` §12.6.4 词表）与失败去向（建议走 `prepare_failed`，卡片写“LFS 对象获取失败”）。
  - 改正 ADR-074 与 `10` L941 中“由安装器步骤预取”的说法，或在安装器阶段中真正加入这一步，并解释先后。
  - 用例：扩展 G13，覆盖“LFS 项目的第一个 Goal（镜像 LFS 存储为空）”和“私有 LFS 端点”。

### D4 领域模型与生命周期

**R24-D4-01｜次要**（`queuedRun` 的保留值与写入表谁优先；`Run.reason` 两条规则冲突；非 Run 出口的残值。R23-D4-01 残留）

- **问题**：
  1. **写入表与用例矛盾。**
     - `16` L25（唯一写入表）：“依赖回退、`resume`、继续目标 `run` → `resume`”。
     - 但 G42(a) 期望“`pause`/`resume` 不回退计数，`resume` 后仍在 `ready` 排队……准入通过时以 `run.requested{kind:"rework"}` 开 Run”；G42(c) 期望“人 `resume` 后按 `rework` 类别准入”；G42(o) 期望 `queuedRun{rework}` 在“`resume` 重新排队后”保留。
     - 照写入表实现，这三个用例都会失败。照用例实现，又违反“唯一写入表”。“已保留的值优先”这条规则只存在于用例期望中。
  2. **`Run.reason` 有两条规则。**
     - `16` L23：“`run.started` → `running`（`Run.reason` = `queuedRun.kind`）”。
     - `06` L292 与 `16` L25：“不经排队直接开 Run 时 `Run.reason` 取同一映射”。
     - 一个保留了 `queuedRun{rework}`（或 `{initial}`）的 `paused` Goal，在解除后有槽位、直接开 Run，此时 `queuedRun` 仍非空。前一条给 `rework`，后一条给 `resume`。“一一对应”因此不成立。
  3. **`prepare_failed` 的重试正好落在这个缝里。**
     - 首次启动失败的 Goal 保留 `queuedRun{initial}`（`04` L947 也说“重试时照常送出”）。“重试”是 `goal.resume`，经继续目标 `run` 回到准入。
     - 照写入表，它变成 `resume`：不再受评审积压闸控；在排序键中排到所有其他首次启动之前（`06` L296）；`Run.reason` 把该 Goal 的第一次运行记为 `resume`。
     - 照用例的读法，它仍是 `initial`。两种结果都可以接受，但必须选一种。
  4. **非 Run 出口的残值**（R23 第 4 项）。
     - ADR-149 规定只在 `run.started` 与 `abandon` 时清除（`15` L1198）。经 `hand_back{reverify}`、`claim_on_behalf`、继续目标 `verify`/`review`/`claim`/`settle` 离开的 Goal，会把旧值带进 `claimed`/`verifying`/`in_review`。
     - 若采用“保留值优先”，这个旧值会在下一次继续目标 `run` 时被采用。例如在评审路径上因硬上限暂停后 `resume`，Goal 会以陈旧的 `initial` 受积压闸控，并把 `Run.reason` 记成 `initial`。
     - 若采用“写入表覆盖”，残值无害，但“保留”本身也就失去了意义。
- **为什么重要**：
  - 唯一受闸控、也唯一排在后面的类别 `initial` 会被误用或丢失。
  - 一张标明“唯一”的表与三个用例期望互相否定，实现者只能二选一。
  - 修订量很小。
- **文档位置**：`16` L23–25；`06` L292、L296、L467；`15` L1198；`14` G42(a)(c)(j)(o)（L128）；`04` L947；`03` L54、L68。
- **期望的回答形态**：
  - 在 `16` L25 加一条优先规则，例如：“Goal 有保留的 `queuedRun` 时，`resume` 与继续目标 `run` 不改写它；自带类别的显式决定（`request_changes`、`retry_after_human_change`、交还 `continue_agent`、自动返工）覆盖它。”
  - `Run.reason` 统一为一条：“`queuedRun` 非空时等于 `queuedRun.kind`，否则按写入表。”
  - 写明 `prepare_failed` 重试后的类别（建议保持 `initial`）。
  - 对残值二选一：
    - 所有不经 Run 离开 `ready`/`paused` 的出口清除该列，并加 CHECK：`queued_run IS NULL OR state IN ('ready','paused')`；
    - 或者写明为什么残值不会被采用。
  - 用例：
    - G42(c) 的期望引用这条规则；
    - 新增“首次启动 `prepare_failed` → 重试”，期望类别仍为 `initial`、受积压闸控。

### D6 系统架构与可靠性

**R24-D6-01｜次要**（120 s 覆盖项目级的长步骤，没有子超时、等待豁免或续做规则；重试可能必然再超时。R23-D6-01 第 1 项残留）

- **问题**：ADR-149 把 120 s 定为“① 步骤 1–4 + ③”的合计（`10` L223）。① 中有几类耗时不随 Goal 本身变化，也不受 Goal 控制：
  1. **首次镜像建立**（步骤 1，`10` L196）：不支持 CoW 或跨卷时是一次完整复制。镜像位于 `~/.tower/projects/…`，而用户检出可能在另一个卷上，复制量等于用户的 `.git/objects`，中型仓库 0.2–2 GB，大仓库更多（`10` L22、L388）。
  2. **项目级锁的等待**：步骤 1 在“Project 级互斥锁内”执行。镜像 gc 持 `repoLock` 写锁 5–60 s（`13` L308），它只在“没有 Goal 处于 `preparing`”时**开始**，但开始之后进入准备的 Goal 要等它结束；另一个 Goal 的镜像 fetch 同样会让人等。
  3. **远端 fetch**（步骤 1，`10` L197）：`baseRef` 是远端引用时，在用户仓库上下文中执行 `fetch origin`，“失败则用本地已知值并记 Fact”。但这一步没有自己的超时。慢网络或挂起时它会耗尽整个 120 s，回退到本地值的规则永远不会触发。
  4. **超大仓库检出**：10–60 s（`10` L943）；**LFS smudge** 的耗时与对象大小成正比。
- `ensureSatellite` 标为“幂等”（`10` L192），但没有写超时中止后已完成的部分（例如已复制一半的镜像、已完成的检出）是保留还是丢弃，也没有写下次重试是否从已完成的步骤续做。若不续做，上述情形中失败卡片上的“重试”必然再超时一次。这正是 R23 第 1 项指出的后果，回应只写清了计时覆盖哪些步骤。
- `16` L459 为 120 s 登记了 SP5/SP2 验证。但上面缺的是规则（豁免哪些等待、子步骤的超时、怎样续做），而不是参数值。R23 建议的用例“首建大仓库时各段计时器的归属”也没有加入。
- **为什么重要**：
  - 外置盘上的大仓库、慢网络下的远端 base 并不罕见。
  - 按现文，这类项目的首个 Goal 可能永远开不了 Run，而人除了放弃没有出路：卫星不可用时不提供“我来改”。
  - 等锁导致的超时会被显示成“启动失败”，归因错误。
- **文档位置**：`10` L22、L51、L192–216、L223、L388、L943；`13` L308；`16` L459；`06` L292；`04` L946–947；`14` G42。
- **期望的回答形态**：
  - 写明 120 s 不计入的等待：项目级锁的等待、首次镜像建立（建议改在添加项目时或后台带进度完成，Goal 在此期间显示 `准备中 · 建立镜像 · <进度>`）。
  - 远端 fetch 给出子超时，到时按现有规则回退到本地值并记 Fact。
  - 写明 `ensureSatellite` 在超时中止后的续做语义：哪些产物原子发布、可复用，哪些丢弃重来。
  - 用例 G42(p)：跨卷添加 SP5 的 200k 文件仓库，并让远端 fetch 挂起，期望首个 Goal 能开始 Run（或给出可行动的失败原因），而不是反复 `prepare_failed`。

**R24-D6-02｜次要**（恢复表“准备阶段中崩溃”行的谓词过宽，会撤销人的暂停与外部写入暂停）

- **问题**：
  - `06` L125 的启动检查谓词是：“已发 `run.requested`，但没有对应的 `run.started`，且 Goal 不在 `paused(prepare_failed)`”，恢复动作是“回到 `ready`，`queued_run` 保留，重新判定准入”。
  - ADR-149 新增了两种同样留下“有 `run.requested`、无 `run.started`”的合法终点，谓词都没有排除：
    - 依赖物化中人按“暂停” → `paused(human)`（`10` L223、G42(l)②）；
    - 准备中途到达外部写入等原因 → `paused(external_change)` 等（G42(n)）。
  - 准备中 `abandon` 进入 `abandoned` 也满足这个谓词。
  - 同一张表的 L139 对 `paused` 又写“什么都不执行”。两行同时匹配，而 L125 只点名排除 `prepare_failed`，读起来像是有意包含其他暂停。
  - 这个谓词在**每次**启动时求值，不只在崩溃之后。所以“准备中暂停 → 退出应用 → 再启动”这条普通路径就会触发它。
- **为什么重要**：
  - 照字面实现，人的暂停会在重启后被撤销，并自动开 Run；来源不明的外部写入还没有处置，Agent 就在其上开始工作。这违反“`human` 只由人显式 `resume` 解除”（`03` L78），也违反 `10` L243 的原则“来源不明的内容不会先被验证或评审，再等人决定”——这里甚至会先交给 Agent。
  - `ready` 中的崩溃已由 L124（“`goals.state='ready'` → 保持 `ready` 并重新判定准入”）覆盖，L125 本可以更窄。
  - 修订量是一个谓词。
- **文档位置**：`06` L124、L125、L139；`16` L23（“准备中崩溃 → 恢复时回到 `ready`”）；`10` L223；`14` G42(i)(l)(n)。
- **期望的回答形态**：
  - 把 L125 的谓词改为“`goals.state='ready'` 且最近一次 `run.requested` 没有对应的 `run.started`”，或者删去该行，并注明由 L124 覆盖。
  - 用例：G42(l)② 之后退出并重启应用，Goal 仍为 `paused(human)`；G42(n) 同理，仍为 `paused(external_change)`。

### D11 安全与自主度

**R24-D11-01｜次要**（安装器日志尾部进入 Agent 开场，没有列入脱敏与出处标注的环节）

- **问题**：
  - ADR-149 恢复了“依赖物化失败 → Agent 简报附失败日志尾部”（`10` L221，`16` L460，`04` L944）。这段文本由 Tower 组装进开场，来源是 `prepare.log`（`10` L215）。它包含安装器各阶段的输出：拉取阶段带注册表令牌 `$TI`，安装阶段运行第三方构建脚本。
  - `11` §11.7 的原则是“密钥永不进入模型上下文”（L389）。它的环节表逐一列出 `tool_result`、验证输出与返工证据（L399–400；`05` L1171 写明返工证据“发出前经过与 `tool_result` 相同的脱敏器”），**没有**列出这条安装器日志 → 开场的通道。
  - 这段第三方输出以 Tower 消息的身份进入上下文，正文也没有要求标明它是引用的外部输出。
- **为什么重要**：
  - 这一类风险是注册表凭据（或构建脚本打印的环境值）进入模型上下文，以及不可信文本借 Tower 消息获得更高的可信度。
  - 环节表就是实现清单，没有列出的通道很可能原样转发。
  - 修订量是表中一行。
- **文档位置**：`11` L389、L399–400；`05` L1171；`10` L215、L221、L321；`16` L460；`04` L944。
- **期望的回答形态**：
  - 在 `11` §11.7 的环节表中加一行：安装器日志尾部进入开场之前，经 Supervisor 中同一个脱敏器；精确匹配集包含本次安装运行持有的令牌值；长度有上限。
  - 在开场中把它标为“安装器输出（引用）”，与返工证据中的测试输出同等对待。
  - 更一般的写法是一条不变式：“一切由 Tower 组装、进入模型上下文的文本都经同一脱敏器。”
  - 用例：在 P 系列中，用一个会打印假令牌的失败安装，检查开场中不出现其值。

### D14 路线图与可验证性

**R24-D14-01｜次要**（“各线余量足以吸收约 0.6–0.8 人周的单线增量”已经不成立；下一轮修订的落点没有安排）

- **问题**：
  - `14` L392 末句：“各线余量此次足以吸收约 0.6–0.8 人周的单线增量。”这是第 18 轮余量（0.38–0.85）时的结论。
  - 同一段给出的现值是：系统 0.11、桌面 0.16、设计 0.29、安全 0.39，只有 Agent（0.72 工作周，约 0.65 人周）满足。
  - 系统线现在是最长线（27.885）。R24-D4-01、R24-D6-01、R24-D6-02 的修订主要落在 W3/W7-core，正是系统线的工作；R24-D13-01 落在 W7（系统或安全）。
- **为什么重要**：这一句是下一次增量决策的依据。照它判断，会以为任何单线都能吸收 0.6 人周，从而错过“改派、③ + ⑤ 或再顺延”的显式选择（同一段要求超出时记 ADR）。
- **文档位置**：`14` L209、L392、L394；`15` L983。
- **期望的回答形态**：
  - 改为按线写出可吸收量：系统约 0.1，桌面约 0.15，设计约 0.26，安全约 0.35（按 0.5 人），Agent 约 0.65 人周。
  - 写明本轮修订的承担线（例如由设计线承担用例与文案，由 Agent 线承担 W3 中可拆出的部分），或者显式接受顺延，并记入 ADR-133 补记。

### D15 文档一致性与可执行性

**R24-D15-01｜次要**（`prepare_failed` 的交还语义：命令规格与 UX 摘要没有同步）

- **问题**：
  - ADR-149 补记（`15` L1199）与 `16` L29 把 `prepare_failed` 列入“交还即解除”。
  - `06` L854 `goal.hand_back` 的命令规格逐个列出“交还即解除”的原因（`human`、`app_quit`、`engine_crash`、`idle_without_submit`、`question_timeout`、`stop_condition`、`post_settle_activity`），没有 `prepare_failed`；这一列表也没有引用 `16`，引用 `16` 的只有“保留原因”。
  - `04` L638 的交还对话框说明同样没有它。
  - 后果：自 `paused(prepare_failed)` 接管并交还后，按 `06` 实现，`prepare_failed` 会留在 `alsoApplies` 中，对话框显示“交还后仍暂停：启动失败”，人还要再按一次“重试”；按 `16` 实现，交还后直接经准入开 Run。两种结果都安全，但不同，也没有用例区分。
  - 同类滞后（明确引用 `16`，不单独扣分）：`05` L591 的优先级列表没有 `prepare_failed`；`03` L78 的入口列没有 `ready`（见 §3）。
- **为什么重要**：命令规格是实现直接照抄的文字。两份规格给出不同的交还结果，测试也无法判定哪一个对。
- **文档位置**：`06` L854；`04` L638；`16` L28–29；`15` L710、L1199；`05` L591；`03` L78。
- **期望的回答形态**：
  - `06` L854 加入 `prepare_failed`，或者把整份列表改为“以 `16` §16.1.1 为准”；`04` L638 加“启动失败”；`05` L591 同步。
  - 用例：G42 新增一项“`paused(prepare_failed)`（卫星可用）→ 我来改 → 交还选‘交给 Agent 继续’”，期望不再暂停、经准入后 `Run.reason = handback`。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D5、D7、D8、D9、D12、D16 为 100。在这九个维度上没有找到可追问的实质问题。
  - 其余七个维度在 97–99 之间，最低为 D6、D13、D15（97）。
- **是否还有可追问的问题：有。** 新增与残留共 **7** 条：阻断 0、**重要 1**、**次要 6**。
  - **第 23 轮核验**：4 条中已解决 2（R23-D6-02、R23-D6-03）、部分 2（R23-D6-01、R23-D4-01）、未解决 0。
  - **其他核对**：
    - lint 全部通过，但抓不到本轮这类语义矛盾；
    - Pi 事实与 v1.2.0 源码一致；
    - 排期算术（WBS 119.0、37 周、余量 0.11–0.72、增人 33 周）全部成立，只有 `14` L392 一句过时断言。
  - **本轮追问**：
    - **R24-D13-01（重要）**：LFS 对象的来源、时机、凭据与网络没有定义，现文的先后不可能成立；
    - **R24-D4-01（次要）**：`queuedRun` 保留值与写入表的优先关系、`Run.reason` 的两条规则、非 Run 出口的残值；
    - **R24-D6-01（次要）**：120 s 覆盖首次镜像建立、等锁与远端 fetch，没有子超时、等待豁免与续做规则；
    - **R24-D6-02（次要）**：恢复谓词会把准备中被暂停的 Goal 拉回 `ready`；
    - **R24-D11-01（次要）**：安装器日志尾部进入开场，没有列入脱敏环节；
    - **R24-D14-01（次要）**：过时的余量断言，修订落点未安排；
    - **R24-D15-01（次要）**：`prepare_failed` 的交还语义在 `06`/`04` 未同步。
