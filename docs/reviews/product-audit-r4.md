# Tower 产品审计 · 第 4 轮（摘要）

> 本轮的审计 Agent 完成了全部检查与探测，但它在写完整报告时被安全分类器中止，且拒绝重新生成含作弊与安全细节的正文。下面是协调者根据它的最终答复整理的摘要：分数、r3 前 25 项的状态和前 10 项修复，安全问题只写到设计层面。证据（探测日志 `q1–q6.log`、测试日志、截图）保存在审计机器的 `/tmp/audit-r4/`，不入库。

## 0. 方法与证据

- Rust 测试 174 个全部通过（r3 为 163）；store 性能测试在高负载下一次超出 300 ms 预算（508 ms），单独重跑 3 次均通过。
- 前端 72 个单元测试通过，类型检查干净；启动 JS 77.1 KB（预算 80 KB）。
- WebKit 端到端测试 21 个通过、1 个跳过（演示数据里只有一个待验收目标，评审队列用例未执行）。
- 真实模型（ClinePass）作弊探测：r3 的作弊（改测试常量、改 golden 文件、改 Makefile）现在都在“待验收”之前被拦下；发现一种新类型的作弊未被识别，被标为完全验证、红 → 绿、风险 0。保留测试对 Agent 不可见，但其失败输出经返工提示回到了 Agent。
- Claude Code 引擎（haiku）：一个诚实的修复 20 秒内从开始走到待验收。
- 手机页：无令牌或错误令牌返回 401；带令牌可用；监听所有网卡；仅凭令牌可以覆盖哨兵暂停。
- 调度缺陷：人暂停的目标可能被调度器自行再次启动（演示数据中表现为两张相同的“已暂停”卡片）。

## 3. 前 10 项修复（审计员建议，设计层面）

1. 反作弊检查从“改动已有测试文件”扩大到 Agent 新增或改动的、会影响测试运行方式的一切文件，并在评审中标为高风险。
2. 调度在启动前重新检查目标状态，人暂停的目标绝不会被自动重启。
3. 合同不允许联网时，截图步骤中 Agent 写的代码不能借浏览器联网。
4. Tower 自己的文件写入（如评审中的编辑）不能落到目标工作区之外。
5. 基线与原测试从 Agent 写不到的存储读取。
6. 保留测试的输出默认不回传 Agent，界面上标明何时展示过。
7. Claude Code 桥对不是 Tower 的工具一律拒绝，而不是批准。
8. 手机页只监听指定网卡（如 Tailscale），安全与哨兵类决定只在电脑上做，增加推送通知。
9. 公开仓库，发布签名并公证的版本，提供 Homebrew 与自动更新。
10. 验证步骤之间重置干净检出；后台检查失败时显示“没能检查”，而不是什么都不显示。

## 4. 与主流 harness GUI 的对比

截至 2026 年 10 月，主流产品中没有一个由 harness 自己重跑验收标准、对 Agent 隐藏测试或检测测试被篡改；这是 Tower 的独特优势。Claude Code、Codex、Cursor、Conductor 都已提供带推送的手机远程控制，Tower 的手机页还没有推送。

## 5. 协调者跟进（本摘要写成时已提交）
