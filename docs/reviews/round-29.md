## 4. 追问清单（新增）

编号 `R29-D<维度>-<序号>`。严重度分为阻断、重要、次要。本轮没有阻断项与重要项，次要 4 条。

### D11 安全与自主度

**R29-D11-01｜次要**（§11.6.2 关于“只看到临时文件路径”的论证对远端 fetch 不成立；脱敏缺通用 URL userinfo 模式；残余风险未入威胁表；“SP6a 核实”无用例；临时文件的位置与崩溃清理未定义）

- **问题**：
  1. **设计规则覆盖不到 git 自身的行为。**
     - `11` L373 的规则写明：Tower 以用户身份执行的命令（推送、远端 fetch、LFS 获取）不由 Tower 把可能含凭据的值放进命令行或环境。
     - `11` L336 据此论证：“Agent 即使观察到这些进程，也只看到临时文件路径”。
     - 但对 https 远端，git 执行 fetch 或 push 时，会把配置中的完整远端 URL（含 userinfo）作为参数交给它派生的传输辅助进程（本轮实测）。Tower 没有把 URL 放进参数，git 自己放了。
     - M1 中正有这样一条命令：`10` L201 在每次为远端引用 base 准备卫星时执行 `git -C <userCheckout> fetch`。
     - M2 中还会更频繁：`10` L876 每 5 分钟一次的远端 base 轮询，以及 `10` L950 的推送。
     - C29(b) 与 G43(j) 只在 LFS 获取期间取样，测不到这一路径。
  2. **脱敏层没有兜底。**
     - `11` L402 的精确匹配集合不含用户 git 配置中 URL 自带的 userinfo，Tower 也不应收集它。
     - 模式只覆盖 `ghp_`、`github_pat_` 等几种固定前缀。`oauth2:glpat-…@`、Bitbucket 应用口令等常见的 URL 内嵌凭据都不匹配。
     - 诊断日志已经按模式脱敏 URL userinfo（`10` L235），工具结果却没有同样的模式。
  3. **登记与验证缺口。**
     - L336 说“若 sandbox-runtime 能拒绝这类查询则启用（SP6a 核实），否则按残余风险登记”。但 `14` L51–61 的 SP6a A1–A11 中没有对应用例。
     - “观察其他进程”的残余风险（含 Tower 进程继承的用户环境）只在 L336 行内一句带过，不在 `11` §11.12 的威胁表 T1–T32 中。
  4. **临时文件的位置与崩溃后的去向。**
     - 文件位置只写“Tower 数据目录下”，没有写明哪个子目录。`06` L1031–1033 规定 `goals/`、`projects/*/mirror.git` 保留在系统备份中，`tmp/` 排除。
     - “命令结束即删除”不覆盖 Supervisor 崩溃或断电的情形，启动时也没有清扫这类残留文件的规则。
     - `06` L1035 写“凭据……不写入 `~/.tower` 下的任何文件”，没有为这个短暂的例外加注。
- **为什么重要**：
  - 后果的类别与 R28-D11-01 相同：用户凭据进入并行 Agent 可观察的位置，进而可能进入模型上下文与第三方提供商。
  - 设计在这里给出了一条不成立的安全论证，实现者会据此认为远端 fetch 已受保护。
  - M1 的暴露面窄：远端引用 base、URL 内嵌凭据、观察恰好落在秒级窗口内，三者同时成立才会发生。所以定为次要。但 M2 的定期轮询会让它反复出现，应当在 M2 之前收口。
  - 临时文件放进会被备份的目录且崩溃后不清理，会让一份凭据副本长期留在备份里。
- **文档位置**：`11` L336、L373、L402、§11.12 威胁表（L530–566）；`10` L201、L235、L876、L950；`05` L1405（C29(b)）；`14` L51–61（SP6a）、L129（G43(j)）；`06` L1010–1035；`15` ADR-154 L1271。
- **期望的回答形态**：
  - `11` L336 的“为什么足够”改为如实表述：Tower 能保证的是自己不放入；git 对远端 URL 的处理（传输辅助进程的参数）属于 git 自身的行为。
  - 二者取一：
    - (a) 对 URL 含 userinfo 的远端，Tower 在用户仓库上下文的 fetch 中改用去掉 userinfo 的 URL，凭据交给用户的 credential helper；没有 helper 时，在卡片上给出可行动的提示；
    - (b) 登记为残余风险。
  - 无论取哪一种，都在 `11` §11.7 的模式脱敏中加入通用的 URL userinfo 模式：`<scheme>://<user>:<secret>@` 中的 `<secret>` 一律替换。这一条同时兜住 Tower 进程继承用户环境的那一类残余风险。
  - 在威胁表新增一行：“同一用户的进程信息（参数、环境）被并行 Agent 观察”，写明缓解（Tower 不放入、模式脱敏、SP6a 结论）与残余风险等级。
  - SP6a 增加一个 A 用例：沙箱内进程能否读取沙箱外同一用户进程的参数与环境，并记录结论。
  - 写明临时文件位于 `~/.tower/tmp/`（已在备份排除之内），启动时删除残留的这类文件；`06` L1035 加注这一例外。
  - 用例：
    - 并入 G43(j)：base 为远端引用、远端 URL 含 userinfo，仓库准备的远端 fetch 期间同样取样。期望按 (a) 看不到，或按 (b) 在 Agent 的工具结果中被替换。
    - 并入 C29(b)：Supervisor 在获取中途被杀，重启后残留文件被删除。

### D13 隔离、git 与并发

**R29-D13-01｜次要**（远端引用 base 的刷新硬编码 `origin`）

- **问题**：
  - `10` L201：“若 baseRef 是远端引用：`git -C <userCheckout> fetch --no-tags origin <ref>`”。M2 的轮询 `10` L876 同样写 `origin <baseRef>`。
  - ADR-154 补记明确支持 base 为 `refs/remotes/<r>/<b>`、且 `<r>` 不是 `origin`，例如 fork 工作流中的 `upstream/main`（`10` L215，`15` L1278，G43(n)）。LFS 一侧取 `<r>`，刷新一侧仍从 `origin` 取。
  - 结果取决于 `<ref>` 怎样解读：
    - `<ref>` 为 `upstream/main`：fetch 失败，退回“本地已知值并记 Fact”；
    - `<ref>` 为 `main`：fetch 成功，但更新的是 `origin/main`，`upstream/main` 静默地保持陈旧，而且不记 Fact。
- **为什么重要**：
  - 用户选择远端引用作为 base，就是要 Goal 从最新的上游开始。
  - 按 L201 实现，fork 工作流中的每个 Goal 都可能建立在陈旧的 base 上，之后集成时才暴露冲突。
  - 这与 ADR-154 补记刚刚确立的“远端引用取其所属远端”直接矛盾。修订只是一处规则。
- **文档位置**：`10` L201、L215–216、L876；`15` ADR-154 补记 L1278；`14` G43(n)。
- **期望的回答形态**：
  - L201 改为：base 为 `refs/remotes/<r>/<b>` 时执行 `fetch --no-tags <r> <b>`（更新 `refs/remotes/<r>/<b>`），失败则用本地已知值并记 Fact。
  - L876（M2）同步。
  - 用例并入 G43(n)：base 为 `upstream/main`，上游有新提交。期望卫星从新提交开始。

**R29-D13-02｜次要**（自动 rebase 到新 base 时 LFS 对象没有补齐路径）

- **问题**：
  - LFS 对象只在仓库准备的步骤 2a 中补齐到镜像的 LFS 库（`10` L204–239），而且只针对 `baseCommit`。
  - 自动 rebase 在 Run 空闲点执行，`rebasePolicy = auto` 是默认值，`16` L893 没有标为 M2（`10` L890–905）。它在影子中合并出树 M，按 §10.8.1 第 1–3 步用 `checkout-index` 写回卫星（`10` L646–656），然后把 `baseCommit` 改为 `newBase`。
  - 文中只说“`newBase` 已由镜像从用户仓库 fetch”，那是 git 对象。`newBase` 新增或改动的 LFS 文件，其对象从未进入镜像的 LFS 库。GitRunner 没有网络，也不能当场获取。
  - 以下几点都没有定义：
    - 写回中这些文件的 smudge 失败时怎样处理：写回中止？写成指针？
    - 随后验证 rebase 之后的 pin 时，槽位怎样物化这些文件；
    - `newBase` 的 `.lfsconfig` 改了 `fetchexclude` 时，按哪一组规则（ADR-154 只说“同一组规则”）；
    - `lfs_excluded` 是否随之更新。
  - 冲突解决 Run 的写回（`10` L909）同理。
- **为什么重要**：
  - M1 支持只读 LFS，素材类仓库中 base 前移、并带有 LFS 改动很常见。
  - 按卫星检出的做法（先跳过 smudge）实现，Agent 会在指针文件上继续工作，违反 `10` L239 的“不允许 Agent 在指针文件上工作”。按 git-lfs 的默认行为实现，写回会在半途失败。
  - 两种结果都没有定义，验证也会反复以环境原因失败。
- **文档位置**：`10` L204–239、L646–666、L890–909、L983；`16` L893；`07` L1535；`15` ADR-154 L1273。
- **期望的回答形态**：
  - 写明一条通则：凡把新 base 的内容写入卫星的操作（自动 rebase、冲突解决 Run 的写回），在 LFS 项目中先对 `newBase` 执行步骤 2a 的补齐。补齐先从用户主检出的 LFS 库 CoW，缺的再按 ADR-154 的方式获取，规则集按 `newBase` 的 `.lfsconfig` 重新解析，并更新 `lfs_excluded`。
  - 补齐失败或超时：本次不 rebase，卫星保持原样，记 Fact（例如 `base 前移：LFS 对象缺失 N 个`）并以卡片提示，下一个空闲点重试。不进入写回。
  - 用例：LFS 项目中 Goal 运行期间，base 前进了一个修改 LFS 文件的提交。
    - 用户主检出已有该对象：rebase 成功，文件为内容。
    - 对象在本地与远端都不可得：不 rebase，卫星不变，出现提示，Agent 不接触指针文件。

### D15 文档一致性与可执行性

**R29-D15-01｜次要**（`lfs_config_ignored` 的展开字段与数据不符；`06` 的认证键清单陈旧；临时文件的内容清单漏了远端 URL）

- **问题**：
  1. **展开视图与 Fact 的数据不符。**
     - `04` L951 与 `12` L660 写“点击展开被忽略的键、原因与来源（`.lfsconfig` 或你的 git 配置）”。
     - `02` L393 与 `16` L127 的 `lfs_config_ignored` 只有 `data = {keys}`，并限定为“被白名单校验拒绝的 `.lfsconfig` 值”。`10` L208–211 也只对 `.lfsconfig` 做协议校验。
     - 展开视图要的“原因、来源”字段不存在。“来源可以是你的 git 配置”还暗示 Tower 也会拒绝用户自己 git 配置中的值，例如内网的 `http://` 端点。这与 `10` 相反，会改变行为。
  2. **`06` L239 的认证键清单陈旧。**
     - 只列了 `credential.*`、`http.<url>.*`、`url.<base>.insteadOf`。
     - 漏了补记 2 的 `core.sshCommand` 与不带 URL 的 `http.*`（全局代理、CA）。`10` L219–221、`11` L374、`16` L470 都有。05-06 回应称补记 2 已落实到 `06`，正文中没有。
  3. **临时文件的内容清单漏了 `remote.<name>.url`。**
     - ADR-154 及 `10` L217–219、`06` L239、`16` L470 的清单是：include 用户全局配置、白名单键的有效值、认证配置。
     - 本轮实测：git-lfs 在获取指定的远端时要求配置中存在该远端的 URL，否则报 “Invalid remote name”；“由远端 URL 推导端点”也需要它。
     - ADR-151 的“复制 `remote.<name>.url`”仍有效，但没有写进 ADR-154 的清单。实现者按清单实现会在最常见的“端点由远端推导”情形失败，G43 能测出来，但文档本身应当完整。
- **为什么重要**：
  - 第 1 项会让界面要求不存在的数据，并可能被误读为“也校验用户自己的配置”，后者会破坏内网 LFS 的正常配置。
  - 第 2、3 项会让按 `06` 或按清单实现的人漏掉必要的键。
- **文档位置**：`04` L951；`12` L660；`02` L393；`16` L127、L470；`10` L208–211、L217–221；`06` L239；`11` L374；`15` ADR-151 L1231、ADR-154 L1271、L1281。
- **期望的回答形态**：
  - 第 1 项二者取一：
    - 展开视图只显示键与固定原因“不支持的协议”，来源固定为 `.lfsconfig`，删去“或你的 git 配置”；
    - 或者 `lfs_config_ignored` 扩为 `{keys, reason, source}`，并在 `10` 写明用户 git 配置中的值是否也受协议校验。推荐前者：用户配置可信，不校验。
  - 第 2 项：`06` L239 补上 `core.sshCommand` 与不带 URL 的 `http.*`。
  - 第 3 项：在 ADR-154 的清单与 `10`、`06`、`16` 中写明，临时文件还包含所选远端的 `remote.<name>.url`（来自用户主检出），`git lfs fetch` 以该远端名与 base 提交为参数。

- **是否还有可追问的问题：有。** 新增共 **4** 条：阻断 0、重要 0、**次要 4**。
  - **第 28 轮核验**：3 条全部已解决（R28-D11-01、R28-D13-01、R28-D15-01）。
  - **其他核对**：
    - lint 全部通过；
    - Pi 事实与 v1.2.0 源码一致；
    - ADR-154 的临时文件机制、git 的传输辅助进程参数、git-lfs 对多值键清空的处理，都已在本机 git 2.56.0、git-lfs 3.8.0 上实测；
    - 排期算术全部成立：WBS 120.51、38 周、余量 0.36–1.24、增人 33 周。
  - **不扣分的观察**：
    - **`http.extraHeader` 的清空**：git-lfs 3.8.0 自己读取这个键时不遵守“空值清空”（实测），但值相同时去重。include 进来的集合通常是主检出上下文集合的子集，所以发出的头与用户自己执行时相同。只有用户在仓库级配置中刻意清空全局 `extraHeader` 时才会不同，结局是获取失败、进入 `prepare_failed`，有定义且安全。
    - **仓库级的自定义传输代理**：写在用户主检出仓库级配置中的 `lfs.customtransfer.*` / `lfs.standalonetransferagent` 不进入临时文件。使用这类代理的项目会以 `prepare_failed` 结束。极少见，结局有定义且安全；写在全局配置中则经 include 生效。
    - **C29(b) / G43(j) 的措辞**：“环境中不含任何 URL”在用户环境含代理 URL 时过宽。应理解为“不含远端、端点 URL 与 userinfo”。测试环境可控，不影响实现。
    - **`14` L395 “增量都不在链上”**：与 W7-core 的增量不一致，对结论没有影响。
    - **上轮观察的延续**：情形 E 没有 `baseCommit` 回退，`lfs_excluded.source` 是单值。两者都有定义且安全。
- **设计是否完成：否。**
  - 四条都是局部的规则与文字补全，不需要新架构，也不影响排期。
  - R29-D11-01 是一条不成立的安全论证，应在实现 W10 的脱敏与 W7 的远端 fetch 之前更正。
  - R29-D13-02 应在实现自动 rebase 的 LFS 路径之前写明。
