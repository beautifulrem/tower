### D4 领域模型与生命周期

**R41-D4-01｜重要**（`secret_file_unseeded` 暂停后没有交还 Agent 返工的出口；“改为 human 标准”需要几步没有写）

- **问题**：
  1. **没有返工出口**：
     - `secret_file_unseeded` 进入的是 `paused(verify_env_error)`（`07` L1582）；
     - `03` §3.2.1 是暂停出口的唯一定义，其中该原因只有一个出口：“修好环境后 `retry_verify`：**同一 pin**，不经 `running`”（L86），L69 也写明 `verify_env_error` 只允许同一 pin；
     - `06` L863 写明 `goal.resume` 对 `verify_env_error` 返回 `E_STATE`；L876 写明 `retry_verify` 在该原因下只允许 `same`。
     - 但 `04` L1480 的第二个选项是“`去掉对该文件的依赖`（附转向让 Agent 改测试，返工）”，`08` L506 也写“修订标准或交给 Agent 返工后重新验证通过”，`12` L417 同样列出这一项。
     - 从 `paused(verify_env_error)` 到 `running` 没有任何命令或转移。
  2. **不会自然消失**：
     - 同一 pin 重试只会再次得到同一个 `secret_file_unseeded`，因为文件不会出现；
     - 已有的变通路径是 `take_over`（人自己改）、修订合同后再重试，或放弃。“交给 Agent”这一项无法照文档实现。
  3. **“改为 human 标准”的步骤没有写**：
     - 该选项走 `contract.amend`（`08` L506）；
     - 但 `03` 没有说修订合同会解除 `verify_env_error`；
     - 因此修订之后目标仍然暂停。界面上的“一键转换”是一个命令还是“修订 + `retry_verify{same}`”两个命令，没有写。
- **为什么重要**：
  - 这是 R40-D7-01 新路径的主要出口之一。ADR-134 要求暂停出口只在 `03` §3.2.1 一处定义；
  - 实现者要么绕过唯一转移函数自行加一条，要么不提供界面已经承诺的选项。
- **文档位置**：`03` L69、L86；`06` L863、L876；`07` L451、L1582；`08` L506；`04` L1480；`12` L417；`15` ADR-166。
- **期望的回答形态**：
  - `03` §3.2.1 的 `verify_env_error` 行加一个仅限 `stage = "secret_file_unseeded"` 的出口。例如 `goal.resume` 附必填 `note`：解除本原因，继续目标改写为 `{kind:"run"}`，`note` 进入 `pendingOpenings`，其语义与 `verify_failed_limit` 的“附转向返工”相同，但不计返工次数；也可以新设一条命令；
  - `06` L863 的 `E_STATE` 例外与 `03` L69 的“显式改写”清单同步；
  - 写明“改为 human 标准” = `contract.amend` 后自动 `retry_verify{same}`（同一事务或明确的两步）；
  - G46(n) 加两组，分别验证这两个出口的去向。

**R41-D4-02｜次要**（本地文件的添加、移除与批准没有命令与决定类型）

- **问题**：
  - `04` §4.15.1 的 `[+ 添加路径]`、建议条目的 `[添加] [忽略]`（L1291），以及“每条都由人添加或批准”（L1296），都没有对应命令；

### D7 诚实与验证

**R41-D7-01｜重要**（`secret_file_unseeded` 的判定条件过宽：常见日志即可把 Agent 的真实失败改判为环境故障，试运行也会丢掉红灯）

- **问题**：
  1. **条件只有“出现文件名”**：
     - `07` L451 的条件是“标准失败（非零退出或报错）且输出中出现某个未播种的机密本地文件的路径或文件名”；
     - 没有要求输出同时带有缺失文件的信号（`ENOENT`、no such file、加载失败）；
     - 没有规定匹配边界：清单中有 `.env` 时，堆栈或代码帧中的 `process.env.X` 就含有子串 `.env`；
     - 也没有规定它与 reporter 已解析出的断言失败谁优先。
  2. **本机实测**：
     - dotenv 17.4.2 在 `.env.local` 不存在时仍默认打印 `injected env (0) from .env.local`；
     - 因此，任何用 dotenv 加载该文件的项目，一条标准只要失败——哪怕原因是普通断言——输出中都会出现文件名。
     - 按现行规则：
       - **验证中**：记 `verify_env_error{secret_file_unseeded}`，“不是 Agent 的失败”，不返工；而 `outcomeOf` 中 `env_error` 优先于 `fail`（L1492），同一次验证里其他标准的真实失败也一并不返工；
       - **试运行中**（在 base 上）：本应是红灯的标准（功能尚未实现，正常失败）全部显示 `◇ 需要本地机密文件，M1 中无法机器验证`，合同失去“可证明完成”的依据（`04` L1092）；
       - **人看到的建议**是“改为 human 标准”，这会把本可机器验证的标准降级为人工确认。
  3. **判定输入不可信**：
     - 判定所依据的输出文本完全由被测进程产生，Agent 可以影响它；
     - 已有先例“缺失程序”（`07` L449）要求 exit 127 或 spawn `ENOENT`，并且输出指明程序名；新规则没有类似的结构性信号；
     - 结果是“不是 Agent 的失败”这一 Fact 级归因，可能建立在 Agent 产生的文本之上。
  4. **用例只有正例**：G46(n)(o) 只测“测试确实读不到 `.env.local`”，没有反例。
- **为什么重要**：
  - 诚实语法要求 Fact 推导的徽标与归因不误导。这里的误判在一个很常见的配置中稳定发生，并不是罕见边界；
  - 它让自动返工回路与红灯机制在这类项目上失效，还把人引向放弃机器验证；
  - 结局不会把失败标为通过，所以不是阻断。但它直接损害 M1 的核心验证回路，评为重要。
- **文档位置**：`07` L449、L451、L1492-1493、L1582；`04` L1092、L1480；`08` L191、L506；`15` ADR-166；`14` G46(n)(o)。
- **期望的回答形态**：在 `07` §7.4.1 把判定收紧为结构性条件，并写入规则：
  - **匹配**：按路径与文件名的完整词元匹配（前后为路径分隔符、引号、空白或行首尾），不做子串匹配；
  - **共现信号**：同一行或同一错误记录中，还要出现缺失文件的信号（`ENOENT`、`no such file`、`Cannot find`、`not found`、`failed to load` 一类，词表登记在 `16`）；只出现“加载了 0 个变量”一类信息性日志，不构成判定；
  - **优先级**：reporter 已解析出具体失败用例，且这些用例的失败消息不满足上面两条时，按普通 `fail` 处理；
  - **保守出口**：只满足文件名匹配、不满足共现信号时，记普通 `fail`，并在失败卡片上附 `◇ 输出中提到未提供的本地机密文件 .env.local`，只作提示，不改变归因；
  - **用例**：G46(n) 加三组反例：
    - dotenv 默认日志加断言失败 → 普通 `fail`，照常返工；
    - 清单含 `.env`，堆栈中有 `process.env.X` → 不匹配；
    - 输出仅提到文件名、没有缺失信号 → 普通 `fail`；
    - 另外，试运行的相同反例仍显示 `✓ 红灯`。

### D8 注意力与交互

**R41-D8-01｜次要**（“我来改”的提示指向在该状态下用不了、也看不到人自己修改的 `O 检验`）

- **问题**：
  - `04` L604-605 的“我来改”信任提示写“要运行应用请用 O 检验，并在其中打开‘带上本地机密文件’”；
  - 但 `O 检验` 从验收面板的 human 标准行发起（`04` L563，`10` L799 “人在评审中按 `O 检验`”）；
  - 而“我来改”可以从 `running`、`ready`、任意 `paused(*)` 发起（`04` §4.6.7，`10` §10.8.4），进入 `paused(human)` 后没有验收面板；`inspect.open`（`06` L874）也没有写允许的源状态；
  - 即使可用，检验检出物化的是 pin，不含人正在 `_human/<goalId>` 中的修改；

- **为什么重要**：这条提示把人引向一个在当前状态下不可用、可用时也运行不到人自己修改的操作。不涉及新暴露，评为次要。
- **文档位置**：`04` L563、L604-605、§4.6.7；`06` L874；`10` L799、§10.8.4 第 5、7 步；`11` §11.3.3。
- **期望的回答形态**：
  - 二选一：
    - 改为“此副本不含本地机密文件。需要时可自行把它们放入此目录：Agent 不能读取这里；交还时被 git 忽略的文件不会带回（`10` §10.8.4）”，并在 §10.8.4 写明交还时排除被忽略文件；
    - 删去对 `O 检验` 的指引。
  - 同时在 `06` L874 写明 `inspect.open` 的允许源状态。

### D11 安全与自主度

**R41-D11-01｜次要**（注册表认证行的 `${VAR}` 引用没有定义；仓库控制的认证行被提升为用户级）

- **问题**：
  1. **`${VAR}` 引用**：
     - `11` L407、`07` L548-550、`16` L1044 都写“从 `~/.npmrc` 与项目 `.npmrc` 读取认证行，写入即时投递文件”；
     - 但认证行最常见的写法是 `//<host>/:_authToken=${NPM_TOKEN}`，尤其是提交进仓库的项目 `.npmrc`；
     - 文档没有说 Tower 是展开这些引用（从哪里取值：首次运行的 shell 快照？每次启动登录 shell？），还是原样写入、由第 1 阶段的包管理器在它自己的环境中展开。第 1 阶段进程的环境本身也没有定义；
     - R40 期望形态明确提到了这一点，ADR-166 没有处理。照字面实现，这类私有注册表项目在 M1 中会拉取失败，结局是 `verify_env_error`，有界但功能不可用。
  2. **信任级别**：
     - 本机 pnpm 12.6.0 对仓库控制的项目级认证设置**不展开**环境变量，并明确警告；它只对用户级配置展开；
     - Tower 把项目 `.npmrc` 的认证行写进经 `--npmrc-auth-file` 交给 pnpm 的用户级认证文件，就把仓库控制的内容提升为用户级，抹掉了包管理器自己设下的区分；
     - 后果类别：仓库内容（base 中来自上游，或经批准的受保护路径改动）决定把用户的哪个凭据发往哪个主机。第 1 阶段的网络只允许注册表名单（`07` L548），因此可达主机有界，这里只作次要。
  3. **哪一份**：“项目 `.npmrc`”是用户检出中的那份，还是 stage 中来自 pin 的那份（`07` L539、`16` L1045），没有写明。
- **为什么重要**：
  - 第 1 项决定私有注册表项目在 M1 中能否安装；
  - 第 2、3 项是一条凭据路由不变式：应当写明“凭据只依据用户控制的文件发送”。
- **文档位置**：`11` L407、L429；`07` L539、L548-550；`16` L1044-1045、L1066；`15` ADR-166；`14` G46(j)(q)。
- **期望的回答形态**：
  - 写明：只有用户级 `~/.npmrc` 的认证行进入即时投递文件；
  - 写明其中 `${VAR}` 的取值来源（例如每次第 1 阶段前从登录 shell 读取被引用的那几个变量，不保存），以及取不到时的提示文案；
  - 项目 `.npmrc`（指明是哪一份）中的字面认证行保持项目级，由包管理器按自己的规则处理；其中的 `${VAR}` **不展开**，与 pnpm 12 一致；
  - G46(q) 加两组：用户级 `${NPM_TOKEN}` 能成功取得；项目级 `${VAR}` 不被展开。

**R41-D11-02｜次要**（`project.verify_profile.update` 是通用补丁，且对 web 开放）

- **问题**：
  - 新命令 `project.verify_profile.update{projectId, patch}`（`06` L875）对整份 `VerifyProfile` 生效；`16` L881 定为 web ✓*，条件只写了 `env.vars` 的机密检查；
  - 而 `VerifyProfile`（`07` L1706-1745）还包含这些字段：
    - `env.network`：验证器与检验检出可访问的主机；
    - `prefetch`：人批准的下载，带 `decisionId`；
    - `sentinelExceptions`、`flakeQuarantine`、`runnerExceptions`：带 `decisionId`，对应的 `sentinel.override`、`signal.mark_benign` 是仅本机命令；
    - `testPathOverrides`、`irrelevantGlobs`、`exposeGit`、`prepare`、`services`。
  - 按 `16` §16.5 总规则 3 与 `contract.amend` 的“web 只允许不放宽”（L906），这些字段的放宽都应仅本机；
  - 另外，此前修改项目配置走 `settings.update`（`06` L925，仅本机），两条命令的分工没有写。
  - `serve` 在 M2 交付（`16` L857），因此不影响 M1，评为次要。
- **文档位置**：`06` L875、L925、L966；`16` L881、L906、§16.5 总规则 3；`07` L1706-1745。
- **期望的回答形态**：
  - 二选一：
    - `project.verify_profile.update` 只接受白名单字段（如 `commands`、`env.vars`、`ports`、`node`），其余带 `decisionId` 或会放宽边界的字段只经各自的命令修改，或者仅本机；
    - 把该命令整体改为仅本机，与 `settings.update` 相同。
  - 写明它与 `settings.update` 的分工。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D5、D6、D9、D10、D12–D14、D16 为 100，这十二个维度上没有可追问的实质问题。
  - D4 94、D7 95、D8 98、D11 97、D15 97。
- **是否还有可追问的问题：有。** 新增共 **7** 条：阻断 0、**重要 2**、**次要 5**。
  - **第 40 轮核验**：已解决 3，部分 4，未解决 0。
  - **其他核对**：
    - lint 全部通过；
    - Pi v1.2.0 源码复核成立，Pi 依赖面不变；
    - 排期算术全部成立：WBS 121.46、38 周、系统线余量 0.14、增人 33 周；
    - 本机 dotenv 17.4.2 与 pnpm 12.6.0 的实测支撑 R41-D7-01 与 R41-D11-01。
  - **不扣分的观察**：
    - **带机密的检验检出**：Tower 会在其中自动运行 Agent 写的生命周期脚本与服务（S2，网络按 `VerifyProfile.env.network`）。这是人发起、有记录、仅本机、明确警告的例外，提示中写明“运行期间 Agent 写的代码会读到这些文件”，并有“只复制文件”一项，不扣分。
    - **glob 条目的内容哈希**：`ProjectLocalFile.path` 可以是 glob（`04` L1287），glob 条目取消标记时的内容哈希怎样计算没有写。实际可取消的只有按内容或用户标记判定的条目，结局保守（内容变化即恢复为机密），不扣分。
    - **保留的检验目录**：带机密的检验目录在“保留目录，稍后决定”时会一直留在磁盘上。这是人的选择，Agent 对 `_inspect/**` 读拒绝，不扣分。
- **设计是否完成：否。**
  - ADR-166 让 M1 的机密面在规则层面闭合。剩下的两条重要条目都落在新加的 `secret_file_unseeded` 路径上：判定条件必须结构化，并且要有交还 Agent 的出口。
  - 修复不需要新架构。
- **下一轮建议按以下顺序修订**：
  1. **R41-D7-01**：收紧判定条件，加入反例用例。
  2. **R41-D4-01**：在 `03` §3.2.1 为 `secret_file_unseeded` 加返工出口；写明“改为 human 标准”的步骤。
  3. **R41-D4-02**：本地文件的 `add` / `remove` 命令、决定类型与仅本机。
  4. **R41-D11-01**：`${VAR}` 的取值来源；只依据用户级文件发送凭据；写明是哪一份项目 `.npmrc`。
  5. **R41-D11-02**：`verify_profile.update` 改为字段白名单或仅本机。
  6. **R41-D8-01**：“我来改”的提示与 `inspect.open` 的源状态。
  7. **R41-D15-01**：文字。

  **工时与排期**：上述修订估计合计约 0.1 人周。
  - R41-D7-01 约 0.04（W9 Agent 0.03，G46 反例用例 W7 Agent 0.01）。
