## 1. 总评

**第 79 轮的 5 条中，R79-D13-01、R79-D13-02、R79-D13-03、R79-D12-01 已解决；R79-D8-01 的主体已落地，但 ② 的替换没有传到 `08` 自身的两处定义与 “阻塞类条目不能关闭” 的判定。§5 的 9 条观察全部落地**，核对见 §3。

**ADR-207 的结构性改动成立**（§3.3）：
- **单一定义**：快照排除什么已收到 `10` §10.7.1 第 1 步一处，以四类列出（L735–L745）。以下各处都引用它，不再各自穷举：
  - `10` §10.1.2（L184）、§10.6（L597）、§10.5（L581）；
  - `07` `worktreeTree`（L242–L253）、L284–L290；
  - `11` §11.8.1 的两种复核（L584、L598）；
  - `16` `Checkpoint.excludedPaths`（L316）。
  - 唯一的残留是 `16` L184 的一句登记（R80-D15-01，次要）。
- **trailer**：
  - `Tower-Local-Exclude` 只写在检查点与 pin 上。seal 的说明由 §10.6 重新生成，不带它；seal 的识别按 sha，patch-id 判定只看 seal 段的差异，都不受影响。
  - 它会随用户开启的 “保留审计地标” 进入用户仓库，带出本地文件的路径名。这是有界的，记为观察 1。
- **比较取记录的 L**：I2、`full` 闸口、`stat_cache_mismatch` 与归因第 4 行都和被比较的提交使用同一个排除集，`decisive` 与 `full` 因此一致。这是一个正确的设计。
- **`getAuth` 探测**：
  - 与 Run 中的请求走同一条认证解析；刷新在凭据存储的文件锁下进行并落盘，同一存储上的并发调用只刷新一次。
  - 但这一保证只在各进程使用**同一路径**的 `auth.json` 时成立。隔离 agentDir 怎样提供凭据，`05` 与 `11` 的说法互相矛盾，见 R80-D5-01（次要）。

**两个自行披露的未决点**：
- **F7 保持 L2**：可以接受，记为观察 6。认证暂停与 `prepare_failed` 同为 L2、同样需要人处理，有先例；只是 `08` L413 给出的理由对 F7 不成立。
- **移出清单的文件记为 Agent 的**：不是可以接受的取舍。Tower 知道这份内容是自己从人的检出复制进来的，却以 ⚙️ 事实标为 Agent 的作者，与 `02` L559 的 “人自己改的代码单独标注” 相矛盾，并改变了 `03` §3.2.1 的失败去向。修正只需复用已有字段，见 R80-D7-01（次要）。

**全范围扫描**：在 ADR-207 之外新发现 8 条次要问题，都是早先 ADR 没有同步到的文字或测试：
- `03` 的 `ready` 行仍把评审余量闸控写成 M1 的转移，ADR-191 已把它移到 M2（R80-D4-01）；

- `04` §4.8.12 对 “通过” 的定义与 ADR-187 相反（R80-D15-02）。

### D5 Agent 架构与 Pi 集成

**R80-D5-01｜次要**（隔离 agentDir 的凭据来源两处说法矛盾；ADR-207 的探测与登录指引依赖这一点）

- **问题**：
  - `05` L459（ADR-158）：使用隔离 agentDir 时，改为 `ModelRuntime.create({credentials: new InMemoryCredentialStore()})` 再 `setRuntimeApiKey`，“**整个凭据集只在 Host 内存中**”。
  - `11` L607：`riskTier = high` 的 Goal 以隔离 agentDir `~/.tower/pi-agent/` 启动，“**只链接 `auth.json`、`models.json`**”。
  - 隔离 agentDir 的使用面不小：除 `riskTier = high` 外，“扩展清单尚未确认时” 也使用它（`05` L1310）。
  - Pi v1.2.0 中，传入 `credentials` 后 `ModelRuntime` 不再读 `auth.json`（`core/model-runtime.ts:218`）。两种读法的后果：
    - **照 `05` 实现**：OAuth 类 provider 在隔离模式下没有凭据。Run 以 `No API key for provider` 失败，按 F7 ① 处理。卡片指引 “在终端 `pi` 中 `/login`”，但登录写入的 `~/.pi/agent/auth.json` 不会被内存存储读到，`getAuth` 探测永远返回 `undefined`。ADR-207 所说的 “人在终端登录后自动继续” 在这里不成立，Goal 停在暂停中。
    - **照 `11` 用符号链接实现**：Pi 的凭据锁以 `realpath:false` 按路径字符串加锁（`core/auth-storage.ts:130-135`）。链接路径上的锁与用户 `~/.pi/agent/auth.json` 上的锁是两把，ADR-207 写的 “在凭据存储锁下……并发调用只刷新一次”（`15` L3315，`06` L101）在隔离 Goal 与其他 Goal、用户自己的 `pi` 之间不成立。provider 轮换刷新令牌时，两边并发刷新会使其中一边失败，表现为一次误报的 F7。Pi 自己的注释也提到刷新令牌可能被轮换（`ai/src/auth/resolve.ts:110-114`）。
    - **第三种实现**是把 OAuth 凭据复制进内存存储。这时刷新得到的新令牌只在内存中，没有落盘。若 provider 轮换刷新令牌，用户 `auth.json` 中的刷新令牌随之失效。这一类后果是使用户自己的登录失效。
- **为什么是次要**：
  - 三种实现都能从正文推出来，结果分别是：隔离模式下 OAuth 不可用而指引错误；锁不共享，造成偶发误报；可能使用户的登录失效。
  - 后果限于认证与重新登录，不涉及代码与验证。但它直接影响 ADR-207 新写的探测语义，以及首次运行（清单未确认时）的 OAuth 用户。
- **文档位置**：`05` L459、L1310、L1317；`11` L607；`06` L101、L1183；`15` L3315。
- **期望的回答形态**：在 `05` L459 写一句，二选一。
  - 隔离模式下 OAuth 仍使用用户凭据文件的**真实路径**：`ModelRuntime.create({authPath: <~/.pi/agent/auth.json 的 realpath>})`，API 密钥照常以 `setRuntimeApiKey` 只写内存覆盖层。隔离的只是扩展、技能与 MCP 的加载目录，与锁共享、刷新落盘一致。`11` L607 的 “链接” 改为 “使用同一凭据文件（真实路径）”。
  - 或者写明隔离模式只支持 API 密钥类 provider：OAuth provider 在隔离模式下不可选，F7 卡片在这种情况下改写为 “高风险目标 / 扩展清单未确认时不能使用 OAuth 登录的 provider”，不给 `/login` 指引。

### D7 诚实与验证

**R80-D7-01｜次要**（移出清单的人的文件以 ⚙️ 事实记为 Agent 的作者，并改变失败去向）

- **问题**：
  - `10` L184 与 ADR-207 写明：移出清单后，该文件 “作为新文件出现在每个活跃 Goal 的下一个检查点或 pin 中（作者按收入它的检查点记录，`running` 中为 `agent`）”。回应把这一点列为 “只如实写明，没有新增归因规则”。
  - 这份内容是 Tower 在创建或重建卫星时从**人的检出**复制进去的（`16` L705 的复制点）。其间 Agent 也可能改过它：清单路径上的写入不进入快照，但工具调用在 Trace 中可见。所以诚实的作者是 “人的文件，可能经 Agent 修改”，不是 “Agent”。
  - 与已陈述规则的冲突：
    - `02` L559：评审单元的 `author` 是 ⚙️（Tower 计算的事实），“人自己改的代码单独标注”。
    - `03` §3.2.1 L74 的失败去向唯一规则以 “人的改动” 为界：窗口内有 `author:"human"` 或 `mixedPaths` 非空的检查点时，不自动返工，进入 `paused(human_change_verify_failed)`。
    - 这个文件记为 `agent` 后，若它（例如人的运行配置）使验证失败，Tower 会把失败自动交给 Agent 返工，并在返工证据中把人的文件当作 Agent 的改动。这正是 ADR-140 要避免的路径。
    - seal 的 `Tower-Human-Edit` 也不会写出（唯一条件是有 `author:"human"` 的 hunk，`10` L672）。
  - Tower 不缺信息：它知道这条路径刚被移出清单，也知道卫星中的这份副本是自己播种的。
- **为什么是次要**：人是有意移出这个文件的，文件在评审差异中可见，不丢失工作。但实现者照字面实现，会产出一条与 Tower 已知事实相反的 ⚙️ 作者，并改变失败的去向。这不是 “Tower 无法区分” 一类的已知限制。
- **文档位置**：`10` L184、L395、L672、L774–L776；`02` L559；`03` L74；`07` L1662；`06` L891；`15` L3329；`round-79-response.md` “偏离与未决” 第 2 条。
- **期望的回答形态**：在 `10` L184 “移出清单后” 一句加半句，用已有字段，二选一。
  - 移出后收入该路径的第一个检查点把它记入 `mixedPaths`（`Checkpoint.mixedPaths`，已有）。评审中显示为 `混合`，按 `03` §3.2.1 计为人的改动，失败不自动返工。`mixedPaths` 的注释补 “或移出清单后首次收入的播种副本”。
  - 或者把 `project.local_files.remove` 对 `running` 之外的 Goal 视为一次人的采纳，下一个检查点对该路径取 `author:"human"`，与交还的 `humanPaths` 同一机制。`running` 中的 Goal 仍按第一种处理。

### D8 注意力与交互

**R80-D8-01｜次要**（F7 ② 代替 `stalled{prepare_failed}` 的规则没有传到 `08` 自身的定义与不可关闭判定）

- **问题**：
  - ADR-207 在 `08` L210、`06` F4b（L1180）、F7（L1183）与 `16` L195 写明：认证预检失败时进入 `paused(prepare_failed)`，Needs-You 是 F7 的 `stalled{engine_error}`（`st:{goalId}:auth`），不另生成 `stalled{prepare_failed}`。

    - L209（`prepare_failed` 的登记行）：“条目与暂停原因 `prepare_failed` **成对出现**”；

**R80-D8-02｜次要**（M1 界面动作没有命令：检验的关闭、丢弃与保留目录；运行中的 `⇧V`）

- **问题**：
  - **检验检出**（M1，`04` §4.6.6）：
    - 面板有 `[关闭检验]`（`04` L585）；清理时有 `[丢弃]`、`[作为人工改动带回目标]`、`[保留目录，稍后决定]`（L587）。
    - `06` §6.4.3 只有 `inspect.open` 与 `inspect.bring_back`。事件 `inspect.closed` 已登记（`10` L1325 “由 🧑 命令触发”），却没有产生它的命令；远程矩阵因此也没有对应行。
    - 选了 “保留目录” 之后，`inspect.open` 在目录已存在时返回 `E_STATE`（`06` L895），而丢弃或稍后带回都没有命令。这个目录只能等 Goal 被验收或放弃时清理（`10` L901）。卡片上的 `◇ 检验目录有未处理的修改` 没有出口。
  - **`⇧V 重新验证`**：
    - `04` L303 的线框中，Goal 处于 “运行中 · 第 2 次运行”，过期标准行显示 “需重验 ⇧V”；`12` L228 对每个过期行都给出 `⇧V 重新验证`，`16` L972 登记为 M1 快捷键。

- **为什么是次要**：

  - `⇧V` 要么在运行中按下即失败，要么有人另造一条运行中的 “立即验证” 路径，改变验证触发的语义。

- **文档位置**：`04` L303、L585、L587；`12` L228；`16` L972；`06` L895、L897、L913；`10` L901、L1325。
- **期望的回答形态**：

**R80-D8-03｜次要**（单向门审批的 L4 分支不可达）

- **问题**：
  - `08` L66：`baseLevel` 只在 severity 3 的分支中检查 `(it.kind === "approval" && isOneWayDoor(it))` → L4。`08` L27 的 L4 定义与 L174 的表格行 “sev3 单向门审批 → L4 立即” 都以 severity 3 为前提。
  - 但正文中给审批定 severity 的只有一处：`07` L1231，`ask` 生成的 Needs-You `approval` 一律为 “severity 2，`costOfDelay:"agent_blocked"`”。`11` §11.4 与 `02` §2.9 都没有为单向门审批另定 severity 3。
  - 因此单向门审批按 L64 走 severity 2 的分支，最高为 L3（在断点投递），L4 的分支永远不会执行。
- **为什么是次要**：单向门审批会阻塞 Agent。它是 “不等断点、立即打扰” 还是 “在下一个断点打扰”，取决于一个没有定义的值。实现者可能把单向门审批定为 severity 3，也可能保持 2，投递时机因此不同。不影响审批本身的安全语义：单向门永不超时放行，也只能在本机批准。
- **文档位置**：`08` L27、L64–L68、L174；`07` L1231；`11` §11.4。
- **期望的回答形态**：在 `07` L1231（或 `11` §11.4）写一句：“动作类为单向门时 severity 3”，于是 L4 的分支成立；或者删去 `08` L66 中的这一项与 L27、L174 的对应说法，写明单向门审批为 L3。

**R80-D15-02｜次要**（`04` §4.8.12 对 “通过” 的定义与 ADR-187 相反）

- **问题**：
  - `03` §3.2.1 L74（失败去向的唯一规则；`06` L864 与 `16` L38 引用）：“‘通过’= 该次验证的结论标签为已验证或有保留的已验证……**结论为未经机器验证的验证不算通过**，ADR-187”。
  - `04` §4.8.12（标题 “验证失败后谁来修（唯一规则，ADR-140、ADR-144）”）L989：“**‘通过’**指验证结果让目标进入待验收（含有保留与**未经机器验证**），或回到已验收”。
  - 后果：按 `04` 的说法，一次 “未经机器验证” 的结果（例如 S0 未授权、零机器标准）会把窗口起点移到它之后。此前人的改动因此落在窗口外，之后的失败会自动返工，而不是进入 `paused(human_change_verify_failed)`。界面告诉用户的规则与服务端的规则相反。

- **文档位置**：`04` L984–L995；`03` L74；`06` L864；`16` L38；`15` ADR-187（L2469）。
- **期望的回答形态**：`04` L989 改为 “‘通过’指结论为已验证或有保留的已验证，并使目标进入待验收或回到已验收；未经机器验证的结果不算（`03` §3.2.1，ADR-187）”。可以把 “未经机器验证不算通过” 登记进 (D) 的反向短语。

  - **不扣分的观察**：
    1. **地标检查点带出本地文件路径名**：
       - 开启 “保留审计地标” 时，地标检查点的说明含 `Tower-Local-Exclude: <路径>`，包括机密条目的文件名，会进入用户仓库并可能随 `push --mirror` 推出；隐私清除保留这些 ref（`09` L556）。

         - `10` L755 “检查点不进入用户仓库” 宜补 “地标除外”；
         - `16` §16.2.6 宜登记检查点与 pin 上的两个 trailer 键。
       - 路径中有换行或非 ASCII 字符时，trailer 的写法宜注明按 git 的 C 风格引号转义。

       - `06` F7 一行的 `retry.ts:30-75` 宜为 `:30-108`。
    3. **比较取哪个 L 的三处空白**：
       - 归因基线为 `baseCommit` 时（`10` L395）取当时的清单；
       - 运行中观察器指纹与 Fact 新鲜度取当时的清单，清单变化只会使 Fact 变旧；
       - pin 沿用 settle 第 4 步 `agent_bg_done` 检查点记录的 L，使 `07` L349 的 I4(b) “pin 的树 = 该检查点的树” 保持成立。
