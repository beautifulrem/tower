### D6 系统架构与可靠性

**R72-D6-01｜次要**（drain 协议在 `run.ended` 之后才 “执行原目标”，接管的物化落在这个窗口中。§6.1.6 的 drain 恢复行只在 “Run 未结束” 时触发，其余各行都要求有未结束的 Run。照字面实现，在这个窗口中崩溃或退出后，没有任何一行处理该 Goal。ADR-199 把这一窗口明确列为残留 H 的来源之一，为它设计的出口在 `running` 来源下到不了）

- **问题**：
  - **顺序**：`06` L96 的 drain 序列写的是：`run.ended{outcome:"aborted"}`；之后对 `take_over`/`rewind`/`dependency`，`reasons` 为空则 “执行原目标；清除 `draining_for`”。`10` L914 起的接管步骤在 Run 空闲后才开始：第 1 步做检查点，第 2 步物化 H（大仓库需要数秒以上），第 3 步建 gitdir；最后 `06` L903 的同一事务写入 `state=paused`、`human_checkout`。`16` L40 的 `CHECK (draining_for IS NULL OR state = 'running')` 意味着这段时间里 Goal 一直是 `running`。
  - **恢复表**：`06` §6.1.6 中与此相关的三行：
    - “Run 在 drain 中途”（L146）要求 `draining_for` 非空**且 Run 未结束**；
    - “settle 中崩溃”与 “Run 中崩溃” 都要求 `draining_for` 为空且有未结束的 Run。
    - 若 `run.ended` 已经提交，这三行都不成立。重启后 Goal 停在 `running`，`draining_for` 非空，没有 Run。
  - **后果**：
    - `06` L903：`running` 中 drain 已在进行时 `take_over` 返回 `E_BUSY`；暂停请求只并入 `reasons`，等待一个不会结束的 drain。
    - 这个 Goal 因此一直停在这里，人能做的只有放弃。
    - ADR-199（`10` L253）恰好把 “§10.8.4 第 2 步物化之后、写入 `humanCheckout` 的事务之前” 列为残留 H 的来源，并以 “我来改 → `E_STATE` → 移到一边” 作为出口。在 `running` 来源下，这个出口被 `E_BUSY` 挡住。

  - 回退（`rewind`）在 drain 之后恢复检查点，同样落在这个窗口中。

  - **放宽触发条件**：改为 “`goals.draining_for` 非空”，不论 Run 是否已结束，恢复动作不变（`take_over`/`rewind` → `paused(reasons ∪ {human})`，由人重做）。这样接管物化中断后 Goal 进入 `paused(human)`，再按 “我来改” 得到 ADR-199 的 `E_STATE` 与 “移到一边”；
