编号 `R23-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。本轮没有阻断项，有重要 1 条、次要 3 条。

### D6 系统架构与可靠性

**R23-D6-01｜重要**（准备阶段两段的顺序与 `ensureSatellite` 相反；依赖安装失败、卫星创建失败的去向各有两套规则）

- **问题**：
  1. **两段的顺序颠倒，各计时器覆盖哪些步骤也没有写清。**
     - ADR-148 补记（`15` L1186）规定：先是“① 依赖物化”，再是“② 启动（卫星创建或复用、Host 握手、开场组装），总时限 120 s”。`06` L292、`05` L245、`10` L223、`16` L23、`04` L944–951 都照此写。
     - 但依赖物化是把 depcache 以 CoW 复制进**卫星**的 `node_modules`（`10` L308、L337）。卫星必须先存在。`10` §10.3.1 的 `ensureSatellite` 步骤也是：镜像（1）→ 卫星（2）→ 影子（3）→ 本地文件播种（4）→ **preparing：依赖物化**（5）→ ready（`10` L195–216）。
     - `06` L314 的流水线“通过 → ensureSatellite → … → adapter.start → run.started”中，依赖物化不是单独的一步。
     - 照补记实现，“卫星创建”这一步落在两段之间：它在依赖物化之前执行，却被划进计 120 s、`pause` 返回 `E_BUSY` 的启动段。由此有三件事不确定：
       - 120 s 是不是分成两截计算（卫星创建一截，Host 握手与开场一截）；
       - 卫星创建期间 `pause` 返回 `E_BUSY` 还是被允许；
       - 镜像建立（不支持 CoW 的卷上是一次完整复制，`10` L219）、大仓库检出、LFS smudge（`10` L210）、本地文件播种、预取（`10` L223，“浏览器与引擎常有数百 MB”）各属于哪一段。
     - 若这些步骤计入 120 s，大仓库或慢网络下的超时是确定性的：失败卡片上的“重试”只会再超时一次，Goal 永远开不了 Run。`16` L457 给 120 s 登记了 SP5/SP2 验证，但验证的前提是先写清它覆盖哪些步骤。
  2. **依赖安装失败：同一失败，两种去向。**
     - 旧规则：`10` L221“步骤 5 失败不阻止 Run：Goal 以 Fact `prepare{ok:false}` 进入 running，Agent 简报中附带失败日志尾部”；`08` L397“依赖安装失败 → 不阻止 Run（Fact `prepare{ok:false}`，L1 chip），Agent 往往能自行修复；10 min 内未出现成功的安装或测试/构建命令时才升为 `stalled{prepare_failed}`”。
     - 新规则：补记、`06` F4b（L1125）、`10` L223、`16` L458、`04` L949 规定“超时或安装器失败 → `paused(engine_crash)` + `stalled{prepare_failed}`”。
     - 两套规则并存，而且 `10` L221 与 L223 在同一节里。
     - 按新规则，后果不只是措辞：
       - 修复依赖本身的 Goal（升级依赖、修复 lockfile、base 上安装就失败的项目）永远到不了 Agent 手里。“重试”必然再失败；“我来改”要人自己修好后交还。这违反“监督而不陪跑”。
       - 这里失败的“安装器”是验证器存储的 depcache 安装器：断网、不带令牌、只允许已登记的下载（`10` L321）。它的失败在验证路径上本来按 `verify_env_error{stage:"install"}` 处理（`07` L567、L718，`10` L1073，`04` L1300），属于环境问题、不怪 Agent。补记把同一种环境故障提前成“Agent 不得开始”，而 Agent 侧的安装（Agent 存储、S2 网络策略）可能完全能成功。
       - G42(l) 的情形“lockfile 已变”说明返工 Run 也会重新物化。于是 Agent 改坏了 lockfile 时，返工无法开始，Agent 也就没有机会修好它。
  3. **卫星创建失败：同样两种去向。**
     - `10` L221：步骤 2 失败（路径已存在且不属于本 Goal）→ `broken` + Needs-You“改名重建 / 放弃”；
     - `06` F4b：“卫星创建 … 报错”→ `paused(engine_crash)` + `stalled{prepare_failed}`，选项为重试、我来改、放弃。
     - 对路径冲突这类失败，“重试”同样必然再失败。
  4. **同一子类型与词表有新旧两种含义。**
     - `08` L397 中，`stalled{prepare_failed}` 同时表示“准备阶段失败（Goal 已暂停）”和“Run 运行中 10 分钟没有装好依赖（Goal 在 `running`）”。后者在 `running` 中，“重试 = `goal.resume`”返回 `E_STATE`，`08` L493 的选项不适用。`16` L186 只登记了前者。
     - `12` L376 的 `preparing` 行把 `物化依赖` 与 `准备中 · 物化依赖 · pnpm install · 42s` 写在“此阶段（至多 120 s）暂停/我来改显示 `正在启动，稍后重试`”下面，与 L377 新增的 `依赖准备中` 行（可暂停、不计 120 s）冲突。
- **为什么重要**：
  - 依赖安装失败与大仓库首建很常见，不是罕见边角。
  - 照现文，实现者在“Run 照常开始”与“Goal 暂停且无法自行恢复”之间没有依据可选。
  - 若按新规则实现，一类正当的 Goal 在 Tower 中根本无法运行。
  - 卫星与依赖的先后是硬约束：顺序写反，计时器与 `E_BUSY` 的边界都无从实现。
- **文档位置**：
  - `15` ADR-148 补记 L1186；
  - `10` L195–223、L308、L321、L337、L1073；
  - `06` L292、L314、L1125；
  - `05` L245；
  - `08` L200、L397、L493；
  - `12` L376–377、L412；
  - `16` L23、L186、L457–458；
  - `04` L944–955、L1300；
  - `07` L567、L718；
  - `14` G42(l)。
- **期望的回答形态**：
  - **按 `ensureSatellite` 的真实步骤重新划段**，例如：
    - ① 工作区准备 = 镜像、卫星、影子、播种、依赖物化、预取，单独以 `prepare.depsTimeoutMin`（或改名为 `prepare.workspaceTimeoutMin`）为限，可 `pause`、可 `abandon`；
    - ② 启动 = Host 启动与握手、开场组装，120 s。
  - 逐步写明归属，并说明 SP5 怎样验证 120 s 与 15 min。
  - **裁定依赖安装失败的去向，并只保留一套规则**。建议：
    - depcache 安装器**失败**（非超时）沿用旧规则：Run 照常开始，Fact `prepare{ok:false}`，Agent 简报附日志尾部；验证时按 `verify_env_error{stage:"install"}` 处理；
    - 只有物化 IO 错误与超时走 `prepare_failed`。
    - 若坚持新规则，写 ADR 明确取代 `10` L221 与 `08` L397，并说明“修复依赖的 Goal”怎样启动（例如允许“跳过依赖准备并开始”的选项）。
  - **卫星创建失败**：对可重试与不可重试的失败分别写出去向。路径冲突沿用 `broken` + 改名重建；其他 IO 错误走 `prepare_failed`。
  - **`prepare_failed` 只保留一种含义**。运行中 10 分钟没有装好依赖的情形改用别的子类型（或删除），`08` L397 同步。`12` L376 删去 `物化依赖` 示例，或把它移到 L377。
  - **用例**：
    - G42(m)：depcache 安装器失败（非超时），lockfile 本身就是本 Goal 要修的对象；
    - G42(n)：卫星路径已存在且不属于本 Goal；
    - G42(o)：首建大仓库（SP5 的 200k 文件仓库）时，各段计时器的归属。

**R23-D6-02｜次要**（准备失败记为 `engine_crash` 并“不 `autoResume`”，与 `engine_crash` 按原因自动解除的规则冲突）

- **问题**：
  - ADR-148 规定准备失败 → `paused(engine_crash)`，**不** `autoResume`（`15` L1184，`06` L292、F4b，`16` L23、L186，`08` L200、L397，`12` L412）。G42(j) 的期望更明确：“**重启 Tower 也不自动重试**”。
  - 但下列各处按**原因**而不是按实例决定自动恢复：
    - `06` §6.1.4 第 5 条（L101）：“`app_quit`/`engine_crash` 在启动时**自动解除**（它们只出现在运行阶段）”；
    - `06` L139：“`app_quit`/`engine_crash` 由 §6.1.4 的 `resumeOnLaunch` 显式解除”；
    - `06` L144：“`autoResume` 按原因决定”；
    - `16` L26：“`autoResume=true` 用于 `app_quit`、`engine_crash`”；
    - `03` §3.2.1 L92：`engine_crash` 行的入口只有“running（Host 崩溃）”，出口是 `autoResume`。
  - 照这些条文实现，准备失败的 Goal 在每次启动应用时都会被解除并自动重新准备。这与“不 `autoResume`，避免重复失败”和 G42(j) 直接矛盾。
  - `03` §3.2.1 是“每个原因的入口条件与出口”的唯一来源（`03` L55–56），这一行至今没有准备阶段的入口。
- **为什么重要**：同一个原因有两种恢复语义，实现者只能二选一。按 `06` 实现，G42(j) 必然失败；按 G42 实现，又违反 `06` 中写明的唯一规则。后果本身有界（每次启动最多多试一次），所以列为次要。
- **文档位置**：`06` L64、L101、L139、L142、L144、L1125；`16` L26、L186；`03` L54、L92；`02` L167；`06` L454（`auto_resume` 列）；`12` L412–413；`14` G42(j)；`15` L1184。
- **期望的回答形态**：二选一。
  - **方案一**：`resumeOnLaunch` 只解除 `auto_resume = 1` 的 `app_quit`/`engine_crash`，准备失败写 `auto_resume = 0`。`06` L101 删去“只出现在运行阶段”；`06` L139、L144 与 `16` L26 改为“按 `Goal.autoResume`（准备失败时为 false）”。
  - **方案二**：准备失败改用独立的暂停原因（例如 `prepare_failed`），登记优先级、文案与出口，`autoResume = false`。
  - 两种方案都需要：
    - 在 `03` §3.2.1 `engine_crash`（或新原因）行加入入口“`ready`（准备阶段失败或超时，ADR-148）”，命令列写“`resume`（重试）/ `take_over`（仅卫星已存在）/ `abandon`”；
    - 补用例：准备失败后退出并重启应用，Goal 保持暂停，Needs-You 条目仍在。

**R23-D6-03｜次要**（准备阶段中出现系统暂停原因时，进行中的准备怎样处理；R22-D6-01 第 3 项没有落地）

- **问题**：
  - 准备阶段中 Goal 的状态仍是 `ready`。`10` L243 规定：`ready`（卫星已存在时）检测到来源不明的写入 → **立即** `paused(external_change)`。
  - 准备阶段可能正在物化依赖或启动 Host，正文没有写进行中的准备是取消还是继续：
    - 若继续，`run.started` 会落在一个 `paused` 的 Goal 上；
    - 若取消，槽位与端口段的释放、`queuedRun` 的保留也没有写。
  - 卫星丢失（叠加态 `satelliteRebuilding`）同理。
  - R22 期望写明二选一，回应与正文都没有处理。
- **为什么重要**：
  - 这不会改变归因：外部写入按归因表第 4 行记入 E，不会被算作 Agent 的。
  - 但它会让“`paused` 中没有活跃 Run”这条状态机约束出现未定义的路径。实现者可能让 Run 在 `paused` 的 Goal 上开始，Agent 随后在人尚未处置的外部内容上工作。
  - 修复量极小。
- **文档位置**：`10` L231（第 1 行写回窗口含依赖物化）、L243；`06` L292、L314；`03` L54、L90；`16` L23；`14` G42。
- **期望的回答形态**：
  - 在 `06` §6.2.4 写一条：准备阶段中任何系统暂停原因（`external_change`、`satellite_missing` 升级等）→ 先 `EngineManager.cancel`（中止物化或启动，释放槽位与端口段），然后按 `ready` 的规则进入 `paused(<原因>)`，继续目标 `run`，`queuedRun` 保留。
  - 或者规定：记下原因，在 `run.started` 的同一事务后立即以该原因 drain。
  - `10` L243 的 `ready` 括注引用这一条。
  - 用例 G42(p)：启动段中外部编辑器写入卫星中的一个源文件。

### D4 领域模型与生命周期

**R23-D4-01｜次要**（`queuedRun` 与 `Run.reason` 的残留：`02` 未同步、立即交还的 reason、逐条 `kind` 表、非 Run 出口的残值）

- **问题**：
  1. **`02` L337 没有同步。** `Run.reason` 仍是 `"shaping" | "initial" | "rework" | "resume" | "handoff" | "verify_fix" | "scratch_promote"`，没有 `handback`，也没有 `06` L533 与 `16` L106 中已有的 `review`。`02` 是领域模型，TypeScript 类型通常从这里生成。
  2. **立即执行的交还记 `resume`。** `06` L853 写交还为空原因时“立即执行：`continue_agent` → `running`，Run `reason:"resume"`”，而 `16` L106 写 `handback` 是“交还 `continue_agent` 开的 Run”，G42(h) 期望排队后为 `handback`。同一决定的 Run 原因因此取决于当时有没有空槽位。
  3. **逐条 `kind` 仍没有列全。** R22 期望列出每条进入 `ready` 的路径写什么 `kind`，现文只写了批准与依赖回退，其余是“写对应类别”（`16` L24）。以下情形各写哪种 `kind` 没有写：
     - `retry_after_human_change`：开场是 `tower.handback`（`06` L854），但它不是交还；
     - `sentinel_high` 中的 `request_changes`：改写继续目标为 `run`（`06` L878），而 `in_review` 中的同一命令直接发 `run.requested{rework}`；
     - 继续目标 `run`：ADR-134 写的是 `run.requested{resume}`（`15` L1008），而 G42(c) 期望“已保留的 `rework` 优先”。
     “已保留的值优先于继续目标默认的 `resume`”只在 G42(c) 的期望中隐含，规则正文中没有。
  4. **非 Run 出口的残值（R22 第 5 项，未处理）。**
     - 该列只在 `run.started` 时清除（`16` L24 列出的“保留”情形也是如此）。经 `hand_back{reverify}`、`claim_on_behalf` 离开排队的 Goal，会把旧值带进 `verifying`/`in_review`。
     - 典型序列：首次启动准备失败（`queuedRun{initial}`，卫星已存在）→ 我来改 → 交还选“直接重新验证” → 验证失败 → `retry_after_human_change` → 继续目标 `run`。若按第 3 项中“已保留的值优先”执行，这个已在评审路径上的 Goal 会以 `initial` 受积压闸控。这正是 `03` L54 要排除的情形，`Run.reason` 也会记成 `initial`。
     - 序列很少见，结果只是等待（人可越过），但它是 R22 已经点名的残值。
- **为什么重要**：
  - 第 1、2 项是类型与命令定义之间的直接矛盾；
  - 第 3、4 项决定唯一受闸控的类别 `initial` 会不会被误用；
  - 修订量都很小。
- **文档位置**：`02` L179、L337；`06` L292、L466、L483、L533、L853、L854、L878；`16` L24、L106；`15` L1008、L1183；`14` G42(c)(h)。
- **期望的回答形态**：
  - `02` L337 加入 `handback`、`review`。
  - `06` L853 改为 `reason:"handback"`，与排队路径一致。或者反过来：规定 `handback` 只用于排队路径，并删去“一一对应”。
  - 在 `06` §6.2.4 给出一张表：转移 → `kind`。规则写明：Goal 在 `paused` 中保留的 `queuedRun` 优先；没有时，继续目标 `run` 写 `resume`。
  - 所有不经 Run 离开 `ready`/`paused` 的出口清除该列：`pendingHandBack.reverify`、`claim_on_behalf`、`abandon`，以及继续目标为 `verify`/`review`/`claim`/`settle` 的执行。可加 CHECK：`queued_run IS NULL OR state IN ('ready','paused')`。
  - 用例：G42(c) 的期望改为引用这张表；新增 G42(q)，覆盖第 4 项的序列，结果是不受积压闸控。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D5、D7、D11、D12、D16 为 100。在这八个维度上没有找到可追问的实质问题。
  - 其余八个维度在 95–99 之间，最低为 D6（95）与 D15（96）。
- **是否还有可追问的问题：有。** 新增与残留共 **4** 条：阻断 0、**重要 1**、**次要 3**。
  - **第 22 轮核验**：3 条中已解决 1、部分 2、未解决 0。
  - **其他核对**：
    - lint 全部通过，但抓不到规则语义的矛盾；
    - Pi 事实与 v1.2.0 源码一致；
    - 排期算术（WBS 118.89、37 周、余量 0.1–0.72、增人备选 32 周）全部成立。
  - **本轮追问**：
    - **R23-D6-01（重要）**：准备阶段两段的顺序与 `ensureSatellite` 相反；依赖安装失败与卫星创建失败的去向各有两套规则；
    - **R23-D6-02（次要）**：准备失败的 `engine_crash` 与按原因自动解除的规则冲突；
    - **R23-D6-03（次要）**：准备中出现系统暂停原因时怎样处理（R22 残留）；
    - **R23-D4-01（次要）**：`queuedRun`/`Run.reason` 的残留。
  - D8、D9、D10、D13、D14、D15 的扣分来自上述条目，不单独编号。
- **设计是否完成：否。**
  - 剩余问题都在 ADR-148 补记新增的准备阶段周边，以及 `queuedRun` 的几处收尾，不需要新的架构。
  - 但 R23-D6-01 照现文实现会出现两类实际后果：
    - 修复依赖的 Goal 根本无法开始；
    - 大仓库首建可能确定性超时。
  - 必须在实现前裁定。
- **下一轮建议按以下顺序修订**：
  1. **R23-D6-01**：
     - 按 `ensureSatellite` 的真实步骤重新划段，逐步写明计时器与 `E_BUSY`/`pause` 的归属；
     - 裁定依赖安装失败的去向（建议恢复“不阻止 Run”，只让物化 IO 错误与超时走 `prepare_failed`），删去另一套规则；
     - 卫星创建失败区分可重试与不可重试；
     - `prepare_failed` 只保留一种含义，`12` L376 同步；
     - 补用例 G42(m)(n)(o)。
  2. **R23-D6-02**：`resumeOnLaunch` 改为按 `Goal.autoResume` 判定，或者为准备失败设独立的暂停原因；`03` §3.2.1 补入口；补“准备失败后重启”的用例。
  3. **R23-D6-03**：写明准备中出现系统暂停原因时先取消准备再暂停；补 G42(p)。
  4. **R23-D4-01**：
     - `02` L337、`06` L853 同步；
     - 给出“转移 → `kind`”表与“保留值优先”规则；
     - 非 Run 出口清除该列，加 CHECK；
     - 补 G42(q)。

  **工时与排期**：上述修订估计合计在 0.3 人周以内，主要落在 W3/W4 与用例。W4（准备阶段）原属桌面线，而桌面线只剩 0.1 工作周。建议由系统线（0.22）或设计线（0.36，用例与文案）承担，延续第 22 轮的改派做法。增人备选已只剩约 0.02 工作周：若下轮增量落在全职线上，`14` L394 的“32 周”需要同步改为 33 周，或者显式声明放弃该备选，并记 ADR。
