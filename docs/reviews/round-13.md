## 4. 追问清单（新增与残留）

编号 `R13-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。

### D4 领域模型与生命周期

**R13-D4-01｜重要**（ADR-115 引入）

- **问题**：
  - I4 的原意是“`submit` 之后没有改变工作区的**工具调用**”，实现上以指纹相等代替（`03` L96、`05` L757）。
  - ADR-115 把比较用的指纹移到“终止后台进程 → `agent_bg_done`”之后（`10` L233、`06` L184、`07` L332）。终止时，watcher 与测试运行器会刷写输出，这是 ADR-115 给 10 s 窗口的理由。
  - 刷写只要落在未被忽略的路径上，`agent_bg_done` 之后的指纹就不等于 `submit` 时的指纹。按 I4 的字面规则，这次 `submit` 作废；`06` L256 的 Projector 断言也会失败。
  - `14` G35c(b) 的预期却是“刷写进入 `agent_bg_done` 检查点、随后的 pin 含该内容，`submit` 不因此作废”。
  - 判定无效之后也没有出口：
    - nudge 只能在 `agent_before_settle` 发出（`05` L757，Pi `types.ts` L1027）；
    - 进程是在 `agent_settled` 之后才被终止的，这时 Agent 已经 settle；
    - `05` L566–570 的“settle 判定”表只有“nudge 次数已用完 → `idle_without_submit`”一行，没有“nudge 未用完但已无法 nudge”的情形。
  - 同一根源在 settle 之前也存在：Run 中 watcher 在 `submit` 之后、`agent_before_settle` 之前写入，会触发一次 nudge；watcher 持续写入时会耗尽配额，最后进入 `idle_without_submit`。G35 的前提正是 Run 中保留这些进程。
- **为什么重要**：这是“Agent 说完成 → 验证”的主路径。按现行文字，开着 watcher 的 Goal 会周期性地进入错误的暂停，而用例的预期与规则相反，实现者无法同时满足两者。
- **文档位置**：`03` §3.3 I4 L96；`05` §5.5 L554、L566–570，§5.6.2c L757；`06` §6.1.10 L184、§6.2.3 L256；`07` §7.4.1 L332；`10` §10.3.1 L226–233；`14` G35c L97。
- **期望的回答形态**：
  - 把 I4 改写为两部分：“`submit` 之后没有**工具调用**改变工作区”（以工具事件判定），以及“settle 之后的指纹”（只用来生成 pin）。或者明确规定：`submit` 之后**仅由后台进程**产生、并已归入 `agent_bg_done` 的变化不使 `submit` 作废，而 pin 以 `agent_bg_done` 之后的树为准；
  - 在 `05` 的“settle 判定”表中补上 settle 之后才发现 `submit` 无效时的出口：进入 `paused(idle_without_submit)`，或由 Tower 开一个提醒 Run，二选一；
  - Projector 断言同步修改；
  - G35c 增加一例：watcher 在 `submit` 后、settle 前持续写入未被忽略的路径。

**R13-D4-02｜重要**（R12-D4-02 的残留，ADR-114 的核心承诺在此路径上不成立）

- **问题**：交还第 6 步的三个选项（`take_human` / `take_external` / `keep_both`）在 `02` L433、`06` L831、`10` L677、ADR-114 L802 中都只有名字，没有树级语义：
  1. **`take_human`（以你的版本覆盖）**：第 7 步只按 `T0→T1` 的差异写回（`10` L678–681）。外部写入如果落在人没有改过的路径上，会原样留在卫星中，然后在第 8 步被 `author:"human"`、landmark `human_edit` 的检查点收入。`04` L613 的示例恰好是这种情形：外部写入的是 `tmp/out.log` 与 `web/.cache/a.json`，人改的是别的文件，而默认选项正是“以你的版本覆盖”。结果是，来源不明的内容不经任何显式采纳就以人的名义进入 seal 的 `Tower-Human-Edit`，与 ADR-114 L804 正好相反。`02` L461 的注释“`external` 只能经……交还变为 `human`”把这一点写成了规则。
  2. **`take_external`（放弃你的改动）**：外部内容留在卫星中，归属没有定义（是否另起 `external_change`、是否需要采纳）。
  3. **`keep_both`（保留两者稍后处理）**：`external_change` 已经“随之解除、不再另发 Needs-You”（`04` L631、`10` L677），所以“稍后”没有任何入口。人的改动是否写回、H 是否保留，也都没有定义。
- **为什么重要**：这是第 12 轮为消除“来源不明的内容以人的名义进入 seal”而设的唯一路径；默认选项恰好违反该承诺，而且是破坏性操作，语义不能留给实现者猜。
- **文档位置**：`10` §10.8.4 第 6–8 步 L674–686；`04` §4.6.7 L609–614、L631；`06` §6.4.3 L831；`02` §2.7 L433、§2.8 L461；`15` ADR-114 L802、L804；`14` G36b(b) L99。
- **期望的回答形态**：
  - 在 `10` 第 6 步为每个选项写出目标树与归因。例如：
    - `take_human`：卫星整体置为 T1，外部写入被丢弃，先做 safety 检查点；
    - `take_external`：卫星保持现状，外部写入的 hunk 标 `external`，按 ADR-114 待采纳；
    - `keep_both`：写回 T0→T1，外部 hunk 仍标 `external` 并保留 `external_change`，或者删去这个选项。
  - `02` L461 删去“交还”这一来源；
  - G36b(b) 改为三个选项各一例，并加入“外部写入与人的改动不在同一文件”的情形。

**R13-D4-03｜次要**（ADR-114 的状态机空洞）

- **问题**：
  1. **失败分支**：评审阶段的外部写入按 `fp_changed_human` 重新验证（`07` L1438）。若验证失败，会进入 `paused(human_change_verify_failed)`（`07` L1390、L1430，`03` L75）。但：
     - `goal.review.adopt_external`/`revert_external` 的前置状态只有 `in_review`、`verifying`、`accepted`（`06` L826），这个暂停状态下无法处置外部 hunk；
     - 该暂停的出口是“交给 Agent（注入人改动说明）”与“撤销人的改动（回退到人编辑前的检查点）”，都把外部写入当作人的改动处理。
  2. **“撤销到 pin”指向哪个 pin**：
     - 外部写入触发 I2 后，Tower 生成了**包含外部内容的新 pin**并验证通过，Goal 才回到 `in_review` 显示外部 hunk。`06` L827 “还原为 pin 中的版本”、`04` L527 “恢复为 pin 中的内容”若指当前 pin，撤销就是空操作；若指前一个 pin，文档没有这样写。
     - `07` L1438 又说目标“以 `10` §10.3.1 为唯一定义”，即“检测前最近的检查点”，与 `10` L241 的“pin 版本”是两种写法。
     - `06` L827 的“树回到 pin 的树则不触发 I2”分支在当前 pin 已含外部内容时永远不成立；若指前一个 pin，Goal 会以新 pin 的证据停在 `in_review`，而工作区已是旧 pin 的树。
  3. **按路径恢复没有算法**：`revert_external` “只动这些路径”，但 `10` §10.8.1 L557–575 是整树恢复（读入整棵检查点树、写出全部文件、删除多余文件）。
- **为什么重要**：评审阶段的外部写入是 ADR-114 新增的路径。失败分支与撤销目标都必须有唯一、可执行的定义，否则同一事件会因为“验证通过与否”得到不同的诚实语义。
- **文档位置**：`03` §3.2.1 L75；`06` §6.4.3 L826–827；`07` §7.10.3 L1390、L1430、L1438；`10` §10.3.1 L224、L241，§10.8.1 L557–575；`04` §4.6.5 L527。
- **期望的回答形态**：
  - 写明外部写入触发的验证失败进入哪个状态。例如新增 `verifyOrigin:"external"`，失败时进入 `paused(external_change)`，在暂停卡片上提供“采纳 / 撤销”；或者让 `adopt_external`/`revert_external` 也适用于 `paused(human_change_verify_failed)`，并按触发来源改写文案；
  - “撤销到 pin”明确为“外部写入被检测**之前**的那个 pin 的树”（或归因基线），只在 `10` 定义一次；
  - 在 §10.8.1 增加按路径恢复的变体；
  - G36b 增加 (d)“`in_review` 中外部写入使验证失败”与 (e)“撤销后的状态与证据”。

### D6 系统架构与可靠性

**R13-D6-01｜次要**（ADR-115 引入与残留）

- **问题**：
  1. **终止排在宽限确认之前**：`05` L554 与 `10` L228–233 都是先终止进程、再做 2 s 宽限确认。宽限确认若失败，或之后在 `claimed`/`verifying` 中出现 `agent_start`，Goal 会撤回到 `running`（`03` L56），但 Agent 的开发服务器与 watcher 已被终止，而 Agent 不知道这一点。Trace 中有 `agent_processes_terminated`，但没有注入给 Agent 的说明。崩溃恢复路径同理：`06` L137 在重启时终止残留进程，而 `app_quit`/`engine_crash` 会 `autoResume`（`03` L82）。
  2. **断言仍然过强**：`10` L235 说“因此 `claimed`/`verifying`/`in_review` 中不会有 Agent 进程写卫星”，而 L230 承认会有存活者，`06` L137 也承认有无法确认身份、不发信号的进程。L224 的归因表只覆盖 `running`/`paused` 与 `in_review`/`accepted`，这些进程在 `claimed`/`verifying` 中的写入归入哪一类没有定义（I2 只在 `in_review`/`accepted` 生效）。
  3. **Linux 身份键**：`06` L185 用 `/proc/<pid>/stat` 的启动时间作为身份，这个值是“开机以来的时钟滴答数”。崩溃恢复包括机器重启的情形，重启后 `(pid, 启动时间)` 并不能跨开机会话唯一标识进程。
- **为什么重要**：第 1 项会让恢复后的 Run 在“服务还在”的错误前提下工作；第 2 项使验证期间的写入没有定义的处理；第 3 项是 PID 复用防护在重启场景下的缺口。
- **文档位置**：`05` §5.5 L554；`10` §10.3.1 L224、L226–235；`06` §6.1.6 L137、§6.1.10 L184–187；`03` L56、L82。
- **期望的回答形态**：
  - 二选一：终止移到宽限确认之后；或者在撤回、恢复 Run 时以一条 `tower.*` 注入告知 Agent 被终止的进程（命令与名称）；
  - L235 改为带前提的陈述；在归因表中加一行：`claimed`/`verifying` 中的写入，在进入 `in_review` 时与 pin 比对，不一致即按 I2 处理；
  - Linux 的身份键加入开机会话标识（例如 `boot_id`），开机会话变化时直接把全部 `tracked` 行记为 `gone`，不发信号；
  - G35c 增加“撤回后 Agent 收到说明”和“重启后的身份确认”两例。

### D7 诚实与验证

**R13-D7-01｜次要**（ADR-114/115 的归因残留）

- **问题**：除 R13-D4-02 外，还有三处与 Fact/Claim/Human 语法不符：
  1. **失败分支的措辞**：外部写入导致的验证失败使用 `12` L402 的“你的改动未通过验证”。`retry_after_human_change` 会向 Agent 注入“人改动说明”（`03` L75、`06` L832）。这是把来源不明的内容说成人的。
  2. **drain 时的回合检查点**：`running` 中检测到外部写入后会先 drain（`03` L80、`10` L224）。若该回合有可变更工具，`turn_end` 检查点会以 `author:"agent"` 收入外部内容。之后人选择“保留”时，非回合检查点的树等于上一个检查点的树，被 §10.7.1 第 2 步（L492，非回合入口不跳过这一步）去重，所以 `external_change_kept` 与 `author:"human"` 都不会产生，seal 也不写 `Tower-Human-Edit`。这与 G36b(a) 的预期相反，外部内容最终记在 Agent 名下。
  3. **存活进程**：`bg_process_survived` 之后，该进程的写入“按外部写入处理”（`10` L230）。但 Tower 确知它是 Agent 的进程：在评审中它被标为 `external`，人选择“采纳为我的改动”之后，又被记为 `author:"human"`（`06` L826）。Agent 产生的内容就这样以人的名义进入 seal。
- **为什么重要**：诚实语法要求作者属性反映 Tower 所知的事实。这三处中，Tower 都**知道**的比它写下的更多，或者不同。
- **文档位置**：`03` L75、L80；`06` L826、L832；`10` §10.3.1 L224、L230，§10.7.1 L485、L492；`12` L402；`14` G36b L99。
- **期望的回答形态**：
  - 失败分支的文案与注入按触发来源区分（见 R13-D4-03）；
  - 检测到外部写入时立即做一个非回合检查点（例如 landmark `external_detected`，不归任何作者）把外部内容隔开，或者规定 drain 期间的回合检查点按路径排除已登记的外部路径；“保留”不受第 2 步去重约束；
  - 存活进程的写入标为 `author:"agent"`，附 `bg_process_survived` 注记，不进入“采纳为人”的流程；
  - G36b 增加“回合内有编辑时外部写入后保留”与“存活进程写入”两例。

### D9 视觉设计与美观

**R13-D9-01｜次要**

- **问题**：`13` L314 规定 settle 等待期（最长 10 s + 2 s）的实况行为 `收尾 · 等待后台进程退出`。但 `12` §12.6.3 的 Mode 是封闭集合，这一段只能是 `settled`（徽章“已停”）；§12.6.4 的实况行表中也没有 `settled` 行，更没有这条文案。人会在卡片上看到“已停”，而 Tower 仍在等待并可能发送 SIGKILL。

### D10 性能

**R13-D10-01｜次要**（ADR-115 引入）

- **问题**：`06` L186 规定，每个进程进入或离开追踪集合时都写一个事件，并投影成 `agent_processes` 表的一行（L558–565）。测试运行器、构建工具、包管理器会派生大量短命进程；macOS 上每 2 s 轮询一次（`10` L223），每一轮都可能产生数十到数百个事件。`13` 只为 settle 时的终止给了预算（L314），没有为这些事件的写入、事件日志的增长、表中 `gone` 行的回收给出预算或策略。
- **为什么重要**：事件日志是单写者的关键路径（`06` §6.1），写放大会挤占同一路径上的其他写入。
- **文档位置**：`06` §6.1.10 L186、§6.3 L558–565；`10` §10.3.1 L223；`13` §13.11.1 L314。
- **期望的回答形态**：
  - 只持久化存活超过 N 秒的进程，或者在每个检查点或 settle 时写一次追踪集合的快照；
  - `gone` 行随 Run 结束回收；
  - `13` 给出 3 个运行中 Goal 时每分钟的事件上限，并在 W18 夹具中测量。

### D11 安全与自主度

**R13-D11-01｜重要**（既有缺口，ADR-120 使其显性）

- **问题**：
  - 文档中 S2 的“任意深度禁止创建 `.git`”写成区分大小写的字面规则（`11` L334 的正则）。
  - macOS 默认卷不区分大小写，git 在这类卷上发现仓库时，按卷的语义把大小写变体当作 `.git`。
  - ADR-120 把 `.git` 的等价比较定为“去除可忽略码位 → NFKC → 大小写折叠”（`15` L841、`10` L76），并规定其他文档只引用它。但 S2 规则没有引用它，`14` G26（L76）也没有大小写变体。
  - 因此，`10` L91 “S2 下名为 `.git` 的条目不可能出现”与 T29 “低（S2）”的前提，在默认卷上不成立。
  - 这道禁令是沙箱外不可发现性的第一道防线：`GIT_CEILING_DIRECTORIES` 只阻止向上发现，`safe.bareRepository=explicit` 只针对裸仓库，注入的 `core.fsmonitor`/`core.hooksPath` 只覆盖两类可执行配置（`10` L93）。可能的后果是：沙箱外的扩展或 MCP git 服务器在卫星子目录中运行时，把 Agent 控制的元数据当作仓库元数据读取，从而以用户身份执行其中的配置。
  - 影子上下文的 `add -A` 遇到这类条目时是跳过、收录还是报错，文档也没有定义。
- **为什么重要**：这是 T29 的核心不变式。ADR-120 已经承认 `.git` 存在等价变体，但沙箱规则仍按字面匹配。
- **文档位置**：`11` §11.3 L208、§11.6.2 L334、T29 L549；`10` §10.1.2 L76、L91、L93，§10.7.1 L488；`15` ADR-089、ADR-120；`14` G26。
- **期望的回答形态**：
  - S2 规则按 ADR-120 的等价规则生效：至少做到对 ASCII 不区分大小写，并说明在卷语义下其余等价如何覆盖；
  - 或者在卫星所在卷不区分大小写时，由沙箱外的扫描在发现等价名时立即暂停 Run，并把这一点登记为残余；
  - 定义影子上下文对这类条目的处理；
  - G26 增加大小写变体与可忽略码位变体；T29 的残余据此重写。

**R13-D11-02｜重要**（ADR-116 引入）

- **问题**：ADR-116 对 pin 中**全部**符号链接做整链解析，并把“经过 tree 中不存在的分量”视为逃逸（`10` L78、`07` L211–216），但没有 base 豁免。base 中原有、Goal 没有触碰的下列链接，会让该项目的**每一个** Goal 都得到 severity 3 `symlink_escape`，阻断 Verified 与集成：
  - 指向被忽略目录的链接（例如指向依赖目录或构建产物）；
  - 悬空链接；
  - 绝对路径链接；
  - 测试夹具中故意越界的链接（路径处理类库的常见夹具）。
  
  同时，这些链接也不会写入两种检出（L87）。人只能逐个 Goal 覆盖，每个 seal 都会带上关于 base 内容的 `Tower-Override`。这与本设计自己确立的原则相悖：
  - ADR-109 第 5 点（`15` L761）：base 中未改动的内容“本已存在于用户自己的主检出中，写出不增加暴露面”；
  - ADR-111 第 3 点：未改动的 base 夹具不触发。
  
  `10` L78 给出的理由（未改动的链接可能因路径中的目录被换成链接而改变落点）只要求“解析结果相对 base 发生变化”的链接被检查。此外，`00` L81 仍写“base 中原有、未改动的……不受影响”。G29（`14` L82）只统计 `nested_repo` 规则的误报，不统计符号链接规则的误报。
- **为什么重要**：这是“永不降级”的 severity 3 闸口。一旦对未改动的 base 内容持续命中，覆盖就会变成例行操作，`Tower-Override` 也就失去了信号价值。
- **文档位置**：`10` §10.1.2 L78、L82、L87；`07` §7.3.2 L211–216；`15` ADR-109 L761、ADR-111 L781、ADR-116 L815；`00` §0.5.1 L81、L84；`13` L312；`14` G29、G34c。
- **期望的回答形态**：
  - 规则改为：链接在 pin 中解析不安全，**并且**满足以下任一条件才命中——该链接是新增或改变的；或者它在 base tree 中的解析结果安全，或与 pin 中的解析结果不同。base 中原本就不安全、且解析结果没有变化的链接只在信任提示中列出；
  - `00` §0.5.1 同步；
  - G29 统计符号链接规则在样本仓库上的误报；G34c 增加“base 中已有悬空或越界链接、Goal 不触碰”的对照组。

**R13-D11-03｜次要**（ADR-117 的粒度与远程边界）

- **问题**：
  1. **单位未定义**：`category` 与 `targetRoot` 在任何文档中都没有定义。Fact 只有 `{op, path|host, toolCallId}`（`11` L348），去重键、`project_benign_targets` 的列（`06` L709–712）与 E7 的降级单位“某类目标”（`08` L531）都依赖这两个字段。`16` L151 的默认良性清单带操作限定（“`~/.ssh/known_hosts`（写）”），但表结构与键中都没有 `op`。若 `targetRoot` 取受保护根（`~/.ssh`），或者“类”按目录划分，那么常见的良性写入（`known_hosts`）会把同一类中价值最高的信号（读取私钥，G32b 的用例）一并降级。这是一类“良性噪声掩盖高价值信号”的后果。
  2. **默认清单与用例冲突**：`16` L151 默认把 `~/.ssh/known_hosts`（写）放进良性清单，因此它一开始就是 severity 1。但 G32b（`14` L92）的良性对照与 `04` L799 的线框都以它作为 severity 2 Needs-You 的例子。
  3. **规则口径不一**：`08` L523 规定规则 F 需要 n ≥ 20 且从 M2 起生效；`07` L1325、`11` L348、`16` L151、`04` L816、ADR-117 都没有这两个限定。
  4. **远程边界**：本轮与上轮的新命令都不在 `16` §16.5 的远程矩阵中（L729–757）：`signal.mark_benign`、`signal.acknowledge`、`goal.review.adopt_external`/`revert_external`、`goal.external_change.keep`/`revert`、`process.terminate_again`。`06` L862 只把 `mark_benign` 标为 `decide`，没有标“禁止远程”。其中 `mark_benign` 会持久地降低整个项目的安全信号级别，性质接近已列为“仅本机”的 `autonomy.grant`。`adopt_external` 会把未经有效评审的内容记为人的改动，而手机上的浏览不计入有效评审。
- **为什么重要**：降级规则一旦粒度过粗，就会系统性地削弱 ADR-113 想保护的那类信号；远程矩阵是“改变安全边界的命令只能在本机执行”这一总规则的唯一落点。
- **文档位置**：`08` §8.4 L193、§8.9.2 L523、L531；`06` §6.3 L709–712、§6.4.3 L860–862；`11` §11.6.2 L348；`16` L151、§16.5；`07` L1325；`04` §4.8.6 L799–816；`14` G32b、E7 L413。
- **期望的回答形态**：
  - 在 `16` 中定义 `category`（凭据类、Tower 数据、用户检出、其他卫星……）与 `targetRoot`（精确到文件，还是到受保护根），并把 `op` 纳入去重键、良性清单与降级单位；
  - 规定凭据**读取**永不因 `false_positive` 比例而自动降级；
  - 让 G32b、`04` 线框与默认清单一致，例如把线框的例子换成一个不在默认清单中的目标；
  - 各处补上“n ≥ 20、M2 起”；
  - 在 §16.5 中逐行登记上述命令，`mark_benign` 改为仅本机，`adopt_external` 改为 mobile 禁止。

**R13-D11-04｜次要**（ADR-116 的清单形式）

- **问题**：覆盖之后，两种检出写出 base 版本的“git 元数据文件”是一份黑名单：`config`、`hooks/**`、`info/**`、`objects/info/**`、`commondir`、`gitdir`、`HEAD`（`10` L88、`07` L224、ADR-116 L817）。它没有覆盖其他会被 git 当作配置读取的文件，例如 base 配置启用 worktree 配置扩展时的 `config.worktree`。覆盖对话框要标出的“可执行或重定向的配置键”有三份不同的枚举：
  - `07` L223：5 个，加“等”；
  - `04` L480：7 个；
  - `10` L88：9 个。
  
  这些枚举都漏掉了 `core.pager`、`core.editor`、`diff.external`、`credential.helper`、`alias.*`、`gpg.program` 等同样会被执行的键。
- **为什么重要**：对话框是人作出覆盖决定的唯一事实来源。清单不全时，Fact 会低估风险；用黑名单定义写出规则，git 增加新的配置来源时就会静默失效。
- **文档位置**：`10` §10.1.2 L88；`07` §7.3.2 L223–224；`04` §4.6.2 L469–480；`15` ADR-116 L817；`11` T31。
- **期望的回答形态**：
  - 写出规则改为白名单：仓库形态目录中，只有 `objects/`（不含 `objects/info/`）、`refs/`、`packed-refs` 等纯数据条目写出 pin 版本，其余一律写出 base 版本或不写出；
  - 配置键在 `16` 中登记一份唯一清单，并以规则描述（“值会被 git 当作命令执行或路径重定向的键”），其他文档只引用；

### D13 隔离、git 与并发

**R13-D13-01｜次要**（R12-D13-01 的残留）

  1. **回退时对话侧的语义**：非回合检查点没有 `piEntryId`（`10` L485），而默认回退是 `navigateTree(cp.piEntryId)`（L548）。回退到这类检查点时，对话停在哪个 entry，是只回退代码，还是回退到它之前最近的回合 entry，都没有定义。
  2. **里程碑写法冲突**：`04` L675 写“可以选中并回退到它（M2）”，ADR-118 L830 与 `10` L485 没有里程碑限定。
  3. **去重吞掉地标**：§10.7.1 第 2 步（L492）对非回合入口同样适用。树没有变化时，非回合检查点不会生成，必带的 landmark 也随之丢失（后果见 R13-D7-01 第 2 项）。
- **为什么重要**：回退是 ADR-015 的核心操作；“必带 landmark”这一规则与第 2 步的去重相互矛盾。
- **文档位置**：`10` §10.7.1 L485、L492，§10.8 L548；`04` §4.7.2 L675；`12` L699；`15` ADR-118。
- **期望的回答形态**：
  - 规定回退到非回合检查点等于“只回退代码”加一条 steer，或者回退到它之前最近的回合 entry 加代码恢复，二选一；
  - 统一里程碑；
  - 写明第 2 步对 `external_change_kept`、`human_edit` 不适用：树不变时也记一个只带 landmark 的检查点，或者把 landmark 追加到上一个检查点。

- **是否所有维度为 100：否。**
