### D7 诚实与验证

**R57-D7-01｜次要**（ADR-184 把 `anyQualified` 改为“任一成立即验收前需书面确认”，但验收延续不经验收闸就回到 `accepted`；条件 ⑨“本次去向为验收延续”按定义无法在验收前确认）

- **问题**：
  - **新规则**：
    - `07` L1629：`anyQualified` 是 `04` §4.6 验收闸的唯一引用对象，“任一成立即验收前需书面确认”（ADR-183/184）。
    - `04` L540 (1)：有保留时写一句确认，逐条列出成立的条件。
  - **验收延续不经验收闸**：
    - `07` L1622–1623：`from === "accepted" && acceptanceCarriesOver(goal, pin)` 时，直接 `to: "accepted"`，`label` 可以是 `verified_qualified`。
    - 延续的判据（`07` L1627，`03` L110 I2）只看三点：已批准单元的 `contentHash` 不变、没有新增 hunk、`outcome == "pass"`。不看是否出现了新的保留条件。
  - **两个后果**：
    1. **⑨ 自相矛盾**：⑨ 只在延续发生时成立，而延续发生时 Goal 已回到 `accepted`，不存在“验收前”。照 `07` L1629 字面实现，⑨ 永远无法满足它自己的确认要求。
    2. **新条件无人确认**：
       - 从 `accepted` 修订验收标准、检验带回（`bring_back`），或交还时选“直接重新验证”，都会以 `verifyFrom = accepted` 重新验证（`16` L34）。
       - 这次验证可能新出现第一次验收时没有的条件：② 计时 flake、⑥ `runner_patched`、⑪ 正则兜底计数等。
       - 只要已批准单元的内容哈希不变，Goal 就会带着这些条件自动回到 `accepted`，人从未为它们写过一句确认。
       - 显示仍诚实（`12` L248：延续或有保留的 `accepted` 加缺角 `●*`），但 ADR-184 声称的诚实闸门在这条路径上不存在。
  - **两种实现**：
    - 照 `07` 的 `decide` 实现：延续不看条件；
    - 照 L1629 的规则实现：出现未确认过的条件时不延续、改为 `in_review`。
- **为什么是次要**：显示上不会出现无保留的“已验证”，安全边界不受影响。但这是 ADR-184 新写的闸门规则与既有的自动转移冲突，实现会分歧。
- **文档位置**：`03` L110；`04` L540；`07` L1622–1634、L1648；`12` L248；`16` L34。
- **期望的回答形态**：二选一，写进 `07` §7.10.3 的唯一定义：
  - 延续额外要求本次成立的条件（不含 ⑨）是上一次验收确认过的条件的子集，否则进入 `in_review`，只要求为新增条件写确认；
  - 或写明书面确认只针对人发起的验收，延续不重新确认。此时把 ⑨ 从“需确认”中排除，并说明新条件如何告知人（例如重入简报中的一行）。
  - G46(bb) 或 G36 补“从 `accepted` 修订标准后出现计时 flake”一组。

**R57-D7-02｜次要**（“升为决定性 / 升为永久保留”假设被升级的非永久重放包还在，但磁盘压力下最先删除的正是这类包；“被覆盖的阻断命中总有可重放的证据”不成立，缺失时怎样处理没有写）

- **问题**：
  - **两条升级规则**（`07` L497，唯一定义）：
    - 人 `override_sentinel` 使 Goal 进入 `in_review` 时，“该 pin 上最近一次以阻断结束的验证”在覆盖事务中升为决定性并写保留 ref——“被覆盖的阻断命中因此**总有**可重放的证据”（ADR-184）；
    - 缓存命中的决定性验证，其“原日志与原重放包随之升为永久保留”（ADR-183）。被复用的原验证可以是机会式验证。
  - **清理规则**（`10` L442，`13` L359）：磁盘压力（可用 < 10 GB）时，第二步就是“删除非永久重放包与完整验证日志”。
    - 以阻断结束的验证与机会式验证，在升级之前都是非永久的。
    - `paused(sentinel_high)` 可以等人几天；opportunistic 的结果可以在很久之后才被正式验证复用。
  - **结果**：
    - 磁盘压力发生在“验证结束”与“升级”之间时，被升级的重放包或原日志已不存在。保留 ref 仍可写（pin 在影子中），但验证日志与 `manifest.json` 引用的内容已被删除。
    - `07` L497 的“总有”不成立；升级时发现包已缺失的分支没有定义：是失败、静默跳过，还是在决定性 Fact 上标注“证据不完整”。
- **为什么是次要**：seal 时的完整重哈希验证仍会永久保留，验收依据不受影响；触发需要磁盘压力。但两条规则按字面实现会互相抵消，被覆盖的哨兵正是最需要可重放证据的场合。
- **文档位置**：`07` L493–497、L894；`10` L442；`13` L359；`06` L928。
- **期望的回答形态**：
  - 在 `10` §10.3.2 的清理顺序中排除“可能被升级”的包：Goal 处于 `paused(sentinel_high)` 时当前 pin 上最近一次以阻断结束的验证，以及被任何未结束 Goal 的缓存条目引用的原重放包；
  - 或者在 `07` L497 写明包已缺失时的处理（保留 ref 照写，决定性 Fact 标“重放包已因磁盘压力清理”，界面如实显示），并把“总有”改为有条件的说法。

### D11 安全与自主度

**R57-D11-01｜次要**（无注解的用户扩展工具与 MCP 工具没有动作类：`Grant` 必须带类，`decide()` 按类求值，“本 Goal 内同类”授权落在哪个类、能否生效都没有定义）

- **问题**：
  - **规则**（`11` L216，ADR-184）：无注解的扩展工具“首次调用 `ask`，人可授予‘本 Goal 内同类’授权（`Grant{scope:"goal"}`，匹配器 = 工具名）”。L217 的 MCP 工具同样写“无注解 → 首次 ask”。
  - **缺失的定义**：
    - `Grant.class: ActionClass` 是必填（`02` L326）。
    - 27 个动作类（`11` §11.1，`16` L235–250）中没有一类对应“无注解的沙箱外工具”。
    - gate 的分类步骤（`05` L967–970）只列 `edit`/`write`、bash、`mcp__*`，没有用户扩展工具。
  - **`decide()` 下的两种读法都与 L216 不符**（`11` L223–232）：
    - **按 `opaque` 处理**（`classes` 为空）：`applyGrants` 不会对任何类求值，`opaque` 的钳制又在授权之后，结果至少是 `ask`。授予的“本 Goal 内同类”永远不生效，人每次都会被再问一次。
    - **映射到某个已有类**（例如 `exec.arbitrary`）：该工具的级别改由合同矩阵决定。在 `spike` 等较宽的预设下可能是 `notify`，与“首次调用 `ask`”相反。工具名匹配器还会与该类原有的命令前缀匹配器混在同一个命名空间里。
  - Goal 页按类撤销（`04` L354：“撤销本目标中 <类> 的 N 条授权”）同样需要知道这个类叫什么。
- **为什么是次要**：两种读法中，较严的一种只多问几次；较宽的一种只在合同把对应类设得较宽时放行，且 `11` L218 的路径扫描仍对这类工具生效，硬底线不受影响。但“首次 ask”是这类沙箱外工具的主要门禁，类与确定度不定义，实现会分歧。
- **文档位置**：`02` L324–327；`04` L354；`05` L967–970；`11` §11.1、L114–118、L216–218、L223–240；`16` §16.1.10；`14` G46(bb)(7)。
- **期望的回答形态**：
  - 在 `11` §11.3.4 写明无注解扩展工具与 MCP 工具的分类结果：所属类（新增一类并登记到 `16` §16.1.10，例如 `tool.external`，各预设默认 `ask`；或明确归入某个已有类）与确定度（`heuristic`，使授权可以生效）；
  - 匹配器写明是“工具名精确匹配”；
  - G46(bb)(7) 补“授予后第二次调用为 `notify`”与“合同把该类设为 `forbid` 时授权不生效”两组。
