## 1. 总评

**第 106 轮的 6 条条目都按所问关闭**（核对见 §3）：
- 6 条都在唯一定义处落地，引用处改为引用；第 106 轮 §5 的 12 条观察全部落地（观察 8 并入 R106-D7-01）。
- 其中三处修法本身带出新的分支：
  - **R106-D5-01**：探测只在 Host 中运行、`getAuth` 的拒绝计为失败，写法成立。但短时 Host 的 “每个打包分组至多一个” 在默认的专用模式下没有定义分组；短时 Host 自身启动失败、崩溃时的去向没有写；每次新起的短时 Host 都会重新执行 `auth.json` 的 `!` 命令（缓存按进程）——这正是第 106 轮所说 “反复弹出密码管理器的提示” 的后果，只是从 Supervisor 换到了短时 Host；登记只覆盖扩展新建的 provider，扩展以内置 id 覆盖时短时 Host 探测的是另一个端点与凭据（R107-D5-01）。
  - **R106-D5-02**：两处读取与 Run 准备时的读取成立。但 Pi 的 `buildRequestOptions` 每次请求还读另一个经同一解析的时限 `websocketConnectTimeoutMs`，它无效时正是 ADR-234 刚为 `httpIdleTimeoutMs` 关掉的 “重试 → F6 → 探测解除” 循环；`retry.provider.timeoutMs` 设置时优先于空闲超时，“两者中较小的起作用” 不准确（R107-D5-02）。
  - **R106-D13-01**：启动时卷未挂载不判为丢失，成立。但新行写明 “运行中的发现” 同样适用、“状态与原因不变”，它取代了卫星丢失一行中 “有活跃 Run 时先 abort” 的一支，卷在 Run 进行中消失时 Run 继续在不存在的目录上运行（R107-D13-01）；此外新行只守卫两行与 Run 准入，§6.1.6 的其他行、情形 C/F、命令范围与 `syncing` 不变式都没有对齐（R107-D13-02）。
- 另外，ADR-234 新写的实况行 `已中止（磁盘已满）· 释放空间后恢复` 无条件写 “恢复”，与 ADR-232 定下的 “自动恢复只在将随之自动继续时写” 不一致（R107-D7-01）。

**对本轮重点问题的回答**：

- **`turn_start` 中的移除是否先于该次请求生效：成立**（评审者逐行核对）。
  - 链上每一步都被等待：
    - `agent-loop.ts:118`（首个回合）、`:147`（`agent.continue()`，Pi 的重试与续跑都经过）、`:207`（其后各回合，在 `prepareNextTurn` 之后）都 `await emit({type:"turn_start"})`；
    - `agent.ts:609-610` 逐个等待监听者；
    - `agent-session.ts:513` 把 `_handleAgentEvent` 订阅为 Agent 的监听者，`:1143` 先等待 `_emitExtensionEvent`，`:1293-1299` 把 `turn_start` 交给扩展；
    - `runner.ts` 的 `emit` 逐个 `await handler`。
  - `transformContext`、`getApiKey` 与 `streamFunction` 都在其后（`agent-loop.ts:388-403`）。SDK 不设 `getApiKey`，凭据在 `streamSimple` → `prepareRequest` → `getAuth` 中每次请求读取（`model-runtime.ts:658-697`），读取不经凭据操作队列；`removeRuntimeApiKey` 的队列任务一开始就同步删除覆盖（`:634-640`），之后才做同步。所以处理器等到移除完成再返回时，下一次请求读不到已移除的覆盖。
  - 不经 `turn_start` 的请求：压缩与分支摘要（`prepareNextTurn` 中的压缩在 `:207` 之前，属于已登记的 “其后的压缩、摘要请求”），以及**缓存预热**（见观察 1）。
- **短时探测 Host 不经准入、不计入整机预留：接受登记，但上限要写清**。`provider_unavailable` 的 Goal 占用槽位（`06` L101），所以只要分组键是扩展集合，短时 Host 的数目以组数（至多 2：`noExtensions` 真与假）为界；在默认的专用模式下若按 Goal 分组，则为每个受影响的 Goal 各起一个，与 Host 退出的时机同步，见 R107-D5-01 (a)。
- **卷未挂载的判别：启动卷上残留的空目录已写明；其余布局见 R107-D13-02 (f)**。
  - `/Volumes/<卷名>` “只是启动卷上的普通目录” 已写明。
  - 另一块同名卷挂在同一位置时，判为 “卷已挂载而目录不在”，回到丢失两行。
  - 经符号链接或非 `/Volumes` 挂载点到达的 `<wtRoot>` 也会落回丢失两行：`<wtRoot>` 只在遍历与沙箱规则中取 realpath（`10` L222、L228），存储的路径是否为 realpath 没有写。
  - 后果都是回到第 106 轮之前的行为，不删除目录。
- **待补失败出口列表与崩溃、退出：成立**。
  - 列表只在进程内。Supervisor 崩溃与应用退出都使它丢失，数据库中留下的 `syncing`、`satellite_rebuilding=1`、`draining_for` 各有 §6.1.6 的一行续做；两条路径的结果不同已登记在回应的偏离中。
  - 列表在解除时先执行；解除要求所有卷可求出且 ≥ 2 GB，所以列表不会在卷未挂载时执行。
  - 写回的 ① 在只读期间未完成的一支见观察 8。

### D5 Agent 架构与 Pi 集成

**R107-D5-01｜次要**（短时探测 Host：专用模式下的分组与 “本轮” 没有定义；自身失败的去向没有写；`auth.json` 的 `!` 命令随每次新起而重新执行；登记只覆盖扩展新建的 provider）

- **问题**：
  - **(a) 分组与上限**：`06` L101 写 “该 Goal 所在打包分组（§6.1.1）中已存活而没有进行中 Run 的 Host……每个打包分组至多一个”。但打包分组的唯一定义（`06` L42）是打包模式下的分组规则；默认的专用模式下每个 Goal 一个 Host，“分组” 可以读作 “按扩展集合的键”（至多 2 个），也可以读作 “每个 Goal 自成一组”。后一种读法下，一次模型服务故障使 N 个 Goal 同时进入 `provider_unavailable`，5 分钟后各自的 Host 退出，按各自的退避计时器每轮各起一个短时 Host——N 个不经准入、不计入整机预留的 Host，且计时器大致同步。“本轮探测” 是按组共享一个探测时刻，还是每个 Goal 的计时器各算一轮，也没有写。
  - **(b) 短时 Host 自身失败**：“按正常的 Host 启动路径” 包含会按 F4b 写 `prepare_failed` 的步骤（静态清单计算 60 s、握手），Host 崩溃按 F4（“一次自动重启并恢复；10 分钟内再次崩溃则转人工 `stalled{crashed}`”），挂死按心跳。短时 Host 启动失败、崩溃或挂死时，是只算这一次探测失败，还是对待探测的 Goal 套用 F4b、F4（改写暂停原因或生成 `stalled` 条目），没有写。F8 只读期间是否探测（探测成功要写数据库）同样没有写。
  - **(c) `!` 命令的重复执行**：`auth.json` 中 `!` 命令的结果按进程缓存（`resolve-config-value.ts:9-10, 208-216`）。同组没有空闲 Host 时（暂停超过 5 分钟后即如此），每一轮探测都新起一个进程、重新执行该命令。第 106 轮 R106-D5-01 列出的后果之一正是 “`!` 命令按退避反复执行，可能反复弹出密码管理器的提示”。ADR-234 把执行者从 Supervisor 换成短时 Host，频率不变（60 s 起退避、上限 10 min），没有登记。
  - **(d) 扩展覆盖内置 id 时的误报**：短时 Host 的运行时由 `ModelRuntime.create` 建出，只有内置 provider 与 `models.json`（`model-runtime.ts:217-268`），扩展的注册只经 services 写入（`agent-session-services.ts:158-181`）。所以扩展以内置 provider 的 id 覆盖时（只改 `baseUrl` 或 `headers` 的也算，`:891-949`），短时 Host 中 `getRegisteredProviderIds()` 为空、照常注入导入的密钥，`getAuth` 按内置定义成功。探测因此对 Run 的 Host 刻意不用的那份凭据与端点通过，Goal 自动继续、再次失败、再次暂停。`06` L101 的登记只写了 “只由扩展新建的 provider……探测失败”。
- **为什么是次要**：
  - 机密不进入 Agent 可影响的进程，安全不变式不受影响；
  - 失败方向是多起进程、多一次提示或多一次 “继续—失败” 循环，不计费、不丢数据。
  - 但 (a) 使资源上限在默认模式下取决于读法，(b) 使暂停原因与收件箱在不同实现中不同，(c)(d) 是已登记取舍的遗漏部分。
- **后果的类别**：
  - 默认模式下模型服务故障时，每轮探测同时起 N 个未预留的 Host；
  - 用密码管理器提供密钥的用户在 Goal 停在 `provider_unavailable` 期间约每 10 分钟被提示一次；
  - 用扩展把内置 provider 指向企业网关的用户，Goal 在网关故障时反复自动继续又失败。
- **文档位置**：`06` L101（唯一定义）、L42、L170、L1196（F4）、L1197（F4b）、L1201（F8）；`11` L517；`05` L486；ADR-234 R106-D5-01。
- **期望的回答形态**：在 `06` L101 的唯一定义中补一句：
  - 分组键在两种模式下都是扩展集合的键（`noExtensions` 与已确认清单的哈希），所以至多两个短时 Host；同组的待探测 Goal 共用一个探测时刻；
  - 短时 Host 的启动失败、崩溃或超时只算本次探测失败，不套用 F4b、F4，不改原因、不生成条目；F8 只读期间不探测；
  - 登记 `!` 命令在每个短时 Host 中重新执行一次；
  - 登记扩展以内置 id 覆盖时短时 Host 中的探测按内置定义求值（或这类 Goal 只在同组有已加载该扩展的空闲 Host 时探测）。

**R107-D5-02｜次要**（Pi 的 SDK 每次请求还读另一个经同一解析的时限设置；它无效时是 ADR-234 刚关掉的同一循环；`retry.provider.timeoutMs` 优先于空闲超时）

- **问题**：
  - `05` L474 为 `httpIdleTimeoutMs` 加了 “适配器在每个 Run 的步骤 ② 之后读一次，抛出时按 F4b”，理由是不读时 Pi 每次请求在读取时抛出、错误文本含 `timeout` 而被重试，耗尽后落入 F6 并被探测反复解除。
  - 但同一个 `buildRequestOptions`（`sdk.ts:340-351`）每次请求还调用 `settingsManager.getWebSocketConnectTimeoutMs()`，它经同一个 `parseTimeoutSetting`（`settings-manager.ts:147-156, 934-936`），无效时抛出 `Invalid websocketConnectTimeoutMs setting: …`，同样含 `Timeout`，命中 Pi 的可重试模式（`retry.ts:73`，不区分大小写）。Host 启动与步骤 ② 都不读它，所以它无效时正是那个循环：重试、F6、探测（不读该设置）解除、再失败。
  - 同一行中请求时限的取法是 `options.timeoutMs ?? providerRetrySettings.timeoutMs ?? effectiveTimeoutMs`（`sdk.ts:345-350`）：你设置了 `retry.provider.timeoutMs` 时它优先于空闲超时。`05` L474 的 “Pi 的 SDK 会话另在每次模型请求时读取同一设置作为请求时限……两者中较小的起作用” 在这种设置下不成立。
- **为什么是次要**：失败可见，不丢数据，不涉及机密。但这是与 ADR-234 刚关闭的分支同一类的缺口，修法相同（步骤 ② 的读取覆盖同一解析的全部 getter），而唯一定义对生效时限的描述在一种合法设置下不准确。
- **后果的类别**：
  - 设置文件中该项写坏之后，Goal 在 `provider_unavailable` 与运行之间无限循环，卡片写 “模型服务不可用”，而原因是本机设置；
  - 设置了 `retry.provider.timeoutMs` 的用户看到的请求时限与文中写法不同。
- **文档位置**：`05` L474、L1450（D63）、L1506（C43）；`06` L1197（F4b）；ADR-234 R106-D5-02。
- **期望的回答形态**：在 `05` L474 改一句：
  - 步骤 ② 之后的读取覆盖 `buildRequestOptions` 每次请求读取、会抛出的全部设置（v1.2.0 为 `httpIdleTimeoutMs`、`websocketConnectTimeoutMs`），D63 的复核范围补 “比对该函数读取的设置”；
  - 写明 `retry.provider.timeoutMs` 设置时请求时限取它；
  - C43 补 `websocketConnectTimeoutMs` 无效一组。

### D7 诚实与验证

**R107-D7-01｜次要**（只读期间的实况行 `已中止（磁盘已满）· 释放空间后恢复` 无条件写 “恢复”，与 ADR-232 的卡片条件不一致）

- **问题**：
  - `12` L395（ADR-234）为 “drain 写不进或只读启动时中止的 Goal” 写实况行 `已中止（磁盘已满）· 释放空间后恢复`，没有条件。
  - 同一事实的卡片文字有条件（`12` L434，ADR-232）：`自动恢复` 一段 “只在该 Goal 将随之自动继续时写——`resumeOnLaunch` 打开，且按第 5 项解除之后没有剩余原因”。
  - 两种情形下 Goal 在解除之后不会继续：
    - F8 向人的暂停或预算上限的 drain 并入 `app_quit`、而 drain 写不进（`06` L1201）：解除时列表执行该 drain 的目标，结果为 `paused(human)` 或 `paused(budget_hard_cap)`；
    - `resumeOnLaunch` 关闭：解除时不移除 `app_quit`。
- **为什么是次要**：只在只读期间显示，解除之后由真实状态的卡片取代；不丢数据。但它与 ADR-232 刚为同一类文字定下的规则相反，读者会以为不用做任何事。
- **后果的类别**：人以为释放空间后一切自动恢复，实际上暂停中的 Goal 停在原处，直到人再看卡片。
- **文档位置**：`12` L395、L434；`06` L1201；`04` L1518。
- **期望的回答形态**：在 `12` L395 加半句：`· 释放空间后恢复` 只在写不进的 drain 目标只有 `app_quit`（或只读启动时中止）且 `resumeOnLaunch` 打开时写，否则只写 `已中止（磁盘已满）`。

### D13 隔离、git 与并发

**R107-D13-01｜次要**（卷在 Run 进行中消失：新行写明运行中的发现同样适用、“状态与原因不变”，取代了卫星丢失一行对活跃 Run 的 abort，活跃 Run 与进行中的写回、验证没有去向）

- **问题**：
  - `06` L139：新行 “先于下方卫星丢失与人工编辑检出两行判定（启动检查与运行中的发现——文件系统事件、操作前检查——相同）：该 Project 的 Goal 不触发这两行……状态与原因不变”；`12` L416 只给不在 `ready` 的目标追加 `· 卷未挂载`。
  - 被取代的卫星丢失一行（`06` L140）与情形 E（`10` L1265）对 `running` 的处理是 “有活跃 Run 时先 abort（无法 drain）→ `paused(satellite_missing)`”。新行之后，强制推出或拔线使卷在 Run 中消失时：
    - Agent 的 Run 继续，bash 与文件工具都失败，`turn_end` 前的 `existsSync`（`10` L1254）发现卫星不在而不触发任何行，settle 序列的检查点与 pin 都在不存在的树上求；
    - 进行中的写回按 “写回在本进程中失败” 走 ①（以 T1 在不存在的卷上重新物化，必然失败），条目写 “你的改动未能保留在目录中，此后不可恢复”，随后 “交还随后按 §6.1.6 检出丢失一行处理”——而目录完好地在未挂载的卷上，这正是 R106-D13-01 要避免的告知；
    - 进行中的验证在 `<wtRoot>/_verify/`（`10` L249）上失败，按哪种结论记没有写。
- **为什么是次要**：Tower 不删除任何目录，文件仍在卷上，卷重新出现之后可以取回；不涉及机密与沙箱。但这是 ADR-234 的新行带来的回退（此前活跃 Run 会被 abort），而运行中卷消失比启动时卷不在更常见；实现会在 “照字面让 Run 继续”“照卫星丢失 abort” 与 “drain” 之间分叉。
- **后果的类别**：
  - Run 在不存在的目录上空转，直到异常检测或预算上限；settle 写出无意义的结果；
  - 写回中卷消失时，人被告知改动不可恢复，交还路径被清除；
  - 验证在卷消失时可能留下 `verify_env_error` 的条目。
- **文档位置**：`06` L139、L140、L145、L922（写回失败出口 ①）、L1198（F5）；`10` L1254、L1265；`12` L416；`14` L120（G35e (q)）。
- **期望的回答形态**：在 `06` L139 新行补一句：运行中发现卷未挂载时，活跃 Run 照卫星丢失一行 abort（无法 drain），以已有原因（如 `engine_crash`，或复用 `app_quit`）进入 `paused`、继续目标按 `03` §3.2.1，卡片注明 `卷未挂载`，卷重新出现后经检查 i 准入；进行中的写回按崩溃处理（不执行 ①③，`syncing` 保留到卷重新出现，由 §6.1.6 续写）；进行中的验证照应用退出取消、卷重新出现后以同一 pin 重跑。G35e (q) 补 “Run 中卸载测试卷” 一组。

**R107-D13-02｜次要**（卷未挂载一行只守卫两行与 Run 准入；§6.1.6 的其他行、隐私清除续做、情形 C/F、“触及该卷的命令”、`syncing` 不变式与判别键都没有对齐）

- **问题**：`06` L139 只写 “不触发这两行”“要开 Run 的转移经检查 i 等待”“触及该卷的命令返回 `E_STATE`”。启动时其余照常执行的路径中：
  - **(a) 卫星重建中途崩溃**（`06` L141，`satellite_rebuilding=1`）不受守卫，在不存在的卷上 “从头续做”，失败后 “升级为暂停原因并生成 Needs-You”；之后 L140 写明已带 `satellite_missing` 而标记为 0 的 Goal “重启不再自动重建”，卷重新出现后也只能由人重试。
  - **(b) `verifying` 重跑**（`06` L122）与继续目标为 `settle`、`verify` 的自动解除在卷上的槽位或卫星上执行，以 `verify_env_error` 或在不存在的树上求 pin 告终。
  - **(c) 隐私清除续做**（`06` L143）“只以事件中的 `id` 与 `roots` 定位，幂等续做文件删除……完成后追加 `filesDone: true`”。`roots` 中的 `<wtRoot>` 未挂载时，删除不存在的路径照样 “成功”，记录写完成；卷重新出现后该 Goal 的卫星、`_gitdirs`、`_stores` 仍在，与 `09` §9.12.4 “删除 Tower 自有的、可能含该 Goal 内容的全部副本” 不符。

  - **(e) 命令范围与 `syncing` 不变式**：“触及该卷的命令” 没有列出（`goal.abandon`、`goal.accept`（写入可能在同一卷上的用户仓库）、`goal.resume` 带 `verify` 继续目标、`goal.delete_kept`、`privacy.purge`、`inspect.close` 等在不同实现中归类不同）。重启时卷未挂载而 `syncing` 仍在的 Goal，人工编辑检出一行（含续写）被跳过，`syncing` 留在数据库中而命令照常受理；`06` L922 的不变式（“`syncing` 只存在于……三种时候”“命令与自动转移从不在 ‘写回已不在进行而 `syncing` 仍在’ 的状态上执行”）没有这一情形，“写回进行中” 的 `E_BUSY` 也不覆盖它。
  - **(f) 判别键**：判别只看路径前缀与卷名（“位于 `/Volumes/<卷名>/` 之下而 `/Volumes/<卷名>` 当前不是已挂载的卷”）。另一块同名的卷挂在同一位置时（两块同型号的外接盘默认同名并不少见），判为 “卷已挂载而目录不在”，回到丢失两行：卫星在错误的盘上重建，`human_checkout` 被清除并告知 “无法恢复”。经符号链接或非 `/Volumes` 挂载点到达的 `<wtRoot>`，存储的路径是否为 realpath 没有写（`10` L222、L228 只在遍历与沙箱规则中取 realpath），同样落回丢失两行。
- **为什么是次要**：
  - 每一种都不删除目录，文件仍在卷上，卷重新出现后可以取回；不涉及沙箱或 Agent 可影响的进程。
  - (c) 是隐私承诺的一处例外，但要 “清除中途崩溃” 与 “重启时卷不在” 两件事同时发生，命令路径可以由 “触及该卷的命令” 挡住；
  - (d) 要求同一仓库另有一份可被找到的克隆。
  - 但新行宣称的效果（“目录完好地在未挂载的卷上，不判为丢失、不重建、不清除 `human_checkout`”）只在两行上成立，其余路径照字面实现会重现 R106-D13-01 的后果，实现会分叉。
- **后果的类别**：
  - 卷不在时重启，正在重建或清除中的 Goal 落入只能人工处理的 `satellite_missing`，或清除记为完成而内容仍在；
  - 有第二份克隆的用户在卷不在时启动，Project 被悄悄改附到另一份克隆，人工编辑检出被告知无法恢复；
  - 插错一块同名的盘，卫星在其上重建，人工编辑检出被清除。
- **文档位置**：`06` L122、L139、L140、L141、L143、L145、L922、L951（`privacy.purge`）；`09` §9.12.4（L555）；`10` L222、L228、L1263、L1266；`16` L290。
- **期望的回答形态**：在 `06` L139 的唯一定义中把守卫写成一条规则而不是两行：
  - 卷未挂载时，该 Project 中读写 `<wtRoot>` 或位于该卷上的主检出的**全部**自动动作——§6.1.6 各行（含卫星重建中途崩溃、`verifying` 重跑、隐私清除续做）、继续目标、`10` §10.16.2 情形 C/D/F 的判定——推迟到卷重新出现；
  - 命令按 “效果读写该 `<wtRoot>` 之下路径” 一条判定返回 `E_STATE`；
  - `06` L922 的不变式补 “卷未挂载期间”，这期间该 Goal 按写回进行中处理；
  - 绑定 Project 或建立 `<wtRoot>` 时记下卷的标识（如卷 UUID），判别以它为准，存储 `<wtRoot>` 的 realpath；或把 (f) 的布局登记为已知限制。

### 不扣分的观察

1. **缓存预热**：Pi v1.2.0 默认 `cacheWarming: "streaming"`（`settings-defaults.ts:60`，经受保护设置读取用户设置），Run 进行中工具执行较久时按 TTL 定时以 `maxTokens: 1` 重放上一次请求（`cache-warmer.ts:296, 330-352`）。
   - 这些请求不经 `turn_start`，`11` L517 与 `15` L4935 的 “不经过 `turn_start` 的请求” 只列了压缩与摘要；它们与已登记的窗口同一类（扩展在密钥的信任边界之内），不扩大机密的去向。
   - 它们的用量以 `usage` 条目写入会话、只发 `entry_appended`，不出现在 `msg.end` 中：`06` L353 的实时累加看不到，只在 `agent.settled` 的对账差值中出现，也不在 “自身开销” 的分类中。
   - 宜在 `11` L517 的窗口与 `06` §6.2.5 各补半句（或在受保护设置中固定该项的取值并登记）。
2. **`turn_start` 处理器出错**：Pi 捕获扩展处理器的异常、报告后让请求照常发出（`runner.ts:1096-1125`）。`bridge` 失败或 `removeRuntimeApiKey` 被拒绝时（覆盖此时已删除，`model-runtime.ts:637-638`）是抛出（计入 F13 的连续三次）还是记录后返回，没有写。宜写一句。
3. **打包模式中的检查与注入竞争**：另一个 Goal 的 Run 开始时的检查可能在等待中决定注入，而 `turn_start` 的移除先完成，之后的 `setRuntimeApiKey` 使 “列出过一次即不再注入” 不成立，到该 Host 退出为止。后果在密钥的信任边界之内。宜写明注入之前再查一次 “已列出” 集合（或按 Host 串行化检查与注入）。
4. **C43、D63 所引 MCP 时限**：Tower 经过的是 Pi 的内置 MCP 扩展，它以 `mcp.json` 的 `timeout`（默认 60 s）作为 `requestTimeoutMs`（`extensions/mcp/runtime.ts:48, 210-211, 363`），覆盖 `client.ts:38` 的 30 s。C43 的 10 s 停顿仍短于两者，测试的分辨力不变；宜改引。
5. **G46 (d) 的观察时机**：探测只做连接与鉴权检查，503 的测试代理在约 60 s 时让探测通过，Goal 自动继续、再失败、再暂停，可观察的窗口是第一次探测之前（每轮重复），不是 “Host 退出之前”。宜写为 “第一次探测之前”，或让测试代理拒绝连接以得到稳定的窗口。
6. **切换模型的位置**：`为受影响目标切换模型`（`04` L1506）对应 `engine.set_prefs{goalId, model}`（`06` L954）与 `goal.resume`，命令已有；对话框中每个目标一行、写该目标的标注，没有写。`04` L1461 的 “之后模型选择器按服务该目标的 Host 的检查写明” 没有引 `11` L517 的 “可见范围”。宜补一句并改为引用。
7. **F8 中接管在 `run.ended` 已提交之后**：接管物化处于 ADR-200 的窗口时，`run.ended` 已写入、不带 `disk_full`；F8 把 drain 的目标并入 `app_quit`，解除规则要求最后一个 Run 的 `outcome_reason` 为 `disk_full`，所以 `app_quit` 不随解除移除，Goal 停在 `paused(human)` 且另有 `app_quit`，人要按两次 “继续” 或重启。宜写明 `run.ended` 已提交之后不并入 `app_quit`，结果为 `paused(reasons ∪ {human})`。
8. **写回 ① 在只读期间未完成**：F8 的列表在解除时 “按解除时的状态求”，例子只写了 ② 未完成；若 ①（来源目录已不在时以 T1 重新物化）本身因 `ENOSPC` 未完成，照 ③ 执行会清除 `targetTree` 并告知 “此后不可恢复”，而此时空间已足、T1 仍在影子中。要三重巧合。宜写明解除时 ① 未完成的先重做 ①。
