>   1. 一个目录含名为 `HEAD` 的**子目录**以及 `objects/`、`refs/` 时，git 判定它不是仓库；`HEAD` 是普通文件时判定为仓库。也就是说，git 只认非目录类型的 `HEAD`。
>   2. 目录中已有 `HEAD` 文件、`objects/`、`refs/`，但 `HEAD` 的内容无效时，git 判定不是仓库；**只改 `HEAD` 的内容、条目的存在性不变**，判定就变为“是仓库”。

## 1. 总评

第 9 轮的方向基本落地：

- ADR-106 把权威的嵌套仓库检查移到物化 pin 上，增加了大小写不敏感的标记条目规则与 `symlink_escape`；
- ADR-107 去掉了 `post_settle_activity`、`policy_wall` 的阻断，也去掉了无效的“返工”；
- ADR-108 统一了 `pendingHandBack` 的触发，trailer 改为如实写入；
- 削减顺序按约束线重排。

本轮没有阻断级问题，但有两处重要的新问题：

- **ADR-106 权威检查的位置与 pin 的生成顺序不自洽**：
  - pin 的排除集合来自早期预警；
  - `verify()` 有多条提前返回的路径，都不经过权威检查；
  - “验收与 seal 在同一物化树上”无法成立，因为槽位在验证后就被拆除；
  - 覆盖之后，排除的目录是否进入 seal 也没有定义。
- **ADR-107 把 `sandbox_violation` 升级为阻断**（第 9 轮期望的是移出阻断）：
  - 没有论证，也与 `07` 自己的阻断原则（“问题不在 diff 里就不阻断”）相反；
  - 它是独立的 Fact kind，而 `sentinel.override` 只适用于 sentinel，阻断后没有合法的覆盖出口。

此外，跨文档残留约 12 处，主要集中在 `03`、`07` 与 ADR-103/104。

### D3 论证与证据

**R10-D3-01｜次要**（R9-D3-01 的残留）

- **问题**：`07` §7.3.2 L195 是验证文档中对权威检查的唯一描述，其中有两处陈述与证据不符：
  - **(a)** “git 自身判定‘不是仓库’的目录（包括 `commondir` 指向不可读位置的情形），对用户的 git 同样不是仓库，不构成风险”。第 9 轮的本机核对已经说明，读被拒绝时 git 的输出与“不是仓库”无法区分。ADR-106 L732 与 `10` L76 正是因此才加了标记条目规则。
  - **(b)** “同一文件系统、同样的大小写语义”被写成事实。但验证槽位位于 `<wtRoot>`，而 `10` §10.4.3 允许 `<wtRoot>` 回退到 `~/.tower/worktrees`，它不一定与用户主检出同卷。有了大小写不敏感的标记规则，这个前提不再影响结论，但它仍是一条无条件的事实陈述。
- **为什么重要**：工程师会按 `07` 实现 `authoritativeNestedRepoCheck`；按现有写法，会漏掉标记规则。
- **文档位置**：`07` §7.3.2 L195；`10` §10.1.2 L76；`15` ADR-106 L732；`10` §10.4.3。
- **期望的回答形态**：
  - `07` 第 1 条改为引用 `10` §10.1.2 第 (1) 层，补上标记规则，删去“不构成风险”的说法；
  - “同一文件系统”改为“同卷时成立；不同卷时由大小写不敏感的标记规则覆盖”。

### D4 领域模型与生命周期

**R10-D4-01｜次要**

- **问题**：
  - **(a) `03` 仍保留旧语义**。`06` L779 声明 `03` §3.2.1 的出口列是唯一来源，但：
    - `03` L85 写“保留原因解除……**或人 `resume` 时**，按 `pendingHandBack.mode` 进入……”，与 ADR-108、`06` L779、`10` L646–648 的“`resume` 只解除当前原因，全部解除才执行”不同；
    - `03` L57 与 L74 中 `sentinel_high` 的出口是“覆盖后评审 / 返工 / 放弃”与 `request_changes`，没有排除 run 类阻断命中（ADR-107 已规定不提供返工）。
  - **(b) seal 的“人的说明”取哪一次**：
    - 第 2 段写入“交还对话框中人写的意图”（`10` L384、ADR-105 L720）。
    - 一个 Goal 可以多次接管与交还；“直接重新验证”模式下也可以写说明；`10` L661 还有一个独立的“提交说明”输入。
    - 设计没有写明：seal 取最后一次、全部，还是只取“提交说明”输入；多段时怎样排列；这段文字与 `HumanDecision{hand_back}.note`（同时用作给 Agent 的意图）是不是同一字段。
- **为什么重要**：`transitions.ts` 与 seal 生成器都会被直接实现。(a) 让唯一来源与实现层的定义相左；(b) 决定用户仓库中会永久留下什么文本。
- **文档位置**：`03` §3.2.1 L57、L74、L85；`06` L779、L810；`10` §10.6 L384、§10.8.4 L661；`15` ADR-104 L714、ADR-105 L720、ADR-108 L744。
- **期望的回答形态**：
  - `03` 改为 ADR-108 的单一触发条件，`sentinel_high` 行按 ADR-107 区分 pin 类与 run 类的出口；ADR-104 加 Amended-by 注，ADR-108 的措辞改为无歧义的说法。
  - 定义“人的说明”的来源字段与多次交还时的合并规则，并在 G30b 中增加两次交还的用例。

### D6 系统架构与可靠性

**R10-D6-01｜次要**

- **问题**：
  - 第 9 轮回应把 `running` 期间的文件系统监视定为 `external_change` 的事件来源（`10` L214、L403；`06` §6.2.3）。`external_change` 的定义是“运行中出现非 Agent、非 Tower 的工作区改动”（`02` L140、`03` L80）。
  - 但 FSEvents/inotify 都不提供写入者的进程信息。Agent 在 bash 中启动的后台进程（开发服务器、`--watch` 模式的编译器与测试运行器）在工具调用之外也会持续写文件。
  - 设计没有给出归因判据：在什么条件下，一个事件被判为“非 Agent”。
  - `external_change` 会让 `running` 中的 Goal 暂停，并且是交还时保留的原因；误判的代价是无谓的暂停与 Needs-You。
- **为什么重要**：这是一个已登记的暂停原因与一条已上线的事件来源，两者之间缺少可实现的判定。
- **文档位置**：`02` L140；`03` L80；`10` §10.3.1 L214、§10.6 L403；`06` §6.2.3 L244；`04` L1198。
- **期望的回答形态**：
  - 写明归因规则。例如：只要有工具调用正在执行，或者 Tower 记录的 Agent 进程组（含后台进程）中还有进程存活，就归因为 Agent；否则才判为 `external_change`。登记已知的漏判与误判。
  - SP6b 或 G 系列增加两个用例：Agent 后台 watcher 持续写文件（不应暂停）；Run 空闲时外部编辑器保存文件（应暂停）。

### D7 诚实与验证

**R10-D7-01｜重要**

- **问题**：ADR-107 把 `sandbox_violation` 列为两项“阻止 Verified 的 run 类命中”之一（`07` L1277、L1287；`16` L129、L151；ADR-107 L739）。第 9 轮之前它不阻断，路由为 `stalled`；R9-D7-01 期望的是把它移出阻断。
  - **(a) 与 `07` 自己的阻断原则相反**：
    - `07` §7.10.1 开头写明，阻断集合不由严重度决定，问题不在 diff 里就不阻断（例如 bash 输出中的密钥，severity 3 也不阻断）。
    - `sandbox_violation` 记录的是**被沙箱拒绝**的尝试：越界写入没有发生，pin 的内容不受影响。
    - ADR-107 只用“安全相关”一词作为理由，没有论证一次被拦下的尝试为什么会使 pin 不可信。
  - **(b) 误报规模没有估计，也没有测量**：
    - 按 `11` L332，Agent 不能写用户的全局缓存与配置目录，网络经代理限制。常见工具会在 Agent 没有恶意的情况下触发拒绝，例如框架遥测写配置文件或连接遥测端点、工具写 `~/Library/Caches` 或 `~/.cache`、包管理器的更新检查。
    - `07` L1126 的 S7 规则（10 分钟内 ≥ 3 次才提示）本身就假设拒绝是常见现象。
    - 这类命中现在按 Goal 作用域保持 open，交还与新 pin 都不清除，只能“覆盖（写明原因）”或“放弃”。
    - 精度目标写的是 0.95，但没有登记任何语料或测量计划；G32b 只测了“被阻断”这一面。
  - **(c) 没有合法的覆盖出口**：
    - `sandbox_violation` 是独立的 Fact kind（`16` L111、L151；`11` L348），既不是 sentinel，也不是 anomaly；
    - 而 `sentinel.override` 明确写着“只适用于 sentinel 类 Fact，不适用于 anomaly”（`06` L814）；
    - 因此按现有定义，人无法覆盖它，Goal 只剩“放弃”。
    - 覆盖的粒度是单个 `factId`，一个 Goal 的 N 次拒绝就要覆盖 N 次。
- **为什么重要**：
  - (a)(b) 直接侵蚀 §7.11 的精度目标与“覆盖即留痕”的信号价值，也会让 Needs-You 变成例行公事（D8）；
  - (c) 是状态机上的死路：Verified 被阻断，又没有可执行的出口。
- **文档位置**：`15` ADR-107 L739；`07` §7.10.1 L1228、L1277、L1287、§7.7.1 L1126；`16` L111、L129、L151；`06` L814；`11` §11.6.2 L332、L348；`14` G7、G32b。
- **期望的回答形态**：二选一并给出论证。
  - **方案一**：`sandbox_violation` 恢复为提示性，进入“运行异常”区块。
  - **方案二**：只把**目标属于受保护类别**的拒绝定为阻断，例如 Tower 管理的根、用户主检出、其他 Goal 的卫星、验证器存储、`.git` 创建、密钥路径。其余拒绝为提示性。同时：
    - 按 (类别, 目标根) 在 Goal 内聚合为一条命中；
    - 定义它的覆盖命令（扩大 `sentinel.override` 的适用范围，或把阻断类拒绝包装为 `sentinel{detector:"sandbox_violation"}`）；
    - 登记误报测量：在 SP6c 或 E7 的参考项目上统计默认环境下良性工具的拒绝分布，并给出阈值；
    - G32b 增加对照：良性工具写全局缓存被拒，Goal 仍进入 `in_review`。

**R10-D7-02｜次要**

- **问题**：标记条目规则写作“目录中出现（大小写不敏感）名为 `HEAD`、`commondir` 或 `gitdir` 的**条目**”（`10` L76、ADR-106 L732、`05` L572、`13` L312），没有限定条目类型。
  - 名为 `head` 的**子目录**在 Web 项目中并不罕见，例如 `layouts/partials/head/`、`components/head/`。按现有写法：
    - 新增这样一个子目录，会使父目录的“`HEAD` 条目存在性”改变，构成“结构变化”；
    - 父目录随即按仓库形态处置：severity 3 阻断、整个父目录从 pin 与 seal 中排除。
  - 本轮核对显示，git 只认非目录类型的 `HEAD`；`commondir`、`gitdir` 也只能是文件。因此把规则限定为“非目录条目”不会漏判。
  - G29 只统计“被 git 确认为仓库”的误报，标记规则绕过了 git 确认，它的误报没有测量；`nested_repo` 的精度目标是 0.99（`07` L1274）。
- **为什么重要**：一次误报会把整个父目录从 pin 中排除，而且阻止 Verified。
- **文档位置**：`10` §10.1.2 L76；`15` ADR-106 L732；`05` L572；`13` L312；`07` L1274；`14` G29。
- **期望的回答形态**：
  - 标记条目限定为普通文件或符号链接；“结构变化”的定义同样只看非目录条目。
  - G29 增加标记规则的误报统计，并加一个对照用例：新增 `layouts/partials/head/` 目录，不产生 `nested_repo`。

### D9 视觉设计与美观

**R10-D9-01｜次要**

- **问题**：
  - `04` L463 的“未纳入评审的路径”中，`symlink_escape` 以 `◇` 标注；
  - 而 `12` L323 规定 `◇` 表示“要注意但不需要你决定”；
  - `symlink_escape` 却是 severity 2、路由到 Needs-You 的 sentinel（`07` L1275），在集成前评审中是确认项，指向 Tower 管理的根时还阻断集成（`10` L87）。同一列表中的 `nested_repo` 用 `■`。
- **为什么重要**：字形语义是 `12` 中“3 秒扫读”的基础；需要人决定的事项不能使用“不需要你决定”的字形。
- **文档位置**：`04` §4.6.2 L463；`12` §12.6.2 L323；`07` L1275；`10` L87。
- **期望的回答形态**：`symlink_escape` 改用 sentinel 字形（与其他 severity 2 的 Needs-You 哨兵一致），或在 `12` 中写明例外及理由。

### D10 性能

**R10-D10-01｜次要**

- **问题**：
  - **(a)** `13` L312 把验收与 seal 时的权威检查预算写为“在验证槽位的物化树上 ≤ 100 ms”。但槽位在 `verify()` 结束时就已拆除并释放（`07` L351），而每个 Project 只有 2 个槽位（`07` L399）。验收可能在验证后几天才发生，那时需要重新取得槽位并物化 pin。这一步的耗时（含 `checkout`、`clean`、`fsck`）、排队位置（`07` §7.4.10 的优先级）、以及它对“验收面板以进度显示”的影响，都没有预算（与 R10-D13-01(c) 一起回答）。
  - **(b)** 人工编辑检出的创建目标是“< 2 s”（`13` L316），前提是依赖能从 depcache 物化。从 `running` 接管时，如果 Agent 改过 lockfile 而这个 depsKey 还没验证过，depcache 中没有对应条目，就需要运行安装器（可能联网、耗时以分钟计）。这一情形的处理与预算没有写（与 R10-D13-02 一起回答）。
- **为什么重要**：两者都发生在人等待的路径上。
- **文档位置**：`13` §13.11.1 L312、L316；`07` §7.4.1 L351、§7.4.2 L399、§7.4.10；`10` §10.8.4 L615。
- **期望的回答形态**：
  - 给出验收与 seal 时检查的执行方式与预算（如果按 R10-D13-01 改为在树对象上检查，这一项随之消失）。
  - 写明 depcache 未命中时，人工编辑检出是先打开、依赖在后台补齐，还是等待；给出预算与界面提示。

### D11 安全与自主度

**R10-D11-01｜次要**（R9-D11-01、R9-D13-02 的残留）

- **问题**：
  - **(a) 只改内容不触发检查**：
    - 权威检查的范围是“新增或结构变化的目录”，结构变化定义为五类条目的**存在性**改变（`10` L76、ADR-106 L733）。
    - 本轮核对显示，`HEAD`、`objects/`、`refs/` 都已存在而 `HEAD` 内容无效的目录不是仓库；只改 `HEAD` 的内容，就会变成仓库。
    - 如果 base 中有这样一个目录（例如 git 工具类项目中“损坏仓库”的测试夹具），它既不是新增，也没有结构变化，又因为在 base 中不是仓库形态而不属于“base 夹具”行。Agent 改写它的 `HEAD` 与 `config` 之后，它会作为普通内容进入 seal，没有哨兵，也没有确认项。
  - **(b) base 夹具的确认项范围不清楚**：`10` L85 只写“修改了其中 `config`、`hooks/` **等**文件时，集成前评审单列为确认项”。改写 `commondir`、`gitdir` 的内容（把它们指向仓库外）、改动 `objects/info/alternates`，都会改变用户 git 读取的位置，但不在明确列举之中。
  - **(c) 指向 Agent 临时目录的符号链接不阻断**：
    - `symlink_escape` 只在目标是“Tower 管理的根（`~/.tower`、`<wtRoot>`、Agent 存储）”时阻断集成（`10` L87）。
    - Agent 在 S2 下还能写 `$TMPDIR/tower-<goalId>/`（`11` L332），它位于系统临时目录，不在上述根之内。
    - `11` L393 称该目录“随 Goal 清理”，但 `10` §10.3.2 的删除清单中没有它。
    - 于是，指向这个目录的目录符号链接在集成后仍可能指向 Agent 造出的仓库形态目录，而集成前只有一个可以勾过去的确认项。第 9 轮期望的是“指向 Tower 管理的根**或 Agent 可写位置**的阻断”。
- **为什么重要**：三处的后果都属 T29 一类：Agent 可控的 git 元数据落入用户主检出的可达路径，而用户自己的 git 不受 Tower 的注入保护。前提都需要特定的 base 内容或用户进入该路径，因此定为次要。
- **文档位置**：`10` §10.1.2 L76、L85、L87、§10.3.2；`15` ADR-106 L733–734；`11` §11.6.2 L332、L393；`14` G27c、G29。
- **期望的回答形态**：
  - (a) 权威检查的范围扩到“含有标记条目、且其中任何标记条目或 `objects/`、`refs/` 下的内容相对 base 有变化的目录”；或者对 base 中含 `HEAD` 文件的全部目录在每个 pin 上重新判定（数量通常很少）。
  - (b) 列出确认项涵盖的完整文件集合（`config`、`hooks/`、`commondir`、`gitdir`、`objects/info/alternates`、`info/`）。
  - (c) 阻断集合加入 `$TMPDIR/tower-<goalId>` 与全部 S2 写允许根（以 `11` §11.6.2 为唯一来源）；`10` §10.3.2 补上该目录的清理。
  - G27c 或 G29b 增加对应三个用例。

### D13 隔离、git 与并发

**R10-D13-01｜重要**

- **问题**：ADR-106 规定权威检查在物化的 pin 上进行，并“从 pin 与 seal 中排除”命中的目录。但规则与实现层的伪代码在四处不自洽：
  - **(a) 先有 pin，后有检查；排除集合来自早期预警**：
    - `07` L204、L213：生成 pin 的 `worktreeTree` 以 `earlyWarningRepos(g.satellite)`（早期预警的结果）作为 `add -A` 的排除集合；权威检查在 pin 生成之后、槽位检出之后才执行（L343）。
    - 由此有两种情况：
      - 早期预警已经排除的目录不在 pin 中，权威检查看不到它，`nested_repo` 只能来自早期预警——与“预警结果不作为 Verified 依据”（ADR-106 L735）矛盾；
      - 早期预警漏掉、而权威检查命中的目录已经在 pin 中，“从 pin 中排除”需要重新生成 pin，这一步没有定义（验证是继续在含该目录的 pin 上运行，还是重来？）。
    - G34 的通过条件（“权威检查记 `nested_repo`，且 pin 中不含 `vendor/x/`”）按现有算法无法同时满足。
  - **(b) 提前返回的路径不执行检查**：
    - `07` L319（子模块）、L327（全部 exec 标准命中缓存，或没有可运行的 exec 标准——纯 artifact、`human_only`、`ecosystem_unsupported`）、L331–336（S0 待授权或被拒）都在取得槽位之前返回 `decide`，从不调用 `authoritativeNestedRepoCheck`。
    - 纯 artifact 标准的 Goal 按 `07` L383 可以得到 `verified`。
    - `13` L342 把这项检查列为“永不降级”，但只有 `10` L76 的文字提到验收与 seal 时也要检查；`06` 的 `goal.accept`（L809）与 seal 恢复行（L128）都没有这一步。
  - **(c) “同一物化树”不成立**：`10` L76 与 `07` L195 写验收与 seal 时“在同一物化树上”检查。但槽位在验证结束时就拆除并释放（`07` L351），之后会被其他 Goal 复用。
  - **(d) 覆盖之后的语义没有定义**：
    - ADR-106 L732 说“合法使用这些文件名的罕见情况由人以 `override_sentinel` 处置”。
    - 覆盖之后，被排除的目录是否进入 seal？如果进入，seal 的树就不再等于已验证 pin 的树（`10` L400 “seal 的树就是已验证 pin 的树”），需要重新生成 pin 并重新验证；如果不进入，覆盖就没有效果。
- **为什么重要**：
  - 对用户主检出，权威检查是唯一的决定性防线（ADR-106 原则），而现在它的执行时机取决于走了 `verify()` 的哪条路径。
  - (a)(d) 还让 pin 的内容与哨兵的来源依赖于非权威的一层，违反“预警不作为依据”。
- **文档位置**：`07` §7.3.2 L195–204、L213、§7.4.1 L310–351；`10` §10.1.2 L76、L84、§10.6 L400；`13` L312、L342；`06` L128、L809；`15` ADR-106 L732、L735；`14` G34。
- **期望的回答形态**：
  - 把权威检查移进 `pinCommit`，在写出 pin 之前、对候选树对象执行：
    - 用 `ls-tree` 对相对 base 新增或有变化的目录做标记规则检查（大小写不敏感，只看非目录条目）。因为 git 必须有 `HEAD` 文件才判为仓库，标记规则本身就是 git 判定的超集，可以不依赖物化。
    - 如仍需 git 确认，只把候选目录物化到一个临时目录中执行。
    - 命中者在写 pin 之前排除，记录 `nested_repo`；早期预警只用于提示与两种检出，不再影响 pin。
  - 验收与 seal 时在 pin/seal 的树对象上重复同一检查（确定性、无需槽位）；`06` 的 `goal.accept` 与 seal 步骤补上这一步。
  - 覆盖的语义：覆盖产生一个包含该目录的新 pin，并重新验证；或者明确规定“覆盖只解除阻断，目录仍不进入 seal”。
  - G34 按新顺序改写通过条件，并增加用例：纯 artifact Goal 的 pin 中含新造的仓库形态目录 → 记 `nested_repo`，不得到 `verified`。

**R10-D13-02｜次要**（R9-D13-02(b) 的残留）

- **问题**：ADR-106 把两种检出改为“由影子树物化”，但有三处没有收口：
  - **(a) 人工编辑检出的依赖与生成产物**：
    - `10` L615 写“被忽略的依赖目录**按需**由安装器从 depcache 物化（与验证槽位同一机制）”。在槽位中，这套机制包括执行项目生命周期脚本与 `VerifyProfile.prepare`（Agent 写的代码，在验证器档位中运行，`07` §7.4.3）。
    - 对人工编辑检出，没有写明：
      - 是否执行这些脚本、在哪个档位执行；
      - 不执行时，生成产物（如 Prisma 客户端）缺失，人在 IDE 中看到的是不可运行的项目；
      - “按需”由谁、在何时触发；
      - depcache 未命中时怎样处理（见 R10-D10-01b）。
    - 此前人工编辑检出是卫星的 CoW 副本，人看到的就是 Agent 看到的环境；现在不同，差异没有登记。
  - **(b) 检验检出的备选来源与 ADR-106 矛盾**：`10` L560–561 仍保留“或从验证槽位最近一次物化结果 CoW 复制，含依赖目录”。槽位物化结果中含仓库形态目录（它们在 pin 中），而且槽位在验证后已拆除。
  - **(c) 未改动的夹具也不写出，理由不成立**：
    - `00` L81 的理由是“防止你在 Tower 之外的 git 发现 Agent 可能造出的仓库”。但内容与 base 相同的夹具本来就在用户主检出中，排除它们不减少任何暴露面，却让 git 工具类项目的检验与“我来改”无法运行测试。
    - 回应只写了“按协调者裁决”，没有给出理由。
- **为什么重要**：(a) 影响“我来改”这一核心逃生口的可用性；(b) 是同一节内的规则冲突；(c) 是一个对一类真实项目代价明确、而收益没有论证的取舍。
- **文档位置**：`10` §10.8.3 L560–563、§10.8.4 L613–616；`07` §7.4.2 L410、§7.4.3；`00` §0.5.1 L81；`13` L316；`15` ADR-106 L735。
- **期望的回答形态**：
  - (a) 规定人工编辑检出的依赖准备流程（是否执行生命周期脚本、档位、未命中 depcache 时的行为与界面提示），并在 `00` §0.5.1 登记与 Agent 环境的差异。
  - (b) 删除“从槽位 CoW 复制”的备选，或写明它同样要去掉仓库形态目录。
  - (c) 给出未改动夹具也不写出的安全理由（例如检出目录位置的信任属性与主检出不同）；如果给不出，改为内容与 base 相同的夹具照常写出。
