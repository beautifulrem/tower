**ADR-198 的主干成立**：
- **编号不复用**：`02` L46 是唯一的分配规则；`06` L1045 目录树、`09` L557/L565、`10` L253 一致引用。逐项推演：
  - **数据库从备份恢复**：高水位不低于被恢复数据库的最大编号，不会复用。
  - **高水位丢失**（手动删除 `~/.tower`）：默认位置的卫星、`_gitdirs`、`_stores` 与保留的 `_human`、`_inspect` 都在 `~/.tower` 之外、仍在 `<wtRoot>` 下，按 “跳过已有同名目录” 仍不会被认领；回退位置下这些目录随 `~/.tower` 一并消失，也就没有可冲突的对象。
  - **多机**：另一台机器的 Tower 在同一 `<wtRoot>`（例如移动磁盘上的检出）留下的卫星同样被跳过。
  - **用户仓库**：用户仓库中的 Goal 分支 `refs/heads/<prefix>/<goalId>-<slug>` 不在跳过规则内，但重新 seal 的识别规则按 sha（`10` L614 起），旧库的 seal 不在新影子中，不会被认作 “Tower 自己的 seal”；`B₀` 已存在时改写 `B₀-v<k>`，不覆盖用户分支。
  - **导入**（`06` L1108，M2）同样 “分配新的 GoalId”。
  - **并发分配**：Supervisor 是唯一写者，分配在 `goal.created` 的事务内完成，不构成实质问题。
  - 高水位文件损坏与 “本机从不复用” 的措辞见 §5 观察 1、2。
- **两种检出的独占新建**：`10` L253（唯一定义）、L863、L918，`06` L895、L903 一致。逐一核对创建它们的流程：
  - 接管与打开检验：有守卫；

  - 卫星重建（情形 E 与 `goal.rebuild_satellite`）：不创建 `_human`、`_inspect`；
  - 删除卫星时（`10` L446）只删本 Goal 的目录，编号不复用之后前提成立。
  - 守卫的代价是：本 Goal **自己** 中途中断的接管或删除留下的 `_human/<goalId>` 也会被拒绝。回应说这一代价 “已写入 `10` §10.2”，正文中没有，见 R71-D13-01。

### D13 隔离、git 与并发

**R71-D13-01｜次要**（ADR-198 的守卫让 `_human/<goalId>` 只能独占新建，路径已存在时 “我来改” 一律 `E_STATE`。被拒绝的对象包括本 Goal **自己** 中断的接管或删除留下的残留。回应把 “交接中途崩溃后残留的 H 需人移走才能再次‘我来改’” 列为有意的代价，并说已写入 `10` §10.2，但正文与界面都没有这句话）

- **问题**：
  - **残留从哪来**：
    - `06` L903 `goal.take_over`：先物化 `<wtRoot>/_human/<goalId>`（影子树写出、gitdir、依赖准备），**之后**才在同一事务写 `state=paused`、`human_checkout`。物化中途崩溃时，H 已部分存在、`human_checkout` 为空、Goal 停在接管前的状态。外部编辑器在事务之后才打开（L903 末、`10` L933），因此这一残留中不会有人的改动。
    - 交还第 8 步（`10` L979 起）与 `goal.discard_human_edits`（`10` L1007）都要 “删除 H；清除 `humanCheckout`”，两者的先后没有规定。H 含依赖目录，删除可能耗时较长，中途中断或部分失败时也会留下残留。此时改动已写回或已被人明确放弃。
  - **守卫的效果**：`10` L253、L918：“路径已存在时不写出、不覆盖、不删除、不改名……返回 `E_STATE` 并列出该路径”。`06` §6.1.6 L144 只处理 `human_checkout` 非空的情形，没有一行处理 “`human_checkout` 为空而 `_human/<goalId>` 存在”。照文实现，这个 Goal 此后每次 “我来改” 都被拒绝，直到人自己删除或移走该目录。回退位置下，这个目录在 `~/.tower/worktrees/<projectId>.noindex/_human/` 里。
  - **人无从判断能否删除**：
    - `04` §4.6.7（L593 起）没有这一 `E_STATE` 的文案；
    - `10` L253 只写 “列出该路径”，没有说明它来自本 Goal 中断的操作、其中没有未交还的改动。
    - 而 ADR-196/197/198 刚刚反复告诉人：`_human` 目录 “可能含你的改动”（`09` L557）。人看到被拒绝的路径，合理的反应是不敢删。
  - **与回应的出入**：`round-70-response.md` “偏离指示之处” 一节写 “代价：‘我来改’在交接中途崩溃后，残留的 H 会使下一次‘我来改’返回 `E_STATE`，需人移走后重试”；“未解决” 一节写 “已写入 `10` §10.2”。`10` L253 与 `15` ADR-198 中都没有这句话。
- **为什么是次要**：不丢数据，也不放宽安全边界，失败方向是拒绝。但这是一个守卫没有区分的状态，结果是一个 Goal 永久失去 “我来改”，而恢复它需要人在 Tower 自有的目录中做出一个文档刚刚警告过可能丢改动的删除。实现者会分出两种做法：照字面永久拒绝；或者自行加启动清理。启动清理与 “不删除” 的字面相反。
- **文档位置**：`10` L253、L446、L918、L933、L979 起第 8 步、L1007；`06` L144、L903；`04` §4.6.7；`09` L557；`round-70-response.md` L98、L109。

  - **识别本 Goal 的残留**：`human_checkout` 为空、Goal 非终态、`_human/<goalId>` 存在时，按 ADR-198，它只能来自本 Goal 中断的接管（编辑器尚未打开）或中断的删除（改动已写回或已放弃）。“我来改” 返回的 `E_STATE` 提供 “移到 `<路径>.stale-<时间>` 后重试”：由人点击，只改名不删除，并在结果中列出新路径。也可以在启动时对这类残留生成一条 Needs-You。

### D4 领域模型与生命周期

**R71-D4-01｜次要**（ADR-198 让此前批准的扩展 “并入新版本的合同值”，但这只靠 “修订编辑器的 `Budget` 各字段预填修订前的生效额度” 实现。`contract.amend` 的参数是 `{goalId, patch, …}`，界面还有不经预算编辑器、直接生成修订的入口。这类修订的 `patch` 不含预算字段，新版本的 `Budget` 按 patch 语义沿用上一版合同值；而 “修订后以新版本为准” 又使此前的 `extend_budget` 不再计入。结果正是 R70-D4-01 要消除的那种 “扩展悄悄失效”）

- **问题**：
  - `06` L349（唯一规则）：生效额度 = 当前合同版本的 `Budget` 与 “该版本批准之后” 的 `extend_budget` 取大；“修订合同产生新版本后，以新版本为准：修订编辑器的 `Budget` 各字段预填修订前的生效额度，此前的扩展因此并入新版本的合同值”。合并只是编辑器行为的推论，没有写成命令层的规则。
  - `06` L878：`contract.amend {goalId, patch, amendmentNote, confirmSecret?}`。正文没有规定 patch 中缺省的字段取什么值；按 patch 的通常语义，取上一版合同值。
  - **界面直接生成的修订**：
    - `03` L86 与 `07` L482：`verify_failed` 卡片的 “改为 human 标准” 由界面生成 “把该标准由 `exec` 改为 `human` 的修订”，再自动发出 `retry_verify`。它不经过预算编辑器，patch 中只有该标准。
    - `09` L383 的超时建议、`04` L942 的 “修订合同后继续” 会打开编辑器，可以按预填处理；但正文没有要求所有入口都经过编辑器。
  - **常见路径**（与 R70-D4-01 相同的后果）：
    - Goal 在 US$10 硬上限暂停，人 `budget.extend{usdHard: 15}` 后继续；
    - 之后一条依赖本地机密文件的标准失败，人点 “改为 human 标准”；
    - 新版本的 `usdHard` 仍是 10，此前的扩展不再计入；
    - 下一次开 Run（例如人随后 “请求修改”）前即进入 `budget_hard_cap`（`03` L83），没有任何提示。
  - **编辑器路径上还有一个并发窗口**：编辑器打开期间，另一客户端批准了 `budget.extend`（手机可批小额，`16` L1103）。提交时比较对象是 “修订前的生效额度”（已更高），而编辑器中的旧预填值低于它，修订被判为 “降低”，远程也可执行。新版本于是悄悄撤销了刚批准的扩展。
- **为什么是次要**：不丢数据，可以再次扩展。但 ADR-198 的目标是 “不因修订而失效”，规则写在编辑器上而不是命令上，照文实现的两条入口表现不同；其中一条会让人在修订后被意外暂停。
- **文档位置**：`06` L349、L878；`03` L83、L86；`07` L482；`09` L383；`04` L942、L1131；`16` L1103、L1143；`14` L115。
- **期望的回答形态**：把合并移到命令层，写在 `06` §6.2.5（唯一规则）：
  - `contract.amend` 在服务端生成新版本时，`Budget` 中 patch 未给出的字段取**修订提交时**的生效额度，给出的字段以 patch 为准；
  - `16` §16.5 的比较对象不变（修订前的生效额度）；
  - 编辑器预填因此只是显示，“改为 human 标准” 等生成的修订自动覆盖；
  - 编辑器提交时若生效额度已不同于预填值（期间有新的扩展），返回 `E_STALE` 并重新预填。

### D6 系统架构与可靠性

**R71-D6-01｜次要**（“彻底忘记一条记忆” 对已归档或放弃的 Goal 提供 “一并删除这些会话”，但这个人的选择与要删的会话清单在 `privacy.purge` 的参数、`privacy.purged` 的载荷与 §6.1.6 的续做规则中都没有落点。数据库事务之后记忆与其注入记录已删除或墓碑化，续做无法再推出该删哪些会话、人是否选了删除）

  - **不扣分的观察**：
    1. **“本机从不复用” 的措辞**：`02` L46 写 “本机从不复用”。但高水位随 `~/.tower` 被手动删除后，没有留下同名目录或 `refs/tower/<编号>/` 的编号仍可能复用。复用之后不会伤到任何东西：受保护的目录被跳过；用户分支按 sha 识别，`B₀` 已存在时另开 `-v<k>`。ADR-198 自己的表述是 “高水位丢失时（目录保护）同样成立”，比 `02` 准确。另外，跳过规则中的 `refs/tower/<编号>/` 默认不存在（`10` §10.6.2：只有开启 “保留审计地标” 时才写），实际起作用的只有目录一项。建议把 `02` 改为 “本机不复用（高水位丢失时至少不与已有目录、地标同名）”。
    2. **高水位文件无法解析**：没有写处置。实现者大多会视同缺失，由跳过规则兜底，并在下一次分配时重写。建议在 `02` L46 加半句写明。
    3. **项目档的重复续做**：`project` 档中途崩溃后，`project` 事件与逐 Goal 事件都未配对，续做会对同一批文件执行两遍。删除是幂等的，结果正确，只是多做。可在 `06` L142 注明 “逐 Goal 事件在其 `project` 事件续做完成时一并配对”，非必须。
    4. **检验检出的临时目录与服务数据目录**：`10` L871 与 `11` L381 都写 “写允许只有检验目录、其临时目录与服务数据目录”，但没有定义后两者的位置。回应断言它们不在 `~/.tower` 之下，因而不进入回退例外，正文没有依据。若实现者把它们放在 `~/.tower/tmp/` 下，默认位置与回退位置都会被读拒绝挡住，实现时会立刻发现，不会放宽什么。建议在 §10.8.3 第 3 步写出位置（例如 `$TMPDIR/tower-inspect-<goalId>/`）。
    5. **多机下的编号**：两台机器对同一仓库各自从 G-0001 编号。用户自行推送分支后，远端可能出现同名的 Goal 分支。v1 不承诺跨机器连续性（`04` L1524，ADR-028），本机的 seal 识别不受影响，属已登记的范围限制。
    6. **取舍判断**：见 §3.3。
