# 00 · 愿景与设计原则

> 代号 **Tower**（暂定，取自空管塔台：一个人同时监督多个自主运行的对象，只在例外时介入）。
> 引擎：Pi（`@earendil-works/pi-coding-agent`，固定版本 1.2.0（精确；核实基线见 `research/pi-release-diff.md`）），通过 Engine Adapter 接入，可替换。

## 0.1 一句话

**Tower 是一个以 Goal 为第一公民的 Agent 监督台：它不展示 Agent 在“说”什么，而展示 Agent 在“做成”什么——并且把“做成了”的证据和 Agent 的自述严格分开。**

## 0.2 出发点：原论述的核心观点（P = Premise）

| # | 原论述观点 | 我们的立场 |
|---|---|---|
| P1 | 现有 Agent GUI 沿用 VSCode 三栏排布（Session 列表 / Chat 流 / Diff 侧栏），是 Chat 时代的思维惯性 | **采纳**。布局改为按监督职能组织（计划 / 监视 / 介入 / 审阅 / 学习），而不是按“文件树-编辑器”组织 |
| P2 | 中间的过程流（Reading…/Running tests…）只在运行时有用，事后无用，且因“人脑聚焦于流动”而制造“很忙但不知道在忙什么” | **采纳并加强**。过程流降级为单行 Live Line；但过程流**不删除**，一键可达且按时间索引（见 R3） |
| P3 | 主屏应显示全局 State：Goal / Task / Cause / Decision / Changes / Validation | **采纳并修正**。字段必须按**可信度来源**分层（Fact / Claim / Human），并补充缺失的 *Projection*（下一步与不确定性）和 *Mode*（见 R1、R4） |
| P4 | Sidebar 以 Session 为单位会随 /new 堆积退化；大量 Session 用过即弃 | **采纳**。Sidebar = Goals + Needs-You；Session 降级为 Trace；用过即弃的对话进入 Scratch 通道 |
| P5 | Context/Memory 与 Session、与文件路径强绑定不合理 | **采纳并修正**。Memory 按 User / Project（仓库身份而非路径）/ Goal 三层作用域；项目级记忆仍跟随项目，但项目身份不再等于路径 |
| P6 | Goal 应进 Sidebar，与文件夹、Session 解耦，完成后自动归档 | **采纳并修正**。“完成”拆为 Claimed → Verified → Accepted，**只有人的验收**触发归档（见 R2） |
| P7 | 要 Review 就要完整 Diff，而非副关注点；要指挥多 Agent 就要看到每个 Agent | **采纳**。Review 是独立的全屏模式；Overview 是多 Goal 看板 |
| P8 | 终端 / Preview 被 Chat 挤压 | **采纳并重新定位**。终端与 Preview 成为“证据面”（Evidence Surface）：附着在 Claim 上的验证工具，而非常驻面板 |
| P9 | 监督只需 Goal、Task、Changes；现代模型会主动 ask | **部分反对**。模型典型失败是“自信地跑偏”而非提问；监督的主力必须是 Harness 侧的异常检测，而不是模型自觉（见 R5） |
| P10 | 我们想知道的是：Agent 在干什么、要做什么、做了什么、改变了什么；不应通读 Chat History | **采纳**，作为北极星问题（见 0.4） |

## 0.3 调研后新增的修正原则（R = Revision）

这些原则来自对抗性审视与理论调研（详见 `01-research-synthesis.md`），它们弥补原论述的盲区：

- **R1 事实与声明分离（Honesty Grammar）。** Agent 的结构化摘要是“声明”而不是“仪表读数”。研究显示 Agent 在相当比例的失败运行中报告成功、会改测试以通过不可能任务、推理链不忠实。因此：
  - **Fact**（事实）只能由 Harness 产生：git diff、命令退出码、测试计数、文件触及集合、时间戳、提交哈希。
  - **Claim**（声明）由 Agent 产生：计划、原因、决策理由、“已完成”、下一步（ADR-030 已删除 ETA 类说法）。Claim 永远不显示为绿色，只能“链接”到 Fact。
  - **Human Decision**（人的决定）：验收、批准、拒绝、合同修订，不可篡改（隐私清除只置空其文本、留下墓碑，`09` §9.12.4）。
  - 这是全产品最重要的一条视觉与数据规则。
- **R2 完成三态。** `Claimed`（Agent 说完成）≠ `Verified`（Harness 在固定提交上重跑验收标准并通过；任何新改动使其失效）≠ `Accepted`（人验收）。只有 `Accepted` 归档。
- **R3 无“接管悬崖”。** 隐藏过程流优化了 95% 的正常情形，却惩罚了 5% 需要人突然接手诊断的情形（Bainbridge《自动化的反讽》、Endsley 的 out-of-the-loop）。所以：Trace 一键可达、按时间索引、能按异常过滤（“显示测试开始失败前后的 6 次工具调用”）；接管时给**诊断视图**而不是平静视图。
- **R4 情境感知三层俱全。** 过程流只提供 L1（感知：发生了什么）；P3 的六字段补上了部分 L2（理解：对目标意味着什么）；还缺 L3（预测：接下来会怎样、多确定）。Goal 页必须显示“验收标准进度”（L2）与“下一步 + 预计何时需要你 + 预算消耗”（L3）。
- **R5 例外管理（Management by Exception）。** 上司不盯下属，但下属出问题必须能叫到上司。注意力只在需要人时被拉取：Needs-You 收件箱遵循工业报警管理纪律（每条可行动、去重、限流、可度量精度）。
- **R6 模式显示器（Mode Annunciator）。** 每个 Goal 时刻处于一个封闭集合中的确定模式（Running / Waiting-on-you / Blocked-by-guard / Budget-capped / Retrying / Compacting / Verifying / Settled…），由 Harness 事件推导，**绝不由模型写**。这是 Live Line 的唯一合法职能：告诉你“它活着，以及它在做哪一类事”。
- **R7 合同而非提示词。** Goal 不是一句 prompt，而是一份 **Goal Contract**：意图（commander's intent）、可执行验收标准、范围围栏、预算、自主度矩阵、停止条件。人批准的计划被编译为运行时的围栏：计划步骤声明的路径并集成为 Harness 强制执行的范围围栏；需要决策的步骤成为注入给 Agent 的 `natural` 停止条件——由 Agent 以提问停下，Tower 不求值、不强制，只在 Agent 声明进入该步骤时提醒（规则见 `02` §2.5 PlanStep，ADR-197）。范围围栏由 Harness 强制，决策点至少被注入并提醒；否则“事前批准计划”反而降低运行中的警惕（2026 CUA 监督研究，ADR-198）。
- **R8 评审是理解迁移，不只是批准。** 大 diff 切成 ≤300 行的评审单元，按风险排序，附意图叙述；在 diff 上评论 = 向 Agent 发出转向指令（带送达回执）。这是原论述“中间几乎没有编辑空间”的答案：人对 Agent 的主要操控通道从“聊天”变为“批注”。
- **R9 学习闭环。** 监督控制的完整循环是 Plan → Teach → Monitor → Intervene → Learn。原论述覆盖了 Monitor，弱化了 Teach 与 Learn：人的转向与返工原因应被沉淀为可批准的规则 / 记忆 / 技能，否则同样的错误每个 Goal 重来一次。
- **R10 成功指标是校准，不是满意度。** 更干净的界面会提高信心却不提高准确度（Microsoft 2026）。我们度量：被抓到的种子错误比例、信心与正确率的校准、Needs-You 的告警精度、重入后首个正确动作的耗时。
- **R11 按评审能力调速。** 生成代码的速度不得长期超过人评审代码的速度（Zechner “按你的评审能力限制每天生成的代码量”；Faros：评审时间 +91%）。Tower 维护“评审积压上限”（ADR-014，按 LOC 计的 WIP 上限）：待审与在途 LOC 超出上限时提示；阻止模式下新 Goal 停在 `ready` 而不是继续堆积待审代码（默认提示模式，E8 通过后切为阻止模式）。可关闭。
- **R12 新范式必须可逃逸。** 强推新布局的产品（Cursor 2.0/3、Antigravity 2.0）都遭到反弹；Claude Code 折叠工具输出也引发反弹。Tower 的默认视图是 Goal 状态，但任何 Goal 都可一键进入 Watch 模式（Live Line + 实时 Trace 尾部），偏好按 Goal 记住。Live Line 始终保留可转向的细节（文件、命令、失败的测试），而不是笼统的“工作中”。

## 0.4 北极星问题

用户在任意时刻扫一眼（≤ 3 秒）应能回答：

1. **哪些事需要我？**（Needs-You，按延迟代价排序）
2. **每个 Goal 现在处于什么模式？是否健康？**（Mode + 异常）
3. **离完成还有多远，证据是什么？**（两轨进度“已验证 V/M · 观测到 O/M”，ADR-020；只有已验证一轨是 Fact；M 只计机器标准，人工标准另列“人工 h/k”，ADR-052）
4. **自从我上次看，发生了什么重要的变化？**（Re-entry Briefing）
5. **我该审什么，先审哪块？**（评审单元，按风险排序）

如果某个界面元素不服务于这五个问题之一，它默认不出现在主视图。

## 0.5 与 Pi 设计哲学的对齐

Pi 的哲学（Mario Zechner 原文与 Pi 1.0 公告）：极简系统提示词与工具集；上下文工程优先、“我要检查与模型交互的每个方面”；可扩展、“让 Pi 适应你的工作流”；不内建 to-do / plan mode / 子 Agent / 权限弹窗，由扩展或宿主提供；新特性“等它被证明再加”。

| Pi 原则 | Tower 的对应做法 |
|---|---|
| 极简：最少工具、最短提示词 | **模型面预算**：Tower 只向模型注入 3 个工具（`ask_user`、`log`、`submit`）；常驻增量（工具声明 + Goal 系统段）≤ 650 token，完整合同按需读取，事件性注入单独封顶（ADR-009）。Task、Mode、Changes、Validation 全部由 Harness 推导，不要求模型维护 to-do（尊重“to-do 会迷惑模型”的经验）。见 `05-pi-integration.md` |
| 上下文透明：看到每个 token | 隐藏过程流只是**默认视图**；Trace 无损可达；Tower 注入的每条上下文（简报、记忆、转向）都在 Trace 中以“Tower 注入”标记原样可见 |
| 可扩展、属于用户 | Tower 自身的 Goal 能力实现为一个标准 Pi 扩展（`tower-goal`），用户已有的 `~/.pi/agent` 扩展、技能、模型配置在多数情况下照常生效（例外见 §0.5.1）；提供“使用我安装的 pi”模式（M2） |
| 不内建权限，交给宿主 | 权限、沙箱、验收全部在 Tower 层（Pi 期待宿主加策略），用 `tool_call` 钩子实现；仓库内 `.pi/` 的技能、提示、主题与 `SYSTEM.md` 只在项目被信任且未被修改时加载，项目扩展、项目包与项目 MCP 服务器在 M1 中不加载（ADR-004、ADR-202） |
| 等特性被证明 | 每个监督特性都附带验证实验与可关闭开关；`pi-durable` 作为中期底座观察而不提前依赖 |
| Session 是 JSONL 树 | Tower 不另造对话存储：Pi 的 JSONL 仍是对话唯一真相，Tower 只引用它（Goal → Traces） |

### 0.5.1 与直接使用 pi CLI 的能力差异

为了安全与可验证，Tower 中的 Pi 有以下有意的差异。每一项都在首次运行或静态扩展清单确认时向用户明示：

| 差异 | 原因 | 依据 |
|---|---|---|
| 注册了 `bash` 的用户扩展在 Tower 中不生效，由 Tower 沙箱版 bash 取代（继承用户的 `commandPrefix` 与 shell 设置） | S2 沙箱必须覆盖 Agent 的所有命令 | ADR-041、ADR-066 |
| M1（SDK 宿主）不提供 `!cmd`（SDK 不发出 `user_bash`）；M2 的 RPC 模式下 `!cmd` 与 `bash` 命令经 `user_bash` 处理器在沙箱中执行 | 同上 | ADR-066，`05` |
| 依赖 git 的用户扩展与 MCP git 服务器在卫星中看不到仓库（工作目录中没有 `.git`，Host 环境设置 `GIT_CEILING_DIRECTORIES`） | 沙箱外的 git 不得读取 Agent 可控的元数据 | ADR-081 |
| 建议（非强制）：用户在自己的全局 git 配置中也设置 `safe.bareRepository=explicit`——Tower 已对它启动的所有进程注入该设置，但你在 Tower 之外、自己打开的终端或 IDE 若进入卫星目录则不受此注入保护 | 卫星中可能存在 Agent 写出的裸仓库布局目录 | ADR-096 |
| 用户扩展（及其派生进程）在 Tower 中运行 git 时，遇到任何裸仓库都会失败（Tower 注入了 `safe.bareRepository=explicit`）；依赖裸仓库的扩展功能不可用 | 同 ADR-096 | ADR-096 |
| 位于扩展包根目录（而非 `skills/` 子目录）的技能在 Tower 中不可用 | Agent 不可读扩展目录 | ADR-100 |
| Agent 改动了任何“仓库形态”目录（含 `HEAD`/`commondir`/`gitdir` 类条目的目录，名字按 `10` §10.1.2 的规则比较，含根目录）下的内容，或让某个符号链接经整链解析后变得不安全（越出仓库、经过 tree 中不存在的分量或 `.git` 分量）——都会阻止验收与集成，直到你写明理由覆盖；检查基于 git tree 的名字规则，与本机 git 版本无关。base 中原有、未改动的夹具，以及 base 中原本就不安全且解析结果未变的符号链接不受影响（后者只在信任提示中列出）。覆盖后，两种检出中该目录只有 `objects/`（不含 `objects/info/`）、`refs/`、`packed-refs` 写出 Agent 的版本，其余写出 base 版本 | 防止 Agent 造出的仓库或越界链接进入你的 git（IDE、shell 提示符、合并后的主检出）与工具 | ADR-109、ADR-111、ADR-112、ADR-116、ADR-124 |
| 你（或任何非 Agent、非 Tower 的程序）直接改动 Goal 工作目录中的文件，会让 Goal 暂停，直到你选择“采纳为我的改动”（之后重新验证，提交中记为你的改动）或“撤销这些改动”——包括评审阶段的就地编辑（M2）；推荐用“我来改”的人工编辑检出。例外：合入后的 24 小时宽限期内不检测，撤销合入时补做一次（`10` §10.3.1，ADR-194/195） | 来源不明的内容不能被验证、评审或以你的名义提交（诚实语法） | ADR-122 |
| 人工编辑检出与检验检出由 Tower 从已跟踪内容物化：人工编辑检出**立即打开**，依赖在后台从缓存复制或由安装器重建（期间显示“依赖准备中”）；Agent 自己安装的未锁定依赖不在其中；**生成产物（如 Prisma 客户端）不自动生成**，M1 中 Tower 也不在人工编辑检出中运行准备步骤：需要时由你在自己的终端中运行——这是在 Tower 沙箱之外、以你的权限运行 Agent 可能改过的代码，是否运行由你判断；在沙箱中运行准备步骤属 M2；依赖目录中的仓库形态目录不写出并在信任提示中列出；被 git 忽略的本地文件只按项目“本地文件”清单写入 | 不直接复制 Agent 的工作目录、不自动执行 Agent 写的准备脚本，避免把 Agent 造出的内容带进你的工具 | ADR-078、ADR-109、ADR-116、ADR-210 |
| 设置中指向过宽路径（例如整个主目录）的自定义技能路径不会加入 Agent 读白名单，相应技能在 Tower 中不可用 | 避免把整个主目录暴露给 Agent | ADR-100 |
| 若 SP6b 证明垫片 exec-path 不可行（ADR-097 备选）：git 内部再次调用的 `git`（`rebase -x`、钩子、别名）继承卫星 `GIT_DIR`，在其中创建临时仓库的测试会失败（只影响 Agent 自己的沙箱） | 垫片无法拦截 git 自身派生的调用 | ADR-097 |
| 以绝对路径调用真实 git（如 `/usr/bin/git`）且继承了卫星 `GIT_DIR` 的进程不经垫片拦截——只会作用于本 Goal 自己的卫星，不越过沙箱 | 垫片只能拦截 PATH 上的 `git` | ADR-090 |
| 用户主检出中**未被 git 跟踪**的 `AGENTS.md`/`CLAUDE.md` 不在卫星中，Agent 看不到（祖先目录中的上下文文件不受影响）；需要时先让 git 忽略它（加入 `.git/info/exclude`），再把它加入项目的“本地文件”清单——清单只接受被 git 忽略的文件 | 卫星是 git 克隆，只含被跟踪的内容 | ADR-060、ADR-078 |
| Agent 的 Pi 总在仓库根运行：monorepo 子包（以及子包与仓库根之间的目录）中的 `AGENTS.md` 与 `.agents/skills` 不加载；你习惯在子包中运行 Pi 时，你的 Pi 会加载它们，Agent 看到的与你不同（需要时把内容写进仓库根的上下文文件或合同） | Run 的 cwd 是主 binding 的卫星根；Pi 只加载 cwd 及其祖先目录中的上下文文件与项目技能 | ADR-204、ADR-205 |
| Agent 侧不经 PATH 中 `git` 的 git 实现（libgit2 绑定、isomorphic-git 等）在卫星中看不到仓库；PATH 中的 `git` 经 Tower 垫片指向卫星 gitdir | 不全局导出 `GIT_DIR`，避免测试中的临时仓库被劫持 | ADR-088 |
| 卫星没有远端：扩展中的 `git fetch`/`push`/`remote` 类操作行为不同；Agent 不能推送或开 PR。**M1 中 Tower 也不推送**：验收后只在你的仓库创建本地分支，由你自己推送（ADR-133）；M2 起可由 Tower 推送并开 PR | 推送是单向门 | ADR-074、ADR-133 |
| **M1 中 Tower 写进你仓库的汇总提交不签名**，即使你的 git 配置要求签名（`commit.gpgSign`）：验收面板如实写“Tower 写入的提交未签名；需要签名的提交请在合并前自行签名”（自行签名会改写该提交，之后再次验收另开 `-v<n>` 分支）。撤销合入时 Tower 也不在你的仓库中生成撤销分支，只写出要撤销的提交与做法。你的仓库任一工作树中有进行中的 rebase、merge、cherry-pick、revert、am 或 bisect 时，Tower 这一次不写入也不删除分支。签名与撤销草案在 M2 | 缩小 Tower 写你仓库的范围：M1 不调用你的签名程序（它可能等待口令或硬件密钥），不打断你进行中的 git 操作 | ADR-193，`10` §10.6、§10.12 |

## 0.6 非目标（v1）

- 不做代码编辑器（不与 VSCode/Zed 竞争）；只提供“就地修一下 Agent 的 hunk”的轻量编辑（M2；M1 中用“我来改”的人工编辑检出）。
- 不做聊天机器人；Scratch 通道是例外而非主路。
- 不自研 Agent 循环（引擎创新不是本产品的价值所在）。
- 不做团队 SaaS 后端（v1 单用户本地优先；数据模型为团队预留字段）。
- 不做移动端原生 App（v1 提供 `serve` 模式供远程只读 + 决策卡片）。
- 不做后台守护进程：退出应用即暂停 Goal、下次启动恢复（ADR-017）。
- Windows 在 M3 前不提供 OS 级沙箱，只有策略层（ADR-018）。
