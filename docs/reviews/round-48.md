## 1. 总评

ADR-173 按第 47 轮的期望形态处理了三条问题，并以删除关闭了其中一条，主体落地干净：

- **记录字段**：`CriterionCheckData.env.localFiles` 已登记（L856-857），只含本应复制的条目。G46(ai) 第二组改为针对该字段。
- **二选一**：`criterion_check` 只按 tree 判新鲜度。`07` L261、§7.3.3 ②（补注“本地文件项不会在两次验证之间使已通过的结果过期”）、L492、`16` L512 与 L373 一致；G46(ai) 断言“修改之后、下一次验证之前仍为 `fresh`”。
- **提示来源**：“未复制”一行取自本次验证的 `not_copied` 条目。`07` L457-460、L1650 模板、`04` L1483、`16` L512、G46(ah) 一致；“之后恢复文件不移除旧卡片上的这一行”也写进了 `04` 与 G46。

- **排期**：WBS 121.63，各线、余量、依赖链 19.7、增人 127.42 / 23.53 / 33 周、M1 38 周，全部经脚本复核成立；`14` 与 `15` 一致。

沿 ADR-173 新加的落点复查，还有四处**次要**问题，都不丢用户数据：
1. **读取提前带来一个新的时间窗**：读取从“取得槽位后”提前到“验证开始时”，写出仍在取得槽位之后，中间可能是数分钟的排队。正文没有说明这段时间内人执行 `mark_secret` 或 `remove` 时，在途验证是否还写出已读入的内容。`04`、`06` 写的是“此后不再复制”（D11）。
2. **重放没有说明本地文件**：重放包规格没有提到本地文件，`env.localFiles` 记录了哈希，却没有被重放使用。依赖已播种文件的验证，其重放结论没有定义（D7，源头早于 ADR-173）。

4. **`extraGlobs` 没有了消费者**：ADR-173 写明指纹 `extra` “保持 ADR-078 的原义”，但 ADR-078 并未定义它，它原本唯一的用途（使结果随本地文件变旧）正是 ADR-173 取消的那一项。`07` 的 VerifyProfile 注释与 `09` 的学习提议仍按旧用途描述它（D15）。

### D7 诚实与验证

**R48-D7-01｜次要**（重放包没有说明本地文件；`env.localFiles` 未被重放使用）

- **问题**：
  - `07` §7.4.1 的重放包是“唯一规格”。内容一行（L473）列出 lockfile、depcache、`$VS` 配置哈希、工具版本、`envHash` 与生效环境；重放一行（L478）列出恢复 pin、按记录取工具、物化或重建依赖。两行都没有提到**本地文件**。
  - 而本地文件是原验证的输入：它们写进槽位，内容哈希进入 `envHash`，ADR-173 之后还逐条记在 `criterion_check.env.localFiles` 中。它们也是 `envHash` 各项中唯一无法从重放包恢复的一项。
  - 正文因此有两种读法：
    - 重放不播种本地文件。依赖 `.env.local` 一类已播种文件的标准在重放中会以不同结论结束，而结论分类（“复现（原 depcache）”“复现（依赖重建…）”“不可重放：<原因>”）中没有对应项；
    - 重放从用户检出播种当前的本地文件。这样它就成了第五个复制点，`16` L512 列的是“目前四处”；而且当前内容可能已与原验证不同，重放报告却不会说明。
  - `env.localFiles` 已经提供了判断依据（逐条比对当前内容哈希），但没有被使用。
- **为什么是次要**：重放是审计工具，不影响 `decide()`、Verified 或任何状态转移；后果是重放结论可能被误读，或两种实现给出不同报告。不涉及安全，不丢数据。源头早于 ADR-173（ADR-070/078），ADR-173 新增的字段使修复变得直接。
- **文档位置**：`07` L468-478（重放包规格）、L856-857（`env.localFiles`）；`16` L512（复制点列举）；`14` G18。
- **期望的回答形态**：
  - 在重放一行写明本地文件的处理，二选一：
    - 重放按 `16` 的规则播种 `seeded` 条目（列为复制点之一，同样读入、判定、写出同一份），并把当前内容哈希与 `env.localFiles` 逐条比对；不同或缺失时结论标注“本地文件不同：<路径>”，不写“复现”；
    - 或者重放不播种本地文件；`env.localFiles` 非空时，结论写“不可重放：依赖用户本地文件”，或允许运行但标注本地文件缺失。
  - 结论分类补上“结论与原验证不同”的情形如何表述（若尚未覆盖）。

### D8 注意力与交互

**R48-D8-01｜次要**（项目级 L1 通知没有呈现位置与送达主题）

- **问题**：
  - 本地文件一域有三条项目级 L1 通知：内容命中改为机密（ADR-170/172）、自动恢复（ADR-172）、无法读取（ADR-173）。`04` L1299-1301 都写作“通知你 …（L1，`08` §8.1）”。
  - `08` §8.1 的 L1 渠道是“Goal 卡片 chip、Live Line 字形、菜单栏/托盘字形、进入简报和摘要”，全部以 Goal 为单位。项目级通知没有对应的 Goal 卡片；重入简报“每次都从账本重新生成”（`08` L583），进程内状态进不去；站会摘要属于 M2。`02` §2.9 的 `owner` 有 `project`，但那是 Needs-You 条目（L2 起），L1 不是 Needs-You。
  - ADR-173 把“无法读取”改为不写账本的进程内状态后，它必须经某个订阅主题推给 renderer（`06` §6.4.2 中 `settings` 与 `system` 都可能），正文没有指定。
  - 结果：实现者可能把它做成收件箱条目（计入 Dock 角标，违反 L1 的定义）、应用内 toast，或只在设置页显示；“消失”的含义（从哪里消失）也随之不同。
- **为什么是次要**：L1 不进入 Needs-You、不消耗打扰预算，这条通知也不影响任何判定；后果是三处 UI 实现可能不一致，或人看不到这条通知。不涉及安全，不丢数据。
- **文档位置**：`08` §8.1（L24）、L583；`04` L1299-1301；`06` §6.4.2；`16` L284-285、L512；`12`（`◇` 提示的位置）。
- **期望的回答形态**：
  - 在 `08` §8.1 或 `04` 本地文件设置一节写明项目级 L1 通知的呈现位置。例如：本地文件设置页对应行的 `◇` 提示，加侧栏或项目切换处的一枚项目级 `◇`；不进入收件箱，不计入 Dock 角标。

### D11 安全与自主度

**R48-D11-01｜次要**（读取提前到验证开始后，在途验证与 `mark_secret` / `remove` 的先后没有规则）

- **问题**：
  - ADR-173 之前，验证槽位的读取发生在取得槽位之后、写出之前，读与写之间几乎没有间隔。现在读取在 `verify()` 第 3 步（L397），写出在 `verifyPool.acquire` 与 `slot.checkout` 之后（L413-416）。中间可能经过 §7.4.10 的排队，p95 以 10–20 min 计（L945、L968）。
  - 这段时间内人可能执行：
    - `project.local_files.mark_secret`：`06` L878 写“此后不自动播种到验证槽位、检验检出或卫星”，`04` L1297 写“此后不再复制”；
    - `project.local_files.remove`：条目已不在清单中。
  - `verify()` 注释写“写出上面已读入的内容，不再读用户检出”，没有说写出前是否按当前的 `seeded` 谓词复核。照字面实现，在途验证会在 `mark_secret` 之后把该文件写进运行 Agent 代码的槽位；另一种实现会在写出前复核，并对已不再 `seeded` 的条目放弃写出（此时 `local.record`、`envHash` 与槽位内容又需要重新对齐）。两种实现都能在正文中找到依据。
- **为什么是次要，不是重要**：
  - 写出的字节在读取时已经按名字、内容与当时的分类判定为非机密；内容命中永远按同一份字节判定，这一面没有缺口；
  - 已批准的普通文件本来就会复制进卫星（Agent 可读），`mark_secret` 不回收已有副本；
  - “人改了文件、在标记之前”这个窗口在 ADR-173 之前就存在，且长度相同，ADR-173 只是把它整体平移了一段排队时间。
  - 所以这不构成新的暴露类别，违反的是“此后”这一时间承诺，以及在途复制与命令之间缺少顺序规则，可能导致实现分歧。
- **文档位置**：`07` L394-399、L413-416、§7.4.10（L914-968）；`16` L512（判定时机、“同一份内容”、`mark_secret` 的效果）；`06` L876、L878；`04` L1297；`15` ADR-173（“一次读取，两种用途”）。
- **期望的回答形态**：
  - 在 `16` L512（判定时机或“同一份内容”之后）写明在途复制的规则，二选一：
    - 写出前按当前状态复核 `seeded`。已不再 `seeded` 的条目不写出，本次验证回到读取一步重新开始（重新读取、重新算 `envHash`、重新查缓存），保持“查询键 = 槽位内容 = 记录”；
    - 或者明确：分类以读取时为准，`mark_secret` / `remove` 从下一次读取起生效，在途验证照常完成；同时把 `04` L1297、`06` L878 的“此后”改为“从下一次复制起”，并在 `mark_secret` 的确认文案中说明“正在排队的验证仍会使用已读入的副本”。
  - G46(ag) 可加一组：验证排队期间执行 `mark_secret`，按所选规则断言。

### D15 文档一致性与可执行性

**R48-D15-01｜次要**（`extraGlobs` 在 ADR-173 之后没有消费者；“保持 ADR-078 的原义”无所指）

- **问题**：
  - `15` ADR-173 与 `07` L492 写：指纹的 `extra`（`extraGlobs`）“保持 ADR-078 的原义”，不与验证结果绑定。但 ADR-078（`15` L531-536）没有定义 `extraGlobs`；它的定义只在 `07`：
    - VerifyProfile 注释“被忽略但影响结果的文件，如 `.env.test`（§7.3.2）”（L1759）；
    - `worktreeTree` 注释“指向被忽略、但影响结果的本地文件”（L259）。
  - 这个配置原本唯一的用途，就是让结果随这些文件变旧：第 1 轮 R1 提出过“或者删除该选项”，第 4 轮 R4 修正了哈希来源。ADR-173 选择 (b) 之后：
    - `criterion_check` 按 tree 比较，不看 `extra`；
    - 已播种文件的内容已经全部进入 `envHash`，`extraGlobs` 对缓存也是多余的；
    - `Verified` 只看标准结果与阻断命中。
  - 剩下的效果只有一个：其他按“fp 变化”判 stale 的 Fact（`diffstat`、`test_inventory`、`sentinel`、`conflict_forecast`）会因本地文件变化而变旧。这对 `diffstat` 一类没有意义，正文也没有声明它是目的。
  - `09` L381 的学习提议（“验证通过但 Agent 环境失败的差异集中在某个被忽略的文件” → 提议加入 `extraGlobs`，需批准）因此会让人批准一个不改变任何验证行为的配置。
- **为什么是次要**：`criterion_check` 的新鲜度在 `07` §7.3.3 写得明确，不会出现诚实问题。后果是一个形同虚设的配置项与一条（M2 的）学习提议，以及实现者对 `extra` 进入哪些 Fact 的指纹可能各做各的。不涉及安全，不丢数据。
- **文档位置**：`07` L241（`fingerprint = "wt1:" + treeSha [+ ":" + extraSha]`）、L259-265、L492、L1759、L1782；`09` L381；`15` ADR-173（L1788）、ADR-078（L531）。
- **期望的回答形态**，二选一：
  - **删除** `fingerprint.extraGlobs`：理由是已播种文件全部进入 `envHash`，只有已播种文件能出现在槽位中。指纹改为 `wt1:${tree}`（`:weak` 照旧），`09` L381 一行删去或改为提议“把该文件加入本地文件清单”，并登记于 `16` 废弃表；
  - **或者**写明它剩余的唯一用途（例如只用于观测轨的 stale 显示，或只用于某类 Fact），把 `07` L1759 的注释与 `09` L381 的提议条件改为与该用途一致，并把 ADR-173 的“保持 ADR-078 的原义”改为指向这条定义。
