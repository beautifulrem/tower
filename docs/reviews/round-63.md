**新发现 3 条，均为次要**：
- **“未提交的写入” 只认最近一个 seal**（R63-D13-01）：
  - 第一次写入未记账之后，第二次验收若在影子中已生成 seal、却在用户仓库更新 ref 时失败（`06` L920 把 ref 锁、磁盘、仓库不可写列为预期的失败），下一次验收就认不出 Tower 自己写的分支。
  - 结果：另开 `-v<k>`，并显示不真实的 “你的分支已有你的提交”。这正是 ADR-190 声明不会再出现的两种结果。
  - 相邻问题：
    - 同树的验收延续会在用户分支上追加一个树不变的提交；
    - “B 的顶端 == P” 一行的 CAS 失败 “转入下一行”，没有区分 ref 锁与 B 被改动；
    - `06` §6.1.6 的 M1 行没有覆盖延续中的写后窗口。
- **RPC（M2）规则的判别条件照字面会误报**（R63-D5-01）：
  - 每次 RPC 进程启动都会发出 `session_start{reason:"startup"}`；
  - Tower 在 Run 之间自己发出的会话命令也会写带 `reason` 的条目，而且每条命令写两次；
  - 分叉还会把旧条目原样复制到新会话；
  - 会话改变后 adapter 把 `get_entries` 游标重置为 `undefined`，下一次读取会读到上面全部条目。
  - 规则只写 “Run 进行中收到这样的条目”，没有说哪些 `reason` 算数，也没有说怎样判定条目写于本 Run 之内。
- **评审积压 “阻止模式” 的里程碑不一致**（R63-D15-01）：
  - `04` L139、`16` L912、`14` E8（M2 前半）与 W13（只有 “积压提示”）把它放在 M2；
  - `04` L1270 的设置树、`04` §4.4.4 的表、`12` L413 的 M1 状态表、`06` L313–314 与 L931 都没有 M2 标记。

### D5 Agent 架构与 Pi 集成

**R63-D5-01｜次要**（M2：`05` §5.4.5 末段以 “Run 进行中收到带 `reason` 的 `tower.selfcheck` 或 `session_tree` 条目” 判定会话被外部改变。但 Pi 在每次 RPC 进程启动时、以及 Tower 自己在 Run 之间发出会话命令时，都会产生同样的条目；分叉还会复制旧条目；游标重置后这些条目会在下一次 Run 的首次读取中出现。规则没有写出哪些条目算数）

- **问题**：
  - **Pi 的事实**（文首核实）：
    - 每次 RPC 进程启动都会 `rebindSession()`，发出 `session_start{reason:"startup"}`（`rpc-mode.ts:382`、`agent-session.ts:509`），用 `--session` 恢复时也一样。`05` §5.4.4 的 `start` 与 `resume` 都是启动子进程，所以每个 RPC Run 开始时 tower-goal 都会写一条带 `reason` 的 `tower.selfcheck`（`05` L413 的既有复核条目，ADR-190 给它加了 `reason`）；
    - RPC 的 `new_session`、`switch_session`、`fork`、`clone` 各重新绑定两次（`agent-session-runtime.ts:187-194` 一次，`rpc-mode.ts:436-441, 604-628` 又一次），所以 Tower 自己在 Run 之间发出的命令各写两条带 `reason` 的条目；
    - `fork` / `clone` 把路径上的 custom 条目连同原 id 复制进新会话（`session-manager.ts:1632-1748`），较早写下的带 `reason` 的条目也随之进入新会话。
  - **正文**：
    - `05` L546：会话命令完成后，`get_entries` 游标重置为 `undefined`；
    - L548：每个 `turn.end` 才 `get_entries{since}`；
    - 所以 Run 之间写下的、以及分叉复制来的条目，都会在下一次 Run 的第一个 `turn.end` 被 “收到”。
    - L554 的条件只有 “Run 进行中收到这样的条目”，没有说：
      - 哪些 `reason` 算数：`startup` 在每个 Run 开始时必然出现；
      - 以写入时间还是读取时间判定 “Run 进行中”；
      - 复制来的条目怎样排除。
  - **两种照字面的实现**：
    - 按读取时间判定：每个 RPC Run 在第一个回合结束后都被 drain 到 `paused(prepare_failed)`；
    - 实现者自行过滤：有人按 `reason`，有人按条目 `timestamp` 与 `run.started` 比较，有人按 id 是否在 Run 开始时已出现。排除的范围各不相同；例如只按 `reason` 过滤时，Run 中途扩展发起的 `switchSession` 产生的 `resume` 是否算数，取决于过滤表。
- **为什么是次要**：
  - 属 M2，不影响 M1；
  - 误报方向偏严：多暂停，不会放过外部会话改变；`get_state.sessionFile` 的比对仍能发现会话切换；
  - 但这是 ADR-190 为 M2 新写的唯一规则，判别条件是规则的全部内容；照字面实现会让 RPC 模式不可用，各自修补又会得到不同的覆盖范围。
- **文档位置**：`05` L413、L546–548、L551–554（§5.4.5）、L524–535（§5.4.4 `start` / `resume` / `fork` / `navigate` 行）；`15` ADR-190 R62-D5-02 条；Pi `modes/rpc/rpc-mode.ts:313-319, 382, 436-441, 604-628, 639-643`、`core/agent-session-runtime.ts:187-194`、`core/agent-session.ts:509`、`core/session-manager.ts:1290-1300, 1632-1748`、`core/extensions/types.ts:755-761, 855-861`。
- **期望的回答形态**：在 `05` L553–554 补一句判别条件，例如：
  - tower-goal 在条目中写本 Run 的 `runId`（取自 `--tower-config`，每个 Run 一份）与条目所属的阶段；
  - Supervisor 只把满足以下条件的条目视为外部会话改变：`runId` 等于当前 Run、写于 `run.started` 之后、`reason ∈ {reload, new, resume, fork}`，或为 `session_tree`；
  - 进程启动时的 `startup`、Tower 自己在 Run 之间的命令产生的条目、分叉复制来的旧条目都不算；
  - 注明 Pi 对 RPC 会话命令会发出两次 `session_start`，条目按幂等处理；
  - C30 或 RPC 契约测试补一组：Tower 自己的 `fork` 之后开始下一次 Run，不暂停；Run 中途扩展调用 `ctx.newSession()`，暂停。

### D13 隔离、git 与并发

**R63-D13-01｜次要**（`10` §10.6 “未提交的写入” 一行只看 “影子中本 Goal **最近的** seal”。第一次写入未记账之后，下一次验收在影子中已生成新 seal、却在用户仓库更新 ref 时失败，那么再下一次验收就认不出 Tower 自己写的分支：另开 `-v<k>`，并显示不真实的 “你的分支已有你的提交”。ADR-190 声明这两种结果不会出现。另有三处相邻缺口）

- **问题**：
  1. **识别范围只到最近一个 seal**：
     - `10` L606–607：“影子中本 Goal 最近的 seal 没有对应的 `integration.performed`，且 B₀ 或某个 B₀-v<k> 的顶端等于它 → 该分支记为 W”；
     - 写入顺序（`10` L590–594、L618–620）：先在影子中 `commit-tree` 并 `update-ref refs/tower/<goalId>/seal/<n>`，再 fetch 或 CAS 更新用户仓库中的 ref。`06` L920 把 “ref 锁、磁盘、仓库不可写” 列为预期的写入失败，返回 `E_INTERNAL`。
     - 序列（设计层面）：
       1. 已有一次记账的验收（B、P），返工后再次验收；
       2. 按 “B 的顶端 == P” 快进到 S1，事务失败或应用退出，B = S1 成为未记账的写入；
       3. 再返工，再验收：W 行认出 B 并快进，S2 已写入影子，用户仓库的 CAS 因 ref 锁失败，返回 `E_INTERNAL`；
       4. 重试：最近的 seal 是 S2，没有分支顶端等于它，W 行不命中。B 的顶端 S1 ≠ P，落入 L621–623：另开 B₀-v<k>，面板写 “你的分支 <B> 已有你的提交，Tower 未改动它”。这句话不真实：S1 是 Tower 自己的提交。
     - 没有先前验收时，第 4 步落入 L595 “B₀ 已存在而不是 W → B₀-v<k>”，B₀ 上留下一条 Tower 自己写的、不在任何记录中的分支，`integrated` 的观测（`10` L626）也不覆盖它。
     - 这与 `06` L920 “都不另开 `-v<k>`，也不说明‘已有你的提交’”、`04` L543 “重试直接沿用该分支”、ADR-190 R62-D13-01(a) 的结论直接矛盾。
     - 同类：W 行按当前的前缀与标题现算 B₀ 与 B₀-v<k>（`10` L246、L601）。两次验收之间改了 Project 前缀（例如按 `[修改分支前缀]`）或经 `goal.update_meta` 改了标题，同样认不出 W。
  2. **CAS 失败的去向**：
     - `10` L620：“`git update-ref B S P` # CAS：期间 B 被改动则失败，转入下一行”；
     - ref 锁同样使 `update-ref` 失败，而 B 并没有被改动。照字面 “转入下一行” 的实现会另开 `-v<k>`，并对一条没人动过的分支显示 “已有你的提交”；`06` L920 则把 ref 锁归为 `E_INTERNAL`。两处没有写出如何区分（例如失败后重读 B 的顶端）。
  3. **同树的验收延续追加空提交**：
     - ADR-190 让 M1 延续 “先按重新 seal 表写分支”。而 `retry_verify`（`07` L1655）在 `accepted` 中以**同一 pin** 重跑，满足延续时进入 “B 的顶端 == P” 一行；
     - 该行总是 `commit-tree <新 pin 的 tree> -p P`，所以用户分支上会多一个树与 P 相同的提交，并成为 “最近一次验收的 seal”。
     - “树与说明都相同就复用” 只写在 W 行。不变式本来已由 P 的记录满足，这次写入没有必要；实现者会有的写、有的跳过。
  4. **延续中的写后窗口**：
     - `06` L141 的 M1 恢复行写 “Goal 仍在 `in_review`”。但延续写分支时 Goal 在 `verifying`：恢复时由 `06` L122 的 `verifying` 行以同一 pin 重跑，之后经 W 行复用。结果正确，但 M1 行的描述只覆盖 `goal.accept`；
     - `06` L920 的 “其间到达的该 Goal 的其他转移排在本命令的事务之后” 也只写在 `goal.accept` 一句中，延续一句只说 “同样先写分支”。
  5. **测试**：G46(bg)(3) 第三组只测 “返工后再验收” 的快进。没有覆盖同一 pin 重试的复用，也没有覆盖上面的两次失败序列。
- **为什么是次要**：
  - 需要两次失败接连发生，或者两次验收之间恰好改了前缀或标题；
  - 用户自己的提交从不被改写，改动不会丢失（影子、bundle 与另开的分支都在）；
  - 但 ADR-190 用 “这一行先于其他各行判定” 换来了 “不另开 `-v<k>`、不出现不真实的说明” 这个明确承诺，上面的序列使它不成立；CAS 失败与同树延续两处，实现者也会各自决定。
- **文档位置**：`10` L246、L590–595、L601–623、L626；`06` L122、L141、L920；`04` L527、L543；`07` L1637、L1655；`14` G46(bg)(3)；`15` ADR-190 R62-D13-01 条。
- **期望的回答形态**：在 `10` L606–609 唯一定义处改至多一句，`06` L920 引用同一句：
  - **识别**：W = 用户仓库中顶端等于本 Goal 影子中**任一**没有对应 `integration.performed` 的 seal 的分支（按 sha 查找，例如 `for-each-ref --points-at`，不按现算的名字）；有多条时取最近写入的。这样第 1 点的序列与前缀、标题改名都能认出 W；
  - **CAS 失败**：L620 改为 “失败后重读 B：顶端 ≠ P → 下一行；仍等于 P → 按写入失败返回 `E_INTERNAL`”；
  - **同树**：“B 的顶端 == P” 一行之前加一条 “新 pin 的树与 P 的树相同且说明相同 → 复用 P，不写入”（或写明这是有意追加的空提交）；
  - `06` L141 的 M1 行补 “验收延续中同理（Goal 在 `verifying`，按 `verifying` 行重跑后经 W 行复用）”；延续一句引用 `goal.accept` 的事务排序规则；
