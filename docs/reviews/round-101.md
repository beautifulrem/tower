## 1. 总评

**第 100 轮的 6 条条目都按所问关闭**（核对见 §3）：
- 重要条目 R100-D13-01 在唯一定义处与 `10`、`06`、`09`、`13` 的引用处都已关闭；但 `04` 中三处复述漏改，见 R101-D15-01。
- R100-D5-01 (c) 的区域判定新写了一条 “与终端中的 Pi 相同” 的断言，对按模型端点取区域的内置模型不成立，见 R101-D5-01。
- §5 的 9 条观察全部落地。

回应 “偏离与未决” 的判断如下：
- 五条接受；
- 一条接受方向、代价的告知有缺口：**R100-D13-01 以删除关闭整类**。

**对本轮重点问题的回答（不自动删除副本带来的磁盘增长）**：
- **以删除关闭整类，方向成立**。
  - 自 ADR-193 起，“何时可以安全删除人的副本” 每轮都补一个分支（ADR-199/221/222/225/226/227），第 100 轮的重要条目正是第八个。
  - 不再判定之后，`10` L258 的唯一定义只有一句规则，交还、带回、关闭与启动续写都不再有删除前的比较。
  - 评审者逐处核对：`10` §10.2、§10.3.2 删除卫星一行、§10.8.3 第 7 步、§10.8.4 第 2、5、8 步，`06` §6.1.6、§6.4.3 各命令，`09` §9.12.4，`13` §13.11.3。这些位置都不再删除人的副本。
- **与 `13` 的 30 GB 预算一致吗**：
  - 文字上一致。`10` L567、`13` L367、`16` L849 都写明人的工作现场 “不计入 Tower 总占用、从不自动删除、单独计量”。`13` L367 如实写出量级 “约每周 0.5–20 GB，数周内即可超过 30 GB 的总预算”。
  - 但预算的含义随之变了。它原本约束 “Tower 让这台机器用掉多少磁盘”，现在只约束其中由 Tower 回收的部分；剩下那部分没有上限，只能靠人删除。
  - `10` L456 把 “worktree 文件夹蔓延” 列为必须清理的产品理由；ADR-228 对人的工作现场重新引入了这种蔓延。这是一个可以接受的取舍，因为它换来的是不丢人的工作。前提是人能及时看到，而这正是缺口所在。
- **10 GB 时一次 severity 1 提示够不够**：作为一条早期信号，阈值与 “回落后再超过时再提示”（`10` L567）都合理。但它在 M1 中没有呈现面：
  - severity 1 只进入 “重入简报” 与 “站会摘要” 两个批处理通道（`08` L241–L243）；
  - 站会摘要属 M2（`04` L136、§4.9.3 [M2]）；
  - 重入简报按 Goal 呈现，而这条提示是跨 Goal 的。
- **需要磁盘压力路径吗：需要，但只是指向，不是删除**：
  - 可用空间 < 10 GB 时，`10` L452 的磁盘压力顺序只回收 Tower 自己的对象：残留卫星、非永久重放包、`paused` > 3 天的依赖目录、depcache。`ENOSPC` 时 F8（`06` L1197）的横幅建议 “scratch、旧 worktree”。
  - 两处都不提人的工作现场，而它现在是唯一没有上限的消耗者。结果是，压力真正来自保留的副本时，Tower 先删掉自己的证据与依赖，人看到的清理建议也解决不了问题。
  - 见 R101-D10-01。

**ADR-228 的其余结构性写法成立**（§3.3）：
- **AWS 并存**：两者并存时同终端中的 Pi，取原始密钥（`bedrock-converse-stream.ts:162-164, 215-217`）。
- **保留的 profile 名与区域判定时机**：`tower-<hostId>` 不与用户的段同名；区域在每次 `host.spawn` 时判定，用户之后改的区域在下一次 Host 启动时生效。
- **记录的值**：存入密钥库，“重新读取” 替换它们。
- **Azure 与 Cloudflare 的配置变量**：与 `azure-openai-config.ts`、`cloudflare-auth.ts`、`provider-env.ts` 一致。
- **挂死**：专用 Host 中准备阶段不计入。
- **逐次批准的代价**：登记、单独度量、复审线与 M2 决定点。
- **归因表第 3 行**：Host 退出或挂死之后、终止一轮完成之前的写入归 `agent_bg`。
- **复述**：`06` §6.2.4 与 `10` §10.7.1 第 2 步已同步。

**ADR-228 带出、或本轮扫描发现的新问题**：
- **`04` 中三处仍写 Tower 删除人的副本**（R101-D15-01，重要）：
  - `04` L669：“Tower 只在写回成功、且副本内容与交还时相同时才删除它”，正是被删去的删除前比较；
  - `04` L736：执行面表中人工编辑检出的生命周期写 “交还……时按文件同步写回并删除”；
  - `04` L737：检验目录写 “关闭检验或目标验收 / 放弃时删除”。
  - 照 `04` 实现，人新建的被忽略文件随副本删除，即 R100-D13-01 的丢失。
- **Bedrock 区域与 Anthropic 头部令牌**（R101-D5-01）：
  - 只有原始密钥、没有区域时，终端中的 Pi 对内置 `eu.*` 模型取 `eu-central-1`；Tower 按 ③ 写 `AWS_REGION=us-east-1`，并且自己的 `AWS_PROFILE` 关掉了 Pi 的端点固定，请求发往错误的区域。`11` L518 “这与终端中的 Pi 相同” 一句不成立。
  - `ANTHROPIC_AUTH_TOKEN` 是以 Bearer 头部发送的令牌，而 Tower 唯一的注入方式按 API Key 发送。
- **磁盘增长的告知**（R101-D10-01）：见上；另外阈值用的是 `10` L563 声明 “仅用于显示” 的逻辑大小，累积量也没有度量。
- **已脱离的副本比影子与记录活得久**（R101-D13-01）：
  - H/.git 经 alternates 取对象于影子与镜像（`10` L963）。归档或放弃 180 天后影子删除（`10` L462），H/.git 中 “人做的提交” 随之不可读。这只在清除时登记过（`09` L560）。
  - 影子不在时，确认框的 “与最近检查点不同的文件” 与提交数没有定义。
  - “清除全部” 之后，`09` 让人 “在设置的存储面板中删除”，而这时已没有记录可供列出。
- **“使用中” 只在 `delete_kept` 一处定义**（R101-D13-02）：`inspect.bring_back` 仍以 “检验目录存在” 为前置条件，人已选 `[不带回]` 或验收时已脱离的目录也满足它；`delete_kept` 与进行中的接管、打开检验不串行。
- **确认框的 git 求值**（R101-D11-01）：“被 git 忽略的条目（按 git 汇报的路径）” 与 “H/.git 中人做的提交数” 是 Tower 第一次对已脱离的副本求 git 信息。所列目录中有 Agent 写过的卫星与 gitdir 副本，也有人可能运行过 Agent 代码的 H，而 `10` §10.1.2 的唯一加固清单中没有这一上下文。
- **其余复述**（R101-D15-02）：
  - `16` L1122 写 “`discard` 删除人在检验目录中的修改”；
  - `06` §6.4.7 的禁止远程清单漏了 `goal.delete_kept`；
  - `13` L368 的 “同上” 因插入新行而变成 “不计入 Tower 总占用”；
  - `06` L1131 的唯一定义指针过期；
  - `11` L516 的 Host 白名单 “其余一律删除”，没有列出 `05` 与 `06` 都写入 Host 环境的代理、`GIT_CONFIG_*`、端口与 Tower 标识变量。

### D5 Agent 架构与 Pi 集成

**R101-D5-01｜次要**（Bedrock 区域第 ③ 步与 Pi 按模型端点取区域不同，等价断言不成立；`ANTHROPIC_AUTH_TOKEN` 的头部类型没有归类）

- **问题**：
  - **(a) 按端点取区域的内置模型**：
    - `11` L518：“③ 仍没有时补 `AWS_REGION=us-east-1`。这与终端中的 Pi 相同：环境中没有 `AWS_PROFILE` 时 Pi 回落到 `us-east-1`”。ADR-228 (c) 写 “与 Pi 的取法相同”，`16` L723 同。
    - Pi 在环境中既没有区域、也没有 `AWS_PROFILE` 时，对标准 Bedrock 端点的模型**先取模型端点的区域**（`bedrock-converse-stream.ts:201`），只有非标准端点才回落 `us-east-1`（`:203-204`）。内置 `eu.*` 推理配置的端点是 `eu-central-1`（`generate-models.ts:1253-1257`），测试断言这时区域与端点都是 `eu-central-1`（`bedrock-endpoint-resolution.test.ts:113-118`）。
    - Tower 在 “只有原始密钥、没有区域” 时写 `AWS_PROFILE=tower-<hostId>` 与 `AWS_REGION=us-east-1`。两者各自都会关掉 Pi 的端点固定（`:167`、`:1249`），`eu.*` 模型的请求因此发往 `us-east-1`。终端中的 Pi 照常可用，Tower 中失败。
    - 即使去掉 ③，Tower 自己传的 `AWS_PROFILE` 也使 `hasAmbientConfiguredProfile` 为真，不会固定端点；所以这不是删一步就能等价的问题。
  - **(b) 以头部发送的令牌**：
    - Pi 的 Anthropic provider 把 `ANTHROPIC_AUTH_TOKEN` 以 `Authorization: Bearer` 发送（`providers/anthropic.ts:34-40`），存储的或运行时注入的密钥以 `apiKey` 发送（`:30-31`）。
    - Tower 对 API Key 类凭据唯一的提供方式是 `setRuntimeApiKey`（`11` L517；`model-runtime.ts:621-629` 以 `{type:"api_key"}` 同步）。
    - 首次运行 “只取变量名并与 provider 对应”（`05` L489）。把 `ANTHROPIC_AUTH_TOKEN` 对应到 Anthropic 并按 API Key 注入，请求带的是另一种头部。ADR-049 的类型表（`15` L333–L340）与 `11` L518 都没有 “头部令牌” 这一类，“变量 → provider 的对应以各 provider 的 `resolve` 为准” 也没有说明这种情况怎么处理。
- **为什么是次要**：没有机密进入 Agent 可影响的进程，也不丢数据；后果是某些配置在终端中可用、在 Tower 中失败，界面只显示通用的 provider 错误。但 (a) 是一条写错的等价断言，(b) 能导出两种实现：照注入，或判为不支持。
- **后果的类别**：使用欧洲推理配置、又没有设区域的 Bedrock 用户在 Tower 中一个请求也发不出去；经网关以头部令牌认证的 Anthropic 用户同样如此。两者都在首次运行时被标为 “已检测到”。
- **文档位置**：`11` L517、L518；`05` L489、D62（L1448）；`16` L723；`15` ADR-049（L333–L341）、ADR-228 (c)（L4594）；`14` G46 (d)。
- **期望的回答形态**：在 `11` L518 的唯一定义处补两句：
  - 区域一支如实写出差别，或改为等价的取法：
    - 一种写法是：只有原始密钥、没有区域时，终端中的 Pi 按模型端点取区域（内置 `eu.*` 为 `eu-central-1`），Tower 每个 Host 只有一个区域，因此补 `us-east-1`，使用 `eu.*` 模型请在 profile 或环境中设区域；
    - 另一种写法是给出等价的做法（例如这种情形不传 `AWS_REGION`，也不让保留的 profile 计为环境 profile），并引用 `:167`、`:201`、`:1249`；
    - 删去 “这与终端中的 Pi 相同” 一句中不成立的部分。
  - `ANTHROPIC_AUTH_TOKEN` 一类以头部发送的令牌：登记为已知限制（Tower 只按 API Key 注入，请改用 `ANTHROPIC_API_KEY` 或 `pi /login`），或写明 Tower 怎样提供它；首次运行检测到这类变量时如实标注。
  - G46 (d) 补一组：只有原始密钥、没有区域，选 `eu.*` 模型，按所选写期望。

### D10 性能

**R101-D10-01｜次要**（人的工作现场是唯一没有上限的磁盘消耗者，而 10 GB 提示在 M1 没有呈现面，磁盘压力与磁盘满不指向它，阈值用 “仅用于显示” 的逻辑大小，累积量不度量）

- **问题**：
  - **(a) 呈现面**：
    - `10` L567：“合计（逻辑大小）超过 10 GB 时以 severity 1 提示一次，附存储面板的入口”。
    - severity 1 只进入两个批处理通道：重入简报（回到该 Goal 时）与站会摘要（`08` L241–L243）。站会摘要属 M2（`04` L136、§4.9.3 [M2]），重入简报按 Goal 呈现，而这条提示不属于任何 Goal。
    - `08`、`12` 都没有写这条提示出现在哪里。只有镜像增长提示写了 “存储面板 severity 1”（`16` L870）。
    - ADR-228 把这条提示作为无上限增长唯一的刹车，回应也以它为代价的告知。照现在的文字，M1 用户可能永远看不到它。
  - **(b) 磁盘压力与磁盘满**：
    - 可用空间 < 10 GB 时，`10` L452 依次删除残留卫星、非永久重放包与完整验证日志、`paused` > 3 天的依赖目录、depcache，并以 severity 1 通知。`ENOSPC` 时 F8（`06` L1197）停止准入、对活跃 Run 走 drain、数据库只读，L3 横幅的清理建议是 “scratch、旧 worktree”。

    - `10` L456 把 “worktree 文件夹蔓延” 作为清理是产品要求的理由，这一类现在只能由人清理，所以人必须在压力出现时被指到它。

    - `10` L563：逻辑大小 “`du -sk`，仅用于显示”，因为 `du` 会对 APFS 克隆块重复计数。
    - 而 L567 的 10 GB 阈值用的正是逻辑大小。`13` L367 的量级按独占大小给出，依赖目录在 APFS 上 “几乎不占新块”，逻辑上却是每个 0.3–2 GB。阈值因此会远早于 `13` 所暗示的时间越过；这与 L563 的声明相互矛盾。
  - **(d) 度量**：
    - `13` L367 “实测由 M1 自用期回填（`14` E6）”。E6 是 8 小时的性能浸泡（`14` L567–L569），不度量按周累积的目录数与大小，也没有复审线。
    - R100-D8-01 对逐次批准的代价给了单独度量与复审线，这一代价没有对应的安排。
- **为什么是次要**：不丢数据；磁盘满时 F8 停止准入并保护数据库。但 (a)(b) 使 ADR-228 登记的代价实际上不被告知，(c) 的两处文字相互矛盾，实现会分叉。
- **后果的类别**：
  - 人的工作现场在没有告知的情况下累积到磁盘压力或磁盘满；
  - Tower 为此回收自己的非永久证据与其他 Goal 的依赖，之后的重放报告 “不可重放”，依赖要重新下载；
  - 人看到的清理建议对症不上。
- **文档位置**：`10` L452、L456、L563、L566、L567；`06` L1197（F8）；`08` L239–L245；`04` L136、L1285、§4.9.3；`12`；`13` L367；`16` L849、L870；`14` E6（L567）。

### D11 安全与自主度

**R101-D11-01｜次要**（`goal.delete_kept` 确认框的 git 求值没有归入唯一加固清单，所列目录中有 Agent 可控的 git 元数据）

- **问题**：
  - `10` L258：确认框列出 “被 git 忽略的条目（按 git 汇报的路径……）与 H/.git 中人做的提交数”，适用于该段所列的每一种目录。这是 Tower 第一次对已脱离的副本求 git 信息。
  - 所列目录包括：
    - 卫星的 `<goalId>.kept-*` 与 `_gitdirs/<goalId>.kept-*`：都由 Agent 写过。`10` L256 对后者专门注明 “不要以它为 gitdir 运行 git”，理由与 `00` L79 “沙箱外的 git 不得读取 Agent 可控的元数据” 相同。
    - H：`10` L959 写明，人在 H 中运行的准备步骤 “以你的权限运行 Agent 可能改过的代码，它能改动 H 中包括 git 元数据在内的任何文件”。
  - `10` §10.1.2 自称 Tower 执行 git 的 “唯一加固清单”（L44），其中没有 “对已脱离的副本求值” 的上下文。交还与带回只在影子上下文中读 H 的工作树、排除 H/.git（`10` §10.8.4 第 5 步）；而 “H/.git 中人做的提交数” 必须读 H/.git，清单中没有对应的读法。卫星 gitdir 只允许 Tower 自行只读解析普通文件（`10` L226）。
  - 照字面最直接的实现，是在 H 或 `.kept-*` 目录中以其自带的 gitdir 运行 git。这会让沙箱外的 Tower 进程读取并按 Agent 可能写过的配置行事。
- **为什么是次要**：删除由人在本机发起，所列目录已被 S2 与验证器沙箱隔离；但缺的是一条已有不变式在新路径上的落点，实现会分叉，其中一种落到不变式之外。
- **后果的类别**：沙箱外的 Tower 进程在人点击 `删除` 时按 Agent 可控的 git 元数据执行操作；`_gitdirs/*.kept-*` 的 “忽略条目” 与 “提交数” 也没有意义。
- **文档位置**：`10` L44（§10.1.2）、L226、L256、L258、L959；`00` L79；`06` L911。
- **期望的回答形态**：在 `10` L258 的确认框一句加一个括注，并在 §10.1.2 的表中加一行：
  - “不同的文件” 与 “被忽略的条目” 在影子上下文中以临时索引对目录求出（与交还第 5 步同一取法）；
  - “H/.git 中人做的提交数” 由 Tower 自行只读解析 H/.git 的 ref 与提交对象（与 `10` L226 同法），不在其上运行 git；
  - 对 `_gitdirs/<goalId>.kept-*` 与卫星的 `.kept-*` 只列出大小与 “其中一切随之删除”，不求 git 信息。

### D13 隔离、git 与并发

**R101-D13-01｜次要**（已脱离的副本比影子与记录活得久：H/.git 中的提交在影子删除后不可读，确认框在影子不在时没有比较对象，清除之后无从列出）

- **问题**：
  - **(a) H/.git 的对象**：
    - H/.git 的 `objects/info/alternates` 指向影子与镜像（`10` L963）。ADR-228 说 H “原样留在原路径”，并明列 “H/.git 中人做的提交”（`10` L258、L1016）。
    - 影子在归档或放弃 180 天后整个删除（`10` L462），之后镜像只保留保留 ref 可达的对象（`10` L1320）。从这时起，H 中的 git 命令因缺少对象而失败，人做的提交只剩它们自己新写入的对象，无法完整读出。文件本身完整。
    - 这一后果只在隐私清除时登记过（`09` L560 “清除之后其中的 git 命令会因缺少对象而失败”）。按 ADR-228，每次交还都留下一个 H，所以它现在是常规情形，而 `10` §10.2、§10.3.2 的影子删除一行与 Goal 页都没有写。
  - **(b) 确认框的比较对象**：`10` L258 的 “与本 Goal 最近检查点的树不同的文件” 与 “H/.git 中人做的提交数”，在影子已删除或 Goal 已清除时都无从求出。空列表会被读成 “不会丢失任何东西”。
  - **(c) 清除之后的列出**：
    - `09` L560 让清除结果写 “不需要时在设置的存储面板中删除（`goal.delete_kept`……）”，并说 “清除全部” 同样跳过并列出这些目录。
    - 但 “清除全部” 删除 `~/.tower` 中的全部内容，包括数据库；“清除一个 Project” 删除 Project 记录，`<wtRoot>` 也随之不再可知；已清除的 Goal 不在列表中显示（`09` L561）。
    - 存储面板按什么列出这些目录（数据库还是扫描文件系统）、没有 Goal 或 Project 记录的目录是否列出、`goal.delete_kept{goalId}` 对已清除的 Goal 是否可用，都没有写。
- **为什么是次要**：工作树中的文件不丢。但 (a) 使 “H/.git 中人做的提交原样保留” 在 180 天后不成立，且没有告知；(b)(c) 是新命令的未定义分支，实现会分叉。
- **后果的类别**：
  - 人在半年后回到一个保留的副本，其中的 git 历史已不可用；
  - 确认框在影子不在时显示空的 “将丢失的内容”；
  - 清除结果指向一个找不到这些目录的面板，目录在磁盘上成为没有入口的残留。
- **文档位置**：`10` L258、L462、L963、L1016、L1320；`09` L560、L561、L566、L568；`06` L911；`04` L374、L1285。
- **期望的回答形态**：在 `10` L258 的唯一定义处补三句：
  - (a) 二选一：登记 “影子删除之后其中的 git 命令会因缺少对象而失败，文件完整”，并在 §10.3.2 影子删除一行与 Goal 页的列出处同样注明；或在脱离时（或影子删除之前）使 H/.git 自含对象，并写出磁盘代价。
  - (b) 影子或检查点不在时，确认框写 “无法与检查点比较：其中的一切随之删除”，提交数写 “无法读取”。
  - (c) 列出的来源，例如按已知的 `<wtRoot>` 扫描名字形如 `_human/*`、`_inspect/*`、`*.kept-*` 的目录。并写明清除之后（含 “清除全部”）这些目录是否仍可在面板中列出与删除；不能时，`09` L560 的结果文案改为给出路径、请人自行删除。

**R101-D13-02｜次要**（“使用中” 只在 `delete_kept` 一处定义：带回的前置条件仍按 “目录存在”，`delete_kept` 与进行中的接管、打开检验不串行）

- **问题**：
  - **(a) 带回的前置条件**：
    - `06` L918 `inspect.bring_back` 的前置条件是 “检验检出 `<wtRoot>/_inspect/<goalId>` 存在、卫星树等于 pin 的树（以 T_pin 为基线），且无 `human_checkout`”；`inspect.close` 是 “检验目录不存在 → `E_STATE`”（L919）。
    - ADR-228 之前，目录存在就意味着检验打开中、以 `keep` 关闭待处理，或中断。现在已脱离的目录在以下情形之后都存在：`[不带回]`、没有修改的关闭、验收或放弃触发的清理。
    - 于是对人已明确选择不带回的目录，或验收时已脱离的目录，`inspect.bring_back` 的前置条件仍满足。验收之后 T_pin 未变、卫星树仍等于它，带回会使 Goal 离开 `accepted`、以人没有选择带回的改动进入 `verifying`。
    - 而 `10` L258 与 `06` L911 已给出 “使用中” 的定义：`humanCheckout.path`、打开中，或以 `keep` 关闭待处理的检验目录。同一概念在两处的取法不同。
  - **(b) `delete_kept` 与进行中的接管**：
    - `goal.delete_kept` 只以 `E_STATE`（使用中）与 `E_BUSY`（写回进行中）守卫，不持该卫星的 `wtLock`（`06` L911）。
    - 接管在 “先改名、再独占新建、物化、写 `humanCheckout` 的事务” 之间（`10` §10.8.4 第 2–4 步），打开检验在 `inspect.opened` 之前，新目录既不是 “已脱离的副本”，也还不算 “使用中”。
    - 照字面，按旧列表发出的 `delete_kept` 会删除正在物化的新 H 或检验目录，而这一后果没有写。
- **为什么是次要**：两者都由人的显式命令触发；(a) 写回的改动由 `author:"human"` 检查点归因、可以撤回；(b) 被删的是只含 Tower 写出内容的新目录，可以重新物化。但同一概念的两种取法会导出不同的实现。
- **后果的类别**：已验收的 Goal 因一个过期的界面或远程客户端回到验证；接管或打开检验因一次删除中途失败，进入检出丢失的处理。
- **文档位置**：`06` L907、L911、L918、L919；`10` L254、L258、L917–L921、§10.8.4 第 2–4 步；`16` L1122。
- **期望的回答形态**：
  - 把 `10` L258 的 “使用中” 写为唯一定义，`06` L918、L919 的前置条件改为引用它：带回要求检验打开中或以 `keep` 关闭待处理，否则 `E_STATE`；已脱离的目录只能 `删除`。
  - `goal.delete_kept` 持该 Goal 卫星的 `wtLock`，或在接管与打开检验持锁期间返回 `E_BUSY`，与 “写回进行中” 一句并列。

### 不扣分的观察

1. **打包模式下准备阶段的看门狗**：
   - `08` L391 “准备阶段不计入” 对专用 Host 成立。打包模式（K=4，设置项，也是 SP2 不达标时的 M1 默认，`06` L42、L44）中，另一 Goal 的会话创建在共享 Host 中同步阻塞时，已置位 `hostExpected` 的 Goal 的看门狗在 30 s 时判挂死。全局根按 `PackageManager` 实例缓存（`package-manager.ts:2102-2116`），新会话的服务会再查一次。
   - 去向有定义：运行中的 Goal 按 F4，准备中的 Goal 按 F4b 的握手失败。`13` L129 对上下文交接登记了同一点。
   - 宜在 L391 补半句 “专用 Host；打包模式中同一 Host 的其他 Goal 按其看门狗处理”，并让 `08` L363 的 “为该 Goal spawn 的 Engine Host” 也覆盖加入已存在 Host 的情形。
2. **自动改名时仍打开着的编辑器与终端**：
   - 交还之后人可能仍开着 H 的编辑器或终端（`10` L1016 明写写回之后人可能继续保存）。
   - 再次接管时，旧目录被改名为 `.kept-*`，新 H 在原路径建立：
     - 终端的工作目录随 inode 进入 `.kept-*`，此后在其中的修改不会交还；
     - 按路径工作的编辑器的未保存缓冲区写入新 H。
   - 两者都不丢数据，前一类在结果中按路径列出。删除 H 时（ADR-228 之前）这一类已部分存在。
   - 宜在第 0 步信任提示或结果中加一句 “上次的副本已改名为 <路径>；仍打开着它的编辑器与终端请先关闭”，`inspect.open` 同。`goal.take_over` 可远程发起（`16` L1152），这一句对远程触发的改名尤其有用。
3. **E3 复审线的分母**：`14` L542 “加载了 MCP 的目标上 `tool.external` 审批的中位 > 3 条/小时” 引用 §14.6.2 的 “每用户每小时”。分母取全部用户小时，还是只取有 MCP Goal 运行的小时，可相差数倍；“中位” 是对用户还是对周取的，也没有写。`14` L436 的 A 列只写 “按‘注意力’行”，分层另列只在 B 列。复审线是初值，宜在 E3 写明分母。
4. **噪声 Goal chip 的建议**：`08` L270 在 1 小时内桶取空 ≥ 2 次时建议 “合同可能不清晰，或自主度过低（审批过多）”，链接到自主度调整。对加载了 MCP 的 Goal，逐次审批来自级别下限，自主度调整能做的只有 `forbid`。宜在这类 Goal 上改为指向 `11` §11.3.4 “代价” 所列的出口。
5. **归因表第 3 行新窗口的注记**：
   - `10` L396 的注记一列 “由该检测器条目打开期间的 `anomaly{bg_process_survived}` Fact 推导”，而终止一轮完成之前的窗口里可能还没有这条 Fact。
   - 范围内没有确认存活者的 Goal 在一轮结束时照样补 `agent_bg_done`（`06` L145 “什么也没终止时同样补”），这期间的外部写入并入一个作者为 `agent` 的检查点。
