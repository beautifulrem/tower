> **核对依据**：
> - Pi 发布标签 `v1.2.0`（`git -C research/pi-mono show v1.2.0:<path>`）：`core/skills.ts`（`Skill.baseDir`）、`core/resource-loader.ts`（`getSkills()`）、`core/agent-session.ts`（`resourceLoader`）、`core/settings-manager.ts`（`getSkillPaths()`）。`05` 引用的行号与发布版相差不超过 5 行，结论成立。
> - 本机最小核对（git 2.56.0，macOS 默认的大小写不敏感 APFS 卷，在 `/tmp` 中完成并已删除）。只核对 ADR-101 识别机制的前提是否成立，正文只写结论：
>   1. 一个目录含 `HEAD` 与 `commondir`，`commondir` 指向一个真实仓库。目标可读时，`rev-parse --absolute-git-dir` 成功；把目标改为当前用户不可读后，git 只报告通用的“不是 git 仓库”，没有单独的权限错误。也就是说，“读被拒绝”与“确实不是仓库”在输出上无法区分。
>   2. 名为小写 `head` 的文件，加上 `objects/`、`refs/` 目录，被 git 识别为仓库（卷不区分大小写）。
>   3. 先只建 `HEAD`，此时 git 判定不是仓库；之后补上 `objects/`、`refs/`，`HEAD` 的 inode 与 mtime 都没有变，git 的判定变为“是仓库”。
>   4. 对照项（不构成问题）：第 7 轮已核对，Seatbelt 对 `.git` 的大小写变体同样拒绝，本轮未重复核对。
>
> 本文只在设计层面描述问题：涉及哪条边界、需要什么前提、会有什么后果、期望怎样缓解。不包含复现步骤。行号以本轮读到的文件为准。

## 1. 总评

第 8 轮的 16 条大多已经落地：

- ADR-101 改为“名字粗筛 + git 确认”；
- ADR-103/104 把交还时的原因清除、待执行选择与重新入队写成了可实现的规则；
- ADR-105 补齐了带回的崩溃恢复、seal 说明结构与垫片重建；
- M1 顺延 1 周，并预先声明了削减顺序。

本轮没有阻断级问题。新问题集中在三处：

- **ADR-101 的识别并不与 git 等价**：名字匹配没有考虑大小写不敏感的卷；确认结果的缓存键只看 `HEAD`；“读被拒绝即按是仓库”在 git 的实际输出下无法实现。
- **S2 下的增量识别在 `running` 期间没有事件来源**：文件监视只为 `in_review`/`accepted` 定义，而 pin 在 `claimed` 时生成，此前没有全量粗筛。
- **ADR-103 的 run 类范围写得过宽**：异常 `post_settle_activity` 与非阻断的 `policy_wall`/`sandbox_violation` 被列为“须覆盖的阻断项”；对 run 类阻断哨兵，“返工”选项无法解除阻断。

## 4. 追问清单（新增与残留）

编号 `R9-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。

### D3 论证与证据

**R9-D3-01｜次要**（R8-D3-01 的残留）

- **问题**：`05` L572 写“成功即为仓库（与 git 自身判定等价，覆盖 `commondir` 与符号链接 `HEAD` 变体）”，`07` L196 也写“覆盖 `commondir`、符号链接 `HEAD` 等布局变体”。本轮核对显示，在以下两种条件下并不等价：
  - 确认沙箱的读范围小于用户环境中 git 能读到的范围时，git 的输出与“不是仓库”相同；
  - 粗筛按名字匹配，而卷不区分大小写。

  所以“等价”只在以下前提下成立：同一 git 版本、读范围等同于用户环境、名字匹配遵循卷的大小写语义。
- **为什么重要**：这条陈述是 ADR-101 取代固定布局枚举的论据；它在 Tower 环境之外是唯一的兜底。
- **文档位置**：`05` §5.5 L572；`07` §7.3.2 L196；`15` ADR-101 L695–696。
- **期望的回答形态**：
  - 把“等价”改写为带前提的陈述，写明成立条件。
  - 不满足的前提登记为已知差异，并给出补救（与 R9-D11-01 一起回答）。

### D4 领域模型与生命周期

**R9-D4-01｜次要**

- **问题**：ADR-104 的待执行选择有三处语义不完整。
  - **(a) 手动与自动的执行条件不一致**：
    - `06` L779：`resume` 对**当前原因**合法时就按 `pendingHandBack.mode` 执行，不论 `also_applies` 中是否还有其他保留原因；
    - 同一行的自动路径要求 `pause_reason` 与 `also_applies` **都为空**才执行；`03` L85 只写“原因解除或人 `resume` 时”。

    例如当前原因是 `budget_soft_cap`、叠加了一条含 run 类阻断命中的 `sentinel_high` 时，`resume` 会直接执行 `continue_agent` 开出 Run，绕过 `10` L614 “先处置哨兵或保留暂停”的对话框约束。哨兵仍会在 `decide` 中阻断，所以诚实性不受影响，但人会得到一个注定停在 `sentinel_high` 的 Run。
  - **(b) 延后执行时，人的意图从哪里取**：
    - `pendingHandBack` 只有 `{mode, at}`（`02` L148、`16` L29）。
    - `continue_agent` 延后执行时要注入 `tower.handback`，其中含“人写的意图说明”（`05` L1154），对话框里的意图同时写进 seal 说明（`04` L579、`10` L377）。
    - 设计没有写明延后执行时从哪里取这段文本（`HumanDecision{hand_back}` 的哪个字段）。重启之后同样需要这段文本。
  - **(c) `post_settle_activity` 作为保留原因**：`16` L25 把它列为交还时保留的原因，但它的出口是 `resume`（禁用扩展后）或 `retry_claim`（`03` L79）。交还后的 Goal 既没有可宣称完成的提交，“重新做宽限确认”也没有对象；而 `pendingHandBack` 的“原因解除”事件对这个原因并不存在。
- **为什么重要**：这些都是 `transitions.ts` 必须实现的边。(a) 让同一个待执行选择在两条路径上的执行条件不同。
- **文档位置**：`06` §6.4.3 L779、L785；`03` §3.2.1 L79、L85；`02` L148；`16` L25、L29；`05` L1154；`10` §10.8.4 L612–635。
- **期望的回答形态**：
  - (a) 统一为“全部保留原因都解除才执行”。`resume` 只解除当前原因，剩余原因仍按 ADR-084 取最高者。
  - (b) `pendingHandBack` 增加 `noteRef`（指向 `HumanDecision{hand_back}`），或写明从该决定读取意图。
  - (c) 二选一：把 `post_settle_activity` 改为“交还即解除”（扩展问题由 run 类异常与 Needs-You 表达）；或者写明它在交还后的出口。G33 增加多原因叠加与延后执行 `continue_agent` 的用例。

### D7 诚实与验证

**R9-D7-01｜重要**（R8-D7-01 的残留）

- **问题**：ADR-103 引入“run 类阻断命中按 Goal 作用域保持 open，直到 `override_sentinel`”，但各文档对“哪些命中属于这一类”说法不一，其中两种写法会改变既有语义：
  - **(a) 列举与阻断列矛盾**：
    - ADR-103 L709、`06` L785、`10` L612–614、`04` L585 把 `policy_wall`、`sandbox_violation` 列为“须覆盖的阻断哨兵”；
    - 而 `07` §7.10.1 L1278 中，它们的“阻断 in_review”列为**否**，路由是 `stalled`，不是 `sentinel_high`。
  - **(b) 异常 `post_settle_activity`**：
    - 它是 anomaly，§7.10.1 L1279 的阻断列为“是（撤回到 running）”，推导来源为 run。按 `07` L1283 的新定义（Goal 作用域内全部未覆盖的 run 类阻断命中都计入 `blocking`），一个 Goal 只要出现过一次 `post_settle_activity`——按 ADR-025，第一次只是自动撤回、无需人处理——之后每次通过的验证都会进入 `paused(sentinel_high)`，直到人对一条异常做 `override_sentinel`。
    - 这与 ADR-025 的语义相反；`override_sentinel` 是否适用于 anomaly 也没有定义。
  - **(c) `16` L129 写得更宽**：它说 run 类“按 Goal 作用域保持 open，交还不清除，须 `override_sentinel` 处置”，没有限定“阻断”。照此，循环与停滞、`burn_vs_progress`、bash 输出中的密钥等非阻断 run 类命中都要逐条覆盖。
  - **(d) “返工”无法解除 run 类阻断**：`sentinel_high` 的 Needs-You 选项是 `override_and_review`、`rework`、`abandon`（`07` L1343），`03` L74 的出口也含 `request_changes`。对 run 类阻断命中，返工产生的新 pin 仍会被同一命中阻断，Goal 回到 `paused(sentinel_high)`。这是一个必然无效的选项，每轮还消耗预算。
- **为什么重要**：
  - (b) 会让一个本来由系统自愈的异常变成每个 Goal 都要人工覆盖，直接抬高误报，侵蚀 §7.11 的精度目标与“覆盖即留痕”的信号价值。
  - (d) 违反 Needs-You 纪律：每个选项都必须可行。
- **文档位置**：`15` ADR-103 L707–710；`07` §7.10.1 L1278–1285、§7.10.3 L1327、L1343；`16` §16.1.6 L129、§16.1.1 L25；`06` L785；`10` §10.8.4 L612–614、L627–629；`04` L585；`03` L74、L79；ADR-025。
- **期望的回答形态**：
  - 以 `07` §7.10.1 为唯一来源，把“按 Goal 作用域保持 open”限定为“**阻断列为是、类型为 sentinel** 的 run 类命中”（当前只有 `input_mutated_after_gate`）。从 ADR-103 与各处列举中删去 `policy_wall`、`sandbox_violation`。
  - `post_settle_activity` 保持 ADR-025 的语义（撤回或暂停），不进入 `openSentinels`。
  - `16` L129 加上“阻断”限定。
  - run 类阻断命中的 Needs-You 去掉“返工”，或把“返工”定义为同时记录一条带原因的处置。
  - G32 增加对照：一次 `post_settle_activity` 撤回之后，正常通过的验证仍进入 `in_review`。

**R9-D7-02｜次要**

- **问题**：seal 的 trailer 块无条件写入 `Tower-Verified-At: <pin sha>`（`10` L385；ADR-105 L720 写作“验证 pin 与时间”）。但被集成的 Goal 不一定得到了“已验证”：
  - `verified_qualified`（有保留）；
  - `not_machine_verified`，原因可以是 `human_only`、`ecosystem_unsupported`、`submodules_unsupported` 或 `s0_denied`（`07` L1344–1347）。

  一条名为 “Verified-At” 的 trailer 会以用户身份（可能带签名）永久留在用户仓库里。下游的人与工具（发布脚本、审计、PR 机器人）读到的就是“已验证”。
- **为什么重要**：事实与声明分离（README 第 3 点）已延伸到 seal 说明（ADR-105）；trailer 是其中最容易被机器读取的部分，它的取值必须与 Verified 的唯一定义（`07` L1381）一致。
- **文档位置**：`10` §10.6 L382–388；`15` ADR-105 L720；`16` §16.2.6；`14` G30。
- **期望的回答形态**：
  - trailer 改为携带结论标签，例如 `Tower-Verification: verified | qualified | not-machine-verified(<原因>)` 加 `Tower-Pin: <sha>`；或者只在 `label = verified` 时写 `Tower-Verified-At`。
  - `16` 登记取值；G30 增加 `not_machine_verified` 的对照用例。

### D11 安全与自主度

**R9-D11-01｜重要**（R8-D11-01 的残留）

- **问题**：ADR-101 用“名字粗筛 + git 确认”取代了固定布局枚举，方向正确。但本轮核对与审读发现，识别有四处前提缺口。任一缺口都会让 Agent 新造的仓库形态目录**不被确认**，于是不排除、不记 `nested_repo`，按普通内容进入 pin、seal，最终进入用户主检出。在主检出中，用户自己的 shell 提示符或 IDE 的 git（不受 Tower 注入保护，`00` L80 只是“建议”）会把它当作仓库，并读取其中 Agent 可控的配置。这正是 R8-D11-01 想关闭的 T29 一类后果。
  - **(a) 名字匹配与卷的大小写语义**：
    - 粗筛找“名为 `HEAD` 的条目”（`10` L74、`07` L195）。
    - 在 macOS 默认的大小写不敏感卷上，小写 `head` 同样被 git 识别为仓库（本轮已核对）。用户主检出通常也在同类卷上。
    - S2 对 `.git` 有大小写不敏感的拒绝（第 7 轮核对），对 `HEAD` 没有。
  - **(b) 缓存键只看 `HEAD`**：
    - 确认结果按 (路径, `HEAD` 的 inode 与 mtime) 缓存（`10` L74、`13` L312）；S2 的增量只检查“新出现的 `.git`、`HEAD` 名称”（`10` L207）。
    - 先出现 `HEAD`（被确认为“不是仓库”），之后再补上 `objects/`、`refs/` 或 `commondir`：`HEAD` 不变，缓存的否定结论一直有效，增量也不会再触发确认（本轮已核对：此时 git 的判定已变为“是”）。
  - **(c) “读被拒绝即按是仓库”无法实现**：
    - 确认沙箱的读范围限定为卫星工作目录（`10` L74）；
    - `commondir` 可以指向工作目录之外、Agent 可写的位置，例如本 Goal 的 Agent 存储、Agent 临时目录、卫星自己的 gitdir。这些位置在集成之后到 Goal 归档清理之前一直存在。
    - 读被沙箱拒绝时，git 给出的只是通用的“不是 git 仓库”（本轮已核对），所以“因读范围被拒而无法判定 → 按是仓库处理”的保守分支没有可依据的信号。
    - 同类问题：用户环境中的 git 版本比确认所用的更新、能识别某个仓库扩展（`extensions.*`）时，确认失败而用户的 git 成功。
  - **(d) 目录符号链接**：
    - 粗筛不跟随符号链接（`10` L74）。卫星中一个指向卫星外、Agent 可写位置（同上）的目录符号链接，会作为普通符号链接进入 seal；
    - 在主检出中进入该路径时，git 按链接目标判定。
    - 两种检出的信任提示会列出指向目录外的符号链接（`04` L559），但集成前的评审没有对应的确认项——ADR-101 的确认项只覆盖仓库形态目录。
- **为什么重要**：ADR-096 只保护 Tower 构造的环境。对用户主检出，ADR-101 的识别加上集成前的确认项是唯一的防线。四处缺口的前提都是 Agent 在 S2 下本来就能做到的普通文件操作。
- **文档位置**：`15` ADR-101 L693–699；`10` §10.1.2 L74–82、§10.3.1 L207；`07` §7.3.2 L193–202；`05` L572；`06` L222；`13` §13.11.1 L312；`11` T29；`14` G27b；`00` L80。
- **期望的回答形态**：
  - (a) 粗筛的名字比较遵循卷的大小写语义（在大小写不敏感卷上不区分大小写）；或者 S2 同样拒绝在工作目录中创建任何大小写变体的 `HEAD`，并登记兼容性代价。
  - (b) 缓存键改为候选目录中所有与仓库判定相关的条目（`HEAD`、`commondir`、`objects`、`refs`、`config`、`gitdir` 等，不区分大小写）的 stat 汇总；增量对这些名字的出现与变化都触发重新确认。或者否定结论不缓存。
  - (c) 二选一：
    - 粗筛命中且候选中存在 `commondir`，或 `HEAD` 内容形如 ref/对象名时，直接按“是仓库”处理，git 确认只用来排除明显的误报；
    - 或者把确认沙箱的读范围扩到与 Agent 可写根相同，并把“非‘不是仓库’的失败”（包括未知扩展、格式版本）一律按“是仓库”处理。
  - (d) 集成前的评审把“新增或改动的、指向仓库外的符号链接”单列为确认项（指向 Tower 管理的根或 Agent 可写位置的阻断）。
  - G27b 增加四个用例：小写 `head`；先建 `HEAD` 后补 `objects/`、`refs/`；`commondir` 指向 Agent 存储；指向 Agent 存储的目录符号链接。每个用例的通过条件都是“被确认（或被确认项拦下），不进入未标注的 seal”。

### D13 隔离、git 与并发

**R9-D13-01｜重要**

- **问题**：S2 下嵌套仓库识别的时机没有覆盖 pin 的生成。
  - **(a) 增量识别在 `running` 期间没有事件来源**：
    - `10` L207、`06` L222、`05` L572、`13` L312 都写“S2 下以 Supervisor 已有的文件系统监视增量维护”，`06` L222 明确说是“I2 的同一路监视，不另开遍历”。
    - 但这路监视只为 `in_review`/`accepted` 定义（`06` L244、`07` L235、L269、`10` L394）。
    - Agent 恰恰在 `running` 期间写文件。全量粗筛只在 Run 开始前、人工交接前、丢事件或监视降级时，以及 S0 下执行（`10` L207）。
    - 因此 S2 下，Run 中新造的仓库形态目录在 `claimed` 时生成 pin 之前可能根本没被识别：检查点、pin、验证、评审与 seal 都把它当普通内容，不产生 `nested_repo`。
    - 这同时意味着 `external_change`（`03` L80，`running` 中“检测到非 Agent、非 Tower 的工作区改动”）也没有写明监视来源。
  - **(b) 闸口没有强制全量**：`13` §13.11.2 的“永不降级”清单含 `submit`/pin 前的决定性指纹、验收与 seal 的完整重哈希，但不含嵌套仓库识别。
  - **(c) Tower 自己的写回暂停了事件**：
    - `hand_back` 与 `inspect.bring_back` 写回期间，该卫星的事件触发被暂停（`10` L394）；完成后只重算指纹，没有写重新识别。
    - 人在人工编辑检出或检验检出中新建的仓库形态目录，会作为人的改动写回卫星。对人工编辑检出，T1 由 `add -A` 生成（`10` L616）；其中人新建的 `.git` 子仓库会形成什么条目、如何写回，也没有定义（影子侧有 `dropGitlinks`，这条路径没有）。
- **为什么重要**：这是 ADR-101 的执行时机问题。(a) 让 S2 这一默认档位上的识别实际上只在 Run 之间发生，使 R9-D11-01 之外又多出一条“未识别即进入 seal”的路径。
- **文档位置**：`10` §10.3.1 L207、§10.6 L394、§10.7.1 L445、§10.8.3 L580–585、§10.8.4 L616；`06` L222、L244；`07` §7.3.2 L195、L235；`05` L572；`13` §13.11.1 L312、§13.11.2；`03` L80。
- **期望的回答形态**：
  - 定义卫星监视的生命周期：所有存在卫星的非终态都监视，或者明确 `running` 期间的事件来源；事件洪峰的合并规则见 R9-D10-01。
  - 在“永不降级”清单中加入：生成 pin 前、验收与 seal 前，对候选集做一次全量粗筛（或至少对全部已知候选重新确认）。
  - `hand_back`/`bring_back` 完成后执行一次全量识别。从人工编辑检出计算 T1 时同样去除 gitlink，并对人新建的仓库形态目录按“新造”处置。
  - SP6b 增加用例：Run 中途新造仓库形态目录、不触发任何交接，随后 `claimed` → pin，期望得到 `nested_repo` 且 pin 中不含该目录。

**R9-D13-02｜次要**（R8-D13-01 的残留）

- **问题**：
  - **(a) “已跟踪”的判据可被利用**：
    - ADR-102 与 `10` L79 的判据是“**目录中的文件**在 base 中已被跟踪”。它没有要求“该目录在 base 中**已经是仓库形态**”（例如决定仓库判定的条目——`HEAD`、`commondir`、`objects/`、`refs/`——在 base 中已被跟踪）。
    - Agent 可以在任何已有被跟踪文件的目录中补上仓库判定所需的条目，使它变成仓库形态目录。按现行写法，它会被当作“夹具”：无哨兵、进入 pin 与 seal，只剩集成前的一个确认项。
  - **(b) 未改动夹具的排除没有安全收益**：base 中已跟踪、内容与 base 相同的夹具，本来就存在于用户自己的主检出中。把它们排除出两种检出，并不减少用户 IDE 已经面对的风险，却使检验不完整（R9-D8-01b）、无法在“我来改”中修改夹具。
- **为什么重要**：(a) 绕过 `nested_repo`，(b) 让一类真实项目的人工检验失效。两者都是 ADR-102 想要解决的问题的边界。
- **文档位置**：`15` ADR-102 L703；`10` §10.1.2 L76–80；`07` §7.3.2 L200–202；`00` §0.5.1；`14` G29。
- **期望的回答形态**：
  - (a) “已跟踪夹具”的判据改为“在 base 的树中，该目录已被 git 确认为仓库形态”（可在影子中对 base 树一次性计算并缓存）。base 中不是仓库形态、本 Goal 使其成为仓库形态的，按“新造”处理。
  - (b) 内容与 base 相同的已跟踪夹具照常复制到两种检出；只有被本 Goal 修改或新造的才不复制。
  - G29 增加“Agent 在已跟踪的普通目录中补上仓库判定条目”的对照用例。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D5、D12、D16 为 100：本轮在这五个维度上没有找到可追问的实质问题。
  - 其余维度在 92–98 之间。最低为 D11、D13（均为 92），其次是 D7（93）。
- **是否还有可追问的问题：有。**
  - **第 8 轮核验**：共 16 条，已解决 11、部分 5、未解决 0；第 8 轮 lint U1 已解决。
  - **本轮追问**：新增与残留共 **12** 条：
    - 阻断 0；
    - 重要 3：R9-D7-01、R9-D11-01、R9-D13-01；
    - 次要 9：R9-D3-01、D4-01、D7-02、D8-01、D9-01、D10-01、D13-02、D14-01、D15-01。
  - **经最小本机核对的前提问题**（R9-D11-01）：
    - 读被拒绝时，git 的输出与“不是仓库”无法区分；
    - 在大小写不敏感的卷上，小写 `head` 被识别为仓库；
    - `HEAD` 不变而补上 `objects/`、`refs/` 后，git 的判定由否变为是。
- **下一轮建议按以下顺序修订**：
  1. 修补 ADR-101 识别的四处前提缺口，并在 pin、验收、seal 前强制全量识别；定义 `running` 期间的监视来源（R9-D11-01、R9-D13-01）。
  2. 以 `07` §7.10.1 为唯一来源收窄 run 类的范围，`post_settle_activity` 回到 ADR-025 语义，去掉无效的“返工”选项（R9-D7-01、R9-D8-01a）。
  3. 把 ADR-102 的判据改为“仓库形态在 base 中已存在”，未改动的夹具照常复制（R9-D13-02）。
  4. trailer 携带结论标签（R9-D7-02）；统一 `pendingHandBack` 的执行条件（R9-D4-01）。
  5. 处理其余次要条目，并修正削减顺序与关键资源的对应关系（R9-D14-01）。
