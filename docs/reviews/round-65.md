**ADR-192 的主干成立**：
- **签名下的识别规则**（`10` L603–608、L667）：
  - “去掉签名头后与影子中某个 seal 逐字节相同” 与 git 的签名语义一致，本轮已实验确认。
  - 不签名时退化为 “sha 相同”，签名与不签名在同一条规则内。不写回影子，不增状态。这比第 64 轮评审建议的 “S′ 写回影子” 更简单，偏离理由成立。
  - 逐条路径核对，口径一致：
    - **复用**：比较 P 的树与说明。签名在头部，不影响比较。记 `sha = P`。
    - **快进**：P 为签名提交时，先经镜像本地 fetch，影子通过 alternates 可见。镜像 gc 前会同步 `refs/tower-live/<goalId>/*`（`10` L1269、L1274）。新 seal 以 S′ 为父，S′ 因此在镜像中可达，不会被回收。
    - **`-v<k>`、撤销行与验收延续**：都走同一张表。
    - **`integrated` 观测与 squash 的 patch-id**：用 `integration.performed.sha`（S′）。S′ 与 S 同树同父，patch-id 相同。
    - **撤销**：`integration_reverted_seal` 按写入记录判定，口径相同。
    - **M2 推送**：用同一个 sha。
    - **写后窗口**（`06` L141）：S′ 已写、事务未提交时，重试按去掉签名头的规则认出 S′ 并复用。
  - `encoding` 头造成不一致时不写入，方向保守。代价见 §5 观察 9。
- **检出守卫**（`10` L636–641）：
  - 覆盖首次 seal、重新 seal 表各行、验收延续、归档前重写、归档删除与清理，各自的去向都写明。
  - 复用一行不写入，因此不受守卫影响，这一点正确。
  - 与 M2 本地合并（`10` L1144）用同一判定。
  - **已正确处理**：
    - 分离 HEAD 不算检出，与 git 一致；
    - 裸主工作树没有当前分支，与 git 一致；
    - 子模块是另一个仓库，不受影响；
    - `prunable` 的链接工作树仍列出，Tower 不动它，方向保守。
  - **遗漏一种**：git 自己认定为 “正在使用” 的状态还包括某个工作树中进行中的 rebase / bisect，见 R65-D13-01。
- **删除条件**（`10` L437）：
  - 三项同时成立才删，并以 CAS 删除。按分支顶端判定，用户追加的提交不会被删。
  - `abandoned` 行（L439）与 `03` L63 一致；清理不删 `refs/tower/_owner`（L708）；`04` L1277 的设置树已加入该动作。

- **§10.16.3 的已知限制**（`10` L1244）：
  - 窗口写得准确：seal 写入之后、进入 `accepted` 的那次 bundle 完成之前；
  - 后果写得如实：另开 `-v<k>`，方向安全，那句说明此时不真实；
  - L632–633 的 “为真（唯一例外……）” 与之对应。本轮没有找到第二种例外。

**新发现 5 条，全部为次要**。三条出在 Tower 写用户仓库的边界上，两条是文案与措辞：
- **检出守卫漏掉进行中的 rebase / bisect**（R65-D13-01）：
  - 守卫只看 `worktree list --porcelain` 中的 “当前分支”，而 rebase 中该工作树显示 `detached`。
  - 照字面实现，Tower 会快进或删除用户正在 rebase 的分支。git 自己的 `branch -f`、`branch -d`、`fetch` 都拒绝这样做。
  - 后果：用户的 rebase 结束时无法更新分支。不丢数据，但打断用户进行中的操作。
- **签名步骤的等待、失败与锁没有定义**（R65-D13-02）：
  - 签名程序可能等待口令或硬件密钥，而验收延续是在人没有操作时自动发起的。
  - 正文没有写签名在哪把锁内执行、等待多久、取消或超时去向何处。实现会明显分歧：
    - 在 `repoLock` 内等待，会拖住同项目其他 Goal 的准备；
    - 在 `wtLock` 的 30 s 上限内被杀掉。
- **撤销草案没有纳入 Tower 写用户仓库的规则**（R65-D13-03）：
  - `10` L1154 的 revert 草案没有写在哪个上下文中生成（`git revert` 本身需要工作树），也没有写是否签名、是否过检出守卫、写后窗口如何处理。
  - L10 与 §10.6.2 列举 “Tower 写进用户仓库的只有……”，都没有它。
- **同一 pin 的验收延续显示 “已更新本地分支”**（R65-D7-01）：
  - 这一情形按 `10` L622–623 走复用行，不写入。`04` L545 却写 “成功时……`◇ 已更新本地分支`”，界面会说一句不真实的话。
- **“仅保留分支” 一词在删除规则中自相矛盾**（R65-D15-01）：
  - `10` L703、L708 与 ADR-192 写 “‘仅保留分支’……的分支一律不删”。
  - 但 “仅保留分支” 是 M1 唯一的集成模式（L1148），M1 中每个 `integrated` 的 Goal 都属于它。这与同一句的 “由 `integrated` 归档的 Goal 按条件删除” 互斥。本意应是 “验收但不合并而归档”。

每一条都回到正文核对过。R65-D13-01 另用实验确认了 git 的行为，不是推测。

### D13 隔离、git 与并发

**R65-D13-01｜次要**（检出守卫只认 `worktree list --porcelain` 中的 “当前分支”。某个工作树正在 rebase 或 bisect 这条分支时，该工作树显示为 `detached`，守卫放行；git 自己的 `branch -f` / `branch -d` / `fetch` 对这种分支都拒绝写入）

- **问题**：
  - **git 的行为**（本轮实验确认）：
    - git 判定一条分支 “正在使用” 时，除了各工作树的 HEAD，还看该工作树中**进行中的 rebase**（`rebase-merge/head-name` 或 `rebase-apply/head-name`）与**进行中的 bisect**（`BISECT_START` 记录的起始分支）；
    - 而 `worktree list --porcelain` 对这样的工作树只输出 `detached`。
  - **照字面实现**（`10` L636：“该分支是主检出或任一链接工作树的当前分支时”）：用户在自己的检出中 rebase Tower 的分支（例如合入前把它变基到最新 `main`，交互式 rebase 停在冲突处）时，以下操作照常执行：
    - 验收、验收延续或归档前重写对这条分支的快进；
    - 归档删除与清理对它的删除。
  - **后果**：用户 `rebase --continue` 到最后一步时，git 以 rebase 开始时的旧值 CAS 更新分支，失败并报错，用户停在 “rebase 进行中、HEAD 分离” 的状态。bisect 时，`bisect reset` 回到的分支已被移动或删除。
  - **对照**：守卫的设计依据正是 “`update-ref` 不检查检出”（L636）。它要补上的就是 git 自己那层保护，判定范围应当一致。
- **为什么是次要**：
  - 用户的提交与工作树都不丢：rebase 的结果仍在分离的 HEAD 与 reflog 中，工作树、索引与 HEAD 都没有被 Tower 改动；
  - 触发需要 “rebase 或 bisect 进行中” 与 “Tower 写这条分支” 两件事同时发生；
  - 但照正文实现，会打断用户进行中的 git 操作，和守卫要保护的东西同类。修正只需扩大一处判定。
- **文档位置**：`10` L10、L636–641、L1144；`06` L920；`14` G46(bg)(3) 第九组（L133）。
- **期望的回答形态**：在 L636 的唯一定义处把 “被检出” 改为与 git 相同的判定：
  - 判定为任一工作树的当前分支，**或**任一工作树中进行中的 rebase / bisect 的目标分支（主工作树读 `<gitdir>/rebase-merge/head-name`、`rebase-apply/head-name`、`BISECT_START`；链接工作树读 `<commondir>/worktrees/<名>/` 下的同名文件）；
  - 去向与 “当前分支” 相同；面板文字可以是 “分支 <B> 正在 <路径> 中被变基 / 二分，Tower 未改动它”；
  - G46(bg)(3) 第九组补一次 “链接工作树中的交互式 rebase 停在冲突处”，期望该分支不变、用户随后的 `rebase --continue` 成功。

**R65-D13-02｜次要**（签名在用户仓库上下文中运行用户配置的签名程序，它可能等待人的输入：口令、硬件密钥的触摸、系统授权。正文没有写这一步在哪把锁内执行、最长等多久、取消或超时去向何处。验收延续又会在人没有操作时自动发起签名）

- **问题**：
  - **签名一段**（`10` L667）只定义了 “签名结果与 S 不一致” 的去向（`E_INTERNAL{step:"seal"}`）。没有写：
    - **签名失败**的去向：签名程序退出非零、人取消、没有可用的密钥代理。按 `06` L920 “seal 或写分支失败…… `E_INTERNAL`” 可以推断，但签名是此前没有的、会等待人的一步；
    - **等待上限**：`10` L1250–1251 的 `wtLock` 为 30 s（seal 在其保护范围内），`repoLock` 写为 60 s（保护 “集成时的 seal fetch、CAS”）。签名夹在 fetch 与 CAS 之间，正文没有说它在不在锁内、受不受这两个时限。
  - **实现会明显分歧**：
    - 在 `repoLock` 内等待：口令框未处理期间，同项目的镜像 fetch 与其他 Goal 的仓库准备（`06` L319 “镜像 → 项目锁 → fetch”）都被挡住，可能因 `prepare.repoTimeoutMin` 进入 `prepare_failed`；
    - 在 `wtLock` 的 30 s 内被终止：输入口令或触摸硬件密钥稍慢就失败，重试又弹一次。
  - **验收延续**（`06` L920、`07` L1637）：是验证完成后自动发起的，人可能已经离开。正文没有说启用签名的项目是照常签名（弹出提示，等待人），还是直接不延续。
- **为什么是次要**：
  - 不丢数据；签名失败时不写入，方向安全；
  - 但 ADR-192 让 Tower 第一次在一个关键写入步骤中运行可能等待人的外部程序。锁与时限的选择会让不同实现在可靠性上明显不同，其中一种会牵连同项目的其他 Goal。
- **文档位置**：`10` L52、L667、L1250–1251；`06` L319、L920；`07` L1637；`04` L545；`13` L305。
- **期望的回答形态**：在 L667 的唯一定义处补一句：
  - 签名在影子 seal 完成之后、**不持有** `wtLock` 与 `repoLock` 时进行，只有随后的 CAS 取 `repoLock`；
  - 签名有单独的时限（例如 120 s），失败、取消或超时都是 `E_INTERNAL{step:"seal", reason}`，面板写 “签名未完成：<原因>”，并给出 `[重试]`；
  - 验收延续二选一，写明：
    - 照常签名，失败按已有规则不延续、回到 `in_review`；
    - 或启用签名的项目一律不自动延续（更保守）。

**R65-D13-03｜次要**（撤销合入时写进用户仓库的 revert 草案分支，没有纳入 Tower 写用户仓库的规则：生成上下文、签名、检出守卫与写后窗口都没有写；`10` L10 与 §10.6.2 的 “Tower 写进用户仓库的只有……” 也不含它）

- **问题**：
  - **生成方式**（`10` L1154）：写的是 “生成 `git revert -m 1` / `git revert <squash>` 草案提交在新分支 `<prefix>/revert-<goalId>`”。
    - `git revert` 需要工作树与索引；
    - 用户主检出不能用（L10 “不 checkout 用户主检出”）；
    - 在用户仓库中临时加一个链接工作树，又会改动用户仓库的 `worktrees/` 元数据；
    - 正文没有写应在影子或镜像中以 `merge-tree` 加 `commit-tree` 生成、再写入。
  - **要撤销的对象**：fast-forward 合入时是 S′ 本身；merge 合入时是合并提交（`-m 1`）；squash 时是 squash 提交。后两者的 sha 不在任何记录中，`local_merged{seal}` 只记 seal。
  - **与 ADR-192 的关系**：
    - 启用签名的项目中，草案是否签名，正文没有写；
    - 检出守卫只列举了 seal 分支的写入与删除；草案是新分支，守卫在这里实际不起作用，但 “已存在时加 `-<k>`” 之后的写入同样应走 CAS 创建；
    - 写后窗口（`06` §6.1.6 只有 M1 验收一行）：草案已写、事务未提交时，Goal 仍在 `integrated`，重试会再建一条 `revert-<goalId>-2`。
  - **列举不全**：`10` L10、L697、L703 的表，以及 `06` L1114、`11` T5（L648）都列举了 Tower 写进用户仓库的 ref，都没有草案分支。因此它何时删除（或一律保留）、清理是否触及，没有定义。
- **为什么是次要**：
  - 撤销合入是宽限期内、由人发起的低频操作；
  - 草案保留在用户仓库中方向安全，重复草案不丢数据；
  - 但 “在用户检出中执行 `git revert`” 这种自然读法会违反 L10，正文没有排除它。
- **文档位置**：`10` L10、L697、L703、L708、L1154；`06` L141、L922、L1114；`03` L61、L159；`11` L648；`16` L287。
- **期望的回答形态**：在 `10` L1154 的唯一定义处补三句：
  - **生成**：在影子中以 `merge-tree --write-tree --merge-base=<被撤销的提交> <baseTip> <被撤销的提交的第一父>` 得到树，`commit-tree -p <baseTip>` 生成草案，按 §10.6 的签名规则签名，以 `update-ref <分支> <草案> ""` 创建。被撤销的提交取 “base 中第一个包含该 seal 的提交”（ff 时即 seal 本身）。

  - **不扣分的观察**：
    1. **守卫与写入之间的竞态**：读 `worktree list` 与 CAS 之间，用户恰好检出该分支，守卫拦不住。git 自己的 `branch -f` 也有同样的窗口，可以不改，或在 L636 登记一句。
    2. **`newBranch:true` 的说明可能过时**：`10` L637 写确认后 “面板说明改为同一句‘正被检出’”。人在两次请求之间已切走分支时，这句话不再为真。另外，服务端是否校验 “上一次确实返回了 `branch_checked_out`” 没有写。建议确认时重读一次，只在仍被检出时显示这句，否则写 “按你的选择写入新分支”。
    3. **M2 恢复行的旧识别规则**：`06` L133 `integrating：seal 步骤` 写 “分支上是否已有 Tower 身份提交、trailer 块含 `Tower-Goal`、且树等于已验证 pin”。这与 ADR-191/192 的 “只带 trailer 不算”、`10` L168 的 “seal 使用用户身份” 不符。该行随 M2 生效（L149），建议 M2 设计时改为引用 `10` §10.6 的识别规则。
    4. **“只有 fetch 来的 seal” 的措辞**：`10` L668、`11` T5（L648）、T26（L669）写的是用户仓库只接收 “集成时 fetch 来的 seal（先对象后 ref）”。ADR-192 之后，签名时改为在用户仓库中 `commit-tree` 再 `update-ref`，删除用 `update-ref -d`。“先有对象、再写 ref” 的性质仍然成立，只是措辞落后，建议改为 “fetch 来的，或签名时在用户仓库上下文以 seal 为模板生成的”。
    5. **签名程序的登记**：`11` §11.6.4 列举了在 GitRunner 沙箱之外运行的例外（LFS 获取），没有列出 “用户仓库上下文中由 git 启动的签名程序”。它与 `10` L52 “用户的配置是可信输入” 一致，不构成冲突，建议加一行指向 `10` §10.6。
    6. **性能预算**：`13` L305 只有 “fetch 进用户仓库 < 100 ms”。守卫读取与去签名比对都是毫秒级，可以并入该行；签名时长取决于用户的程序，建议注明 “签名不计入预算”，并指向 R65-D13-02 的时限。
    7. **`backlog` 出口表**：`08` L509 的 “越过” 没有 M2 标记，而条目定义 `08` L297 写 “单次越过（……M2：仅阻止模式）”。建议补 “（M2）”，并把这张表纳入 lint (z′)。
    8. **存储面板的动作名**：`10` L446 写 “清理全部已归档”，`04` L1277 写 “清理工作目录 · 清理 Tower 引用”，`10` L1278 与 `16` L813 另有 “清除早于 N 天的重放包”，`04` 的树中没有。建议统一名称并补全。
    9. **`encoding` 不一致的出路**：用户设置了非 UTF-8 的 `i18n.commitEncoding` 并启用签名时，每次验收都返回 `E_INTERNAL{step:"seal"}`。正文没有给面板写出路，例如 “关闭本项目的签名，或去掉该设置”。另一种做法是在签名命令上以 `-c i18n.commitEncoding=UTF-8` 覆盖：S 的说明本来就是 UTF-8，这样不改变任何字节。二者选一写明即可。
    10. **归档前重写的映射**：`06` L920 写 S′ 已被回收时 “以对应的影子 seal 重新签名后写入”。但 `integration.performed` 只记 S′ 的 sha，S′ 已不存在时无法去掉签名头来找到对应的 seal。建议写明映射：取影子中树等于最近一次验收 pin 的树、n 最大的 seal。另外，重签得到的 S″ 不等于记录中的 sha。归档是终态，没有后果，可以注一句。
    11. **影子删除后的清理**：归档 180 天后影子被删除（`10` L1268），此后 “清理 Tower 引用” 已无法按识别规则核对分支顶端，只能保留，原因写成 “顶端不是 Tower 的汇总提交，可能含你的提交”。方向安全，但原因不准确。建议另列一个原因：“无法核对（审计数据已过保留期）”。
