## 1. 总评

**第 103 轮的 7 条条目都按所问关闭**（核对见 §3）：
- 7 条都在唯一定义处落地，引用处改为引用。
- 其中三处修法本身带出新的分支：
  - **R103-D5-01**：改问 Pi 的 `checkAuth` 是对的，但同时带出两个问题：
    - 探查只在 Host 中定义，首次运行与模型选择器的标注没有写由哪个进程求出，而 `checkAuth` 的结果依赖所在进程的环境与命令缓存（R104-D5-01）；
    - ADR-231 新写明 “每个 Host 一个 `ModelRuntime`”，没有处理扩展注册的 provider：探查运行时看不到它们，而它们在 Host 的运行时中跨 Run、跨 Goal 保留（R104-D5-02）。
  - **R103-D5-02**：`NODE_EXTRA_CA_CERTS` 必要，但不充分。ADR-231 引来作依据的 `EnvHttpProxyAgent` 只在 Pi 的 CLI 中安装，SDK 嵌入的 Host 中，代理变量本身就不起作用（R104-D5-03）。
  - **R103-D6-02**：F8 的解除写成 “只有 `app_quit` 一个原因的 Goal 按 §6.1.4 第 5 项解除（与重启 Tower 的结果相同）”，与第 5 项本身、与 “只重启 Supervisor 也算一次启动”（ADR-207）都不一致（R104-D6-01）；只读期间进行中的验证没有去向（R104-D6-02）。
- §5 的 11 条观察中 10 条完全落地；观察 8 在 `05` L475 留下一处 “Azure 配置目录等”（本轮观察 7）。

**对本轮重点问题的回答**：

- **环境一类的结果按 “没有” 处理：接受**。
  - Host 环境中没有任何模型密钥（`05` L472 的封闭列表），`checkAuth` 的环境一类结果只可能来自 ⑦ 由 Tower 传入的变量，如 Bedrock 的 `AWS_PROFILE`。
  - Bedrock 的判定中 `AWS_BEARER_TOKEN_BEDROCK` 先于 profile（`amazon-bedrock.ts:64` 先于 `:65-70`），回应举的 “令牌与 profile 并存” 一例成立。
  - 唯一的例外是没有 `key`、只带配置的存储条目，属于手工编辑的少见配置，记为观察 3。
- **依赖 Pi 的 `source` 标签：接受，附一条观察**。
  - `stored credential` 与 `configured API key` 两个字符串都在 v1.2.0 中（`provider-composer.ts:441`、`:446`、`:451`）；OAuth 为 `{source:"OAuth", type:"oauth"}`，正文按 `type` 判定，是对的。
  - 没有 `models.json` 覆盖的内置 provider，标签来自各 provider 自己的 `resolve`（`ai/src/auth/helpers.ts:21`、`anthropic.ts:31`、`amazon-bedrock.ts:62, 69`、`google-vertex.ts:72, 85`、`cloudflare-auth.ts:50`），不经 `provider-composer.ts`。D57 的升级复核范围宜包括它们（观察 5）。
- **磁盘满沿用 `app_quit`：接受这一取舍，解除的写法不成立**。
  - 不新增暂停原因成立：drain 与原因合并都用已有规则（`06` L90–L96、L146），恢复出口与 `app_quit` 相同。
  - 回应如实登记的缺口成立：“最后一个 Run 的 `run.ended` 写不进、Supervisor 又在恢复之前重启时，卡片只能写 `应用退出`”。
  - 但 F8 的解除只对 “只有 `app_quit` 一个原因” 的 Goal，而第 5 项对任何暂停中的 Goal 都移除 `app_quit`；“Supervisor 其间重启时保持 `paused(app_quit)`” 与 ADR-207 “只有 Supervisor 重启……同样算一次启动” 相撞（R104-D6-01）。
- **探查运行时的代价与副作用：成立，记一条观察**。
  - 不联网、不刷新 OAuth、不加载扩展、不启动子进程。
  - `AuthStorage` 的构造在文件修订变化时于锁内同步重读，最多忙等约 200 ms（`auth-storage.ts:81-95`、`:97-115`）。`auth.json` 不存在时会建出 `{}`（`:75-79`），这与 Host 自己的运行时、终端中的 `pi` 相同，不是新的副作用。
  - 读取在锁内进行（`:402-440`），“不会读到写了一半的文件” 成立。
  - 回应写的 “只读本地 `models.json` 与内置目录” 略弱于实际；正文没有这句（观察 2）。
- **`auth.json` 中的 `!` 命令在 Host 中执行：可以接受，已写明**。
  - 它是你自己的 Pi 配置中的命令，终端中的 `pi` 在请求时执行同一条；ADR-230 起 Tower 不注入时，Pi 在请求时本就执行它。
  - 执行它的是 Tower 自己的可信进程，环境是白名单，不经 Agent 可写的位置。
  - `11` L517 写明了 10 s 时限与 “在该 Host 进程内缓存到退出”。
  - 命令结果按进程缓存（`resolve-config-value.ts:10`），所以每个 Host 进程只在第一次检查时执行一次，不是每个 Run 一次。
  - 没写的是：执行是同步的，会阻塞 Host 的事件循环；失败的结果同样被缓存。阻塞上限 10 s，低于看门狗的 30 s，不会误判挂死（观察 1）。
- **磁盘满的自动解除与其他暂停原因**：见 R104-D6-01。阈值本身成立：
  - 触发是 `ENOSPC`，解除要可用空间 ≥ 2 GB，磁盘压力是 < 10 GB（`16` L852），有回差，不会紧密循环；
  - 与启动自检的 “剩余空间 ≥ 2 GB”（`06` L1181）一致。

**ADR-231 的其余写法成立**（§3.3）：
- `$VAR` 条目判为没有并照 ADR-049 导入，消除了与类型表的冲突；
- `models.json` 一层；
- 按 Host 的范围与打包模式的如实写法；
- Run 中途 `/logout` 与 F7 的新检测键（`model-runtime.ts:676` 经 `lazy.ts` 成为流的错误）；
- 读不出时按 “没有” 处理；
- `NODE_EXTRA_CA_CERTS` 的取值、排除与 `mcpBaseEnv`；
- `hostExpected` 的置位条件；
- F8 的写入次序、只读期间的 `E_STATE` 与横幅视觉；
- `inspect.open` 按状态判定；
- 租约下的标注与 `E_STATE`；
- `06` §6.2.4 只留引用；
- 工具链变量的取值来源。

**本轮扫描发现的新问题**（全部为次要）：
- **首次运行与模型选择器的标注由哪个进程求出没有写**（R104-D5-01）。
- **每个 Host 一个 `ModelRuntime` 与扩展注册的 provider**（R104-D5-02）：探查看不到它们；在打包或跨 Run 保留的 Host 中，它们作用于 `noExtensions` 的会话。
- **SDK 嵌入的 Host 中，代理变量不使模型请求经过代理**（R104-D5-03）。

  - 但 ADR-231 只定义了一种求值：“每次 `host.spawn` 与每个 Run 创建会话之前，Host 新建一个……探查运行时”。首次运行发生在任何 Host 之前；模型选择器显示时也未必有 Host。
  - `checkAuth` 的结果依赖所在进程：
    - `$VAR` 取的是该进程的 `process.env`（`core/resolve-config-value.ts:88-89`）；
    - `!` 命令在该进程中以它自己的环境执行，结果按进程缓存（`:10`、`:185-216`）。
    - ADR-230 用的 `readStoredCredential` 只是读文件，在哪个进程中做结果都一样；改为 `checkAuth` 之后不再如此。
  - 照字面，实现会分叉：
    - 在 main 或 Supervisor 中建探查：`$VAR` 按 Tower 自己的环境解析。从 Dock 启动时这个环境与 Host 的白名单都不同，结果可能相反。用户的 `!` 命令还会在一个正文从未说过会执行它们的进程中运行。
    - 为首次运行启动一个 Host：没有写。
    - 模型选择器显示最近一次 Host 检查的结果：没有写，也没有 “尚未检查” 的显示。
- **为什么是次要**：不涉及机密进入 Agent 可影响的进程，不丢数据；模型请求实际用哪份凭据仍由 Host 中的检查决定。但标注说的 “Tower 用它” 可能与 Host 实际所用的不同，而这正是 ADR-230/231 要让用户看清的一件事。
- **后果的类别**：首次运行写 “Tower 用你的 pi 配置”，第一个 Run 却注入了导入的密钥，或者反过来；用户的 `!` 命令在 Tower 的另一个进程中多执行一次，环境不同。
- **文档位置**：`11` L517；`05` L489；`04` L1458–L1459；`05` §5.10 登录前提（L1343）。
- **期望的回答形态**：在 `11` L517 的唯一定义中补一句，写明首次运行与模型选择器的标注取自哪里。例如：
  - 由 Supervisor 以 Host 环境的同一白名单启动一次只做检查的 Host，用后退出；
  - 或模型选择器显示该 provider 最近一次 Host 检查的结果，首次运行之前写 `将在第一次运行时确定`。
  - 同时写明 `!` 命令只在 Host 中执行。

**R104-D5-02｜次要**（每个 Host 一个 `ModelRuntime` 与扩展注册的 provider：探查看不到它们；它们在 Host 的运行时中跨 Run、跨 Goal 保留）

- **问题**：
  - **(a) 探查的范围**：
    - 每个会话的扩展在创建时把注册的 provider 写进传入的 `modelRuntime`（`core/agent-session-services.ts:158-181`）。
    - `ModelRuntime.create` 只装内置 provider 与 `models.json`（`core/model-runtime.ts:216-268`），所以探查运行时看不到它们：
      - 扩展新建的 provider，`checkAuth` 返回 `undefined`（`ai/src/models.ts:688`）；
      - 扩展以同名覆盖内置 provider、带了自己的密钥或 OAuth 时，探查按内置的判定。
    - 后一种情况下，探查判为 “没有”，Tower 注入导入的密钥；覆盖作为存储凭据交给扩展的 `resolve`（`core/provider-composer.ts:459-464`）。终端中，扩展用它自己的凭据；Tower 中，用的是 shell 的密钥，发往扩展配置的端点。“用哪份凭据、由谁计费与终端相同” 对这类配置不成立，正文也没有登记。
  - **(b) 生命周期**：
    - 这些注册一直保留在该运行时中，直到显式 `unregisterProvider`（`core/model-runtime.ts:891-903`、`:928-957`）。
    - ADR-231 把 “每个 Host 一个 `ModelRuntime`” 写为定义（`11` L517），而 `noExtensions` 按会话决定：清单确认之前与 `riskTier=high` 时为真（`05` L352、L481 “这些只决定每个会话的 `noExtensions`……Host 不因它们重启”）。
    - 打包模式（`06` L42；SP2 测得 p95 > 120 MB 时是 M1 的默认值，`16` L877）下，`riskTier=high` 的 Goal 可以与加载了用户扩展的 Goal 共用一个 Host。前者的模型请求会经过后者的扩展注册的 provider，扩展代码因此收到前者的完整对话上下文。
    - 同一 Goal 跨 Run 保留的 Host 上，`noExtensions` 在两个 Run 之间变化时也是如此。
    - 正文对打包模式只登记了 “一个 Goal 的扩展崩溃会连带同一 Host 中的其他 Goal”（`06` L44）。
- **为什么是次要**：
  - 这些代码只来自你确认过清单的用户扩展，不是 Agent 可影响的进程，也不向 Agent 交出机密；
  - Agent 不能调用 provider，它不是 `riskTier=high` 要关掉的那类沙箱外工具；
  - 不丢失人的工作。
  - 但 “`riskTier=high` 时用户扩展不加载” 在打包的 Host 中只对会话的工具与钩子成立，对模型请求的路径不成立，正文没有写这条边界；(a) 又使 ADR-231 自称的 “与终端相同” 在一种已支持的配置下不成立。
- **后果的类别**：
  - 用扩展覆盖内置 provider 的用户，Tower 中的花费落到 shell 中那份密钥的账户，请求发往扩展的端点；
  - 打包模式下，高风险 Goal 的对话内容经过另一个 Goal 加载的扩展代码，而界面说该 Goal 不加载扩展。
- **文档位置**：`11` L517；`05` L352、L481、L486、D57（L1443）；`06` L42、L44；`16` L877；`11` §11.8.2。
- **期望的回答形态**：在 `11` L517 “范围” 一句后补两句：
  - (a) 探查只覆盖内置与 `models.json` 中的 provider；扩展注册或覆盖的 provider 不注入导入的密钥（或如实登记差别）。
  - (b) 写明运行时与扩展注册的关系。可以是 “会话结束时移除该会话的扩展注册的 provider”；或 “打包模式只合并 `noExtensions` 相同的 Goal”；或登记为打包模式的已知限制，写进 `06` L44 与设置页的同一句注明。

**R104-D5-03｜次要**（SDK 嵌入的 Host 中，代理变量不使模型请求经过代理；正文引作依据的是 Pi CLI 的行为）

- **问题**：
  - `05` L474：Host “**直接**使用用户代理（ADR-079）：模型请求……都如此”；企业 CA 一句写 “模型请求经 undici 的 `EnvHttpProxyAgent` 发出，`core/http-dispatcher.ts:81-100`”。ADR-231 的 Pi 核实同引此处。
  - 这几行原文无误，但 `configureHttpDispatcher` 只在 Pi 的 CLI 路径上被调用（`cli/setup.ts:12`、`main.ts:597`、`:875`、`interactive-mode.ts:2063`）。它不从 `index.ts` 导出，包的 `exports` 只有 `.` 与 `./rpc-entry`。Pi 的 `httpProxy` 设置也只在 `main.ts:596`、`:874` 应用。
  - Tower 以 SDK 在自己的 Host 中嵌入 Pi，不经过这些入口。`packages/ai/src` 中只有 Bedrock 自己按代理变量建 agent（`api/bedrock-converse-stream.ts:226-227`）；其余 provider 用全局 `fetch`，而 Node 的全局 `fetch` 默认不读代理变量。
  - 所以照正文把代理变量放进 Host 环境，Bedrock 之外的模型请求与 HTTP 类 MCP 连接不经过代理。
  - 各文档都没有写 Tower 的 Host 自己安装代理感知的分发器；Host 环境的封闭列表中也没有让 Node 读代理变量的开关。
- **为什么是次要**：失败明确可见，不丢数据，也不放宽任何沙箱。但它使一类已声明支持的配置（企业上游代理，ADR-067/079）在 M1 中不可用，与 R103-D5-02 同类；R103-D5-02 补的 CA 变量在这类网络中因此还不够。照正文实现正是这个结果，不需要实现者犯错。
- **后果的类别**：
  - 只能经代理出网的网络中，Tower 的模型请求全部失败，而终端中的 `pi` 正常；
  - 允许直连的网络中，模型流量绕过企业代理，与用户的终端不同；
  - 用户在 Pi 设置中写的 `httpProxy` 在 Tower 中不生效。
- **文档位置**：`05` L474、L472 ⑤；ADR-079；`15` L4761（ADR-231 的 Pi 核实）；`00` §0.5.1；G46 (d) 第九组的 CA 一组（`14` L134）。
- **期望的回答形态**：在 `05` L474 “代理” 一行写明 Host 怎样让模型请求经过代理。例如：
  - Host 启动时自己安装一个读代理变量的全局分发器（与 Pi CLI 的 `configureHttpDispatcher` 同一做法，并写明它是 Tower 的代码、随 Pi 升级复核）；
  - 或在 Host 环境中加入让 Node 读代理变量的开关，并写明所需的 Node 版本；
  - 二者之一。另写明 Pi 设置中的 `httpProxy` 是否读取。G46 (d) 的 CA 一组改为 “只能经代理出网” 的网络，以覆盖这一点。

### D6 系统架构与可靠性

**R104-D6-01｜次要**（F8 的解除只对单一原因的 Goal，与 §6.1.4 第 5 项、ADR-207 不一致；卡片 `释放空间后自动恢复` 在这些分支上不成立）

- **问题**：
  - **(a) 多原因的 Goal**：
    - `06` L1197：“本次由 F8 暂停、只有 `app_quit` 一个原因的 Goal 随之按 §6.1.4 第 5 项解除（只在 `resumeOnLaunch` 打开时，与重启 Tower 的结果相同）”。
    - 但第 5 项（`06` L101）在启动时从任何暂停中的 Goal 移除 `app_quit`，“解除后按统一规则——剩余原因非空则保持 `paused`”，不限于单一原因。
    - drain 期间到达的请求并入 `reasons`（`16` L30），所以 F8 的 drain 可以得到 `{app_quit, budget_hard_cap}` 或 `{human, app_quit}`。
    - 照 F8 的字面，这些 Goal 的 `app_quit` 在空间恢复之后留下，“与重启 Tower 的结果相同” 不成立。优先级 `human` > `app_quit` > `budget_hard_cap` 下：
      - 前者显示的仍是 `app_quit`，卡片写 `已暂停 · 磁盘已满 · 释放空间后自动恢复`（`12` L432，依据是最后一个 Run 的 `outcome_reason`），这个承诺永远不会兑现；
      - 后者在人继续之后，留下一个过时的 `app_quit`。
  - **(b) 只重启 Supervisor**：
    - 同一行：“这一集合只在 Supervisor 进程内，Supervisor 其间重启时它们保持 `paused(app_quit)`，由人 `继续`”；G35e (q) 也这样断言（`14` L120）。
    - 但 Supervisor 每次启动都跑中间状态检查（`06` L116）；ADR-207 规定 “只有 Supervisor 重启、main 一直在运行的恢复同样算一次启动”（`08` L393，`06` L148 依此区分两种原因）。所以 `resumeOnLaunch` 打开时（默认），重启后的 Supervisor 按第 5 项移除 `app_quit`。
    - 数据库所在的卷仍满时，这次写入失败，结果未定义。只有 worktree 所在的卷满时，写入成功，新进程又不记得 “停止准入”，这些 Goal 被准入，再次 `ENOSPC`，再次进入 F8。两种情形都与正文所写不符。
    - G35e (q) 把两个卷都写满，所以碰巧通过。
  - **(c) 卡片**：(b) 中的 Goal 最后一个 Run 的 `outcome_reason` 仍是 `disk_full`，卡片照写 `释放空间后自动恢复`，正文却说它们要由人继续。
- **为什么是次要**：不丢数据，Goal 停在 `paused`，人可以继续；需要磁盘满再加多原因或 Supervisor 重启这一前提。但这是新写的解除规则与它所引用的规则之间的直接冲突，照字面实现会违反 “与重启 Tower 的结果相同” 这一句，卡片也会给出不兑现的承诺。
- **后果的类别**：释放空间之后，部分 Goal 的卡片一直写 “将自动恢复” 却不恢复；Supervisor 崩溃恢复后，Goal 在磁盘仍满时被准入，反复进入 F8。
- **文档位置**：`06` L1197、L101、L116、L146–L148；`08` L393；`16` L30；`12` L432、L529；`04` L1516；`14` L120（G35e (q)）。
- **期望的回答形态**：在 `06` L1197 的 “解除” 一句改两处：
  - “本次由 F8 暂停的 Goal 都按 §6.1.4 第 5 项移除 `app_quit`（剩余原因非空则保持暂停）”，去掉 “只有一个原因” 的限定；
  - 写明 Supervisor 在只读期间重启时，启动检查先复查可用空间：不足 2 GB 时重新进入 F8，不按第 5 项解除、不准入；足够时与正常启动相同。
  - `12` L432 的卡片只在该 Goal 将被自动解除时写 `释放空间后自动恢复`，其余写 `已暂停 · 磁盘已满`。G35e (q) 补一组多原因，并把 Supervisor 一组改为只写满 worktree 所在的卷。

**R104-D6-02｜次要**（只读期间进行中的验证与准备阶段没有去向）

- **问题**：
  - F8 只定义了准入、活跃 Run 的 drain 与 UI 命令（`06` L1197）。
  - `verifying` 的 Goal 没有 Run，不在 drain 中：
    - 它的验证照常进行，`verify.result` 写不进只读的数据库；
    - 槽位本身也可能遇到 `ENOSPC`。
  - 中断的验证只有一个重跑点：应用退出时取消的验证，“在启动时以……同一个 pin 重跑”（`06` L101、L122；`03` L97 “verifying 不进入这两个暂停”）。F8 的解除明确 “不需要重启 Tower”，所以结果没写进去的验证在解除之后没有出口。实现会在 “丢弃并重跑”“结果留在内存中补写”“等下一次启动” 之间分叉。
  - 测试命令自身因 `ENOSPC` 失败时，是记为标准失败（计入返工）还是验证环境错误，没有写。
  - 准备阶段（`preparing_since`）的 Goal 同样如此：`prepare_failed` 或 `run.started` 写不进去。
  - G35e (q) 只覆盖运行中的 Goal。
- **为什么是次要**：不丢失人的工作，验证从不可变的 pin 重跑是幂等的；但新写的 “不需要重启” 使这一分支从 “下次启动兜底” 变成没有出口，且照字面无法判断哪种实现正确。
- **后果的类别**：
  - 空间恢复之后，Goal 停在 `verifying` 直到人重启 Tower；
  - 或磁盘满导致的测试失败被算作 Agent 的返工。
- **文档位置**：`06` L1197、L101、L122；`03` L97；`07` 验证结果的判别；`14` L120（G35e (q)）。
- **期望的回答形态**：在 `06` L1197 补一句。例如：
  - “进入只读时，进行中的验证与应用退出时一样取消，Goal 保持 `verifying`；恢复可写时以同一 pin 重跑；`ENOSPC` 期间结束的验证不计结论”；
  - 准备阶段中的 Goal 按 F4b 的同一出口在恢复可写时补写。
  - G35e (q) 补一组 `verifying`。

### D8 注意力与交互

**R104-D8-01｜次要**（`12` 的 “同一时刻至多一个自动出现的覆盖层” 比 `08` 更严，两处相撞）

- **问题**：
  - `12` L528：“多个自动覆盖层（应用级简报、单目标简报、自动诊断、断点提示条）的优先级与互斥由 `08` 定义；本文只规定：同一时刻屏幕上至多一个自动出现的覆盖层，被压后的覆盖层不丢失，在侧栏顶部以一行入口保留。”
  - `08` L691（规则 1）：“同一时刻至多一个‘整页或浮层’覆盖层（优先级 2–4）；提示条（1、5）可以与之共存，但同一时刻至多一条提示条，L4 替换 L3”。
  - 前者把提示条也算作覆盖层，并规定至多一个；后者允许一条提示条与一个浮层同时出现。`12` 先说由 `08` 定义，又自己写了一条与之相反的规则。
  - 照 `12` 实现，重入简报打开时，L4 或 L3 的提示条会被压到侧栏的一行入口中；照 `08`，它们照常出现。
- **为什么是次要**：被压的提示条不丢失，侧栏有入口；`08` 是定义处。但两处给出相反的规则，实现会分叉，而被影响的恰是最需要人立即看到的那一级提示。
- **后果的类别**：人从离开状态回来、简报打开时，看不到正在等决定的 L4 提示条。
- **文档位置**：`12` L528；`08` L691（§8.x 覆盖层规则 1）。
- **期望的回答形态**：`12` L528 改为只引用：“同一时刻的数量与共存规则见 `08`（至多一个整页或浮层，提示条可与之共存）”，删去 “本文只规定” 的一句；或写明此处的 “覆盖层” 不含提示条，并把 “断点提示条” 从括号中移出。

### 不扣分的观察

1. **`!` 命令的同步阻塞与失败缓存**：
   - `auth.json` 的 `!` 命令以同步的 `execSync` 执行（`resolve-config-value.ts:185-196`），第一次检查时最多阻塞 Host 的事件循环 10 s。打包模式下，同一 Host 中其他 Goal 的心跳随之推迟，可能出现 15 s 的 `◇` 提示，但低于 30 s 的挂死判定。
   - 失败的结果（`undefined`）同样缓存到进程退出（`:208-215`，`:214` 不区分成败）：你在终端中解锁密码管理器之后，已在运行的 Host 仍判为 “没有”。
   - `models.json` 中 `!` 形式的 `apiKey` 每次请求都执行，不缓存（`provider-composer.ts:467` → `resolveConfigValueOrThrow`）。
   - 宜在 `11` L517 “10 s 时限” 后补半句 “同步执行；失败的结果同样缓存”。
2. **探查运行时的副作用**：
   - 文件修订变化时，构造中会在锁内同步重读，最多忙等约 200 ms；终端正在锁内刷新时，读取可等待锁。`auth.json` 不存在时会建出 `{}`，与 Host 自己的运行时相同。
   - 都在 120 s 准备时限之内。回应的 “只读本地 `models.json` 与内置目录” 略弱，正文不受影响。
3. **没有 `key`、只带配置的存储条目**：
   - Bedrock 的存储条目只带 `env.AWS_PROFILE` 时，Pi 先看环境中的 `AWS_BEARER_TOKEN_BEDROCK`（`amazon-bedrock.ts:64` 先于 `:65-70`）。终端中 shell 有令牌时用令牌；Tower 的探查看不到令牌（它只经运行时注入），判为 `stored credential`、不注入，用的是 profile。
   - Vertex 的存储 ADC 配置与 shell 的 `GOOGLE_CLOUD_API_KEY` 同理（`google-vertex.ts:71-72, 85`）。
   - `/login amazon-bedrock` 存下的是不带 `env` 的条目（`:49-52`），所以只在手工编辑时出现。宜在 `11` L518 “少见配置” 一句登记。
4. **`!` 命令在 Tower 中失败、在终端中成功时**：Tower 注入导入的密钥，终端用命令给出的密钥，可能是不同的账户。正文写明了 Tower 的行为，但首次运行与模型选择器不标注这一差别；宜按 `ANTHROPIC_AUTH_TOKEN` 的写法加一句标注。
5. **D57 的标签依赖**：
   - 没有 `models.json` 覆盖的内置 provider，`source` 来自各 provider 自己的 `resolve`（`ai/src/auth/helpers.ts:21`、`anthropic.ts:31`、`amazon-bedrock.ts:62, 69`、`google-vertex.ts:72, 85`、`cloudflare-auth.ts:50`，经 `models.ts:679-680`），不经 `provider-composer.ts:441/446/451`。
   - 宜把它们列入 D57（`05` L1443）的升级复核范围。
6. **`11` L517 “`models.json` 中为该 provider 配了 `apiKey` 时不注入” 略宽**：`$VAR` 形式而 Host 中没有该变量时，`check` 返回 `undefined`（`provider-composer.ts:447-449`），Tower 照 ADR-049 导入该变量并注入，结果与终端相同。宜与 `auth.json` 的 `$VAR` 一句同样写出。
7. **残留与措辞**：
   - `05` L475 仍写 “`GOOGLE_APPLICATION_CREDENTIALS`、Azure 配置目录等”（第 103 轮观察 8），唯一定义在 `11` L518，不影响实现；宜删去，并在 `16` §16.1.13 补登这一写法。
   - `05` L1354 的确认卡片说 “扩展与 MCP 服务器只看到……工具链变量只有 JAVA_HOME、……PNPM_HOME……”，但 `mcpBaseEnv` 不含 ④（`05` L455、第 103 轮回应观察 8），MCP 服务器看不到 `PNPM_HOME`。宜把 MCP 与扩展分开写。
8. **CA 的两个边缘**：
   - S0 中代理变量原样透传给 bash，`NODE_EXTRA_CA_CERTS` 却不进入（`05` L474），S0 下 Agent 的 npm 一类请求在 TLS 拦截的代理后失败；
   - 企业根证书装在 macOS 钥匙串而不是文件中时，Node 要另一个读系统证书的开关，它不在 Host 环境的列表中。
   - 宜在 `00` §0.5.1 S2 一行旁登记这两种情形，以及 “指向 Agent 可写位置时不传入”（`00` L113–L114 没有写这一排除）。
9. **租约过期而未接管的窗口**：`10` L259 的条件是 “仍在租期内”，之后写 “租约过期并由本机接管之后照上一句”；过期到接管之间，`06` L184 只写 “询问人是否接管”，没有写 Project 是否仍只读、目录怎样标注。对方已 24 h 没有续租，风险小；宜写明这一段按只读处理。
10. **F8 的几处呈现**：
    - `12` L529 横幅的 `释放空间后自动恢复` 没有 `resumeOnLaunch` 关闭时的写法；它说的是 Tower 自己的恢复，影响小。
    - `04` L1516 的卡片文字没有关闭时的变体（`12` L432 有）。
    - `02` L394 `outcomeReason` 的举例没有 `app_quit`（`16` L115 有），只是举例。
    - 只读期间，Host 的事件与持久化的心跳写不进，Host 中的缓冲增长；Run 已被中止，有界。
    - 可用空间 ≥ 2 GB 时就恢复准入，而磁盘压力是 < 10 GB，填得快的负载可能多次进入 F8。每次只中止 Run，检查点保留工作，可以接受。
11. **`14` L399 的 QA 周次**：“各线的 QA 都在第 31–32 周结束，第 33–34 周是完整的 2 周冻结前缓冲”。设计线需要 29.03 个工作周，QA 延入第 33 周 0.03，缓冲相应为 1.97 周。余量 0.97 已反映这一点，只是这句与甘特图的 “QA（31–32）” 略粗。
12. **应用级横幅在 `04` 中的位置**：横幅不在 `04` §4.3.1 的外壳线框与 §4.17.3 的焦点模型中，`打开存储面板` 链接的 Tab 次序与它相对 §4.3.3 标题栏的位置没有写。`12` L529 已定义一次 `assertive` 读屏与无动画，其余一位称职的实现者会同样处理。
