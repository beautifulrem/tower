## 1. 总评

ADR-158 方向正确：如实承认 macOS 上无法阻止同一用户的进程互相观察，并按“闸门失败”设计。Pi 依赖（D57）与源码一致，排期算术全部成立。

R32 的 8 条中 4 条已解决，4 条部分解决。

新增 9 条（重要 3、次要 6），集中在 ADR-158 引入的三处新面：
- **机密改为文件注入**：验证器沙箱对 Tower 数据目录的读规则从未定义；`06` 仍写“不写入 `~/.tower` 下的任何文件”；默认的文件注入会让按惯例读取环境变量的测试拿不到值，而且界面不作任何说明。
- **T33 的不变式**：“Tower 不把机密放进任何环境”不成立。MCP 服务器的授予变量与 `secrets.access` 仍在环境中，前者没有登记。
- **新命令与新规则的语义**：`goal.base.choose` 没有持久化，也没有接进 `baseTip`；获取没有上限，也没有并发规则；“无法确认”在全量扫描中的去向没有定义。

### D4 领域模型与生命周期

**R33-D4-01｜次要**（项目级事实的归属；`base_fetch_failed` 的显示生命周期；卡片清单缺项）

- **问题**：
  1. **归属**：`Fact.goalId` 是必填字段（`02` L369 `interface Fact`）。但 `remote_credential_blocked{remote}` 是项目级判定（`10` L82–84）：

     - 一个项目下多个 Goal 同时命中时，应当记一条还是每个 Goal 各记一条，没有写。
  2. **生命周期**：
     - `10` L105 规定卡片第 5 行只显示最新的一条 base 类 Fact，集合是 `base_advanced`、`base_unchanged_nonancestor`、`base_diverged`；

     - 它何时消失（下一次获取成功？Goal 进入 `integrated`？）没有写。
     - `04` L1448 在凭据被拒时也显示同一句，但凭据被拒时不会发生获取，也就没有 `base_fetch_failed`。这句提示的事实来源没有写。
  3. **清单缺项**：
     - `04` L229 卡片第 5 行的提示清单没有 `base 已变化，但不是在原来的基础上前进` 与 `无法获取远端 base`；
     - `12` L660 的词表没有后者。
- **为什么重要**：
  - 事实没有确定的归属，实现者只能随意挑一个 Goal，或者绕过 `NOT NULL`。
  - “无法获取远端 base”没有消失规则，可能在获取恢复后仍然留在卡片上，与诚实语法中“提示引用当前事实”不符。
- **文档位置**：`02` L369（`interface Fact`）、L398–403；`10` L82–84、L101、L105；`04` L229、L1448；`12` L660。
- **期望的回答形态**：
  - 写明 `remote_credential_blocked` 的写法：对每个受影响的 Goal 各记一条，在它下一次需要获取时记录；或者 `Fact.goalId` 对这一 kind 可空，并在 `06` 的 `CHECK` 中列出例外。二者取一。
  - 把 `base_fetch_failed` 加入 `10` L105 的集合，或者单列它的消失条件，例如同一远端下一次获取成功即不再显示。
  - 凭据被拒时，Goal 卡片的提示引用 `remote_credential_blocked`。
  - `04` L229 与 `12` L660 补齐两条提示。

### D6 系统架构与可靠性

**R33-D6-01｜次要**（“无法确认”在全量扫描中的去向；重启清理没有进程树来源）

- **问题**：
  1. **去向不明**：
     - ADR-158 规定“环境读取成功但为空”与“读取失败”同样视为无法确认（`10` L416，`06` L192）。
     - `06` L141（启动恢复表）与 L194（崩溃恢复）仍写“读不到环境 → 只生成提示（Needs-You severity 1），不发信号”。
     - 令牌全扫描遍历同一用户的全部进程，而其中每个 Apple 平台二进制（用户自己的 shell、`sleep`、系统工具）的环境都“成功但为空”。照字面实现，重启清理会对它们逐个生成提示。
     - 正文只说“无法确认不当作没有令牌”，没有说“无法确认且不在进程树中”的进程该怎样处理：忽略、提示，还是计入存活者？
  2. **进程树的来源**：
     - `10` L415 说 ② 重启清理也“从这些直接子进程出发，取进程树”。
     - 但直接子进程的记录在 Host 的 `exec` 内存中。按 ADR-142 的约定，“持久化的只有令牌”（`10` L414）。
     - Supervisor 或 Host 崩溃后，这份记录已经没有了，原来的子进程也已被 `launchd` 收养。
- **为什么重要**：
  - 第 1 项会让实现者在每次重启时制造大量无意义的注意力条目，违背 Needs-You 纪律；或者各自发明过滤条件。
  - 第 2 项是一个写在规则里、却无法实现的步骤。
- **文档位置**：`06` L141、L192、L194；`10` L414–417、L419；`11` L351。
- **期望的回答形态**：
  - 写明：在全量扫描中，“无法确认”的进程一律不发信号、不生成提示，只有进程树中的成员才参与终止与存活判定。`06` L141、L194 的“读不到环境 → 提示”限定为进程树中的成员。
  - 写明：重启清理只按令牌枚举（进程树不可得），脱离进程树的平台二进制在重启后同样属于登记窗口 (d)。或者把直接子进程登记为可持久化的数据并说明代价。二者取一。
  - G35c 增加一组：重启后，用户自己的若干 `/bin/bash` 与 `/bin/sleep` 进程存在，期望不生成任何提示。

### D7 诚实与验证

**R33-D7-01｜重要**（默认文件注入让按惯例读取环境变量的测试拿不到机密，结局可能是虚假通过或无法转绿，且界面不说明）

- **问题**：
  - ADR-158 把验证器机密的默认注入方式改为 `<NAME>_FILE`（`07` L696，`11` L400，`16` L83），`04` L1092 写明默认方式“不加标注”。
  - 但测试与被测代码读取机密的普遍惯例是读环境变量 `<NAME>`。默认方式下，这个变量不存在。
  - 耦合保护（`07` L698）又把这些测试强制列为 protected，Agent 不能修改它们去读 `_FILE`。
  - 结局有两种，都不会被现有规则拦下：
    1. **运行时跳过**：测试在缺少机密时跳过（常见写法），其余用例通过。`verdictOf`（`07` L757–758）只在 `total = 0` 或 `passed = 0` 时判 `vacuous`，合同没写 `minTests` 时判 `pass`。依赖机密的检查从未执行，标准却显示通过。静态的 `skippedDeclared` 比较 base 与 head，两边都缺机密，没有差异。
    2. **红灯无法转绿**：测试因缺少机密而失败。base 试运行（`04` L1088）把它当作能证明完成的红灯，Agent 无论怎样改都转不了绿，只会消耗返工次数，最终进入 `verify_failed_limit`。
  - 改为 `env` 才能工作，而 `env` 带风险标注。用户不知道默认方式需要测试配合，也就不知道自己需要做这个选择。
- **为什么重要**：
  - 第 1 种结局是 Fact/Claim 语法中的虚假通过：标准行显示 ✓，实际上关键断言没有运行。
  - 第 2 种结局浪费 Agent 的预算，还把环境问题误当成 Agent 的失败。
  - 带机密的标准属于 M1（R1-D7-03）。默认值决定了大多数用户的实际体验。
- **文档位置**：`07` L693–702、L757–758；`04` L1088、L1092；`11` L400；`16` L83；`14` G46(b)。
- **期望的回答形态**：
  - **批准时提示**：合同批准时，对声明了机密的标准，静态检查其 TestPathSet（耦合保护已经要解析出这个集合）中是否引用 `<NAME>` 或 `<NAME>_FILE`：
    - 只引用 `<NAME>` 时，在标准行显示 `◇ 测试读取环境变量 <NAME>，默认的文件注入不会提供它`，并给出两个选择：改为 `secretsVia: "env"`（带风险标注），或者人自己修改测试；
    - 两者都没有引用时，显示“无法确认测试如何读取机密”。
  - **结果处理**：带机密且 `secretsVia: "file"` 的标准，若该次运行中注入的文件从未被打开，在结果上标 `◇ 机密文件未被读取`，并且不计为能证明完成的通过。验证器可以检查文件的访问时间，或在删除前检查是否打开过。或者规定这类标准必须设 `minTests`。二者取一。
  - **用例**：G46 增加一组，测试只读 `process.env.<NAME>` 且缺失时跳过，期望出现上述提示，结果不被呈现为干净的通过。

### D11 安全与自主度

**R33-D11-01｜重要**（Tower 数据目录中的机密文件：谁能读、放在哪、是否进备份，都没有定义；与“只存密钥库”冲突）

- **问题**：
  1. **读规则**：
     - ADR-158 及补记 2 把三类机密以 0600 文件放进 Tower 数据目录：验证器机密（每条标准一份）、只有原始变量时的云凭据原文，以及 M2 RPC 的 `auth.json`。
     - 它们的保密依据只写了一句“Agent 沙箱对 `~/.tower/**` 读拒绝”。
     - 但读这些文件的是验证器。验证器在槽位中以 S2 运行 Agent 写的代码（`07` L702 第 4 条已承认被测代码能读取注入的机密）。验证器 S2 的读规则在全部文档中都没有定义：`07` §7.4.4 的“文件系统（S2）”一行只列写允许与写拒绝，`16` §16.8 只列包管理器相关的路径。
     - 两种实现都有问题：
       - 沿用 Agent 的读拒绝：G46(b) 的“标准照常通过”不可能成立；
       - 不拒绝：一个 Goal 的验证运行中，被测代码能读到同时进行的其他标准、其他 Goal 的机密文件，以及云凭据原文。
  2. **与既有规则冲突**：`06` L1038 规定“provider 凭据和工具令牌只存在系统密钥库中（ADR-033），不写入 `~/.tower` 下的任何文件”。ADR-158 没有声明修订 ADR-033、ADR-049。
  3. **位置与备份**：
     - 验证器机密文件与云凭据文件的路径没有写。`06` §6.6 的目录树中没有对应目录。
     - 云凭据文件是长期存在的。若不在 `tmp/`，它就不在备份排除之列（`06` L1036 一带），原始密钥会以明文进入系统备份。
- **为什么重要**：
  - 这是 ADR-158 新建的明文机密落点，同时关系到功能（验证器能否读到）与保密（谁还能读到）。
  - 云凭据原文通常有很大的权限，经由被测代码或备份泄露的后果重。
  - 实现者没有规则可依，而两个自然的选择一个让功能失效，一个让保密失效。
- **文档位置**：`15` L1362、L1379；`07` L696–702、§7.4.4（L708–721）；`11` L398、L400；`06` L233、§6.6 目录树（L1000–1025）、L1036、L1038；`16` §16.8；`14` G46(b)(d)。
- **期望的回答形态**：
  - **验证器的读规则**：在 `11` §11.6.2 或 `07` §7.4.4 写明验证器 S2 的读规则：
    - `~/.tower/**` 读拒绝；
    - 例外只有“本次运行、本条标准”的机密文件（按精确路径加入读允许）；
    - 其他槽位与其他 Goal 的 `_verify/**` 读拒绝。
  - **目录**：在 `06` §6.6 的目录树中给出两类文件的目录。验证器机密放在随标准结束删除、启动时清空的目录；云凭据文件放在加入备份排除的目录，并写明它在何时生成、何时删除，以及凭据变化后怎样重写。
  - **ADR 关系**：`06` L1038 改为与 ADR-158 一致，ADR-158 标注 Amends ADR-033/049。
  - **用例**：G46 增加两组，期望都被沙箱拒绝：
    - 两个 Goal 同时验证带机密的标准，一方的被测代码尝试读取另一方的机密文件；
    - 被测代码尝试读取云凭据文件。

**R33-D11-02｜重要**（T33 的不变式与实际不符：MCP 授予变量没有登记；`secrets.access` 前后矛盾）

- **问题**：
  1. **MCP 授予变量**：
     - T33 的缓解写“Tower 自己不把凭据或密钥放进任何参数或环境”（`11` L336、L566，`10` L121）。
     - 但 SDK 下，Tower 自己的 `createTransport` 启动每个 stdio MCP 服务器，环境中含该服务器在 `mcp.json` 中声明的 `env` 与用户的显式授予（`05` L387，C21，`11` L398）。这正是 MCP 服务器访问令牌通常所在的位置。
     - 这些服务器多为非平台二进制。按 ADR-158 的事实，它们的环境对同一用户的任何进程可读，包括本 Goal 与其他 Goal 的 Agent bash。
     - R32-D11-01 第 3 项点名了这一类，但 T33 的残余里没有它，`11` L398 只把它放在 T28（MCP 服务器能读文件）下。
  2. **`secrets.access` 前后矛盾**：
     - `15` L1362 的标题是“验证器注入的机密与 `secrets.access`：默认改为文件注入”；
     - `11` L401 仍写“经 `spawnHook` 注入环境变量”，审批卡片写明“可能被读到”。
     - 这里文件注入本来就行不通，因为 Agent 的 bash 读不了 `~/.tower/**`。
     - C29(b)（`05` L1406）说唯一例外是 `secretsVia:"env"`，没有列 `secrets.access`。
     - `04` 中没有这张审批卡片的文案，G46 也没有对应的用例。
- **为什么重要**：
  - 第 1 项是一个常见配置下的真实暴露：用户只授予某个 MCP 服务器的令牌，可以被任何并行的 Agent 读到，而威胁表告诉用户“残余只来自你自己的其他进程”。
  - 按评审规则，“已登记、已评级”的残余才算已处理，这一类没有登记。
  - 第 2 项让实现者在三处规则之间无从选择，C29(b) 在 `secrets.access` 被批准时会失败。
- **文档位置**：`11` L336、L398、L401、L566；`10` L120–121；`05` L387、L1406（C29）、C21；`15` L1362；`04`（审批卡片）；`14` G46。
- **期望的回答形态**：
  - T33 的缓解改为如实的说法：“Tower 不把它自己持有的机密放进参数或环境；例外是 `secretsVia:"env"`、`secrets.access` 单次注入与 MCP 服务器的环境”。
  - T33 的残余列出 MCP 一类并评级。
  - 在清单确认卡片上写明“macOS 上，此服务器环境中的变量可被同一用户的其他进程（含 Agent）读到”。如有可能，提示用户改用服务器支持的文件或钥匙串方式。
  - `15` 的 ADR-158 第 4 项把 `secrets.access` 从“默认文件注入”中拿出，与 `11` L401 一致。C29(b) 列出这一例外。
  - `04` 给出审批卡片的文案。
  - G46 增加两组：`secrets.access` 卡片的文案；MCP 服务器授予变量的标注。

**R33-D11-03｜次要**（凭据判定只看 URL；git 同样会放进子进程命令行的其他认证类值没有判定，也没有登记）

- **问题**：
  - ADR-158 拒绝带凭据 URL，理由是 git 会把 URL 放进传输辅助进程的命令行。
  - Tower 照常使用用户配置中的全部认证类键（`10` L68：`credential.*`、`core.sshCommand` 等）。其中有两类值，git 同样会作为子进程命令行的一部分启动，与 URL 属于同一类：
    - 以 `!` 开头的内联 credential helper：本机 git 2.56 以 `/bin/sh -c` 启动整段文字，平台二进制的命令行对同一用户可读；
    - 写进 `core.sshCommand` 的口令参数。
  - 用户把令牌字面写进这些值时，Tower 自动触发的获取会让它在并行 Agent 运行期间出现在命令行中。
  - 凭据判定（`10` L77–80）不检查它们，T33 也没有登记这一类。
- **为什么重要**：
  - 这与 ADR-158 拒绝带凭据 URL 的理由完全相同，处理却不一致。
  - 这类配置不如带凭据 URL 常见，后果也与用户自己执行 `git fetch` 时相同，所以定为次要。
- **文档位置**：`10` L68、L76–80；`11` L373、L566；`16` L487。
- **期望的回答形态**：二者取一。
  - 把判定扩展到这两类值：对内联 helper 的文字与 `core.sshCommand` 按 `11` §11.7 的模式与熵规则检查，命中时按带凭据的远端处理，并显示同一张卡片；
  - 或者在 T33 中如实登记为残余，写明理由（与用户自己执行时相同），并在首次添加项目时提示。
  - G45(f) 相应加一组。

### D13 隔离、git 与并发

**R33-D13-01｜次要**（分叉时 `baseTip` 的返回值未定义；`goal.base.choose` 不落库，也不接进 `baseTip`）

- **问题**：
  1. **返回值**：`baseTip` 的取值规则（`10` L129–135）在分叉时只写了“不自动选择、`baseCommit` 不变、记 Fact”，没有写函数返回什么。但它是 `integrated` 观测与 M2 Q2 `newBase` 的唯一来源（L143–147）。
  2. **选择的持久化**：
     - `goal.base.choose` 只记事件 `goal.base.chosen{side}`（`06` L850，`16` L281）。
     - `02` 与 `06` 都没有保存这一选择的字段，`baseTip` 的规则也不读取它。实现者只能从事件日志临时推算。
  3. **“直到下一次分叉”**：
     - 分叉的两侧在用户重新获取之前一直保持分叉。每次获取之后，`baseTip` 都会再次判为分叉、再记一条 `base_diverged`。
     - 选择对哪一对提交有效、何时失效，无法判定。
  4. **边界**：
     - 没有分叉时调用 `goal.base.choose` 的结果（`E_STATE`？）没有写；
     - 选择属于“该 base”还是“该 Goal”没有写：同一项目中以同一 base 运行的多个 Goal，是否需要各自选择？
- **为什么重要**：
  - G45(c) 第四、五组的期望“此后的前进提示与 `integrated` 观测以所选一侧为准”在现有规则下无法实现。
  - 分叉时 `integrated` 观测的取值不定，影响的是生命周期转移，不只是提示。
- **文档位置**：`10` L125–151；`06` L239、L850；`16` L281、L486；`02` Goal / Binding；`14` G45(c)。
- **期望的回答形态**：
  - `baseTip` 在分叉时：若存在对**这一对提交**的有效选择，返回所选一侧；否则返回“无值”，此时不做前进检测，`integrated` 观测只用 `baseCommit` 已知的祖先关系，或者跳过。
  - 在 `Binding`（或 Goal）上加持久字段，例如 `baseChoice{side, tower, user}`。任一侧的值变化即失效。
  - 写明选择的范围（建议按 Goal，与命令参数一致）。
  - 没有分叉时调用返回 `E_STATE`。
  - G45(c) 增加一组：选择之后再次获取，两侧不变，期望不再出现新的分叉提示。

**R33-D13-02｜次要**（非准备时机的获取：合并单位、总时长上限、超时之后的行为）

- **问题**：
  1. **合并单位**：
     - 获取“按 Goal 合并”（`10` L97），但它写的是项目镜像中的同一个引用 `refs/tower-remote/<r>/<b>`（L74）。
     - 同一项目中以同一 base 运行的多个 Goal 同时触发时（打开详情、进入 `in_review`），会对同一引用并发获取。git 对引用加独占锁，后到的一次会以锁冲突失败，并被记为 `base_fetch_failed`。
     - 与准备时机所用的项目锁（`10` L369）是什么关系，也没有写。
  2. **上限**：
     - 准备时机受 `prepare.repoTimeoutMin` 约束；其余时机（`goal.base.check`、`project.remote.recheck`、进入 `in_review` 前的那次在 10 s 之后）没有总时长上限。
     - git 的 HTTP 获取默认没有总时长限制。挂起的获取会让“合并到进行中的请求”的后续 `检查 base` 永远得不到结果。
  3. **两处说法不一致**：
     - `13` L301 写“超时照常转移，获取在后台结束后刷新提示”，即获取继续；
     - `10` L99、L101 写“失败或超时……记 `base_fetch_failed`”，即超时就是失败。
     - 获取继续时，先记一条失败、之后又成功，卡片应当显示哪一条，没有写。
- **为什么重要**：
  - 多个 Goal 并行是核心场景，第 1 项会制造虚假的“无法获取远端 base”。
  - 第 2 项会让手动检查永久失灵。
  - 第 3 项是两份文档之间的直接矛盾。
- **文档位置**：`10` L74、L91–103、L369；`13` L301；`06` L849。
- **期望的回答形态**：
