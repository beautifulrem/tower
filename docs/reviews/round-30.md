>      - 对该 URL 设 `useHttpPath = true` 时，helper 也被调用，git-lfs 提交的路径是远端 URL 的路径。
>      - 这一结果用于 R30-D13-01。
>   3. **对照组：ADR-155 之前的行为**：`remote.<name>.url` 自带 `user:pass@` 时，git-lfs 直接用它发出 Basic 认证。用户自己执行 `git lfs pull` 也是这样。

### D11 安全与自主度

**R30-D11-01｜次要｜M2**（`pre-push` 钩子经 `git hook run` 调用时收不到标准输入；没有钩子即判失败；失败后没有去向）

- **问题**：
  1. **标准输入不会到达钩子。**
     - `10` L74、L984，`15` L1303 与 `16` L473 规定：推送前在用户检出中执行 `git hook run pre-push -- <远端名> <URL>`，“标准输入按 git 规范给出一行 `<本地引用> <seal 提交> <远端引用> <远端提交或全零>`”。
     - 实测：送给 `git hook run` 进程的标准输入**不会**转给钩子，钩子读到空输入。只有 `--to-stdin=<文件>` 才会转给钩子。
     - 常见的 `pre-push` 密钥扫描都按标准输入中的引用逐行确定检查范围。空输入时，它们通常什么都不查就以 0 退出。
  2. **没有钩子即判失败。**
     - 实测：仓库中没有 `pre-push` 钩子时，`git hook run pre-push` 的退出码为 1。
     - 按 `10` L74“钩子失败（非零退出）时不推送”，只要项目设置允许运行用户钩子，所有没有 `pre-push` 的仓库都无法推送。
     - `--ignore-missing` 可以避免这一点。
     - G44(e) 的三组都没有覆盖“允许运行钩子、但仓库没有钩子”。
  3. **失败后的去向没有定义。**
     - `push_hook_failed` 只写了“不推送、记 Fact、卡片显示输出”。
     - 合并队列条目随后进入哪个状态（`failed`、`needs_human`），是否有 Needs-You，有哪些出口（修好后重试、改为仅保留分支、放弃集成），`10` §10.11 的 Q6 与 `04` 都没有写。
     - 一般的推送失败（网络、认证）在 Q6 中同样没有失败处理，这一次新增出口正好暴露了它。
  4. **版本**：`--to-stdin` 比 `git hook run` 本身加入得晚，需要在 Tower 的最低版本 git 2.40（`15` L661）上核实。
- **为什么重要**：
  - 后果的类别是“用户自己设置的安全闸门在 Tower 代理推送时静默失效”。用户以为密钥扫描在把关，含密钥的 seal 却被推送到远端。这正是补记 3 想保住的东西。
  - 第 2 项会让启用该设置的项目全部无法推送。
  - 第 3 项让实现者不知道推送失败后队列与 Goal 停在哪里。
  - 都属于 M2，不影响 M1 排期，但规则本身是错的，应当在 M2 实现之前改正。

### D13 隔离、git 与并发

**R30-D13-01｜次要**（URL 凭据迁移到 `credential.<URL>.*` 之后，git-lfs 用不到这些凭据；只有用户名的 URL 会断开用户自己的 helper）

- **问题**：
  1. **git-lfs 不匹配带路径的 credential 键。**
     - `10` L65–68、`06` L239、`11` L378、`16` L473 规定：用户名写为 `credential.<去掉 userinfo 的 URL>.username`，密码经 `credential.<同一 URL>.helper = store --file=…` 提供，并先清空该 URL 上的 helper 列表。
     - 这里的 URL 是远端的完整 URL，带路径。
     - 实测：`git fetch` 会匹配这样的键。git-lfs 向 `git credential fill` 只提交协议与主机（`useHttpPath` 未设时），带路径的键因此**不匹配**：helper 不被调用，用户名也不被带上，获取以 “credentials not found” 失败。
     - 对照：ADR-155 之前，以及用户自己执行 `git lfs pull` 时，git-lfs 直接使用 URL 自带的 `user:pass` 并成功。
     - 所以 ADR-155 让“远端 URL 内嵌令牌的 LFS 项目”从可用变成每次 `prepare_failed`。SP6a A12(b) 期望“两条命令都照常完成”，会在实现后失败，但规则本身应当正确。
  2. **只有用户名的 userinfo。**
     - Bitbucket Cloud（`https://<用户名>@bitbucket.org/…`）与 Azure DevOps（`https://<组织>@dev.azure.com/…`）的默认 HTTPS 克隆地址都带用户名、不带密码。
     - 规则对“URL 含 userinfo”一律清空 helper 列表、写入 store 文件。没有密码时，store helper 跳过这一条目，用户自己的 helper（钥匙串、Git Credential Manager）又已被清空。
     - 实测 `git fetch` 因缺密码而失败。于是这两类托管上、以远端引用为 base 的每个 Goal，都退回“本地已知值并记 Fact”，从陈旧的 base 开始。R29-D13-01 要解决的正是这个后果。
     - 规则没有区分“只有用户名”与“用户名加密码”。而用户名本身不是凭据，`11` §11.7 的模式也只替换 `:` 与 `@` 之间的部分。
- **为什么重要**：
  - 这是一次修复带来的功能退化，覆盖的用户群并不小：URL 内嵌令牌加 LFS 的项目；Bitbucket 或 Azure DevOps 的 HTTPS 远端加远端引用 base 的项目。
  - 结局都有定义且安全（`prepare_failed`，或陈旧的 base 加 Fact），所以定为次要。
  - 但实现者按文档实现，必然交付这一退化。第 2 项没有任何用例能测出来。
- **文档位置**：`10` L65–69、L241–252；`06` L239；`11` L338、L378；`16` L473；`15` ADR-155 L1292；`14` A12(b)（L62）、G44(d)（L131）；`05` C29(c)（L1405）。
- **期望的回答形态**：
  - credential 键改为按 `<scheme>://<host>[:port]` 限定。临时文件只服务于一条命令，按主机限定不会扩大作用范围。另一种做法是对该 URL 同时写 `useHttpPath = true`，并让 store 条目带同一路径。二者取一，并写明理由。
  - 只有 userinfo 中**含密码**时，才写 store 文件并清空 helper 列表。只有用户名时，只写 `credential.<…>.username`，保留用户自己的 helper 链。
  - `10` L65–68、`06`、`11` L378、`16` 同步。
  - 用例：
    - A12(b) 明确包含 LFS 获取成功；
    - 新增一组：远端为 `https://user@host/…`（只有用户名），用户自己的 helper 能提供密码。期望 base 的 fetch 与 LFS 获取都成功，取样中看不到密码。

**R30-D13-02｜次要**（远端引用 base 在镜像中有两个来源，准备之后以哪个为准没有定义；rebase 前补齐 LFS 期间的前置条件）

- **问题**：
  1. **两个来源。**
     - 补记 2 之后，同一个远端引用 base（`refs/remotes/<r>/<b>`）在镜像中有两个值：
       - Tower 自己网络 fetch 写入的 `refs/tower-remote/<r>/<b>`（`10` L223、L1105）；
       - 从用户检出 fetch 来的 `refs/user/remotes/<r>/<b>`（`10` L225、L1104）。
     - Tower 不再更新用户的 `refs/remotes/*`，两者可以互相领先：Tower 刚取过上游，或者用户自己刚 fetch 过。
     - 只有准备阶段写明了取哪个：`10` L226，fetch 成功取前者，否则取后者。
     - 以下几处都只写“base”或 `rev-parse <baseRef>`，而镜像中并没有 `refs/remotes/<r>/<b>`：
       - “base 前移”的判定（`10` §10.9.3 L903、§10.10）；
       - 合并队列 Q2 的 `newBase = rev-parse <baseRef>`（`10` L968）；
       - M1 `integrated` 观测中的 `<base>`（`10` L987）。
  2. **向后“前移”。**
     - Goal 的 `baseCommit` 取自较新的 `refs/tower-remote`，之后若以较旧的 `refs/user/remotes` 判定“前移”，值不同就会触发 rebase。
     - 这会把 Goal 合并到一个**更旧**的 base 上，把上游的新提交从工作区中“撤回”。随后的验证也在更旧的代码上进行。
     - 文档没有写“前移”必须满足“`newBase` 是 `baseCommit` 的后代”。
  3. **补齐窗口内的前置条件。**
     - rebase 前的 LFS 补齐可能耗时到 `prepare.repoTimeoutMin`（15 分钟，`10` L922）。
     - 此前 rebase 只是一次短暂的 merge-tree 加写回，现在中间多了一段网络获取。
     - 期间人可能“继续”（开始新的 Run）、“我来改”或打开检验，这些情形下自动 rebase 本应暂停（`10` L917）。
     - 文档没有写：补齐期间是否持有卫星锁（持有则这些命令要等到 15 分钟）；不持有时，写回前是否重新检查“仍在空闲点、没有人工编辑或检验检出、`baseCommit` 未变”。
- **为什么重要**：
  - 第 1、2 项是补记 2 引入的状态来源分裂。实现者在多个入口各自选一个 ref，可能造成静默的倒退 rebase，或者在 M1 中永远观测不到 `integrated`。
  - 第 3 项若按最直接的方式实现，可能在 Agent 工作中途移动它脚下的代码，违反 §10.10 的原则“不在 Agent 工作中途移动它脚下的代码”。
  - 结局可以收口，只需几条规则，所以定为次要。
- **文档位置**：`10` L223–226、L903、L916–925、L930、L968、L987、L1104–1105；`16` L473、L605；`14` G44(a)(b)。
- **期望的回答形态**：
  - 写一条唯一规则：“远端引用 base 的当前值”。
    - 两个 ref 中一个是另一个的后代时，取较新者；
    - 两者分叉（上游被强制推送）时，取 `refs/tower-remote` 并记 Fact；
    - 只有其中一个存在时，取它。
    - §10.9.3、§10.10、Q2 与 `integrated` 观测都引用这条规则。
  - “base 前移”的定义加上“新值 ≠ `baseCommit`，且 `baseCommit` 是新值的祖先”。否则只记 Fact，不 rebase。
  - rebase 前的补齐在卫星锁之外进行。写回前在锁内重新检查前置条件，不成立则放弃本次 rebase，等下一个空闲点。补齐期间人的命令不被阻塞。
  - 用例：
    - 用户检出中的 `origin/main` 比 Tower 取到的旧：不 rebase；
    - 用户自己 fetch 之后更新：rebase 到新值；
    - LFS 补齐进行中人点“继续”：补齐结束后不写回。

- **是否所有维度为 100：否。**
  - D1–D10、D12、D16 为 100，这十二个维度上没有可追问的实质问题。
  - D11 99、D13 97、D14 99、D15 99。
- **是否还有可追问的问题：有。** 新增共 **5** 条：阻断 0、重要 0、**次要 5**。
  - **第 29 轮核验**：4 条全部已解决（R29-D11-01、R29-D13-01、R29-D13-02、R29-D15-01）。
  - **其他核对**：
    - lint 全部通过；
    - Pi 事实与 v1.2.0 源码一致；
    - git 与 git-lfs 的 credential 匹配、只有用户名的 userinfo、`git hook run` 的标准输入与退出码，都已在本机 git 2.56.0、git-lfs 3.8.0 上实测；
    - 排期算术全部成立：WBS 120.78、38 周、余量 0.18–1.18、增人 33 周。
  - **不扣分的观察**：
    - **git-lfs 写入镜像 config**：一次带认证的获取之后，git-lfs 会在镜像的 `config` 中写入 `lfs.<端点>.access = basic`（实测）。“镜像的 config 只含 Tower 写入的内容”（`10` L70）在字面上不精确。这个值优先于临时文件中白名单的 `lfs.<url>.access`。它只是 git-lfs 自己缓存的认证方式，与用户本机的行为相同，不扩大任何来源的影响，不扣分。建议改成“只含 Tower 写入的项与 git-lfs 自身的缓存键”。
    - **C29(c) 的措辞**：“只出现 `~/.tower/tmp/` 下的文件路径”，而按设计，参数中还会出现去掉 userinfo 的 URL。应理解为“不出现密码或 token”，测试可控，不影响实现。
    - **远端名含 `/`**：`refs/remotes/<r>/<b>` 中 `<r>` 本身含 `/` 时会有歧义，需要按已配置的远端名最长匹配。极少见；失败时的结局是“本地已知值加 Fact”，有定义且安全。
    - **M2 推送后的跟踪引用**：从镜像以 URL 推送不会更新用户检出中的 `refs/remotes/<r>/<分支>`。写入 `.remote`/`.merge` 之后，用户的 `git status` 在下一次 fetch 之前显示上游不存在。属于 M2 的显示问题，不影响正确性。
    - **`14` L397 “增量都不在链上”**：与 W7-core 的增量不一致，对结论没有影响。
- **设计是否完成：否。**
  - 五条都是局部的规则与文字修正，不需要新架构，也不影响 M1 日期。
  - R30-D13-01 是一次已实测的功能退化，应在实现 W7-core 的网络命令之前改正。
  - R30-D14-01 决定了 R30-D13-02 与 G44(a) 落在哪个里程碑，应当先裁定。

  1. **R30-D13-01**：
     - credential 键改为按主机限定（或使用 `useHttpPath`）；

  3. **R30-D13-02**：

     - “前移”要求祖先关系；

  4. **R30-D15-01**：同步 `05`、`06`、`11` 的文字；统一 `GIT_CONFIG_NOSYSTEM` 的条件与认证键的读取范围。
