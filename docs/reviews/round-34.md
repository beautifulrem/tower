## 1. 总评

ADR-159 把散落在多轮中的机密规则收拢成一张投递表，静态存放、即时投递目录、验证器读规则、T33/T33b 的评级都已落地。默认改回 `env` 也消除了 R33-D7-01 的虚假通过。Pi 依赖（单次调用中止）与 v1.2.0 源码一致，排期算术全部成立。

R33 的 9 条中 5 条已解决，4 条部分解决（残留都是小项）。

新增 7 条（重要 4、次要 3），几乎都集中在本轮新机制**独占窗口**上：
- **读者集合不完整**：窗口只约束“其他 Goal 的 Agent”，没有覆盖持有者自己正在运行的 Agent（机会式验证就在 `running` 中进行）、并发的其他验证槽位与检验检出服务，也没有覆盖 Scratch。
- **开启协议没有定义**：Pi 先发 `tool_execution_start` 再进 gate，按事件计“在途调用”会自锁；gate 读标志与 Supervisor 判定在途之间存在竞态；两个窗口可以同时存在，但标志只有一个值。
- **嵌套调用自锁**：codemode 的嵌套调用被 gate 挡住，它的父调用又被当作在途调用等待。
- **超时后的状态**：`verify_env_error{stage:"secret_window"}` 一边进入 `paused`，一边“继续等待”，“等待”与“以 file 方式重试”两项没有命令。

     - 但 `secret_window` 的各处写法假定验证**仍在等待**：
       - `08` L506：“窗口在人处置前自行开启、验证照常完成 → `obsolete`”；
       - `04` L1096：“`等待`（继续等）”；
       - `12` L416：“已暂停 · 验证在等待机密窗口”；
       - G46(f)：选“中止”后“窗口随即开启”。
     - 两种读法下，实现完全不同：前者在 5 分钟时撤下验证；后者让一个 `paused` 的 Goal 背后仍有验证在等待，`03` 的状态机里没有这条路径（`paused` 中验证完成之后转到哪里？）。
  2. **选项没有命令**：
     - “以 `file` 方式重试”：`06` L857 的 `goal.retry_verify{goalId, pin?}` 没有投递方式参数。这又是对已批准合同字段（`secretsVia`，合同不可变，I3）的一次性覆盖，其结果与合同的关系没有写：`envHash`（`07` L693）随 `secretsVia` 改变，这次结果是否计入该标准的 V？
     - “等待”：不对应任何命令。若 Goal 已 `paused`，“等待”之后什么也不会发生；若验证仍在等待，5 分钟计时是否重新开始、是否再次生成卡片，没有写。
     - “中止”之后：若 Goal 已 `paused`，中止对方的调用并不会让本 Goal 的验证继续，需要谁来发 `retry_verify`？
  3. **`secrets.access` 的等待超时**：
     - 超时出口只按验证器定义（“该验证记 `verify_env_error`”）。
     - `secrets.access` 的那次调用同样要等其他 Goal 的在途调用结束才能开启窗口，但等待发生在哪一步（gate 批准之后、`spawnHook` 之前？），等待期间的 Mode 与实况行，超过 5 分钟怎么办，都没有写。
- **为什么重要**：
  - 这是本轮新增的暂停原因分支。照不同文档实现，会得到两种互不兼容的状态机，其中一种会让卡片上的“等待”永远不起作用。
  - “以 file 方式重试”是界面上有、命令层没有的按钮（lint (v) 只核对命令有没有远程级别，查不出这一类）。
- **文档位置**：`03` L86；`07` L699、L1451、L1498；`08` L191、L506；`04` L1096；`12` L416；`06` L233、L853、L857；`11` L424；`14` G46(f)。
- **期望的回答形态**：二者取一，并在上述各处统一。
  - **(甲) 不暂停**：5 分钟时只生成 Needs-You，Goal 保持 `verifying`，验证继续等待。
    - “等待”= 关闭打扰（`informative`），不再计时；
    - “中止”= `goal.tool.abort`，窗口随后自然开启；
    - “以 file 方式重试”= 新命令，例如 `goal.verify.secret_via_file{goalId, criterionId}`，撤下等待、以 `file` 方式运行该标准。
    - 删除 `07` L1498 对 `secret_window` 的适用。
  - **(乙) 暂停**：进入 `paused(verify_env_error)`，验证撤下。
    - “等待”= `goal.retry_verify{pin:"same"}`（重新排队等待窗口）；
    - “以 file 方式重试”= `goal.retry_verify{pin:"same", secretsVia:"file"}`（新参数，只作用于本次）；
    - “中止”= `goal.tool.abort`，随后同样需要 `retry_verify`，界面写明。
    - 删除 `08` L506 的“自行开启 → `obsolete`”。
  - 无论取哪一种，都写明一次性 `file` 结果与合同的关系：例如结果带 `secretsVia:"file"` 标注，照常计入 V；或者只计入 O。
  - `secrets.access`：写明窗口在 gate 批准之后、`spawnHook` 之前开启，等待期间 Mode 为 `blocked_guard`、实况行写“等待机密窗口”；超过 5 分钟时生成 `approval` 类 Needs-You，选项为“继续等待 / 中止对方调用 / 取消本次调用”。
  - G46(f) 按所选方案改写期望，另加一组 `secrets.access` 等待超时。

### D5 Agent 架构与 Pi 集成

**R34-D5-01｜重要**（gate 第 0 步：嵌套调用自锁；等待不观察中止与 `draining`；C39 的期望与 Pi 的事件顺序不符）

- **问题**：
  1. **嵌套调用自锁**：
     - Pi v1.2.0 中，经 `ctx.executeTool()` 发出的嵌套调用（codemode 脚本中的 `tools.*`，以及任何调用其他工具的扩展工具）同样经过 `tool_call` 钩子，带 `parentToolCallId`（`agent-session.ts:657-673、727-740`，`codemode/tool.ts:7-10`）。`05` L967 与 C5 已登记这一点。
     - 第 0 步只豁免“Tower 自己的工具”，没有豁免嵌套调用。窗口标志写入时，若某个 Goal 的 codemode 调用正在执行：
       - Supervisor 把它当作在途调用，等它结束才开启窗口；
       - 它的下一个嵌套调用在第 0 步等待窗口结束；
       - 两者互相等待。codemode 的脚本超时缺省为无限（`codemode/execute.ts:507`）。
     - 5 分钟后出现 Needs-You，但 codemode 是扩展工具，卡片不提供“中止”。剩下的“等待”永远不会结束；“以 file 方式重试”只对验证器窗口有效。
     - codemode 按 ADR-032 默认随用户的 Pi 配置启用（`05` L332），这不是罕见配置。
  2. **等待不观察中止与 `draining`**：
     - 第 0 步排在第 2 步（`draining` → block + terminate）之前，等待循环只在“标志清除”时退出（`05` L960）。
     - 人在窗口期间暂停一个正在第 0 步等待的 Goal，或退出应用：
       - Supervisor 写入的 `draining` 不会被看到；
       - Pi 的 run 级中止只在 `beforeToolCall` 返回之后才检查（`agent-loop.ts:736-743`）。
     - 暂停、退出因此被推迟到窗口结束，可能长达该标准的超时。而 `ExtensionContext.signal`（`types.ts:351-352`）本来就可用。
  3. **C39 的期望与事件顺序不符**：
     - Pi 先发 `tool_execution_start`，再进 gate（`agent-loop.ts:541-549`，`05` L598）。
     - 因此被暂缓的调用**一定**出现在 `tool.start` 之后。C39 写“不出现在 `tool.start` 之后”，不知要验证什么。
- **为什么重要**：
  - 第 1 项是默认配置下的死锁，出口只有人手动关窗或放弃。
  - 第 2 项让“暂停”这个最基本的人类控制在窗口期间失效，违背“随时可逃逸”。
- **文档位置**：`05` L960-961、L967、L598、L1378（C5）、L1411（C39）；`11` L419；`06` L233。
- **期望的回答形态**：
  - 第 0 步写明：带 `parentToolCallId` 且父调用在标志写入之前已通过第 0 步的嵌套调用，视为父调用的一部分，**不等待**。窗口仍等父调用整体结束后才开启，所以不变式不变。
  - 第 0 步的等待循环同时观察 `ctx.signal`（中止即返回 block）与 `policy.mode === "draining"`（返回第 2 步的 block + terminate），使暂停、退出不被窗口推迟。
  - C39 改写：被暂缓的调用已有 `tool.start`，Mode 为 `blocked_guard`，没有 `tool.end`，工具的 `execute` 没有被调用。另加两组：
    - codemode 脚本在窗口标志写入前开始、之后发出嵌套 bash，期望不自锁，窗口在脚本结束后开启；
    - 某 Goal 在第 0 步等待时人暂停它，期望在 drain 时限内进入 `paused{human}`。

### D6 系统架构与可靠性

**R34-D6-01｜重要**（独占窗口的开启协议：在途调用怎样计、竞态、并发窗口、窗口期间开始的 Run）

- **问题**：
  1. **“在途调用”怎样计**：
     - `11` L420 与 `06` L233 写“窗口等这些 Goal 当前的工具调用结束后才真正开启”“只有在没有其他 Goal 的工具进程仍在运行时才注入机密”。Supervisor 据什么判断？
     - 最自然的实现是按 `tool.start`/`tool.end` 计数（`05` L556 的“活跃工具数”）。但 Pi 先发 `tool.start` 再进 gate，所以在第 0 步等待的调用也被计为在途：窗口等它，它等窗口，每一次有别的 Goal 在开启前发出调用都会自锁到 5 分钟超时。
     - 这时“中止”也无效：被挡在 gate 中的调用还没有进入 `execute`，没有可中止的控制器。
  2. **竞态**：
     - gate 在调用开始时读一次标志（等待中才每 250 ms `stat`）。
     - 一个调用若在标志写入前的瞬间通过第 0 步，而它的进程尚未启动、Supervisor 也还没有把它计为“已放行”，Supervisor 可能判定“无在途”，随即 `SIGSTOP` 已识别的进程、注入机密。随后该调用启动的进程既不在暂停集合中，也不受 gate 约束，整个窗口期间都在运行。
     - 不变式“机密只在没有其他 Agent 工具进程启动的窗口中存在于环境里”（`11` L418）没有协议保证。
  3. **并发窗口**：
     - 槽位数 c 通常为 2（`07` L903-904），两个 Goal 的带机密标准可以同时运行。
     - `TowerPolicy.secretWindow` 是单值 `{holderGoalId, openedAt}`（`05` L951）。第二个窗口会覆盖第一个的标志；任一窗口关闭时清除标志并 `SIGCONT`，另一个窗口却仍在进行。
     - 一个持有者在另一个窗口中算不算“其他 Goal”：它自己的验证要不要排队，排队时间算不算进它的 5 分钟，也没有写。
  4. **窗口期间开始的 Run**：标志只“写入其他**运行中** Goal 的 `policy.json`”。窗口期间开始或恢复 Run 的 Goal（准入、`resume`、返工），它新编译的策略带不带标志，没有写。不带时，这个 Agent 在窗口内不受任何约束。
- **为什么重要**：
  - 第 1 项按最自然的实现会让窗口几乎每次都自锁，独占窗口在多 Goal 场景下不可用。
  - 第 2、3、4 项都是 T33b 评为“低”的前提失效的路径。
- **文档位置**：`11` L418-424；`06` L233；`05` L951、L960、L556、L598；`16` L499；`07` L903-904；`13` L302；`14` G46(e)。
- **期望的回答形态**：
  - **开启握手**：
    - Supervisor 写入带版本号的标志；
    - 每个运行中 Goal 的 tower-goal 在看到该版本后**回执**：本 Goal“已通过第 0 步、尚未结束”的调用集合（SDK 经 bridge 同步回执，RPC 经 `appendEntry`）；
    - Supervisor 只等这个集合清空，被挡在第 0 步的调用不计入；
    - 之后才 `SIGSTOP` 并注入。
    - 另在 Tower 自己的 `exec` 中再查一次标志作为第二道防线：标志存在且该调用不在回执集合中时，不派生进程。
  - **并发窗口**：二者取一。
    - 全局互斥、FIFO 排队：排队时间不计入 5 分钟，卡片显示“排在 G-xxxx 的机密窗口之后”；
    - 或者标志改为集合、`SIGSTOP`/`SIGCONT` 按引用计数。
  - **新开始的 Run**：策略编译时带上当前窗口；或者窗口期间推迟 Run 的开始（计入 `ready` 的排队原因）。二者取一。
  - G46 增加三组：
    - 窗口标志写入时另一 Goal 正有调用停在第 0 步，期望不自锁；
    - 两个 Goal 的带机密标准同时进入两个槽位，期望窗口串行（或引用计数），先关闭的一方不会放行第三个 Goal；
    - 窗口期间第三个 Goal 开始 Run，期望它的首个工具调用被暂缓。

### D11 安全与自主度

**R34-D11-01｜重要**（独占窗口没有覆盖的读者：持有者自己的 Agent、并发的验证槽位与检验检出服务、Scratch）

- **问题**：
  - 窗口只约束“其他 Goal 的 Agent”：第 0 步只在 `holderGoalId ≠ 本 Goal` 时等待，`SIGSTOP` 只对“其他 Goal 已识别的进程”（`05` L960，`11` L419-421）。
  - 但在 macOS 上，任何同一用户、运行 Agent 写的代码的进程都能读到持有者验证进程的环境。以下几类都不在范围内：
    1. **持有者自己的 Agent**：
       - 机会式验证只在 `goal.state == "running"` 时进行，并且跑全部 exec 标准（`07` L167-172），带机密的标准也在其中；
       - `agent_bg` 触发的重新验证发生在本 Goal 的存活进程仍在运行时（`16` L49）；
       - 此时持有者自己的 Agent 照常发起调用，其开发服务器照常运行，都不受窗口约束。
       - `07` §7.4.3 的规则 1、2（耦合保护、不回送输出）正是为了让 Agent 拿不到验证器机密。ADR-158 的默认文件注入下，Agent 沙箱对 `~/.tower/**` 读拒绝，这一点成立；改回 `env` 后，这道保护在机会式验证中失效。
    2. **并发的其他验证槽位**：
       - c 通常为 2，另一个 Goal 的验证同时在跑它的 Agent 写的测试代码；
       - 那些标准若不带机密，输出末尾照常进入那个 Goal 的返工提示（`11` L442）；
       - `07` L707 的变换检测只作用于带机密标准的日志。
       - 其结果是一个 Goal 的机密跨越到另一个 Goal 的模型上下文，违背了密钥库条目“允许的 Goal/标准”（`11` L437）。
    3. **检验检出的服务**：Tower 在检验检出中以验证器档位运行 Agent 写的服务（`11` L364），它们不在任何 Goal 的进程树或令牌中。
    4. **Scratch**：它有自己的 Agent 与 S2 沙箱 bash（`11` §11.6.5），但不是 Goal。
  - 同时，带机密的标准进入机会式验证后，其他 Goal 的停顿频率成倍上升（每 Goal 约每 15–25 min 一次，`07` L173），`13` L302 与 `07` §7.4.10 的容量模型都没有计入。
- **为什么重要**：
  - 第 1 类在默认配置下直接把验证器机密暴露给本应拿不到它的那个 Agent，T33b 的“低”评级不成立。
  - 第 2 类是跨 Goal 的授权越界。
  - 第 3、4 类与 T33 的威胁属于同一类（“被并行的 Agent 观察”），但没有登记。
- **文档位置**：`11` L418-425、L437、L442、L364、§11.6.5、L605（T33b）；`05` L960；`06` L233；`07` L167-176、L703-708、L895-952；`13` L302；`14` G46。
- **期望的回答形态**：
  - **持有者自己**：二者取一。
    - 带机密的标准**不参加机会式验证**，只在 `claimed` 及之后、本 Goal 的 Agent 进程已终止时运行；`agent_bg` 触发的重新验证在存活者仍在时同样跳过带机密的标准；
    - 或者验证器窗口同样约束持有者自己的 Agent（`secrets.access` 窗口仍然豁免持有者）。
  - **其他读者**：二者取一。
    - 窗口期间暂停（`SIGSTOP`）其他槽位、检验检出与 Scratch 的进程组。这些进程组都由 Tower 自己创建，pgid 已知；
    - 或者带机密的标准独占验证器：其他槽位在窗口期间不启动新标准，已在运行的进程组被暂停。
    - 无论取哪一种，都写明 Scratch 是否在范围内。
  - `13` 写明窗口频率的上限，并说明它对其他 Goal 吞吐的影响。若采用“不参加机会式验证”，这一项自然有界。
  - T33b 的残余据此改写。
  - G46 增加三组：
    - 持有者处于 `running`，机会式验证触发带机密的标准，期望该标准不在此时运行，或者持有者的新调用被暂缓；
    - 两个 Goal 的验证同时进行，一方的标准带机密，期望另一方的验证进程在窗口内被暂停或未启动；
    - 窗口期间一个 Scratch 会话在运行。

**R34-D11-02｜次要**（窗口关闭后仍带机密环境的后代进程；关闭窗口时 `secrets.access` 审批卡片的文案）

- **问题**：
  1. **后代进程**：
     - 窗口持续“该工具调用期间”或“该标准运行期间”（`11` L413-414）。
     - 但从 `secrets.access` 那次调用派生、转入后台的进程继承了机密环境，调用结束后仍在运行，直到本 Run settle 才被终止。
     - 验证器以 `-pgid` 终止标准（`07` L714），脱离进程组的后代不在其中，也没有“槽位回收前确认无残留进程”的规则。
     - 窗口关闭后，这些进程的环境对其他 Goal 可读。“有界的例外”（`11` L373，T33）在这里不再有界。
  2. **审批卡片**：R33-D11-02 期望的 `secrets.access` 审批卡片文案仍不在 `04`。项目关闭独占窗口时，标准行有风险标注（`04` L1094），`secrets.access` 的审批卡片却没有对应说明。
- **为什么重要**：
  - 一个无辜的持有者在后台启动带机密的进程是很常见的做法。T33 的威胁正是并行运行、可能被注入的另一个 Goal。
  - 在“关闭窗口”的项目中，人批准时不知道风险。
- **文档位置**：`11` L373、L413-414、L439、L604-605；`07` L714、L723；`04` §4.10、L1094。
- **期望的回答形态**：
  - 二者取一。
    - 窗口关闭时，Tower 终止该调用（或该标准）派生的全部进程（进程树 ∪ 令牌）。工具结果注明“后台进程已随机密窗口结束而终止”；
    - 或者窗口持续到这些后代全部退出，等待计入窗口时长与 5 分钟上限。
  - 脱离进程树、又无法识别的后代登记进 T33b 的残余。
  - `04` 给出 `secrets.access` 审批卡片的文案（窗口开启与关闭两种情形）。
  - G46(h) 增加一组：那次调用把一个进程放到后台，期望窗口关闭时它已终止（或窗口延续）。

### D13 隔离、git 与并发

**R34-D13-01｜次要**（分叉且未选择时 `baseTip` 的返回值；没有分叉时调用 `goal.base.choose`）

- **问题**：
  - `10` L138-145 只写了两种情形的返回值：分叉且已选择时返回所选一侧；准备时分叉取用户一侧。
  - **分叉且没有有效选择**时，`baseTip` 返回什么仍然没有写。而它是 `integrated` 观测（`10` L154，§10.12）与 M2 `newBase` 的唯一来源。

- **为什么重要**：`integrated` 是生命周期转移，不只是提示。取错一侧可能在被强制推送覆盖的历史上观测到“已合入”。这是 R33-D13-01 期望中没有落实的部分。
- **文档位置**：`10` L131-154；`06` L855；`16` L40；`14` G45(c)。
- **期望的回答形态**：
  - 写明分叉且未选择时 `baseTip` 返回“无值”：不做前进检测，`integrated` 观测跳过，卡片保持分叉提示；或者写明另一条保守规则，例如两侧都包含 seal 提交时才判 `integrated`。
  - 没有分叉时调用 `goal.base.choose` 返回 `E_STATE`。
  - G45(c) 第三组补期望：分叉未选择期间 seal 被合入一侧，期望不进入 `integrated`（或按所写规则）。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D7、D9、D12、D14、D16 为 100，这八个维度上没有可追问的实质问题。
  - D4 97、D5 96、D6 95、D8 99、D10 99、D11 90、D13 99、D15 99。
- **是否还有可追问的问题：有。** 新增共 **7** 条：阻断 0、**重要 4**、**次要 3**。
  - **第 33 轮核验**：已解决 5（R33-D6-01、R33-D7-01、R33-D11-01、R33-D11-03、R33-D13-02），部分 4（R33-D4-01、R33-D11-02、R33-D13-01、R33-D15-01），未解决 0。
  - **其他核对**：
    - lint 全部通过；
    - Pi 单次中止的接口与错误路径与 v1.2.0 源码一致；
    - `SIGSTOP` 后 `SIGTERM` 的挂起行为经本机实测，`10` L425 的顺序规则正确；
    - 排期算术全部成立：WBS 121.51、38 周、余量 0.23–1.04、增人 33 周。
  - **不扣分的观察**：
    - **MCP 服务器作为读者**：MCP 服务器与用户扩展的子进程在 Host 下、沙箱外运行，窗口不暂停它们。这已由 T28（“沙箱外的扩展与 MCP”）登记为残余，评级合理，不重复计入。
    - **崩溃恢复中只靠进程树识别的进程保持暂停**：`11` L423 已如实登记为 ADR-158 的窗口。后果是资源占用而不是泄露，结局保守，不扣分。
    - **`file` 方式下测试失败（而不是跳过）**：`file` 是人显式选择的，返工浪费由人的选择承担，不扣分。
- **设计是否完成：否。**
  - 独占窗口是本轮新建的机制，方向正确（它是 macOS 事实下唯一能落地的缓解），但三处规则还不足以让它安全、可用：
    - **读者集合**（R34-D11-01）；
    - **开启协议**（R34-D6-01）；
    - **gate 等待的豁免与退出**（R34-D5-01）。
  - 超时出口的状态语义（R34-D4-01）需要在两种模型中取一。
  - 都只需补规则、补命令与用例，不需要新架构。
