## Pi v1.2.0 核实（`packages/coding-agent/src/`，`git show v1.2.0:<path>`）

**Host 中读取包管理器配置的代码**只有包目录的解析：
- 每次 `createAgentSessionServices` 都新建 `DefaultResourceLoader` 并 `reload()`（`core/agent-session-services.ts:148-154`）；`reload()` 无条件调用 `packageManager.resolve()`（`core/resource-loader.ts:529`）。
- 用户级 npm 来源先算安装路径（`core/package-manager.ts:1321-1324`）。`getNpmInstallPath` 在 `<agentDir>/npm/node_modules/<名字>` 不存在时调用 `getLegacyGlobalNpmInstallPath`（`:2151-2158`、`:2143-2149`）。

**查询的环境**：
- 经 `runNpmCommandSync` → `runCommandSync` 同步运行（`:1846-1849`、`:2752-2765`）。
- `env` 取 `getEnv()`，即 Host 的 `process.env`；Linux 上为空时读 `/proc/self/environ`（`:16-33`）。
- 不传 `cwd`，不设超时。命令取用户级设置的 `npmCommand`（`:1787-1797`）。
- 所以 npm 读到的配置（含 `NPM_CONFIG_USERCONFIG` 所指文件中的 `prefix`）与工作目录都来自 Host 进程。

**查询的次数**：
- npm 的 `root -g`（bun 为 `pm bin -g`）按 `npmCommand` 在每个 `PackageManager` 实例中缓存（`:2102-2116`）。
- pnpm 的 `list -g --depth 0 --json` 每个包运行一次、不缓存（`:2118-2130`），找不到时再落到 `root -g`（`:2145`）。
- 离线时缺失的来源在 `installMissing` 返回 false 后直接跳过，不再第二次求路径（`:1309`、`:1325-1327`）。
- 版本判定只读 `package.json`，不运行子进程（`:1513-1519`、`:1538-1549`）。

## R85-D11-01（重要）：Host 环境不引用 Agent 可写的位置

**唯一定义**：`05` §5.3.6 新增一段（L445）。
- Host 进程环境与它的工作目录中，没有任何值指向 Agent 可写的位置：本 Goal 的卫星与 gitdir、`$GS`、`$TMPDIR/tower-<goalId>`（`11` §11.6.2 写允许一行）。
- `16` §16.8 的角色 A 变量（含 `NPM_CONFIG_USERCONFIG=$GS/npmrc`）只由 `bashEnv` 与 Tower `exec` 的同一白名单加入 Agent 一侧。环境表 “包管理器私有存储” 一行（L453）的 Host 列改为 “—”。
- **理由写在规则旁**：Host 在沙箱外运行全局根查询，它的结果决定 Host 从哪里加载扩展包，所以它读到的配置不能由 Agent 改写。

**Host 的包管理器环境是你自己的**：
- `PATH`（L459）：首次运行时从登录 shell 读到、经人确认的目录，再加系统路径。Agent 可写位置之下的目录与相对路径不收入。
  - Tower 按项目选出的 Node 与包管理器只在 A、I、V 的 `PATH` 中（`16` §16.8；ADR-085 本就只规定这三者）。
- 包管理器位置变量：`NPM_CONFIG_PREFIX`、`NPM_CONFIG_USERCONFIG`、`NPM_CONFIG_GLOBALCONFIG` 的大小写两种写法，以及 `PNPM_HOME`。取登录 shell 的值，有值才传入，落在 Agent 可写位置之下时不传入。
- 配置文件是你自己的（如 `~/.npmrc`），Agent 不可写。工作目录是你的主目录。
- 这些值与 `PI_CODING_AGENT_DIR` 一样在首次运行时读取一次（ADR-209，L466），整台机器同一个。
- Supervisor 的清单查询用同一环境（`05` §5.10，L1332）。

**同步**：
- `06` §6.2.4 Host 环境拼装（L320）；
- `07` §7.4.3（L551、L569）；
- `11` §11.7.1 Host 环境白名单（L507）、§11.8.2 清单行（L607）与残余风险（L611）；
- `16` §16.8 篡改用例（L1355）；`14` P8（L142）。

**Host 存活期间的重新解析**（评审期望 (b)）：
- 没有新增 “每次创建会话后比对清单” 的机制。
- 规则成立之后，Pi 在新会话中重新解析时，读到的都是你自己拥有、Agent 不可写的位置，结果只会因你自己的改动而变。这与你在 Host 存活期间改动 `extensions/` 同类。
- 新的代码要到下一次 Host 启动前的清单计算才列出并要求确认。`05` §5.10 与 `11` §11.8.2 写明这是已知限制。
- 被保护的不变式是：Agent 可写的内容不能决定 Host 在沙箱外加载哪些代码。这一条照常成立。

**测试**：
- C40（`05` L1475）补两组：
  - Host 进程环境与工作目录中没有指向 Agent 可写位置的值，`PATH` 与包管理器位置变量等于登录 shell 的值；
  - Agent 改写 `$GS/npmrc`（加入 `prefix`，指向卫星中它写出的同名包）之后，在同一 Host 中新建会话：全局根与 `extensionsResult` 不变，该包仍为 “未安装”。
- G46 补 (bj)（`14` L134），只写期望：
  - Host 环境不含这些值；
  - 上下文交接前后全局根与已加载的扩展集合不变；
  - 下一次 Host 启动前的清单仍列为 “未安装”、没有新的确认卡片；
  - Agent bash 中仍是 `$GS/npmrc`。

**ADR-212 的说法**：“与安装器第 1 阶段同类” 不成立（第 1 阶段的配置在 Agent 不可读的 `$TI`）。已在 ADR-212 原文加删除线并注明更正，并登记在 `16` §16.1.13。

## R85-D5-01：全局根查询的环境

随 R85-D11-01 的规则成立。

**(a) 与用户终端一致**：
- Host 与 Supervisor 用你登录 shell 中的 `PATH`、包管理器位置变量与你自己的配置文件，所以 Tower 与你在终端中运行的 `pi` 得到同一个全局根。“请在你的终端中运行 `pi` 安装” 的补救因此有效（`00` L99 补一句说明）。
- 如实写明例外：你在某个项目目录中运行 `pi`，而该项目的包管理器配置改变了全局位置时，结果可能不同。用户级的包集合本就与项目无关。

**(b) 一份环境**：整台机器同一个，不随项目或 Goal 变化，清单只有一份。

**(c) C40**：改为 “全局根查询之外没有包管理器子进程”，不限次数，npm 与 pnpm 各跑一遍。G46 (bi) 同样不限次数。

**观察 3 一并写入 `05` §5.10**：
- 运行的是你配置的 `npmCommand`（可以是包装脚本）；
- Supervisor 的查询限时 10 s，超时或失败按 “没有全局根” 处理（与 Pi `:2143-2149` 一致）。

## R85-D6-01：载荷上限与只追加的列

**(a) 上限**（`16` §16.1.14，L663，唯一定义）：
- 载荷会超过 16 KB 时，非空的路径集合都整组写入 `goals/<G>/artifacts/paths-<sha256>.json`。文件按内容哈希命名，写入并 `fsync` 之后才追加事件。
- 载荷中这些字段换成 `{sha256, count}`，Projector 与重建按哈希读回。
- **没有取 “由检查点的树重算”**：
  - `mixedPaths`、`externalPaths`、`humanPaths` 由当时的归因求出；
  - `excludedPaths` 是 git 拒绝收录、本就不在树中的路径；
  - 这四个集合都不能从树重算，所以也不截断。
- `13` §13.9.1（L247）与 `06` 数据目录（L1051）写明这一处置。

**(b) 只追加的列**：“建立后不再改写” 改为显式列表，建立后只追加两列：
- `landmarks` 只追加 `verify_pass`/`verify_fail`/`criteria_flip`；
- `unusable` 投影自 `workspace.recovered`。

**写入规则**（`10` §10.7.1 `landmarks`，L794，唯一定义）：
- `submit` 在回合检查点建立时写：本回合含 `submit` 调用。
- `rework_start` 同样在建立时写：`Run.reason = rework` 的 Run 的第一个回合检查点。
- 本回合没有建立检查点时，这两个值都不补写到别的检查点。
- 三个验证类值在一次验证的全部 `criterion_check` Fact 记录之后，由 Supervisor 追加到被验证 pin 的 “当前 pin 的检查点”；重建时由同一组 `fact.recorded` 推出。
- 时间线的验证地标仍以 Fact 为准（§10.8.2）。
- `10` §10.8.4 第 7 步（L985）改为引用。

## R85-D6-02：重建的三处例外

取 “收窄断言”。`06` §6.2.1（L221，唯一定义）列出全部例外与各自的来源：
1. **`checkpoints.in_user_repo`**：按用户仓库中的地标 ref 求出。
2. **`runs` 中不由 `run.*` 载荷承载的列**：
   - 从被重建的库逐行沿用，那份库不可用时取最近的 `db-backups/`；
   - 两处都没有时，未结束的 Run 记为 `crashed`，它的后台进程不能再按令牌识别。
3. **`needs_you`**：没有创建事件。重建后由各生产者按状态重新判定生成，推迟与级别的历史丢失。

**没有取 “补全事件载荷”**：那要给 `runs` 的十余列与每种 Needs-You 新增载荷，超出一个字段的修改。

## 偏离与未决

- **R85-D11-01 (b) 没有采用 “每次创建会话后比对清单”**：以 Host 环境的规则关闭，Host 存活期间由你自己的改动带来的变化写为已知限制，理由见上。若评审认为这一限制不可接受，最小的补法是 Host 在 `session_start` 时把 `extensionsResult` 的路径与已确认的清单比对、不符即以 `noExtensions` 重建本会话。这会是一条新机制，本轮未加。
- **Host 的 `PATH` 不再以 Tower 按项目选出的 Node 开头**：MCP 服务器与扩展的子进程因此使用你终端中的同一套工具，与 CLI 一致。这是行为变化，不是安全放宽：`$SH` 本就不是 Agent 可写的位置。
- **登录 shell 的值只读一次**：你之后修改 `PATH` 或包管理器位置变量，Tower 不会自动重新读取，与 `PI_CODING_AGENT_DIR` 相同（ADR-209）。
- **`runs` 的重建**：依赖被重建的库或 `db-backups/`。两者都缺失时有一个已登记的识别窗口。
