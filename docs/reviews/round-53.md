### D11 安全与自主度

**R53-D11-01｜重要**（`Contract` 封闭表把“新增 `exitCode`”列为收紧，实际可以放宽验收依据）

- **问题**：
  - `16` L986：`criteria[].expect`、`repeat` 一行，web 允许的方向是“收紧：提高 `minTests`、降低 `maxFailures`、提高 `repeat`、新增 `exitCode`/`stdoutMatches`”。
  - 但判定函数（`07` L787）是 `run.exitCode !== (c.expect.exitCode ?? 0)` 则失败。没有 `exitCode` 键时，期望值就是 0。
  - 因此“新增 `exitCode`”只有在新增值为 0 时才不改变判定；新增非零值会让以非零码退出的命令（通常就是测试失败）判为通过。`maxFailures` 缺省时不检查计数（`07` L792），这一放宽不会被其他条件拦住。
  - 这正是总规则 3（`16` L923）、`11` L578 与该表自己的“仅本机：任何放宽”一列要排除的事。
- **违反的不变式**：`16` §16.5 总规则 3 与 `11` §11.9：改变验收依据的修订只能在本机。
- **为什么是重要**：
  - 封闭表是 ADR-178 指定的唯一定义。实现者照表实现，就会接受一条从远程客户端降低验收标准的修订。
  - 远程验收的五个条件都不检查合同版本之间的变化，条件 ⑤ 的“已验证新鲜”会按放宽后的标准成立。
  - `serve` 属于 M2，修复只需改一格。
- **文档位置**：`16` L923、L986；`07` L787–792；`11` L578。
- **期望的回答形态**：
  - 把 `exitCode` 从 web 允许的方向中删去（任何改动仅本机）；或者只允许新增 `exitCode: 0`。
  - 在封闭表前加一句判别原则：“收紧”以该字段缺省值下的判定为基准，任何可能使原本失败的运行变为通过的改动都属于放宽。
  - G46(ao) 补一组“web 新增非零 `exitCode` → `E_FORBIDDEN`”。

**R53-D11-02｜重要**（安装器第 2、3 阶段的 npmrc 副本不在 §16.8 规则 5 之内）

- **问题**：
  - `16` L1165 用户级 npmrc 一行，I 列写“I-install（第 2、3 阶段）用不含令牌的副本”。这是黑名单写法（去掉令牌），不是 A、V 两列采用的白名单 + userinfo 剥除 + 凭据判定。
  - §16.8 规则 5（`16` L1149）只覆盖“Agent 或验证器可读副本”，安装器不在其中。lint (p) 能通过，是因为同一行的 A 列含有两个关键词。
  - 按白名单被排除、却不属于“令牌”的内容，例如代理 URL 中的 userinfo、内联的客户端私钥，在这份副本中仍可能保留。
  - 第 3 阶段运行 `.pnpmfile.cjs` 与第三方依赖的构建脚本。`11` L458 按原则把它定义为“Agent 活动”：运行 Agent 编写或可影响内容的进程。它的输出经发布进入 depcache，验证器可读，`$GS` 预热时再复制到 Agent 可读的位置（`16` §16.8 规则 3）。
  - 副本的位置也互相矛盾：
    - `07` L550 写“I 的配置在 `$TI`”；
    - `16` L1139 规定 I-install 对 `$TI` 读写拒绝。
- **违反的不变式**：`11` §11.7.0“Tower 不会自动把机密交给 Agent 可影响的进程”（L399）。这与 ADR-176/177/178 对 Agent 可读副本统一采用白名单的理由相同。
- **为什么是重要**：
  - 这是 M1 的安装器路径（W8）。照“不含令牌的副本”实现，Tower 会自己把用户配置中的非令牌凭据交给运行第三方代码的阶段，而该阶段的产物会流向 Agent 与验证器可读的存储。

- **文档位置**：`16` L1139、L1149、L1165；`07` L550；`11` L399、L458。
- **期望的回答形态**：
  - 把规则 5 的范围改为“由用户配置生成、供 Tower 之外的任何代码读取的副本（A、I-install、V）”。I 列改为“白名单与凭据剔除同 A 列；第 1 阶段的认证行另由即时投递文件提供”。

**R53-D11-03｜次要**（网页端合同修订的三处边角：新增 exec 标准改变命令分类、修订不重算致命三要素、`env.tz` 的归类）

- **问题**：
  - **新增 exec 标准**：
    - 封闭表允许 web 新增任意命令的 `exec` 标准（`16` L984），却把修改已有标准的 `command` 列为仅本机（L987）。
    - 分类器把“与合同 `exec` 标准命令规范化后字符串相等”的命令判为 `exec.test`/`exec.build`，certainty 为 `exact`（`11` L185）。因此，一条 web 修订可以把 Agent 原本会被判为 `exec.arbitrary` 或 `opaque` 的命令，变成按 `exec.test` 的自主度处理：S2 下通常不询问，S0 下由 Goal 级 S0 授权覆盖（`11` L106）。
    - 这等于从远程放宽了自主度，而同一张表规定 `autonomy.levels` 在 web 上只能收紧（L998）。
    - 字符串相等的一行在“展开结构、逐个简单命令分类、取并集”（`11` L164）之前还是之后适用，也没有写明。
  - **致命三要素**：
    - `intent.context` 在 web 上可以任何方向修改（`16` L982）。“合同 `context` 含外部链接或粘贴的 issue 文本”是“不可信内容”一项的判定条件（`11` L519）。
    - 三要素只在批准 v1 时判定，运行中只在“因授权凑齐”时产生 Needs-You（`11` L534）。合同修订（无论本机还是远程）使三要素凑齐时是否警告，没有定义。
    - 远程 `quick_ratify` 却以“无致命三要素警告”为前提（`16` L958）。
  - **`env.tz`**：`VerifyProfile` 表把它与时限、资源字段并列为“任何方向（只影响时限与资源）”（`16` L1018）。但时区会改变与时间相关的测试结果，与列为仅本机的 `env.vars`（L1022）同类。
- **为什么是次要**：属于 M2 `serve`。远程验收另有五个条件，S2 下沙箱仍然生效。但第一处与封闭表自身“凡能放宽验证、运行命令…的字段都在仅本机一侧”的原则冲突，实现会分歧。
- **文档位置**：`16` L958、L982、L984、L987、L998、L1018、L1022；`11` L106、L164、L185、L519、L534。
- **期望的回答形态**：
  - 二选一：(a) web 新增的 `exec` 标准在本机确认前不参与 `11` L185 的分类匹配；(b) 新增 `exec` 标准改为仅本机。另写明该匹配行适用于整条命令还是逐个简单命令（建议逐个，且不短路并集）。
  - 在 `03` §3.4.5 或 `11` §11.8 写明：任何合同修订后重算三要素，凑齐时生成与批准时相同的决策块；凑齐的修订在远程返回 `E_FORBIDDEN`。
  - `env.tz` 移到仅本机一侧，或写明它为什么不改变验收依据。

**R53-D11-04｜次要**（远程审批授权的事件型失效没有可写的存放处）

- **问题**：
  - ADR-179 把 `expiresOn` 加在 `AutonomyMatrix.grants[]` 上（`02` L317），而 `AutonomyMatrix` 是 `Contract.autonomy`（`02` L263）。批准后的合同不可变：`06` L520–522 的触发器 `contracts_immutable`，以及 I3。

### D4 领域模型与生命周期

**R53-D4-01｜次要**（修订标准的改写 `review{state, pin}` → `verify{pin}` 丢了来源状态）

- **问题**：
  - ADR-178 规定：`paused` 中继续目标为 `review{state, pin}` 时，修订标准把它改写为 `{kind:"verify", pin}`（`03` L69、L167，`06` L867，`16` L35）。
  - `verify{pin}` 不携带来源状态，执行时取 `Goal.verifyFrom`，“不变”（`07` L1644）。`verifyFrom` 的写入点（`16` L34，唯一定义）包含“标准修订从 `in_review`/`accepted` 进入 `verifying` 时”，却不包含这次改写：Goal 是从 `paused` 进入 `verifying` 的。
  - 于是 `verifyFrom` 是上一次验证留下的陈旧值：
    - (a) 正常路径验收的 Goal，`verifyFrom` 通常是 `claimed`。它在 `accepted` 中暂停（例如 `external_change`），修订标准，解除后以 `from = claimed` 判定。验证通过后进入 `in_review`、全部单元需重新评审（`07` L1619），与 `03` L167 `accepted` 列“通过且其余不变 → 验收延续”相反。
    - (b) 反方向：曾经从 `accepted` 经 I2 验证、未能延续而停在 `in_review` 的 Goal，`verifyFrom` 是 `accepted`。暂停、修订、解除后以 `from = accepted` 判定（`07` L1598）。若人在此期间重看过变化的单元，`acceptanceCarriesOver` 可能成立，Goal 未经人验收就进入 `accepted`。
  - 改写之前，`verify{pin}` 只会来自 `claimed`/`verifying`，此时 `verifyFrom` 总是新鲜的，因此这是 ADR-178 引入的回退。
  - 同类的其他改写（`keep_external_change`、守卫）都用 `verify_new{returnTo: state}` 保留状态，`16` L35 也写着“改写只换目标、不丢数据”。
  - 另外，`03` L60 `accepted` 行在 ADR-178 新增的“`contract.amend` … 以新标准验证”之后紧接着写“验证通过后回 `in_review`，仅内容变化的评审单元需重新验收”，与同文 L109 的验收延续、L167 的矩阵和 `07` L1620 不一致。
- **为什么是次要**：路径窄（`accepted`/`in_review` → 暂停 → 修订标准 → 解除），不丢数据。(a) 只是多一次评审。(b) 是否成立取决于 `acceptanceCarriesOver` 的基线，该函数体在 `07` L1604 中省略；若以当前评审状态为基线，它会绕过“人的验收”，此时应按重要处理。
- **文档位置**：`03` L60、L69、L109、L167；`06` L867；`07` L1598–1604、L1619–1620、L1644；`16` L34、L35。
- **期望的回答形态**：
  - 改写的同一事务写 `goal.verifyFrom = review.state`，并在 `16` L34 的写入点中登记这一项。或者改写为 `verify_new{returnTo: state}`，但它会生成新 pin。
  - `03` L60 的那半句限定为“I2 或合并队列 rebase 引起的验证”，或删去。

**R53-D4-02｜次要**（重建卫星之后的告知、守卫与两处陈旧注释）

- **问题**：
  - **自动重建的告知**：
    - `10` L1169 写：`running` 中丢失时“先 abort → `paused(satellite_missing)`”，重建成功后“以 `steer` 告知 Agent…后恢复 Run”。`16` L291 也写“自动重建的同类告知以 `steer` 发出”。
    - 但此时 Run 已经中止，恢复是经准入开的新 Run（`03` L70 ②），没有可以 steer 的会话。手动重建用的是 `pendingOpenings` 中的开场（`06` L921），自动重建没有对应的入队规则。
  - **手动重建的告知只认继续目标 `run`**（`06` L921、`03` L94）：
    - 继续目标为 `verify`/`review`/`verify_new` 时，从更早的检查点重建后，守卫以重建的树验证并回到评审；之后 `request_changes` 开的 Run，Agent 不会得知工作目录已回到检查点 n。
    - 继续目标为 `claim{decisionId}` 时，人代为提交会提交重建后的旧树，而人作出 `claim` 决定时看到的是重建之前的状态。
  - **守卫**：`goal.rebuild_satellite` 的守卫是“`satellite_missing` 是 `pause_reason` 或在 `also_applies` 中（即自动重建已失败）”（`06` L921）。但 `running` 中丢失时，`satellite_missing` 在自动重建**开始之前**就已写入（`06` L139、`10` L1169），括注中的“即”不成立。守卫不检查 `satellite_rebuilding=1`，手动重建可以与正在进行的自动重建竞争；两次手动重建之间也没有互斥。
  - **陈旧注释**：`02` L493 与 `16` L144 的 `rebuild_satellite` 说明仍写“不开 Run、不改写继续目标”，与 ADR-178 的 `settle → run` 改写（`06` L921、`03` L69、`16` L35）矛盾。`02` 是类型的唯一来源，实现者会读到它。
- **为什么是次要**：都是低频路径，内容仍在影子检查点中。但第一处照文无法实现；第二、三处会让 Agent 的认知或人的决定与实际内容错位，实现会分歧。
- **文档位置**：`02` L493；`03` L70、L94；`06` L139、L921；`10` L1169；`16` L144、L291。
- **期望的回答形态**：
  - 自动重建成功时，若继续目标为 `run`（或曾在 `running`），同样把 `tower.satellite_rebuilt` 追加到 `pending_openings`，删去“以 steer 告知”。

### D13 隔离、git 与并发

**R53-D13-01｜次要**（接管期间从更早检查点重建后，交还与放弃改动的定义不一致）

- **问题**：
  - **交还的写回集合**：
    - `10` L894 第 6 步：接管期间 Tower 重建过卫星时，以 `humanCheckout.rebuiltTree` 作比较基准，“写回集合以它代替 T0，使卫星整体成为 T1”。
    - 但第 7 步（L910）仍写“写回集合 = `git diff --name-status -z T0 T1` 的路径…崩溃续写使用同一集合”。`06` L893 ② 写“写回集合见 `10` §10.8.4 第 7 步：…T0→T1 的差异 ∪ E”。崩溃续写行 `06` L142 写“写回集合与 `10` §10.8.4 第 7 步相同（T0→T1 的差异…）”。三处都没有 `rebuiltTree`。
    - 第 5 步（L893）的“T1 == T0 → 无改动，直接第 8 步”会在人没有改动、但卫星已从更早检查点重建时跳过写回，卫星停在检查点 n。
    - 照 `06` 实现时，人没有碰过的路径保留检查点 n 的版本，人改过的路径是 T1，卫星成为一棵谁都没见过的混合树。第 8 步把它记为 `author:"human"` 的检查点，随后被验证，甚至被 seal。这违反第 6 步自己写的“卫星整体成为 T1”，G46(aq) 的期望也会失败。
  - **放弃改动**：
    - `goal.discard_human_edits`（`06` L895）在 `takeover_from ∈ {in_review, accepted}` 且卫星树 ≠ pin 时，把差异按归因表分类，非存活进程的写入记入 `external_change`。
    - 接管期间 Tower 从更早检查点重建卫星后，这一差异全部来自 Tower 自己的重建，却会被记为来源不明的外部改动。这正是 ADR-178 为 `hand_back` 关闭的那一类误判，`discard_human_edits` 没有跟进。
    - 它也没有 `hand_back` 新增的卫星守卫（缺失或正在重建时 `E_STATE`）。
- **为什么是次要**：触发需要接管、卫星丢失、自动重建失败、从更早检查点手动重建四步，内容都在影子中。但交还的写回集合在三处定义不同，照不同处实现会得到不同的树，并把 Agent 的内容记到人的名下。
- **文档位置**：`10` L886、L893、L894、L907–910；`06` L142、L893、L895；`14` G46(aq)。
- **期望的回答形态**：
  - 第 7 步与 `06` L893 ②、L142 改为“写回集合 = `B→T1` 的差异（`B = humanCheckout.rebuiltTree ?? T0`）∪ E（仅 `take_human`）”。第 5 步的短路条件改为 `T1 == B`。
  - `discard_human_edits` 加与 `hand_back` 相同的卫星守卫。`rebuiltTree` 存在时，先把卫星恢复到 pin 的树（Tower 自己的写入），或者把 `rebuiltTree` 与 pin 的差异排除在外部改动判定之外。

### D5 Agent 架构与 Pi 集成

**R53-D5-01｜次要**（OAuth 过期的检测键与登录前提所依据的 Pi 行为与 v1.2.0 不符）

- **问题**：
  - ADR-179 按第 52 轮的观察把 D58（`05` L1362）、C39（L1411）与 F7（`06` L1171）改为“认证失效时 `prompt` 的预检先于发送，直接报认证错误”。F7 以“`prompt` preflight 的错误文本”为检测键，C39(c) 断言该文本含 `/login <provider>`。
  - v1.2.0 源码：
    - 预检（`agent-session.ts:2118-2120`）只看 `hasConfiguredAuth`。只要存有 OAuth 凭据，`checkProviderAuth` 就返回 `{type:"oauth"}`，不检查是否过期（`ai/src/models.ts:656-663`）。因此 OAuth 令牌过期时预检**通过**，Run 开始，user 消息进入会话。
    - 刷新发生在请求时：`resolve.ts:120-142` 刷新失败抛出 `ModelsError("OAuth refresh failed for <provider>")`，文本中没有 `/login`。
    - D58 引用的 “Run '/login ${provider}' to re-authenticate” 分支（2121-2128）要求 `hasConfiguredAuth` 为假而 `isUsingOAuth` 为真。但 `snapshot.auth` 与 `configuredProviders` 总是同时增删（`model-runtime.ts:343-369`、`:396-425`），这个分支实际上走不到。
    - 预检“先于发送”报错只发生在完全没有凭据时，文本是通用的 `formatNoApiKeyFoundMessage`（`auth-guidance.ts:22-25`）。
  - 后果：
    - OAuth 过期这一主要情形不会产生 F7 的检测键，而以运行期的引擎错误出现，落入 F6（`stalled{engine_error}`，可能被当作 provider 故障重试）。用户看不到登录指引。
    - C39(c) 照写会失败。
  - 另外，D58 的标题“登录只在交互界面中完成”只对 `pi` CLI 成立。SDK 宿主可以经 `AgentSession.modelRuntime`（`agent-session.ts:528`）调用公开的 `ModelRuntime.login(providerId, "oauth", interaction)`（`model-runtime.ts:826-838`，`index.ts:235` 导出），Pi 自己的 `/login` 就是调用它。R52-D5-01 选择方案 (a)“需要已安装的 `pi` CLI”是产品选择，不是 Pi 的约束，但 `05` 把 D58 作为依据登记，没有提到被放弃的方案 (b)。
- **为什么是次要**：认证过期是必然会走到的路径。照现在的检测键实现，F7 在主要情形下不会触发，用户会看到错误归类的停滞卡片；C39 也会给出与实现相反的结论。
- **文档位置**：`05` L1261、L1362、L1411；`06` L1171（F6、F7）；`15` ADR-179。
- **期望的回答形态**：
  - F7 的检测改为：预检错误（无凭据），**或**运行期错误中 `ModelsError` 的 `oauth` 类（“OAuth refresh failed”），或 Tower 在开 Run 前自行检查凭据的过期时间。F6 的根因合并排除这一类。
  - D58 与 C39 改为与源码一致：(a) 已认证时 `pi "/login faux"` 作为消息进入会话；(c) 以“已存但刷新失败的 OAuth 凭据”构造过期，断言运行期错误类型，而不是预检文本。
  - 在 `05` §5.10 注明 SDK 有 `ModelRuntime.login`，Tower 不使用它的理由（例如不在 Tower 内处理 OAuth 回调、凭据写入用户 `auth.json` 的一致性）。如果理由不成立，就改选方案 (b)。

### D7 诚实与验证

**R53-D7-01｜次要**（计划步骤字形的两处残留：`✓` 会出现在未开始的步骤上；`✕ 不一致` 用 danger 表示软矛盾）

- **问题**：
  - **`✓` 的条件**：
    - ADR-178 规定，计划步骤在“关联标准（`criteriaIds`）全部由验证器新鲜通过”时显示事实 `✓`（`12` L238）。

- **文档位置**：`12` L187、L230–232、L238；`04` L317、L348、L1071–1072；`07` L1377、L1388。
- **期望的回答形态**：

**R53-D7-02｜次要**（评论的两处残留：F4 流程仍显示“已处理”；轨迹/Watch 事件上的批注没有锚点类型）

### D14 路线图与可验证性

**R53-D14-01｜次要**（G46(ak) 对 `@corp:registry` 的期望与 §16.8 规则 5 的处理顺序相反）

- **问题**：
  - §16.8 规则 5（`16` L1149，唯一定义）的顺序是：只保留白名单的键 → URL 中的 userinfo 一律剥除 → 保留的值再经凭据判定，命中即剔除该键。
  - 按这个顺序，`@corp:registry=https://u:tok@npm.corp/` 先被剥除为 `https://npm.corp/`，再经凭据判定，不再命中，于是该键**保留**。Go 一组正是这样期望的：保留剥除后的 `GOPROXY`。
  - G46(ak) 的期望却是 `$GS/npmrc` 与 `$VS/npmrc`“只含 `registry`——`@corp:registry` 因 URL userinfo 被凭据判定剔除”。
  - npmrc 一行（`16` L1165）的写法也与规则 5 不同：只写“保留下来的值再经凭据判定（URL userinfo、token 形态），命中即剔除该键”，没有“剥除”一步。
  - 两种结果都不泄露凭据，但同一个净化器只能实现其中一种，照用例写断言的测试作者会与照规则 5 实现的代码冲突。这与 R52-D14-01 属于同一类问题。
- **文档位置**：`14` L133 G46(ak)；`16` L1149、L1165；`10` L83。
- **期望的回答形态**：二选一并统一三处：
  - (a) 先剥除再判定：G46(ak) 改为 `$GS/npmrc` 含 `registry` 与剥除后的 `@corp:registry`；L1165 补“URL 中的 userinfo 一律剥除”。
  - (b) 带 userinfo 的值整键剔除：改规则 5 的顺序，Go 组的期望同步改为不含 `GOPROXY`。
