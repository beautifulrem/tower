## 1. 总评

**第 108 轮的 8 条条目都按所问关闭**（核对见 §3）。ADR-236 守住了 “在唯一定义处细化、不另设平行机制” 的取向：
- 判定单位改为 Goal，终态不冻结；
- 失败先判可达、启动时的解除推迟与 ①②③④ 共用一次判定；
- 线程按挂载点隔离，`~/.tower` 所在卷读不出时按未知计；
- 清除只推迟不可访问的根；
- 放弃在不可达期间可用，绑定处理有了一条仅本机的命令；
- `retry.provider.timeoutMs` 取正整数并加上限；
- 退出确认框只在一处定义。

第 108 轮 §5 的 16 条观察中，15 条按所述落地，观察 6 只落了一半（`04` L1516、`03` L96 未改）。

**新命令与新规则带出的分支**。本轮的问题集中在 ADR-236 新开放的两条出口，以及第 108 轮评审自己建议的 “数据库最后删除”：
- **R109-D12-01（重要）**：“清除全部” 的根被推迟时，`~/.tower` 已清空而数据库留下。正文没有写这段时间 Tower 怎样处理，你可以照常使用。推迟的根可访问时，续做把这段时间新建的数据连同数据库一起删除。
- **R109-D13-01（重要）**：`project.relocate` 改变 `<wtRoot>` 之后，旧位置的卫星、`_gitdirs`、`_stores`、`_verify` 原样留下，但不再被任何记录引用。之后的清除只按事件中的 `roots`（当前的 `<wtRoot>`）定位，既不删除也不列出它们；旧位置的人工编辑检出与检验目录也从存储面板中消失。
- **R109-D13-02**：旧卷永久丢失时，旧路径上的人工编辑检出、使用中的检验检出仍算必需路径，迁移不能使 Goal 可达，只剩放弃——连已验证、待验收的 Goal 也只能放弃。
- **R109-D13-03**：不可达期间放弃一个带回写到一半（`syncing`）的 `in_review`/`accepted` Goal，`goal.abandon` 不清除 `human_checkout`，违反 `goals` 的 CHECK；它也与 `06` L923 “命令从不在 `syncing` 待续写的状态上执行” 相矛盾。
- **R109-D4-01**：推迟只写了 `app_quit`。只重启 Supervisor 时生成的 `engine_crash` 照常解除，继续目标为 `settle` 时在不可访问的卫星上执行 settle 序列，而 “失败先判可达” 不含 settle。
- **R109-D7-01**：验证命令以非零退出时按该 Goal 的全部必需路径判定，含验证不使用的附着检出。附着检出在网络卷上短暂停顿时，一次已观察到的失败被整次丢弃、不留 Fact，同一 pin 重跑通过即显示为已验证，与 `07` §7.4.6 “同一提交上先失败后通过绝不能显示为已验证” 相冲突。反方向的竞争（卷恢复早于判定）没有登记。

**扫描发现的其他缺口**（Pi 侧）：
- **R109-D5-01**：上限 2147483647 只加在 `retry.provider.timeoutMs`。经 getter 读取的 `httpIdleTimeoutMs`（未设置前者时它就是请求时限）与 `websocketConnectTimeoutMs` 超过上限时，是同一个立即超时、重试循环。
- **R109-D5-02**：F13 与 `05` L1062 依赖 “`tool_call` 处理器出错后 Pi 发出 `extension_error`”。Pi v1.2.0 不发，所以 gate 出错时 sentinel 条目与 “连续 3 次则暂停” 都不会触发：工具被阻断，Run 照常继续。

**对本轮重点问题的回答**：
- **`project.relocate`**：
  - 身份核对与路径规则成立（`10` §10.3.0、§10.1.1）。
  - 仅本机：成立。
  - 对用户仓库不改动：成立。
  - 进行中的 Run 与写回返回 `E_BUSY`，成立；准备、重建、接管物化未列，观察 3。
  - 旧路径上的目录与记录：见 R109-D13-01、R109-D13-02。
  - 主动迁移的作用范围：观察 4。
- **“中断还是失败”**：
  - 卷确实在验证中途消失时，判为中断成立，这正是 R108-D13-02 要的。
  - 判定的路径集合过宽，会把真实的失败丢掉；反方向的竞争没有登记。见 R109-D7-01。
  - 写回的同类竞争只会产生 `stalled{write_back_failed}`，人工编辑检出保留，不丢数据，不另立条目。
- **按挂载点的线程**：
  - 隔离本身成立：一个挂起的挂载不再使其他挂载点上的 Goal 判为不可达。
  - 启动等待在同一挂载点上要两次超时才把整个挂载点判为不可访问，实为约 10 s，观察 1。
  - `13` §13.8.1 的 Supervisor 预算（空闲 ≤ 70 MB）没有计入每个挂载点至多两个的线程，观察 2。数值是待 E6 回填的假设值，不扣分。
- **清除的推迟**：判定对象与范围按所问修正，但推迟期间 Tower 的状态没有定义，见 R109-D12-01。

### D4 领域模型与生命周期

**R109-D4-01｜次要**（推迟只写了 `app_quit`：只重启 Supervisor 时生成的 `engine_crash` 照常在启动时解除，继续目标为 `settle` 时在不可访问的路径上执行 settle 序列）

### D5 Agent 架构与 Pi 集成

**R109-D5-01｜次要**（上限 2147483647 只加在 `retry.provider.timeoutMs`：经 getter 读取的 `httpIdleTimeoutMs` 与 `websocketConnectTimeoutMs` 超过上限时，是同一个立即超时、重试循环）

- **问题**：
  - `05` L474 对 `httpIdleTimeoutMs` 与 `websocketConnectTimeoutMs` 写 “适配器以同一 getter 读取，抛出即无效”。但 getter 背后的 `parseTimeoutSetting`（`settings-manager.ts:147-156`）经 `parseHttpIdleTimeoutMs`（`http-dispatcher.ts:31-34`）接受任意有限的非负数，没有上限。
  - `retry.provider.timeoutMs` 未设置时，`sdk.ts:350` 把 `httpIdleTimeoutMs` 原样作为请求时限（`:346` 只换算 0），交给厂商 SDK 的 `setTimeout(abort, ms)`（`@anthropic-ai/sdk` 0.129.0 `client.js:668`，`openai` 7.19.0 `client.js:996`）。超过 2147483647 时 Node 按 1 ms 计，请求立即中止、报 “Request timed out”，命中 Pi 的可重试模式（`retry.ts:72-73`）。
  - 这正是 ADR-236 为 `retry.provider.timeoutMs` 加上限所依据的现象（回应 “另一处：超过 2147483647 时 Node 的定时器按 1 ms 计”）。`websocketConnectTimeoutMs` 在 Codex 的 WebSocket 连接上同理。
  - 用一个很大的数表示 “不限时” 是常见写法，而 Pi 的不限时写法是 `disabled` 或 0。
- **为什么是次要**：失败可见，几乎不计费，不丢数据，不涉及机密；但校验的目的写明是关掉这个循环，而唯一定义的取值范围放过了一类取值，C43 也没有这一组。
- **后果的类别**：设置中把 `httpIdleTimeoutMs` 写成超过上限的数时，每个 Run 都在 `provider_unavailable` 与运行之间循环，卡片写 “模型服务不可用”，而原因是本机设置。
- **文档位置**：`05` L474、L1450（D63）、L1506（C43）；`06` L1198（F4b）。
- **期望的回答形态**：
  - `05` L474 写明两项经 getter 读取的设置同样不得超过 2147483647（0 与 `disabled` 仍为不限时），超过时按 F4b、卡片原因同 `启动失败：Pi 设置 <名字> 无效`；
  - Host 启动时与每个 Run 都校验；
  - C43 补一组超过上限的取值（顺带补 `retry.maxRetries` 一组）。

**R109-D5-02｜次要**（F13 与 `05` L1062 依赖 “`tool_call` 处理器出错后 Pi 发出 `extension_error`”，Pi v1.2.0 不发：gate 出错时 sentinel 条目与 “连续 3 次则暂停” 都不会触发）

- **问题**：
  - `05` L1062（故障保护）写：“handler 抛出异常时，Pi 会阻断这次工具调用。随后 `extension_error` 会触发一条 Needs-You `sentinel`（severity 3）。连续 3 次出错时……暂停该 Goal，不会在 gate 失效的情况下继续运行。”`06` L1207 F13 的检测列写 `extension_error`（tower-goal），ADR-236 又写明 “按 `extension_error` 的 `event` 区分”；`05` L649 把 `extension_error` 映射为 sentinel 条目。
  - Pi v1.2.0 中：
    - 只有通用的 `emit` 捕获处理器异常并 `emitError`（`runner.ts:1100-1120`），`turn_start` 走这里；
    - `emitToolCall`（`runner.ts:1249-1267`）没有 try/catch，`agent-session.ts:667-681` 只重新抛出，`agent-loop.ts:770-776` 把它转为一条错误的工具结果；
    - 所有 `emitError` 的调用处都没有 `event: "tool_call"`。
  - 所以 “阻断这次工具调用” 成立（fail-safe 不受影响），但 Tower 收不到 `extension_error`：sentinel 条目不出现，“连续 3 次” 不计数，Run 在每次工具调用都被阻断的状态下继续，直到停滞检测或预算上限介入。
  - 这一依赖在 ADR-236 之前就有，第 108 轮观察 5 的修法把它写得更具体。
- **为什么是次要**：工具确实被阻断，安全不变式成立，不丢数据；但 `05` L1062 写明的保证 “不会在 gate 失效的情况下继续运行” 照文字实现不成立，人也得不到告知，只是浪费预算与时间，并由其他检测兜底。
- **后果的类别**：gate 出错（例如 tower-goal 的内部异常）时 Goal 持续运行、每次工具调用都返回错误，消耗预算，界面上没有 sentinel 条目。
- **文档位置**：`05` L649、L1062、§5.6.5；`06` L1207（F13）；C5（`05` §5.11）。
- **期望的回答形态**：
  - F13 的检测改为 tower-goal 自己报告：`tool_call` 处理器内部捕获异常，经 bridge 报给 Supervisor 计数，再抛出以保持 Pi 的阻断；`extension_error` 只用于 `turn_start` 等经通用 `emit` 的事件；
  - `05` L1062 同步改写，并引 `runner.ts:1249-1267`、`agent-loop.ts:770-776`；
  - C5 加一条断言：`tool_call` 处理器抛出时没有 `extension_error`，Tower 的计数仍然增加。

### D7 诚实与验证

**R109-D7-01｜次要**（验证命令以非零退出时按该 Goal 的全部必需路径判定，含验证不使用的附着检出：已观察到的真实失败可能被整次丢弃，同一 pin 重跑通过即显示为已验证；反向竞争没有登记）

- **问题**：
  - **(a) 路径集合过宽**：
    - `06` L139 的 “失败先判可达” 对 “验证命令以非零退出” 判定 “该 Goal 的必需路径”，即各 binding 的附着检出、`WorktreeRecord` 所在的 `<wtRoot>` 与人工编辑检出。
    - 验证在 `<wtRoot>/_verify/` 的槽位中运行（`10` L249），不读附着检出——它只在验证开始前用于播种本地文件。
    - 有一种布局很常见：用户仓库在网络卷或外接盘上，`worktreeRoot` 改到本机（`10` §10.4.3 本就建议不放在同步或网络位置）。这时附着检出一次超过 5 s 的 `stat`（`06` L139 已登记 “不做第二次采样”）会使一次真实的失败被判为中断：不写 `verify.result` 与 Fact，不计返工，可达后以同一 pin 重跑（`07` L498）。
  - **(b) 与 §7.4.6 的冲突**：
    - `07` L854 的原则是 “改动引入的竞态恰好表现为‘同一提交上先失败后通过’，绝不能因此显示为已验证”。§7.4.6 依靠同一次验证中的重跑与 base 确认来识别它。
    - 被丢弃的那次失败不留任何 Fact，重跑若一次通过，就直接显示为已验证，没有可比对的失败观察。
    - 应用退出或磁盘满时取消验证也会重跑，但那时结论还没得出。这里丢弃的是一个已经得出、可能真实的失败，判据是一条与验证无关的路径。
    - `07` L463–466 的伪代码在 `runCriterion` 之后立即 `recordFact`，也没有体现 L498 的判定。
  - **(c) 反向竞争没有登记**：卷短暂停顿使验证以 `EIO` 失败，判定时卷已恢复，于是按真实失败记录：计返工、计入失败上限，Agent 被要求返工。`07` L498 只为 `ENOSPC` 登记了同类竞争（“如实登记”），路径不可访问一支没有。
- **为什么是次要**：要一次真实失败与一次与之无关的路径停顿同时发生，重跑才可能掩盖不稳定；Agent 难以有意触发；写回的同类竞争只产生 `stalled{write_back_failed}`、不丢数据。但 (b) 触及 `07` §7.4.6 写明的 “绝不能”，(c) 与已登记的磁盘满一支不对称。实现会在 “按全部必需路径” 与 “按验证实际使用的路径” 之间分叉。
- **后果的类别**：
  - 改动引入的偶发失败在罕见的时序下被标为已验证（有条件、无保留的绿色）；
  - 卷短暂停顿造成的失败被记为 Agent 的失败，消耗返工次数。
- **文档位置**：`06` L139（失败先判可达）；`07` L463–466、L498、L854–L876；`10` L249、§10.4.3。
- **期望的回答形态**：
  - “失败先判可达” 对验证一支只判定该次验证实际使用的路径（槽位所在的 `<wtRoot>`），对写回只判定来源与目标；
  - 或者被判为中断时仍把已观察到的失败（`failedIds`）记为一条 Fact，同一 pin 重跑时按 §7.4.6 视为一次已观察的失败；
  - 在 `07` L498 的磁盘满一句旁登记反向竞争，或写明判定时卷已恢复的处理；伪代码在 `recordFact` 之前加判定。

### D12 记忆与学习（隐私）

**R109-D12-01｜重要**（“清除全部” 的根被推迟时，`~/.tower` 已清空而数据库留下：推迟期间 Tower 的状态没有定义，可以照常使用；推迟的根可访问时，续做把这段时间新建的数据连同数据库一起删除）

- **问题**：
  - ADR-236 之后，`06` L143 与 `09` L575 写：不可访问的根推迟，“`~/.tower` 中的副本与可访问的根立即删除”，推迟的根 “随 30 s 的复查……可访问时续做”，“全部完成才追加 `filesDone: true`”，“`all` 档的数据库在全部完成之后才删除”。`09` L569 的 `all` 档清单是 “删除 `~/.tower` 中的全部内容……以及各 `<wtRoot>` 下 Tower 创建的目录”。
  - 在 ADR-235 之前，续做在接受界面命令之前完成（`06` L116），不存在 “清除已开始而 Tower 仍在使用” 的时段。现在这一时段没有上限——外接盘可能几个月后才插上，或再也不插上——而正文没有写这期间 Tower 的状态：既没写 “清除全部” 之后应用怎样重新开始，也没写有未完成的 `all` 档时是否允许新建 Project 与 Goal。
  - 照字面实现：
    - 清除之后数据库仍在、`~/.tower` 其余内容已删，Tower 照常启动并接受命令；
    - 你重新添加项目、新建 Goal，它们的影子、会话与证据写进新的 `~/.tower/goals/*`，状态写进同一个数据库；
    - 推迟的根可访问后，续做按 `all` 档的清单幂等执行（“删除 `~/.tower` 中的全部内容”），全部完成后删除数据库。这段时间新建的全部数据随之删除。
  - `project` 档有同类但较轻的一支：ProjectId 由身份哈希得出（`02` L47、L78），再次添加同一项目得到同一个 id；续做按清单重新删除 “该 Project 的镜像库” 时，删掉的是重新添加之后的镜像（之后按情形 G 恢复，补不回的检查点标为不可用）。
  - 这一后果是第 108 轮评审建议的写法（“`all` 档的数据库最后删除”）与 ADR-235 引入的推迟叠加而来，评审与回应都没有注意到推迟期间的状态。
- **为什么是重要**：照文字实现会丢失你的工作——清除之后新建的 Goal 的检查点、会话与全部记录，在一次与它们无关的事件（插上旧盘）之后被删除，事先没有任何提示。触发条件是 “清除全部时某个根不可访问”，这并不罕见（想清空 Tower 重新开始时，旧外接盘常常不在手边）。
- **后果的类别**：用户工作与 Tower 记录的不可恢复删除（影子中的检查点与会话随之删除，卫星中的文件留下但失去全部记录）。
- **文档位置**：`06` L116、L143、L952；`09` L569、L572–L575；`02` L47、L78；`10` §10.16.2 情形 G。
- **期望的回答形态**（任选其一，写在 `06` L143 的唯一定义处）：
  - `all` 档的数据库与 `~/.tower` 立即删除，推迟的根记在库外一个只含路径的小文件中（同 `goal-id-hwm` 的做法），续做只消费这个文件、只删除这些根下 Tower 创建的目录；
  - 或者有不可访问的根时，`all` 档在执行之前列出这些根，让你选择 “现在只清除可访问的部分、这些根之下的目录列入结果由你删除” 或取消；
  - 两种做法都要写明：续做只作用于推迟的根，不再重新执行 `~/.tower` 部分；`project` 档的续做不重新删除按 ProjectId 定位、可能已被重新添加的同一项目所用的 `~/.tower` 内容；
  - 写明 “清除全部” 完成后应用的状态（如重新开始首次运行）。

### D13 隔离、git 与并发

**R109-D13-01｜重要**（`project.relocate` 改变 `<wtRoot>` 之后，旧位置的卫星、`_gitdirs`、`_stores`、`_verify` 原样留下而不再被任何记录引用：之后的清除既不删除也不列出它们；旧位置的人工编辑检出与检验目录从存储面板中消失）

  - `06` L921：`<wtRoot>` 随之改变的按情形 F 在新位置重建卫星，“旧位置的目录 Tower 不删除、原样留在原处（`10` §10.2）”。但 `10` §10.2 的 “人的工作现场不自动删除”（L259）只覆盖 `_human`、`_inspect` 与各 `.kept-*`。旧卫星是一个普通的 `<goalId>` 目录，旧的 `_gitdirs/<goalId>`、`_stores/<goalId>` 也不在其列，情形 F（`10` L1267）没有写它们的去向。
  - 迁移之后 `WorktreeRecord` 指向新位置，`Project.worktreeRoot` 已被覆写：
    - **清除**：`roots` 是 “该 Goal 各 binding 的 Project 与 `<wtRoot>`”（`06` L952），即当前的 `<wtRoot>`，清除与续做 “只按事件中的 `id` 与 `roots` 定位”。旧位置的副本既不删除，也不在 “清除之后仍可能存在的副本”（`09` L572 起）中列出。
    - **列出**：已脱离副本的 “列出的来源” 是 “每个已知 Project 的 `<wtRoot>`”（`10` L259），旧 `<wtRoot>` 不再已知，于是旧位置的 `_human`、`_inspect` 与 `.kept-*` 从 Goal 页 `保留的目录` 与存储面板中消失；`goal.delete_kept` 要求路径在某个已知 Project 的 `<wtRoot>` 之下，也删不到它们。
    - **到期删除**：卫星的到期删除只按记录进行，旧卫星永不删除。
  - 每一次改变 `<wtRoot>` 的迁移都会产生这些副本——主动迁移时它们完好且可删，旧卷丢失时它们至少应列出。
- **为什么是重要**：照文字实现会违反两条写明的承诺：
  - `09` §9.12.4 “删除 Tower 自有的、可能含该 Goal 内容的全部副本”，无法删除的 “清除结果如实列出”；
  - `10` §10.2 “Tower 不删除它们，只把人指到它们”。
  清除之后，完整的代码副本与 Agent 写过的内容留在旧位置，清除结果却显示已完成。
- **后果的类别**：隐私清除不完整且不告知；人的工作现场脱离 Tower 的列出与删除入口；磁盘占用不可见。
- **文档位置**：`06` L921、L952；`09` L567–L569、L572 起；`10` L259（列出的来源）、L1267（情形 F）、§10.3.2（到期删除）。
- **期望的回答形态**：
  - `project.relocate` 把旧位置记下来：例如旧 `<wtRoot>` 继续列入该 Project 的已知 `<wtRoot>` 集合（供列出与 `goal.delete_kept`），并写入之后 `privacy.purged` 的 `roots`（不新增字段：`roots` 本就是列表）；
  - 或者迁移时把旧卫星、`_gitdirs`、`_stores` 按 `10` §10.2 “Tower 自动改名保留” 的形状改名为 `.kept-*`（可访问时），使之进入已有的列出规则；不可访问时在迁移结果与之后的清除结果中列出完整路径；
  - 情形 F 补一句旧位置目录的去向。

**R109-D13-02｜次要**（旧卷永久丢失时，旧路径上的人工编辑检出、使用中的检验检出仍算必需路径，迁移不能使 Goal 可达：出口只剩放弃，连已验证、待验收的 Goal 也只能放弃）

- **问题**：
  - `06` L139 的必需路径含 “它的人工编辑检出（……`<wtRoot>` 经 `project.relocate` 改变之后仍按原路径计）”，以及 “未删除的卫星、检验检出或验证目录记录（`WorktreeRecord`）所在的 `<wtRoot>`”。`WorktreeRecord.role` 含 `inspect` 与 `human`（`10` L284）。情形 F 只在新位置重建卫星，正文没有写迁移是否结束旧的 `inspect`、`human` 记录。
  - 外接盘连同仓库、`<wtRoot>` 一起丢失时：
    - `paused(human)` 的 Goal，人工编辑检出在丢失的盘上；
    - `in_review` 的 Goal，有一个使用中的检验检出在丢失的盘上。
    迁移到新克隆、新 `<wtRoot>` 之后，它们仍然不可达。
  - 本可使用的出口都被 ③ 挡住：
    - `goal.discard_human_edits` 本已支持 “检出已丢失”（`06` L914）；
    - `inspect.close` 本已支持 “使用中而目录已不存在时照常结束检验”（L924，`10` §10.2）；
    - 已有的 “人工编辑检出丢失” 一行只在可达时执行（④）。
  - 情形 D 的触发写的是 “情形 C 中人确认原路径不会再出现”（`10` L1265），但这一确认没有命令，也不产生任何效果。于是唯一的出口是放弃：一个已验证、只等验收的 Goal 只能放弃，之后由你手动从影子取分支或复活为新 Goal。
- **为什么是次要**：不丢已有的工作（检查点在影子中，分支可取出，可以复活），不涉及机密；丢失的人工编辑本就随盘丢失。但 ADR-236 把迁移定为永久不可达时的出口，而这一类 Goal 恰恰在最常见的布局下（人工编辑检出与检验检出默认在附着检出的父目录下，与仓库同盘）走不通；实现会在 “迁移时结束旧记录”“永远冻结” 之间分叉。
- **后果的类别**：外接盘丢失后，待验收的 Goal 不能验收，接管中的 Goal 不能放弃改动后继续，只能放弃整个 Goal。
- **文档位置**：`06` L139、L914、L921、L924；`10` L284、L1265、L1267、§10.2。
- **期望的回答形态**：
  - 写明 `project.relocate` 对旧位置记录的处理：它结束旧的 `goal` 角色记录；对 `inspect`、`human` 角色，在你确认 “原路径不会再出现” 时（即情形 D 的确认，可作为 `project.relocate` 的确认项），把这些旧路径交给已有的丢失处理（人工编辑检出丢失一行、`inspect.close` 的 “目录已不存在”）；
  - 或者允许只写数据库的 `goal.discard_human_edits` 与 `inspect.close` 在 “只有这些路径不可访问” 时执行；
  - 或者如实登记这一类 Goal 只能放弃。

**R109-D13-03｜次要**（不可达期间放弃一个带回写到一半的 `in_review`/`accepted` Goal：`goal.abandon` 不清除 `human_checkout`，违反 `goals` 的 CHECK；也与 `06` L923 “命令从不在 `syncing` 待续写的状态上执行” 相矛盾）

- **问题**：
  - 卷在 `inspect.bring_back` 的写回中途消失时，② 写 “数据库中的 `syncing`……原样保留”。“写回进行中” 的定义是 “这次写回正在本进程中执行”（L923），写回停止后不再算进行中，所以 `goal.abandon` 不返回 `E_BUSY`。③ 现在允许 `goal.abandon`。
  - `goal.abandon`（L942）只在 “从 `paused(human)` 放弃时另清除 `human_checkout`”。`goals` 的 CHECK（L506–L507）只允许 `human_checkout` 在 `paused(human)` 或 `syncing` 的 `in_review`/`accepted` 时非空。所以从 `in_review`/`accepted`（`syncing`）转到 `abandoned` 的事务违反 CHECK、被回滚——ADR-236 给出的唯一出口失败。
  - L923 另写 “命令与自动转移从不在‘写回已不在进行而 `syncing` 仍在’的状态上执行，DDL 的 CHECK 只需要允许写回中的 `in_review`/`accepted`”。ADR-236 允许的 `goal.abandon`（以及作用于这些 Goal 的 `project.relocate`）恰好在这个状态上执行，这句话已不成立。
  - 在 ADR-236 之前不会出现这种组合：③ 挡住放弃，F8 只读期间挡住所有写数据库的命令，崩溃之后的续写在接受命令之前完成。
- **为什么是次要**：不丢数据，检验目录本就保留；实现者在测试中会撞上约束错误。但这是 ADR-236 新开放的出口与已有不变式的直接矛盾，修法有 “放弃时清除”“放弃时 `E_BUSY`”“改 CHECK” 三种，会分叉。
- **后果的类别**：带回中途拔盘、之后放弃该 Goal 时得到内部错误，Goal 留在冻结状态。
- **文档位置**：`06` L139 ②③、L506–L507、L923、L942。
- **期望的回答形态**：
  - `goal.abandon` 一行补：从 `in_review`/`accepted` 放弃而 `human_checkout.syncState='syncing'` 时，同一事务清除 `human_checkout`（检验目录按 ADR-228 保留，写回到一半的卫星随 Goal 进入终态、按终态的到期删除处理）；
  - L923 的不变式改为 “……只在本进程写回中、崩溃到重启之间、F8 只读期间与该 Goal 不可达期间存在；不可达期间只有 `goal.abandon` 与 `project.relocate` 可以在其上执行，前者清除它”，并写明 `project.relocate` 对 `syncing` 的 Goal 是 `E_BUSY` 还是照常。

### 不扣分的观察

1. **启动等待的上界与符号链接**：`13` L130 写 “各挂载点并行、每个至多 5 s，所以……至多推迟约 5 s”。按同节的规则，同一挂载点上第一个路径超时后另起线程执行下一个路径，“再次超时时” 才把整个挂载点判为不可访问，所以一个挂起的挂载使命令的受理推迟约 10 s。同理，两条经符号链接指向同一个挂起卷的路径会触发第二次超时，使链接所在挂载点（通常是启动卷）上的全部路径判为不可访问——比 “只多占该组一个线程” 的登记更宽。不丢工作。宜改为 “约 10 s”，或第一次超时即把该挂载点上排队的路径判为不可访问；符号链接一句如实改写。
2. **新线程的内存**：`13` §13.8.1 的 Supervisor 预算（L173，空闲 ≤ 70 MB、负载 ≤ 120 MB，“SQLite 页缓存 32 MB、投影、合并器”）没有计入每个挂载点至多两个的 `worker_thread`，每个都是一个独立的 V8 isolate。数值是待 E6 回填的假设值，宜写明线程按需创建、空闲时退出，或在该行注明。
3. **`project.relocate` 的 `E_BUSY` 集合**：只列 “活跃 Run 或写回进行中”。准备中（`10` §10.3.1 正在旧 `<wtRoot>` 创建卫星）、卫星重建中（`satellite_rebuilding=1`）、接管物化中、验证进行中，与情形 F 的重建并发时会留下两份卫星或记录。实现者会自然补上；宜写一句 “这些情形同样 `E_BUSY`，或按 ② 取消后重做”。
4. **主动迁移的作用范围**：没有附着检出不可访问的 binding 时，`project.relocate` 作用于 “全部非终态 Goal 的 binding” 并记为默认检出。在一个有多个附着点的 Project 中，移动一个检出会把附着在其他检出上的 Goal 一并改指，它们的 seal 目标随之改变、卫星按情形 F 重建。正文写得明确，不会分叉，是取舍；宜加一个 `fromCheckoutPath`（默认当前的默认检出），只改附着在它上面的 binding。
5. **情形 F 与迁移的细节**：
   - 情形 F（`10` L1267）写 “作为新 Run（reason `resume`）”，迁移现在会对 `in_review`、`accepted`、`verifying`、`paused(human)` 的 Goal 触发它，宜写明分叉出的会话供下一次 Run 使用、迁移本身不开 Run；
   - `06` L921 的 “`restoreCheckpoint(最新)`” 读起来像覆盖了情形 E 接管期间 “只用接管时的检查点 k” 的规则，宜改为 “重建来源按情形 E”；
   - “默认检出” 在 `02` 与 `projects` 的 DDL 中没有落点（应在 `settings` JSON 中），选择顺序 (2)（`10` L40）也不检查它是否可访问。
6. **终态集合**：`06` L139 写 “终态 Goal（`integrated`、`archived`、`abandoned`）”，而 `16` L21 的唯一定义是 “终态：`archived`、`abandoned`”，`06` L942 与 `09` L560 也把 `integrated` 当作非终态。L139 给了显式列表，判定本身不会分叉；但 `project.relocate` 的 “非终态 Goal 的 binding” 是否含 `integrated` 随之不清。宜在 L139 写 “`integrated`（宽限期内）、`archived`、`abandoned`”，不称之为终态。
7. **备份 bundle 会读用户检出**：`06` L139 ③ 把备份 bundle 归入 “只涉及 `~/.tower` 的” 后台工作，但 `10` L1281 的选择规则执行 `git -C <userCheckout> branch -r --contains <baseCommit>`。不可达时这条命令失败或挂起（子进程，不阻塞事件循环）。宜写明不可达期间沿用上一次的 thin/full 选择或直接取完整 bundle。
8. **情形 D 的克隆命令**：`10` L1265 让界面给出 `git clone <normalizedRemote> <新位置>`。`Project.identity.remotes` 是 “去协议、去 .git、小写 host” 的别名（`02` L82），作为命令它会被 git 当作本地路径。`10` L1293 仍写 “恢复（情形 B、D）：从 `normalizedRemote` 克隆”，没有写由谁执行，与 “Tower 不替你克隆” 不一致。宜改为 “请从你的托管服务克隆（远端为 <别名>）”，并对齐 L1293。

   - `04` L1516 与 `03` L96 仍无条件写 `提供方可能已恢复？[重试]`（第 108 轮观察 6 的另一半）。
   - `04` L980 的示例 `启动失败：Pi 设置 retry.provider.timeoutMs 无效（须为正整数）；请先在 Pi 设置中改正再重试` 与 `12` L435 的模板不同，“须为正整数” 对两项次数不对，也漏了上限。
   - 唯一定义都在 `06`、`12`，不会分叉，宜对齐。
10. **引文细节**：
    - `agent-session.ts:3795` 是 `this._retryAttempt > settings.maxRetries`（`:1204` 才是 `>=`），ADR-236、回应与 `05` L474 写成 `>=`；
