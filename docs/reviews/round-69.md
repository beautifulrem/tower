**R69-D13-02｜次要**（镜像以 `'+refs/heads/*:refs/user/heads/*'` 获取用户分支，不带 `--prune`；而 `10` §10.17.1 的保留表写这些 ref “随用户删除分支”，ADR-196 观察 2 又明确依赖 “不 prune”。不 prune 时，用户删除的分支永远留在镜像中；分支名出现目录 / 文件冲突时，镜像获取一直失败，正文没有出路）

- **问题**：
  - **两处相反的定义**：
    - `10` L309：`GIT_DIR=<mirror> git fetch --no-tags <userCheckout> '+refs/heads/*:refs/user/heads/*' '+refs/remotes/*:refs/user/remotes/*'`，不带 `--prune`。
    - `10` L1268 保留表 “删除” 列：“随用户删除分支；被 rebase 掉的旧提交由此变为不可达”。
    - `09` L570 与 `15` L2740（ADR-196 观察 2）以 “获取命令不带 `--prune`” 为依据，写 “这些副本不随‘清除一个 Goal’删除，清除该 Project 或清除全部时随镜像库删除”。
  - **不 prune 的后果**：
    - **增长**：用户删除的分支在镜像中永不删除，它们独有的对象也永不回收。`10` L1281 的增长估计与上限提示（“可对已归档或已放弃的 Goal 执行‘清除一个 Goal’”，每个 Goal 约 1–5 MB）都没有计入这一来源。
    - **获取失败**：用户删除 `feature` 后新建 `feature/x`（或反之）时，镜像中残留的 `refs/user/heads/feature` 使 `refs/user/heads/feature/x` 无法创建。git 对这一 ref 报错，获取以非零退出。
      - 下一次获取残留仍在，所以从此每次都失败。
      - `10` L307–310 只为远端获取写了失败去向（按 `baseTip` 取值并记 Fact），用户检出的获取失败没有去向。
      - 镜像是 Tower 私有的，人无法自行修复。实际后果是该 Project 的新 Goal 准备一直失败，直到清除整个 Project。
  - 实现者会各自选择 “加 `--prune`”（与 `09` L570 冲突）或 “保持不 prune”（与 L1268 冲突、有上述失败）。
- **为什么是次要**：不丢数据；触发需要特定的分支命名变化。但它会让一个 Project 停摆，而且两处正文的说法相反，ADR-196 的清除说明又建立在其中一种之上。
- **文档位置**：`10` L307–310、L1262–1281；`09` L570；`15` L2740。
- **期望的回答形态**：二选一，写在 `10` §10.17.1（唯一定义），`09` L570 随之改写：
  - **加 `--prune`**（只作用于 `refs/user/*` 两个目标命名空间）：保留表一行照旧，`09` L570 改为 “用户删除这些分支后，下一次获取时从镜像删除”；
  - **保持不 prune**：保留表改为 “不随用户删除分支；只随清除 Project 或清除全部删除”，并写出冲突处理——获取前删除与新 ref 名冲突的旧 `refs/user/*`，或获取失败时以该 ref 名列出并重试；增长估计补入这一来源。

### D4 领域模型与生命周期

### D6 系统架构与可靠性

**R69-D6-01｜次要**（ADR-196 把 “该 Goal 的 `privacy.purged` 事件” 定为已清除 Goal 的唯一判据：它决定 Goal 是否从列表中隐藏、能否复活。但该事件没有载荷定义，“彻底忘记一条记忆” 也追加同名事件。清除横跨一个数据库事务与大量文件删除，中途崩溃没有续做规则）

- **问题**：
  - **判据的载荷未定义**：

    - 若实现者按 “`goal_id = G` 且 `type = privacy.purged`” 判定，进行中的 Goal 会从看板上消失，也无法复活。正文没有给出区分两者的字段（如 `scope`）。

- **为什么是次要**：没有安全或人的改动受影响。但这是隐私承诺的唯一定义，判据又被 ADR-196 设为唯一来源。

  - **不扣分的观察**：
    1. **“删除卫星时” 对保留的检验目录**：`10` L442 只对 `_human` 写 “有未交还改动时先询问”，`_inspect` 只写 “仍存在的……（§10.8.3）”。终态 Goal 仍留有的检验目录正是人选择 “保留目录，稍后决定” 的那些（`09` L557），归档时与放弃 7 天后会走到这一行。按 §10.8.3 第 7 步（唯一定义）先比较并询问即可不出错。建议在该行明写 “`_inspect` 按 §10.8.3 第 7 步先比较并询问”。
    2. **被保留的 H 与检验目录**：
       - 二者创建时已设系统备份排除（`06` L1082、`10` L539），ADR-184 保留后 “不再由 Tower 管理”，排除标记仍在。放弃确认框与清除结果没有提示 “此目录不在系统备份中”。`11` T24 以 “可重建” 说明排除，对这两类不成立。

    4. **墓碑 Goal 行的措辞**：`09` L558 “只留标识、状态与时间”，而 `owner`、`kind`、`risk_tier`、`counters`、`engine_prefs`、`stop_condition_silences` 等列仍在。这些都不是人写的文本，建议改为 “置空人写的文本列”。
    5. **重复墓碑化**：已被 “彻底忘记” 墓碑化的决定，在之后的 “清除一个 Goal” 中再次更新时会被守卫拒绝（`06` L646 要求原 payload 无墓碑），整笔清除中止。建议在 `09` L558 注明 “只更新尚未墓碑化的行”；对已清除的 Goal 再次清除时直接返回已清除。
    6. **M2 的分叉**：“分叉为新 Goal”（`10` L802，M2）以 `createBranchedSession` 复制源会话从根到分叉点的全部条目，新会话行的 `parent_session_id` 指向源 Goal 的会话。届时清除源 Goal 会被外键拒绝，复制的对话也不在清除范围内。M2 设计时一并处理即可。
    7. **`payload_hash` 保留**：墓碑化后事件仍保留未加盐的 `sha256(canonicalJSON(payload))`（`06` L396）。对低熵载荷（如简短的作答），拿到数据库的人可以验证猜测的内容。建议在 “清除之后仍可能存在的副本” 中列出，M2 计算哈希链时考虑以本机密钥做带密钥哈希。
    8. **“清除全部” 未列出**：钥匙串中 Tower 写入的模型提供商密钥与云 SDK 凭据（`11` L509），以及 Electron `userData`（`06` L1037）。建议列出，或提供一并删除的选项。
    9. **`07` §7.4.10 排队表**：c = 1 一行 ρ = 0.79、λ = 0.11 意味着服务时间约 7.18 min，Erlang C 给出 Wq 均值约 27 min、p95 约 94 min；表中为 26 / 79 min，“claimed → in_review p95 ≈ 90 min” 也应在 100 min 左右。L987 把 90 min 称为 “验证排队 p95”。该行不是承诺场景，结论不变。

        - `13` L262 写 “日增长 ≤ 260 MB” 与 “30 天窗口峰值 ≤ 3 GB”，但 0.85 × 260 MB × 30 天 ≈ 6.6 GB（按约 22 个工作日也约 4.9 GB），3 GB 只在日增长 ≤ 约 115 MB 时成立；M1（约 30%）不受影响。

    12. **`08` 的三处小出入**：
