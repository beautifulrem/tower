## 1. 总评

**第 87 轮的 5 条次要条目都已按所问关闭**（核对见 §3）。R86-D6-01 随 R87-D6-01 一并关闭：两份清单合起来覆盖 `06` §6.3 DDL 的全部 28 张表，每张表恰好出现一次（`retention_guard`、`events`、`payloads` 单列）。§5 的 15 条观察全部落地。

**ADR-215 的主体成立**（§3.3）：
- **内置 MCP 的来源自检**：判定条件、时机、出口与 Pi 的取代机制逐一吻合；取最严的一支（取代者启用期间不开 Run），与 ADR-187 对同名 Tower 工具的处理一致。
- **全局根查询的 60 s 时限**：归入第 ③ 步、计入 120 s，Run 之外有 “无法确定” 与 `[重试]`，到时终止进程组；`03` L97、`06` F4b、`10` L381、`16` L23/L29、`13` L129、`00` L100 一致。
- **接管守卫**：写进了转移的唯一来源 `03` L81，`nested_repo_live` 的出口在 `03` L87、L102，`06` L238、L904，`10` L204，`16` L31、L45、L178，`14` G26c 一致；`04` L595、L664、L933 与 `12` L424 有置灰与后果提示。
- **重建**：改为 “由事件重放的表” 正清单加 “其余一律沿用”，表的覆盖由构造保证，“第三次不完整” 的那类问题不会再以同样方式出现。

**ADR-215 带出或暴露的新问题**：
- **共享空目录在多个 Host 之间的关系**（R88-D11-01）：
  - 默认每个 Goal 一个 Host（`06` L42），同时可有多个 Run；`~/.tower/mcp-cwd/` 却是全机一个路径，每次任一 Host 启动前都被删除并重建；
  - 于是 “写进其中的东西不越过一次 Host 的生命周期”“只有打包模式下同一 Host 的其他 Goal 受影响” 不成立：已在运行的 Host 之后启动的服务器（交接、恢复时的新会话）落进另一个 Host 刚建的目录；
  - 另一个 Goal 每开一次 Run，其他 Goal 中正在运行的服务器就失去工作目录；删除与重建之间的窗口里启动的服务器失败，stdio 没有自动重连。
- **相对路径 forbid 的实际范围远大于披露的代价**（R88-D11-02）：
  - 对未写 `cwd` 的 stdio 服务器，任何含 `/` 的字符串参数都解析进 `mcp-cwd`，按写处理，硬 forbid、不可授权覆盖；
  - 这包括 `owner/repo`、分支名、MIME 类型、远程仓库中的文件路径等本不是本地路径的参数；而 `00` §0.5.1 与 `11` L222 只把代价写成 “代码智能类服务器须写绝对 `cwd`”。
- **观察 1 的 “这类选项置灰” 范围未定，与 ADR-215 自己写的出口列表冲突**（R88-D4-01）：
  - `resume` 对 `nested_repo_live` 与 `sentinel.override` 都 “改写继续目标”，照字面都应置灰；那样 `nested_repo_live` 只剩放弃，被保留的 `input_mutated_after_gate` 也只剩放弃；
  - 而 `pendingHandBack.mode = reverify` 时，附转向的 `resume` 不让 Agent 运行，先做一次必然被 run 类命中挡住的验证。

**全范围扫描**在 ADR-215 之外新发现：
- **重建的正清单仍有两处没有定义**（R88-D6-01）：
  - 隐私清除与 “彻底忘记” 留下的 Goal 墓碑行与决定墓碑行，其事件已墓碑化、没有载荷，无法重放，而 `09` L560 明写保留它们是为了让外键仍然成立；
  - “不由任何事件载荷承载的列” 以列为粒度，而 `human_checkout`、`counters` 这类 JSON 列只有部分字段由事件承载，写回中途的崩溃恢复正依赖其余字段。

### D11 安全与自主度

**R88-D11-01｜次要**（`~/.tower/mcp-cwd/` 是全机一个目录，却在任一 Host 启动时删除并重建；默认模式下多个 Host 并发时，声称的 “不越过一次 Host 的生命周期” 不成立，其他 Goal 中正在运行的服务器还会失去工作目录）

- **问题**：
  - **前提**：
    - 默认每个 Goal 一个专用 Host（`06` L42），并发 Run 默认上限 3；Host 只在 Goal 有活跃 Run 时存在，所以每开一次 Run 往往就有一次 `host.spawn`。
    - `towerMcpTransport` 以固定路径 `~/.tower/mcp-cwd/` 求工作目录（`05` L438），每次 `host.spawn` 时 Supervisor 把它删除并重建（`11` L222 (a)）。
  - **正文声称的界限**：
    - `11` L222 (a)：写进其中的东西 “不越过一次 Host 的生命周期（打包模式下同一 Host 承载的其他 Goal 在这期间仍可能受影响）”；
    - `00` L99 的理由列：“清空与相对路径的检查使写进空目录或你检出中的东西不影响之后启动的服务器”；
    - 回应的 “偏离” 也只承认打包模式下同一 Host 的情形。
  - **实际上**：
    - 已在运行的 Host 之后启动的 stdio 服务器（交接与恢复时的新会话会重新连接，`extensions/mcp/index.ts:1114`；扩展在会话中途注册的服务器），落进的是另一个 Host 刚建的目录。两个 Goal 的服务器在此后共用它，直到下一次任一 Host 启动。所以写进去的东西的寿命是 “到下一次任一 Host 启动”，影响范围是 “这期间任一 Host 启动的服务器”，与是否打包无关。
    - 另一个 Goal 每开一次 Run，其他 Goal 中正在运行的服务器的工作目录就被删除。`11` L222 只写了它们 “看不到新目录”，没有写后果：常见的运行时在工作目录被删除后取当前目录会出错，按相对路径解析的操作随之失败，服务器可能报错或退出。
    - 删除与重建之间的窗口里，另一个 Host 恰好启动的服务器会因工作目录不存在而启动失败。stdio 没有自动重连（`runtime.ts:343` 只有 HTTP 重试），该服务器在这个会话中一直是 `failed`。
  - **后果的类别**：
    - 安全一侧：一个 Goal 中经批准的写入（只剩单个文件名这条路径，偏离中已承认）或服务器自己的写入，可以影响另一个 Goal 之后启动的服务器的包运行器选择。这正是 R87-D11-02 想限定在一次 Host 生命周期内的那类后果，跨越了 Goal 的边界。
    - 可靠性一侧：并发的 Goal 之间互相使对方的 MCP 服务器失效，Agent 在 Run 中途失去 MCP 工具，而用户看不出原因。
- **为什么是次要**：安全一侧仍需要一次人批准的写入或服务器自己的行为；可靠性一侧不丢数据。但 ADR-215 写下的不变式在默认配置下不成立，实现者会在 “共享目录 + 删除重建”“每个 Host 一个目录”“原子替换” 之间各取其一。
- **文档位置**：`00` L99；`05` L438、L1460（C21）；`06` L42、L1060；`11` L212、L222；`14` L134（G46 (bk)）。
- **期望的回答形态**：在 `11` L222 (a)（唯一定义）二选一：
  - **每个 Host 一个目录**：如 `~/.tower/run/<hostId>/mcp-cwd/`，`host.spawn` 时新建为空、Host 退出时删除（启动时清理残留）。`towerMcpTransport` 以本 Host 的目录为基准；硬底线与门禁的 “已知工作目录” 指 `~/.tower/run/*/mcp-cwd/`。这样 “不越过一次 Host 的生命周期” 与 “不删除其他 Host 正在用的目录” 同时成立，打包模式的残余照旧写明；
  - 或保留共享目录，把界限改写为 “到下一次任一 Host 启动为止，这期间启动的服务器（不论哪个 Goal）共用它”，写明删除对其他 Host 中运行的服务器的后果，并以原子替换（新建到旁边、改名替换、再删旧目录）消除启动失败的窗口。`00` L99 的理由列同步。
  - G46 (bk) 补一组只写期望：两个 Goal 并发（默认模式），Goal A 的 Host 运行中 Goal B 开 Run，A 中已启动的服务器继续可用（或按所选方案如实表现），A 之后新会话启动的服务器看不到 B 期间写下的文件。

**R88-D11-02｜次要**（对未写 `cwd` 的 stdio 服务器，任何含 `/` 的字符串参数都按写进 `mcp-cwd` 处理而硬 forbid；波及大量非路径参数，而披露的代价只说代码智能类服务器）

- **问题**：
  - **规则**：
    - `11` L221 (3) 把 “含 `/`，且不以 `/`、`~` 或 `<scheme>://` 开头的字符串值” 一律当作相对路径；
    - `11` L222 (b) 对经 `towerMcpTransport` 启动的 stdio 服务器，以工作目录与 `roots` 两个基准解析，任一结果落在硬底线即 forbid、不可授权覆盖；
    - 方向未知时只禁止写的位置按写处理（L221 首句），而 `mcp-cwd` 正在 “写” 一项硬底线中（`11` L212）。
  - **于是**：未写 `cwd` 的服务器，其工具的任何含 `/` 的字符串参数都解析进 `~/.tower/mcp-cwd/`，一律硬 forbid。这包括许多本不是本地路径的值：
    - 代码托管类服务器的 `owner/repo` 与远程仓库中的文件路径；
    - 分支名、MIME 类型、不带协议的 URL 路径、glob 模式；
    - 这些在 ADR-215 之前 “至少 ask”，人可以批准；现在是硬底线，人无法批准。
  - **披露的代价**：
    - `11` L222 (b)：“代价：以 `roots` 解析相对路径的代码智能类服务器，未写 `cwd` 时相对路径参数一律被拒绝”；
    - `00` L99 同此；回应 “偏离” 也只提代码智能类。
    - 实际受影响的是所有未写 `cwd` 的 stdio 服务器，而 `mcp.json` 中的 stdio 服务器绝大多数不写 `cwd`（以 `npx`/`uvx` 启动的服务器通常不需要）。
  - **用户看到的**：Agent 收到 forbid，Tower 不出现审批卡；用户不知道 “给这个服务器写一个绝对 `cwd`” 就能解决，因为能力差异表只对代码智能类这样建议。
- **为什么是次要**：规则本身清楚，实现不会分叉，也不削弱任何安全不变式（偏严）。但这是 ADR-215 新引入的、不可授权覆盖的误判，波及常见的服务器；`00` §0.5.1 作为面向用户的能力差异表，把代价的范围写窄了。
- **文档位置**：`00` L99；`05` L438；`11` L212、L221、L222。
- **期望的回答形态**：在 `11` L222 (b)（唯一定义）二选一：
  - **缩小规则**：未写 `cwd` 的服务器，以 `mcp-cwd` 为基准的解析结果，只在 `mcp-cwd` 下确有已存在的对应条目时才按硬底线 forbid，其余回到 “至少 ask”（`mcp-cwd` 每次 Host 启动前为空，写入后才有条目）；或对 `mcp-cwd` 这一基准只在参数值为 `.`、`..` 或以 `./`、`../` 开头时 forbid。写明取舍；
  - **或扩大披露**：代价改写为 “未写绝对 `cwd` 的 stdio 服务器，其工具参数中任何含 `/` 的值都被拒绝、不可批准；建议为每个 stdio 服务器写一个指向你自己目录的绝对 `cwd`”，`00` L99 同步；静态清单（`05` §5.10）在未写 `cwd` 的 stdio 条目旁写同一句，forbid 的理由文字点明这一出路。
  - C21 或 G46 (bk) 补一组只写期望：未写 `cwd` 的服务器收到 `owner/repo` 形状的参数时，按所选方案表现。

### D4 领域模型与生命周期

**R88-D4-01｜次要**（`pendingHandBack` 期间 “会改写去向的选项置灰” 没有列出范围：照字面会置灰 `nested_repo_live` 的 `resume` 与被保留的 `input_mutated_after_gate` 的覆盖，只剩放弃；`reverify` 模式下附转向的 `resume` 不让 Agent 运行）

- **问题**：
  - **观察 1 的回应写下的规则**：
    - `16` L45：`pendingHandBack` 非空期间 “其他命令对继续目标的改写……照常写入、但不改变结果……界面上这类选项置灰”；
    - `04` L664：“会改写去向的选项（如预算硬上限卡片的 `按当前状态送去验证`）同样置灰”。
    - 只给了一个例子，没有列出是哪些命令。
  - **照字面落入这一规则的命令**：
    - `goal.resume` 对 `nested_repo_live` “显式改写” 继续目标为 `{kind:"run"}`（`06` L882）；
    - `sentinel.override` 把继续目标改写为 `review{…}`（`06` L939）；
    - `goal.external_change.keep` 也改写继续目标（`06` L900）。
  - **与 ADR-215 自己写的出口冲突**：
    - `03` L87、L102，`04` L933，`14` G26c (b)：`nested_repo_live` 交还后仍暂停时 “只有 `resume` 附转向与 `abandon`”。若 `resume` 按 `04` L664 置灰，就只剩放弃（另有 `04` L929 的 “在别处删除”）；
    - 被保留的 `input_mutated_after_gate` 只有覆盖与放弃两个出口（`03` L87，`07` L1536），覆盖若被置灰，就只剩放弃。
  - **即使不置灰，`reverify` 模式下结果也与文字不符**：
    - `resume` 解除最后一个原因后，`onAllReasonsCleared()` 第 ① 步先执行 `pendingHandBack`（`03` L73）。`mode = reverify` 时它直接以当前树验证、不开 Run，转向留在 `pendingOpenings`；
    - 条目仍在卫星中，`nested_repo_live` 是阻止 Verified 的 run 类命中（`16` §16.1.6），这次验证必然再次停在 `paused(sentinel_high)`，人须再按一次；
    - 而 `04` L933 写 “之后只能让 Agent 删除（继续时附说明）”，G26c (a) 期望 “附转向 → `running`”，`04` L664 又把 `继续` 改名为 “重新验证”。
  - **漏同步**：`07` L1518 的出口列表仍是 “`resume` 附转向 / `take_over` / `abandon`”，没有 ADR-215 的例外。
- **为什么是次要**：不丢已提交的数据，`04` L929 的 “在别处删除” 也是一条出路。但这是 ADR-215 刚定义的分支，两个实现者会置灰不同的集合；置灰覆盖的那一种会让 `input_mutated_after_gate` 的 Goal 只能放弃。
- **文档位置**：`03` L73、L87、L102；`04` L664、L929、L933；`06` L882、L900、L939；`07` L1518、L1536；`14` L91（G26c）；`16` L45、§16.1.6。
- **期望的回答形态**：在 `16` `Goal.pendingHandBack`（L45，该规则的唯一定义）写一句，`04` L664 引用：
  - 列出置灰的命令：只有 “唯一作用就是改写继续目标” 的选项（如 `claim_on_behalf`）置灰；解除某个原因的命令（`resume` 解除 `nested_repo_live`、`sentinel.override`、`external_change.keep`/`revert`）不置灰，它们对继续目标的改写照常被第 ① 步取代；
  - `nested_repo_live` 在 `pendingHandBack.mode = reverify` 时二选一：附转向的 `resume` 同时清除 `pendingHandBack`（人的新选择取代交还时的选择），使它真正开 Run；或如实写明 “先按交还时的选择重新验证，验证会因条目仍在而停下，之后再继续时才交给 Agent”，`04` L933 的文字与 G26c (a) 的期望相应区分两种模式；
  - `07` L1518 补例外或改为引用 `03` §3.2.1。

### D6 系统架构与可靠性

**R88-D6-01｜次要**（重建的 “由事件重放的表” 有两处没有定义：载荷已墓碑化的 Goal 行与决定行无法重放；部分字段由事件承载的 JSON 列没有字段级规则）

- **问题**：`06` L221（唯一定义）对清单 (1)：“清空后按事件重放；其中不由任何事件载荷承载的列……按主键从被重建的库逐行沿用”。
  - **(a) 墓碑行**：
    - 隐私清除一个 Goal 时，`goals` 行与 `decisions` 行**保留为墓碑行**，相关事件只保留元数据、载荷删除（`09` L560，`06` L387 起 `payload_ref` 为空）；“彻底忘记一条记忆” 也把相关决定墓碑化（`09` L564）。
    - 这些行的身份（决定的 `id`、Goal 的状态等）只在载荷中，事件墓碑化之后无法重放；“按主键沿用” 又只作用于重放产生的行。照字面实现，重建后这些墓碑行消失。
    - `09` L560 明写保留墓碑行是为了让 “决定、其他 Goal 的 `parent_id`/`resurrected_from` 与 `goal_deps` 的外键仍然成立”。其他 Goal 由事件重放时，这些外键（`06` L488、L494、L511）与沿用表 `project_benign_targets.decision_id`（L769）都会指向不存在的行：重建要么因外键失败而中止，要么由实现者自行丢弃引用或墓碑。
    - 重建也用于投影版本迁移（`06` L221），所以这不是只在 `tower doctor` 中出现：任何清除过 Goal 或忘记过记忆的安装，下一次投影版本迁移都会走到这里。
  - **(b) 部分由事件承载的列**：
    - 规则以 “列” 为粒度。`goals.human_checkout` 的 `path`、`baseTree` 等由 `human_checkout.created` 承载，而 `syncState='syncing'`、`targetTree`、`params`、`written` 在交还事务中直接写入、没有事件承载（`06` L475、L905）；
    - 写回中途崩溃后的恢复正读这几个字段（`06` L144）。把这一列当作 “由事件承载” 的实现会把它重放为 `idle`，丢掉写回目标；`counters.reworkCycles` 同样在 `decide()` 中递增、没有专门的事件（`06` L269），重新推导会违背 “返工计数在 Goal 生命周期内不重置”（`03` L86，I6）。
    - `doctor --rebuild` 恰恰常在崩溃之后运行。
- **为什么是次要**：只在重建与投影版本迁移时出现；(a) 中的墓碑行不含人写的内容；(b) 中人工编辑检出的文件仍在，人可以再交还一次。但这是正清单的唯一定义，照字面实现会让迁移失败，或丢掉 `09` 承诺保留的审计墓碑。
- **文档位置**：`03` L86；`06` L144、L221、L269、L387、L475、L488、L494、L511、L769、L905；`09` L560、L564、L572。
- **期望的回答形态**：在 `06` L221 补两句：
  - **(a)**：清单 (1) 中载荷已墓碑化、无法重放的行（清除留下的 Goal 墓碑行与决定墓碑行），从被重建的库原样沿用；
  - **(b)**：“按主键沿用” 以字段为粒度：重放只覆盖事件载荷中出现的字段，其余字段（含 JSON 列中未由事件承载的键，如 `human_checkout.syncState`/`targetTree`/`params`/`written`、`counters`）取被重建的库中的值；
  - 补一组只写期望的场景（`14` G 类或 `06` 的契约测试）：清除一个被其他 Goal 以 `parent_id` 引用的 Goal 之后做投影版本迁移，迁移成功，两个墓碑行仍在，外键成立。

- **是否还有可追问的问题：有。** 新增共 **4** 条：阻断 0、重要 0、**次要 4**。
  - **D11**：R88-D11-01、R88-D11-02。
  - **D4**：R88-D4-01。
  - **D6**：R88-D6-01。
  - **第 87 轮核验**：
    - 5 条全部按所问关闭，其中 R87-D11-02、R87-D4-01、R87-D6-01 各带出新条目；R86-D6-01 已解决；

    - lint 全部通过（exit 0；ADR 215，section_refs 7800，(v) 98 条命令，(e) 216 对，(i′) 5 个事件，(D) 344 个短语，(z′) 53 处，(C) 19 行并覆盖 §14.8），与第 87 轮记录逐行一致。
    - Pi v1.2.0：ADR-215 的引文全部为原文；自检时机、取代条件（只有命令名 `mcp`）、内置 MCP 工厂在构造时没有副作用、`reload` 在 Tower 中被拒绝，都已逐个核实（见文首）。
    - 排期结论成立：WBS 123.33；余量 0.12 / 0.17 / 0.36 / 0.51 / 0.12；依赖链 19.91；增人 129.28、T 23.87、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **`07` 以外的同步**：F4b（`06` L1184）只列了内置 MCP 被取代与 Run 中途的同名工具，`03` L97 列出的 “启动时 Tower 工具被同名扩展工具遮蔽” 只能从 “Host 握手失败” 推知，宜补半句。
    2. **“因而在任何 MCP 服务器启动之前”**（`05` L366、ADR-215）：取代者是非 `replaceable` 的用户扩展，它的工厂在资源加载中、自检之前已经运行；Pi 只建议工厂 “只注册”。`05` L433 末句的残余已覆盖，宜把这句限定为 “内置 MCP 管理的服务器”；C21 “没有任何 MCP 服务器进程被启动” 的期望只对在 `session_start` 才连接的夹具成立，宜写明夹具的性质。
    3. **C21 只在首次启动时测内置 MCP 的自检**：交接与恢复时运行时重建、自检再跑，宜仿照 C28a 补一组（新会话中取代者仍在时同样 `prepare_failed`）。
    4. **相对 `cwd`**：`config.cwd` 为 `sub` 时解析为 `~/.tower/mcp-cwd/sub`。“`mcp-cwd` 本身除外” 是否含其子目录未写，而该目录每次启动前为空、`sub` 必然不存在；两种实现都表现为不启动，只是文字不同。C21 “写了相对 `cwd` 的相对它求出” 因此没有有效的测试输入。宜写明 “除 `.` 外的相对 `cwd` 实际不可用，请写绝对路径”，或把它与 Tower 目录之下一样以同一句文字拒绝。
    5. **README 与 `00` 的两处措辞**：README L19 “相对路径参数按它检查” 与 `00` L99 只提工作目录，未提 `roots` 一侧；`00` L99 “`cwd` 指向 Tower 工作区的服务器不启动” 比唯一定义的 “工作区或数据目录之下” 窄。
    6. **单个文件名与主检出**：绝对 `cwd` 在主检出之内时（`05` L438 允许，主检出不在 Agent 可写的集合中），不含 `/` 的单个文件名仍不当作路径，一次批准即可写进硬底线 “读写主检出” 的位置。这是 T7/T26 已登记的尽力而为限制，但 `00` L99 “一律被拒绝” 没有这一限定；宜在 `00` L99 的建议旁写明 “不要把 `cwd` 指向你的仓库检出”，或由静态清单对这类条目提示。
    7. **相对路径与密钥路径表**：(b) 只写了落在硬底线时 forbid；解析结果命中 §11.3.1 密钥路径表时是否同样按 (2) 归 `secrets.access`，没有写。资源工具（`read_mcp_resource` 等）为所有服务器只注册一次、以参数指明服务器，宜写明按该参数取工作目录。
    8. **中止准备时的查询子进程**：`abandon` 与新到的暂停原因会中止准备（`10` L381），`05` L1337 只定义了超时时终止进程组；中止时宜同样终止。
    9. **Run 之外的总时长**：pnpm 的 `list -g` 每个包运行一次、不缓存（`05` L1337），每次各有 60 s；首次运行卡片与 “重新读取” 之后的重新计算最多可等 N × 60 s。宜写明第一次超时之后其余查询直接记为 “无法确定”，或设一个总时限。
    10. **从 `running` 放弃**：`06` L933 只列了从 `paused` 放弃时清除的列；`draining_for` 非空时放弃，CHECK（L497、L502–L503）还要求清除 `draining_for`，以及只在 `draining_for.reasons` 中出现的 `external_change`。第一次测试就会暴露、只有一种改法，宜在同处补上。
    11. **重建的实现方式**：“清空后按事件重放” 与 `decisions_no_delete` 触发器（`06` L654）、`PRAGMA foreign_keys = ON` 下沿用表对 `goals`/`decisions` 的引用（`bindings`、`sessions`、`review_units`、`scratch`、`project_benign_targets`）不能就地相容；`09` L572 “不替换现有的库” 已暗示写入新库，宜在 `06` L221 写明 “写入新库、按外键顺序插入、完成后替换”。另外，清单 (1) 的表若本身损坏、事件中有而旧库中没有某行，`runs.process_token` 等 NOT NULL 的非事件列没有来源，宜写明这时重建中止并指向 `db-backups/`。
    12. **`08` L45 的旧措辞**：`RoutingRuntime` “可由事件重建”，而它存于 `needs_you.routing`，`needs_you` 现属沿用；宜改为 “随 `needs_you` 沿用”。
    13. **`16` L665 的旧措辞**：“不能从事件重建的全部例外见 `06` §6.2.1”，`06` 已不再列 “例外”，宜改为 “见 `06` §6.2.1 的两份清单”。
    14. **设置页的重新计算**：`05` L471 与 L1337 说 “重新读取” 之后清单在设置页重新计算，失败时显示 “无法确定” 与 `[重试]`；`04` §4.15 L1267 没有说这张卡片出现在哪里，宜补半句引用 `04` §4.18.1 的同一卡片。
- **设计是否完成：ADR-215 正确地关闭了第 87 轮的五条次要条目。**
  - 内置 MCP 的来源自检与 Pi 的取代机制逐一吻合；全局根查询有了步骤归属与 Run 之外的规则；接管守卫写进了转移的唯一来源；重建改为正清单，表的覆盖由构造保证。
  - 本轮没有重要条目。4 条次要条目分三类：
    - **ADR-215 的新机制在相邻配置下的后果**：R88-D11-01（共享目录在并发 Host 之间）、R88-D11-02（硬 forbid 波及非路径参数）；
    - **观察回应带出的规则冲突**：R88-D4-01（置灰范围与出口列表）；
    - **正清单的未定义处**：R88-D6-01（墓碑行与 JSON 列）。
- **下一轮建议**：
  1. **R88-D11-01**：每个 Host 一个空目录；或改写界限并原子替换。G46 (bk) 补并发的一组。
  2. **R88-D11-02**：缩小 `mcp-cwd` 基准下的 forbid；或扩大披露并在清单中提示未写 `cwd` 的 stdio 服务器。
  3. **R88-D4-01**：列出置灰的命令；`nested_repo_live` 在 `reverify` 模式下的结果写一句；`07` L1518 同步。
  4. **R88-D6-01**：墓碑行原样沿用，沿用以字段为粒度；补一组迁移场景。
  5. §5 的十四条观察各补半句。

  **工时与排期**：约 0.03–0.05 人周，不在依赖链上。系统线与安全线余量都是 0.12、都在改派阈值上，本轮可能落在这两条线上的增量（R88-D6-01 在 W3；R88-D11-01 的门禁一侧若落在 W10）都须先按 ADR-136 改派（§3.2）。预计 M1 仍可维持 38 周（2027-07-30）。
