## 1. 总评

**第 101 轮的 7 条条目都按所问关闭**（核对见 §3）：
- 重要条目 R101-D15-01 在 `04` 三处都已改为引用 `10` §10.2，lint (d) 的严格匹配组经变异检查起作用。
- 六条次要条目都在唯一定义处落地。其中有三处修法本身带出新的分支：
  - R101-D13-02 把带回与关闭的前置条件由 “目录存在” 改为 “使用中”，丢掉了目录已不存在的一支（R102-D13-02）；
  - R101-D15-02 把 Host 白名单改为引用 `05` 表中 “Host 列为 ✔ 的各行”，过滤条件漏掉了 Host 一列写的是变量值而不是 ✔ 的 git 发现一行（R102-D15-01）；
  - R101-D5-01 的观察 8 新写了一句 “存储的凭据为准、与终端相同”，对同一轮定义的 bearer 令牌一支不成立（R102-D5-01）。
- §5 的 9 条观察全部落地。

**对本轮重点问题的回答**：

- **AWS 只有原始密钥、没有区域的 `eu.*` 失败：如实、最小，M1 可接受**。
  - **如实**：`11` L518 写出了差别与原因，首次运行的确认卡片写明 `只有原始密钥、没有区域：Tower 中的请求发往 us-east-1；使用 eu.* 等模型请设区域`。G46 (d) 第七组按 “请求以 provider 错误失败” 写期望。
  - **最小**：没有为求等价新增传递途径，也没有让原始密钥进入 Host 环境。
  - **Pi v1.2.0 中有没有更简单的途径**：评审者逐一核对了三条。
    - **经 Pi 选项给区域**：会话路径不传 `region`，coding-agent 中也没有任何设置项提供它。
    - **经存储凭据给 profile**：可行。自定义 `CredentialStore` 返回 `{type:"api_key", env:{AWS_PROFILE:"tower-<hostId>"}}` 时，`amazon-bedrock.ts:65-70` 返回该 `env`，`model-runtime.ts:682-685` 把它并入请求；`AWS_PROFILE` 不在进程环境中，`:167` 为假，端点照常固定，区域与终端相同。
      - 但 `ModelRuntime` 只接受一个凭据存储，它同时承担用户 `auth.json` 中 OAuth 令牌的刷新与落盘。文件型 `AuthStorage` 没有从包入口导出，所以这条途径要求 Tower 自己实现 `auth.json` 的读写与跨进程锁。D57 不采用内存凭据存储，理由正是这一点。
      - 结论 “M1 中没有途径” 成立。但 ADR-229 与 `11` L518 给出的依据只有 “请求级 `env` 会话路径不传（`:671-675`）”，漏了存储凭据的 `env` 这一支，见观察 1。
    - **按所选模型的端点给 Host 设区域**：同一 Host 中途换模型或打包模式下就不成立，属于设计取舍。
  - **用户的出路简单**：在环境或 profile 中设区域，终端中的 Pi 也是这样。
- **`ANTHROPIC_AUTH_TOKEN` 不提供：如实、最小，M1 可接受**。
  - Pi 只从 `ctx.env` 读它（`anthropic.ts:34-40`）；存储凭据的 `env` 不叠加到 `ctx`，只有请求级 `overrides.env` 叠加（`resolve.ts:54, 83`）。所以不经进程环境就只能替换整个 Anthropic provider：`registerNativeProvider`（`model-runtime.ts:891`），并在 `resolve` 中返回头部。这比登记为限制重得多。
  - 放进 Host 环境则违反 T33 与 ADR-158。
  - `11` L517 把它写为选择（“M1 不提供”），而不是做不到，措辞恰当。
  - 但它与已存储凭据的关系没有写清，并入 R102-D5-01。
- **存储提示复用 `◇` 而不计入 Dock 角标：接受**。
  - 设置入口的 `◇` 是 M1 中不属于任何 Goal 的通知的现成呈现面（ADR-174/175），条件成立期间一直显示。
  - 人不打开 Tower 时看不到它；但真正到磁盘满时 F8 另有 L3 横幅。
  - 不新增 Needs-You kind 符合收敛规则。
  - 剩下的只是 “已查看” 怎样从界面送到 Supervisor，以及与项目级 `◇` 并存时的排布（R102-D8-01）。

**ADR-229 带出、或本轮扫描发现的新问题**（全部为次要）：
- **运行时注入的密钥压过 `pi /login` 存储的凭据**（R102-D5-01）：
  - Tower 对导入的每个 API Key 都调用 `setRuntimeApiKey`，而 `RuntimeCredentials.read` 先返回覆盖、后读存储。终端中的 Pi 恰好相反，存储的凭据优先。
  - 后果一：既用 `/login` 订阅登录、shell 中又有 `ANTHROPIC_API_KEY` 的用户，在 Tower 中的请求改按 API Key 计费，而终端中用的是订阅。
  - 后果二：`11` L518 “经 `pi /login` 存储了 Bedrock 的 profile 或令牌时以存储的凭据为准、与终端相同” 一句，对同一行定义的 bearer 令牌一支（按 API Key 运行时注入）不成立。
- **复用的 Host 上该 Goal 自己的准备阶段仍计入看门狗**（R102-D6-01）：`hostExpected` 只在 Host 退出时清除。Host 在暂停不足 5 分钟等情形下保留、为下一个 Run 复用，这时新 Run 的会话创建阻塞会按 30 s 挂死处理。这与 “准备阶段不计入” 相反。
- **存储提示的 “已查看” 没有协议落点**（R102-D8-01）：唯一定义说它是 “Supervisor 的进程内状态”，而协议中只有 `goal.viewed` 与 `project.local_files.viewed`；ADR-229 又声明不新增命令。推送的主题、与项目级 `◇` 并存时的排布也没有写。
- **交还对话框的提交数没有求值上下文**（R102-D11-01）：`04` L635 “你在副本中做的 1 个提交会被忽略” 与事件字段 `ignoredCommits` 都要读 H/.git，而唯一加固清单的新行限定 “只为 `goal.delete_kept` 的确认框”；H/.git 又可能被人在 H 中运行的 Agent 代码改过（`10` L960）。
- **确认框与列出的三个分支**（R102-D13-01）：
  - 提交数只沿一条分支数，并以 “对象不在 H/.git 自己的库中” 为停止条件。它少报其他分支、分离的 HEAD 与 stash；在人照 `10` L259 的建议执行 `repack` 之后又会把整段历史数进来，并撞上解析器 200 个提交的上限，上限的含义没有写。

  - “清除全部” 或清除 Project 之后再次添加项目，重新列出的目录没有 Goal 行，标注与 `goal.delete_kept` 是否接受没有写。
- **“使用中” 取代 “目录存在” 之后，目录已不存在的一支**（R102-D13-02）：检验打开中、目录被人删掉时，`inspect.close` 按 “不在使用中（含……不存在）” 返回 `E_STATE`，打开着的检验关不掉；`inspect.bring_back` 则对不存在的目录求 T1。
- **Host 白名单的引用过滤**（R102-D15-01）：
  - `11` L516 只引入 `05` 表中 “Host 列为 ✔” 的行，git 发现一行的 Host 一列是 “ceiling；……”，于是 `GIT_CEILING_DIRECTORIES` 被 “此外一律删除” 排除；

- **Pi 的内置 MCP 扩展把服务器日志写进用户 agentDir 的 `mcp.log`**（R102-D12-01）：其中可能有 Goal 内容，`09` §9.12 “清除之后仍可能存在的副本” 没有列出。

### D5 Agent 架构与 Pi 集成

**R102-D5-01｜次要**（运行时注入的密钥压过 `pi /login` 存储的凭据，与 Pi 的优先顺序相反；`11` L518 对 bearer 一支的 “与终端相同” 不成立）

- **问题**：
  - **(a) 优先顺序**：
    - Tower 对导入的 API Key 一律经 `setRuntimeApiKey(provider, key)` 在 Host 内存中提供（`11` L517，`05` L486）；首次运行第 2 步对 shell 中的模型提供商变量无条件提示导入（`04` L1459，`05` L489 “API Key 提示导入密钥库”）。
    - Pi v1.2.0 中，`RuntimeCredentials.read` 先返回运行时覆盖，再读存储（`runtime-credentials.ts:24-28`）。终端中的 Pi 则以存储的凭据决定该 provider，环境变量只在没有存储凭据时判定（`resolve.ts:27-31, 70-87`；`anthropic.ts:30-46`；`amazon-bedrock.ts:61-64`）。
    - 所以对同一 provider 既有 `/login` 存储的凭据、shell 中又有 API Key 的用户，Tower 与终端用的是不同的凭据。最常见的是 Anthropic 订阅登录加 `ANTHROPIC_API_KEY`：终端按订阅，Tower 按 API Key 计费。
    - 这与 `05` L486 “用户自己 `auth.json` 中的 OAuth 登录照常读取”、`05` L1343 “（`/login` 之后）Tower 之后读取” 的含义不符：导入之后，人之后的 `/login` 在 Tower 中不起作用。
  - **(b) ADR-229 新写的一句**：
    - `11` L518 “少见配置”：“你经 `pi /login` 存储了 Bedrock 的 profile 或令牌时，Pi 以存储的凭据为准……与终端相同，Tower 传入的变量随之不起作用”。
    - 对同一行定义的 `AWS_BEARER_TOKEN_BEDROCK` 一支（“按 API Key 运行时注入”）不成立：运行时覆盖先于存储凭据，存储的 profile 被忽略。
  - **(c) 标注**：
    - 只有 `ANTHROPIC_AUTH_TOKEN` 时标 “该凭据只在你的终端中可用，Tower 中不可用”（`11` L517）。
    - 同一用户另有 `/login` 存储的 Anthropic 凭据，或同时有 `ANTHROPIC_API_KEY` 时，Anthropic 在 Tower 中可用，而终端用的是令牌（`anthropic.ts:34-46`），这一标注与实际不符。
    - 另：`AWS_BEARER_TOKEN_BEDROCK` 与原始密钥并存时，Tower 仍写投递文件与 `AWS_PROFILE` 并按 ③ 补 `us-east-1`，而终端用 bearer 令牌、按端点取区域；这种组合不在已登记的两处差别中。
- **为什么是次要**：没有机密进入 Agent 可影响的进程，也不丢数据。但 (a) 改变了用哪份凭据、由谁计费，且没有告知；(b) 是 ADR-229 新写的一条与 Pi 源码不符的等价断言。
- **后果的类别**：同时有订阅登录与 API Key 的用户在 Tower 中的花费落到另一个账户；人在终端重新 `/login` 后以为 Tower 也随之改变。
- **文档位置**：`05` L486、L489、L1343；`04` L1459；`11` L517、L518；`16` L724。
- **期望的回答形态**：在 `11` L517 “模型凭据” 一行（唯一定义）加一句，二选一：
  - **与终端相同**：每次 `host.spawn` 以 `readStoredCredential(provider, authPath)`（`coding-agent/src/core/auth-storage.ts:497`，自包入口导出）检查；该 provider 已有存储的凭据时不调用 `setRuntimeApiKey`，首次运行对这类变量写明 “已有 `pi /login` 的凭据，Tower 用它”。
  - **如实登记**：写明 Tower 导入的密钥优先于 `/login`，设置页与模型选择器显示生效的来源。
  
  同时改正 `11` L518 一句，使其限于 profile 与原始密钥两支；写明 `ANTHROPIC_AUTH_TOKEN` 与其他来源并存时的标注；登记或处理 bearer 令牌与原始密钥并存的组合。G46 (d) 补一组。

### D6 系统架构与可靠性

**R102-D6-01｜次要**（复用的 Host 上，该 Goal 自己新一个 Run 的准备阶段仍计入 30 s 看门狗）

- **问题**：
  - `08` L365：`hostExpected` 在该 Goal 的准备握手完成（`run.started`）时置位，清除条件只有 “该 Host 进程退出”。
  - `08` L393：“**准备阶段不计入**……这只对该 Goal 自己成立”。
  - Host 不随每个 Run 退出：它在 Goal 进入 `in_review`、`paused` 超过 5 分钟、被中止或应用退出时才退出（`06` L169）；准入链写 “（需要启动 Host 时）静态清单计算……”（`06` L323），即已有存活 Host 时复用。
  - 每个 Run 都新建会话服务，会再做一次包管理器的全局根查询（`05` L486、R101 观察 1，`package-manager.ts:2102-2116`）。
  - 于是在 “暂停不足 5 分钟后继续”“验证失败后返工” 等情形下，同一 Goal 的下一个 Run 在复用的 Host 上准备，`hostExpected` 仍是上一个 Run 置的位。这时会话创建中的同步阻塞超过 30 s 即按挂死 SIGKILL，进入 `engine_crash`，而不是按 120 s 时限进入 `prepare_failed`。打包模式下同一 Host 的其他 Goal 一并被终止。
  - ADR-228 为专用 Host 排除的正是这一类，复用的 Host 没有覆盖到。
- **为什么是次要**：去向有定义（`engine_crash` 自动重启一次），不丢数据；但判定与 “准备阶段不计入” 相反，实现会在 “Run 之间清除” 与 “只在 Host 退出时清除” 之间分叉。
- **后果的类别**：全局根查询较慢的机器上，复用的 Host 被误判挂死并终止；同一 Host 的其他 Goal 随之中断；排障时 `engine_crash` 与 `prepare_failed` 指向不同的原因。
- **文档位置**：`08` L365、L393；`06` L169、L323、§6.1.3、§6.8 F4/F4b；`05` L486；`13` L129。
- **期望的回答形态**：在 `08` L365 `hostExpected` 一行的清除条件加一句，例如 “或该 Goal 的 Run 结束（`run.ended`），下一个 Run 在同一 Host 上于其 `run.started` 时重新置位”；同时写明打包模式下 “已置位” 按 Goal 计。G35c (x) 补一组：复用的 Host 上，新 Run 准备中的阻塞超过 30 s 而不足 120 s 时不判挂死。

### D13 隔离、git 与并发

**R102-D13-01｜次要**（删除确认框的提交数遍历范围与停止条件、求值失败的回落、没有 Goal 行的目录）

- **问题**：
  - **(a) 提交数**：
    - `10` L53：“从 `refs/heads/tower-human/<goalId>` 沿父链数 H/.git 自己对象库中的提交，遇到不在其中的对象……即停”。
    - **少报**：人在 H 中新建的其他分支、分离的 HEAD 与 `refs/stash` 上的提交都不在这条父链上。常见的情形是人 stash 了改动，或在侧分支上提交后切回。这时工作树等于检查点，确认框显示没有不同的文件、0 个提交，而删除会连同这些提交一起删除。交还时人的提交按规则被忽略（`10` L975），H/.git 可能是它们唯一的副本。
    - **多报**：`10` L259 建议人在影子删除前执行 `git repack -a -d` 并删去 alternates。照做之后，检查点与 base 的历史都在 H/.git 自己的库中，停止条件永不触发，整段历史都被数成 “人做的提交”，直到撞上解析器 “总计 ≤ 200 个提交” 的上限（`10` L227）。撞上限时显示一个数还是 “无法读取”，没有写。
  - **(b) 求值失败**：
    - 文件差异 “临时索引从检查点的树起 `add -A`”（`10` L53）要把未被忽略的文件写成影子中的对象。
    - 磁盘满时这一步失败，而 F8 与磁盘压力正把人指到这里（`06` L1197，`10` L453）。
    - `10` L259 只给出 “影子已删除或 Goal 已清除” 时的写法，求值失败时确认框显示什么、是否仍允许删除，没有写。
  - **(c) 没有 Goal 行的目录**：
    - `09` L560：清除 Project 或清除全部之后，“再次添加同一项目且工作目录位置不变时，它们按名字重新列出”。
    - 但 `10` L259 只对墓碑行标 `（已清除）`；清除全部之后数据库已删除，这些 goalId 连墓碑行都没有。标注是什么、`goal.delete_kept{goalId}` 对不存在的 Goal 是否接受，没有写。按常规的命令校验会返回 “不存在”，存储面板上的 `删除` 随之不可用。
- **为什么是次要**：删除由人显式发起，对象是人自己的目录，Tower 从不自动删除的不变式成立；但 (a) 使 “先列出将丢失的内容” 在常见情形下少列，并与 ADR-229 自己的 `repack` 建议冲突，(b)(c) 是新命令的未定义分支，实现会分叉。
- **后果的类别**：
  - 人按 “0 个提交” 删除了只存在于 stash 或侧分支中的提交；
  - 照建议 `repack` 之后，确认框报出几百个 “人做的提交”，计数失去意义；
  - 磁盘满时确认框出错，人无法在 Tower 中释放空间；
  - 重新列出的目录点 `删除` 失败。
- **文档位置**：`10` L53、L227、L259、L975；`09` L560；`06` L911、L1197；`10` L453。
- **期望的回答形态**：在 `10` L53 与 L259 的唯一定义处各补一句：
  - (a) 遍历 H/.git 的 `HEAD`、全部 loose ref 与 `packed-refs`（含 `refs/stash`），只数不可从 H 起始检查点 k 到达的提交。k 是 `tower-human/<goalId>` 建立时的值，可由 H/.git 的 reflog 第一条或 Goal 记录得到；得不到时退回 “对象不在自己的库中”。列出 `tower-human` 之外的 ref 名。撞上限时写 `至少 200 个`。
  - (b) 任何求值失败（含磁盘满）都退回 `无法与检查点比较：其中的一切随之删除` 并列出文件数与大小，删除照常可用。也可以改为不写对象的比较。
  - (c) 没有 Goal 行的目录同样标 `（已清除）`；`goal.delete_kept` 对它只校验名字形状与已知的 `<wtRoot>`，不要求 Goal 行存在。

**R102-D13-02｜次要**（“使用中” 取代 “目录存在” 之后，使用中而目录已不存在的一支没有去向）

- **问题**：
  - 第 101 轮之前，`inspect.bring_back` 的前置条件是 “检验检出……存在”，`inspect.close` 是 “检验目录不存在 → `E_STATE`”。ADR-229 把两者改为引用 “使用中”（`06` L918、L919），而 “使用中” 按状态定义：检验打开中，或以 `keep` 关闭待处理（`10` L255）。
  - 检验打开中、或以 `keep` 关闭待处理，而人在 Finder 或终端中删掉或移走了 `_inspect/<goalId>` 时：
    - `inspect.close` 写 “检验目录不在使用中（含已脱离与不存在）→ `E_STATE`”（`06` L919），把 “不存在” 归入 “不在使用中”。照此，打开着的检验关不掉，服务与端口段要等验收或放弃时才回收。
    - 若按状态把它算作使用中，`inspect.close` 要 “以临时索引比较检验目录与 T_pin”，`inspect.bring_back` 要 “影子对检验检出计算目标树 T1”。两者都是对不存在的目录求树：实现或者报错，或者得到空树，把 “删除全部文件” 作为人的改动写回卫星。
  - 人工编辑检出有 “目录丢失” 的一支（`06` L144），检验目录没有。`06` L899 `inspect.open` 写 “已存在且仍在使用中”，可见 “使用中” 并不蕴含 “存在”。
- **为什么是次要**：由人删除目录这一外部操作触发；写回的改动有 `author:"human"` 检查点、可以撤回。但这是 ADR-229 修法带出的回退，同一前置条件可以导出两种相反的实现。
- **后果的类别**：检验关不掉、端口段被占住；或一次带回把人没有做过的整树删除写进卫星、触发验证。
- **文档位置**：`06` L144、L899、L918、L919；`10` L255、§10.8.3 第 7 步（L918–L926）。
- **期望的回答形态**：在 `10` L255 “使用中” 的唯一定义后加一句：使用中而目录已不存在时，`inspect.close` 不比较、直接结束检验（停止服务、回收端口段，结果写明目录已不存在）；`inspect.bring_back` 返回 `E_STATE`（“检验目录已不存在”）。`06` L919 的括注改为 “不在使用中（含已脱离的目录）”。

### 不扣分的观察

1. **“没有途径” 的依据**：
   - ADR-229 与 `11` L518 以 “请求级 `env` 会话路径不传（`model-runtime.ts:671-675`）” 说明 Tower 不能不经进程环境给出 profile。
   - 漏了存储凭据的 `env` 一支：自定义 `CredentialStore` 返回带 `env.AWS_PROFILE` 的凭据时，`amazon-bedrock.ts:65-70` 返回它，`model-runtime.ts:682-685` 并入请求，区域与终端相同。
   - 这条路不可取的真实理由是：`ModelRuntime` 只接受一个凭据存储，它还要承担用户 `auth.json` 的 OAuth 刷新与落盘，而文件型 `AuthStorage` 不从包入口导出，Tower 要自己实现跨进程锁（D57）。
   - 宜把依据改为引用 D57。结论不变。
2. **`ANTHROPIC_AUTH_TOKEN` 的另一条途径**：`registerNativeProvider`（`model-runtime.ts:891`）可以在内存中以头部提供令牌，代价是替换整个 Anthropic provider。`11` L517 写为选择而非做不到，恰当；宜在登记中提一句这条途径与不采用的理由。
3. **F8 的 “L3 横幅”**：
   - `06` L1197 写 “L3 横幅和清理建议”。`08` §8.1 的 L3 是在断点投递、消耗预算的 Needs-You；F8 没有对应的 kind，此时数据库又是只读的。
   - `04`、`12` 只定义了 Watch 视图的横幅。这一写法早于 ADR-229，ADR-229 把它作为磁盘满时的告知依赖。
   - 宜在 `08` §8.1 “存储提示” 旁写明 F8 是应用级横幅、不是 Needs-You、不计入角标与预算。
4. **`00` §0.5.1 的凭据一行**：
   - L112 只写 “凭据以 Tower 密钥库与按类型的透传为准”，影响一列只写 “bash 环境最小化”。
   - ADR-229 登记的几种限制都已在首次运行如实标注（`05` L489）：`ANTHROPIC_AUTH_TOKEN` 与工作负载身份联合不可用；只有原始密钥、没有区域时 `eu.*` 失败；Web Identity 等只在终端中生效。
   - 宜在影响一列补 “部分凭据类型只在终端中可用（`11` §11.7.1）”。
5. **删除确认框的过期确认与 drain 之后的接管**：
   - `goal.delete_kept{goalId, paths}` 不带确认框求值时目录的身份。若确认框打开期间发生了一次接管与交还（`goal.take_over` 可远程发起），确认会删除新的副本，而它的内容没有被列出。
   - 从 `running` 接管时，改名在 drain 之后才执行，与正在进行的 `goal.delete_kept` 怎样串行没有写。
   - 两者都需要罕见的交错，且对象仍是人的目录。宜让命令带上所列路径的 inode 或建立时间，不符时返回 `E_STATE`；drain 之后的续做同样检查 “`goal.delete_kept` 执行中”。
6. **估计独占大小**：
   - 人工编辑检出在其他 Goal 写同一卷时物化，`statfs` 差值会有噪声，可能为负或大于目录的逻辑大小；卫星一行写了 “单 Goal 准备串行执行时有效”，这一行没有写。
   - Goal 清除之后，改名保留的卫星 “沿用的记录” 不在了。
   - 扫描与求值的频率也没有写。
   - 宜限定在 [0, 逻辑大小]，没有记录时退回逻辑大小，并在 `13` 写明求值时机。
7. **E6 复审线的时间窗**：
   - “任一自用机器的合计在 4 周内超过 30 GB” 可以读为合计达到 30 GB、4 周增量超过 30 GB，或滚动窗口；M1 自用期只有 3 周（`14` L399、L425）。
   - M2 决定点针对 “与对应检查点相同的副本”，E6 不度量这一份额。
   - 宜写明窗口，并注明这一份额属于 M2 的数据。
8. **“逐个删除” 与多选**：`14` L456、`08` L38、`06` L1197 写 “逐个 `删除`”，`04` L1285 写 “每行与所选行可 `删除`”，命令本身接受 `paths: string[]`。宜统一措辞，与 M2 的 “一键批量删除” 区分。
9. **清除结果与机密副本**：`09` L560 的清除结果只写 “可能含你的改动”，没有重复存储面板对 `withSecrets` 检验目录的注明 “含本地机密文件的副本”（`10` L259）。宜补半句。
10. **措辞与引用**：
    - `11` L518 与 D62 以 `ai/src/models.ts:865-866` 为 “未配置” 的抛出位置；coding agent 的路径上实际在 `model-runtime.ts:676` 抛出，消息相同。
    - `11` L517 “Anthropic 的工作负载身份联合同样不提供” 没有理由：它由指向文件的变量与非机密的 id 组成，与 Vertex 同类。
    - `14` G46（L134）标题的 ADR 列表止于 ADR-228，而 ADR-229 补了组。
    - `04` 中 “F8” 指放弃的快捷键（L865、L1393），`06` 与 `14` W17 中指磁盘满，宜在 `14` 写 “`06` §6.8 F8”。
