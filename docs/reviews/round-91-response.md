## Pi v1.2.0 核实（`git show v1.2.0:<path>`，`packages/coding-agent/src/` 下）

- **求值的位置**：六个内置文件工具在 `execute` 中才求路径——`core/tools/write.ts:65`、`edit.ts:161`、`ls.ts:83`、`find.ts:111`、`grep.ts:125` 调用 `resolveToCwd`，`read.ts:124` 调用 `resolveReadPathAsync`；`ls`/`find`/`grep` 省略路径时为 `.`。`edit` 的 `prepareArguments`（`edit.ts:103-134`）只整理 `edits`，不动 `path`。所以 `tool_call` 钩子看到的是原始参数。
- **求值本身**：`resolveToCwd`（`core/tools/path-utils.ts:48-50`）= `resolvePath(…, {normalizeUnicodeSpaces:true, stripAtPrefix:true})`（`utils/paths.ts:103-107`）。其中 `normalizePath`（`:76-101`）依次：
  - 把 U+00A0、U+2000–U+200A、U+202F、U+205F、U+3000（`:7`）换成普通空格；
  - 去掉一个前导 `@`；
  - Windows 上另做 `normalizeWindowsShellPath`；
  - 把恰为 `~` 与以 `~/` 开头（Windows 另有 `~\`）的值展开为 `os.homedir()`；
  - 把以小写 `file://` 开头的值经 `fileURLToPath` 转换。
  之后以 `path.resolve` 求绝对路径，`..` 按词法消去；`trim` 未开启。`~user/…`、`FILE://…`、`file:/…` 都不转换，按字面的相对路径落在 `cwd` 之下。
- **`read` 的名字变体**：`resolveReadPathAsync`（`path-utils.ts:86-118`）在求出的路径不存在时依次试 AM/PM 前的窄空格、NFD、弯引号、NFD 加弯引号四个变体，替换作用于整条路径（可能改变目录部分）。
- **是否导出**：不导出。`package.json` 的 `exports` 只有 `.` 与 `./rpc-entry`；`src/index.ts:335-392` 导出 `create*ToolDefinition`、各工具的 `*Operations`/`*ToolOptions` 类型，`:490-496` 的 `utils/` 导出不含 `paths.ts`。工具把求出的绝对路径交给可替换的 `operations`（如 `read.ts:69, 92, 124-127`、`write.ts:41, 48, 65, 82`），所以契约测试能以导出的工厂观察 Pi 自己的求值，不依赖未导出的模块。`git diff v1.2.0 HEAD` 对这些文件为空。
- **观察 8、9 的依据**：`StdioTransport.close()` 在服务器进程已退出时只结束 stdin、直接返回（`packages/mcp/src/transports/stdio.ts:160-163`）；`exit` 钩子（`:43-52`）挂在 `process.once("exit")` 上。内置 MCP 为每个服务器的工具带上 `namespace`，其 `aliases` 为原始服务器名（`extensions/mcp/index.ts:387-397`，传入在 `:424`）；`ToolInfo` 带 `namespace`（`core/extensions/types.ts:2121-2131`）。

## R91-D11-01（重要）：文件工具的分类以字面 `resolve` 求路径

**决定**：分类器用与 Pi 内置文件工具完全相同的求法求路径，再取 `realpath`。Pi 的函数不导出，所以用 Tower 固定于 v1.2.0 的移植，并由契约测试与 Pi 自己的求值逐项比对。

**唯一定义**：`11` §11.3.1 新增的 “求路径” 一条（L159）；伪代码（L144–L146）的 `resolve(cwd, stripAt(input.path))` 改为 `piResolve(input.path || ".", cwd)`，并对 `read` 的候选逐个判定。
- 求法即上方核实的全部步骤：Unicode 空格、前导 `@`、`~` 与 `~/`、`file://`，再相对会话 `cwd` 按词法求值；`ls`/`find`/`grep` 省略路径时为 `.`。
- **`read` 的名字变体**：四个变体不论是否存在都各判定一次，取最严格者。替换作用于整条路径、可能改变目录部分，所以不能以 “不改变所在目录” 免除。
- **不能确定地求出时**（Pi 一侧会抛错的 `file://` 值，如主机名不是 `localhost` 或含编码的 `/`；取不到主目录）：该调用为 `opaque`、至少 ask。
- `..` 由 `path.resolve` 按词法消去，Pi 交给文件系统的路径中不再有 `..`，所以文件工具只有一种求值。
- 本条只用于这六个工具：bash 的路径参数按 shell 的展开（§11.3.2），沙箱外工具按 §11.3.4。

**同步**：
- `11` §11.1（L31、L36）：`read.external`、`edit.outside_worktree` 的例子补 `file://` 与 `@~/` 写法；§11.3.1 开头的 certainty 句写明 `opaque` 的情形；T3（L682）的 S1 引用求路径。
- `11` §11.3.1 密钥路径表的范围注同时改正（观察 5）。
- `05` §5.11.1 **D60**（L1430）：登记上述行号（C 类）；上游候选为导出 `resolveToCwd`/`resolveReadPath`，或在 `tool_call` 事件中带上求出的路径；发布版核实为 “同”。
- `05` §5.11.2 **C41**（L1483）：
  - (a) 夹具一组：相对路径、`..`、绝对、省略、`@x`、`@~/x`、`~`、`~/x`、`~user/x`、`~foo`、`file:///abs`、`file://localhost/abs`、`FILE:///abs`、`file:/abs`、含 `%20` 的、主机名不是 `localhost` 的与含编码 `/` 的 `file://` 值、含 U+00A0/U+202F/U+3000 的路径及其与 `~/` 的组合。`piResolve` 与 Pi 的求值逐项相等，Pi 一侧以导出的六个工具工厂配记录路径的 `operations` 执行；Pi 抛错的值在 Tower 一侧为 `opaque`。
  - (b) 只存在变体名字的文件：Pi `read` 实际读到的路径在 Tower 的候选集合之中。
  - (c) 只写期望：`~/…`、`@~/…`、`file:///…` 与带 Unicode 空格的同一路径都同样判定——写卫星之外为 `edit.outside_worktree`，读主目录下的凭据为 `secrets.access`，读写主检出、影子目录或其他 Goal 的卫星为硬底线 forbid、不出现审批卡；`~user/x`、`FILE:///x` 按卫星中的相对路径判定，与 Pi 实际读写的位置相同。
- `16` §16.1.10 工具表文件类工具一行（L259）：写明同一求法、`read` 变体取最严格者、不能确定地求出时为 `opaque`。

## R91-D11-02（次要）：(1) 的 `..` 与符号链接只按一种方式求值

**决定**：一条共用的求值规则，(1)(3) 与 (b) 都引用它。

**唯一定义**：`11` §11.3.4 路径检查（L223）新增的 “求值” 一句：
- 每个路径都按两种方式各求一次：按词法规范化 `..`，与按操作系统的方式（先解析符号链接、再处理其后的 `..`）。这里的路径指 (1) 的绝对路径、`~` 路径展开后与 `file:` URI 解码后的路径，以及 (3)(b) 以各基准解析出的相对路径。
- 两种方式在最后几段尚不存在时，都对最长已存在前缀取 `realpath`、其余照写；
- 两个结果都判定、取更严格者。
- (1) 的 “经 `realpath` 后” 改为 “按上述两种方式求值后”；(b) 的括注（L224）改为引用这一句。

**验收**：G46 (bk)（`14` L134）补符号链接一组。已授权的工具以三种形式写入：经卫星中符号链接、含 `..` 的绝对路径，同样形状的 `file:` URI，以及 `~/` 路径；它们按词法落在卫星内、按操作系统的方式落在主检出。期望：三次写入都被 forbid、不出现审批卡。

## R91-D6-01（次要）：写回中途的非崩溃失败没有出口

**决定**：
- 恢复 “且写回正在本进程中执行” 的限定；
- 写回在本进程中失败时还原卫星，把 `human_checkout` 退回写回之前的状态，并返回 `E_INTERNAL`；
- 还原也失败或来源已不存在时保留 `syncing`。这时写回已不在进行，所以不返回 `E_BUSY`，放弃照常可用。

**唯一定义**：`06` §6.4.3 `inspect.bring_back` 行的 “写回进行中” 与 “写回在本进程中失败”（L914）。
- **范围**：
  - 条件：`syncState='syncing'` **且这次写回正在本进程中执行**——交还 ① 到 ③、带回，或 §6.1.6 的启动续写。
  - 被阻断的命令：其他会改写该 Goal 的状态、暂停原因、继续目标、开场或 `human_checkout` 的命令，以及删除检验目录的 `inspect.close`。它们返回 `E_BUSY`，判定先于前置条件。
  - 接管期间的自动重建等写回结束再开始。
- **失败**（文件系统错误、目标目录不可写、卫星中途消失；`10` §10.1.3 的逐路径跳过不算）：
  1. 停止写回，把 `written` 中已写的路径还原为写回开始时的版本：交还为 B 中的版本，`take_human` 并入的 E 中路径取第 6 步 safety 检查点中的版本；带回为 T_pin。对象都在影子中。
  2. 用一个事务把 `human_checkout` 退回写回之前的状态：交还为 `idle` 并清除 `targetTree`、`written`、`params`；带回则清除 `human_checkout`。不写决定，状态不变。
  3. 命令返回 `E_INTERNAL`（`detail` 写步骤、路径与原因）。人工编辑检出或检验目录保留，人可以重试同一命令或放弃。启动续写失败时没有命令可回，原因显示在 Goal 卡片上。
- **还原也失败、或来源目录已不存在**（这时 T1 是人的改动仅剩的副本，不还原）：
  - `syncing` 与 `targetTree`、`written` 保留，但写回已不在进行，所以不返回 `E_BUSY`；
  - `goal.abandon` 照常可用，同时清除 `human_checkout`；
  - 检出仍在时，再次交还按 `10` §10.8.4 第 6 步续写；
  - 下次启动由 §6.1.6 续写。
- 所以 `E_BUSY` 只出现在本进程中正在写的有限时间内，放弃与放弃改动都不会被无限期阻断：放弃改动在保留 `syncing` 时返回 `E_STATE`，出口是重试交还或放弃。

**引用与同步**：
- `06` §6.1.6 人工编辑检出一行（L144）：续写期间同样是写回进行中，续写失败按同一规则处理；
- `goal.discard_human_edits`（L907）：写回失败后保留的 `syncing` 返回 `E_STATE`；
- `goal.abandon`（L933）：写回结束或失败后即可放弃。带回失败后保留 `syncing` 的 `in_review`/`accepted` 放弃时同样清除 `human_checkout`，满足 DDL 的 CHECK（L499–L500），检验目录按 `10` §10.8.3 第 7 步处理；
- `16` §16.1.12 `ProtoError.code`（L293）、§16.1.1 `Goal.humanCheckout`（L43）、`02` §2.4（L178）：`syncing` 改为 “写回已开始而未完成”；
- `10` §10.8.4 检出丢失一条（L1035）：续写失败时 `syncing` 保留，出口按 `06`；
- `04` §4.6.7（L667）与 `12` §12.6.4（L389）：写回期间与失败的文字（观察 2）。

**验收**：G31（`14` L107）补两组：
- 写回期间请求 `inspect.bring_back`、`inspect.close`、`goal.discard_human_edits`：都返回 `E_BUSY`（`inspect.bring_back` 不是 `E_STATE`）；
- 交还写回中途某个父目录持续不可写：
  - 命令返回 `E_INTERNAL`，卫星恢复，`idle`，Goal 仍为 `paused(human)`，检出保留；
  - 修复后重试成功，不修复时放弃照常被接受；
  - 还原也失败的一组：`syncing` 保留但不返回 `E_BUSY`，放弃被接受，重启后续写。

## 偏离与未决

- **失败出口取 “还原并退回写回之前的状态”，不取评审期望形态中的 “保留 `syncing` 等待重试”**：
  - 按指示，`syncState` 回到写回之前的状态，并给出失败提示与重试；
