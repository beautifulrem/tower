## 1. 总评

**第 105 轮的 4 条条目都按所问关闭**（核对见 §3）：
- 4 条都在唯一定义处落地，引用处改为引用；第 105 轮 §5 的 12 条观察全部落地（`06` L483 的 DDL 注释一处遗漏，记入观察 11）。
- 其中三处修法本身带出新的分支：
  - **R105-D5-01**：分发器总是安装、选项与 Pi 相同，写法成立。但 “空闲超时在 Host 启动时读一次，之后的改动从下一个 Host 起生效” 只说了分发器一半：Pi 的 SDK 会话在每次模型请求时再读一次同一设置，作为厂商 SDK 的请求时限（R106-D5-02）。
  - **R105-D5-02**：第三种结论与 “按服务该目标的 Host 保留” 成立；但标注因此只在服务该目标的 Host 存活时可见，而模型选择器的两个位置中，默认模型一处恒写条件句，另一处只在模型服务不可用时出现。G46 (d) 第八、九、十组的期望在照定义实现的版本上没有可观察的位置（R106-D7-01）。
  - **R105-D6-01**：只读启动时中止存活 Host 中的 Run 成立；但这次中止不经 settle 序列，第 ② 步（按令牌终止本 Run 的进程）不执行，而后台进程一行的终止范围恰好排除存活 Host 的 Run，被中止 Run 的后台进程在只读期间与解除之后都没有去向（R106-D6-01）。
- 另外，ADR-233 的横幅为未挂载的外接盘新写了 “不再使用该卷时请重启 Tower” 这一出口，重启之后的路径（卫星丢失、人工编辑检出丢失两行照字面触发）没有定义（R106-D13-01）。

**对本轮重点问题的回答**：

- **偏离（求不出的卷只在解除时按不足计）：接受**。
  - 理由成立：自检对每次启动都适用，若也按不足计，一个未挂载外接盘上的 Project 会使每次启动都只读，而只读期间不能移除该 Project，没有出路。
  - 两处规则不对称如实登记在 `16` L854 与 `12` L530。
  - 但它把 “重启 Tower” 变成登记的出口，重启之后未挂载卷上的 Goal 怎样处理见 R106-D13-01。
- **总是安装的分发器：成立**。
  - Bedrock 只在求出代理时自建 agent，否则走 Node 的 `https`，都不经全局 undici 分发器，与终端相同；
  - HTTP 类 MCP 在构造时取全局 `fetch`（`streamable-http.ts:211`），安装先于任何 MCP 连接，成立；
  - Host 中 Tower 自己的代码不发 HTTP 请求。
  - 空闲超时的另一半见 R106-D5-02。
- **`httpIdleTimeoutMs` 经受保护设置读取：成立**。M1 中 `projectTrusted` 恒为假（`05` L309），只读用户设置，打包的 Host 中各 Goal 读到同一值；值无效时 Host 启动失败按 F4b，与终端中 `pi` 启动失败相当。运行中改为无效值的分支见 R106-D5-02。
- **每次投递之前读列表：代价可以忽略；窗口的写法字面为真**。
  - 一个 Run 通常只有开场一次 `prompt`，`steer`、`followUp` 只在人介入时出现，所以 “一次投递之内” 在实际中常是 Run 的余下部分（含压缩与重试的请求）。
  - Pi 在每次模型调用之前等待 `turn_start` 的处理器（`agent-loop.ts:207`），tower-goal 已处理这一事件（`05` L625），在那里读一次即可把窗口缩到一次调用；ADR-233 只否定了包装 `registerProvider`，没有考虑这一读取点。
  - 后果按方向登记（扩展在密钥的信任边界之内，Agent 可影响的进程不因此得到密钥），属于已登记的取舍，记为观察 1。
- **只读启动时中止存活 Host 的 Run 与人工编辑检出、写回**：
  - 写回续写（`syncState='syncing'`）、重建中途崩溃两行都写数据库，属于推迟的中间状态检查，解除时执行，成立；
  - `goal.delete_kept` 对写回进行中返回 `E_BUSY`（`06` L913），人工编辑检出的目录不会在只读期间被这一命令删除，成立；
  - 但 Supervisor **没有重启**时进入只读，进行中的写回、卫星重建与接管物化在本进程中失败，它们的失败出口都要写数据库，解除时又没有推迟的检查可执行，见 R106-D6-02。
- **准入检查 i：成立**。租约一项给出 `waitReason = slot` 与卡片注明；F8 一项不写数据库。检查 i 排在 a–h 之后、而 a、f 等会写数据库，F8 一项宜先短路，称职的实现者会这样做，记为观察 6。

**ADR-233 的其余写法成立**（§3.3）：
- 分发器的选项、`undici.install()` 与单份 undici；
- “列出即不再注入” 是按 Host 的单向规则，C44 锁定；
- 代价一句与 `00` §0.5.1 一行；
- F8 并入 drain 时的 `outcome_reason`；复查的卷集合与求不出的卷；准备步骤的 `ENOSPC` 归 F8，③ 不终止 Host；
- `08` 规则 6、`12` 卡片条件、实况行、横幅与读屏；`16` 打包时 Host 预留的登记。

**本轮扫描发现的新问题**（全部为次要）：
- **`provider_unavailable` 的探测在哪个进程运行没有写**，而 ADR-232/233 已把凭据判定、`!` 命令、导入密钥与代理分发器都限定在 Host 中（R106-D5-01）。
- **Pi 的 SDK 每次请求都读 `httpIdleTimeoutMs`**：“Host 启动时读一次” 只对分发器成立；运行中改为无效值的分支没有定义；C43 的两次超时断言分辨不出分发器是否取了该值（R106-D5-02）。
- **只读启动时被中止的 Run 的后台进程没有去向**（R106-D6-01）。
- **进入只读时进行中的写回、卫星重建与接管物化没有去向**（R106-D6-02）。
- **标注只在服务该目标的 Host 存活时可见**，G46 (d) 的期望没有可观察的位置（R106-D7-01）。
- **`<wtRoot>` 所在卷未挂载时启动**，卫星丢失与人工编辑检出丢失两行照字面触发（R106-D13-01）。

  - 探测的唯一定义在 `06` L101（§6.1.4 第 5 项）：“探测只做连接与鉴权检查……**鉴权检查**（唯一定义，ADR-207）调用 Pi 的 `ModelRuntime.getAuth(provider)`”。`03` L96、`05` L486、C39 (e) 只引用它。没有一处写明探测在哪个进程中运行，“连接检查” 连向哪里、经不经代理也没有写。
  - 探测的对象是已暂停的 Goal，而 Host 在 Goal 暂停超过 5 分钟后退出（`06` L169）；探测从 60 s 退避到 10 min，多数探测发生时没有服务该 Goal 的 Host。实现者最自然的落点是持有暂停状态与计时器的 Supervisor。但这时：
    - **(a) 导入的密钥**：导入的密钥只作为 Host 运行时的覆盖存在（`11` L517；ADR-233 安全不变式 “模型密钥仍只经运行时注入、只在 Host 内存中”）。Supervisor 中新建的运行时没有这一覆盖，对密钥只在 shell 中、靠导入密钥运行的 provider，`getAuth` 得到 `undefined`（`ai/src/models.ts:300-314`），而正文写明 “探测把 `undefined` 计为失败”（`06` L101）——这些 Goal 永远不会自动解除；若为此在 Supervisor 的运行时中注入密钥，又与上述不变式的写法不符。扩展注册的 provider 在新运行时中是未知的，同样永远失败。
    - **(b) `!` 命令**：`11` L517 写明 “`auth.json` 中的 `!` 命令也只在 Host 中执行，Tower 的其他进程不求值、不执行它们”（ADR-232，理由是避免在 Host 之外再次触发密码管理器的提示）。`getAuth` 会执行 `auth.json` 的 `!` 命令，`models.json` 的 `!` 命令每次都执行、不缓存（`provider-composer.ts:467`）。探测放在 Supervisor 即违反这条规则，且每次退避都执行一次；`$VAR` 也会按 Supervisor 的环境求值，而 Supervisor 的环境没有定义。
    - **(c) 代理与 CA**：分发器只在 Host 中安装（`05` L474），`NODE_EXTRA_CA_CERTS` 只在 Host 环境中。只能经代理出网或做 TLS 拦截的网络中，Supervisor 的连接检查与 `getAuth` 中的 OAuth 刷新都会失败，自动解除同样不会发生。
  - 放在 Host 中则要为探测另起 Host（ADR-232 刚否定了 “短时的探查进程”），且没有会话时扩展 provider 尚未注册。
  - `getAuth` 被拒绝（令牌刷新失败、`!` 命令失败、存储读取失败，`ai/src/models.ts:305-309`）时是否计为失败也只隐含在 OAuth 一句中。
- **为什么是次要**：
  - 失败方向是 “不自动解除”，人仍可 `继续`（`goal.resume`）或切换模型，不丢数据；
  - 机密不进入 Agent 可影响的进程，Tower 的安全不变式（不自动把机密交给 Agent 可影响的进程）不受影响；
  - 但 `provider_unavailable` 的 `autoResume=true` 是 M1 的承诺（`03` L96、`16` §16.1.1），照正文实现的版本会在 “Supervisor 中探测、对导入密钥与代理网络永远失败、并在 Host 之外执行 `!` 命令” 与 “另起 Host” 之间分叉，且前者与 ADR-232/233 自己写下的两条规则冲突。
- **后果的类别**：
  - 靠导入密钥、扩展认证或只能经代理出网的用户，模型服务恢复之后 Goal 一直停在 `provider_unavailable`，卡片仍写自动恢复；
  - 你的 `!` 命令在 Supervisor 中按退避反复执行，可能反复弹出密码管理器的提示。
- **文档位置**：`06` L101（唯一定义）、L169；`03` L96；`05` L474、L486、L1499（C39）；`11` L517；ADR-207、ADR-232 R104-D5-01、ADR-233 安全不变式一段。
- **期望的回答形态**：在 `06` L101 的唯一定义中加一句写明探测的进程，二选一：
  - 探测在 Supervisor 中**只做连接检查**，经与 Host 相同的分发器与选项、带 Host 环境中的 CA 变量；鉴权一半推迟到下一次 Run 开始时 Host 中的检查（失败按 F7），并把 `03` L96 的 “鉴权检查会真正刷新 OAuth 令牌” 相应收窄；
  - 或探测在服务该 Goal 的 Host 存活时在其中执行，Host 已退出时只做连接检查；
  - 两种都写明 `getAuth` 被拒绝计为失败，C39 (e) 补一组导入密钥的 provider。

**R106-D5-02｜次要**（Pi 的 SDK 每次模型请求都读 `httpIdleTimeoutMs`；“Host 启动时读一次” 只对分发器成立；运行中改为无效值的分支没有定义；C43 的两次超时断言分辨不出分发器是否取了该值）

- **问题**：
  - `05` L474：空闲超时 “在 Host 启动时读一次，之后的改动从下一个 Host 起生效（Pi 的 CLI 同样在启动时读取，`main.ts:875`）；值无效时……Host 启动按 `06` §6.8 F4b 失败”。
  - 但 Pi 的 SDK 会话在每次模型请求时调用 `settingsManager.getHttpIdleTimeoutMs()`，作为请求的 `timeoutMs`（`core/sdk.ts:340-349`，`disabled` 换算为 2147483647），厂商 SDK 以它为客户端的 `timeout`（`ai/src/api/anthropic-messages.ts:636-644` 等）。Tower 的受保护设置管理器每个 Run 新建一次（`05` L261 ②），所以：
    - **(a)** Host 存活期间改了该设置，同一 Host 上后一个 Run 的请求时限取新值、分发器仍是旧值：例如改为 `disabled` 之后，响应仍在 300 s 无输出时被分发器中断，与 “从下一个 Host 起生效” 的写法不符（终端中交互模式改设置时两者一起变，`interactive-mode.ts:2063`）。
    - **(b)** Host 启动之后该设置被写成无效值，后一个 Run 的每次请求都在读取时抛出（`settings-manager.ts:147-156`），落在请求的错误路径上，而不是 F4b；它按 F6、F7 中的哪一条、是否进入 `provider_unavailable` 并被探测 “解除” 又失败，没有写。
    - **(c)** C43（`05` L1505）以 “30 s 时一个 40 s 不发响应头的端点失败、`disabled` 时成功” 断言空闲超时。30 s 时厂商 SDK 自己的 30 s 时限同样使请求失败；`disabled` 时即使分发器停在默认的 300 s，40 s 的停顿也会成功。两次断言都分辨不出分发器是否取了该值，而 C43 断言的分发器选项中不含两个超时。
- **为什么是次要**：失败明确可见（请求报错或 Host 启动失败），不丢数据，不放宽沙箱，Host 环境不变。但正文对生效时机的承诺与 Pi 的实际行为不符，运行中改为无效值的分支会使实现分叉，契约测试对唯一定义中新写的一项没有约束力。
- **后果的类别**：
  - 在终端中关掉空闲超时、使用慢速本地模型的用户在同一 Host 的后续 Run 中仍于 300 s 失败——这正是回应拒绝 “不读取” 时要避免的情形；
  - 设置写坏之后，Goal 在不同实现中分别停在 `prepare_failed`、`stalled{engine_error}` 或反复的 `provider_unavailable`；
  - 分发器漏掉超时选项的回退在 C43 中照样通过。
- **文档位置**：`05` L474、L261、L1449（D63）、L1505（C43）；`06` L1195（F4b）；ADR-233 R105-D5-01 一条。
- **期望的回答形态**：在 `05` L474 的唯一定义中改一句：
  - 写明两处读取：分发器取 Host 启动时的值，SDK 的请求时限由 Pi 按每个 Run 的设置管理器读取；或让 Tower 传给 Pi 的受保护设置管理器在 Host 存活期间固定返回 Host 启动时的值（`ReadThroughSettingsStorage` 已由 Tower 实现，一处守卫）；
  - 写明 Host 存活期间该设置变为无效时的去向（如沿用 Host 启动时的值并记 `engine.error`）；
  - C43 改为直接断言分发器的 `bodyTimeout`/`headersTimeout`，或以超过 300 s 的停顿区分。

### D6 系统架构与可靠性

**R106-D6-01｜次要**（只读启动时被中止的 Run 不经 settle 序列，其后台进程既不在 settle 第 ② 步、也不在后台进程一行的终止范围内；会话也不 dispose）

- **问题**：
  - 正常的 F8 drain 中，Run 被 `abort` 之后照常经 settle 序列（`05` L645 `agent_settled{aborted}` 一行），其中第 ② 步 “按 Run 令牌枚举并终止本 Run 的全部进程”，drain 最后还有 `dispose`（`06` L97）。
  - `06` L1199 新写的只读启动：“Supervisor 让它们中止其中进行中的 Run（`abort`，不写数据库、不 drain）”，随后 “按 §6.1.6 ‘Agent 后台进程’一行终止残留的后台进程”。但该行的范围（`06` L145，终止范围的唯一定义）：
    - 第一类是 “**Host 已不存在**的未结束 Run 的令牌”；第二类是 “因 Host 退出或挂死而以 `crashed` 结束” 的 Run；
    - 并明确写 “只重启 Supervisor 时，main 交回的存活 Host 重新接上，其中进行中的 Run 不在此列——不终止”。
  - 所以本轮新中止的、存活 Host 中的 Run，其后台进程（开发服务器、`--watch` 构建等，Pi 的 bash 以 `detached` 派生，`06` L64）在只读期间不被终止；解除时 “Run 中崩溃” 一行结束这些 Run，Host 仍存活，它们仍不属于任一类，要等到该 Host 退出之后的一轮。drain 写不进之后 Supervisor 重启、Host 存活的一支同此。被中止的会话也没有 `dispose`。
- **为什么是次要**：不丢失人的工作，不涉及机密或 git 元数据；Host 退出之后的一轮最终会终止它们。但这是 ADR-233 新写的中止与唯一的终止范围之间的缺口，照字面实现，F8 “只读期间因此没有 Run 在运行” 的意图只对 Agent 的回合成立。
- **后果的类别**：
  - 只读期间后台进程继续写盘，可能使空间无法回到 2 GB 之上、解除迟迟不发生；
  - 解除并自动继续之后，旧令牌的进程不属于新 Run，它们在没有工具调用时的写入按来源不明处理，Goal 进入 `paused(external_change)`；端口段与新 Run 冲突；
  - 被中止的会话仍加载在 Host 中，同一 Goal 的新 Run 在同一 Host 上再开会话。
- **文档位置**：`06` L1199、L145、L64、L97；`05` L645；`10` §10.3.1 扫描时机 ②。
- **期望的回答形态**：在 `06` L1199 “只读启动时” 一句补半句，二选一：
  - 中止之后对这些 Run 执行 settle 的第 ② 步（按令牌终止，不写数据库；补检查点推迟到解除）并 `dispose` 会话；
  - 或在 `06` L145 的第一类中加 “§6.8 F8 中止而数据库中没有 `run.ended` 的 Run（Host 存活时同样）”。
  - G35e (q) 只杀死 Supervisor 的一组布置一个后台进程，断言只读期间它已被终止。

**R106-D6-02｜次要**（Supervisor 没有重启时进入只读：进行中的写回、卫星重建与接管物化在本进程中失败，它们的失败出口都要写数据库，解除时又没有推迟的检查可执行）

- **问题**：
  - F8 为进入只读时进行中的验证与准备给了去向（`06` L1199 “进行中的验证与准备”），没有写其他会写卫星或用户检出的进行中操作：
    - **写回**（交还、检验带回，`syncState='syncing'`）：写回集合大量写入卫星所在的 `<wtRoot>` 卷，正是最可能遇到 `ENOSPC` 的地方；“写回在本进程中失败” 的出口（`06` L920 ③）在一个事务中重置 `human_checkout` 并生成 Needs-You。数据库只读时这一事务写不进，`syncing` 留在数据库中，而正文的不变式是 “`syncing` 只存在于本进程中正在写的有限时间内，以及崩溃到重启之间……命令与自动转移从不在 ‘写回已不在进行而 `syncing` 仍在’ 的状态上执行”（同处）。
    - **卫星重建**（`satellite_rebuilding=1`）：重建失败的出口（`06` L139）在同一事务中清除标记并进入 `paused`；写不进时标记留在 1，`goal.resume` 的守卫因此返回 `E_STATE`。
    - **接管物化**（`goal.take_over` 从改名到写入 `human_checkout` 的事务）：同理。
  - 解除时 F8 “先执行推迟的中间状态检查”——只有只读**启动**时才有推迟的检查（同处 “只读期间 Supervisor 启动”）。Supervisor 一直在运行时，上述三种状态的续做（`06` L144、L140 两行）只在下一次启动时发生。
- **为什么是次要**：不丢失人的工作——T1 已写入影子，人工编辑检出与检验目录保留，`.kept-*` 不被删除；重启 Tower 即由 §6.1.6 的已有行续做。但这是与 R104-D6-02（验证与准备）同类的缺口：F8 让 “释放空间后自动恢复、不需要重启” 成为承诺，而这几种进行中的操作在解除之后停在只有重启才能清除的中间状态，正文写下的 `syncing` 不变式在这一分支上不成立。
- **后果的类别**：
  - 释放空间之后，写回到一半的 Goal 停在 `syncing`，交还与带回返回 `E_BUSY`，卫星停在半写的树；
  - 重建到一半的 Goal 不能 `继续`，直到重启 Tower；
  - 不同实现分别选择 “解除时补跑 §6.1.6 的对应行”“当作崩溃要求重启” 或 “在本进程中重试”。
- **文档位置**：`06` L1199、L920、L910、L909、L139、L140、L144；`10` §10.8.4、§10.16.2。
- **期望的回答形态**：在 `06` L1199 “进行中的验证与准备” 一句补一句：进入只读时进行中的写回、卫星重建与接管物化在本进程中停止，按崩溃处理（不执行写数据库的失败出口），解除时与只读启动相同，先按 §6.1.6 的对应行（人工编辑检出 `syncing`、卫星重建中途崩溃）续做，再执行其余规则；G35e (q) 补一组写回中途写满 `<wtRoot>` 卷。

### D7 诚实与验证

**R106-D7-01｜次要**（标注只在服务该目标的 Host 存活时可见；模型选择器的两个位置中一处恒写条件句、一处只在模型服务不可用时出现；G46 (d) 的期望没有可观察的位置）

- **问题**：
  - `11` L517（ADR-233）：某个目标的标注取服务该目标的 Host（“正在运行它的，或上一次运行它而仍存活的”）的结论；还没有这样的结论时（“服务它的 Host 已退出”）以及 “设置中不属于某个目标的默认模型” 写条件句。模型选择器的位置写为 “设置 › 引擎的默认模型，`04` §4.15；为目标切换模型，`04` §4.18.3 模型服务不可用一行”。
  - 三者合在一起：
    - 设置中的默认模型**恒写**条件句；
    - 按目标的选择器只出现在 `04` L1506 的 `为受影响目标切换模型`，即只在模型服务最终失败时；
    - Host 在 Goal 进入 `in_review` 或暂停超过 5 分钟时退出（`06` L169），所以第一个 Run 正常结束之后，照定义实现的版本写条件句。
  - 于是 `已有你的 pi 配置中的凭据，Tower 用它`、`由扩展处理认证`、`Tower 用导入的密钥` 三种标注，只在 “模型服务不可用、且服务该目标的 Host 尚未退出” 时可见。而 `11` L517 对 `!` 命令在 Tower 中得到空值、在终端中成功的情形，正是靠这一标注告知 “两边可能是不同的账户”。
  - G46 (d)（`14` L134）：第八组 “第一个 Run 之后模型选择器写 `已有你的 pi 配置中的凭据，Tower 用它`”，第九组两处 `Tower 用导入的密钥`，第十组 “该 Goal 的模型选择器写 `由扩展处理认证`”、打包的两个 Goal “分别写……不随另一个 Host 的报告翻转”。这几组都没有布置模型服务不可用，照定义实现的版本上没有可观察的位置；若在第一个 Run 之后观察，按定义应为条件句。
  - Supervisor 只重启时各 Host 的结论（只在内存中）丢失，Host 重新接上时是否重报、投递边界读取之后是否重报，也没有写（C44 期望 `followUp` 之前的读取之后得到第三种结论）。
- **为什么是次要**：用哪份凭据的实际行为由 Pi 判定、与终端一致，标注不实不改变计费以外的任何事；不丢数据，不涉及 Agent 可影响的进程。但 R104-D5-01 起要求的 “标注与 Host 实际所用的一致” 现在成了几乎看不到的告知，G46 的三组期望在正确的实现上无法照写法验证，实现会在 “另设目标页上的显示位置” 与 “照字面只在切换模型时显示” 之间分叉。
- **后果的类别**：
  - 用 `!` 命令取密钥、在 Tower 中回落到导入密钥的用户，日常看不到 `Tower 用导入的密钥`，不知道两边计入不同的账户；
  - G46 (d) 的验收结果取决于测试者在哪里、什么时候观察。
- **文档位置**：`11` L517；`04` L1461、L1506、L1273（默认模型）；`05` L489；`06` L169；`14` L134（G46 (d) 第八至十组）；`05` L1506（C44）。
- **期望的回答形态**：在 `11` L517 的唯一定义中二选一：
  - 定义一个按目标、始终可见的位置（如目标页的引擎一行或卡片的模型悬停），取服务该目标的 Host 的结论，Host 退出之后保留最近一次的结论并注明 “上次运行时”；或 Supervisor 按 (provider, 扩展集合) 保留最近一次结论，供默认模型一处使用；
  - 或保留现有位置，把 G46 (d) 三组的期望改为 “Run 进行中、在 `为受影响目标切换模型` 中”，并布置触发条件；
  - 两种都写明 Host 重新接上与投递边界读取之后重报结论。

### D13 隔离、git 与并发

**R106-D13-01｜次要**（`<wtRoot>` 所在卷未挂载时启动：卫星丢失与人工编辑检出丢失两行照字面触发，后者告知 “未交还的改动无法恢复”，而 ADR-233 把 “重启 Tower” 写成了这一情形的出口）

- **问题**：
  - ADR-233 新写：复查中求不出剩余空间的卷 “如 `<wtRoot>` 在未挂载的外接盘上”（`06` L1199），横幅写 `挂载它后自动恢复，不再使用该卷时请重启 Tower`（`12` L530），`16` L854 登记 “只读要到挂载或重启 Tower 才解除”；启动自检中求不出的卷不触发只读启动。
  - 重启之后 §6.1.6 照常执行，而正文没有任何一处定义 “Project 的 `<wtRoot>` 所在卷不可用” 时的处理（只有进行中操作守卫对 `locked` 而位置不存在的工作树停写，`15` R67-D13-03）：
    - **卫星丢失**一行（`06` L139）由 “启动检查……发现检出完成标记存在的卫星的工作目录或 `_gitdirs/<goalId>` 不存在” 触发，对该卷上每个 Goal 自动重建；重建目标在不存在的卷上，失败则逐个进入 `paused(satellite_missing)` 并生成 Needs-You；
    - **人工编辑检出**一行（`06` L144）：“`idle` 且目录不存在（重启时检查……）→ 清除 `human_checkout`……生成 Needs-You……‘人工编辑检出已丢失，未交还的改动无法恢复’”。目录其实完好地在未挂载的卷上；清除 `human_checkout` 之后交还的路径也随之断开，重新挂载后该目录只是已脱离的副本。
  - 横幅的 “不再使用该卷” 一句暗示放弃该卷，但同一情形也发生在 “只是暂时拔掉外接盘就启动了 Tower” 时，后者不经横幅、更常见。
- **为什么是次要**：
  - Tower 不删除任何目录（`10` §10.2 “人的工作现场不自动删除”），文件仍在未挂载的卷上，重新挂载之后可以手工取回；
  - 不涉及机密、沙箱或 git 元数据。
  - 但照字面实现会对人说 “无法恢复” 而事实并非如此，并断开交还的路径；对每个 Goal 发起注定失败的重建与 Needs-You；实现会在 “照字面触发” 与 “先判别卷不可用” 之间分叉。
- **后果的类别**：
  - 人看到 “未交还的改动无法恢复”，可能放弃本可交还的修改；重新挂载之后要手工从已脱离的副本取回；
  - 该卷上的全部 Goal 进入 `satellite_missing` 并各生成一条 Needs-You，重新挂载之后仍要人逐个重试重建（`satellite_missing` 且 `satellite_rebuilding=0` 的 Goal 不再自动重建，`06` L139）。

- **期望的回答形态**：在 `06` §6.1.6 加一条守卫（或在 L139、L144 两行各加半句）：`<wtRoot>` 本身不存在（卷未挂载）时，该 Project 视为不可用——两行不触发，卡片注明 `<wtRoot> 所在卷不可用`，准入经检查 i 的同一写法等待，卷重新出现时照常；或保留现行为，把 L144 的告知改为 “目录在 `<路径>` 不可访问；卷重新出现后它是已脱离的副本”，并在 `12` L530 的 “重启 Tower” 一句后登记这一后果。

### 不扣分的观察

1. **投递之内的窗口与更窄的读取点**：一个 Run 通常只有开场一次 `prompt`，所以 “一次投递之内” 在实际中常是 Run 的余下部分（含 Pi 的重试与压缩请求）。Pi 在每次模型调用之前等待 `turn_start` 的处理器（`agent-loop.ts:200-208`），`transformContext` 也在组装请求之前被等待（`:385-391`），tower-goal 已处理 `turn_start`（`05` L625）；在其中读一次列表并等待 `removeRuntimeApiKey`，可把窗口缩到一次调用（`before_provider_request` 不行，它在求出凭据之后）。不采用时宜把 `11` L517 的窗口写为 “到该 Run 结束（含压缩与重试）”，`00` L112 同步。
2. **F8 中止的判别**：`06` L148 写 “§6.8 F8 中止而没有写进 `draining_for` 的 Run 不论 Host 是否存活都按本行处理、取 `app_quit`”，F8 本身（L1199）只写存活 Host 一支。Host 已不存在、Supervisor 又重启时，来源无从得知，这一句与同行 “只有 Supervisor 重启而该 Run 的 Host 已不存在时取 `engine_crash`” 冲突。按可观察状态判别也会收入非 F8 的中止：Supervisor 重启的几秒内扩展调用 `ctx.abort()`，以及回应已登记的卫星丢失双重故障，这些 Goal 的卡片写 `磁盘已满` 并按第 5 项自动继续。宜把 L148 收窄为 Host 存活一支，或让 Host 在内存中记下 `abort` 的原因、重新接上时报告。
3. **只读期间没有记录的中止与 G35e (q) 的卡片**：drain 写入失败与只读启动中止的 Goal，数据库中仍为 `running`、Mode 为 `settled`，实况行写 `已停`（`12` L370），不提磁盘满；横幅已说明 Tower 已暂停运行，影响小。宜在 `12` L395 补一种 `已中止（磁盘已满）· 释放空间后恢复`。G35e (q) 的 `已暂停 · 磁盘已满 · 释放空间后自动恢复` 只对 drain 写入成功的一组成立（期望的字面已分组），宜写明。
4. **③ 中止的会话**：开场已发出而 `run.started` 写不进时，被中止的会话没有 `dispose`，开场已追加在会话文件中，重新准入时是否复用、开场是否重复没有写；这一窗口内派生的进程的令牌没有持久化（`runs.process_token` 随 `run.started` 写入），不在任何终止范围内。窗口为秒级。
5. **复查集合与触发集合**：F8 由任何 git 的 `ENOSPC` 触发，含用户仓库中的写入（租约、M1 验收的分支）；`<wtRoot>` 为回退位置（`16` L290）时用户仓库所在卷不在复查集合中，可能解除之后又进入。宜并上本次触发 `ENOSPC` 的卷（进程内），或登记。
6. **准入检查 i 的位置**：检查 a、b、d、g、h 写 `wait_reason`，f 写 `paused(budget_hard_cap)`，都在 i 之前；F8 已写 “停止准入新 Run”，宜把 F8 一项写为先于 a 短路。
7. **只读启动时已写入 `draining_for` 的 drain**：属于推迟的中间状态检查，解除时续做；`app_quit` 无法并入，结果是 drain 自己的目标（如 `paused{human}`），不带 `disk_full`；`take_over` 的目标在解除时（可能数小时之后）执行。宜写一句。
8. **`由扩展处理认证` 的含义**：扩展只加头部、请求按 F7 失败时，模型选择器仍写 `由扩展处理认证`，读来像认证正常；宜在该情形下与 F7 的卡片并列，或把文字写为 `由扩展 <名字> 负责认证，Tower 不用导入的密钥`。
9. **规则 6 与横幅的几处细节**：侧栏顶部一行入口的生命周期（下一次离开、点开或打开该 Goal 时消失）与多个被压下时的写法、与 “下一件” 的次序没有写；横幅在自检不足 2 GB 而未满时同样写 `磁盘已满`；横幅消失与后缀追加时不播报，读屏用户不知道已恢复可写。

### 设计是否完成

ADR-233 关闭了第 105 轮的全部四条条目：
- Host 总是安装与 Pi 相同的分发器，空闲超时读你的设置，只用一份 undici；
- 扩展注册的 provider 在每个 Run 与每次投递之前读取，列出即不再注入，标注有第三种结论并按 Host 保留，代价一句如实；
- 只读启动时中止存活 Host 的 Run、由已有恢复行求出结果，不写数据库的清理照常执行，复查的卷集合确定；
- 准备步骤的 `ENOSPC` 归 F8，③ 不终止共用的 Host。

- **R106-D13-01**：`<wtRoot>` 所在卷未挂载时启动，两行恢复规则照字面触发。

全部为次要：没有一条会使照文字实现的人违反所述的安全不变式或丢失人的工作，每一条都能在已有的唯一定义处加一句或一条守卫关闭。
