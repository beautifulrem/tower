## 1. 总评

**第 69 轮的 8 条全部落地**：
- 逐条回到正文核对：已解决 8，部分 0，未解决 0。其中三条的修订文字本身带出了新的边界，另立为本轮条目（见下）。
- 第 69 轮 §5 的 18 条观察中，17 条按回应改动并已核对，观察 18 本就无需改动。

**ADR-197 的主干成立**：
- **回退位置的 “清除全部”**：`09` L565 写明 `_human/<goalId>/`、`_inspect/<goalId>/` 与其上级目录留在原路径，`~/.tower` 中其余内容照删，`~/.tower` 不作为整体删除；L557 引用；G46 第十组补了回退位置一组（`14` L134）。
- **Agent 沙箱的回退例外**：`11` L351 的例外集合 = 写允许三项（卫星工作区、`_gitdirs/<goalId>`、`_stores/<goalId>/`）+ 只读的 `$SH` 与 `_stores/_shim/`，与默认位置下 Agent 的允许集合逐项相同。其他 Goal 的卫星与 gitdir、`_human/**`、`_inspect/**`、`_verify/**`、`$VS`、其他 Goal 的 `_stores/<id>` 照常拒绝。`$SH` 与镜像 `objects/` 在默认位置下本就可读，**没有因例外而多读到其他 Goal 的数据**。
- **`⌘⇧O`**：已删除（全文只在 `16` §16.1.13 与 `15` 历史中出现）。`10` L29 补了 “任何入口都不在外部程序中打开卫星”。逐一核对其他打开路径：
  - `E` / `⌘⇧T` 只打开人工编辑检出；
  - `O` 在 human 标准行上只打开检验检出，其余位置在 Tower 内打开证据与日志；
  - `04` 与 `16` 中没有 “在 Finder 中显示”、文件链接或用默认程序打开产物的入口；
  - 只有 http(s) 链接经确认后交给 `shell.openExternal`（`11` L607），与卫星无关。
  - 结论成立。
- **`--prune`**：命令行带 refspec 时，`git fetch --prune` 只修剪这两个目标命名空间，并且先修剪再写入。Tower 要求 git ≥ 2.40，这一行为早已具备，D/F 冲突因此不再使获取一直失败。保留表（`10` L1272）与 `09` L570 已改为同一说法。活跃 Goal 的 base 祖先由 `refs/tower-live/*` 保持可达，不依赖 `refs/user/*` 的残留。
- **生效额度与跨越触发**：`06` L349–351 是唯一规则，`03` L82–83、`06` L881、L938、`08` L352/L504、`12` L585、`16` L614 都已对齐；G33f 的三组与规则一致。
- **`privacy.purged` 的判据**：只认 `scope = "goal"`，“彻底忘记” 不再使进行中的 Goal 消失。
- **派生副本**：待批准的提议随清除删除；复活出的 Goal、子 Goal 与汇总条目如实列出；搜索索引只在内存中（`13` L119），丢弃即可。
- **`00` R7**：改弱为真，与 `02` §2.5 L356–366、`04` L347/L1130、`16` L615 一致。

**新发现 5 条：重要 1、次要 4。**
- **“清除全部” 之后 Goal 编号从头开始，与被保留的 `_human/<goalId>`、`_inspect/<goalId>` 同名**（R70-D13-01，**重要**）。
  - ADR-196/197 让这些目录在清除全部后留在原路径，并告诉人 “Tower 不再管理”。
  - 但 GoalId 是数据库内的单调短号（`02` L46）。数据库删除后再添加同一仓库，`<wtRoot>` 路径不变，新 Goal 会复用旧编号。
  - 照 `10` L444 “删除卫星时……一并删除仍存在的 `_human/<goalId>/`”，或照 §10.8.3、§10.8.4 在该路径上物化检出，都会删除或覆盖人留下的改动。
- **次要 4 条**：
  - 回退位置的读拒绝例外对**验证器与检验检出**不完整：两者都要读 `$SH` 中的 Node 运行时，检验沙箱还要读检验目录本身。另外，命令分类器 “写 `~/.tower/**` → 硬底线” 一行没有回退例外，而 `10` L541 声称这类规则 “各有一条例外” 并只列了两处（R70-D11-01）。
  - `privacy.purged` 的续做规则有两处缺口（R70-D6-01）：
    - `goal` 档的事件不含定位信息，而 Goal 到 Project 的关联在事务内已被删除；
    - `project` 档为每个 Goal 追加的事件从不配对 `filesDone`，按续做行会在每次启动时被判为未完成。
    - 此外，G46 的期望 “`privacy.purged{scope:"goal"}` 只有一条” 与协议矛盾。
  - 待批准提议所在的 `ratify` 条目是 “每天每作用域一条” 的聚合条目，ADR-197 对它同时给出 “按彻底忘记删除” 与 “汇总条目不改写、只列条数” 两条相反的规则，G46 的期望又取前者（R70-D12-01）。
  - 合同修订后 “以新版本为准” 会悄悄作废此前的 `extend_budget`，修订编辑器对预算的预填没有规定；而预填生效额度又会使修订被判为 “放宽”，只能在本机执行（R70-D4-01）。

### D13 隔离、git 与并发

**R70-D13-01｜重要**（“清除全部” 删除数据库后，GoalId 从头编号，而 ADR-196/197 保留在原路径的 `<wtRoot>/_human/<goalId>/`、`<wtRoot>/_inspect/<goalId>/` 以旧编号命名。再次添加同一仓库后，新 Goal 会与这些目录同名。`10` 中删除与物化这两类目录的规则都只按 `<goalId>` 拼路径，不区分 “本库创建的” 与 “先前保留的”，照做会删除或覆盖人留下的改动）

- **问题**：
  - **编号会复用**：
    - `02` L46：`GoalId` 是 “人类可读短号，如 G-0142（单调递增，本地唯一）”。正文没有分配规则，计数只能来自数据库。
    - “清除全部”（`09` L565）删除 `~/.tower` 中的数据库与一切元数据，只留下 `_human`、`_inspect` 及其上级目录。之后重新启动即是一个新库，编号从头开始。
  - **路径会复用**：
    - 默认 `<wtRoot>` = `<checkoutParent>/.tower-wt.noindex/<repoName>`（`10` L237），只由检出路径决定；
    - 回退 `<wtRoot>` = `~/.tower/worktrees/<projectId>`，而 `projectId = hash(canonical_root)`（`06` L435），同一仓库再次添加时不变。
    - 因此清除全部后再添加同一仓库，新 Goal `G-000N` 的 `<wtRoot>/_human/G-000N`、`_inspect/G-000N` 正是被保留的旧目录。
  - **会走到的三条路径**：
    - **删除卫星时**（`10` L444，归档时与放弃 7 天后）：“一并删除……仍存在的 `<wtRoot>/_inspect/<goalId>/`（先比较，有被修改的文件时先询问）与 `<wtRoot>/_human/<goalId>/`（有未交还改动时先询问）”。
      - 新 Goal 从未接管，`humanCheckout` 为空，“未交还改动” 没有比较基准。照字面实现，该目录被当作本 Goal 的残留直接删除。
      - 即使询问，提示也以新 Goal 的名义出现，人无从知道其中是旧 Goal 留下的改动。
      - 这条路径不需要人做任何操作，只要新 Goal 走到归档。
    - **我来改**（`10` L912 第 2 步）：在 `H=<wtRoot>/_human/<goalId>` 以 `checkout-index` 物化 T0，第 3 步再 “新建 gitdir H/.git”。路径已存在时没有规则，覆盖写出会改掉人原来的文件。
    - **打开检验**（`10` L857 第 1 步）：同样在 `_inspect/<goalId>` 上覆盖写出 pin。
  - **与已声明的承诺相反**：
    - `09` L557：这些目录 “可能含你的改动，Tower 不再管理；不需要时请自行删除”。
    - ADR-196/197 为此专门写了 “从不删除”，并在回退位置下改为原路径保留。
    - 它们又被排除在系统备份之外（`10` L543–546），删除后无处找回（第 69 轮观察 2 已写入结果说明）。
  - G46 第十组（`14` L134）只验证清除前后目录逐文件相同，不覆盖 “清除全部 → 再添加同一仓库 → 新 Goal 走到同一编号” 的后续。
- **为什么是重要**：
  - 照 `10` 的删除与物化规则逐字实现，会删除或覆盖人留下的改动，正是 ADR-196/197 要保护的那一类数据。
  - 触发条件：
    - 清除全部时有被保留的目录（ADR-184 的 H，或人选择 “保留目录，稍后决定” 的检验目录）；
    - 之后再次添加同一仓库；
    - 新 Goal 的编号增长到旧编号并被归档。
    - 第三步在继续使用 Tower 时几乎必然发生：编号从头开始、逐个递增。
  - 修法只需一句。
- **文档位置**：`02` L46；`06` L435；`09` L557、L565；`10` L237–239、L444、L543–546、L857、L912、L923；`14` L134。
- **期望的回答形态**：在唯一定义处加一条守卫，二选一或并用：
  - **两种检出只作用于本库记录过的目录**（`10` §10.8.3、§10.8.4 与 L444）：
    - 创建时若路径已存在且不是本 Goal 当前记录的检出（`humanCheckout.path` / 本次检验记录），不覆盖。可以把旧目录原样改名到同级的 `<goalId>.preserved-<时间>` 并在结果中列出，或返回 `E_STATE` 并列出该路径。
    - “删除卫星时” 只删除本 Goal 记录过的两类检出，其余同名目录跳过并列出。
  - **编号不复用**（`02` §2.2 加一句分配规则）：新 Goal 的编号跳过任一已知 `<wtRoot>` 下已存在的 `<goalId>`、`_human/<goalId>`、`_inspect/<goalId>`；或在清除全部时保留一个只含编号高水位的文件。

### D6 系统架构与可靠性

**R70-D6-01｜次要**（ADR-197 的续做规则有两处缺口：`goal` 档事件不带定位信息，而该 Goal 到 Project、`<wtRoot>` 与镜像的关联在同一事务中已被删除；`project` 档为每个 Goal 追加的 `{scope:"goal", id}` 事件从不配对 `filesDone`，按续做行会在每次启动时被判为未完成。G46 的期望 “只有一条” 又与 “完成后再追加一条” 的协议矛盾）

- **问题**：
  - **定位信息**：
    - `06` L941：`roots` 只在 `project` / `all` 档写入，理由是 “Project 行删除后续做仍需要”。
    - 但 `goal` 档的文件清单（`09` L563）同样需要 Project：
      - 卫星路径（`bindings.worktree_path`）；
      - `<wtRoot>/_gitdirs/<goalId>`、`_stores/<goalId>`；
      - 备份 bundle `goal-bundles/<projectId>/<goalId>.bundle`；
      - 镜像 `~/.tower/projects/<projectId>/mirror.git` 中的 ref；
      - 验证槽位。
    - 而 `goals` 表没有 `project_id` 列（`06` L452–505）。Goal 与 Project 的关联只在 `bindings` 与 `checkpoints` 中，二者都在同一事务中删除（`09` L563 “删除本 Goal 的合同、绑定、Run、会话、检查点……”）。
    - 正常路径可以在事务前读出路径；崩溃后续做（`06` L142）与 “对已清除的 Goal 再次执行时只重做文件删除”（L941）都无从定位。照字面实现，只能删 `~/.tower/goals/<goalId>/`，其余静默跳过，而 Goal 已按事件隐藏。这正是 R69-D6-01 要避免的 “清除结果不真且无从察觉”。
    - 实现者可以遍历全部 Project 去找，也可以给事件补字段，两种做法的结果不同（Project 改过 `worktreeRoot` 时前者找不到）。
  - **配对**：
    - `06` L941：“`project` 档在同一事务中另为范围内每个 Goal 追加 `{scope:"goal", id}`……完成后追加同一 `scope`、`id` 且 `filesDone: true` 的一条”。只说为本命令的 `scope`、`id` 追加完成事件。
    - `06` L142 续做行的判据：“有不带 `filesDone` 的 `privacy.purged`，且没有同一 `scope`、`id` 带 `filesDone: true` 的一条”。
    - 照字面实现，逐 Goal 的事件永远没有配对，每次启动都会对它们 “续做”。这在幂等时只是浪费，但它同样需要定位信息，而这时连 Project 行都已删除。
  - **测试期望与协议矛盾**：`14` L134 G46 第十组：“中途终止的一组重启后续做完文件删除，`privacy.purged{scope:"goal"}` 只有一条”。按 L941，完成后应有两条（不带与带 `filesDone`），再次清除是否追加事件也没有写。
- **为什么是次要**：不涉及安全或人的改动。但这是隐私承诺的续做规则，照文实现会出现两种结果：漏删且无从察觉，或每次启动无谓续做。
- **文档位置**：`06` L142、L452–505、L529–541、L577–590、L941；`09` L563；`14` L134。
- **期望的回答形态**：在 `06` L941（唯一定义）补两句：
  - **定位**：`roots` 改为各档都写，`goal` 档另带 `projectIds`（或直接写入该 Goal 的卫星、bundle 与镜像路径）。续做只按事件中的定位信息执行，不读已删除的行。
  - **配对**：`project` 档逐 Goal 的事件随 `project` 的完成事件一并视为完成（续做行排除它们），或为每个 Goal 各追加一条 `filesDone`。
  - G46 的期望改为 “不带 `filesDone` 与带 `filesDone` 的 `scope:"goal"` 事件各一条；再次清除不追加”（或按所选写法改写）。

### D12 记忆与学习（隐私）

**R70-D12-01｜次要**（待批准的记忆提议在收件箱中以 `ratify` 条目出现，而 `ratify` 是 “每天每作用域一条” 的聚合条目，可能同时含有其他 Goal 的提议。ADR-197 对它同时给出两条相反的规则：“以它们为对象的 Needs-You 条目……按‘彻底忘记’处理”（删除），与 “项目或全局汇总的 Needs-You 条目（`ratify`……）不改写，列出条数”。G46 的期望取前者）

- **问题**：
  - `08` L209：`ratify` 的去重键为 `rt:{scope}:{yyyy-mm-dd}`，“每天每作用域一条聚合条目，‘N 项待批准’”；`08` L239、`09` L431 同此。
  - `09` L563（清除一个 Goal）：来源为本 Goal 且仍为 `proposed` 的提议删除，“以它们为对象的 Needs-You 条目与相关决定按‘彻底忘记’一行处理”。L562 “彻底忘记” 的处理是 “以它为对象的 Needs-You 条目删除”。
  - `09` L573：“项目或全局汇总的 Needs-You 条目（`ratify`、`digest`、`flood`、`backlog`）……不改写，结果列出条数，随其 owner 的清除删除”。
  - `14` L134 G46 期望：“待批准的提议与以它为对象的 `ratify` 条目已删除”。
  - 两种读法的结果：
    - **删除整条**：同一天同一作用域中其他 Goal 的待批准提议从收件箱消失，只能在记忆管理器中找到，直到下一条聚合条目出现。
    - **不改写**：条目的 “N 项待批准” 与证据中仍有已删除提议的文本，与 “提议随清除删除” 不一致，结果只列出条数。
  - “彻底忘记” 单独作用于一条提议时，也有同样的歧义。
- **为什么是次要**：不丢人批准过的数据；影响限于收件箱中一条聚合条目，但两条规则直接冲突，测试期望又取其中一边。
- **文档位置**：`09` L431、L562、L563、L573；`08` L209、L239、L509；`14` L134。
- **期望的回答形态**：在 `09` §9.12.4 写一句：聚合的 `ratify` 条目从其对象集合中移除被删除的提议，并重算 “N 项待批准”；集合为空时以 `obsolete` 关闭（`08` §8.8 已有该结局）。L573 的 “不改写” 改为只指 `digest`、`flood`、`backlog`。“彻底忘记” 一行同样适用。

### D4 领域模型与生命周期

**R70-D4-01｜次要**（生效额度 “修订合同产生新版本后，以新版本为准”，即修订之后此前的 `extend_budget` 不再计入，G33f(c) 明确测试了这一点。但合同修订往往与预算无关，修订编辑器对 `Budget` 预填什么没有规定：预填合同值时，人批准过的扩展在修订后悄悄失效，硬上限可能立即再次触发；预填生效额度时，修订相对上一版 “提高” 了预算，按 `16` §16.5 判为放宽，只能在本机执行）

- **问题**：
  - `06` L349：生效额度 = 当前合同版本的 `Budget` 与 “该版本批准之后” 的 `extend_budget` payload 取最大值；“修订合同产生新版本后，以新版本为准”。
  - `14` L115 G33f(c)：修订后 “此前的 `extend_budget` 不再计入”。
  - **常见路径**：
    - Goal 在 US$10 硬上限暂停，人 `budget.extend{usdHard: 15}` 后继续，用量到 US$12；
    - 之后进入 `verify_failed_limit`，出口正是 “`resume` 并修订合同”（`03` L86）；
    - 人只改验收标准，新版本的 `Budget` 若沿用上一版合同的 US$10，下一次开 Run 前即进入 `budget_hard_cap`（`03` L83 “任何开 Run 的转移在开 Run 前遇到硬上限”）。人批准过的扩展在没有任何提示的情况下失效。
  - **另一种预填同样有后果**：`16` L1140：合同修订中预算 “降低” 可远程、“提高” 仅本机。若编辑器预填生效额度（US$15），新版本相对上一版合同提高了预算，修订被判为放宽，只能在本机执行；手机上的 “修订并继续” 因此不可用。
  - `04` L1130 的修订编辑器、`02` §2.5 `Budget` 都没有写预填规则，也没有在修订预览中提示 “此前的扩展将不再计入”。
- **为什么是次要**：不丢数据，可以再次扩展。但这是 ADR-197 刚定下的唯一规则的直接后果；两种预填都 “照文”，表现差别很大，且一种会让人在修订后立刻被意外暂停。
- **文档位置**：`06` L349–351、L938；`03` L83、L86；`04` L1130、L1503；`16` L1100、L1140；`14` L115。
- **期望的回答形态**：二选一，写在 `06` §6.2.5（唯一规则），`04` 编辑器引用：
  - **修订编辑器预填生效额度**，并在 `16` §16.5 写明：与生效额度相同的预算字段不算 “提高”（比较对象改为修订前的生效额度）；
  - **或修订保留扩展**：生效额度 = 当前版本 `Budget` 与全部 `extend_budget` 取最大值，只有修订**显式改动**了某一预算字段时，该字段才以新版本为准。G33f(c) 相应改写。
  - 无论取哪种，修订预览中显示 “预算：合同值 / 生效额度”。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D5、D7–D10、D14–D16 共十一个维度为 100，在这些维度上没有可追问的实质问题。
  - D4、D6、D11、D12 各为 98；D13 为 94。
- **是否还有可追问的问题：有。** 新增共 **5** 条：阻断 0、**重要 1**、**次要 4**。
  - **D13**：R70-D13-01（重要）。
  - **D11**、**D6**、**D12**、**D4** 各 1 条：R70-D11-01、R70-D6-01、R70-D12-01、R70-D4-01。
  - **第 69 轮核验**：8 条全部解决；§5 的观察全部落地。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 197，section_refs 5918，(v) 96 条命令，(e) 183 对，(D) 200 个短语，(z′) 35 处，(T) 9 种，(H) 77 个提示键，(J) 134 对，(C) 19 行并覆盖 §14.8，(M) 1 个，(B) 1 条，(O) 31 行）。
    - Pi v1.2.0：另抽查 7 条承重引用，行为全部成立，行号在 “±≤5” 之内。
    - 排期结论成立：WBS 122.82；余量 0.12 / 0.26 / 0.40 / 0.88 / 0.22；依赖链 19.91；增人 128.73、T 23.77、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **`15` 的格式**：L1253 与 L1254 之间缺空行，第 69 轮补记的 “分配：” 一段（L1259）没有像前几轮那样与条目列表空一行分开。纯排版。
    2. **回退位置下的违规分类**：`16` L174 的判定顺序 “先 `credential`，再 `tower_data`，再 `user_config`，其余 `system`” 没有提到 `user_checkout` 与 `other_satellite`。回退位置下其他 Goal 的卫星同时落在 `tower_data`（`~/.tower/**`）与 `other_satellite` 中。两类都是 severity 2，结果相同，只影响去重键与良性清单中的类别。建议在判定顺序中加入这两类（例如放在 `tower_data` 之前）。
    3. **“软上限 / 当前硬上限” 的口径**：`12` L585 的预算条与 `16` L1100 的手机端 “单次延长 ≤ 当前硬上限的 20%” 没有写明指生效额度。`06` L349 已写 “下文的软、硬上限都指生效额度”，实现者会同样理解；建议两处各补 “（生效额度，`06` §6.2.5）”。
    4. **“彻底忘记” 的续做**：数据库事务先删除记忆的全部版本并墓碑化事件，Run 目录开场文件中的改写在事务之后执行。`contract.md` 的 `## Memory` 带条目 id（`09` L215），可以按 id 改写；`brief.md` 常驻 `Notes:` 段是否带 id 没有写。崩溃后续做时若该段不带 id，就找不到要改写的原文。建议写明常驻段同样带 id，或在事务前把要改写的文件与行号写入事件。
    5. **回退位置的目录名**：`10` L237 与 L546 写回退根是 “带 `.noindex` 后缀的子目录”，而 `10` L521、L541、`09` L565、`11` L351 都写 `~/.tower/worktrees/<projectId>` 或 `~/.tower/worktrees/…`。建议在 L521 写出实际路径（如 `~/.tower/worktrees/<projectId>.noindex`），其余位置引用。
    6. **`00` R7 末句**：改弱之后，“否则‘事前批准计划’反而降低运行中的警惕” 主要由强制的范围围栏与步骤提醒支撑，决策步骤本身依赖 Agent 提问。正文已如实写出机制，不影响实现；可考虑把末句改为 “范围围栏由 Harness 强制，决策点至少被注入与提醒”。
    7. **取舍判断**：见 §3.3。
- **设计是否完成：ADR-197 的主干已收敛。** 本轮唯一的重要问题不在 ADR-197 的新文字里，而在它与 ADR-196 共同留下的一个后续状态：被保留的目录以旧编号命名，而数据库重建后编号从头开始。四条次要问题中，三条是 ADR-197 新规则的边界（验证器 / 检验的例外集合、续做的定位与配对、修订对扩展的作用），一条是两条新规则对同一对象的冲突。
  - 第 69 轮的 8 条都在唯一定义处关闭，lint、Pi 引用与排期全部成立。
  - 剩下 5 条都可以各用一两句话关闭：
    - 两种检出只作用于本库记录过的目录，或编号跳过已存在的同名目录（R70-D13-01）；
    - 例外集合补 `$SH` 与检验目录，分类器一行引用同一例外（R70-D11-01）；
    - 事件带定位信息，逐 Goal 的事件有明确的完成判据（R70-D6-01）；
    - `ratify` 聚合条目移除被删除的提议（R70-D12-01）；
    - 修订编辑器的预算预填与放宽判定（R70-D4-01）。
- **下一轮建议**（按优先级）：

  2. **R70-D11-01**、**R70-D6-01**：各补全一条规则，并修正 A3 正向运行与 G46 的期望。
  3. **R70-D12-01**、**R70-D4-01**：各写一句。

  **工时与排期**：合计约 0.02–0.05 人周，系统线最多 +0.01（若 R70-D13-01 取编号分配的做法，落在 W3），在余量之内，不在依赖链上。预计 M1 仍可维持 38 周（2027-07-30），以修订后的 ADR-133 补记为准。
