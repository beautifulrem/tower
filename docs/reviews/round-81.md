## 1. 总评

**第 80 轮的 10 条中，9 条已解决。R80-D7-01 的规则已落地，但它的触发条件只覆盖了实际使用中较少见的一种情形**（R81-D7-01）。§5 的 8 条观察全部落地，核对见 §3。

**ADR-208 的结构性改动成立**（§3.3）：
- **凭据不隔离**：
  - 这一改动没有引入机密投递的违例。Host 读写的是用户自己的 `auth.json`；非隔离模式本来如此，所以没有新的读者。
  - Agent 沙箱对 `~/.pi/agent/auth.json` 读拒绝：`11` L160 的密钥路径表、L349 动态技能路径的排除、L507。
  - 投递表中 “模型提供商密钥 → Host 内存覆盖层” 不变（`11` L449）。
  - 删去 “链接” 之后，隔离 agentDir 中也不再有指向凭据文件的条目，比此前更收敛。
  - 锁共享、刷新落盘与 “登录后自动继续” 都经源码核实成立。
- **`inspect.close`**：
  - 命令、事件、远程规则（仅本机）、`inspect.open` 的 `E_STATE` 出口、`04` 的三个按钮都对齐。
  - 但 “保留目录 = 检验已关闭” 与 `10` 中三处 “检验检出存在期间” 的条件不一致（R81-D13-01）。
- **单向门审批 → L4**：`baseLevel` 的守卫成立。但 `routeTick` 与 §8.5.2、§8.5.3 的向下调整仍按 severity 判定，severity 2 的 L4 条目会被预算或洪泛压回 L2，与 §8.1 的 “L4 可透支” 相反（R81-D8-01）。
- **`mixedPaths`**：
  - 与 `Tower-Human-Edit` 不冲突：`mixed` 不进入该 trailer（`16` L212、`10` L672）。
  - 与归因窗口一致：`mixedPaths` 非空的检查点按人的改动计，见 `03` L74、`07` L1599。
  - 缺口在触发条件，见 R81-D7-01。

**四个自行披露的未决点**：
- **第一个检查点之前移出**：可以接受。代价只是归属，评审中文件可见，用户检出不受影响。宜在披露中补上 “`ready` 中排队的时间也在窗口内”。见观察 1。
- **M2 RPC 的凭据路径**：属于明确推迟到 M2 的设计项，可以接受。
- **被吊销的 API 密钥使探测反复解除**：是 ADR-207 之前已有的 F6 行为，`06` L101 已如实写明，可以接受。这时每次失败都在请求前后的鉴权阶段，不消耗模型用量。
- **两条 lint 建议没有实现**：可以接受。辅助检索用脚本核对了 `14` 中定义的 76 个 G 用例：除 G26L、G46b（SP6b 行已标 M2）外都在 B0–B4 中。
  - 但批次覆盖检查不检查 “进入批次的用例是否以 M2 能力为前提”，G33f 正是这样被补进 B4 的（R81-D14-01）。

**全范围扫描**：在 ADR-208 之外新发现 1 条次要问题，属于与 R80-D8-02 同类的遗漏：人工编辑面板的 “在验证器沙箱中运行准备步骤” 没有命令（R81-D8-02）。

**排期**：
- WBS 123.02；角色合计 Agent 26.53 / 系统 26.35 / 桌面 27.84 / 设计 28.69 / 安全 13.61。
- 余量：系统 0.12、Agent 0.26、桌面 0.36、设计 0.74、安全 0.16。
- 依赖链 19.91；增人备选 128.94 / T 23.81 / 33 周；M1 38 周。
- 以上全部经脚本复核成立，`14` 与 `15` 一致。

**新增合计**：阻断 0、重要 0、**次要 5**。

### D7 诚实与验证

**R81-D7-01｜次要**（移出清单的人的文件：`mixed` 的触发条件只覆盖少见的一种情形）

- **问题**：`10` L742 的规则是：“在**上一个检查点**记录的 L 中、而不在本次 L 中的路径，若出现在**本检查点**的树中，记入本检查点的 `mixedPaths`”。它在以下两种常见路径上都不触发。
  - **(a) 收入它的第一个快照是 pin，不是检查点。**
    - `verify()` 每次都以 `pinCommit(goal)` 对工作区重新快照，并按当时的清单求值 L（`07` L376，`10` L597、L741），中间不建检查点。
    - `10` L184 写明 “`in_review`/`accepted` 中的 Goal 在下一次生成 pin 之前不受影响”。`in_review`/`accepted` 中的 `retry_verify`、修订验收标准与 `grant_s0_exec` 都会生成新 pin（`07` L1661，`06` L897）。
    - 这时该路径进入 pin 与评审差异，却不在任何检查点中：
      - 评审作者的推导没有检查点可依（`16` L212）；
      - 归因窗口只数检查点（`03` L74，`07` L1599），所以验证失败按 Agent 路径**自动返工**。
    - 这正是 `04` L1313 教给用户的做法（“想让某个目标提交它，先移除……标为 `混合`……之后的验证失败不自动交给 Agent”），而在待验收的目标上，结果恰好相反。
  - **(b) 移出时文件仍被忽略，之后才解除忽略。**
    - 清单只接受被 git 忽略的路径（`04` L1313，`16` `ProjectLocalFile` 行）。移出后它按 `10` L183 的忽略规则处理；“没有被忽略时” 才进入快照（`10` L184）。
    - 影子的 `info/exclude` 只在 fetch 新 base 时刷新（`10` L183）。所以常见的经 `.git/info/exclude` 忽略的文件，要等到下一次刷新才出现。
    - 那时 “上一个检查点记录的 L” 早已不含它，规则不触发，文件以 `author:"agent"` 进入，这正是 R80-D7-01 要消除的结果。
    - 只有 G46 (bh)(6) 第五组那样 “忽略来源在 Goal 创建之后才加入、Goal 的树中仍是旧版本” 的情形，移出时文件才不被忽略。
  - `04` L1313、L658 与 `10` L184 末句都说 “想让 Goal 提交它，先移出清单”，没有提到还要解除忽略。照做的用户在常见情形下什么也看不到。
- **为什么是次要**：
  - 后果与 R80-D7-01 相同：一条与 Tower 已知事实相反的 ⚙️ 作者，以及失败去向从 “人处理” 变为 “自动返工”。
  - 不丢失工作，文件在评审中可见。
  - 但 ADR-208 声称已关闭这一类问题，而实际触发的只是较少见的一种情形。

  - 另外，`inspect.closed` 只写明由命令产生。第 7 步中 “Goal 被验收或放弃” 触发的清理是否产生它、是否也回收端口段，没有写。
- **为什么是次要**：

  - 但两种实现给出的运行中 Fact 新鲜度不同，重启后对一个保留目录的处理也不同。
- **文档位置**：`06` L914；`10` L254、L902–L907、L1099、L1143；`16` L659。
- **期望的回答形态**：在 `10` L905 写一句：暂停条件是 “检验打开期间”，即从 `inspect.open` 到 `inspect.close`（含 `keep`）或带回；保留的目录不再暂停任何活动，带回时照常以 “卫星当前树 = T_pin” 判定、不满足时走冲突选项。L1099、L1143 与 L254 同步为 “打开期间” 或 “存在”，按各自语义选用。另写半句：验收或放弃触发的清理同样产生 `inspect.closed`。
