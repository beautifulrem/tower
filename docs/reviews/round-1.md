## 1. 总评

设计的完整度和自我批判意识都很强：原论述逐条有立场，Pi 集成大部分逐行对得上源码，诚实语法、完成三态、报警纪律、事件溯源的骨架都成立。但它还远没到“可以开工且无可追问”的程度，主要有四类问题。

第一，几条核心承诺在机制上不成立：运行中的“标准进度 N/M”没有数据来源，线框图与新鲜度规则互相矛盾；Agent 可写的共享依赖缓存和验证器的密钥注入，破坏了“干净环境验证”这个事实根基；`exec.test` 在任何预设里都是静默放行，等于给任意代码执行留了后门。第二，跨文档矛盾有几十处，各文档末尾的“主干修订状态”本身已经过时。第三，M1 范围与 12 周、4.5 人的投入明显不匹配，关键实验存在混杂变量和功效不足。第四，差异化护城河在 v1 并没有兑现。

## 3. 追问清单

编号格式：`R1-D<维度>-<序号>`。严重度：**阻断**（不解决就不能开工或核心承诺不成立）/ **重要** / **次要**。

### D1 原论述契合度

**R1-D1-01｜重要**
- 问题：原论述 P3 明确列出 Cause（原因），但 Cause 没有任何数据通路。`log` 工具的 kind 枚举只有 `plan|step|decision|assumption|finding|risk|next|memory`，没有 `cause`；Goal 页也没有 Cause 区块，只在账本里零散出现。
- 为什么重要：Cause 是原论述“六个一等字段”之一。00 声称“采纳并修正”，实际上丢掉了一项。
- 文档位置：`00` §0.2 P3（L16）；`02` §2.7 Claim.kind（L322）；`05` §5.6.2(b) `log` schema（L591）；`04` §4.5.1 线框、§4.20 L1094。
- 期望的回答形态：二选一。要么给出 Cause 的生产者（扩展 `log` kind，或由 Harness 从失败签名推导）、语法（Fact 还是 Claim）和在 Goal 页的位置；要么在 §4.20 中写明“有意偏离”并给出理由。

**R1-D1-02｜重要**（机制细节见 R1-D7-01）
- 问题：北极星 Q3“离完成还有多远、证据是什么”在 Run 运行期间无法回答。验收标准只在 `claimed`、`fp_changed(in_review)`、`manual`、`merge_queue` 这几个时机验证；按新鲜度规则，Agent 一编辑，旧的 `criterion_check` 立刻变为 stale，不计入 N/M。于是运行中的 Goal 卡片 N/M 几乎总是 0 或全部过期。
- 为什么重要：R4 声称“验收标准进度”提供 L2 理解，这是替代过程流的核心理由。如果运行中给不出这个数，P2“用状态代替流”的论证就站不住。
- 文档位置：`00` §0.4 Q3、R4；`07` §7.4.1 L203（触发枚举）、§7.3.3、§7.4.8 L381；`04` §4.4.1 第 3 行规则、§4.5.1 L267–270（运行中 C1/C2 显示“新鲜通过 @9f3e1a·6分前”）。
- 期望的回答形态：一份运行期进度的明确定义，说明数据源（周期性验证、Agent 环境观察结果以第三种语法显示，或接受运行中无 L2）。同时改正线框图，并在 E4/E2 中度量运行中 Q3 的可答性。

**R1-D1-03｜重要**
- 问题：原论述 P4 批评 Session 列表会随 `/new` 堆积退化。Tower 的 Goal 列表同样会堆积：一行快速路径鼓励“一句话一个 Goal”；`draft`、`ready(等待评审余量)`、`paused` 都没有超时或自动清理；`accepted`（仅保留分支、PR 未合）没有归档期限。
- 为什么重要：如果只是把 Session 换了个名字，P4 并没有被解决。
- 文档位置：`03` §3.2；`04` §4.3.2 侧栏规则；`04` §4.10.3。
- 期望的回答形态：各非终态 Goal 的老化与清理策略（时长阈值、提示形式、自动归档条件）；侧栏容量的设计目标（例如 50 个 Goal 时如何呈现）。

**R1-D1-04｜重要**
- 问题：`02` 声称“换文件夹、换机器不丢 Goal 与记忆”，但 Goal、账本、合同都只存在本机 `~/.tower/tower.db`。同步目录只同步记忆，而且 Goal 记忆默认不同步；跨机器只能手动导出、导入 `.towergoal`。
- 为什么重要：P5“与路径和机器解耦”是原论述的核心之一，这条声明不成立。
- 文档位置：`02` §2.1 L35；`09` §9.12.3 L452；`06` §6.6.3 导出/导入。
- 期望的回答形态：要么删除这条声明并在 §4.20 标为“偏离”，要么给出 Goal 级多机方案（同步什么、冲突怎么处理、worktree 和检查点 ref 如何迁移）。

**R1-D1-05｜重要**
- 问题：聊天形态在多处回流：塑形对话、便笺、每个 Goal 页底部常驻的转向输入框、Watch 模式、评论回执。这些叠在一起，本质上仍是“对 Agent 说话 → 看回执”的会话模型。§4.20 只写了“部分偏离”，没有度量。
- 为什么重要：原论述的核心是逃离 Chat 中心。如果用户实际的操控主要靠转向输入框，Tower 就只是“带仪表盘的聊天”。
- 文档位置：`04` §4.5.1 L297–299、§4.20 L1104；`14` 只对 Watch 模式设了使用率指标。
- 期望的回答形态：增加度量，例如“转向输入框消息数 / Goal”与“评审批注数 / Goal”的比值，并设定判定阈值。同时给出“若转向主要通过聊天框发生”时的设计应对。

**R1-D1-06｜次要**
- 问题：Goal 状态视图同时包含 9 个主区块和 7 个右栏区块，与原论述“只显示当前行 + 关键状态”有张力，也没有说明哪些区块默认折叠。
- 为什么重要：信息过载正是原论述批评的“很忙但不知道在忙什么”的另一种形态。
- 文档位置：`04` §4.5.1–4.5.2。
- 期望的回答形态：区块的默认可见性与折叠规则（按生命周期和模式分别给出），以及“3 秒扫读”在 Goal 页上的验证方法。

**R1-D1-07｜次要**
- 问题：P8 的“证据面”（终端和预览）只出现在模式表和路由里，没有规格：预览服务器由谁启动、在哪个 worktree、占用哪个端口、如何与 Agent 正在跑的 dev server 区分。
- 为什么重要：原论述把“终端和预览被挤压”列为三大问题之一。
- 文档位置：`04` §4.1.2 表、§4.2.1；`13` §13.7 只涉及终端渲染。
- 期望的回答形态：一份证据面规格，覆盖启动、附着、端口、生命周期，以及与 Claim/Fact 的锚定方式。

### D2 Pi 哲学契合度

**R1-D2-01｜重要**
- 问题：`05` 声称“所有 Pi API 已对照源码核实”，但压缩接管的回落条件“用户配置了压缩专用模型（`CompactionModelOverride`）”是误读。源码中 `CompactionModelOverride` 只是按模型覆盖 `reserveTokens`/`keepRecentTokens`（`settings-schema.ts:12-25`），不存在“压缩专用模型”；`session_before_compact` 事件也没有任何字段能让 `hasCompactionModelOverride(event)` 成立。
- 为什么重要：这削弱了“逐项核实”的可信度，回落逻辑本身也是错的。
- 文档位置：`05` §5.6.5 L836、L868。
- 期望的回答形态：改正回落条件；重新审一遍 §5.9 陷阱清单与 §5.6.5，给出“已用契约测试验证 / 仅读源码”的逐条标注。

**R1-D2-02｜重要**
- 问题：MCP 默认值互相矛盾。`05` §5.3.1 L254 写“默认与 CLI 一致，全部开启”（MCP、codemode、tool_search）；`11` §11.3.4 L207 写“Tower 默认不启用 MCP”。
- 为什么重要：MCP 会直接把“不可信内容”和“对外通信”两个要素带进致命三要素的判定（`11` §11.8），默认值决定了绝大多数合同的安全状态。
- 文档位置：如上。
- 期望的回答形态：统一默认值，说明理由，并同步更新三要素的判定与预设表。

**R1-D2-03｜重要**
- 问题：Pi 的系统提示加工具定义不到 1000 token，而 Tower 常驻增加约 415–600 token（增幅 40–60%），另有事件性注入（返工 400、交接 300、nudge、压缩指令）。工具部分实测 299/300，没有任何余量。token 估算口径也不一致：`05` 用 chars/4（与 Pi 一致），`09` §9.5.1 用 `ascii/4 + cjk/1.5`。
- 为什么重要：“尊重极简”是 D2 的核心承诺。用两种口径估算，C15 门禁可能测的不是实际发生的量。
- 文档位置：`15` ADR-009；`05` §5.6.3 L681–699；`09` §9.5.1 L162。
- 期望的回答形态：统一估算口径；给出相对 Pi 基线的增幅论证（为什么 +50% 仍算极简）；给工具声明留出余量，或给出精简方案。

**R1-D2-04｜重要**
- 问题：Pi 的原则是“等特性被证明再加”，但 ADR-019 把多数尚未经过实验的监督特性设为默认开启：声明交叉校验、虚假成功提示、测试完整性哨兵、调速器、重入简报、站会摘要、冲突雷达。
- 为什么重要：这与 `00` §0.5 的对齐声明直接冲突。
- 文档位置：`00` §0.5 L68；`15` ADR-019；`14` §14.5。
- 期望的回答形态：逐项说明默认开启的依据（已有外部证据，或风险不对称），或改为默认关、实验通过后再开；同时写明“未被证明”时的撤回规则。

**R1-D2-05｜重要**
- 问题：对 Pi 的依赖面远超“最小”，而且依赖了大量非公开行为：
  - 按结构实现未导出的 `SettingsStorage`，重写未导出的 `noOpUIContext`；
  - 调用 `compact()` 的内部参数顺序；
  - 依赖队列“整段文本精确匹配”移除、`agent_settled` 的延迟动作语义、system-prompt section 的差分补丁行为。

  ADR-004 的 API 清单与 `05` §5.11 的清单也不一致：后者多出 `on(input|agent_settled|session_shutdown)`、`getApiKeyAndHeaders`、`compact`，`05` 自己也承认“要么补进 ADR-004”。
- 为什么重要：K1 被评为“高可能 / 高影响”，依赖越多、越靠内部行为，升级成本越高。
- 文档位置：`15` ADR-004 L43；`05` §5.3.3、§5.3.4、§5.11 L1098；`05` §5.7.2 L938。
- 期望的回答形态：一张完整的依赖清单（公开 API / 公开但未文档化 / 内部行为三类），每项对应一个契约测试编号；并说明哪些可以向上游提 PR 变成公开契约。

**R1-D2-06｜重要**
- 问题：README 和 `00` §0.5 承诺“你的 Pi 扩展与配置照常生效”，但 `11` §11.7 规定 Engine Host 以白名单环境启动，删除 `*_TOKEN`、`*_KEY`、`ANTHROPIC_API_KEY`、`OPENAI_API_KEY` 等。依赖环境变量认证的 Pi 用户，以及依赖环境变量的用户扩展和 MCP 服务器（例如 `GITHUB_TOKEN`），会直接失效。
- 为什么重要：这破坏了 Pi 的“适应你的工作流”承诺，首次运行就可能失败。
- 文档位置：`README.md` L19；`00` §0.5 L66；`11` §11.7 L344–345。
- 期望的回答形态：说明如何迁移环境变量凭据（读入 `setRuntimeApiKey`？），如何向用户扩展、MCP 子进程按需传递变量，以及首次运行时的检测和提示。

### D3 论证与证据

**R1-D3-01｜重要**
- 问题：“45–76% 的失败运行被报告为成功”来自 tau2（客服场景）与 AppWorld，不是编码 Agent 的通用测量；TF-IDF 检测器的 AUROC 0.83–0.95 是同分布内的结果。`07` §7.9 拿它为一个手工权重、跨分布的检测器背书。
- 为什么重要：R1 的强度、措辞检测器的存在理由都依赖这些数字。
- 文档位置：`07` §7.0 L11、§7.9；`01` §1.2 第 2 条；`research/theory-brainstorm.md` L147。
- 期望的回答形态：如实标注数据来源的领域；给出措辞检测器在 Tower 场景的评估计划（标签定义、样本量、阈值），否则把它降为“实验特性，默认关”。

**R1-D3-02｜重要**
- 问题：BCG/HBR 的“约 3 个 AI 工具时生产力见顶”研究的是工具种类，被拿来设定并发 Agent 数默认值；ISA-18.2 的告警速率针对全职控制室操作员，被直接套用到同时在做其他工作的开发者身上。两处都没有给出迁移论证。
- 为什么重要：默认并发 3、打扰预算 6 次/小时都是全局默认值，影响全部用户。
- 文档位置：`02` §2.14 L559–562；`08` §8.5.2–8.5.3；`01` §1.6。
- 期望的回答形态：逐条说明迁移假设，并指向 E3/E8 中检验这些默认值的具体指标。

**R1-D3-03｜重要**
- 问题：差异化的第 (2) 条“执行式验证”并不独特：landscape 自己就记录了 Factory Missions 的 validator、Devin 运行测试、Copilot coding agent 跑 CI，Claude Code 的 Stop 钩子运行测试也是常见做法。`01` §1.3 的对比表没有覆盖这些。
- 为什么重要：差异化如果只剩“UI 更诚实”，商业风险 K5/K6 会被低估。
- 文档位置：`01` §1.3 L50；`research/landscape.md` L539；`14` K5。
- 期望的回答形态：一张逐项对比矩阵（Claude Code Projects + hooks + /goal、Cursor Projects、Devin、Antigravity、Conductor、Factory Missions），按“验证在哪运行、是否干净环境、是否带新鲜度、是否防改测试”逐列比较。

**R1-D3-04｜重要**
- 问题：设计没有正视“合同仪式感”的反证。红灯先行要求改动前至少有一条会失败的标准，这在重构、新功能、无测试的代码库上等于强制先写测试（TDD）。Kiro 和 Spec Kit 的批评正是针对这类仪式。
- 为什么重要：K7 被评为“高影响”，而它的唯一缓解措施（快速路径）本身仍需要红灯先行。
- 文档位置：`03` §3.4.1 L71–74；`04` §4.10.2、F1 第 5 步；`14` K7。
- 期望的回答形态：给出“无可执行标准”时的合法路径（例如只用 human 标准，但 Verified 如何定义见 R1-D4-02），并设计一个测量仪式成本的实验。

**R1-D3-05｜次要**
- 问题：不少关键数字是轶事或二手来源（例如 X2 的“37% 的完成声明在最后一次通过后还有编辑”被自己标为“轶事性”），却直接用于设阈值。
- 为什么重要：阈值的来源决定了误报预算是否合理。
- 文档位置：`07` §7.8 X2；`08` §8.3。
- 期望的回答形态：一份“阈值来源审计表”：数值 → 来源 → 证据等级 → 回填它的实验。

**R1-D3-06｜次要**
- 问题：SmartBear 的评审速率（200–400 LOC、300–500 LOC/h）来自对人写代码的评审，被直接用于 Agent 代码的容量默认值和时长估算。
- 为什么重要：Agent 代码的冗余度和风格不同，评审速率可能不同。
- 文档位置：`04` §4.6.2；`15` ADR-014。
- 期望的回答形态：说明 E8 如何在 Agent 代码上重新标定这些数。

### D4 领域模型与生命周期

**R1-D4-01｜重要**
- 问题：快速路径 `draft → ready` 不在转移表中。表中 `draft` 只能转到 `shaping`，但 `03` §3.4.1 和 `04` F1 都写了从 draft 一键批准进入 ready。`06` 的 `contract.ratify` 命令也没有说明它可以从哪些状态发起。
- 为什么重要：转移表要求 100% 穷举覆盖，这里在数据层就缺一条边。
- 文档位置：`03` §3.2 L37、§3.4.1 L69；`04` F1；`06` §6.4.3 `contract.ratify`。
- 期望的回答形态：补全转移表（源状态、命令、守卫条件）。

**R1-D4-02｜重要**
- 问题：如果 Goal 没有任何 exec 标准（调研类，或只有 human 标准），按 `07` 的定义“所有 exec 标准新鲜通过”是空真，Goal 会直接进入 `in_review`，显示绿色 ▲“已验证”，而实际上没有任何机器验证；nudge 也因“至少一条 exec/artifact 标准”的条件而失效。
- 为什么重要：这会让绿色出现在零事实之上，违反 R1/R2 的根本规则。
- 文档位置：`07` §7.3.3 L192；`05` §5.6.5 nudge 条件 L882；`12` §12.6.1 in_review 字形。
- 期望的回答形态：定义零 exec 标准时的 Verified 语义与视觉（例如中性色“无机器验证”），以及对应的状态转移。

**R1-D4-03｜重要**
- 问题：`artifact` 类标准没有验证语义。`checks?: string[]` 未定义，验证器只执行 `exec`。调研类和文档类 Goal 的 artifact 标准永远不会产生 Fact，进度无法前进。
- 为什么重要：`03` §3.6 把这两类 Goal 当作一等公民。
- 文档位置：`02` §2.5 L205；`07` §7.4.1 L206；`03` §3.6。
- 期望的回答形态：artifact 检查的语法、执行者、Fact 格式与新鲜度规则。

**R1-D4-04｜重要**
- 问题：`03` §3.5 引用了自动标准 `subgoal_accepted`，但 `Criterion` 联合类型中没有这一 kind。
- 为什么重要：父子 Goal 的完成判定没有类型支撑。
- 文档位置：`03` §3.5 L113；`02` §2.5 L196–205。
- 期望的回答形态：补充类型，说明它的验证者（状态机还是验证器）和新鲜度（子 Goal 被复活或撤销时怎么办）。

**R1-D4-05｜重要**
- 问题：塑形阶段的失败路径没有定义。塑形 Run 停下却没有调用 `propose_contract`、崩溃、超出预算、无响应时，Goal 停在什么状态？`pauseReason` 和 nudge 都只针对 running。
- 为什么重要：塑形是标准和高风险 Goal 的必经之路。
- 文档位置：`03` §3.2 shaping 行；`05` §5.6.5 nudge 条件（`phase === "running"`）；`02` §2.4 pauseReason。
- 期望的回答形态：塑形阶段的完整转移与暂停原因。

**R1-D4-06｜重要**
- 问题：应用退出或崩溃时，正处于 `verifying` 或合并队列中间状态（rebasing、reverifying、integrating）的 Goal 如何恢复？`06` §6.1.4 只覆盖“活跃 Run”。
- 为什么重要：集成中途中断可能留下 seal 提交、半完成的 rebase 或 CAS 前的状态。
- 文档位置：`06` §6.1.4；`10` §10.11 Q1–Q7；`07` §7.4.1。
- 期望的回答形态：每个中间状态的恢复规则（幂等重做还是回滚），以及启动时的检查。

**R1-D4-07｜重要**
- 问题：合同在 `running`、`in_review` 期间修订时，对状态与 Run 的影响散落在各文档，规则不完整：`03` 状态图只画了 `ready ↔ shaping`；`05` §5.8 说修改标准或范围时开新会话；`07` 说标准定义变化时 Fact 失效。修订期间正在跑的 Run 怎么处理（drain？立即更新 policy？）没有写。
- 为什么重要：I3 合同不可变 + 修订是常见操作，必须有确定的转移。
- 文档位置：`03` §3.1；`06` §6.4.3 `contract.amend`；`05` §5.8 表；`07` §7.3.3。
- 期望的回答形态：按“修订字段 × 当前状态”给出一张矩阵，列出每格的动作。

**R1-D4-08｜重要**
- 问题：`ProjectId = hash(normalizedRemote ?? "", rootCommit)` 不稳定：
  - 先在本地建库、后加远端，或改远端 URL，ID 都会变；
  - 浅克隆的“根提交”是嫁接点，与完整克隆不同；
  - 多根仓库的“最早一个”定义含糊。
- 为什么重要：Project 身份是记忆、信任、Goal 归属的主键，ID 一变，这些全部成为孤儿。
- 文档位置：`02` §2.3 L69–72、L87–89。
- 期望的回答形态：身份的稳定键（例如只用根提交，远端作为别名），以及身份变化时的迁移和合并流程。

**R1-D4-09｜重要**
- 问题：`NeedsYouItem` 要求 goalId 与 scratchId 恰有其一（`06` DDL 有 CHECK），但 `08` 定义了多种无归属 Goal 的条目：项目级根因合并条目、洪泛汇总、站会摘要、评审积压条目。
- 为什么重要：实现时这些条目要么插不进表，要么只能随便挂到某个 Goal 上，污染精度统计。
- 文档位置：`02` §2.9 L417；`06` §6.3 L455；`08` §8.4 L175、§8.5.2、§8.5.5、§8.11。
- 期望的回答形态：扩展条目归属（project/global），并更新 DDL 与 kind 枚举。

**R1-D4-10｜重要**
- 问题：领域联合类型普遍不完整：
  - `Fact.kind` 缺少其他文档使用的 `prepare`、`ci_check`、`engine_error`、`policy_notify`、`compaction`、`host_memory_high`、`sandbox_violation`、`resource_exceeded`；

- 为什么重要：`02` 自称是“共同语言”，类型不全时工程师只能各自补字段。
- 文档位置：`02` §2.7、§2.9；`06` §6.4.3；`07` §7.2；`10` §10.18；`11` §11.6.2；`13` §13.8。
- 期望的回答形态：一份完整的枚举表（含产生者文档），并在 CI 中做“文档枚举 vs 类型定义”一致性检查。

**R1-D4-11｜重要**

**R1-D4-12｜次要**
- 问题：`02` §2.1 说“每次运行对应一个 Pi session 文件”，`05` §5.8 却说返工是“新 Run，会话文件不变”，二者的 Run ↔ Session 基数不一致。
- 为什么重要：Trace 定位、对账游标（`runs.last_entry_id`）都以此为前提。

- 期望的回答形态：明确基数为 N:1（多个 Run 共享一个 session），并检查所有使用 `sessionPath` 的地方。

**R1-D4-13｜次要**

**R1-D4-14｜次要**

- 文档位置：`03` §3.2 L40、L46；`04` F7.7。
- 期望的回答形态：补全这两条转移。

### D5 Agent 架构与 Pi 集成

**R1-D5-01｜重要**
- 问题：gate 处理顺序的说法有误。`05` §5.3.5 的 `extensionFactories` 把 tower-goal 放在第一位，MCP、codemode、toolSearch 排在后面。按 Pi 源码，inline 扩展按数组顺序在最后加载（`resource-loader.ts:775-781`），而 `tool_call` 的语义是“后面的处理器看到前面的修改，修改后不再校验”。因此 MCP 等扩展的 `tool_call` 处理器运行在 gate **之后**，可以在 gate 判定之后改动输入。
- 为什么重要：gate 的判定可能对着一个与最终执行不同的输入，策略层因此被绕过。
- 文档位置：`05` §5.3.5 L310–315、§5.6.5 第 6 条 L785；`11` §11.4 L252；源码 `types.ts` ToolCallEvent 注释、`resource-loader.ts:775-781`。
- 期望的回答形态：把 tower-goal 放到数组末尾，或在 gate 中冻结输入（深拷贝后执行时比对）；增加契约测试“gate 之后不再有 tool_call 处理器”。

**R1-D5-02｜重要**
- 问题：三份文档对 Tower 对话框的实现互相矛盾：
  - `05` §5.6.4：一律用 `ctx.ui.input`，Pi 侧兜底超时取 `afterSec + 60`；
  - `08` §8.7.1：用 `ctx.ui.select`，兜底取 `afterSec + 24h`；
  - `11` §11.4：用 `host.requestApproval({timeoutSec: 1800, defaultOption: "deny"})`，与 `02` 的 `unattended: "wait"` 不超时直接冲突，`08` 自己也把这一点列为“仍开放”。
- 为什么重要：超时语义直接决定安全默认动作，以及 Agent 会不会被静默放行或静默卡住。
- 文档位置：`05` §5.6.4 L718–733；`08` §8.7.1 L385–395；`11` §11.1 L59、§11.4 L241–242；`02` §2.5 L190。
- 期望的回答形态：一份唯一的对话框规格（方法、兜底超时、`wait` 时的行为），其余文档改为引用它。

**R1-D5-03｜重要**
- 问题：pi-rpc 模式下，心跳来自 RPC Host 进程，而不是 `pi --mode rpc` 子进程。子进程挂死（事件循环阻塞但不退出）检测不到，只有进程退出码这一个信号。
- 为什么重要：`unresponsive` 模式和恢复流程都基于心跳。
- 文档位置：`05` §5.4.2、§5.4.8；`08` §8.6.3 L337；`06` §6.1.3。
- 期望的回答形态：子进程活性探测方案（例如定期 `get_state` 探针及其超时）和对应的判定阈值。

**R1-D5-04｜重要**
- 问题：`agent_settled` 不是终态。源码中，在 `agent_settled` 发出期间调用 `prompt()` 或 `sendCustomMessage()` 的动作会被放入 `_deferredSettledActions`，并在事件发出后立即执行，即开始一个新 Run（`agent-session.ts:2059-2061, 2345-2346, 1091-1098`）。如果任一用户扩展在 `agent_settled` 处理器中这样做，Tower 会把 Goal 置为 `claimed → verifying`，而 Agent 同时在继续改代码。
- 为什么重要：I4 把 `agent_settled` 当作完成信号，这个前提可能不成立。
- 文档位置：`03` I4；`05` §5.5 `agent_settled` 行、§5.6.5 检查点等待。
- 期望的回答形态：识别并防护这种情况（settled 之后的宽限检查、claimed 后发现新 run 时撤回），并增加契约测试。

**R1-D5-05｜重要**
- 问题：压缩接管直接调用导出的 `compact()`，没有传 Pi 默认路径使用的 `streamFn`（`this.agent.streamFunction`）、重试策略和回调、sessionId 以及路由解析。结果是：通过自定义 streamFunction 接入的 provider 会失效，`summarization_retry_*` 事件不会发出，行为与 Pi 默认压缩分叉。
- 为什么重要：这是对 Pi 核心路径的替换，失败时会引发上下文溢出。
- 文档位置：`05` §5.6.5 L837–842；源码 `agent-session.ts:2748-2771`。
- 期望的回答形态：要么只在摘要后追加账本块（通过 `session_compact` 补发，不接管），要么说明如何与 Pi 默认路径保持一致，并补充契约测试。

**R1-D5-06｜重要**
- 问题：Fact 的确定性依赖于 `tool.end` 的内容，而 `tool.end` 已经经过所有 `tool_result` 处理器，其中包括用户扩展和受信任项目的扩展。这些扩展可以改写 `content`、`isError`、`details`、`structuredContent`（`types.ts:1478-1489`），也就能伪造退出码。现有防护只检测“缺少 structuredContent”。
- 为什么重要：R1 的根基“Fact 只由 Harness 产生”在这里被扩展链绕过。
- 文档位置：`07` §7.2 L39；`05` §5.6.5 `tool_result` 观察点 L791–802；`02` H2。
- 期望的回答形态：要么让 Observer 在扩展链之前取数（例如由 tower-goal 包装 bash 并自签结果），要么把 `command_result` 降为“由扩展链转述的观测”，并在 UI 中区分。

**R1-D5-07｜重要**
- 问题：“尝试 = 会话树分支”与实际流程不符。验证失败时的默认返工是“沿用当前分支”，不做 `navigate`，所以不会产生会话树分支；但 UI 中“尝试 A 自称完成 → 验证失败 已分支 / 尝试 B 运行中”画成了分支。
- 为什么重要：时间线、`AttemptBranch` 组件、`attempt.n` 的语义都依赖这一点。
- 文档位置：`05` §5.8 表第 1 行 L985；`04` §4.5.1 L291–292、§4.5.2 尝试行；`02` §2.6 attempt；`15` ADR-015。
- 期望的回答形态：定义“尝试”的确切边界（每次返工都算，还是只有回退和分叉才算），使 UI 与会话树一致。

**R1-D5-08｜次要**
- 问题：drain 协议与 nudge 冲突。drain 时 gate 以 `terminate:true` 拦截，Run 正常结束（outcome 可能为 `completed`）；这时 `agent_before_settle` 的 nudge 条件不排除 draining，会再触发一次 LLM 调用（随后又被 gate 拦截）。
- 为什么重要：暂停或预算封顶时会多花钱，还会在轨迹中留下噪声。
- 文档位置：`05` §5.6.5 nudge 条件 L877–883、gate 第 2 步 L773；`06` §6.1.4。
- 期望的回答形态：在 nudge 条件中加入 `policy.mode !== "draining"`，并增加契约测试。

**R1-D5-09｜次要**
- 问题：独立评审 Run 的工具，`05` 写 `log`，`07` 写 `review_report`。`09` 使用 `log{kind:"memory", scopeHint}`，但 `log` 的 schema 中没有 `scopeHint`。
- 为什么重要：接口定义不一致，无法实现。
- 文档位置：`05` §5.6.2 L542、(b) L590；`07` §7.12 L824；`09` §9.3.1 L76。
- 期望的回答形态：统一工具名与参数，并重算 token 预算。

**R1-D5-10｜次要**
- 问题：回执 `acknowledged` 有两种定义：`05` 是“送达后第一条正常结束的 assistant 消息”，`04` F4 是“Agent 的 log 或消息引用了该评论 id”。前者只说明模型生成了回复，不说明模型理会了这条评论。
- 为什么重要：回执是防止“转向被静默丢弃”的关键信号。
- 文档位置：`05` §5.7.3 L950；`04` F4 L854。
- 期望的回答形态：统一为一个定义，或把两者拆成两个状态。

**R1-D5-11｜次要**
- 问题：问题回答声称“10 秒内可撤销（仅在 Pi 尚未消费答案时）”，但在 SDK 下，应答会立即兑现对话框的 Promise，实际可撤销窗口接近 0。
- 为什么重要：这是对用户的错误承诺。
- 文档位置：`04` F3 第 4 步 L847；`12` DecisionCard 状态。
- 期望的回答形态：说明真实的可撤销窗口，或改为“改判以转向送达”（F3 第 5 步已有类似机制）。

**R1-D5-12｜次要**
- 问题：检查点的预筛 `turnMutated(event.toolResults)` 看不到 codemode 的嵌套调用（嵌套 id 不出现在 transcript 中），也可能漏掉有写操作的自定义工具。
- 为什么重要：漏建检查点会导致回退粒度变粗、恢复时数据丢失。
- 文档位置：`05` §5.6.5 L810；`10` §10.7.1 第 0 步。
- 期望的回答形态：预筛规则覆盖嵌套调用和未知工具（宁可多做检查点）。

### D6 系统架构与可靠性

**R1-D6-01｜重要**
- 问题：分层保留要求删除归档 Goal 的 `engine.*` 事件，但 `events.caused_by REFERENCES events(seq)`，而且 `foreign_keys = ON`。被保留的 Fact、状态变化事件的 `caused_by` 多半指向 engine 事件，所以删除会失败；若改为把 `caused_by` 置空，又会被 `events_append_only` 触发器拒绝。
- 为什么重要：ADR-005 的保留策略在 DDL 层不可执行。
- 文档位置：`06` §6.3 L298、L308–312、§6.6.4 L776；`02` §2.13 L549；`15` ADR-005。
- 期望的回答形态：调整外键（`ON DELETE SET NULL` 并让触发器允许这一种更新），或把 engine 事件放进独立的表。

**R1-D6-02｜次要**
- 问题：`events_append_only` 只拦截 UPDATE，不拦截 DELETE；哈希链只覆盖 `audit.*`。所谓“追加式唯一真相”实际上可以被静默删除。
- 为什么重要：可审计性的声明需要与实现一致。
- 文档位置：`06` §6.3 L308；`11` §11.11。
- 期望的回答形态：增加 DELETE 触发器（只允许保留任务在特定条件下删除），或扩大哈希链的覆盖范围。

**R1-D6-03｜重要**
- 问题：安全模式被描述为“只读，但仍可暂停或中止正在运行的 Run”。暂停需要写 HumanDecision 和状态事件，与“只读”矛盾；而且安全模式是因为 Supervisor 反复崩溃才进入的，它靠什么执行 drain？
- 为什么重要：这是系统最脆弱时的唯一操作路径。
- 文档位置：`06` §6.1.3 L61、F3。
- 期望的回答形态：安全模式的精确能力清单，以及在数据库可能损坏时的实现路径。

**R1-D6-04｜次要**
- 问题：Host 的存续规则不一致。`13` §13.5 说 Run 结束（settled、paused 超过 5 分钟、in_review）后 Host 退出；`06` 的崩溃语义假定 Host 存活并缓存事件。Host 退出与 Supervisor 重放的时序如何配合（Host 退出前是否必须等到 ack 清空）没有写。
- 为什么重要：Host 退出时缓冲区里未确认的事件会丢失。
- 文档位置：`13` §13.5；`06` §6.1.3、§6.6.5 第 3 条。
- 期望的回答形态：Host 退出协议（等待 ack 清空、超时、落盘位置）。

**R1-D6-05｜次要**
- 问题：幂等键只覆盖了引擎事件、命令、Pi 对账和 Claim。Observer、哨兵、AttentionRouter 产生的派生事件（Fact、Needs-You）在 Host 重放时是否会重复，取决于它们是否与源事件在同一事务内提交，文档没有明确。
- 为什么重要：重复的 Needs-You 会打扰用户，重复的 Fact 会污染精度统计。
- 文档位置：`06` §6.6.5 第 2–3 条；§6.2.1。
- 期望的回答形态：派生事件的幂等键规则（例如 `derived:<sourceKey>:<producer>`）。

**R1-D6-06｜次要**
- 问题：同一用户在两台机器上同时对同一仓库（例如共享的网络 checkout）运行 Tower 时，`refs/tower/*` 和 `.tower-wt` 会互相冲突，单实例锁只在本机生效。
- 为什么重要：这是多机场景的真实风险。
- 文档位置：`06` F23；`10` §10.1。
- 期望的回答形态：用仓库级锁（例如 `refs/tower/_lock` 记录 install_id）或在文档中明确声明不支持。

### D7 诚实与验证

**R1-D7-01｜阻断**
- 问题：运行期验收标准进度的机制缺失（与 R1-D1-02 同源）。验证器只在 claimed、in_review 期间指纹变化、手动、合并队列时运行；默认 `cleanEnv:true`，Observer 的结果不能替代 `criterion_check`。因此运行中 N/M 只能是 0 或全部过期，与线框图、简报示例（“C1 转为通过 @9f3e1a”）矛盾。
- 为什么重要：R4（L2 理解）、卡片第 3 行、燃烧进度检测（`07` §7.7.2 用了“observer 或 verifier 通过”，口径与卡片不同）、重入简报都失去数据源。
- 文档位置：`07` §7.4.1 L203、§7.4.8 L381、§7.7.2 L653；`04` §4.4.1、§4.5.1 L266–270、§4.9.2 L597；`12` §12.10.1。
- 期望的回答形态：给出运行期进度的数据源与语法。备选方案有三种：(a) 低优先级的周期性干净验证，需说明成本与节奏；(b) Agent 环境的观察结果作为第三种语法“Agent 环境观测”，不着绿、不计入验收；(c) 明确运行中不展示进度，并修改北极星。同时统一 N/M 的口径。

**R1-D7-02｜阻断**
- 问题：依赖缓存投毒可以伪造“通过”。
  - Agent 的 bash 沙箱允许写全局包缓存（`~/.pnpm-store`、`~/.npm/_cacache`、`~/.cache/uv`、`~/.cargo/registry` 等）。
  - 验证器沙箱同样允许写“各依赖缓存目录”。
  - depcache 在非 APFS/reflink 卷上退化为硬链接，共享 inode。
  - 结果：Agent 编写的代码（测试代码、`postinstall`、构建脚本）可以篡改测试运行器（例如 `node_modules/vitest` 的实现）在 store 或 depcache 中的文件，使验证器在“干净”的源码树上用被篡改的运行器跑出“通过”。指纹不包含被忽略的目录，这一篡改对新鲜度完全不可见。
- 为什么重要：“在干净环境中执行验证”是 R2 和整个诚实语法的根基；被篡改的通过结果会显示为绿色事实。
- 文档位置：`11` §11.6.2 L312；`07` §7.4.3 L268、§7.4.4 L286；`10` §10.4.1–10.4.2；`11` T7。
- 期望的回答形态：验证器依赖的完整性方案。例如：depcache 和 store 对 Agent 与验证器都只读；安装只由 Supervisor 在独立沙箱中执行；每次验证前按 lockfile 的完整性哈希校验 depcache（pnpm integrity / `npm ci --verify`）；验证器的 `node_modules` 只用 CoW，禁止硬链接。并给出残余风险评级。

**R1-D7-03｜重要**
- 问题：验证器可以被当作密钥泄露通道。合同声明的密钥会注入到运行 Agent 所写代码的验证子进程中；Agent 写的测试可以把密钥做 base64 等变换后输出到失败日志里，绕过精确匹配的脱敏；而返工消息会把失败日志末尾 30 行送回模型上下文。
- 为什么重要：这违反 `11` §11.7 的原则“密钥永不进入模型上下文”。
- 文档位置：`07` §7.4.3 L257–258、§7.10.3 L771；`11` §11.7 L347–349。
- 期望的回答形态：带密钥的标准的输出处理规则（例如不回送原文、只回送失败用例名）；“带密钥标准的测试文件必须为 forbid”之类的耦合约束；残余风险的说明。

**R1-D7-04｜重要**
- 问题：外部服务与端口没有定义。VerifyProfile 没有服务的启动和清理（数据库、docker compose、mock 服务器）；执行阶段默认禁网；docker socket 是否可达也没说。`04` §4.7.2 的诊断示例写着“验证器环境正常”（5433 端口有 Postgres），但这个 Postgres 从哪里来？此外，macOS 没有网络命名空间，并行的验证槽位与各 Goal 的 dev server、测试数据库会争用固定端口。
- 为什么重要：多数真实项目的 e2e 或集成测试会在验证器里失败，或互相干扰，导致误报“验证失败”和返工循环。
- 文档位置：`07` §7.4.3 L275、§7.4.4；`09` §9.7 VerifyProfile 类型；`04` §4.7.2 L483。
- 期望的回答形态：VerifyProfile 增加 `services`/`setup`/`teardown`；端口分配策略（环境变量注入或随机端口）；docker 的沙箱策略；“验证环境故障”与“标准失败”的区分规则。

**R1-D7-05｜重要**
- 问题：不稳定测试默认算通过，这对并发类 Goal 恰恰是错的。一个改动引入的竞态（例如 G-0142 的并发扣款）表现为“同一提交上先失败后通过”，会被归为 flaky，`pass_with_flakes` 直接进入 `in_review`。
- 为什么重要：最危险的一类缺陷会被标成“已验证”。
- 文档位置：`07` §7.4.6 L341–352；`07` §7.10.3 L759。
- 期望的回答形态：判定 flaky 之前，先在 base 上对同一用例重复运行，确认“base 上本来就不稳定”；改动引入的不稳定按失败处理，或至少阻止 Verified。

**R1-D7-06｜重要**
- 问题：`cleanEnv:false` 的观察器替代很容易被伪造：Agent 环境中被忽略的目录（例如 `node_modules` 被打补丁）不进入指纹；`tool.end` 又受扩展链影响（R1-D5-06）。目前的护栏只有“高风险禁止 + UI 标签”。
- 为什么重要：绿色可能来自 Agent 可控的环境。
- 文档位置：`07` §7.4.8 L381、§7.3.2 L157。
- 期望的回答形态：这类结果的视觉语法不得为绿色，或要求 `extraGlobs` 覆盖依赖目录；也可以考虑从 v1 中删除该选项。

**R1-D7-07｜重要**
- 问题：哨兵的精度目标（0.6–0.95）没有标注数据集，也没有上线前的测量计划。自动调节需要每个项目 n ≥ 20，可能要几个月才能积累到。R-T5（测试数下降）是严重度 3 的阻断项，而 jest 的测试清单靠正则静态估计，重构（例如合并成 `.each`）会触发误阻断。
- 为什么重要：高误报会训练出用户的“反射式覆盖”，这正是 ADR-010 要避免的事。
- 文档位置：`07` §7.10.1、§7.11、§7.5.4 L489。
- 期望的回答形态：一个哨兵基准语料（真实 diff + 标注），给出各检测器的离线精度；`source:"static"` 的计数不得触发阻断。

**R1-D7-08｜次要**
- 问题：Verified 的定义前后不一。`07` §7.3.3 是“不存在未处置的 severity 3 哨兵”；`decide()` 用的是 `blocksReview` 子集，而 §7.10.1 中 bash 输出里的密钥是 severity 3 但不阻断。`decide()` 还引用了不在签名里的 `trigger` 变量，和不在触发枚举里的 `fp_changed_by_human`；对 `merge_queue` 触发，`decide()` 缺少“验收延续”分支（`10` Q4）。
- 为什么重要：状态机的核心判定函数必须无歧义。
- 文档位置：`07` §7.3.3 L192、§7.10.3 L756–768、§7.4.1 L203；`10` §10.11 Q4。
- 期望的回答形态：一个完整的 `decide(goal, pin, trigger)`，覆盖全部触发来源与源状态。

**R1-D7-09｜次要**
- 问题：指纹的快速路径依赖 fsmonitor token，而 git 内置的 fsmonitor 在 Linux 上不可用（需要 watchman），token 失效或误报时会把过期的 Fact 显示为新鲜。
- 为什么重要：I2 的正确性不能依赖一个优化路径。
- 文档位置：`07` §7.3.2 L139–140、L155；`10` §10.7.2 L286。
- 期望的回答形态：快速路径的正确性论证，例如验收面板打开或 in_review 期间强制走慢路径。

**R1-D7-10｜次要**
- 问题：交叉校验 X1–X8 依赖中英文关键词正则，误判会以红色“✕ 矛盾”呈现；H2 声称模型文本永远不成为 Fact 字段，但 `command_result.command` 正是模型生成的文本。
- 为什么重要：错误的“矛盾”会损伤信任校准；规则表述应当精确。
- 文档位置：`07` §7.8；`07` §7.1 H2；`07` §7.2.2。
- 期望的回答形态：给“矛盾”判定的置信分级（硬矛盾 / 软矛盾），软矛盾不使用 danger 色；修正 H2 的表述。

**R1-D7-11｜重要**
- 问题：验证的成本和延迟没有算账。每次 claim 都要跑：全部 exec 标准、测试清单、base 清单（有缓存）、flaky 重跑、哨兵；合并队列的 Q5 还要跑最多 5 个其他 Goal 的标准，上限 15 分钟。验证槽位每项目 2 个、全局 `floor(cores/4)`（8 核时只有 2 个），3–5 个 Goal 并发时会排队；每轮返工又要重跑整套。
- 为什么重要：验证延迟直接决定吞吐和“自称完成 → 待验收”的等待体验。
- 文档位置：`07` §7.4.8；`06` §6.2.4 L226；`13` §13.11；`10` §10.11 Q5。
- 期望的回答形态：基于参考项目（例如 5 分钟测试套件）的验证排队模型，给出 p50/p95 等待时间；明确 M1 的验证延迟预算与降级策略。

### D8 注意力与交互（UX）

**R1-D8-01｜重要**
- 问题：问题类超时默认动作的安全规则是“只能默认为 Agent 推荐且可逆的选项”，但“可逆”由谁判定？这本身是 Agent 的 Claim。示例 G-0142 是高风险的支付 Goal，12 分钟后会自动选择幂等键方案 1；同时 `04` 又规定“推荐项不预选”。
- 为什么重要：一个关键安全判定建立在 Agent 的说法之上，违反 R1；高风险 Goal 尤其不应自动作答。
- 文档位置：`02` §2.9 L434–438；`04` §4.8.1 L508–509、§4.10.1 L633；`08` §8.7.1。
- 期望的回答形态：可逆性由 Harness 判定的规则；高风险 Goal 禁止问题类超时默认；或者问题类超时一律转为暂停。

**R1-D8-02｜重要**
- 问题：快捷键冲突。`⌘⇧D` 在 `04` 是“切换密度”，在 `06` §6.7 是“调试面板”；“下一件最值得看的事”在 `04` 是 `G N`，在 `08` 建议 `G X`；`E` 在 Goal 页是修订合同，在评审中是“我来改”。
- 为什么重要：快捷键是“键盘优先”设计的契约。
- 文档位置：`04` §4.17.1 L938、L945；`06` §6.7 L820；`08` §8.5.6 L277。
- 期望的回答形态：一份全局快捷键注册表（作用域、冲突检测），其余文档只引用它。

**R1-D8-03｜重要**
- 问题：远程验收权限有三种说法：`06` 的 `decide` scope 包含“验收或请求修改”；`04` §4.14 规定手机上不能验收；`11` §11.9 只禁止验收 `riskTier=high` 的 Goal。
- 为什么重要：这是安全边界的不一致。
- 文档位置：`06` §6.4.7 L680；`04` §4.14 L784；`11` §11.9 L403。
- 期望的回答形态：一份统一的远程能力矩阵。

**R1-D8-04｜重要**
- 问题：打扰预算可能把阻塞 Agent 的问题饿死。L3 投递需要令牌，令牌不足时问题降为 L2（不发 OS 通知）。用户离开时，在 `unattended: "wait"`（默认）下，Agent 可能被静默阻塞数小时。
- 为什么重要：吞吐与“例外必须能叫到人”（R5）冲突。
- 文档位置：`08` §8.3.4 L147、§8.5.3；`02` §2.14 L562–563。
- 期望的回答形态：为 `agent_blocked` 的条目设定最长静默时长（超过后强制 L3 或进入简报置顶），并给出吞吐损失的估算。

**R1-D8-05｜重要**
- 问题：同一 Goal、同一时刻，卡片显示“标准 2/5”，Goal 页显示“验收标准 3/5”（C4 已过期，按规则不应计入），简报写“2/5 → 3/5”。
- 为什么重要：Q3 的答案在不同界面上不一致，正说明 N/M 的口径不清（另见 R1-D7-01）。
- 文档位置：`04` L132、L266、L597。
- 期望的回答形态：统一口径，并修正线框图。

**R1-D8-06｜次要**
- 问题：首次运行有 7 步（引擎、项目、信任、验证配置试运行、导入历史、注意力、默认视图），再加上第一个 Goal 的红灯先行和 worktree 依赖准备（`pnpm install` 可能要几分钟）。目标“首个运行中 Goal ≤ 5 分钟，快速路径 ≤ 60 秒”没有可行性分析，也没有实验。
- 为什么重要：K7 被评为高影响。
- 文档位置：`04` §4.18.1；`14` §14.6.2 L245。
- 期望的回答形态：首次运行的时长分解（各步 p50），可跳过、可延后的步骤，以及一个可用性测试计划。

**R1-D8-07｜次要**
- 问题：注意力公式的常数（S、k、τ、θ、g）都是拍定的。例如 θ(`busy_in_tower_review`) = 6，实际上几乎总被“最长等待 180 秒”覆盖，等于没有作用。
- 为什么重要：没有标定的公式会显得精确，实际是任意的。
- 文档位置：`08` §8.3.2–8.3.3。
- 期望的回答形态：几个典型场景的演算表（各状态、各 kind 的实际投递延迟），说明哪些常数是有效约束；E3 中的标定方法。

**R1-D8-08｜次要**
- 问题：多个自动覆盖层的优先级没有定义：回来时的应用级简报、打开 Goal 时的单 Goal 简报、满足条件时自动进入诊断视图、断点提示条，可能同时出现。
- 为什么重要：多个覆盖层同时弹出会制造“重入时的打扰”。
- 文档位置：`04` §4.5 L255、§4.9；`08` §8.10.2、§8.13.1。
- 期望的回答形态：覆盖层的优先级与互斥规则。

### D9 视觉设计与美观

**R1-D9-01｜重要**
- 问题：text-3 只有 Lc 46，却被用于 12px/400 的卡片实况行和 meta 文本。按 APCA 的字号与字重查表，12px 常规字重的正文需要 Lc 约 75 以上；Lc 45 只适用于大字号或粗体。
- 为什么重要：卡片实况行是 3 秒扫读的主信息面，它在 dark cockpit 下本来就最暗。
- 文档位置：`12` §12.4.2 L150、§12.3.2 L83、§12.12 LiveLine。
- 期望的回答形态：按 APCA 字号表重新设定目标，或把卡片实况行提到 text-2，并在目标屏上实测。

**R1-D9-02｜重要**
- 问题：`blocked_guard`（等待人批准，对应一个 Needs-You）的模式徽章用 danger 红 `■`，而同一个审批条目在收件箱和侧栏中是琥珀 `◆`。这违反“琥珀是需要你的唯一含义”，同一件事在两个界面颜色不同。
- 为什么重要：Q1“哪些事需要我”依赖颜色和形状的一致性。
- 文档位置：`12` §12.6.3 L324、§12.4.3 L187–188；`04` L373。
- 期望的回答形态：`blocked_guard` 改用 attention，或给出拆分“被拦截（已拒绝，红）”与“等你审批（琥珀）”两种模式的理由。

**R1-D9-03｜次要**
- 问题：托盘规则自相矛盾：`12` §12.16 #12 说“托盘只显示数字，不闪烁”；§12.7 说“菜单栏字形升到 L3/L4 时一次性淡入”；`04` §4.13 说每个运行中的 Goal 一个字形。
- 为什么重要：外周显示的规格必须唯一。
- 文档位置：`12` §12.7 L429、§12.16 L765；`04` §4.13。
- 期望的回答形态：一份统一的菜单栏规格。

**R1-D9-04｜次要**
- 问题：`◌` 同时表示“塑形中”（生命周期字形）和“要注意但不需要你”（断环）。侧栏和卡片上两者可能相邻出现。
- 为什么重要：形状编码是首要通道，不应一形两义。
- 文档位置：`12` §12.6.1 L289、§12.6.2 L312。
- 期望的回答形态：为其中一方换一个字形。

**R1-D9-05｜次要**
- 问题：绿色 ▲“已验证”覆盖了几种并不等价的情况：`pass_with_flakes`、被覆盖的哨兵、携带的结果、零 exec 标准（见 R1-D4-02）。`12` §12.1 写“当前 HEAD 上通过”，而新鲜度实际按 tree 判定；§12.6.4 排在 §12.6.5、§12.6.6 之后，编号顺序错乱。
- 为什么重要：“绿色 = 已确认”是视觉语法的核心规则。
- 文档位置：`12` §12.1 L21、§12.6.1、§12.6 小节顺序。
- 期望的回答形态：“有保留的已验证”变体，以及措辞和编号的修正。

### D10 性能

**R1-D10-01｜重要**
- 问题：内存预算缺乏依据。Engine Host 的目标是 ≤ 60 MB（`05` 写 40–70 MB），但它要装 Pi、用户扩展、tree-sitter-bash WASM 分类器、MCP、Node 基线；`research/pi.md` 估算每个 Node 子进程约 100 MB。此外，每个 worktree 一个 fsmonitor 守护进程、验证槽位的 fsmonitor，都没有计入。M1 的退出标准却依赖这些预算达标。
- 为什么重要：K2/K10 的风险评级取决于这些数字。
- 文档位置：`13` §13.1 L36、§13.8.1；`05` §5.4.8 L431；`10` §10.14。
- 期望的回答形态：SP2 之前标注为“假设值”，给出不达标时的 M1 退出策略（例如改为打包模式）。

**R1-D10-02｜重要**
- 问题：后台 git 负载没有总账。每次 bash 结束（防抖 500 ms）和每个 turn_end 都会做 `git add -A + write-tree`，在 5 万文件的仓库里每次 0.3–1.5 秒；5 个并发 Goal 再加上雷达、fs watcher、验证器，会与 Agent 自己的构建争抢 CPU 和 IO。目前只有“雷达 CPU ≤ 2%”一项预算。
- 为什么重要：这会拖慢 Agent，也会让 UI 卡顿。
- 文档位置：`07` §7.3.2 计算时机表；`10` §10.7.2；`13` §13.11。
- 期望的回答形态：并发 N 个 Goal 时后台 git 的 CPU 和 IO 总预算、测量方法与降级规则。

**R1-D10-03｜次要**
- 问题：冷启动 p50 ≤ 500 ms（Electron + utilityProcess + node:sqlite + React）没有基准证据，只沿用了 `gui.md` 的目标。
- 为什么重要：这是 CI 的硬门槛。
- 文档位置：`13` §13.1、§13.10。
- 期望的回答形态：一个原型测量值，或标注为待 SP 验证。

**R1-D10-04｜次要**
- 问题：机器负载的准入只看空闲内存 ≥ 1 GB。每个 Goal 进程树的上限是 4 GB，再乘以 5 个 Goal，加上验证器的 `min(8 GB, RAM×0.4)`，在 16 GB 机器上会严重超售。
- 为什么重要：整机变慢会让所有预算失效。
- 文档位置：`13` §13.8.3；`07` §7.4.4 L284；`06` §6.2.4。
- 期望的回答形态：一个考虑验证器的整机资源模型和准入公式。

**R1-D10-05｜次要**
- 问题：刷新节奏的说法不一：`13` §13.0 说后台 ≤ 2 Hz；`06` 的 board 节奏是 250 ms（4 Hz）；`04` 和 `12` 说实况行 ≤ 1 次/秒。
- 为什么重要：节奏规格需要唯一。
- 文档位置：`13` §13.0、§13.3；`06` §6.5.1；`04` §4.4.1。
- 期望的回答形态：一张统一的节奏表。

### D11 安全与自主度

**R1-D11-01｜阻断**
- 问题：`exec.test`/`exec.build` 在全部预设中都是 silent，而且只要命令匹配合同标准或项目测试命令（脚本体相对 base 未改），分类就是 `exact`。但测试运行执行的正是 Agent 写的测试代码和源码，只要往测试文件里写恶意代码再跑 `pnpm test`，就能在不触发任何 ask 的情况下执行任意代码。没有 S2 时（Windows S0、SP6 失败后的回退），这等于以用户权限在沙箱外执行任意代码；`11` §11.0 的“无沙箱 → ask”规则对 exact 类不生效。
- 为什么重要：这是策略层的系统性缺口，直接对应 T3、T5 的“高”残余风险，而且这些风险在默认路径上。
- 文档位置：`11` §11.2 L80、§11.3.2 第 8 条、L176–177、§11.0 第 2 条；`15` ADR-018；`14` SP6 回退 L30。
- 期望的回答形态：没有 S2 时，`exec.test`/`exec.build` 至少为 `ask`，或以“测试代码相对 base 是否改动”为条件；在威胁表中新增此项并给出残余风险。

**R1-D11-02｜重要**
- 问题：Agent 的沙箱允许写全局包缓存（pnpm store 等）。这类缓存被用户在 Tower 之外的项目共享，被篡改的文件会经由硬链接进入用户自己的构建，是越过 Tower 边界的持久化。T7 只评为“中”，也没有缓解措施。
- 为什么重要：这破坏了“绝不碰用户工作现场”的承诺。
- 文档位置：`11` §11.6.2 L312、T7 L459。
- 期望的回答形态：使用 Tower 专用的 store 或缓存目录，或缓存对 Agent 只读、由 Supervisor 代为安装。

**R1-D11-03｜重要**
- 问题：用户扩展和 MCP 工具在 Engine Host 中以用户权限、在沙箱外运行（T16 的残余风险为“高”），而 `05` §5.10 默认 `userExtensions: on`。也就是说，最高的残余风险恰恰是默认配置。“隔离 Agent 目录”只是可选项。
- 为什么重要：默认配置决定绝大多数用户的安全水位。
- 文档位置：`11` §11.8.1 L389、T16；`05` §5.10 开关表。
- 期望的回答形态：高风险 Goal 默认使用隔离的 agentDir，或对首次加载的用户扩展弹出清单确认；给出理由。

**R1-D11-04｜重要**
- 问题：致命三要素的判定条件过宽：标准预设中 `read.external = ask`（不等于 forbid），即满足“私有数据”；S2 不可用时“对外通信”恒为真。结果是几乎每份合同都会出现琥珀警告，在 Windows 上则每次都会出现。
- 为什么重要：一个总是出现的警告就是滋扰告警，违反 ADR-010。
- 文档位置：`11` §11.8 L367–371；`04` §4.10.1 L637–640。
- 期望的回答形态：用标准预设和典型项目测算触发率，收紧判定（例如私有数据只在实际密钥路径可读时为真）。

**R1-D11-05｜次要**
- 问题：便笺“只读挂载项目 checkout”没有实现机制：macOS 没有用户态只读 bind mount，Pi 的工具也可以写任意路径。
- 为什么重要：“便笺不得写真实 checkout”是 ADR-012 的约束。
- 文档位置：`02` §2.12 L502、L523；`04` §4.11；`15` ADR-012。
- 期望的回答形态：便笺使用的 policy 与 S2 配置（例如 cwd 指向临时副本，checkout 只读）。

**R1-D11-06｜次要**
- 问题：上下文文件（AGENTS.md、CLAUDE.md）不受 trust 控制，而且总会加载。S2 只拒绝写“worktree 内的 AGENTS.md、CLAUDE.md”，没有写明是否覆盖子目录下的 `**/AGENTS.md`；每个 Run 的信任复核只检查 `.pi`、`.agents`，不检查上下文文件的改动。
- 为什么重要：这是跨 Run 植入指令的路径（T4）。
- 文档位置：`11` §11.6.2 L314、§11.8.1 L386；`05` G31。
- 期望的回答形态：沙箱规则覆盖嵌套路径；Run 启动时比对上下文文件相对 base 的差异，并在简报中提示。

**R1-D11-07｜次要**
- 问题：`~/.tower` 中的 Pi JSONL、日志、事件库以明文保存完整对话与工具输出，只有已知模式的密钥被脱敏；worktree 位于用户目录树中。没有静态加密，也没有权限说明。
- 为什么重要：笔记本丢失、备份泄露、云同步都会暴露这些数据。
- 文档位置：`06` §6.6.1；`09` §9.12.1；`11` §11.11。
- 期望的回答形态：文件权限（0700）、可选的加密方案、备份和同步排除，或在残余风险中如实登记。

**R1-D11-08｜次要**
- 问题：gate 的 p95 ≤ 5 ms 包含了 tree-sitter 解析、读取 package.json 或 Makefile、用“只读 git 查询”确认脚本体未改。其中 git 子进程调用本身就是几毫秒到几十毫秒量级。
- 为什么重要：gate 在每个工具调用的关键路径上。
- 文档位置：`11` §11.4 L233；`05` §5.6.5 判定流程。
- 期望的回答形态：缓存策略（例如脚本体哈希在检查点时预算好），以及测量计划。

### D12 记忆与学习

**R1-D12-01｜重要**
- 问题：`tainted` 的判定过窄，只统计“worktree 之外的文件、网页、MCP、合同中粘贴的外部文本、`net.other` 输出”，漏掉了：
  - worktree 内的不可信内容（`node_modules`、vendored 代码、测试夹具、他人在 base 上的提交）；
  - 测试输出；
  - 被归类为 `net.registry` 的 GET 请求（例如从 github.com 抓取原始内容）的输出；
  - 用户扩展工具的结果。
- 为什么重要：记忆投毒（T22 评为“低”）的主要入口没有被覆盖。
- 文档位置：`09` §9.2 L66；`11` §11.8、T22。
- 期望的回答形态：重新定义不可信输入的分类，或改为默认标记、反向白名单，并重评 T22。

**R1-D12-02｜重要**
- 问题：记忆优先级是“Goal 记忆 > Project 记忆 > 仓库 AGENTS.md”，即个人的项目记忆会压过团队提交进仓库的约定，并在注入文本中明确告诉模型“冲突时听记忆的”。
- 为什么重要：在团队仓库里，这会让某个人的偏好静默覆盖团队规则。
- 文档位置：`09` §9.4.3 L136–140、§9.5.3。
- 期望的回答形态：论证这一顺序，或改为 AGENTS.md 优先、冲突时提示用户。

**R1-D12-03｜重要**
- 问题：每条记忆最多 300 字符，而常驻记忆预算只有 120 token。按 `09` 自己的估算（中文 1.5 字符/token），一条 300 字符的中文记忆约 200 token，永远无法常驻；`05`/C15 用 chars/4 估算，又会低估中文。
- 为什么重要：面向中文用户时，常驻记忆这一机制可能实际为空。
- 文档位置：`09` §9.5.1 L162；`02` §2.10 L463；`05` §5.0 L13。
- 期望的回答形态：统一估算口径，并调整条目长度上限或预算。

**R1-D12-04｜次要**
- 问题：F10 允许批量批准（`⇧X` 多选 + `Y`）记忆提议，与“tainted、可疑指令不能一键批准”冲突。
- 为什么重要：批量操作是绕过逐条确认的典型路径。
- 文档位置：`04` F10.5 L909；`09` §9.2 L66、§9.3.3。
- 期望的回答形态：批量操作排除带标记的条目。

**R1-D12-05｜次要**
- 问题：同步合并用“(id, version) 较新者胜”。两台机器从不同基线各自编辑，产生的版本号不同，会静默覆盖对方（丢失更新）。
- 为什么重要：同步是跨机器记忆的唯一途径。
- 文档位置：`09` §9.12.3 L455。
- 期望的回答形态：用 base version 或向量时钟检测并发编辑。

**R1-D12-06｜次要**
- 问题：学习效果的度量（之后 5 个相关 Goal 的复发率）样本很小，也没有退役规则的阈值。
- 为什么重要：没有阈值，就无法判断学习闭环是否有效。
- 文档位置：`09` §9.6.4。
- 期望的回答形态：统计方法与阈值。

### D13 隔离、git 与并发

**R1-D13-01｜重要**
- 问题：`<checkoutParent>/.tower-wt` 会落入用户的同步或索引目录。很多 macOS 用户把代码放在 iCloud 同步的 ~/Documents 或 Desktop、Dropbox、网络卷里；worktree 加上 `node_modules` 会被云同步、Spotlight 和 Time Machine 处理。现有检测只覆盖“父目录本身是 git 仓库”这一种情况。
- 为什么重要：这会带来性能、费用和数据泄露问题，用户也会感到惊讶。
- 文档位置：`10` §10.4.3 L183–192；`15` ADR-008。
- 期望的回答形态：检测云同步目录（例如 `~/Library/Mobile Documents`、Dropbox 标记）并强制回退；说明排除 Time Machine 和 Spotlight 的方法。

**R1-D13-02｜重要**
- 问题：并发 Goal 与验证槽位之间没有端口和服务隔离。dev server、测试数据库、固定端口的 e2e 测试会互相干扰；macOS 没有网络命名空间；Linux 上 bwrap 的 `--unshare-net` 会破坏 docker。（与 R1-D7-04 相关，但这里是并发隔离问题。）
- 为什么重要：隔离承诺“互不干扰”目前只覆盖文件。
- 文档位置：`10` 全文（缺失）；`07` §7.4.4。
- 期望的回答形态：端口分配协议、服务实例化策略，以及对并发度的影响。

**R1-D13-03｜重要**
- 问题：附着模型下，所有 Goal 的分支和影子 ref 只存在于用户主检出的 `.git` 里。用户删除或重新克隆仓库，未推送的工作就全部丢失（情形 D 承认了这一点）；目前只“建议”在 claimed 时推送。
- 为什么重要：数据丢失是 K16 的高影响项，而这里的风险是结构性的。
- 文档位置：`10` §10.1、§10.16 D L509。
- 期望的回答形态：一个 Tower 自有的备份（定期 `git bundle` 或 `~/.tower` 下的镜像 refs）及其成本。

**R1-D13-04｜次要**
- 问题：“本地合并”在 base 已被用户主检出时，会直接在用户检出中执行 `git merge --ff-only`，与“绝不碰用户的工作现场”相悖，也会触发用户 IDE 和构建工具的文件监听。
- 为什么重要：需要把这一例外写清楚。
- 文档位置：`10` §10.12 L447、设计基调 L10。
- 期望的回答形态：把它列为显式例外，并在 UI 中确认。

**R1-D13-05｜次要**
- 问题：同一 Project 有多个本机 checkout 时，选哪个作为附着点（共享对象库）、worktree 根在哪个父目录，都没有规则。
- 为什么重要：附着点决定了数据存放位置和恢复路径。
- 文档位置：`02` §2.3 checkouts；`10` §10.4.3。
- 期望的回答形态：附着点的选择与迁移规则。

### D14 路线图与可验证性

**R1-D14-01｜阻断**
- 问题：M1 的范围与 12 周、4.5 人的投入明显不匹配。M1 要交付：
  - Electron 外壳与全部加固；SDK 适配器与 tower-goal；worktree、depcache、检查点、恢复；
  - 验证槽位、沙箱和测试完整性哨兵；评审单元与风险排序；合并队列（rebase、重验证、CAS）；
  - Needs-You（断点、令牌桶、默认动作）与重入简报；
  - 基于 tree-sitter 的 bash 分类器（E7 召回 ≥ 99%）；S2 Seatbelt；脱敏；审计哈希链；
  - 性能 CI（P1–P7）；基于属性的测试；E5 完成；E1 试点；4 名内部用户连续 3 周、≥ 100 个验收 Goal。

  后两项要求功能在大约第 8–9 周就完成。
- 为什么重要：路线图的可信度直接影响整个设计是否可交付。
- 文档位置：`14` §14.3.2–14.3.4；§14.8。
- 期望的回答形态：一份工作分解（人周）与关键路径；进一步收缩 M1（例如推迟 bash AST 分类器和合并队列，M1 只做“仅保留分支”）；或者延长时间。

**R1-D14-02｜重要**
- 问题：E1 的设计存在混杂变量和功效不足：
  - 条件 A（Watch + diff）是否展示验证器的 Fact 没有写；如果不展示，比较的是“有没有验证”而不是“有没有语法”。
  - “机制可检测”的种子失败本来就会被 Harness 标红，检出率衡量的是“读到红色 ✕”而不是人的监督能力。
  - 每个条件每人只有 2 个种子失败，个人检出率只能取 0、0.5、1；N = 18 的功效估算没有给出推导。
  - 条件 A 也不代表真实竞品（例如 Claude Code 的折叠式转录）。
- 为什么重要：E1 是“诚实语法是否有效”的唯一裁决实验。
- 文档位置：`14` §14.5 E1。
- 期望的回答形态：明确各条件下事实层的可见性；种子失败数量与功效计算；增加一个真实竞品基线。

**R1-D14-03｜重要**
- 问题：E5 的决策规则功效不足。60 个任务 × 2 个模型 × 3 个种子，成功率差的 95% 置信区间半宽约 ±6 个百分点，要求“单侧下界 > −5 个百分点”等于要求观测差 ≥ +1 个百分点，规则天然偏向“删掉 log”。
- 为什么重要：`log` 是 Claim 层的主要来源，删掉它会连带影响账本、交叉校验和记分板。
- 文档位置：`14` E5 L185–187；`15` ADR-009。
- 期望的回答形态：给出功效计算，采用按任务配对的分析；或把规则改为等效性检验（TOST）。

**R1-D14-04｜重要**
- 问题：退出标准存在循环依赖。M1 要求“E7 单向门召回 ≥ 99%、开启 S2 时审批率 ≤ 5%”，但 S2 能否进入 M1 取决于 SP6；若 SP6 失败，M1 回退到“无沙箱时 opaque 一律 ask”，审批率必然升高。这时 M1 按什么标准退出？
- 为什么重要：退出标准必须在所有分支下都有定义。
- 文档位置：`14` §14.3.4 L104；SP6 L30。
- 期望的回答形态：按 SP6 的结论给出分支化的退出标准。

**R1-D14-05｜重要**
- 问题：核心论点没有对应的实验：Goal 侧栏 vs Session 列表（P4）、合同仪式成本（K7）、评审单元风险排序的有效性、“状态视图足以监督”的 3 秒扫读（北极星）。
- 为什么重要：“等特性被证明”需要覆盖最核心的特性。
- 文档位置：`14` §14.5；`00` §0.4。
- 期望的回答形态：增加实验或可用性研究，或者说明为什么不需要。

**R1-D14-06｜次要**
- 问题：M1 的自用用户就是开发团队本身，Needs-You 精度、打扰率等指标有自我偏倚。
- 为什么重要：门槛可能在偏倚样本上虚假达标。
- 文档位置：`14` §14.3.4。
- 期望的回答形态：至少引入 2 名非团队用户，或对指标打折。

**R1-D14-07｜次要**
- 问题：风险登记表缺少几项：上游单一供应商（Earendil 收购后方向变化）、模型厂商对第三方 harness 使用订阅凭据的条款（K4 只部分覆盖）、`sandbox-exec` 被弃用的公证或合规影响、用户目录中 worktree 的数据丢失、挖掘人类评论原话发送给模型的隐私合规。
- 为什么重要：登记表应完整列出已知风险。
- 文档位置：`14` §14.7。
- 期望的回答形态：补齐这些风险条目。

**R1-D14-08｜次要**
- 问题：北极星“每周可信交付的 Goal 数”会激励拆小 Goal，`maxDiffLoc` 也在推动拆分，护栏指标里没有对应的约束。
- 为什么重要：计数类指标容易被刷。
- 文档位置：`14` §14.6.1。
- 期望的回答形态：按规模加权，或增加护栏指标。

### D15 文档一致性与可执行性

**R1-D15-01｜重要**
- 问题：`02` 说“分支上唯一由 Tower 生成的提交是集成时的 seal 提交”，但 `04` §4.6.4 规定就地编辑“以你的身份提交到目标分支”，`10` §10.6 也有带 `Tower-Human-Edit` trailer 的提交。
- 为什么重要：分支历史的约定是 seal、验收延续、作者归因的共同前提。
- 文档位置：`02` §2.4 L157–158；`04` L419；`10` L243。
- 期望的回答形态：统一约定。

**R1-D15-02｜重要**
- 问题：“有效评审”的速率算错了一个数量级。停留 ≥ `loc × 0.6 s` 等于每小时 6000 行，而 ADR-014 写的是“≈ SmartBear 上限 500 LOC/小时的折算”（应为 7.2 秒/行），差 12 倍。
- 为什么重要：这个口径就是“防止橡皮图章喂饱调速器”的机制，按现在的数值它几乎不起作用。
- 文档位置：`15` ADR-014 L104；`04` L403；`06` L227；`08` L241；`12` L514。
- 期望的回答形态：修正系数，并评估对体验的影响（300 行的单元需要 36 分钟停留）；或改用其他有效性信号。

**R1-D15-03｜重要**
- 问题：调速器公式 `H = C − R − P − F` 有逻辑问题：一个单元被有效评审时，它的 LOC 从 P（待审）移到 R（今日已评审），H 不变。所以当天的评审永远不会释放余量，只有验收后被移出、集成，或第二天 R 清零才行。这与 F7 第 5 步“待审行数减少 → 评审余量恢复 → 就绪 Goal 自动开始”矛盾。
- 为什么重要：R11 的核心机制与 UI 承诺不一致。
- 文档位置：`15` ADR-014 L103–106；`04` F7.5 L885、§4.4.4；`06` §6.2.4 L216；`08` §8.5.5。
- 期望的回答形态：重新定义公式（例如 `H = (C − R) − P − F` 中 R 只对“今日新增产出”计费，或改为基于速率的模型），并给出数值演算示例。

**R1-D15-04｜重要**
- 问题：独立评审 Run 的默认值不一致：`07` §7.12 写“riskTier=high 默认开启”，ADR-019 和 `04` 设置页写“默认关”。
- 为什么重要：这决定高风险 Goal 的成本与流程。
- 文档位置：`07` L823；`15` ADR-019；`04` L815。
- 期望的回答形态：统一默认值。

**R1-D15-05｜次要**
- 问题：多处命名和数值不一致：
  - git 版本要求：`06` 写 ≥ 2.38，`10` 和 `14` 写 ≥ 2.40；
  - 并发上限：`maxConcurrentGoals`（`02`、`06`）与 `maxConcurrentRuns`（`13`）；
  - 动作类：`edit_out_of_scope`（`07` §7.6.1）与 `edit.out_of_scope`（`11`）；
  - `projects.trust` 在 DDL 中是枚举 `ask|trusted|untrusted`，在 `02` 中是对象 `{state, decidedAt, resourcesSeen}`；
  - `contracts` 的 CHECK 在 §6.2.3 和 DDL 中写法不同；
  - DDL 中 `facts.producer` 含 `git`，`02` 中没有。
- 为什么重要：工程师会按不同文档实现出不同的东西。
- 文档位置：如上。
- 期望的回答形态：一份术语与标识符的唯一来源表。

**R1-D15-06｜次要**
- 问题：Mode 的优先级列表，`05` §5.5 L474 缺少 `preparing`，`08` §8.6.2 有。
- 为什么重要：同一个推导函数有两个版本。
- 文档位置：如上。
- 期望的回答形态：保留一处定义，另一处改为引用。

**R1-D15-07｜重要**
- 问题：各文档的“主干修订状态”多处已经过时，而且彼此矛盾：
  - `13` 说 `06` 用 `wal_autocheckpoint=1000`、保留期 90 天、16 ms 预算，但 `06` 已改为 0、30 天、分档；
  - `04` §4.21 和 `12` §12.17 说 `08` 的声音默认是 `l4_only`，但 `08` 已不再有该字段；
  - `05` §5.12 #5、#6 说 `03`、`10` 尚未修改，实际已修改；
  - `10` 修订状态 #2 说 `07` 和 `06` 的验证槽位仍在 ~/.tower，实际已更新；
  - `08` 修订状态 #7 说 `02` 交叉引用错误，实际已修正。
- 为什么重要：评审者和工程师无法判断哪份是现行规格。
- 文档位置：各文档末节。
- 期望的回答形态：删除这些状态表，改为在 `15` 或 reviews 中集中跟踪未决项；仍开放的项逐条列出。

**R1-D15-08｜次要**
- 问题：示例数值不一致：`04` 的积压 3,645（= 2,192 + 1,453）与 `12` §12.10.5 读屏示例中的“待审 3,012”不符；评审头部“预计 6–10 小时”按 3,012 行计算，但正文说生成文件 1,140 行已排除（1,872 行应为 3.7–6.2 小时）。
- 为什么重要：线框图是界面文案初稿，数字自相矛盾会误导实现。
- 文档位置：`04` L126、L369；`12` L516。
- 期望的回答形态：修正示例。

**R1-D15-09｜次要**
- 问题：README 写“只向模型增加 3 个工具”，但塑形期是 `ask_user + propose_contract`，评审期是 `log`（或 `review_report`），没有写明这是指运行期。
- 为什么重要：对外表述应当准确。
- 文档位置：`README.md` L19；`00` §0.5 L64；`15` ADR-009。

**R1-D15-10｜次要**

### D16 创新与差异化

**R1-D16-01｜重要**
- 问题：护栏所依赖的三项差异化，在 v1 都不成立或不独特：
  - “引擎中立”：v1 只支持 Pi，ACP 到 M3 才有原型；
  - “本地优先”：Conductor、Superset、Emdash 都是本地的；
  - “执行式验证”：已有多家在做（见 R1-D3-03）。

  在 v1，哪一项是 Claude Code Projects 一个季度内难以复制的？
- 为什么重要：K5/K6 都是“高可能 / 高影响”，差异化必须在 v1 就能兑现。
- 文档位置：`01` §1.3 L57；`14` K5、K6。
- 期望的回答形态：一份竞品逐项矩阵，外加“厂商结构性不愿做”的具体论证（激励、架构或法律层面的原因）。

**R1-D16-02｜重要**
- 问题：新颖之处（诚实语法、评审调速、报警纪律、重入简报）都是 UI 和策略层的设计，复制成本低。是否存在会随使用不断积累的资产（账本、校准记分板、学习得到的 VerifyProfile、可迁移的 Goal 和记忆格式），能形成防御？文档没有论证。
- 为什么重要：没有积累型资产，产品护城河就只是先发优势。
- 文档位置：`09` §9.8；`01` §1.3。
- 期望的回答形态：说明数据资产的可迁移性和锁定效应（以及与“用户拥有数据”的取舍）。

**R1-D16-03｜次要**
- 问题：如果 Pi 上游（`pi-durable`）或某个 Pi 扩展先实现了 Goal 加验证，Tower 的价值剩下什么？ADR-006 只说“观察”。
- 为什么重要：这是对上游依赖的战略风险。
- 文档位置：`15` ADR-006；`01` §1.5。
- 期望的回答形态：给出情景分析。

**R1-D16-04｜次要**
- 问题：K6“薄编排层难以盈利”被评为“高 / 高”，但文档明确不讨论定价，连谁付费、为何付费的假设都没有。
- 为什么重要：商业可行性影响路线图的取舍。
- 文档位置：`01` §1.3 L57；`14` K6。
- 期望的回答形态：一句话的付费假设，以及 M2 验证它的方法。

## 4. 结论

- **是否所有维度为 100：否。** 最高分为 D9 的 72，最低为 D15 的 40。
- **是否还有可追问的问题：有。** 本轮共 **123** 条：**阻断 4 条**（R1-D7-01、R1-D7-02、R1-D11-01、R1-D14-01），**重要 70 条**，**次要 49 条**。
- 下一轮建议按以下优先级修订：
  1. 重新设计运行期进度与验证器的完整性：依赖缓存只读、校验与 CoW，带密钥标准的输出处理，服务与端口隔离（R1-D7-01/02/03/04、R1-D13-02）；
  2. `exec.test` 在无沙箱时的策略，以及缓存可写的问题（R1-D11-01/02）；
  3. 调速器的公式与有效评审系数（R1-D15-02/03）；
  4. 统一对话框规格、gate 顺序、`agent_settled` 防护（R1-D5-01/02/04）；
  5. 补全状态机与领域枚举（R1-D4-*）；
  6. 删除过时的“主干修订状态”，建立唯一来源表（R1-D15-*）；
  7. 收缩 M1 或给出工作分解，并修正 E1 和 E5 的设计（R1-D14-*）。
