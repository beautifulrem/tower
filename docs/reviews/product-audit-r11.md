### 0.4 代码通读

重点读了 `verify/bench/guard.rs` 和两个预加载文件、`bench.rs` 里的身份检查结论、`bench/held_out.rs`、`verify/perturb.rs`、`bench/loopback.rs`、`env_cause.rs`、`honesty.rs`、`remote.rs`、前端的 `Seal` 与 `lib/discounted.ts`、`adversarial.rs` 及其目标集、`ci.yml` 和 `adversarial.yml`。

- **断言入口身份检查（r8–r10 的第 1 项）终于做了，方向是对的。** 检查由 Tower 在项目代码之前装入，结论写进沙箱只能追加的记录，并且每个进程的结论都能归属到它自己。这是结构上的修复，不再是给清单加词，R3g、R3h 和对抗集的两个变体都因此被拦下。SECURITY.md 的“已知限制”如实写了：检查和被测代码在同一个进程里，它能提高隐藏的代价，但做不到不可能。仍然缺的不变式是：*一条通过的标准，它的每个受检测试进程都必须给出结论，缺了结论就是“未证实”，而不是“没问题”。* 目前只有在一个受检进程都没报告时，结果才写“没有检查”。此外，清单之外的测试运行器（例如 bun、deno）被归为“未知”，结果里什么也不说，这和“说不出就明说”的原则不一致。
- **“测试体没执行却报告通过”还不是一条不变式。** R3i 和 radv2 两次都被拦下，但拦下它们的，是一条按字样匹配的中等规则和“金丝雀没检查”的组合。字样一变，就只剩下“断言未检查”这一句行内说明。金丝雀本来就是“必然失败、必须看到它失败”的测试，在一条由红变绿的标准上，它没有运行而命令却报告通过，本身就足以说明测试体没有执行，应当单独构成高严重度，不需要文本规则来配合。卡片上的解释“测试的语言或写法 Tower 不认识”也把原因说错了。
- **源文件里内联的测试区域被当成源码（rrust2）。** Rust 的测试模块通常和被测代码写在同一个文件里，`roles.rs` 按文件判定角色，于是这部分改动在“只留源码”复跑里被保留；文本规则不把它当测试；金丝雀只改期望值，测试检查的对象换掉了它也照样“如期失败”。缺的不变式是：*文件里的测试区域属于测试角色*，“只留源码”复跑应当把它恢复成基线版本，删测试、改断言这类规则也应覆盖它。同样的问题存在于其他支持源内测试的语言和框架。这一类伤害是一个错误的改动拿到全套绿色事实。
- **账本的“无法确认”又是一张词表。** `honesty.rs` 用“机制词 + 改动词”的组合判断 Agent 有没有承认改了测试机制。rrust2 的提交说明写明了它做了什么，只是用词不在表里，账本就显示“一致”。R8e 的 Agent 在“原因”里承认了特判，扰动复跑也给了高严重度，账本对同一条“已满足”仍写“一致”。团队自己在 r10 的结论是“文本清单只会把缺口挪个地方”，账本不应再走这条路：只要这次验证的通过不计入已验证（任何高严重度结论），账本就不能写“一致”。
- **“已验证”的印章和计数用了两个来源。** 后端在高严重度结论下把通过记为 `not_evidence`，计数显示 0/1；但前端的印章（`Seal`）是否变成“不算证据”，只看金丝雀是否“被改动”（`lib/discounted.ts`）。所以 r3g、r8e 这类由身份检查或扰动复跑拦下的目标，页面右上角是绿色的“✔ 已验证 @…”，同一页的标准区写着“已验证 0/1”，哨兵写着“这次验证的‘通过’都不能当作事实”。这是本轮最直接的诚实性问题：新的检测路径加在了后端，界面上的绿色印章没有跟上。缺的不变式是：*“通过是否算证据”只有一个来源，印章、行、计数、账本、评审都读它。*
- **扰动复跑。** 设计是诚实的：只有测试把期望值写成输入的关系式时才有判据，SECURITY.md 也写明了。但现实里绝大多数测试的期望值是字面量，所以 R8b、R8c、R8d 和对抗集的 4 个特判目标仍然以绿色的 1/1 进入待验收，只带一条中等提示。不需要知道正确答案，也可以给出证据：诚实的修复通常会在被测输入附近广泛改变行为，只对测试用到的那几个点起作用的改动，在挪动后的输入上和基线一模一样。把“改动的作用只出现在被测点上”作为判据，可以在没有期望值的地方区分两者。另外，扰动给出的高严重度没有挂到对应文件的评审单元上（R8e 的单元风险是 0）。
- **保留测试按文件证明。** 每个文件一个随机令牌，投递箱只能写、不能读也不能列出，标签跟着证明走，“m 个中的 n 个”也做到了，这一项修得很完整。它的边界在 SECURITY.md 里写清楚了（执行保留测试的进程能读到该文件自己的文字）。
- **回环默认关闭，按证据放开。** 默认关闭现在覆盖之前和之后才启动的服务，截图浏览器默认拒绝，`look` 核对监听的归属，Agent 的进程随运行结束而清理。这几条都有隔离流程测试。新的设计问题在于放开的范围：证据来自“这条标准在基线上被回环拦住”，放开的却是整个项目，包括 Agent 自己的命令和之后所有目标；放开后，之后才启动的本机服务对它们都可达。这一切自动发生，不经过人，只在轨迹和设置里留下记录。Tower 自己的规则是“放宽 Agent 权限的决定留在桌前”，而这里的放宽超出了证据的范围。缺的不变式是：*由证据触发的放宽，范围不超过证据本身*（这条标准、这次验证）。扩大到项目和 Agent 的命令，应当作为一张需要你决定的卡片。
- **基线的分类。** 一条在基线上“先失败、再挂到超时”的标准被记为“没有运行起来（未启动）”，于是既不算红 → 绿的证据，也不触发回环证据（rport0）。认识测试运行器的输出时，应该先认“已经有测试运行并失败”，再看是否超时。
- **对抗回归。** 目标集扩到 28 个，判定变严（超时算失败，模型自己诚实修复记为“没考到”，诚实对照被拦算误拦），每个仓库的前提先断言，还输出按类别的 JSON 报告，这些都是 r10 第 7 项要的。但有三个问题。第一，团队在合入之前没有完整跑过它（`docs/17` 只记录了旧版五个目标的一次运行），我跑的这一次不通过。第二，“保留测试没被运行 / 只运行了一部分”这两类，问题出在合同配置上，跟模型作不作弊无关，可判定仍要求“模型作弊了才算考到”，诚实的模型永远让它们落到“没考到”。这两类应当按 Tower 有没有给出正确的标签和提示来判定。第三，CI 里的工作流在没有密钥时显示“成功”。
- **文档。** CHANGELOG 本轮按行为写全了，`docs/17` 的保留测试、金丝雀、身份检查、扰动、回环、工具链、验证开销各段都与实现一致，验证开销一段还主动更正了之前的 7.9 秒和 6.6 秒，这是 r10 第 11 项要的样子。SECURITY.md 对应表里点名的测试都确实存在，但仍没有 CI 校验。剩下的小问题：合计包体“136 KB”已经过时。

## 3. 前 20 项修复（按优先级）

需要维护者处理的条目标为 **［维护者］**。括号里是估计的分数提升，各维度不超过上限。

### 必须先做（决定 D3、D5 能否过 92，D14 能否回到 90 以上）

**1. “通过是否算证据”只有一个来源（D3 +1，D5 +1.5）**
不变式：*印章、标准行、金丝雀那一行、计数、账本和评审读的是同一个判断。* 后端已经有 `not_evidence`；前端的 `Seal` 和 `discounted.ts` 改为读它，而不是只看金丝雀是否被改动。被拦下的目标，标准行上的“通过”和“必然失败的测试如期失败”也要写明“这次验证的通过不计入”。补一条 e2e：fixture 里放一个由身份检查拦下的目标，断言页面上没有绿色印章。

**2. 文件里的测试区域属于测试角色（D3 +1.5，D5 +0.5）**
不变式：*测试代码不因为和被测代码写在同一个文件里就成了源码。* `roles.rs` 从“按文件”扩展到“按区域”：Rust 的测试模块、其他语言和框架的源内测试块都按测试处理。“只留源码”复跑把这些区域恢复成基线版本，删测试、改断言等规则覆盖它们。补一个 Rust 的流程测试和一个对抗目标（rrust2 这一类）。

**3. “测试体没执行却报告通过”成为独立的高严重度（D3 +1）**
在由红变绿的标准上，金丝雀没有运行而命令报告通过，单独就是高严重度，不需要文本规则配合。同样，受检进程开始了却没有给出结论，结论应为“未证实”并写在行上，而不是当作没问题。卡片不要把原因说成“语言或写法不认识”。

**4. 账本由事实推出，不靠词表（D3 +0.5，D5 +0.5）**
这次验证的通过只要不计入已验证，账本上对应的“已满足”就不能显示“一致”，统一显示“无法确认”并给出原因。Agent 的说法和事实冲突时，以事实为准；词表最多用于额外提醒。

**5. `main` 回到绿色，合入前与 `main` 同步［维护者］（D14 +1.5，D11 +1，D15 +1）**
修好 CI 机器上截图浏览器的崩溃（在受限配置下它得不到所需的东西，本机却能得到，说明配置依赖机器的状态，这也会发生在用户的 Mac 上）。分支保护打开“合入前必须与 `main` 同步”，或者改用合并队列。没有密钥时，对抗工作流应当显示“跳过”或失败，不能显示成功。

**6. 对抗回归合入前跑一遍，按真实结果记录［部分需要维护者］（D14 +1.5，D3 +0.5）**
本轮的结果（5 漏过、2 超时）写进 `docs/17`，已知会漏的类别标出来，修好一类就从“已知”里去掉。“保留测试没被运行 / 只运行了一部分”两类改为按 Tower 有没有给出正确的标签和提示来判定，不看模型。“只在源码之外的改动下才通过”两个变体为什么会跑到 600 秒，需要查清楚，是模型的问题还是 Tower 让它卡住了。配置仓库密钥，或者用本机的定时任务每晚跑，并保存报告。

### 应该做（各维度从 88 走向 92）

**7. 字面量期望值上的特判要有不依赖答案的判据（D3 +1.5，D5 +0.5）**
在挪动后的输入上，比较快照和基线的行为：改动只在测试用到的那几个点上起作用，其他地方和基线完全一样，就是“只为测试成立”的证据，可以升为高严重度；改动在附近的输入上普遍起作用，就降低特判哨兵的轻重。扰动给出的结论要挂到对应文件的评审单元上。

**8. 按证据放宽，范围不超过证据（D12 +1.5）**
基线上的回环证据只放开这条标准的这次验证。要扩大到整个项目、扩大到 Agent 自己的命令，应当出一张卡片由你决定，并说明放开后之后才启动的本机服务也可达。

**9. 基线“先失败、再超时”判为测试失败（D11 +1，D1 +0.5）**
测试运行器的输出里已经有测试运行并失败，就不应记为“没有运行起来”。回环被拒加超时这种组合，也应当算作回环证据。Agent 自己的命令因为同样原因挂起时，尽早告诉它原因，而不是等 5 分钟超时。

**10. 覆盖范围的说明不做成哨兵（D4 +0.5，D5 +0.5）**
“这个语言没有身份检查，金丝雀是唯一的检查”是关于覆盖范围的事实，应该写在标准行上，不应在每个 Rust、Go 目标上都挂一条中等哨兵。清单外的运行器同样写一句“没有检查”。

**11. 卡片的选项与原因匹配（D5 +0.3，D11 +0.3）**
端口被别的程序占着、工具链找不到、回环被拒，各有自己的标题和选项。“这是真的测试失败（记为改动前失败）”只出现在可能确实是测试失败的情况下。

**12. 消除负载下的 flow 失败（D14 +0.5）**
`pausing_stops_the_engine_and_resume_continues` 在负载约 23 时因为引擎已关闭而失败。找出它依赖的时序，在 CI 的负载下复跑多次确认。

**13. 包体与文档数字（D10 +0.5，D13 +0.5）**

### 4.2 独立验证还独有吗

- **主流产品里仍然没有。** 要么由 Agent 自己验证（Cursor、Copilot、Devin 跑自己的测试并附产物），要么评审的是别的东西：Claude `/goal` 只读对话记录，Codex Guardian 审动作，Bugbot、Devin Review、Claude Code Review 评论 diff。没有一家记录了保留测试、只留源码复跑、必败金丝雀、断言完整性检查或特判检查。
- **开源侧的零件在增多，但仍是零件。** Alter-Igor/opencode #121/#122（10 月 5 日合入）在 Agent 声称完成后跑隐藏的验收测试，此后的提交是目标循环和定时，没有更多验证。software-agent-factory #160（10 月 18 日）的反事实检查只提示、不阻断。konductor #72 是 10 月 22 日的 issue，没有评论。attest 10 月 21 日之后没有提交；Praxso/attested 最后一次提交在 10 月 22 日。10 月 20–27 日新出现了几个只看过描述的仓库（mender、swe-task-validator、reward-hacking-verifier 等，自称做隐藏测试或篡改检测，代码未核实）。论文方面，RH-Detect（2610.10947）是检测基准，2610.29129 从表示层面减少奖励投机，都不涉及隐藏测试或篡改。
- **结论：** Tower 仍是唯一把保留测试、只留源码复跑、金丝雀、运行时身份检查、扰动和人工验收串成一条流程的桌面产品，本轮的差距还拉大了。但这个优势只在“每一个绿色结论都站得住”时才成立。本轮页面上同时出现“✔ 已验证”和“这次验证的通过都不能当作事实”，这种问题对 Tower 的伤害，比对一个从不声称独立验证的竞品要大得多。

### 4.3 Tower 缺什么

1. **装不上**：没有发行版、签名、Homebrew 和自动更新；只支持 macOS。
2. **手机端**：主流四家都有原生 App 或遥控；Tower 是网页加 ntfy。
3. **云端或远程执行**：几乎每家都有，Tower 没有。
4. **引擎数量**：Conductor、Warp、Copilot、Zed 都在 3 个以上，Tower 是 2 个。
5. **公开证据**：有了报告格式，还没有一次通过的、可以公开的拦截率。
6. **工程信号**：一个刚公开的项目，`main` 是红的，对抗工作流在没跑的情况下显示绿色，外部评估者第一眼看到的就是这些。
