**ADR-191 的主干成立**：
- **识别规则**（`10` L602–607）：
  - 按影子中的 seal sha 识别，而不是按 trailer。用户 amend 或 cherry-pick 后的提交按用户的提交处理，不会在其上快进而撤掉用户的改动。
  - 第 63 轮列出的序列都由同一规则接住：两次失败、未记账的写入、改前缀或标题、同一 pin 的延续、CAS 遇到 ref 锁。
  - 只在 Tower 生成的名字中查找，快进合入了 seal 的 `main` 不会被当作 B。
  - 相似 goalId 不构成问题：查找条件要求 `<goalId>` 之后紧跟 `-` 或名字结束，而且命中还要求顶端是**本 Goal 影子中**的 seal。所以即使 `GoalId` 只在本机唯一（`02` L46），跨机器同号的分支也不会被认作本 Goal 的写入。
- **M2 RPC 一句**：`05` L551、`00` L100、`05` L281 一致。`prepare_failed` 的六处定义不再有 M2 来源注记。全文只剩 `05` L413 既有的 `tower.selfcheck`（工具来源复核，与已删除的规则无关）。
- **阻止模式**：全文 30 余处都带 M2（或 E8）标记，见 §3。
- **其余**：
  - P9 与 `13` L44 预算行已落地，`08` L757、`16` L760 引用一致；
  - 去重键 `st:{goalId}:satellite` 已在 `08` L206、`16` L194 登记；
  - `↩` 两行已在 `16` §16.3 登记。

**新发现 3 条：重要 2，次要 1**。三条都出在 Tower 改动用户仓库中 Goal 分支的那一步，ADR-191 的识别规则让它们浮现出来：
- **启用提交签名时识别规则失效**（R64-D13-01，重要）：
  - `10` L656 规定 seal 的签名 “在用户仓库上下文中用 `git commit-tree -S` 的等价流程重做”。影子上下文只允许执行 git、最小配置里没有签名设置（L176–178、L182），所以签名后的提交只能在用户仓库中生成，sha 与影子中的 `refs/tower/<goalId>/seal/<n>` 不同。
  - ADR-191 的规则又写明 “只带 trailer 不算”。照字面实现时，对启用签名的用户：
    - 每次重新验收都落入 “B 的顶端不是 Tower 自己的 seal”，另开 `-v<k>`，并显示不真实的 “你的分支已有你的提交”；
    - M1 的验收延续因此从不成功；
    - `integration.performed.sha` 记哪一个、`integrated` 的观测用哪一个，正文都没有写。
- **快进或删除一条正被用户检出的分支**（R64-D13-02，重要）：
  - 重新 seal 表以 `git update-ref B S P` 快进 B（`10` L623）。ADR-190 起，M1 的验收延续会不经人的决定自动做这一步。
  - 若 B 正在用户主检出或某个链接工作树中被检出，HEAD 会在用户不知情时移动，工作树与索引随之和 HEAD 不一致。这违反 `10` L10 的 “绝不碰用户的工作现场”：该条的显式例外只有两个，都要人逐次确认。
  - 归档时删除分支也有同样的缺口。
- **删除分支的两条路径不用识别规则**（R64-D13-03，次要）：
  - `integrated` 归档时的 “已合入才删”（`10` L437）没有写判定的是 seal 还是分支顶端；
  - 一键 “清理 Tower 引用”（`10` L697）无条件删除已集成或已放弃 Goal 的 `refs/heads/<prefix>/*`，并告诉人 “丢失的只是查看这些提交的能力”。这与 `03` L63 “`abandoned` 保留分支” 相反；
  - 它还删除 “全部 `refs/tower/*`”，包括多机租约 `refs/tower/_owner`；
  - `04` §4.15 的设置树里没有这个动作。

每一条都回到正文核对过，不是推测。

### 3.3 取舍的判断

| 取舍 | 判断 |
|---|---|
| **按影子中的 seal sha 识别 Tower 自己的提交**，不按 trailer | **可接受，理由成立**：只看 trailer 会在用户 amend 过的提交上快进。代价：sha 必须就是写进用户分支的那个提交。签名会使两者不同，见 R64-D13-01 |

| **M1 验收延续自动快进用户分支**（ADR-190，本轮未改） | **可接受，但需要一条守卫**：只快进、不改写的论证成立。前提是分支没有被检出，否则自动快进就是在移动用户检出的 HEAD，见 R64-D13-02 |

### D13 隔离、git 与并发

**R64-D13-01｜重要**（`10` L656：seal 的签名 “在用户仓库上下文中……重做”。所以启用签名时，写进用户分支的提交与影子中的 `refs/tower/<goalId>/seal/<n>` 不是同一个 sha。ADR-191 的识别规则（L602–603）只认影子中的 sha，并明确 “只带 trailer 不算”。照字面实现，签名用户的每次重新验收都另开 `-v<k>`，并显示不真实的 “已有你的提交”）

- **问题**：
  - **签名只能在用户仓库上下文中进行**：
    - 影子上下文的 git 运行在 “只允许执行 git” 的进程沙箱中（`10` L176–178），最小全局配置只有身份与换行相关的键（L182），签名程序既读不到配置也无法启动；
    - L656 因此写 “签名在用户仓库上下文中用 `git commit-tree -S` 的等价流程重做”；
    - 签名提交的签名字段不同，sha 必然不同于影子中的 S。
  - **正文没有写签名提交 S′ 的去向**：
    - 不写回影子的 `seal/<n>`；
    - 不说明 `integration.performed.sha` 记 S 还是 S′；
    - 不说明 L594、L622–623 的 fetch 与 CAS 写入的是哪一个。
  - **照字面组合的结果**（设计层面）：用户分支的顶端是 S′，不在影子的 seal 中，又带 `Tower-Goal` trailer。按 L603，它 “按用户的提交处理”，于是：
    - 每次重新验收都落入 L626–628：另开 `B₀-v<k>`，面板写 “你的分支 <B> 已有你的提交，Tower 未改动它”。分支上没有任何用户提交，这句话不真实，而 L628 写的是 “只在本行显示，所以这句话总是真的”；
    - 复用一行（L619–620）永远不命中，`06` L920 “只要其间没有人改动该分支，就不另开 `-v<k>`，也不说明‘已有你的提交’” 不成立；
    - M1 的验收延续一律落入 “另开 `-v<k>` 的行”，不延续、回到 `in_review`（`06` L920）。ADR-190 给延续的承诺对这类用户从不成立；
    - 相邻的两处也取决于记哪个 sha：
      - `10` §10.12 的 `integrated` 以 `merge-base --is-ancestor <seal> <base>` 判定。若记 S，人合入 S′ 后永远观测不到合入；
      - `06` L920 的 “归档前核对分支”：以该条 `sha` 重写被删的分支时，若记 S′ 而用户仓库已回收这个对象，重写会一直失败、无法归档。
- **为什么是重要**：
  - 照正文实现就会违反两条明文的不变式：`10` L628 的 “总是真的”、`06` L920 的 “不另开 `-v<k>`”。前一条又是本产品的诚实约束，面板会对人说一句不真实的话；
  - 触发条件不是罕见的失败序列，而是一个常见的用户配置（`commit.gpgSign`，`14` K12 把 “要求签名提交的仓库” 列为已知风险）。对这些用户，每一次重新验收与每一次延续都会出现；
  - 不丢用户的数据：影子、另开的分支都在。所以不是阻断。
- **文档位置**：`10` L176–178、L182、L591–596、L602–607、L618–628、L656–657、L1137–1139；`06` L920；`14` K12（L704）、G46(bg)(3)（L133）；`15` ADR-191 R63-D13-01 条。
- **期望的回答形态**：在 `10` L656 的唯一定义处写一句签名的顺序，`10` L602 不需要改：
  - 签名时以影子中的 S 为模板，在用户仓库上下文中生成 S′（同树、同父、同说明，带签名），**先**把 S′ fetch 回影子并以它作为 `refs/tower/<goalId>/seal/<n>`，**再**按 L594 / L622–623 写用户仓库中的分支；
  - `integration.performed.sha` 与 `integrated` 的观测一律用这个 seal（即 S′）；
  - 这样 “sha 是影子中的 seal” 对签名与不签名都成立，写后窗口的顺序也不变（影子先于用户仓库）；
  - G46(bg)(3) 补一组：项目启用签名，验收、返工后再验收，同一 pin 再延续一次。期望：在同一分支上快进或复用，不另开 `-v<k>`，不显示 “已有你的提交”。

**R64-D13-02｜重要**（重新 seal 的快进一行以 `git update-ref B S P` 移动 B（`10` L623）。ADR-190 起，M1 的验收延续不经人的决定自动执行这一步。若 B 正在用户主检出或某个链接工作树中被检出，这一步就在用户不知情时移动了该检出的 HEAD。`10` L10 的 “绝不碰用户的工作现场” 只列了两个显式例外，都要人逐次确认）

- **问题**：
  - **git 的行为**：`update-ref` 是底层命令，不检查分支是否被检出；而 `fetch` 到被检出的分支、`branch -f` 都会被 git 拒绝，正是为了保护工作树。B 被检出时：
    - CAS 照常成功，该检出的 HEAD 指向新 seal；
    - 工作树与索引仍是旧内容，在用户看来像是 “有一批未提交的改动，正好撤销 Tower 的新内容”；
    - 用户之后的一次普通提交就会把 Tower 新验收的改动撤掉。
  - **正文的覆盖**：
    - 本地合并（M2）已经处理 base 正被检出的情形（`10` L1133：先查 `worktree list --porcelain`，只能在该检出内 `merge --ff-only`，并逐次确认）；
    - 重新 seal 表（L618–625）与 `06` L920 的延续一句都没有这条检查；
    - 第一次 seal（L594）用 `fetch` 写入，git 会拒绝被检出的分支；但那时 B₀ 还不存在，所以不受影响。
  - **触发场景很普通**：人检出 Tower 的分支来试用或推送，同时目标在 `accepted`；之后的 `retry_verify`、检验带回、合同修订或交还触发验证延续，或者人在另一窗口再次验收。
  - **删除路径同样如此**：归档时删除分支（`10` L437）、一键清理（L697）若删除的是被检出的分支，该检出的 HEAD 会指向一个不存在的 ref。
- **为什么是重要**：
  - 照正文实现，就违反 `10` L10 明文的不变式，以及 “显式例外只有两个，都需要人在 UI 中逐次确认”；
  - 而且在延续路径上是自动发生的，没有任何确认；
  - 用户自己的提交与未提交改动不会丢（工作树不被写），所以不是阻断。但后果是用户工作现场的状态被改变，并可能导致 Tower 的改动被无意撤回。
- **文档位置**：`10` L10、L591–596、L618–628、L437、L697、L1133；`06` L920；`04` §4.6.5（L545）；`14` G46(bg)(3)；`15` ADR-190 R62-D13-01(b)、ADR-191。
- **期望的回答形态**：在 `10` L618–625 唯一定义处加一条守卫，`06` L920 与删除路径引用它：
  - 写入前在用户仓库上下文中读 `worktree list --porcelain`。B 被任一工作树检出时**不移动它**，二选一并写明：
    - 按 “B 的顶端不是 Tower 自己的 seal” 一行另开 `B₀-v<k>`，面板写一句为真的说明（例如 “分支 <B> 正被检出，Tower 未改动它”）；
    - 或返回 `E_INTERNAL`，`step` 记一个新值，面板提示切换分支后重试。
  - 验收延续遇到这一情形时按已有规则不延续、回到 `in_review`；
  - 归档删除与清理跳过被检出的分支；
  - G46(bg)(3) 补一组：人检出 Goal 分支后，从 `accepted` 触发验收延续。期望：用户检出的 HEAD 不变。

**R64-D13-03｜次要**（Tower 删除用户仓库中 Goal 分支的两条路径都不用 ADR-191 的识别规则：`integrated` 归档时 “已合入才删”（`10` L437）没有写判定的是 seal 还是分支顶端；一键 “清理 Tower 引用”（`10` L697）无条件删除已集成或已放弃 Goal 的分支，还删除多机租约 `refs/tower/_owner`；`04` 的设置树里没有这个动作）

- **问题**：
  1. **归档删除**：
     - `10` L437 写 “删除用户仓库中的 Goal 分支（已合入才删；squash 合并以 `gh pr view` 或 patch-id 确认）”。
     - 一个 Goal 可能写过多条分支（B₀、`-v<k>`）。用户也可能在 seal 合入之后继续在 B 上追加提交（ADR-136 的前提，`10` L598）。
     - “已合入” 若按 Goal 的 seal 判定（patch-id 的写法暗示判的是 seal），24 h 宽限后的自动归档会删掉带有未合入用户提交的分支。按分支顶端判定才安全。正文没有说是哪一种，也没有写用 CAS 删除（期望旧值）。
  2. **一键清理**（`10` L697）：
     - 写的是 “删除已集成或已放弃 Goal 的 `refs/heads/<prefix>/*`”，没有任何条件。`03` L63 写 `abandoned` “保留分支”，`06` L923 允许从任何非终态放弃，包括 `accepted`。
     - 所以 “人在 Tower 写的分支上继续工作，然后放弃这个 Goal” 之后，清理会删掉带用户提交的分支。
     - 而说明写的是 “丢失的只是‘在用户自己的 git 工具中查看这些提交’的能力”，这对用户的提交不为真。
     - 它还删除 “全部 `refs/tower/*`”，包括 `06` L181–183 的多机租约 `refs/tower/_owner`。租约在本机仍有效时，另一台机器的 Tower 会因此不再进入只读状态。
     - 前缀改过之后，旧前缀下的分支也不在 `<prefix>/*` 中。
  3. **两处说法不一致**：
     - `10` L697 与 L446 把清理放在 “设置页 → 存储”；
     - `04` §4.15 的设置树（L1260–1280）没有 “存储” 一节，只有 “数据 · 清理工作目录 · 清理审计地标引用（仅在开启‘保留审计地标’时出现）”；
     - M1 是否交付会删分支的清理，实现者无法确定。
- **为什么是次要**：
  - 清理是人主动发起的操作；归档删除的 “已合入” 按分支顶端读（类似 `git branch -d` 的语义）是安全的，有经验的实现者多半这样读；
  - 但两处都可能删掉用户的提交，一处的说明不真实，一处还会删掉并发控制用的租约；ADR-191 的识别规则正好可以作为删除条件，改动很小。
- **文档位置**：`10` L437、L446、L598、L602–607、L686、L697；`03` L63；`06` L181–183、L923、L1114；`04` L1260–1280；`16` L287。
- **期望的回答形态**：在 `10` L437 与 L697 各改一句：
  - 只删除顶端是 Tower 自己的 seal（按 L602 的识别规则）且该顶端已在 base 中的分支，以 `update-ref -d <分支> <顶端>` 删除；其余保留，并在清理结果中列出 “含你的提交，未删除”；
  - 清理不删 `refs/tower/_owner`；
  - `04` §4.15 与 `10` 统一清理的位置与 M1 范围：要么在 `04` 的 “数据” 一节加入这个动作，要么在 `10` 标为 M2；
  - 说明文字改为为真的一句。
