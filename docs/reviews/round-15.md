## 1. 总评

第 14 轮的 13 条中，已解决 5 条、部分解决 8 条、未解决 0 条。lint 全部通过，D54 与 Pi 源码一致。

ADR-128 把 `external_change` 的出口改成“先解除本原因，再按通用规则继续”，但通用规则本身缺少一个持久的“继续目标”。以下几种常见路径都没有定义去向：
- 在暂停中检测到外部写入，之后另一原因先解除；
- 交还时选 `take_external`；
- 接管期间检测到外部写入，之后放弃改动；
- `nested_repo_live` 自动解除。

### D4 领域模型与生命周期

**R15-D4-01｜重要**（ADR-128 的通用原因解除规则没有持久的“继续目标”）

- **问题**：ADR-128 规定 `keep`/`revert` 都“先解除本原因，再执行通用的原因解除规则”。按原因逐一推演，有五类组合没有去向，或者与其他规则冲突。

  1. **`detectedIn.state = paused` 没有去向。**
     - 在 `paused(X)` 中检测到外部写入时，`external_change` 进入 `alsoApplies`，`detectedIn = {state:"paused", pauseReason:X}`（`10` L238）。
     - 之后 X 先被解除，`external_change` 就成为唯一原因（`06` L838：“原因解除后若 `also_applies` 非空，Goal 保持 `paused`，取其中最高者”）。X 先解除的例子：
       - `provider_unavailable` 自动恢复；
       - `extend_budget` + `resume`；
       - `app_quit` 后重启；
       - 卫星重建完成；
       - 接管期间检测到外部写入后，交还使 `human` 解除。
     - 此时 `keep`/`revert` 要“按 `detectedIn` 继续”，但 `03` L81、`10` L247、`06` L841–842 只列出 `running`/`settling`/`verifying`/`in_review`/`accepted`/`claimed`，没有 `paused`。X 原本的出口（例如 `budget_hard_cap → running`）在它被解除时并没有执行（`06` L838 只“保持 `paused`”），这一意图就丢了。
     - `goal.resume` 解除 `human` 时，是否同时发出 `run.requested{resume}`，也因此不确定。

  2. **`pendingVerify{trigger:"human_change"}` 与剩余原因的出口冲突。** 规则是：已有 pin 且 `keep` 使树 ≠ pin 时，记 `pendingVerify`，“离开 `paused` 时执行”（`03` L81、`10` L247）。但：
     - **由运行行为进入的暂停**（`budget_*`、`stop_condition`、`provider_unavailable` 等），出口是 `running`（`06` L838）。若 Goal 之前返工过，就有一个旧 pin；Agent 工作过之后，树 ≠ 旧 pin 几乎总是成立，于是会记下一个无意义的 `pendingVerify`。离开 `paused` 时是开 Run 还是去验证，没有定义。G33b(a) 正是断言了这种记录。
     - **由 pin 推导的暂停**，出口都绑定“同一 pin”或直接进入评审：
       - `s0.grant` 以同一 pin 回到 `verifying`（`06` L850）；
       - `verify_env_error` 用同一 pin 重新验证（`03` L77）；
       - `override_sentinel` 进入评审（`03` L75）；
       - `s0.deny` 进入 `in_review`（`06` L850）。

       采纳外部改动之后，这些出口会把一棵与 pin 不同的树送进评审或以旧 pin 验证，`pendingVerify` 是否、何时取代它们没有定义。
     - `pendingVerify` 只有一个槽位（`02` L159）。`keep` 会覆盖 `s0_grant_pending` 或人暂停时保存的 `{pin, verifyFrom}`，原 `verifyFrom` 随之丢失。

  3. **交还时选 `take_external` 的去向自相矛盾。**
     - `04` L645 写明选 `放弃你的改动` 时，“交给 Agent 继续 / 直接重新验证”置灰；`10` L706–707 写明不注入 `tower.handback`。
     - 但 `goal.hand_back` 的 `mode` 是必填参数（`06` L846）。`take_external` 又保留了 `external_change`，`also_applies` 非空，按 `06` L846 会写 `pending_hand_back={mode,…}`。
     - 于是只有两种结果：
       - 写了 `pendingHandBack`：之后 `keep` 触发 `applyPendingHandBack`，`continue_agent` 会注入 `tower.handback`，与“不通知 Agent”相反；
       - 不写：回到第 1 项，`detectedIn = {paused, human}` 没有去向。从 `in_review` 接管时，本应在 `keep` 后重新验证、在 `revert` 后回到评审，现在都没有定义。

  4. **放弃改动时与已有检测记录冲突。**
     - 接管期间，watcher 会立即记录外部写入（`10` L239），此时 `externalChange` 已存在：`detectedIn = {paused, human}`，基线为接管时的 safety 检查点。
     - `discard_human_edits` 又规定 `detectedIn = takeoverFrom`、基线 = pin 的检查点（`06` L848、`10` L741）。
     - 而“重复检测时基线与状态保持首次值”（`02` L146–151 注释、`16` L28）。
     - 两条规则直接冲突。G36e（`14` L119）断言 `detectedIn = in_review`，只有当接管期间 watcher 没有检测到时才成立。

  5. **`nested_repo_live` 自动解除后没有去向。**
     - “条目从卫星中消失时命中解除”（`03` L75、`10` L94、`04` L892，G26c(e)：“不需要人再操作”）。
     - 当它是唯一原因时，Goal 解除后去哪里没有定义：留在一个没有原因的 `paused`？自动恢复 Run？
     - 并且条目在暂停中被删除，本身就是一次来源不明的写入，会回到第 1 项。
- **为什么重要**：
  - 这些组合都在主路径上：用户在 Agent 停下时改文件、预算或网络暂停期间改文件、接管期间有进程写入。实现者照现行文字，会写出没有原因的 `paused`，或者把与 pin 不同的树送进评审。后者违反 ADR-122 的核心承诺“来源不明的内容不会先被验证或评审”，以及 `03` §3.3 要求断言的不变量。
  - 第 14 轮期望的答案是“剩余最高原因成为 `pauseReason`、全部解除时调用 `applyPendingHandBack`”。这只覆盖了带 `pendingHandBack` 的情形，没有覆盖“全部解除之后、没有 `pendingHandBack` 时去哪里”。
- **文档位置**：`02` §2.4 L146–159；`03` §3.2.1 L69、L75、L77、L81、L86、L88、L90；`06` §6.4.3 L838、L841–842、L846、L848、L850；`10` §10.3.1 L238–247，§10.8.4 L706–707、L741；`04` §4.6.7 L623、L645，§4.8.9 L892；`16` L28；`14` G26c L90、G33b L110、G36e L119。
- **期望的回答形态**：
  - 引入一个持久的**继续目标**，例如 `Goal.pausedFrom = {state, pin?, verifyFrom?}`：
    - 在 Goal 第一次进入 `paused` 时写入，叠加原因不覆盖它；
    - 每个原因的命令只做“解除自己”，并可**显式地**改写目标。例如：起源于 pin 的暂停被 `keep` 后，目标改为“新 pin 验证”；起源于运行的暂停被 `keep` 后，不记 `pendingVerify`。
  - 全部原因解除时，唯一的转移函数按 `pendingHandBack` > 继续目标 执行，取代各行“按 `detectedIn` 继续”的枚举。
  - 规定 `override_sentinel`、`s0.deny` 这类直接进入评审的出口，在树 ≠ pin 时改为先验证。
  - `take_external` 时 `mode` 为空，不写 `pendingHandBack`。
  - `discard_human_edits` 在 `externalChange` 已存在时：路径并入，基线保持首次值，继续目标显式改为 `takeoverFrom`。
  - `nested_repo_live` 自动解除后保持 `paused(human)`（由人显式继续），或者写明自动恢复的条件。
  - 增加用例 G36g：
    - (a) `paused(provider_unavailable)` 中检测，自动恢复后 `keep`；
    - (b) `paused(s0_grant_pending)` 中检测并 `keep` 后授权；
    - (c) `paused(sentinel_high)` 中检测并 `keep` 后覆盖；
    - (d) 交还选 `take_external` 后 `keep`/`revert`（从 `in_review` 接管）；
    - (e) 接管期间检测后放弃改动；
    - (f) `nested_repo_live` 的条目在暂停中被外部删除。

**R15-D4-02｜重要**（ADR-128 引入：`revert` 之后的“剩余差异”判定在运行中检测时会把 Agent 自己的改动判为新的外部写入）

- **问题**：
  - **规则**：`revert` 先按 `restorePaths(基线, E)` 恢复，之后若“**树** ≠ 基线的树”，剩余差异按两类处理：存活进程 → `agent_bg`，“其余视为一次新的检测”（`10` L246、`06` L842 第 ③ 步、`03` L81、`07` L1461、`04` L861）。
  - **基线**：在 `running` 中检测时，基线是“检测之前最近的检查点”（`10` L232）。
  - **剩余差异的来源**：检测时，本回合尚未建检查点的 Agent 工具编辑已在树中；随后 drain 回合里 Agent 又有编辑（这正是 drain 检查点存在的原因，`10` L236）。所以只恢复 E 之后，树几乎必然 ≠ 基线。剩下的差异来自 **Agent 工具调用**，既不是“存活进程”，也不是外部写入，现行两类规则只能把它归入“其余”，于是判为一次新的检测：
    - Goal 立即重新进入 `paused(external_change)`，E′ 是 Agent 自己改过的文件；
    - 人若再次撤销，就会把 Agent 的合法工作恢复到基线（虽然有 safety 检查点可以找回）。
  - **settle 序列中检测**：被追踪进程在第 3 步之前刷写的内容（归因表第 2 行，记为 Agent）同样落入“其余”。
  - **与用例冲突**：这与 G36b(a) 的预期相反（`14` L116：`revert` 只恢复 E，`src/a.ts` 不动，回到 `running`）。规则与它自己的用例矛盾。
- **为什么重要**：在 Agent 运行时用户自己改文件，是外部写入最常见的情形。按字面实现会形成“撤销 → 再次暂停 → 再撤销 → 丢失 Agent 的工作”的循环，并在卡片上把 Agent 的编辑说成“来源不明”。这违反 ADR-128 第 1 条对归因的要求。
- **文档位置**：`10` §10.3.1 L232、L236–237、L246；`06` §6.4.3 L842；`03` §3.2.1 L81；`07` §7.10.3 L1461；`04` §4.8.7 L861；`14` G36b(a)(g) L116。
- **期望的回答形态**：
  - 把“剩余差异”限定为 **E 中的路径**：恢复之后，E 中仍与基线不同的路径才需要分类。
  - 或者把比较对象改为“检测后的最新检查点，并把其中 E 的路径换成基线版本”。
  - 分类时，带 Agent 工具写入归因的路径（drain 检查点的 `author:"agent"`、`mixed`）记为 Agent，不进入新的检测。
  - 修订 `10`/`06`/`03`/`07`/`04` 五处的措辞。
  - 增加 G36b(h)：在 `running` 中检测；drain 期间 Agent 改了其他文件；`revert` 后回到 `running`，不产生新的检测。另一组在 settle 序列中检测，此时有进程刷写。

### D5 Agent 架构与 Pi 集成

**R15-D5-01｜次要**（ADR-129 的残留）

- **问题**：
  1. **只由压缩引起的宽限失败会永久等待。**
     - 宽限失败的判据包括 2 s 内出现 `isCompacting`，处理是“回到等待下一次 `agent_settled`”（`05` L554）。`05` L554 自己也列出了“settle 之后的 `ctx.compact()`”这一来源。
     - 但 Pi 的手动压缩只发 `compaction_start`/`compaction_end`，不发 `agent_settled`（见文首核对）。
     - 因此，扩展在 settle 后 2 s 内调用 `ctx.compact()` 时，Goal 会带着有效提交永久停在 `running`/`settled`。
  2. **nudge 守卫不成立时，settle 判定表没有对应的行。**
     - tower-goal 只在合同至少有一条 `exec`/`artifact` 标准、`nudge.max > 0`、`outcome === "completed"` 时才 nudge（`05` L1037–1045）。
     - settle 表只有“没有有效 submit，nudge 次数已用完”这一行（`05` L570）。
     - 只有 human 标准的 Goal、`nudge.max = 0`、或 `outcome = error` 时，无有效提交的 settle 没有去向。`03` L73 写的是“一次提醒后仍停下”，这条前提在这些情况下不成立。第 14 轮 R14-D5-01 第 3 项问的就是这个守卫差异；删除提醒回合之后，这一缺口仍在。
  3. **“Tower 不以 user 角色注入任何消息”与设计不符。** 这一断言见 `15` L942、`05` L564、`03` L101、`06` L257、`07` L350。但：
     - resume 与返工 Run 的第一条消息是 user 角色：`05` L88、L95 的 `initialInput`/`resumeInput` 都是“第一条用户消息”；`05` L1152 写“resume 后用 `prompt` 发 `tower.rework` 证据”。
     - `tower.processes_terminated` 在恢复时也“作为第一条消息”。
     - RPC 本来就没有 custom message 命令。

     诚实显示实际上依靠标记行与 Trace 的“Tower 注入”过滤器（`05` L1235）来保证，断言应当据此改写。另外 `03` L139 写返工以“custom_message”开启，与 `05` L1152 不一致。
  4. **RPC 下没有投递触发点。**
     - `tower.processes_terminated` 在 RPC 下“由 tower-goal 执行 `pi.sendMessage`”（`05` L554、C32）。
     - 但 `05` §5.6.1 的通道表（L626–631）中，Host → 扩展只有文件，并且只在 `before_agent_start`/`session_compact`/`tool_call` 时读取。撤回后新 run 中的哪个钩子去读、读哪个文件、怎样去重，都没有写。属于 M2。
- **为什么重要**：第 1 项是 settle 主路径上的活性缺口。第 3 项是诚实语法的元陈述，与实现相反，会误导审查者以为 Trace 中没有 Tower 写的 user 消息。
- **文档位置**：`05` §5.5 L554、L564–571，§5.6.1 L624–631，§5.6.5 L1037–1057，§5.8 L1152，L88、L95、L1235；`03` L73、L101、L139；`15` ADR-129 L941–943；`14` G35c(g)(k)、C32。
- **期望的回答形态**：
  - 只由 `isCompacting` 引起的宽限失败：等到 `compaction_end` 后重做宽限确认，而不是等 `agent_settled`。增加契约测试。
  - settle 表加一行：“没有有效 submit，且 nudge 守卫不成立” → 直接 `paused(idle_without_submit)`。
  - ADR-129 的断言改为：“Tower 的陈述只以 `tower.*` custom message 或带 Tower 标记行的 user 消息出现，Trace 一律标‘Tower 注入’；提醒只经 `agent_before_settle`”。统一 `03` L139 与 `05` L1152 的返工注入方式。
  - 在 §5.6.1 加一行“Host → 扩展（待投递消息）”：例如 `pending-messages.json`，在 `turn_end`/`tool_call` 时检查，用 `details.key` 去重。

### D6 系统架构与可靠性

**R15-D6-01｜次要**

- **问题**：
  1. **macOS 每 Run 进程组怎样建立没有定义。**
     - ADR-128 规定“每个 Run 启动时持久化其 Agent 进程组 id（每 Run 一行）……覆盖尚未满 5 s、未单独持久化的组内进程”（`06` L187，DDL L575，`10` L263）。
     - 但 Pi 自带的 bash 每次调用都 `detached`（即 `setsid`，见文首核对），每条命令自成一个会话和进程组。Node 的 `child_process` 也无法把子进程放进一个已有的进程组。
     - Tower 的 `createSandboxedBashOperations`（`05` L340）没有说明它怎样让一个 Run 的全部命令属于同一组：是常驻的组长 helper，还是每次调用各记一行？
     - 若沿用 Pi 的做法，一个 Run 有 N 个组，“每 Run 一行”覆盖不到。若不 `detached`，命令会留在 Host 自己的进程组里，按组终止会波及 Host。
  2. **I2 的 Projector 断言会误报合法转移。** `06` L255 要求 `in_review`/`accepted` → `verifying` 必须引用 rebase、合并队列、`keep`/`hand_back`/`bring_back` 或 `agent_bg`。但 `retry_verify`、`s0.grant`、修订验收标准（`03` L59–60、§3.4.5）也会产生这条转移，按现行断言都会被判为 bug。
  3. **`settling` 阶段的序列位置没有持久化。** `keep`/`revert` 之后“回到 settle 序列的下一步”（`06` L841），但下一步是第几步没有写入 `externalChange`，重启之后无法判定。由于归因表第 2 行的限制，`settling` 中只有在进程树已经清空之后才可能检测到外部写入，所以下一步其实可以唯一确定为：`agent_bg_done` → I4 → `claimed`。应当写明。
- **为什么重要**：第 1 项是第 14 轮 R14-D6-01 修复所依赖的机制；第 2 项是 `03` §3.3 要求断言的不变量，误报会让正确的实现被判为违例。
- **文档位置**：`06` §6.1.10 L187、§6.2.3 L255、§6.3 L575、§6.4.3 L841；`10` §10.3.1 L228、L263；`05` §5.3 L338–345；`13` L320。
- **期望的回答形态**：
  - 在 `05` §5.3 写明沙箱 bash 的进程组策略。可以是每 Run 一个组长 helper，以 `posix_spawn` 的 `POSIX_SPAWN_SETPGROUP` 让命令进入同一组；也可以是每次调用持久化一行 `pgid`（只写入，Run 结束时删除），并修正 DDL 与 `13` 的预算。
  - I2 断言限定为“由指纹变化触发的转移”。
  - 在 `10` L237 写明 `settling` 中检测到外部写入只发生在进程树清空之后，解除后执行“`agent_bg_done` → I4 → `claimed`”。

### D11 安全与自主度

**R15-D11-01｜次要**（ADR-131 的 `user_config` 规则）

- **问题**：
  - `user_config` 包含“主目录下名字以 `.` 开头的顶层文件与目录”（`16` L154）。点目录**之内**的文件是否属于 `user_config`，仍可两读。

  - lint (x) 增加检查：默认良性条目的类别必须等于按 `16` 规则计算出的类别。

### D13 隔离、git 与并发

**R15-D13-01｜次要**

- **问题**：
  1. **④′ 之后的重新 seal 没有定义。**
     - 在 M1，用户被告知“推送与开 PR 由你自己完成”（`04` L523、L1217）。他们很可能在 `tower/<goal>` 分支上追加提交、推送、开 PR。
     - 同时 `accepted` 中的 `keep`、交还与 I2 都会让 Goal 离开 `accepted`，再次验收时会重做 seal。
     - seal 写入用户仓库的命令是 `git fetch <影子> refs/tower/<goalId>/seal/<n>:refs/heads/<prefix>/…`（`10` L428），没有 `+`，非快进时会失败。分支已被用户推送或追加提交时应当怎样（覆盖、改名、提示），没有定义。M2 有 `--force-with-lease`（`10` L875），M1 没有对应规则。
     - ④′ 把这条路径变成了 M1 的常态。
  2. **`:(exclude)` 只重试一次。**
     - git 的 `add` 在第一个非法路径处就失败（`10` L94；G26d：“重试仍失败时按基础设施错误处理”）。
     - 卫星中有两个或更多会被 `protectHFS/NTFS` 拒绝的条目时，检查点与 pin 会持续失败。`protectNTFS` 拒绝的名字（如 `git~1`、末尾带点或空格的 `.git`）还不在 watcher 的等价规则之内，运行中不会触发 `nested_repo_live`。
     - 后果是 Verified 永远无法产生，而失败被标为“基础设施错误”，不是 `nested_repo`。这属于“Agent 可控内容导致验证拒绝服务、且原因被误标”一类。
- **为什么重要**：第 1 项会在 M1 用户最常见的操作之后出现 git 错误或覆盖用户的提交；第 2 项会让一道 severity 3 闸口退化成不可诊断的故障。
- **文档位置**：`10` §10.1.2 L94，§10.6 L422–428，§10.12 L875–878；`04` §4.6.5 L521–523，F7 L1217；`14` G26d L91。
- **期望的回答形态**：
  - 在 `10` §10.6 写明 M1 的重新 seal：目标分支已存在且不是上一次 seal 时，不覆盖，改写到 `<branch>-v<n>` 并在验收面板提示；或者是上一次 seal 时以 CAS 方式更新。增加用例。
  - `:(exclude)` 改为循环排除，直到成功或达到上限（例如 32 条）。也可以在 `add` 之前用“`10` §10.1.2 的名字规则 ∪ git 的 `verify_path` 规则”预先排除。超过上限时以 `nested_repo` 阻断并列出路径，不标为基础设施错误。G26d 增加两条被拒路径的变体。

### D14 路线图与可验证性

**R15-D14-01｜次要**

- **问题**：

- **是否所有维度为 100：否。**
  - D1、D9、D10、D12、D16 为 100，在这五个维度上没有找到可追问的实质问题。

- **是否还有可追问的问题：有。**
  - **第 14 轮核验**：共 13 条，已解决 5、部分 8、未解决 0；lint 全部通过，U1、U2 已关闭。
  - **本轮追问**：新增与残留共 **10** 条。
    - 阻断 0；
    - **重要 2**：R15-D4-01、R15-D4-02；
    - 次要 8：R15-D5-01、D6-01、D7-01、D8-01、D11-01、D13-01、D14-01、D15-01。

- **设计是否完成：否。**
  - 两个重要项都出在 ADR-128 新写的通用出口规则上，实现时会直接表现为两类错误：一是出现没有原因的 `paused`，或者与 pin 不同的树被送进评审；二是撤销后循环暂停，并误撤 Agent 的工作。
  - 两项都可以用一段设计规则关闭：一个持久的继续目标，加上“剩余差异只看 E”。
  - 关闭之前，不宜开工 Supervisor 中 `external_change` 的出口与暂停叠加部分。其余次要项多为接线、用例与措辞问题，范围有限。
- **下一轮建议按以下顺序修订**：
  1. 引入持久的暂停继续目标，统一“全部原因解除后”的唯一转移，规定 `pendingVerify` 与 `override_sentinel`/`s0.*`/运行类原因出口的优先次序，修正 `take_external`、放弃改动、`nested_repo_live` 自动解除三处（R15-D4-01）；
