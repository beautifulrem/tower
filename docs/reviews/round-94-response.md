3. 在已有的唯一定义处加至多一条守卫、一行或一个字段。

**本轮的取向**：九条都是 ADR-221 新文字的边角。每条都先找可以复用的已有机制：

- 文件工具的访问仍在访问那一刻由 S2 判定，合并启动不改变这一点；
- 硬底线、密钥路径表与上下文文件名的写拒绝不变；

- 观察器删除前校验路径，校验不过的不删除。

## R94-D5-01（次要）：辅助进程规格的三处余项

**唯一定义**：`11` §11.3.1 使用时强制（L160）。
- **(1) 反复失败**：改弱为真——“M1 不另行检测反复失败：每次失败只返回一个错误结果，与 Pi 自己的文件工具报错相同；`07` §7.7.1 的 S1 只看 bash 命令的退出码，不覆盖文件工具”。没有把 S1 扩到文件工具。
- **(2) 写入中途失败**：
  - 写入在进程启动之后失败时（超时、崩溃、回复不合规；Host 崩溃时正在写的进程读到标准输入的结束，写完已收到的部分后退出，观察 1），工具结果另写 “文件可能已部分写入，请重新读取后再改”；
  - 超时时杀的是该进程所在的进程组，等它们都退出。
  - **没有采用临时文件加改名**（指示的首选），理由见 “偏离与未决”。
- **(3) S0**：S0 下没有辅助进程，同一 `operations` 在 Host 中以 Node 的 `fs` 执行：
  - 16 MB 上限照样适用（读取前按文件大小、写入按内容长度判定，文字相同）；
  - 10 s 超时不适用（进程内的文件调用无法以杀进程中止，与 Pi 自己的内置工具相同）。
  - `13` L173 的 “≤ 16 MB” 因此在 S0 下同样为真。

**同步**：`05` 骨架注释（L386、L388）；`00` §0.5.1（S0 同样不读写超过 16 MB 的文件、写入中途失败时可能部分写入）；`16` §16.2.8（L897，S0 的适用范围、回填依据由 E7 改为 E6）；C42 (g) 补 “写到一半被杀时的文字” 与 S0 下 17 MB 失败。

## R94-D6-01（次要）：③ 的重启路径与卫星丢失一行的顺序

`06` §6.1.6 卫星丢失一行（L139）的排除条件补一条：
- `human_checkout.syncState='syncing'` 的 Goal 不触发本行。重启时先由下方人工编辑检出一行续写，续写因卫星已不在而失败时，按 §6.4.3 `inspect.bring_back` 行的 ③ 转入重建。
- 运行时，③ 持 `wtLock` 期间自己的改名产生的文件系统事件不触发本行；其事务提交之后按提交后的状态重新判定，这时已置 `satellite_rebuilding=1`，本行本就不触发。

所以同一次崩溃只有一种恢复结果：转入写回失败与重建。情形 E 不会先于续写重建，带回时也不会撞 `goals` 的 CHECK。

## R94-D10-01（次要）：辅助进程没有开销预算

**先减少启动**（`11` §11.3.1，L160）：
- **读取一次**：`access` 时由一个 `/bin/sh` 先 `test -e`、再 `test -r`（`edit` 另加 `test -w`），然后 `exec /bin/cat` 交回整份内容。同一次调用随后的 `detectImageMimeType` 与 `readFile` 直接用这份内容（调用结束或中止时丢弃），不再启动进程。
- **写入一次**：`mkdir` 只记下目录，由写入的同一个 `/bin/sh` 先 `mkdir -p` 再经重定向写入。
- 一次 `read` 一次启动、`write` 一次、`edit` 两次（原为三、两、三）。`head -c 4100` 不再需要：图像类型由 Host 对已交回内容的前 4100 字节判定。
- 访问仍在该进程打开文件的那一刻由 S2 判定，合并不改变使用时强制。

**再加预算**（仿照 git 垫片一行）：
- `13` §13.11.1 新增一行（L320），`16` §16.2.7 登记（L889）：
  - 单次启动的额外开销 p95 ≤ 30 ms（⚫）；
  - SP6a A3 另测一项回填：以同一包装读取卫星中 4 KB 文件 200 次的 p95，属测量、不是闸门；
  - 超过 60 ms 时回退为同一批并行调用中同时等待启动的读取共用一次启动。
- `16` §16.2.8 的回填依据由 E7（分类器语料，测不到这一项）改为 E6。

## R94-D11-01（次要，本轮分量最重）：必然拒绝使文件工具读取凭据只剩 chip

**决定**：读取凭据不论经文件工具还是 bash，都适用同一条规则。

**唯一定义**：`11` §11.3.1 “S2 必然拒绝的访问不询问”（L162）加一条例外，**读取凭据不在本条之内**：
- **范围**：读取一侧命中密钥路径表、且写入一侧（若有）不落在拒绝范围的文件工具调用。
- **处理**：
  - 不带 `hardFloor`，照常归 `secrets.access`，按自主度矩阵询问，与 bash 读取凭据的命令出同一张单向门审批卡；
  - S2 下这张卡（不论来自哪个工具）写明 “S2 下批准也不会让沙箱允许这次读取（M1）”；
  - 人拒绝时不发生访问；批准时 S2 照常拒绝，按 “经批准的目标” 只记 severity 1。
- **效果**：Agent 读取凭据的尝试不论经哪个工具，都以同一张卡告知人，ADR-125 的信号不因工具而变弱。
- **不变**：上下文文件名的写入、用户主检出的读取等其他必然拒绝照旧 forbid。

**没有采用的方案**：评审建议的 “forbid 时另记 severity 2 sentinel”。那会让 bash 与文件工具对同一种尝试给出两种告知形态（卡片与哨兵），与 “一条规则” 相反。

**同步**：
- `04` §4.10.2（L1133）：“文件工具与 bash 出同一张卡”，S2 下卡上的文字；文件工具的其他必然拒绝不出卡（观察 14）；
- `00` §0.5.1（L104）：读取凭据除外，与 bash 相同出卡；
- C42 (f)：`~/.aws/credentials` 夹具移出 forbid 一组，改为出卡、拒绝时不访问、批准时读取失败且只记 severity 1；
- G46 `~/.aws` 一组：`read` 与 `cat` 出同一张卡，拒绝 `read`、批准 `cat`。

## R94-D11-02（次要）：“经批准的目标” 的匹配口径

**唯一定义**：`11` §11.6.2 “经批准的目标”（L372）补 “匹配口径”：
- 所列路径取批准时求出的字面与 `realpath` 两种形式（与 §11.3.1 比较的规范形式相同）；
- 与 `target` 按 `16` §16.1.6 的同一规范化写法比较，任一形式相等即算；
- **只按相等、不按包含**：所列为目录时只覆盖对该目录本身的拒绝，其下文件的拒绝照常按类别分级。一次所列范围很宽的批准因此不会压低其中的凭据信号。

**G46**：`~/.aws` 链接组的期望写明 “所列路径的 `realpath` 与 `target` 相等”，因此只有一条 severity 1 的提示。

另把 “这一条实际只作用于 bash” 改为真：文件工具中，S2 必然拒绝而仍出审批卡的只有读取凭据；判定误为允许或分类之后被改向时，其他文件工具调用同样可能批准后被拒绝，同样适用本条（观察 4）。

## R94-D12-02（次要）：观察器只删除超过 1 MB 的全文文件

**唯一定义**：`07` §7.2.2 `fullOutput` 注释（L82 起）。
- **全文的来源**：Pi 的全文文件存在时取它，否则取 `output` 或错误文本。
- **删除的路径**：
  - 取 `details.fullOutputPath`（截断的每种情形都有）；
  - 超时、中止与无退出码时工具抛错、没有 `details`，只取 Pi 附在错误文本末尾、状态行之前的 “Full output: <path>”；

## §5 观察

1. **按次启动的进程身份**：Host 崩溃时正在写的进程读到标准输入的结束、写完已收到的部分后退出。并入 R94-D5-01 (2) 的同一句：窗口同样至多一次写入，文字相同。
2. **`/bin/test` 与错误码**：`11` §11.3.1 写明先 `test -e`，再 `test -r`（`edit` 另加 `-w`），分别对应 `ENOENT` 与 `EACCES`；`cat` 被沙箱拒绝同样对应 `EACCES`。C42 (g) 断言这两种错误码。
3. **`read` 中止后的辅助进程**：`11` §11.3.1 补 “`read` 在中止时立即返回（`read.ts:116-119`），它的辅助进程只读，由 10 s 超时收回”。
4. **必然拒绝的路径数据与基础档**：
   - `11` §11.3.1 要求同一份路径数据显式包含 Seatbelt 基础档允许读取的系统路径，`/usr/include` 一类因此不被误判；
   - 如实写出 `read` 的名字变体取最严格者时，一个不会被打开的变体落在拒绝范围同样会挡掉一次本可成功的读取；
   - §11.6.2 的 “实际只作用于 bash” 改为真（见 R94-D11-02）。
5. **③ 与 ① 的两个失败分支**（`06` L914，`10` L256）：
   - ③ 的改名本身失败时不置标记、不重建，只生成 ④ 的条目，并写明工作目录未恢复；
   - ① 的 `renameat` 遇到原路径已存在时，旁路目录按 §10.2 改名保留并列出，条目不写 “重新建立的”。§10.2 “Tower 自动改名保留” 由两处改为三处，L254 改为 “所列的几处”，不再写数目；
   - 工作目录与 gitdir 用改名之前取一次的同一时间。
6. **交还预算的措辞**：`13` §13.11.1 人工编辑检出一行（L331）改为 “交还与检验带回：两次求树（求 T1 与删除前比较；第二次沿用同一临时索引的 stat 缓存，只重新哈希变过的文件）+ 逐文件复制”。
7. **S0 下删除全文文件**：同样删除，如实写出提示所指的文件随之不在；删除前的路径校验见 R94-D12-02。
8. **① 失败后 T1 的可达性**：条目写 “你的改动未能保留在目录中，此后不可恢复”。并写明原因：③ 清除 `targetTree` 后，T1 只是影子中不被引用的对象，影子 gc 的宽限期（`16` §16.2.6）之后删除。
9. **改名保留的界面与验收**：
   - `04` §4.6.7（L667）：目标页右栏末尾的 `保留的目录` 一行，每个路径一行，只在有这类目录时出现；
   - `10` §10.2：告知它的是该次结果，即交还或带回的成功提示，或 `write_back_failed` 条目；
   - G31 “还原也失败” 一组补断言：旧卫星工作目录与 gitdir 改名为 `<goalId>.kept-<时间>` 并列出。
10. **§10.2 的旧理由**：`10` L254 改为 “改动或已写回、或已被人放弃；中断的删除若发生在删除前比较之前，其中还可能有写回期间又保存的改动——它不被删除，移到一边之后仍在 `.kept-` 目录中，不丢失”。交还侧没有加重启比较：残留的 H 不会被删除，结果同样不丢数据。

## 偏离与未决

- **R94-D5-01 (2) 没有采用 “写临时文件再改名”**（指示的首选），取 “如实写出”。原因有三：
  - 改名会把符号链接与硬链接换成普通文件。Pi 的 `fs.writeFile` 经链接写到目标，改名则替换链接本身，语义变了；
  - 改名会丢掉文件原有的权限位，例如脚本的可执行位。要保留就得在同一进程中先读取再设置，又多一处平台差异；
  - 被杀时临时文件会留在卫星中，进入下一个检查点的 diff。
  - Pi 自己的 `fs.writeFile` 同样不原子。如实写出的代价只是工具结果多一句，而且写入的是卫星中 Agent 自己的文件，有检查点与验证兜底。
- **R94-D11-01 选了 “出卡” 而不是评审的 “另记 severity 2 sentinel”**：与指示一致，取一条同时适用于 bash 与文件工具的规则。
  - 代价：S2 下这张卡的批准不起作用，Agent 在等卡期间被阻塞（`blocked_guard`，默认 30 分钟后拒绝）。这与 bash 读取凭据的现状相同。卡片如实写明批准不会使沙箱允许，人通常选拒绝。
  - 其他必然拒绝（上下文文件名的写入、用户主检出的读取等）仍直接 forbid，信号仍为 chip（这是 ADR-221 之前就有的设计）。
- **R94-D10-01 的取值是假设值**（p95 ≤ 30 ms、回退阈值 60 ms，⚫），由 SP6a A3 回填。回退（同一批同时等待的读取共用一次启动）只在实测超出时实现，不计入本轮工时。
- **R94-D5-01 (1) 没有给文件工具加检测器**：M1 中反复失败的文件工具调用只靠 Agent 自己看到错误结果。S2–S4 推迟到 M2，届时 S3（无新事实）与 S4（烧 token 不动 diff）会覆盖这一类。
- **§10.2 “Tower 自动改名保留” 由两处变为三处**（观察 5 的 ① 分支）：增加的一处只在 ① 物化完毕时原路径已被占用时出现，选择宁可多留，不覆盖。
- **排期**：估计按真实实现计；M1 维持 38 周，各线余量为正；桌面与设计两线的余量合计降到 0.40，已如实写出后续的选择点。
- **未决**：无。
