## 1. 总评

ADR-163 把 R37 的三条重要项基本修好：
- `not_run` 不再算作失败，`sentinel_high` 可以到达；
- 冻结改为单一闸口、整机范围、原子完成；
- 收尾含 teardown，崩溃恢复有了次序。

排期算术全部成立（WBS 121.82，38 周）。

把机密标准放回整个系统核对后，发现两条此前没有触及的重要缺口：
- **合同试运行**是 `verify()` 之外的另一条执行带机密标准的路径，没有规则；
- **密钥库条目**没有实体、命令、界面，也没有“可注入范围”的不变式。目前模型密钥与工具令牌在名义上可被标准按名称注入。

另有七条次要项。

### D11 安全与自主度

**R38-D11-01｜重要**（合同试运行是 `verify()` 之外执行带机密标准的路径，没有任何机密规则）

- **问题**：
  1. **路径存在，而且常用**：
     - `exec` 标准可以在 base 上“试运行”（`03` L125；`04` L1065-1071、L1090）；
     - 快速路径**自动**在后台试运行（`04` L1133、L1306）；
     - 命令是 `contract.trial_criterion` → `verify.requested{trial:true}`（`06` L846）。
  2. **机密阶段的唯一定义不覆盖它**：
     - 机密阶段只定义在 `verify(goal, pin)` 之内（`07` L362-370、L454-483）；
     - 等待、冻结、串行与 10 分钟 Needs-You 都以 Goal 处于 `claimed`/`verifying` 为前提（“Goal 保持 `verifying`”，`07` L368、`11` L441）；
     - `VerifyTrigger`（`07` L373-380）中没有 `trial`；
     - `02` L266 只写了“只在没有其他 Agent 活动时运行”，没有执行机制。
     - 试运行发生在 `draft`/`shaping`，此时本 Goal 自己的 Shaping Run 就是 Agent 活动，其他 Goal 通常也在运行。
  3. **两种自然的实现，结果相反**：
     - **按 `env` 注入**：违反 T33b 的不变式“机密在环境中期间没有其他 Agent 活动”（`11` L419），而且没有人作出接受风险的决定。危害类别与 R35–R37 相同：跨 Goal 的机密暴露；
     - **不注入**：带机密的测试在 base 上因缺少机密而失败，被显示为 `✓ 红灯，可证明完成`（`04` L1068 一类）。这是一条与事实不符的 Fact。
  4. **合同尚未批准**：塑形中的标准命令与 `env` 名称可能是 Agent 起草、尚未经人确认的（`04` L1093 的 `┆` 字段）。在这时注入机密，等于在人批准合同之前，就把机密交给 Agent 起草的命令。
- **为什么重要**：
  - 这是与 R36/R37 同一不变式的又一个出口，而且由快速路径自动触发；
  - 实现者照 `07` 写机密阶段，不会想到试运行；照 `04` 写试运行，又找不到机密规则。
- **文档位置**：`03` L125；`04` L1065-1071、L1090、L1093、L1133、L1306；`06` L846；`07` L362-370、L373-380、L454-483；`02` L266；`11` L419、L441；`16`（无 `trial`）。
- **期望的回答形态**：在 `07` §7.4.1 写成唯一定义，二者取一。
  - **(a) 推荐**：试运行**从不注入**机密。带机密的标准行显示 `试运行：未注入机密，结果不作为红灯证据`（中性），不参与“红灯 / 回归保护”的判定。
  - **(b)**：试运行走同一机密阶段（整机判定、冻结、串行）。需要写明：
    - 等待卡片挂在 `draft` Goal 上；
    - 只对人已确认的标准允许试运行（Agent 起草、未经人改动的不允许）。
  - 两种做法都要写明：
    - `VerifyTrigger` 或 `16` 登记 `trial`；
    - G46 增加一组：Goal B 运行中，人对 Goal A 带机密的标准点“试运行”，另一组是快速路径的自动试运行。

**R38-D11-02｜重要**（密钥库条目没有实体、命令与界面；没有“哪些机密可被标准注入”的不变式）

- **问题**：
  1. **只有一句话**：
     - `11` L458 写“条目 = 名称 + 值 + 允许的 Goal/标准”；
     - 但 `02`、`16` 中没有这一实体，也没有字段与写入者；
     - `06` 的命令表中没有新增、删除机密或设定允许范围的命令；
     - `04` §4.15 设置中只有“从 shell 导入到系统钥匙串”（`04` L1254、L1429）。ADR-033 导入的是 provider 凭据与常见工具令牌（`15` L247）。
     - 用户因此**无法在 Tower 中登记**一个 `STRIPE_TEST_KEY` 这样的测试机密，除非它恰好在 shell 环境中、并被导入流程识别。这是 M1 功能“带机密的标准”的前提，却没有入口。
  2. **注入按名称取值，不检查范围**：
     - 验证器“从系统钥匙串取值”（`07` L755），没有任何允许范围检查；
     - 同一个钥匙串中还存放着经 ADR-033 导入的模型提供商密钥与 `GITHUB_TOKEN` 等工具令牌；
     - 标准的 `env` 名称可以由 Shaping Agent 起草（`02` L265）。
     - 没有规则阻止一条标准声明模型提供商密钥或工具令牌的名称。人批准合同时若没注意到这一项，验证器就会把它注入到运行 Agent 所写代码的进程环境中。
     - 这直接违反投递表：模型密钥“不进入任何参数、环境或文件”（`11` L412）。
     - `07` L765-768 的缓解只保护测试文件与模型上下文：被测的非测试代码仍可读取机密（残余为“中”），标准还可以声明网络（`11` L363）。
  3. **缺失或不允许时的去向没有定义**：是合同批准时拒绝，还是验证时记 `verify_env_error`？
- **为什么重要**：
  - 这是一条缺失的不变式。它允许一类后果：高价值凭据（模型密钥、代码托管令牌）经一个由 Agent 起草的合同字段，进入 Agent 可控的进程；
  - 它也是“只有数据、没有命令与界面”的缺口，影响 M1 的可用性。
- **文档位置**：`11` L363、L412、L458；`07` L755、L765-768；`02` L265-266；`04` L1094-1097、L1254、L1429；`06` 命令表；`15` L245-247（ADR-033）；`16`。
- **期望的回答形态**：在 `11` §11.7.0 写为唯一定义。
  - **实体**（`02`/`16`）：
    - 字段：名称；类别（`provider` · `cloud` · `tool_token` · `test_secret`）；允许范围（项目，或项目 + 标准）；写入者只能是人；值只在钥匙串中。
  - **不变式**：
    - 验证器只注入类别为 `test_secret`、且允许范围覆盖本 Goal 所属项目的条目；
    - `provider`、`cloud`、`tool_token` 永不可注入标准。
  - **两个检查点**：
    - 合同批准时：编辑器逐个列出 `env` 名称对应的条目与范围，缺失或不允许时不能批准（或要求先登记）；
    - 验证时：再查一次，不满足 → `verify_env_error{stage:"secrets", detail}`。
  - **命令与界面**：
    - 命令：`secrets.create` / `secrets.delete` / `secrets.set_scope`，仅本机；
    - 界面：设置 → 项目 → “测试机密”。
  - **G46 增加**：
    - 标准声明 provider 密钥的名称 → 不能批准，验证时也不注入；
    - 标准声明一个未登记的名称 → 环境错误。

**R38-D11-03｜次要**（机密输入检查仍按命令枚举，没有覆盖全部人类文本；匹配集未定义）

- **问题**：
  1. **原则与枚举不一致**：
     - 原则是“所有由人输入、会进入模型上下文的文本”（`11` L445，`04` L1105）；
     - 但带 `confirmSecret?` 的命令只有五个（`16` L274）。
  2. **仍会进入上下文、却没有检查的文本**：
     - `goal.resume{note}`（`06` L852）：自带开场，作为 `opening.human` 发送，见 `03` L69；
     - `goal.retry_after_human_change{note}`（`06` L869）；
     - 合同的意图与草案：`goal.create.intent`、`contract.edit_draft`、`contract.amend.amendmentNote`。合同会交给 Agent；
     - 人手写的记忆：`memory.edit`，会注入上下文。
  3. **匹配集**：“同一机密模式检查（§11.7）”没有写明是否包含 §11.7.1 的**精确匹配集**（密钥库中的值）。人粘贴的恰好是 Tower 已存的值时，精确匹配最可靠。熵规则是否适用于人输入，也没有写。
- **为什么重要**：实现者照 `16` 的命令列表实现，会漏掉 `resume` 的 note，而这是暂停后最常见的输入框。危害由人发起，因此为次要。
- **文档位置**：`11` L445；`04` L1105；`06` L852、L869、L880-893；`03` L69；`16` L274。
- **期望的回答形态**：
  - `16` 改为按“该字段是否会进入模型上下文”列全，并补上上述四处；
  - 匹配集写为“精确匹配集 + 模式；熵规则不用于人输入”，以免误报；
  - G46(af) 增加 `resume` note 一组。

**R38-D11-04｜次要**（钥匙串查找拒绝扩展到验证器后，A8 没有回退；由拒绝导致的验证失败会被归因给 Agent）

- **问题**：
  - `11` L336 把拒绝扩展到验证器与检验检出。A8（`14` L58）的期望只写“被拒绝”，没有写拒绝破坏常用工具或测试时怎么取舍（R37-D11-02 第 3 点）；
  - 在验证器中，被测代码或测试运行器经 Security 框架访问钥匙串而被拒绝时，表现为标准失败。照 `decide()` 的失败路径，这会被计为 Agent 失败并自动返工，与 ADR-037“环境问题不返工、不计次数”相悖；
  - G46(w) 没有“验证槽位中的标准读取 Tower 条目”一组。
- **为什么重要**：这是一个由环境引起、却按 Agent 失败处理的误报来源，会消耗返工次数与预算。有 SP6a 测量兜底，因此为次要。
- **文档位置**：`11` L336、L376；`14` L58、G46(w)；`07` L1517-1536。
- **期望的回答形态**：
  - A8 写明回退：若拒绝破坏 A3 工作流或常见测试，验证器与检验检出只保留 ACL 与分类，并在 T33b/T18 如实登记；
  - 验证器中的处理：本次运行的沙箱拒绝日志中出现钥匙串服务时，记 `verify_env_error{stage:"sandbox", detail:"keychain_denied"}`，不记 `fail`；
  - G46(w) 增加验证槽位一组。

**R38-D11-05｜次要**（机密阶段期间仍存活的沙箱外代码：不在活动定义中，也不在 T33b 的残余中）

- **问题**：
  - “Agent 活动”排除了 Engine Host（`11` L420）。但 Host 只在 Goal 进入 `in_review` 或 `paused` 超过 5 分钟时才退出（`06` L166）；
  - 因此机密阶段的持有者（处于 `verifying`）自己的 Host，以及其他 `claimed`/`verifying` 或刚暂停的 Goal 的 Host，在整个机密阶段中都存活，连同 Host 派生的 MCP stdio 服务器与用户扩展的子进程；
  - 这些代码在沙箱外、以用户权限运行（`11` §11.8.2）。它们按 Agent 的工具调用启动的进程不经 Tower 的 `exec`，不在 Run 的进程树与令牌集合中（`07` L352；Pi `stdio.ts:94`），settle 时不会被终止，也不会进入 `bg_process_survived`；
  - T33b（`11` L626）把残余只列为“用户自己的其他进程”与 ADR-158 的窗口，评为“低”。这与 T26/T28 对“加载了沙箱外工具”评为“中”的口径不一致。
- **为什么重要**：评级与实际残余不符。需要用户配置了能执行命令的沙箱外工具，因此为次要。
- **文档位置**：`11` L420、L626、§11.8.2、T26、T28；`06` L166；`07` L352。
- **期望的回答形态**：二者取一。
  - 机密阶段开始前，令 `claimed`/`verifying` 的 Goal 的 Host 退出（settle 后不再需要 Host）；
  - 或在 T33b 的残余中登记“沙箱外工具（MCP 服务器、用户扩展）及其派生进程”，并按 T26 分级：加载了此类工具时为“中”。

### D6 系统架构与可靠性

**R38-D6-01｜次要**（跳过“无活动”判定时取槽位的规则；R37 要求的两组用例）

- **问题**：
  1. **“必有空闲槽位”只在判定不被跳过时成立**：
     - 补记写“判定成立时整机没有其他验证在运行，该项目的槽位池必然有空闲槽位”（`07` L365，`11` L433，`16` L505，`15` L1525）；
     - 但 `run_now`（`07` L367、L458）与 `secretMutex.enabled=false`（L459）都会**跳过**判定。此时本项目池可能全满：重项目的 c 为 1（`07` L963-968）；
     - `secretPhaseGate` 在这种情况下怎样取槽位没有定义。在冻结设置之前，其他排队的普通验证仍经 `startAgentActivity` 正常启动，并按 `07` L1014 的优先级（表中没有机密阶段）先取到空出的槽位。`run_now` 因此可能一直取不到槽位，与 G46(h) 的期望“标准立即运行”不符。
  2. **用例**：R37 期望回答中的两组没有加入 G46：
     - 同一次槽位释放同时唤醒一个普通验证与一个等待中的机密阶段。这正是单写者原子性要证伪的场景；
     - 机密阶段期间某 Goal 的 lockfile 变化触发预热。这是“预热也经闸口”的唯一证据。
- **为什么重要**：这是一个未定义的次序，只影响活性，不影响机密安全（冻结仍在取得槽位时设置），因此为次要。
- **文档位置**：`07` L365、L367、L455-462、L963-968、L1014；`11` L433、L443；`15` L1525；`14` G46(h)(u)。
- **期望的回答形态**：
  - 写明：判定被跳过时，机密阶段预留本项目池中下一个空出的槽位（优先于一切排队验证，不抢占），取得时设置冻结；
  - `07` L1014 加入机密阶段；
  - G46(h) 第二组改为“在下一个空闲槽位开始”；
  - 补上上述两组用例。

### D7 诚实与验证

**R38-D7-01｜次要**（`plainFailed` 的范围；`not_run.reason` 与实际去向可能不符）

- **问题**：
  - `07` L442 仍是 `plainTodo.some(...)`，只看本次实际运行的不带机密的标准；
  - 漏掉的有：
    - 同指纹缓存命中的失败：缓存只排除含 flake 的结果与 `not_run`，见 `07` L912，所以失败结果会被缓存；
    - 无关路径携带的结果；
    - artifact 标准的失败（L393）。
  - **后果一**：结局已定（`outcomeOf` 必为 `fail`）时，仍然进入机密阶段，整机冻结可达 10 分钟加各标准超时之和。
  - **后果二**：缓存或 artifact 的失败与阻断哨兵并存时，`not_run` 记为 `blocked_by_sentinel`，界面显示 `因阻断哨兵未运行`。但 `decide()` 先判 `fail`，走返工。记录的原因与实际去向不符。
- **为什么重要**：违反 Fact 语法（原因字段与事实不符），并造成无谓的整机冻结。不影响机密安全，因此为次要。
- **文档位置**：`07` L393、L402、L442-448、L912、L1517；`12` L378；`14` G46(t)(y)。
- **期望的回答形态**：
  - `plainFailed` = 该 pin 上全部不带机密的机器标准（含缓存命中、携带与 artifact）的最新结果中有任一未通过；
  - 失败与哨兵并存时，原因记为 `other_criteria_failed`（失败优先）；
  - G46(t) 增加“一条缓存命中的失败”一组。

### D10 性能

**R38-D10-01｜次要**（冻结上限不是上界；超过准备时限时的处理）

- **问题**：
  1. **公式漏项**：
     - `13` L302 写明冻结“从获取槽位时起……经终止槽位进程与 teardown，到释放槽位为止”；
     - 上限却只写 `verify.slotPrepareTimeoutMin` + Σ 标准超时（`07` L368，`11` L439，`16` L507）。
     - 冻结期间同一槽位里还会发生：
       - 终止宽限 10 s（`07` L353）；
       - teardown，包括 `docker compose down -v` 与服务清理；
       - ADR-054 的重跑一次，以及没有历史时在 base 上的对照运行（`07` L834-844）；
       - flake 的 pin 重跑至多 2 次，加上**在同一槽位检出 base** 并对每个用例重复至多 5 次（`07` L853-865）。
     - 最坏情况超过所写上限的两倍。`13` 的承诺因此不可证伪。
  2. **超时后的处理**：
     - 超过 `slotPrepareTimeoutMin` 时怎样处理没有写；
     - 只读 depcache 未命中时，是在冻结中安装，还是记环境错误，也没有写（R37-D6-02 第 2 点）。
- **为什么重要**：整机冻结阻塞所有 Goal，它的上界是 `13` 的一条预算。
- **文档位置**：`07` L353、L368、L464、L468、L834-845、L853-871；`11` L439；`13` L302；`16` L507。
- **期望的回答形态**：二者取一。
  - 把上限写全：准备时限 + Σ(标准超时 × (1 + 重跑次数)) + base 确认预算 + 终止宽限 + teardown 时限；
  - 或者规定机密阶段内不做 base 确认与对照运行，结果记为有保留，使原公式成立。
  - 两种做法都要写明：
    - 准备超时 → `verify_env_error{stage:"prepare", detail:"secret_phase_prepare_timeout"}`；
    - depcache 未命中 → 记 `verify_env_error{stage:"prepare", detail:"depcache_evicted"}`，不在冻结中安装；
    - G46(u) 断言实测的冻结时长不超过该上限。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D5、D9、D12–D14、D16 为 100，这十个维度上没有可追问的实质问题。
  - D4 99、D6 98、D7 98、D8 98、D10 98、D11 84、D15 98。
- **是否还有可追问的问题：有。** 新增共 **9** 条：阻断 0、**重要 2**、**次要 7**。
  - **第 37 轮核验**：已解决 1，部分 6，未解决 0。各条主体都已落地，残留都并入本轮的次要项。
  - **其他核对**：
    - lint 全部通过；
    - Pi v1.2.0 的相关源码复核成立，ADR-163 没有新增 Pi 依赖；
    - 排期算术全部成立：WBS 121.82、38 周、系统线余量 0.12、增人 33 周。
  - **不扣分的观察**：
    - **带机密标准的失败用例名**（`07` L766-768）：规则 2 称“保证不进入模型上下文”。但用例名可能在运行时由被保护测试从 Agent 可改的非测试模块取得（例如数据驱动的用例表），因此是一个有界的通道。建议对带机密的标准只回送在被保护测试源码中字面出现的用例名，其余改为哈希；或者把规则 2 的措辞改为“有界”。触发条件罕见，不扣分。
    - **`06` L122 与 L124**：在机密阶段中崩溃的 Goal 同时满足两行。两行都会导致机密阶段重跑，结果相同，顺带写明先后即可。
    - **安全线余量** 0.55 与 0.56 是舍入差。
- **设计是否完成：否。**
  - ADR-163 修好了 R37 的主体。
  - 本轮两条重要项都来自**机密标准的边界**，而不是机密阶段本身：
    - 一条是另一个执行入口（试运行）；
    - 一条是注入什么（密钥库条目与可注入范围）。
  - 两者都只需补规则、一个实体、几条命令与用例，不需要新架构。
- **下一轮建议按以下顺序修订**：
  1. **R38-D11-02**：
     - 密钥库条目实体与类别；
     - “只注入登记为测试机密、范围覆盖本项目的条目；provider、cloud、tool_token 永不可注入”的不变式；
     - 批准时与验证时两处检查；
     - 管理命令与设置页；
     - G46 两组。
  2. **R38-D11-01**：试运行对带机密标准的唯一规则（推荐“从不注入，结果不作为红灯证据”），`trial` 登记，G46 两组。
  3. **R38-D6-01**：判定被跳过时预留下一个空槽位；优先级表加入机密阶段；补两组 R37 的用例。
