## 1. 总评

**第 85 轮的 1 条重要、5 条次要条目都已按所问关闭**，其中两条只是部分关闭（核对见 §3）：
- R85-D6-02 的例外列表声称完整，实际不完整；
- R85-D5-01 (a) 只在首次运行那一刻成立。

§5 的 11 条观察都已落地。

**ADR-213 的主体成立**（§3.3）：
- **Host 环境的规则**：唯一定义在 `05` L445，与 `06` L320、`07` L551/L569、`11` L507、`16` §16.8、C40、G46 (bj) 一致。
  - S2 下 Agent 可写的位置是本 Goal 的卫星与 gitdir、`$GS`、`$TMPDIR/tower-<goalId>`（`11` L348），不含主目录、用户 npm 配置、全局前缀与登录 shell `PATH` 中的目录（L348 明写不允许写用户全局缓存）。
  - 规则成立后，Host 与 Supervisor 的全局根查询都只读你自己拥有的位置。
- **回应的偏离**（不做每会话比对）：在 S2 下接受。理由经源码核实成立：Pi 在新会话中重新解析时读的是 Host 进程的 `process.env` 与工作目录，二者都不含 Agent 可写的位置。
  - S0 下前提不成立，但增量后果被已接受的 T23 包含，见观察 1；
  - 已确认的扩展可在进程内改写 `process.env` 或工作目录，属于 §11.8.2 残余中 “用户确认的那段代码的行为”，见观察 2。
- **检查点载荷外置、只追加的两列、`pendingHandBack.returnTo`、删去 “逐项加回”**：唯一定义处与引用处一致，lint (i′)、(d)、(o) 覆盖。

**ADR-213 带出或暴露的新问题**：
- **Supervisor 查询限时 10 s，而 Pi 在 Host 中的同一查询没有时限**（R86-D11-02）：
  - 超时被当作 “没有全局根”，包列为 “未安装：Tower 不安装、不加载”；
  - Host 中的 Pi 却会等到查询成功并加载该包。已确认的清单与实际加载的集合因此不一致，界面上的说法也不实。
- **“经人确认的目录” 没有界面**（R86-D5-01）：
  - Host `PATH` 取 “首次运行时从登录 shell 读到的、经人确认的目录”，但首次运行流程与设置页都没有这一步，也没有显示或重新读取的入口；
  - 所以 R85-D5-01 (a) “与你在终端中运行的 `pi` 相同” 只在首次运行那一刻成立。

**全范围扫描**在 ADR-213 之外新发现：
- **MCP 服务器以卫星为工作目录、在沙箱外启动**（R86-D11-01，重要）：
  - 以包运行器启动的服务器会按工作目录中的项目配置与本地依赖，决定实际执行什么；
  - 卫星内容由 Agent 写。这违反 T4 “Agent 写下的代码不会在后续 Run 中于宿主内或沙箱外执行”，也违反 R85-D11-01 所依据的同一原则。
- **`pending_hand_back` 存在时再次接管**（R86-D4-01）：没有规则，第二次交还会覆盖、或留下第一次交还的意图。
- **重建例外列表不完整**（R86-D6-01）：`sessions`（`runs.session_id` 的外键目标）与 `watermarks` 不由事件承载；`paused(question_timeout)` 所依赖的问题条目在重建后的去向自相矛盾。
- **16 KB 上限只处理了 `checkpoint.created`**（R86-D6-02）：`goal.external_change.detected`、`workspace.paths_restored`、`human_checkout.handed_back` 同样带无上限的路径集合。

- 余量：系统 0.12、Agent 0.22、桌面 0.36、设计 0.61、安全 0.12。

### D11 安全与自主度

**R86-D11-01｜重要**（stdio MCP 服务器以卫星为工作目录在沙箱外启动；包运行器据卫星中 Agent 可写的内容决定执行什么）

- **问题**：
  - **启动的位置**：
    - 内置 MCP 扩展以会话的工作目录（即卫星）启动每个 stdio 服务器：`sessionCwd = ctx.cwd`，经连接传给传输工厂，默认 `cwd = resolve(cwd, config.cwd ?? ".")`（文首 Pi 核实）。
    - Tower 在 SDK 下用自己的 `createTransport`（`05` L433：`new StdioTransport({…, env: {...mcpBaseEnv, ...serverEnv}, inheritEnv: false})`），正文只规定了环境，没有规定 spawn 的 `cwd`。照 Pi 的默认，它仍是卫星。
    - `11` L221 还建议代码智能类 MCP “以卫星为根运行”，G10 的夹具也以 “MCP git 服务器（cwd = 卫星）” 为前提（`14` L72）。
  - **这一步读什么**：
    - 用户的 `mcp.json` 中常见以包运行器启动服务器（`11` L188 的同一类命令：`npx`、`pnpm dlx`、`bunx`、`uvx`）。
    - 这类启动器会按工作目录所在项目的配置文件与本地已安装的依赖，决定实际执行哪一个程序：项目中已有同名依赖时用项目里的，项目级配置还能改变来源与运行方式。
    - 卫星的项目配置与依赖目录都在 S2 写允许之内（`11` L348）。
  - **没有任何一环拦住它**：
    - MCP 服务器的启动不是工具调用，不经门禁（`11` §11.3.4 只管调用）；
    - 清单记录的是 “MCP 命令行以及可执行文件哈希”（`05` L1332），即启动器本身，不是它解析出来要执行的程序；
    - 环境中的 `GIT_CEILING_DIRECTORIES`、`safe.bareRepository` 只挡 git 元数据（T16、T29）；
    - ADR-213 的新规则只约束 Host 进程自身的环境与工作目录（`05` L445）。
  - **后果**：对配置了这类服务器的用户，Agent 在卫星中写下的内容可以在下一次服务器启动时（新的 Run、暂停后的恢复、Host 内的上下文交接、断线重连）在沙箱之外、以你的权限执行，不需要任何人的批准，也不出现在任何确认卡片上。
    - 这正是 T4（`11` L680）“Agent 写下的代码不会在后续 Run 中于宿主内或沙箱外执行” 要排除的一类后果；
    - 也违反 R85-D11-01 所依据的同一原则：Agent 可写的配置不得被沙箱外的进程读取并据此决定执行什么（`11` L358，`07` L551 为验证器立的同一规则）。
  - **与已登记残余的区别**：
    - T16 与 §11.8.2 的残余（`11` L611、L692）说的是已确认的扩展或 MCP 服务器 “自己执行卫星中的文件，例如运行项目脚本或测试”，那属于用户确认的那段代码在被调用时的行为。
    - 这里是 Tower 为启动器选择的工作目录：在服务器自己的代码运行之前，就决定了运行哪份代码。
    - 你在终端中运行 `pi` 时工作目录是你自己的仓库，内容由你信任；在 Tower 中它换成了由 Agent 写的卫星。所以这是 Tower 引入的差异，不是 Pi 的既有风险。
  - 这一问题早于 ADR-213，前 85 轮均未提出。
- **为什么是重要**：照 `05` L433 与 Pi 的默认实现，一个 M1 中常见的配置（以包运行器启动的 MCP 服务器）就能让 Agent 写的代码在沙箱外、无人批准地运行，直接违反 T4 的陈述与 §11.6.2 的原则。只有高风险 Goal 与清单确认之前（`noExtensions:true`，不加载 MCP）不受影响。
- **文档位置**：`05` L433、L445、L1332；`11` L188、L221、L348、L358、L611、L680（T4）、L692（T16）、L705（T29）；`07` L551；`14` L72（G10）。
- **期望的回答形态**：在 `05` §5.3.5 Tower `createTransport` 的唯一定义处写一句，并把 `05` L445 的规则推广到 “Host 启动的沙箱外子进程的工作目录”。二选一：
  - **(a)** stdio 服务器的 spawn `cwd` 不取会话工作目录，取 Tower 拥有、Agent 不可写的目录（例如你的主目录）；`mcp.json` 中写了 `cwd` 的，只接受不在 Agent 可写位置之下的绝对路径。
    - `roots` 仍声明卫星：Pi 的连接单独以会话工作目录声明 `roots`，与传输工厂的 spawn `cwd` 无关，所以代码智能类服务器仍以卫星为根。
    - `11` L221 的建议改为 “以 `roots` 为根”；
  - **(b)** 若保留卫星为工作目录，则在 T16 中把这一情形单列为已知限制（写明触发条件与后果），在清单确认卡片上对以包运行器启动的服务器写明这一后果，并说明为什么不采用 (a)。
  - 另在契约测试（C21 或新的一组）中只写期望：卫星中出现与服务器同名的本地依赖或项目级配置之后，新会话启动的服务器进程的工作目录与实际执行的程序都不变。

**R86-D11-02｜次要**（Supervisor 查询限时 10 s，而 Pi 在 Host 中的同一查询没有时限：超时时 Host 加载清单列为 “未安装” 的包）

- **问题**：
  - `05` L1332：“Supervisor 的这次查询限时 10 s，超时或失败按 ‘没有全局根’ 处理（与 Pi 出错时返回 undefined 相同）”，只能在全局根中找到的包因此列为 “未安装：Tower 不安装、不加载”。`11` L607、`13` L129 同此。
  - 但 Pi 在 Host 中的同一查询是同步的，没有时限（`package-manager.ts:2752-2765`）。它不会因为慢而失败，查询返回后照常求出全局路径并加载该包（`:2151-2158`、`:1322-1333`）。“与 Pi 出错时相同” 只对失败成立，对超时不成立。
  - 加载之后没有任何一步把实际加载的路径与已确认的清单比对：“首次加载后发现的能力” 只比对注册的工具名，且 “只告警，不改变已作出的确认”（`05` L1332，`11` L607）。
  - 于是在包运行器较慢的配置下（`npmCommand` 为包装脚本，或 pnpm 每个包查询一次而 “10 s” 是否按整份清单计没有写明）：
    - 清单持续把这个包列为 “未安装”，从不哈希，内容变化也不会触发重新确认；
    - Host 却在每次会话中加载它；
    - 界面对你说的 “Tower 不加载”（`05` L1332、`00` L99）不实；
    - `11` L609 “标准 / 低风险 Goal 加载已确认清单中的扩展” 也不成立。
  - 你照 “请在你的终端中运行 `pi` 安装” 去做时，终端里 `pi` 找得到它，什么也不会改变，卡片也不会消失。
- **为什么是次要而不是重要**：
  - 被加载的是你自己列在 Pi 设置 `packages` 中、装在你自己全局目录里的包。S2 下 Agent 无法影响它的内容（R85-D11-01 的规则已经保证），所以没有越过沙箱边界。
  - 被破坏的是 “清单 = 实际加载的集合” 与界面说法的真实性，后果有界。
  - 但照字面实现必然出现这种不一致，且不同实现者会各自补救（取消时限、超时即失败、加载后比对），所以列为条目。
- **文档位置**：`00` L99；`05` L1332、L1475（C40）；`11` L607、L609；`13` L129。
- **期望的回答形态**：在 `05` §5.10（唯一定义）写一句，三选一：
  - 查询未在时限内成功时，清单标为 “全局根未知”（不是 “没有全局根”），本次 Host 启动以 `noExtensions:true` 运行，卡片写明 “无法确定全局安装的包（查询超时）”，与真正的 “未安装” 分开；

### D5 Agent 架构与 Pi 集成

**R86-D5-01｜次要**（Host `PATH` “经人确认的目录” 没有界面；取值冻结在首次运行，没有显示与重读入口）

- **问题**：
  - `05` L459：Host 的 `PATH` 是 “首次运行时从登录 shell 读到的 PATH 中、**经人确认**的目录”；L445 的包管理器位置变量同样 “首次运行时从登录 shell 读到”，“之后修改不会自动重新读取”。
  - 但首次运行流程（`04` L1450–L1460）的八步中没有确认目录的一步，设置页（`04` §4.15 引擎组，L1266）也没有显示所用值或重新读取的入口。W16 只计了 “读取”（`14` L235）。“经人确认” 因此没有定义：逐个目录勾选、整体确认，还是不确认，实现者各取其一。
  - 顺序也未写明：全局根查询在第 1 步的清单卡片之前运行，而它依赖这一环境（`05` L1332）。确认必须在第 1 步之前完成，或者第 1 步以未确认的值运行。
  - 取值冻结的后果，比 ADR-209 当时登记的 agentDir 一项大得多：
    - 常见的 Node 版本管理器把带版本号的目录放进 `PATH`。你切换或卸载版本后，Tower 的 Host 仍指向旧目录；
    - 于是 `npmCommand` 找不到或得到另一个全局根，清单把包列为 “未安装”，以 `npx` 启动的 MCP 服务器失败；
    - 而 `00` L99 无条件地写 “与你在终端中运行的 `pi` 找到的相同”，给的补救（在终端运行 `pi` 安装）不会改变任何东西。
  - 回应的 “偏离与未决” 把只读一次列为已知限制，可以接受；但 “经人确认” 这一承诺与没有任何恢复途径，不在那条限制之内。
- **为什么是次要**：不越过安全边界（取值落在 Agent 可写位置之下时不收入，`05` L459）。但一个界面步骤缺失，实现会分叉；对使用版本管理器的用户，R85-D5-01 (a) 要修复的 “恒为未安装、补救无效” 会在一次版本切换后重新出现。
- **文档位置**：`00` L99；`04` L1450–L1460、L1266；`05` L445、L459、L466；`14` L235（W16）；`15` L3526（ADR-209 观察 10）。
- **期望的回答形态**：在 `05` §5.3.6 “首次运行检测”（唯一定义）写明，二选一：
  - 第 1 步之前显示读到的目录与变量，整体确认一次；设置页显示所用值，并提供 “重新读取登录 shell”（同时重读 `PI_CODING_AGENT_DIR`），下一次 Host 启动生效。`04` §4.18.1 第 1 步与设置页各补一行；
  - 或删去 “经人确认”，`00` L99 改为 “与首次运行时你终端中的结果相同；之后修改 `PATH` 需……”，并写明恢复办法。

### D4 领域模型与生命周期

**R86-D4-01｜次要**（`pending_hand_back` 非空时再次接管没有规则）

- **问题**：
  - **可达**：交还时若仍有保留原因，Goal 留在 `paused`，写 `pending_hand_back`（`06` L904，`10` L1012）。`goal.take_over` 接受 `paused(*)`，守卫只看卫星、`human_checkout`、`_human` 路径与 `external_change`（`06` L903），不看 `pending_hand_back`。所以人看到 “交还后仍暂停” 后再次接管，是正常可达的路径。
  - **再次接管时**：`takeover_from = 'paused'`，继续目标保持，`pending_hand_back` 原样保留。没有任何规则说明它在新的接管期间的地位。
  - **第二次交还时**：
    - 选 `take_human`/`keep_both`：覆盖 `pending_hand_back`。`returnTo` 取 “本事务清除之前的 `takeover_from`”，即 `paused`，不写。第一次接管时从 `in_review`/`accepted` 取得的 `returnTo` 丢失，`verifyFrom` 落到 `claimed`。ADR-213 刚为保住这一信息加了字段；
    - 选 `take_external`：“不写 `pending_hand_back`，继续目标不变”（`06` L904，`10` L1014），第一次交还留下的模式因此仍在，由 `onAllReasonsCleared()` 第 1 步优先执行（`03` L73）。若它是 `continue_agent`，就会注入 `tower.handback`，与 `10` L1014–L1015、`03` L100 “`take_external` 之后由继续目标决定去向，不会注入 `tower.handback`” 相矛盾，且执行的是人已经用一次新接管推翻过的意图；
    - `goal.discard_human_edits` 退出第二次接管时同样留下第一次的 `pending_hand_back`。
  - `pending_openings` 中第一次交还的开场仍在，这一点无害，两次开场都如实。
- **为什么是次要**：不丢数据（`returnTo` 丢失偏保守，多走一次评审）；但三处文字（`03` L100、`10` L1014 的 “不会注入”，`06` L904 的覆盖规则）在这一分支上互相冲突，实现者会各自补规则。这一分支早于 ADR-213（自 ADR-134 起）。
- **文档位置**：`02` L182；`03` L73、L100、L104；`06` L480、L903、L904；`10` L1012–L1019、L1031；`16` L45。
- **期望的回答形态**：在 `16` L45（`pendingHandBack` 的唯一定义）加一条，二选一：
  - `goal.take_over` 在同一事务中清除 `pending_hand_back`，并把其中的 `returnTo` 保存为新的 `takeover_from` 的等价值：从 `paused` 接管且 `pending_hand_back.returnTo` 存在时，`takeover_from` 取该值。之后的交还、放弃改动都只按新的接管处理；
  - 或 `goal.take_over` 在 `pending_hand_back` 非空时返回 `E_STATE`，提示先解除保留原因或放弃这次交还的选择。
  - `06` L903 的源状态列同步。

### D6 系统架构与可靠性

**R86-D6-01｜次要**（重建例外 “只有以下三处” 不完整；问题条目的去向自相矛盾）

- **问题**：
  - `06` L221（唯一定义，ADR-213）：“一切写入都经过 `EventLog.append`……可以从 `events` 重建……**例外只有以下三处**”。
  - **列表漏了不由事件承载的表**：
    - `sessions`（`06` L565）：Pi 会话文件与 Run 的 N:1 映射、`parent_session_id`、对账游标 `last_entry_id`。`16` §16.1.14 没有任何 `session.*` 事件，而 `runs.session_id` 是 NOT NULL 的外键（L551）。例外 (2) 让 `runs` 的这一列从旧库沿用，却没有让它指向的行一起沿用。照字面重建，`sessions` 为空，外键失败；或者游标丢失，对账（`06` L1145）从头读 JSONL；
    - `watermarks`（L746）：`watermark.advanced` “不进入 EventLog，只更新 watermarks 表”（`06` L946，`16` L668），与 “一切写入都经过 `EventLog.append`” 直接冲突，重建后全部已读水位归零；
    - `timers`、`engine_outbox` 是运行时状态，同样没有事件。是否属于 “领域表” 没有写，读者无从判断。
  - **问题条目的去向自相矛盾**：
    - 例外 (3) 说 `needs_you` “由各生产者按重建后的状态重新判定生成……随 Run 一起失效的 `question` 与工具审批本就不重建”。
    - 但 `paused(question_timeout)` 中的问题条目不随 Run 失效：“条目保持打开……人之后仍可作答”（`08` L435、L461），而 `goal.resume` 只在 “阻塞问题已作答” 时解除这一原因（`06` L881）。
    - 问题条目的生产者是 Run 中的界面请求，不是按 Goal 状态判定的生产者。重建后没有生产者会重新生成它，`resume` 的守卫因此要么永远不成立，要么空成立。
    - 而它的内容其实在 `engine.ui_request` 事件中（`16` L651），可以重建。
- **为什么是次要**：只在重建与投影迁移时出现，日常路径不受影响。但 R85-D6-02 选择的正是 “列出全部例外”，列表不完整时，实现者会按 “其余都能重建” 去写 `tower doctor --rebuild`。
- **文档位置**：`06` L221、L551、L565、L709、L739、L746、L881、L946、L1145；`08` L435、L461；`16` L651、L668。
- **期望的回答形态**：在 `06` L221 补全：
  - (2) 改为 “`runs` 与 `sessions` 中不由事件承载的行与列”；
  - 写明 `watermarks`、`timers`、`engine_outbox` 是不属于领域表的运行时表，重建时从旧库沿用或清空，各自的后果一句；
  - (3) 写明问题条目由 `engine.ui_request` 与 `needs_you.resolved` 重建（或写明 `question_timeout` 的 Goal 重建后 `resume` 的守卫如何判定）。

**R86-D6-02｜次要**（16 KB 上限只处理了 `checkpoint.created`；另外三个事件带无上限的路径集合）

- **问题**：
  - `13` L247：“单条负载上限 16 KB，超出即视为 bug（CI 断言）”，ADR-213 只为 `checkpoint.created` 写了外置规则（`16` L663），理由是 “这些集合由当时的归因求出，不能重算，所以不截断”。
  - 同一理由同样适用于另外三个事件，它们的载荷都带没有上限的路径集合：
    - `goal.external_change.detected{paths, mixedPaths, …}`（`06` L409，`16` L301、L647）：`goals.external_change` 由它投影（`16` L42），`keep`/`revert` 按其中的 `paths` 处置；
    - `workspace.paths_restored{cp, paths, safety}`（`16` L662）：`restorePaths` 的路径集合（`10` L859）；
    - `human_checkout.handed_back{changed, ignoredCommits, skipped, …}`（`10` L1027）：大的交还会有上千个改动路径。
  - 外部写入一次涉及数百个文件（例如在卫星中运行格式化或生成工具）就会越过 16 KB。照字面实现，生产中触发 CI 断言所称的 “bug”，或者实现者自行截断。截断后 `revert` 只撤销一部分路径，余下的外部写入会进入之后的 pin，违反 “外部写入不经处置不进入检查点或 seal”（`10` L402）。
- **为什么是次要**：与 R85-D6-01 (a) 同类同级。触发需要大的外部写入，但照字面实现必然遇到。
- **文档位置**：`06` L409；`10` L402、L859、L1027；`13` L247；`16` L42、L301、L647、L662、L663。
- **期望的回答形态**：在 `13` §13.9.1 把外置规则写成通则（唯一定义）：任何事件的路径数组字段使载荷超过 16 KB 时，按 `16` §16.1.14 `checkpoint.created` 的同一方式整组外置，以 `{sha256, count}` 代替，Projector 与重建按哈希读回，不截断。列出适用的事件，`16` 各行引用；lint (i′) 的范围随之扩大（§3.1）。

       - `05` L445 “包管理器读取的配置文件是你自己的（如 `~/.npmrc`），Agent 不可写”、L1332 与 `11` L611 “变化只可能来自你自己的改动”，只在 S2 下成立。S0（`11` L330，M1 的回退档位，`14` L200）下 Agent 的代码以你的权限运行。

    7. **已送达评论的 `comment.edit`**（`06` L920）：
       - `body` 或 `timing` 在送达之后修改时是否重新送达没有写；模型看到的仍是旧文本，而界面显示新文本；

    8. **`goal.abandon` 从 `paused` 退出**（`06` L932）：`continuation`、`pending_hand_back`、`pause_reason`、`also_applies`、`external_change` 的清除由 DDL 的 CHECK（L496–L503）强制，只有一种实现。宜在命令行写明，与 `integrated` 出口（`10` §10.12）对称。
    9. **`runs` 两处来源都没有的行**（`06` L221 (2)）：事件与 `runs` 在同一个库中，被重建的库不可用时事件同样不可用，这一分支实际上走不到。若保留，宜写明这时 Goal 同时进入 `paused(engine_crash)`，以及 NOT NULL 列的填充值。

  - 本轮有 **1 条重要条目**，不来自 ADR-213，而来自同一条原则的另一处落点：
    - Host 启动的 stdio MCP 服务器以卫星为工作目录；
    - 以包运行器启动的服务器会按卫星中 Agent 写的项目配置与依赖决定执行什么；
    - 这使 T4 的陈述在一个常见配置下不成立。
    - 修正只需在 Tower 自己的 `createTransport` 中把 spawn 的工作目录与声明的 `roots` 分开。
  - 5 条次要条目分三类：
    - **ADR-213 的连带后果**：R86-D11-02（10 s 时限与 Pi 无时限）、R86-D5-01（“经人确认” 没有界面、冻结值没有重读入口）；
    - **第 85 轮修订的不完整处**：R86-D6-01（重建例外列表）、R86-D6-02（另外三个事件的载荷上限）；
    - **全范围扫描**：R86-D4-01（`pending_hand_back` 非空时再次接管）。

  1. **R86-D11-01**：`createTransport` 的 spawn `cwd` 取 Tower 拥有、Agent 不可写的目录，`roots` 仍为卫星；或单列为已知限制并在确认卡片上写明；契约测试补一组。
