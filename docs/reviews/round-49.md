## 1. 总评

ADR-174 按第 48 轮的期望形态处理了四条问题，主体落地干净：
- **写出前复核**：唯一定义在 `16` L513。`07` `verify()` 改为循环：复核只查清单行；有条目不再 `seeded` 时不写出任何本地文件，回到读取一步，重新读取、重算 `envHash`、重查缓存，槽位保留；重查后全部命中则经 `finally` 释放槽位。“查询键 = 槽位内容 = 记录”在每一轮都成立。`06` L876/L878、`04` L1298 的“此后”照字面成立，G46(ag) 加了排队中 `mark_secret` 一组。
- **重放**：重放列为第五个复制点（`16` L513 两处列举同步），重放包内容加 ⑦ `env.localFiles`（只有路径与哈希），结论分类加“复现条件不同：本地文件 `<路径>` 已变化或缺失”；导出包不含本地文件（`16` L91、`06` L1107）。E13 把这一类单列，不计入成功阈值的分子与分母，与 `07` 一致。
- **项目级通知**：`08` §8.1 写明位置（设置页行 + 侧栏底部设置入口的项目级 `◇`）、送达（`settings` 主题，重新订阅随快照）、消失（事件类按项目级水位，`project.local_files.viewed`，`read` 能力；“无法读取”沿用 ADR-173 的条件）。`06` 命令表、DDL scope、`settings` 行，`16` 远程矩阵，`04` §4.3.2 与 §4.15.1，`12` L326 都已登记。
- **删除 `extraGlobs`**：`07` §7.3.2、§7.4.2、§7.10，`09` L381，`16` 废弃表、lint (d) 一致，没有现行残留。
- **排期**：WBS 121.65、各线、余量、依赖链 19.7、增人 127.44 / 23.53 / 33 周、M1 38 周，全部经脚本复核成立；`14` 与 `15` 的数值一致。

M1 头号安全不变式仍然成立：判定与写出用同一份字节，写出前复核保证 `mark_secret` / `remove` 之后不再有新的写出（在复核与写出确实串行的前提下，见 R49-D6-01），机密与未批准条目不进入 `envHash`，重放不把本地文件带出本机。

沿 ADR-174 新加的落点复查，还有四处**次要**问题，都不丢用户数据：
1. **“同一个 Supervisor 回合”没有定义**：`06` §6.2.1 的 Supervisor 是单个 Node 事件循环，耗时工作放到 worker 或 Verifier Runner。复核之后的写出是异步 I/O，跨过 `await` 时事件循环会处理其他命令。正文没有说明这个“回合”靠什么排斥 `mark_secret` / `remove`，也没有说明它是否在写出期间挡住全部命令（D6）。
2. **重放比对只有一个方向**：比对按原 `env.localFiles` 逐条进行。原验证之后才批准的条目会被重放写进槽位，却不在比对范围内，重放仍可能写“复现”（D7）。
3. **事件类通知在打开设置页时立即消失**：通知的说明只显示在设置页的对应行上，而打开这一页就推进水位。照字面实现，人打开页面时说明随即消失；水位推进是否沿用 §8.10.1 / `16` L603 的“聚焦可见 ≥ 3 s”也没有写（D8）。
4. **两处残留**：`12` L326 仍写“侧栏项目切换处”，这个位置在 `04` 中不存在，主干补充说已统一改掉；`14` L215、W11 行与 `15` L1115 仍写“按条目记最后查看序号”，现行设计是项目级水位（D15）。

### 3.1 ADR-174 的边界检查

| 检查 | 结论 |
|---|---|
| 循环的终止 | ✓ 只有使某个已读入条目不再 `seeded` 的状态转移才会让复核失败：`mark_secret`、`remove`、内容命中写 `content`、取消标记的自动恢复。内容命中与自动恢复之后，条目要重新变为 `seeded` 需要人的决定（`unmark_secret`）。所以每进入一次新的循环，都要消耗一次新的转移，Tower 自身不会造成活锁。正文没有写上限，不扣分（见 §5 观察） |
| 重读后的槽位 | ✓ 重查后全部命中：`try` 内返回，`finally` 执行 `teardown` 与 `release`，槽位此时只做过 `checkout`。部分命中：`todo` 按新的 `local.record` 重算，进入槽位的标准与记录一致 |
| S0、机会式、取消 | ✓ S0 判定在循环之前，以首次 `todo` 为准；授权按 Goal 授予，重读后 `todo` 变化不影响授权。机会式验证的槽位可抢占，被抢占时与原先一样放弃本次尝试。取消路径没有变化 |
| 复核与写出的串行 | ✗ “同一个 Supervisor 回合”没有定义，见 R49-D6-01 |
| 复核覆盖的条目 | △ “读入的每个条目”是否包括 `not_copied` 条目（没有读到字节），字面不确定。两种读法都只影响 `local.record` 中是否还留着一个已被移出清单的 `not_copied` 项，并且都保持查询键、槽位内容与记录一致，不扣分 |
| 重放比对与结论 | ✓ 内容哈希不同、缺失、原为 `not_copied` 三种情形都写“复现条件不同”；E13 单列，与 `07` 一致。<br>✗ 当前多出的 `seeded` 条目不在比对范围内，见 R49-D7-01。<br>△ 原记录为 `not_copied`、重放时仍不可读的条目，两次条件其实相同，却按规则写“已变化或缺失”。这个方向是保守的，不会把条件不同说成复现，不扣分 |

### D6 系统架构与可靠性

**R49-D6-01｜次要**（“同一个 Supervisor 回合”没有定义，与异步写出和事件循环模型之间缺一条机制）

- **问题**：
  - `16` L513、`07` L415 与 ADR-174 写“复核与写出在同一个 Supervisor 回合内完成，与命令层的 `mark_secret` / `remove` 串行（单写者）”。伪代码为 `supervisor.turn(async () => { stillSeeded(...); await slot.seedLocalFiles(local) })`。
  - “Supervisor 回合”与 `supervisor.turn` 在全文只出现在这几处，没有定义。`06` §6.2.1（L199-220）的模型是：整个 Supervisor 在一个 Node 事件循环里串行处理，单个事务目标 p95 < 2 ms，耗时工作放到 git worker 或 Verifier Runner；“单写者”指的是 `EventLog.append` 的事务。
  - 写进槽位是异步 I/O：可能由 Supervisor 直接写文件，也可能经 MessagePort 交给持有槽位池的 Verifier Runner（`06` L20-37）。在 `await` 期间，事件循环会照常处理 CommandBus 上的其他命令。单写者事务本身并不能让复核与写出成为一个不可分的整体。
  - 因此正文有三种读法，都能找到依据：
    - 全局闸门：回合期间 CommandBus 暂停处理一切命令，直到写出完成。这与 L220 的“耗时工作不在 Supervisor 中进行”相冲突，写出期间所有 Goal 的命令都要等待；本地文件没有大小上限，等待时间没有界；
    - 按 Project 的本地文件锁：只让该 Project 的 `project.local_files.*` 写入与内容命中写入在写出期间排队；
    - 只在同一个同步片段内完成“复核并发起写出”，不等待写出完成。这样，在写出完成之前提交的 `mark_secret` 会出现在写出之前。`06` L878 说的“此后不自动播种”是否成立，取决于“此后”从提交算起还是从命令返回算起。
- **为什么是次要**：写出的字节在读取时已按名字、内容与当时的分类判定为非机密，第三种读法的时间窗只有一次小文件写出的长度，不构成新的暴露类别；后果是实现分歧（全局阻塞，或时间承诺不严格），不丢数据。
- **文档位置**：`16` L513（“写出前复核”末句）；`07` L414-420；`06` §6.2.1（L199-220）、L20-37（Verifier Runner 持有槽位池）、L878；`15` ADR-174 第一条第 4 点。
- **期望的回答形态**：在 `16` L513 用一句话写明这个回合的机制，二选一：
  - 一个按 Project 的本地文件闸门：`project.local_files.{remove, mark_secret, unmark_secret}` 的提交与复制服务交来的内容命中写入，在该 Project 有写出进行时排队，等写出完成后再处理；闸门只覆盖“复核 + 写出”，其他命令不受影响。必要时给本地文件一个大小上限，或说明写出时长的量级；
  - 或者明确“复核并发起写出”在一个同步片段内完成，`mark_secret` / `remove` 的效果从其提交起作用于此后**发起**的写出，提交之前已发起的写出照常完成；同时把“与命令串行”改为这一表述。
  - 伪代码中的 `supervisor.turn` 改为所选机制的名字。

### D7 诚实与验证

**R49-D7-01｜次要**（重放比对按原记录单向进行；原验证之后才批准的条目进入槽位却不参与比对）

- **问题**：
  - `07` L488：重放“按同一规则读入、判定、写出 `seeded` 条目，并把当前内容哈希与原验证的 `env.localFiles` **逐条**比对”；有内容哈希不同、缺失或原记录为 `not_copied` 的条目时，结论为“复现条件不同”。
  - 这个比对以原记录为准。可是重放写出的是**当前**全部 `seeded` 条目。原验证之后才 `add` 并 `approve` 的条目，或原验证时是机密、之后取消标记并批准的条目，都会写进重放槽位，却不在原 `env.localFiles` 中，逐条比对时不会被检查。
  - 结果是重放槽位比原验证多出一个文件，结论仍可能写“复现（原 depcache）”。这正是 ADR-174 要防止的情形，只是方向相反：原来缺失的一侧有规则，多出的一侧没有。
  - 重放自己按同一规则读入，也能得到一份与原记录同形的列表（排序后的 `(path, contentHash | "not_copied")`）。两份列表直接比较，就能覆盖两个方向，但正文没有这样要求。
- **为什么是次要**：重放是审计工具，不影响 `decide()`、Verified 或任何状态转移；E13 的样本中这种情形很少。后果是少数情况下把条件不同的重放标为“复现”，以及两种实现给出不同报告。不涉及安全，不丢数据。
- **文档位置**：`07` L483（⑦）、L488；`16` L513（复制点、派生谓词）；`14` E13（L637）、G46(aj)（L133）；`15` ADR-174 第二条。
- **期望的回答形态**，二选一：
  - 比对改为两份列表整体比较：重放的读取结果与原 `env.localFiles` 作为集合比较，任一方向的差异（多出、缺失、哈希不同、原为 `not_copied`）都写“复现条件不同：本地文件 `<路径>` 已变化、缺失或新增”；
  - 或者重放只写出“原记录中出现、且当前仍 `seeded`”的条目，不写出当前多出的条目，比对规则保持不变。
  - G46(aj) 可加一组：原验证之后新批准一个本地文件，再重放，按所选规则断言。

### D8 注意力与交互
