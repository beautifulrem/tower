| 复核项 | 结论 |
|---|---|
| **四档 scope × 存储清单** | • `goal`：`09` §9.12.1 每一行都在 L560 或 L565–569 中有去向，`06` §6.6.1 目录树的每个顶层项也都覆盖，只缺 `recovery/`（见 R68-D12-01）。<br>• `project`：L561 写 “对其下每个 Goal 执行上一行”，另删项目级数据；Project 行本身与 `project_local_files`、`project_benign_targets` 是否删除没有写（见 R68-D12-01）。<br>• `all`：删整个 `~/.tower` 与各 `<wtRoot>` 下 Tower 创建的目录；后者包括 `_human` 与 `_inspect`，见 R68-D13-01。<br>• `memory`：L559 只处理 Pi 会话，而 L484 新写明 Run 目录中有注入的记忆文本，见 R68-D12-01 |

| **seal 段 × `local_merged` 的顺序** | 成立，见 §1 |
| **`prunable` × `locked`** | 成立。未锁定、位置不存在的条目若随后重新出现（如卷重新挂载），其中 rebase 结束时以旧值校验更新分支，会因 Tower 的写入而失败并报错，人的提交仍在 HEAD 的 reflog 中，不丢数据；这与 git 自己的 `prune` 行为一致，可接受 |

| **`integrated` 中 `contract.amend` 的 `E_STATE`** | 成立。`03` L177 与 `06` L870 一致 |

| 取舍 | 判断 |
|---|---|

### D13 隔离、git 与并发

**R68-D13-01｜重要**（`09` §9.12.4 的 “清除一个 Goal” 与 “清除全部” 无条件删除人工编辑检出与检验检出，其中可能有人尚未交还或带回的改动。其他所有删除这两类检出的路径都先询问；ADR-184 的情形下 H 还被明确声明 “不随 Goal 清理”。对非终态 Goal 执行清除时的效果也没有写）

- **问题**：
  - **`09` 的写法**：
    - L560 “清除一个 Goal”：删除 “卫星及其分离 gitdir、`_stores/<goalId>`、`$TMPDIR/tower-<goalId>/`、**人工编辑与检验检出**”。
    - L562 “清除全部”：删除 “各 `<wtRoot>` 下 Tower 创建的目录（卫星、`_gitdirs`、`_verify`、`_inspect`、`_human`、`_stores`）”。
    - 两处都没有条件，也没有询问。
    - 该节的前提是 “清除只删除 **Tower 自己的数据**”（L553）。
  - **其他删除路径的规则**：
    - `10` L442 “删除卫星时”：删除 `_human/<goalId>` 前 “**有未交还改动时先询问**”；ADR-184 的情形 “H 原样保留、不在此列”。
    - `10` L999 与 `06` L923：接管期间卫星缺失且无法重建时放弃，H “原样留在原路径（**不删除，此后不再由 Tower 管理、不随 Goal 清理**）”，确认框与 Goal 页给出路径，人可自行取回改动或删除。
    - `10` L878–880：检验检出删除前比较目录与 T_pin，有被修改的文件时提示 “丢弃 / 作为人工改动带回 / **保留目录，稍后决定**”。
  - **照 `09` 实现的后果**：
    - **删掉只存在于该处的人的改动**：
      - H 中未交还的改动在交还第 8 步之前不进入任何检查点（`10` §10.8.4）；
      - ADR-184 情形下卫星已缺失、无法重建，H 是这些改动的唯一副本；
      - `_human/`、`_inspect/` 又被排除在系统备份之外（`06` L1076），删除后无处找回。
    - **“清除全部” 违反 ADR-184 的承诺**：它整体删除 `<wtRoot>/_human/`，连同 Tower 已声明 “不再管理” 的 H。
    - **对非终态 Goal 没有规则**：`privacy.purge`（`06` L933）与 `09` 都没有状态前提。
      - 对 `paused(human)` 的 Goal 清除，等于不经询问地丢弃人工编辑中的改动；
      - 对 `running` / `verifying` 的 Goal 清除，Engine Host 仍在写正被删除的会话目录，验证槽位正被占用（L560 只写 “仍载有本 Goal 内容的验证槽位立即重置”）；
      - 对宽限期内的 `integrated` Goal 清除，撤销合入所需的卫星与 seal ref 随之消失。
      - 实现者会各自选择 “拒绝”“先中止再清除” 或 “直接删除”。
    - **“清除一个 Project”**（L561）对其下每个 Goal 执行同一行，因此对仍在进行的 Goal 同样适用上述各点。
- **为什么是重要**：
  - 照 `09` 的唯一定义实现，会违反 `10` §10.3.2、§10.8.3、§10.8.4 与 ADR-184 的明文规则，并丢失人的改动。这与第 67 轮 R67-D13-02（清除删除用户拥有的分支）同类：清除被定义为只删 Tower 的数据，实际删到了人的工作现场。
  - 清除是人发起的，但人清除的是 Tower 的记录；确认框（L555）只提到分支，没有提到这些检出中可能有未交还的改动。
  - 触发需要 “检出中有未交还或未带回的改动” 与 “清除” 叠加。ADR-184 的情形较少见，但 `paused(human)` 中清除并不罕见；修法也只需一两句。
- **文档位置**：`09` L553、L555、L560–562；`10` L442、L878–880、L999；`06` L923、L933、L1076；`14` G46(bg)(3) 第十组（L133）。
- **期望的回答形态**：在 `09` §9.12.4 的唯一定义处加一段，`06` `privacy.purge` 行引用：
  - **状态前提**：`goal` 档只接受终态 Goal（`archived` / `abandoned`）；非终态返回 `E_STATE`，界面提示先放弃——放弃已有对未交还改动的询问（`06` L923）。`project` 档对其下的非终态 Goal 同样先要求放弃，或在结果中列出 “未清除：仍在进行”。
  - **人的工作现场**：
    - 人工编辑检出与检验检出中有未交还或被修改的文件时，按 `10` §10.3.2 / §10.8.3 先询问（丢弃 / 保留并列出路径）；
    - ADR-184 保留的 H 与 “保留目录，稍后决定” 的检验目录不在清除范围内，结果列出其路径；
    - “清除全部” 删除 `<wtRoot>` 下的目录时同样跳过这些目录并列出。
  - **测试**：G46 第十组补一组：已放弃 Goal（ADR-184 情形）的 H 中有人的改动，执行 “清除一个 Goal” 与 “清除全部”，期望 H 仍在、结果列出其路径；另一组对 `paused(human)` 的 Goal 清除返回 `E_STATE`。

### D12 记忆与学习（隐私）

**R68-D12-01｜次要**（`09` §9.12.4 要求删除 “数据库中的 Goal 行、账本行”，但 `06` 的 `decisions` 表有无条件的禁止删除与禁止更新触发器，并以外键引用 `goals`，照写无法执行；另有几类数据库内副本与 “彻底忘记一条记忆” 的副本没有列出）

- **问题**：
  - **照写无法执行**：
    - `09` L560：“数据库中的 Goal 行、账本行与 Goal 记忆……事件按 `02` §2.13 墓碑化”。`06` §6.3 的 “账本” 一节（L599 起）就是 `facts`、`claims`、`decisions` 三张表。
    - `06` L645–646：`decisions_no_update` 与 `decisions_no_delete` 两个触发器**无条件** `RAISE(ABORT)`。`02` L491 写 “HumanDecision（不可变）”，`00` L32 写 “不可篡改”。
    - `06` L363 `PRAGMA foreign_keys = ON`，`decisions.goal_id REFERENCES goals(id)`（L630）。所以只要该 Goal 有任何决定（每个 Goal 至少有合同批准一条），Goal 行也删不掉。
    - 同理，`goals.resurrected_from`、`parent_id`（L486、L492）与 `goal_deps`（L509）引用被清除的 Goal 时，删除同样被外键拒绝。
    - `decisions` 中有人写的自由文本：`note`、`reason_detail`、`payload`。例如作答文本、交还说明、放弃原因、`edit_memory` 的记忆文本，以及人在 `E_CONFIRM` 后仍确认发送的 “看起来像机密” 的文字（`06` L913、L918）。
    - 实现者只能二选一：放宽触发器，与 “不可变” 的不变式冲突；或保留这些行与 Goal 行，与 “删除全部副本” 冲突。正文没有给出取舍。G46 第十组的 “清除一个 Goal” 会在实现时暴露这一点，但没有给出答案。
  - **没有列出的数据库内副本**（L560 只写 “Goal 行、账本行”）：
    - `needs_you` 的已解决条目永久保留（`06` L1120），含标题、选项与证据。它们以 `owner_id` 关联 Goal，没有外键，不会随 Goal 行级联。
    - `projections` 快照、`engine_outbox` 中的转向载荷、`comments` 与 `review_units`。后两者有外键，会被迫删除，但正文没有写。
    - `~/.tower/recovery/last-board.json` 与 `journal.jsonl`（`06` L157–158、L1056）。前者含看板投影，后者含安全模式下写入的决定。
    - “清除一个 Project”（L561）没有写 Project 行、`project_checkouts`、`project_local_files`、`project_benign_targets` 与项目级 Fact 的去向。
  - **“彻底忘记一条记忆” 的副本**（L559）：
    - 只处理 Pi 会话 JSONL。而 ADR-195 新写的 §9.12.1 L484 明确 Run 目录中的 “简报、合同、情节等开场文件（含注入的记忆文本）”。`contract.md` 的 `## Memory` 与 `brief.md` 都有原文，该行没有处理，也没有列出。
    - `edit_memory` / `ratify_memory` 决定中的文本同样受上述触发器约束。
    - 数据库日 / 周备份中的副本没有像 “清除一个 Goal” 那样列出。
  - **备份期内的系统备份**：
    - `db-backups/` 默认保留在系统备份中（`06` L1076）。所以清除之后、这些数据库备份过期之前做的每一次系统备份快照，同样含被清除的内容。
    - L566 只写 “**已**备份的副本不随清除删除”。结果中的 “最晚于 <日期> 过期” 容易被读成 “此后不再有副本”。
    - 日 / 周备份也没有由人立即删除的出路，迁移前备份则有（L560）。
- **为什么是次要**：
  - 触发器使冲突以失败告终（清除整笔中止），不会悄悄违反不变式，也不丢人的数据。
  - 留下的副本都在本机。
  - 但清除是隐私承诺的唯一定义，而照写无法执行，两种可行的修法会删掉不同的东西。
- **文档位置**：`09` L484、L491、L559–562、L566；`06` L157–158、L363、L486、L492、L509、L599–646、L649–672、L701、L727、L913、L918、L1056、L1076、L1120；`02` L491、L742；`00` L32。

  - **`decisions` 二选一**：
    - 在与 `retention_guard` 同形的 “清除守卫” 下允许删除该 Goal 的决定，同一事务追加 `privacy.purged`；
    - 或只把其文本列（`note`、`reason_detail`、`payload` 中的人写文本）置为墓碑，保留种类、时间与目标。
    - 两者都在 “HumanDecision 不可变” 处写明 “隐私清除是唯一例外”。
  - **Goal 行二选一**：删除，并说明引用它的 `resurrected_from` 等字段如何处理；或保留只含 id、状态与时间戳的墓碑行。
  - **逐项列出**：`needs_you`、`projections`、`engine_outbox`、`comments`、`review_units`、`recovery/` 的处理；“清除一个 Project” 对 Project 行与项目级表的处理。

  - **备份期**：结果写明 “在这些数据库备份过期之前，系统备份的新快照同样会含有被清除的内容”，并给出 “立即删除这些数据库备份（失去对应的回滚点）” 的选项。

### D15 文档一致性与可执行性

**R68-D15-01｜次要**（两处存储动作以 “隐私清除语义” 或 “等同隐私清除” 定义：“清除早于 N 天的重放包” 与 “Project 被删除”。ADR-195 把 `privacy.purge` 收窄为 `memory` / `goal` / `project` / `all` 四档之后，两者都没有对应的 scope 或命令）

- **问题**：
  - **“清除早于 N 天的重放包”**：
    - `10` L1281 写 “提供‘清除早于 N 天的重放包’（隐私清除语义，删除对应保留 ref）”；`04` L1277 与 `16` L826 把它列为 M1 的设置项，没有 M2 标记。
    - `13` L362 写永久重放包 “只能经隐私清除删除”。
    - 但 `09` §9.12.4 的四档中没有 “按时间删除重放包” 一档，`06` §6.4.3 也没有对应的命令（ADR-195 删去了此前未定义的 `run`、`events` 两档）。
    - 实现者需要自己决定以下几点：
      - 是否同时删除 “随其重放包永久保留” 的验证日志（`09` L485）；
      - 相关事件与 Fact 是否墓碑化；
      - 是否列出数据库备份中的副本；
      - 对仍在进行的 Goal 是否适用。
  - **“Project 被删除”**：
    - `10` L445 写 “先提示‘该 Project 的重放包与镜像保留 ref 将一并删除（**等同** `09` §9.12.4 隐私清除）’，确认后删除镜像”。
    - 读法一：这就是 “清除一个 Project”（删除其下全部 Goal 的会话、影子等）。
    - 读法二：只删除镜像与重放包，Goal 仍在。
    - `06` 的命令表中没有删除 Project 的命令。两种读法删除的东西相差很大。
- **为什么是次要**：
  - 镜像超出上限的提示在 M1 自用期很难出现（`10` L1281 估计每年 0.1–1 GB）；删除 Project 是人发起、需确认的操作。

  - **D12**、**D15**、**D14** 各 1 条：R68-D12-01、R68-D15-01、R68-D14-01。
  - **第 67 轮核验**：8 条全部解决；§5 的 11 条观察全部落地。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 195，(v) 96 条命令，(e) 180 对，(D) 185 个短语，(z′) 35 处，(T) 9 种，(H) 77 个提示键，(J) 135 对，(C) 19 行，(M) 1 个，(B) 1 条，(O) 31 行）。

  - **不扣分的观察**：
    1. **`12` L437 的宽限期例外**：`pause external_change` 一行仍写 “任何状态检测到都先暂停（ADR-122）”。第 67 轮观察 1 只改了 `00` L84 与 `04` L1510。唯一定义（`10` §10.3.1）清楚，按它实现不会出错。建议补 “合入后的 24 小时宽限期除外”。
    2. **镜像中的用户分支副本**：镜像以 `+refs/heads/*:refs/user/heads/*` 获取用户仓库（`10` L309）。只要 Goal 分支仍在用户仓库中（清除从不删除它），被清除 Goal 的 seal 对象在镜像中就仍可达。`09` L560 的 “对象随之不可达” 只对其余对象成立。建议在 L567 “用户仓库” 一条补 “以及 Tower 镜像中这些分支的副本，随分支删除后的下一次镜像 gc 回收”。
    3. **“先执行清理 Tower 引用”**：`10` L711 的清理是全局操作。开启 “保留审计地标” 时，它会删除**所有** Goal 的地标，而不只是要清除的那一个。人为清除一个 Goal 而照 `09` L555 的提示执行它，会顺带删掉其他 Goal 的地标（检查点仍在影子中，不丢数据）。建议在确认框中注明这是全局操作。
    4. **“清除全部” 之后 24 小时内的租约提示**：再次添加仓库时，`06` L183 生成的 Needs-You 写 “该仓库正被另一台机器上的 Tower 使用”，而实际是本机此前的安装；24 小时内也没有 “接管” 选项。清除结果已如实说明后果并给出手动出路，按此不会出错。建议当 `_owner` 中的 `hostname` 与本机相同时改写为 “可能是本机此前的 Tower 安装”，并提供接管。
    5. **`13` L221 docker 一行**：降为 1 个槽位后，该槽位的 docker 实例（1 GB）与 fsmonitor 份额也随之去掉，应为约 10.8 GB，表中为 11.8 GB。偏保守，结论不变。
    6. **`13` L262 “按年 ≤ 10 GB”**：15–40 MB/天 × 365 天为 5.5–14.6 GB；按约 250 个工作日计才是 ≤ 10 GB。建议写明计算口径。
    7. **`04` 中没有隐私清除的入口**：`09` §9.0.1 把清除列为 M1，W17 计入 “隐私清除的范围补全与结果列表”。但 `04` §4.15 设置树的 “数据” 一行与记忆管理器中都没有 “清除一个 Goal / Project / 全部”“彻底忘记” 的入口与确认框说明。建议在 `04` §4.15 “数据” 一行补一项并引用 `09` §9.12.4。
    8. **从 `integrated` 放弃后的字形**：`12` §12.6.1 中 `abandoned` 一律为 `⊘`，看不出 “已合入后放弃”。base 中的改动仍在，该信息只在事件中。建议放弃列表在 `⊘` 旁保留 `◉` 结论标记，与归档列表的做法（L327）相同。
    9. **`09` L244 的注释**：“置顶优先，至多占一半”，而代码允许 `max(60, 82) = 82` 个 token，约占 68%，注释后半句已说明原因。建议把前半句改为 “至多占一半，但总能放下一条上限 80 token 的条目”。
    10. **取舍判断**：见 §3.3。
- **设计是否完成：ADR-195 的主干已收敛；本轮扫描发现清除在两个层面仍未闭合——人的工作现场，以及数据库约束。**
