编号 `R26-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。本轮没有阻断项，也没有重要项，次要 5 条。

### D4 领域模型与生命周期

**R26-D4-01｜次要**（情形 E、启动检查与卫星监视没有排除尚未建成的卫星；ADR-151 的“重试时删除工作目录”会触发它们。R25-D4-01 残留）

- **问题**：
  1. **情形 E 对没有工作目录的 Goal 生效。**
     - 情形 E 的判定是“任意非终态 Goal；操作前检查或文件系统事件发现卫星工作目录或其 gitdir 不存在”（`10` L991）。启动恢复表（`06` L138）与 10 分钟定期检查（`10` L981）用的是同一判据。
     - 首次启动时，在镜像复制、LFS 获取（2a）或检出中途暂停的 Goal，会以 `paused(human)` 停在“卫星不存在或未检出、影子不存在”的状态。G42(v)(x) 正是这种情形。
     - 照字面，下一次启动或定期检查会把它判为“卫星丢失”，并从“影子中最新的检查点或 pin”重建。可是影子不存在，重建失败，于是升级为 `satellite_missing`，生成琥珀色 Needs-You，选项是“从更早的检查点重建 / 放弃”。
     - 结果是一个从未有过工作目录的 Goal：一条不真实的告警；`resume` 解除 `human` 之后，`satellite_missing` 仍然留着；实际出口只剩“放弃”。
  2. **ADR-151 新增的删除会触发情形 E 与外部写入。**
     - “重试时卫星存在而标记缺失 → 删除工作目录后重新检出”（`10` L224）。
     - 卫星监视在“卫星存在的全部非终态”开启（`06` L261，`10` L239），“卫星根目录消失”的事件“先按情形 E 处理”（`10` L491）。
     - 归因表第 1 行的 Tower 写回窗口列出了回退恢复、rebase 写回、交还写回、检验带回与依赖物化（`10` L245），没有列卫星创建、检出与本地文件播种。
     - 因此照字面，G42(y) 的重试本身会被判为卫星丢失。检出与播种在 `ready` 中写卫星，也会被判为来源不明的写入（`10` L257），后者又会“中止准备”（`10` L237）。
  - `10` L155–160 的状态图其实已经暗示了正确读法：只有 `ready`、`in_use`、`sealed` 的卫星会进入 `rebuilding`。但情形 E 的“唯一定义”和恢复表都没有采用这一前提。
- **为什么重要**：
  - “在首次准备中暂停，过一会儿再继续”是一条普通路径。照字面实现，这样的 Goal 会被一条虚假告警卡住，只能放弃，违背“Needs-You 只放真实、可行动的事”。
  - 这是上轮指出、回应没有处理的那一半。修订只需要一个前提。
- **文档位置**：`10` L155–160、L224、L237、L239、L245、L257、L491、L981、L991；`06` L138、L261；`14` G42(v)(x)(y)。
- **期望的回答形态**：
  - 在情形 E 的判定（`10` L991）与 `06` L138 中加一个前提：只对**检出完成标记存在**的卫星生效（等价于 `WorktreeRecord.state ∉ {creating}`）。
  - 写明标记写出之前，卫星目录的缺失或删除属于仓库准备，由重试重做，不算“丢失”。
  - 卫星监视（含 `external_change` 与嵌套仓库预警）在标记写出后才对该卫星开启；或者把“卫星创建、检出、本地文件播种、重试时的删除”列入归因表第 1 行的 Tower 窗口。二者取一。
  - 用例：G42(x) 之后重启 Tower，并等过一次定期检查；G42(y) 的重试。期望都是不出现 `satelliteRebuilding`、`satellite_missing` 与 `external_change`，`resume` 后照常继续准备。

### D13 隔离、git 与并发

**R26-D13-01｜次要**（“`.lfsconfig` 取 base 提交中的版本”在裸镜像上没有实现机制；“不读镜像中的任何内容”与 git-lfs 的行为不符）

- **问题**：
  - ADR-151 规定，LFS 获取的仓库级配置“不读镜像中的任何内容……`.lfsconfig` 取 base 提交中的版本”（`10` L206–207，`06` L239，`11` L372，`15` L1228）。命令的“作用对象只有镜像”，而镜像是裸库（`10` L22）。
  - git-lfs 的行为是：
    - **裸库只从 `HEAD` 读 `.lfsconfig`**，不看调用者给出的提交；
    - git 配置（含命令行 `-c`）覆盖 `.lfsconfig`。
  - 镜像的 `HEAD` 指向什么，文档没有定义。镜像由同一 Project 的全部 Goal 共享（`10` L22、L41），不同 Goal 的 base 不同，也不能并发地把 `HEAD` 依次指向各自的 base。
  - 照常执行这条命令，结果有两种：
    - git-lfs 读到的是镜像 `HEAD` 所指提交中的 `.lfsconfig`，不是 base 中的版本；
    - `HEAD` 悬空时，git-lfs 什么都不读。
  - 对于用 `.lfsconfig` 指定独立 LFS 服务器的仓库（企业中常见），远端获取会发往错误的端点并失败，进入 `prepare_failed`，重试仍然失败。这正是上轮要防止的那类“重试无效”。
  - 要符合规则，实现者必须自己设计一个机制：由 Tower 读取 base 中的 `.lfsconfig`、筛选键、以命令行配置传入，并让镜像 `HEAD` 不提供任何 `.lfsconfig`。文档没有写出这一机制，G42(p)(w) 也没有一组测试 `.lfsconfig` 自定义端点。
  - 顺带：`remote.<name>.url` 中的 `<name>` 怎样选（与步骤 1 的 `origin` 相同，还是 git-lfs 的默认远端规则），没有写。
- **为什么重要**：
  - 规则写出了结果，却与工具的默认行为相反。实现者照字面直接调用会得到错误的端点，而且现有用例测不出来。
  - 端点“只由可信内容决定”是 ADR-151 的安全理由之一。“读哪一个提交的 `.lfsconfig`”正是这条理由成立的前提，应当写成可执行的规则。
- **文档位置**：`10` L22、L41、L54、L203–211；`06` L239；`11` L372；`15` ADR-151 L1228；`14` G42(p)(w)（L128）。
- **期望的回答形态**：
  - 在 `10` §10.1.2 的例外段或步骤 2a 中写明以下几点：
    - Tower 从 base 读取 `.lfsconfig` 的内容；
    - 只保留 git-lfs 允许的键；
    - 以命令行配置传给这条命令（git 配置覆盖 `.lfsconfig`）；
    - 镜像的 `HEAD` 指向一个不存在的引用，使 git-lfs 在镜像中找不到任何 `.lfsconfig`。
    - 也可以给出等价的、不依赖共享 `HEAD` 的机制。
  - 把“不读镜像中的任何内容”改为准确的表述，例如：“镜像中只有 Tower 写入的配置，不提供 `.lfsconfig`”。
  - 写明远端名的选取规则。
  - 用例：G42(p) 增加一组“base 的 `.lfsconfig` 把 `lfs.url` 指向独立服务器，镜像 `HEAD` 指向别的提交”，期望请求发往 base 指定的端点。

### D11 安全与自主度

**R26-D11-01｜次要**（“credential helper 返回的凭据只在内存中参与精确匹配”没有机制，SSH 远端不适用；LFS 获取输出的去向没有定义）

- **问题**：
  - ADR-151 把“LFS 获取期间 credential helper 返回的凭据（只在内存中参与匹配，不落盘）”加入精确匹配集（`11` L400，`05` L245，`10` L210，`06` L239，`15` L1234），并以此支撑“凭据从不进入……日志或 Trace”。
  - 但这条命令以用户身份、使用用户的凭据配置执行（`10` L54、L206）。凭据在 git、git-lfs 与助手之间交换，作为父进程的 Supervisor 看不到这些值。
  - Tower 要得到它们，只能把自己插入用户的凭据链，例如额外注册一个观察者，或者代替用户调用助手。这意味着 Tower 进程会持有用户的远端凭据。这是一条需要设计裁定的凭据处理边界，文档没有裁定，也没有登记残余风险。
  - SSH 远端的 LFS 认证经 ssh 取得临时令牌，不经过 credential helper。按现文，这类凭据不在匹配集中。
  - 另一方面，这条命令的 stdout/stderr 去向哪里，文档也没有写：写不写 `prepare.log`、进不进 Trace、卡片显示什么。这些输出是精确匹配真正要作用的对象。依赖物化的日志尾部会进入开场（`11` L401），而两者是否共用日志文件同样没有写。
- **为什么重要**：
  - 这一类风险是用户远端凭据经日志或 Trace 外泄，或者 Tower 以未经审定的方式持有凭据。
  - 现文的保证依赖一个不存在的机制。实现者要么悄悄放弃这条保证，要么自行决定“让 Tower 读用户凭据”。后者正是 R24、R25 要求先裁定的那类边界。
  - 修订量很小：选一种写法即可。
- **文档位置**：`11` L372、L400、L401；`05` L245；`10` L54、L206–211、L229；`06` L239；`15` ADR-151 L1227–1234；`14` G42(p)。
- **期望的回答形态**：二选一。
  - **(a) 不取凭据**（建议）：删除“helper 凭据参与精确匹配”。改为规定 LFS 获取的输出：
    - 不进入任何注入模型的路径；
    - 落盘与进入 Trace 之前，去除 URL 中的 userinfo，并经模式与熵两层脱敏；
    - 卡片只显示分类后的原因（可借此顺带区分认证、网络与远端无对象，见 §3 中不扣分的观察）。
    - 与安装器日志分开存放。
  - **(b) 取凭据**：写明取得机制及其边界：只在内存中，不落盘，进程结束即丢弃，不改变用户的凭据存储。在 `11` 的威胁表登记“Tower 进程在 LFS 获取期间持有用户远端凭据”的残余，并说明 SSH 远端不在其中。
  - 用例：G42(p) 的期望写明“该命令的输出只出现在 Tower 私有日志中，不进入开场与 Trace 正文”，并加一组“获取因认证失败”的情形。

### D14 路线图与可验证性

**R26-D14-01｜次要**（G42(z) 的前置在 ADR-151 下不可达；自 `prepare_failed` 交还的用例第三次缺席）

- **问题**：
  1. **(z) 测不到新的清除点。**
     - G42(z) 的前置是“从 `in_review` 接管……此前 `queuedRun` 非空（由排队的返工留下）”（`14` L128）。
     - 按 ADR-151，`queuedRun` 在 `run.started` 时清除，进入 `in_review` 时也清除（`16` L24）。从 `in_review` 接管的 Goal，`queuedRun` 必然为空，前置构造不出来。
     - 期望“进入 `verifying` 的同一事务中被清除”也就区分不了“实现了新清除点”与“没实现”。
     - 真正能留下残值的路径都从 `ready`/`paused` 出发，例如：
       - 排队返工的 `ready`（`queuedRun{rework}`）→ 我来改 → 交还选“直接重新验证”；
       - 握手失败的 `paused(prepare_failed)`（标记存在，`queuedRun{initial}`）→ 我来改 → 交还。
  2. **R24-D15-01、R25 两次要求的“`prepare_failed` → 我来改 → 交还”用例仍然没有。** 这是 ADR-149 补记“`prepare_failed` 归入交还即解除”与 ADR-150 “人的显式决定覆盖保留值”的交点，现在有了检出标记，前置可以构造了。
- **为什么重要**：清除点是 R25-D4-02 的全部修订内容。它唯一的用例测不到它，属性测试之外再没有回归保护。
- **文档位置**：`14` L128（G42(c)(o)(z)）；`16` L24、L25；`06` L856；`03` L93。
- **期望的回答形态**：
  - 把 (z) 改为从 `ready` 出发：排队返工的 `ready` → 我来改 → 交还选“直接重新验证”。期望进入 `verifying` 的同一事务中 `queuedRun` 被清除；之后若验证失败并自动返工，`Run.reason = rework`，不是陈旧值。
  - 新增一组：握手失败的 `paused(prepare_failed)` → 我来改 → 交还选“交给 Agent 继续”。期望 `Run.reason = handback`，`prepare_failed` 被交还解除。
  - R26-D13-01 的 `.lfsconfig` 用例组计入同一行。

### D15 文档一致性与可执行性

**R26-D15-01｜次要**（ADR-151 之后的滞后文字；其中 `06` 的暂停命令与新的步骤划分直接矛盾）

- **问题**：
  1. **`06` L846 `goal.pause`** 仍写“仓库准备与依赖物化期间中止该步骤……**卫星检出**、握手、开场期间（至多 120 s）返回 `E_BUSY`（ADR-149/150）”。

     - 检出含 LFS 内容写出，可能长达数分钟。命令表是命令语义的落点，照它实现，人在这段时间里无法暂停。
  2. **“我来改”的条件**：

  3. **`prepare.progress` 的 producer**：`06` L401 写“git / verifier 安装器”，`16` L280 写“`git`/`engine`”。依赖步骤由安装器产生，握手由引擎产生，两处都不完整，而且互不一致。这是 R25-D15-01 的残留。

  5. **`04` L940** 的括注“目标至少运行过一次，且检出完成”不准确：握手失败、从未运行过的 Goal 也有检出标记，可以接管。规则本身（“只在……已完成检出时出现”）是对的，只是括注错了。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D5、D7、D8、D9、D10、D12、D16 为 100，这十个维度上没有可追问的实质问题。
  - 其余六个维度在 98–99 之间，最低为 D15（98）。
- **是否还有可追问的问题：有。** 新增与残留共 **5** 条：阻断 0、重要 0、**次要 5**。
  - **第 25 轮核验**：6 条中已解决 3（R25-D4-02、R25-D6-01、R25-D11-01）、部分 3（R25-D13-01、R25-D4-01、R25-D15-01）、未解决 0。
  - **其他核对**：
    - lint 全部通过；
    - Pi 事实与 v1.2.0 源码一致；
    - 排期算术（WBS 120.02、38 周、余量 0.56–1.53、增人 33 周）全部成立；
    - git-lfs 的 `.lfsconfig` 读取规则已在本机 3.8.0 的文档上核对。
  - **不扣分的观察**：
    - LFS 失败原因没有细分。
    - 远端 fetch 没有子超时。
    - 没有加 `queued_run` 的状态 CHECK。
    - “等待项目锁”计入 15 分钟，可能让同一新项目的并发首启中有一个超时。结局是 `prepare_failed`，重试会复用已建好的镜像，结局有定义且保守。
    - 检出标记按 Goal 而不是按 binding 存放：多仓库属于 M3，届时需要按 binding 存放。
- **设计是否完成：否。**
  - 五条都是局部的文字或规则补全，不需要新的架构，也不影响排期。
  - 其中 R26-D13-01 与 R26-D11-01 应在实现 W7/W10 的 LFS 部分之前裁定。照现文，前者会让用 `.lfsconfig` 指定端点的项目无法开始 Goal，后者会把“Tower 是否持有用户凭据”留给实现者决定。
- **下一轮建议按以下顺序修订**：
  1. **R26-D13-01**：写明 `.lfsconfig` 从 base 读取并以命令行配置传入、镜像 `HEAD` 不提供 `.lfsconfig`、远端名的选取规则；补用例。
  2. **R26-D11-01**：删除“helper 凭据参与匹配”，改为规定 LFS 获取输出的去向与脱敏（建议）；或者写明取得机制并登记残余。
  3. **R26-D4-01**：情形 E、启动检查与卫星监视以检出完成标记为前提；或者把准备中的 Tower 写入与删除列为 Tower 窗口。
  4. **R26-D15-01**：改正 `06` L846，同步“我来改”的条件、producer、W10 的描述与 `04` L940 的括注。
  5. **R26-D14-01**：把 G42(z) 改为可达的前置，补上自 `prepare_failed` 交还的两组用例与 `.lfsconfig` 用例。

  **工时与排期**：上述修订估计合计约 0.15 人周：
  - R26-D13-01 约 0.05（W7，系统）；
  - R26-D4-01 约 0.05（W3/W7，系统）；
  - R26-D11-01 约 0.02（W10，安全）；
  - 其余为文字与用例。

  系统线余量 0.56、安全线 1.06 工作周，足以吸收，不需要顺延。
