### D11 安全与自主度

**R39-D11-01｜重要**（含密钥的本地文件进入验证槽位与检验检出，与 ADR-164 的 M1 不变式矛盾；跨 Goal 观察的残余没有登记）

- **问题**：
  1. **不变式写得绝对**：
     - `11` L399：“**M1 中没有任何机密进入 Agent 可影响的进程**，即 Agent、验证器与检验检出中的进程”；
     - `11` §11.6.3 L363：“M1 中验证器不接触任何机密”；
     - `07` L700：“M1 中验证器、验证槽位与检验检出的进程都不接触任何机密”；
     - `15` L1540、`16` L503、`05` C29 标题（L1407）、`14` G46 标题（L133）同此口径。
  2. **既有的 M1 机制与之相反**：
     - 本地文件清单（ADR-078/082，`04` §4.15.1 标为 [M1]）中**含密钥的条目只复制进验证槽位与检验检出**（`11` L339，`07` L477，`10` L367、L812，`15` L534）；
     - 验证槽位中运行的是 Agent 写的代码，所以这些值处在 Agent 可影响的进程中；
     - 这是有意的设计：`11` L497 的致命三要素与 T32（`11` L638，评级“中”）都写明“Agent 写的测试在验证槽位中带着这些值运行”；
     - `07` L477 与 L700、`11` L339 与 L363 因此在同一文档内互相矛盾。
  3. **少登记了一类残余**：
     - T32 只登记“值经测试输出回流到模型”这一条通道；
     - 测试运行器与开发服务器常把 env 文件加载进自身环境，再派生子进程；
     - macOS 上同一用户的其他进程可以读取非 Apple 二进制的环境（`11` L337，ADR-158 的平台事实）；
     - M1 中验证与其他 Goal 的 Run 并行进行，没有任何互斥。
     - 因此，验证期间并行运行的其他 Goal（包括其他项目的 Goal）的 Agent 可能观察到这些值。这正是 R33–R37 为钥匙串机密设计调度互斥时要防的那一类危害。
     - 但 T33 的残余只列了 MCP 环境与“用户自己的其他进程”（`11` L639）；T33b 以“M1 中没有向 Agent 可影响进程投递机密的路径”判为“M1 不适用”（L640）。后者的前提不成立。
  4. **用户看到的说法**：
     - §4.15.1 的线框与规则写“检验目录 · 验证槽位（不给 Agent）”（`04` L1281、L1290）；
     - 用户批准含密钥的条目时，看不到“Agent 写的代码会带着这些值运行，运行期间同一用户的其他进程可能读到”。
  5. **自然的绕行**：合同编辑器拒绝 `env` 之后，想让带机密的测试在 M1 中跑起来，最直接的办法就是把 `.env.local` 登记进本地文件清单。这条路径完全受支持。所以“需要机密的检查写为 human 标准”（ADR-164）实际上不是 M1 中唯一的做法，文档没有说明两者的关系。
- **为什么重要**：
  - ADR-164 的不变式是 M1 安全叙述的核心，`11`、`07`、`15`、`16`、`05`、`14` 都引用它。它在字面上不成立，评级与登记也随之不准：T33b 被判为不适用，跨 Goal 观察的残余没有登记。
  - 实现者会照 `07` L700 与 `11` L363 认为验证槽位中没有机密，不会把它们纳入任何检查；用户批准本地文件时，也得不到如实的暴露说明。
  - 这不需要新机制，只需要把例外与残余写清楚。但它属于“残余风险是否诚实”这一维度的实质缺口。
- **文档位置**：`11` L337、L339、L363、L399-402、L497、L638-640；`07` L477、L700；`04` L1272-1291；`05` L1407（C29）；`10` L367、L812；`14` L133（G46）、A9；`15` L534、L1540-1551；`16` L503。
- **期望的回答形态**：在 `11` §11.7.0 写成唯一定义，二者取一。
  - **(a) 推荐**：如实写出例外并登记。
    - 不变式改为：“M1 中 **Tower 持有的机密**（钥匙串条目）不进入 Agent 可影响的进程；唯一由人批准的例外是本地文件清单中含密钥的条目，它们进入验证槽位与检验检出”；
    - 投递表加一行“含密钥的本地文件”：投递方式为复制进验证槽位与检验检出（对 Agent 读拒绝）；暴露为 T32 的输出通道，以及加载进进程环境后的同用户观察；
    - T33 的残余加上这一项（macOS S2：中；M2 决定点同为专用系统用户），T33b 的“M1 不适用”改为指向它；
    - `07` L700、`11` L363 改为同一口径；

  - **(b)**：M1 不把含密钥的本地文件复制进验证槽位（只给检验检出，或都不给）。需要这些值的检查与 ADR-164 同一口径，写为 human 标准。采用此项须同时写明：缺少这些文件导致的标准失败怎样归类，以免按 Agent 失败自动返工。
  - 两种做法都要在 `15` 记一条补记，说明本地文件与“需要机密的检查写为 human 标准”的关系。

**R39-D11-02｜次要**（M1 的机密清单不完整，与“全部机密”表和“钥匙串只存 Tower 自用凭据”的说法不符）

- **问题**：投递表自称给出“全部机密的存放、投递与可读者”（ADR-159，`16` L503），ADR-164 又说“钥匙串在 M1 中只存放 Tower 自己使用的凭据：模型提供商密钥与云 SDK 凭据”（`11` L402、L472）。下面三处与之不符：
  1. **合同授予 registry 令牌**：
     - `16` L1037 与 ADR-063（`15` L434）写明 Agent 的 npmrc 副本 `$GS/npmrc` 是净化副本，“只有合同显式授予某个 registry 令牌时，才写入那一个令牌”；
     - `$GS` 对 Agent 可读，所以这是一条把令牌放进 Agent 可影响进程的路径，与 ADR-164 的不变式直接冲突；
     - 同时，`02` 的 `Contract` 中没有这一字段，`06` 中没有命令，`04` 中也没有界面。条款悬空，但实现安装器配置的人会照着它实现。
  2. **ADR-033 的工具令牌**：
     - ADR-033（`15` L247）在首次运行时把 `GITHUB_TOKEN` 等常见工具令牌导入密钥库，并“按 MCP 服务器/扩展的显式声明逐项传递”；
     - `11` L471 的“用户在清单确认（§11.8.2）时对该服务器的显式授予”在 §11.8.2 中找不到定义；
     - `04` L1424 的首次运行只导入 provider 变量。
     - 因此 M1 是否导入工具令牌、导入后交给谁，没有唯一答案。这也影响机密输入检查的精确匹配集（“钥匙串中 Tower 持有的值”）包含哪些值。
  3. **安装器令牌**：
     - `$TI` = `~/.tower/installer/<projectId>/` 中长期存放含令牌的 npmrc 副本（`07` L525，`16` L1014、L1037）；
     - 这与“`~/.tower` 下没有长期存放的明文机密”（`11` L404，`06` L1048）的说法冲突；
     - 投递表也没有这一行。它只交给不执行代码的 I-fetch 阶段（ADR-085），这一设计本身没有问题。
- **为什么重要**：
  - 第 1 项若照字面实现，就会在 M1 中开出一条 ADR-164 声称不存在的通道；
  - 第 2、3 项是“唯一定义”与其他文档之间的矛盾，会让实现者在密钥库内容与 `~/.tower` 的存放规则上各取一边。
  - 条款都没有界面或字段可以触发，因此为次要。
- **文档位置**：`16` L503、L1014、L1037；`15` L247（ADR-033）、L434（ADR-063）；`11` L402、L404、L469、L471-472、§11.8.2；`07` L525；`06` L1048；`04` L1424。
- **期望的回答形态**：
  - 第 1 项：删除“合同显式授予 registry 令牌”这一条款，或标为 M2，与 `secrets.access` 一并设计；ADR-063 加 “Amended by ADR-164”。M1 中 Agent 侧新增私有依赖已有 `dep.add` 代理安装（`16` L1059），不需要这条。
  - 第 2 项：写明 M1 是否导入工具令牌。若导入，把“只交给用户在 `mcp.json` 中显式声明它的 MCP 服务器”写成投递表的一行，并修正 `11` L402、L472 的“只存放”；若不导入，ADR-033 加修订标记，`11` L469 同步。
  - 第 3 项：投递表加一行“安装器的注册表令牌”（存放在 `$TI`，`0700`/`0600`，只给 I-fetch）；“没有长期存放的明文机密”改为把它列为例外。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D10、D12–D14、D16 为 100，这十四个维度上没有可追问的实质问题。
  - D11 92、D15 98。
- **是否还有可追问的问题：有。** 新增共 **3** 条：阻断 0、**重要 1**、**次要 2**。
  - **第 38 轮核验**：已解决 9，部分 0，未解决 0。ADR-164 的 M2 推迟是干净的：M1 伪代码、枚举、命令、界面与用例都已分开，M2 材料都有标注。
  - **其他核对**：
    - lint 全部通过；
    - Pi v1.2.0 源码复核成立，Pi 依赖面不变；
    - 排期算术全部成立：WBS 121.18、38 周、系统线余量 0.19、增人 33 周。
  - **不扣分的观察**：
    - **验证器中由钥匙串查找拒绝引起的失败**（R38-D11-04 第 2 点）：M1 中验证器沙箱仍拒绝钥匙串服务的查找（`11` L336）。被测代码若用到钥匙串（少见），失败会按 Agent 失败处理。`15` L1550 的“验证器沙箱不受此影响”指的是机密安全，不是这一点。结局有界（返工上限后暂停），而且少见，因此不扣分。顺手可以在 A8 的记录中加一句：A8 显示常见测试受影响时，验证器沙箱同样取消该拒绝。
    - **把机密直接写进标准命令**：编辑器拒绝 `env` 之后，用户可能改为在 `command` 中内联 `NAME=value`。`contract.edit_draft` 的机密检查会对符合模式的值给出提示（`06` L845），但测试密钥常见的形态不一定符合模式。建议编辑器在 exec 命令中出现对 `*_KEY`/`*_TOKEN`/`*_SECRET` 一类变量的内联赋值时，显示与 `env` 相同的引导（`转为 human 标准`，或登记到本地文件清单，见 R39-D11-01）。这由人发起，有提示兜底，因此不扣分。
- **设计是否完成：否。**
  - ADR-164 以减法收住了 R28–R38 的机密追问，M1/M2 的边界整体干净。
