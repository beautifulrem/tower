## 1. 总评

**第 109 轮的 9 条条目都按所问关闭**（核对见 §3）。ADR-237 守住了 “不留之后会删除数据的推迟续做” 的取向：
- 清除一次完成，推迟续做连同 “数据库最后删除” 一起删除；
- 迁移把旧位置记入 `Project.settings.relocatedFrom`，旧位置照常列出、照常清除；
- 放弃时清除 `syncing`，CHECK 不变；
- 不可达期间每一种自动解除都推迟；
- 三项超时设置同一上限；
- F13 改由 tower-goal 自报，引文都已对照 Pi 源码；
- 验证一支只判定实际使用的路径，反向竞争已登记。

第 109 轮 §5 的 14 条观察都已落地。观察 9 只剩 `04` L1522 恢复栏的一处小遗漏（观察 7）。

**ADR-237 的收窄带出一个旧缺口的新面**。本轮唯一的重要条目来自 “不可访问” 的定义：
- 它是对路径本身做 `stat`，并明言 “不区分卷未挂载、被移动、被删除或没有权限”。
- ADR-236 把人工编辑检出的路径列为必需路径；ADR-237 又把写回、重建与接管物化的判定落到 “来源目录与卫星”“卫星与要物化的目录” 这些叶目录上。
- 这些恰恰是 Tower 自己的失败分支预期会消失、或在操作完成前本就不存在的目录。于是：
  - 已设计的丢失分支成为死代码：
    - “人工编辑检出被删除 → `human_checkout_lost`”（`06` L145、`10` L1042）；
    - “写回中来源目录被删除 → 以 T1 重新物化”（`06` L923 ①）；
    - “卫星在写回中途消失 → 还原、改名、重建”。
  - 只有操作路径不可访问、而 Goal 的必需路径都可访问时，操作被判为中断，Goal 却不在不可达集合中。④ 不会续做，`syncing` 或 `satellite_rebuilding=1` 悬空。
  - 中断的交还只剩 `goal.abandon` 一个出口，它连同 T1 一起清除，而 T1 是你交还的改动仅剩的副本。
  - `14` G31 的两组期望（L107）与 `04` L671 的承诺因此与唯一定义相矛盾。见 **R110-D13-01（重要）**。

**扫描发现的其他缺口**：
- **R110-D13-02**：路径丢失的确认在字面上对检验检出不成立（必需路径是记录所在的 `<wtRoot>`），也没有写它与 `syncing` 的关系。
- **R110-D13-03**：`relocatedFrom` 无条件写入并结束旧位置的记录，没有覆盖三种情形：`<wtRoot>` 不变的迁移、迁回旧位置、项目合并与拆分。
- **R110-D12-01**：清除遗留清单的几处空白：
  - 写入次序；
  - 条目移除与 “清除全部” 的关系；
  - 存储面板在遗留根之下列出的范围（`09` L575、`04` L1287 漏了 `10` L259 的限定）；
  - `09` L561、`10` L259 两句已不成立。
- **R110-D11-01**：tower-goal 的 `tool_result` 脱敏处理器出错时 Pi 放行原文。ADR-237 把 `extension_error` 改为 “只进诊断”，这类失败于是没有任何告知。
- **R110-D7-01**：§7.4.6 的 base 确认中，因文件系统错误失败的运行被计为 “base 上失败”。改动引入的不稳定因此可能被判为 `preexisting`，并写入台账缓存。

**对本轮重点问题的回答**：
- **清除遗留清单**：
  - 它确实留存路径。默认的 `<wtRoot>` 形如 `<checkoutParent>/.tower-wt.noindex/<repoName>`（`10` L239），含目录布局与仓库名。“清除全部” 之后它与 `goal-id-hwm` 一起留下，这一点已写明（`09` L569）。
  - 条目只在根重新可访问、且其下已没有 Tower 创建的目录时移除。永不再出现的根永远留在清单里，界面没有移除入口。
  - 写入次序与 `all` 档对清单中根的处理没有写。见 R110-D12-01。
- **`relocatedFrom`**：身份不受影响。重复迁移、`<wtRoot>` 不变的迁移与合并没有写，见 R110-D13-03。
- **路径丢失的确认与安全不变式**：成立，见上文 “经复核不成立”。条件写法见 R110-D13-02。
- **自报加重新抛出**：
  - 对 `tool_call` 成立：Pi 把重新抛出的异常转为错误的工具结果，工具被阻断；自报使计数增加。
  - 对 `turn_start` 成立：Pi 捕获后照常发请求，自报计数，Pi 的 `extension_error` 只进诊断、不重复计数。
  - 对 `tool_result` 不成立：重新抛出等于放行，见 R110-D11-01。
  - “连续 3 次” 的复位条件与暂停原因没有写，这在 ADR-237 之前就是如此，记为观察 1。

**ADR-237 的其余写法成立**（§3.3）：
- `06` L143、L952 与 `09` L567、L569 的清除一次完成；
- `06` L942 的放弃清除 `syncing` 与 L923 的例外；
- `06` L139 ③ 的每一种自动解除都推迟；
- `05` L474 的上限；

- `12` L416、L434、L436；
- `13` L130、L173；

### D7 诚实与验证

**R110-D7-01｜次要**（§7.4.6 的 base 确认中，因文件系统错误失败的运行被计为 “base 上失败”：改动引入的不稳定可能被判为 `preexisting`，得到有保留的已验证，并写入台账缓存）

- **问题**：
  - `07` §7.4.6（L858 起）在 `runCriterion` 内部重跑失败用例，再 “在同一槽位检出 `baseCommit` …… 重复运行 id 至多 5 次”，规则为 `origin = (base 上至少失败一次) ? "preexisting" : "introduced"`。base 结果按 `(id, baseTree)` 缓存进 `flakeLedger`。
  - “失败先判可达”（`06` L139）只在 `runCriterion` 返回之后、对整条标准的结论判定一次（`07` L465）。base 运行中的单次失败不经任何判定。
  - 槽位所在卷在 base 运行期间短暂停顿时，这几次运行以文件系统错误失败，于是被计为 “base 上失败一次”。
    - 结论变为 `pass_with_preexisting_flakes`，计入 V。
    - 若卷到判定时已恢复，结论按真实结果记录；若仍不可访问，验证被中断，但 `flake` Fact 与台账缓存已经写下，同一 pin 重跑时直接取缓存的 `preexisting`。
  - 第 109 轮接受的反向竞争，前提是 “暂时的错误把结论推向失败”。这里方向相反：暂时的错误把结论推向通过。
- **为什么是次要**：
  - 要一次改动引入的不稳定与一次槽位卷的停顿恰好重合。
  - 结论是 “有保留的已验证”，验收面板列出这些测试与 base 上的失败证据，不是无保留的绿色。
  - 但它违背 §7.4.6 自己选定的保守方向（“拿不准时判为 introduced”）。台账缓存还会把误判带到同一 base 上之后的验证与隔离提议中。
  - 实现会在 “base 失败一律计入” 与 “区分环境错误” 之间分叉。
- **后果的类别**：改动引入的竞态在罕见时序下被标为 “base 上本就不稳定”，进入有保留的已验证；台账中留下错误的 `preexisting` 记录，之后可能生成 “隔离该测试” 的提议。
- **文档位置**：`07` L465、L855–L881（§7.4.6）；`06` L139（失败先判可达）。
- **期望的回答形态**：
  - 写明 base 运行以文件系统错误失败，或该次运行后槽位所在的 `<wtRoot>` 判为不可访问时，这次运行不算 “base 上失败”，只算无结论；
  - 无结论的用例按 `introduced` 处理（§7.4.6 已选的保守方向），不写入 `flakeLedger`；
  - 或者对 base 运行同样适用 “失败先判可达”，不可访问时整次验证中断，且不写 `flake` Fact 与台账。

### D11 安全与自主度

**R110-D11-01｜次要**（tower-goal 的 `tool_result` 脱敏处理器出错时，Pi 让原始结果照常进入模型；ADR-237 之后这类失败只进诊断，没有任何告知）

**R110-D13-01｜重要**（“不可访问” 按路径本身的 `stat` 判定并包含 “被删除”，而它被套用到 Tower 预期会消失或尚不存在的目录上：已设计的丢失与失败分支成为死代码，中断的操作无人续做，中断的交还只剩丢弃 T1 的出口）

  - **定义**：

### 不扣分的观察

1. **F13 的计数细节**（ADR-237 之前已如此）：
   - “连续 3 次” 没有写由什么复位：同一处理器的一次成功、任一处理器的一次成功，还是新的 Run。
   - 第三次时进入哪个暂停原因，以及交还时是否随 `sentinel_high` 的规则清除，也没有写。
   - `turn_start` 处理器因 `bridge` 本身失败而抛出时，经同一 `bridge` 的自报可能也失败，而 Pi 为它发的 `extension_error` 又被排除在计数之外。可写 “没有收到自报时，以该 `extension_error` 计数”。M1 的 `bridge` 是进程内对象，这一情形很少见。
2. **契约测试**：C5 只覆盖 `tool_call` 一半；`turn_start` 自报计数、且不与 `extension_error{event:"turn_start"}` 重复计数，没有断言。
3. **超时的下限**：三项设置取 1 ms 之类的极小正数时，同样是 “立即超时 → 可重试 → F6 → 探测” 的循环。这与终端中的 `pi` 相同，宜在 `05` L474 登记一句。
4. **中断的验证中已写入的 Fact**：
   - `06` L139 ②、`07` L499 与 G35e (q) 写 “不写 `verify.result` 与 Fact”。但 `07` 的伪代码在判定之前已经写下：
     - 前面各条标准的 `criterion_check`（L466）；
     - 哨兵（L397）与产物（L405）的 Fact；
     - `sentinelsP`、`inventoryP` 也未等待。
   - `env.error`、`svc.error`（L458、L461）中的文件系统错误直接成为 `verify_env_error`，不经可达判定。
   - 宜写明 “不写” 只指该条标准与 `verify.result`，并对这两处补判定。
5. **“验证不读的附着检出”**（`06` L139）：验证在开始前从用户检出读取并播种本地文件（`07` L440–L453、L506）。附着检出这时停顿，条目记为 `not_copied`，失败照常记录、计返工。这属于已接受的反向竞争的方向，宜改一句措辞。
6. **`◆` 的条件**：`12` L436 与 `06` L1197（F4）写 “启动时未自动解除后 `◆`”；唯一定义 `08` L393 限定为 “因 `resumeOnLaunch` 关闭而没有自动解除”。因不可达而推迟的解除按 `08` 不生成条目，宜让两处摘要对齐，免得推迟时显示 `◆`。
7. **`04` 的摘要**：
