## 1. 总评

**第 91 轮的 1 条重要、2 条次要条目都已按所问关闭**（核对见 §3）。§5 的 14 条观察全部落地。回应 “偏离与未决” 的五条全部接受。

**ADR-219 的主体成立**（§3.3）：
- **求路径**：`piResolve` 与 Pi 的求值逐步一致，`read` 变体 “不论是否存在都各判定、取最严格者” 比 Pi 实际的选择更宽，方向正确；`..` 在 `path.resolve` 后不再出现，所以文件工具只有一种求值的论证成立。C41 用导出的工厂与记录路径的 `operations` 观察 Pi 自己的求值，在 v1.2.0 中可行。
- **共用求值**：`11` L223 的 “求值” 一句由 (1)(3)(b) 共用，(1) 的 “经 `realpath` 后” 与 (b) 的括注都改为引用它，G46 (bk) 补了符号链接一组。
- **写回失败**：“本进程中执行” 的限定恢复；还原途中崩溃时，§6.1.6 的续写只跳过 “`written` 中已写且内容等于 T1” 的路径（`06` L144），被还原过的路径会被重写，结局一致；还原成功时退回 `idle`、放弃与重试都可用。

**ADR-219 带出的新问题**：
- **写回失败后保留 `syncing` 的状态没有定义完整**（R92-D6-01，重要）：
  - 带回失败而保留 `syncing` 的 `in_review`/`accepted` 目标上，`goal.request_changes`、`goal.retry_verify`、`contract.amend`、`goal.hand_back` 与 I2 一类自动转移都不再被 `E_BUSY` 挡住，而 DDL 的 CHECK 只允许这一组合停在 `in_review`/`accepted`；带回本身无法经命令重试，界面却写 “可以再次交还”。
  - 这一状态下人工编辑检出或检验目录被告知 “保留”，人此后再改动它们时，启动续写仍以失败之前的 `targetTree` 完成，然后删除该目录，失败之后的改动丢失。

**全范围扫描**在 ADR-219 之外新发现两处此前各轮都没有触及的分类缺口，都在 `11` §11.3.1：
- **分类与执行之间文件系统可变**（R92-D11-01，重要）：
  - 分类在 `tool_call` 钩子中对 `realpath` 判定；内置文件工具在 Host 中、S2 之外执行，执行时由操作系统重新跟随路径中的符号链接。
  - Pi 默认并行执行一批工具调用：整批的钩子先跑完，再并发执行。同一批中的沙箱 bash，或仍在运行的后台进程，都能在两者之间改变卫星中的路径分量。
  - 照文字实现，第 3 条硬底线（文件工具 forbid）、`edit.outside_worktree` 与 `secrets.access` 对文件工具都可被绕过；T3 的 “低” 评级依赖的 “S2 写允许列表” 对这些工具并不适用。
- **目录型工具只按搜索根分类**（R92-D11-02，重要）：
  - `grep`/`find`/`ls` 的分类只判定搜索根这一个点，而 `grep` 递归读取整棵子树并返回内容。
  - 搜索根是受保护位置的祖先时（卫星的上级目录、用户主检出的上级目录、主目录），子树中的硬底线位置与密钥路径表条目都会被读到，调用只按 `read.external` 处理（spike 与调研预设为 notify）。
  - 受保护位置本身经符号链接存放（点号文件管理器的常见做法）时，`real` 与按字面写的表比较也会漏判。

### D11 安全与自主度

**R92-D11-01｜重要**（文件工具在 `tool_call` 钩子中按 `realpath` 分类，Pi 在之后的 `execute` 中由操作系统重新跟随路径；Agent 能在两者之间改变卫星中的路径分量）

- **问题**：
  - **判定的时刻**：`11` §11.3.1 伪代码（L146）在钩子中对求出的路径取 `realpath(最长已存在前缀) + 剩余部分`，注释为 “防 worktree 内符号链接指向外部”。之后不再有判定。
  - **执行的时刻**：内置文件工具在 Engine Host 中、S2 之外运行（`11` L162 “内置文件工具在 Host 中运行，不在 S2 之内”）。它们把按词法求出的绝对路径交给文件系统（`write.ts:65` 之后的 `mkdir`/`writeFile`，`read.ts:124` 之后的 `readFile` 等），由操作系统在打开时逐段跟随符号链接。
  - **两者之间可以发生什么**（Pi v1.2.0）：
    - `toolExecution` 默认为 `"parallel"`（`packages/agent/src/agent.ts:253`）。并行模式先对整批调用逐个运行 `beforeToolCall`（即门禁），全部通过之后才并发执行（`agent-loop.ts:586-648`）。Tower 只给 `ask_user` 设了 `sequential`（`05` L743）。所以同一批中的沙箱 bash 的效果，发生在同批文件工具调用被分类之后、执行之前或之间。
    - 即使按顺序执行，Agent 留下的后台进程也在持续运行（`10` §10.3.1 的后台进程识别、G35c）。
    - S2 允许 Agent 在卫星中创建符号链接（`11` L223 自己写明 “Agent 又能在卫星中建立符号链接”）。
  - **文档中已有的防护不覆盖这里**：`10` §10.1.3 的 “逐级不跟随” 只约束 Tower 自己的文件操作；`05` §5.6 gate 第 8 步的输入比对只防参数被改写，不防文件系统状态改变；事后检测（`11` L292）只看卫星内的变更。
  - **评级依据不成立**：T3（`11` L682）“S1 路径守卫 + S2 写允许列表 + 硬底线 → 低”，T26（L705）“用户仓库对 Agent 只读（S2）”。对内置文件工具，S2 不在场，S1 是唯一的守卫，而 S1 的判定对象在判定之后可变。
- **后果的类别**：照唯一定义实现时，一次被判为工作区之内（`edit.in_scope`，多数预设 silent）的写入，可以在执行时落到用户主检出、影子目录、其他 Goal 的卫星等第 3 条硬底线位置，越过 “不可授权覆盖” 与各预设都 forbid 的 `edit.outside_worktree`，造成用户工作或 Tower 完整性数据被改写；一次被判为 `read.worktree` 的读取，可以在执行时读到密钥路径表中的凭据，内容进入模型上下文，越过 `secrets.access`（单向门）。这正是受提示注入的 Agent 可以主动构造的条件。
- **为什么是重要**：实现者照 §11.3.1 实现，硬底线对文件工具的承诺（`11` L214 “文件工具 forbid”）与 T3 的评级都不成立。文档没有任何一处提到判定与执行之间的窗口。
- **文档位置**：`11` L143–L157、L159、L162、L214、L223、L260（`decide` 的 `env.sandbox`）、L292、L682（T3）、L705（T26）；`05` §5.3.5 `TOWER_BUILTINS`（L391）、L743；`10` §10.1.3（L216–L229）；`05` §5.11.1 依赖清单。
- **期望的回答形态**：在 `11` §11.3.1（唯一定义）写明一条不变式——**文件工具实际访问的对象就是被分类的对象**，并选定一种实现：
  - **使用时校验**：Tower 以导出的工厂（与 bash 一样经 `customTools` 注入）为六个工具提供自己的 `operations`，在打开时从卫星根逐段不跟随（复用 `10` §10.1.3 的做法）或打开后核对实际路径，不符即失败；`grep`/`find` 的实际读取由 `rg`/`fd` 完成、`operations` 包不住，须在派生之前复核搜索根，并说明子树遍历不跟随符号链接（`rg`/`fd` 的默认行为）由契约测试锁定。来源变为 `<sdk:…>` 之后，`11` §11.3.4 的来源允许表、`16` §16.1.10、ADR-130 的只读白名单与 D 类依赖表同步。

**R92-D11-02｜重要**（`grep`/`find`/`ls` 只按搜索根这一个点分类，`grep` 却递归读取整棵子树并返回内容；受保护位置与求出的路径也没有规定在同一规范形式下比较）

- **问题**：
  - **只判定一个点**：§11.3.1 伪代码对 `grep`/`find`/`ls` 与 `read` 同样只求一个 `real`，判断它是否在 `worktreeRoots` 之内、是否 “命中” 密钥路径表；第 3 条硬底线（`11` L214）也按 “落在其中” 判定。
  - **Pi 实际读取的范围**：`grep` 以 `rg --hidden` 从搜索根递归搜索，返回匹配行的内容（`grep.ts:162-168`）；`find` 以 `fd --hidden` 列出子树中的名字（`find.ts:182-216`）；`ls` 列出一层名字。不在 git 仓库中的目录不受忽略规则限制。
  - **搜索根是受保护位置的祖先时**：
    - 卫星的上级目录含其他 Goal 的卫星（`<checkoutParent>/.tower-wt.noindex/<repoName>/`，相对路径 `..` 即可到达）；
    - 再上级含用户主检出；
    - 主目录含 `~/.ssh/**`、`~/.aws/**`、`~/.tower/**` 等密钥路径表条目。
    这些根本身既不在硬底线位置 “之内”，也不 “命中” 表中的任何一条，所以按 `read.external` 处理：spike 与调研预设为 notify，其余预设为 ask 且可授予 “本 Goal 内同类”。
  - **规范形式不一致**：伪代码只把求出的 `real` 与各集合比较，没有写这些集合本身是否取 `realpath`（`11` L367 只对沙箱策略要求先取 `realpath`）。受保护位置本身是符号链接时（点号文件管理器把 `~/.aws`、`~/.npmrc` 链到别处的常见做法，或用户以经链接的路径登记了主检出），`real` 与按字面写的条目不相等，读取同样落到 `read.external`。
  - §11.7.1 的脱敏只能兜住 Tower 已知的值与固定模式（如私钥只有首行被模式命中），不能代替分类。
- **后果的类别**：凭据文件的内容与用户主检出、其他 Goal 卫星中的内容进入模型上下文，而分类结果既不是 `secrets.access`（单向门、spike 与调研 forbid），也不是硬底线 forbid；在 spike 与调研预设下只是 notify，不出现审批卡。§11.8 三要素中的 “私有数据” 一项（`11` L538 起）也默认这些位置在 S2 下不可读，对 Host 中的文件工具不成立。
- **为什么是重要**：照唯一定义实现，硬底线（`11` L214 对主检出与其他卫星的 “读写” forbid）与 `secrets.access` 的分类对目录型调用都不成立；这与 R91-D11-01 同属 “门禁判定的对象与 Pi 实际访问的对象不一致”，但 ADR-219 只对齐了单个路径的求法。
- **文档位置**：`11` L143–L148、L159、L162、L214、L367、L538 起；`16` L259（文件类工具一行）；`05` C41（L1483）；`14` G46（L134）。
- **期望的回答形态**：在 `11` §11.3.1（唯一定义）补两句：
  - **目录型调用按子树判定**：`grep`/`find`/`ls` 的搜索根（含省略时的 `.`）若是第 3 条硬底线位置、其他 Goal 的卫星或密钥路径表中任一位置的祖先（或等于它），按相交项中最严格者判定（硬底线 forbid、密钥 `secrets.access`）；或者更简单地写成 “搜索根不在工作区之内且其子树与上述位置相交时 forbid”。`find`/`ls` 只泄露名字，可以写明取较轻的处理，但须写出。
  - **同一规范形式比较**：受保护位置（`worktreeRoots`、硬底线位置、密钥路径表中的绝对条目、Pi 资源目录）在编入 `policy.json` 时各取字面与 `realpath` 两种形式，求出的路径以字面与 `real` 两种形式与之比较，任一命中即按命中处理（与 ADR-217/218 “每种解释各查一次、取更严格者” 同一原则）。
  - C41 (c) 或 G46 补一组只写期望：以主目录、卫星上级目录为搜索根的 `grep` 被 forbid 或归 `secrets.access`；`~/.aws` 是指向别处的符号链接时，读取其中的凭据文件归 `secrets.access`。

### D6 系统架构与可靠性

**R92-D6-01｜重要**（写回失败后保留 `syncing` 的状态没有定义完整：带回一侧的命令与自动转移撞上 DDL CHECK、带回无法经命令重试；续写以旧的 `targetTree` 完成后删除人此后又改过的目录）

- **问题**：
  - **新状态**：ADR-219 规定 “还原也失败、或来源目录已不存在” 时 `syncing`、`targetTree`、`written` 保留，“写回已不在进行：不返回 `E_BUSY`”（`06` L914）。触发条件之一正是 L914 列出的失败原因 “卫星在写回中途消失”——卫星不在时还原无从进行。这一状态在 Tower 运行期间持续存在，直到人放弃、重试成功或重启。
  - **带回一侧（`in_review`/`accepted`）没有定义**：
    - DDL CHECK（`06` L499–L500）只允许 `human_checkout` 非空的 Goal 停在 `paused(human)`，或停在 `in_review`/`accepted` 且 `syncing`（注释仍写 “inspect.bring_back 写回中”）。
    - 此前 `syncing` 期间这些 Goal 上的改写命令都返回 `E_BUSY`；现在不再如此，而它们的前置条件大多不看 `human_checkout`：`goal.request_changes`（L931，转出到 `ready`/`running`）、`goal.retry_verify`、`contract.amend`（增删标准时转入 `verifying`）、`goal.accept{integrate:"none"}`（转入 `archived`），都会产生 CHECK 不允许的组合。
    - `goal.hand_back` 的前置条件只要求 `human_checkout` 非空（L905），在 `in_review` 上同样会被接受，而它要写的 `pending_hand_back` 受 `CHECK (pending_hand_back IS NULL OR state='paused')`（L501）约束。
    - 自动转移同样没有交代：写回窗口结束后指纹变化触发的 I2（`in_review` → `verifying`）、外部写入检测、卫星重建失败（`paused(satellite_missing)`）。
    - 带回本身无法经命令重试：`inspect.bring_back` 的前置条件 “无 `human_checkout`”“卫星树等于 pin 的树” 此时都不成立（L914），只能放弃或重启；而 `06` L914 写 “人可以重试同一命令”，`04` L667 写 “交还与检验带回相同……可以再次交还或放弃”。
  - **来源目录在失败之后被改动**：
    - 这一状态下界面告诉人 “你的副本保留”（`04` L667），人工编辑检出或检验目录照常可编辑。
    - 经命令重试交还时，① 从当前检出重算 T1（`06` L905），没有问题；但启动续写（`06` L144）只从保存的 `targetTree` 续写，“不依赖人工编辑检出仍存在”，完成后按 “对应命令的后续步骤” 删除人工编辑检出（`10` L1010）或检验目录（`10` L924），不与目录的当前内容比较。
    - 所以人在失败提示之后对检出所做的改动，在一次重启（`04` L667 写明 “重启 Tower 后也会自动续写”）之后被删除，没有任何提示。这一缺口此前只存在于 “崩溃到重启” 的窗口，ADR-219 把它变成了界面主动引导人停留的长期状态。
- **后果的类别**：
  - 用户在失败之后对自己副本的改动丢失（目录被删除，内容不在任何检查点或影子对象中）；
  - 带回一侧的实现会分叉：有的照常执行命令而撞上 CHECK（命令以内部错误失败，或自动转移的事务被拒绝而停在不一致的中间态），有的为满足 CHECK 清除 `human_checkout`——来源已不存在时，T1 是人的改动仅剩的副本，清除即丢失。
- **为什么是重要**：照文字实现会丢失用户的工作（第二部分），并在文档自己列出的失败原因下产生 DDL 不允许的转移（第一部分）。
- **文档位置**：`06` L144、L499–L501、L905、L907、L914、L931、L933；`10` L916–L928、L972、L1010、L1035；`04` L667；`12` L389；`16` L43、L293；`14` L107（G31）。
- **期望的回答形态**：在 `06` L914（唯一定义）补：
  - **保留 `syncing` 时的命令**：除 `goal.abandon`（以及交还一侧的 `goal.hand_back`）外，会改写该 Goal 状态、暂停原因、继续目标、开场或 `human_checkout` 的命令一律返回 `E_STATE`（“写回未完成：重试或放弃”），`goal.hand_back` 只在 `paused(human)` 上接受；由指纹或文件事件触发的自动转移在续写完成之前继续抑制（与写回期间相同），或写明它们怎样与 CHECK 相容。
  - **带回的重试出口**：要么 `inspect.bring_back` 在 “`human_checkout` 为本目录的 `syncing` 且不在进行中” 时按 `targetTree` 续写（前置条件中的 “无 `human_checkout`”“卫星树等于 pin 的树” 对这一情形豁免），要么写明带回失败后只能放弃或重启，并改正 `04` L667 与 `06` L914 的 “重试同一命令”。
  - **续写前比较来源目录**：续写（命令重试之外的启动续写）在删除人工编辑检出或检验目录之前，若目录仍在且其内容与 `targetTree` 不同，不删除——按 `10` §10.2 改名保留并在结果中列出，或重算 T1；或写明失败提示中告诉人 “不要再改动该目录”。
  - DDL 注释与 `06` L144 “写回中途崩溃” 的措辞同步（观察 2）。
  - G31 补带回失败一组只写期望：带回写回中途卫星消失 → `in_review` 不变、`goal.request_changes`/`goal.accept` 按所选规则返回、带回可按所选出口重试或放弃；另一组：交还失败且保留 `syncing` 后改动人工编辑检出，再重启 → 改动不丢失。

    6. **“稍后重试” 的按钮清单**：`04` L667 与 `12` L389 只列 `放弃`、`放弃改动`、再次交还与带回；带回期间目标在 `in_review`，界面上可见的是 `验收`、`请求返工`、`关闭检验`，它们同样返回 `E_BUSY`（`06` L914 的清单）。宜改为 “这期间改动该目标的操作都提示……”。失败提示中的 “或放弃” 指放弃改动还是放弃目标，宜写明。
    7. **写回实况行的先后**：`12` L389 新增的 `写回中` 一行没有写与卡片第二行 `<状态> · <原因>`（`04` L228）及 `已暂停 · 人工编辑中`（`12` L419）的先后。宜写明写回期间以哪一行为准。
    8. **文件工具的 `opaque` 在 S2 下的级别**：`11` L159 写 “该调用为 `opaque`、至少 ask”，而 `decide()` 对非沙箱外工具以 `env.sandbox = sandbox.active` 求值（`11` L260），S2 下 `opaque` 只提到 `exec.arbitrary` 的级别（标准预设 notify、spike silent）。这些值 Pi 一侧都会抛错、不发生读写，所以不影响安全；宜改为 “按 `opaque` 判定”，或在 `decide` 的调用处写明文件工具的 `opaque` 以无沙箱求值。
    9. **C41 的夹具说明与 `index.ts` 的措辞**：`read` 的变体探测用 Node 的 `fs.access`、不经 `operations`，所以 (b) 须在临时目录中放真实文件；`grep` 在求路径之前先 `ensureTool("rg")`（`grep.ts:119`），在 `PI_OFFLINE=1` 且 PATH 上没有 `rg` 时会先失败，宜写明夹具固定 `rg`，并把求路径之前的失败当作夹具错误而不是 “Pi 抛错 → `opaque`”。`11` L159 “只导出工具工厂与类型” 偏窄（另有 `withFileMutationQueue`、`truncate*` 等），不影响结论。
    10. **G46 符号链接组的覆盖面**：`14` L134 的三种写法（绝对路径、`file:` URI、`~/` 路径）都属于 (1)；(3) 的相对路径经卫星中的符号链接求值的情形没有一组。只对 (1)(b) 实现两种求值的实现同样能通过。宜补一组相对路径。

    12. **W16 行的措辞**：`14` L235 “路径检查的 (1) 同样按两种方式求值”，L216、`15` L1416 与 ADR-219 写 “(1)(3) 与 (b) 共用”。宜补 (3)。`00` L99 的依据列止于 ADR-218，而该行已按 ADR-219 观察 7 修改，宜补 ADR-219。

  - 本轮 3 条条目分两类：
    - **此前各轮未发现的旧规则缺口**：R92-D11-01（判定与执行之间的窗口）、R92-D11-02（目录型调用只判定一个点）。两者与 R91-D11-01 同属 “门禁判定的对象与 Pi 实际访问的对象不一致”，ADR-219 只对齐了单个路径的求法。
