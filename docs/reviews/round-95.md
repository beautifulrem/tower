## 1. 总评

**第 94 轮的 9 条次要条目都已按所问关闭**（核对见 §3）。§5 的 14 条观察全部落地。回应 “偏离与未决” 的六条都接受，没有发现未写出的偏离。

**ADR-222 的主体成立**（§3.3）：
- **合并读取**：Pi 的三个工具在一次调用中对同一个 `absolutePath` 依次调用各操作（`read.ts:124-155`），所以 “`access` 时一次交回整份内容、随后的判定与读取直接用它” 与 Pi 的语义一致。受强制的那次打开是 `cat` 的打开；`test` 与 `cat` 之间的改向同样在打开时由 S2 判定。图像判定与读取用的是同一份字节，比第 93 轮的三次打开少了一个 “判定与读取之间被换掉” 的窗口。
- **一次写入**：`mkdir -p` 与重定向在同一进程中执行；中止在 `mkdir` 之后、`writeFile` 之前到来时什么都不留下，比 Pi 默认实现更干净。
- **读取凭据出同一张卡**：对卫星之外的密钥路径（`~/.ssh/**`、`~/.aws/**`、`~/.pi/agent/auth.json`、工具配置）成立。卡上的 S2 句子对这些文件读取为真；`edit` 这类文件时写入一侧在写允许之外，仍为必然拒绝。
- **经批准的目标只认相等**：比包含更严，G46 `~/.aws` 一组与之相符。
- **观察器的删除**：`details.fullOutputPath` 覆盖每种截断情形。删除前的校验（`os.tmpdir()` 的直接子项、`pi-bash-<16 位十六进制>.log`、不跟随链接）足以挡住伪造的删除：名字含 64 位随机数；S2 下 Agent 列不出 Host 的临时目录；它从自己此前的结果中得知的路径都已被复制并删除；S0 下它本来就能直接删除，不多出能力。
- **`.kept-*`**：四种形状在 `09` L559/L565/L567、`06` L142/L1077、`16` L174、`10` L256 与 `02` L46 的编号跳过中一致。

**ADR-222 带出、或本轮扫描发现的新问题**（都是次要）：
- **带回一侧的 `write_back_failed` 仍可能永不关闭**（R95-D8-01）：带回的 ① 物化失败，或人在失败之后删掉了检验目录，这时再次带回与关闭检验都返回 `E_STATE`。`discard_human_edits` 需要 `human_checkout`，而 ③ 已清除它；`goal.resume` 需要 `paused`。`08` L516 列出的 “知悉” 没有任何命令承载。
- **读取凭据例外的适用范围**（R95-D11-01）：
  - 卫星内的密钥路径（未跟踪的 `.env`、`*.pem`、`id_*`）被 `11` L148 分为 `read.worktree`（silent），出不了 “同一张卡”；
  - 与第 3 条硬底线的先后没有写；
  - S2 卡片上的 “批准也不会让沙箱允许这次读取” 被写成对每张 S2 卡片都成立，包括 `printenv`、钥匙串查找这类不是文件读取的 bash 命令。
- **同卷硬链接**（R95-D11-02）：S2 的读写拒绝都以路径表达，而卫星与用户主检出、主目录同卷。在可写位置建立指向被拒绝文件的硬链接是否被拒绝，文字没有写，SP6a 也没有探测。
- **观察器复制所用的路径**（R95-D12-01）：
  - 校验只写在删除之前。超时与中止时，复制的来源只能从含 Agent 输出的错误文本中求出，这一步可能在沙箱外读入 Agent 指定的路径；
  - D61 写 “超时与中止时只在错误文本中”，与 Pi 不符：流式更新中同样带有该路径；
  - MCP 截断结果的全文文件没有列入隐私残余。

### D11 安全与自主度

**R95-D11-01｜次要**（读取凭据例外的适用范围：卫星内的凭据、与第 3 条硬底线的先后、S2 卡片句子的适用面）

- **问题**：
  - **(1) 卫星内的密钥路径出不了卡**：

  - **(2) 与第 3 条硬底线的先后**：
    - 有些密钥文件位于第 3 条硬底线的区域内（§11.3.3 L217）：用户主检出或 `_human`、`_inspect` 中未跟踪的 `.env`；`~/.tower/**` 本身就在密钥路径表中，而影子目录、`$TI`、`$VS` 都在其中。

  - **(3) S2 卡片句子的适用面**：
    - L162 与 `04` L1133 写 “S2 下这张卡（不论来自文件工具还是 bash）写明‘S2 下批准也不会让沙箱允许这次读取（M1）’”。
    - `secrets.access` 的 bash 命令不只是文件读取（L206）：
      - `printenv`/`env`/`set` 在 S2 中照常运行，读到的是净化后的环境；
      - `security find-*` 在 A8 的回退下（L358 取消钥匙串查找拒绝）只受系统授权提示约束；
      - `op`/`vault`/`gh auth token` 走进程间通信或网络，不受文件读拒绝约束。
    - 对这些命令，这句话不为真：单向门卡片给了人一个不实的保证。
- **后果的类别**：
  - (1)：同一种尝试经两种工具得到两种告知形态（卡片与哨兵），与 ADR-222 选定的 “一条规则” 相反；实现会分叉，有的在伪代码中补检查，有的照伪代码。
  - (2)：硬底线是否可经审批卡触达，取决于读法。访问本身仍被 S2 拒绝，所以有界。
  - (3)：人在一张单向门卡片上依据不实的说明作决定。
- **文档位置**：`11` L29、L50、L77、L148、L162、L165、L206、L217、L357、L358；`04` L1133；`05` L1499 C42 (f)；`14` L134 G46。

  - **不扣分的观察**：
    1. **按调用的缓存**：`11` L160 写 “同一次调用随后的 `detectImageMimeType` 与 `readFile` 直接用这份内容（调用结束或中止时丢弃）”。但 Pi 的各操作只收到 `absolutePath`，`05` L388 的 `fileOps` 又按会话构造一次；`read` 中止时在 `access` 之后返回、不调用 `readFile`（`read.ts:127-128`）。宜写明按调用作用域：在 Tower 包装的 `execute` 中为每次调用新建 `operations`，同一批中对同一路径的两次 `read` 因此不共用缓存，中止时随调用丢弃。`13` L320 的回退方案同样需要这一点。
    2. **错误的映射与上限的落点**：
       - `edit.ts:176-181` 中，`access` 抛出的错误带 `code` 时只显示 “Error code: <code>”。合并读取之后，16 MB、超时、崩溃与回复不合规的失败都在 `access` 中抛出，所以这些错误宜不带 `code`，承诺的工具结果文字才能保留。目录与其他 `cat` 失败宜映射为 Pi 自己会给的错误码（如 `EISDIR`），不一律映射为 `EACCES`。
       - S2 下 16 MB 上限只能在交回的字节流上执行（超出即终止进程），宜写一句。
       - S0 下 “读取前按文件大小” 管不住大小为 0 的特殊文件与读取期间增长的文件；有上限的读取循环可以一并覆盖，FIFO 在 S0 下没有超时。
    3. **回退方案的按调用语义**：`13` L320 的回退（同一批同时等待的读取共用一次启动）与 `11` L160 的按次规则有三处待定：
       - “每次操作墙钟 10 s” 与 “失败只使这一次操作失败”：共用进程被杀时，同批读取一并失败；
       - `sandbox_violation` 的 `toolCallId`：一个进程服务多次调用时，宜按路径对应；
       - C42/G46 钩子 “该次调用的辅助进程启动之前” 的时机。
       另外，SP6a A3 的 “额外开销” 宜写明基线（不经包装的同一命令，或 Host 内的 `fs` 读取）。回退只在实测超出时实现，实现前补齐即可。
    4. **情形 E 的触发处**：`10` L1264（情形 E 的唯一定义）写 “操作前检查或文件系统事件发现……”，没有引用 `06` L139 的三条排除（含本轮的 `syncing`）。这些排除历来只写在 `06`，一贯如此；宜在 `10` L1264 加一句 “触发的排除见 `06` §6.1.6 卫星丢失一行”，避免只读 `10` 实现 watcher 的人漏掉。
    5. **③ 的部分改名**：`06` L914 “工作目录与 gitdir 各自改名……改名本身失败时不置标记、不重建”，没有写只有一半改名成功的情形。这时提交之后的重新判定会使卫星丢失一行触发，与 “不重建” 相反，情形 E 的旁路改名还会撞上仍在原位的另一半。两次改名都失败的带回一支，卫星停在半写的状态而 I2 已被抑制。宜写：有一半改名成功即按改名成功处理并置标记；③ 提交之后按提交后的状态重新求指纹，I2 照常。这是双重故障中的再一次故障，有界。
    6. **`syncing` 期间的其他事件**：`06` L139 只对 ③ 自己的改名写了 “提交之后重新判定”。在最后一次读写卫星与带回的最终事务之间，卫星若被别的原因删除，事件被排除、之后不再判定，要等 10 分钟的周期检查或下一次启动。宜把 “`syncing` 清除的事务之后按提交后的状态重新判定本行” 推广到所有事件。
    7. **重启清理的顺序与文案**：`06` L116 写 §6.1.6 的检查 “在接受 UI 命令之前” 执行，而 `13` L324 写重启清理（终止上一次 Run 的后台进程）“在冷启动之后后台执行，完成前相关 Goal 显示‘正在清理残留进程’”。两处的先后不同；这条文案只出现在 `13`，没有进 `04`/`12`；清理期间 `goal.resume`/`goal.take_over` 是否等待，也没有写。`06` L145 的 “恢复开场含 `tower.processes_terminated`” 已隐含 Run 要等清理结束，宜写明。
    8. **`04` L667 的两个罕见分支**：
       - ③ 的改名本身失败（`06` L914 “写明工作目录未恢复”）；
       - ① 的物化也失败（“此后不可恢复”）。
       这两支在 `04` 中没有提示文案，实现者容易沿用 “工作目录已恢复原样” 一句。条目内容的唯一定义在 `06`，`04` 宜补两句。
    9. **`保留的目录` 一行的位置**：`04` L667 把它放在目标页右栏末尾，但右栏的定义（L354）与按模式的表（L372）中没有它。评审与终态模式的右栏只有 “合同摘要”，而 `.kept-*` 恰恰在 Goal 终结之后仍然存在。该行写 “副本与原来的工作目录”，`10` L256 还包括 `_gitdirs/<goalId>.kept-*` 与 ① 的旁路目录，宜同步。
    10. **`12` L680 的措辞**：“`secrets.access` 批准卡片及其风险行属 M2，M1 不出现”，指的是 M2 的机密注入卡片。M1 中读取凭据的 `secrets.access` 卡片确实出现（`04` L1133、`11` L162），宜改为 “注入机密的批准卡片”。卡片上的 S2 句子在 `12` 中也没有登记。
