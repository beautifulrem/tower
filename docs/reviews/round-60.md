**ADR-187 的主干没有引入回归**：

- **Tower 工具来源自检**：`05` L374–378（唯一定义）、L393，`03` L94，`04` L972，`00` L98，`11` L218，`16` L260 一致；按 Pi v1.2.0 的注册规则，加载期注册的同名工具都能被检出。但自检的**时机**早于 `session_start`，见 R60-D5-01。

- **标签写入点**：`07` L1679、L1690，`16` L53，`06` L899、L928，`04` L1371 一致。覆盖哨兵后 `exec_not_run` 的 Goal 不再显示 `▲*`、不写 `Tower-Verified-At`。
- **“通过”收窄**：`03` L71（唯一定义）、`16` L38、`07` L1578/L1588、L1652 一致。逐个核对了消费者：
  - 唯一的判定点是 `decide()` 的 `humanTouched`。收窄只会让窗口起点更早，因此只会把原本“自动返工”的失败改判为 `human_change_verify_failed`，不会反向；
  - 受影响的只有“未经机器验证进入评审之后、且其间没有把工作交给 Agent 的决定”的失败，例如 S0 被拒后又授权重新验证、修订合同加入 exec 标准。改判方向是更严格，与收敛规则“拿不准时取更严格”一致；
  - 验收延续只在 `outcome == pass` 时发生，标签总是 `verified`，所以“经验收延续回到 `accepted`”永远算通过，与 G33e(j) 一致；
  - G33e 各组的期望都不依赖“未经机器验证算通过”。
- **§8.8 一出口一类**：表头规则写明“单列优先、通用行补缺”。逐行核对了新通用行“交还或 `resume` 解除对应暂停原因 → actionable”与各单列行，没有发现两类并存：`stop_condition` 的“这里不该停”、`stalled` 的“继续且 10 min 内有进展”都由单列行优先。

**新发现 5 条：重要 1，次要 4**：
- **重要**：
  - `s0.deny`（以及 `use_defaults` 下的超时拒绝）把继续目标直接改写为 `review{in_review, pin}`，绕过了 `decide()`。`decide()` 在检查阻断哨兵与 artifact 失败**之前**就返回 `s0_grant_pending`，所以这时 pin 上已经算出的阻断命中与失败的 artifact 标准都不会被看到。ADR-187 又把这条路径的标签固定为 `exec_not_run{s0_denied}`。按正文实现，带有未覆盖阻断命中的 pin 会进入 `in_review` 并可被验收，违反“阻断集合阻止进入评审”的不变式（R60-D7-01）。
- **ADR-187 派生或暴露的次要条目**：
  - Tower 工具的来源自检在 `bindExtensions`（`session_start`）之前执行。Pi 支持在 `session_start` 或之后注册工具，优先级按扩展位置而不是注册时间，所以晚注册的同名工具不会被检出（R60-D5-01）；
  - 从 `in_review` 选“不合并并归档”不写分支，同时删除卫星。M1 没有导出与取回入口，被验收的改动对用户不可达，而面板上没有后果说明（R60-D4-01）；
  - `16` §16.3 为诊断视图补登 `⇧J`/`⇧K` 时，与已有的“轨迹、诊断”行重复，并且方向相反（R60-D15-01）。

### D7 诚实与验证

**R60-D7-01｜重要**（`s0.deny` 与 `use_defaults` 下的超时拒绝把继续目标直接改写为 `review{in_review, pin}`，不经过 `decide()`。`decide()` 在检查阻断哨兵与机器标准结果**之前**就返回 `s0_grant_pending`，所以这个 pin 上已算出的阻断命中与失败的 artifact 标准都不会被看到；ADR-187 又把这条路径的标签固定为 `exec_not_run{s0_denied}`）

- **问题**：
  1. **pin 上的结果在暂停前已经写入**：
     - `07` L378–388：`pinSafetyCheck`、L-c 静态哨兵与 artifact 标准都在 S0 分支之前运行，“openSentinels 因此总含本次结果”；
     - `07` L413–417：S0 未授权时 `return done({ s0: "pending" })`；
     - `07` L1570–1571：`decide()` 的第一项检查就是 `s0 === "pending"`，直接返回 `paused(s0_grant_pending)`。阻断检查（L1617）与 `outcomeOf` 的 artifact 判定（L1561–1563）都没有执行。
  2. **拒绝时不再判定**：
     - `06` L899：拒绝 → 继续目标改写为 `review{state:"in_review", pin}`，解除本原因；
     - `07` L1679：`review` 目标“回到 `state`，不验证”，标签取 `exec_not_run{s0_denied}`（ADR-187）；守卫只比较树；
     - `03` L58、L87 与 `06` L271 也写“拒绝授权 → `in_review`”；
     - `use_defaults` 下超时由系统写 `denied_timeout`，“按拒绝处理”（`06` L899）。所以这条路径可以**没有任何人的决定**就走完。
  3. **与 `decide()` 自身的结论矛盾**：同一个 pin，如果在验证开始前 `s0Grant` 已经是 `denied`，会走 `07` L418–419 的 `done({execSkipped:"s0_denied"})`：
     - artifact 标准失败 → `outcomeOf` 为 `fail` → 按归因返工或 `human_change_verify_failed`；
     - 有阻断命中 → `paused(sentinel_high)`（`07` L1656；L1649 的 `in_review` 行限定“阻断命中：无”）。
     - 先暂停、后拒绝，结局却是进入 `in_review`。
  4. **之后也拦不住**：
     - 验收闸的“阻止”项（`04` L536）不含未覆盖的阻断哨兵，因为按不变式它们不可能出现在评审中；
     - 验收只重做 `pinSafetyCheck`（`06` L919），所以只有 `nested_repo`/`symlink_escape` 会在验收时再被拦下；
     - 其余阻断类，例如 diff 中的密钥、受保护路径、不允许的新增依赖、修改已有迁移、`lifecycle_script_changed`、R-T1 forbid 残留（`07` §7.10.1），都可能不经带结构化原因的 `override_sentinel` 就被验收。这样也没有 `Tower-Override` trailer 与 ⑦，标签与学习数据都失真。
- **为什么是重要**：按 `06` L899 与 `07` L1679 实现，会违反已声明的不变式：“阻断 in_review”是 Verified 定义与 `decide()` 唯一使用的阻断集合（`07` L1462）；`03` L58 规定进入 `in_review` 须“无高严重度哨兵”；阻断命中须由人以结构化原因覆盖（ADR-107/109）。触发条件是 S0（M1 中用户关闭沙箱即可，`11` L330）加上一次拒绝或一次超时，不需要罕见组合。标签本身仍是诚实的（“未经机器验证”），所以不是阻断级。
- **文档位置**：`03` L58、L87；`04` L536、L1500；`06` L271、L899、L919；`07` L378–388、L413–419、L1462、L1570–1571、L1617、L1648–1649、L1656、L1679；`11` L330；`14`（没有覆盖此路径的用例）。
- **期望的回答形态**：在 `06` L899 唯一定义，二选一：
  - **拒绝改写为 `verify{pin}`**（`s0Grant` 已置 `denied`/`denied_timeout`）：离开暂停时重新验证同一 pin，走 `07` L418–419 的 `done({execSkipped:"s0_denied"})`。只重跑 `pinSafetyCheck`、静态哨兵与 artifact 检查，不取槽位、成本很低；
  - **或者在拒绝的同一事务中**，以已写入的 Fact 调用 `decide(goal, pin, trigger, {execSkipped:"s0_denied", by})`，按其结果转移（`fail` → 归因去向；阻断 → `sentinel_high`；否则 `in_review` + 标签）。

  - G46 或 G33 补一组：S0、pin 带一条阻断静态哨兵与一条失败的 artifact 标准，分别以人拒绝与 `use_defaults` 超时拒绝，期望 `paused(sentinel_high)` 与返工 / `human_change_verify_failed`，不进入 `in_review`。

  - **不扣分的观察**：
    1. **其余进入 `in_review`/`accepted` 的转移的标签**：`07` L1690 的“唯一写入点”只写了两个来源（`decide` 与 `review` 继续目标）。没有写到的转移有：
       - `goal.accept`（`in_review` → `accepted`，seal trailer 正在这一步读标签）；
       - `goal.undo_integrate`（`integrated` → `accepted`）；
       - 较旧 seal 被合入后 `accepted` → `in_review`（ADR-137）。
       - `02`/`06` 也没有存放 `label` 的字段或列，只能从事件中回溯。多数实现者会沿用上一次写入的标签，建议在 L1690 写一句“其余转移沿用最近一次写入的 `label`”，并说明它是否投影到 `goals`。
    2. **“第二次 accept”的记录内容**：`02` §2.7 `HumanDecision` 没有 `integrate` 字段，`06` L919 却写“只记 `human.decision{accept}`（`integrate:"none"`）”。从 `accepted` 归档时不重做闸口，该决定记录的合同版本与各单元 contentHash 也没有写明（`04` L542 说验收记录这两项）。建议注明存放在 `human_decisions.payload`，并沿用上一次验收的值。
    3. **归档与集成观测的边角**：
       - `10` L1129 规定“Goal 进入 `accepted` 时（任何来源）”判定 `integrated`；从 `in_review` 走 `none` 时 Goal 在同一事务中短暂进入 `accepted`。此时“最近一次验收的 seal”指上一次验收的 seal，还是本次（无 seal）的验收，没有写。多数情况下“卫星树等于该 seal 的树”不成立，所以不会触发；
       - 从 `accepted` 归档时，人可能已经合入、只是 Tower 还没观测到，Goal 会以“未合并”归档。北极星条件 3“合入后 14 天内未被 revert”（`14` L651）对未合并的已验收 Goal 怎么计也没有写。
       - 都不影响状态安全，建议在 `06` L919 或 `14` §14.6.1 各补一句。
    4. **只读白名单的两种读法**：`16` L122 在“Pi 内置的只读工具”括注中写“覆盖了这些名字的扩展工具不在白名单中”，同一句末尾又接受“声明 `readOnlyHint:true` 且通过路径检查的工具”。带注解的 `read` 覆盖者算不算白名单，读法不同；Pi 示例 `tool-override.ts` 不带注解，所以 G46(be)(1) 的期望不受影响。建议把括注改为“覆盖了这些名字的扩展工具不按本项进入白名单（仍可按末项）”。
    5. **`07` L1528 的旧概括句**：“run 类阻断命中保持打开，仍须人以带结构化原因的 `override_sentinel` 处置”不适用于不可覆盖的 `nested_repo_live`（同节 L1526 与 `16` L151 已写明）。建议改为引用 `16` §16.1.6。
    6. **阶段工具集按名字激活**：`05` L674–676 的 shaping / review 阶段以名字 `setActiveTools(["read","grep","find","ls",…])`，扩展覆盖这些名字时激活的是扩展版。门禁按来源归 `tool.external` 逐次 ask，不越权，但塑形与评审阶段会出现审批卡。建议在 `05` §5.6.2 注明。
    7. **依赖“满足”的定义**：`06` L305 的“`dependsOn` 全部满足（`03` §3.5）”在 `03` §3.5 中没有定义，`03` L55 只定义了依赖回退（验收失效或被放弃）。依赖的 Goal 经“不合并并归档”结束时，依赖方是否满足、以哪个分支为 base，读法不同。Goal 依赖不在 ADR-059 的 M1 清单中（`14` L189），所以只记为观察，建议 M2 前补定义。
    8. **`08` §8.8 与 `07` §7.11.1 的投影**：`07` §7.11.2 称可行动率“就是 `08` §8.8 告警精度在检测器维度上的投影”。但对 `nested_repo_live` 的 `resume`（附转向），`08` 按新通用行定为 `actionable`，`07` §7.11.1 的 TP-actionable 列表中没有它。M1 只展示不调节，影响限于周报。
    9. **`03` L192 的冲突雷达**：“共享资源冲突被冲突雷达视为隐式依赖”没有 M2 标记（同类的 L147 已补）。
    10. **连续缓存命中**：`07` L897 的前提是“原验证该标准的完整日志仍在”。上一次本身是缓存命中时，“原验证”应指被引用日志所属的那次运行，而不是上一次命中（它没有自己的日志文件）。按字面实现只会多跑一次，不影响正确性。建议写明“沿引用链取实际运行的那次验证”。
    11. **取舍判断**：ADR-187 复用 `accept` 决定种类、以自检代替 `customTools`、收窄“通过”、完整重哈希一致时不留证据，都写得诚实、方向偏严或中性，可以接受，判断见 §3.3。
- **设计是否完成：主干已收敛。** 第 59 轮的全部条目与观察都已落地，ADR-187 的“一条守卫、一处计算、一处删除”在各文档中一致，没有引入状态、事件或表。剩下的 5 条：

  - **前几轮没扫到的旧处**：角色容量表（R60-D14-01）。
