## 1. 总评

ADR-160 把运行中的拦截换成调度层的互斥，方向正确，R34 的四条重要项中有三条的主体问题因此消失：gate 第 0 步、嵌套调用自锁、开启握手、`SIGSTOP`。Pi 依赖面缩回到一个只传 `toolCallId` 的包装，经源码核实成立；排期算术全部成立（WBS 121.38、38 周）。

仍有三处重要缺口：
- “Agent 活动”漏掉了**其他验证槽位**，两个带机密的标准可以并发运行；
- `secrets.access` 放行之后**既不冻结准入，也不处置后台后代**；
- Agent 怎样**请求注入**某个机密，没有定义。

另有三条次要项。

### D4 领域模型与生命周期

**R35-D4-01｜次要**（`approved_waiting` 没有建模：所属实体、`requestId`、暂停与重启时的去向、不接受风险的出口、实况行）

- **问题**：
  1. **所属实体与标识**：
     - `approved_waiting` 被称为“该请求的状态”（`11` L431，`15` L1453），但 `02` 中没有这样一个请求实体，也没有这个状态值；
     - `secrets.access.use_now{goalId, requestId}`（`06` L856）中的 `requestId` 在任何地方都没有定义：它是 Needs-You 的 `itemId`、`TowerDialog.reqKey`，还是 `toolCallId`？
  2. **转移没有写**：
     - 持有者在 `approved_waiting` 中被人暂停、因预算硬上限 drain、被放弃时，这次已批准的请求是作废（下一个 Run 重新询问），还是保留？
     - Supervisor 在 `approved_waiting` 中重启时（`06` L63：Host 继续运行，“未决的对话框保持等待”），重启后怎样知道这个对话框已获批准、正在等待互斥，而不是尚未回答？
  3. **只有接受风险一个出口**：
     - 卡片只提供“现在使用（接受风险）”（`04` L1112）。人若不愿接受风险、又不想无限等待，唯一的办法是暂停整个 Goal；
     - 两个 Goal 同时处于 `approved_waiting` 时，互相把对方视为活动，只能靠人解开，界面也没有提示这一点。
  4. **呈现**：
     - `12` §12.6.4 没有它的实况行；
     - `05` L979 写“已批准，等待其他 Agent 结束”，`04` L1112 写“等待其他 Agent 停止”；
     - `08` 没有写这张卡片在 `approved_waiting` 期间的结局分类：仍是那条 `approval` 条目，还是新条目？
- **为什么重要**：这是 ADR-160 新增的状态。实现者需要知道持久化什么、恢复时怎么做。否则重启后要么丢掉人的批准，要么在互斥条件不满足时误放行。
- **文档位置**：`02` §2.7、§2.9；`05` L979、§5.6.4；`06` L63、L856；`11` L428-432；`04` L1112；`12` §12.6.4；`08` §8.8；`15` L1453；`14` G46(i)。
- **期望的回答形态**：
  - 写明 `approved_waiting` 挂在哪里，例如 Needs-You `approval` 条目的子状态，持久化为 `needs_you` 的一列，并写明 `requestId` = 该条目的 `itemId`；
  - 转移：
    - 持有者离开 `running` 时，该请求以 `obsolete` 关闭，下一个 Run 重新询问；
    - Supervisor 重启后按持久化的子状态重新判定互斥，满足则答复，不满足则继续等待；
  - 卡片增加“撤回批准”（`deny_action`，本次调用被 block）。两个 Goal 互相等待时，卡片提示“G-xxxx 也在等待”；
  - `12` 增加实况行，并统一 `04`/`05` 的措辞；
  - G46(i) 增加两组：等待中暂停持有者；两个 Goal 同时处于 `approved_waiting`。

### D5 Agent 架构与 Pi 集成

**R35-D5-01｜重要**（`secrets.access` 的“请求注入”没有输入面；`approved_waiting` 套用到不注入环境的读取类调用）

- **问题**：
  1. **注入请求从哪里来**：
     - `11` L50 把 `secrets.access` 定义为“读取凭据**或请求密钥注入**”。但分类规则（`11` L197）与示例只列出读取类命令：`printenv`、`security find-*-password`、`gh auth token`、`cat .env`，以及 §11.3.4 中路径扫描命中密钥路径的 MCP 与扩展工具；
     - 没有任何地方写明 Agent 怎样**请求把某个密钥库条目注入**它的下一次 bash 调用：
       - 是工具参数，还是命令中对某个变量名的引用，或是 `ask_user`？
       - 注入成什么变量名？
       - 怎样核对密钥库条目的“允许的 Goal/标准”（`11` L445）？
       - 批准卡片上显示的是哪个条目？
     - `05` L369 的“单次机密表”由谁、按什么填写，也没有写；
     - G46(i) 写“Goal A 的 Agent 请求一个机密”，但按现有文档无法构造这个请求。
  2. **`approved_waiting` 的适用范围过宽**：
     - `05` L979 与 `11` L428-432 对**一切**获批的 `secrets.access` 调用都套用互斥等待；
     - 读取类调用（例如经批准的 `gh auth token`），以及非 bash 工具（MCP 路径扫描命中），根本不把机密放进进程环境，互斥对它们没有保护作用；
     - 后果：Agent 被无谓地挂起，直到其他所有 Goal 停止；卡片上“其他 Agent 可能读到”的风险文案对这类调用也不成立。
- **为什么重要**：
  - ADR-160 把注入一侧写得很具体（`toolBash`、单次机密表、`approved_waiting`），请求一侧却是空的，W6 与 G46(i) 无法照文档实现。
  - 机密条目与 Goal/标准的绑定是这条路径唯一的授权检查。它的位置不写清，就可能出现“批准了 A，注入了 B”。
- **文档位置**：`11` L50、L97、L197、L216、L428-432、L445、L447；`05` L365-370、L979；`06` L856；`14` G46(i)。
- **期望的回答形态**：
  - 定义请求形式与核对规则。例如（只作示意，取舍由作者定）：
    - bash 命令中引用的环境变量名与本 Goal 允许的密钥库条目同名时，分类为 `secrets.access{inject:[NAME]}`；
    - gate 核对条目的允许范围，不在范围内一律 `forbid`；
    - 批准卡片显示条目名（不显示值）；
    - 放行时 gate 把 `{toolCallId → [NAME]}` 写入单次机密表；
  - 写明 `approved_waiting` 与互斥**只在注入列表非空时**适用；读取类的 `secrets.access` 按普通单向门 ask 处理；
  - G46(i) 增加两组：
    - 请求不在允许范围内的条目，期望 `forbid`；
    - 读取类 `secrets.access` 在其他 Goal 运行时获批，期望立即执行、不进入 `approved_waiting`。

### D11 安全与自主度

**R35-D11-01｜重要**（“Agent 活动”漏掉了验证槽位：两个带机密的标准可以并发，其他 Goal 的验证代码与带机密标准同时运行；存活者也未计入）

- **问题**：
  1. **其他验证槽位不算活动，也不在冻结范围内**：
     - “Agent 活动”= `running`/settle/准备、Scratch、检验服务（`11` L419，`06` L233，`07` L700，`16` L499）。冻结的也只是新的 Run、Scratch 与检验服务（`11` L421，`06` L292）；
     - c 通常为 2（`07` L903-906），所以带机密的标准运行时，另一个槽位可以正在运行（或在此期间开始运行）另一个 Goal 的验证：槽位准备中的项目生命周期脚本、服务、标准命令（`07` L409、L524），全都是那个 Goal 的 Agent 写的代码；
     - 本机实测：同一用户的普通进程能读到非 Apple 二进制进程的环境。
     - 后果：
       - 那个 Goal 的**非机密**标准不受 `07` §7.4.3 规则 1、2 保护（没有耦合保护，输出末尾会回送模型），变换检测也只作用于带机密标准的日志（`07` L709）；
       - 于是一个 Goal 的机密可能以编码形式进入另一个 Goal 的返工提示，越过密钥库条目“允许的 Goal/标准”的绑定。
  2. **两个带机密的标准可以同时开始**：两个 `verifying` 的 Goal 都不把对方视为活动，R34-D6-01 第 3 项（并发窗口）在新模型下原样存在。两者都运行 Agent 写的代码，各自能观察对方的机密。
  3. **等待者是否占用槽位、次序**：
     - 没有写等待中的带机密标准是否占用槽位；也没有写同一次验证中，它排在其他标准之前还是之后（先跑完不带机密的标准、再释放或保留槽位）；
     - 若占用，c = 2 时两个等待者会挡住所有 Goal 的验证，`07` §7.4.10 与 `13` 的延迟模型没有计入。
  4. **存活者**：
     - `11` L422 断言持有者进入 `claimed`/`verifying` 时“进程已按 ADR-115/158 终止”；
     - 但 `bg_process_survived`（`06` L190）正是“终止后仍有存活者”的已定义状态，它在未解除期间同样是 Agent 控制的代码。其他 Goal 的存活者同理。
  5. **残余评级**：T33b 在互斥开启时评为“低”，残余只列“用户自己的其他进程、ADR-158 的脱离进程窗口”（`11` L613，`07` L710），没有包括上面这几类。
- **为什么重要**：
  - 第 1、2 项是跨 Goal 的授权越界，正是 T33/T33b 要防的那一类（“被并行的 Agent 观察”）。默认配置（c = 2、默认 `env`）下多 Goal 同时验证并不罕见。
  - 第 3 项是 rubric 所说的“未定义的次序”，直接影响验证延迟。
- **文档位置**：`11` L336、L418-423、L613；`06` L190、L233、L292；`07` L409、L524、L700、L709-710、L903-906；`13` L302；`16` L499；`14` G46(e)(f)。
- **期望的回答形态**：
  - 二者取一，并在 `11`/`06`/`07`/`16`/`13` 统一：
    - **验证器池互斥**：带机密的标准只在其他槽位都空闲时开始；运行期间其他槽位不开始任何工作（冻结范围扩展到验证器池）。带机密的标准之间全局串行（FIFO）；
    - 或者把“其他槽位正在运行的验证”计入 Agent 活动，同时冻结槽位的新工作。
  - 写明等待中**不占用槽位**：先运行同一验证中不带机密的标准，槽位释放后再按互斥条件排队。或者写明占用，并把它计入 `07` §7.4.10 的排队模型。
  - “Agent 活动”加入“任何 Goal 存在未解除的 `bg_process_survived`”。
  - 按最终规则改写 T33b 的残余清单。
  - G46(e) 增加两组：
    - Goal A 的带机密标准排队时，Goal B 正在另一个槽位验证；
    - 两个 Goal 的带机密标准同时就绪，期望串行。
  - G46(f) 增加一组：带机密的标准运行期间，Goal C 进入 `claimed`，期望它的验证排队。

**R35-D11-02｜重要**（`secrets.access` 放行后：准入不冻结，后台后代带着机密环境运行到持有者 settle）

- **问题**：
  - 不变式写作“机密在环境中期间，没有其他 Agent 活动”（`11` L336）。对验证器标准，它由“开始条件 + 冻结准入 + 结束时终止槽位进程”三件事共同保证。对 `secrets.access`，只有第一件：放行时没有其他活动（`11` L430、`05` L979）。
  - 缺的第二件：放行之后，那次调用最长可运行 1800 s（`05` L963 的默认 `timeout`）。`06` §6.2.4 的冻结只针对“带机密的验证标准”，所以这段时间内其他 Goal 的 Run、检验服务照常被准入。
  - 缺的第三件：
    - 那次调用中转入后台的进程继承了机密环境，调用结束后仍在运行，直到持有者的 Run settle 才被终止（`06` L190）；
    - 持有者的 Run 可能还要运行数小时，期间其他 Goal 被准入、开始运行；
    - R34-D11-02 第 1 项提出的正是这一点，ADR-160 只处理了验证槽位一侧。
  - 人选择 `use_now` 时，风险文案只覆盖“此刻”正在运行的 Agent；后来被准入的 Agent 不在人的知情范围内。
- **为什么重要**：在后台启动一个带机密的服务（例如带 API key 的开发服务器）是 Agent 的常见做法。这正是 T33b 的 `secrets.access` 一半要防的情形，而 T33b 评级的前提在这条路径上不成立。
- **文档位置**：`11` L336、L414、L428-432、L447、L613；`05` L963、L979；`06` L190、L292；`14` G46(i)(j)。
- **期望的回答形态**：
  - 二者取一：
    - **调用结束即收尾**：从放行起冻结准入，直到那次调用结束。结束时 Tower 终止由该次调用派生的全部进程：`exec` 已知该调用的直接子进程，再取其进程树 ∪ 令牌中派生于它的部分。工具结果注明“带机密的后台进程已随调用结束而终止”。随后解冻；
    - **冻结到持有者 settle**：从放行起冻结准入，直到持有者本 Run settle 并完成进程终止；`13` 写明这段冻结的上限与对吞吐的影响。
  - `use_now` 的确认文案写明它覆盖的时间段：只到调用结束，或到本 Run 结束。
  - 脱离进程树、又无法识别的后代，归入 ADR-158 的已登记窗口，在 T33b 中写明。
  - G46(i) 增加两组：
    - 获批调用在后台启动一个长期进程后结束，期望该进程被终止（或准入一直冻结到 settle）；
    - 获批调用运行期间，另一个 Goal 请求开始 Run，期望排队。

### D13 隔离、git 与并发

**R35-D13-01｜次要**（`baseTip` 未选择时“返回 `baseCommit` 所在的一侧”有歧义）

- **问题**：
  - `10` L139、`06` L239、`15` L1449 都写“返回 `baseCommit` 所在的一侧，即‘不变’”。
  - 上游强制推送最常见的形态是只改写 `baseCommit` 之后的提交。这时两侧都以 `baseCommit` 为祖先（本机 git 实测），“所在的一侧”同时指两侧。
  - 若实现者照字面返回其中一侧的 tip，§10.1.2 L157 的前进检测会判为“base 前进”并记 `base_advanced`；`integrated` 观测也会在那一侧上进行。这与“即‘不变’”和 G45(c) 第三组的期望（“视为不变”）矛盾。
- **为什么重要**：`integrated` 是生命周期转移。R34-D13-01 担心的“在被强制推送覆盖的历史上观测到已合入”，取决于这句话怎么实现。
- **文档位置**：`10` L139、L157；`06` L239；`15` L1449；`14` G45(c)。
- **期望的回答形态**：改为“分叉且尚未选择时，`baseTip()` 返回 `baseCommit` 本身”。前进检测与 `integrated` 观测因此都不成立，直到人选择。三处同步。

### D15 文档一致性与可执行性

**R35-D15-01｜次要**（仍未同步的说法与 ADR-160 引入的不一致）

- **问题**：
  1. **`02` L547、L567**（自 R32 起第四次提出）：`owner` 注释仍不含项目级凭据卡片；`integration` 仍注为“M2：推送失败……去重键 `int:{goalId}`”，没有 macOS M1 的项目级用法 `int:{projectId}:credential_url`（`08` L209）。
  2. **`04` L1471**：
     - 凭据卡片只写“此远端的 URL 中带有凭据”，没有覆盖配置键（`08` L209、G45(f) 要求写明命中的配置键）；
     - 目标卡片的 `◇ 无法获取远端 base` 在这里没有事实来源：被拒绝时不会获取，也就不会有 `base_fetch_failed`；
     - `08` L503 的自动关闭条件也只写“URL 不再含凭据”。
  3. **密钥库的两种说法**：
     - `11` L398、`15` L1405、`07` L697 写“只存在系统钥匙串”；
     - `11` L445、`06` L1047 写 `~/.tower/secrets.enc`（`safeStorage` 加密，密钥在钥匙串中）。
     - 照前者会用 Keychain 条目实现，照后者会用加密文件实现。
  4. **`13` L302**：把 `approved_waiting` 与验证器等待放在同一行，并说“等待 10 min 后生成 `ve:{goalId}:secret_wait`……期间 Goal 保持 `verifying`”。对 `approved_waiting` 而言，两点都不成立：Goal 是 `running`，`11` 也没有给它 10 分钟的条目。
  5. **`16` L372-373**：ADR-159 两行的“新说法”列仍写“在独占窗口内运行”“受独占窗口保护”。lint (d) 把它们视为历史而放过，但这一列的含义是“现行说法”。
  6. **`05` L1412（C29(c)）**：开头写“机密只进入**验证槽位**”，与同一格末尾的 `secrets.access` 单次注入矛盾。
  7. **注入点**：`11` L447 写 `secrets.access`“经 `spawnHook` 注入”，`05` L369、L979 写由 `exec` 按单次机密表加入。两者都能实现，但必须选一个，契约测试才知道该测哪一处。
- **为什么重要**：
  - 第 1–3 项分别是数据模型、凭据卡片与密钥存放的实现依据；第 4 项会让实现者给 `approved_waiting` 也生成 `secret_wait` 条目。
  - 其余是同一事实的不同说法。
- **文档位置**：见上。
- **期望的回答形态**：
  - 逐处改写。第 3 项建议统一为“密钥库（`~/.tower/secrets.enc`，`safeStorage` 加密，密钥在钥匙串中）”；
  - `13` L302 拆成两行；
  - `16` L372-373 的“新说法”改为指向 ADR-160 行；
  - lint (d) 的历史豁免不应覆盖废弃表的“新说法”列。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D7、D9、D12、D14、D16 为 100，这八个维度上没有可追问的实质问题。
  - D4 99、D5 96、D6 98、D8 99、D10 99、D11 88、D13 99、D15 98。
- **是否还有可追问的问题：有。** 新增共 **6** 条：阻断 0、**重要 3**、**次要 3**。
  - **第 34 轮核验**：已解决 1（R34-D5-01），部分 6（R34-D4-01、R34-D6-01、R34-D11-01、R34-D11-02、R34-D13-01、R34-D15-01），未解决 0。
  - **其他核对**：
    - lint 全部通过；
    - `toolBash` 包装、gate 无超时等待、并行批次的准备次序与 Pi v1.2.0 源码一致；
    - 同用户读取非 Apple 二进制进程环境、强制推送后两侧共同祖先，两项均经本机实测；
    - 排期算术全部成立：WBS 121.38、38 周、余量 0.19–1.04、增人 33 周。
  - **不扣分的观察**：
    - **饥饿**：等待期间不冻结准入，系统繁忙时带机密的标准几乎总会等到 10 分钟。这是有意的取舍：结局安全，由人决定，`13` L302 也如实说明了延迟影响。不扣分。
    - **人工检出中由人启动的进程**：人在检验或人工编辑检出的终端、IDE 中运行 Agent 写的代码，属于 T33b 已登记的“用户自己的其他进程”。不扣分。
    - **MCP 服务器与用户扩展的子进程**：由 T28 登记，评级合理，不重复计入。
- **设计是否完成：否。**
  - 调度互斥比独占窗口简单得多，也更可实现，R34 的拦截类问题已经全部消失。
  - 但“没有其他 Agent 活动”这条不变式还有两个出口没有关上：
    - 验证器池内部（R35-D11-01）；
    - `secrets.access` 放行之后（R35-D11-02）。
  - `secrets.access` 的请求一侧也还没有定义（R35-D5-01）。
  - 三者都只需补规则与用例，不需要新架构。
- **下一轮建议按以下顺序修订**：
  1. **R35-D11-01**：
     - 验证器池互斥（带机密的标准之间串行，其他槽位冻结），或把槽位计入活动；
     - 等待中不占用槽位，以及同一验证内的次序；
     - 存活者计入活动；
     - T33b 残余改写；
     - G46(e)(f) 加三组。
  2. **R35-D11-02**：从放行起冻结准入，调用结束时终止其派生进程（或冻结到 settle）；`use_now` 文案写明覆盖的时间段；G46(i) 加两组。
