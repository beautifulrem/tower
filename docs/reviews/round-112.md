## 1. 总评

**第 111 轮的 7 条条目在所问的范围内都已改写**（核对见 §3）：
- T1 在写回开始之前由 `handback-t1` 引用，只在写回成功时删除，不按时间删除，清除时列出；
- Tower 不重新建立根；新 Goal 从准备开始计入将要使用的根；迁移的新记录与标志在迁移事务中写入；
- 写回中断时迁移返回列出原因的 `E_STATE`，界面不列出迁移；
- F13 按处理器计数，以 `anomaly{tower_goal_handler_error}` 自报，来源清单只在 `16` §16.1.1；
- 脱敏覆盖 `details`，占位结果带 `details: {}`；
- `flake` 在判定之后写；base 无结论是环境故障；准备与服务的任何失败先判可达；
- 六处措辞。

第 111 轮 §5 的 9 条观察都已落地。

**ADR-239 按 “类” 关闭了上一轮的主要缺口，但三处 “类” 的边界没有完全合上**：
- **T1 的引用**：ref “每个 Goal 至多一个”“已有时改指它”。写回失败 ① 的物化也失败之后，它是你改动唯一的副本，而 `human_checkout_lost` 卡片推荐的 “再次接管” 与下一次交还会把它改指到新的 T1。ADR-239 的不变式 “没有任何出口使 T1 成为不被引用的对象” 照文字不成立（R112-D13-01）。
- **迁移的次序**：新记录与 `satellite_rebuilding=1` 提前到迁移事务之后，与两条既有规则冲突（R112-D13-02）：
  - 卫星重建中途崩溃一行假定 “原路径上只可能是重建自己 rename 到位的目录”；
  - “Tower 只在没有任何当前 `WorktreeRecord` 时建立根”。
- **“界面不提供会被拒绝的动作”**（R112-D13-03）：
  - 只覆盖 ③ 与 `syncing`，没有覆盖中断留下的 `satellite_rebuilding=1`（迁移 `E_BUSY`）与卫星守卫（`放弃改动` 返回 `E_STATE`）；
  - 隐藏迁移的条件又比命令宽。

**扫描发现的其他缺口**：
- **R112-D6-01**：失败先判可达对卫星重建与接管物化只认文件系统错误码，对 git 子进程的非零退出不适用；新 Goal 仓库准备中的失败不在其列；排队中的新 Goal 在复查时是否重新判断 “可建立” 没有写。ADR-239 只为验证中的子进程补了 “任何非零退出”。
- **R112-D7-01**：
  - base 确认确定性地无结论时，`verify_env` 的出口（重试、修改验证档案、暂停）都解决不了，`test.quarantine` 没有界面入口；
  - `env_error` 优先，使同一 pin 上其他标准的真实失败不返工；
  - §7.4.5 的 base 对照运行没有 “无结论” 一支。
- **R112-D15-01**：
  - `03` L55 仍复述不含 F13 的 `prepare_failed` 来源；
  - `06` L945 `signal.acknowledge` 不含新检测器；
  - `16` L661 的现行列仍写已被 ADR-239 取代的两条规则；
  - `08` L520 “改动已无法恢复”；
  - `10` L925、L996 的写回步骤没有 `handback-t1` 一步；
  - ADR-239 说要如实登记的 “挂载点目录中建立根” 没有写进 `06`、`10`；
  - `04` L1522 与 `12` L416 的迁移隐藏条件（并入 R112-D13-03）。

    - ADR-239 为验证补了 “验证中的子进程……以任何错误或非零退出失败时……先判可达”，理由是 “卷消失时子进程通常以非零退出，而不是 Tower 自己的文件系统错误码”（`06` L139）。
    - 同一理由同样适用于卫星重建与接管物化。两者都以 git 子进程完成主要工作：情形 E 的 `clone --separate-git-dir`、`checkout-index`，接管的 `read-tree` 与 `checkout-index`（`10` L361–L363、L952）。
    - 但 `06` L139 对它们只写 “以文件系统错误失败（`ENOENT`、`EIO` 等）”；`06` L140 的重建失败同样只写 “文件系统错误先按……失败先判可达”。
    - 卷在重建中消失、git 以非零退出时，结果是 “重建失败”：
      - 清除 `satellite_rebuilding`、进入 `satellite_missing`，生成需要你重试的条目；
      - 而不是 ② 的中断、可达后由 ④ 自动续做。
    - 接管物化同理。
  - **(b) 新 Goal 的仓库准备**：
    - ADR-239 把将要使用的 `<wtRoot>` 从准备开始计入必需路径，准备开始时不可访问则 “按 ② 中止、回到排队”（`06` L139，`10` L361）。
    - 但准备中途根变为不可访问时，clone、checkout 或 LFS 写出失败。失败先判可达的枚举（写回、验证、卫星重建、接管物化）不含仓库准备，所以按 `16` L29 “仓库准备……失败” 进入 `paused(prepare_failed)`：不在启动时自动解除，卡片写 `启动失败：…`，真正的原因（卷不在）不出现。
    - 这与 ADR-239 “不另设 `prepare_failed` 来源，复用已有的不可达处理与出口” 的意图相反。
  - **(c) 排队中的新 Goal**：
    - 准入检查 i 只看 “它的必需路径都可访问”（`06` L324）。
    - 新 Goal 没有记录，准备中止之后 “将要使用的 `<wtRoot>`” 是否仍计入它的必需路径，没有写。
    - 若不计入：检查 i 通过，准备再次开始又中止，反复执行镜像 fetch 与 LFS 补齐。
    - 若仍计入：④ 的复查只判 “可访问”，不判 “现在可按规则建立”（例如其他 Goal 的记录已结束）。这个 Goal 会一直不可达，直到重启。
- **为什么是次要**：
  - 三者都要求卷在操作的特定阶段消失，或根在准备开始后改变状态。
  - 后果是多一次手动重试、一张写错原因的卡片，或一次重复的准备，不丢数据。
  - 但这是 ADR-239 声明 “按类关闭” 的那一类：同一个 “卷消失时子进程以非零退出” 的理由，只用在了验证上。
- **后果的类别**：
  - 卷短暂消失时，重建与接管停在需要手动重试的 `satellite_missing` 或失败上，而不是自动续做；
  - 新 Goal 停在 `prepare_failed`，显示错误的原因；
  - 排队中的新 Goal 反复准备，或一直不可达。
- **文档位置**：`06` L139（失败先判可达的枚举、新 Goal 一句）、L140、L324、L1199（F4b）；`10` L361–L363、L952；`16` L29。
- **期望的回答形态**：
  - `06` L139 的失败先判可达改为：卫星重建、接管物化与新 Goal 仓库准备中的子进程以任何错误或非零退出失败时，同样先判可达，与验证同一句；`06` L140 引用；
  - 写明新 Goal 准备中止之后，“将要使用的 `<wtRoot>`” 仍计入它的必需路径，直到它有记录或被放弃；④ 的复查对缺失的根同样按 “Tower 不重新建立根” 判断能否建立。

### D7 诚实与验证

**R112-D7-01｜次要**（确定性的 base 无结论没有出口；`env_error` 优先使其他标准的真实失败不返工；§7.4.5 的 base 对照运行没有无结论一支）

- **问题**：
  - **(a) 出口**：
    - ADR-239 之后，只因无结论而不能通过的标准记 `verify_env_error{stage:"baseline"}`，Goal 进入 `paused(verify_env_error)`（`07` L876–L888，L1688）。
    - 回应自己举的例子是 “base 的依赖已无法安装这类确定性的故障”。这类故障在 base 不变时每次重试都一样。
    - `verify_env` 的出口是：
      - `重试 / 打开验证档案 / 暂停`（`07` L1688、`08` L533）；
      - `重试验证 / 打开项目验证配置 / 查看安装器日志`（`04` L1507）。
    - 没有一个能解决它：验证档案改不了 base 的锁文件。
    - 真正能解决的动作不在卡片上：
      - `test.quarantine`（`06` L918）：隔离之后 base 确认被跳过（`07` L869）；
      - 把该标准改为 human 标准的修订。
    - `test.quarantine` 唯一的界面来源是 `flakeLedger` 的 ratify 提议（`07` L891），而无结论从不写入台账，所以这个测试永远不会成为提议。
  - **(b) `env_error` 优先**：
    - `outcomeOf` 先查 `latestVerifyEnvError`，有则返回 `env_error`（`07` L1586–L1587）。
    - ADR-239 之前，无结论 → `introduced` → `fail` → 返工。现在标准 A 的 base 确认无结论时，同一 pin 上标准 B 的真实失败也不返工，Goal 停在环境故障上。
    - 与 (a) 叠加，A 的故障是确定性的时候，B 的失败永远不会交给 Agent。
  - **(c) §7.4.5 的对照运行**：
    - 超时与资源超限的判别中 “base 上没有历史 → 在 base 上跑一次该标准作为对照，再按上两行判定”（`07` L852）。
    - 上两行只有 “base 上同样超时/超限” 与 “base 正常而 pin 两次超时”。base 的依赖物化失败时，对照运行两者都不是。照字面会落入 “计为失败，触发返工并计次”。
    - ADR-239 把 §7.4.6 的无结论定为环境故障，理由是 “与 §7.3 安装器失败、§7.4.5 base 上同样超时同一原则”，但 §7.4.5 自己的对照运行没有这一支。同一根因（base 无法物化）在 §7.4.5 归 Agent、在 §7.4.6 归环境。
- **为什么是次要**：
  - (a)(b) 要求 base 上的确定性故障，同时 pin 上有时过时不过的测试；(c) 要求 base 上没有历史。
  - 后果是 Goal 停在需要你处理的状态，或多几次返工，从不得出绿色。
  - 但 (a) 让 Goal 停在一个卡片给不出有效出口的暂停中，违背 D8 “可逃逸”。(c) 与 ADR-239 自称的原则不一致。
- **后果的类别**：
  - Goal 停在 `verify_env_error`，卡片上的动作都无效，只能从别处修订合同或放弃；
  - 其他标准的真实失败被遮蔽，不返工；
  - 同一类环境故障在超时判别中仍按 Agent 的失败计返工。
- **文档位置**：`07` L852、L869、L876–L888、L891、L1586–L1587、L1688；`08` L201、L533；`04` L1507；`06` L918。
- **期望的回答形态**：
  - `verify_env` 卡片在 `stage:"baseline"` 时另列出口：`隔离该测试`（`test.quarantine`，仅本机，`06` L918）与 `改为 human 标准`（同 `07` §7.4.6 已有的 `contract.amend` 入口），并写出无结论的用例；
  - `outcomeOf` 写明 `baseline` 的环境故障不遮蔽其他标准的 `fail`：有其他标准失败时照常返回 `fail`，返工消息分开列出；或如实登记取舍；
  - §7.4.5 的 “base 上没有历史” 一支补上：对照运行无结论（检出或物化失败）时记 `verify_env_error{stage:"resources"}` 或 `baseline`，不计返工。

### D13 隔离、git 与并发

**R112-D13-01｜次要**（`handback-t1` “每个 Goal 至多一个”“已有时改指它”：它是唯一副本时，下一次交还或带回把它改指到新的 T1，旧 T1 不再被引用，由影子 gc 回收；ADR-239 的不变式照文字不成立）

- **问题**：
  - **只有一个 ref**：
    - `10` L246 写 “每个 Goal 至多一个”；
    - `06` L923 写交还与带回在写 `syncing` 之前写 `handback-t1`，“已有时改指它”。
  - **它是唯一副本的情形**：写回失败 ① 的重新物化也失败时，条目写 `你的改动未能保留在目录中，仍保存在 Tower 中（目标页写明如何取回）`，交还随后按检出丢失一行处理（`06` L923、`04` L671）。
  - **卡片推荐的动作**：
    - `human_checkout_lost` 条目另写 `最近一次未写完的交还仍保存在 Tower 中`，选项的第一项是 `再次接管`（`06` L145，`08` L520）。
    - 再次接管由检查点 k 的树 T0 物化新的人工编辑检出（`10` L952），其中没有旧 T1 的改动。
    - 之后的交还写 `handback-t1` 时把它改指到新的 T1′，旧 T1 不再被任何 ref 引用：
      - 交还成功时 ref 被删除，旧 T1 立即不被引用；
      - 交还失败时 ref 指向 T1′，旧 T1 同样不被引用；
      - 影子 gc 在宽限期后回收旧 T1（`10` L1306）。
    - 写入时的 bundle 也随之更新，不留旧 T1（`10` L1290）。
    - 检验带回同理：① 失败之后再次打开检验并带回。
  - **与唯一定义的冲突**：
    - `10` L462 写它 “只在两种情形下删除”（存储面板与清除），外加写回成功；改指是第四种，没有列出。
    - `06` L923 末段 “没有任何出口使 T1 成为不被引用的对象” 照文字不成立。
    - `08` L520 把 `放弃改动` 的理由写作 “改动已无法恢复”（R112-D15-01）。
- **为什么是次要**：
  - 前提是双重故障：根可访问而来源目录已不在，并且重新物化也失败。
  - 之后还要你在取回之前再次接管并交还。
  - 但这正是 ADR-239 为 T1 “按类关闭” 的那一类。触发它的是卡片的第一个选项，丢失不经告知、不可恢复。
- **后果的类别**：交还而未写完、Tower 告诉你 “仍保存在 Tower 中” 的改动，在你按卡片再次接管并交还之后静默丢失。
- **文档位置**：`06` L145、L923（“T1 的保留” 与末段不变式）；`10` L246、L462、L952、L1290、L1306；`04` L671；`08` L520。
- **期望的回答形态**（任选其一，在 `06` L923 一处写定）：
  - 改指时以旧提交为新提交的父提交，使旧 T1 仍可达；写回成功时只在 ref 没有更早的未取回 T1 时删除，否则改指回父提交；
  - 或已有 `handback-t1` 而 `human_checkout` 中没有它的内容（即它来自 ① 失败或放弃之前的写回）时，再次接管以它物化人工编辑检出，而不是以 T0；
  - 或这时交还返回 `E_STATE`，提示先取回或在存储面板中删除它，界面相应不列出交还。
  - 并且 `10` L462 的删除枚举与 `06` L923 的不变式随之改写；G31 补 “① 物化失败之后再次接管并交还” 一组。

**R112-D13-02｜次要**（迁移事务先写新记录与 `satellite_rebuilding=1`，而它与新根的建立、`.kept-*` 改名的先后没有写：照字面，新根有了当前记录之后就不能再由 Tower 建立；新记录先于改名时，崩溃续做行会把旧卫星当作自己的半成品移走并删除）

- **问题**：
  - **(a) 新根的建立**：
    - “Tower 只在一个 `<wtRoot>` 中没有任何当前 `WorktreeRecord` 时建立它”（`06` L139）。
    - 迁移 “新位置的 `goal` 角色 `WorktreeRecord`（`rebuilding`）与 `satellite_rebuilding=1` 在迁移的同一事务中写入、先于重建开始”，并要求新根 “须可访问，或可按 §6.1.6 ‘Tower 不重新建立根’ 建立”（`06` L921）。
    - 但何时建立没有写。事务提交之后，新根中已有这次迁移写入的当前记录，照字面不能再由 Tower 建立。
    - 常见情形会落入这里：迁移到另一处重新克隆的检出，其父目录中还没有 `.tower-wt.noindex/<repoName>`。重建因根不存在而失败，失败先判可达把它判为不可访问 → 中断。这个 Goal 停在一个没有人删除过的根上。
  - **(b) `.kept-*` 改名与崩溃续做**：
    - 情形 F 写 “新路径上已有同名目录……都在重建之前……改名为 `.kept-*`”，同时写新记录与标志 “在迁移的同一事务中写入、先于重建”（`10` L1267）。两者的先后没有写。
    - 卫星重建中途崩溃一行（`06` L141）以 `satellite_rebuilding=1` 为条件，前提是 “重建在置本标记之前已把仍在原位的工作目录或 gitdir 改名保留……所以原路径上只可能是重建自己 `rename` 到位的目录，`.kept-*` 不在此列”。它对原路径上的目录的处置是 “原样移入……旁路目录，续做成功后删除”。
    - 情形 E 满足这个前提：先改名，再在同一事务中置标记（`06` L923 ③）。
    - 情形 F 在 ADR-239 之后，标记在迁移事务中置上。若改名在事务之后，两者之间崩溃时，重启看到 `satellite_rebuilding=1` 与原路径上的目录：
      - 这正是 A → B → A 时 A 上的旧卫星与 gitdir；
      - ADR-238 特意写明 “其中可能有最后一个检查点之后的改动”，所以改名保留、“从不覆盖、也不当作已建成而复用”。
      - 崩溃续做行会把它们移入旁路目录，续做成功后删除。
- **为什么是次要**：
  - (a) 照常理实现者会先建根，但规则的字面禁止这样做。
  - (b) 只在事务与改名之间的窗口内崩溃时发生。
  - 但 (b) 删除的正是 ADR-238 决定保留的内容，而前提失效的原因是 ADR-239 自己移动了置标记的时刻。
- **后果的类别**：
  - 迁移到新目录之后该 Goal 停在不可达上；
  - 迁回旧位置时崩溃，旧卫星中最后一个检查点之后的改动被删除。
- **文档位置**：`06` L139（“Tower 不重新建立根”）、L141、L921、L923 ③；`10` L257 (e)、L1267。
- **期望的回答形态**：
  - `06` L921 写明次序：先校验新根，按 “Tower 不重新建立根” 建立它（这时还没有新记录）；再把新路径上已有的同名目录改名为 `.kept-*`；最后提交写入新记录与 `satellite_rebuilding=1` 的事务。
  - 前两步之后、事务之前崩溃时，迁移没有提交，留下的只是空根与 `.kept-*`，照常列出。
  - 或者改写建根规则为 “没有任何当前记录，或只有本次迁移、准备写入的记录”。
  - `06` L141 的前提补一句 “情形 F 的改名同样在置标记之前”。
  - G35e 补 “迁回旧位置、事务与重建之间杀掉 Tower” 一组。

**R112-D13-03｜次要**（中断留下的 `satellite_rebuilding=1` 使迁移永久返回 `E_BUSY`；路径丢失的 `放弃改动` 会被卫星守卫拒绝却仍列出；迁移重建的崩溃续做不在 ③ 的豁免之内；界面隐藏迁移的条件宽于命令。“界面不提供会被拒绝的动作” 因此不成立）

- **问题**：
  - **(a) 迁移被永久 `E_BUSY`**：
    - 不可达时 “进行中的……卫星重建……在本进程中停止……`satellite_rebuilding=1` 原样保留”（`06` L139 ②）。ADR-239 又为迁移重建写明：新根在重建中变为不可访问时判为中断，由 ④ 续做（`06` L921）。
    - 迁移对 “卫星重建中（`satellite_rebuilding=1`）” 的 Goal 返回 `E_BUSY`（`06` L921）。与 `syncing` 不同，这里没有 “而重建已不在进行” 的区分。
    - 该根永久不回来时，永久不可达的唯一出口迁移一直返回 `E_BUSY`，界面显示 “稍后重试”，而这永远不会解除。
    - 界面也照常提供迁移：`12` L416 只在 `syncing` 时不列出它。
  - **(b) 卫星守卫**：
    - `goal.discard_human_edits` 有卫星守卫，`satellite_rebuilding=1` 或 `satellite_missing` 时返回 `E_STATE`。路径丢失的分支同样受它约束（`06` L914），尽管这一支 “不做差异比较”。
    - `12` L416 在 “满足路径丢失确认的条件时” 列出 `放弃改动`，条件只按 ③。
    - ADR-239 登记的双重故障（迁移后旧位置上仍有人工编辑检出、新根上的重建失败）正是 `satellite_missing` 与路径丢失条件同时成立：卡片列出的 `放弃改动` 会被拒绝。
    - 迁移重建进行中（同样满足路径丢失条件）也是如此。
  - **(c) ③ 的豁免**：
    - 豁免写的是 “`project.relocate` 自身在新根上的情形 F 重建”（`06` L139 ③）。
    - 迁移重建中途崩溃之后，重启时由 “卫星重建中途崩溃” 一行续做（`06` L141）。该 Goal 若因旧位置上的人工编辑检出仍不可达，③ “本表其他各行对它都不执行”，这一行不在两处例外之中。
    - 数据库中也没有字段区分 “这是迁移的重建”。于是标记悬空，回到 (a) 与 (b)。
  - **(d) 隐藏的范围**：
    - 命令只在 “受影响的 Goal” 中有 `syncing` 时返回 `E_STATE`（`06` L921）。以 `newCheckoutPath` 迁移时，受影响的只是附着检出不可访问的 Goal。
    - `12` L416 与 `04` L1522 写 “同一 Project 中有写回中断而 `syncing` 的目标时……不列出它”。
    - 一个附着检出可访问、只因人工编辑检出所在的根而 `syncing` 的 Goal，会让另一个附着检出丢失的 Goal 失去本来会被接受的迁移。
- **为什么是次要**：
  - (a)(c) 要求重建期间卷消失或崩溃，且旧位置或新根永久不回来；(b) 是已登记的双重故障；(d) 要求同一 Project 中两类不可达并存。
  - 出口仍有放弃，不丢人的改动。
  - 但 ADR-239 把 “界面不提供会被拒绝的动作” 写成唯一定义（`12` L416 “所以界面不提供会返回 `E_STATE` 的动作”），而它只按 ③ 与 `syncing` 求出。
- **后果的类别**：
  - 永久不可达的 Goal 的迁移出口失效，界面反复提示 “稍后重试”；

### 不扣分的观察

1. **冗余的 `handback-t1` 与影子删除**：写回失败而人工编辑检出仍在时，ref 是冗余副本（回应已登记）。之后你 `放弃改动` 或以 `take_external` 交还时，它仍按 `未写完的交还` 列出，并使影子删除无限推迟，直到你删除它。与 ADR-228 同一取向，可以接受；宜在目标页把 “冗余副本” 与 “唯一副本” 区分标注（后者即 ① 物化失败与不可达期间放弃）。
2. **两处崩溃窗口与 `take_external`**：
   - 写 ref 之后、写 `syncing` 的事务之前崩溃时，留下一个从未开始写回的 `handback-t1`；
   - 成功提交之后、删除之前崩溃时同理（已登记）。
   - 两者都按 `未写完的交还` 列出，之后 `human_checkout_lost` 条目也会写 “最近一次未写完的交还仍保存”。宜在启动时对 “没有 `syncing`、且 `human_checkout` 中有它的内容” 的 ref 做一次核对，或如实登记第一种。
   - `take_external` 不写回，`06` L912 的 ① 是否照写 ref 与 `syncing`，`10` L996–L1013 的 “不执行本步” 是否包括持久化，不清楚。宜写明 `take_external` 不写 `handback-t1`。
3. **删除 `handback-t1` 的副作用**：影子 180 天删除以它为前提推迟（`10` L463）。在 180 天之后删除它，会随即触发影子删除，已脱离的人工编辑检出中的 git 命令随之因缺少对象而失败（`10` L259）。`goal.delete_kept{handbackT1}` 的确认框只写 `删除之后 Tower 不再保留这次未写完的交还`（`06` L915），宜补 “该目标的检查点历史将随之删除”。该命令 “不产生事件” 的理由（“这些目录不是 Goal 的工作区”）也不适用于这个 ref，宜如实登记它没有审计记录。
4. **`turn_start` 的界**：`05` L1006、L1062 写 “至多三次请求受影响”。Pi v1.2.0 中，一个 turn 内 `turn_start` 之后可能还有自动压缩的请求（`agent-session.ts:838-840`），`agent_end` 之后也可能压缩（`:3041`、`:3069`），provider 层还有重试；新的 Host 进程从 0 计数。准确的写法是 “至多三个 turn（每个可含压缩与重试的请求），在同一 Host 进程内”。
5. **anomaly 条目只有 “知悉”**：`tower_goal_handler_error` 是 severity 3、L3，唯一出口是 `informative`，按 `08` §8.8 的定义（L543）它的 `interruptPrecision` 恒为 0，§8.9.2 规则 A（L574，M2）会把这一来源从 L3 降到 L2。第三次出错时你还会再被 `prepare_failed` 条目打断一次。“只在首次打开时打断” 在 “知悉” 之后再出错时是否重新打断，宜写明。可以接受为设计取舍。
6. **占位结果与全文文件**：`details: {}` 也去掉了 `details.fullOutputPath`，观察器这一次不复制、不删除 bash 的全文文件，它随 Host 的临时目录删除（`07` L85 已覆盖 “最终 `details` 没有路径” 的情形）。结论不变，宜在 `05` L1062 的如实登记中补一句。
7. **“当前 `WorktreeRecord`” 与位置算法**：
   - “当前” 没有写明取哪些 `state`（`10` L288 有 `retiring`、`removed`）；
   - `10` L527 第 2 步不可建立时落入第 3 步回退到 `~/.tower`，而 `06` L139 说这样的根 “就是不可访问的根”。只在为新附着检出首次计算、且候选位置已有其他检出的记录时出现。
8. **“清除全部” 与 `handback-t1`**：`09` L567 的单个 Goal 一行列出它，L568 的 Project 一行继承；L569 的 “清除全部” 一行没有写确认框列出它（`04` L1287 的总述写了）。宜在 `09` 补半句。
9. **回退位置被删除**：`~/.tower/worktrees/<projectId>.noindex` 不在可达判定之内，又受 “Tower 不重新建立根” 约束。它被外部删除而仍有记录时，重建会一直失败为 `satellite_missing`。`~/.tower` 内的目录被外部删除属于情形 B 一类，宜写明回退位置由 Tower 重建（它不在你可移除的卷上）。
10. **“列出的来源”**：`10` L259 只写按 `<wtRoot>` 扫描目录，存储面板列出 `handback-t1` 的来源（各 Goal 的影子）没有写进 “列出的来源”。
11. **Pi 引文细节**：
    - `details` 的替换为 `runner.ts:1207-1210`（`05` L1062、ADR-239 写 `:1206-1209`）；
    - 立即结果为 `agent-loop.ts:604-617`（写 `:600-613`）；
    - `_afterToolCall` 的返回块为 `agent-session.ts:717-723`。
    - 结论不变。
12. **G35e 的两处期望**：
    - “放弃时不写任何东西” 应为 “不写、不改指 `handback-t1`”（放弃本身写决定与状态事件）；
    - base 物化失败的一组宜写明夹具保证该标准没有稳定失败、也没有有结论的 `introduced`，并断言 `paused(verify_env_error)` 与 `ve:{goalId}:baseline` 条目。
13. **“约 0.9 的改派考虑线”**：第 111 轮的 `14` L216、L399 与 `15` L1566、L5284 都写 “系统线余量 0.93 仍高于约 0.9 的改派考虑线”，但 ADR-136 与 `14` 中只定义了改派阈值约 0.12 与顺延评估线约 0.2 人周。本轮条目落地后系统线约 0.87–0.89，会低于这条未定义的线。宜删去，或在 ADR-136 中定义它与越过时的动作。
14. **“写回未完成” 的两种含义**：`04` L671 用它指 `stalled{write_back_failed}`（本进程中失败，已退回 `idle`），`06` L139、L921 与 `12` L416 用它指不可达期间中断而仍在 `syncing` 的写回。宜把后者写作 “写回中断”。

### 设计是否完成

ADR-239 关闭了第 111 轮的全部七条：
- 写回期间 T1 一直被引用，卷永久丢失后放弃不丢交还的改动；
- Tower 不替你重新建立根；
- 迁移在写回中断时说明原因；
- F13 对持续失败真正起作用；
- `details` 不再留下原文；
- base 无结论不再推着 Agent 返工；
- 没有新增状态、暂停原因、事件类型、表、列或命令；
- 安全不变式都保持。

本轮 6 条中：
- 三条来自 ADR-239 自己 “按类关闭” 的边界：
  - T1 的改指；
  - 迁移事务的次序；

- 两条是同一理由没有用全：
  - 子进程非零退出只在验证上先判可达；
  - 无结论是环境故障，而 §7.4.5 与出口没有跟上。
- 一条是遗留措辞。

各条如下：
- **R112-D13-01**：`handback-t1` 改指之前保留旧 T1，或以它物化、或拒绝交还；不变式与删除枚举改写；
