## 1. 总评

**第 95 轮的 4 条次要条目都已按所问关闭**（核对见 §3）。§5 的 13 条观察全部落地。回应 “偏离与未决” 的七条中，六条接受；观察 13 的收窄部分接受，另一部分带出 R96-D11-03。

**ADR-223 的主体成立**（§3.3）：
- **硬链接**：取 “拒绝一切硬链接创建”，比 “按源路径区分” 更严，也不依赖平台按哪个名字判定。
  - git 写对象时，链接失败（`EEXIST` 之外）即改用改名，卫星内的常用 git 操作不受影响。
  - pnpm 在 Tower 中本来就配置为 `clone-or-copy`（`16` L1338），从不硬链接。
  - 本机的 npm 已不用硬链接。
  - 验证槽位、`$GS` 预热与 depcache 发布都由沙箱外的 Tower 以写时复制或改名完成，不受这条拒绝影响。
- **平台做不到时本机不使用 S2**：复用 ADR-022 的已有路径，不新设回退，§14.3.5 的 “SP6a = B” 一列随之适用。对使用者是很重的降级，回应如实写出，接受。
- **读取凭据**：
  - 卫星之内与默认位置下，规则对两种工具相同；
  - 第 3 条硬底线先于例外，写明了；
  - “卡上的 S2 句子” 按路径数据加条件，对 `printenv`、钥匙串、密码管理器改写为真实后果。
- **观察器**：复制与删除共用同一次校验与同一次不跟随链接的打开，校验不过的既不复制也不删除。路径改取 Pi 自己累加器的快照，Agent 的输出伪造不了它。
- **`write_back_failed`**：“知悉” 接到 `needs_you.dismiss`。该条目不对应任何暂停原因（`16` §16.1.7 的映射中没有它），不是阻塞类，所以任何时候都能关闭。

**ADR-223 带出、或本轮扫描发现的新问题**：
- **回退位置下的读取凭据规则**（R96-D11-01，**重要**）：`<wtRoot>` 回退到 `~/.tower/worktrees/…` 时，卫星位于 `~/.tower/**` 之下，而 `~/.tower/**` 是密钥路径表的一项。
  - “卫星内外同一规则” 之后，Agent 对自己卫星中每个文件的 `read` 与 `edit` 都追加 `secrets.access`：spike、依赖升级、调研三种预设下一律 forbid，其余预设下每次读取都出一张单向门卡。
  - 表中 `~/.tower/**` 对本 Goal 卫星的除外只写给沙箱外工具（`11` L227 (2)），`10` L544–L548 又写明 “例外只在三处定义”。
  - 这违反 “回退后权限与默认位置相同”（`11` L358）与 SP6a A3 的期望（`14` L53）。
- **硬链接与钥匙串两行的范围漏掉安装器的安装阶段**（R96-D11-02）。
- **无锚定密钥模式的作用范围**（R96-D11-03）：卫星之外过窄，是对 “收窄是否打开凭据路径” 的回答；卫星之内的 “跟踪状态” 没有来源。
- **启动时的两道新闸门**（R96-D6-01）：不在唯一的准入闸口中，等待中的 Goal 没有合法的状态；探测出错或超时没有去向。
- **只丢了一半的卫星**（R96-D13-01）：一般路径的重建无法处理仍在原位的另一半。
- **观察器取路径的通道**（R96-D12-01）。

**R96-D11-03｜次要**（无锚定密钥模式的作用范围：卫星之外过窄，卫星之内 “跟踪状态” 没有来源）

- **问题**：
  - **(1) 卫星之外过窄**。这是对 “收窄是否打开凭据路径” 的回答：**打开了一部分**。
    - L166 写 “这些无锚定的模式只在卫星工作区中按跟踪状态匹配、在 Pi 资源目录中不论跟踪状态匹配……不作用于系统路径、`$SH` 与镜像 `objects/`”。正向的范围同时排除了主目录中的其他位置、其他仓库、外接卷：例如其他项目中的 `.env`、下载目录中的 `*.pem`、某个目录中的 `*.key` 与 `id_*` 私钥。这些都不是 `~/.ssh/**` 这类显式条目。
    - 回应给出的理由（“这些位置原本就只读，内容来自系统或 Tower 自己”）只覆盖被点名的三处。
    - 各路径的后果：
      - **S2，文件工具**：这类路径在读允许列表之外，按 “必然拒绝” 带 `hardFloor`，只得到 forbid chip，不出卡、不记 `sandbox_violation`。读取凭据的信号（ADR-125）对这类文件消失。
      - **S2，bash**：`cat` 一类按 `read.external` 询问；批准后被沙箱拒绝，只记 severity 1。两种工具的告知形态因此又不一样。
      - **S0**：文件工具按 `read.external` 判定，spike 与调研两种预设中为 notify（L79），读取照常发生。按此前的自然读法，这类文件归 `secrets.access`，在这两种预设中是 forbid。
      - **沙箱外工具**：§11.3.4 (2) 不再为这类路径追加 `secrets.access`，只按该工具自身的类与授权求值；它们不受 S2 约束，可以读到。
    - ADR-223 的 “安全不变式全部保留并取更严” 对这一项因此不为真。
  - **(2) 卫星之内，“跟踪状态” 没有来源**：
    - “按跟踪状态匹配” 要编入 S2 档位（静态，按 Run 生成），但正文没有写跟踪状态取自哪里、何时求值：base 树、pin 树、最新检查点（影子中也包含未被 git 跟踪的文件），还是卫星索引。而 Tower 从不读取卫星 gitdir 中的索引。
    - `id_*`（非 `.pub`）、`*.key`、`*.pem` 都是无锚定的基名模式。Agent 在 Run 中新建的普通源文件或测试夹具（基名以 `id_` 开头的源文件、TLS 测试用的 `*.pem`）按 “未跟踪” 处理，在 S2 中对 Agent 自己的 bash 与测试读拒绝。
    - 每次拒绝都记 `credential` 类的 severity 2 哨兵（L374，“可能表明提示注入”）。ADR-223 改为卫星内也出卡之后，S0 下读这些文件还会出读取凭据卡。
- **后果的类别**：
  - (1)：卫星之外的凭据形文件失去 `secrets.access` 的单向门。S0 与沙箱外工具下可以以普通读取的审批读到；S2 下失去告知。
  - (2)：Agent 读不回自己刚写的文件，测试失败被当作产品失败；误报的凭据哨兵。实现会分叉，取决于跟踪状态取自哪棵树。
- **文档位置**：`11` L79、L98、L163、L166、L227、L357、L374；`10` §10.1.3；`05` §5.3.5（Tower 不读取卫星索引）；`15` ADR-223 观察 13；`round-95-response.md` “偏离与未决”。
- **期望的回答形态**：
  - (1) 把正向范围改为 “不作用于系统路径、`$SH`、镜像 `objects/`（以及其他 Tower 生成的只读位置）；其余位置照常匹配”，“按跟踪状态” 只在卫星工作区中适用。或者如实写出收窄的后果（S0 与沙箱外工具下的降级），并登记进 T 表。
  - (2) 写明跟踪状态的来源与求值时机（例如 “生成档位时以 pin（或最新检查点）中被 git 跟踪的路径为准；Run 中新建的文件按未跟踪处理”），并对 Agent 在本 Run 中自己写出的文件给出处理：例如只对播种与 base 中存在的未跟踪文件应用读拒绝，或把这一类拒绝登记为已知误报并降级。

### D13 隔离、git 与并发

**R96-D13-01｜次要**（只丢了一半的卫星：一般路径的重建无法处理仍在原位的另一半）

  - 重建按 §10.3.1 第 2 步，“旁路目录构造后原子 `rename`”（`06` L139）：`clone --separate-git-dir=$G <mirror> $W` 要求 `$W` 不存在或为空（`10` L361）；把旁路目录改名到一个仍存在的非空目录上同样会失败。

    - 删除仍在的工作目录：与 “检查点 n 之后的改动无法恢复” 的告知相符，但其中若有尚未解除的外部写入（`external_change`），这些内容并没有随卫星丢失，而是由 Tower 删掉了；

### D12 记忆与学习（隐私）

**R96-D12-01｜次要**（观察器取路径依赖可合并、可丢弃的流式更新；“由观察器复制为证据之后删除” 在这些情形下不为真）

- **问题**：
  - `07` L86–L89：超时、中止与无退出码时，路径取 “该调用最后一次 `tool_execution_update` 的 `details.fullOutputPath`”。观察器运行在 Supervisor 中（`07` L36）。
  - 事件到达 Supervisor 之前要经过两道处理：
    - **Host 侧预合并**（`13` L69）：`tool_execution_update` 每个 `toolCallId` 只保留最新、且 ≤ 10 Hz；`tool_execution_start/end` 立即转发、不合并。所以 Pi 的最后一次更新可能在 `tool_execution_end` 之后才到。
    - **Supervisor 背压**（`05` L598）：消费跟不上时 “其次丢弃 `tool.update`”，`tool.start/end` 永不丢弃。截断恰恰发生在输出量大的时候，也是最可能产生背压的时候。
  - Pi 一侧还有两种边缘（`output-accumulator.ts:64-89, 239-243`；`bash.ts:283, 342`）：
    - 临时文件可以在 `finish()` 中才建立，而 `finishOutput` 的再发一次只在有新数据时发生；
    - 临时文件按原始字节数建立，最终 `details` 却只在 `truncated` 时给出。
    这两种情形下，文件存在，但最终 `details` 与此后的更新都不带它的路径。
  - 文字的处理（“两者不同时不取”“校验不过的既不复制也不删除”）在这些情形下的结果是：全文文件留在 Host 的临时目录中。
  - 这与以下说法不符：
    - `09` L565：隐私清除结果写 “bash 截断输出的全文文件，含超时与中止的命令，由观察器复制为证据之后删除”；
    - `11` L525：“观察器把它复制为证据之后删除它，含超时与中止的命令”。
  - 校验写 “`os.tmpdir()` 的直接子项”，但没有写是哪个进程的 `os.tmpdir()`。Pi 在 Engine Host 中写文件，Host 的环境由白名单与登录 shell 构造（`05` §5.3.6），可能与 Supervisor 的不同。
- **后果的类别**：含原文的全文文件在少数情形下留在用户临时目录中（0600，S2 下 Agent 读不到），而清除结果与残余说明写它已删除。有界，但它是清除结果 “如实列出” 的一部分。实现会分叉：有的只看 Supervisor 收到的最后一条更新，有的在 Host 侧保存路径。
- **文档位置**：`07` L36、L82–L92；`13` L69；`05` L598、L1446（D61）；`09` L565；`11` L525。
- **期望的回答形态**：

    1. **转入 S0 的说明与翻转**：
       - 硬链接探测未通过时，各 Goal 只看到通用的 `本机没有可用的 OS 写入沙箱`（`04` L831）与 `沙箱 S0 · 仅策略层` 徽标。没有任何地方说明 “本机的沙箱存在，但未通过启动自检（硬链接）”，也没有诊断入口。宜给这一来源一句原因变体，并在设置或诊断中列出。
       - 探测每次启动都做，结果可能在两次启动之间翻转（系统更新）：
         - 由 S0 回到 S2 时，`paused(s0_grant_pending)` 的卡片原因不再为真，人若拒绝，结果是 “未经机器验证（S0 未授权）”，而 S2 本可验证；
         - 由 S2 转为 S0 时，`11` L545 的三要素告警 “或 S2 不可用” 只在批准、修订与授权时重算。
         宜写一句：启动时按探测结果解除已不适用的 `s0_grant_pending`（`obsolete`），并重算三要素。
       - 自用期中途发生转入时，§14.3.5 “SP6a = B” 一列的附加条件（只用不含生产凭据的仓库、签署残余风险接受）不会被触发，也没有报告；宜让这次转入进入自用期的记录。
    2. **`00` §0.5.1 没有登记硬链接拒绝**：
       - 卫星中的 `.git` 夹具有对应的一行（`00` L95）。硬链接拒绝的用户可见后果同类，却没有登记：
         - 调用 `link()` 的测试在 Agent 与验证器中都失败，不论目录在哪里；
         - 显式 `--local` 的本地克隆失败；
         - 可选的硬链接安装模式失败。
       - 验证器中的这类失败会被当作产品失败、触发返工。宜登记一行，并在验证失败卡上对 `EPERM` 的链接失败附一句说明（`verify_env_error` 与产品失败的区分属于既有原则）。
    3. **`04` L669 带回一侧的首条提示**：`…可处理后再次交还（检验带回为再次带回），或放弃改动` 在带回一侧仍给出 “放弃改动”。③ 已清除 `human_checkout`，`goal.discard_human_edits` 返回 `E_STATE`；带回的出口是再次带回或关闭检验（`06` L914、`08` L516）。同段 “以你交还时的内容” 在带回一侧应为 “带回时”；罕见分支 “工作目录未能恢复，也未重建” 没有写下一步。重建一支的变体已经正确，照它补齐即可。
    4. **`清理中 · 残留进程` 的边界**（`12` L390）：
       - 没有写它是否替换卡片第二行；
       - 与 `写回中`、`准备中`、`验证中` 的先后没有写（Run 等清理结束，同时出现的机会很小）；
       - 清理期间 `放弃`、`暂停`、打开检验的行为没有写。
       另外，`06` L145 的重启清理现在排在 `06` L144 的启动续写之后：带回崩溃、又有未解决 `bg_process_survived` 的 Goal，存活者在 I2 被抑制期间的写入会并入 `human_change` 的 pin。这是双重故障中的一种先后，有界。
    5. **D61 与 `07` L87 的措辞**：
       - D61 “未截断时错误文本的末尾就是命令自己的输出”：错误文本以状态行结尾（`bash.ts:375-387`），应为 “状态行之前就是命令自己的输出”；

    7. **`11` L163 的括注**：“影子、`$TI`、`$VS` 中的文件——它们在 `~/.tower/**` 之下，也命中密钥路径表”。默认位置下 `$VS` = `<wtRoot>/_stores/_verifier`（`16` L1318），不在 `~/.tower/**` 之下，只在回退位置下才是。结论不变（第 3 条硬底线照常 forbid），措辞宜改为 “影子与 `$TI` 在 `~/.tower/**` 之下；`$VS` 按第 3 条”。
