## 1. 总评

ADR-169 把第 43 轮的两条次要问题都按建议关闭了：
- “改为 human 标准”的后续状态在 `03` §3.4.5 一处定义，`04`、`07`、`08`、G46 都改为引用，状态机没有改；
- `isSecret` / `seeded` 两个谓词的唯一定义在 `16`；
- 检验 pin 已有定义，并排除了 `nested_repo_live`；
- 删去了没有来源的文件建议。

排期算术仍然成立（WBS 121.50，M1 38 周）。

但谓词写成纯字段函数以后，暴露出一个此前被措辞掩盖的缺口：
- `isSecret` 只看持久化的 `secretBy`；
- `secretBy` 只在加入清单时判定一次；
- 而 `07` 与 `11` 规定“复制前按内容扫描”。

按唯一定义实现时，一个已批准的普通本地文件后来被写入机密，下次播种仍会被复制到 Agent 可读的卫星。这直接触及 M1 的头号安全不变式，评为**重要**。

另有一条次要问题：第 43 轮修订的排期增量没有登记，G46(ac) 的前提测不到它要断言的卡片。

### D11 安全与自主度

**R44-D11-01｜重要**（`isSecret` 依赖只在加入时判定的 `secretBy`，与“复制前按内容扫描”矛盾；建议条目可能绕过判定）

- **问题**：
  1. **判定时机不一致**：
     - `16` L509 是唯一定义：`isSecret(f) = f.secretBy ≠ null ∧ f.unmarked = null`，是持久化字段的纯函数。`secretBy` 由 `project.local_files.add`“加入时按名字与内容判定”（`16` L509、L881；`06` L872）。
     - “每次播种前重新扫描”只写给已取消标记的条目：内容变化且再次匹配时清除 `unmarked`（`16` L509；`06` L234、L876；`02` L113；`04` L1299）。
     - 但 `07` L482 把含机密的本地文件定义为“……或**复制前的扫描**发现内容匹配”，`11` L339 写“内容匹配 §11.7.1 的机密模式（**复制前按内容扫描**，不只看文件名）”。
     - 情形：一个加入时内容干净、已批准的普通本地文件（`secretBy = null`、`approved ≠ null`），之后被开发者写入一个机密值。按 `07` / `11`，下次复制前的扫描命中，不播种；按 `16` / `06` 的谓词，`isSecret` 仍为假、`seeded` 为真，文件被播种到卫星（Agent 可读）、验证槽位与检验检出。
     - 第一种实现被写成“唯一定义”，后一种（安全的）实现只出现在引用方。
  2. **建议条目直接 `approve`**：
     - `04` L1296 把建议条目的 `[添加]` 映射为 `project.local_files.approve{path}`，不是先 `add`；
     - `06` L874 的 `approve` 只写“写 `approved={decisionId}`”，没有规定清单中尚无该行时返回错误，还是先按 `add` 的规则判定 `secretBy` 再插入；
     - 建议来源恰好以 `.env*` 为主（`04` L1296），而 `.env*` 正是 `name` 机密模式。若实现在缺行时直接插入一行而没有经过判定，这一行的 `secretBy` 为空、已批准，即 `seeded`。
  3. **连带问题**：
     - 脱敏器的精确匹配集取“本地文件清单中扫描命中的值”（`11` L496）。扫描若只在加入时进行，后来写入的值也不在匹配集里；
     - `06` DDL 没有 `unmarked IS NULL OR secret_by IS NOT NULL` 的约束，也没有写 `unmark_secret` 对 `secretBy = null` 的条目如何处理。这样的行在内容变化后“自动恢复”（清除 `unmarked`）仍得不到 `isSecret`。
- **为什么重要**：
  - `11` §11.7.0 的 M1 不变式“Tower 不会自动把机密交给 Agent 可影响的进程”是 G46 的标题，也是 M1 安全论证的支点（三要素中“私有数据”判为假依赖它，`11` L518；T32 的 M1 残余“低”也依赖它，`11` L659）。
  - 按唯一定义实现会放进一类后果：机密值进入 Agent 可读的工作目录，并可能经工具结果进入模型上下文；同时三要素与 T32 的评级失去前提。
  - 设计意图在 `07` / `11` 中写得很清楚，修复只需要文字，但目前唯一定义与引用方方向相反，危险的那一边是“唯一定义”，所以评为重要。
- **文档位置**：`16` L509、L881-882；`06` L234、L737-744、L872-876；`02` L109-114；`07` L482；`11` L339、L496、L518、L659；`04` L1296、L1299；`10` L367、L814；`14` G46(h)(i)(p)。
- **期望的回答形态**：
  - **第 1 点**：在 `16` L509 一处写明判定时机，`06` / `07` / `11` 引用。二选一：
    - **(A，推荐)** 每次播种（卫星、验证槽位、检验检出）前，对清单中**每个**条目按名字与当前内容重新判定，命中时写入 `secretBy`（`content`），不播种并通知；`approved` 保留但不再使文件 `seeded`。谓词不变，`secretBy` 的写入者增加“播种前扫描”。
    - **(B)** 把 `approved` 绑定内容哈希（`{decisionId, contentHash}`），`seeded` 增加“当前内容哈希 = 批准时的哈希，或重新扫描未命中”。
    - 两种方案都要写明扫描命中的值同时加入脱敏器匹配集。
  - **第 2 点**：`06` L874 写明 `approve` 对清单中不存在的路径返回 `E_STATE`，界面的建议 `[添加]` 先发 `add` 再发 `approve`；或者 `approve` 在缺行时按 `add` 的规则判定后插入。`04` L1296 同步。
  - **第 3 点**：DDL 加 `CHECK (unmarked IS NULL OR secret_by IS NOT NULL)`，`unmark_secret` 对 `secretBy = null` 返回 `E_STATE`。
  - **用例**：G46 加两组：
    - (i) 中的 `config/dev.local.json` 已批准，随后写入一个 `sk_live_…` 形态的值并触发播种：不播种、`secretBy` 变为 `content`、通知人，卫星中没有该文件；
    - 从建议条目 `[添加]` `.env.development.local`：该行 `secretBy = name`，不播种。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D5–D10、D12、D13、D16 为 100，这十三个维度上没有可追问的实质问题。
  - D4 99、D11 96、D14 99、D15 99。
- **是否还有可追问的问题：有。** 新增共 **2** 条：阻断 0、**重要 1**、次要 1。
  - **第 43 轮核验**：已解决 2，部分 0，未解决 0。
  - **其他核对**：
    - lint 全部通过（exit 0）；
    - Pi v1.2.0 源码复核成立，Pi 依赖面不变；
    - 排期算术全部成立：WBS 121.50、38 周、系统线余量 0.14、增人 33 周。只是 ADR-169 的增量没有登记。
  - **不扣分的观察**：
    - **串联两步之间中断**：`contract.amended` 入账后、`retry_verify` 发出前若 renderer 崩溃或应用退出，Goal 停在暂停中，Needs-You 保持打开，结局有界。这与 `08` L196“修订合同后继续”（`contract.amend` + `goal.resume`）是同一既有模式。但卡片上此时再点“改为 human 标准”会打开一个空修订，F6 L1353 的选项中也没有单独的“重新验证”。建议一句话写明：失败标准已是 human 时，该按钮改为直接发出 `retry_verify{pin:"same"}`。
    - **“改为 human 标准”的远程分类**：`16` L910 只允许 web 做“不放宽”的修订，没有说 exec → human 是否算放宽（它让一条机器标准不再计入“已验证”）。远程能力属于 M2（`serve`），不扣分；M2 设计远程矩阵时应把它列入。
    - **建议模式的冗余**：`config/*.local.json` 已被 `*.local.*` 覆盖，只是示例，不影响实现。
- **设计是否完成：否。**
  - ADR-169 干净地关闭了第 43 轮的两条问题，没有引入新的状态机分支。
  - 谓词形式化让“机密判定的时机”第一次落成可检查的文字，于是暴露了一个从 ADR-166 起就潜在的方向性矛盾。它只需要文字修订，但关系到 M1 的核心安全不变式，必须在冻结设计前写定。

  2. **R44-D14-01**：登记第 43 轮（及本轮）增量；修正 G46(ac) 的前提。

    - W3 系统 0.01（播种前判定写入 `secretBy`、`approve` 守卫、DDL 约束）；
