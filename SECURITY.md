# Security policy

Tower runs coding agents that execute commands on your machine. Its safety rests on a few properties; reports that break them are the most valuable:

- everything the agent runs — its shell commands and its `read`, `edit` and `write` tools — runs under a deny-by-default macOS Seatbelt profile generated per goal;
- reads are an allow-list: system locations, toolchains (from package-manager prefixes only `bin`, `lib`, `Cellar`, `opt`, `share` and the like — not `var` or `etc`, apart from TLS certificates and rustup's default-toolchain setting), what version managers read to pick your default version (their homes, version-only files such as `~/.tool-versions`), system-wide defaults (not other apps' preferences), its own workspace and private directories; not your home directory, other volumes, shared temporary folders or other apps' data; credential stores (`~/.ssh`, `~/.aws`, `~/.config/gh`, Pi's `auth.json`, …) are denied even where reading is otherwise allowed, and no `*_API_KEY`-style variable reaches it;
- the agent can write only its workspace, its private temporary directory and its private package caches (seeded by copy-on-write from yours, so your own caches cannot be poisoned);
- without the contract's network switch nothing beyond this Mac is reachable, and loopback is closed by default too: a sandboxed command reaches only the ports the contract declares and the servers its own sandbox's processes were listening on when it started — not services you, other users or the system run, whether they started before or after the goal. Loopback opens wider only on evidence from your own code or by your choice: when a criterion is refused loopback on the base commit (your unchanged code, before the agent did anything), or the project's setting says so, or the contract does; local proxy ports and Unix sockets outside its directories (for example `docker.sock`) are never reachable; the keychain service is never reachable, with or without the network;
- processes the agent starts do not outlive its run: when a run ends (submitted, paused, abandoned, crashed) and when Tower quits or starts again, every process in that goal's agent sandbox is stopped, wherever it moved; your own programs, even working in the same folder, are not touched;
- a `look` screenshot is only ever of the app the verification started: the port must be free before it starts, every listener answering it must be in the verification's own sandbox, and the screenshot browser runs under a deny-by-default profile that reaches only that app's ports and writes, in your home, only its own crash folder (`Library/Application Support/<browser>/Crashpad`, which Chromium uses whatever its flags say);
- the model can call only seven tools (`read`, `bash`, `edit`, `write`, `ask_user`, `log`, `submit`); MCP and a repository's own Pi resources are disabled;
- Tower never pushes or writes to your repository except a new local branch you accepted;
- verification runs in a clean checkout under the same sandbox rules, without credentials and without anything the agent could write (a fresh package cache each time);
- the agent cannot change the git configuration or hooks Tower itself uses.

## Reporting

Please **do not** open a public issue for a vulnerability. Use GitHub's private vulnerability reporting ("Security" → "Report a vulnerability") on this repository. Describe the property that fails and the class of harm; a minimal reproduction helps. We aim to acknowledge within three days.

## Engines

- **Pi**: Tower's extension replaces Pi's four tools with sandboxed ones and adds three; Pi starts with exactly these seven.
- **Claude Code** (through the ACP bridge, `extensions/tower-goal/acp.ts`): Claude Code is started with no built-in tools, no user or project settings, hooks or MCP servers; its only tools are Tower's MCP server (MCP configuration is strict, and the connectors of your claude.ai account are switched off for it), which applies the same gate and Seatbelt profile as with Pi.
- Claude Code's ACP adapter is installed by Tower on first use with `npm ci` from a manifest and lockfile shipped with Tower (every package checked against its integrity hash, install scripts off), not fetched at whatever version the registry serves.
- In both cases the engine process itself (which holds your model login) runs outside the sandbox; only what the model can cause to happen runs inside it.

## The phone page

Off by default. When you turn it on (Settings), Tower serves a small page on your network so a phone can answer Needs-You items and pause goals. Every request must carry a 256-bit pairing token from the link or QR code in Settings; the page itself holds no data, and the token travels in the link's fragment, which browsers do not send. It listens only on Tailscale's address, and only while Tailscale is connected (encrypted); when it is not, the page is not served at all and Settings says why. Listening on the plain local network is a separate switch (it then listens on this Mac's own address on that network, never on every interface), because anyone who can watch that network could read the token. A paired phone keeps the token in the page's own storage. Settings can issue a new token at any time. Decisions that widen what the agent may do — allowing a gated action, overriding a sentinel, installing changed dependencies with the network — are refused from the phone and stay at the desk.

## Pushes

Off by default. With an ntfy topic URL in Settings (https, or http only to this Mac or a Tailscale address), each item that blocks a goal sends the goal's id and title and a fixed sentence for the kind of item to that URL — nothing the agent wrote, no code, no output and never the pairing token (when the phone page is on, the notification links to the page without it). The text is passed to curl as data on standard input, never as an argument. Settings shows whether the last push was delivered — a failure as a reason in the interface language, from curl's exit code, never curl's or the service's own text — and can send a test push. Prefer your own ntfy server; a public one sees goal titles.

## Known limits

- Pi itself (which holds the model credentials and talks to the provider) runs outside the sandbox; only what the model can cause to happen runs inside it.
- Setup commands (installing dependencies) run the code the manifests choose, inside the sandbox. In the agent's workspace they have the network. In verification, setup runs with the network only on the base commit (your content); on the agent's snapshot it runs offline unless the contract allows the network or you approved that very snapshot on a decision card. Local files such as `.env` are present only while criteria run, never during setup. A malicious dependency you approve can still reach the network during setup; it cannot read your credentials.
- The browser that takes `look` screenshots runs the agent's page with its own sandbox off (it cannot nest) inside a Tower profile that is closed by default: it starts only its own app bundle's programs, reads the system, its bundle and your fonts, writes only to its throwaway profile, the screenshot's folder and your per-user temporary folder (where it keeps its single-instance socket), reaches a fixed list of system services (fonts, preferences through the system's preferences service for its own and the global domain, logging, launch services — not the keychain or the pasteboard), cannot read credential stores, and without the network reaches on this machine only the ports the app's own processes listen on (no DNS, no outside address, no proxy on loopback). It may look up where files are and how big (metadata), not read them.
- Verification uses a fresh package cache for every run, seeded from yours and thrown away afterwards, so nothing the agent wrote reaches a verdict through a cache.
- Sentinels for passing-but-wrong work are text rules over the diff, not a semantic analysis. They explain and order; the verdict itself is re-checked with only the agent's source changes kept, with a must-fail canary going through each test file's own assertions (JavaScript, TypeScript and Python), and with Tower's check of assertion identity while the criteria run. A criterion whose assertions could not be checked says so on its row.
- The assertion-identity check runs inside the same sandbox as the code under test, which is what lets it see the entry points at all. A run can therefore add lines of its own to the transcript; it cannot remove or rewrite Tower's (the file is append-only and the profile allows nothing else there), and it cannot produce the secret a silent process never revealed, so a forged verdict does not replace a real one. What remains is that a process can always impersonate code running inside it: the check raises the cost of hiding a replaced assertion and removes the blind spot of matching words, rather than making it impossible. Compiled languages have no hook for loading a check before the test code; there the must-fail canary, which changes the tests' own expected values, is the check, and the result says so.
- Held-out proof is per file and per run: each file Tower can mark (JavaScript, TypeScript, Python, shell, Rust) carries its own random token and, when loaded, leaves it in a drop box the sandbox may write but not read or list. Code under test cannot produce a proof it was not given, copy another file's, or learn which files ran. The process that executes a held-out file can still read that file's own text, token included; code that reads the held-out files at run time is already beyond what held-out tests can defend, so the proof is as strong as their secrecy. A JavaScript file in an ES module on a Node without a synchronous file module (before 22.3), and a Rust test selected away by name, leave no proof and are reported as not run. Other languages are reported as "cannot prove they ran". Without the macOS sandbox the box is an ordinary directory.
- Folders named `node_modules` above the project are readable from the sandbox (Node and npm look for them; third-party packages, not secrets); writing to them is not allowed.
- A failing command counts as an environment problem (rather than a failing test) only when Tower itself sees the refusal: a path the output names that Tower can read and the same sandbox profile cannot, checked with a probe Tower runs. In the source-only re-run, a command that does not finish counts as failing.
- Loopback without the network is an allow-list fixed when each command starts (Seatbelt names one port per rule, has no port ranges, and a profile cannot change under a running process). What is covered: every service on this Mac — yours, other users', the system's, started before or after the goal — is closed unless the contract declares its port; the agent's own earlier servers are opened within about two seconds of their starting listening (Tower rewrites the agent's profile; a command that starts before that does not see them); a `look` app is reached by the screenshot browser only once Tower has checked it is the verification's own. What is not: a server a command starts and connects to within the same command on a port it picks at run time (port 0, a build daemon) is closed to it too, unless the port is declared — or loopback is opened for it. Tower opens it on evidence only: when the preflight (or a verification's base step) runs a criterion on the base commit, your unchanged code, and the only thing stopping it is a refused loopback connection, the need comes from your test suite, not from the agent; Tower then runs that criterion's verification with loopback open, records the decision in the trace and on the criterion's row, and sets the project's “Open loopback for this project's tests” (Settings, yours to turn off), which later goals of the project start with and which also opens loopback for the agent's own commands. The project setting and the contract's “Open loopback” mean the same: everything on loopback is reachable except the services listening when the command started, so a service started later by someone else is reachable. A refusal that first appears on the agent's snapshot is never taken as such evidence: it pauses the goal. Opening loopback changes the network rules only: the assertion-identity guard, its read-only files and its append-only transcript are the same in every verification profile, loopback closed or open. Known proxies on loopback — common proxy apps', `*_proxy` variables' and the system's proxy settings' — are closed whenever the network is off, even when declared. A refused loopback connection in a criterion counts as an environment problem with its own card, not as a failing test; Tower reads that refusal from the command's output, so code under test can only turn its own failure into a pause, never into a pass.
- Which processes are a goal's is decided by the kernel's sandbox check: a process is the agent's when its Seatbelt profile lets it write the goal's private directories and does not let it write Tower's data directory; a verification's when its profile lets it write that verification's checkout. Without an OS sandbox the agent's leftovers are not identified (its workspace is one you may also work in), and a verification's are found by working directory and open files only.
- When the verification sandbox still cannot resolve a toolchain the way your terminal does, the card names the cause (rustup's default toolchain, a Node version manager's default, the developer tools, a program missing from your login shell's `PATH`, a closed loopback port) from the command's output, with a way out that changes your machine's setup, never the repository. For this Tower reads your interactive login shell's environment, and makes readable what the version managers need to choose a version: their homes named by your environment, version-only files in your home (`.tool-versions`, `.nvmrc`, …), rustup's fallback settings under a package manager's `etc/rustup`, and mise's global configuration only when it sets no environment variables (which may hold secrets).
- On Linux and Windows there is no OS sandbox yet; reads and writes are fenced by path only and Tower says so in its environment check.
- Pi extensions you choose to load run outside the sandbox with your permissions.
