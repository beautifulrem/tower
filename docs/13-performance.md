# 13 · 性能

本文把 `research/gui.md` §9 的性能预算落实为可执行的工程规则、测量方法与降级策略。性能在 Tower 中不是体验锦上添花：监督工具在负载下变慢、变旧或丢事件，会直接破坏 R1（陈旧状态被当作当前状态，theory §C16 #1）与 R5（Needs-You 迟到）。

依据：ADR-004（每 Goal 一个 Engine Host）、ADR-005（Supervisor 单写者 + 事件溯源 + 投影）、ADR-007（Electron + React）、`02` §2.13（`message_update` 增量不进事件日志）、`research/gui.md` §2.4、§3–4、§9、`01` §1.6（默认并发上限 3）。

## 13.0 原则

1. **事件量是瓶颈，不是框架 diff。** 10 个流式 Agent 原始事件约 500–1000 条/秒（`gui.md` §3.1）；任何 UI 框架都不应直接看到这个速率。合并在 Supervisor（与 Engine Host）完成，渲染进程每帧最多提交一次。
2. **安静即性能。** 后台 Goal 低频刷新（数据帧 ≤ 4 Hz、可见文本变化 ≤ 1 Hz，精确值见 `16` §16.4 节奏表）既是“暗驾驶舱”规则（`gui.md` §7），也是性能规则；两者由同一个合并器实现。
3. **注意力关键路径永不排队。** Needs-You、状态转移、人的命令回执绕过所有节流与降级。
4. **降级必须可见。** 任何为保性能而丢弃或延迟的展示，都要在 UI 上可见（例如 Live Line 旁的“节流中”标记），否则就是在制造“陈旧但看起来是最新”的状态。
5. **预算进 CI。** 每一项预算都有自动化测量；超预算即失败（§13.12）。

## 13.2 数据通路与延迟拆分

```
Pi AgentSession (Engine Host, utilityProcess)
  │ ① 订阅 → 转为增量事件（剥离累积快照）           ≤ 0.1 ms/事件
  │ ② Host 侧预合并（text_delta 拼接、tool 更新取最新）  10 ms 窗口
  ▼ MessagePort（结构化克隆）                           ≤ 0.5 ms
Supervisor (utilityProcess)
  │ ③ 归一化 → 状态机/观察器 → 事件日志（批提交）     见 §13.9
  │ ④ 投影折叠 → 每订阅者合并器（§13.3）               聚焦：首事件立即发，其后 ≤ 1 帧/刷新周期（16/8 ms）
  ▼ MessagePort                                          ≤ 1 ms（≤ 8 KB）
Renderer
  │ ⑤ store.apply（立即）→ rAF 通知订阅者 → React 提交   ≤ 4 ms 脚本
  │ ⑥ 热文本直接写 DOM（textContent/appendData）
  ▼ paint
```

**① 必须剥离累积快照。** SDK 的 `message_update` 事件携带累积的 `message` 与 `assistantMessageEvent.partial`（`packages/agent/src/types.ts` L526）；Pi 的 JSON/RPC 线协议则只发增量，“使流大小保持线性”（`docs/json.md` L72、L200）。Engine Host 若把 SDK 事件原样 `postMessage`，结构化克隆的成本随消息长度平方增长（一条 8k token 的回复在 50 Hz 下每秒克隆数 MB）。Host 必须先做与 Pi 导出的 `JsonAgentSessionEvent` 相同的转换再发送。

**② Host 侧预合并。** 同一 `(messageId, contentIndex)` 的 `text_delta`/`thinking_delta` 在 10 ms 窗口内拼接；`tool_execution_update` 每个 `toolCallId` 只保留最新、且 ≤ 10 Hz；其余离散事件（`tool_execution_start/end`、`turn_*`、`agent_*`、`message_end`、compaction、retry、`queue_update`）立即转发、不合并。

## 13.3 合并器（Coalescer）

合并器的节奏、合并规则、帧拆分与背压（`inflight > 8` 或未确认 > 256 KB 即停发增量、标记 `dirty`、追上后补发）**以 `06` §6.5、§6.4.5 为准**。本文只追加对性能预算有直接影响的要求：

| 要求 | 说明 |
|---|---|
| 聚焦 Goal 前沿刷出 | 聚焦 topic 在空闲后的第一个变化**立即**刷出，之后才按 `06` §6.5.1 的刷新率节奏（60 Hz 16 ms、120 Hz 8 ms）合并。否则“等待 tick + 等待 rAF”两段叠加，60 Hz 下 p95 超过 §13.1 预算 |
| 按刷新率调节 | 渲染进程在 `hello` 中上报显示器刷新率；120 Hz 时聚焦节奏为 8 ms（§13.1 的 120 Hz 档预算依赖于此） |
| 周边文本 | 后台 Goal 的 Live Line 文本对周边视野至多 1 Hz（`gui.md` §7.1），即使 `06` 的 board 节奏为 250 ms |
| Watch 模式 | 只有**一个** Goal（当前聚焦者）获得聚焦节奏的 Trace 尾部流；其他处于 Watch 模式但未聚焦的 Goal（如分屏）降为 4 Hz |
| 注意力关键 | 立即刷出的集合以 `06` §6.5.1 为准，且不受 §13.13 任何降级影响 |

### 13.3.1 统一节奏表（R1-D10-05）

本表已原样迁入 `16` §16.4（ADR-039），Tower 所有周期性刷新与后台节奏以注册表为准；本文的预算与降级规则只引用其中的值。

## 13.5 Supervisor 与 Engine Host 规则

- Supervisor 事件循环延迟（`perf_hooks.monitorEventLoopDelay`）p99 ≤ 20 ms；超过 50 ms 触发降级（§13.13）。
- 所有 git 操作以子进程运行（不阻塞事件循环）；同步 SQLite 调用每次 ≤ 10 ms（批提交，§13.9）；重查询（Trace 搜索、跨 Goal 统计）放到 `worker_threads` 中、使用只读连接。
- Engine Host **只在 Goal 有活跃 Run、以及其后按 `06` §6.1.8 退出之前存在**（例如暂停后的 5 分钟内；`provider_unavailable` 的探测依赖这段存活，`06` §6.1.4 第 5 项，ADR-236）。Host 在 Run 已 settle 且 Goal 进入 `in_review`、`paused` 超过 5 分钟、被人中止或应用退出时退出（时机以 `06` §6.1.8 为准，ADR-185）；恢复时由 `SessionManager.open` 重新加载 JSONL（冷恢复目标 ≤ 800 ms，M0 SP2 实测；不含包管理器的全局根查询——用户级 npm 来源不在 `<agentDir>/npm/` 下时，Pi 在创建会话时同步运行它、没有超时，`05` §5.10；你配置的包装命令挂起时，会话创建由 120 s 的准备时限兜底，进入 `paused(prepare_failed)`；Supervisor 自己在 Host 启动之前的清单查询以 60 s 为限、到时终止该子进程，出错或超时都不启动 Host，`05` §5.10，ADR-215；Host 存活期间新建会话（上下文交接）时这一同步查询阻塞 Host 的事件循环，含心跳与打包模式中的其他 Goal，挂起超过心跳阈值时按 `06` §6.1.3 的 Host 心跳超时处理）。这让“10 个 Goal”中真正占内存的只有运行中与刚停下的那几个。
- Project 可达性检查（`06` §6.1.6 Project 不可达一行：启动检查、30 s 复查、操作前检查与失败后的判定；`10` §10.16.1 的存在性检查；隐私清除的根）中对路径的 `stat` 与 §6.8 F8 复查的剩余空间读取**按挂载点隔离**（ADR-235/236）：每个挂载点（按路径在系统挂载表中的最长前缀求出——只读挂载表、不访问该路径，只决定由哪个线程执行，不是可达的判据）由一个专用的 `worker_thread` 执行（挂起的系统调用只占住该线程，不占 Supervisor 的事件循环与 libuv 线程池）；5 s 从该次调用开始执行时计，到时该路径按不可访问计，该线程被放弃（不再向它派发，调用返回后退出），同一挂载点另起一个线程继续其他路径的检查；每个挂载点至多有一个被放弃而尚未退出的线程，再次超时时该挂载点上的全部路径按不可访问计、不再另起，直到被放弃的线程退出；同一路径上一次检查未返回时不再发起新的。所以一个挂起的 SMB/NFS 挂载只影响它上面的路径，不阻塞 Supervisor，也不使其他挂载点上的 Goal 判为不可达。经符号链接指向别的卷的路径按链接所在的挂载点分组：目标卷挂起时该组多占一个线程；两条这样的路径先后超时，就是该组的“再次超时”，链接所在挂载点（常为启动卷）上的全部路径在被放弃的线程退出之前按不可访问计、其上的 Goal 这段时间判为不可达——受影响的包括它们这时进行中的 Run：按 `06` §6.1.6 ① 中止、以 `app_quit` 暂停，不只是注明不可达（不丢工作，可达后照常，`resumeOnLaunch` 打开时自动继续；如实登记，ADR-237/238）。启动时 `06` §6.1.6 在接受界面命令之前执行，各挂载点并行；同一挂载点上第一条路径超时后另起的线程要再超时一次才把整个挂载点判为不可访问，所以有挂载点挂起时命令的受理至多推迟约 10 s（ADR-237 更正此前的 “约 5 s”）；本节冷启动的预算没有计入这段等待（如实登记，ADR-236）。
- Host 启动参数：`execArgv: ["--max-old-space-size=512"]`——宁可让单个 Host OOM 崩溃并由 Supervisor 从 JSONL 恢复，也不要让它把整机拖进交换。

## 13.6 Diff 分级

Supervisor 运行 `git diff --histogram -M` 并按文件惰性发送（文件列表先到，文件内容随滚动进入视野）。分级按“本次视图中的总变更行数”与“单文件规模”两维度：

| 档 | 条件 | 行为 |
|---|---|---|
| T0 | 总变更 ≤ 3k 行 | 全量高亮、词级差异 |
| T1 | 3k–20k 行 | 只高亮可见 hunk ± 1 屏；词级差异仅可见区 |
| T2 | > 20k 行 | 不着色；提供“仍然高亮”按钮 |
| 单文件大 | 单文件总行数 > 10k，或变更 > 5k 行 | 该文件默认折叠为摘要；展开时以纯文本分块渲染；> 20k 变更行时懒加载 Monaco diff 作为后备（`gui.md` §4.2） |
| 生成 / 锁文件 | `.gitattributes` 的 `linguist-generated`、已知锁文件名、文件头含 `@generated`、平均行长 > 300（压缩产物） | 默认折叠，只显示 diffstat；锁文件另有结构化摘要（新增/升级/移除的包，来自 `07` 的锁文件哨兵） |
| 二进制 | git 判定为二进制 | 只显示大小变化；图片显示前后缩略图 |

评审单元（≤ 300 LOC，`02` §2.8）是主要的评审路径，因此 T1/T2 主要出现在“全部变更”视图。阈值是起点：M0 实验 SP3（`14`）在锁文件为主的变更集、6 万行生成文件、200 文件 × 50 行、单行 2 MB 压缩文件四种最坏情况下测量 @pierre/diffs 的主线程停顿（已知 6 万行文件停顿 438–761 ms，`gui.md` §4.2），据此回填。

## 13.7 终端

- Chromium 每页最多 16 个 WebGL 上下文，超出时淘汰最旧的；`WebglAddon.dispose()` 不释放上下文（xterm #6068），需手动调用 `WEBGL_lose_context`（`gui.md` §4.4）。
- **Tower 预算：同时附着的 WebGL 终端 ≤ 4 个**（只给可见终端），为图表等其他 WebGL 用途留出余量；第 5 个可见终端改用 DOM 渲染器。
- 不可见终端从渲染进程分离，状态保存在 Engine Host 的 `@xterm/headless` 中（scrollback 上限 5000 行）；重新附着时序列化恢复。
- PTY 字节：Host → MessagePort（转移 `ArrayBuffer`）→ 每终端每帧一次 `write`。
- **Agent 的 bash 输出不是终端**：在 Trace 中以 ANSI → span 解析器渲染于虚拟行内，不创建 xterm 实例（`gui.md` §4.4）。

## 13.8 内存

### 13.8.1 进程预算

进程内存预算的**唯一定义**（ADR-185；`06` §6.1 的进程表只引用本表）。“空闲”一列是 E6 与 CI 的回归门槛，main + renderer + GPU + Supervisor 四项之和 = §13.1 的空闲总预算 250 MB；“负载时”一列是有活跃 Goal、打开大 diff 或终端时的上限。数值为假设值，M1 自用期按 E6 实测回填（回填时两列与 §13.1 一并修改）。

| 进程 | 空闲 | 负载时 | 主要构成 |
|---|---|---|---|
| main | ≤ 50 MB | ≤ 80 MB | 窗口、托盘、通知、更新器 |
| renderer | ≤ 100 MB | ≤ 300 MB（打开大 diff + Trace） | store 副本、虚拟化 DOM、Shiki 缓存（上限 64 MB），Web Worker 计入 |
| GPU | ≤ 30 MB | ≤ 150 MB（含至多 4 个 WebGL 终端） | 每个 WebGL 终端约 10–30 MB |
| Supervisor | ≤ 70 MB | ≤ 120 MB | SQLite 页缓存 32 MB、投影、合并器；§13.5 可达性检查的 `worker_thread`（每个挂载点至多两个，各是一个独立的 V8 isolate）未计入，E6 一并测量后回填（ADR-237） |
| Engine Host（每个活跃 Goal） | —（空闲时不存在，§13.5） | 目标 ≤ 60 MB；软上限 150 MB；硬上限 512 MB（V8 堆）；打包时 ≤ 15 MB/Goal | Node 基线 + Pi 模块 + 会话条目；文件工具调用期间 Pi 在 Host 中持有整份文件（≤ 16 MB，`edit` 时为其数倍，瞬时）。文件工具辅助进程不在本行：它是按次启动的一次性子进程，与 Agent 的工具子进程一样计入 §13.8.3 的进程树预留（`11` §11.3.1 使用时强制，ADR-221），所以 Host 的各项测量只量 Host 进程本身仍然完整 |
| Verifier Runner | — | ≤ 60 MB，不含被测进程 | 一次验证尝试 |
| RPC Host（**M2**，ADR-059） | — | Host 本身约 40 MB；每个 pi 子进程约 100 MB | `RpcProcessClient` × K |

### 13.8.2 长会话增长

Pi 的 `SessionManager` 把会话全部条目保存在内存中；长时间运行的 Goal（数千条目、大工具输出）会让 Host 增长。策略：

| Host RSS | 动作 |
|---|---|
| > 150 MB | Fact `host_resource{kind:"memory_high"}`；Goal 卡片周边提示 |
| > 300 MB 或 V8 堆 > 400 MB | 在下一个 Run 边界建议“以交接包开新会话”（`02` §2.11，ADR-015 中“上下文过长时才开新会话”的同一机制） |
| 崩溃（OOM） | Supervisor 从 JSONL 恢复；Mode 经 `unresponsive` → 恢复；记 Fact |

### 13.8.3 整机资源模型与准入（ADR-042，R2-D7-01、R2-D10-02）

工具子进程（测试、编译、dev server、服务）与验证器决定整机体验。模型是**预留式**的：每个活跃实体在被准入时预留内存与 CPU，准入只看预留总和；瞬时空闲内存与内存压力只作为额外的刹车。所有数值登记在 `16` §16.2.6，本节给出语义与演算。

| 实体 | 内存预留 `m` | CPU 预留 `c`（核） | 硬上限（超出即处置） |
|---|---|---|---|
| 系统与用户其他应用 | **RAM 的 25%**（不进入 Tower 的可分配额度） | `max(2, 0.25 × cores)` | — |
| Tower 自身（main + renderer + GPU + Supervisor） | 0.65 GB（= §13.8.1 四项“负载时”之和，假设值，ADR-186） | 0.5 | — |
| 每个运行中 Goal | Host `h` + 进程树预留 `p90_g`（该项目近 20 次 Run 进程树峰值的 p90；无历史时 **1.2 GB**；Tower 为文件工具启动的一次性辅助进程同样作为已知的直接进程计入，它们不带 Run 令牌、不会被下述上限终止，ADR-221）——它只用于**预留**（准入记账），不用于杀进程 | 1 | **杀进程上限 = `max(m_kill_v, 1.5 × p90_g, 2 GB)`**（`m_kill_v` 为该项目验证器的杀进程上限 `max(2 GB, 2 × m_v)`，`07` §7.4.4；R3-D10-01）：Agent 在自己的卫星里跑同一套测试，其峰值与验证器相当，上限不得低于验证器的上限，否则会误杀合法的测试运行。**采样机制**（ADR-145/146；`10` §10.3.1 第 ⑤ 种时机）：macOS 上每 5 s 从 Tower `exec` 已知的直接进程出发，以 `proc_listchildpids` 递归遍历后代树、`proc_pidinfo` 求内存之和——**后代树遍历预算**：每个节点约 20–50 µs，一个 Goal 的进程树通常 ≤ 50 个节点 → ≤ 2.5 ms / Goal / 5 s；脱离进程树的后台进程由**令牌全扫描**覆盖，仅当 Run 活跃且该 Goal 设有内存上限时**最多每 60 s 一次**（单次预算见 §13.11.1“令牌扫描”行：1 000 个进程 ≤ 50 ms，即 ≤ 0.001 核）；Linux 读 Run 子 cgroup 的内存统计。超过上限 → 终止 RSS 最大的、带本 Run 令牌的进程（发信号前再确认令牌），Fact `host_resource{kind:"resource_exceeded"}`，`steer` 告知 Agent。残余：脱离进程树的后台进程的内存最多晚 60 s 计入 |
| Host `h` | 按 `16` §16.2.6 的唯一回退规则：独占模式 = SP2 实测 RSS p95（假设值 ≤ 0.12 GB——实测超过 120 MB 时按同一规则改为打包模式，ADR-185）；打包模式 = 打包 Host 实测 p95 / K | 含在上一行 | `--max-old-space-size=512` |
| 每个验证槽位（正式验证） | **按项目实测**：`max(1 GB, 1.3 × p95(验证进程树峰值 RSS, 最近 20 次))`；无历史时 **2 GB** | 2（测试运行器多进程；验证以 `taskpolicy -c utility` 运行，超订时变慢而不卡 UI） | 同 `07` §7.4.4（以本预留为限） |
| 机会式验证（ADR-020） | 不另外预留：**只在正式验证队列为空、有空闲的已预留槽位、且整机 CPU 负载 < 70% 时**运行（ADR-042；CPU 配额见 §13.11.2） | 同上 | 正式验证到来时立即让出槽位（中止机会式验证） |
| 声明 `services` 的项目（ADR-037） | 每个实例 `VerifyProfile.services[].memMb`（未声明时 0.5 GB；docker 服务 1 GB）；Goal 卫星与验证槽位各一份实例 | 0.5 | — |
| fsmonitor 守护进程 | ADR-060 下影子上下文默认禁用 fsmonitor → **M1 为 0**；若 SP5 评估通过而启用 Tower 内置守护进程，则每个卫星或槽位 15 MB | — | — |

**准入规则**（扩展 `06` §6.2.4 的 d 步“资源”检查）：

```
A    = 0.75 × RAM                                        # Tower 可分配额度
Mres = m_tower + Σ_running(h + p90_g) + Σ_slots(m_v) + Σ_services(m_svc) + Σ_fsmonitor(15 MB)
准入新 Run（候选 g）：     Mres + h + p90_g(g) [+ g 的服务] ≤ A
维持验证槽位数 k：         以 k = 2 计算 Mres；若 > A，k 降为 1（UI 显示该项目的预计验证排队时间）
CPU（软约束）：            Cres = c_tower + c_os + Σ_running(1) + 2k ≤ 1.5 × cores；超出时只降 k，不阻止 Goal
刹车：                     系统内存压力（macOS memory_pressure / Linux PSI some avg10 > 20%）在 warn 及以上时不准入新 Run
```

验证**优先于**新 Run 准入：槽位预留先于 Goal 计算。

**参考配置演算**（M1 Pro 10 核 / 16 GB；A = 12 GB）：

| 场景 | Tower | 3 个 Goal（各 0.15 + 1.2） | 验证槽位 | 服务 | fsmonitor（5 个，若启用） | 合计 | 余量 | 槽位数 |
|---|---|---|---|---|---|---|---|---|
| 无服务的 Node 项目 | 0.65 | 4.05 | 2 × 2 = 4.0 | 0 | 0.075 | **8.8 GB** | 3.2 GB | 2 |
| 每实例 0.5 GB 服务（5 个实例） | 0.65 | 4.05 | 4.0 | 2.5 | 0.075 | **11.3 GB** | 0.7 GB | 2 |
| docker 服务 1 GB（5 个实例） | 0.65 | 4.05 | 4.0 | 5.0 | 0.075 | 13.8 GB > A | — | **降为 1**：10.8 GB（少一个槽位及其服务实例与 fsmonitor 份额） |
| 项目实测验证峰值 3 GB（`m_v` = 3.9） | 0.65 | 4.05 | 2 × 3.9 = 7.8 | 0 | 0.075 | 12.6 GB > A | — | **降为 1**：8.7 GB |

CPU：10 核时 `0.5 + 2.5 + 3 + 2×2 = 10 ≤ 15`（8 核变体同样得出 2 个槽位：`0.5 + 2 + 3 + 4 = 9.5 ≤ 12`）。结论：参考硬件上“3 个 Goal + 2 个验证槽位”在无服务与轻服务项目上成立，为系统与用户应用保留 25%（4 GB）；重服务或验证峰值高的项目自动降为 1 个槽位，并如实显示排队时间。M1 的验证延迟预算（claimed → in_review p50 ≤ 10 min、p95 ≤ 20 min，`16` §16.2.6）**只对参考项目承诺**（ADR-042）。

**机会式验证的预期频率**：参考配置下 2 个槽位、3 个运行中 Goal，正式验证占用约 30–40% 的槽位时间（`07` §7.4.10 演算），空闲槽位足以让每个 Goal 约每 15–25 min 获得一次机会式验证（每次约 17 核分钟，即每 Goal 每小时约 40–70 核分钟——上限 50 核分钟/小时会把频率压到约每 20–25 min 一次）；E4 与 E12 测量运行中 V 轨的实际推进频率。

**Agent 存储预热的成本**（R2-D10-02）：每个新 Goal 的 `<wtRoot>/_stores/<goalId>/` 从验证器存储 CoW 预热（`10` §10.4.1、`16` §16.8），APFS 上为元数据级复制（通常 < 2 s、几乎不占新块），不产生网络下载；跨卷或无 CoW 的卷上为完整复制，计入 `10` §10.4.4 的磁盘预算与 §13.11 的后台预算。

被资源挡住的 Goal 停在 `ready`（`waitReason = slot`，Mode `queued`），卡片注明“机器资源”（`06` §6.2.4 步骤 d，ADR-197）。评审积压上限（ADR-014）限制“待审代码的生成速度”，资源准入限制“机器负载”，两者在卡片上分别说明。验证器的优先级由 `07` §7.4.4 定义；冲突雷达、depcache 预热、备份 bundle 以最低优先级运行（macOS `taskpolicy -b`，Linux `nice -n 19 ionice -c3`）。设置页按此模型给出 `maxConcurrentGoals` 的推荐值，用户设置超过推荐值时提示“将排队等待资源”，不阻止。

## 13.9 事件日志：写入吞吐与 SQLite 调优

### 13.9.1 负载估算

| 来源 | 每个运行中 Goal | 说明 |
|---|---|---|
| 工具起止 | ~0.2–1 次调用/s × 2 | `tool_execution_start/end` |
| 回合 / 消息结束 / 模式变化 | ~0.2/s | |
| Fact（观察器、哨兵、指纹、预算） | ~0.3/s | |
| 合计 | ~1–3 事件/s，突发 20/s | `message_update` 不入日志（`02` §2.13） |

10 个运行中 Goal：稳态 ≤ 30 事件/s，突发 ≤ 200 事件/s。合成压力测试使用 1000 事件/s 验证 30 倍余量。

事件负载控制在小尺寸：`tool.end` 只记退出码、耗时、输出字节数、`piEntryId`，**不记输出正文**（正文在 Pi JSONL 中）；大块证据（验证日志、diff）写文件，以 `EvidenceRef{type:"log", path, byteRange}` 引用。单条负载上限 16 KB，超出即视为 bug（CI 断言）；带路径集合的事件（适用的事件只在 `06` §6.3“载荷中的路径集合”列出）超限时按该处以内容哈希外置，不截断（ADR-213/214）。

### 13.9.2 Schema 与连接参数

DDL、索引与连接参数**以 `06` §6.3 为准**（`events` 带 `idem_key`、`v`、`producer`；索引 `events_goal_seq`、`events_run_seq`、`events_type_seq`）。从性能角度对 `06` 的参数只提两条需在 P2/P7 场景中验证的意见：

- `06` 已采用 `wal_autocheckpoint = 0` + 空闲定时器每 30 s `wal_checkpoint(PASSIVE)`：自动检查点会在提交路径上同步执行，突发写入时可能造成数十毫秒的提交停顿。P2 中需验证空闲定时器下 WAL 不超过 64 MB（§13.12.5）、批提交 p99 ≤ 10 ms。
- 读多的跨 Goal 统计与 Trace 搜索使用 `worker_threads` 中的只读连接，避免同步 `DatabaseSync` 调用阻塞 Supervisor 事件循环（§13.5）。

### 13.9.3 写入路径的性能要求

- **组提交**：事件进入内存队列，每 50 ms 或满 256 条时在一个 `BEGIN IMMEDIATE` 事务中写入（`06` §6.6.5：投影与事件同一事务）。M1 级硬件上可支撑数万行/秒，远超需求；预算为批提交 p99 ≤ 10 ms。
- **注意力关键与人的决定**立即单独提交，不等 50 ms 窗口；人的决定的持久性规则（立即单独提交并使用 `synchronous=FULL`）唯一定义在 `06` §6.3，本文不另写（ADR-194）。
- **投影快照**：每个投影每 1000 个相关事件或 60 s（取先到者）写一次快照，供启动（§13.10）与订阅者重同步使用。
- **保留**：按 ADR-005 的分层保留——`archived` **与 `abandoned`**（ADR-057）30 天后，在写出最终投影快照的前提下删除 `engine.*` 细粒度事件，永久保留 Fact / Claim / HumanDecision / 状态变化 / 审计；隐私清除用墓碑化。删除后在空闲时增量回收空间。
- **数据库预算重算**（ADR-057）：细粒度事件约占每 Goal 事件量的 85%、每条约 300 B。重度使用（10 个并发 Goal、8 h/天）每天约 1–3 事件/s × 10 × 28 800 s ≈ 30–90 万条 ≈ 90–260 MB/天，其中约 85% 在终态 30 天后删除；稳态数据库 ≈ 最近 30 天的细粒度事件（按约 22 个工作日计 0.85 × 90–260 MB × 22 ≈ 1.7–4.9 GB 峰值，取决于终态 Goal 的比例；ADR-197）+ 长期保留部分（约 15%，≈ 15–40 MB/天；按每年约 250 个工作日计 ≤ 10 GB，每天都满负荷时 ≤ 14.6 GB）。预算：日增长 ≤ 260 MB；30 天窗口峰值 ≤ 5 GB；超过时设置页提示并提供“立即压缩已终态 Goal”。M1（3 并发）约为上述的 30%。

### 13.9.4 Trace 读取

Tower 不复制对话内容；Trace 抽屉读取 Pi 的 JSONL。Supervisor 为每个会话文件维护增量的 `entryId → byteOffset` 索引（文件尾追加时增量更新），翻页时按偏移读取并解析 200 条（p95 ≤ 30 ms）。全文搜索在 search worker 中进行，索引按需构建。

| 安装阶段的只读 store 回退（ADR-092 修订，R8-D10-01，规则以 `07` §7.4.3 为准） | 只在 SP6c 证明某 pnpm 版本无法在只读 store 上离线安装 / rebuild 时启用；按序：① 只私有化 store 的索引与临时目录；② 对 store 做 CoW 私有副本（不支持写时复制的卷上禁用，改报 `verify_env_error{stage:"install", detail:"readonly_store"}`） | ①：额外 ≤ 2 s、磁盘 ≤ 50 MB；②：APFS 上逐文件克隆约 1–3 s / 10 万文件（元数据级，几乎不占新块），只在首次安装某 depsKey 时发生，临时占用计入 30 GB 预算并随暂存目录删除。副作用缓存关闭：每个新 depsKey 都重建原生依赖，参考项目约 +20–90 s（node-gyp 类包数决定），计入首次验证的服务时间。SP6c 测量“只读 store / ① / ② / 副作用缓存关闭”四种情况的时长与磁盘，结果回填本行并据此分支 | 首次验证关键路径（单列显示） |
| 人工编辑检出（`10` §10.8.4） | `goal.take_over` / `hand_back` | 创建：由影子树物化（read-tree + checkout-index）后**立即打开**，目标 < 2 s（SP5 回填）；依赖在后台准备——depcache 命中时 CoW 物化 < 2 s，未命中（Agent 改过 lockfile、该 depsKey 未构建）时由安装器后台构建，量级同首次验证的安装（参考项目 1–5 min，含预取），期间检出与卡片显示 `依赖准备中`（R10-D10-01b）；交还与检验带回：一次求树（求 T1，同指纹预算）+ 逐文件复制；之后来源目录不删除，不再为删除重新求树（`10` §10.2，ADR-228） | 普通（人在等待打开；依赖为后台） |

### 13.11.2 总预算

单项预算不够：N 个 Goal 的指纹、检查点、diffstat、雷达、备份叠加起来，会与 Agent 自己的构建争抢 CPU 和 IO。总预算以**核秒**计（git 的 `add`/`write-tree`/`diff` 基本单线程，保守地按“墙钟 × 1 核”计）：

| 指标 | 预算（60 s 滑动窗口） | 说明 |
|---|---|---|
| 后台 git 核秒（指纹 + 检查点 + diffstat + 雷达 + 备份 + fetch 的本地部分 + 缓存完整性全量哈希） | ≤ `0.10 × cores × 60` 核秒（10 核机器 = 60 核秒/分钟，即平均 1 核） | 不含正式验证与机会式验证（它们按 §13.8.3 预留） |
| 后台 git 磁盘读 | ≤ 50 MB/s 平均 | 主要来自无 fsmonitor 时的 `add -A` stat 与 rehash |
| 机会式验证 | 每运行中 Goal 每小时 ≤ 6 次、累计 ≤ 50 核分钟（参考项目每次约 17 核分钟，`07` §7.4.10）；只在正式验证队列为空、有空闲已预留槽位、且整机 CPU 负载 < 70% 时运行（数值见 `16` §16.2.3） | 超过任一上限即延长间隔（10 → 20 → 40 min）；CPU 负载 ≥ 70% 时不启动、运行中的不中止 |

**负载估算**（无 fsmonitor、5 万文件仓库、指纹 0.8 s）：每个运行中 Goal 约每 10 s 一次 bash/edit 结束 + 每 20 s 一次 `turn_end` → 约 0.12 核秒/秒；3 个 Goal ≈ 0.36 核，在 10 核机器的 1 核预算内；5 个 Goal + 雷达接近上限。ADR-060 下影子上下文不使用 fsmonitor，这就是 M1 的常态；若 SP5 评估通过启用 Tower 内置 fsmonitor，快路径可降到 1/10 以下。

**测量**：`GitRunner` 记录每次调用的墙钟时长、操作类型与 Goal（核秒近似 = 墙钟）；macOS 另每 5 s 用 `proc_pid_rusage`（经 `ps -o time=` 采样 git 子进程）校准 CPU 占用率。指标进入性能面板与 CI 场景 P8（§13.12.2，ADR-185）。

**降级（预算超出持续 30 s 时按序启用，低于 70% 持续 2 min 时逆序恢复）**：

1. 冲突雷达暂停；备份 bundle 推迟（`claimed`/`accepted`/退出时仍必做）。
2. 指纹防抖 500 ms → 5 s（`in_review` 期间的文件系统事件驱动检查不降级，但同一 Goal 的事件合并为每 5 s 至多一次）。
3. 检查点改为每 3 个有变更回合一次（`10` §10.7.2 的降级档）。
4. diffstat 只在 Goal 页聚焦或检查点地标时计算。
5. 设置页提示为超大仓库启用稀疏检出（`10` §10.14）；若 SP5 评估通过，启用 Tower 传入的内置 fsmonitor（ADR-060 下默认关闭）。

**文件系统事件的可靠性（R5-D10-02，规则以 `07` §7.3.2 为准）**：`in_review`/`accepted` 的新鲜度依赖 FSEvents/inotify。监视器必须暴露丢事件标志（Node 的 `fs.watch` 不暴露 FSEvents 的标志位，因此用直接封装 `FSEventStream` 的原生模块或 `@parcel/watcher` 一类实现，SP5 选定）。FSEvents 报告 `MustScanSubDirs`、`UserDropped`、`KernelDropped`，或 inotify 报告 `IN_Q_OVERFLOW` → 立即执行一次 decisive（影子索引 stat 检查，2 万文件 ≤ 150 ms），完成前该 Goal 的新鲜度标签显示“确认中”。监视建立失败（inotify `ENOSPC`：`max_user_watches` 耗尽；FSEvents 流创建失败）→ 该 Goal 退回每 60 s 一次 decisive 巡检，新鲜度旁注明“监视降级”（Fact 最长可能晚 60 s 才过期）。Linux 上建立监视前先估算所需 watch 数（未被忽略的目录数），超过剩余额度的 50% 直接使用巡检。成本：每个降级 Goal 每分钟 ≤ 0.15 核秒，计入 §13.11.2。

**永不降级**：`submit`/验证 pin 前的决定性指纹（stat 检查）、`pinSafetyCheck`（`verify()` 第一步、验收、seal 前，ADR-109）、卫星 watcher 的 `.git` 名字判定（ADR-131；监视降级时改为检查点前全量，不跳过）、验收与 seal 闸口的完整重哈希、`in_review` 期间文件系统事件触发的 I2 判定（事件合并可放宽，但不跳过）、地标检查点（submit、rework_start、safety）。

### 13.11.3 磁盘：重放包与证据（ADR-095，R6-D6-01、R6-D10-01c）

| 对象 | 规则 | 量级 | 计入 |
|---|---|---|---|
| 永久重放包（只限走到槽位路径的决定性验证：导致 `in_review`/`accepted` 的验证，`07` §7.4.1，ADR-187） | 永久，只能经隐私清除（`09` §9.12.4）删除；每条标准的脱敏输出 ≤ 2 MB；本地不另存瘦 bundle（`07` §7.4.1） | 平均每个 Goal 1–2 个；不含输出时 < 1 MB，含输出常见 1–10 MB → 每个 Goal ≈ 2–20 MB | Tower 总占用（`16` §16.2.6 的 min(30 GB, 卷可用 20%)） |

## 13.12 测量与 CI

### 13.12.1 合成 Agent

`FakeEngineAdapter` 实现 `EngineAdapter`（`05`），两种模式：

- **回放**：读取真实 Pi JSONL 会话（来自团队自用，脱敏后入库为测试夹具），按原时间轴 1× / 10× 重放为 Pi 事件序列（含 `message_update` 增量、工具起止、重试、压缩）。
- **生成**：按参数生成事件：每 Goal 100 事件/s（`text_delta` 80/s、`tool_execution_update` 10/s、工具起止、偶发 `ask_user` 与哨兵），持续时长、Goal 数可配。

合成 Agent 同时驱动一个真实的临时 git 仓库（按脚本写文件），使检查点、指纹、雷达、diff 走真实路径。

### 13.12.2 场景（Playwright for Electron，`_electron.launch`）

| 场景 | 内容 | 主要断言 |
|---|---|---|
| P1 冷启动 | 预置 200 个 Goal（含 10 个运行中）的数据库 | 冷启动 p50/p95、启动包大小 |
| P2 看板满载 | 10 Goal × 100 事件/s，看板视图 5 分钟（10 Goal 是以预置数据与合成事件驱动的夹具负载，不经准入，与 M1 的 3 个构建并发上限不冲突，ADR-194） | 主线程脚本 ≤ 2 ms/帧、无长任务、合并器输出帧率 |
| P3 聚焦 + Watch | 聚焦一个 Goal 并开启 Watch 模式，滚动 10 万条 Trace | 事件 → 绘制 p95、滚动帧率 |
| P4 大 diff | 打开 1 万行 / 200 文件变更集，以及 §13.6 四种最坏情况 | 文件列表、首屏、高亮时间；最大主线程停顿 |
| P5 评审中输入 | 在评审评论框中以 IME 输入中文，同时 10 Goal 流式（夹具负载，同 P2） | 按键 → 绘制 p95 ≤ 8 ms；IME 回车不提交 |
| P6 Needs-You 洪峰 | 1 分钟内 50 条 Needs-You | 产生 → 可见 p95 ≤ 100 ms；洪峰合并生效（`08`） |
| P7 恢复 | 杀死 Supervisor 与一个 Host | 恢复时间、无事件丢失（seq 连续） |
| P8 后台 git 负载（ADR-185，原写作 P2 的另一种定义） | 3 个与 5 个运行中 Goal、5 万文件夹具仓库 | 后台 git 核秒/秒不超过 §13.11.2 的预算；超支时降级按序启用与恢复 |
| P9 诊断视图（ADR-191） | 一个运行中 Goal 产生 `stalled` 后（诊断包已在后台预计算）按 `T` 接管，同时 3 Goal 流式 | 接管 → 诊断视图首屏 p95 ≤ 300 ms |

### 13.12.3 采集

渲染进程：`performance.mark/measure`；`PerformanceObserver` 订阅 `event`（`durationThreshold: 16`）、`long-animation-frame`、`longtask`；帧时间来自 rAF 时间戳差。主进程：`app.getAppMetrics()`（每进程 CPU/内存）、`contentTracing` 录制 Chromium trace 作为 CI 产物。utilityProcess：`process.memoryUsage()`、`monitorEventLoopDelay`。端到端延迟用同一单调时钟：Supervisor 在帧上附 `performance.timeOrigin + now()`，渲染进程在绘制后的下一个 rAF 中打点。

### 13.12.4 判定

- 专用性能机：Mac mini（Apple Silicon，16 GB，120 Hz 外接屏），关闭 Spotlight 索引与自动更新。
- 每个场景运行 10 次，取 p50/p95；**失败条件**：超过绝对预算，或相对基线（`main` 最近 5 次的中位数）回退 > 10% 且 Mann-Whitney U 检验 p < 0.05。
- 每个 PR：P1 + P2（2 分钟）+ P5 冒烟；每晚：全部场景；每周：8 小时浸泡。

### 13.12.5 8 小时浸泡（E6，`14`）

10 个合成 Goal（真实速率：每 Goal 3 事件/s，含突发）+ 2 个真实 Pi Goal（廉价模型，执行脚本化任务）；导航脚本每 30 s 切换视图（看板 → Goal 页 → diff → Trace → 收件箱）。在 0、1、4、8 h 拍堆快照。通过条件：渲染堆增长 < 10%、Supervisor < 20%、分离 DOM 节点数稳定、xterm/Monaco 实例数回到基线、文件描述符数稳定（`lsof` 计数）、WAL ≤ 64 MB、无崩溃、事件 seq 无空洞、全程满足 §13.1 预算。

## 13.13 过载降级

### 13.13.1 触发（带迟滞：超过阈值持续 2 s 进入，低于阈值持续 10 s 退出）

| 信号 | 阈值 |
|---|---|
| 渲染进程帧时间 p95（滑动 2 s） | > 20 ms（60 Hz）/ > 12 ms（120 Hz） |
| 长动画帧（> 50 ms） | 5 s 内 ≥ 3 次 |
| Supervisor 事件循环延迟 p99 | > 50 ms |
| 合并器 `dirty`（`06` §6.4.5） | 任一订阅者 |
| 系统内存压力 | macOS `memory_pressure` 级别 warn / 可用内存 < 10% |
| 电池且低电量模式 | 开启 |

### 13.13.2 丢弃顺序（先丢的在上）

| 级别 | 降级项 | 用户可见标记 |
|---|---|---|
| D1 | 周边装饰冻结：活动发丝线（sparkline）、相对时间文本只在档位变化时更新 | 无（本就是周边信息） |
| D2 | 后台 Goal 的看板卡片数据帧（`16` §16.4：250 ms，仅计数类字段 500 ms）→ 2 s（ADR-194） | 看板角落“节流中” |
| D3 | 语法高亮只处理可见区；新打开的 diff 先以纯文本显示 | diff 顶部“高亮已延迟” |
| D4 | 聚焦 Goal 的流式文本改为只在 `message_end` 渲染（不逐 token），Live Line 仍按 1 Hz 更新动作与对象 | Live Line 旁“流式已暂停” |
| D5 | Trace 抽屉停止自动跟随，显示“N 条新事件”胶囊 | 胶囊 |
| D6 | 终端输出合并到 10 Hz；不可见终端仅保留 headless | 终端标题栏标记 |
| D7 | 冲突雷达、依赖预热、备份 bundle、机会式验证（ADR-020）、观察器重算（diffstat）暂停；正式验证并发降到 1 | 设置页“后台任务已暂停” |
| D8 | 准入控制：属于 `06` §6.2.4 步骤 d（资源）的一种情形，不是另一个准入条件——整机预留不足时 Goal 停在 `ready`（`waitReason = slot`，Mode `queued`），卡片注明“机器资源”（ADR-197） | 卡片说明 |

**永不丢弃**：事件日志写入（事件只在 UI 侧合并，从不在日志侧丢弃）、Needs-You 的产生与投递、生命周期状态变化、Mode 变化、命令回执、心跳与 `unresponsive` 检测、steer 投递、哨兵 severity ≥ 2。

当 Supervisor 本身过载到无法按时写日志时，背压沿通路回传：Host 侧预合并窗口从 10 ms 放宽到 100 ms（只影响 `text_delta`/工具部分输出这类可合并事件），仍然不丢离散事件。RPC 适配器下 Pi 遵守 stdout 背压，读端变慢会让 Agent 变慢而不是丢事件（`gui.md` §4.6）——这是可接受的退化方向。
