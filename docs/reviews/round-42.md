## 1. 总评

ADR-167 收齐了 R41 的大部分条目：
- `secret_file_unseeded` 有了交还 Agent 的出口；
- 本地文件的 add / remove / approve 有了命令与决定类型；
- 交还时排除机密本地文件；
- npmrc 只读用户级文件；
- `verify_profile.update` 有了字段级远程规则。

排期算术成立（WBS 121.63，38 周）。

仍有一处实质缺口：判定依据从“输出中的文件名”换成了“沙箱记录到读取尝试”。这解决了伪造问题，没有解决过宽问题：
- dotenv、Vite、Next 一类加载器每次运行都会尝试读取 `.env.local`，读取尝试与失败原因之间没有因果关系；
- 文件不存在时，Seatbelt 的拒绝规则本机实测根本不生效；
- 新加的反例用例 G46(t) 与 C29(e) 设定了一个不可能出现的前提。

### D4 领域模型与生命周期

**R42-D4-01｜次要**（“改为 human 标准”的 `contract.amend` 是否解除 `verify_env_error`，三处说法不一致）

- **问题**：
  - **`03` 的读法**：
    - `03` L86 在 `verify_env_error` 行的“命令 / 守卫”列中写“改为 human 标准 → `contract.amend`（……按 §3.4.5 修订矩阵以新合同重新验证）”；
    - 按 `03` L69 的唯一规则，该列中的每个命令都“解除本原因”。
    - 照此读法：修订即解除，继续目标仍是 `verify{pin}`，`onAllReasonsCleared()` 以同一 pin 按新合同重新验证。
  - **`06` 与 §3.4.5 的读法**：
    - `06` L860 `contract.amend` 的效果列只写 `contract.ratified`、`superseded` 与清除 `until_amend` 静默，没有“解除 `verify_env_error`”；
    - `03` §3.4.5 L167 的 `paused` 列写“受影响 Fact `expired`……修订后可 `retry_verify`”，这是两步。
    - 照此读法：修订后目标仍暂停。
  - **Needs-You 的去向**：`08` L506 规定“改为 human 标准（`contract.amend`）→ `actionable`”，修订时就关闭条目。实现者若按 `06` 写处理函数，界面也没有补发 `retry_verify`，Goal 就停在 `paused(verify_env_error)`，而且没有打开的 Needs-You。
  - **哪些修订算数**：哪些修订会解除本原因，也没有写。任意修订都算，还是只有改动了 `files` 所涉标准的修订才算？
  - R41-D4-01 的期望形态已经点出这一项：“同一事务或明确的两步”。
- **为什么重要**：
  - ADR-134 要求暂停出口只在 `03` §3.2.1 一处定义，而命令表是实现者写处理函数的地方；
  - 两种读法会得到不同的状态，其中一种会让 Goal 在没有 Needs-You 的情况下停住；
  - 结局有界（人仍可在卡片上手动重试），评为次要。
- **文档位置**：`03` L69、L86、L167；`06` L860、L879；`07` L454；`08` L506；`04` L1480；`14` G46(w)。
- **期望的回答形态**：
  - `06` L860 加一句：`paused(verify_env_error{secret_file_unseeded})` 中，修订改动了 `files` 所涉的标准时，解除本原因（继续目标不改写，仍为 `verify{pin}`），否则不解除；

### D7 诚实与验证

**R42-D7-01｜重要**（“沙箱记录到读取尝试”仍是共现信号：容错加载器每次都会尝试读取；文件不存在时拒绝规则不生效；反例用例的前提不可能出现）

- **问题**：
  1. **读取尝试 ≠ 失败原因**：
     - `07` L453 的条件是“标准失败**且**沙箱报告记录了对这些路径的读取尝试”；
     - 但最常见的读取者是**容错**加载器：
       - dotenv 对配置的路径总是调用 `readFileSync`，文件不存在就吞掉错误继续运行（本机 17.4.2，`lib/main.js:277`）；
       - Vite 系工具链与 Next 的环境加载同样在每次启动时尝试 `.env`、`.env.local`、`.env.<mode>`、`.env.<mode>.local`；
     - 也就是说，在 R41 指出的同一类项目中（用 dotenv 加载 `.env.local`，或任何 Vite / Next 项目），只要有一条标准失败，即便失败原因是普通断言，也**必然**伴随一次读取尝试。
     - 规则一旦生效，R41-D7-01 列出的后果原样存在：
       - 真实失败被改判为“不是 Agent 的失败”，不返工；而 `outcomeOf` 中 `env_error` 优先于 `fail`（`07` L1498-1499），同一次验证中其他标准的真实失败也一并不返工；
       - 试运行中，本应是红灯的标准全部显示 `◇ 需要本地机密文件`（`04` L1092）；
       - 人被引导把可机器验证的标准改为 human 标准。
     - `.env.local` 恰好是各文档中本地文件的标准示例（`07` L484、`04` L1480）。
  2. **文件不存在时拒绝规则不生效**：
     - 未播种就意味着该路径在槽位中**不存在**（`07` L479 `clean -ffdx` 之后只播种普通条目）；
     - 本机实测，对不存在的路径设置 Seatbelt 读取拒绝，读取返回 `ENOENT` 而非 `EPERM`，拒绝没有发生，日志中也没有观察到记录；
     - 于是有两种可能：
       - (a) 生产中规则永远不触发。这时既不做归类，也**不**显示回退提示，因为提示只在 A13 判为“报告不可用”时启用（`07` L456），人得到的是没有任何线索的返工循环；
       - (b) 实现者为了让规则触发而在路径上放占位文件，或找到能记录不存在路径查找的机制。那就回到第 1 条。
     - `14` A13（L63）的方法是“对一组路径设置拒绝并报告的读取规则，被测代码……分别读取这些路径”，没有规定这些路径不存在。用存在的文件测得“可用”，再在生产中走 (a)，这正是该实验最可能给出的误导结论。
  3. **反例用例的前提不可能出现**：
     - G46(t)（`14` L134）设定“测试用 dotenv 加载 `.env.local`（不存在，dotenv 打印了文件名）……且沙箱报告中**没有**对该路径的读取尝试”；
     - `05` C29(e)（L1407）同样写“dotenv 打印文件名但断言失败的反例归为普通失败”；
     - 在规则自身的假设下（沙箱能记录对这些路径的读取），dotenv 加载该文件**一定**产生读取尝试，所以这两条用例要么无法构造，要么按现行规则会失败。R41 要求的反例因此没有真正落地。
  4. **期望形态未采纳**：R41 期望形态中的“优先级”（reporter 已解析出与该文件无关的失败用例时按普通 `fail`）与“保守出口”（只提示、不改归因），ADR-167 都没有采纳。换了信号源，但没有补上因果条件。
- **为什么重要**：
  - 诚实语法要求 Fact 推导出的归因（“不是 Agent 的失败”）不误导。读取尝试只能证明“被测代码想要这个文件”，不能证明“失败是因为没有它”；
  - 第 1 条在一类很常见的项目上稳定发生，第 2 条让主规则可能完全失效，连回退提示也一起丢掉；
  - 不会把失败标为通过，所以不是阻断。但它仍然直接损害 M1 的自动返工回路与红灯机制，与 R41-D7-01 同级，评为重要。
- **文档位置**：`07` L451-456、L1498-1499、L1588；`04` L1092、L1480；`08` L191、L506；`11` L413-414；`12` L417；`16` L97；`15` ADR-167（L1613）；`14` A13（L63）、G46(n)(t)(u)（L134）、L178；`05` C29(e)（L1407）。
- **期望的回答形态**：在 `07` §7.4.1 把读取尝试降为**证据注记**，或补上一个结构性的因果条件，二选一写成规则：
  - **注记方案（推荐，最保守）**：
    - 有读取尝试时，失败仍按普通 `fail` 处理，照常返工；
    - 该标准的 `criterion_check` 附 Fact 注记 `secretFileReadAttempted{files}`。卡片写 `◇ 运行时尝试读取未提供的本地机密文件 .env.local`；返工开场如实告诉 Agent 验证中没有该文件；
    - 同一标准连续因失败进入 `verify_failed_limit`，且每次都有该注记时，`verify_failed` 的 Needs-You 把“改为 human 标准”列为首选；
    - 试运行照常显示 `✓ 红灯`，旁边附同一注记；
    - `secret_file_unseeded` 这个 stage 可以删去，或只保留给下一种情形。
  - **因果条件方案**：只有“读取尝试 + 该标准没有任何已解析的用例结果（加载期即失败，reporter 报告 0 个已执行用例）”才记 `secret_file_unseeded`；reporter 解析出具体失败用例时一律按普通 `fail`，并附上面的注记。
  - **A13**：
    - 方法改为在**路径不存在**（生产条件）与路径存在两种条件下分别测量；
    - 另加容错加载器（dotenv、Vite 系、Next 的环境加载）一组，记录它们是否每次运行都产生读取尝试；
    - 写明：只有存在路径的读取能被记录时，按“不可用”处理。
  - **回退提示**：与 A13 的分支脱钩。凡项目有机密本地文件、而该次失败没有被归类时，都显示提示。
  - **用例**：
    - G46(t) 改为真实前提：dotenv 尝试读取不存在的 `.env.local`，读取尝试已被记录，失败来自无关断言 → 按修订后的规则判定，期望为普通 `fail` 并照常返工；
    - 另加 Vite 系一组；
    - 再加试运行一组：同样前提下仍显示 `✓ 红灯`；
    - C29(e) 同步。
