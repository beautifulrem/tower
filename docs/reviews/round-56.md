## 1. 总评

**第 55 轮的 20 条基本落地**：
- 逐条回到正文核对：已解决 18，部分 2（R55-D8-01、R55-D11-02），未解决 0。
- 两条重要条目都已关闭：
  - **R55-D7-01**：`07` §7.4.1 `verify()` 中，L-c 静态哨兵在 `pinSafetyCheck` 之后、任何提前返回之前启动（L384）。每个返回都经 `done()`，它先等哨兵写完、再 `decide()`（L385）。有可运行的 exec 标准时，即使全部命中缓存也取槽位、运行测试清单（L402–405、L439）。缓存只复用标准结果（L890）。缓存命中的决定性验证写保留 ref，并在 `manifest.json` 中列出被复用的事实（L493）。
  - **R55-D13-01**：“从更早的检查点重建”推迟到 M2。M1 的重建只从链上最新的检查点进行，接管期间 B = T0（`10` L907）。`keep_both` 的不相交判定改用写回集合（L918）。“归为人的路径”有了唯一定义（L941–942）。接管期间 `keep`/`revert` 返回 `E_STATE`（`06` L888–889）。
- 第 54 轮的四条“部分”全部关闭。第 55 轮 §5 的 8 条观察全部落地。

**两条“部分”的残留都来自同一种情形：推迟或新增的机制没有落到每一处复述或命令契约上**：
- 新暂停原因 `stalled_timeout` 在 `03` 的出口是 `resume`，但 `06` `goal.resume` 的封闭列表没有它，照 `06` 实现返回 `E_STATE`（R56-D8-01）。
- 项目级运行时授权推迟到 M3 后，`11` L216 仍对无注解的扩展工具提供“本项目内此工具”授权，没有 M3 标记。Goal 页逐条“撤销”的实际作用范围又是整个项目，并且照 `11` 排除 (b) 的写法还包括合同授权（R56-D11-01）。

**全范围扫描新发现 8 条，都是次要，大多是 ADR-183 新规则的派生效果**：
- **开场队列**：消费点唯一化之后，第 ③ 步组装之后追加进队列的作答在 `run.started` 被一并清空，却没有投递（R56-D6-01）。
- **交还归因**：“take_human 恢复的路径沿用 B 中的作者”在数据模型中没有载体。照 §10.7.1 的作者推导实现，Agent 的改动会记为人的改动，并写 `Tower-Human-Edit`（R56-D13-01）。
- **推迟后的 M1 出口**：链上最新的检查点不可用时（情形 G），M1 的重建重试永远失败。接管期间交还与放弃改动都被守卫挡住，人只剩放弃 Goal（R56-D13-02）。
- **其余**：
  - `anyQualified` 自称“`04` 的验收闸只引用本条”，`04` 却另有一张不同的清单（R56-D7-01）；
  - 计划被删空时 `plan:*` 停止条件无法删除（R56-D4-01）；
  - G46(aw) 对非决定性验证期望写保留 ref（R56-D14-01）。

每一条都回到正文核对过，不是推测。本轮没有发现会让实现者违反已声明的安全不变式、或丢失用户数据的问题。

    - 作者推导（`10` L733–734，`16` L211）的顺序是：`mixedPaths` → `mixed`；`externalPaths` 且未 keep → `external`；否则“取检查点的 `author`”。
  - **照推导实现的结果**：
    - 接管前 Agent 改过路径 p（p 在 B 中，不在 T0→T1 中）。接管期间来源不明的写入改了 p，人选 take_human。
    - 第 6 步先做 `safety` 检查点，它含外部内容（`10` L912）。第 8 步的 `human_edit` 检查点把 p 写回 T1（= B）的版本。
    - 最后改动 p 的检查点就是 `author:"human"` 的 `human_edit`，p 不在它的 `externalPaths` 中（只有 keep_both 记）。
    - 推导结果是 p 的 hunk 作者为“你”：
      - seal 因“base..pin 中有作者为 human 的 hunk”（`10` L639）写 `Tower-Human-Edit`，即使人没有任何改动；
      - 评审单元把 Agent 的代码显示为“你的改动”；
      - 验证失败按人的改动不自动返工。
    - 这与 L941–942 本身、L911（任何选项都不会把外部写入记为人的改动）以及 L409 相反。
  - G46(ar) 用的 `docs/x.md` 没有 Agent 的 hunk，覆盖不到这条路径。
- **为什么是次要**：触发条件窄（接管、外部写入落在 Agent 改过的路径上、选 take_human），不丢内容。但规则写对了、载体缺失，实现者只能自行发明字段，或照推导得出相反的结果。归因错误又直接影响 trailer 与返工去向。
- **文档位置**：`02` §2.8（`ReviewUnit.hunks[].author`）；`06` checkpoints DDL；`10` L409、L639、L725–734、L907–912、L941–942；`16` L211；`14` G46(ar)(ax)。
- **期望的回答形态**：
  - `Checkpoint` 增加 `humanPaths?: string[]`（DDL 与 `16` 同步）。`human_edit` 检查点只对其中的路径取 `author`，其余变化的路径在推导中穿透到上一个改动该路径的检查点。或者等价地增加 `agentPaths`。
  - `Tower-Human-Edit` 的条件与 `03` §3.2.1 的“人的改动”窗口改用该字段。
  - G46(ar) 补一组：E 落在 Agent 已改过的路径上，选 take_human，seal 不带 trailer，评审单元作者为 Agent。

**R56-D13-02｜次要**（推迟“从更早的检查点重建”之后，链上最新的检查点不可用时 M1 没有可用的重建出口；接管期间只剩放弃 Goal）

- **问题**：
  - **重建的来源没有排除不可用的检查点**：
    - M1 的自动重建与人发起的重试，都“从影子中最新的检查点或 pin”重建（`10` L1189，`06` L921，`03` L95）。
    - 情形 G（`10` L1191）在对象补不回时把“受影响的检查点标为不可用”，但：
      - 这个标记没有字段（`Checkpoint` 中没有，`16` 中也没有）；
      - “最新的检查点”是否跳过不可用者，没有写；
      - “检查点或 pin”二者怎样取舍，也没有写。
    - 照字面实现，若最新的检查点正是不可用的那个，每次重试都会失败。ADR-183 之前，人还可以选择更早的检查点；现在这条路属 M2。
  - **接管期间的死角**：
    - 接管期间 `satellite_missing` 持续时，`goal.hand_back` 与 `goal.discard_human_edits` 都返回 `E_STATE`（`06` L893、L895，卫星守卫）；
    - 放弃 Goal 时若人工编辑检出 H 中有未交还的改动，先问“丢弃 / 先交还”（`10` L969），而“先交还”此时不可用。
    - 人的改动只留在 H 中，Tower 不提供任何把它们交还的路径，人只能自己复制出来，或丢弃。
- **为什么是次要**：触发需要卫星丢失与镜像对象损坏并存，H 中的内容仍在磁盘上。但这是 ADR-183 推迟一个出口之后留下的未定义分支，并且会把人引向“丢弃”。
- **文档位置**：`03` L95；`06` L893、L895、L920–921；`10` L725–745、L969、L1189、L1191；`16` §16.1.1、L292。
- **期望的回答形态**：
  - 写明重建来源 = “最新的**可用**检查点；都不可用时为 pin（再不可用时为 base）”，并给“不可用”一个持久字段（例如 `checkpoints.unusable`，`16` 登记）。
  - 接管期间重建持续失败时，给出 M1 的出口。例如：
    - 允许在 `satellite_missing` 下以 base 重建卫星后交还，T0 记为重建所用的树（与 ADR-178 的 `rebuiltTree` 同一机制）；
    - 或放弃 Goal 时把 H 原样保留并注明路径，不提供“先交还”。

### D4 领域模型与生命周期

**R56-D4-01｜次要**（修订把计划删空时，“没有计划 = 空操作”与“删除步骤即删除对应条目”冲突：`plan:*` 停止条件无法删除，`include` 停在上一次编译的值）

- **问题**：
  - `02` L354：“没有计划（plan 为空或缺省）时编译是空操作：`include`、`includeOrigin` 与 `stopConditions` 都不变。”
  - L358–359：生成的停止条件“每个版本整体重算……删除步骤即删除对应条目；`plan:` 前缀的条目只由编译产生，不能经修订单独增删改”。
  - **冲突的情形**：本机修订删除全部步骤（`16` L1043：删除步骤仅本机）。按 L354，编译是空操作，旧的 `plan:<stepId>` 停止条件保留；按 L359，它们又不能经修订删除。Agent 仍被要求在开始一个已不存在的步骤前 `ask_user`。
  - **同一分支中的 `include`**：它停在上一次由 `touches` 编译出的集合，`includeOrigin` 仍为 `compiled`。是回到模板值还是保留，没有写。这与 L353 的“编译是合同的确定函数”不符：同一份合同内容，因历史不同而得到不同的 `include`。
- **为什么是次要**：不放宽围栏（保留的 `include` 只会更窄），影响有限；但两条规则直接冲突，实现会分歧。
- **文档位置**：`02` L353–360；`16` L102、L1041、L1043；`14` G46(ba)。
- **期望的回答形态**：
  - 写明计划从非空变为空时，编译删除全部 `plan:*` 条目；
  - `include` 回到 `includeOrigin` 变为 `compiled` 之前的值（需要记录来源），或明确保留并把 `includeOrigin` 改为 `explicit`；
  - G46(ba) 补“删空计划”一组。

### D14 路线图与可验证性

**R56-D14-01｜次要**（G46(aw) 对以 `paused(sentinel_high)` 结束的验证期望“写保留 ref”，与“只有决定性验证写保留 ref”相反；覆盖哨兵之后进入 `in_review` 的那次验证是否算决定性，没有写）

- **问题**：
  - G46(aw)（`14` L133）：`claimed` 的验证中 exec 标准全部命中缓存，测试清单发现 R-T5 阻断 → `paused(sentinel_high)`，“重放包的 `manifest.json` 列出被复用的 `criterion_check`，**写保留 ref**”。
  - 但决定性验证只定义为“导致 `in_review` / `accepted` 的验证，以及验收与 seal 时的完整重哈希验证”（`07` L493，`06` L1112，`16` L465）。其他验证“不写保留 ref”。以 `sentinel_high` 结束的验证属于后者。
  - 反方向的缺口：人 `override_sentinel` 之后，继续目标为 `review{state:"in_review", pin}`，不重新验证（`06` §6.4.3）。于是使 Goal 进入 `in_review` 的，正是这次以阻断结束的验证。它在覆盖时是否升为决定性、何时写保留 ref，没有写。
- **为什么是次要**：seal 时的完整重哈希验证总会保留，证据链不会断；但用例与规则相反，会让实现者按错误的期望修改正确的实现。
- **文档位置**：`06` L1112、§6.4.3 `sentinel.override`；`07` L493；`14` L133（G46(aw)）；`16` L465。
- **期望的回答形态**：
  - (aw) 改为“不写保留 ref（非决定性）”；
  - 或者在 `07` L493 写明：经覆盖进入 `in_review` 的验证在覆盖决定的同一事务中升为决定性并写保留 ref，(aw) 相应改为“覆盖后写保留 ref”。

- **是否所有维度为 100：否。**

  - D4 99；D6 99；D7 99；D8 99；D11 99；D13 98；D14 99。
- **是否还有可追问的问题：有。** 新增共 **8** 条：阻断 0、重要 0、**次要 8**。
  - **第 55 轮核验**：20 条中已解决 18、部分 2（R55-D8-01、R55-D11-02），未解决 0。第 54 轮四条“部分”全部关闭；第 55 轮 §5 的 8 条观察全部落地。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 183，(v) 96 条命令，(e) 158 对，(r′) 40 对，(p) 10 格，(P) 8 格，(i) 31 个名称，(D) 92 个短语，(g) 19 行，(o) 8 行）。
    - Pi v1.2.0 复核约 30 条，没有行为断言被否定，漂移都在 ±5 行以内。
    - 排期结论成立：WBS 122.45；余量 0.12 / 0.42 / 0.53 / 0.95 / 0.32；依赖链 19.7；增人 128.32、T 23.69、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **缓存命中时新写事实的字段**：§7.4.8（L890）写命中时“新写一条 Fact，`cache.hit=true`”，但 `verify()` 中没有对应的 `recordFact`，也没有写 `data.trigger` 与 `atCommit` 取原值还是本次值。若沿用机会式的 `trigger`，`progress()` 的 ADR-053 守卫（L136）可能把它排除出 V，而 `outcomeOf` 已判为“已验证”，卡片与状态不一致。建议写明取本次的触发与 pin。
    2. **只跑清单的路径**：`todo` 为空的正式验证仍执行 `slot.prepare` 与 `slot.startServices`（`07` L435–437），而 L961 写“只运行它与依赖物化”。服务的健康检查失败会让一次标准结果全部可复用的验证得到 `verify_env_error`。建议写明 `todo` 为空时不启动服务。另外，L436、L438 的 `envError` 返回不经 `done()`，不等哨兵。结局是 `verify_env_error`，不越过闸门，但与“任何提前返回”的措辞不一致。静态哨兵在槽位之外的执行位置与成本可在 `13` §13.11.1 补一行。
    3. **D59 的延迟分支**：`_isEmittingAgentSettled` 期间调用 `prompt()`，会被推入延迟队列，直接 resolve，不调用 `preflightResult`（`agent-session.ts:2054-2057`）。延迟执行时的预检失败只在 `_emitAgentSettled` 的循环中抛出（:1088–1093），到不了原调用者。`05` L144–146 的适配器写法在这一分支下既没有回调、也没有 rejection。ADR-183 让扩展的 `agent_settled` handler 最多等 5 s，窗口因此变宽。Tower 只在引擎空闲（公开的 `agent.settled` 之后）调用 `prompt`，所以不构成条目。建议 D59 登记 :2054–2057，并写明“公开 `agent.settled` 之前不调用 `prompt`/`triggerTurn`”或给适配器设超时。
    4. **影子写者的措辞**：
       - `05` L1042“只读 JSONL 就能重建这张映射”，与 L1044 的“超过 5 s 时条目可能晚于 `agent.settled` 追加（Host 已退出时不再追加）”不完全相符，建议加限定；
       - L1044 与 `10` L759 的“请求已在 Supervisor 的队列中”只对在途的那一个请求成立，`cpQueue` 中其后的请求仍在 Host 侧（后续快照包含更新的树，影响有限）；
       - 5 s 的等待只出现在 `05`、`10` 与 §16.1.13，没有登记在 §16.2 的默认值表中。
    5. **take_human 与第 7 步的去重**：take_human 第 6 步先做的 `safety` 检查点（`10` L912）与第 7 步的 `agent_bg_done` 检查点同树。`agent_bg_done` 不是去重例外（§10.7.1），它的 landmark 与 `bg_process_survived` 注记会被去重掉。内容仍归 Agent（safety 检查点的作者为 agent）。建议写明顺序，或让第 7 步在去重时把注记附到 safety 检查点上。
    6. **人的 note 的去重**：`06` L853 在 ③ 崩溃后按 `details.key` 对 JSONL 去重，但人的 note 以 user 角色发送（`05` L1416），没有 `details.key`。Pi 写入之后、`run.started` 之前崩溃时，note 可能重复。窗口极小，建议在 G46(az) 旁注明。
    7. **措辞残留**：
       - `06` L912 与 `08` L516 仍写“只能作答、拒绝或稍后”（`S` 已改称“延后”）；
       - `03` L200 的 `docs` 类写“`artifact` + 链接检查 `exec`”，与 §7.4.9 的内置 artifact 检查不符，也没有 M2 标记；
       - `16` L969 的“项目级授权（`autonomy.grant`）仅本机”没有 M3 标记；
       - `16` L292 的 `satellite.recovered{checkpointN}` 可注明 M1 中只取最新的检查点。
    8. **`■` 的绝对化措辞**：`12` L335 新增“`■` 只出现在本行列出的用途中”。以下用法都可以归入“异常与阻断”，但没有逐项登记：`04` L519–520 与 `12` L722 的验收阻止项、`04` L1348 与 L1508 的 `■ 未送达`、`04` L578 与 L614 的未写出路径、`12` L456 的沙箱被覆盖徽章。建议在该行补登，或把措辞改为“只用于异常与阻断类”。
    9. **兜底计数不是保留条件**：注入失败后的无注入重跑改用正则兜底，界面标“计数为估计”（`07` L786）。但 `anyQualified` ①–⑩ 没有这一项，Goal 可以显示无保留的“已验证”，同时标准行写着计数为估计。触发判据与正则读取的都是被测代码能写的输出；退出码与 R-T5 照常把关，影响有限。可考虑列为第 ⑪ 项。
    10. **单向门的“目标名”**：`11` L104 只以 `prod` 为例，没有逐类写明输入哪个名字（环境名、分支名、迁移名）。输入目标名的方式同时是按住确认的无障碍替代，建议在 `16` §16.3 补一张表。
    11. **小处**：
        - `05` L238 由 `compaction_end` 推出 `retry.end{success}`，不适用于 `summarization_retry_*{source:"branchSummary"}`（导航带摘要时没有 `compaction_end`）；
        - `05` L934 以叶子变化判定 `/tower-nav` 完成（M2），导航到当前叶子时会误判为失败；
        - `repeat > 1` 时，ADR-054 的“pin 上两次超时”判别在首次超时即停（`07` L808），可写明；
        - M2 的 `secretPhaseOnly` 草图（`07` L1056）直接 `return decide(…)`，应改用 `done()`。
- **设计是否完成：主干已收敛。** 本轮没有重要条目。剩下的都是 ADR-183 新规则的边角分支（推迟后的出口、数据载体、命令契约的封闭列表）与一处单方引用声明，都可以用一个字段、一条守卫或一处引用关闭，不需要改变架构。
- **下一轮建议**（按优先级）：
  1. **R56-D8-01、R56-D6-01**：新暂停原因的主出口；开场队列只消费组装过的条目。
  2. **R56-D13-01、R56-D13-02、R56-D11-01**：归为人的路径的载体；“最新可用的检查点”与接管期间的出口；授权推迟的残留与撤销范围。
  3. **R56-D7-01、R56-D4-01、R56-D14-01**：验收闸引用 `anyQualified`；删空计划；G46(aw) 的保留 ref 期望。

  **工时与排期**：都是补守卫、字段或规则：W3、W6、W7-rest、W10、W12b、W14、SP6b 各约 0.01–0.02。系统线余量只有 0.12，应按 ADR-136 先改派。预计 M1 仍可维持 38 周（2027-07-30），以修订后的 ADR-133 补记为准。
