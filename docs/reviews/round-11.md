## 1. 总评

第 10 轮的两项重要问题收口方向正确：ADR-109 把权威检查改为只依赖两个 tree 的确定性函数 `pinSafetyCheck`，放在 `verify()` 第一步、验收与 seal 时复核，不排除只阻断，覆盖语义写入 trailer；ADR-110 以“不在 diff 中就不阻断”为据把 `sandbox_violation` 降为提示性。

但 ADR-109 第 5 点以与 `10` 自身规则相反的理由（“Agent 改动的都会命中”），把 Agent 改过 git 元数据的 base 夹具写进两种检出——这正是人用自己的 IDE 与 shell 打开的目录，构成本轮唯一的重要问题。标记规则自称“git 判定的超集”也不成立。另有 14 条次要问题，集中在规则完备性、检查点树口径、`external_change` 的出口与跨文档残留。

### D3 论证与证据

**R11-D3-01｜次要**

- **问题**：ADR-109 的两处论证与证据或与文档自身的规则不符：
  - **(a)** `10` L77 称标记规则“是 git 判定的超集，不需要在用户环境中重演 git 的判定”。必要条件“存在非目录 `HEAD`”确实被规则覆盖，但规则只在**标记文件本身被新增或改变**时触发。本轮核对表明，标记文件保持不变时，新增 `objects/` 或删除 `commondir` 都能让一个目录由“不是仓库”变为“是仓库”（R11-D11-02）。“超集”只对静态判定成立，对“由变化触发”不成立。
  - **(b)** ADR-109 第 5 点（L761）以“需要防住的只是 Agent 新造或改动的，而这些正是 `pinSafetyCheck` 的命中”为理由，让两种检出照常写出 base 夹具。但 `10` L82 明确规定，Agent 改动 base 夹具中的 `config`、`hooks/**`、`objects/info/alternates` 等**不命中**，只在集成前单列确认项。理由与规则相反（后果见 R11-D11-01）。
- **为什么重要**：这两句是本轮安全论证的支点；工程师与后续评审会据此认为“tree 检查已完全覆盖 git 的识别”与“检出中不会有 Agent 改过的 git 元数据”。
- **文档位置**：`10` §10.1.2 L77、L82；`15` ADR-109 L758、L761；`07` §7.3.2 L213–214。
- **期望的回答形态**：两处改为带前提的陈述，或随 R11-D11-01/02 的修订使其成为真命题。

### D6 系统架构与可靠性

**R11-D6-01｜次要**

- **问题**：`10` §10.3.1 的归因表有两处缺口：
  - **(a) 比较基线**：第 3 行用“当前工作区 vs 最近的检查点/pin”判定内容是否变化。但第 2 行归因为 Agent 的写入不一定已经进入检查点，例如回合结束的检查点之后，后台进程又写了文件，然后退出。之后任何一个事件触发第 3 行的比较时，这些 Agent 写入都会被当作“内容确有变化”，判为 `external_change` 并暂停 Run；人若选择保留，它们又被记为 `author:"external"`。表中没有“Agent 归因的写入推进基线”的规则（例如 Agent 进程树清空时补一个检查点）。
  - **(b) 后台进程的生命周期**：没有写 Agent 的进程组在 settle、`claimed`、`verifying`、`paused`、`in_review` 时是否终止。
    - 若不终止：`in_review` 中仍在运行的 watcher 写入未忽略的文件时，按第 2 行归因为 Agent、“内容进入下一个检查点”，但 `in_review` 中没有 Run，也没有检查点；按 `07` L1410，这应当“不会发生”。在 `claimed`/`verifying` 中，这类写入会使 `submit` 作废（`03` I4）。
    - 若终止：G35 的预期（watcher 在回合结束后持续写入、Run 不暂停）需要写明它只适用于 `running`，并写明终止的时机。
    - `03` 把 `paused` 定义为“引擎空闲”。
- **为什么重要**：两者都会产生无谓的暂停与 Needs-You，或让不在 Run 中的 Agent 进程改动已验证的工作区；这正是第 10 轮要求的“可实现的判定”。
- **文档位置**：`10` §10.3.1 L215–223；`07` L1410；`03` §3.3 I4；`14` G35、G36。
- **期望的回答形态**：
  - 写明 Agent 进程树在各状态的处置（例如 settle 时终止并在 Trace 中记录；或保留到 `claimed` 前，并说明之后的写入如何归因）；
  - 第 3 行的基线改为“最近检查点 + 已归因为 Agent 的写入”，或在 Agent 进程树清空时补做检查点；
  - G35/G36 增加“后台进程在检查点后写入然后退出，随后无关事件不应触发 `external_change`”与“`in_review` 中残留的 Agent 进程写入”两例。

### D7 诚实与验证

**R11-D7-01｜次要**

### D8 注意力与交互

**R11-D8-01｜次要**

### D11 安全与自主度

**R11-D11-01｜重要**（ADR-109 第 5 点引入的回退）

- **问题**：两种检出（人工编辑检出、检验检出）只不写出 `pinSafetyCheck` 命中的路径（`10` L86、L573、L625；`07` L214、L429）。而 `10` L82 规定，Agent 改动 base 中仓库形态夹具的 `config`、`hooks/**`、`info/**`、`objects/info/alternates`、`packed-refs`、`refs/**` 时**不命中**。`14` G29 的预期甚至写明：Agent 改了夹具的 `config` 之后，“两种检出照常写出该夹具”。
  - **边界**：两种检出正是人用自己的 IDE、外部终端与 shell 提示符打开的目录。`10` §10.8.4 L614 说明人工编辑检出存在的理由：“人的 IDE、shell 提示符对 Agent 写过的 git 元数据运行 git，正是 R5-D11-01 的攻击面”。
  - **前提**：项目在 base 中跟踪仓库形态夹具（git 工具类项目），Agent 改写了其中的可执行配置或重定向文件；人进入或在 IDE 中打开该目录。
  - **后果**：用户自己的 git 默认接受裸仓库发现（Tower 只在自己启动的终端中注入 `safe.bareRepository=explicit`；`10` L678 承认 IDE 自带的 git 不受控），会读取 Agent 可控的配置，可能在沙箱外以用户身份执行命令。这发生在接管或检验时，早于任何集成前确认。
  - 信任提示只列“未写出”的目录（`10` L632），不列这些写出了、但被改动的 git 元数据。
  - 第 9 轮的规定是“任何确认为仓库的目录都不复制”（`11` T29 L549 仍这样写），ADR-109 放宽时连“被改动的”也一起放行了。`11` T31 接受“IDE 执行检出中 Agent 可控的代码”为中残余，但它的缓解与提示只针对编辑器配置与依赖；这一类不需要任何 IDE 扩展，一次普通的 git 调用就会触发，也不受 IDE 受限模式影响。
- **为什么重要**：这是沙箱外执行 Agent 可控配置的路径，它绕过了人工编辑检出被设计出来要防的那一类攻击面，而且 ADR 给出的理由与 `10` 的规则相反（R11-D3-01b）。
- **文档位置**：`15` ADR-109 L761；`10` §10.1.2 L82、L86，§10.8.3 L573，§10.8.4 L614、L625–632、L678；`07` L214、L429；`11` T29 L549、T31 L551；`14` G29 L80；`00` §0.5.1 ADR-109 行。
- **期望的回答形态**：
  - 两种检出的“不写出”集合扩大为：`pinSafetyCheck` 命中 ∪ “base 中的仓库形态目录、且确认项文件集合中任一文件相对 base 有变化”的目录（含子树）。或者写出这些文件的 base 版本并在提示中列出差异。二选一并说明理由。
  - 信任提示列出这些目录；改正 ADR-109 第 5 点的理由；`11` T29/T31、`00` §0.5.1 同步。
  - G29 改写预期，并增加对照：Agent 改了 base 夹具的 `config` → 两种检出不写出该目录（或写出 base 版本），信任提示中列出。

**R11-D11-02｜次要**（R10-D11-01(a) 的残留）

- **问题**：`pinSafetyCheck` 规则 (a) 只在名为 `HEAD`/`commondir`/`gitdir` 的文件被新增，或内容/模式改变时命中（`07` L200–203）。本轮核对表明，标记文件不变时，目录也可以变成仓库形态：
  1. 已有有效 `HEAD` 与 `refs/`、但没有 `objects/` 的目录，只新增 `objects/` 即被判为仓库；
  2. `commondir` 指向不存在位置的目录，只删除 `commondir`（删除不属于“新增或改变”）即被判为仓库。

  因此，base 中一个“含 `HEAD`、但不是仓库形态”的目录，可以在标记文件不变的情况下变成仓库形态并进入 seal，不产生哨兵。它也不落在 `10` L82 的“base 夹具”行内，因为那一行要求该目录在 base 中已经是仓库形态。第 10 轮期望的“目录中标记条目或 `objects/`、`refs/` 下的内容相对 base 有变化即检查”没有采纳。

  另：名字比较只做 `toLowerCase()`（`07` L201），而 `10` §10.4.3 允许不支持写时复制的卷。HFS+ 上的文件名比较还会忽略某些 Unicode 码点；git 的 `core.protectHFS` 对 `.git` 处理了这一点，规则对 `HEAD` 没有对应处理。`10` L77 “不依赖卷的大小写语义”因此只对 APFS 成立。
- **为什么重要**：前提需要特定的 base 内容，所以定为次要；但后果与 T29 相同——Agent 可控的仓库形态内容进入用户主检出，而用户的 git 不受 Tower 注入保护。
- **文档位置**：`07` §7.3.2 L196–208；`10` §10.1.2 L76–82、§10.4.3；`15` ADR-109 L758；`14` G27c、G29b、G34。
- **期望的回答形态**：
  - 规则改为目录级：pin 树中凡含非目录 `HEAD`（按目标卷的文件名等价规则）的目录，只要其子树相对 base 有任何新增、改变或删除，且不属于“base 中已是仓库形态、变化只在确认项集合之外”的情形，即命中。
  - 名字比较采用与 git `is_hfs_dotgit` 同类的等价规则；或在 §10.4.3 只接受 APFS 与区分大小写的卷，并登记。
  - G27c 增加上述两例与一个 HFS+ 等价名用例（或登记不支持）。

**R11-D11-03｜次要**

- **问题**：规则 (b) 对每条新增或改动的符号链接单独判断“规范化后是否越出仓库根”，`escapesRepoRoot` 没有定义。若规范化是词法的（逐段折叠 `..`），它与操作系统的解析不一致：
  - 路径在中途经过另一条符号链接（包括 base 中未改动的链接）后再出现 `..` 时，物理解析的位置由那条链接的目标决定，而词法折叠按链接本身所在的位置计算。
  - 因此，一组单独看都在根内的链接，组合后的物理解析可以落到仓库之外（包括 Agent 临时目录），不产生 `symlink_escape`。
- **为什么重要**：`symlink_escape` 是 severity 3 的唯一防线；第 10 轮把 Agent 临时目录纳入它的范围，正是为了防住“集成后链接指向 Agent 可控位置”。
- **文档位置**：`07` L204；`10` L78；`15` ADR-109 L758；`16` L152；`14` G34。
- **期望的回答形态**：
  - 定义 `escapesRepoRoot` 为在 pin 树内的物理解析：遇到树中的符号链接，按其目标继续解析，限制深度，越界或成环即命中。
  - 或者采用保守规则：目标含 `..`、且解析路径经过任何符号链接分量，即命中。
  - G34 增加组合用例（含经过 base 中未改动链接的情形）。

**R11-D11-04｜次要**

- **问题**：覆盖按 `(detector, subject)` 在新 pin 上延续，内容哈希不变即静默合并（`07` §7.10.2 L1320、L1314）；`nested_repo` 的 subject 是 `HEAD` 文件的路径。
  - 设想人以 `intended_change` 覆盖了一个新建的仓库形态目录。Agent 之后在同一目录中新增或改写 `config`、`hooks/`、`objects/info/alternates`：
    - `HEAD` 未变，覆盖延续；
    - 这些文件不是标记文件，不命中；
    - 该目录不是 base 夹具，不进入 `10` L82 的确认项。
  - 人批准的是“一个夹具”，最终进入 seal 的却是含 Agent 后来写入的可执行配置的仓库；seal 上只有 `Tower-Override: nested_repo`。
- **为什么重要**：覆盖是“显式的人的决定”（ADR-109 第 3 点），但它的作用范围比人看到的内容更大。
- **文档位置**：`07` §7.10.1 L1314、§7.10.2 L1320、§7.11.4 L1457；`10` L80–82；`15` ADR-109 L759。
- **期望的回答形态**：`nested_repo` 的 subject 改为仓库形态目录，覆盖绑定该目录中 git 元数据文件集合的内容哈希，任一变化即重新呈现；或者对覆盖过的目录，集成前评审同样单列确认项文件的变化。G27c 增加用例。

**R11-D11-05｜次要**

- **问题**：ADR-110 把全部 `sandbox_violation` 统一为 severity 1 的 chip（`07` L1301）。“不阻止 Verified”的论证成立，但 ADR-110 同时取消了按目标区分的注意力信号：
  - 被拒绝的读取密钥路径表、`~/.ssh`、用户主检出、其他 Goal 的卫星、`$VS`、`~/.tower` 等尝试，是提示注入或越权意图的直接证据。它们与“写全局缓存被拒”这类良性拒绝一样，只是一个 chip，只有在评审时才可能被看到。
  - ADR-110 与 `11` L348 依赖“计入 `policy_wall`”，但 S7 是 M2（`07` L1126、L1150），M1 中没有任何升级路径。
  - E7 只做事后统计。
- **为什么重要**：越权尝试是运行中最早的安全信号；`08` 的告警纪律是按价值分级，而不是一律降级。
- **文档位置**：`15` ADR-110 L766–767；`07` L1126、L1150、L1301；`11` §11.6.2 L348、§11.3.1（密钥路径表）；`14` G32b、E7。
- **期望的回答形态**：
  - 按目标类别分级：受保护目标（密钥路径、用户主检出、其他 Goal、Tower 存储与验证器存储）→ severity 2 的 Needs-You 安全提示（不阻止 Verified）；其余 → chip。按 (类别, 根) 在 Goal 内聚合。
  - 或者论证为什么 chip 已经足够，并在 `11` 登记残余。
  - 修正 ADR-110 中“计入 `policy_wall`”在 M1 不成立的问题；G32b 增加对照：一次被拒的密钥读取。

### D13 隔离、git 与并发

**R11-D13-01｜次要**

- **问题**：检查点树的口径在 `07` 与 `10` 之间冲突，且依赖历史：
  - `07` L220、L257：检查点与 pin 同用 `worktreeTree(g, "decisive")`，只排除名为 `.git` 的条目与 gitlink，并完整收录大文件（L269）。

- **期望的回答形态**：
  - §10.7.1 第 1 步改为引用 `worktreeTree`（只排除 `.git` 与 gitlink，不排除大文件），删除 X；
