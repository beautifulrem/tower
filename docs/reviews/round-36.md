## 1. 总评

ADR-161 用“推迟到 M2”一次性消解了 `secrets.access` 的三条问题（R35-D4-01、D5-01、D11-02），取舍干净：M1 的 Agent 工具调用不再获得任何密钥库机密，Pi 依赖面也随之缩回。`baseTip` 措辞、凭据卡片与密钥库称呼都已统一，排期算术全部成立（WBS 121.32、38 周）。

### D6 系统架构与可靠性

**R36-D6-01｜重要**（带机密的标准在 `verify()` 中的槽位生命周期、加锁与冻结时点没有定义）

- **问题**：
  1. **与单槽位模型冲突**：
     - `07` §7.4.1 的 `verify()`（L405-423）对一次验证**只取一次槽位**，依次执行检出、`slot.prepare`（生命周期脚本与 `VerifyProfile.prepare`）、`startServices`，再按 `orderByExpectedCost(todo)` 顺序运行全部标准，最后拆除；
     - ADR-161 却要求两件事（`11` L427-428，`07` L700，`06` L233）：带机密的标准排在同一验证的最后；等待期间不占槽位，并在每个槽位空出时重新判定；
     - 两者怎样衔接没有写：
       - 不带机密的标准跑完后，是拆除槽位、释放、进入等待，还是在条件已满足时直接在同一槽位继续？
       - 释放后再次开始时，是否要重新检出、物化、执行生命周期脚本并启动服务？
  2. **加锁时点**：
     - 冻结的起点写作“标准开始后”（`11` L430，`13` L302）；
     - 如果重新准备发生在“判定条件满足”与“标准开始”之间，这段时间不冻结。准备阶段默认上限 600 s（`07` L591 的 `prepareTimeoutSec`），期间其他 Goal 照常被准入；
     - 到标准开始时条件可能已经不成立，这时只剩两种做法，规则都没有覆盖：
       - **持槽等待**：违反“等待不占槽位”。两个 Goal 各持一个槽位互等时，c = 2 的验证器全部停住；
       - **再次释放**：反复准备，系统繁忙时形成活锁。
  3. **前序失败**：
     - 同一验证中不带机密的标准已失败（或触发 `failFastOnExpensive`，L419）时，没有写带机密的标准是否仍要等待、独占验证器并冻结全局准入；
     - 这一次验证的结局已经确定是返工，为它冻结全系统的代价最大、收益最小。
  4. **人工出口取槽位**：
     - `run_now` 写作“立即运行”，`as_file` 写作“无需等待”（`06` L854-855，`04` L1106）；
     - 但两者都需要一个空槽位。c 个槽位都忙时，它们是排到下一个空槽位（优先级如何），还是抢占？没有写。
  5. **性能上限**：若冻结必须从取槽位起算，`13` L302 的“冻结时长 ≤ 该标准的超时”应改为“≤ 准备上限 + 服务健康检查上限 + 标准超时”。
- **为什么重要**：
  - 这是 ADR-161 新规则与既有验证流程的接缝，属于 rubric 所说的“未定义的次序”；
  - 照 `07` 伪代码实现会持槽等待，与“不占槽位”冲突并可能死锁；照“不占槽位”实现又没有加锁点，会出现准备期间被准入抢先、反复准备的活锁；
  - W9 无法照文档实现，G46(n)(o)(p) 也测不到这些情形。
- **文档位置**：`07` L405-423、L591、L700、L954；`11` L425-436；`06` L233、L292、L854-855；`13` L302；`04` L1096、L1106；`14` G46(n)–(p)。
- **期望的回答形态**：
  - 在 `11` §11.7.0 写明加锁顺序（作为唯一定义），例如：
    - 条件满足时，Supervisor **先冻结**（准入与验证器），**再**取槽位，然后依次检出、准备、启动服务、运行标准、终止进程、拆除，最后解冻；
    - 冻结期间不再重新判定。
  - 同一 Goal 的验证分两段：
    - 不带机密的标准在一次槽位占用中跑完；
    - 此时若条件已满足，可以不拆除，直接冻结后继续（作为优化）；否则拆除、释放，带机密的标准以“待运行”排队，重新开始时完整准备一次。
  - 写明前序失败的处理，二者取一：
    - 跳过带机密的标准，记为“未运行：前序标准失败”，直接 `decide()`；
    - 或者照常运行，并说明理由。
  - 写明 `run_now`/`as_file` 取下一个空槽位、排在队首、不抢占。
  - 改写 `07` §7.4.1 伪代码；`13` L302 的冻结上限改为“准备 + 服务 + 标准”的上限之和。
  - G46 增加三组：
    - 带机密的标准释放槽位等待后重新准备，准备期间另一个 Goal 请求开始 Run，期望该 Run 排队；
    - 前序标准失败；
    - 两个槽位都忙时选择“以文件方式运行”。

### D11 安全与自主度

**R36-D11-01｜重要**（“Agent 活动”按组件枚举，漏掉了执行受 Agent 影响代码的安装器，以及其他槽位中“运行标准”以外的阶段）

- **问题**：
  1. **安装器第 3 阶段**：
     - 安装阶段会执行项目的 `.pnpmfile.cjs` 与依赖的构建脚本（`07` L556-574，`pnpm rebuild --pending`/`npm rebuild`）。Agent 能改动这两类输入：它可以编辑 pnpmfile、改 lockfile、新增依赖；
     - 安装器的运行时机：
       - Goal 的 lockfile 变化时在后台预热（`07` L676，`13` L304）。这类运行可以在该 Goal 的 Run settle 之后继续；
       - 验证槽位准备时 depcache 未命中；
       - 人工编辑检出与检验检出的后台依赖准备（`07` L478）。人工编辑检出不计入活动；
     - 这三种情形都不在“Agent 活动”中（`11` L419-424），冻结范围（`11` L430）也不包括新的安装器运行；
     - 安装阶段断网，但它的产物经 depcache 物化进其他 Goal 的验证槽位与卫星的 `node_modules`（`10` L498）。这构成一条跨 Goal 的出口，越过密钥库条目“允许的 Goal/标准”的绑定。危害类别与 R35-D11-01 相同。
  2. **槽位中“运行标准”以外的阶段**：
     - 定义写作“任何验证槽位**正在运行其他标准**”（`11` L423，`06` L233，`16` L502，T33b L618）；
     - 而另一个槽位的检出之后、拆除之前，还在运行以下 Agent 写的代码：生命周期脚本、`VerifyProfile.prepare`、服务、与标准并行的测试清单（`07` L409-414）；
     - `04` L1092 的“没有其他验证在运行”与 G46(n) 的“槽位空出后才开始”暗示单位是“槽位占用”，但唯一定义没有这样写。照唯一定义实现，这些阶段不算活动。
  3. **残余评级**：T33b 在互斥开启时评为“低”，残余只列“用户自己的其他进程、ADR-158 的脱离进程”（`11` L618，`07` L710），没有包括上面两类。
- **为什么重要**：
  - 这是 R35-D11-01 同一条不变式（“机密在环境中期间没有其他 Agent 控制的代码在运行”，`11` L418）上剩下的出口；
  - lockfile 变化后的预热是常态，不是罕见情形；
  - 用组件枚举来定义活动，以后每增加一类后台执行都可能再漏一次。
- **文档位置**：`11` L418-430、L618；`07` L409-414、L478、L556-574、L676、L710；`10` L465、L498；`06` L233、L292；`13` L304；`16` L502；`14` G46。
- **期望的回答形态**：
  - 先给出原则：“Agent 活动”= 任何执行**可能受 Agent 影响的代码**的进程，再给出完整枚举。枚举中改写或增加两项：
    - “任何验证槽位处于占用中（取得到释放，含准备、服务与测试清单）”；
    - “任何安装器第 3 阶段正在运行”（输入全部来自 base、未经 Agent 改动的除外，也可以不区分）。
  - 冻结范围加入新的安装器运行：预热在冻结期间排队；人工检出的依赖准备同样排队，并在实况行中说明。
  - 按最终规则改写 T33b 的残余清单。
  - G46 增加两组：
    - Goal B 的 lockfile 变化触发的预热正在运行时，Goal A 的带机密标准排队，期望等待；
    - 带机密的标准运行期间，Goal B 触发预热，期望预热排队到解冻之后。

**R36-D11-02｜次要**（M1 中“Agent 从不获得密钥库机密”在读取一侧缺少机制；Agent 需要机密时没有出口）

- **问题**：
  1. **读取一侧**：
     - 静态存放处是系统钥匙串（`11` L398、L450）。动作类 `secrets.access` 在 M1 仍会把读取钥匙串的命令分类为 ask（`11` L50、L197，ADR-161 补记）；
     - `11` L50 断言“批准也不会让 Agent 获得密钥库中的机密”，`14` G46(i) 也写“在任何情况下”，但只检查环境；
     - 实际结果取决于两点，文档都没有写：
       - 沙箱能否挡住钥匙串服务：SP6a A8（`14` L58）只是测量；
       - Tower 写入的钥匙串条目是否只允许 Tower 自己读取：访问控制或访问组没有写。
     - 人一旦批准一条指向 Tower 条目的读取命令，这个断言就可能不成立。
  2. **Agent 需要机密时的出口**：
     - ADR-161 去掉了 M1 中唯一被认可的路径；
     - Agent 简报没有告诉 Agent“M1 中拿不到密钥库机密，需要机密的检查由带机密的标准在验证时运行”（`05` 简报段没有这一条）；
     - Agent 于是可能以 `ask_user` 索要密钥，人在回答框中粘贴的值会作为 user 消息直接进入模型上下文与会话文件。人的回答不经过精确匹配脱敏，回答框也没有提示。这与 §11.7 的原则“密钥永不进入模型上下文”相悖。
- **为什么重要**：
  - 第 1 项是 M1 安全不变式的表述与机制脱节，实现者可能用默认访问控制写入钥匙串条目；
  - 第 2 项是 ADR-161 直接引出的常见用户行为。
  - 两者都有人工批准兜底，危害有限，因此为次要。
- **文档位置**：`11` L50、L197、L375、L398、L437、L450、L452；`14` L58（A8）、G46(i)；`05` 简报与开场段；`04` 问答卡片。
- **期望的回答形态**：
  - 第 1 项，二者取一：
    - 写明 Tower 的钥匙串条目只允许 Tower 自己的签名身份读取（或放在 Tower 专用的访问组中），A8 增加“沙箱内读取 Tower 条目”的测量，G46(i) 的 M1 组增加“批准一次读取 Tower 条目的命令，期望读不到”；
    - 或者分类器对指向 Tower 条目的读取一律 `forbid`。
    - 否则把断言改为如实的残余。
  - 第 2 项：
    - 简报的 `tower_goal` 段写明 M1 规则；
    - 回答框对精确匹配集与模式命中给出提示（“这看起来是一个机密，它会进入模型上下文；建议改为带机密的验收标准”），不阻止发送；
    - 增加对应用例。
