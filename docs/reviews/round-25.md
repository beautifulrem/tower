     - `10` §10.1.2 是 Tower 执行 git 的唯一加固清单（L46），其中包括：
       - 镜像上下文带 `-c credential.helper=`、`-c protocol.allow=never`、`-c core.sshCommand=false`、`GIT_TERMINAL_PROMPT=0`（L58、L62）；
       - 最小全局配置“不含任何其他 filter、diff、merge、credential、include 配置”（L75）；
       - Seatbelt 的 `process-exec` 只允许 git、git-core 目录与 git-lfs（L69）。
     - 步骤 2a 要求“以用户的 credential helper 从项目远端获取”（L213）。但下面几件事都没有写：
       - 这条命令在哪个上下文执行（镜像上下文、用户仓库上下文，还是新上下文）；
       - 放开清单中的哪几项；
       - 用户的凭据助手是否允许执行（常见的助手程序并不在 git-core 目录中）；
       - SSH 远端的 LFS 认证是否允许执行 ssh。
     - 照清单原样执行，这条命令无法取得凭据。要让它工作，实现者只能自己决定放开什么，而这正是 R24 要求先裁定的安全边界。
  2. **“沙箱外”与“GitRunner 档位内”两种说法并存。**
     - `10` L213、`11` L372、`06` L239、ADR-150（`15` L1209）都写“GitRunner 在**沙箱外**获取”。
     - `10` L68–72 写的是：GitRunner 的每个 git 进程都运行在“只允许执行 git”的档位中，这条命令只是该档位的**网络例外**。`06` L239 同一段落中两种说法都有。
     - 这两种读法给出不同的进程边界。
  3. **端点来源没有写。**
     - 镜像只以路径从用户检出 fetch（`10` L51、L200），自身没有远端配置。
     - LFS 端点从哪里取（用户检出的 `remote.*.url`、`lfs.url`，或工作树中的 `.lfsconfig`）决定了凭据请求发往哪台主机。这也是需要写明的边界：凭据请求的目标主机应只由可信配置决定。
  4. **网络范围与 LFS 协议不符。**
     - `11` L372 写“网络只对这一条获取命令开放，且只到项目远端”，`10` L71 写“开放到项目远端的网络”。
     - 但 LFS 批量接口返回的下载地址可以在任意主机。本轮核对，GitHub 返回的下载地址主机是 `github-cloud.githubusercontent.com`。
     - 按“只到项目远端”的主机白名单实现，GitHub 上凡是需要远端获取的 LFS 对象都会失败，Goal 进入 `prepare_failed`，“重试”必然再次失败。
     - 失败卡片只写“LFS 对象缺失：<数量>”（`04` L949），没有区分认证、网络与对象不存在，也没有告诉人一条可行的出路：先在自己的检出中取得对象，再重试，这样 CoW 路径会用上它们。
     - 企业代理：`11` L336 的 PAC 解析只用于 S2 网络。这条命令走用户代理还是沙箱代理，没有写。
- **为什么重要**：
  - 这是上轮唯一一条重要项中的安全边界部分，回应只写了原则（“凭据不进入卫星或 Agent 环境”），没有写出可实现的规则。
  - 照字面实现，有两种结局：
    - 在最常见的托管平台上，需要远端获取的 LFS 项目无法开始 Goal，而且重试无效；
    - 或者实现者自行放宽沙箱档位、全局配置与网络。这会放进的一类后果是：用户凭据被交给未经审定的进程或配置，或者凭据请求被发往由仓库内容决定的主机。
  - G42(p) 期望“网络只对该命令开放”，测的正是这条不可实现的策略。
- **文档位置**：
  - `10` L46、L51、L58、L62、L68–72、L75、L199–200、L211–217、L948；
  - `11` L336、L372；
  - `06` L239；
  - `15` ADR-150 L1209；
  - `04` L944、L949；
  - `12` L411；
  - `14` G42(p)（L128）、G13（L74）。
- **期望的回答形态**：
  - 在 §10.1.2 的上下文表中为这条命令单列一行“LFS 获取”，写明：
    - `GIT_DIR` 或 `-C` 的目标；
    - 读哪些配置：建议只读用户全局与用户仓库配置中的 credential 与 LFS 端点项，不读工作树中的 `.lfsconfig`，或写明为什么可以读；
    - 相对清单放开的项目，逐项列出；
    - 进程档位：允许执行用户配置的凭据助手与 ssh，或者明确这条命令不在 GitRunner 档位内运行，并统一“沙箱外”的说法。
  - 网络规则改为与协议一致的写法，例如：“该进程可访问 LFS 端点，以及批量接口返回的传输地址（仅 HTTPS），经用户的代理设置”。或者给出别的、可实现且有边界的规则，并说明残余风险。
  - 失败原因分为认证失败、网络不可达、远端没有该对象三类。卡片加一条说明“在你的检出中运行 LFS 获取后重试”（重试会经 CoW 路径复用这些对象）。
  - 用例：G42(p) 增加三组：下载地址在另一台主机（GitHub 形态）、SSH 远端、凭据助手不在 git-core 目录中。另加“认证失败”组，期望得到可区分的原因。

### D4 领域模型与生命周期

**R25-D4-01｜次要**（仓库准备中暂停后，Goal 可能没有卫星或影子，而 `take_over` 与“卫星丢失”规则没有为此设守卫；步骤 2a 在代码块中的位置造成半建卫星）

- **问题**：
  1. **新允许的暂停会产生没有工作目录的 `paused(human)`。**
     - ADR-150 补记允许在仓库准备（①）中 `pause`（`10` L230，`06` L846，`16` L23）。仓库准备主要发生在首次启动，此时卫星（步骤 2）与影子（步骤 3）都还不存在。
     - 暂停后 Goal 是 `paused(human)`。`goal.take_over` 允许的源状态是“任意 `paused(*)`”（`06` L855，`10` L699）。只有 `ready` 与 `paused(prepare_failed)` 有“仅当卫星已存在（且可用）”的守卫。
     - 照字面，人在卡片上按“我来改”时，Tower 要“先对卫星当前内容做检查点，再由影子树物化”，可是两者都不存在。
     - 另一种读法是由“操作前检查”触发 `10` L984 的情形 E（卫星丢失），从“影子中最新的检查点或 pin”后台重建，而影子本身不存在，于是重建失败，升级为 `satellite_missing`，生成琥珀色 Needs-You，选项是“从更早的检查点重建 / 放弃”。对一个从未有过工作目录的 Goal，这既不真实，也没有可行的选项。
  2. **步骤 2a 的位置与“① 在 ② 之前”不一致。**
     - `10` L230 与 `06` L314 写“仓库准备（含 LFS）在卫星检出之前”。
     - 但 `10` 的代码块把 2a 放在步骤 2 的 `clone --shared`、删除 `.git`、写模板配置**之后**、checkout 之前（L204–216）。
     - 于是在 2a 中暂停或失败时，会留下“卫星目录存在、没有检出、没有影子”的半建状态。`prepare_failed` 的“我来改（仅当卫星已存在且可用）”（`03` L93，`10` L230）在这种状态下是否“可用”，没有定义。
- **为什么重要**：
  - 在 15 分钟的 LFS 获取中先暂停、再想自己动手，是一条普通路径。
  - 照字面，它要么在命令层出错，要么产生一条虚假的卫星丢失告警。后者违背“Needs-You 只放真实、可行动的事”。
  - 修订量是一个守卫，加上代码块中一行的位置。
- **文档位置**：`10` L204–217、L230、L699、L984；`06` L314、L846、L855；`03` L78、L93；`16` L23；`04` L944、L949；`14` G42(b)(v)。
- **期望的回答形态**：
  - 把 `take_over` 的守卫统一为一条：卫星与影子都已完成（`WorktreeRecord.state ∉ {creating}`、影子存在），否则 `E_STATE`，界面不显示“我来改”。这条守卫对 `ready`、`paused(prepare_failed)` 与准备中暂停后的 `paused(human)` 一律适用。
  - 情形 E 只对“卫星曾经建成”的 Goal 生效。
  - 把代码块中的 2a 移到步骤 1 之后、步骤 2 之前，与 L230 一致。或者写明半建卫星在暂停、失败与重试时怎样处理，以及“可用”的判据。
  - 用例：G42(v) 之后按“我来改”，期望返回 `E_STATE`（界面不提供），且不产生 `satellite_missing`。

**R25-D4-02｜次要**（`queuedRun` 在不经 Run 的出口留下残值，R24-D4-01 第 4 项未回应；`07` 的自动返工显式写类别，与“自动路径不覆盖保留值”冲突）

- **问题**：
  1. **残值仍会被采用。**
     - `queuedRun` 只在 `run.started` 与 `abandon` 时清除（`16` L24，`06` L469）。
     - 经不开 Run 的出口离开 `ready`/`paused` 的 Goal，会把保留值带进 `verifying`、`in_review` 等状态。这类出口包括：`hand_back{reverify}`（`06` L856：“`reverify` → `verifying`，不开 Run”），以及继续目标 `verify`/`review`/`claim`。
     - 例如：首次启动在 Host 握手处失败，Goal 进入 `paused(prepare_failed)`，`queuedRun{initial}`；卫星可用，人接管后交还选“直接重新验证”；之后在评审路径上因硬上限暂停（`07` L1450 写继续目标 `run`，不写 `queuedRun`），提高上限后 `resume`。
     - 按 ADR-150 的优先规则，陈旧的 `initial` 优先，于是这次返工受积压闸控，排在所有其他首次启动之后，`Run.reason` 记为 `initial`。
     - R24 要求二选一（在这些出口清除并加 CHECK，或说明残值不会被采用），回应与 ADR-150 都没有涉及。
  2. **`07` 与 `16` 冲突。**
     - `07` L1455–1458 的 `decide()` 在自动返工进入 `ready` 时显式写 `queuedRun: { kind: "rework" }`，即覆盖。
     - `16` L25 只列出三个覆盖保留值的人的决定，写明“自动路径不覆盖”，写入表也“只在 `queuedRun` 为空时适用”（L27）。
     - 自动返工遇到残值时，两份文本给出不同的类别。这种冲突只在残值存在时出现，因此修掉第 1 项即可同时消除它。
- **为什么重要**：
  - 唯一受闸控的类别 `initial` 会被陈旧值误用。
  - 一段伪代码与一张“唯一”表在同一情形下给出不同结果，属性测试无法判定哪一个对。
  - 路径虽窄，但修订只需一列的清除规则加一条 CHECK。
- **文档位置**：`16` L24、L25、L27；`06` L292、L469、L486、L856；`07` L1450–1458；`15` ADR-150 L1214；`14` G42。
- **期望的回答形态**：
  - 在所有不经 Run 离开 `ready`/`paused` 的转移中清除 `queued_run`（包括 `onAllReasonsCleared()` 执行的 `verify`、`review`、`claim`、`settle`，以及立即执行的 `reverify` 交还），并加 `CHECK (queued_run IS NULL OR state IN ('ready','paused'))`。
  - 在 `16` L25 把“自动返工”列为覆盖项（与 `07` 一致），或者改 `07` 的伪代码。二者取一。
  - 用例：“`paused(prepare_failed)`（卫星可用）→ 我来改 → 交还选‘直接重新验证’”，期望进入 `verifying` 时 `queuedRun` 为空。这一组同时补上 R24-D15-01 要求的“自 `prepare_failed` 交还”用例；另一组选“交给 Agent 继续”，期望 `Run.reason = handback`。

### D6 系统架构与可靠性

**R25-D6-01｜次要**（LFS smudge 进卫星仍计入 120 s；部分 smudge 的卫星在重试时是否“校验通过”没有定义。R24-D6-01 第 4 项残留）

- **问题**：
  - 步骤 2 末尾“由 Tower 从镜像的 LFS 存储 smudge 受跟踪文件”（`10` L217），属于 ② 卫星检出，计入 120 s（`10` L230，`16` L463）。
  - 它的耗时与 LFS 内容的字节数成正比。镜像位于 `~/.tower/projects/…`，卫星位于 `<checkoutParent>/.tower-wt.noindex/…`（`10` L23、L130）。用户检出在外置卷上时（大 LFS 仓库常见），每个 Goal 的 smudge 都是一次跨卷整份复制。数 GB 到数十 GB 的内容再加上大仓库检出的 10–60 s（`10` L943），可能超过 120 s。
  - ADR-150 的“已存在且校验通过的卫星直接复用”没有说明部分 smudge 的卫星算不算“校验通过”，也没有说明重试是逐文件续做还是整体重来。若整体重来，这类项目的首个 Goal 会反复 `prepare_failed`。这正是 R24-D6-01 要防止的后果。
  - 顺带（不单独扣分）：远端 fetch 仍没有子超时，挂起时耗尽 15 分钟，`10` L199 的“回退到本地已知值”不会触发。
- **为什么重要**：LFS 的主要用户恰好是大二进制仓库。在 120 s 内做与字节数成正比的工作，又没有续做规则，与 ADR-150 自己的设计意图（与仓库规模成正比的步骤不计入 120 s）不一致。
- **文档位置**：`10` L23、L130、L217、L230、L943；`16` L463–464；`06` L292；`13` §13.11.1；`14` G42(q)(r)。
- **期望的回答形态**：
  - 把卫星的 LFS smudge 移入仓库准备的计时（或给它单独的、带进度的时限），子状态显示为 `LFS · <已写/总量>`。
  - 写明它逐文件幂等、重试只补写未完成的文件，以及“校验通过”的判据。
  - 可选：远端 fetch 给出子超时，到时按 L199 回退并记 Fact。
  - 用例：G42(q) 增加一组“跨卷、LFS 内容数 GB”，期望首个 Goal 能开始 Run，或者重试时从未完成的文件继续。

### D11 安全与自主度

**R25-D11-01｜次要**（安装器日志尾部的脱敏精确集不含 `$TI` 中的注册表令牌；G42(u) 的期望没有规则保证。R24-D11-01 残留）

- **问题**：
  - `11` L401 规定安装器日志尾部注入开场之前“经同一脱敏器（精确匹配与模式）处理”。
  - 精确匹配集的定义（`11` L400 ①）是：密钥库中的值、被删除的环境变量值、本地文件扫描命中的值、验证器为标准注入的值。安装器拉取阶段持有的注册表令牌来自 `~/.npmrc`，写在 `$TI/npmrc`（`07` L521，`16` L985），不属于其中任何一类。
  - 模式表（L400 ②）也没有 npm 等注册表令牌的形态。L401 只写“精确匹配与模式”，没有提熵规则。
  - 于是 G42(u) 的期望“令牌的值已被替换为脱敏标记”依赖一条不存在的规则。
- **为什么重要**：这一类风险是注册表凭据经日志进入模型上下文。Tower 自己生成了 `$TI/npmrc`，完全知道这些值，修订只需在精确集的定义中加一项。
- **文档位置**：`11` L400、L401；`07` L521、L542；`16` L985；`14` G42(u)。
- **期望的回答形态**：
  - 在 `11` L400 ① 中加入“Tower 为安装器生成的含令牌配置中的每个令牌值（含 base64 与 URL 编码形式）”。这一项同样覆盖验证输出与返工证据。
  - L401 写明使用完整的三层（精确、模式、熵）。
  - G42(u) 的期望引用这条规则。

### D15 文档一致性与可执行性

**R25-D15-01｜次要**（`prepare_failed` 的定义在几处摘要中仍是 ADR-149 的版本；`prepare.progress` 的取值在登记表与正文之间不同）

- **问题**：
  1. **`prepare_failed` 的入口没有仓库准备。**
     - `03` L93 的 `prepare_failed` 入口写“……或**除依赖物化外的步骤超过 120 s**”。它与“仓库准备不计入 120 s”（`10` L230）直接矛盾，也没有列出仓库准备失败、超时与 LFS 缺失。
     - `02` L148（“卫星、Host 握手、开场组装”）、`16` L29（`pauseReason` 行：“卫星创建、Host 握手或开场组装失败，或这些步骤超过 120 s”）、`16` L189（`stalled` 子类型）同样没有仓库准备。
     - 同一份 `16` 的 L23、L463–464 却是全的。`08` L397 写“卫星创建或复用、Host 握手、开场组装共计时限 120 s”，没有提仓库准备与其中允许的 `pause`。
  2. **`prepare.progress` 的取值与 producer 两处不同。**
     - `step` 的取值，`06` L401、`10` L230、ADR-150 补记（`15` L1218）是 `mirror | lock | fetch | lfs | deps`；`16` L280 是“仓库准备、LFS 补齐、卫星检出、依赖物化、Host 握手、开场组装”。
     - producer，`06` 写 `git` / 安装器，`16` 写 `git` / `engine`。
     - UI 的子状态文字按 `step` 取值渲染（`04` L944），两边按不同的表实现就会对不上。
- **为什么重要**：
  - `03` §3.2.1 与 `16` §16.1.1 是暂停原因的规则来源，实现者照它们实现，会把仓库准备算进 120 s，或者漏掉仓库准备的失败出口。
  - 事件取值是生产者与 UI 之间的契约。
  - 修订都是文字同步。
- **文档位置**：`03` L93；`02` L148；`16` L29、L189、L280；`08` L397；`06` L401；`10` L230；`15` L1218。
- **期望的回答形态**：
  - 上述各处的入口统一为“仓库准备失败或超时（含 LFS 缺失）、卫星检出失败、Host 握手失败、开场组装失败，或卫星检出与握手、开场合计超过 120 s”，或者改为只引用 `10` §10.3.1。
  - `16` L280 的 `step` 取值与 producer 与 `06` L401 对齐（是否包括卫星检出与握手两步，二选一后两处一致）。
  - 可加一条 lint：`prepare.progress.step` 的取值作为枚举纳入 (s′) 检查。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D5、D7、D8、D9、D12、D16 为 100，这九个维度上没有可追问的实质问题。
