### D6 系统架构与可靠性

**R12-D6-01｜次要**（R11-D6-01 修订引入）

- **问题**：`10` L222 规定 settle（进入 `claimed`、`paused`、`in_review`）时“对该进程组发 SIGTERM，5 s 后 SIGKILL”，并据此断言“`claimed`/`verifying`/`in_review` 中不会有 Agent 进程写卫星”。这里有四个缺口：
  1. **与 pin 的先后顺序**：`03` L56–57 规定，`claimed` 经 2 s 宽限确认后“自动立即”进入 `verifying` 并生成 pin。终止窗口最长 5 s，进程在这期间仍可写入；许多 watcher 与测试运行器收到 SIGTERM 时还会刷写输出或缓存。按归因表第 2 行，这些写入算作 Agent 的，但 `claimed`/`verifying` 中已经没有“下一个检查点”。pin 可能取在写入之前；写入之后，按 `03` I4 会使提交作废，或者在 `in_review` 中被 I2 判为 `fp_changed_human`。G35c 预期“`submit` 不因此作废”，但正文没有定义能保证这一点的顺序。
  2. **终止对象**：被终止的是“该进程组”，而第 2 行追踪的范围包括“`setsid` 脱离进程组、按父链追踪”的后代。这些后代不在进程组内，不会被组信号终止。
  3. **PID 复用**：在 macOS 上，追踪方式是每 2 s 轮询一次 PID 列表，延迟 5 s 后按 PID 发 SIGKILL。若原进程已经退出、PID 被复用，信号会发给无关的用户进程。
  4. **崩溃后的追踪状态**：没有写追踪状态是否持久化。Supervisor 或 Engine Host 崩溃后，Agent 的子进程被 init 收养，Tower 重启后既不知道它们存在，也无法终止它们。它们之后的写入会被判为 `external_change`，或在 `in_review` 中被判为人的改动（R12-D7-01）；它们还占着本 Goal 的端口段。
- **为什么重要**：这是第 11 轮为消除误判而引入的机制；如果顺序不对，它会把同一类误判搬到验证闸口，并波及无关进程。
- **文档位置**：`10` §10.3.1 L219–222、L226；`03` §3.2 L56–57、§3.3 I4；`14` G35c；`06` §6.1（崩溃恢复）。
- **期望的回答形态**：
  - 写明顺序：进入 `claimed` 时先终止，并**等待进程树清空**（或 SIGKILL 完成）→ 补做 `agent_bg_done` 检查点 → 宽限确认 → pin；
  - 终止对象改为“已追踪的全部进程”（Linux 用 cgroup 整体终止）；
  - 在 macOS 上，发信号前用进程启动时间或审计令牌确认身份；
  - 追踪集合随事件日志持久化，崩溃恢复时据此清理，无法确认身份的只提示、不发信号；
  - G35c 增加“SIGTERM 时刷写输出”与“Supervisor 崩溃后重启”两例。

### D7 诚实与验证

**R12-D7-01｜次要**（R11-D7-01 的残留）

- **问题**：第 11 轮的裁决是“保留外部改动 = 人显式采纳 → `author:"human"` → `Tower-Human-Edit`”，前提是人看过并作出选择。但：
  - `10` L220 与 `06` L783 规定，`in_review`/`accepted` 中内容确有变化的外部写入一律按 I2 走 `fp_changed_human`，“归因 `author:"human"`，不经这两个命令”；
  - `07` L1373 的注释也承认 `!agentCaused` 包括“未知来源”；
  - `10` L226(b) 承认，脱离追踪的 Agent 后台进程会产生这类写入。
  
  结果是：同一种来源不明的写入，在 `running` 中需要人显式采纳，在评审阶段却**不经任何决定**就以人的名义写进 seal 的 `Tower-Human-Edit`。这正是 `10` L389 “事实与声明分离延伸到写进用户仓库的持久产物”要避免的情形。另外，spine 回应说 `02` L455 的 hunk `author:"external"` 用于“尚未处置的外部改动”；但按 `06` L783，评审阶段的这类改动已经被记为 `human`，`external` 在什么情况下出现没有定义。
- **为什么重要**：seal 是永久记录；把来源不明的内容署名为人，与把它署名为 Agent 一样不诚实。
- **文档位置**：`10` §10.3.1 L220、L226，§10.6 L389–410；`06` §6.4.3 L783；`07` §7.4.1 L330、L1373；`02` §2.8 L455；`12` L203。
- **期望的回答形态**：二选一。
  - 评审阶段的外部写入在重新验证的同时，在评审单元中标为 `external`，验收面板要求“采纳为我的改动 / 撤销到 pin”之一；采纳之后才产生 `author:"human"` 检查点；
  - 或者 seal 只对显式的人工决定（交还、就地编辑、`keep`）写 `Tower-Human-Edit`，对 I2 路径中未经处置的变化另写一个标注。
  
  G36b 增加 `in_review` 一例。

### D8 注意力与交互

**R12-D8-01｜次要**（ADR-113 引入）

- **问题**：受保护目标的沙箱拒绝会生成 severity 2 的 Needs-You（`kind:"sentinel"`，L2）。
  1. **没有出口**：`06` L816 的 `sentinel.override` 明确不适用于 `sandbox_violation`，`04` L512 与 `12` L695 也说“不要求逐条覆盖”。这条 Needs-You 由什么动作关闭（知悉 / 标为误报 / 收紧策略 / 放弃 Goal）没有定义。`08` L477 对 `sentinel` 条目的标注（`intended` 覆盖 → `informative`，误报 → `false_positive`）依赖覆盖，这类条目因此永远得不到标注，`08` L525 基于精度的降级规则也无法作用于它。
  2. **去重键冲突**：`08` L192 规定 `sentinel` 条目按 `s:{goal}:{detector}` 合并，ADR-113 与 `07` L1310 规定按“(类别, 目标根)”去重，实现时只能取其一。
  3. **证据前提**：ADR-113 与 `11` L348 称这类拒绝是“提示注入或越权意图的直接证据”。但 `04` L512 自己的示例 `写 ~/.ssh/known_hosts ×2` 是 ssh 首次连接时的常规行为；云 SDK 启动时读取凭据文件、git 走 ssh 远端时读取 `~/.ssh/config`，也会命中受保护集合。E7（`14` L405）只设了“良性占比 > 50% 的规则进入复审”，没有针对 severity 2 这一级给出误报率阈值与降级规则。
- **为什么重要**：Needs-You 的纪律是“每一条都有明确的决定与出口”；一条关不掉、标不了的 severity 2 条目会逐步损耗收件箱的可信度，而这正是 ADR-113 想保护的信号。
- **文档位置**：`15` ADR-113；`07` §7.10.1 L1310；`11` §11.6.2 L348；`06` L217、L816；`08` L192、L477、L525；`04` L512；`14` G32b、E7 L405。
- **期望的回答形态**：
  - 定义这条 Needs-You 的出口动作与标注映射（例如“知悉”→ `informative`，“这是良性的”→ `false_positive`，并可一键把该目标加入项目的良性清单）；
  - 统一去重键；
  - 把“直接证据”改为带前提的陈述；
  - E7 增加 severity 2 一级的误报率阈值与降级规则；
  - G32b 增加一例良性的受保护目标拒绝（`known_hosts`）。

**R12-D8-02｜次要**（R11-D8-01 的残留）

### D11 安全与自主度

**R12-D11-01｜次要**（ADR-112 的定义缺口）

- **问题**：`10` L78 与 ADR-112 只对“pin 中**新增或改变**的符号链接”做整链解析，而且没有定义解析时遇到 tree 中不存在的路径分量该怎么办。
  1. **未改动的链接因为路径分量改变而逃逸**：base 中一条未改动的相对链接，如果目标中含 `..` 并经过某个目录，而 Agent 把这个目录换成一条在根内的符号链接，那么这条未改动链接的物理解析就可能越出仓库根。新链接自身的解析仍在根内，未改动的链接又不在检查范围内，所以不会产生 `symlink_escape`。G34b(a) 只覆盖了相反的组合（新链接经过未改动的链接）。
  2. **tree 中不存在的分量**：两种检出与用户主检出中都有 tree 里没有的内容。
     - 被忽略的依赖目录由安装器按 Agent 可改的 lockfile 生成，其中可能有指向仓库外的链接（例如 `link:` 依赖）；
     - `.git` 被 `worktreeTree` 排除，但集成后它就是用户真实的 git 元数据目录。
     
     对于目标经过这类分量的链接，“在 pin tree 内解析”的结论没有定义：可能判为“不存在”从而不命中，而物理上指向仓库外，或指向用户的 `.git/`。
  3. **根目录作为候选目录**：`07` L210 伪代码中的 `e.path === d || e.path.startsWith(d + "/")` 在 `d` 为仓库根时永远不成立。正文“之内或就是该目录”的语义包括根，但伪代码会漏掉“根目录直接含 `HEAD` 类条目”的情形。按 `04` L539，检验检出的根目录没有 git 元数据，这种情形正好会被当作仓库根被发现。
- **为什么重要**：`symlink_escape` 与 `nested_repo` 都是 severity 3 的唯一防线；第 11 轮修订的目标就是“与操作系统解析一致”，这三处是剩余的不一致。
- **文档位置**：`10` §10.1.2 L77–78；`07` §7.3.2 L200–215；`15` ADR-112；`16` L152；`14` G34b；`04` L539。
- **期望的回答形态**：
  - 对 pin 中**全部**符号链接（或至少全部目标含 `..` 的链接）做整链解析，或者只要有链接或目录改变就重新解析受影响的链接；
  - 规定解析经过 tree 中不存在的分量时视为逃逸（保守），或者明确接受并登记于 `11` T31；目标经过名为 `.git`（按同一名字等价规则）的分量一律视为逃逸；
  - 伪代码把根目录写成显式情形；
  - G34b 增加 (d) 未改动链接因目录被换成链接而逃逸、(e) 经过依赖目录的链接、(f) 指向 `.git/hooks` 的链接、(g) 根目录含 `HEAD`。

**R12-D11-02｜次要**（ADR-111/112 的覆盖路径）

- **问题**：`10` L86 规定，被改动的 base 夹具“覆盖后按覆盖时的哈希写出”到两种检出。这时被写出的，正是第 11 轮重要问题中那一类内容：Agent 改过的 `config`、`hooks/`、`objects/info/alternates`。两种检出是人用 IDE、shell 提示符与外部终端打开的目录，`10` L89 与 `11` T31 都承认 IDE 自带的 git 不受 `safe.bareRepository` 注入保护。然而：
  - 覆盖对话框（`04` L463）只显示“路径 · tree 哈希”与“之后变化会重新阻断”，没有指出该目录中被改动的文件里含有会被 git 当作命令执行的配置项；
  - 信任提示（`04` L565）只列出“未写出”的目录，覆盖之后的目录不再出现在提示中；
  - `11` T29/T31 的残余也没有登记“覆盖之后写入检出”这一条。
- **为什么重要**：覆盖是显式的人工决定，但人看到的是一个哈希，而不是“这一步会让你的 git 执行 Agent 写的命令”。人最可能以“这是有意的夹具修改”为由覆盖，而这时风险最高。
- **文档位置**：`10` §10.1.2 L80、L86；`04` §4.6.2 L463、§4.6.7 L565；`11` T29 L549、T31 L551；`15` ADR-112。
- **期望的回答形态**：
  - 覆盖对话框以 Fact 形式列出该目录相对 base 改动的 git 元数据文件，并标出其中的可执行或重定向配置键；
  - 两种检出的信任提示列出“已覆盖、已写出的仓库形态目录”；
  - 或者规定即使覆盖之后，两种检出也写出这些文件的 base 版本，或者不写出；
  - `11` 登记对应的残余；
  - G27d 增加“覆盖之后打开检出”一例。
