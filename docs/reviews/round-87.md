## 1. 总评

**第 86 轮的 1 条重要、5 条次要条目都已按所问关闭**，其中一条只是部分关闭（核对见 §3）：R86-D6-01 的例外列表再次声称完整，实际仍不完整，由 R87-D6-01 承接。§5 的 15 条观察都已落地，其中观察 8、10 各留一处尾巴（观察 2、3）。

**ADR-214 的主体成立**（§3.3）：
- **重要条目的修法正确**：
  - Pi 让传输工厂决定 spawn 的工作目录，`roots` 由连接单独声明。所以 Tower 在自己的工厂中不取会话工作目录，就切断了 “包运行器按卫星中的配置与依赖选择程序” 这条路，而代码智能类服务器仍以卫星为根。
  - 评审者逐一排查了 `env`（`${NAME}`、`!cmd`）、`command`、`args` 与包运行器的向上查找，都不再触及卫星。
- **基准取空目录而不取主目录**，比回应初稿更严，理由成立。
- **其余五条**：
  - 查询不另设时限、失败即 “未知” 并不启动 Host，消除了 “清单 ≠ 实际加载” 的不一致；
  - 路径值的显示与 “重新读取”（仅本机，`06` L951、L992，`16` L1139）有了界面与命令；
  - `take_over` 的守卫在唯一定义处写明；
  - 例外列表补了 `sessions`、运行时表与 `question_timeout` 的问题；
  - 路径集合的外置成了通则，lint (i′) 随之扩大。
- 唯一定义处与引用处一致：`05` L433/L445/L459/L466/L1332，`00` L99–L100，`11` L212/L221/L607/L611/L680/L692，`06` L221/L788/L904/L951/L1060，`16` L45/L637/L664，`14` G10、G46 (bk)，C21、C40。

**ADR-214 带出或暴露的新问题**：
- **内置 MCP 被第三方 MCP 扩展取代时，Tower 的传输工厂不再生效**（R87-D11-01）：
  - Pi 的内置 MCP 是 “可取代” 的；用户已确认的第三方 MCP 扩展注册 `/mcp` 时，内置 MCP（连同 `towerMcpTransport`）不加载；
  - 那些服务器的工作目录与环境都由那个扩展决定，可能又回到卫星与完整的 Host 环境；
  - 而 T4、T16、`11` L611 与 C21 都无条件地说 “stdio 服务器的工作目录由 Tower 选定”“不含 Host 的云凭据”。
- **共享空目录的 “始终为空” 没有任何一环保证；相对路径的门禁规则没有随 ADR-214 更新**（R87-D11-02）：
  - Tower 现在知道每个 stdio 服务器的工作目录（是它自己求出的），但 `11` L221 (3) 仍按 “门禁不知道按工作目录还是 `roots` 解析” 只 ask；
  - 于是写入 `~/.tower/mcp-cwd/` 的硬底线只对绝对路径成立；
  - `00` §0.5.1 引导你写的绝对 `cwd` 常常就是你的主检出（硬底线 “读写” 一项），相对路径同样只 ask。
- **全局根查询的失败规则只对 Run 的准备成立**（R87-D5-01）：
  - 120 s 的唯一定义只计第 ③ 步 “Host 握手与开场组装”，清单计算不在任何准备步骤中；
  - 首次运行第 1 步的确认卡片不在任何 Run 中，查询挂起或出错时没有规则。
- **新守卫只落在 `06` 与 `16`**（R87-D4-01）：
  - 转移与出口的唯一来源 `03` §3.2.1 仍无条件列出 `take_over`；`nested_repo_live` 的出口列表仍说 “只有 `resume`、`take_over`、`abandon`”；
  - 而 “交还时不勾选删除” 正好是写下 `pending_hand_back` 的路径；`04` 也没有置灰状态。

**全范围扫描**在 ADR-214 之外新发现：
- **重建例外 “只有以下四处” 仍不完整**（R87-D6-01）：
  - (3) 说只有 `question_timeout` 的问题不随 Run 失效，与 `05` L638–L639 “问题条目都保持打开” 矛盾；
  - (4) 让 `projections` 重新生成，与 “已归档 Goal 只能从快照 + 保留事件重建” 矛盾；
  - `depcache_entries`（验证器存储的来源记录）、`project_checkouts`、`meta` 既不在例外中，也没有事件。

### D11 安全与自主度

**R87-D11-01｜次要**（第三方 MCP 扩展取代内置 MCP 时，Tower 的 stdio 工作目录与环境规则都不生效，而正文无条件地陈述它们）

- **问题**：
  - **Pi 的行为**：
    - 内置 MCP 登记为 `replaceable`（`extensions/index.ts:9-13`）。另一个扩展注册了同名的工具、命令或标志时，资源加载略去内置扩展，只留一条警告（`core/resource-loader.ts:115-149`）。
    - Pi 文档点名：注册 `/mcp` 的第三方 MCP 扩展取代内置 MCP，Pi 不再读 `mcp.json`、不再连接它的服务器，改由该扩展负责（`docs/mcp.md:264-266`）。这类扩展在 Pi 有内置 MCP 之前就已流行，从 CLI 迁来的用户很可能装着它。
  - **Tower 中的后果**：
    - Tower 的 `towerMcpTransport` 挂在内置 MCP 扩展上（`05` L344），内置扩展被略去时它也不存在；
    - 服务器改由那个扩展以自己的方式启动：工作目录可能是会话工作目录（卫星），环境可能是完整的 Host 环境（含云凭据）。
  - **正文的陈述无条件**：
    - T4（`11` L680）：“用户级 stdio MCP 服务器不以卫星为工作目录启动”；
    - T16（L692）与 `11` L611：“启动 stdio MCP 服务器的工作目录则由 Tower 选定，不是卫星”；
    - C21（`05` L1455）：stdio 服务器的环境 “不含 Host 的云凭据”。
  - **没有任何一环发现它**：
    - 静态清单的文本扫描只标出注册 `tool_call` 处理器、名为 `bash` 的工具与同名内置或 Tower 工具的扩展（`05` L1332）；
    - SDK 自检只比对 Tower 工具的来源（`05` L428）；
    - `11` L222 处理了 codemode 与 `tool_search` 被取代的情形，没有处理 `/mcp`；
    - C21 只测 `-builtin:mcp`，不测被取代。
  - 同一份清单对注册 `bash` 的扩展已有明示（ADR-066 “该扩展的 bash 将被 Tower 沙箱版本取代”），方向相反的这一种却没有。
- **为什么是次要而不是重要**：
  - 取代内置 MCP 的是你自己装、并在清单上确认过的扩展；它怎样启动服务器，属于 §11.8.2 残余中 “用户确认的那段代码的行为”。
  - 但正文的安全陈述在这一常见配置下不成立；你在确认卡片上看不到 “Tower 对 MCP 的保护不适用” 这一后果；实现者也会各自决定是否检测、是否告知。

  - 静态清单的文本扫描另标出 “可能注册 `/mcp`（或内置 MCP 的其他名字）” 的扩展，确认卡片写明 “该扩展取代 Pi 内置 MCP：Tower 对 MCP 服务器工作目录与环境的规则不适用，服务器按该扩展的方式启动”；`session_start` 时由 `extensionsResult` 的警告或来源判定内置 MCP 是否生效，未生效时写入能力摘要。T4、T16、`11` L611 的陈述限定为 “内置 MCP 生效时”；

**R87-D11-02｜次要**（Tower 选定的 stdio 工作目录已知，但门禁的相对路径规则仍按 “不知道基准” 只 ask：共享空目录的 “始终为空” 与主检出的硬底线都没有保证）

- **问题**：
  - **ADR-214 改变了相对路径的落点**：
    - 以 `.` 或其他相对路径为根的服务器，此前落在卫星（本来就由 Agent 写）。现在它们落在共享空目录 `~/.tower/mcp-cwd/`（`00` L99 明写）；

    - `11` L212 第 3 条：沙箱外工具 “读写用户主检出” 与 “写 `~/.tower/mcp-cwd/`” 都是 forbid、不可授权覆盖；

    - 每个 stdio 服务器的工作目录现在是 Tower 自己求出的（`05` L433），门禁可以知道它；

  - **空目录的不变式没有执行者**：

    - 没有任何一步在启动前检查它是否为空。C21 与 G46 (bk) 的 “始终为空” 只是夹具的性质（“夹具中的服务器不写文件”）。
  - **后果的类别**：
    - 一旦这个目录中出现项目配置或本地依赖，之后所有未写绝对 `cwd` 的 stdio 服务器的包运行器，都会在服务器代码运行之前按它们选择程序。这正是 R86-D11-01 要排除的那一类后果；
    - 而且这个目录跨 Goal、跨 Host 共享且从不清空，影响不限于批准时所在的 Goal。按工具名的 Goal 级授权（`11` §11.3.4）在这里会越过 Goal 的边界；
    - 在主检出一侧：相对路径的读写落在 ADR-082 “读写都在硬底线内” 的位置，门禁只 ask。
- **为什么是次要而不是重要**：
  - 两条路径都需要人批准一次沙箱外的写入调用，或事先授予按工具名的放行；
  - T7/T26 已把 “加载了能写文件系统的沙箱外工具” 评为中风险，并写明路径扫描是尽力而为（`11` L221 末句）。
  - 但 ADR-214 把这一 “尽力而为” 的缺口移到了两个它自己列入硬底线的位置；对空目录的 “始终为空” 也作出了无人执行的陈述。实现者对是否检查、是否清空、怎样处理相对路径会各取其一（`05` L433 还明写 “不清空”）。
- **文档位置**：`00` L99；`05` L433、L1455（C21）；`11` L212、L221、L683（T7）、L702（T26）；`14` L134（G46 (bk)）。
- **期望的回答形态**：在 `05` §5.3.5 “stdio 服务器的工作目录”（唯一定义）加至多一条守卫，并在 `11` L221 (3) 改一句：
  - **空目录**：`towerMcpTransport` 每次创建 stdio 传输前检查该目录为空（不为空时不启动该服务器，文字说明原因与恢复办法）；或改为每次 Host 启动时新建的空目录（在 `~/.tower/run/` 之下，Host 退出时删除），使写入不越过一次 Host 的生命周期。二者择一，写明理由。
  - **相对路径**：对由 Tower 求出工作目录的 stdio 服务器，门禁把相对路径分别按该工作目录与 `roots` 解析，任一结果落在硬底线内即按其方向 forbid；其余情形照旧 ask。或者明写不这样做，并在 T7/T26 中把 “绝对 `cwd` 指向主检出时，相对路径的读写落在硬底线内只 ask” 列为已知限制，在 `00` L99 的建议旁写明。
  - G46 (bk) 补一组只写期望：服务器在该目录中留下文件之后，下一次启动（新会话或新 Host）时服务器进程的工作目录为空，或该服务器不启动；以相对路径写入该目录的工具调用被 forbid（若取解析一支）。

### D5 Agent 架构与 Pi 集成

**R87-D5-01｜次要**（全局根查询 “由 120 s 的准备时限兜底”，但 120 s 只计第 ③ 步，清单计算不在任何准备步骤中；Run 之外的清单计算没有时限与失败规则）

- **问题**：
  - **步骤归属**：
    - `05` L1332、`11` L607、`13` L129 与 C40 都说 Supervisor 的查询 “与 Pi 一样不另设时限，由 120 s 的准备时限兜底”。

    - 清单计算是否在 ③ 中、计时从何时开始、其间 `goal.pause` 是否返回 `E_BUSY`（③ 中返回 `E_BUSY`，① ② 中允许并中止，`06` L881），都没有写。
    - `prepare_failed` 的入口列表（`03` L97、`06` L1184 F4b）也没有 “全局根查询出错或超时”。
  - **Run 之外的计算**：
    - 首次运行第 1 步 “扩展清单确认卡”（`04` L1454，不可跳过）不在任何 Run 中，没有准备时限；

- **文档位置**：`03` L97；`04` L1454；`05` L253、L466、L1332、L1475（C40）；`06` L320、L881、L1184；`10` L381；`11` L607；`13` L129；`16` L23、L703。
- **期望的回答形态**：在 `05` §5.10（唯一定义）写一句：
  - 清单计算（含全局根查询）属于准备第 ③ 步，计入 120 s，其间命令的行为同 ③；时限到达时终止查询子进程；`03` L97 与 `06` F4b 的入口列表补这一原因；

       - 宜写明按 `realpath` 比较，并考虑大小写不敏感的卷（macOS 的 `$TMPDIR` 经由符号链接）；

       - 简单的做法是 “任一 `<wtRoot>` 或 `~/.tower/` 之下一律不启动”（`mcp-cwd` 本身除外）。

       - L100 “所以与那时你在终端中运行的 `pi` 找到的相同” 未带 `05` L445 的限定（`XDG_DATA_HOME`、`pnpm_config_*` 不传入时可能不同），宜补半句；
       - L99 “以 `npx`/`node` 启动的 MCP 服务器与扩展在 Tower 中失败” 宜按 `05` L459 改为 “扩展的子进程”。
    8. **重新读取之后的过渡**：新值 “下一次 Host 启动生效”。打包模式下正在运行的 Host 仍用旧值，这期间 “整台机器同一个值”（`05` L445、L458）不成立。宜写明正在运行的 Host 不重启、新 Goal 不并入旧值的 Host（或接受混用）。
    9. **扩展注册的 MCP 服务器**：`pi.registerMcpServer` 注册的服务器经同一工厂，工作目录规则同样适用；但静态清单只列 `mcp.json` 的条目，“静态清单在该条目旁写同一句” 对它们无从落实。宜写明它们只在运行时显示 `failed` 与文字。
    10. **“没有 Node” 的提示**（`05` L466 定义于首次运行与重新读取）不在 `04` §4.18.1 第 1 步与 §4.15 中，宜各补一处引用。
    11. **`roots` 与服务器自己的行为**：服务器按 `roots` 在卫星中运行程序（例如语言服务器启动项目中的工具），仍属 T16 已登记的残余。`11` L221 把代码智能类服务器 “以 `roots` 为根” 作为建议，宜在同处引用 T16，避免读者以为 ADR-214 也覆盖了这一点。
    12. **写法**：
        - `10` L797 说追加的三个 landmark 值 “由 Supervisor” 写入，L800 说 “由 Projector”，宜统一；
        - `16` L637 新说法列把 `projections` 与 “原样沿用” 的运行时表并列，而 `06` L221 让它重新生成，宜分开写。
    13. **查询失败阻断不加载扩展的 Run**：清单确认之前与高风险 Goal 的 Run 都以 `noExtensions` 运行，却同样因全局根查询失败而不能开始。这是回应 “偏离” 中已接受的取舍，`00` L100 的说法覆盖了它；宜在 `05` §5.10 写明是有意为之（清单只有一份，确认卡片也依赖它）。
    14. **`resolvePinHits` 的路径数组**：`human.decision{hand_back}` 与 `human_checkout.params` 中的 `{path, action}[]` 是路径集合，不在 `06` L788 通则与 lint (i′) 的命名范围内。通常很小，宜在通则中写明 “不适用” 的理由，或纳入。
    15. **从隐私清除之前的备份恢复**：`db-backups/` 中清除之前的副本含有已被清除的事件，而它们引用的路径集合文件已随 `goals/<G>/` 删除；按 `06` L788，重建会整体停止，而不只是跳过该 Goal。`09` §9.12.4 已把备份列为 “无法删除的副本”，宜在同处写明这时的恢复办法。
- **设计是否完成：ADR-214 正确地关闭了第 86 轮的重要条目。**
  - Tower 在自己的传输工厂中不再以卫星为 stdio 服务器的工作目录，而服务器仍以卫星为 `roots`。
  - 经源码核实，`env`、`command`、`args` 与包运行器的向上查找都不再触及卫星。
  - 本轮没有重要条目。5 条次要条目分三类：
    - **ADR-214 的前提在相邻配置下不成立**：R87-D11-01（内置 MCP 被取代时工厂不存在）、R87-D11-02（空目录与绝对 `cwd` 下的相对路径，门禁未随 “基准已知” 更新）；
