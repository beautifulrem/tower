## 2. 逐维度评审

### D1 上手与引导 · 79（+5）

**修好的**
- 欢迎页在 Pi 不可用时把“试一个演示目标”设为主按钮（`welcome-zh.png`）；缺 `node` 或 `python3` 时按钮禁用并写明缺什么（`environment.rs:116`、`lib.rs:382-386`）。
- 0 个模型时有“打开 Pi 登录”按钮：在 Terminal 里启动 `pi`，旁边提示“输入 /login，回来后点重新检查”（`src-tauri/src/lib.rs:203-211`，`settings-zh.png`）。
- 添加仓库后，在沙箱里对 base 的干净副本跑一次测试命令，结果写进项目视图。概览输入框下面会出现“测试在 main 上已经失败：第一条标准会成为红 → 绿的证据”（`project_check.rs`，`overview-zh.png`）。第 2 轮的第 22 条做到了。
- 最低 Pi 版本由后端给出（`min_pi_version`），不再写死在前端。

**剩下的问题（按影响排序）**
1. **还是装不上。** 仓库私有，0 个 release。签名流程和 cask 模板已经准备好（`RELEASING.md`、`packaging/homebrew/tower.rb`），但没有真正发布过一次。只要外部用户还得装 Rust、Node 22、pnpm、Xcode CLT 再从源码构建，D1 就过不了 85。
2. **`python3` 的检查只看 `which`。** 在没装 CLT 的新 Mac 上，`/usr/bin/python3` 是一个会弹出“安装开发者工具”的占位程序，`which` 能找到它，所以演示按钮仍然可点，结果是暂停或弹窗。第 2 轮指出的正是这个场景，没有修到点上。应改为：`xcode-select -p` 失败时视为缺失，或者用 2 秒超时实际执行一次 `python3 -c 0`。更彻底的做法是把 `demo_pi.py` 改写成 Node 脚本，只留 `node` 一个依赖。
3. **登录仍然要切到终端。** 用 osascript 控制 Terminal，首次会触发 macOS 的“Tower 想要控制 Terminal”授权弹窗；登录完成后也不会自动重新检查。Claude Code 桌面版和 Codex App 都是应用内一步完成 OAuth。
4. 预览中 Pi 版本是 `demo-engine` 这种非 semver 字符串时，会显示“太旧”（`welcome-zh.png`）。真实用户遇到非标准版本号（例如自己编译的 `1.5.0-dev`）也会被误判，应该把“无法解析”和“太旧”分开报告。

**要超过 95**
- 公开仓库，发布签名并公证的 universal DMG，cask 进 tap；第一次打开不需要右键。
- 演示引擎只依赖 Node，或者检查改为“能实际执行”。
- 登录：检测到 0 个模型时，在应用内提供“粘贴 API key（写入 Pi 的 auth，不进 Tower 数据库）”或者内嵌一个 PTY 运行 `pi /login`，完成后自动重新检查。
- 首次添加仓库时，把 base 测试检查的结论直接变成第一张合同的默认标准（“测试已经失败：这条可以当红灯标准”）。

### D2 核心流程完整度 · 85（+7）

**修好的**
- **CI 失败闭环**：PR 中新出现的失败检查生成一张“CI 失败”决策卡（新的 `InboxKind::CiFailed`），可以选“把失败发给 Agent”或“先不管”。发回时会收集失败检查的名字、链接，以及 GitHub Actions 失败步骤日志的尾部（截断并脱敏，`pr.rs:235`），然后以 `ci-fix` 运行继续，并告诉 Agent 不要削弱测试。再次验收时，在上一次封存的提交之上加一个提交，快进同一分支，推送即更新原 PR。第 2 轮第 8 条基本做到。
- **回退**：每次运行开始时的快照保存为 `refs/tower/runs/<n>`，目标页的运行行在有快照时显示“回到这里”，要确认（`GoalPage.tsx:570-589`）。**撤销 hunk** 在评审页 hunk 头上（`review1-zh.png` 右上“撤销这一块”）。两者都记为人的改动，必须重新验证才能验收（`edits.rs`）。
- 暂停页不再显示多余的“接下来”区块（`goal4-zh.png`）。
- 验收面板写出将要创建或更新的分支名，可复制。

**剩下的问题**
1. **重启仍会多开一次运行。** `recover()` 对以 `AppQuit` 暂停的目标调用 `run::resume`，后者用 `start_run(…, "resume", …)` 开一次新运行（`lib.rs:196-203`、`control.rs:104-123`）。夹具里的“第 84 次运行”（`overview-zh.png`）就是这么来的。这是第 2 轮第 14 条，没有动。用户会以为 Agent 返工了几十次，预算和停滞判断也会被干扰。
2. **回退在长目标上会失败。** `rollback` 只在最近 10,000 条事件里找 `RunStarted`（`edits.rs:44-50`），而 store 的性能预算正是按 2 万条事件设计的（`tower-store/tests/perf.rs`）。跑了很久的目标，回退到早期运行会报“没有快照”。应改为按 `run_no` 直接查询，或者把 `start_pin` 存进运行投影。
3. **回退之后找不回来。** 被回退掉的工作在 pin ref 和轨迹里，但界面上没有“恢复到回退之前”。第 2 轮要求“被回退的改动保存为一个可以恢复的 ref”，只做了一半。
4. **塑形仍未实现**（`docs/17` §17.5）。合同的命令、范围、预算仍然要自己写。
5. **PR 评审评论不回灌**，只看 CI 检查。Cursor 的 Bugbot Autofix、Conductor 都能处理评论。
6. 撤销 hunk 或回退之后，要从 `⋯` 菜单里找“重新验证”（`GoalPage.tsx:292`）。人刚改过工作区，下一步只有这一个，应该直接出现在“接下来”。

**要超过 95**
- 应用退出后恢复的运行记为同一次运行的续段（`R-03 续`），不增加 `run_no`，轨迹里写明“Tower 重启后继续”。
- 回退前把当前工作区快照存为 `refs/tower/undo/<n>`，toast 带“撤销回退”。
- 塑形：一句话 → Agent 只读扫描仓库 → 提议标准命令、范围、预算，逐条勾选。
- 读取 PR 的 review comments，作为“要求修改”的一个来源，与 CI 失败卡并列。
- 人改过工作区之后，“接下来”直接显示“重新验证（↩）”。

### D3 可信度与诚实 · 86（+7）

**加分**
- **P1 实测：第 2 轮的作弊现在会被扣下。** `expectations_changed` 用“去掉字面量后的行形状相同、字面量不同”判断断言期望被改（`sentinel.rs:318-334`），严重度 3，验证通过也会暂停，等人确认。
- **“恢复原测试再跑”**（`verify.rs:385-450`）：Agent 修改过已有测试时，在 pin 上把这些测试文件恢复成 base 版本，再跑一遍标准；只有改过的测试才能让它通过时，记一条哨兵命中。这是**执行级**的证据，不依赖文本规则，P2 中正是它抓到了作弊。主流产品都没有这一项。
- **验证器缓存隔离**：每次验证从用户缓存 CoW 克隆一份新缓存，用完删除（`verify.rs:474-478`）；Agent 的缓存永远不进验证。有 flow 测试 `verification_does_not_see_the_agents_cache`。第 2 轮 D3.2 已修。
- 新增哨兵：Rust 源文件中的 `#[ignore]`、测试文件改名到运行器看不到的位置、`pyproject` 和 `Cargo` 中的测试配置（`sentinel.rs:233-269、356-368`）。
- 待验收卡的正文只会是 Agent 的提交说明（作为“声称”标出）或空（`verify.rs:611-628`），Tower 不会再用自己的句子替 Agent 背书。
- P3 中，基线检查抓到了一个在 base 上空转、恒为 0 的 `make test`，把它标为“不能证明完成”。这是“诚实语法”在真实场景里第一次显出价值。

**问题（按影响排序）**
1. **最强的证据被当成最弱的信号。**（P2 实测）
   - `passes_only_with_edited_tests` 证明的是“不改测试，标准就失败”，它不是启发式，而是执行结果。可它的严重度是 2（`verify.rs:437-446`），**在目标已经进入待验收之后**才由后台算出，只弹一个 toast，不撤回待验收卡，不阻止验收。
   - 同一个目标，C1 的基线是“改动前失败”，于是目标页照常显示“红 → 绿”（`GoalPage.tsx:665-671`、`Trace.tsx:280`）。也就是说，界面上同时出现“这是区分性证据”和“它只靠改测试才通过”两条互相矛盾的说法，而前者更显眼。第 2 轮要求“红 → 绿只认新测试，且旧测试在 pin 上仍通过”，没有做。
   - 只要换一种写法绕开文本哨兵（P2 是改常量；还可以改 fixture 文件、改测试辅助函数，`sentinel.rs:321` 只对断言行做形状比较），作弊就能进入待验收，通知和角标语义都是“可以验收了”。
2. **Rust 的模块内测试仍是盲区。** `#[ignore]` 补上了，但期望值检查（`sentinel.rs:321`）和“恢复原测试”（`verify.rs:398-402`）都只看 `is_test_path`，`src/*.rs` 里 `#[cfg(test)] mod tests` 的断言被改，两道防线都看不到。Go 的 `testdata/`、常见的 `fixtures/`、`__fixtures__/`、`golden` 文件也不在 `is_test_path`（`sentinel.rs:29-44`）里，而 2026 年的作弊分类研究正把“改 fixture 和 golden 文件”列为测试神谕篡改的主要形态（[The Verification Horizon](https://arxiv.org/pdf/2606.26300)）。
3. **验收命令自己的“装置”没有冻结。** `test_command_changed` 只检查 `package.json` 的 `scripts.test*`（`sentinel.rs:343-354`）。标准是 `make test`、`just test`、`./scripts/test.sh`、`tox` 时，Agent 改 Makefile、justfile、脚本本身，没有严重度 3 的命中（`TEST_CONFIGS` 也不含它们）。第 2 轮建议的 `Makefile` 的 `test:` 目标没有做。
4. **观测的匹配仍然过宽。** `observe()` 还是“命令包含标准命令”。P1 里 Agent 跑的是 `npm test 2>&1 | tail -20`、`npm test > /dev/null 2>&1; echo …`，都会被记成观测；`docs/17` §17.6 承认管道会让失败记成通过。观测不计入“已验证”，危害有限，但账本的“一致”会被抬高。第 2 轮第 5 条未修。
5. 按输入特判（P6 的意图）这类作弊，文本哨兵和“恢复原测试”都抓不到，而且会显示为“红 → 绿”。这是所有工具的共同上限，但 Tower 可以做得更好：允许合同里放“保留测试”（只在验证器侧存在、Agent 看不到的测试文件），这是对付“针对可见测试过拟合”的标准做法。

**要超过 95**
1. `passes_only_with_edited_tests` 升为**严重度 3**，并把“恢复原测试”挪到**进入待验收之前**：只要 Agent 修改过已有测试文件，就和 pin 验证并行跑，两个结果都出来才决定去向。代价是同一份缓存克隆多用一次（见 D10.1 的修法）。
2. “红 → 绿”只在“恢复原测试后 pin 仍通过”时显示；否则显示“红 → 绿（依赖被改的测试）”，用警告色，并在账本里记为“不一致”。
3. `is_test_path` 加 `testdata/`、`fixtures/`、`__fixtures__/`、`golden/`、`*.golden`、`*.snap` 以外的快照格式；含有 `#[cfg(test)]` 的 `.rs` 文件，其 diff 中位于测试模块内的行按测试处理（期望值检查和“恢复原测试”都要覆盖：恢复时只还原该模块的区间）。
4. 标准命令引用到的文件（`Makefile`、`justfile`、`Taskfile.yml`、`tox.ini`、`noxfile.py`、命令里出现的脚本路径）一律视为“验收装置”，有改动就报严重度 3；更好的做法是验证时把这些文件恢复成 base 版本再跑一遍，与“恢复原测试”同一套机制。
5. 观测只在命令去掉首尾空白后**等于**标准命令（允许前置 `cd <workspace> &&`）时记录；带管道、重定向、`;`、`||` 时记为“观测（不完整）”，不参与账本一致判定。
6. 合同增加“保留测试”字段：路径只在验证器的检出里写入，Agent 的工作区和提示中都不出现。

### D10 性能与响应 · 76（−2）

  - 准备阶段（依赖清单和锁文件与 base 相同、或已获批准）可写；
