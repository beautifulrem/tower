### D13 隔离、git 与并发

**R79-D13-01｜重要**（按路径排除的规则没有进入检查点树与 pin 树的唯一定义；两段 “唯一定义” 直接冲突）

- **问题**：
  - `10` L184 定义：Tower 的**每一次**快照 `add` 都对清单中的全部路径加 `:(exclude)`，快照包括检查点、pin（因此 seal）以及验收与 seal 时的全新临时索引；指纹也不含这些路径。
  - 但检查点树与 pin 树另有自己的唯一定义，没有随之修改：
    - `10` §10.7.1 第 1 步（L735）：“**检查点树与 pin 树的唯一定义（`07` §7.3.2 引用本条）**：……**只排除**名为 `.git` 的条目……与 gitlink……**唯一的例外**是 git 在 `core.protectHFS/NTFS` 下会拒绝收录的路径”；L737 的命令为 `git add -A -- . ；T = git write-tree`，注释 “不再有排除列表 X”。
    - `10` §10.6（L597）：pin “树的定义以 §10.7.1 第 1 步为唯一来源：只去除名为 `.git` 的条目、gitlink 与 git 拒绝收录的 `excludedPaths`”。
    - `07` §7.3.2 的 `worktreeTree`：检查点、pin、`decisive` 指纹与 `full` 闸口共用这一个函数。它只排除 `[...excluded, ...refused]`（L243、L255）。L281 再次写 “只排除名为 `.git` 的条目与 gitlink……因此同一工作区内容总得到同一棵树，与影子索引的历史无关”。
  - `11` §11.8.1 每个 Run 启动时的两种复核（L584、L598）也是对卫星的快照，`10` L184 的枚举没有列出它们，正文没有说是否排除。G46 (bh)(6) 的预期 “`protected_path` 与上下文文件复核都不列出它” 隐含排除。
- **为什么是重要**：
  - 实现 GitService 与验证器的人，最直接的依据就是 §10.7.1、§10.6 与 `07` 的 `worktreeTree`。三处都给出了**穷尽的**排除列表，并自称唯一来源。
  - 照它们实现，ADR-206 要覆盖的那些情形会全部回到第 78 轮的状态：Goal 创建后才忽略、只靠仓库级 `core.excludesFile` 忽略、只在当前分支提交的 `.gitignore`。清单中的个人文件会进入检查点、pin 与 seal，并写进用户仓库的分支。
  - 这违反了写给用户的承诺：`04` L1313 “清单中的文件从不进入检查点、汇总提交或你交还的改动”，以及 `16` L704、`06` L890 的同一说法。
  - 危害本身与 R78-D13-01 同类，是有界的：机密本地文件不播种到卫星，交还时另按路径排除；进入 seal 的只能是评审差异中可见的非机密文件。但这一次的原因是正文的两条唯一定义互相矛盾，照其中一条实现就违反已陈述的不变式，所以列为重要。
- **文档位置**：`10` L184、L597、L735–L737；`07` L243、L255、L259、L277、L281；`11` L584、L598；`16` L704；`06` L890；`04` L1313；`14` L134 (bh)(6)。
- **期望的回答形态**：在唯一定义处各改一句。
  - `10` §10.7.1 第 1 步改为 “排除名为 `.git` 的条目、gitlink、git 拒绝收录的路径（记入 `excludedPaths`），以及 §10.1.2 按路径排除的本地文件（不记入 `excludedPaths`）”；L737 的命令与注释同步。
  - `10` L597 的枚举同步。
  - `07` `worktreeTree` 的 `add` 参数加入 `localFileExcludes(g)`（清单路径减去在该 Goal 的 base 中被跟踪的路径），L281 同步。
  - `11` §11.8.1 两种复核写明 “快照同样按 `10` §10.1.2 排除清单路径”，与 G46 (bh)(6) 一致；或者写明不排除，并改 G46 的预期。

**R79-D13-02｜次要**（清单在 Goal 进行中变化时，对该 Goal 的影子索引、检查点、指纹与归因的效果没有定义）

- **问题**：
  - **排除对已在索引中的条目无效**：
    - 检查点与 pin 用持久的影子索引（`10` L736；创建时 `read-tree <baseCommit>`，L371）。`add -A` 的 pathspec 排除不会触碰索引中已有的条目。
    - 正文对 gitlink 已经写了同样的处理：“影子索引中若已有 gitlink，先 `update-index --force-remove`”（`10` L185，`07` L238）。对本地文件路径没有对应的一步。
  - **加入清单**（`add`）时的后果：
    - Agent 先在卫星中写了某个文件；它在该 Goal 的影子上下文中没有被忽略，所以进入了检查点。之后人在用户检出中忽略它，并加入清单。
    - 此后 `decisive` 树（检查点、pin、I2）保留旧条目，Agent 之后对它的修改不再进入；`full` 闸口从 `read-tree <baseCommit>` 开始，没有这个条目。
    - 结果是验收时按 `07` L277 记 `stat_cache_mismatch`，按归因表把该路径判为来源不明，进入 `paused(external_change)`。卡片会写 “在没有 Agent 工具调用时被写入”，这不是事实。
    - 另一种实现会在加入时把它从索引中删除，此时 Agent 的这份工作从 Goal 的改动中消失。两种实现都说得通。
    - ADR-206 的 “已进入检查点再被 `mark_secret` 的问题随之不再出现，因为清单中的路径从不进入检查点”（`15` L3269）对加入清单之前就已进入的路径不成立。
  - **移出清单**（`remove`）时的后果：
    - `06` L891：“此后该路径不再按路径排除，是普通的未跟踪文件”。
    - 移出作用于该 Project 的**所有**活跃 Goal。在影子上下文中不被忽略的已播种副本，会在每个这样的 Goal 中作为新文件出现，而不只是人想提交的那一个。
    - 在 `running` 中，G46 (bh)(6) 第五组定义它进入下一个检查点。它的作者按检查点记为 `agent`，实际上是 Tower 播种的、人的文件。
    - 在 `in_review`/`accepted` 中，树发生变化但没有任何写入事件。归因表（`10` L387–L393）由写入事件驱动，I2 与 `external_change` 的分界（L405）也没有 “清单变化” 一项。按 I2 回到 `verifying` 还是进入 `paused(external_change)`，没有写。
- **为什么是次要**：
  - 加入清单的情形在 M1 中可以按提示走到：Agent 生成了运行配置，人在差异中看到后把它改为本地文件。移出清单则正是 ADR-206 推荐的提交方式。实现者必须自行决定索引清理、作者与归因，各家的结果会不同：丢弃 Agent 的工作、误报外部写入，或者重置评审。
  - 危害是有界的。不丢失用户检出中的原件；机密条目不播种；误报的 `external_change` 可以 `keep`/`revert`。
- **文档位置**：`10` L184、L185、L371、L387–L405、L736；`07` L238、L277、L281；`06` L890、L891；`16` L704；`15` L3268–L3269；`14` L134 (bh)(6) 第三、五组。
- **期望的回答形态**：在 `10` L184 加两句。
  - **索引**：每次影子 `add` 之前，对影子索引中位于清单路径、且不在该 Goal 的 base 中被跟踪的条目执行 `update-index --force-remove`，与 gitlink 相同。由此，加入清单即从此后的快照中去掉该路径，`decisive` 与 `full` 一致；`07` L281 的 “与影子索引的历史无关” 重新成立。另写明这会把 Agent 此前对它的修改移出 Goal 的改动，加入确认框如实提示。
  - **归因**：清单的 `add`/`remove` 引起的树变化归为 Tower 自己的工作，在 `in_review`/`accepted` 中按 I2 回到 `verifying`，不判 `external_change`；检查点作者与 landmark 取一个已有值，例如 `safety`。或者更窄的写法：`remove` 只在没有处于 `claimed`–`accepted` 的 Goal 时允许，否则 `E_STATE`。`remove` 的确认框列出受影响的活跃 Goal。

**R79-D13-03｜次要**（`mark_secret` 的 “已有副本” 删除没有尊重 base 中被跟踪的例外）

- **问题**：
  - `16` L704 的 “已有副本”（唯一定义，`06` L893 引用）写道：条目由非机密变为机密时，“从该 Project **所有活跃卫星**（非终态 Goal 的卫星）与人工编辑检出中删除这份副本；这是 Tower 自己的写入……不触发 `external_change`；该路径按 `10` §10.1.2 按路径排除，**不改变指纹与 diff**”。
  - ADR-206 引入了例外：路径在某个 Goal 的 base 中被跟踪时，Tower 不向那个卫星复制它，也不排除它（`10` L184）。G46 (bh)(6) 第四组正是这种情形，`config/dev.json` 被提交进 base 之后，新 Goal 中的 Agent 修改它。
  - 照现有文字，对这样的条目执行 `mark_secret`（例如人发现它含有令牌）时，会删除那个 Goal 卫星中的仓库文件：
    - 删除落在 Tower 的写回窗口内（`10` L389），不判外部写入；
    - 该路径对那个 Goal 不被排除，删除会进入下一个检查点与 pin，在 `in_review` 中经 I2 重置评审，并可能随 seal 删除仓库中的文件；
    - Agent 自上一个检查点以来对它的修改丢失；
    - “不改变指纹与 diff” 对那个 Goal 不成立。
- **为什么是次要**：
  - 要同时满足 “清单中的路径在某个 Goal 的 base 中被跟踪” 与 “人对它执行 `mark_secret`”，情形少见。删除在评审差异中可见，此前的内容仍在影子的检查点中。
  - 但实现者照字面实现会删除仓库文件，与例外的用意相反；“副本” 一词又可以读成只删 Tower 复制过的，两种读法的结果不同。
- **文档位置**：`16` L704（“已有副本”）；`06` L893；`10` L184、L389；`04` L1314；`14` L134 (bh)(6) 第四组。
- **期望的回答形态**：在 `16` L704 “已有副本” 一句加半句：“只删除 Tower 复制进去的副本；路径在某个 Goal 的 base 中被跟踪时，该 Goal 的卫星与人工编辑检出不动（那里是仓库文件）”。必要时在确认框中列出这些 Goal：“以下目标的代码中跟踪了该文件，未改动”。

### D8 注意力与交互

**R79-D8-01｜次要**（F7 条目只在路径 ① 上与 `provider_unavailable` 成对；② 的暂停原因与关闭、③ 的出口、探测对过期 OAuth 的语义都没有定义）

- **问题**：

  - **② 预检失败**：
    - `05` L149–L150：`session.prompt` 在回调之前被拒绝即预检失败，“按 06 F7 ② 处理”。F7（`06` L1183）只给 Needs-You，没有给状态。
