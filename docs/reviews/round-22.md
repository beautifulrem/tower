## 4. 追问清单（新增与残留）

编号 `R22-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。本轮没有阻断与重要项。

### D4 领域模型与生命周期

**R22-D4-01｜次要**（`queuedRun` 的写入点、清除点与 NULL 语义不完整；`kind` 与 `Run.reason` 对不上）

- **问题**：
  1. **首次启动的 Goal 没有 `queuedRun{initial}`。**
     - `02` L179、`06` L464、`16` L24 都写明：`queuedRun` 在“要开 Run 的转移因准入失败进入 `ready` 时写入”。
     - 合同批准（`contract.ratify`/`quick_ratify`，`06` L836–837）只发 `goal.state_changed(→ready)`，不属于这种转移，也不写该列。
     - 准入第 c 项（`06` L300）却是“只对 `queued_run.kind = initial`（首次启动）生效”，`16` L23 也写“只有 `initial` 受评审余量闸控”。
     - 照字面实现，首次启动的 Goal 的列为 NULL，积压闸门永远不生效，ADR-014 的阻止模式（E8 通过后默认开启）形同虚设。
     - `06` L294 的排序键仍写“`initial`（`ready → running`）”，这是 R21 要求改、本轮没有改的定义。
  2. **依赖回退也不写 `queuedRun`。**
     - `running → ready{dependency}`（`03` L55；`06` §6.1.6 drain 行的 `dependency` 目标）是 drain 后直接进入 `ready`，不是准入失败，同样不写该列。
     - 这类 Goal 已在工作中。如果实现者为了修复第 1 项而把 NULL 当作 `initial`，依赖恢复后，它在阻止模式下会被卡在 `ready{review_capacity}`。这正是 `03` L54“否则会卡住已在评审路径上的 Goal”要排除的情形。
     - 第 1、2 项合起来：无论 NULL 按哪种方式解释，总有一类 Goal 出错。
  3. **清除点过早，重建规则缺失。**
     - 该列在准入通过时清除（`06` L290），而 `pending_openings` 在 `run.started` 的同一事务中消费（`06` L824）。
     - 准备阶段可能持续数分钟（`02` L121）。若这期间应用退出或崩溃，重启后 Goal 是 `ready`，`queued_run` 已为 NULL，`pending_openings` 仍在，`run.requested` 也已发出，但没有 `run.started`。
     - `06` §6.1.6 的恢复表没有 `ready` 的行。R21 期望写明的“重启后据此重建队列”在正文中找不到。排序键第 3 项“入队时间”也没有持久化的来源。
  4. **`handback` 不是合法的 `Run.reason`。**
     - `queuedRun.kind` 的取值是 `initial | resume | rework | handback`，准入“通过时以它发出 `run.requested{kind}`”（`06` L290，`16` L23–24，`15` L1168）。
     - 但 `Run.reason` 的取值（`02` L337，`06` L530 的 CHECK，`16` L106）没有 `handback`。另外，`06` L849 写的是交还的 Run 以 `reason:"resume"` 开始。
     - 照字面实现，排队后的交还在写 `runs` 行时违反 CHECK。
     - 哪些命令写哪种 `kind`也没有逐条列出：`retry_after_human_change`、`sentinel_high` 中的 `request_changes`（经继续目标 `run`）、继续目标 `run` 本身各写什么，都没有写。排序键（`06` L294）也没有 `handback`。
  5. **残值。**
     - 该列只在准入通过时清除。从 `ready` 派生出来的路径可能不经准入就离开排队：
       - 自 `ready` 接管后 `hand_back{reverify}`，进入 `verifying`，不开 Run；
       - 准入第 f 项进入 `paused(budget_hard_cap)` 后选 `claim_on_behalf`。
     - 这两种情况下，`queued_run` 会带着过期的 `rework` 留在 `verifying`/`in_review` 中的 Goal 上，下一次走不写该列的路径（例如第 2 项）时被误用。
     - 另外，`16` L24 列出的“保留”情形只有 `pause`/`take_over`/外部写入，没有准入第 f 项的硬上限。
- **为什么重要**：
  - 第 1、2 项落在 ADR-014 的积压闸门上，这是“评审是瓶颈”这一产品主张的执行机制。
  - 第 4 项照文档实现会直接写库失败。
  - 第 3 项让崩溃恢复在准备中这一段没有定义。
  - 五项都来自 ADR-147 新增的同一个字段，修订量很小。
- **文档位置**：`02` L179、L337；`03` L54、L55；`06` L290、L294、L300、L464、L530、L824、L836–837、L849、§6.1.6；`07` L1458；`16` L23、L24、L106；`15` ADR-147 L1168；`14` G42。
- **期望的回答形态**：
  - 写明每条进入 `ready` 的路径写什么 `kind`：
    - `ratify`/`quick_ratify` 写 `{initial}`（`goal.start` 同）；
    - 依赖回退写 `{resume}`；
    - 自动返工与 `request_changes` 写 `{rework}`；
    - `retry_after_human_change` 与交还 `continue_agent` 写 `{handback}`；
    - 继续目标 `run` 在没有已保留的值时写 `{resume}`。
    - 或者另一种写法：规定 NULL 即“首次启动”，并保证所有非首次路径都写非 NULL。
  - `06` L294 的 `initial` 改为“首次启动（Goal 从未开过 Run）”，排序键加入 `handback`。
  - 给出 `kind → Run.reason` 的映射，例如 `handback → resume`，与 `06` L849 一致。或者把 `handback` 加入 `Run.reason` 的 CHECK。
  - 清除点改为 `run.started` 的同一事务（与 `pending_openings` 一起）。在 `06` §6.1.6 加一行“`ready`（含准备中）”：以 `queued_run` 重建队列，入队时间取最后一次写该列的事件序号。
  - 离开排队的非 Run 出口（`reverify`、`claim_on_behalf`、`abandon`）清除该列。可加 CHECK：`queued_run IS NULL OR state IN ('ready','paused')`。
  - 用例：
    - G42(g)：阻止模式下，新批准的 Goal 被积压闸门挡在 `ready{review_capacity}`；
    - G42(h)：依赖回退后依赖恢复，不受积压闸门限制；
    - G42(i)：排队的交还开 Run，`Run.reason` 合法；
    - G42(j)：准备中退出应用，重启后按原类别重新排队。

### D6 系统架构与可靠性

**R22-D6-01｜次要**（准备阶段没有失败与中断的出口；`E_BUSY` 在失败时没有终点）

- **问题**：
  1. **准备失败时 Goal 无法放弃。**
     - ADR-147 规定，准入通过到 `run.started` 之间，`pause`/`take_over`/`abandon` 一律返回 `E_BUSY`，“准备阶段结束后按 `running` 处理”（`06` L290、L840；`16` L23、L268；`04` L942；`12` L376）。
     - 但准备阶段可能以失败告终，永远到不了 `run.started`：
       - 卫星创建失败：`08` L396 记为 `stalled{prepare_failed}`，“Run 无法开始”；
       - Host 握手 20 s 无响应：`05` L463 判定启动失败。
     - 两种情况下 Goal 停在 `ready`、Mode 为 `preparing`，没有任何转移把它带出准备阶段：
       - `03` L54 的 `ready` 出口没有失败边；
       - `06` L64 的 Host 崩溃处理写明“只影响 running 的 Goal”。
     - 于是 `放弃` 在这个 Goal 上永远返回 `E_BUSY`，与 `03` L45“abandon（任何非终态）”矛盾。
     - 这是 ADR-147 的回归：ADR-146 时 `ready` 中可以 `abandon`。
  2. **Needs-You 的选项全部不可用。**
     - `stalled` 条目的选项是“暂停、转向、回退、接管、重启宿主”（`08` L491）。在准备阶段，前四项要么返回 `E_BUSY`，要么没有 Run 可作用；“重启宿主”的定义（`06` L64）又以 `paused(engine_crash)` 为前提。
     - 去重键 `st:{goal}:{runId}`（`08` L199）在 Run 还没开始时的 `runId` 取值也没写。
  3. **准备中的系统暂停与崩溃。**
     - `10` L243 规定，`ready`（卫星已存在时）中检测到来源不明的写入立即进入 `paused(external_change)`。但准备中的 Goal 同样是 `ready`，而启动序列（`06` L324–333）可能正在 `host.spawn`。
     - 立即转为 `paused` 之后，进行中的启动是取消，还是在 `run.started` 后 drain，没有写。
     - 应用退出或崩溃发生在准备中时，恢复表同样没有对应的行（与 R22-D4-01 第 3 项同源）。
- **为什么重要**：
  - 卫星创建失败（磁盘满、权限）与 Host 启动失败（Pi 或 Node 环境损坏）都是现实中会遇到的失败。
  - 照现文实现，这样的 Goal 卡在“准备中”：所有按钮都提示“稍后重试”，而“稍后”永远不会到来，执行槽位也可能一直占着。
  - D8 的“可逃逸”要求在这一处不成立。
- **文档位置**：`03` L45、L54；`05` L463、L543；`06` L64、L283（`EngineManager.cancel`）、L290、L324–333、L840、L877、§6.1.6；`08` L199、L396、L491；`10` L243；`16` L23、L268；`04` L942；`12` L376；`15` ADR-147 L1173；`14` G42(e)。
- **期望的回答形态**：
  - 在 `06` §6.2.4 定义“准备阶段结束”包含失败，并写明失败的去向。例如：
    - 释放槽位与端口段；
    - Goal 进入 `paused(engine_crash)`（Host 启动失败，沿用 10 分钟内自动重试一次的规则）；或者进入 `paused(satellite_missing)`（卫星创建失败，沿用重建或放弃的出口）；
    - 继续目标 `run`，`queued_run` 保留或恢复；
    - `03` L54 增加这条边，`06` L64 的“只影响 running”加上“及准备中的 `ready`”。
  - `abandon` 在准备阶段改为先 `EngineManager.cancel` 再放弃，与 `03` L45 一致。若坚持 `E_BUSY`，须写明它的上界（准备结束或失败即终止），并由界面在失败时立即恢复按钮。
  - 准备阶段检测到外部写入、预算硬上限等系统原因时，二选一：
    - 取消准备、释放槽位，然后按 `ready` 的规则进入 `paused`；
    - 或者记下原因，在 `run.started` 后立即以该原因 drain。
  - `08` 写明 `stalled{prepare_failed}` 的可用选项（重试准备 / 放弃 / 诊断），去重键在没有 Run 时用 `st:{goal}:prepare`。
  - 用例：
    - G42(k)：准备中卫星创建失败，人按“放弃”；
    - G42(l)：Host 握手超时；
    - G42(m)：准备中检测到外部写入；
    - G42(n)：准备中退出应用并重启。

### D15 文档一致性与可执行性

**R22-D15-01｜次要**（声明为唯一来源的 `03` §3.2.1 `human` 行没有跟上 ADR-147）

- **问题**：
  1. **放弃改动的判定。**
     - `06` L852 写明 `discard_human_edits` 的“语义以 `03` §3.2.1 `human` 行为唯一来源”，随后在同一行写 `takeover_from ∈ {running, ready}` 时不解除 `human`。
     - 但 `03` L78 仍是“`takeoverFrom = running` 或 `takeoverPriorReasons` 含 `human` 时不解除 `human`”。
     - 自 `ready` 接管时，接管前的原因集合为空。按唯一来源实现，放弃改动会解除 `human`，`onAllReasonsCleared()` 执行继续目标 `run`，自动开 Agent Run。这正是 ADR-137 与 ADR-147 要排除的情形。
     - `07` L1512 的同一段也只写 `takeoverFrom = running`。
  2. **同一行的另两处。**
     - `03` L78 的入口列：`pause` 只列 `running、verifying`，`take_over` 只列 `running/paused/in_review/accepted`；
     - 同行“继续目标在接管时按来源状态写入”的列表也没有 `ready`。
     - `03` L54、L68 已覆盖这些边，因此这两处单独不会误导；但它们与第 1 项在同一行，应一并对齐。
  3. **其他滞后的摘要。**
     - `02` L162 `takeoverFrom` 注释仍列四个值；
     - `04` L575、`05` L1171 的接管源状态没有 `ready`；
     - `16` L284 只写“不与 Agent 工具调用重叠”，没有写 ADR-147 的存活进程条件；
     - `10` L895 Q5(a)（M2）仍写“回到 `running`（返工 +1）”，没有经准入，R21 已提过。
     - 这些都有正确的唯一定义可循，单独不扣分。
- **为什么重要**：第 1 项是“唯一来源”与引用它的命令定义互相矛盾，按哪一份实现都说得通，而按唯一来源实现会违反一条已登记的不变式（放弃改动不自动开 Run）。lint (r′) 只比对互相声明“一致”的成对文字，抓不到这种单向引用，所以需要人工对齐。
- **文档位置**：`03` L78；`06` L852；`07` L1512；`02` L162；`04` L575；`05` L1171；`10` L774、L895；`16` L33、L39、L284；`15` ADR-137 L1043、ADR-147 L1171。
- **期望的回答形态**：
  - `03` L78 的出口条件改为“`takeoverFrom ∈ {running, ready}` 或 `takeoverPriorReasons` 含 `human`”；入口列加入 `ready`（`pause`、`take_over`，后者注明“仅卫星已存在时”）；继续目标列表加入“从 `ready` 接管 → `run`（`queuedRun` 保留）”。
  - `07` L1512 同步。`02` L162、`04` L575、`05` L1171、`16` L284 同步。`10` L895 改为引用 `07` 的 `decide`。
  - 可选：在 lint 中增加一项检查——凡写“以 X 为唯一来源”的行，比对它与 X 中同一判定条件的取值集合。
  - 用例：G42(c) 已覆盖行为，不需要新增。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D7、D9、D10、D11、D12、D13、D16 为 100，在这十个维度上没有找到可追问的实质问题。
  - 其余六个维度在 98–99 之间，最低为 D4、D6、D15（98）。
- **是否还有可追问的问题：有，但都是次要项。**
  - **第 21 轮核验**：3 条中已解决 1、部分 2、未解决 0。
  - **其他核对**：
    - lint 全部通过；
    - Pi 事实（`user_bash` 处理器返回值、RPC `bash` 的 `operations` 传递、`exec` 不传 `env`、`!cmd` 与流式并发）与源码一致；
    - 排期算术（WBS 118.52、37 周、余量 0.21–0.72、增人备选 32 周）全部成立。
  - **本轮追问**：新增与残留共 **3** 条，阻断 0、重要 0、**次要 3**：
    - R22-D4-01；
    - R22-D6-01；
    - R22-D15-01。
  - D5、D8、D14 的扣分来自上述条目，不单独编号。
- **设计是否完成：否。**
  - 剩余问题都在 ADR-147 新增的 `queuedRun` 字段与准备阶段 `E_BUSY` 周边，以及一处唯一来源没有同步。不需要新的架构，每一条都可以用几句规则加一两个用例关闭。
  - 其中三处若照现文实现会直接出错：
    - 排队的交还以 `run.requested{handback}` 写 `runs` 行，违反 `Run.reason` 的 CHECK；
    - 首次启动的 Goal 不受评审积压闸门约束（或者依赖回退的 Goal 被它卡住）；
    - 准备失败的 Goal 无法放弃。
- **下一轮建议按以下顺序修订**：
  1. **R22-D4-01**：
     - 逐条写明各入口写入的 `kind`，首次启动写 `initial`；
     - 给出 `kind → Run.reason` 映射；
     - 清除点移到 `run.started`；
     - 补恢复表 `ready` 行与残值清除。
     这一条在准入这个唯一闸口上，且关系到 ADR-014，最优先。
  2. **R22-D6-01**：
     - 定义准备失败与中断的去向；
     - `abandon` 在准备阶段先取消准备；
     - 写明系统暂停原因在准备中的处理；
     - 写明 `stalled{prepare_failed}` 的选项。
  3. **R22-D15-01**：`03` L78 与 `07` L1512 按 ADR-147 对齐，其余摘要同步。

  各线缓冲外余量为 0.21–0.72 工作周，最紧的是桌面 0.21、安全 0.39。上述修订估计合计在 0.2 人周以内，主要落在系统线（W3）与设计线（用例），`04`/`08` 的文案改动很小，不应触发顺延。若桌面线承担界面改动后超出余量，按 ADR-136/143/144 显式选择，并记 ADR。
