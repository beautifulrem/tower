## 1. 总评

第 1 轮的 123 条中，101 条已在文档中真正落地，22 条只解决了一部分，没有完全未处理的条目。最难的几项（两轨进度、依赖存储隔离、`exec.test` 在 S0 下需授权、对话框唯一规格、调速器公式、`decide()`）都给出了具体机制，`16-registry` 也让大部分标识符有了唯一出处。

剩下的问题集中在三处。第一，几项修复在 Pi 源码层面不成立，或与其他文档的模型互相抵消。tower-goal 用同名 `bash` 实现 S2 沙箱，但 Pi 的同名工具是“先注册者胜”，SDK 下 tower-goal 恰好最后加载。`session_compact` 里以 steer 投递账本块，会在 `submit` 之后强行多跑一轮。`13` 的整机内存模型在参考硬件上只允许 1 个验证槽位，这使 `07` 自己给出的 M1 验证延迟预算不可达。第二，状态机仍有出口缺失（验证阶段的暂停如何回到 `verifying`）和枚举缺口。第三，修订后残留的旧说法与跨文档冲突仍有十余处，`04` 与 `14` 对 M1 范围的说法互相矛盾。

- 问题：北极星 Q3 的分母 M 有两种定义。
  - `07` §7.2.4（L129–138）：M 只计机器标准（exec + artifact），human 标准单独显示为“人工 h/k”。
  - `04` 的 G-0142 有 C1–C4 四条机器标准和 C5 一条人工标准，却处处显示“已验证 2/5 · 观测 3/5”（L154、L212、L242、L290）；O = 3 也只有在 M = 5 时才能与“C1、C2、C4”对上。
  - `12` §12.10.1（L513）写“V = 验证器新鲜通过数（+ 已勾选的人工标准）”，把人工勾选也算进 V，与 `07` 的“V 只来自验证器”直接冲突；“人工已勾选”分段的 ASCII 同样画成 `▰`。
- 为什么重要：Q3 是 R4 与 ADR-020 用来替代过程流的核心读数，也是 E4、E12 的测量对象。口径不唯一，等于 R1-D8-05 又回来了；把人的勾选计入“已验证”还违反“绿色只属于验证器”。
- 文档位置：`07` §7.2.4；`04` §4.3.1、§4.4.1、§4.5.1、§4.9；`12` §12.10.1；`16` 未登记 M 的定义。
- 期望的回答形态：在 `16` §16.1 登记唯一定义，例如“M = 机器标准数；human 标准另列 `人工 h/k`，从不进入 V 或 O”，并改正所有线框与 `12` 的分段规则。

### D2 Pi 哲学契合度

**R2-D2-01｜重要**
- 问题：所有“源码核实”都基于 `research/pi-mono` 的 HEAD `b06c1f2`，而这份源码在 1.2.0 之上还有 `[Unreleased]` 改动。`05` §5.11 用来支持“精确固定版本”的 `CHANGELOG.md:11` 本身就属于未发布部分。Tower 固定的是 npm 上的 `1.2.0`（`05` L10、L1177），与被核实的代码并不相同。
- 为什么重要：D2 和 D5 的全部事实（行号、事件顺序、加载顺序、`agent_settled` 的推迟语义等）都可能与实际随应用发布的版本不同。
- 文档位置：`05` §5.0、§5.11；`01` §1.5；`14` SP2。
- 期望的回答形态：改为对照 `v1.2.0` 发布标签或 npm 包的 tarball 重新核实，在 §5.11.1 增加“已在发布版上验证”一列；或把固定版本改为一个明确的提交，并说明打包方式。

**R2-D2-02｜重要**
- 问题：ADR-019 规定默认开启的特性必须同时满足 (a) 不增加模型面、(b) 确定性或有外部证据、(c) 风险不对称（`15` L140）。但 `log` 工具默认开启（ADR-019 表、`16` §16.6），它恰恰是在增加模型面，并且改变 Agent 的行为。另外，nudge、简报注入等同样改变模型输入的机制，在 `16` §16.6 中被标成“非监督特性”，从而绕开了这条规则，而这种分类没有任何判据。
- 为什么重要：这是 R1-D2-04 要求的“等特性被证明”的落实点。规则自己默认就被违反，准入规则形同虚设。
- 文档位置：`15` ADR-019；`16` §16.6 L663、L678；`14` §14.5.0。
- 期望的回答形态：二选一。要么 `log` 在 E5 结论出来之前默认关；要么修改规则 (a)，把“模型面变化，但有预算上限并由 E5 裁决”列为明确的例外类别，并说明 nudge 和简报属于哪一类、依据是什么。

**R2-D2-03｜重要**
- 问题：`05` §5.11.1 自称是“唯一清单”，却漏掉了多项实际依赖：
  - `createBashTool` 的 `operations` / `spawnHook`，以及同名工具的优先级规则（`runner.ts:636-646` 是“先注册者胜”；`agent-session.ts:3590-3593` 中扩展工具覆盖内置工具）。S2 正是靠这一点实现的（`11` §11.6.2 L314）。
  - `SessionManager.forkFrom`、`createBranchedSession`（`10` §10.1.1、§10.8、§10.16 F）；`SessionManager.listAll`（`02` §2.12）；`parseSessionEntries`（`06` §6.6.5）。

- 期望的回答形态：补齐清单条目，每项指定分类（A/B/C）和契约测试；为“同名工具的优先级”新增一个契约测试。

**R2-D2-04｜重要**
- 问题：Engine Host 只保留白名单中的环境变量（`05` §5.3.6、`11` §11.7），而 ADR-033 只处理“API Key 类”凭据。下列凭据会因此失效，又无法用 `setRuntimeApiKey` 注入：

  - `HTTPS_PROXY` / `NO_PROXY` 等代理变量；

### D4 领域模型与生命周期

**R2-D4-01｜重要**
- 问题：`03` §3.2 的 `paused` 行只有两个出口：→ `running` 和 → `in_review`。下列情况都没有定义：
  - `paused(verify_env_error)`、`paused(s0_grant_pending)`：代码已经提交，修好环境或获得授权之后，应当以同一个 pin 回到 `verifying`，而不是回到 `running` 让 Agent 再跑一轮。`07` §7.10.3 的选项“重试”指向哪个状态？
  - `paused(human_change_verify_failed)`：选项没有定义（交给 Agent？人自己修？撤销人的改动？）。
  - `paused(question_timeout)`：`ask_user` 已经返回“No answer; pause and wait.”，Run 已 drain。人之后作答时，答案怎样送达？`05` §5.6.4 与 `08` §8.7.1 都没有写（是作为 `resumeInput` 送达，还是锚定在原问题上的转向）。
  - `claimed → paused(post_settle_activity)`（ADR-025 规定 1 小时内第 2 次时进入）不在 `03` 的 claimed 行、`05` §5.5、`06` I4 中。
- 为什么重要：`06` §6.2.3 要求按“状态 × 输入”穷举、CI 100% 覆盖。缺出口时，实现只能各自猜测，而验证阶段的暂停是高频路径。
- 文档位置：`03` §3.2 L41–43；`07` §7.10.3 L1014；`05` §5.6.4；`08` §8.7.1；`15` ADR-025。
- 期望的回答形态：补全转移表，写明每个暂停原因的出口目标、触发命令和守卫，例如 `paused(verify_env_error) --retry_verify--> verifying(同一 pin)`，并写明 `question_timeout` 下答案的投递机制。

**R2-D4-02｜重要**
- 问题：`pauseReason` 枚举仍有缺口，DDL 也与枚举不一致：
  - `04` §4.18.3：“工作区出现非 Agent 改动 → 运行中则暂停”（L1040）、“离线 → 重试后暂停”（L1035），都没有对应的原因值。
  - `06` §6.2.5：`usdHard` 超出后暂停且没有“继续”选项，复用 `budget_soft_cap` 吗？
  - `04` 的 G-0139 显示“已暂停 · 超时默认 · 已拒绝新增依赖”（L160、L245），但按 `05`、`11`，审批超时默认拒绝只会把 block 返回给 Agent，不会暂停 Goal。
  - `06` DDL 中 `pause_reason` 的 CHECK（L420–422）没有 `question_timeout`，而 `02` §2.4 和 `16` 都有，写入会失败。
- 为什么重要：同一个状态的解释性字段，在 UI 文案、Needs-You 和自动恢复规则（`autoResume`）中都要用到。
- 文档位置：如上；`12` §12.6.5。
- 期望的回答形态：补齐原因值（例如 `external_change`、`provider_unavailable`、`budget_hard_cap`），更新 DDL、`16` 与 `12` 的文案表；修正 G-0139 线框，或定义“默认拒绝后暂停”的规则。

**R2-D4-03｜重要**
- 问题：I4 规定 `claimed` 需要“无未决 Needs-You”（`03` L57、`06` §6.2.3）。“未决 Needs-You”的范围没有界定：以该 Goal 为 owner 的 `ratify` 聚合条目（severity 1，默认攒批）、非阻断的 `sentinel`、`conflict` 等都可能长期处于打开状态，Goal 就永远无法进入 `claimed`。这时 Goal 停在 `running`，Run 已经 settled，下一步是什么也没有定义（会被判为 `idle_without_submit` 吗？）。
- 为什么重要：这会在高频路径上造成静默死锁。
- 文档位置：`03` §3.3 I4；`06` §6.2.3；`05` §5.5 L497。
- 期望的回答形态：把条件限定为“本 Run 产生的、`costOfDelay = agent_blocked` 的 question/approval 条目”，并定义 settle 时存在这类条目的处理方式。

**R2-D4-04｜重要**
- 问题：“计划编译为运行时围栏”的立场前后不一：
  - `00` R7（L39）、`01` §1.2 #3 与 §1.8、`02` §2.5（L256–260）：批准计划时，`scope.include = ∪ steps.touches`，`needsDecision` 生成停止条件，并在 `log{kind:"step"}` 时检查；
  - `04` §4.5.2（L331）与 §4.10.2（L727）：“计划步骤只用于预测与停点，不是可执行约束”；回应文件（`round-1-response-04-12.md`）还声称已删除“编译”的说法。
- 为什么重要：两种说法下，范围围栏的生效值不同（是否被计划自动收窄），门禁行为也不同。
- 文档位置：如上。
- 期望的回答形态：选定一种说法，在 ADR 中记录；若保留编译，说明合同中显式的 `scope` 与 `∪ touches` 冲突时以哪个为准，以及合同编辑器如何显示编译后的围栏。

**R2-D4-05｜次要**
- 问题：
  - 修订矩阵（`03` §3.4.5）缺少 `paused`、`draft`、`shaping` 三列；其中 `paused(verify_failed_limit)` 时修订标准是最常见的操作。
  - “claimed/verifying 期间修改意图文字 → 取消验证、回到 running”缺少理由（只改了措辞也会作废已提交的工作）。
  - §3.1 的状态图与 §3.2 的转移表不一致：图中缺 draft→ready、verifying→paused、claimed→running、integrated→accepted、running→ready；图中的 ready→shaping（amend）又不在表中。
- 为什么重要：转移表要求穷举，图是工程师的第一入口。
- 文档位置：`03` §3.1、§3.4.5。
- 期望的回答形态：补齐三列；以表为准重画状态图。

**R2-D4-06｜次要**
- 问题：`canonicalRoot` 取“当前所有根提交中字典序最小的一个”（`02` §2.3、ADR-028）。仓库之后引入新的根提交（例如 `git merge --allow-unrelated-histories`、`git subtree add`）时，如果新根的字典序更小，Project 身份就会改变，记忆、信任和 Goal 归属随之成为孤儿。

### D5 Agent 架构与 Pi 集成

**R2-D5-01｜阻断**
- 问题：S2 的实现方式是 tower-goal 用 `createBashTool(worktree, {operations: sandboxedOps, spawnHook})` 注册一个同名的 `bash`，覆盖内置工具（`11` §11.6.2 L314）。Pi 合并工具的规则是：扩展中的同名工具覆盖内置工具，而多个扩展之间“先注册者胜”（`runner.ts:636-646`；`agent-session.ts:3534-3593`）。
  - **SDK（默认）**：为了让门禁看到最终输入，tower-goal 被放在最后加载（ADR-024）。于是任何先加载、且注册了 `bash` 的用户或项目扩展（例如 Pi 自带的 sandbox 示例、远程执行类扩展）都会胜出。Agent 的 bash 在 Tower 的 S2 之外运行，而 UI 仍显示“沙箱 S2”，`exec.test` 也仍是 silent。
  - **RPC**：方向正好相反，tower-goal 最先加载，它的 bash 胜出。
  - 门禁需要“最后”，bash 覆盖需要“最先”，这两个要求在同一份扩展上互相冲突。`11` §11.4 只写了“名称不变则分类照常”，没有处理沙箱失效的问题。
- 为什么重要：ADR-022（S2 下 exec 为 silent）、T3、T5、T7 的残余风险评级，以及“已验证”不带 S0 限定，都以 S2 生效为前提。这个前提在默认路径上可以静默失效。
- 文档位置：`11` §11.6.2、§11.4 L259；`05` §5.3.5、§5.11.1；`15` ADR-024、ADR-040。
- 期望的回答形态：SDK 下改用 `customTools` 注入沙箱 bash（它在扩展工具之后写入注册表，`agent-session.ts:3535-3541`），或由 Host 启动后检查生效的 `bash` 定义的 `sourceInfo` 是否属于 tower-goal，不是则拒绝启动或降级为 S0 并显示。RPC 下给出等价规则，并增加契约测试。

**R2-D5-02｜重要**
- 问题：`05` §5.6.5（L840）与 ADR-026 在 `session_compact` 中调用 `pi.sendMessage(ledger, {deliverAs:"steer"})`。按阈值触发的压缩通常发生在 `agent_end` 之后、run 之内（`agent-session.ts:1866-1873, 3087-3089`），此时 `isStreaming` 仍为真。steer 进入队列后，`_runAutoCompaction` 返回 `hasQueuedMessages() = true`（L3229–3231），循环调用 `agent.continue()`。结果是 Agent 本来要停下（包括 `submit` 带 `terminate:true` 之后），却被账本块强行开启一个新的 LLM 回合。这可能改动工作区，使有效提交作废，并触发 nudge 等连锁反应。
- 为什么重要：这与 ADR-026“不改变 Pi 默认路径”的初衷相反，也直接干扰 I4。
- 文档位置：`05` §5.6.5；`15` ADR-026；契约测试 C17。
- 期望的回答形态：改用 `{triggerTurn:false}`（流式中进入 `_pendingCustomMessages`，在回合结束、settle 前或 run 结束时写入，不触发回合，L2348–2356）；C17 增加断言“压缩后没有额外的 `agent_start`”。

**R2-D5-03｜重要**
- 问题：RPC 模式下门禁的兜底弱于文档所说：
  - 哈希比对在 `tool_result` 中进行，此时工具已经执行。人批准的是输入 A，实际执行的是 B（包括单向门动作），`05` §5.4.1 却称之为“主要防线”。
  - 被后续处理器 block 的调用不会到达 `tool_result`（`agent-loop.ts:744-756`），`approvedInput` 会泄漏。
  - 注册了同名工具的扩展可以完全绕过比对（参见 R2-D5-01）。
  - 后续的 `tool_result` 处理器可以整体替换 `details`（`runner.ts:1206-1209`），抹掉 `details.tower`，脱敏处理器也不再是最后一个（`11` §11.7 L366 没有考虑 RPC 下的顺序）。
  - `11` §11.4（L256–257）仍写“tower-goal 必须最后加载”，并称 RPC 启动时会检查其后注册的 `tool_call`，但 RPC 没有任何命令能暴露处理器顺序。
  - 威胁表中没有这一项。
- 为什么重要：RPC 是 M2 的交付项，也是“使用我安装的 pi”的承诺；这个缺口既涉及安全，也涉及脱敏。
- 文档位置：`05` §5.4.1、§5.6.5 第 6–7 条；`11` §11.4、§11.7、§11.12；`15` ADR-024。
- 期望的回答形态：在 RPC 门禁中深度 `Object.freeze(event.input)`，使后续的修改抛错并阻断调用（需要测试内置工具的兼容性）；新增威胁条目 T26 与 RPC 适用范围（例如只用于 low 风险，或检测到用户扩展注册了 `tool_call`/`tool_result`/`bash` 时拒绝）；修正 `11` §11.4。

**R2-D5-04｜重要**
- 问题：ADR-025 的覆盖面与归因都有缺口：
  - 由定时器发起的 `sendUserMessage` 不会被推迟，可以在 2 s 宽限之后的任意时刻开始新 run；
  - settle 之后的 `ctx.compact()` 只设置 `isCompacting`，不会被捕获；
  - `05` L497 说“通过对比 settled 前后 `extensionsResult` 中注册了 `agent_settled` 的扩展列表来推断来源”，但注册列表在前后是相同的，这种比较无法识别是哪个处理器发起了活动；
  - “1 小时内第 2 次 → `paused(post_settle_activity)`”只写在 ADR-025 中。
- 为什么重要：`claimed` 之后又出现活动，会让验证面对一个正在变化的工作区；归因错误会把用户引向错误的扩展。
- 文档位置：`05` §5.5 L497；`03` §3.2 claimed 行；`06` §6.2.3 I4；`15` ADR-025。
- 期望的回答形态：把宽限确认扩展为“`claimed`/`verifying` 期间持续监视 `isStreaming`、`isCompacting` 与 `agent_start`”；归因改为如实标注“未知，以下扩展注册了相关钩子：…”；把 1 小时规则写进 `03`、`05`、`06`。

**R2-D5-05｜次要**
- 问题（集成细节的事实错误）：
  - `05` L225 说 Observer 从 `tool.end` 读取 `args`，但 `tool_execution_end` 不带参数（`agent-loop.ts:919-928`）；`tool.start.args` 是原始参数（L543–547），看不到门禁注入的 `timeout` 和之后的修改。
  - L269 说 `switchSession` 不能覆盖 cwd，实际它接受 `cwdOverride`（`agent-session-runtime.ts:196-211`）。
  - `--session-id` 是“打开或创建”，不只是新建（`main.ts:435-447`）。
  - entry id 只在单个文件内唯一（`session-manager.ts:277-284`），fork 后会保留原 id；`Provenance.piEntryId` 与 Cue 中的引用都需要带上会话。
  - ADR-024 引用“`05` §5.3”，应为 §5.4.1。
- 为什么重要：这些错误会导致对账与 Trace 定位出错。
- 文档位置：如上。
- 期望的回答形态：逐条改正；Observer 改为把 `tool.start` 与 `tool.end` 按 `toolCallId` 合并，并说明它看不到门禁之后的修改。

### D6 系统架构与可靠性

**R2-D6-01｜次要**
- 问题：分层保留与删除守护只针对 `state = 'archived'` 的 Goal（`06` L391、`02` §2.13）。`abandoned` 的 Goal 的 `engine.*` 事件永远不会被清理，而放弃是常见的结局（ADR-029 每周提示批量放弃）。

### D7 诚实与验证

**R2-D7-01｜阻断**
- 问题：验证容量在参考硬件上不可行。
  - `07` §7.4.10 的排队模型假设 c = `floor(cores/4)`，8 核时 c = 2，由此得出 M1 预算 claimed → in_review p50 ≤ 10 min、p95 ≤ 20 min。
  - `13` §13.8.3 的整机模型为每个验证槽位预留 `min(8 GB, 0.4 × RAM)`。它自己的演算结论是：16 GB 机器上“默认并发 3 + 1 个验证槽位恰好可行；第 2 个验证槽位只能在 Goal 数 ≤ 1 时启动”。而 `13` §13.1 的参考硬件正是 M1 Pro / 16 GB。
  - 所以 3 个 Goal 时实际 c = 1。按 `07` 表中“c = 1，3 个 Goal”一行，p95 ≈ 90 min，是预算的 4.5 倍。
  - 同时，机会式验证“只使用未被预留的余量”。只要有一次正式验证在进行，余量就只剩约 50 MB，机会式验证几乎从不运行，运行中 Q3 的 V 轨也就很少前进。
- 为什么重要：这同时击穿了 M1 退出标准中的验证延迟预算（`14` §14.3.5 性能行、`16` §16.2.3），以及 ADR-020“运行中也有答案”的承诺。
- 文档位置：`07` §7.4.10 L545–561；`13` §13.1 L19、§13.8.3 L190–207；`16` §16.2.3、§16.2.6。
- 期望的回答形态：统一两个模型。例如按项目实测的验证进程树峰值预留内存，而不是固定的 40% RAM；或把 M1 参考硬件改为 32 GB；或修订延迟预算。并给出机会式验证在参考硬件上的预期频率，在 E4、E12 中测量。

**R2-D7-02｜重要**
- 问题：“验证器存储只读 + 从 depcache 写时复制物化”在多个生态上不可行或没有规格：
  - cargo 需要可写的 `CARGO_HOME`（`.package-cache` 锁文件，构建时还要把 crate 解压到 `registry/src`）。验证器沙箱对它写拒绝，`cargo test` 会直接失败。
  - `uv run` 默认会同步环境，写缓存锁。
  - `10` §10.4.2（L191）自己就说 `.venv` 含绝对路径、不可克隆；Rust 的 `target/` 也依赖路径。可 `07` §7.4.2–7.4.3 仍规定“依赖目录每次从 depcache 经写时复制物化到槽位”。
  - 安装器在哪个目录里执行、depcache 的目录布局（monorepo 每个包都有自己的 `node_modules`）、物化到槽位的映射，都没有写。
- 为什么重要：这是 R2“干净环境验证”的地基。若按现状实现，大量项目会落到 `verify_env_error`，或被迫放宽隔离。
- 文档位置：`07` §7.4.2–7.4.3；`10` §10.4.2；`11` §11.6.3。
- 期望的回答形态：一张逐生态的物化规格表（安装位置、可写叠加层、哪些可以 CoW 复制、哪些必须在槽位内重建、哪些路径必须保留绝对路径），以及 SP5、SP6 对应的测试矩阵。

**R2-D7-03｜重要**
- 问题：机会式验证“只跑 exec 标准，不跑测试清单与哨兵”（`07` §7.2.4 L161），但它的通过结果以事实语法、绿色 ✓ 显示，并计入 V。如果 Agent 在运行中把 `package.json#scripts.test` 改成 `echo ok`，或削弱了测试，L-b 层会立即出现 `■` 哨兵，同时 C1 却显示“⚙ 通过 · 已验证”，卡片写“已验证 2/5”。
- 为什么重要：这违反“绿色只属于验证器的结论”的精神：验证器确实跑了，但它跑的是一个已经被改掉含义的标准。
- 文档位置：`07` §7.2.4、§7.5.5；`12` §12.5.4；ADR-020。
- 期望的回答形态：规定 TestPathSet 或间接定义存在未处置改动时，机会式验证的结果不计入 V（或以“有保留”的形态显示），并在 `decide()` 之外为 V 的计算加入这条守卫。

**R2-D7-04｜重要**
- 问题：验证器超时与资源问题的归类，三处说法不一：
  - `07` §7.4.5：`timeout`、`hung`、`resource_exceeded → "error"` 都不算通过，于是 `outcomeOf` 为 fail，触发自动返工并计入返工次数；
  - `04` §4.18.3（L1033）：“验证器未能执行（超时）”按验证环境故障处理（不返工、不计次数、进 Needs-You）；
  - `06` F20（L996）：verdict 记为 `resource_exceeded`，但 `07` 的 verdict 枚举里没有这个值。
- 为什么重要：Agent 引入的死锁或内存泄漏是真实的失败；环境过慢则不是 Agent 的问题。归类错误会让 Agent 为环境问题返工，或让真实缺陷绕过返工。
- 文档位置：如上；`16` §16.1.3。
- 期望的回答形态：一条判别规则，例如同一 pin 上用相同资源重跑一次、对比 base 上同一标准的耗时，并在三处统一。

**R2-D7-05｜次要**
- 问题：`07` §7.2.4（L149）说 artifact 检查“足够便宜，可在每次指纹变化后立即执行”，但检查项包括 `links:reachable`（至多 50 个外部链接，每个 5 s），而验证器的网络默认只允许 localhost（§7.4.4）。
- 为什么重要：成本与网络策略互相冲突，结论可能长期为“有保留”。
- 文档位置：`07` §7.2.4、§7.4.9。
- 期望的回答形态：外部链接检查只在 claimed 时执行，并说明它所需的网络权限。

### D11 安全与自主度

**R2-D11-01｜重要**
- 问题：首次加载清单确认依赖一次“只加载、不运行”的探测（`05` §5.10 L1168、`11` §11.8.2 L426）。但加载扩展本身就会执行模块顶层代码和 factory 函数，即在人确认之前，以用户权限、在沙箱外执行了未确认的代码。RPC 模式“用同一份用户配置在 SDK 中解析”时，解析所用的 Pi 版本与用户实际安装的版本也不同。
- 为什么重要：清单确认是 R1-D11-03 的核心缓解措施，探测步骤本身就绕过了它。
- 文档位置：如上。
- 期望的回答形态：探测前只做静态清单（路径与内容哈希），确认之后才加载；或把探测放在 S2 包裹、禁网、禁写的一次性进程中执行，并说明残余风险。

**R2-D11-02｜重要**
- 问题：S2 允许 Agent 写 `$GIT_COMMON_DIR/objects/**` 与 `logs/**`（`11` §11.6.2 L319）。这些是**用户主检出**的对象库。沙箱的“写允许”包括删除和覆盖，Agent（被注入时，或经混淆的 bash，在 S2 下 opaque 只是 notify）可以删除 `objects/pack/*.pack` 等文件，造成用户仓库数据丢失；也可以替换松散对象，影响验证器从共享对象库检出 pin 时读到的内容。T5 只覆盖了 `config` 与 `hooks`。
- 为什么重要：这是越过 Tower 边界、作用于用户资产的破坏路径，也会影响“已验证”的完整性。
- 文档位置：`11` §11.6.2、§11.12 T5/T21；`07` §7.4.2。
- 期望的回答形态：让 Agent 的 git 使用私有对象目录（`GIT_OBJECT_DIRECTORY` 加上指向公共对象库的 alternates，由 Tower 在 seal 时迁回）；或限定为只能新建、不能删除覆盖，并在 pin 检出前执行 `git fsck`。在威胁表中新增此项。

**R2-D11-03｜重要**
- 问题：私有存储的环境变量清单，四处写法不同，并且都不完整：
  - `05` §5.3.6 没有 `GOCACHE`；`07` §7.4.3 没有 `YARN_CACHE_FOLDER`；`10` §10.4.1 和 `11` §11.6.2 又各不相同。
  - 遗漏：pnpm 的 `cache-dir` 与 `state-dir`（`npm_config_cache` 并不改变 pnpm 的元数据缓存位置）；Yarn Berry 默认的全局缓存（需要 `YARN_GLOBAL_FOLDER` 或 `YARN_ENABLE_GLOBAL_CACHE=false`，否则 `YARN_CACHE_FOLDER` 无效）；Corepack 的 `COREPACK_HOME`；node-gyp 的头文件目录；Playwright、Cypress、Puppeteer、Prisma 的下载缓存；uv 的 `UV_PYTHON_INSTALL_DIR` 与 `UV_TOOL_DIR`。
  - 把 `CARGO_HOME` 指向私有目录，会丢掉用户 `~/.cargo/config.toml` 中的镜像、私有 registry 与凭据，私有 registry 的项目会直接失败。

  在 S2 写拒绝之下，这些都会表现为安装或测试失败，而且会被归为 Agent 的失败或 `verify_env_error`。
- 为什么重要：这决定 R1-D11-02 的修复能否在真实项目上运行，SP6 也需要一份明确的待测清单。
- 文档位置：`05` §5.3.6；`07` §7.4.3；`10` §10.4.1；`11` §11.6.2；`14` SP6。
- 期望的回答形态：在 `16` 中建一张“包管理器 × 环境变量 × 只读或可写 × 是否继承用户配置”的唯一表，并写进 SP6 的验收条目。

**R2-D11-04｜次要**
- 问题：
  - Pi 的信任判定会检查**任意祖先目录**中的 `.agents/skills`（`trust-manager.ts:196-207`），而 Tower 的条件信任只对 worktree 执行 `git diff -- .pi .agents`。在 S0 下，Agent 可以写 `<checkoutParent>/.tower-wt.noindex/.agents/skills/`，然后在 `--approve` 下被加载。
  - `11` §11.3.3 先说下列路径“视为 `config.change`（而非 protected）”，紧接着又写“`**/AGENTS.md`……也按 protected 处理”，前后矛盾。
- 为什么重要：涉及信任边界的表述需要精确。
- 文档位置：`05` §5.4.1；`11` §11.3.3、§11.8.1。
- 期望的回答形态：复核时把祖先目录也纳入检查；改正 §11.3.3 的措辞。

### D13 隔离、git 与并发

**R2-D13-01｜重要**
- 问题：端口方案的可行性有四个缺口：
  - (a) 只注入 `TOWER_PORT_BASE` 和 `PORT`。数据库等服务所需的其他端口（例如线框中的“base + 5”）以及 `DATABASE_URL` 这类连接串，在 `VerifyProfile.env.vars` 中无法表达（没有模板语法），大多数带数据库的 Web 项目只能标为 `ports:"fixed"`，并发度降为 1，削弱了多 Goal 并行这一核心前提；
  - (b) 41000 起的端口段落在 Linux 默认的临时端口范围 32768–60999 内，出站连接会随机占用这些端口，导致偶发的 `EADDRINUSE`（Linux 在 M2 交付）；
  - (c) 分配之前不检查端口是否空闲；
  - (d) “项目不支持端口注入”只能在首次验证失败后才检测到。
- 为什么重要：R1-D13-02 的修复决定了并发能否成立。
- 文档位置：`10` §10.19；`07` §7.4.4、§7.13；`04` §4.7.2。

**R2-D13-02｜次要**

### D14 路线图与可验证性

**R2-D14-01｜重要**

## 5. 结论

- **是否所有维度为 100：否。** 最高为 D6 与 D9 的 91，最低为 D5 与 D7 的 70。
- **是否还有可追问的问题：有。** 第 1 轮 123 条中，已解决 101、部分 22、未解决 0。本轮新增与残留追问共 **44** 条：**阻断 2 条**（R2-D5-01 同名 bash 覆盖使 S2 静默失效；R2-D7-01 验证容量在参考硬件上不可行），**重要 26 条**，**次要 16 条**。
