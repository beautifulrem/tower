## Pi v1.2.0 核实（`packages/coding-agent/src/`，`git show v1.2.0:<path>`）

**用户扩展怎样取代内置 MCP**（R87-D11-01 的依据）：
- CLI 的内置扩展表把 `mcp` 登记为 `replaceable: true, builtin: true`，注释写明注册 `codemode`、`tool_search` 或 `/mcp` 的扩展（如第三方 MCP 扩展）取而代之（`extensions/index.ts:9-13`）。
- `InlineExtension.replaceable`：另一个扩展在加载时注册了同名的工具、命令或标志时略去它，工厂仍会运行（`core/extensions/types.ts:2058-2065`）。
- 资源加载在扩展加载完成后调用 `omitReplacedExtensions`（`core/resource-loader.ts:709`、`:785`）：以全部非 `replaceable` 扩展的 `tool:`/`command:`/`flag:` 名字为占用集合，重名的可取代扩展被略去；被略去的是 `builtin:` 路径时只留一条警告，写出取代者与名字（`:115-150`；`BUILTIN_PATH_PREFIX = "builtin:"`，`core/source-info.ts:15`）。SDK 以 `builtin: true` 提供的条目同样以 `builtin:<name>` 加载并带上 `replaceable`（`:380-382`、`:727-743`）。所以 Tower 在 SDK 下提供的内置 MCP 同样可被取代。
- 内置 MCP 在加载时只注册命令 `mcp`（`extensions/mcp/index.ts:1260`；没有 `registerFlag`）；MCP 工具在连接之后才注册（`:387-460`），连接从 `session_start` 开始（`:1114`）。所以在 v1.2.0 中 “取代内置 MCP” 就是 “另一个已加载的扩展注册了命令 `mcp`”。
- Pi 文档：注册 `/mcp` 的扩展（如 `pi-mcp-adapter`）取代内置 MCP，Pi 不再读 `mcp.json`、不再连接其中的服务器（`docs/mcp.md:264-266`）。
- Host 在会话创建之前就能读到最终的扩展集合：`createAgentSessionServices` 返回的 `resourceLoader`（`core/agent-session-services.ts:78`，`:154` 完成加载）的 `getExtensions().extensions[]` 带 `path` 与 `commands`（`core/extensions/types.ts:2268-2284`）。

**其余**：
- `pi.registerMcpServer` 注册的服务器经同一连接与工厂（`extensions/mcp/index.ts:343-363`）。
- 默认工厂对 `command`、`args`、`cwd` 只展开 `~`，对 `env` 的值解析 `${NAME}` 与 `!cmd`（`extensions/mcp/runtime.ts:98-122`，`core/mcp-servers.ts:84`）。

## R87-D11-01：第三方 MCP 扩展取代内置 MCP

**决定**：沿用 ADR-187 的来源自检，取最严的一支——这类扩展在 M1 中不可用。

**唯一定义**：`05` §5.3.5 “内置 MCP 的来源自检”（L433；骨架代码 L366–L369）。
- 时机：资源加载之后、会话创建与 `session_start` 之前，因此在任何 MCP 服务器启动之前。
- 判定：已加载的扩展中注册命令 `mcp` 的，只能是路径为 `builtin:mcp` 的 Tower 条目（带 `towerMcpTransport`）。
- 不符时不开 Run → `paused(prepare_failed)`，卡片 `启动失败：扩展 <名字> 取代了 Pi 内置的 MCP（注册了 /mcp），Tower 对 MCP 服务器的保护在它之下不生效；请在 Pi 设置中禁用该扩展`。
- 用户设置 `-builtin:mcp` 而没有别的扩展注册 `/mcp` 时没有 MCP，照常开 Run；不加载扩展的 Run（清单确认之前、高风险 Goal）不受影响。
- 静态清单的文本扫描另标出可能注册 `/mcp` 的扩展，确认卡片写 “该扩展取代 Pi 内置的 MCP，M1 中不可用：启用期间 Tower 不能启动运行”（`05` §5.10）。
- 扩展不经 `/mcp`、自己启动的子进程（含它自己连接的 MCP 服务器）仍属 `11` §11.8.2 残余中 “用户确认的那段代码的行为”，写明。

**同步**：
- `11` §11.3.4 MCP 一条（L220）、§11.8.2 清单行（L608）与残余（L612）、T4、T16：陈述限定为内置 MCP 生效时；

- `04` §4.8.11 卡片示例、§4.18.1 第 1 步确认卡；`00` §0.5.1 新增一行（L103）；README 的例外补半句；

## R87-D11-02：空工作目录与相对路径

**唯一定义**：`11` §11.3.4 “stdio MCP 服务器的空工作目录与相对路径”（L222），`05` §5.3.5 引用。
- **(a) 目录**：`~/.tower/mcp-cwd/` 由 Tower 拥有。Supervisor 每次 `host.spawn` 时、Host 启动之前删除并重建为空目录，删除不跟随符号链接。
  - 删去 “Tower 之后从不写入、不清空”。
  - 它仍在硬底线（写）之内，三种沙箱都拒绝读写。
  - 写进其中的东西不越过一次 Host 的生命周期；打包模式下同一 Host 的其他 Goal 在这期间仍可能受影响，如实写明。
- **(b) 相对路径**：经 `towerMcpTransport` 启动的 stdio 服务器（含扩展注册的）的工作目录由 Tower 求出。
  - 门禁把它们的工具参数中的相对路径分别以该工作目录与 `roots` 为基准解析，任一结果落在硬底线之内即 forbid。例如绝对 `cwd` 在主检出之内时，相对路径的读写与其他对主检出的读写一样 forbid。
  - 沙箱外工具的读写方向门禁无法判定，路径扫描中只禁止写的位置一律按写处理（偏严；此前 “按其读写方向” 没有定义方向从何而来）。
  - 用户扩展工具与 HTTP 服务器的工具没有已知基准，照旧至少 ask。
  - 不含 `/` 的单个文件名仍不当作路径，尽力而为的限制不变（T7/T26）。

**同步**：
- `05` §5.3.5 stdio 工作目录一条（L438）；`11` §11.3.3 第 3 条硬底线、§11.3.4 路径检查 (3)（L221）；`06` §6.6.1 目录布局；

## R87-D5-01：全局根查询的时限

**唯一定义**：`05` §5.10 “查询的时限与失败”（L1337）。
- Supervisor 的每次查询自有 **60 s** 时限，到时终止该子进程（连同进程组），按出错处理；出错或超时 → 全局根 “未知”，不启动 Host。
- **Run 中**：清单计算属于准备第 ③ 步（Host 启动之前，计入 120 s，其间命令同 ③），失败 → `paused(prepare_failed)`。
- **Run 之外**（首次运行第 1 步的确认卡片、设置页 “重新读取” 之后的重新计算）：受影响的包写 “无法确定是否已全局安装（全局根查询出错或超过 60 秒）” 并附 `[重试]`，不列为 “未安装”，其余条目照常确认。
- 写明它同样阻断不加载扩展的 Run，是有意的取舍（观察 13）。
- 取代 ADR-214 的 “与 Pi 一样不另设时限，由 120 s 的准备时限兜底”。

**同步**：
- 准备步骤：`05` §5.3.1、`10` §10.3.1 ③、`16` §16.1.1 `ready` 行与 `pauseReason` 行、`06` §6.2.4 流水线与 F4b、`03` §3.2.1 `prepare_failed` 入口；

不再列 “例外”。`06` §6.2.1（L221，唯一定义）改为两份清单，合起来覆盖 DDL 的全部表：

   - `projects`、`project_checkouts`、`project_local_files`、`project_benign_targets`、`bindings`、`sessions`；
   - `needs_you`：所属 Run 已被 abort 或兜底超时、仍可作答的 `question` 条目，与 `question_timeout` 的阻塞问题，都原样保留，连同推迟与级别；

## §5 观察

1. **`pendingHandBack` 等待时改写继续目标的命令**：`16` `Goal.pendingHandBack`（L45）写明这类改写照常写入但不改变结果（第 1 步先执行交还的选择）；`04` §4.6.7 写明这类选项（如 “按当前状态送去验证”）置灰并提示。
2. **`goal.abandon`**：`06` 从 `paused(human)` 放弃时另清除 `human_checkout`（目录按 `10` §10.8.4 保留）；“只允许这一种写法” 改为 “DDL 的 CHECK 要求离开 `paused` 时这些列为空”。
3. **ceiling**：
   - `05` §5.3.5 主防线与 `10` §10.1 改为 `<全部 wtRoot>`；
   - `~/.tower/mcp-cwd/` 不在 ceiling 之下，写明可能向上发现主目录中的仓库，那不是 Agent 可写的位置。没有把 `~/.tower` 加入 ceiling：要同步十余处取值写法，而这不是越界。
4. **解析规则的概括**：`05` §5.3.5 与 D53 改为 “`command`、`args`、`cwd` 只展开 `~`；`env` 解析 `${NAME}` 与 `!cmd`，不展开 `~`”。
5. **代码片段**：`05` §5.3.1 改为 `createMcpExtension({createTransport: towerMcpTransport})`。
6. **“落在 Agent 可写位置之下” 的判定**：
   - 按 `realpath` 比较，大小写不敏感的卷按该卷的规则比较；
   - 集合加上任一 `<wtRoot>` 与 `~/.tower/` 之下的一切（含 Scratch 的工作目录与 `_verify`、`_inspect`、`_human`；`mcp-cwd` 本身除外），即评审建议的简单做法；
   - 文字改为 “Tower 的工作区或数据目录之下”，C21、G46 (bk) 同步。
7. **`00` 的措辞**：L100 补 `XDG_DATA_HOME`、`pnpm_config_*` 的限定（“通常…相同”）；L99 与 `05` §5.3.6 的提示改为 “MCP 服务器与扩展的子进程”。
8. **重新读取之后的过渡**：`05` §5.3.6 写明正在运行的 Host 不重启、继续用旧值，打包模式下并入它的 Goal 同样用旧值，这期间新旧两个值同时在用（接受混用）；“整台机器同一个” 带上这一限定；`04` §4.15 同步。
9. **扩展注册的 MCP 服务器**：`05` §5.3.5 写明规则同样适用，只在运行时显示 `failed` 与文字，不出现在静态清单上；`11` §11.3.4 的相对路径规则同样覆盖它们。
10. **Node 提示**：`04` §4.18.1 第 1 步与 §4.15 各补一处引用。
11. **`roots` 与服务器自己的行为**：`11` §11.3.4 在 “以 `roots` 为根” 的建议处写明服务器按 `roots` 在卫星中运行程序仍属 T16 的残余，ADR-214 没有改变这一点。
12. **写法**：`10` §10.7.1 验证类 landmark 统一为 “由 Projector 追加”；`16` §16.1.13 第 86 轮一行把 `projections` 与沿用的运行时表分开写。
13. **查询失败阻断不加载扩展的 Run**：并入 R87-D5-01，`05` §5.10 写明是有意的取舍，`00` §0.5.1 同步。
14. **`resolvePinHits`**：纳入 `06` §6.3 “载荷中的路径集合”（`{path, action}` 数组），适用的事件补 `human.decision`（只有 `hand_back` 的这一个字段）；`16` §16.1.14 `human.decision` 行写明 16 KB 与 `06` §6.3；lint (i′) 5 个事件。没有写 “不适用”：命中数没有上界。
15. **从清除之前的备份恢复**：`09` §9.12.4 “清除之后仍可能存在的副本” 补一条——在恢复的库上重建会因缺少路径集合文件而停止并列出它们；对这些 Goal 重新执行清除（尚未终结的先放弃）后再重建。

## 偏离与未决

- **代码智能类 MCP 服务器的相对路径**：按方向未知时偏严的规则，未写 `cwd` 的服务器，其工具参数中的相对路径解析后落在 `~/.tower/mcp-cwd/`（写入属硬底线），一律 forbid。以 `roots` 解析相对路径的代码智能类服务器因此须写一个指向你自己目录（不在仓库检出与 `~/.tower` 中）的绝对 `cwd`。
  - 这是可用性代价，写在 `00` §0.5.1 与 `11` §11.3.4；
  - 另一选择是对只禁止写的位置在方向未知时 ask，但那样硬底线对相对路径就不成立，未采用。
- **取代内置 MCP 的扩展在 M1 中不可用**：装着 `pi-mcp-adapter` 一类扩展的用户，确认清单之后在禁用它之前不能开 Run（清单确认之前与高风险 Goal 不受影响）。比 “登记为残余” 更严，与 ADR-187 对同名 Tower 工具的处理一致。
- **打包模式下的空目录**：清空只发生在 Host 启动时，同一 Host 承载的多个 Goal 在其生命周期内共享该目录。经批准的写入（只剩不含 `/` 的单个文件名这一条路径）仍可能影响同一 Host 中之后启动的服务器；已写明，未加新机制。
- **重建的 (1) 清单偏短**：只列出确有事件族承载的表，其余沿用（见 R87-D6-01）。若之后要让更多表可由事件重放，先在正文中写明它们的事件，再移入 (1)。
- **没有新增针对重建的 G 场景**：评审没有要求；`06` §6.2.1 的两份清单与 `16` §16.1.13 的旧说法由 (D) 守住。
- **评审 §3.1 的两条 lint 建议未采用**：理由见 `round-87-lint.md`。
