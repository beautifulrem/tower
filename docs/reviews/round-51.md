### D11 安全与自主度

**R51-D11-01｜重要**（`11` §11.7.0 投递表仍把“项目 `.npmrc` 中的认证行”列为注册表认证的来源）

- **问题**：
  - `11` §11.7.0 的标题是“机密投递（唯一定义，ADR-159）”。其投递表 L438 一行写：“注册表认证（`~/.npmrc`、**项目 `.npmrc` 中的认证行**）｜Tower 不保存；安装器第 1 阶段每次运行时读取……（ADR-166）”。
  - 同节 L425 的正文、`11` L407 与 L420（ADR-167“npmrc 的信任边界”）、`05` L403、`06` L234、`16` L1052，以及 `16` L376 的“被取代的说法”表，都写的是另一回事：**只读用户级 `~/.npmrc`，项目 `.npmrc` 的认证行不读取**。
- **为什么是重要**：投递表自称唯一定义。照这一格实现，带网络、能访问私有注册表的拉取阶段会采用仓库控制的认证行。这正是 ADR-167 要排除的一类后果：由仓库内容决定 Tower 使用哪个凭据、发往哪个主机，其中的变量引用还会按用户登录环境展开。修复只需改一格，但这一格与安全不变式直接相关。
- **文档位置**：`11` L438；对照 `11` L407、L420、L425，`16` L376、L1052，`05` L403。
- **期望的回答形态**：L438 第一列改为“注册表认证（只限用户级 `~/.npmrc`；项目 `.npmrc` 的认证行不读取，ADR-167）”。

**R51-D11-02｜重要**（Agent 可读的净化副本与 Scratch 的检出读允许，都没有排除 Tower 自己已能识别的凭据形态）

- **问题**：
  - **`$GS/gitconfig`**：`11` L333 规定，`~/.gitconfig` 的净化副本放在 Agent 沙箱可读的 `$GS` 中，生成规则只有“去掉 `credential`、`include`、`core.*Command` 类条目”。可是 Tower 在 `10` L80、`16` L509、`11` L440 中把下列内容判定为凭据：
    - `http.extraHeader` / `http.<url>.extraHeader` 中的 token；
    - `insteadOf` 替换目标中的 userinfo；
    - URL 中的 userinfo。
    - 这些键都不在删除清单内。用户全局配置中有这类值时，它们会原样进入 Agent 可读的副本。
  - **`$GS/npmrc`**：`16` L1052 的生成规则同样是删除清单（`_authToken`、`_auth`、`_password`、`username`、`node-options`、`script-shell`）。可携带凭据的代理 URL userinfo、客户端证书与私钥类配置项不在清单内。
  - **Scratch**：`11` L387 规定真实检出“读允许”，例外只有清单中的机密条目、密钥路径表与 `~/.tower/**`。仓库元数据中的远端配置（含 URL userinfo 或认证头）不在例外中。Goal 对用户检出整体读拒绝（ADR-082），Scratch 没有对应规则。
- **违反的不变式**：`11` L17 硬规则 1“凭据本身不在 Agent 可达范围内”；`11` §11.7.0“M1 中 Tower 不会自动把机密交给 Agent 可影响的进程”。上面三处都是由 Tower 自己构造、自己声明可读的位置，凭据形态的值会留在其中。
- **为什么是重要**：实现者照删除清单实现即违反上述不变式；而判定这些凭据形态的规则在 `10` §10.1.2 已经写好，只是没有用到这里。
- **文档位置**：`11` L333、L387、L17、L440；`16` L509、L1052；`10` L80。
- **期望的回答形态**：
  - 净化副本改为**白名单**（只保留列明的键），或者在删除清单之外，再以 `10` §10.1.2 / `16` L509 的凭据判定剔除命中的键；对 `$GS/npmrc` 同理。
  - Scratch 的读拒绝例外中加入仓库元数据中的配置文件（或整个 `commonDir`），与 Goal 的检出读拒绝口径一致；如果有意保留，应作为残余登记到 T 表。
  - 在 G46 中各补一组用例。

**R51-D11-03｜重要**（改变安全边界的设置可经“未单列”的命令在远程完成）

**R51-D11-04｜次要**（`mark_secret` 之后，已在卫星或检验检出中的副本如何处理没有定义）

- **问题**：

### D7 诚实与验证

**R51-D7-01｜次要**（`full` 与 `decisive` 指纹不一致时直接回到 `verifying`，绕过“来源不明 → `external_change`”）

- **问题**：
  - `07` L277：“`full` 的结果与紧邻的 `decisive` 结果不一致时，以 `full` 为准，记录 `anomaly{detector:"stat_cache_mismatch"}`……并**按 I2 回到 `verifying`**”。
  - ADR-128 之后 I2 分两路：可归因的变化 → `verifying`；来源不明 → `paused(external_change)`（唯一定义在 `10` L399；`03` L109、`16` L400、`06` L262 引用）。`10` L396 还强调“来源不明的内容不会先被验证或评审，再等人决定”。
  - stat 检查漏掉的内容变化，按定义没有任何已知来源。`07` L277 却指定了 `verifying` 这一路。ADR-128 的待改清单没有包含 `07` §7.3.2。
- **为什么是次要**：只在 stat 缓存失配这一异常路径上出现，人仍要重新评审变化的单元；但照文实现，来源不明的内容会先被验证，并作为 Agent 的内容进入评审，违反上述唯一规则。
- **文档位置**：`07` L277；`10` L396、L399；`03` L109；`16` L400；`15` ADR-128。
- **期望的回答形态**：`07` L277 改为“……并按 I2 与 `external_change` 的分界（`10` §10.3.1）处理：变化路径按归因表分类，来源不明者进入 `paused(external_change)`”。

**R51-D7-02｜次要**（评论 `addressed` 的 Claim 来源与 `acknowledged` 的触发条件相同，却能满足验收闸门）

- **问题**：
  - `05` L1133：`acknowledged` =（a）某次 `log` 的 `evidenceRefs` 包含 `comment:<key>`，或（b）文本中出现该 key。
  - `05` L1134：`addressed` 有两个来源，其中 🤖 来源是“模型在 `log.evidenceRefs` 中引用了该评论”，与 `acknowledged`（a）是同一个条件。同一事件究竟进入哪一个状态无法判定。
  - 验收闸门只看状态：`requiresChange` 的评论“验收前须 `addressed` 或被人关闭”（`02` L541、`03` L137、`05` L1099、`16` L211），远程验收条件 ③（`06` L971、`16` L868）也只看是否“未关闭”。于是 Agent 的一次引用（Claim）就能解除“必须修复”的闸门，不需要任何 Fact。
  - `04` L499 与 `12` L694 要求两个来源“分开显示”，而 `08` L704-706 的摘要把两者合并计数（“2 条必须处理的评论中 1 条已处理”）。
  - 另外，`05` L1133 把界面词写作“已确认”，`04`/`12` 写作“已回应”。
- **为什么是次要**：验收仍由人做，且评审中显示 `┆ Agent 称已处理`；但闸门本身被一条 Claim 满足，与“Agent 的说法只是声明”（README 主张 3、`07` H3）相抵触，实现会分歧。
- **文档位置**：`05` L1099、L1133-1134；`02` L541；`03` L137；`16` L211、L868；`06` L971；`04` L499；`12` L694；`08` L704-706。
- **期望的回答形态**：
  - 闸门只接受 ⚙️ 来源的 `addressed`（hunk 已变）或人关闭；🤖 来源只显示为说法，不满足闸门；
  - 给 🤖 来源一个与 `acknowledged` 可区分的条件（例如 `log{kind:"addressed"}` 一类的显式声明），或者直接取消这个来源；
  - `08` 的摘要按来源分开计数；界面词统一为“已回应”。

### D9 视觉设计与美观

**R51-D9-01｜次要**（计划步骤与发现用 `✓`、超时默认用 `HumanStamp`，与 `12` 自己的诚实语法冲突）

- **问题**：
  - **计划步骤**：`04` L317 线框为“计划（你批准的 v2）· S1 ✓ S2 ✓ S3 ✓ S4 ◆ S5 ○”。`02` L326-331 的 `PlanStep` 没有状态字段，“当前步骤”只来自 🤖 最近一次 `log` 声明的 `step`（`02` L343）；所以“已完成”是 Agent 的说法。`12` L223 规定说法“永不使用 verified；不带 ✓”。全文没有定义计划步骤的字形集（`04` L347 只写“一行步骤字形”）。
  - **发现**：`04` L694 诊断时间线中的“✓ 发现 1”也属于同一情形（Finding 是说法）。
  - **超时默认**：`12` L656 规定“超时默认显示为 `你 · 默认`”，`04` L1031 的线框与 `08` L624 的“Human（超时）”与之一致。但 `12` L234 说“`HumanStamp` **只用于你亲手写的转向与回答**”，`12` L863 #26 的理由是“把 Tower 的话显示成你说的话，违反诚实语法”。数据侧记为 `resolution.by = "timeout"`（`08` L450）；对低风险问题，默认值就是 **Agent 推荐的选项**（`08` L428）。于是一条由计时器套用的 Agent 推荐，被盖上“你”的印章。
- **为什么是次要**：属于界面语法问题，不影响状态与判定；但它正好落在 `12` 用来区分 Fact / Claim / Human 的那几个字形上，同一文档内的两条规则互相矛盾。
- **文档位置**：`04` L317、L347、L694、L1031；`12` L223、L234、L656、L863；`08` L428、L450、L624；`02` L326-343。
- **期望的回答形态**：
  - 为计划步骤定义字形集：“Agent 称已完成”用说法样式（例如 `┆✓` 或空心字形），只有与 Fact 交叉校验一致时才换成事实样式；“发现”同理；
  - 超时默认改用 `⚙ 超时默认` 一类的系统印章（实线发丝框，与 `Tower 注入` 同族），删去 `12` L656 的“你 · 默认”；`04` L1031、`08` L624 同步改。

### D12 记忆与学习

**R51-D12-01｜次要**（`09` 数据清单仍写影子检查点 ref 在用户仓库中）

- **问题**：`09` L482 的数据位置表写“影子检查点 ref｜**用户仓库的 `.git` 中**，`refs/tower/<goalId>/*`｜……180 天后全部删除”。但 `10` L21 规定“Tower **不在其中保存任何 `refs/tower/*`**（R4-D13-08）：检查点、pin、基线快照都只在影子或镜像中”；`10` L244、`06` L1106 也一致。只有开启“保留审计地标”（默认关）时，地标才写入用户仓库（`02` L97）。
- **为什么是次要**：这张表是隐私与数据清单的对外说明，也是清除功能的依据；照它实现，会到用户仓库中寻找并删除并不存在的 ref，或误以为用户仓库中留有快照。
- **文档位置**：`09` L482；`10` L21、L244；`06` L1106；`02` L97。
- **期望的回答形态**：改为“影子检查点 ref｜`~/.tower/goals/<goalId>/git/<projectId>.git` 中的 `refs/tower/<goalId>/*`；开启‘保留审计地标’时，地标另写入用户仓库（`10` §10.6.2）”。

### D13 隔离、git 与并发

**R51-D13-01｜次要**（撤销外部改动的 safety 检查点在恢复之前还是之后，两处矛盾；`take_human` 的写回机制只覆盖 T0→T1）

- **问题**：
  - **撤销的可恢复性**：
    - `10` L404 写 `restorePaths(归因基线, E)`“（§10.8.1：只恢复 E 中的路径，**先做 safety 检查点，可再撤销**）”。
    - 但它引用的定义 `10` L787 写“……其他路径不动；不调整卫星的 git 状态；**完成后**做一个 `safety` 检查点”；`06` L885（“随后 `safety` 检查点”）、`15` L868 同。
    - 在非 `running` 状态检测到外部写入时，Tower 不做任何检查点（`10` L396，只暂停）。若 safety 在恢复之后才做，被撤销的内容在任何检查点中都不存在，撤销不可逆。`goal.external_change.revert` 又允许在手机端执行（ADR-125，`16` L893）。
  - **`take_human` 的写回**：
    - `10` L895 规定“以你的版本为准”时“卫星**整体**置为 T1，外部写入被丢弃”。
    - 但写回机制只有第 7 步“按 `git diff --name-status -z T0 T1` 逐项”（`10` L903），崩溃续写同样只写其余路径（`06` L141）。E 中不在 T0→T1 差异内的路径会保留来源不明的内容，而第 8 步的检查点为 `author:"human"`，`external_change` 也已解除。
    - 这与 ADR-122 的“任何选项都不会把外部写入记为人的改动”（`10` L894、`06` L889）相抵触。
- **为什么是次要**：两处都是机制与声明的结果不一致：前者决定被撤销的内容能否找回，后者决定来源不明的内容是否会被记为人的改动。撤销与以你为准都是人显式选择的出口，所以不列为重要。
- **文档位置**：`10` L396、L404、L787、L894-903；`06` L141、L885、L889；`15` L868；`16` L893。
- **期望的回答形态**：
  - `restorePaths` 的定义改为“恢复**之前**先做 safety 检查点（记录被撤销的内容），完成后可再做一次”；或者删去 L404 的“先做 / 可再撤销”，并在撤销确认文案中写明不可恢复。
  - `take_human` 的写回范围写为“T0→T1 的差异 ∪ E”：E 中的路径按 T1 的版本写出或删除；崩溃续写使用同一集合。

  - **第 50 轮核验**：R50-D15-01 已解决；R49-D15-01（W11 部分）已解决；未解决 0。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 175，(v) 95 条命令，(e) 144 对，(r′) 30 对）；
    - Pi v1.2.0 复核约 240 条，只有 R51-D5-01 一条用户可见的说法不成立；

  - **不扣分的观察**：
    - **Pi 的小出入**：
      - `10` L761/L763 写作 `SessionManager.createBranchedSession(…)`，实际是实例方法，会把该 manager 切换到新文件。新文件头沿用旧 `cwd`，写在原会话目录中；Tower 恢复时一律带 `cwdOverride`（`05` L280），所以不影响行为。Best-of-N 属于 M3，届时注意 N 次调用的 `parentSession` 链。
      - `11` L273 把 `shellPath` 列为 `createBashToolDefinition` 的参数；传入 `operations` 时 Pi 会忽略它，`05` §5.3.5（R4-D2-01）已写明由 Tower 自行解析，结果相同。
      - `05` L375 的 `getShellEnv` 不在 v1.2.0 包入口导出，Tower 需要自己实现一个等价函数（Host 环境本来就是白名单）。
    - **`take_over` 在依赖物化（②）期间的返回值**：`16` L23 只写了 ③ 中返回 `E_BUSY`；`03` L54、`06` L888、`10` L376 一致写为准备中一律 `E_BUSY`（守卫缺标记时先 `E_STATE`）。读法唯一。
    - **`verify()` 只读入 `seeded` 条目**：`07` L395 的 `readSeededLocalFiles` 与 `16` L513 的“对清单中**每个**条目重新判定”范围不同；未批准的条目本来就不复制，差别只在内容命中通知出现的时机。
    - **线框中的通配条目**：`04` L571、L1288 的 `config/dev-certs/*.pem` 与“每个条目一个 `path`”的模型不符；按模型实现即可，线框可改为两条具体路径。
    - **本地文件命令的边缘结果**：重复 `add`、对已取消标记的条目再次 `unmark_secret`、文件不可读时 `unmark_secret` 绑定什么哈希，都没有写明，属于常规的守卫实现。
    - **`waitReason:"manual"`**：`02` L152、`16` L22、`12` L398 登记了它，但没有写入时机。目前没有路径会产生它，可以删除，或写明“项目关闭自动开始”时使用。
    - **镜像首次建立与项目锁的先后**：`10` L304 写“Project 级互斥锁内”，L376 的顺序写“镜像首次建立 → 等待项目锁”。实现时首次建立自然需要互斥，可统一措辞。等待项目锁计入 15 分钟的仓库准备时限，并发时可能使后到的 Goal 进入 `prepare_failed`（需人工 `resume`），建议在 `10` 写明这是有意的取舍。
    - **`project.remote.recheck` 与已 `prepare_failed` 的 Goal**：重新判定通过后不会自动解除这些 Goal 的暂停，符合“`prepare_failed` 不 `autoResume`”的规则，卡片可提示“重试相关目标”。
    - **“用户显式放行的变量”**：`05` L402 的白名单行允许它们进入 Host 与 bash 环境，但没有命令，也没有机密检查；这属于人的显式决定，不构成“自动交出”，可补一句它在哪里设置、是否经过 `11` §11.7 的机密检查。
    - **上游代理的 Basic 凭据**：`05` L403 把用户代理变量交给 Host（Tower 自身进程，属于继承），T33 的残余列表没有点名这一项，可补登记。
    - **“可证明完成”**：`04` L1071-1072 的措辞全文一贯，`07` L470 在机密文件情形下有限定；属于用词，不扣分。
    - **`integration.performed`**：`10` L1238 的“`integrated` 判定”用途属于 M2；M1 的判定来自 `local_merged`，可加 M2 标注。
- **设计是否完成：近期修订的区域已收敛，较早定稿的安全与生命周期细节还有缺口。**
  - 本地文件（ADR-165–175）、继续目标、准备阶段、git / LFS 的主干规则经本轮抽查一致，第 50 轮的漏改已补齐。
