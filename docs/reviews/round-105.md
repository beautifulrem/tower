## 1. 总评

**第 104 轮的 7 条条目都按所问关闭**（核对见 §3）：
- 7 条都在唯一定义处落地，引用处改为引用；第 104 轮 §5 的 12 条观察全部落地。
- 其中三处修法本身带出新的分支：
  - **R104-D5-03**：Host 自己安装分发器是对的，但只在 “Host 环境中有代理变量” 时安装（C43 还断言不安装）。Pi 的每个 CLI 入口都无条件安装，并带固定的选项与你的空闲超时设置；SDK 路径又会加载 undici，使没有代理的 Host 落在 Pi 有意避开的混用状态（R105-D5-01）。
  - **R104-D5-01、R104-D5-02**：标注改由 Host 报告、扩展注册的 provider 不注入，这两件事合在一起时，标注只有两种文字，对扩展处理认证的 provider 两种都不成立；“不注入” 只在第一个会话创建之后做一次，覆盖不到 Pi 明确支持的加载之后的注册；代价一句比实际窄（R105-D5-02）。
  - **R104-D6-01、R104-D6-02**：
    - 新写的 “只读期间 Supervisor 启动” 推迟了全部中间状态检查，而存活 Host 中可能仍有进行中的 Run；
    - 自检把 “任一卷不足 2 GB” 变为只读启动，但解除只复查 “发生过 `ENOSPC` 的卷”，这一集合在新进程中为空（R105-D6-01）；
    - 准备阶段本身遇到 `ENOSPC` 时，F8 与 F4b 给出两个去向（R105-D6-02）。

**对本轮重点问题的回答**：

- **标注只取 Host 的检查：接受**。
  - 判定依赖所在进程的环境与命令缓存，只在 Host 中求值是唯一与实际注入一致的做法；不另起进程，也避免在 Host 之外再执行一次你的 `!` 命令。
  - 代价（首次运行与重启之后只写条件句）如实登记。扩展处理认证的 provider 没有对应的标注，见 R105-D5-02 (a)。
- **打包的分组：接受，比会话结束时注销更简单且对 `riskTier=high` 成立**。
  - 同一 Host 中的会话总加载同一扩展集合，扩展的 provider 跨会话保留（`agent-session-services.ts:158-181`；会话结束不注销）不再越过扩展集合的边界。
  - 专用模式下扩展集合变化时先让旧 Host 退出，写法成立。
  - **对内存预算的影响**：§13.8.1 的 Host 一行是按进程的预算，单独占一个 Host 的高风险 Goal 落在专用 Host 的同一预算内，不超出；准入记账中打包时每 Goal 的 `h = p95(打包 Host)/K` 对未满的 Host 偏低，这在 ADR-232 之前（Goal 数不是 K 的倍数时）就存在，分组使它更常见，量级约每个未满的 Host 0.1 GB，记为观察 2。
- **分发器是 Pi 未导出代码的副本：接受这一做法，安装条件与选项见 R105-D5-01**。
  - D63、C43 的升级复核成立。
  - 替换全局 `fetch` 与各路径的关系成立：
    - Pi 的 HTTP 类 provider 与 HTTP 类 MCP（`streamable-http.ts:211` 在构造时取全局 `fetch`）在 “任何模型请求与 MCP 连接之前” 安装的前提下都经过它；
    - Bedrock 只在按自己的规则求出代理时自建 agent，与终端相同；
    - stdio MCP 服务器经 `mcpBaseEnv` ⑤ 拿到代理变量；
    - 扩展自己的网络代码与终端中一样受全局分发器影响。
  - `NO_PROXY` 由 `EnvHttpProxyAgent` 读取，成立；它不读 `ALL_PROXY`，与终端中的 `pi` 相同，不是差别。
  - `httpProxy` 不读取：接受，已在 `00` L114 登记。
- **只读启动时推迟中间状态检查：接受原则，范围与存活 Host 见 R105-D6-01**。推迟的检查中有不写数据库的清理（死去 Host 的即时投递文件、`tmp/`、残留的 Agent 后台进程），它们在只读期间同样可以、也应该执行。
- **`ENOSPC` 之前已写入的失败按标准失败计：接受**，如实登记，窗口很窄。

**ADR-232 的其余写法成立**（§3.3）：
- `getRegisteredProviderIds()` 只列出扩展注册的 provider，跳过它们不影响内置与 `models.json` 的判定；
- F8 的解除集合由数据库求出，与 §6.1.4 第 5 项、ADR-207 一致；多原因的 Goal 解除后保持暂停；
- 取消的验证按 §6.1.6 `verifying` 一行重跑，机会式验证丢弃，中止准备的 Goal 按 `10` §10.3.1 启动恢复；
- `12` §12.6.5 卡片的 `自动恢复` 条件，`12` §12.8 只引用 `08` §8.10.5；横幅不是覆盖层、位置与 Tab 次序（`04` L184）；
- 租约只读到本机接管为止（`10` L259、`06` L184）；G46 的同机与异机两组。

    - `allowH2: false`、`proxyTunnel: true`、连接尝试时限 2 s（`core/http-dispatcher.ts:86-96`；`:5-6` 的注释：Node 默认的 250 ms 会中断高延迟线路上的正常连接）；
    - `bodyTimeout`/`headersTimeout` 取你的 `httpIdleTimeoutMs` 设置（`main.ts:875`、`interactive-mode.ts:2063, 5014`、`settings-manager.ts:900-901`；`disabled` 为 0）；
    - 一个吞掉 undici 内部 `error` 事件的监听（`:59`），以及 `undici.install()`，使 `fetch` 与分发器出自同一份 undici（`:100-112`，替换的不只是 `fetch`）。
  - 没有代理变量的 Host 也不是 “Node 的默认状态”：`settings-manager.ts:11` 引入 `http-dispatcher.ts`，后者引入 undici，所以 SDK 路径同样加载它；undici 8.10.2 加载时若全局分发器尚未设置，就装上自己的默认 `Agent`，并以包装器写入 Node 内置 `fetch` 读取的旧版符号（`lib/global.js`）。这正是 Pi 用 `undici.install()` 避开的 “内置 `fetch` 配 npm undici 分发器” 的混用状态，而该默认 `Agent` 允许 HTTP/2，Pi 有意关掉了它。结果还取决于 Host 中谁先触及 `fetch`，并不确定。
  - 有代理时，“同一做法” 是否包括这些选项、空闲超时读不读你的设置，正文没有写；`httpProxy` 写明不读取，`httpIdleTimeoutMs` 一字未提。
- **为什么是次要**：失败明确可见（请求报错，按 F6/F7 处理），不丢数据，不放宽任何沙箱，Host 环境不变。但它使 “与终端中的 `pi` 一样” 在没有代理的默认网络中不成立：照正文实现，Host 的模型请求以与终端不同的协议与时限发出，实现者也无法从正文判断有代理时取哪组选项。
- **后果的类别**：
  - 高延迟线路上终端中的 `pi` 正常、Tower 的连接被提前中断；
  - 在终端中关掉空闲超时、使用慢速本地模型的用户，Tower 的请求在 300 s 无输出时失败；
  - 没有代理的 Host 中，模型请求经 HTTP/2 与另一份 undici 发出，出现终端中没有的协议层差别。
- **文档位置**：`05` L474、L1449（D63）、L1505（C43）；`00` L114；ADR-232 R104-D5-03 一条。
- **期望的回答形态**：在 `05` L474 的唯一定义中改一句：
  - Host 启动时**总是**安装（没有代理变量时 `EnvHttpProxyAgent` 即普通的 agent），选项与 Pi 的 `configureHttpDispatcher` 相同，并同样调用 `undici.install()`；
  - 写明空闲超时取你的 `httpIdleTimeoutMs`（经 Tower 的受保护设置读取），或登记为不读取，与 `httpProxy` 同列于 `00` L114；
  - C43 改为两种情形都断言已安装、选项与 Pi 相同。

**R105-D5-02｜次要**（扩展注册的 provider：标注没有第三种结论；“不注入” 只在一个时刻执行；代价一句偏窄）

- **问题**：
  - **(a) 标注**：
    - `11` L517：Host 报告 “每个有导入密钥的 provider 一项：凭据是否来自你的 Pi 配置”，模型选择器写 `已有你的 pi 配置中的凭据，Tower 用它` 或 `Tower 用导入的密钥`；ADR-232 说新增的只有 “两种标注文字”。
    - 对 `getRegisteredProviderIds()` 列出的 provider，Tower “不注入导入的密钥……认证由该扩展自己处理：每次检查都跳过它们”。这时两种文字都不成立：跳过的 provider 报告什么没有写，最自然的实现报 “不是来自你的 Pi 配置”，显示 `Tower 用导入的密钥`，而 Tower 恰恰没有用它。
    - 打包的分组下，加载扩展的 Host 与不加载扩展的 Host（高风险、清单待确认）对同一内置 provider 的实际来源不同；Supervisor 只保留 “最近一次”，标注随最后报告的 Host 翻转。
    - G46 (d) 第十组（`14` L134）正好布置了这一情形，但没有断言标注。
  - **(b) 执行时机**：
    - 正文只在 “Host 的第一个会话创建之后、第一次请求之前再做一次这一步”。但：
      - Pi 明确支持加载之后的注册，“立即生效，可以在命令处理器或事件回调中调用”（`core/extensions/types.ts:1814-1817`），会话把它直接绑到 Host 的运行时（`core/agent-session.ts:3496-3502`）；
      - 每个 Run 都重新创建会话服务（`05` L396 的运行时工厂），注册随之重新写入；依赖工作目录的扩展在打包 Host 的后一个会话中可能注册新的同名覆盖；
      - 扩展在 `session_start` 中经 `ctx.modelRegistry` 发出的请求早于 “会话创建之后” 的这一步。
    - 这些情形下，已注入的导入密钥被交给扩展覆盖的 provider，直到该 Host 上下一个 Run 开始时的检查。ADR-232 把 “扩展注册的 provider 不再收到导入的密钥” 列为保留的性质，在这几种情形下不成立。
  - **(c) 代价一句**：
    - `11` L517 只登记 “只覆盖 `baseUrl`、依赖 shell 中密钥变量的扩展在 Tower 中判为未配置”。
    - 实际上任何以内置 provider 的 id 调用 `registerProvider` 的扩展都会进入这一列表，只给 `models` 或 `headers` 也算（合并见 `core/model-runtime.ts:928-949`），`registerNativeProvider` 同样如此。对只在 shell 中有该 provider 密钥的用户，这些扩展都使该 provider 在 Tower 中不可用。
- **为什么是次要**：
  - 不涉及 Agent 可影响的进程：同一 Host 中的用户扩展本就能经 `ctx.modelRegistry` 读取已注入的密钥（`core/model-registry.ts:198-204`），它们在密钥的信任边界之内；(b) 的后果是用哪份凭据、由谁计费与端点，不是机密交给 Agent。
  - 不丢数据；F7 的失败明确可见。
  - 但 (a) 使 R104-D5-01 要求的 “标注与 Host 实际所用的一致” 在一种已支持的配置下不成立，(b) 使 ADR-232 自己写下的一条性质在 Pi 文档明确支持的用法下不成立，实现会在 “只检查一次” 与 “每次都检查” 之间分叉。
- **后果的类别**：
  - 模型选择器写 `Tower 用导入的密钥`，实际由扩展认证，或请求按 F7 失败；标注随 Host 翻转；
  - 在事件回调中注册覆盖的扩展，Tower 的导入密钥被发往扩展配置的端点、计入 shell 中那份密钥的账户，而正文说不会；
  - 只给内置 provider 加模型或头部的扩展使该 provider 在 Tower 中不可用，用户只从 F7 卡片得知。
- **文档位置**：`11` L517；`05` L1450（D64）、L1506（C44）；`06` L42；`14` L134（G46 (d) 第十组）；`04` L1461；ADR-232 R104-D5-01、R104-D5-02 两条与安全不变式一段。
- **期望的回答形态**：在 `11` L517 的唯一定义中补三处：
  - (a) 结论加第三种 “由扩展处理”，标注写如 `由扩展 <名字> 认证，Tower 不用导入的密钥`；写明结论按扩展集合（或只取不加载扩展的 Host）保留，不随 Host 翻转；G46 (d) 第十组断言它。
  - (b) 这一步在每次创建会话服务之后、绑定扩展之前执行；对加载之后的注册，或在每个回合开始时再读一次 `getRegisteredProviderIds()`（内存读取），或把性质收窄为 “初次加载时的注册”，其余登记为限制；C44 补一组在事件回调中注册。
  - (c) 代价一句改为 “以内置 provider 的 id 注册的任何扩展（含只加模型或头部的）”。

### D6 系统架构与可靠性

**R105-D6-01｜次要**（只读状态启动：存活 Host 中的 Run 没有去向；drain 写入失败而 Host 存活时没有对应的恢复行；复查的卷集合与推迟的范围没有定义）

- **问题**：
  - **(a) 存活 Host 中的 Run**：
    - `06` L1197：只读期间 Supervisor 启动（含只重启 Supervisor）时 “以同一只读状态启动（不准入、横幅、会写数据库的命令返回 `E_STATE`），中间状态检查（§6.1.6，含第 5 项）推迟到解除时执行”。括号里的 “同一只读状态” 不含 “对活跃 Run 走 drain”。
    - 只重启 Supervisor 时，main 交回存活 Host、Supervisor 以 `replay` 补齐事件（`06` L63），其中的 Run 照常进行；对 Host 存活而 drain 未完成的 Run，唯一的去向是 §6.1.6 “Run 在 drain 中途” 一行的 “Host 存活时……继续这次 drain”（`06` L146），而它属于被推迟的中间状态检查。
    - 两种前提下照正文实现，存活 Host 中的 Run 会一直运行到空间释放：
      - Supervisor 在 F8 检测到 `ENOSPC` 之后、发出 `abort` 之前崩溃（`ENOSPC` 本身就可能使它崩溃）；
      - 自检（`06` L1181）现在对**每次**启动都适用：只重启 Supervisor 时某个卷不足 2 GB、此前并无 `ENOSPC`，正常运行中的 Run 都在存活 Host 中。
    - 这期间它们的事件写不进数据库，Host 的缓冲满后溢出到 `runDir/overflow.jsonl`（`05` L600），而 `runDir` 在 `~/.tower/runs/<R>/` 下（`06` L1056），可能正在已满的卷上；F8 一行的 “只读期间 Host 的事件缓冲随之增长，Run 已中止，有界” 在这一分支上不成立。
  - **(b) drain 写入失败、Supervisor 重启而 Host 存活**：
    - F8：“Supervisor 在此之前重启时按 §6.1.6 的同一规则进入 `paused{app_quit 或 engine_crash}`”。
    - 但 §6.1.6 的 “Run 中崩溃” 与 “settle 中崩溃” 两行只对 Host 已不存在的情形取原因（`06` L147–L148）；“Run 在 drain 中途” 一行要求 `draining_for` 非空，而它正是没写进去的那一项（`06` L146）。
    - Host 存活时（只重启 Supervisor 的常见情形），Run 已被中止、会话空闲，重放的 `agent.settled{aborted}` 落到 settle 判定表 “`outcome ∈ {aborted, error}`，非 draining → 按 abort 原因”（`05` L666），而这次 abort 的原因没有持久化；这些 Goal 也没有 `disk_full` 的 `outcome_reason`，不在解除集合中。
  - **(c) 复查的卷集合与推迟的范围**：
    - 解除只复查 “发生过 `ENOSPC` 的卷”（`06` L1197，`16` L853）。只读启动的新进程没有这一记录；因自检不足 2 GB 而只读启动、此前并无 `ENOSPC` 时，这一集合同样为空。照字面，空集合 “都 ≥ 2 GB” 立即成立而解除，或者永不解除，两种实现都符合文字。
    - 自检对 “各 Project 的 `<wtRoot>` 所在卷” 求剩余空间，某个 Project 在未挂载的外接盘上时求不出，正文没有写按什么处理；按 “任一不足 2 GB” 处理会使整个 Tower 只读。
    - 推迟的是整组中间状态检查，其中有不写数据库、反而释放空间或收回机密的步骤：清空不属于存活 Host 的 `~/.tower/tmp/`、`run/`（含死去 Host 的即时投递凭据文件，`06` L138），以及终止残留的 Agent 后台进程（`06` L145，后者在只读期间可能继续写盘）。
- **为什么是次要**：
  - 前提都要只重启 Supervisor，且与磁盘满或磁盘将满同时发生，少见；
  - 不丢失人的工作，Pi 的会话 JSONL 仍可对账（`06` §6.6.5）；
  - 不涉及机密进入 Agent 可影响的进程、沙箱或 git 元数据；即时投递文件在 `~/.tower` 下、三种沙箱都拒绝读取。
  - 但这是 ADR-232 新写的启动规则与 F8 自己的 drain 规则、与 §6.1.6 的恢复行之间的缺口，照字面实现会让 Run 在只读期间继续运行，解除条件也无法确定。
- **后果的类别**：
  - Supervisor 崩溃恢复之后，存活 Host 中的 Agent 在数据库只读时继续工作并花费额度，事件记录可能缺失；
  - drain 写入失败的 Goal 在解除之后停在没有原因的 `running`，或以 `abort` 的未知原因暂停；
  - 只读启动之后立刻解除又再次进入 F8，或一直不解除；
  - 外接盘未挂载时整个 Tower 只读；死去 Host 的凭据文件与残留进程在只读期间留存。
- **文档位置**：`06` L1197、L1181、L63、L138、L145–L148；`05` L600、L666；`16` L853；`14` L120（G35e (q)）。
- **期望的回答形态**：在 `06` L1197 “只读期间 Supervisor 启动” 一句补三处：
  - (a) 只读启动时照常接上存活 Host，对其中进行中的 Run 按 F8 的同一规则 drain（`app_quit`、`outcome_reason: disk_full`，写不进时目标留在内存、解除时补写）；§6.1.6 “Run 在 drain 中途” 一行的 Host 存活一支不推迟。
  - (b) 写明 drain 写入失败、Host 存活时，解除时按 F8 的 drain 补写（视为 `draining_for{pause, [app_quit]}`、`outcome_reason: disk_full`）。
  - (c) 复查的卷为 “发生过 `ENOSPC` 的卷与自检中不足 2 GB 的卷”；求不出剩余空间的卷不计入只读的触发（该 Project 另按卷不可用处理）；只推迟会写数据库的检查，`tmp/`、`run/` 的清理与残留进程的终止照常执行（补检查点推迟到解除）。G35e (q) 补一组 “只重启 Supervisor 时某个 Goal 仍在运行”。

**R105-D6-02｜次要**（准备阶段本身遇到 `ENOSPC`：F8 与 F4b 给出两个去向；打包 Host 中 ③ 的中止范围）

- **问题**：
  - `06` L1197：“准备阶段中的 Goal 中止准备（终止当前步骤的进程，同 `10` §10.3.1 准备被中止），不写数据库，留在 `ready`、`preparing_since` 非空”，解除时按启动恢复重新准入。
  - 但准备阶段最可能遇到磁盘满的，正是准备步骤本身：镜像、fetch、LFS 补齐与检出都在 `<wtRoot>` 与镜像所在卷上大量写入。这时 F4b（`06` L1193）“仓库准备……失败 → `paused(prepare_failed)`，不 `autoResume`、启动时不自动解除” 同样成立。
    - 数据库在另一个卷上、此刻仍可写时，先处理哪一个没有写：照 F4b 写下 `prepare_failed`，解除之后要人点重试；照 F8 不写，解除之后自动继续。
    - 数据库在同一卷上时，F4b 的写入失败，结果才与 F8 一致。
  - ③（Host 握手与开场组装）“进行中 `pause`/`take_over` 返回 `E_BUSY`”（`10` L386），F8 却要终止 “当前步骤的进程”。打包模式下这一步的进程是与其他 Goal 共用的 Host，而这些 Goal 的 Run 正由 F8 drain、需要该 Host 存活；开场已经发出而 `run.started` 写不进时，Pi 中已有一个数据库里没有记录的 Run，F8 的 drain 只说 “活跃 Run”。
- **为什么是次要**：不丢数据，Goal 停在可重试的状态；③ 的窗口不超过 120 s。但 “准备阶段的 Goal 在解除后自动继续” 这一 ADR-232 新写的承诺，在准备阶段最常见的磁盘满情形下取决于实现选了哪一行。
- **后果的类别**：释放空间之后，部分准备中的 Goal 自动继续，部分停在 `prepare_failed` 等人重试，且卡片写 “准备失败” 而不是磁盘满；打包模式下终止共用的 Host 使其他 Goal 的 drain 变为崩溃恢复。
- **文档位置**：`06` L1197、L1193（F4b）、L126；`10` L386（§10.3.1 准备期间的命令与启动恢复）；`14` L120（G35e (q) 准备中的一组）。
- **期望的回答形态**：在 `06` L1197 “进行中的验证与准备” 一句补两处：
  - 准备步骤因 `ENOSPC` 失败时归 F8、不按 F4b 写 `prepare_failed`；
  - ③ 中只处置该 Goal 的会话、不终止共用的 Host，开场已发出的按 drain 中止。
  - G35e (q) 准备中的一组改为由准备步骤自己写满 `<wtRoot>` 所在卷。

### 不扣分的观察

1. **F8 并入进行中的 drain 时的 `outcome_reason`**：drain 中再收到的暂停请求只并入 `reasons`（`06` L90），`run.ended` 只写一次。人暂停或预算上限的 drain 进行中遇到 F8 时，“`outcome_reason` 写 `disk_full`” 是否仍适用没有写；不适用时该 Goal 不在解除集合中，卡片写 `应用退出`，人 `继续` 只解除当前的 `human`（`06` L885），`app_quit` 要到下次启动或第二次 `继续`。窗口不超过 drain 的 8 s。宜写 “F8 向 drain 并入 `app_quit` 时一律写 `disk_full`”。
2. **打包时的 Host 预留**：`13` L196、`16` L878 的 `h = p95(打包 Host)/K` 假设 Host 满载；分组之后单独占一个 Host 的高风险或清单待确认的 Goal 实际占一整个 Host，准入少记约 (K−1)/K × p95，每个未满的 Host 约 0.1 GB，内存压力刹车仍在。宜写 “新起 Host 的 Goal 预留整个 Host，加入已有 Host 的预留 1/K”，或登记这一偏差。
3. **租约只读与 F8 的停止准入不在 §6.2.4 的检查之中**：`06` L298 称本节是 “一切要开 Run 的转移的唯一闸口”，检查 a–h 中没有 “Project 因租约只读”（`06` L184 “不启动 Run”）与 “数据库只读”（F8 “停止准入”）。称职的实现者会加上，但 `waitReason` 与卡片注明没有写。宜各加一项（`waitReason = slot`，卡片注明 `另一个 Tower 安装正在使用` 或 `磁盘已满`）。
4. **G35e (q) 多原因一组的卡片**：期望 “卡片写 `已暂停 · 磁盘已满`、没有 `自动恢复`”（`14` L120）；按优先级 `human` > `app_quit` > `budget_hard_cap`（`16` L30），`budget_hard_cap` 在 `alsoApplies` 中，卡片按 `12` L445–L450 应为 `已暂停 · 磁盘已满 · 另有：硬预算上限`。以完整字符串断言时照定义实现的版本会失败。另 `12` L443 写 `硬预算上限`，L447 的示例写 `预算硬上限`。宜把期望写全并统一措辞。
5. **“被压下的覆盖层” 的去处**：`12` L528 “被压下的整页或浮层覆盖层不丢失，在侧栏顶部以一行入口保留” 是行为而不只是视觉；`08` 规则 4（L694）把进入诊断视图时的单 Goal 简报折叠到诊断视图顶部的一行，规则 2 的 “不再弹出” 是否算 “被压下” 没有写。`12` L528 的 “自动诊断” 与 `08` L683 “从不在回到应用时自动弹出” 措辞不同。宜在 `08` §8.10.5 定义去处，`12` 只引用。
6. **只读期间被取消的验证与中止的准备的实况行**：`12` L392、L394 的实况行只为进行中的工作定义（`验证 · 标准 · 3/4 已跑`、`准备中 · 依赖 · …`）；F8 下窗口一直开着，这些 Goal 的实况行照字面仍写进行中。横幅已写明 Tower 已暂停运行，影响小；宜补一行 `验证已取消（磁盘已满）· 释放空间后以同一 pin 重跑`、`准备已中止（磁盘已满）`。
7. **`00` §0.5.1 的凭据一行**：`00` L112 只泛写 “部分凭据类型……只在你的终端中可用”；ADR-232 新登记的 “以内置 provider 的 id 注册的扩展在 Tower 中不用 shell 的密钥” 是首次运行确认卡上应当列出的能力差异之一（`04` L1460 引用这一列表）。宜加半句。
8. **卡片条件的两处细节**：`04` L1517 的 `应用退出` 一行仍自写条件 “`resumeOnLaunch` 打开时”，没有 “`app_quit` 是唯一的原因”（L1518 已改为只引用 `12`）；`12` L432 的 “`app_quit` 是唯一的原因” 没有考虑第 5 项同样解除的 `engine_crash`（没有 `stalled` 条目时），`{app_quit, engine_crash}` 同样会自动继续。都几乎不可见。
9. **几处登记**：`03` L97 `app_quit` 的来源列只写 “应用退出 / Host 崩溃”，没有 F8；`02` L200、`16` L26 的 `preparingSince` 写 “中止……时清除”，F8 有意保留它，宜注明例外。
10. **`models.json` 中 `!` 形式的 `apiKey`**：每次请求都以 `execSync` 执行（`resolve-config-value.ts:221-226` → `:185-196`），每次至多阻塞 Host 的事件循环 10 s，打包时影响同一 Host 的其他 Goal；`11` L517 只对 `auth.json` 的第一次检查写了阻塞。低于 30 s 的挂死判定。宜补半句。
11. **模型选择器与读屏表**：“模型选择器” 在 `04`、`12` 中没有定义的界面位置（最接近的是 `04` L1273 设置中的默认模型），G46 却对它断言；`12` §12.13.3 的读屏表（L770–L781）没有列出横幅的 `assertive` 一次。
12. **G46 (d) 第九组 CA 一组**：在只能经代理出网的网络中，“指向 `<wtRoot>` 之下” 的一次期望模型请求以哪一条 F 路径失败没有写。

### 设计是否完成

ADR-232 关闭了第 104 轮的全部七条条目：
- 标注只取 Host 的检查，`!` 命令只在 Host 中执行；
- 扩展注册的 provider 不注入，打包只合并扩展集合相同的 Goal，高风险 Goal 的模型请求不经扩展代码；
- Host 自己安装读代理变量的分发器；
- F8 的解除按第 5 项、由数据库求出，进行中的验证与准备有了去向；
- `12` 只引用 `08` 的覆盖层规则；
- G46 的同机与异机两组。

本轮 4 条都是修法带出的分支：
- **R105-D5-01**：分发器只在有代理变量时安装，与 Pi 每个入口都安装不同；
- **R105-D5-02**：扩展处理认证的 provider 没有标注，“不注入” 只执行一次，代价一句偏窄；
- **R105-D6-01**：只读启动时存活 Host 中的 Run、drain 写入失败而 Host 存活、复查的卷与推迟的范围；
- **R105-D6-02**：准备步骤本身遇到 `ENOSPC` 时 F8 与 F4b 的先后。

全部为次要：没有一条会使照文字实现的人违反所述的安全不变式或丢失人的工作，每一条都能在已有的唯一定义处加一句关闭。
