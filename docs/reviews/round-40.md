## 1. 总评

ADR-165 的方向正确：含机密的本地文件不再播种，注册表令牌改为即时投递，钥匙串收窄为三类。`11`、`07`、`16`、`04` §4.15.1 与 G46(h)–(l) 都已落地，排期算术成立（WBS 121.27，38 周）。

- `10` §10.3.1 第 4 步与 §10.8.3（检验检出的规则正文）仍把含机密的条目播种进检验检出；
- `04` 的检验信任提示与“我来改”提示仍按旧行为写；
- R39 对“不播种”这一选项明确要求的失败归类没有写；
- 人怎样完成依赖机密的 human 标准没有定义；
- 本地文件清单的取消标记是新的安全决定，却没有实体、命令与远程策略。

### D4 领域模型与生命周期

**R40-D4-01｜重要**（本地文件清单没有实体、命令与远程策略；取消标记与复制前扫描的关系未定义）

- **问题**：
  1. **没有实体**：
     - 本地文件清单（ADR-078/082/165）被多处当作持久数据使用，例如 `07` L261 `hashSeededLocalFiles(g.projectId, …)`、`04` L1277-1288 的逐行“批准”列；
     - 但 `02` 的 `Project`（L77-98）与 `VerifyProfile`（`07` L1706-1745）都没有这一字段；
     - `06` 的 DDL 中也没有对应的表或 JSON 列。
  2. **界面有操作，协议没有命令**：
     - §4.15.1 有 `[+ 添加路径]`、建议条目的 `[添加] [忽略]`、逐行 `标记为机密` / `取消标记`；
     - `06` 命令表（lint (v) 统计 87 条）中没有任何对应命令；`02` L455-472 的 `HumanDecision.kind` 中也没有批准本地文件或取消机密标记的决定；
     - 因此 `16` §16.5 的远程矩阵也没有覆盖这些操作。
  3. **ADR-165 让这块数据带上了安全含义**：
     - 取消标记会使文件“被复制到 Agent 可读的工作目录”（`11` L339，`04` L1293）。这是与 `project.set_trust` 同一类的边界决定，后者是“仅本机”（`16` L906），且记录为 HumanDecision；
     - 取消标记却没有决定记录、审计，也没有远程策略。
  4. **取消标记与复制前扫描的先后关系**：
     - `07` L477 与 `11` L339 规定内容判定发生在“复制前”，即每次播种都重新扫描；
     - G46(l) 又要求按内容判定的文件取消标记后“照常播种”；
     - 两条合在一起有两种读法：取消标记永久压过扫描，则文件之后加入真正的密钥也会被播种进 Agent 可读的卫星；每次扫描重新判定，则取消标记无效。文档没有选择。
- **为什么重要**：
  - 实现者必须自行决定数据放在哪里、走什么命令、远程能否执行。其中“远程客户端能否取消机密标记”和“取消标记是否随内容变化失效”直接决定 ADR-165 的不变式是否成立。
  - 这不是 M2 细节：§4.15.1 标为 [M1]，W11 本轮也计入了“本地文件设置页的机密分类与取消标记确认”。
- **文档位置**：`02` L77-98、L455-472；`07` L261、L477、L1706-1745；`04` L1272-1295；`06` 命令表、DDL；`11` L339；`16` L506、§16.5、L906；`14` G46(l)。
- **期望的回答形态**：
  - `02` 的 `Project` 加 `localFiles: { path | glob; approvedBy: DecisionId; secretBasis: ("filename" | "content" | "user")[]; unmarked?: { decisionId; contentHash } }[]`（或等价形态），`06` 加对应的 JSON 列；
  - `06` 加命令，例如 `project.local_files.add` / `.remove` / `.mark_secret` / `.unmark_secret`，`02` 加相应的 `HumanDecision.kind`；在 `16` §16.5 中把 `unmark_secret` 列为**仅本机**（与 `project.set_trust` 同理）；
  - 写明取消标记**绑定内容哈希**：之后内容变化时，复制前的扫描重新判定，命中则恢复为含机密，设置页提示“内容已变化，已重新标为机密”；
  - G46(l) 加一组：取消标记后在文件中加入一个 `sk_live_…` 形态的值，下一次播种前被重新判为含机密、不复制；另一组从远程客户端尝试取消标记，被拒绝。

### D7 诚实与验证

**R40-D7-01｜重要**（依赖未播种机密文件的标准失败时没有归类：试运行误标“红灯”，验证失败按 Agent 失败自动返工）

- **问题**：
  1. **影响面不小**：
     - 按文件名判定的条目不可取消（ADR-165 补记），而 `.env*` 覆盖了大多数 Node Web 项目的 `.env`、`.env.local`、`.env.test.local`；
     - 测试与开发服务器常经 dotenv 读取它们；
     - ADR-165 之前，这些文件会播种进验证槽位；现在不会。
  2. **试运行会误标**：
     - 合同编辑器中 exec 标准在 base 上试运行（`04` L1090，`03` L125）；
     - 因为缺少 `.env.local` 而失败的标准，会显示为 `✓ 红灯，可证明完成`（`04` L1068-1069 的线框）；
     - 这是由 Fact 推导出的徽标，却给出了相反的含义：该标准在验证槽位中永远不会通过，无法区分改动前后。
  3. **验证失败会自动返工**：
     - 同一标准在 Goal 的验证中继续失败，按归因进入自动返工，直到 I6 的返工上限（`07` L1536-1537）；
     - Agent 的卫星中同样没有这些文件，它无法修复，只能消耗返工轮次，或者去改测试以绕开（哨兵会兜住一部分）。
  4. **有先例，却没有用上**：
     - 缺失程序（exit 127 / `ENOENT`）有专门的归类：`verify_env_error{stage:"exec"}`，不返工、不计为 Agent 失败（`07` L449）；
     - “缺少未播种的本地机密文件”这一类没有对应规则；
     - R39 的期望形态 (b) 明确要求写明，ADR-165 与各回应都没有处理。
- **为什么重要**：
  - 诚实语法的核心是 Fact 徽标不误导。“红灯，可证明完成”在这里是错的；
  - 自动返工浪费预算，还诱导 Agent 修改测试；
  - 用户也看不到失败与未播种文件之间的联系：设置页只有一句“需要它的检查请写为 human 标准”，没有指出是哪条标准受影响。
- **文档位置**：`07` L449、L477、L1530-1540；`04` L1065-1071、L1090、L1293；`03` L125；`11` L339；`15` ADR-165；`14` G46。
- **期望的回答形态**：在 `07` §7.4.2 写一条保守规则，例如：
  - **判定输入**：项目有未播种的含机密本地文件时，Tower 只读取这些文件中的**变量名**（不读值，不进入任何日志）；
  - **试运行**：标准在 base 上失败，且输出中出现这些变量名或文件名时，不显示 `✓ 红灯`，改为 `◇ 可能依赖未提供的本地机密文件 .env.local`，给出“改为 human 标准”或“改用项目变量（非机密）”两个出口；
  - **验证**：同样条件下的失败记 `verify_env_error{stage:"exec", detail:"local_secret_missing", file}`，不返工、不计为 Agent 失败，生成相应的 Needs-You；
  - **简报**：Agent 简报列出未提供的文件名，让 Agent 如实报告，而不是去改测试；
  - **用例**：G46 加一组：`.env.local` 中定义 `DATABASE_URL`，测试读不到时报错；试运行显示 `◇` 而不是 `✓ 红灯`，验证失败不进入返工。
  - 若认为启发式不可靠，至少把“项目存在未播种的含机密文件时，试运行失败的标准一律不标 `✓ 红灯`，改标 `◇ 未知原因失败`”写为规则。

### D8 注意力与交互

**R40-D8-01｜重要**（依赖机密的 human 标准在 M1 中怎样完成没有定义；检验与人工编辑的提示仍按旧行为写）

- **问题**：
  1. **人被引导去写 human 标准，却没有地方完成它**：
     - ADR-165 让设置页写“需要它的检查请写为 human 标准”；
     - M1 中勾选 human 标准的路径是 `O 检验`（`04` §4.6.6，`10` §10.8.3 第 6 步）；
     - 但检验检出现在也不含这些文件（`07` L477），检验服务与人在终端中运行的应用都拿不到它们；
     - 文档没有说明人怎样带着自己的机密去确认 Agent 的成果：在检验终端中自行提供？只在验收后的分支上确认（那时 human 标准已经必须勾选）？还是别的方式？
  2. **提示与新行为相反**：
     - `04` L568-570 的检验信任提示列出“本地密钥文件 .env.local（2 处密钥）、config/dev-certs/*.pem”，告诉人终端“能读取”它们；
     - `04` L581 写“播种的 `.env.local` 若写死端口……”；
     - `04` L603 的“我来改”提示写“此副本不含含密钥的本地文件……要运行应用请用 O 检验”，而 `O 检验` 现在同样没有这些文件；
     - `04` L564 的“播种了含密钥文件时再次提示”这一触发条件已不存在。
  3. **残余登记**：如果人自行把机密带进检验目录，Tower 启动的检验服务（在验证器沙箱中，属于 Agent 可影响的进程）同样可能读到。T31（`11` L646）登记了“人在外部终端中运行 Agent 写的应用并带着真实本地密钥”，但它的前提仍是“Tower 播种了这些文件”，没有改为“由人自行提供”。
- **为什么重要**：这是 M1 的核心人工检验路径。按现在的文案，用户会被指向一个打不开应用的地方；依赖机密的 human 标准没有可执行的完成方式；残余风险的叙述也与实际行为不符。
- **文档位置**：`04` L560-584、L603、L1293；`10` L803-830；`07` L477-478；`11` L365、T31（L646）；`15` ADR-165。
- **期望的回答形态**：
  - 在 `10` §10.8.3（规则正文）写明 M1 的做法，推荐：
    - 检验检出不含含机密的本地文件；
    - 信任提示改为“本目录不含 .env.local 等含机密的本地文件。需要它们的检查：可在 Tower 打开的终端中由你自行提供；这样做时，Agent 写的代码会带着这些值运行，Tower 启动的检验服务也可能读到”；
    - 面板给出受影响的 human 标准行的提示；
  - `04` L568-570、L581、L603 同步。“我来改”的提示改为不指向 `O 检验`，或指向上面的做法；
  - T31 改写为“人自行提供机密”的残余，评级不变或说明理由；
  - 若选择“只在 Tower 外确认”，写明 human 标准在 `in_review` 中怎样勾选（例如允许附注“在我的环境中确认”），不要形成先后矛盾。

### D11 安全与自主度

**R40-D11-01｜重要**（`10` 的准备步骤与检验检出规则正文仍播种含机密的条目，与 ADR-164/165 的不变式矛盾）

- **问题**：
  - `10` §10.3.1 第 4 步（L367）：“把……**不含密钥**的条目复制进卫星（**含密钥的条目只进验证槽位与检验检出**，不给 Agent）”。`05` L245 规定准备步骤顺序以 `10` §10.3.1 为唯一定义；
  - `10` §10.8.3 第 2 步（L812）：“播种本地文件：……清单中的**全部条目**（含密钥的条目只复制到这里与验证槽位，Agent 不可读，ADR-082）”。`04` L560 与 `07` L478 都以 `10` §10.8.3 为检验检出的规则正文；
  - 同节第 0 步（L803-805）的信任提示“能读取以下本地密钥文件：<列表>”，第 5 步（L827）“播种的 .env.local……”；
  - `11` §11.6.3 L365 的检验信任提示同样写“能读到列出的本地密钥文件”。
  - 第 39 轮回应称 `10` 已同步，但只改了 L127、L426、依赖矩阵与卫星重建，没有改这两处步骤。
- **为什么重要**：
  - ADR-164/165 的核心不变式是“M1 中验证槽位与检验检出里不存在任何机密”（`07` L477，`11` L411）；
  - 检验检出的实现者照 `10` §10.8.3 写，会把 `.env.local` 复制进去，而检验服务运行的正是 Agent 写的代码；
  - 唯一定义与规则正文互相矛盾，正是 R39-D11-01 要消除的那一类问题。
- **文档位置**：`10` L367、L803-805、L812、L827；`11` L365；`05` L245；`04` L560；`07` L477-478。
- **期望的回答形态**：
  - `10` L367 改为“普通本地文件复制进卫星；含机密的本地文件在 M1 中不播种（`11` §11.6.2，ADR-165）”；
  - L812 改为“只播种普通本地文件”；L803-805、L827 与 `11` L365 按 R40-D8-01 的做法改写；
  - 建议在 lint 中加一项：凡出现“含密钥/含机密的条目……复制/播种/进”的 M1 文本，必须同时出现“不”或“M2”。

**R40-D11-02｜次要**（注册表令牌的来源、身份与刷新未定义；`dep.add` 代理安装与登记处仍按旧口径）

- **问题**：
  1. **来源只写了“shell 环境”**：
     - `04` L1249 与 L1428 写“从 shell 导入……私有注册表令牌到系统钥匙串”；
     - 私有注册表令牌最常见的存放处是 `~/.npmrc` 中按主机写的 `_authToken` 行，不在 shell 环境中；
     - ADR-165 之前，`$TI` 的 npmrc 由 `~/.npmrc` 生成，令牌随之更新；现在令牌只从钥匙串取（`07` L546），而导入、对应哪个注册表主机、用户更新 `~/.npmrc` 后怎样刷新，都没有定义。
  2. **`dep.add` 代理安装**：
     - `16` L1061 写“`dep.add` 获批后，由 Supervisor 以 I 的身份（`$TI/npmrc`）把新依赖安装进本 Goal 的 `$GS`”；
     - `$TI/npmrc` 已不含令牌（`07` L525），P7（`14` L140）因此不成立；
     - 文档也没有说明代理安装是否同样按“阶段 1 拉取带令牌、不执行代码；安装不带令牌”分段；而 `11` L415 说即时投递文件“只有两个使用者”。
  3. **登记处不一致**：
     - `11` §11.7.0 的投递表（L419-428，自称“全部机密”）没有注册表令牌一行；
     - 同文档 §11.7.1 “Tower 密钥库”行（L481）仍写只存两类；
     - `16` L504 写“M1 中只存 Tower 自己使用的凭据”，没有列注册表令牌；L507 写“M1 中唯一的使用者是……云 SDK 凭据”；L1014、L1027 写“I-fetch = 带 `$TI` 令牌”。
  4. **悬空条款**：`11` L480 的“用户在清单确认（§11.8.2）时对该服务器的显式授予……除非对该服务器显式授予”，在 §11.8.2 中仍没有字段、命令与界面（R39-D11-02 第 2 项的残留）。
- **为什么重要**：
  - 第 1、2 项若照字面实现，私有注册表项目在 M1 中无法安装依赖，`dep.add` 代理安装也会失败（结局是 `verify_env_error`，有界，但功能不可用）；
  - 第 3、4 项是唯一定义与其他文档之间的矛盾。
  - 都不放进新的暴露，因此为次要。
- **文档位置**：`04` L1249、L1428；`07` L525、L546；`16` L504、L507、L1014、L1027、L1039、L1061；`14` P7（L140）；`11` L415、L419-428、L480、L481、§11.8.2。
- **期望的回答形态**：
  - 写明注册表令牌的来源（例如从 `~/.npmrc` 的 `//<host>/:_authToken` 行，以及其中 `${VAR}` 引用的 shell 变量）、钥匙串条目以注册表主机为键、`~/.npmrc` 变化时重新导入并提示；或者改为每次阶段 1 前由 Supervisor 直接从 `~/.npmrc` 生成即时投递文件，不进钥匙串；
  - `16` L1061 改为“经安装器同一流水线：阶段 1 以即时投递文件带令牌拉取，不执行代码；安装阶段不带令牌”，P7 同步；
  - 投递表加一行“私有注册表令牌”；`11` L481、`16` L504、L507、L1014、L1027 改为三类与两个使用者；
  - `11` L480 的“显式授予”标为 M2，或删去。

**R40-D11-03｜次要**（`VerifyProfile.env.vars` 进入 Agent bash 与验证进程，却不在人输入机密检查的范围内）

- **问题**：
  - 项目变量 `VerifyProfile.env.vars` 只在类型注释中写了“非机密”（`07` L1731），同时注入 Agent 的 bash 与验证进程（`05` L408 两列都是 ✔）；
  - 它经通用的 `settings.update {path, value}` 一类路径修改，没有任何机密检查；
  - ADR-164 的人输入文本机密检查以“会进入模型上下文”为原则（`11` L433）。Agent bash 中的环境变量对模型可达，按这一原则应当覆盖；
  - ADR-165 把 `.env.local` 挡在验证之外后，`04` L735 与 `10` L1249 推荐的“项目变量”正是用户最自然的替代位置（例如带密码的 `DATABASE_URL`）。
- **为什么重要**：这是一条由人发起、但没有任何提示的通道，与“M1 中没有机密进入 Agent 可影响的进程”的说法不符。R39 对 `command` 中内联 `NAME=value` 不扣分，理由是“有提示兜底”；这里连提示都没有。
- **文档位置**：`07` L1731；`05` L408；`06` `settings.update`（L912）；`11` L432-436；`04` L735；`10` L1249；`16` L274。
- **期望的回答形态**：
  - 对写入 `VerifyProfile.env.vars` 的值执行同一检查（钥匙串精确匹配 + §11.7.1 模式），命中返回 `E_CONFIRM`，文案写明“项目变量会进入 Agent 的终端环境与验证进程”；
  - 设置页在该字段旁写明“非机密”；
  - G46(e) 加一组。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1–D3、D5、D6、D9、D10、D12–D14、D16 为 100，这十二个维度上没有可追问的实质问题。
  - D4 95、D7 95、D8 95、D11 91、D15 97。
- **是否还有可追问的问题：有。** 新增共 **7** 条：阻断 0、**重要 4**、**次要 3**。
  - **第 39 轮核验**：已解决 0，部分 3，未解决 0。各条的主体都已落地，残留集中在 ADR-165 没有触及的 `10` 与 `04` 检验流程。
  - **其他核对**：
    - lint 全部通过；
    - Pi v1.2.0 源码复核成立，Pi 依赖面不变；
    - 本机 pnpm 12.6.0 的 `fetch` 支持 `--ignore-pnpmfile`（含 config dependencies 的 pnpmfile）与单独的认证文件；
    - 排期算术全部成立：WBS 121.27、38 周、系统线余量 0.19、增人 33 周。
  - **不扣分的观察**：
    - **`.env*` 不可取消**：会把少数只含非机密值的 `.env.local` 也挡在验证之外。结局保守，且有项目变量作为替代，不扣分。R40-D7-01 的提示可以顺带指向项目变量。
    - **内容扫描的模式集**是否含熵规则没有写明。两种选择都是保守的，不扣分。
- **设计是否完成：否。**
  - ADR-165 的方向与唯一定义都对，M1 的机密面已经收得很窄。
  - 但“不播种”这一决定带来的连锁后果没有写完：`10` 的规则正文、检验文案、失败归类、human 标准的完成方式，以及本地文件清单本身的数据与命令。修复都不需要新架构。
- **下一轮建议按以下顺序修订**：
  1. **R40-D11-01**：`10` L367、L812、L803-805、L827 与 `11` L365 改为“含机密的本地文件不播种”。纯文字，但它是规则正文。
  2. **R40-D7-01**：失败归类、试运行徽标、简报与用例。
  3. **R40-D8-01**：依赖机密的 human 标准在 M1 中的完成方式；`04` 的三处文案；T31 改写。
  4. **R40-D4-01**：本地文件清单的实体、命令、决定类型、仅本机，以及取消标记绑定内容哈希。
  5. **R40-D11-02**：注册表令牌的来源与刷新；`dep.add` 的令牌路径；登记处改齐；`11` L480 的悬空授予。
  6. **R40-D11-03**：项目变量纳入机密检查。
  7. **R40-D15-01**：文字。
