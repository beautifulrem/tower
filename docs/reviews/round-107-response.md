决策：
- ADR-235（`15` 末尾，L4978 起）；
- ADR-234、ADR-233、ADR-207 标题加 “Amended by ADR-235”；
- ADR-133 第 107 轮补记（`15` L1534）。

本文件关闭 `round-107.md` §4 的 5 条次要条目与 §5 的 13 条观察。行号为修改后的位置。

**收敛规则**（同 ADR-186–234）：只用三种办法关闭条目：
1. 把说法改弱，但保证为真；
2. 删除或推迟不属于 M1 主循环的机制；
3. 在已有的唯一定义处加至多一条守卫、一行或一个字段。

**本轮的取向：以删除与简化收敛**。ADR-234 的两个机制各自带出了一串分支：
- 为探测起的短时 Host：专用模式下的分组与上限、自身失败、`!` 命令随每次新起而重新执行、扩展以内置 id 覆盖时的误报；
- 按卷名判别的 “卷未挂载” 一行：Run 进行中卷消失、其余恢复行、隐私清除续做、情形 C/F、命令范围、`syncing` 不变式、同名卷与符号链接。

这两类不逐条加守卫，而是删掉机制本身：
- R107-D5-01 删除短时探测 Host；
- R107-D13-01、R107-D13-02 以一条 “Project 不可达” 规则取代按卷名判别的一行。

新增的只有：
- `06` §6.1.6 “Project 不可达” 一行（取代 “卷未挂载” 一行），卡片注明 `Project 不可达`（替换 `12` §12.6.5 的一行）；
- `Run.outcomeReason` 的已用值 `project_unreachable`（开放字符串；暂停原因仍为 `app_quit`，与 F8 的 `disk_full` 同一做法）；
- 卡片文字 `提供方可能已恢复？[重试]`（已有的 `goal.resume`）与 `已暂停 · Project 不可达 · 可访问后自动恢复`；
- Supervisor 内一个做可达性检查的 `worker_thread`（`13` §13.5）。

不新增状态、暂停原因、事件类型、表、列、命令、决定种类、Needs-You kind、landmark、`wait_reason` 值、锁或常驻进程。

安全不变式全部保留：
- Tower 不会自动把机密交给 Agent 可影响的进程。模型密钥仍只经运行时注入、只在 Host 内存中。
- 探测仍只在 Host 中求值 `$VAR`、`!` 命令与导入的密钥。删除短时 Host 之后，不再有任何为探测起的进程。
- 缓存预热请求与已登记的压缩、摘要请求同属一类，不扩大机密的去向（扩展本就在密钥的信任边界之内）。
- Project 不可达时 Tower 不删除、不改名、不重建任何目录，不执行任何丢失处理。人的工作现场不自动删除。

安全问题只写到设计层面。

## Pi v1.2.0 核实（`git show v1.2.0:<path>`，`packages/coding-agent/src/` 下，另注 `ai`）

- **R107-D5-02：哪些设置会造成重试循环**
  - `core/sdk.ts:340-353`：`buildRequestOptions` 每次请求调用 `getProviderRetrySettings()`、`getHttpIdleTimeoutMs()` 与 `getWebSocketConnectTimeoutMs()`。请求时限取 `options.timeoutMs ?? providerRetrySettings.timeoutMs ?? effectiveTimeoutMs`（`:350`）；`maxRetries`、`maxRetryDelayMs` 取 `retry.provider.*`（`:352-353`）。
  - `core/settings-manager.ts:147-156`：`parseTimeoutSetting` 对无效值抛出 `Invalid <名字> setting: …`。`:900-901`、`:934-936`：前两个时限经它读取。
  - `:925-932`：`getProviderRetrySettings` 不解析，原样返回。`:891-898`：会话自动重试的 `retry.maxRetries` 同样不解析。
  - `ai/src/api/anthropic-messages.ts:641, 655-661`：`timeoutMs` 成为厂商 SDK 的 `timeout`，`maxRetries` 交给 `retryProviderRequest`。
  - `ai/src/utils/provider-retry.ts:111-125`：非数值的 `maxRetries` 使 `retriesRemaining <= 0` 永不成立（`NaN` 比较恒假），可重试的错误一直重试。
  - `ai/src/utils/retry.ts:198, 218`：会话自动重试的 `attempt >= maxAttempts` 同样如此。`:73`：可重试模式不区分大小写地含 `timeout`。
  - **结论**：v1.2.0 中会造成重试循环的设置是 `httpIdleTimeoutMs`、`websocketConnectTimeoutMs`、`retry.provider.timeoutMs`、`retry.provider.maxRetries` 与 `retry.maxRetries`。`retry.provider.maxRetryDelayMs`、`retry.baseDelayMs` 等无效时不使重试无界，不列入。
- **观察 1：缓存预热（已核实：不经 `turn_start`）**
  - `core/sdk.ts:427-429`：每次会话请求之后 `cacheWarmer.start`。`core/settings-defaults.ts:60`：默认 `cacheWarming: "streaming"`。`core/settings-manager.ts:913-917`：只读全局设置。
  - `core/cache-warmer.ts:296`：由定时器触发。`:330-339`：直接调用 `this.models.streamSimple`，带 `maxTokens: 1`，不经 Agent 循环，所以不经 `turn_start`；凭据在这次请求中照常求出。`:342-348`：用量以 `appendUsage("cache_warm", …)` 写入会话。
- **观察 2**：`core/extensions/runner.ts:1096-1125`：`emit` 逐个等待处理器，异常被捕获、经 `emitError` 报告，事件继续。`core/model-runtime.ts:634-640`：`removeRuntimeApiKey` 的队列任务开始时同步删除覆盖，之后才同步状态。
- **观察 4**：`extensions/mcp/runtime.ts:48, 210-211, 363`：内置 MCP 扩展的请求时限取 `mcp.json` 的 `timeout`，默认 60 s。
- **观察 13**：`core/resource-loader.ts:781`：inline 扩展最后加入。
- 评审所引其余各处均为原文。

## R107-D5-01（次要）：短时探测 Host 的分组、失败分支、`!` 命令的重复执行与覆盖 provider 的误报

**按指示删除短时探测 Host**。唯一定义在 `06` §6.1.4 第 5 项（L101）。
- **探测在哪里运行**：只在该 Goal 所在打包分组中已存活、没有进行中 Run 的 Host 里运行。分组键在两种模式下都按扩展集合；专用模式下即服务该 Goal、尚未退出的 Host。
  - 从不在 Supervisor 中运行，也不为探测另起 Host。
  - `!` 命令的结果已缓存在该 Host 进程中，探测不会使它重新执行。
  - 探测不延长 Host 的存活。
- **不自动探测的三种情形**：
  - 没有这样的 Host。专用模式下暂停超过 5 分钟、Host 退出之后即如此。
  - 该 provider 在扩展注册的列表中，不论是扩展新建的，还是以内置 id 覆盖的：认证与端点由扩展决定。
  - F8 的只读期间。
- **这时**：不解除暂停。卡片写 `提供方可能已恢复？[重试]`（`goal.resume`），F6 或 F7 的 Needs-You 保持打开。
- **随之消失的分支**：(a) 分组与上限、(b) 自身失败、(c) `!` 命令重新执行。(d) 的误报也不再出现：扩展注册的 provider 一律不自动探测，同时删掉 “只在同组有已加载该扩展的空闲 Host 时自动解除” 一支。
- **引用处**：
  - `03` §3.2.1 `provider_unavailable` 一行（L96）；
  - `08` §8.6.5 一行的 L2 理由（L419）；
  - `05` §5.3.6 SDK 一句（L486）与 C39 (e)（L1500）：Host 存活期间探测在该 Host 中执行、`!` 命令不重新执行；Host 退出之后不再探测、卡片显示重试；覆盖 provider 的一遍不探测；
  - `11` §11.7.1（L517）；`12` §12.6.5（L444）；`04` §4.18.3（L1516）；`16` §16.1.1（L29）。
- **lint**：(d) 新增 DELETED 项 `short-lived probe Host`。

## R107-D5-02（次要）：SDK 每次请求读取的其他时限设置与请求时限的先后

按指示，唯一定义在 `05` §5.3.6 代理一行（L474）。
- **每个 Run 的校验**：步骤 ② 之后，校验扩到会造成重试循环的全部设置（列表见上方核实）。
  - `httpIdleTimeoutMs`、`websocketConnectTimeoutMs`：以 Pi 的 getter 读取，抛出即无效。
  - `retry.provider.timeoutMs`、`retry.provider.maxRetries`、`retry.maxRetries`：Pi 不解析，由适配器要求为有限的非负数，次数为整数。
  - 任一无效时，该 Run 的准备按 F4b 失败，不开会话。
- **请求时限的先后**（如实写明）：设置了 `retry.provider.timeoutMs` 时，SDK 的请求时限取它；分发器的空闲超时仍按 Host 启动时的值。两处时限中先到者起作用。删去 “两者中较小的起作用”。
- D63（L1450）补：比对 `buildRequestOptions` 读取的全部设置。
- C43（L1506）补两组：`websocketConnectTimeoutMs` 无效，`retry.provider.maxRetries` 为非数值。

## R107-D13-01、R107-D13-02（次要）：卷在 Run 进行中消失；卷未挂载一行的覆盖面与判别键

**按指示，以一条规则取代按卷名判别的一行**。唯一定义在 `06` §6.1.6 “Project 不可达” 一行（L139），先于本表其他各行判定。

- **判定**：Project 的必需路径之一不可访问。
  - 必需路径：附着的用户检出；该 Project 有卫星、人工编辑检出或检验目录记录时，还有 `<wtRoot>`。
  - 不可访问：`stat`（跟随符号链接）失败，或 5 s 内没有结果；或 F8 复查读不出其所在卷的剩余空间。
  - 删除 `/Volumes/<卷名>` 判别。同名卷与符号链接因此不再落回丢失两行，(f) 关闭。
- **① 进行中的 Run**（D13-01）：
  - 中止（无法 drain），以已有的 `app_quit` 进入 `paused`；
  - `run.ended` 的 `outcome_reason` 写 `project_unreachable`（同 F8 的 `disk_full`，不另设暂停原因）；
  - 继续目标按 `03` §3.2.1；进行中的 drain 照卫星丢失一行结束，`reasons` 并入 `app_quit`。
- **② 进行中的操作**（D13-01）：
  - 验证照应用退出取消；准备中止，回到排队。
  - 写回、卫星重建、接管物化与隐私清除的文件删除都停止，不执行失败出口：不改名，不清除 `human_checkout`，不告知 “不可恢复”。
  - 数据库中的 `syncing`、`satellite_rebuilding=1` 与不带 `filesDone` 的 `privacy.purged` 原样保留。
- **③ 不可达期间**（D13-02 (a)–(e)）：
  - 不准入：检查 i，`ready{slot}`，卡片 `Project 不可达`。
  - 本表其他各行都不执行，只有两处例外：后台进程的终止；启动时三行未结束 Run 的暂停写入。
  - 因此不判丢失、不重建、不重跑验证、不续做写回与清除，也不查找或重新附着另一份克隆。
  - 作用于该 Project 或其 Goal 的命令返回 `E_STATE`（`Project 不可达：<路径>`）。例外：查询、`goal.pause`，以及绑定处理（迁移、重新克隆、改 `worktreeRoot`）。
- **④ 恢复**：
  - 每 30 s 复查一次，人对该 Project 发出命令时也复查。
  - 可达后，按启动顺序执行各行，这时目录确实不在的才按丢失处理。
  - 照 F8 解除的同一规则，移除 `outcome_reason` 为 `project_unreachable` 的 `app_quit`（只在 `resumeOnLaunch` 打开时）。
- **不变的部分**：Tower 从不在 Project 不可达时自动执行丢失处理。Project 可达而目录确实不在时，丢失处理不变。

## §5 的观察

1. **缓存预热**（已核实不经 `turn_start`）：
   - `11` §11.7.1 的窗口改为 “这一次调用与下一次 `turn_start` 之前的压缩、摘要与缓存预热请求”；
   - `06` §6.2.5（L353）写明预热的用量只以 `usage` 条目写入会话，实时累加看不到，只在对账差值中出现，也不归入 “自身开销”；
   - D64 补依据。预热沿用你的设置，不在受保护设置中固定。
2. **`turn_start` 处理器出错**：`05` §5.6.5（L1006）写明处理器抛出。Pi 捕获后以 `extension_error` 报告、照常发出请求，这计入 F13。这一次请求可能仍带已注入的密钥，窗口延续到下一次 `turn_start`（如实登记）。
3. **检查与注入的竞争**：`11` §11.7.1 写明同一 Host 中对同一 provider 的注入与读取、移除串行执行，注入之前再查一次已列出的集合。
4. **MCP 时限**：C43、D63 改引内置 MCP 扩展的请求时限（默认 60 s）。
5. **G46 (d) 的观察时机**（`14` L134）：测试代理在重试耗尽后拒绝连接，探测因此失败，状态稳定到 Host 退出。同时写明：仍返回 503 时，可观察的窗口只剩第一次探测之前。
6. **切换模型**：
   - `04` §4.18.3（L1506）写明对话框每个目标一行、写该目标的标注，确认后发 `engine.set_prefs{goalId, model}` 与 `goal.resume`；
   - `04` §4.18.1 第 2 步（L1461）改为引用 `11` §11.7.1 “可见范围”。
7. **F8 中接管在 `run.ended` 之后**：F8 写明 ADR-200 窗口中不并入 `app_quit`，结果为 `paused(reasons ∪ {human})`。
8. **写回 ① 未完成**：F8 写明解除时先重做 ①，成功后不再执行 ③。
9. **残留**：
   - 短时 Host 删除后，`13` 的 “只在有活跃 Run 时存在” 不再有例外；
   - `16` §16.1.1 `waitReason` 一行补检查 i 的两项（L22）；`06` L331 的阻塞原因列表补 “该仓库正被另一个 Tower 使用”；
   - 情形 E 与 `04` 工作目录被外部删除一行补 Project 不可达的例外；
   - `16` §16.1.12 `E_BUSY` 改按 `06` §6.4.3 “写回进行中”（L293）；`06` §6.3 `human_checkout` CHECK 注释补 F8 与 Project 不可达期间（L507）；
   - `14` §14.1 M1 一行的历史括注补到第 107 轮；G46 标题的 ADR 列表补到 ADR-235、评审轮次补到 R107；
   - `04`、`12` 的 “恢复后提示继续” 改为按 `06` §6.1.4 第 5 项写。
10. **长期不可访问的卷与 F8**：F8 复查不含不可达 Project 的卷，读不出剩余空间的卷所在的 Project 判为不可达。同时删除：
    - “求不出的卷按不足计”；
    - `12` §12.8 横幅的 “无法读取 <路径> 所在卷的剩余空间” 后缀及其 `polite` 播报（§12.13.3 同步）；
    - `16` §16.2.6 中 “只读要到挂载或重启 Tower 才解除” 的登记。
11. **网络卷的阻塞**：`13` §13.5（L130）写明：
    - 可达性检查的 `stat` 与剩余空间读取在专用的 `worker_thread` 中执行；
    - 每次以 5 s 为限，到时按不可访问计；
    - 同一路径上一次检查未返回时，不再发起新的。
12. **短时 Host 的细节**：随短时 Host 删除，不再需要。
13. **`turn_start` 窗口的前提**：`05` §5.6.5 写明 SDK 中 tower-goal 最后加载（`resource-loader.ts:781`）。
