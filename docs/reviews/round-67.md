两条出在 ADR-194 的新文字：

- **从 `paused(*)` 进入 `integrated`**（R67-D4-01）：`03` §3.2.1 写着 “离开 `paused` 的唯一规则” 是 `onAllReasonsCleared()`。新通则开了一条不经该函数的出口，却没有写暂停原因、交还意图与对应的阻塞类 Needs-You 条目如何处理。

- **隐私清除删除用户仓库的分支**（R67-D13-02，**重要**）：`09` §9.12.4 规定 “清除一个 Goal” 时删除用户仓库中的 seal 分支，“清除全部” 时按前缀删除全部分支与 `refs/tower/*`。这几处都不受删除条件与两个守卫约束，也不区分已放弃或不合并而归档的 Goal。这与 `10` L10 “删除只有……按删除条件的 CAS 删除”，以及 `10` L440、L711 的 “用户拥有、一律不删”“你的提交不会因此丢失” 直接冲突，会删掉人在该分支上的提交，也会删掉多机租约。
- **`prunable` 的工作树使整个仓库的写入停住，且提示无法照做**（R67-D13-03）。
- **patch-id 已知限制写窄了**（R67-D7-01）：squash 前 base 在改动附近有变化、解决过冲突、或与其他改动合成一个提交时同样判定不到，侧栏随后写 “14 天未合入”。
- **隐私清除的范围不完整**（R67-D12-01）：遗漏备份 bundle、镜像中的基线快照、每日数据库备份；`09` 与 `06` 的命令定义也不一致。

- **审计保留期两处矛盾**（R67-D15-01）：`11`、`09`、`16` 写 1 年，`02`、`06` 写永久，而且 `06` 的触发器不允许删除 `audit.*`。

### D13 隔离、git 与并发

**R67-D13-02｜重要**（`09` §9.12.4 的 “清除一个 Goal” 与 “清除全部” 删除用户仓库中的分支与 `refs/tower/*`，不经删除条件与两个守卫，也不区分分支是否属于用户。这与 `10` 对用户仓库删除的唯一规则直接冲突）

- **问题**：
  - **`09` 的写法**：
    - L551 “清除一个 Goal”：“……用户仓库中若已有 seal 或地标 ref，一并删除；……已推送的分支是否保留由用户选择”。
    - L553 “清除全部”：“从已知检出中删除 `refs/tower/*` 与 seal 分支 `refs/heads/<前缀>*`（前缀取项目设置中的分支前缀，默认 `tower/`）”。
  - **与 `10` 的规则冲突**：
    - `10` L10：“删除只有 §10.3.2 / §10.6.2 按删除条件的 CAS 删除”。
    - L438 的删除条件：顶端是 Tower 自己的 seal、已在 base 中、未被检出、没有进行中的 git 操作。
    - L439、L440、L711：验收但不合并而归档的分支与已放弃 Goal 的分支 “用户拥有”“一律保留，清理也不删”。
    - L711：清理 “**不删** `refs/tower/_owner`”，并承诺 “你的提交不会因此丢失”。
    - L636、L643：两个守卫适用于 “任何分支” 的删除。
  - **照 `09` 实现的后果**：
    - **删掉人的提交**：`10` §10.6 明确预期人会在 Goal 分支上追加提交（重新 seal 表最后一行），这些提交只在该分支上；删除分支连同其 reflog 一起删除。
    - **改变正被检出的工作树**：删除某个工作树的当前分支，会使该工作树的 HEAD 指向不存在的分支。这正是检出守卫要防的情形。
    - **影响进行中的 git 操作**：进行中的 rebase 结束时要更新的分支已不存在。
    - **按前缀删除会扩大范围**：L553 按前缀模式删除，会删到用户自己建在同一前缀下的分支。`16` L287 的前缀默认值写作 `tower`，`09` 写作 `tower/`，带不带分隔符决定模式是否会匹配 `tower-…` 一类分支。
    - **删除多机租约**：L553 删除 `refs/tower/*` 时一并删除 `_owner`。另一台机器正持有租约时，它的续租 CAS 会失败（失败的去向也没有写，见 §5 观察 9）。
    - **“已推送” 在 M1 中无法判定**：M1 不推送、不轮询远端（`10` L1148），所以 “已推送的分支由用户选择” 没有可靠的依据。
  - **`06` 的命令定义不含这一步**：`privacy.purge`（`06` L933）只删除载荷、写墓碑、删除 Pi 会话，不写用户仓库，所以两份文档对 “清除” 的效果说法不同。
- **为什么是重要**：
  - 照 `09` 的唯一描述实现，会违反 `10` L10 的不变式与 ADR-192 的 “用户拥有” 规则。
  - 后果是删掉人在 Goal 分支上的提交。提交可能还能从 HEAD 的 reflog 或悬空对象中找回，但链接工作树被移除后它的 HEAD reflog 也不在了，普通用户实际上找不回来。
  - 清除是人发起的，但人想清除的是 Tower 的记录与副本，不是自己的提交。`10` §10.6.2 对 “清理 Tower 引用” 也明确承诺了不删人的提交。
- **文档位置**：`09` L551、L553；`10` L10、L438–440、L636、L643、L711；`06` L933；`16` L287。
- **期望的回答形态**：在 `09` §9.12.4 改一句，并在 `06` `privacy.purge` 行引用：
  - 清除对用户仓库的写入只走 `10` §10.3.2 的删除条件与两个守卫：满足条件的 Tower 分支照常删除；其余一律保留，结果列出 “分支 <B> 未删除：<原因>”，与清理相同；
  - 地标 ref 按 §10.6.2 删除，不删 `refs/tower/_owner`；
  - “清除全部” 不按前缀模式删除，只删各 Goal `integration.performed.branch` 记录中满足删除条件的分支；
  - 删去 “已推送的分支由用户选择”（M1 中无从判定），或改为 “对保留的分支，由人在清除结果中逐条决定”；
  - G46 第十组补一组：已放弃 Goal 的分支上有人的提交，执行 “清除一个 Goal”，期望该分支与 `_owner` 都还在，清除结果列出原因。

### D7 诚实与验证

**R67-D7-01｜次要**（`10` L1151 只登记了 “逐个改写多个 seal 后再合入” 一种判定不到的情形。git 的 patch-id 包含 diff 上下文，squash 前 base 在改动附近有变化时同样判定不到，这在活跃仓库中并不少见。判定不到时，侧栏随后写 “14 天未合入”）

- **问题**：
  - **正文**：非祖先合入 “以 patch-id 判定：base 中有提交的 patch-id 等于本次合入的 seal 段整体差异的 patch-id → `integrated`”；之后只写 “逐个改写多个 seal 后再合入时没有提交与整段相等，Goal 停在 `accepted`……（M1 已知限制）”。ADR-194 的说法是 “squash 多个 seal 时同样能判定”。
  - **git 的行为**（本轮实验确认）：patch-id 忽略行号与空白，但包含上下文行。
    - base 在 Goal 改动的 3 行之内先有一处无关改动，再 squash 合入（合并没有冲突）：squash 提交的 patch-id 不等于整段差异的 patch-id；
    - base 的改动离得远时相等。
    - 同理，判定不到的还有：合入时解决过冲突；人把 Goal 的改动与自己的修改合成一个提交；只合入了其中一部分。
  - **界面后果**：Goal 停在 `accepted`。14 天后侧栏显示 `◇ 14 天未合入 · 建议归档`（`04` L194），把一个 Tower 判定不到的状态写成了事实。`04` 中没有告诉人 “若你已以 squash 合入而 Tower 没有认出，可选择‘验收但不合并’”。
- **为什么是次要**：
  - 方向安全：不会误判为合入，Goal 停在 `accepted`，人可选 “验收但不合并” 归档，分支保留。
  - 但已知限制写得比实际窄，界面上还出现一句不真实的 “未合入”，与 “事实与声明分离” 不符。
- **文档位置**：`10` L1151；`15` ADR-194 观察 3；`04` L194、L1382；`14` G40(h)（L127）。
- **期望的回答形态**：
  - `10` L1151 把已知限制改为：“base 中没有与整段差异 patch-id 相同的提交时判定不到，例如 squash 前 base 在这些改动附近已有变化、合入时解决过冲突、与其他改动合成一个提交，或逐个改写多个 seal”。
  - `04` L194 的提示改为 “14 天未观测到合入”，并给出 “已以其他方式合入？选择‘验收但不合并’” 的说明。
  - G40(h) 的 squash 一组注明 base 未在改动附近变化；另补一组 “base 在改动附近有变化后 squash”，期望停在 `accepted` 并显示上述说明。

  - **D13** 3 条：R67-D13-02（重要）、R67-D13-01、R67-D13-03。
  - **D4**、**D7**、**D11**、**D12**、**D15** 各 1 条：R67-D4-01、R67-D7-01、R67-D11-01、R67-D12-01、R67-D15-01。
  - **第 66 轮核验**：5 条全部解决；§5 的 15 条观察全部落地；放弃的撤销条删除干净。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 194，(v) 96 条命令，(e) 179 对，(D) 178 个短语，(z′) 35 处，(T) 9 种，(H) 77 个提示键，(J) 135 对，(C) 19 行，(M) 1 个，(B) 1 条，(O) 31 行）。
    - Pi v1.2.0：另抽查 10 条承重引用，行为全部成立，行号在 “±≤5” 之内。
    - git 语义：整段 revert 使 base 回到合入前；patch-id 对 diff 上下文敏感；`prunable` 管理目录中的 rebase 状态只有 `worktree prune` 能清除。三项均经实验确认。
    - 排期结论成立：WBS 122.73；余量 0.12 / 0.26 / 0.43 / 0.94 / 0.24；依赖链 19.91；增人 128.63、T 23.75、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **对人的承诺与宽限期**：`00` L84 写 “直接改动 Goal 工作目录中的文件，会让 Goal 暂停”；`04` L1510 写 “任何非终态都进入 `paused(external_change)`……任何状态下检测到都先暂停”。ADR-194 之后 `integrated` 是例外（`10` L397），只有 `03` 同步了。唯一定义清楚，按它实现不会出错。建议两处补 “合入后的 24 小时宽限期内不检测，撤销合入时补做一次”。
    2. **`03` L65 的引用**：“上表只在 `accepted` 与 `paused(external_change)` 行写出这条边”。`paused(external_change)` 不是 §3.2 表的行，而是 §3.2.1 表的行，其出口列也没有写这条边，只在 “命令 / 守卫” 列中提到。建议改为 “§3.2 表的 `accepted` 行与 §3.2.1 `external_change` 行”。
    3. **卫星重建期间的判定**：`accepted` 中卫星丢失只设 `satelliteRebuilding`，状态不变（`10` L1219）。这时人合入 seal，“卫星树等于该 seal 的树” 无从比较。若判为不成立，(ii) 会把当前 seal 当作 “较旧版本”，使 `accepted` 降回 `in_review`。建议把 `satelliteRebuilding` 与人工编辑检出、活跃 Run 一样列为 (i) 的 “临时条件”：只记 Fact，重建完成后按状态再判定。
    4. **`integrated` 中的其他命令**：`contract.amend`（`06` L870）没有写 `integrated` 中的效果；`goal.abandon` 允许从 `integrated` 发起（“任何非终态可放弃”），会把已合入的工作记为放弃。返回 `E_STATE` 或保持现状都说得通，建议在 `06` 写明。
    5. **`pendingOpenings` 在撤销合入后**：保留并在下一次 Run 送出，ADR-186（`16` L560）已覆盖，本轮核对无问题。
    6. **Tower 未运行期间对卫星的写入**：`in_review` / `accepted` 的新鲜度依赖文件系统事件（`07` L275、`13` L354），正文没有写监视（重新）建立时先做一次 decisive。验收与 seal 闸口的完整重哈希会拦住不一致，所以不违反不变式。建议在 `07` §7.3.2 补 “监视建立时（含启动后）先做一次 decisive”。
    7. **备份 bundle 的保留**：
       - `10` L453 写 “备份 bundle 按 §10.16.3 保留”，L700 写 “审计长期保留依赖影子与备份 bundle”，而 §10.16.3（L1245）在 `integrated` 归档时即删除 bundle；
       - `integrate:"none"` 归档的 bundle 何时删除没有写；
       - 已归档 Goal 的影子在 180 天内被外部删除时，情形 B（L1216）既无 bundle 也无卫星。这时清理写 “无法核对：审计数据已过保留期”，说的是 “过期” 而实际是丢失。
       - 建议 L700 改为 “依赖影子”，L438 的原因改为 “影子已删除或已过保留期”。
    8. **已放弃 Goal 的非永久证据**：非永久重放包与完整日志的保留写作 “Goal 归档后 30 天”（`07` L500、`06` L1115、`13` L364、`09` L484），已放弃的 Goal 永远不满足 “归档”。ADR-057 只把事件的分层保留扩展到了 `abandoned`。磁盘压力时仍会被回收，所以只是存储问题。建议写作 “归档或放弃后 30 天”。
    9. **租约与用户仓库中的 ref**：
       - `06` L182 的续租 CAS 失败（ref 被删或已被他人改写）时的去向没有写；
       - `10` L1260 “默认情况下用户仓库中没有任何 `refs/tower/*`” 没有考虑 `_owner`；
       - `10` L671 “删除只有 §10.3.2 的 CAS 删除” 漏了 §10.6.2。
       - 建议续租失败按 “发现 `_owner` 属于另一个 `installId`” 一行重新判定，另两处改为引用 `10` L10。
    10. **证据的导出并清除**：`04` L1277 的 “导出并清除早于 N 个月的证据” 没有里程碑标记，而它依赖 M2 的 `.towergoal` 导出（同一行标 M2）。M1 自用期很难触及 10 GB 阈值（`13` L366）。另外，磁盘压力下的清理顺序，`13` L364 写非永久重放包 “最先删除”，`10` L443 先删残留卫星，口径不同。建议标注 M2，并统一为引用 `10` §10.3.2。
    11. **取舍判断**：见 §3.3。
- **设计是否完成：ADR-194 的主干已收敛；本轮的扫描发现了一处与核心不变式冲突的旧路径。**
  - 第 66 轮的 5 条都在唯一定义处关闭，lint、Pi 引用与排期全部成立。
  - 剩下 8 条中，7 条次要的都可以各用一两句话关闭；1 条重要的也只需把隐私清除改为复用已有的删除条件与守卫：
    - 隐私清除对用户仓库只走 `10` §10.3.2 的删除条件与守卫，不按前缀删除，不删 `_owner`（R67-D13-02）；
