安全不变式全部保留：
- Tower 不会自动把机密交给 Agent 可影响的进程。模型密钥仍只经运行时注入、只在 Host 内存中，Host 环境中仍没有任何模型密钥。

- `httpIdleTimeoutMs` 仍经受保护的设置读取，不进入任何环境。
- 只读启动时的终止只发信号、不写数据库，只处理令牌已确认或在进程树中的进程。
- 卷未挂载时 Tower 不删除、不改名、不重建任何目录。人的工作现场不自动删除。
- 沙箱外的 Tower 进程不在 Agent 可控的 git 元数据上运行 git。

## R106-D5-01（次要）：`provider_unavailable` 的探测在哪个进程运行

按指示。
- **唯一定义** `06` §6.1.4 第 5 项（L101）补 “探测在哪个进程运行”：
  - 只在 Engine Host 中，从不在 Supervisor 中：用该 Goal 所在打包分组中已存活、没有进行中 Run 的 Host。
  - 没有这样的 Host 时，按正常的 Host 启动路径为探测起一个短时 Host：同一 Host 环境与分发器（`05` §5.3.6），同一 `host.spawn` 检查与导入密钥的注入（`11` §11.7.1）。它不建会话、不开 Run、不占 Run 槽位，同组待探测的 Goal 共用，本轮探测完成即退出。它不经准入、不计入整机预留，每个打包分组至多一个（如实登记）。
  - 连接检查因此经 Host 的分发器与 CA 变量，`$VAR`、`!` 命令与导入的密钥按 Host 的规则求值，与 Run 中的请求相同。
  - `getAuth` 的 `undefined` 与拒绝都计为失败，引文改为 `ai/src/models.ts:300-314`（观察 11）。
- **如实登记**：短时 Host 不加载用户扩展。只由扩展新建的 provider 在其中为未知、探测失败；这类 Goal 只在同组有已加载该扩展而空闲的 Host 时自动解除，否则由人 `继续`。
- **引用处**：`11` §11.7.1（L517）“只在 Host 中执行” 一句引用。
- **测试**：C39 (e)（`05` L1500）补一组：一个只靠导入密钥的 provider，服务它的 Host 退出之后，探测在短时 Host 中执行，Supervisor 中没有 `getAuth` 调用，也没有执行 `!` 命令。
- ADR-207 R79-D8-01 加〔ADR-234 更正〕。
- **为什么短时 Host 不与 ADR-232 冲突**：ADR-232 否定的是标注用的 “只做检查的进程”。这里起的是同一个 Host（同一启动路径与环境），不是另一种进程。

## R106-D5-02（次要）：Pi 的 SDK 每次请求都读 `httpIdleTimeoutMs`

按指示。
- **唯一定义** `05` §5.3.6 代理一行（L474）改写为 “两处读取”：
  - 分发器在 Host 启动时读一次；
  - Pi 的 SDK 会话在每次模型请求时，从该 Run 在步骤 ② 新建的设置管理器读取同一设置，作为请求时限（`sdk.ts:340-349`），读到的是载入时的值；
  - 所以 Host 存活期间的改动从下一个 Run 起改变请求时限，分发器仍取启动时的值，两者中较小的起作用（如实登记）。
- **值无效**：
  - Host 启动时读到：仍按 F4b。
  - Host 存活期间变为无效：适配器在每个 Run 的步骤 ② 之后读一次，抛出时该 Run 的准备按 F4b 失败（`prepare_failed`），不开会话。
  - 写明不做这一读取时 Pi 的行为：重试、F6 与探测反复解除（见核实）。Run 中途设置被重新载入而变为无效的，仍是 Pi 的这一行为（如实登记）。
- **C43**（L1506）：改为在不经 SDK 请求时限的路径上断言。
  - `httpIdleTimeoutMs` 为 5 s 时，一个 10 s 不发响应头的 HTTP 类 MCP 服务器的连接以 undici 的响应头超时失败；设为 20 s 时成功。
  - 分发器漏掉该设置、停在默认 300 s 时，前一次会成功，测试因此失败。
  - 另补一组：Host 存活期间把设置改为无效值。
- D63（L1450）补 SDK 的读取，引文改为 `:211`。
- ADR-233 R105-D5-01 加〔ADR-234 更正〕。
- **不取 “受保护设置在 Host 存活期间固定返回启动时的值”**：那会使 Tower 与终端中 SDK 的读法不同，而且仍要定义启动之后的无效值。

## R106-D6-02（次要）：Supervisor 没有重启时进入只读，进行中的写回、重建与接管

按指示，单一定义在 `06` §6.8 F8 “进行中的写回、卫星重建与接管”（L1201）。
- **进入只读时**：这些操作在本进程中停止，文件系统上能回退的立即回退：
  - 写回：照 §6.4.3 失败出口的 ①、②；
  - 卫星重建：丢弃未完成的旁路目录；
  - 接管物化：已写出的部分目录不删除，下一次接管改名保留，命令返回 `E_STATE`。从 `running` 接管时，drain 的目标照 F8 并入 `app_quit`，原目标放弃（ADR-144）。
- **待补失败出口列表**：要写数据库的失败出口（写回的 ③ 与其 Needs-You、重建失败的事务）与 F8 原有的写不进的 drain 目标，一起记入 Supervisor 进程内的这一列表。
  - 解除时先按列表执行，按解除时的状态求，例如写回 ② 未完成的照 ③ 改名并重建；
  - 然后执行推迟的中间状态检查与其余规则。
- **Supervisor 在解除之前重启**：列表随进程丢失。数据库中留下的 `syncing`、`satellite_rebuilding=1`、`draining_for`，由 §6.1.6 对应行作为推迟的中间状态检查，在解除时续做。
- **`syncing` 不变式写准确**（§6.4.3，L922）：
  - `syncing` 只存在于三种时候：本进程中正在写的有限时间内；崩溃到重启之间；§6.8 F8 的只读期间（解除时消除）。
  - 列表中的写回仍算写回进行中，`goal.delete_kept` 对它返回 `E_BUSY`。
  - §6.1.6 人工编辑检出一行（L145）同步。
- **测试**：G35e (q) 补一组：写回中途写满。
- ADR-231 R103-D6-02 加〔ADR-234 更正〕。

## §5 的观察

1. **更窄的读取点**：tower-goal 新注册 `turn_start` 处理器（`05` §5.6.5 L1006），经 `bridge` 读列表，并等移除完成后才返回（理由见核实）。
   - 窗口缩到一次模型调用，以及其后、下一次 `turn_start` 之前的压缩与摘要请求。
   - 同步：`11` §11.7.1 改写；D64（L1451）补依据；C44（L1507）与 G46 (d) 第十组改为 “下一次模型调用”。
   - `00` §0.5.1 一行不涉及窗口，不改。
2. **F8 中止的判别**：`06` §6.1.6 “Run 中崩溃” 一行（L149）收窄为 Host 存活一支；Host 已不存在时照同行的两种情形取。另如实登记：按可观察状态判别，会收入 Supervisor 重启几秒内其他来源的中止。
3. **实况行**：`12` §12.6.4（L395）补 `已中止（磁盘已满）· 释放空间后恢复`。G35e (q) 的 `已暂停 · 磁盘已满 · 释放空间后自动恢复` 限定为 drain 写入成功的一组。
4. **③ 中止的会话**：Host 按进程树与令牌的并集终止这一窗口中派生的进程，并 `dispose` 会话。开场已追加在会话文件中时，重新准入可能再出现一次（如实登记）。
5. **复查集合**：F8 并上本次触发 `ENOSPC` 的卷（只在进程内），`16` §16.2.6 同步。
6. **检查 i 的位置**：F8 一项写明在 a 之前先判，命中即短路。
7. **只读启动时已写入 `draining_for` 的 drain**：属于推迟的中间状态检查。`app_quit` 不并入，结果为该 drain 自己的目标；`take_over` 在解除时执行。
8. **`由扩展处理认证` 的含义**：`11` §11.7.1 写明它只说明 Tower 不注入、不说明认证成功；请求按 F7 失败时以 F7 的条目为准。界面文字不改。
9. **规则 6 与横幅**：
   - `08` §8.10.5 规则 6（L696）补侧栏一行的生命周期、多个时合为一行，以及它不进入 “下一件”；
   - `12` §12.8 横幅在自检不足 2 GB 而未写满时以 `磁盘空间不足 2 GB` 开头，后缀追加与消失时 `polite` 播报；§12.13.3 读屏表同步。
10. **投递目录一组**：G35e (q) 以测试钩子留下一个已退出 Host 的 `run/<hostId>/` 目录，断言不再恒真。
