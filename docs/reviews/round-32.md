>   1. **按目标拒绝 `process-info*`**（对非自身进程）：能阻止对其他进程的 `lsof -p` 一类查询，但**不能**阻止经进程参数接口读取其他进程的命令行与环境，也不能阻止进程列表枚举。

>      - 对 Apple 平台二进制（`/bin/bash`、`/bin/sleep`），即使不在沙箱中，非 root 进程也只能读到命令行，读不到环境；

### D6 系统架构与可靠性

**R32-D6-01｜重要**（Run 令牌识别读不到 Apple 平台二进制的环境）

- **问题**：
  - ADR-142/144 识别 Agent 后台进程的唯一依据，是读取同一用户进程的环境，看其中是否有 `TOWER_RUN_TOKEN`。依据：`10` L377“macOS 以 `sysctl(KERN_PROCARGS2)` 读取进程环境”，`06` L141、L194，`11` L353–358。
  - 本机 macOS 27.0.1 实测：非 root 进程对 Apple 平台二进制（`/bin/bash`、`/bin/sleep`）只能读到命令行，读不到环境，而且读取本身**成功返回**。
  - 后果如下：
    - **识别不到**：Agent 用系统 shell 写的后台循环、`sleep`、`tail -f`，以及其他系统自带工具，一旦脱离进程树（shell 退出后被收养、`nohup`、`setsid`），令牌全扫描就认不出它们。
    - **文档断言不成立**：`10` L377 写“`sh -c 'x &'`、`setsid`、双重 fork 都不影响识别（令牌随环境继承）”，这对上述进程不成立。
    - **分支覆盖不到**：`06` L141 只定义了“读不到环境（权限、平台接口失败）→ 提示”。实际情形是“读取成功、环境为空”，实现者会把它当作“没有令牌”跳过。
    - **结局**：settle 第 3 步不终止这些进程；`bg_process_survived` 不出现；端口段不释放；它们之后的写入被误判为外部写入（已知误判 (b)），但卡片的前提，即“进程不带令牌是因为 Agent 主动清空环境”，并不成立。
  - G35/G35c 的后台进程全是 node（`vite`、`tsc`），覆盖不到这一类。
- **为什么重要**：
  - macOS 是 M1 唯一平台，用系统 shell 放后台循环是 Agent 的常见做法。
  - 存活进程在 Goal 结束后继续占用 CPU、端口与文件写入，界面不显示，违背“settle 之后 Agent 不再动手”的承诺。
  - 这是对既有机制前提的实测证伪，不是边缘情形。
- **文档位置**：`10` L377–379；`06` L141、L194；`11` L351–358；`13` §13.8.3；`14` G35、G35c（L115、L117）。
- **期望的回答形态**：
  - 在 `10` L377 写明这一平台事实。
  - 读取成功但环境条目为零时，结果是“未知”，而不是“没有令牌”。
  - 为“未知”选定识别手段，例如：
    - Run 启动时记录会话或进程组，作为辅助条件；
    - 或者用别的成员标记，使脱离进程树的系统二进制仍能归属到 Run；
    - 或者如实登记为新的已知误判 (d)：写明结局（不终止、提示措辞、端口段处理），并在 settle 时对“未知且在本 Run 时间窗内出现、父进程为 launchd”的进程给出提示。
  - G35c 增加两组：
    - 以系统 shell 放到后台的循环；
    - 以 `nohup` 脱离的 `sleep`。
  - 期望按选定规则识别或提示。

### D11 安全与自主度

**R32-D11-01｜重要**（ADR-157 的平台前提在 macOS 上不成立；闸门的判据不可满足；预案的范围窄于它要关闭的威胁）

- **问题**：
  1. **前提与实测不符。**
     - `11` L336、T33（L566）、`10` L58、L100、`16` L477、`15` L1332 都写 Seatbelt 能拒绝对非自身进程树的 `process-info*` 与 `kern.procargs2`/`kern.proc` 读取，`10` L58 甚至写“已在沙箱层面关闭”。
     - 本机 macOS 27.0.1 实测（见文首）：内核的进程参数接口不经 Seatbelt 的 `process-info*` 或 `sysctl-read` 检查，`(deny default)` 也挡不住。只要目标进程不是平台二进制，沙箱内进程就能读到它的命令行和环境。
     - 因此 A12(a) 几乎必然不通过，M1 实际运行的会是预案分支。
  2. **闸门判据中有一半不可满足。**
     - A12(a) 期望“对自身进程树的 `ps`、`lsof -i` 照常可用”（`14` L62）；`11` L336 写“`ps`、`lsof` 对自己的进程照常可用”。
     - `/bin/ps` 是 setuid root，在任何 Seatbelt 配置下都无法执行（实测）。
     - 这一判据与“拒绝是否生效”无关，却会单独让闸门失败。这也说明现有的 S2 中 `ps` 本来就不可用，`11` 的说法不实。
  3. **预案的范围窄于它要关闭的威胁。**
     - T33 的威胁是“同一用户的进程信息（命令行参数、**环境**）被并行的 Agent 观察”。
     - 预案只做一件事：带凭据的 git 远端不执行网络命令。闸门失败时，同一通道还会暴露以下由 Tower 自己放进进程环境或参数的值：
       - 验证器为标准注入的密钥。它们在验证进程的环境中（`11` §11.7 L400），验证进程多为用户工具链中的非平台二进制，其他 Goal 的 Agent 在验证期间能读到。
       - 其他 Goal 经 `secrets.access` 批准、只对单次 bash 注入的值（`11` L401）。如果命令把它展开到参数中，平台二进制的参数同样可见。
       - Engine Host 进程环境中透传的云 SDK 凭据（ADR-049，`11` L398），是否可读取决于该进程的签名标志，需要实测。
       - MCP 服务器的显式授予变量，以及 Supervisor 继承的用户环境。
     - 这些值的唯一残余防线是 §11.7 的精确匹配脱敏。脱敏只作用于进入模型的工具结果，挡不住经允许域名的外传，也挡不住改变编码后的值。
     - T33 的残余评级只有“低（S2，闸门通过时）”与“高（S0）”，**没有“S2、闸门未通过”这一档**，而这恰恰是最可能的 M1 状态。
     - `11` L373 的规则“Tower 不把可能含凭据的值放进命令行与环境”明确把验证器注入的密钥排除在外，靠的是 Agent 读不到。这一点在预案分支下也没有重新评估。
  4. **“带 token”的判定没有定义。**
     - 预案拦截“URL 中带密码或 token 的远端”，放行“只带用户名的 URL”（`10` L76–80）。但没有规则区分“只有用户名”和“token 放在用户名位置”，后者是常见的 CI 与个人令牌写法。
     - 按“有没有冒号”实现时，后者被放行，凭据正好经这条通道暴露。
- **为什么重要**：
  - 第 1、3 项会让 M1 用户在 T33 上得到一个过于乐观的评级，而且被正文的“已关闭”误导。验证密钥“只注入验证器”的承诺，在多 Goal 并行这一产品核心场景下，实际上只靠脱敏。
  - 第 2 项让闸门本身无法给出有意义的结论。
  - 按评审规则，“有闸门、有预案”的风险视为已处理，前提是闸门与预案本身没有缺陷。这里两者都有缺陷，所以定为重要。
  - 不定为阻断，因为修正主要是诚实登记，加上有限的规则补充，不需要新架构。
- **文档位置**：`15` L1331–1336；`11` L336、L373、L398–402、L566；`10` L58、L76–80、L100；`16` L477；`14` L62（A12）、L130（G43(j)）、L131（G44(d)）、L132（G45(a)(f)）；`05` L1405（C29(b)）。
- **期望的回答形态**：
  - **前提**：在 ADR-157 中如实记下“Seatbelt 无法拒绝进程参数接口”这一预期。A12(a) 仍然执行，用来确认当时最新的 macOS 版本上的行为。正文中“已在沙箱层面关闭”改为条件句。
  - **闸门判据**：自身进程树的可用性改用非 setuid 的工具判定，例如 `pgrep`、`lsof`，或者从判据中删去。
  - **T33 增加“S2、闸门未通过”一档**：
    - 列出可经此通道读到的值的类别：git 远端凭据（预案已拦截），以及验证器注入、`secrets.access`、Host 透传、MCP 授予等环境值；
    - 逐类给出缓解或如实的残余。例如：在验证运行期间，是否对同一机器上的其他 Goal 降低信任；验证器密钥能否改用文件描述符或只读文件传递；`secrets.access` 的提示中写明“同一时间运行的其他 Agent 可能读到”。
    - 写明评级。
  - **判定规则**：带 password 成分的 userinfo 一律拦截；只有用户名时，按 `11` §11.7 的模式与熵规则判断。命中令牌形态的拦截，不确定时按“带 token”处理（保守）。G45(f) 加一组“token 在用户名位置”。

### D13 隔离、git 与并发

**R32-D13-01｜次要**（`baseTip` 中用户一方的“时间”偏新；`in_review` 前的获取是否阻塞未定义）

- **问题**：
  1. **时间代理有系统性偏差。**
     - 用户一方的时间是“镜像观察到该值变化的时间”（`10` L104），而每个时机中，镜像同步用户检出排在 Tower 获取之后（`10` L264–266、L87）。所以只要用户一方在本轮首次被观察到变化，它就一定显得比 Tower 的获取更新。
     - 情形：用户在上游强制推送**之前**执行过 `git fetch`，镜像在下一个时机才观察到这个旧值；同一时机中，Tower 取到的是强制推送后的新值。两者分叉，按规则取用户一方，也就是强制推送前的旧值，并提示“使用较新获取的版本”。
     - 后果：
       - 这句提示不真实；
       - 新 Goal 准备时以上游已改写掉的提交为 base；
       - `integrated` 观测以旧值为准。
     - 用户检出中远端跟踪引用的 reflog 默认开启（非裸仓库中 `core.logAllRefUpdates=true` 覆盖 `refs/remotes/`），它记录了用户实际获取的时间，是更准确的来源。
  2. **“进入 `in_review` 之前”的获取。**
     - `10` L83 把它列为获取时机，但没有写 `verifying → in_review` 是否等待它完成，也没有写超时。
     - git 的 HTTP 获取默认没有总时长限制。如果阻塞，网络挂起时 Goal 会停在 `verifying`，`review_ready` 迟迟不出现。如果不阻塞，“之前”的说法就不准确。
     - `13` L301 写“不阻塞”，但那一行仍是 M2 的 5 分钟轮询（见 R32-D15-01）。
- **为什么重要**：
  - 第 1 项是 R31-D13-02 修正后的同类残余：一条 `◇` Fact 提示可能说错话，违背诚实语法。概率低，所以定为次要。
  - 第 2 项是未定义的先后关系。实现者如果放进转移路径，会出现无限等待。
- **文档位置**：`10` L81–87、L102–109、L264–267；`04` L1325；`13` L301；`03` §3.2；`14` G45(c)(d)。
- **期望的回答形态**：
  - 用户一方的时间：优先取用户检出中该远端跟踪引用 reflog 的最新时间戳，没有 reflog 时才用观察时间；两者相同时取 Tower 一方。
  - G45(c) 增加上述“强制推送前已 fetch”一组。
  - 写明 `in_review` 前的获取不阻塞转移：转移照常进行，获取在后台完成后刷新提示；或者规定阻塞的上限（例如 30 s），超时按失败处理并记 Fact。
  - `13` 列出 M1 的触发与预算。

**R32-D13-02｜次要｜M2**（推送失败后的队列状态不在枚举中）

- **问题**：
  - `10` L95 与 `16` L477 写推送失败后“合并队列条目保持‘待推送’”。但 `MergeQueueEntry.state` 的取值是 `waiting · rebasing · reverifying · awaiting_reacceptance · integrating · awaiting_remote · done · failed · needs_human`（`10` L1008，`16` L275），没有“待推送”。
  - 条目等待人决定期间，是否占住该 base 的 FIFO（并发度 1）没有写。R31-D11-01 已要求这一点。
- **为什么重要**：
  - 实现者会自造状态，或者随意映射到某个现有状态，两种做法的 FIFO 行为不同。
  - 占住时，同一 base 的其他 Goal 全部停住；不占住时，人重试推送就要重新排队。
- **文档位置**：`10` L94–98、L1002–1022；`16` L275、L477；`08` L208；`14` G44(e)。
- **期望的回答形态**：
  - 写明进入 `needs_human`，原因字段为 `push_failed`，并让出 FIFO：后续条目继续，人选“重试推送”时以 Q2 重新入队。
  - 或者明确占住 FIFO 并写明理由。
  - G44(e) 第七组补一条同 base 的第二个条目，期望符合所选规则。
