## 1. 总评

ADR-060（卫星克隆 + 影子 git 目录）的方向正确，第 3 轮的两个阻断项按原攻击面都已关闭。我复现了第 3 轮的实验：植入卫星配置的 fsmonitor 和 clean filter 不会被触发，用户仓库也不再出现悬空 ref。ADR-061 至 ADR-070 也基本落地。

但新架构带来了新的攻击面与脆弱点，其中两条是确定的沙箱逃逸：

1. **嵌套仓库 / 子模块**：影子上下文对 gitlink 运行 `status` 或 `add` 时，会在嵌套仓库中启动子 git，执行该仓库中由 Agent 写入的 filter。我在 git 2.56 上复现了。
2. **卫星 `.git` 配置**：它整个归 Agent 所有，但用户的 IDE（“我来改”流程）、用户扩展的 `pi.exec("git …")` 和 MCP git 服务器都会在沙箱外对卫星运行 git。

其余问题：
- 影子对象经 alternates 借用用户对象库，并不独立；
- 没有处理 LFS、部分克隆和卫星远端；
- ADR-062 让项目生命周期脚本在验证槽位中改写第三方依赖，不触发任何哨兵；
- pnpm 主版本无法从 lockfile 判定，Corepack 已不随 Node 25+ 分发；
- 决定性指纹的实测耗时远超预算；
- 26 周甘特图违反了自身的依赖关系。

## 4. 追问清单（新增与残留）

编号格式：`R4-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。

### D1 原论述契合度

**R4-D1-01｜次要**
- **问题**：
  - `04` §4.5.1 的线框与 §4.5.3 的可见性规则冲突。“等你”一列有 6 个展开区块，超过自动展开 ≤ 4 的上限；Changes 区块全部展开，规则却是“摘要一行”；表中的例子说账本折叠，线框中却是展开的。
  - Changes 区块的数字来自实时指纹（@9f3e1a），`打开改动视图（检查点 cp/37）` 打开的却是检查点 diff，两者可能不是同一棵树。
- **为什么重要**：原论述 P3 的“改变了什么”需要一个确定的口径。
- **文档位置**：`04` §4.5.1 L283-322、§4.5.3 L352-364；`12` §12.10.6。
- **期望的回答形态**：把线框标注为“人手动展开后”或重画；写明改动视图使用哪棵树（实时指纹，或带时间差标注的最近检查点）。

**R4-D1-02｜次要**
- **问题**：ADR-060 之后，`04` 中缺少面向用户的集成说明：
  - Goal 头部在 running 期间显示 `tower/G-0142-fix-double-charge`，但这个分支要到 seal 才存在；卫星中的分支名是 `tower/<goalId>`。
  - seal 会把 Agent 的多个提交压成一个（ADR-060 第 7 点），F7 与 §4.6.5 都没有告诉用户。
  - “我来改”打开的是一个 `origin` 为本地路径、位于隐藏 `.noindex` 目录中的独立仓库。
- **为什么重要**：原论述 P4 要求不读聊天也能知道“它改了什么、落在哪里”。用户在自己的 `git branch` 中找不到这个分支，就会回去翻 Trace。
- **文档位置**：`04` §4.5.1 头部、§4.6.5、§4.7.3 L560、F5/F7；`15` ADR-060 第 7 点。
- **期望的回答形态**：在 F5、F7 与 §4.6.5 中补文案，说明卫星的位置、分支何时出现及其名称、squash 行为；头部在 seal 之前显示卫星分支，或显示“尚未集成”。

### D2 Pi 哲学契合度

**R4-D2-01｜次要**
- **问题**：ADR-066 和 `05` L342 声称把用户的 `shellPath` 传给 `createBashToolDefinition`。但 v1.2.0 中 BT:248 是 `options?.operations ?? createLocalBashOperations({ shellPath })`：只要 Tower 传入了 `operations: sandboxedOps`，`shellPath` 就被忽略。Pi 自带的 sandbox 示例同样写死了 `spawn("bash")`（`examples/extensions/sandbox/index.ts:142`）。C28a（“`shellPath` 与用户设置一致”）因此会失败。
  - 核实成立的部分：`commandPrefix`、`exposeSessionEnvironment`（名称准确，默认 true，BT:221、250）、`spawnHook`；`PI_*` 在 `spawnHook` 之前写入环境（BT:193-211）。
- **为什么重要**：这是 R3-D2-01 想兑现的“你的 bash 设置照常生效”。
- **文档位置**：`15` ADR-066；`05` §5.3.5 L342；C28a。
- **期望的回答形态**：`sandboxedOps` 用 `getShellConfig(shellPath)`（`index.ts:496` 导出）构造 shell；或者删掉这个声明并改 C28a。

**R4-D2-02｜次要**
- **问题**：README L19 与 `00` §0.5 L66 仍无条件承诺“你的 Pi 扩展与配置照常生效”。实际情况是：
  - 用户的 bash 覆盖被取代（ADR-066）；
  - 高风险 Goal 与未确认清单的扩展使用隔离的 agentDir（`11` §11.8.2）；
  - `custom()` UI 不支持，设置写入被抑制；
  - 存在 `tool_call` 处理器时禁用 RPC（ADR-065）。
- **为什么重要**：这是对 Pi 用户的首要承诺，也是 D2 的核心。
- **文档位置**：README L19；`00` L66。
- **期望的回答形态**：加限定语，并链接一张“能力差异表”。

**R4-D2-03｜次要**
- **问题**：ADR-066、D50 与 C31 只把 `!cmd` 和 RPC `bash` 命令登记为沙箱外路径。但 Pi 提供了现成的钩子：`user_bash` 处理器可以返回 `{operations}`（TY:1465-1475），RPC 的 `bash` 命令也遵守它（`rpc-mode.ts:562-579`）。Pi 自带的 sandbox 示例就是这样做的（`sandbox/index.ts:229-231`）。
- **为什么重要**：Pi 的哲学是用扩展点由宿主加策略。有现成的钩子却只做登记，需要给出理由。
- **文档位置**：`15` ADR-066 最后一点；`05` D50/D51、C31；`11` T16。
- **期望的回答形态**：tower-goal 注册 `user_bash`，在 S2 下返回沙箱化的 operations；或者说明不这样做的理由（例如人自己输入的命令应当有完整权限），并写进 T16。

### D4 领域模型与生命周期

**R4-D4-01｜重要**
- **问题**：`worktree_missing` 有三种互斥的定义：
  - `03` §3.2.1 L83：入口是 running、paused、ready，出口一律“→ running”，做法是“从分支与最近检查点重建”。
  - `04` §4.18.3 L1063 与 `12` §12.6.5 L396：红色 ■ 的 `paused(worktree_missing)`。
  - `10` §10.16.2 情形 E（L609）：先 abort，Goal 留在 running、Mode 为 `preparing`，失败时为琥珀色 `stalled{worktree_missing}`。这又是一个“无 Run 的 running”，违反 `03` L54 与 `16` §16.1.2 L54，与 R3-D4-03 同类。

  此外：
  - 一律 → running，会覆盖人的暂停（入口为 `paused(human)` 时），也会让 `ready` 绕过槽位、依赖与评审余量的闸控；
  - 卫星在 claimed、verifying、in_review、accepted 期间被删，没有定义。in_review 期间的 fs.watch 会把“文件消失”当成指纹变化，触发 I2，然后对一棵空树验证；
  - ADR-060 之后分支在卫星里，随卫星一起丢失，“从分支重建”已不成立。
- **为什么重要**：同一事件有三种颜色、三种紧急度、三种转移，实现者只能猜。
- **文档位置**：`03` §3.2、§3.2.1 L83；`10` §10.16.2 情形 B/E/G；`04` §4.18.3；`12` §12.6.5；`16` §16.1.1、§16.1.7。
- **期望的回答形态**：一种定义。例如：
  - 入口为“任意非终态”，出口回到原状态与原 pauseReason；
  - 重建依据影子中的检查点或 pin，而不是分支；
  - in_review/accepted 下先检查卫星是否存在，再判定 I2；
  - 写明 Run 中途发生时 Mode 的语义，并同步 `03`、`04`、`12`、`16`。

**R4-D4-02｜重要**
- **问题**：
  - `03` L58 中 in_review 只有 accept、request_changes、I2 三个出口，缺少：
    - 手动重新验证（`07` 已有 `VerifyTrigger = manual`）；
    - ADR-068 中“在评审中改为授权后重新验证”；
    - `accepted` 状态下的重新验证。
  - `s0Grant(goal)` 的三态（`07` L315）没有存储模型：`02` 与 DDL 只能记录授予（`grant_s0_exec`），拒绝用什么 HumanDecision 记录没有写。
  - `use_defaults` 下验证阶段的授权请求超时后默认拒绝，于是 Goal 在**无人决定**的情况下以 `s0_denied` 进入评审，而 ADR-068 写的是“人拒绝”。
  - 从 `paused(s0_grant_pending)` 回到 verifying 时，`verifyFrom` 是否保留没有写，这决定了验收延续是否成立。
- **为什么重要**：在 M1 的 S0 分支下，每个 Goal 都会走这条路径。
- **文档位置**：`03` L58、§3.2.1；`07` L311-317、§7.10.3；`02` §2.9；`06` §6.3。
- **期望的回答形态**：
  - in_review/accepted 行补 `retry_verify` / `grant_s0_exec` → verifying；
  - 定义 S0 授权状态（未请求 / 待决 / 授予 / 拒绝 / 超时拒绝）以及对应的 decision kind；
  - 写明超时拒绝的标签口径（例如 `s0_denied{by:"timeout"}`）。

**R4-D4-03｜次要**
- **问题**：应用退出时正在验证的 Goal，`03` 与 `06` 说法不同。
  - `03` L57 写 `verifying → paused(app_quit)`。
  - `06` §6.1.4 第 2 条只对有活跃 Run 的 Goal 走 drain；verifying 没有 Run，会直接退出。
  - `06` §6.1.6 L120 重启后在 verifying 状态直接重跑；§6.1.4 第 5 条把 `app_quit` 一律当作 `resume` Run 入队。
  - `03` L82 允许 `verifying → paused(engine_crash)`，但 Host 崩溃不应取消验证。
- **为什么重要**：`transitions.ts` 与恢复代码会互相矛盾。
- **文档位置**：`03` L57、L82；`06` §6.1.4、§6.1.6。
- **期望的回答形态**：删掉 verifying 的这两个入口，或在 `06` 中补“回到 verifying”的分支。

**R4-D4-04｜次要**
- **问题**：`05` §5.5 L553 规定“abort + 有效 submit + 未答阻塞条目 → `question_timeout`”。如果 abort 的原因是 `app_quit`、`human` 或 `budget_*`，这条规则会覆盖原本的 pauseReason，以及它的 `autoResume` 语义。
- **为什么重要**：`app_quit` 会自动恢复，`question_timeout` 不会；选错了，Goal 就会在重启后停住或继续花钱。
- **文档位置**：`05` §5.5；`03` I4、§3.2.1。
- **期望的回答形态**：一张 pauseReason 优先级表（例如 human > app_quit > budget > question_timeout）。

### D5 Agent 架构与 Pi 集成

**R4-D5-01｜重要**
- **问题**：`05` §5.6.5 gate 第 7 条（L942）在 `tool_result` 中重算 `event.input` 的哈希，与 `approvedInput` 不一致就产生 severity 3 的哨兵并 drain。
  - 在 v1.2.0 中，同一个 `validatedArgs` 对象会依次传给 `tool_call`、`execute` 和 `tool_result`（`agent-loop.ts` 约 L727-760、L832-834；AS:659-700）。
  - 因此，任何在 `execute` 中修改自己参数的扩展工具或 MCP 工具，都会触发 `input_mutated_after_gate`，SDK 下也一样。这与 C30(b)（L1353 “能正常执行”）和“SDK 中理论上不会出现”相矛盾。
- **为什么重要**：误报会让合法的扩展工具每次都 drain，而且 severity 3 会进入注意力层。
- **文档位置**：`05` §5.6.5 第 7 条、C22、C30；`15` ADR-024、ADR-065。
- **期望的回答形态**：哈希比对只用于内置工具与 Tower 的沙箱 bash，或者在 `execute` 之前快照（例如在 gate 中保存深拷贝，再在 `tool_result` 之前的最早时点比对）；C30(b) 断言“不产生哨兵”。

**R4-D5-02｜次要**
- **问题**：ADR-065 的“RPC 只在用户扩展集合不含 `tool_call`/`tool_result` 处理器时可用”有两个问题：
  - 静态扫描只看用户扩展路径，但 Pi 内置的 mcp 扩展注册了 `tool_call` 处理器（`extensions/mcp/index.ts:1191`；它只等待服务器就绪，不修改输入），并且在 RPC 下排在 tower-goal 之后默认加载。所以 `05` L420 的“gate 之后不存在能修改输入的处理器”字面上不成立。
  - RPC 下没有 API 能枚举其他扩展的处理器（`Extension.handlers` 只出现在 SDK 的 `extensionsResult` 中），“启动自检”实际无法实现。
- **为什么重要**：这是 RPC 适用性的唯一判据。
- **文档位置**：`15` ADR-065；`05` §5.4.1 L420、C30。
- **期望的回答形态**：给内置扩展一个显式的白名单（附版本）；写明 RPC 下只能依赖静态扫描；C30 增加内置 mcp 的用例。

**R4-D5-03｜次要**
- **问题**：扩展之间是“先注册者胜”（RN:637-646）。tower-goal 以 `-e` 最先加载，它的 bash 不可能被之后的 `registerTool(bash)` 取代。所以 ADR-065 的“每次 `tool_call` 用 `getAllTools()` 复核”永远不会触发，C28b（“复核能发现，并降为 S0”）测的是不可能发生的情形。这与第 3 轮对 C28 的批评是同一类问题。
- **为什么重要**：不可能成立的契约测试要么永远失败，要么被改成空测试。
- **文档位置**：`15` ADR-065；`05` L358、C28b。
- **期望的回答形态**：把 RPC 复核定位为回归保护（与 SDK 相同），C28b 改为“模拟 Pi 改变优先级时能检出”。

**R4-D5-04｜次要**
- **问题**：
  - RPC 下 tower-goal 从哪里取 `commandPrefix`/`shellPath`，没有写（可用 `pi.getSettings()`，TY:1772）。
  - SDK 会话工厂在每次 `newSession`/`fork` 时是否重新传入 `customTools`，没有写。
- **为什么重要**：漏传一次，就会在那次会话中回落到不受沙箱限制的内置 bash。
- **文档位置**：`05` §5.3.5、§5.4.1。
- **期望的回答形态**：各补一句，并在 C28a 中覆盖 fork 之后的会话。

### D6 系统架构与可靠性

**R4-D6-01｜次要**
- **问题**：
  - `refs/tower/<goalId>/base` 的删除时机：`10` §10.3.2 L159 是归档时，`06` §6.6.4 L942 是 180 天。
  - 删除卫星的前提：`06` L941 要求“最后一个检查点”同时在影子与用户仓库中，`10` 只 fetch 地标检查点。
  - 影子 `gc --prune=now` 在“空闲时”运行（`10` L649），但 §10.17 的锁表没有写它持有 `wtLock`，可能与正在进行、对象尚未被引用的检查点或决定性指纹赛跑。
  - `06` L905 称影子是“唯一副本”、可以被 Time Machine 备份。但由于 R4-D13-01，影子不能单独恢复。
  - ADR-070 的重放包不在 §6.6 的数据布局与保留规则中。
- **为什么重要**：这些是数据丢失窗口与备份承诺。
- **文档位置**：`06` §6.6.1、§6.6.4；`10` §10.3.2、§10.17。
- **期望的回答形态**：统一时机；影子 gc 持锁，并对新近对象设宽限期（`--prune=<时长>`）；修正“唯一副本”的说法；把重放包加入布局与保留表。

### D7 诚实与验证

**R4-D7-01｜重要**
- **问题**：ADR-062 为验证器依赖篡改开了新路径。
  - `07` L406 在槽位中、针对 pin 执行根与各 workspace 的 `preinstall`/`install`/`postinstall`/`prepare`，而槽位的 `node_modules` 是可写的 CoW 副本（L417）。
  - 这些脚本键不在 `criterionIndirection` 中（L737-746 只覆盖标准调用的 `scripts.X` 及其 pre/post）；`package.json` 不在 `config_changed` 中（L883）；`pass_mutated` 只检查被跟踪的文件。
  - 所以 Agent 只要把 `postinstall` 改为改写 `node_modules/vitest`，让它总是通过，就不会触发任何哨兵。这正是 ADR-021 与 R1-D7-02 要防的攻击。
- **为什么重要**：“已验证”是整个诚实语法的信任锚。这里的改动在 diff 中可见，但没有机器防线（与 R3-D7-01 同级）。
- **文档位置**：`07` §7.4.3 L400-410、§7.5.1、§7.6；`15` ADR-021、ADR-062。
- **期望的回答形态**：
  - 把生命周期脚本键及其调用的文件加入受保护集合（变化即 severity 3 哨兵）；
  - 生命周期步骤之后，按 depcache manifest 的树哈希复核第三方依赖目录，只放行声明过的生成路径（如 `node_modules/.prisma`）；
  - SP6c 增加攻击用例。

**R4-D7-02｜重要**
- **问题**：ADR-063 的主版本识别（`07` L382、`16` 规则 2）做不到它承诺的事。
  - **lockfile**：实测 pnpm 10.34.6、11.28.2、12.6.0 写出的都是 `lockfileVersion: '9.0'`，恰恰无法区分 ≤ 10 与 ≥ 11 这条唯一关键的边界。
  - **Corepack**：Node 25 起不再随 Node 分发（本机 Node 26.10 没有 `corepack`），而 `16` L813 与 P10 依赖它来遵守 `packageManager`。
  - **自切换**：没有 Corepack 时，全局 pnpm 12 会按 `packageManager` 自动切换到 10.34.6，并下载到用户全局的 `~/Library/pnpm/package-manager-store`，§16.8.1 没有这一行。后果按档位不同：
    - S2：Agent 写这个目录被拒；
    - V（禁网）：未缓存时下载失败；
    - S0：Agent 可以投毒 V 将要执行的 pnpm 二进制。
  - 没有 `packageManager` 字段时，实际运行的是 PATH 上的哪个版本，没有规定。
- **为什么重要**：前缀选错，M1 唯一支持的生态的私有存储就整体失效。这是 R3-D7-04 的同一根问题。
- **文档位置**：`15` ADR-063；`07` §7.4.3 L382；`16` §16.8 规则 2、L813；`14` SP6c P1–P12。
- **期望的回答形态**：
  - 识别顺序：`packageManager` → `devEngines` → 在项目根执行 `pnpm --version`；
  - 由 I 把确切版本的 pnpm 取进 `$SH`，并放在 A/I/V 的 PATH 首位；关闭自切换（`manage-package-manager-versions=false`）；
  - P1–P12 增加“Node 25+、无 Corepack”与“无 `packageManager` 字段”的用例。

**R4-D7-03｜重要**
- **问题**：`07` §7.4.1 L306 的 `ecosystemSupported(goal)` 没有定义。
  - 它在检查是否存在 exec 标准**之前**就返回 `execSkipped`。于是 Python 仓库中只有 artifact 标准的文档类 Goal，明明已被完整机器验证，却被标为“未经机器验证（生态未支持）”。
  - Node 加 Python 的混合 monorepo：要么在没有 venv 的情况下执行 `pytest`（永久 `verify_env_error`），要么连 Node 标准也一起跳过。
  - 有 `yarn.lock`、`bun.lock` 的 Node 项目落入“均未命中 → 不准备”（`10` L208），于是在空的 `node_modules` 上验证。
- **为什么重要**：标签是事实，不能按项目一刀切。
- **文档位置**：`07` §7.4.1 L306、§7.10.3；`10` §10.4.2 L208；`15` ADR-043、ADR-064。
- **期望的回答形态**：按标准与 lockfile 逐条分类；写明 yarn/bun 在 M1 中的去向（例如按“生态未支持”处理）；先判断有无 exec 标准，再判断生态。

**R4-D7-04｜重要**
- **问题**：卫星侧的物化没有规定。`10` L189 的卫星也从 depcache 物化，但改写 `.modules.yaml` 只出现在 V 列（`16` L809）。
  - 实测（pnpm 10）：把用另一个 store-dir 安装的 `node_modules` 复制过来，在无 TTY 时执行 `pnpm install --frozen-lockfile`，报 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`。Agent 的 bash 没有 TTY，所以它的第一次 install 就会失败。
- **为什么重要**：这是 M1 每个 pnpm 10 项目的首次体验。
- **文档位置**：`10` §10.4.2 L189；`16` §16.8.1 L809；`07` §7.4.3。
- **期望的回答形态**：A 列同样改写为 `$GS` 的 store，或设 `confirm-modules-purge=false` 并接受一次重新链接；P1–P4 增加这个用例。

**R4-D7-05｜重要**
- **问题**：stage 与安装器的规则互相矛盾，或会破坏常见配置。
  1. `10` L204 仍是 `pnpm install --frozen-lockfile --prefer-offline`，没有 `--ignore-scripts`，与 `07` L395 矛盾。
  2. stage 的 `package.json`“只保留依赖字段”（`07` L392-393）：如果因此去掉了 `pnpm.overrides`、`patchedDependencies`、`onlyBuiltDependencies`/`allowBuilds`、`packageExtensions` 或 npm 的 `overrides`，frozen 安装会因设置不一致而失败；pnpm 10+ 还会不构建任何依赖。
  3. 项目 `.npmrc`（scope registry、`node-linker`、`shamefully-hoist`）既不在 stage 清单中，也不在 `depsKey` 中，但 `16` L812 说 I 会读它。
  4. 生命周期脚本在禁网的槽位中执行：常见的 `"preinstall": "npx only-allow pnpm"` 会在每次验证时失败；`prepare` 常常是完整构建，它的耗时既不在 S（`07` §7.4.10）中，也超出了 5 s 的 prepare 预算；workspace 之间的执行顺序没有规定。
  5. 依赖 rebuild 的具体命令仍是“SP6 核实”。
- **为什么重要**：这是 M1 唯一生态的地基，按现状无法直接实现。
- **文档位置**：`07` §7.4.3 L390-410、§7.4.10；`10` §10.4.2 L204；`16` §16.8.1 L812。
- **期望的回答形态**：逐条裁决；写明保留哪些 `package.json` 字段（建议保留所有影响解析与构建的字段）；`.npmrc` 进入 stage 与 `depsKey`；给生命周期脚本定网络与超时规则；给出确切的 rebuild 命令。

**R4-D7-06｜次要**
- **问题**：`$VS` 配置哈希不符时的处置：`07` L380 是“重新生成 + `verifier_config_tampered`”，`16` L796 是“`verify_env_error` + `depcache_tampered`”。检测器与后果都不同。
- **为什么重要**：同一事件有两个哨兵 id。
- **文档位置**：`07` L380；`16` L796、§16.1.6。
- **期望的回答形态**：统一。

### D8 注意力与交互

**R4-D8-01｜重要**
- **问题**：M1 没有让人实际操作应用、勾选 human 标准的路径。
  - 预览在 M2，但 M1 的验收面板线框（`04` §4.6.5 L486）有 `[O 打开预览]`。
  - 用外部终端或编辑器打开卫星会暂停 Goal（§4.7.3 L560）；dev server 写入的任何被跟踪文件都会使验证失效（I2）；被忽略的本地文件（`.env.local` 等）不在卫星中（`clone --shared` 只带被跟踪的内容，见 R4-D8-02）。
  - pin 在用户仓库中只是隐藏的 `refs/tower/<G>/pin`，Goal 分支要到 seal 才出现（`10` L29）。
- **为什么重要**：原论述 P8 要求人检验成果而不必看过程。没有路径，human 标准在 M1 就只能凭信任勾选。
- **文档位置**：`04` §4.6.5、§4.7.3；`14` M1 范围；`15` ADR-059。
- **期望的回答形态**：一条 M1 人工检验流程。例如 Tower 生成一份 pin 的只读检出，播种本地文件，使用槽位的端口段；或者允许 in_review 期间打开卫星而不暂停，并写明对 I2 的影响。同时修正线框。

**R4-D8-02｜重要**
- **问题**：
  - S2 对整个密钥路径表读拒绝（`11` §11.6.2 L330，含 `**/.env.*`），于是已提交的、不含机密的 `.env.test`/`.env.development` 对 Agent 不可读。由 dotenv 加载这些文件的测试在 Agent 侧失败，在验证器侧却可能通过。
  - 三要素表那一行（`11` §11.8 L396）的前提是“被跟踪或未忽略的 `.env` 在 S2 下可读”，与上述规则矛盾。
  - 被忽略的本地文件不会进入卫星。`07` L208/L1287 对 `extraGlobs`（`.env.test`）的哈希读的是卫星中并不存在的文件；验证槽位又被 `clean -ffdx` 清理。没有任何规则把被忽略的本地配置播种到卫星与槽位。
- **为什么重要**：Agent 侧的失败看起来像 Agent 的错误，用于人工检查的 dev server 也起不来。
- **文档位置**：`11` §11.3.1、§11.6.2 L330、§11.8 L396；`07` L208、L1287；`10` §10.3.1。
- **期望的回答形态**：
  - 被跟踪的 env 文件可读（仍做密钥扫描）；
  - 被忽略的 env 文件经每个项目一份、由人批准的“本地文件”清单播种到卫星与槽位，并做脱敏；
  - 与三要素表那一行对齐。

**R4-D8-03｜次要**
- **问题**：
  - S0 授权卡的“若不处理：→ 拒绝（人不在时等待）”（`04` §4.8.5）违反 §4.8.2 L613 的 CountdownLabel 规则：只在 `use_defaults` 下显示，并显示默认值与时间。
  - §4.8.2 说 `riskTier ≥ standard` 的问题显示“不会超时”，但 `08` §8.7.1 L410 在 `use_defaults` 下会把它们超时为 `paused(question_timeout)`。
- **为什么重要**：倒计时文案是对人的承诺。
- **文档位置**：`04` §4.8.2、§4.8.5；`08` §8.7.1。
- **期望的回答形态**：改为“30 分钟后 → 拒绝（仅 use_defaults）”与“超时后暂停（不自动作答）”。

**R4-D8-04｜次要**
- **问题**：
  - running 期间，`ecosystem_unsupported` 与 `s0_denied` Goal 的卡片第 3 行仍是“已验证 0/M · 观测 O/M”，暗示验证还会到来，而 V 永远不可能大于 0。`04` §4.4.1 L226 与 `12` §12.10.1 L523 只对 human-only 的 Goal 做了特殊处理。
  - §4.6.5 的验收闸没有说明：未执行的机器标准在验收时是否需要书面确认。
- **为什么重要**：卡片是首页唯一的状态行。
- **文档位置**：`04` §4.4.1、§4.6.5；`12` §12.10.1。
- **期望的回答形态**：从一开始就显示“观测 O/M · 未经机器验证（原因）”；给未执行的机器标准加一条验收闸规则。

### D9 视觉设计与美观

**R4-D9-01｜重要**
- **问题**：`12` L188 把 `accepted`、`integrated` 一律列为验证绿；§12.6.1 L309 中 accepted 是 `●`/`●*` 加 `verified`。因此 `human_only`、`s0_denied`、`ecosystem_unsupported` 的 Goal 一旦被验收就着绿。而 L188 自己禁止对“未经机器验证”的 in_review 着绿。`●*`（缺角）是否覆盖这种情况，没有说明。
- **为什么重要**：违反 ADR-024 与 R1 以来的核心规则“只有验证器的结论着绿”，而且在归档列表中会永久误导。
- **文档位置**：`12` §12.3 L188、§12.6.1 L309；`03` L58。
- **期望的回答形态**：为 accepted 增加一个“未经机器验证”变体（形状与颜色都不用验证绿）；或者论证为什么人的验收可以着绿，并修改 L188 的规则文字。

### D10 性能

**R4-D10-01｜重要**
- **问题**：决定性指纹（全新临时索引，ADR-060 第 4 点）没有预算，实测远超文档。
  - 本机，影子上下文同样的 `-c`：
    - 2 万文件（78 MB）：全新索引 `add -A` 2.6–7.2 s；带 stat 缓存、无变化 100–150 ms。
    - 5 万文件：冷 15.5 s，热 4.7–9.5 s。
  - 文档的说法：
    - `07` L218/L223 写“参考项目（3 万文件）≤ 2 s”；
    - `13` L43、L293 与 `16` L431 写“无变化快路径 ≤ 30 ms”（fsmonitor 已关闭，这条路径不复存在）；
    - `07` L210/L219 让每个 `in_review`/`accepted` 的 Goal 每 60 s 做一次决定性检查，`13` L327 标为“永不降级”，打开评审面板会阻塞在它上面。
  - 使用全新索引的理由也偏弱：影子索引归 Tower 所有；git 的 stat 检查包含 ctime 与 inode，无特权的 Agent 伪造不了；`in_review` 期间也没有 Agent 在运行。
- **为什么重要**：5 万文件的仓库在 3 个评审中的 Goal 下会持续占用约半个核，这与 `13` §13.11 的空闲预算直接冲突。
- **文档位置**：`07` §7.3.2 L210-223；`13` §13.3 L43、§13.10 L293-327、§13.11；`16` §16.2.3 L431；`15` ADR-060 第 4 点。
- **期望的回答形态**：
  - SP5 按仓库规模测量决定性指纹的耗时；
  - 60 s 巡检改为 advisory（影子自有索引），决定性只在闸口执行；
  - 或论证“影子索引 + ctime/inode”已足够可信，从而去掉全新索引；
  - 修正 ≤ 30 ms 与 ≤ 2 s 两个数字。

**R4-D10-02｜次要**
- **问题**：
  - ADR-064 写“依赖按 Goal 下载（成本计入 `13`）”，但 `13` §13.11 与 `10` §10.4.4 都没有这项计算。
  - `clone --shared` 从**浅克隆**的用户仓库执行时，会静默不写 alternates，退化为完整复制（已实验），与“秒级、几乎不占空间”（`10` L149）不符。
- **为什么重要**：磁盘与网络预算失真。
- **文档位置**：`13` §13.11；`10` L149、§10.4.4；`15` ADR-064。
- **期望的回答形态**：补非 Node 依赖下载的估算；添加项目时检测浅克隆并提示，或改用其他方案。

### D11 安全与自主度

**R4-D11-01｜阻断**
- **问题**：嵌套仓库与子模块会让影子上下文在沙箱外执行 Agent 写入的命令。
  - 本轮复现（git 2.56）：
    1. Agent 在卫星中 `git init sub`，在 `sub/.git/config` 写入 `filter.evil.clean=<脚本>`，在 `sub/.gitattributes` 写 `*.txt filter=evil`，然后提交。
    2. Tower 按 `10` §10.1.2 的方式（`GIT_CONFIG_NOSYSTEM=1`、最小全局配置、`-c core.fsmonitor=false -c core.hooksPath=/dev/null -c core.untrackedCache=false -c protocol.allow=never -c core.attributesFile=/dev/null`）对卫星执行全新索引的 `add -A`：不触发，但 gitlink 进入了影子索引。
    3. 之后 Agent 只修改 `sub/f.txt` 的 mtime（内容不变）。Tower 在影子上下文中执行 `status --porcelain` 或 `add -A`，**脚本被执行**。
  - 原因：索引中存在 gitlink 时，git 会在嵌套仓库中启动子 git 检查其是否“脏”，子 git 读取的是嵌套仓库自己的、Agent 可写的配置。另一个复核实验中，`-c diff.ignoreSubmodules=all` 也挡不住。
  - 触发条件是现成的：
    - `10` L71 把嵌套仓库记为 gitlink（Fact `nested_repo`），从下一次 advisory 检查点开始，影子索引（§10.7.1 第 1 步的 `<SH>/index`）就带着 gitlink；
    - base 中的真实子模块（§10.14 L571）从一开始就在索引中，它们的 gitdir 在卫星的 `.git/modules/*`，归 Agent 所有；
    - 一个 `sub/.git` 文件也可以指向卫星自己的 `.git`。
  - 另一个后果：gitlink 目录的内容不进入 pin，Agent 只要在 `src/` 下 `git init`，整个目录就从验证与评审中消失。
- **为什么重要**：这正是 R3-D11-01 的同一类逃逸。ADR-060 的“工作区 `.gitattributes` 无法触发命令”（`15` L415）与 T29 的“低”（`11` L534）都不成立，SP6b G1–G8 也没有这个用例。
- **文档位置**：`15` ADR-060；`10` §10.1.2、L71、§10.7.1、§10.14 L571；`11` T29；`14` SP6b。
- **期望的回答形态**：
  - 每次影子操作之前，扫描工作区中所有嵌套的 `.git`（目录或文件），用 pathspec 排除，并且绝不让 gitlink 进入影子索引；
  - 规定嵌套仓库内容的处理：作为普通文件纳入，或者拒绝并发出哨兵；
  - 子模块项目在 M1 中的明确策略；
  - SP6b 增加 G9（嵌套仓库 filter / fsmonitor / hooks、`.git` 文件指针），在每个支持的 git 版本上回归。

**R4-D11-02｜阻断**
- **问题**：卫星的 `.git`（config、hooks、`info/attributes`）整个归 Agent 所有（`10` §10.1 L22/L27，`11` §11.6.2 L327），T29 只保护 Tower 自己的 git。但在沙箱外、以用户身份对卫星运行 git 的还有：
  1. 用户扩展经 `pi.exec`。Pi v1.2.0 自带的示例就会这样做：`examples/extensions/dirty-repo-guard.ts:16`（`git status --porcelain`）、`auto-commit-on-exit.ts:13,42-43`、`git-checkpoint.ts:22`、`git-merge-and-resolve.ts:28,75`。它们的 cwd 正是卫星。
  2. MCP git 服务器。
  3. 用户本人。`04` L560/L935 的“E 我来改”会用外部编辑器或终端打开卫星，`10` L311 也预期用户在编辑器中打开它。IDE 的 git 集成和带 git 状态的 shell 提示符都会运行 `git status`，从而执行 `core.fsmonitor`、hooks 与 filter。
- **为什么重要**：`11` L334 自己写明了这种危险（“让……用户自己下一次的 git 命令执行任意代码”），并以此论证用户仓库必须只读。可是它在卫星中原样存在，而“我来改”恰恰是设计好的流程。T16、T29 都没有覆盖。
- **文档位置**：`11` §11.6.2 L327、L334、T16、T29；`10` §10.1、L311；`04` §4.7.3 L560、L935；`15` ADR-060。
- **期望的回答形态**：二选一，并做实验：
  - S2 对 `<卫星>/.git/{config,config.worktree,hooks/**,info/attributes}` 写拒绝（Agent 的 `git config` 会失败，需论证可接受）；
  - 或者在任何人工交接之前与每次 settle 时，由 Tower 以纯文件方式把卫星配置重写为白名单内容、清空 hooks，并对扩展的 `pi.exec` 注入 `GIT_CONFIG_*` 加固（如果做不到，就登记为残余风险并调整评级）。

  另外，SP6b 增加“扩展执行 `pi.exec("git status")`”和“我来改”的用例。

**R4-D11-03｜重要**
- **问题**：ADR-067 只有决定，没有机制。
  - 没有写出 srt 的 `network.parentProxy`，也没有固定 srt 版本。
  - PAC 按目标地址决定上游，无法变成一个静态的上游 URL，而 `11` L331 写的是“PAC 解析结果”。
  - srt 的上游认证只支持 URL 中的 userinfo（Basic）；企业常见的 NTLM/Kerberos（Negotiate）没有处理。
  - srt README（L365/L890）说明 parentProxy 路由会跳过已解析地址的检查（回环、链路本地、本机 IP），这项保护被交给了企业代理，没有登记为残余风险。
  - Engine Host 调用模型、Supervisor 执行 `git push`/`gh pr create` 时如何经过企业代理，没有规定。
- **为什么重要**：R3-D11-02 想服务的企业用户，现方案在认证上仍不可用，或者安全边界被悄悄削弱。
- **文档位置**：`15` ADR-067；`11` §11.6.2 L331；`16` §16.8 规则 4；`14` SP6a。
- **期望的回答形态**：写明 srt 配置项与版本；给出 PAC 与认证的支持范围（不支持时 S2 网络明确失败并提示，或降为 S0）；补一行残余风险；规定 Host 与 Supervisor 的代理规则；列出 SP6a 用例。

**R4-D11-04｜重要**
- **问题**：§11.3.4 的路径级 forbid 只覆盖硬底线路径：用户仓库、影子、`$VS`/depcache、`$SH`。（§11.3.3 第 3 条列表中没有 `$SH`，而 §11.3.4 引用的正是这张列表。）
  - **漏掉的密钥路径**：密钥路径表（`~/.ssh`、`~/.pi/agent/auth.json`）与 `$TI`（含令牌的 npmrc）不在沙箱外工具参数的扫描范围内。
  - **只读的 MCP**：带 `readOnlyHint:true` 的 MCP 文件系统服务器被归为 `read.external`，在 spike/调研预设下是 notify，在标准预设下可以授权，于是可以读走令牌。
  - **相对路径**：MCP 的相对路径按服务器自己的 cwd 解析，gate 不知道这个 cwd，realpath 的基准没有规定。
  - **过度阻断**：forbid 不区分读写，也不可覆盖。以用户检出为根的代码智能 MCP 连读都会被拒，而 Agent 自己的 bash 可以读。
- **为什么重要**：T7/T26 的分档评级依赖这条规则。
- **文档位置**：`11` §11.3.1、§11.3.3、§11.3.4、T7/T26。
- **期望的回答形态**：
  - 对所有字符串参数应用 §11.3.1 的密钥表（命中即 `secrets.access`）；
  - `$TI` 加入硬底线；
  - 无法解析的相对路径视为不透明参数（→ ask）；
  - 用户仓库只禁写、不禁读。

**R4-D11-05｜次要**
- **问题**：
  - Agent 侧的 `git.push`/`git.pr` 在四个预设中是 ask（`11` §11.2 L93），但按设计它必然失败：卫星的 `origin` 是用户仓库的本地路径，在 S2 下只读，而且 Agent 没有凭据（§11.6.4）。批准它只会浪费一次人的决定。在 S0 下，同样的 push 会**直接写进用户仓库**（R4-D13-04 已实验）。
  - 威胁表中的过时表述：
    - T18“S2 拒绝写非 Goal refs”：卫星的 refs 现在全归 Agent；
    - 硬底线中“指向 `refs/tower/`”：在卫星中没有意义；
    - T26“验证器从用户仓库检出 pin 前 fsck”：lint U1 已改为槽位从影子检出；`14` W9 L104 也是同样的旧说法；
    - T16 的“Watch 模式的终端”：Watch 模式没有终端。
- **为什么重要**：动作分类与威胁表是安全模型的唯一来源。
- **文档位置**：`11` §11.2、T5、T16、T18、T26；`14` W9。
- **期望的回答形态**：Agent 侧的 push/PR 在所有预设下 forbid（“推送由 Tower 在验收后代理执行”）；同步上述条目。

### D12 记忆与学习

**R4-D12-01｜重要**
- **问题**：canonicalRoot 是“首次绑定时字典序最小的根提交”（`02` L72）。用 `--allow-unrelated-histories` 合并 A、B 得到 monorepo M 之后，如果首次绑定发生在合并之后且 `a0 < b0`，那么 canonicalRoot(M) = a0 = canonicalRoot(A)。即使在同一台机器上，M 与 A 也是同一个 ProjectId：检出并列，记忆、信任、VerifyProfile 共享（`02` L93 甚至写明“根相同 → 同一 Project”）。不带 `--squash` 的 `git subtree add` 同理。反过来，两台机器分别在合并前后首次绑定同一个仓库，会得到不同的身份，永远只能人工合并。
- **为什么重要**：这正是 R3-D12-01 的原例。ADR-069 只处理了“别名相交”，这条路径依旧自动合并，会把记忆与信任跨项目传播。
- **文档位置**：`02` §2.3 L72、L93；`15` ADR-058、ADR-069；`09` §9.12.3。
- **期望的回答形态**：绑定时如果已存在同 canonicalRoot 的 Project，但根集合或远端不一致，就要人确认；或者把身份改为“首次绑定时的完整根集合”加消歧规则。

**R4-D12-02｜次要**
- **问题**：`09` L512 把“合并 Project 确认”复用为 `sync_conflict`，但它的 dedupeKey 是 `sc:{memoryId}`（`08` L200），outcomeClass 是“选择版本”（L474），决定类型是 `resolve_sync_conflict`，而这里需要的是 `merge_projects`。`.towergoal` 导入时用哪种 Needs-You 也没有规定。
- **为什么重要**：一个 kind 承载两种语义，告警精度与命令都会错。
- **文档位置**：`09` §9.12.2–9.12.3；`08` §8.4、§8.8；`16` §16.1。
- **期望的回答形态**：新增一个 kind，或者为这种用法单独定义键、选项与决定类型。

**R4-D12-03｜次要**
- **问题**：`Project.checkouts` 与附着点选择（`10` §10.1.1）都没有排除 `.tower-wt.noindex` 下的卫星。用户从卫星“添加项目”，或者在卫星中打开 Tower 时，根提交匹配，卫星就会被登记为检出。由此可能出现“卫星的卫星”，其 alternates 指向一个会随 Goal 归档而被删除的目录。
- **为什么重要**：这会造成静默的对象缺失与记忆归属错误。
- **文档位置**：`02` §2.3；`10` §10.1.1。
- **期望的回答形态**：识别卫星（路径或 `refs/tower/_owner` 标记），拒绝把它登记为检出。

### D13 隔离、git 与并发

**R4-D13-01｜重要**
- **问题**：影子与卫星的对象经 alternates 借用用户对象库，并不独立，base 保活 ref 保护不了它们。
  - 实验步骤：
    1. 用户仓库有分支 `exp`。Agent 在卫星中 `cherry-pick origin/exp`，只产生 1 个新对象。
    2. 影子 `add -A`、`write-tree`、`commit-tree`：影子新增的树与 blob 对象为 **0**，因为 alternates 中已有的对象 git 不会再写。
    3. 用户执行 `branch -D exp`、`reflog expire --expire-unreachable=now`、`gc --prune=now`。
  - 结果：影子 `fsck` 报检查点 `missing tree`；卫星 `bad tree object HEAD`；`bundle create … --not base` 失败。
  - 现实中的触发：squash 合并的 PR 分支被 `fetch --prune` 删除并在之后被 auto-gc，而 Agent 曾经合并或 cherry-pick 过它。
  - 这与三处文档的说法相反：`10` §10.16.2 情形 G L611“正常情况下不会发生（base 保活 + 影子对象独立）”、§10.17 L650、`06` L905“唯一副本”。
- **为什么重要**：检查点、pin 与已验证的证据会在用户的正常 git 维护之后静默损坏。
- **文档位置**：`15` ADR-060 第 6 点；`10` §10.7.1、§10.16.2 情形 G、§10.17；`06` §6.6.1。
- **期望的回答形态**：每个检查点或 pin 之后，把“从它可达、从 base 不可达”的对象复制进影子（`rev-list --objects <cp> --not <base>` → `pack-objects`）；或者在用户仓库为每个检查点保留 ref。修正情形 G 与备份的表述；SP6b 增加这个用例。

**R4-D13-02｜重要**
- **问题**：LFS 与“影子不定义任何驱动”矛盾。`10` §10.14 L574 说检查点的 `add -A` 会“经 clean filter”，但 §10.1.2 L70 与 ADR-060 规定影子配置不定义任何 filter。结果是在卫星中 `git lfs pull` 之后：
  - 影子存的是**原始二进制**，而 base 中是指针，每个 LFS 文件都显示为改动；
  - pin 与 seal 中是原始二进制，从用户仓库 `git push` 时绕过 LFS，超过 100 MB 的文件会被 GitHub 拒绝；
  - 同一行还写着验证器“从用户仓库检出 pin”，已经过时。
- **为什么重要**：在使用 LFS 的仓库中，改动统计、验证与集成全部出错。
- **文档位置**：`10` §10.1.2 L70、§10.14 L574；`15` ADR-060 第 3 点。
- **期望的回答形态**：二选一，并写明槽位如何取得 LFS 对象：
  - 白名单恰好一个驱动（取自用户全局配置的 `git-lfs clean`，并评估它的执行风险）；
  - 或者由 Tower 自己计算 LFS 指针。

  M1 也可以选择检测到 LFS 时拒绝，并给出提示。

**R4-D13-03｜重要**
- **问题**：部分克隆与浅克隆的用户仓库没有处理。
  - 实验：用户仓库以 `--filter=blob:none` 克隆，然后 `clone --shared --no-checkout` 加 `checkout`，报 `unable to read sha1 file … invalid object`。卫星没有 promisor 配置，影子又设了 `protocol.allow=never`，所以卫星创建、影子 diff 与验证槽位全部失败。大型 monorepo 常用部分克隆（`scalar`）。
  - 浅克隆见 R4-D10-02：会退化为完整复制。
- **为什么重要**：这种失败发生在添加项目或启动 Goal 的第一步。
- **文档位置**：`10` §10.1.1、§10.3.1、§10.14。
- **期望的回答形态**：添加项目时检测 `extensions.partialClone` 与 `shallow`；然后拒绝、先在用户仓库上下文中补齐所需的 blob，或者把卫星配置为 promisor。§10.14 增加这两行。

**R4-D13-04｜重要**
- **问题**：卫星唯一的远端是用户仓库的本地路径。
  - 实验：`clone --shared user sat` 之后，`sat` 的 `origin` 为本地路径，用户仓库的 GitHub URL 不可用。
  - S0 下 `git push origin HEAD` 会在**用户仓库**中创建 `refs/heads/tower/G1`，违背“Agent 对用户仓库完全只读”（T5 对 S0 的评级虽然是高，但没有点出这条路径）。
  - `gh pr view`、`gh issue view` 无法从卫星推断仓库；读 `remote.origin.url` 的脚本得到的是本地路径；相对的子模块 URL（`../lib.git`）按用户路径解析，§10.14 的 `submodule update --init --reference` 对这类项目会失败。
  - PR 路径（`10` §10.12 L547：在用户仓库上下文中 push 并 `gh pr create`）已有定义，但 Agent 在卫星中能对远端做什么，没有定义。
- **为什么重要**：Agent 的常见操作（看 PR、`git fetch`、更新子模块）的行为没有定义，S0 下还会写入用户仓库。
- **文档位置**：`10` §10.1、§10.3.1、§10.12、§10.14；`11` T5；`15` ADR-060 第 1 点。
- **期望的回答形态**：
  - 规定卫星的远端配置，例如 `origin` 设为规范化的远端 URL 并禁用 `pushurl`，另设 `tower-local` 指向用户仓库；
  - 从用户的 `.git/config` 复制绝对子模块 URL；
  - 写明 Agent 的 `git push` 与 `gh` 在 S0、S2 下各自如何处理。

**R4-D13-05｜次要**
- **问题**：
  - ref 命名空间的 D/F 冲突：实验中，用户已有名为 `tower` 的分支时，fetch 到 `refs/heads/tower/G1-fix` 报 `some local refs could not be updated`。
  - 用户仓库中 Goal 分支的名称有两种写法：ADR-060 第 7 点（`15` L419）是 `refs/heads/tower/<goalId>`，`10` L29/L84/L305 与 `16` L223 是 `<goalId>-<slug>`。
- **为什么重要**：seal 与集成会在部分用户的仓库上失败。
- **文档位置**：`15` ADR-060；`10` §10.2；`16` §16.1.12。
- **期望的回答形态**：添加项目时检测冲突；前缀可配置；修正 ADR 的写法。

**R4-D13-06｜次要**
- **问题**：
  - lint U1 只落实了一半，“验证器从用户仓库检出 pin”仍出现在 `10` §10.14 L574、`11` T26 L531、`14` W9 L104。
  - `07` L196 的 `towerGit` 是 `core.untrackedCache=true`，而 `10` L64/L369 与 `16` L444 是 `false`（理由是 Agent 可以写目录的 mtime）。
  - `07` 的“统一形式”缺少 `GIT_ATTR_NOSYSTEM`、`core.attributesFile=/dev/null`、`protocol.allow=never`、`credential.helper=`、`diff.external=`，两份文档给出了两份不同的加固清单。
  - `07` §7.4.2 在 `protocol.allow=never` 之下于槽位中执行 `submodule update --init`，取不到任何内容；而 `.gitmodules` 的 URL 来自 pin，也就是来自 Agent。
- **为什么重要**：加固清单必须只有一份，否则实现时会漏掉一项。
- **文档位置**：`07` §7.3.2 L196、§7.4.2；`10` §10.1.2、§10.14；`11` T26；`14` W9。
- **期望的回答形态**：`10` §10.1.2 作为唯一清单，`07` 只引用它；写明子模块在槽位中的来源（从用户仓库按 base 中的 gitlink 取，而不是按 pin 中的 URL）。

**R4-D13-07｜次要**
- **问题**：影子与 Agent / 用户看到的忽略规则和换行规则不同。
  - 影子不读用户仓库的 `.git/info/exclude`（只复制了 `core.excludesFile`，`10` L70），也不读全局的 `core.autocrlf` 与全局属性文件。
  - 于是 Agent 从用户检出复制过来、只经 `info/exclude` 忽略的文件（如 `.env.local`）会进入 pin，在 `in_review` 时被 fetch 进用户仓库，seal 之后被推送。
  - CRLF 内容也可能与用户自己的 git 提交出的结果不同。
- **为什么重要**：机密可能经 pin 外泄，改动统计也会失真。
- **文档位置**：`10` §10.1.2 L70；`07` §7.3.2。
- **期望的回答形态**：把 `info/exclude` 的模式复制进影子（它们是数据，不是可执行内容）；写明换行策略（例如沿用用户的 `core.autocrlf`）。

**R4-D13-08｜次要**
- **问题**：`refs/tower/*` 在用户仓库中保留 180 天，其中包括检查点、pin，以及保存了用户未提交改动的 `base-snapshot`。这些 ref 会出现在 `git log --all` 与各种图形界面中；用户执行 `git push --mirror` 时也会被推送出去（`--mirror` 的禁令只针对 Agent）。
- **为什么重要**：这会把未提交的工作推送到远端，也违背“不碰用户的工作现场”。
- **文档位置**：`10` §10.2、§10.3.2；`06` §6.6.4。
- **期望的回答形态**：缩短保留期；或者改为只在需要时 fetch、用完即删；在 `04` 中告知用户；在 `refs/tower/` 下加说明，或改用不会被 `--mirror` 推送的位置（例如只保存在影子中）。

## 5. 结论

- **是否所有维度为 100：否。** 最高为 D3 的 96，最低为 D11 的 70。
- **是否还有可追问的问题：有。** 第 3 轮 29 条中，已解决 13、部分 16、未解决 0。本轮新增与残留追问共 **49** 条：**阻断 2 条**、**重要 21 条**、**次要 26 条**。
  - 阻断：R4-D11-01（嵌套仓库与子模块让影子上下文执行 Agent 写入的 filter，已复现）；R4-D11-02（卫星 `.git` 配置被用户 IDE、扩展与 MCP 在沙箱外执行）。
- **下一轮建议按以下顺序修订**：
  1. 堵住两条 git 逃逸路径，并给出覆盖嵌套仓库、子模块、IDE 与扩展的 SP6b 实验（R4-D11-01/02）；
  2. 让影子对象真正独立于用户 gc；裁决 LFS、部分克隆与浅克隆、卫星远端的处理（R4-D13-01–05）；

  4. 重新确定决定性指纹的频率或机制，并实测（R4-D10-01）；
  5. 统一 `worktree_missing`，补 in_review 的重新验证出口与 S0 授权模型（R4-D4-01/02）；未经机器验证的 accepted 不着绿（R4-D9-01）；
  6. 给出 M1 的人工检验路径与本地文件播种策略（R4-D8-01/02）；

  8. 补命令表，清理残留（R4-D15-01/02）。
