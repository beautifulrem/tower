## 1. 总评

第 19 轮 7 条：已解决 3、部分 4、未解决 0。归因窗口改以事件序号界定，交还后恢复自动返工在主路径上成立；开场在 `run.started` 同一事务消费，撤回能区分“已发送”；D15 清单全部关闭，新 lint (r′)(q) 已用植入错误验证。Pi 事实与源码一致，排期算术无误。

- `paused → ready` 只覆盖了一条路径，自动返工等其他开 Run 路径遇到槽位已满时仍无状态可去；

### D4 领域模型与生命周期

**R20-D4-01｜次要**（等待槽位只定义了“离开暂停”这一条路径；从暂停转入 `ready` 后失去出口；依赖回退在 drain 中到达）

- **问题**：
  1. **其他开 Run 路径遇到槽位已满。**
     - ADR-145 只给 `onAllReasonsCleared()` 的继续目标 `run` 加了“无槽位或依赖未满足 → `ready{waitReason}`”（`03` L70，`06` L822，`16` L28）。
     - 以下开 Run 路径在 `03` 中直接写成 `→ running`，没有等待分支：
       - `verifying` 失败后的自动返工（`03` L58）；
       - `in_review` 中的 `request_changes`（`03` L59）；
       - `paused(human_change_verify_failed)` 的 `retry_after_human_change`（`03` L85）；
       - `pendingHandBack.continue_agent`（`03` L70 第 ① 步）。
     - 这几条路径同样经过准入：队列类别含 `resume / rework / verify_fix`（`06` L294），第 a 项检查槽位（L298）。
     - 这是常见情形，不是边角情形。验证时 Run 已结束、槽位已释放（`05` L566“最后释放槽位”），排队中的第四个 Goal 会占用它；验证一失败，返工就拿不到槽位。
     - 此时 Goal 无状态可去：
       - `running` 的定义是“有一个活跃 Run”（`03` L55），`05` L581 也写明“不存在没有活跃 Run、却处于 `running` 的状态”；
       - `ready` 的进入条件只列了“合同 ratified”与“离开 `paused`”（`03` L54）；
       - `16` L68 又写“`ready` 中的 Goal 只可能处于 `queued`/`preparing`”。
     - 实现者只能在“违反 `running` 的定义”与“自造一条转移”之间选一种。
  2. **从暂停转入 `ready` 后失去出口。**
     - `goal.pause` 的源状态只有 `running`、`verifying`（`06` L838），`goal.take_over` 的源状态不含 `ready`（`06` L847）。
     - 一个原本处于 `paused(app_quit)` 的 Goal，启动时自动解除后因槽位已满进入 `ready{slot}`。此后人既不能把它停住，也不能“我来改”，只能等它开跑或放弃。
     - 在 ADR-145 之前，这个 Goal 停在 `paused`，这两个出口都在。`waitReason:"manual"`（`02` L142，`16` L22）没有任何命令产生它。
  3. **依赖回退在 drain 中到达。**
     - ADR-145 规定“drain 期间只有暂停原因可以并入，其他目标返回 `E_BUSY`”（`06` L90，`16` L33）。
     - 但依赖回退是系统事件，不是命令，没有调用方可以“稍后重试”。它在 `pause`/`take_over` 的 drain 中到达时，是丢弃、记标记，还是延后，都没有写。
     - 实际上准入第 b 项会在下一次开 Run 时重新检查依赖，后果是安全的，但正文没有把这一点写成规则。
- **为什么重要**：第 1 项落在核心循环“验证失败 → 自动返工”上，并且在并发饱和时经常发生；`03` 作为唯一状态机来源，在这里缺边。第 2 项是 ADR-145 新边带来的回归，削弱了 D8 的“可逃逸”。
- **文档位置**：`03` L54、L55、L58、L59、L70、L85；`05` L566、L581；`06` L90、L294–311、L822、L838、L847；`16` L22、L28、L33、L68；`14` G33d(h)。
- **期望的回答形态**：
  - 在 `03` §3.2.1 把 ADR-145 的边推广为一条通则：**任何开 Run 的转移**（继续目标 `run`、`pendingHandBack.continue_agent`、自动返工、`request_changes`、`retry_after_human_change`）都先请求准入。准入不立即通过时，同一事务转入 `ready{waitReason}`，保留请求类别（`rework`/`resume`，不受评审余量限制）与 `pendingOpenings`；返工证据也以 `{id, factId}` 入队，开 Run 时再消费。`03` L58、L59、L85 的 `→ running` 改为“→ `running`（准入通过）/ `ready`（否则）”。
  - 规定 `ready` 中由上述路径进入的 Goal 可以 `goal.pause`（→ `paused(human)`，继续目标 `run`）与 `goal.take_over`；或者明确说明不允许并给出理由。删除或定义 `waitReason:"manual"`。
  - 补一句：drain 中检测到依赖回退时不改 `target`、不返回错误，由下一次准入的第 b 项判定。
  - 用例：G33e(l)，3 个槽位都被占用时验证失败，断言进入 `ready{slot}`、类别为 `rework`、返工证据在队列中、获得槽位后开场含返工证据；G33d(i)，`ready{slot}`（来自暂停）中人按“暂停”；G35e(m)，`pause` 的 drain 中发生依赖回退。

**R20-D4-02｜次要**（`boundSeq` 随 rebase 移动，与“rebase 带入的变化算人的改动”冲突；多仓库时取哪个 binding）

- **问题**：
  1. **rebase 移动窗口起点。**
     - `Binding.boundSeq` 定义为“绑定（**或最近一次 rebase**）事件的事件序号”（`02` L207，`16` L32），没有通过的验证时它就是窗口起点（`07` L1432）。
     - 但 U2 裁决与 ADR-145 都规定，rebase 带入的 base 变化**属于**窗口内的“人的改动”（`03` L71，`16` L31，`07` L1435 以 landmark `rebase` 识别）。
     - 在 M2 中，若 Goal 还没有通过的验证（例如“基于 G1 分支开始”的依赖 Goal 被提示 rebase，`03` L189），rebase 会：
       - 把起点移到 rebase 事件，使 rebase 之前人的改动（`keep`、交还）落到窗口外；
       - rebase 检查点本身是否在起点之后，取决于它与 rebase 事件的写入先后，而这一点没有规定。
     - 两种情况下，含有人的改动或 base 变化的失败都会被交给 Agent 自动返工，与本规则的目的相反。
  2. **多仓库。**
     - `07` L1432 写 `goal.binding.boundSeq`，但 `Goal` 只有 `bindings: WorkspaceBinding[]`（`02` L184）。多仓库 Goal 的起点取哪个 binding（最小值？），没有写。
- **为什么重要**：这是 ADR-145 新加的字段，作用就是定义窗口边界；“或最近一次 rebase”这半句与同一 ADR 的 U2 定义方向相反。只影响 M2，因此列为次要。
- **文档位置**：`02` L184、L207；`16` L31、L32；`07` L1432–1435；`03` L71、L189；`10` L572；`06` L510–520（`bindings` DDL）。
- **期望的回答形态**：
  - `boundSeq` 只取**绑定事件**，rebase 不改它。rebase 带入的变化由 landmark `rebase` 检查点计入窗口，这已经足够；或者写明 rebase 检查点在 rebase 事件之后写入，且 rebase 不移动起点。二选一。
  - 多仓库时起点取 `min(bindings[].boundSeq)`（或 Goal 级的“首次绑定事件序号”），`07` 伪代码同步。
  - 用例：G33e(m)（M2），无通过验证时人 `keep` 一次，随后 rebase，验证失败 → 断言不自动返工。

### D6 系统架构与可靠性

**R20-D6-01｜次要**（`runs.phase` 只写不回写；Host 不存在的 settle 在 I4 不成立时没有去向）

- **问题**：
  1. **没有回写 `running`。**
     - `phase` 在每次 `agent_settled` 时写为 `settling`（`06` L188，`07` L358，`16` L281）。
     - 但以下两种情形都会回到运行，正文没有一处把它写回 `running`：
       - 宽限确认失败（出现 `agent_start`：follow-up、转向、扩展定时器等）时“回到等待下一次 `agent_settled`”（`05` L566，`06` L188）；
       - `claimed`/`verifying` 期间因 `agent_start` 撤回到 `running`（`03` L57，`05` L566）。
     - 若此后 Agent 正在工作时 Tower 崩溃，恢复表会读到 `phase = 'settling'`，按“settle 中崩溃”处理（`06` L141）：继续目标 `settle`，重启后“加载会话、不开 Run，引擎空闲即视为宽限满足”。
     - 后果：Agent 被打断的回合不会继续，而是直接按当时的工具事件判定 I4。这正是恢复表拆成两行想要避免的误判，只是换了入口。
  2. **I4 不成立时没有去向。**
     - `phase = 'settling'` 写在宽限确认之前，因此也覆盖“没有有效提交”的 settle（之后会去 `idle_without_submit`）和“提交在宽限失败后作废”的情形。
     - 但 Host 不存在时的 settle 规则（ADR-143；`07` L1511；`05` L566）只写了成功路径“pin 与 `claimed` 同一事务”。I4 不成立时，Host 不在、不能 nudge，Goal 去哪里没有定义。
     - `06` L141 的“有效提交保留”也默认了提交一定存在。
- **为什么重要**：第 1 项会让恢复表在一个常见的 Pi 行为（settle 后又被唤醒）之后给出错误结论。第 2 项是“settle 中崩溃”这一新恢复行的失败分支，实现者只能自行决定。
- **文档位置**：`06` L141、L142、L188、L535；`05` L566、L578–585；`07` L358、L1511；`03` L57；`16` L281；`15` ADR-143 L1102、ADR-145 L1140；`14` G35c(g)(h)(o)(o′)。
- **期望的回答形态**：
  - `06` L188 与 `05` L566 写明：宽限失败（`agent_start`）与撤回到 `running` 时，同一事务把 `phase` 写回 `running`。或者改为“`phase = settling` **且** 本 Run 最后一次 `agent.settled` 晚于最后一次 `agent.start`”作为判据。
  - Host 不存在的 settle 补失败分支：I4 不成立 → 按 Run 中崩溃处理（继续目标 `run`，`paused{app_quit|engine_crash}`），或者 → `paused(idle_without_submit)`。二选一，写入 `05` settle 判定表与 `07` L1511。
  - 用例：G35c(g′)，宽限窗口内 Agent 又被唤醒并开始编辑，此时杀掉 Supervisor 后重启，断言继续目标为 `run`；G35c(o″)，没有有效 `submit` 的 settle 中崩溃，断言去向。

### D7 诚实与验证

**R20-D7-01｜次要**（M2：`user_bash` 时间窗口优先于 Agent 工具调用，Agent 的并发写入进入 Human 层；rebase 的状态标签）

- **问题**：
  1. **时间窗口不区分写入者。**
     - `10` L233 的规则 2′ 写明“**先于第 2 行判定**”：`user_bash` 调用窗口（命令开始到返回）内发生的**所有**写入都记 `author:"human"`。
     - Pi v1.2.0 明确允许 `user_bash` 与 Agent 的流式运行并发（文首：`executeBash` 不检查 `isStreaming`，结果延后到 `agent_end` 才写入会话）。在人执行一条较长的 `!cmd` 期间，下面两类写入都会落进 Human 层：
       - Agent 并发执行的 `edit`/`write`/`bash` 工具调用；
       - 本 Run 已在运行的后台进程（watcher、开发服务器）。
     - 2′ 解决了“Agent 设置环境值伪造人”的问题，但缺的不变式仍然是 R19 提出的那一条：Human 层只能包含 Tower 能证明**由人的那次调用产生**的写入。时间重叠不是这样的证明。
     - 后果与 R19 相同：评审界面把 Agent 的 hunk 显示为人的改动，失败去向改为不自动返工，Fact/Claim/Human 的“Human”层混入 Agent 的内容。
  2. **状态标签仍写“你的改动”。** 只有 rebase 变化时，失败卡片首行已改（`04` L958，`12` L408 说明列），但目标进入的状态标签仍是“已暂停 · 你的改动未通过验证”（`04` L954，`12` L408 标签列）。卡片、侧栏与 Needs-You 中都会看到这一行。
  3. **实例的写法不一致**：`05` L381 仍写 `user_bash` 处理器“返回 `{operations: sandboxedOps}`”，即工具路径的同一实例；`10` L233 与 ADR-144 补记 2 写的是“另一个 `BashOperations` 实例”。2′ 正是靠“哪个实例”来判定的。
- **为什么重要**：这是 Fact/Claim/Human 分层在 M2 中剩下的唯一入口，而 Pi 的并发设计会让它经常发生，不是罕见情形。只影响 M2（M1 没有 `user_bash`），因此列为次要，但应在 M2 定稿前关闭。
- **文档位置**：`10` L233、L268；`07` L1489；`11` L353；`05` L381；`15` ADR-144 L1130、ADR-145 L1145；`04` L954、L958；`12` L408；`14` G35c(s)。
- **期望的回答形态**：
  - 写入不变式：`author:"human"` 只给“调用窗口内、且没有 Agent 工具调用在执行、且没有本 Run 其他进程写同一路径”的写入。其余重叠写入记为 `mixedPaths`（已经计入人的改动，但在评审中显示为 `混合`，不显示为“你的”）。
  - 或者在 M2 中由 Tower 的界面只在 Run 空闲（`isStreaming = false`）时发送 RPC `bash`，并登记后台进程仍可能并发写入的残余。
  - 不论选哪种，2′ 都不再写“先于第 2 行”这种无条件优先。
  - 状态标签：只有 rebase 时用“已暂停 · 包含 base 变化的验证未通过”（或类似措辞），`04` L954 与 `12` L408 同步。
  - `05` L381 改为“M2 中返回专用于 `user_bash` 的实例”。
  - 用例：G35c(s′)（M2），人执行 10 s 的 `!sleep 10; echo x > a.txt` 期间，Agent 的 `edit` 改 `b.ts`、后台 watcher 写 `dist/`；断言 `b.ts` 与 `dist/` 不是 `author:"human"`（或标为 `mixed`）。

### D10 性能

**R20-D10-01｜次要**（macOS 每 Goal 内存上限只采样 shell，主要场景不会触发）

- **问题**：
  - ADR-145 规定每 5 s 以 `proc_pidinfo` 采样“Tower 的 `exec` **直接启动**的已知命令 pid”，内存之和越过上限的 80% 时才做一次令牌扫描（`10` L268 第 ⑤ 项，`13` L190，`06` L190，`16` L781）。
  - 按 Pi 的启动方式（`tools/bash.ts` L112–118，Tower 的实现在外层再包一层沙箱），这个直接 pid 是 shell（或沙箱包装进程）。测试运行器、编译器、开发服务器都是它的后代，`proc_pidinfo` 对单个 pid 取到的只是 shell 自身的 RSS，通常只有几 MB。
  - 因此：
    - 前台的测试运行再大，直接 pid 的和也不会越过 80%；
    - `nohup … &` 一类后台进程在 shell 退出后连直接 pid 都没有；
    - 上限在 macOS 上实际不会触发。
  - `13` L190 的残余写作“低于 80% 阈值时，后台进程的内存……只在下一次越过 80% 时计入”。这低估了问题：没有任何东西会让它越过 80%。
  - G35c(u)（`14` L116）的期望“越过上限 80% 时做一次令牌扫描，把该后台进程计入；超过上限 → 终止”无法由所述机制推出。
- **为什么重要**：这是 M1 平台上防止 Agent 跑飞的测试或开发服务器耗尽整机内存的唯一单 Goal 保护（`07` L710 的验证器上限只管验证槽位）。现在文档声称它已可执行，残余也写得很窄，实现者会照着做出一个不起作用的保护，用例也会被写成“通过”。
- **文档位置**：`10` L268 第 ⑤ 项；`13` L190、L315；`06` L190；`16` L768、L781；`07` L710；`14` G35c(u)；`15` ADR-145 L1141。
- **期望的回答形态**：
  - 采样对象改为**每个直接 pid 的后代树**。可以在内存中按 ppid 遍历（例如 `proc_listchildpids`，只在运行中使用，不持久化，不违反 ADR-142 的“持久化只有令牌”）；或者沿用验证器的做法，按 `detached` 建立的进程组采样（`ps -g pgid`，进程组同样只在内存中）。
  - 已脱离父子关系的后台进程如实登记为残余，或在 Run 有后台命令期间以较低频率（例如每 60 s）做一次令牌扫描，并把它列入扫描时机与 `13` L315 的预算。
  - `13` L190 的残余改写为与所选机制相符的说法；G35c(u) 拆为两例：前台大内存测试（应被处置）、`nohup` 后台进程（按所选机制被处置或如实列为残余）。

### D15 文档一致性与可执行性

**R20-D15-01｜次要**

- **问题**：以下各处均已逐处核对。
  1. **`E_BUSY` 不在错误码枚举中**：
     - `ProtoError.code` 是封闭联合类型 `"E_STALE" | "E_INVALID" | "E_FORBIDDEN" | "E_CONFLICT" | "E_STATE" | "E_ENGINE" | "E_INTERNAL"`（`06` L788，`16` L264）；
     - ADR-145 新增的 `E_BUSY`（`06` L90、L847、L861，`04` L1276，`16` L33）不在其中。
     - 照类型实现会编译失败，或被迫改用 `E_STATE`；后者又与“`E_STATE` 表示须先处理原因”的界面语义相冲突（`04` L1276 区分“稍后重试”与“置灰”）。
  2. **`Binding.boundSeq` 没有 DDL 列**：
     - `02` L207 标注为 ⚙️ 持久字段，`16` L32 登记；
     - `06` L510–520 的 `bindings` 表没有 `bound_seq`，也没有写明它由事件推导。
     - 07/08 写作者在回应中请主干确认这一点，主干没有回答。
  3. **`03` 的硬上限出口**（R18、R19 两次点名）：
     - L58 的 `verifying` 行仍没有 `→ paused(budget_hard_cap)`（L58 只在 `→ running` 的条件里写了“预算未达硬上限”）；
     - L68 的通则（从 `verifying` 进入时继续目标为 `verify{pin}`）仍未注明“L71/L80 的硬上限分支优先，继续目标为 `run`”。
     - 照 L68 实现，恢复时会以同一失败的 pin 重新验证，而不是返工。
  4. **`05` L381** 的 `user_bash` 实例写法（见 R20-D7-01 第 3 项）。
- **为什么重要**：第 1、2 项是类型与 DDL 层面的缺口，工程师照文档开工时会直接碰到；第 3 项若按通则实现会导致错误去向，且已是第三次出现。
- **文档位置**：如上。
- **期望的回答形态**：
  - `06` L788 与 `16` L264 加入 `E_BUSY`，并在 §6.4.1 写一句语义（“目标正在进行中，稍后重试，不改变状态”）；
  - `bindings` 表加 `bound_seq INTEGER NOT NULL`，或在 `02`/`16` 写明它由 `binding.bound` 事件推导；
  - `03` L58 加出口，L68 加优先说明；
  - lint 增加一项：命令行与正文中出现的 `E_[A-Z]+` 必须属于 `ProtoError.code`；`02` 中标 ⚙️ 的持久字段必须在 `06` DDL 中有列或有“推导”注记。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D9、D12、D16 为 100，在这六个维度上没有找到可追问的实质问题。
  - 其余十个维度在 97–99 之间，最低为 D4、D6、D10（97）。
- **是否还有可追问的问题：有，但都是次要项。**
  - **第 19 轮核验**：7 条中已解决 3、部分 4、未解决 0。
  - **其他核对**：lint 全部通过；Pi 事实与源码一致，并新核对了 `user_bash` 并发与 bash 进程结构两条；排期算术（WBS 117.7、37 周、余量 0.39–0.85、增人备选 32 周）全部成立。
  - **本轮追问**：新增与残留共 **6** 条，阻断 0、重要 0、**次要 6**：
    - R20-D4-01、R20-D4-02；
    - R20-D6-01；
    - R20-D7-01；
    - R20-D10-01；
    - R20-D15-01。
  - D5、D8、D11、D13、D14 的扣分来自上述条目，不单独编号。
- **设计是否完成：否。**
  - 剩余问题仍是边界与机制层面的缺口，不需要新的架构。每一条都可以用一两句规则加一个用例关闭。
  - 其中三条若照现文实现会直接出错：
    - 槽位已满时验证失败，返工没有合法的状态可去；
    - 宽限失败后崩溃，恢复时不再继续 Agent 的回合；
    - macOS 每 Goal 内存上限实际上不会触发，而文档与用例都声称它会。
- **下一轮建议按以下顺序修订**：
  1. 把 ADR-145 的 `ready` 边推广为“任何开 Run 的转移先过准入”，`03` L58/L59/L85 同步；补 `ready` 中可用的出口与依赖回退在 drain 中的处理（R20-D4-01，核心循环，优先）；
  2. `runs.phase` 在宽限失败与撤回时回写 `running`；Host 不存在的 settle 补 I4 失败分支（R20-D6-01）；
  3. macOS 内存采样改为直接 pid 的后代树或进程组，残余与 G35c(u) 如实改写（R20-D10-01）；
  4. 补 `E_BUSY` 枚举与 `bound_seq` 列，`03` L58/L68 的硬上限文字残留，加两项 lint（R20-D15-01）；
  5. M2 定稿前：`user_bash` 窗口不再无条件优先，并发写入记为 `mixed` 或改为只在空闲时允许；rebase 的状态标签；`boundSeq` 不随 rebase 移动、多仓库取值（R20-D7-01、R20-D4-02）。
