## 4. 追问清单（新增与残留）

编号 `R28-D<维度>-<序号>`。严重度分为阻断、重要、次要。本轮没有阻断项，重要 1 条，次要 2 条。

### D11 安全与自主度

**R28-D11-01｜重要**（取自用户私有 git 配置、可能内嵌凭据的 URL 经命令行参数传给 LFS 获取命令；设计没有规定 Agent 进程看不到这些参数）

- **问题**：
  - **规则现状**：
    - ADR-152/153 规定“生效的键全部以命令行 `-c` 显式传给 `git lfs fetch`”（`10` L214，`06` L239，`16` L469，`15` L1245、L1257）。
    - 按键解析时，`lfs.url` 与 `remote.<name>.lfsurl` 可以来自**用户主检出的 git 配置**（覆盖 `.lfsconfig`）。推导端点还需要用户主检出的远端 URL（ADR-151 L1230 “从用户主检出复制 `remote.<name>.url`”）。
    - 这些值都可能以 userinfo 形式内嵌令牌或口令。这是一种常见、虽不被推荐的做法，文档自己也承认它存在：`10` L220 专门对输出中的 URL userinfo 做脱敏。
  - **暴露面**：
    - 这条命令最长运行 15 分钟（`prepare.repoTimeoutMin`）。它的命令行参数对同一用户的其他进程可读。设计自己就依赖这一点：`06` L192 的 Supervisor 以 `sysctl(KERN_PROCARGS2)` 读取同用户进程的环境；Linux 的 `/proc/<pid>/cmdline` 同理。
    - Tower 的核心场景是多个 Goal 并行。其他 Goal 的 Agent bash 进程与这条命令同属一个用户。S2 的 Seatbelt 档位（`11` L316、L333）只规定了文件读写与网络，没有规定 Agent 进程能否观察非本 Run 进程的参数。
    - Agent 在调试端口或开发服务器时列出进程，是很普通的动作，并不需要恶意。这样一来，参数中的凭据就会进入工具输出，进而进入模型上下文与会话 JSONL。`11` L397 的脱敏只覆盖 Tower 已知的机密与几种固定前缀的令牌，不覆盖一般的 URL userinfo。
  - **与既定原则冲突**：
    - `05` L415 与契约测试 C29 明确要求“密钥不出现在环境变量、argv 和 JSONL 中”；
    - `11` §11.7 的原则是“密钥永不进入模型上下文”；
    - ADR-152 的“输出从不进入 Agent 可读的位置”只管了输出，没有管输入。
  - **来源**：ADR-151 只说“复制”，没有说用什么通道；ADR-152 把通道定为命令行 `-c`；ADR-153 又扩大了传入的键。
- **为什么重要**：
  - 这一类后果是：用户凭据经 Tower 自己的机制，进入并行 Agent 可以观察的位置，进而可能进入第三方模型提供商。这正是 ADR-152 “Tower 看不到也不截取凭据”想要排除的一类。
  - Tower 不运行这条命令时，git 与 git-lfs 自己不会把这些 URL 放进任何进程的参数（凭据经 stdin 与 helper 交换），所以这是 Tower 引入的暴露。
  - 修订只需要一条不变式、一处通道选择、一组用例。
- **文档位置**：`10` L54、L207–221；`06` L192、L239；`11` L316、L333、L372、L397；`05` L415、L1405（C29）；`15` ADR-151 L1230、ADR-152 L1245、ADR-153 L1257；`16` L469；`14` G43（L129）。
- **期望的回答形态**：
  - 在 `10` 步骤 2a 与 `16` L469 写明一条不变式：取自用户 git 配置、可能含凭据的值（URL 类键与远端 URL）**不经命令行参数传递**。二者取一：
    - (a) 写入 Tower 数据目录中只对该命令可读的临时配置文件（Agent 在 S2 下对 Tower 数据目录读拒绝），经 git 的配置包含机制引入，命令结束后删除；
    - (b) 传入前剥离 userinfo，凭据完全交给用户的 credential helper。这时要写明内嵌凭据的用户会得到什么：失败卡片上给出可行动的提示。
  - 取自 base `.lfsconfig` 的键属于仓库内容，Agent 本来就能读到，可以继续用命令行，但要写明这一区分。
  - 在 `11` S2 档位中写明：Agent 进程能否观察非本 Run 进程的参数与环境。如果不能限制，就登记为残余风险，并说明上面的不变式为什么足够。
  - 用例（并入 G43）：用户主检出的远端 URL 含 userinfo，LFS 获取进行中，另一个 Goal 的沙箱进程列出进程。期望看不到 userinfo；获取照常完成，或者按 (b) 给出明确提示。

### D13 隔离、git 与并发

**R28-D13-01｜次要**（远端选择与 git-lfs 不一致；排除对象在其他检出中的处理没有定义；被拒绝的配置在卡片上不可见。R27-D13-01 残留）

- **问题**：
  1. **远端选择不是“与 git-lfs 一致”。**
     - 现规则：“远端名 = 用户主检出中 base 分支的上游远端（`branch.<base>.remote`），没有则 `origin`”（`10` L213，`06` L239，`16` L469，`15` L1258）。
     - 本机 git-lfs 3.8.0 实测的顺序是：当前分支上游 → `remote.lfsdefault` → 唯一远端 → `origin`（见篇首）。
     - 因此有两类配置会选错远端：
       - base 没有上游，而项目设了 `remote.lfsdefault`：git-lfs 用 `lfsdefault`，Tower 用 `origin`；
       - 唯一的远端不叫 `origin`（克隆时改过名，或改名为 `upstream`/`github`）、且 base 没有上游：Tower 找不到远端 URL，端点无从推导。
     - base 是远端引用（`10` L201 “若 baseRef 是远端引用”，例如 `upstream/main`）时，`branch.<base>.remote` 不存在，规则落到 `origin`，与 base 实际所属的远端不符。
     - 上轮期望写明“`remote.lfsdefault` → 唯一远端 → `origin`”，回应没有采纳，也没有给出理由。
     - 在这些配置下，结局都是 `prepare_failed` 后重试无效。结局安全，但用户无从得知原因（见第 3 项）。
  2. **排除对象在其他检出中的处理没有定义。**
     - `10` L966 写“卫星与验证槽位从中（镜像的 LFS 存储）smudge”。人工编辑检出、检验检出与情形 E 的重建同样从影子或镜像物化。
     - ADR-153 只规定了**卫星**中被排除的文件保持指针（`10` L215，Tower 自己 smudge 时跳过）。被排除的对象不在镜像存储中，验证槽位等检出怎样处理，没有写。
     - 这些检出在 GitRunner 中运行，没有网络，最小全局配置复制了用户的 `filter.lfs.*`，其中通常含 `filter.lfs.required=true`。照 git-lfs 的默认行为实现，缺失对象会使 smudge 失败。结果是使用 `fetchexclude` 的项目每次验证都以环境错误失败，正是 ADR-153 要在卫星上避免的那种“重试无效”。
     - G43(h) 只验证了卫星。
  3. **被 Tower 拒绝的配置只进诊断日志，卡片误导。**
     - `.lfsconfig` 中的 `http://` 端点在 git-lfs 自己的子集内，内网自建服务并不少见。这类不合规的值“记入诊断日志并忽略”（`10` L210），端点于是退回由远端推导（G43(f)）。
     - 获取随后失败时，卡片只显示 `LFS 对象缺失：N 个（HTTP 4xx）`（`04` L949，`12` L411）。用户在自己的检出中执行 `git lfs pull` 是成功的，卡片上又没有任何线索指向“Tower 忽略了项目的 `lfs.url`”，重试也不会有用。
     - 这是 Tower 自己的取舍造成的失败。按 Fact/Claim 语法，它应当作为 Fact 出现，而不是藏在诊断包里。
- **为什么重要**：
  - 第 2 项会让一类真实配置的项目无法通过验证，而 G43 测不出来。
  - 第 1、3 项让一部分项目无法开始 Goal，用户又看不到原因。
  - 三项都只需要补规则，不需要新架构。
- **文档位置**：`10` L201、L210、L213、L215、L233、L966；`06` L239；`16` L469；`15` ADR-153 L1257–1260；`04` L949；`12` L411；`14` G43(f)(g)(h)（L129）。
- **期望的回答形态**：
  - **远端名**：改为“base 的上游远端（base 为远端引用时取该引用所属的远端）→ `remote.lfsdefault` → 唯一远端 → `origin`”，都取自用户主检出；或保留现规则，但删去“与 git-lfs 一致”，并写明不一致的两种配置下会得到什么提示。
  - **排除对象**：写明一条通则：凡从镜像 LFS 存储物化的检出（验证槽位、人工编辑检出、检验检出、情形 E 重建），被生效的 `fetchinclude`/`fetchexclude` 排除的对象一律写出指针，不算错误；生效规则沿用该 Goal 的 `lfs_excluded` 记录。
  - **被拒绝的配置**：Tower 忽略或拒绝了 `.lfsconfig` 中的键或值时，记 Fact（例如并入 `prepare` 或 `lfs_excluded` 一类的数据字段）。随后若获取失败，`prepare_failed` 卡片附一行，例如“已忽略项目 `.lfsconfig` 中的 `lfs.url`（不支持的协议）”。
  - **用例**：
    - 并入 G43(g)：唯一远端为 `upstream`、base 没有上游；`remote.lfsdefault=upstream`、base 没有上游。
    - 并入 G43(h)：同一 Goal 进入验证，期望槽位物化成功、被排除的文件为指针、验证照常运行。
    - 并入 G43(f)：随后获取失败，卡片显示被忽略的键。

### D15 文档一致性与可执行性

**R28-D15-01｜次要**（`04` 的编辑错位；G43(c) 与卡片格式不一致；残留的绝对化措辞）

- **问题**：
  1. **`04` L950 的编辑错位。**
     - 新增的“LFS 按项目配置排除的文件”条目写着“这不是失败”，却紧接着写“**不**自动重试，**应用重启后仍保持暂停**。选项：`重试`（`goal.resume`；从已完成的步骤继续…）、`我来改`（仅工作目录已完成检出时出现）、`放弃`。排队的开场与返工序号保留…”。
     - 这些显然是 L949 “启动失败或超时”条目的后半段，L949 因此只剩原因与文案，没有了出口。
     - 按 `04` 实现的人会给一个非失败的提示配上重试与放弃，而失败卡片缺少出口。`12` L411 仍是正确的，所以设计本身可以复原，但 `04` 作为 UX 的主文档会误导。
  2. **G43(c) 的期望与卡片格式不一致。**
     - `14` L129 G43(c) 的期望是“缺失对象 N 个 · HTTP 401 类”；
     - `04` L949 与 `12` L411 是 `LFS 对象缺失：128 个（HTTP 4xx）`，并写明只显示 `4xx` / `5xx` / `网络不可达` 三类。
     - 两者的粒度不同（401 与 4xx）。按 `12` 实现的界面在字面上通不过 G43(c)。
     - 顺带：401/403（凭据问题）与 404（端点错误）对用户来说是两种完全不同的行动。如果决定只显示 `4xx`，就请确认这是有意的取舍。
  3. **残留的绝对化措辞**（R27-D11-01 与 R27-D13-01 期望中的文字项）：
     - `10` L207 仍写“仓库级配置不读镜像中的任何内容”。git 必然读取镜像自己的、由 Tower 写入的 `config`。
     - `10` L54、L218，`06` L239，`11` L372 仍写“Agent 不能影响这条命令的任何输入”。base 可以包含曾由 Agent 写入、经验收合入的 `.lfsconfig`，准确的说法是“只能经白名单键影响下载来源与范围”（`11` L372 同段已有这句）。
- **为什么重要**：
  - 第 1 项会直接产生错误的界面。
  - 第 2 项会让界面实现与验收用例对不上。
  - 第 3 项是同一事实在几处有不同写法。
- **文档位置**：`04` L949–950；`12` L411；`14` L129 G43(c)；`10` L54、L207、L218；`06` L239；`11` L372。
- **期望的回答形态**：
  - 把 `04` L950 中从“**不**自动重试”到“重试时照常送出（ADR-149）”的文字移回 L949 的失败条目末尾。L950 只保留排除提示、Fact 与简报说明。
  - G43(c) 的期望改为与 `12` 一致的格式，例如 `LFS 对象缺失：N 个（HTTP 4xx）`；或者 `12` 改为显示具体状态码（例如 `HTTP 401`），二者取一。
  - `10` L207 改为“镜像中不存在可被 git-lfs 读取的 `.lfsconfig`（`HEAD` 为占位引用），镜像 `config` 只含 Tower 写入的项”。“Agent 不能影响任何输入”统一改为带前提的表述。

  - **其他核对**：
    - lint 全部通过；
    - Pi 事实与 v1.2.0 源码一致；
    - 镜像 `HEAD` 占位与 git-lfs 的远端选择已在本机 git 2.56.0、git-lfs 3.8.0 上实测；
    - 排期算术全部成立：WBS 120.33、38 周、余量 0.43–1.32、增人 33 周。
  - **不扣分的观察**：
    - 情形 E 对“标记存在但从未运行”的 Goal 没有 `baseCommit` 回退，结局只剩放弃，但有定义且安全。
    - `lfs_excluded.source` 是单值。`fetchinclude` 与 `fetchexclude` 分别来自 `.lfsconfig` 与 git 配置时，只能记一个来源，只影响展开显示。
    - 步骤 2a 先从用户主检出 CoW 复制“base 所需的对象”。用户本地恰好有被排除的对象时，卫星中这些文件可能被 smudge 为内容，与 `lfs_excluded` 的路径清单不符。极少发生，且结果偏向“内容更全”，是安全的。
    - `14` L395 “增量都不在链上”与 W7-core 的增量不一致，对结论没有影响。
- **设计是否完成：否。**
  - R28-D11-01 是 ADR-152 定下“以 `-c` 传入”时留下的一处凭据暴露面，ADR-153 又扩大了传入的键。它必须在实现 W7 的 LFS 部分之前写明。
  - 其余两条是局部的规则与文字补全，不需要新架构，也不影响排期。

  3. **R28-D15-01**：把 `04` L950 的错位文字移回 L949；统一 G43(c) 与卡片格式；修正绝对化措辞。
