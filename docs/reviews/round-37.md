## 1. 总评

ADR-162 把“Agent 活动”改为按原则定义，把带机密的标准拆成 `verify()` 的独立阶段，伪代码、`13` 的冻结上限、钥匙串访问控制与机密输入提示都已落地，排期算术全部成立（WBS 121.55、38 周）。

仍有三条重要缺口：
- **冻结仍按组件枚举**：安装器、预热、检验检出的准备不在其中；
- **阻断哨兵触发的 `not_run` 被 `decide()` 判为失败**：走自动返工，绕过 `sentinel_high`，覆盖后机密标准也没有再运行的路径；
- **独占与冻结的范围**：伪代码按项目冻结，`run_now` 与正在进行的另一个机密阶段之间的关系没有定义。

另有四条次要项。

### D6 系统架构与可靠性

**R37-D6-01｜重要**（机密阶段的独占与冻结范围：按项目还是全局；`run_now` 与另一个机密阶段；判定与冻结的原子性）

- **问题**：
  1. **范围矛盾**：
     - “Agent 活动”是全局的：Tower 启动的任何此类进程，不分项目（`11` L419）；准入也是全局的（`06` L292、L300，`maxConcurrentGoals`）；
     - 但唯一定义处的伪代码按项目取槽位、按项目冻结（`07` L458 `verifyPool.acquire(goal.projectId, "secret_phase", {exclusive:true})`，L459 `freezeAdmission(goal.projectId, …)`）。槽位池本身也按项目划分（`07` L516、L1726）；
     - 照伪代码实现，项目 X 的机密阶段运行期间，项目 Y 的 Run、Scratch、验证都会被准入，项目 Y 的机密阶段也可以同时进行。这与“两个机密阶段不会同时运行”（`11` L429，G46(m)）和 T33b 的前提都不符。
  2. **`exclusive` 没有定义**：
     - 它是“整个池空闲才授予”，还是“授予一个空槽位并阻止其他授予”？
     - 前者会让 `run_now` 在槽位全忙时继续等待，与“跳过等待”（`11` L437，`06` L854“立即运行”）冲突；后者在槽位全忙时又没有写排队的优先级。`07` L1007 的优先级表中也没有 `secret_phase`。
  3. **`run_now` 与正在进行的另一个机密阶段**：
     - `run_now` 跳过“等待无 Agent 活动”，而另一个 Goal 的机密阶段本身就是 Agent 活动（槽位中运行的标准）；
     - 若 `run_now` 也跳过它，本 Goal 准备阶段运行的代码（生命周期脚本、`VerifyProfile.prepare`、服务）会与另一个 Goal 已注入的机密并存。人在 `run_now` 中接受的只是“**本标准**的机密可能被其他 Agent 读到”（`04` L1108 卡片文案），并没有接受另一个 Goal 的机密暴露；
     - 若 `run_now` 不跳过它，也就是冻结优先于 `run_now`，这一点同样要写明。
  4. **原子性**：
     - 伪代码中 `await waitNoAgentActivity` → `await verifyPool.acquire` → `freezeAdmission` 是三个异步步骤；
     - “每当槽位空出时重新判定”（`06` L233）意味着同一次槽位释放会同时唤醒排队的普通验证、待准入的 Run 与等待中的机密阶段。哪个先生效没有定义：若普通验证或 Run 先取得资源，而机密阶段沿用之前的“无活动”判定，机密就会与刚启动的 Agent 代码并存（G46(p) 正是这个场景）；
     - 规则没有要求“判定 + 取槽位 + 冻结”在 Supervisor 的同一同步步骤内完成，也没有要求冻结之后再确认一次。
- **为什么重要**：
  - 第 1、3 点让 T33b 的核心不变式“机密在环境中期间，没有其他 Agent 控制的代码在运行”（`11` L418）在多项目与 `run_now` 两种常见情形下不成立，危害类别与 R35-D11-01 相同：跨 Goal 的机密暴露；
  - 第 3 点还是一个**无人同意**的暴露。
  - 第 2、4 点是未定义的次序，W9 无法照文档实现。
- **文档位置**：`07` L363-367、L453-459、L516、L1007、L1726；`11` L418-419、L429-430、L437；`06` L233、L292、L300、L854；`04` L1099、L1108；`13` L302；`16` L504-505；`14` G46(m)(p)(u)(v)。

**R37-D6-02｜次要**（机密阶段的收尾与时限）

- **问题**：
  1. **不执行 `teardown`**：
     - 普通阶段在 `finally` 中调用 `slot.teardown()`（`07` L434）；机密阶段的 `finally` 只有 `killAll` → `release` → `unfreezeAdmission`（L473-476），两条 `envError` 提前返回（L464、L466）也不经 `teardown`；
     - `teardown` 负责 `VerifyProfile.teardown`，以及 `docker: true` 时的 `docker compose -p tower-slot-k down -v`（`07` L777-778）。容器不在槽位的进程树中，`killAll` 终止不到；
     - 照伪代码实现，机密阶段的容器会在解冻后继续运行，卷也会保留。该槽位下一次为其他 Goal 启动同名 compose 项目时，会复用这个卷，里面可能有机密标准写入的数据。`docker: true` 需要人批准（单向门），因此为次要。
  2. **时限没有定义**：
     - “机密阶段的槽位准备时限”（`07` L368，`11` L433，`13` L302）没有对应的参数；
     - 现有时限是分开的：检出与物化（5 s 是目标，不是时限）、`prepareTimeoutSec`（L643，只含生命周期与 prepare）、各服务自己的健康检查超时（L777）、终止宽限 10 s（L353）；
     - 机密阶段 depcache 未命中时，是运行安装器（冻结时长随之增加），还是记 `verify_env_error`，也没有写。
  3. **Supervisor 在机密阶段中崩溃**：
     - 冻结只在 Supervisor 内存中，Verifier Runner 是另一个 utilityProcess，崩溃后可能仍在运行（`06` L63、L66）；
     - 恢复表只写“丢弃槽位、按同一 pin 重跑”（`06` L122），没有写它必须先于准入的重新判定（L124）。这种情形很少见，但写一句即可确定。
- **为什么重要**：第 1 点是伪代码的遗漏，照抄会漏掉清理；第 2 点让 `13` 的承诺不可证伪；第 3 点是未定义的次序。
- **文档位置**：`07` L353、L368、L434、L462-476、L643、L777-778；`11` L431-433；`13` L302；`06` L63、L66、L122-124。
- **期望的回答形态**：
  - 机密阶段的 `finally` 改为 `teardown` → `killAll` → `release` → 解冻；两条错误返回同样经过它；
  - 把冻结上限写成现有参数之和：`prepareTimeoutSec` + 各服务的健康检查超时 + 各带机密标准的超时 + 终止宽限；

### D7 诚实与验证

**R37-D7-01｜重要**（阻断哨兵引起的 `not_run` 让 `decide()` 走返工，绕过 `sentinel_high`；覆盖之后机密标准没有再运行的路径）

- **问题**：
  1. **去向错误**：
     - 普通标准全部通过、但有未覆盖的阻断哨兵时，机密标准记 `not_run`（`07` L364、L438-443）；
     - `outcomeOf` 把一切非通过都算作 `fail`（L1477，`not_run` 不计为通过，`16` L99）；
     - `decide()` 先判 `o === "fail"`（L1507），后判阻断哨兵（L1529）。结果是 Goal 被自动返工，或进入 `human_change_verify_failed`、`verify_failed_limit`，**永远到不了** `paused(sentinel_high)`；
     - 07 回应称“`decide()` 无需改动：触发它的普通标准失败已经决定了去向”。这对“普通标准失败”成立，对“阻断哨兵”不成立。
  2. **后果**：
     - **run 类阻断命中**（`input_mutated_after_gate`）按 ADR-107 不能靠返工消除（L1531-1532 正因此不提供“返工”）。这里却会反复返工，直到返工上限，白白消耗返工次数与预算；
     - **pin 类命中**本应由人在“覆盖并评审 / 返工 / 放弃”中选择（`03` L84），这里被替换成了无人决定的自动返工；
     - 返工提示与验收面板会写“因其他标准失败未运行”，而实际上没有任何标准失败。这是一条与事实不符的 Fact。
  3. **覆盖之后**：
     - 即使 `decide()` 改为先判哨兵，`sentinel.override` 也会把继续目标改写为 `review{in_review, pin}` 并直接进入 `in_review`（`06` L899）；
     - 这时机密标准在该 pin 上仍是 `not_run`，从未运行。`in_review` 的定义却是“全部机器标准通过”（`03` L59）。
  4. **缓存**：
     - 同指纹缓存“复用上次的 `criterion_check`”（`07` L905），没有排除 `not_run`；
     - 覆盖后以同一 pin 重新验证时，若 `not_run` 命中缓存，机密阶段永远不会运行。
  5. **判定范围**：
     - `plainFailed` 只检查本次运行的 `plainTodo`（L438）；
     - 缓存命中或无关路径携带的失败、artifact 标准的失败都不在其中，于是在结局已定时仍会进入机密阶段并冻结全系统。规则文字“其中任一未通过”（L364）也没有写明范围。
- **为什么重要**：
  - 这是状态机的漏洞：一个明确设计过的出口（`sentinel_high` 的三个选项）在有带机密标准的合同上不可达；
  - 它违反 Fact/Claim 语法：记录了一个不存在的失败原因；
  - 覆盖路径会让从未运行的机器标准进入待验收状态。
  - G46(t) 第二组只断言了 `not_run`，没有断言 Goal 的去向，测不到这个问题。
- **文档位置**：`07` L364、L436-446、L880、L905、L1463-1477、L1480-1541；`06` L899；`03` L59、L84；`11` L428；`16` L99、L505；`14` G46(t)。
- **期望的回答形态**：二者取一，在 `07` §7.4.1 写为唯一定义。
  - **(a) 推荐**：拆分 `reason`：
    - `other_criteria_failed` 只用于普通标准失败；
    - 阻断哨兵时记 `not_run{reason:"blocked_by_sentinel"}`，`outcomeOf` 不把这一类计为失败。这样 `decide()` 先落到 `sentinel_high`；
    - `sentinel.override` 解除最后一个阻断命中、且该 pin 上有 `blocked_by_sentinel` 的机密标准时，继续目标改写为“只运行机密阶段”的 `verify{pin}`，通过后再进入 `in_review`。
  - **(b)**：阻断哨兵不阻止机密阶段，照常运行，并说明为此冻结的代价可以接受。
  - 两种做法都要写明：
    - `not_run` 不进入同指纹缓存；
    - `plainFailed` 覆盖该 pin 上全部不带机密的机器标准（含缓存命中、携带与 artifact）。
  - G46(t) 第二组补上期望去向；另增“覆盖后机密阶段运行并进入 `in_review`”一组。
