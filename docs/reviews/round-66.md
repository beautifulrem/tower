## 1. 总评

**第 65 轮的 5 条全部落地**：

- 第 65 轮 §5 的 13 条观察全部有落点（观察 5、9、10 随签名推迟而不再存在，观察 13 无需改动）。

**ADR-193 的主干成立**：
- **“缩小写入面” 的方向正确**。第 62–65 轮的条目都出在 Tower 写用户仓库的那一步。本轮不再逐条补规则，而是把两种写入整体推迟到 M2，并用一条整体守卫避开用户进行中的 git 操作。这比第 65 轮评审建议的三处补丁更简单。
- **不签名**：
  - 识别规则回到 ADR-191 的 “sha 是影子中本 Goal 的某个 seal”（`10` L603）。以下各处口径一致：`06` L132、L141、L242、L920，`16` L587、L591、L595，`14` G40(g)、G46(bg)(3) 第八组。
  - `integration.performed.sha` 记影子中的 seal，复用时记 P（`10` L669、L1295）。`integrated` 观测（L1150）、撤销记录与 M2 推送都用这个 sha。
  - 残留扫描：`签名`、`S′`、`gpgsig`、`gpgSign`、`重新签名` 在 `README`、`00`–`14`、`16` 中的出现，要么是 M1 限制的如实说明，要么带 M2 标记，要么属于无关语义（代码签名、失败签名）。lint (d) 的两项 `DELETED` 生效。
  - 本轮实验确认 `commit-tree` 不读 `commit.gpgSign`，所以 “从不调用签名程序” 在任何用户配置下都为真（见文首）。
  - `commit.gpgSign` 为真时的说明行在 `04` L545、`12` L723、`00` L92 一致。
- **撤销不写仓库**：
  - `goal.undo_integrate` 只在同一事务中记两件事：`integrated → accepted` 与 `integration_reverted_seal`（`06` L922、`10` L1156）。没有写入，也就没有写入失败的分支。
  - 与重新 seal 表 “被撤销的 seal 曾写入 B” 一行（L613–619）的配合不变。
  - `03` L61、L159，`16` L287、L596，`14` G40(e)(f) 同步。
  - **写给人的撤销做法在快进合入时不完整**，见 R66-D13-01。
- **进行中操作守卫**（`10` L642）：
  - **时机**：与检出守卫相同，在取对象之前。
  - **各路径的去向写全了**：`goal.accept`（含 `newBranch:true`）与归档前重写返回 `repo_busy`，不记决定；验收延续回到 `in_review`；删除全部跳过并列出原因。复用一行不写入，因此不受影响。
  - **`repo_busy` 只在一处定义**：`06` L920 的 `step` 枚举；`04` L545、`12` L723、`07` L1637、`16` L597 引用它，lint (s′) 为 0。
  - **状态文件的选择与 git 一致**：`rebase-apply/` 同时覆盖 rebase 的 apply 后端与 `am`；`BISECT_START` 按工作树存放（本轮已确认）。
  - **链接工作树的 gitdir 写成 `<commonDir>/worktrees/<名>/`，`<名>` 没有来源**，自然读法会读错目录，见 R66-D13-02。
- **`newBranch`**：只决定写入新分支、从不改动 B，服务端不要求上一次的返回。写入后的说明不再重复 “正被检出”（`10` L636、`06` L920、`04` L545）。前后一致。
- **排期 −0.02**：全在桌面线 W15，经脚本复核成立，见 §3.2。

**新发现 5 条，全部为次要**。两条出在 ADR-193 的新文字，三条是此前各轮都没有扫到的旧缺口：
- **快进合入的撤销做法只撤销最后一个 seal**（R66-D13-01）：
  - M1 中重新 seal 在原分支上快进，分支上常有一串 seal。人快进合入后照 Goal 页的 `git revert <seal>` 操作，只撤销最后一个 seal 的增量，前面各 seal 的改动留在 base 中。
  - `14` G40 的共同前置正好造出这样的分支，(e) 的期望因此不一定成立。
- **进行中操作守卫读不到部分链接工作树**（R66-D13-02）：
  - `<名>` 是 git 的管理目录名，不能从 `worktree list` 的路径推出。同名目录与 `worktree move` 都会使两者不同。
  - 照自然读法实现，守卫读错目录、照常写入，重现 R65-D13-01 要防的后果。
- **影子中 seal ref 的保留期短于识别规则对它的依赖**（R66-D15-01）：
  - 归档 30 天后影子只留地标检查点（`06` 另留 pin），seal ref 被删。
  - 此后 “清理 Tower 引用” 认不出 Tower 写过的分支，一律保留，并写出不真实的原因 “可能含你的提交”。
  - ADR-193 让归档时被跳过的删除 “之后可由清理再删”，这条路径因此更常走到。`10` 与 `06` 对 pin 的保留也不一致。
- **`03` 状态表中 `integrated` 的进出不完整**（R66-D4-01）：
  - `10` §10.12 的唯一条件允许任何非终态进入 `integrated`，`03` 只列了两条入边。
  - `integrated` 宽限期内卫星仍被监视，但来源不明的写入在该状态下没有去向。
- **放弃的 8 秒撤销没有对应的命令或转移**（R66-D4-02）：
  - M1 界面提供撤销放弃，而 `abandoned` 是终态，`06` 也没有反向命令。两种实现都会碰到未定义的状态。

每一条都回到正文核对过。R66-D13-01、R66-D13-02 另用实验确认了 git 的行为，不是推测。

### D13 隔离、git 与并发

**R66-D13-01｜次要**（`10` L1156 写给人的撤销做法：“快进合入时 `git revert <seal>`”。M1 中重新 seal 在原分支上快进，分支上常有多个 seal，`git revert <seal>` 只撤销最后一个 seal 相对前一个 seal 的增量）

- **问题**：
  - **分支形态**（`10` L621–626）：B 的顶端是 Tower 自己的 seal P 时，新 seal 以 P 为父快进写入。因此 B 上是一串 S₁ → S₂ → … → Sₙ，只有 S₁ 以 `baseCommit` 为父。`10` L1152 指出，M1 中合并由用户自己完成，“这一情形因此是常态”。
  - **合入与判定**：人在 base 未前进时执行 `git merge B`，git 默认快进，base 因此带入 S₁…Sₙ。`integrated` 按最近一次验收的 seal Sₙ 判定。
  - **撤销**：Goal 页让人执行 `git revert <Sₙ>`。这只撤销 Sₙ 相对 Sₙ₋₁ 的差异，S₁…Sₙ₋₁ 带入的改动留在 base 中（本轮实验确认）。界面上，Goal 回到 `accepted` 并显示 “已撤销合入”。
  - **以合并提交合入**时 `git revert -m 1 <合并提交>` 撤销整次合并，**squash** 时撤销对应的 squash 提交，这两种都对。只有快进一种不完整。
  - **测试自身就会走到**：`14` G40（L127）的共同前置是 “已验收、写入分支；之后 `keep` 使 Goal 离开 `accepted`，重新验证并再次验收”。若用户未动分支，(a) 的期望就是 “新 seal 以上一次 seal 为父”，所以 (e) 中被合入的分支上有两个 seal。
    - 人照 Goal 页撤销之后，base 仍含 S₁ 的改动；
    - 之后以 `baseCommit` 为父写入的 `-v2` 再合入时，可能冲突，结果也可能不等于 pin 的树，取决于返工是否改动了 S₁ 已带入的行；
    - 这与 (e) 的期望 “人合并后 base 含 Goal 的全部改动（与 pin 的树逐路径一致）” 不符。
- **为什么是次要**：
  - Tower 不写仓库，执行 revert 的是人，revert 的差异人看得见；不丢数据。
  - 但这是 Tower 在 “如实写出要由人完成的撤销” 一句下给出的做法，在 M1 的常见路径上不完整。人照做后会以为合入已撤销，而 base 中留着 Goal 的一部分改动。
- **文档位置**：`10` L613–626、L1152、L1156；`03` L61、L159；`06` L922；`16` L596；`14` G40（L127）。
- **期望的回答形态**：在 `10` L1156 的唯一定义处改一句：
  - 快进合入时撤销本分支上本 Goal 的全部 seal：`git revert <S₁ 的父提交>..<seal>`。S₁ 是沿第一父链从 seal 回溯、仍满足 §10.6 识别规则的最早一个 seal，Tower 直接写出范围起点。只有一个 seal 时，等于 `git revert <seal>`。
  - G40 补一组：分支上有两个 seal、人快进合入后照 Goal 页撤销，期望 base 回到合入前的内容，之后 (e) 的期望成立。
  - `16` L596 的现行说法同步。

**R66-D13-02｜次要**（进行中操作守卫读 “链接工作树为 `<commonDir>/worktrees/<名>/`” 中的状态文件，但 `<名>` 没有来源。`git worktree list --porcelain` 只给出工作树路径，而 git 的管理目录名在同名时会加数字，`worktree move` 后也保持不变）

  - 不丢数据，结果与 R65-D13-01 相同：用户的提交仍在分离的 HEAD 与 reflog 中。
  - 需要同名目录或移动过的工作树，再叠加进行中的操作与 Tower 的写入。

  - **两种实现都会碰到未定义的情形**：
    - **客户端延迟 8 秒才发出 `goal.abandon`**：这 8 秒内 `ready` 的 Goal 可能被准入并开始 Run，随后的放弃会终止一个 Run，与 “只在没有活跃 Run 被终止时出现” 不符。另一个窗口或之后的远程客户端看到的状态也不一致。
    - **服务端先放弃、撤销时再恢复**：需要一条未定义的 `abandoned → <原状态>` 转移，还要恢复 `queued_run`、继续目标与已关闭的 Needs-You，并撤回已记入复盘的决定，与 “终态” 和 `HumanDecision` 只追加的约定冲突。
- **为什么是次要**：
  - 放弃前已有必填原因的确认框，所以不会误删数据；卫星、影子与分支在 7 天内都还在，也可以复活为新 Goal。
  - 但这是一个 M1 界面动作，没有对应的命令或转移，两种实现的行为不同。
- **文档位置**：`03` L63；`04` L1386–1389；`06` L297、L923、L925；`08` L520；`12` L735；`16` L914。
- **期望的回答形态**：二选一，写在 `06` §6.4.3 `goal.abandon` 行：
  - 按收敛规则 2 删除放弃的撤销条：确认框已有必填原因，`UndoBar` 在 M1 中可以没有使用者，`04`、`12`、`16` 同步；
  - 或写明 “客户端在确认后延迟 8 秒发出 `goal.abandon`，期间该 Goal 不被准入”，并定义 “不被准入” 由哪个命令或字段表达。

  - **不扣分的观察**：
    1. **两个守卫的先后**：分支正被检出、同时仓库中有进行中的操作时，返回 `branch_checked_out` 还是 `repo_busy`，`10` L642 只写了 “同一时机”。两者都不写入，只影响先看到哪一句提示：先报 `branch_checked_out` 时，人选 “写入新分支” 后还会再遇到 `repo_busy`。建议写明先判进行中操作守卫。
    2. **`10` L10 的写入列举**：
       - “Tower 写进用户仓库的只有……Goal 分支（以及……地标 ref）” 没有列出多机租约 `refs/tower/_owner` 及其 blob（`06` L181）。`10` §10.6.2 与 `06` L1114 已写明它是唯一例外。
       - L10 新加的 “这一次不写也不删” 照字面也可能被读作适用于租约续写与地标写入；L642 只针对分支写入与删除。
       - 建议 L10 补上租约，并注明守卫的范围以 L642 为准。
    3. **要求签名的用户自行签名后合入**：
       - 面板建议 “需要签名的提交请在合并前自行签名”。人改写 seal 后合入，base 中只有 S′，`merge-base --is-ancestor <seal>` 不成立，`integrated` 只能靠 L1150 的 patch-id 判定（S′ 与 seal 同树同父，patch-id 相同）。
       - 而正文把 patch-id 写成 “squash 合并以 patch-id”。建议注明 patch-id 判定对任何非祖先情形都适用，并给 G40(g) 补 “自行签名后合入，期望 `integrated`” 一组。
       - 这时 R66-D13-01 的撤销做法应指向 base 中实际的提交。
    4. **“已撤销合入” 徽章**：M1 中 Tower 不写仓库，人可能还没有执行 revert，徽章（`12` L348）却说已撤销。建议改为 “已撤销合入（需在你的仓库中 revert）” 一类说法，直到下一次写入新 seal。
    5. **`04` L1382 的归档文案与 `newBranch`**：
       - 从目标页 “归档（不合并）” 时只写了写分支失败的提示，缺 `repo_busy` 与 `branch_checked_out` 两行；复用 §4.6.5 的同名行即可。
       - 另外，从 `accepted` 归档前重写时，只在分支已被删除时才写入，此时 “正被检出” 只在孤儿分支检出时才可能出现，所以 `integrate:"none"` 加 `newBranch:true` 没有定义，并不构成实际缺口。可以注一句 “此路径不提供写入新分支”。
    6. **Pi 行号的基准混用**：
       - `05` L14、L1345 声明引用以 HEAD `b06c1f2` 为准，发布版 “+1…+5”，实际 v1.2.0 中是提前 1–5 行；第 65 轮观察 12 改成的 3529–3553 已经是 v1.2.0 的行号，却仍标 “发布版 +≤5”。
       - 本轮抽查中有 8 处行号区间偏 1–5 行：`steer` / `followUp`、压缩期间 `prompt` 抛错（G12）、G17、G26、G18 的替换在 `runner.ts:1056`、`new_session` 的 `parentSession`、压缩默认路径、`input` 被吞。
       - 建议统一以 v1.2.0 行号书写，删去 “+≤5” 列的含糊方向。
    7. **人的决定的持久性**：
       - `13` L259 写 “提交后 `wal_checkpoint(PASSIVE)`，见 `06` §6.3”，`06` L362、L371 写的是 “`synchronous=FULL`”；`13` L251 与 `06` 又互相声明 “以对方为准”。
       - 两种做法都能保证持久，但应只有一处定义，建议 `13` 改为引用 `06` 的 FULL。
    8. **全局缓存写入的级别**：`11` L366 与 `07` L1515 举例 “写全局缓存……为 severity 1”。按 `16` L174 的唯一定义，`~/.npm/**`、`~/.cache/**` 等点目录中的缓存属于 `user_config`，写入为 severity 2（`16` 同处也明说了）。按唯一定义实现不会出错，建议把举例改为 `~/Library/Caches/**` 一类 `system` 路径。
    9. **S7 的里程碑标记**：`11` L62 `forbid` 行写 “10 分钟内 ≥ 3 次同类被拒 → `stalled` 检测”，没有 M2 标记；同文 L366 与 `07`、`08`、ADR-059 都写 S7 在 M2。建议补 “（M2）”，并考虑纳入 lint (z′)。
