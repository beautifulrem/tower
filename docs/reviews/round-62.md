  - SDK 下六个动作都有定义。抛错由 Pi 在 `_tryExecuteExtensionCommand` 中捕获，不破坏分派。

**新发现 3 条，均为次要**：
- **`builtin:` 前缀不能唯一标识 Pi 核心内置工具**（R62-D5-01）：
  - Host 以 builtin 条目加载的 codemode、tool-search、mcp 注册的工具，来源同样以 `builtin:` 开头；codemode 的来源恰为 “`builtin:` + 自身名字”。
  - `11` L218（唯一定义）对 “白名单之外的 Pi 内置工具” 的界定与这些来源重叠，优先关系只能从 `05` gate 步骤顺序中推出。
  - C28a 对照组的断言 “来源为 `builtin:` 的名字恰为两个常量之并” 在 Tower 的配置下必然失败。
- **RPC（M2）下的命令上下文动作没有规则**（R62-D5-02）：
  - ADR-189 只定义了 SDK。Pi 的 RPC 模式接的是真实的重载与会话替换，Tower 无法替换；Tower 自己的 `/tower-fork`、`/tower-nav` 也依赖它们。
  - `00` L100 写成不分模式的能力差异。
- **先写分支之后、事务提交之前的窗口没有去向**（R62-D13-01）：
  - 写分支成功、事务未提交（崩溃或数据库写入失败）时，用户仓库中留下一条没有 `integration.performed` 记录的分支。正文引用的 “`06` §6.1.6 seal 行” 属 M2 的合并队列恢复规则（`06` L147）。
  - Goal 换了 pin 后再次验收，会走 “首次 seal” 写入已存在的同名分支，或命中 “B 的顶端 ≠ P” 一行，两者都没有定义好的结果。
  - 相邻：验收延续是 M1 中进入 `accepted` 的另一个入口，不写分支。所以 ADR-189 写的 “M1 中进入 `accepted` 时总有本次验收的 `integration.performed`” 不成立。

每一条都回到正文与源码核对过，不是推测。

### D5 Agent 架构与 Pi 集成

**R62-D5-01｜次要**（“白名单之外的 Pi 内置工具” 以 `builtin:<name>` 来源界定，但 Host 以 builtin 条目加载的 codemode、tool-search、mcp 注册的工具，来源同样以 `builtin:` 开头，codemode 的来源恰为 `builtin:codemode`。唯一定义没有写出排除或优先关系；C28a 对照组的断言在 Tower 的配置下必然失败）

- **问题**：
  - **Pi 的事实**（文首核实）：
    - `builtin:` 同时是内置工具与 builtin 扩展的路径前缀（`source-info.ts:14-15`）；
    - 扩展注册的工具取扩展的来源（`loader.ts:296-299`），所以 codemode 工具的来源是 `builtin:codemode`，`tool_search` 是 `builtin:tool-search`，MCP 工具与 MCP 资源工具是 `builtin:mcp`；
    - codemode 的工具名就是 `codemode`（`codemode/tool.ts:39`），它的来源与 “`builtin:` + 自身名字” 完全相同。
  - **正文的界定**：
    - `11` L218（唯一定义）：“白名单之外的 Pi 内置工具（来源为 `builtin:<name>`、名字不在白名单中…）……门禁按沙箱外执行处理，硬底线 forbid”。`05` L1001、`16` L260 同样写法。
    - 两种读法：
      - 按 “来源以 `builtin:` 开头” 读，codemode、`tool_search` 与全部 MCP 工具都落入 forbid；
      - 按 “`<name>` 即该工具自己的名字” 读（`16` L122 的写法暗示这一种），codemode 仍然落入。
    - 能化解冲突的只有 `05` §5.6.5 的步骤顺序：第 1 步先放行 codemode 与 `tool_search`。但 `11` L218 与 `16` §16.1.10 的工具表都没有写出优先关系；MCP 工具在 `11` L220 归 “上一条” 的 `tool.external`，与第一种读法冲突。
  - **C28a 对照组**（`05` L1441）：
    - 断言 “来源为 `builtin:` 的名字恰为 `TOWER_BUILTINS ∪ NON_TOWER_BUILTINS`”；
    - 但 `getAllTools()` 列出全部已注册工具（`agent-session.ts:1498-1510`）。codemode 与 tool-search 在加载期就注册，`defaultActive:false` 也照样在列；配置了 MCP 服务器时还有 MCP 工具；
    - 对照组没有写明关闭这些 builtin 扩展，所以这条用来在 Pi 升级时报警的断言，按字面实现永远失败。
- **为什么是次要**：
  - 方向偏严：任何读法都不会把沙箱外执行放过，最坏情况是 codemode 或 MCP 被 forbid，C21 等契约测试会暴露；
  - 但这是 ADR-189 新写的唯一定义，实现者会各自决定按前缀、按 “`builtin:` + 名字”，还是按排除表判定。修 C28a 的方式（排除哪些名字）也会各不相同，而这一组正是 Pi 升级时的报警。
- **文档位置**：`05` L337–339、L374–377、L996、L1001、L1441；`11` L218、L220；`16` L122、L258–260；Pi `core/source-info.ts:14-15`、`core/extensions/loader.ts:296-299`、`core/resource-loader.ts:718-745`、`extensions/codemode/tool.ts:39`、`extensions/codemode/index.ts:34`、`extensions/tool-search/index.ts:14`、`core/agent-session.ts:1498-1510`。
- **期望的回答形态**：在 `11` L218 唯一定义处改一句：
  - “Pi 内置工具” 指来源恰为 `builtin:<自身名字>`、且该来源不是 `05` §5.3.5 `extensionFactories` 中 `builtin: true` 条目的扩展路径（目前为 `builtin:codemode`、`builtin:tool-search`、`builtin:mcp`）的工具；

  - `05` L1001、`16` L260 引用同一句；

### D13 隔离、git 与并发

**R62-D13-01｜次要**（ADR-189 让 M1 验收先写分支、后提交事务。分支写成而事务未提交（崩溃或数据库写入失败）时，用户仓库中留下一条没有 `integration.performed` 记录的分支，M1 没有恢复规则；之后再次验收会撞上它。另有一个 M1 进入 `accepted` 的入口，即验收延续，它不写分支，与 ADR-189 写下的不变式不符）

- **问题**：
  1. **写后窗口没有 M1 去向**：
     - `06` L919：重试 “复用已写的 seal 与分支（按步骤幂等，同 §6.1.6 seal 行）”。但该行（`06` L132）以合并队列状态 `integrating` 为键；集成日志按合并队列条目记录（L118）；L147 写明 “上面这些恢复规则随‘推送并开 PR’一起在 M2 生效”。F26（L1192）也只指向 §6.1.6。
     - 所以 M1 中，如果写分支后、事务提交前崩溃，或事务本身失败，重启后 Goal 在 `in_review`，用户仓库中已有分支，Tower 不记录、也不检查它。
  2. **之后再次验收的结果没有定义**：
     - **首次验收后的窗口**：人没有重试而是返工、接管交还或修订标准，得到新 pin；再次验收时没有任何 `integration.performed`，按 `10` L594 走 “首次 seal”，写入已存在的同名分支 B₀；
       - 新 seal 以当前 base 为父，与孤儿分支上的 seal 是兄弟而非后代。正文的写入形式不是快进，会被拒绝，于是每次重试都是 `E_INTERNAL`；
       - 若实现者改成强制更新，则会改写人可能已在该分支上追加的提交，与 `10` §10.6 “从不改写用户已改动的分支” 相反；
       - `10` L253 的前缀冲突检查只看 `refs/heads/<prefix>`，不看 B₀。
     - **再次验收时的窗口**：B 已存在，按 `10` L613 以 CAS 把 B 快进到新 seal 后事务失败，B 的顶端已不是记录中的 P；
       - 重试时 `10` L616 “B 的顶端 ≠ P” 一行成立，Tower 会另开 `B₀-v<k>`，并在面板上写 “你的分支 <B> 已有你的提交”。这句话不真实，也与 `06` L919 的 “复用已写的分支” 不一致。
     - **观测**：孤儿分支不在 `integration.performed.branch` 中，人合入它时 Tower 观测不到（`10` L621）。
  3. **验收延续是进入 `accepted` 的第二个入口**：
     - `07` L1629–1634：从 `accepted` 来的验证满足延续判据时，`decide()` 直接回到 `accepted`，不经 `goal.accept`；
     - I2 只在指纹即树变化时触发（`03` L110、`06` L263），所以延续后的 pin 树总与最近一次 seal 的树不同；
     - M1 没有合并队列，延续不重做 seal（`10` L1110 的延续只在 M2 合并队列中接着 seal）。
     - 结果：
       - ADR-189 写在 `06` L919 的 “M1 中进入 `accepted` 时总有本次验收的 `integration.performed`” 不成立；
       - 之后从 `accepted` 选 “不合并并归档”，守卫只检查分支是否存在（`06` L919、`10` L438）。Goal 会以分支停在较旧 seal 的状态归档，延续带来的改动只剩影子与 bundle。ADR-188 的 “已验收的改动总能从用户仓库取回” 在这条路线上不成立。
     - `integrated` 一侧有卫星树条件兜底（`10` L1129），不受影响。
  4. **相邻的小缺口**：
     - 面板只提供 `[重试]`（`04` L543），但前缀冲突只有改 Project 设置才能消除，重试必然再次失败；
     - 从目标页 `归档（不合并）`（`04` L1382）返回的 `E_INTERNAL` 显示在哪里没有写；
     - G46(bg)(3) 只测 “写入前失败” 与 “归档时分支已删”，不测写后窗口。
- **为什么是次要**：
  - 写后窗口需要崩溃或数据库写入失败恰好落在一次 git 写入与一次事务之间；延续在 M1 中也只在少数采纳路径上出现；
  - 改动不会立即丢失，影子与 bundle 仍在；
  - 但 ADR-189 正是以 “先写分支” 关闭 R61-D13-01，写后窗口是这个新顺序直接产生的状态；验收延续则使它写下的不变式失真。实现者会各自决定：强制更新、另开分支或报错。
- **文档位置**：`03` L60、L110；`04` L543、L1379、L1382；`06` L118、L132、L147、L263、L919、L1192；`07` L1629–1634；`10` L253、L438、L594、L599–621、L1110、L1129；`14` G46(bg)(3)；`15` ADR-189。
- **期望的回答形态**：在 `06` L919 唯一定义处补：
  - **写后窗口**：二选一并写明：
    - 写分支前以既有的集成日志写法记一条 “开始写分支{branch, sha}”，启动时对 M1 同样检查，未提交的写入按 “分支顶端 == 记录的 sha” 判定为 Tower 自己的写入，可复用或回退；
    - 或者首次 seal 的目标分支已存在而本 Goal 没有记录时，按 `10` §10.6 的命名规则改写 `B₀-v<k>`，并在 “B 的顶端 ≠ P” 一行之前加一条 “B 的顶端等于本 Goal 未提交的 seal → 视为 P”；
  - **验收延续**：二选一并写明：
    - M1 中延续到 `accepted` 时按 `10` §10.6 重新 seal 表（快进或 `-v<k>`）写分支，与 `goal.accept` 同一顺序，失败则不延续、进入 `in_review`；
    - 或者 M1 中不做验收延续（总进入 `in_review`，只需重看变化的单元），并把 `06` L919 的不变式限定为 “经 `goal.accept` 进入时”；
  - 前缀冲突的失败在面板上给出 “修改分支前缀” 的入口；写明目标页 `归档（不合并）` 的失败如何显示；
  - G46(bg)(3) 补一组：写分支后、事务提交前终止 Supervisor，重启后先返工再验收；另一组为 M1 中从 `accepted` 经交还触发验收延续，再选 “不合并并归档”。

       - `08` L405 的定义句已含来源 `running`，句中仍写 “重试从已完成的步骤继续”，没有区分来源；
       - `06` L1170（F4b）的界面列与 `04` L972 的选项句 “选项说明写‘从 <步骤> 继续’” 同样没有区分；
       - 而 `16` L581 把这种写法登记为被取代的说法。行为相同（`resume` 后经准入重新准备，步骤幂等），只是文案可能被照抄成 “从 握手 继续”。建议三处各加 “（运行中途停止的一种写‘开新的运行’）”。
    2. **验收失败行的 `◇`**：`04` L543 用 `◇ 未能在你的仓库创建分支`。`12` L334 规定 `◇` 是 “要注意但不需要你决定”，L335 规定验收阻止项、未写出的路径用 `■`；`12` L723 的 `AcceptPanel` 也没有这一状态。建议按 `12` 改用 `■`（不用 `◆`，因为没有 Needs-You），或在 `12` 注明例外。
    3. **验收顺序的旧措辞**：
       - `04` L1379 的走查写 “`⌘↩ 验收` → `accepted`。此时 Tower 生成汇总提交（seal），在你的仓库中创建分支……（之前该分支不存在）”，顺序与 ADR-189 相反，括注在写后窗口下也不必然成立；
       - `03` §3.4.4（L157）只写 “记录 `HumanDecision{kind:"accept"}`”；
       - `03` L60 的 “分支写入的同一事务” 指的是记 `integration.performed` 的事务。
       - 以 `06` L919 为准不会实现错，建议改为引用。
    4. **`reload` 抛错与未等待的调用**：扩展若不 `await ctx.reload()`，Tower 抛出的错误会成为 Host 进程中的未处理拒绝。正文没有写 Host 对进程级未处理拒绝的处理（这对任何扩展缺陷都适用，不是 ADR-189 独有）。建议在 `05` §5.5 写一句：记 `engine.error`，不终止 Host。
    5. **拒绝表按名字作用于一切来源**：Pi 的 `excludeTools` 同样过滤扩展与 `customTools` 中的同名工具（`agent-session.ts:3536`）。用户扩展注册的 `powershell`（例如自带沙箱的实现）在 Tower 中也会消失，被移除时没有沙箱外工具那样的确认卡片说明。建议在 `00` L99 补半句。
    6. **重新绑定后的 `waitForIdle`**：骨架中的 `commandContextActions` 闭包引用最初的 `session`。Tower 自己替换 runtime 后（`05` L280）应随新会话重建该对象，与 Pi 的 RPC 模式在 `rebindSession` 中先更新 `session` 一致。C28a 中 “fork 和 newSession 之后同样成立” 也宜覆盖 `powershell` 的断言，因为 `excludeTools` 由 runtime 工厂每次传入。属实现细节。
    7. **SDK 下人写文字的命令分派**：`05` L267 以 `session.prompt(text)` 发送 `opening.human`，`expandPromptTemplates` 默认为真（`agent-session.ts:2058`）。Goal 描述若恰以某个扩展命令名或提示模板名开头，会被分派或展开，而不是作为 user 消息进入会话。评论与转向带 `[Tower ·` 标记行，不受影响。ADR-189 之后命令已无法改变会话，后果只是这条描述可能没有送达模型。建议对人写的文字传 `expandPromptTemplates:false`，与 C28a 所说 “SDK 下 Tower 不提供斜杠命令入口” 一致。
    8. **“接管” 的两种含义**：`16` L915 的 `T` 是 “接管：诊断视图”，`⌘⇧T` 是 “我来改：接管为 `paused(human)`”；`04` L291 的目标页线框把 `[T 接管]` 与 `[E 我来改]` 并列。`16` 的说明足以区分，属沿用已久的措辞。
    9. **取舍判断**：ADR-189 的两个常量、一个参数、一个动作对象与一处顺序都写得诚实，方向偏严或中性，判断见 §3.3。
