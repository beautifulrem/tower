## 1. 总评

**第 90 轮的 3 条次要条目都已按所问关闭**（核对见 §3）。§5 的 15 条观察全部落地，观察 6 只落在 (b) 一处（R91-D11-02）。回应 “偏离与未决” 的五条全部接受，但回应没有沿用第 90 轮期望形态中 “且写回正在本进程中进行” 这一限定，带出 R91-D6-01。

**ADR-218 的主体成立**（§3.3）：
- **`~/.tower/**` 的收窄**只在沙箱外工具的路径检查 (2) 中生效（`11` L221），`11` L160、`10` L542–L546 引用它。
  - 其余使用者都不受影响：文件工具的分类（`11` L144–L147，工作区内的读不查密钥表）、命令分类器 “写 `~/.tower/**`” 的硬底线（L203）、沙箱读拒绝（L352）、验证器（L380）、§11.7 可读者规则（L444）、`sandbox_violation` 的 `tower_data` 类别（`16` L174）；
  - 以绝对路径或 `file:` URI 写本 Host 空目录仍按第 3 条 forbid，只有 (b) 的例外免除硬底线；
  - 打包模式下 “本 Goal 的调用” 按调用所属会话的 Goal 判定，其他 Goal 的卫星本就在硬底线中。
- **`~` 的两种解释**（`11` L221 (1)(3)）：恰为 `~` 或以 `~/` 开头的按 Pi 的 `expandHome` 展开，`~user/…` 按 shell 规则展开，同一个值另按 (3) 以 (b) 的基准作字面的相对路径各查一次，取更严格者。字面一侧为 `opaque`，所以按工具名的授权不再把它降为 `notify`。G46 (bk) 两组的期望与规则一致。
- **写回进行中**（`06` L914）：`syncState='syncing'` 期间，交还与带回共用一条规则，判定先于各命令的前置条件。`06` L905、L907、L933 与 `16` L293 引用它，`16` L293 把 “`abandon` 始终允许” 限定为准备阶段，G31 补了一组。`06` L499–L500 的 CHECK 因放弃不再能在带回中途成功而不会再被触发。远程端的命令矩阵与它没有交集：`E_BUSY` 不取决于来源，相关命令都是 `full`。
- **Pi 引文的更正**：三处都在原文后加注保留，所指行号都已核实。

**ADR-218 带出的新问题**：
- **写回中途的非崩溃失败没有出口**（R91-D6-01）：
  - “写回进行中” 只按 `syncState='syncing'` 定义，规则写 “崩溃后由 §6.1.6 续写完成，不需要人的命令解除”，而 §6.1.6 只在启动时运行。
  - Tower 仍在运行而写回出错时（文件系统错误、Agent 留下的目录权限、卫星在写回中途消失），文档没有定义 `syncState` 怎样变化。ADR-218 之前，再次交还（`10` L972 的 `syncing` 分支）或从 `paused(human)` 放弃都是出口；现在两者都返回 `E_BUSY`。错误持续时，重启后仍是同一结局，Goal 连放弃都不能。

**全范围扫描**在 ADR-218 之外新发现：
- **文件工具的路径解析与 Pi 不一致**（R91-D11-01，重要）：
  - `11` §11.3.1 的唯一定义以 `resolve(cwd, stripAt(input.path))` 求路径；
  - Pi 的内置文件工具在 `execute` 中经 `normalizePath` 另外展开 `~`、`~/`，并把 `file://` 开头的值转换为本地路径。
  - 照伪代码实现时，这两类值被判为工作区之内（`read.worktree`、`edit.in_scope`，多数预设 silent），而 Pi 实际读写的是主目录或任意绝对位置。内置文件工具在 Engine Host 中、S2 之外运行，分类器是唯一的守卫（S1，`11` L332）。
- **(1) 的 `..` 与符号链接**（R91-D11-02）：ADR-218 对 (b) 写了 “按词法与按操作系统各求一次”，(1) 的绝对路径、`~` 路径与 `file:` URI 仍只写 “经 `realpath`”。这类值不是 `opaque`，在按工具名的授权下只是 `notify`。

### D11 安全与自主度

**R91-D11-01｜重要**（文件工具的分类以字面 `resolve` 求路径，Pi 的内置文件工具却展开 `~` 并转换 `file://`：工作区之外、包括硬底线位置与密钥路径的读写会被判为工作区之内）

- **问题**：
  - **唯一定义**：`11` §11.3.1（L142–L148）对 `read`/`grep`/`find`/`ls`/`edit`/`write` 求路径为 `p = resolve(cwd, stripAt(input.path))`，再取最长已存在前缀的 `realpath`，判断是否在 `worktreeRoots` 之内；之内的读为 `read.worktree`，之内的写按范围归 `edit.in_scope` 等，之外的写为 `edit.outside_worktree`，命中密钥路径表的读为 `secrets.access`。
  - **Pi 实际怎样解析**（v1.2.0）：
    - 六个内置文件工具都在 `execute` 中经 `resolveToCwd`/`resolveReadPathAsync` 求路径（`core/tools/write.ts:65`、`edit.ts:161`、`read.ts:124`、`ls.ts:83`、`find.ts:111`、`grep.ts:125`）；
    - 它们调用 `normalizePath`（`utils/paths.ts:76-101`）：把 Unicode 空格变体换成普通空格，去掉前导 `@`，把恰为 `~` 与以 `~/` 开头的值展开为主目录，把以 `file://` 开头的值经 `fileURLToPath` 转换为本地路径；
    - `read` 在文件不存在时另试 AM/PM、NFD、弯引号及其组合的变体（`path-utils.ts`）；
    - `tool_call` 钩子看到的是这些处理之前的原始参数（`edit` 的 `prepareArguments` 不动 `path`）。
  - **两者的差别**：伪代码只模拟了 `@` 一项。照伪代码，以 `~/` 开头的值与 `file://` URL 被当作卫星中的相对路径，求出的位置在工作区之内；Pi 实际读写的是主目录下或 URL 所指的任意绝对位置。
  - **文档自身的例子按展开理解**：`11` L31 `read.external` 的例子 `read ~/code/other/README.md`、L36 `edit.outside_worktree` 的例子 `write ~/.zshrc`、`read.pi_resources` 的 `~/.pi/agent/…`，以及 T3（L680）都默认 `~` 被展开。伪代码与这些例子相反；`file://` 与 `@` 之后的 `~` 在文件工具一侧则没有任何提示。路径扫描（L221）已为沙箱外工具定义了 `~` 与 `file:` 的处理，但只适用于沙箱外工具。
  - **为什么只有分类器能挡**：内置文件工具在 Engine Host 中运行，Host 不在沙箱内（`11` L444）；S2 只包住 bash（§11.6.2）。对这些工具，S1 “工具级写守卫”（L332）就是 §11.3.1 的分类，T3 的 “低” 评级依赖它。
- **后果的类别**：照唯一定义实现时：
  - 对主目录下凭据文件的读取被判为 `read.worktree`（各预设 silent，`11` L77），不出现 `secrets.access`，内容进入模型上下文；
  - 对工作区之外的写入被判为 `edit.in_scope` 一类（多数预设 silent，L80），而不是各预设都 forbid 的 `edit.outside_worktree`（L84）；
  - 以 `file://` URL 指向用户主检出、影子目录或其他 Goal 卫星的读写越过第 3 条硬底线（“不可授权覆盖”），也不出现审批卡。
  这正是 Agent 受提示注入时最直接的越界途径，而写明的不变式是这类动作一律 forbid 或至少逐次审批。
- **为什么是重要**：实现者照 §11.3.1 的唯一定义（伪代码）实现，就会违反写明的硬底线与 `edit.outside_worktree`、`secrets.access` 的分类。表中的 `~` 例子只能提示其中一种形式；`file://` 一种在文件工具一侧没有任何依据。验收测试（C 类、G46）也没有覆盖文件工具参数中的这两种形式，裁决不了。
- **文档位置**：`11` L29–L36（类别与例子）、L77–L84（预设）、L142–L148（伪代码）、L221（沙箱外工具已有的 `~` 与 `file:` 规则）、L332（S1）、L444、L680（T3）；`05` §5.3.5 `TOWER_BUILTINS`（L391）；C 类契约测试（`05` §5.11）。

  - **求路径与 Pi 一致**：写明分类所用的路径就是 Pi 的 `resolveToCwd` 会求出的路径——同样的 Unicode 空格归一、去掉前导 `@`、`~` 与 `~/` 展开、以 `file://` 开头的值按 `fileURLToPath` 转换（不能转换的按 Pi 的行为处理，或直接 forbid），再相对 `cwd` 解析；最好写成 “调用与 Pi 同版本的同一函数”，并在 D 类依赖表中登记这些行号，Pi 升级时由契约测试复核。

**R91-D11-02｜次要**（ADR-218 观察 6 的 “按词法与按操作系统各求一次” 只写进 (b)；(1) 的绝对路径、`~` 路径与 `file:` URI 仍只写 “经 `realpath`”，而这类结果不是 `opaque`，授权后只是 `notify`）

- **问题**：
  - `11` L222 (b) 现在写明：相对路径 “按词法规范化 `..`、已存在的部分取 `realpath`，与按操作系统的方式——先解析符号链接、再处理其后的 `..`——各求一次，两个结果都判定”。
  - `11` L221 (1) 对绝对路径、`~` 路径与解码后的 `file:` URI 只写 “经 `realpath` 后，落在第 3 条硬底线之内的 forbid”。最后一段尚不存在（写入新文件）时 `realpath` 无从直接求，实现者会复用 §11.3.1 的做法，而那里是先按词法 `resolve`、再对最长已存在前缀取 `realpath`。
  - 服务器怎样解释同一个绝对路径同样有两种：直接交给操作系统打开的按物理方式处理 `..`；先以 Node 的 `path.resolve` 一类规范化的按词法处理。Agent 可以在卫星中建立符号链接（S2 允许），所以同一个含 `..` 的绝对路径可以按一种方式落在卫星之内、按另一种方式落在硬底线位置。
  - 第 90 轮把观察 6 记为观察，理由是 “相对路径恒为 `opaque`、逐次 ask，有界”。这一理由对 (1) 不成立：(1) 的结果不是 `opaque`，在 “本 Goal 内同类”（按工具名）的授权下只是 `notify`。
- **后果的类别**：经授权、能写文件的沙箱外工具在不出审批卡的情况下写入第 3 条硬底线中的位置（用户主检出、Tower 的完整性存储、其他 Host 的空目录），越过 “不可授权覆盖”。
- **为什么是次要**：与 R90-D11-02 同一口径——需要用户配置了接受路径参数、能写文件的沙箱外工具，并由人授予过该工具的 Goal 级授权；路径扫描本是尽力而为（L221 末句）。但 ADR-218 已为 (b) 确立了 “两种方式各求一次” 的原则，(1) 没有沿用，实现会在两种取法之间分叉，而任选一种都可以被另一种解释绕开。
- **文档位置**：`11` L221 (1)、L222 (b)、L144–L146；`14` L134（G46 (bk)）；`05` L1461（C21）。
- **期望的回答形态**：在 `11` L221 (1)（唯一定义）补半句：绝对路径、`~` 路径展开后与 `file:` URI 解码后的路径，同样按词法与按操作系统两种方式各求一次（最后一段不存在时对最长已存在前缀取 `realpath`），两个结果都判定、取更严格者；或者写明只取一种并把另一种登记为残余（T7/T26 同步）。C21 或 G46 (bk) 补一组只写期望：已授予 “本 Goal 内同类” 时，含 `..` 且经卫星中的符号链接按一种方式落在主检出的绝对路径被 forbid、不出现审批卡。

### D6 系统架构与可靠性

**R91-D6-01｜次要**（“写回进行中” 只按 `syncState='syncing'` 定义：写回在 Tower 运行期间失败时没有出口，而放弃、放弃改动与再次交还在这期间都返回 `E_BUSY`）

- **问题**：
  - **规则**：`06` L914 “`human_checkout.syncState='syncing'` 期间……该 Goal 上其他会改写状态或 `human_checkout` 的命令……返回 `E_BUSY`……这一判定先于各命令自己的前置条件……崩溃后由 §6.1.6 续写完成，不需要人的命令解除”。
  - **§6.1.6 只在启动时运行**：`06` L116 “Supervisor 每次启动……都会在接受 UI 命令之前跑一遍”。
  - **非崩溃失败没有定义**：写回由多个事务组成（`06` L905 ①–③，`10` L989–L1003），不能整体回滚。文档只定义了两种局部情形：
    - 目标不是普通文件、父目录链中有符号链接 → 跳过并列出（`10` L224、L996）；
    - 来源检出在 `syncing` 时丢失 → 以 T1 续写，“无法完成则列出未写回的文件”（`10` L1035），之后 `syncState` 怎样变化没有写。
    其余失败——卫星中的目录不可写（Agent 在接管之前可以改动卫星中的目录权限）、文件系统错误、卫星在写回中途消失并触发自动重建——都没有定义。
  - **ADR-218 之前的出口都被关闭**：
    - 再次 `goal.hand_back` 本可进入 `10` L972 的 `syncing` 分支（“跳过本步，以 T1 为目标对未写完的文件幂等续写”），现在在前置条件之前就返回 `E_BUSY`，这一分支经命令已不可达；
    - 从 `paused(human)` 放弃（`06` L933）与 `goal.discard_human_edits` 同样返回 `E_BUSY`。
  - **结局**：Goal 停在 “稍后重试”，直到应用重启；错误持续时，重启后的续写再失败，同一结局延续，连放弃都不能。第 90 轮期望形态中的 “且写回正在本进程中进行” 正是为区分 “正在写” 与 “写过但已停下” 而设，ADR-218 没有采用。
- **为什么是次要**：不丢数据（T1 在影子中，人工编辑检出在放弃时保留）；触发需要写回中途的持续错误。但实现会分叉：一些实现把 `syncState` 退回 `idle`（违背 “续写只从 `targetTree` 读取” 的前提，卫星停在写了一半的树），一些在进程内无限重试，一些停住等重启。用户看到的是一个永远 “稍后重试” 的 Goal，而 `03` L45、`06` L933 承诺任何非终态都可以放弃。
- **文档位置**：`06` L116、L144、L905、L907、L914、L933；`10` L224、L972、L989–L1003（L996）、L1035；`16` L293；`14` L107（G31）。
- **期望的回答形态**：在 `06` L914（唯一定义）：
  - **限定 “进行中”**：`syncState='syncing'` 且写回正在本进程中执行；
  - **非崩溃失败的出口**：写回在运行中失败时停止写回、保留 `syncing` 与 `targetTree`、`written`，生成 Needs-You（复用已有的 kind 或子类型），出口为 “重试写回”（即再次 `goal.hand_back`/`inspect.bring_back`，按 `10` L972 续写）与放弃（`06` L933 照常，人工编辑检出保留）；或者写明逐路径的失败一律按 `10` L224 “跳过并在结果中列出”，使写回总能完成；
  - G31 补一组只写期望：交还写回中途某个目标路径持续不可写 → Goal 不停在 “稍后重试”，按所选出口可以重试或放弃。

- **是否还有可追问的问题：有。** 新增共 **3** 条：阻断 0、**重要 1**、**次要 2**。
  - **D11**：R91-D11-01（重要）、R91-D11-02（次要）。
  - **D6**：R91-D6-01（次要）。
  - **第 90 轮核验**：
    - 3 条全部按所问关闭，其中 R90-D6-01 带出 R91-D6-01；
    - §5 的 15 条观察全部落地，观察 6 只落在 (b)，带出 R91-D11-02；
    - 回应的五条偏离全部接受；另有一处未写出的偏离（“本进程中” 的限定），见 R91-D6-01。
  - **其他核对**：
    - lint 全部通过（exit 0；ADR 218，section_refs 8042，(v) 98 条命令，(e) 227 对，(r′) 57 对，(D) 378 个短语，(z′) 53 处，(C) 19 行并覆盖 §14.8），与第 90 轮记录逐行一致。
    - Pi v1.2.0：ADR-218 的引文与更正都是原文；R91-D11-01 所依据的 `normalizePath`、`resolveToCwd`、`resolveReadPathAsync` 与六个工具的解析位置已逐个核实（见文首）。
    - 排期结论成立：WBS 123.44；余量 0.12 / 0.14 / 0.36 / 0.42 / 0.12；依赖链 19.91；增人 129.40、T 23.89、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **写回进行中的适用范围**：
       - “会改写状态” 是否包括只改 `pause_reason`、`also_applies`、`continuation`、`pending_openings` 的命令（`sentinel.override`、`goal.openings.withdraw`、无 Run 时的 `needs_you.answer`）没有写明。命令逐个串行执行、③ 在当时读取原因，未发现 CHECK 失败或丢数据，宜写 “会改写该 Goal 任何持久字段”。
       - `inspect.close`（`06` L915）明写 “不改变 Goal 状态”，所以不在规则之内；带回写回期间它能删除作为来源的检验目录。`10` L1035 已规定 `syncing` 时来源丢失按 T1 续写，有界，宜点名 “`inspect.close` 在带回写回期间同样返回 `E_BUSY`”。
       - 规则只说命令；接管期间的自动重建会写 `human_checkout.rebuiltTree`，而交还写回以 `B = rebuiltTree ?? T0` 求写回集合。两者都持 `wtLock`，宜写明重建等写回结束。
       - `06` L914 写 “`goal.hand_back`、`goal.abandon` 两行与 `16` §16.1.12 引用”，实际还有 L907 一行，宜改为三行。`06` L882、L900–L901、L904 与 `16` L43 的 “`human_checkout` 非空 → `E_STATE`” 因判定在先而在写回期间变为 `E_BUSY`，不必逐处改，但 `03` L45 “abandon（任何非终态）” 宜加 “写回进行中稍后”。
    2. **写回期间的可见状态**：`04`、`12` 没有为 `syncState='syncing'` 定义卡片或实况行的文字，人点 `放弃` 只得到 “稍后重试”。G31 也没有检验 “判定先于前置条件”（写回期间 `inspect.bring_back` 返回 `E_BUSY` 而不是 `E_STATE`）与 `goal.discard_human_edits`。宜补一个 `◇ 正在写回你的改动` 一类的实况行与一组期望。
    3. **不含 `/` 的以 `~` 开头的值**：(3) 的相对路径是 “含 `/` 或等于 `.`、`..`”，又写 “以 `~` 开头的值也在其中”。`~`、`~foo`、`~1.2.3`（版本范围）是否算相对路径有两种读法：算，则授权后的工具对每个版本范围参数都 ask；不算，则它们只是单个文件名，属已登记的限制。不涉及不变式，宜写明条件 “含 `/`” 同样适用。`~user`（无 `/`）同此。
    4. **回退一项的括注范围**：`11` L221 (2) “本 Goal 的卫星工作区（§11.6.2 回退位置例外中 Agent 的读写项）”，括注可读作整组读写项（含 `_gitdirs/<goalId>`、`_stores/<goalId>/`），而回应与 `10` L545 只免除工作区。宜改为 “（§11.6.2 回退位置例外中 Agent 读写项的第一项）”。
    5. **密钥路径表的范围注**：`11` L160 “S2 下用户主目录本就在读允许列表之外，补全影响的是 S0 的分类与技能路径排除”。S2 只包住 bash；内置 `read` 在 Host 中运行，S2 下同样经 §11.3.1 分类，这些条目在 S2 下同样起作用（`~/.tower/run/` 的即时投递文件、`~/.gitconfig` 等）。起作用的伪代码（L147）不分 S0/S2，所以不改变行为，但宜改为 “影响 S0 与 S2 下文件工具的分类与技能路径排除”，随 R91-D11-01 一并修改。
    6. **`10` L546 “后者” 的指代**：L542–L545 由两处改为三处之后，“其余规则引用后者” 的 “后者” 变成第三处（路径检查），而 `11` §11.3.2 的硬底线、§11.6.3、§11.7 引用的是第二处（沙箱的逐路径例外，`11` L203、L352）。宜改为 “第二处”。
    7. **`00` L99 的措辞**：“也不当作读取密钥” 没有提表中其他条目照常适用（如空目录中名为 `.env` 的相对路径）；“既按你的主目录” 没有提 `~user/…`；也没有提以 `~/` 开头的值对用户扩展工具与 HTTP 服务器在授权后仍逐次 ask。都是描述偏宽、行为更严，宜各补几个字。
    8. **Pi 措辞**：
       - `11` L222 (a) “Host 非正常退出（被信号终止、超出内存上限、致命错误）时两者都不运行”：Node 的 `exit` 事件在未捕获的 JS 异常与未处理的 Promise 拒绝时仍会触发，只在信号、V8 中止与内存耗尽时不触发。宜把 “致命错误” 改为 “运行时中止”。
       - `close()` 在服务器进程已退出时只结束 stdin、不再按进程组终止（`stdio.ts:160-163`），所以服务器的子进程可能在 `dispose` 之后存活。都偏保守，不影响结论。
    9. **工具到服务器的关联键**：`11` L222 (b) “取自 Tower 的工厂为该连接记下的条目” 没有写从一次工具调用怎样找到该连接。Pi 在注册时为每个服务器的工具带上 `namespace`，其 `aliases` 为原始服务器名（`extensions/mcp/index.ts:387-397`），宜写明按它或按注册时的工具对象关联。有界：相对路径恒为 `opaque`。
    10. **目录删除失败的出口**：`11` L222 (a) 按 F4b 处理，但没有原因文字；同一不可删除的条目会使 `重试` 反复失败。宜在 `06` F4b 的原因清单中补一行，并提示人手动删除该目录。
    11. **验收组的区分力**：
        - G33（`14` L110）只检验扩展之前出现 `先扩展预算`，没有检验 `budget.extend` 之后它消失、而 `按当前状态送去验证` 仍按条件置灰，旧的无条件文字同样能通过；
        - G46 的标题 ADR 列表止于 216、R83–R88，而 (bk) 已含 ADR-217/218 的组。
    12. **`04` 的两处措辞**：
        - L995 “（上一条所说的决定）” 位于 “结果” 列表中，上一条是 “窗口内没有 → …”，宜写 “窗口起点一条所说的决定”；
        - L1132 “**Agent 使用经你批准的机密**（`secrets.access`）[M2]……M1 界面中不出现” 指的是密钥注入的卡片，而 M1 中路径扫描与命令分类仍会出 `secrets.access` 的审批卡（`11` L50、L221，G46 (bk)）。宜写明 “M1 中这一类只出现在读取凭据的审批卡上”。
    13. **M1 性能门槛的 CI 清单**：`14` L427 要求 “`13` §13.1 在 M1 负载下达标”，CI 清单只列 P1/P2/P5–P8。聚焦事件 → 绘制、大 diff、诊断视图首屏只由 P3、P4、P9 测量，命令 → 回执与 steer → Pi 队列没有场景。门槛本身要求全部预算达标，所以去向不变，宜把 P3、P4、P9 列入或写明它们以别的方式测量。
    14. **`02` 的两处注释**：L178 “syncing = 交还写回进行中” 漏了检验带回（`16` L43 是对的）；L528 `mode` 的注释 “取自 `Goal.humanCheckout.params`” 对置换的 `resume` 不成立（L527 的标题注释是对的）。
- **设计是否完成：ADR-218 正确地关闭了第 90 轮的三条次要条目。**
  - 本 Host 空目录与回退位置下本 Goal 卫星中的结果不再按 `~/.tower/**` 归密钥；以 `~` 开头的值按两种解释各查一次；交还与带回共用写回进行中的 `E_BUSY`；十五条观察全部落地，Pi 引文都已更正。
  - 本轮 3 条条目分两类：
    - **此前各轮未发现的旧规则缺口**：R91-D11-01（文件工具的路径语义与 Pi 不一致）。这是本轮唯一的重要条目：它不在 ADR-218 的范围内，此前各轮的伪代码都只模拟了 Pi 路径处理中的 `@` 一项；
    - **ADR-218 的新规则与已有规则的交集**：R91-D11-02（“两种方式各求一次” 没有用到 (1)）、R91-D6-01（`E_BUSY` 关闭了写回失败时原有的出口）。
- **下一轮建议**：

  2. **R91-D11-02**：(1) 同样按词法与按操作系统各求一次，或如实登记残余。
  3. **R91-D6-01**：“写回进行中” 限定为本进程中正在执行；写回在运行中失败时给出重试与放弃的出口，或逐路径跳过并列出。
  4. §5 的十四条观察各补半句。

  **工时与排期**：约 0.04–0.05 人周，不在依赖链上。系统线与安全线余量都是 0.12、都在改派阈值上，本轮三条的落点（W10 两条、W3 一条）恰好都在这两条线上，都须先按 ADR-136 改派（§3.2）。预计 M1 仍可维持 38 周（2027-07-30）。
