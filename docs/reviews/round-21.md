## 4. 追问清单（新增与残留）

编号 `R21-D<维度>-<序号>`。严重度：**阻断** / **重要** / **次要**。本轮没有阻断与重要项。

### D4 领域模型与生命周期

**R21-D4-01｜次要**（`ready` 成了“带卫星、带开场的等待态”，接管、外部写入与准备阶段的通则没有跟上）

- **问题**：
  1. **接管源状态 `ready` 无法持久化。**
     - `06` L848、`16` L23、`03` L54 都允许从 `ready` 接管，并在同一事务写 `takeover_from=<源状态>`。
     - 但 `06` L463 的 DDL 是 `CHECK (takeover_from IN ('running','paused','in_review','accepted'))`；`02` L162 的注释是同样四个值；`16` L36 `Goal.humanCheckout` 行列出的源状态也不含 `ready`。
     - 照 DDL 实现，这条新命令在写入时就违反约束。
  2. **从 `ready` 接管后放弃改动，去向没有定义。**
     - `discard_human_edits` 只在 `takeoverFrom = running` 或 `takeoverPriorReasons` 含 `human` 时保留 `paused(human)`（`03` L78，`06` L851，`07` L1508，`16` L31）。
     - 从 `ready` 接管时，接管前的原因集合为空，`takeover_from` 也不是 `running`。照现文，命令会解除 `human`，`onAllReasonsCleared()` 执行继续目标 `run`，自动开 Agent Run。
     - ADR-137“放弃改动不得自动开 Run”（`15` L1042）的保留条件只覆盖 `running`，而 `ready` 与 `running` 同属“Agent 即将或正在工作”。
     - 两种去向都说得通。问题是现在由一个非法值的缺省分支来决定。
  3. **首次启动的 `ready` 没有卫星。**
     - 卫星在准入通过后由 `ensureSatellite` 创建（`06` L312、L326；`03` L131）。
     - `12` L393 把“暂停 / 我来改 / 放弃”写在 `wait slot` 整行，首次排队也包含在内；`06` L290 也笼统写“`ready` 中允许 `goal.take_over`”。
     - 接管的第一步却是“先对卫星当前内容做检查点”（`06` L848）。
     - `04` L940 只在“要开 Run 但需要等待”的语境中提供这三个动作，与 `12` 的范围不一致。
  4. **`ready` 中的外部写入没有入口。**
     - ADR-145/146 之后，`ready` 中的 Goal 常常带着有内容的卫星：返工等槽位、离开暂停后等槽位、依赖回退。卫星监视在所有非终态都开启（`10` L225）。
     - 但 `external_change` 的入口只列 `running`、`claimed`/`verifying`/`in_review`/`accepted`、`paused`（`03` L90；`10` L243 写作“任何非 `running` 状态（`claimed`、`verifying`、`in_review`、`accepted`、`paused(*)`）”）。
     - 继续目标的写入通则也没有“从 `ready` 进入 → ?”（`03` L68，`16` L29）。
     - 实现者若没有为 `ready` 补这条边，Goal 准入后开 Run，下一个回合检查点会把来源不明的内容记为 `author:"agent"`，随后进入验证与评审。这正是 ADR-122“来源不明的内容不会先被验证或评审”要排除的情形。
  5. **准备阶段。**
     - 准入通过（`admit`）之后、`run.started` 之前，Goal 仍是 `ready`，`Mode = preparing`，`waitReason` 已清除（`06` L325）。这一段可能持续数分钟（`02` L121）。
     - `06` L839、L848 把源状态写作“`ready`（等待准入的 Run）”。准备阶段是否算在内，这时 `pause`/`take_over` 是返回 `E_BUSY`、取消准备，还是在 `run.started` 后转为对 `running` 的 drain，都没有写。
     - 若在依赖物化写卫星的同时创建人工编辑检出，检出会读到写了一半的内容。
- **为什么重要**：
  - 第 1 项照文档实现即失败。
  - 第 2、4 项分别触及两条既有不变式：“放弃改动不自动开 Run”和“来源不明的内容不进入验证”。
  - 第 3、5 项是界面上能直接点到、却没有定义结果的按钮。
  - 五项都是 ADR-146 新出口带来的回归，或被它放大的旧缺口，集中在 `ready` 一处。
- **文档位置**：`03` L54、L68、L78、L90；`02` L121、L162；`06` L290、L312、L325、L463、L839、L848、L851；`07` L1508；`10` L225、L243；`12` L393；`04` L940；`16` L23、L29、L31、L36；`15` ADR-137 L1042、ADR-146 L1154；`14` G33d(j)。
- **期望的回答形态**：
  - `takeover_from` 加入 `ready`（`06` CHECK、`02` L162、`16` L36）。或者规定从 `ready` 接管时记 `takeoverFrom = running`（视同即将运行），并写明理由。
  - 写明 `takeoverFrom = ready` 时 `discard_human_edits` 的去向：保留 `paused(human)`（与 `running` 同等，建议），或回到 `ready`。写入 `03` L78 与 `16` L31 的判定。
  - 明确 `ready` 中三个动作的适用范围：卫星不存在（从未开过 Run）时，`take_over` 返回 `E_STATE`、界面不提供“我来改”；或者先执行 `ensureSatellite`。`12` L393 与 `04` L940 统一。
  - `03` L68 与 `16` L29 增加“从 `ready` 进入 → `run`”。`03` L90 与 `10` L243 的状态列表加入 `ready`：检测到来源不明的写入 → `paused(external_change)`，继续目标 `run`，`pendingOpenings` 保留。
  - 在 `06` §6.2.4 规定准备阶段的三个命令，二选一：
    - `pause`/`take_over` 返回 `E_BUSY`，直到 `run.started`；
    - 或者取消准备、释放槽位后按 `ready` 处理。
    - `abandon` 在两种方案下都先取消准备。
  - 用例：
    - G33d(j′)：从 `ready{slot}` 接管后放弃改动；
    - G33d(k)：首次排队、没有卫星的 Goal 按“我来改”；
    - G36b(i)：`ready{slot}` 中人在编辑器里保存卫星中的文件；
    - G35e(m)：准备阶段按“暂停”。

**R21-D4-02｜次要**（进入 `ready` 的返工丢失请求类别；`reworkCycles` 的递增点没有定义）

- **问题**：
  1. **`initial` 的定义已不成立。**
     - 准入的排序与评审积压闸门都按请求类别区分：`resume / rework / verify_fix` 排在 `initial` 之前，积压上限“只对 initial（首次启动）生效”（`06` L294、L300；`03` L54“评审余量只闸控首次启动”）。
     - 但 `06` L294 把 `initial` 定义为“`ready → running`”。ADR-146 之后，`ready → running` 也可能是返工、恢复或交还。
  2. **自动返工的类别没有写。**
     - 其他路径的类别都写明了：`request_changes` 发 `run.requested{rework}`（`06` L874）；继续目标 `run` 发 `run.requested{resume}`（`06` L823）；交还以 Run `reason:"resume"` 开始（`06` L849）。
     - 自动返工在 `decide` 中的 `ready` 分支只返回 `{to:"ready", waitReason, appendOpening}`（`07` L1453–1455）。它没有发 `run.requested{rework}`，也没有说明 Goal 停在 `ready` 时类别存在哪里、重启后怎样重建队列。
     - 照 L294 的字面定义，这次返工会被当作 `initial`：
       - 排在其他延续之后；
       - 阻止模式（E8 通过后默认开启）下会被积压上限卡在 `ready{review_capacity}`，而这正是 `03` L54 要避免的情形。
  3. **`reworkCycles` 的递增点不明。**
     - 递增只写在直接开 Run 的分支上：`07` L1488“否则 `running`（返工 +1）”；`10` L895“回到 `running`（…返工 +1）”。
     - 以下两条路径都没有写是否计数：
       - 经 `ready` 排队后再开的返工 Run；
       - ADR-144 的硬上限分支（`paused(budget_hard_cap)` → `resume` → Run `reason:"resume"`）。
     - 若不计数，I6（`03` L112，“违反即为 bug”）在槽位饱和时失效：每次失败都经 `ready` 排队，返工次数不增长，自动返工只剩预算这一道限制。
  - 另：R20 期望 `03` L58/L59/L85 的 `→ running` 改为“准入通过 / 否则 `ready`”，没有改。L54 的入口列已覆盖，不单独扣分，修订时宜一并对齐。
- **为什么重要**：并发饱和是常见情形。此时返工可能越过 I6 的上限，或者在阻止模式下被积压闸门卡住。两者都落在核心循环“验证失败 → 自动返工”上，并且照现有伪代码实现就会出现。
- **文档位置**：`06` L294、L300、L823、L849、L874；`07` L1448–1456、L1488；`10` L895；`03` L54、L58、L112；`02` L194、L336；`14` G33d(i)。
- **期望的回答形态**：
  - 定下返工计数的递增点，二选一：
    - `decide` 判定“按 Agent 路径返工”的那一刻，与随后是立即开 Run、排队还是遇到硬上限无关；
    - 或者以 `rework` 类别开 Run 的那一刻。
  - `07` 的伪代码与 L1488 同步，`10` L895 改为引用。
  - `decide` 的 `ready` 分支同样发 `run.requested{rework}`。写明排队请求的类别随 Goal 持久化（例如由最后一次 `run.requested` 事件投影），重启后据此重建队列。
  - `06` L294 的 `initial` 改为“首次启动（Goal 从未开过 Run）”，不再以 `ready → running` 定义。
  - 用例：
    - 在 G33d(i) 中补断言：Run `reason = rework`，`reworkCycles` + 1，阻止模式下不受积压上限限制；
    - 新增 G33e(n)：槽位持续饱和时连续失败，第 `maxReworkCycles` 次之后进入 `verify_failed_limit`。

### D7 诚实与验证

**R21-D7-01｜次要**（M2：`!cmd` 窗口内 Agent 后台进程的写入仍记为人的改动；`05` 的实例写法未改）

- **问题**：
  1. **Agent 后台进程的写入。**
     - ADR-146 只把与 Agent **工具调用**窗口重叠的写入改记为 `mixedPaths`（`10` L233 第 2′ 行；`06` L190；`07` L1497）。
     - R20-D7-01 列出的第二类没有处理：本 Run 早已在运行的后台进程（watcher、开发服务器、`--watch` 编译器）在人的 `!cmd` 窗口内写入。此时没有工具调用在执行，第 2′ 行又“先于第 2 行判定”，这些写入仍记 `author:"human"`。
     - `user_bash` 实例注入的是同一个 Run 令牌（`15` ADR-144 补记 2，L1131）。第 ③ 种扫描因此只能确认“本 Run 有存活进程”，分不出是人的命令还是 Agent 的 watcher。
     - G35c(s)（`14` L116）只测了 `!cmd` 自己启动的后台进程在调用返回之后的写入，没有测 Agent 的 watcher 在调用窗口之内的写入。
     - 缺的不变式仍是 R19、R20 提出的那一条：Human 层只能包含 Tower 能证明由人的那次调用产生的写入。M2 采用 RPC 形态，Agent 开着 watcher、人执行一条较长的 `!cmd`（例如跑测试），是常见情形。
  2. **`05` 的实例写法。**
     - `05` L381 仍写处理器“在 S2 下返回 `{operations: sandboxedOps}`”，与 ADR-144 补记 2 及 `10` L233 的“另一个 `BashOperations` 实例”不一致（R20-D15-01 第 4 项）。
     - 第 2′ 行要靠“是哪个实例”来界定窗口的起止，这一写法直接决定它能否实现。
- **为什么重要**：这是 Fact/Claim/Human 分层在 M2 中剩下的唯一入口。后果与 R20 相同：
  - 评审中把 Agent 的产物显示为“你的改动”；
  - 失败去向改为不自动返工；
  - seal 写 `Tower-Human-Edit`。
  只影响 M2，因此列为次要，但应在 M2 定稿前关闭。
- **文档位置**：`10` L233、L268（第 ③ 种扫描与后台写入表）；`06` L190；`07` L1497；`05` L381；`15` ADR-144 L1131、ADR-146 L1157；`14` G35c(s)。
- **期望的回答形态**：
  - 第 2′ 行加条件，二选一：
    - 调用窗口内若本 Run 有**不属于该次 `user_bash` 调用进程树**的存活进程，窗口内的写入记 `mixedPaths`，不记纯 `human`。`user_bash` 实例知道自己直接启动的 pid，可以用 R20-D10-01 已采用的后代树遍历确定“本次调用的进程”。
    - 或者 `user_bash` 实例为本次调用另加一个子令牌（Run 令牌保留，settle 照常终止），据此区分写入者。
  - 或者如实登记为 M2 残余：窗口内有 Agent 存活进程时，评审界面把人的改动标为 `混合`。
  - `05` L381 改为“S2 下返回专用于 `user_bash` 的 `BashOperations` 实例（与工具路径不同，ADR-144 补记 2）”。
  - 用例：G35c(s″)（M2）。Agent 先启动 `vite --watch` 持续写 `dist/`，人在此期间执行一条持续 10 s、最后写 `a.txt` 的 `!cmd`。断言 `dist/` 不记纯 `human`（记 `mixed` 或 `agent`），`a.txt` 的归属符合所选规则。

## 5. 结论

- **是否所有维度为 100：否。**
  - D1、D2、D3、D9、D10、D12、D16 为 100，在这七个维度上没有找到可追问的实质问题。
  - 其余九个维度在 97–99 之间，最低为 D4（97）。
- **是否还有可追问的问题：有，但都是次要项。**
  - **第 20 轮核验**：6 条中已解决 4、部分 2、未解决 0。
  - **其他核对**：
    - lint 全部通过，错误码手工核对无违例；
    - Pi 事实（`!cmd` 与流式并发、RPC `bash` 的 `operations` 传递）与源码一致；
    - 排期算术（WBS 118.22、37 周、余量 0.26–0.77、增人备选 32 周）全部成立。
  - **本轮追问**：新增与残留共 **3** 条，阻断 0、重要 0、**次要 3**：
    - R21-D4-01；
    - R21-D4-02；
    - R21-D7-01（M2）。
  - D5、D6、D8、D11、D13、D14、D15 的扣分来自上述条目，不单独编号。
- **设计是否完成：否。**
  - 剩余问题都在 ADR-146 新增的 `ready` 等待态周边，以及 M2 的一条归因规则上，不需要新的架构。每一条都可以用一两句规则加一个用例关闭。
  - 其中两处若照现文实现会直接出错：
    - 从 `ready` 接管违反 `takeover_from` 的 CHECK；
    - 槽位饱和时排队的返工不计入返工次数，或在阻止模式下被积压闸门卡住。
- **下一轮建议按以下顺序修订**：
  1. **R21-D4-02**：定下返工计数的递增点；`decide` 的 `ready` 分支发 `run.requested{rework}`，并持久化请求类别；`06` L294 的 `initial` 改为“首次启动”。这一条在核心循环上，且关系到 I6，最优先。
  2. **R21-D4-01**：
     - `takeover_from` 加 `ready`，并写明放弃改动的去向；
     - 明确没有卫星的 `ready` 与准备阶段中三个命令的行为；
     - `03` L68/L90、`10` L243、`16` L29 把 `ready` 列入继续目标与外部写入的通则。
  3. **R21-D7-01（M2 定稿前）**：`!cmd` 窗口内存在 Agent 存活进程时记 `mixed`，或改用子令牌区分；`05` L381 的实例写法同步。
