## 1. 总评

**第 84 轮的 10 条次要条目与第 83 轮遗留的 R83-D14-01 全部关闭**（核对见 §3）。§5 的 9 条观察都已落地。

**ADR-212 的主体成立**（§3.3）：
- **隔离 agentDir 推迟到 M2**：理由成立。`noExtensions:true` 经源码核实确实单独挡住用户扩展、包中的扩展与 MCP，inline 的 tower-goal 不受影响。连带去掉 codemode 与 tool-search 不破坏 M1 功能。R84-D6-01 与 R84-D5-02 (b)(c) 随之消失。正文中隔离 agentDir 的残留只剩两处措辞（观察 2）。
- **`bashEnv`**：唯一定义（`05` L441）与 Pi `bash.ts:185-206` 一致，`05` L376、`11` L287、L507、C28a 都改为引用，没有 “保留 `PI_*`” 的残留。
- **丢失检出**：运行中与重启时同一规则（`06` L144），`goal.take_over` 的守卫只在检出丢失时生效。经核对，`human_checkout` 为空而 `takeover_from` 非空只可能来自检出丢失：交还、放弃改动与 `goal.resume` 都清除 `takeover_from`。守卫不会误触发。
- **评论 “人关闭”**、**`dropped` 只剩 Pi 的 `handled`**、**情形 B 的影子索引**、**七个用例移到 B4**：唯一定义处的改写都成立，甘特与批次表一致。

**ADR-212 带出或暴露的新问题**：
- **全局根查询的环境**（R85-D11-01，重要）：
  - ADR-212 让 Supervisor “以 Host 的同一环境” 运行这一查询，并称它 “与安装器第 1 阶段同类”。
  - 但按 `05` L451 与 `06` L320，Host 环境含指向 Agent 可写的 `$GS` 的包管理器配置；安装器第 1 阶段的配置在 Agent 不可读的 `$TI`。
  - 于是 Agent 可写的内容能影响沙箱外、决定 Host 从哪里加载扩展包的这一步。Host 存活期间新建会话时 Pi 会重新查询，而清单只在 Host 启动前计算。
- **同一查询的环境与用户终端不同**（R85-D5-01）：
  - 默认情况下全局根是 Tower 自己的 Node 前缀，用户 `pi` 能加载的旧布局全局包在 Tower 中永远列为 “未安装”，而给用户的补救办法无效；
  - 清单是全局的，查询环境却按项目与 Goal 变化；
  - C40 的 “唯一子进程” 对 pnpm 不成立。
- **高风险 Goal “合同中逐项加回扩展”**（R85-D11-02）：没有字段，也没有在 `noExtensions` 下只加载选定扩展的定义。现在 `noExtensions` 是唯一机制，这一项因此变成未定义分支。
- **完整载荷与检查点不可改写的两个后果**（R85-D6-01）：
  - 完整载荷会超过事件载荷 16 KB 的上限（CI 断言），而路径集合不设上限；
  - `verify_pass`、`verify_fail`、`criteria_flip` 三个 landmark 只能在建立之后补写，与 “不再改写” 冲突；`submit`、`rework_start` 也没有写入规则。

**全范围扫描**在 ADR-212 之外新发现：
- “领域表可以从 `events` 完全重建” 对 `runs`（`process_token` 等 NOT NULL 列）与 `needs_you`（没有创建事件）仍不成立。ADR-212 只修了 `checkpoints`（R85-D6-02）。
- 延后执行的交还 `reverify` 读取已被同一交还事务清除的 `takeover_from`，于是丢失 `returnTo`（R85-D4-01，早于 ADR-212）。

### D11 安全与自主度

**R85-D11-01｜重要**（全局根查询所在的环境含 Agent 可写的包管理器配置；Host 存活期间的新会话不经清单复核）

- **问题**：
  - **查询读什么**：
    - ADR-212 规定，静态清单与 Pi 一样，在用户级 npm 来源不在 `<agentDir>/npm/` 下时查包管理器的全局根。“Supervisor 以 Host 的同一环境与同一 `npmCommand` 运行同一查询”，并称它 “与安装器第 1 阶段同类”（`05` L1330，`11` L607）。
    - Pi 在 Host 中以 `process.env` 运行这一查询（文首）。全局根的取值取决于包管理器读到的用户配置。
  - **Host 环境里有什么**：
    - `05` L451 的 “包管理器私有存储” 行在 Host 列打 ✔，写明 `NPM_CONFIG_USERCONFIG` 指向 “Tower 为角色 A 生成的副本（`$GS`）”；`07` L569 同此；
    - `06` L320 的 Host 环境拼装同样列入 “`16` §16.8 的包管理器环境变量表”。
  - **这份配置 Agent 可写**：
    - `$GS` = `<wtRoot>/_stores/<goalId>`，“A 可写”（`16` L1305）；
    - S2 写允许包含整个 `_stores/<goalId>/`，写拒绝一行没有它（`11` L348、L350）；
    - 篡改用例 P8 正是以 “Agent 改写 `$GS/npmrc`” 为前提（`14` L142，`16` L1354），而该用例只断言验证器不受影响。
    - 第 1 阶段的配置在 `$TI`，Agent 不可读（`16` L1303、L1329）。所以 “与安装器第 1 阶段同类” 不成立。
  - **复核点只有一个**：
    - 清单只在 “Engine Host 启动前” 计算（`11` L607）；
    - 但 Host 在 `paused` 5 分钟内保持存活（`06` L169），恢复后的新 Run，以及 Run 中的上下文交接（`05` L1234 `newSession`），都会经 runtime 工厂重新创建会话；
    - 按 Pi 的写法，这会重建资源加载器、重新查询全局根（文首）。正文没有要求这时与已确认的清单比对：“首次加载后发现的能力” 只比对注册的工具名，不一致时只告警（`05` L1330）。
  - **后果**：
    - 用户设置中有尚未装进 `<agentDir>/npm/` 的 npm 包时（正是 ADR-211/212 预期并单列为 “未安装” 的情形），Agent 可写的配置能改变沙箱外这一步的结果；
    - 于是在标准风险、清单已确认的 Goal 中，Host 可能把 Agent 写出的内容当作扩展包、在沙箱之外加载，且不经过清单确认。
    - 这正是 `05` §5.10 “确认之前不执行任何扩展或包的代码”“与 Pi 实际加载扩展的目录相同” 要排除的一类后果。它也违反 `11` §11.6.2 的原则：Agent 可写的配置不得被沙箱外的进程读取，并据此决定执行什么（`07` L551 为验证器立了同一条规则）。
  - 下次 Host 启动时，Supervisor 以同一环境重新计算，会把变化后的条目列为新增并要求确认。所以在 Host 重启之后，这一防线落在人对确认卡片的审查上；在 Host 存活期间，则没有任何确认。
- **为什么是重要**：
  - 照 `05` L451、`06` L320 与 ADR-212 的字面实现，沙箱外决定加载哪份扩展代码的这一步，会读取 Agent 可写的配置；
  - 清单的不变式在 Host 存活期间的新会话上不成立。
  - 触发需要用户设置中有一个未装进 agentDir 的 npm 包，并不罕见：旧版 Pi 把包装在全局目录，正是 Pi 保留这条回落路径的原因。

- **期望的回答形态**：在 `05` §5.3.6（Host 环境的唯一定义处）与 §5.10 各写一句：
  - **(a)** Host 进程环境中不含任何指向 Agent 可写位置的包管理器配置：
    - 角色 A 的包管理器变量只由 `bashEnv` 加入 bash 环境（表中该行 Host 列改为 “—”）；`06` L320 与 `11` L507 同步；

**R85-D11-02｜次要**（高风险 Goal “合同中逐项加回扩展” 没有字段与机制）

- **问题**：
  - `11` L608 “合同中可逐项加回（属于合同修订，记录在审计中）”，`16` L1230 “合同逐项加回”，`05` L1330 末句 “高风险 Goal 要逐项加回扩展，需要修订合同”。
  - ADR-212 之后，高风险 Goal 不加载扩展的唯一机制是会话级的 `noExtensions:true`，它全有或全无。正文没有定义怎样只加回选定的一项：
    - `RunSpec.resources` 的类型 `PiResourcePolicy` 只在 `05` L89 出现一次，从未定义；骨架只读 `noExtensions`、`skills`、`contextFiles`（L352–L357）；
    - `Contract` 没有扩展相关的字段（`02` §2.5）；
    - 降低 `riskTier` 不是合同修订，还会同时改变评审下限与验收位置（`16` L1131）。
  - Pi v1.2.0 其实可以做到：`noExtensions:true` 时保留 `additionalExtensionPaths` 中的扩展，内置的 mcp 也可以以 `builtin:mcp` 的形式列入。但 `extensionsOverride` 不行，它在加载之后才过滤，代码已经执行（`11` L576）。
  - 没有定义时，实现者会各取一种：
    - 以 `noExtensions:false` 加 `extensionsOverride`：高风险 Goal 中全部已确认扩展的模块顶层代码都会执行，违背 “高风险 Goal 默认不加载扩展”；
    - 以 `additionalExtensionPaths`；
    - 或干脆不做。
- **为什么是次要**：承诺的功能没有定义；其中一种自然的实现（`extensionsOverride`）与高风险 Goal 的默认规则冲突，但触发需要人主动修订合同。
- **文档位置**：`05` L89、L352–L357、L1330；`11` L576、L608；`16` L1131、L1230；`02` §2.5。
- **期望的回答形态**：在 `05` §5.10（唯一定义）二选一：
  - 删去 M1 的 “逐项加回”（`11` L608、`16` L1230 同步）：高风险 Goal 要用扩展只能降低 `riskTier`（仅本机）；
  - 或给 `RunSpec.resources` 加一个字段（取已确认清单中的条目 id），写明映射为 `noExtensions:true` + `additionalExtensionPaths`，MCP 只能整体加回，并写明不得以 `extensionsOverride` 实现。

### D5 Agent 架构与 Pi 集成

**R85-D5-01｜次要**（全局根查询的环境与用户终端不同，且按项目与 Goal 变化）

- **问题**：R85-D11-01 修正之后仍然存在的三点：
  - **(a) 补救建议无效**：
    - Host 的 `PATH` 以 Tower 按项目选出的 Node 与包管理器开头（`05` L457）；角色 A 的 npmrc 副本按白名单去掉了 `prefix` 与 `globalconfig`（`16` L1329）。
    - 默认 `npmCommand` 下，全局根因此是 Tower 自己的 Node 前缀，而不是用户终端中的全局目录。
    - 用户自己的 `pi` 能从旧布局全局目录加载的包，在 Tower 中会恒为 “未安装”。
    - 清单与 `00` L99 给的补救（“请在你的终端中运行 `pi` 安装”）无效：用户的 `pi` 找得到这个包，不会安装任何东西。
  - **(b) 清单只有一份，环境却有多份**：
    - 清单是全局的（`owner:global`，`11` L607），而 “Host 的同一环境” 随项目（Node 版本）与 Goal（`$GS`）变化；
    - 打包模式（`06` L42，可能成为 M1 默认，`16` L858）中，一个进程环境容不下多个 Goal 的这些值。
    - 正文没有说清单按哪个环境计算；不同环境求出的全局根不同，清单会在两种结果之间来回变化、反复要求确认。
  - **(c) C40 的断言对 pnpm 不成立**：C40（`05` L1473）断言全局根查询 “是唯一的包管理器子进程”。npm 的结果按实例缓存，pnpm 的 `list -g` 每个包运行一次（文首），夹具里有两个 npm 来源，在 pnpm 下就会有两次。
- **为什么是次要**：不越过安全边界。(a) 使一类用户的扩展在 Tower 中永远不可用，且给的说法不实；(b)(c) 使实现与测试分叉。
- **文档位置**：`00` L99；`05` L457、L1330、L1473；`06` L42；`11` L607；`16` L858、L1329。
- **期望的回答形态**：与 R85-D11-01 (a) 合在一句：
  - 写明全局根查询的环境是整台机器同一个、不随项目与 Goal 变化的环境，以及其中 `PATH` 与包管理器配置的来源；
  - 二选一：取用户登录 shell 中的包管理器，使结果与用户终端一致；或写明 “旧布局全局安装的包在 Tower 中不加载，请用 `pi install` 重新安装到你的 Pi 目录”，清单与 `00` L99 的文案改为这一句；
  - C40 改为 “全局根查询之外没有包管理器子进程”，不限次数。

### D6 系统架构与可靠性

**R85-D6-01｜次要**（完整的 `checkpoint.created` 载荷与 16 KB 上限；三个 landmark 只能事后补写）

- **问题**：
  - **(a) 载荷大小**：
    - ADR-212 把载荷定为 `checkpoints` 行的全部列，含 `excludedPaths`、`externalPaths`、`mixedPaths`、`humanPaths`（`16` L662），“Projector 只从它写入该行”。
    - 事件载荷有统一上限：“单条负载上限 16 KB，超出即视为 bug（CI 断言）”（`13` L247，`06` L383 `CHECK` 注释，`16` L870）。
    - 而这些路径集合没有上限：`excludedPaths` 明写 “路径数不设上限”（`10` L207）；后台进程写出构建目录时的 `externalPaths`、大的交还的 `humanPaths` 都可能有上千条。
    - 实现者只能自选：截断（行与载荷都丢路径，作者推导与评审 “混合” 标注随之出错）、破坏 CI 断言，或自创溢出格式。
  - **(b) landmark 的写入点**：
    - `Checkpoint.landmarks` 的取值仍含 `submit`、`verify_pass`、`verify_fail`、`criteria_flip`、`rework_start`（`10` L792，`06` L594–L597 触发器，`16` L184）。
    - 但 `10` L732 列出的建立入口（回合、`agent_bg_done`、`external_change_kept`、`safety`、`human_edit`）中，没有任何一条规则写这五个值。
    - 其中 `verify_pass`、`verify_fail`、`criteria_flip` 在验证结束之后才可求出，那时检查点早已建立。按 ADR-212 “建立后不再改写”，它们永远写不进去；若事后补写，又不在载荷中，重建时丢失。
    - 时间线实际以 Fact 事件为验证地标（`10` L862），这三个值看来已无用途。
    - `submit` 与 `rework_start` 在建立时可求出，`13` L356 也依赖它们（“地标检查点（submit、rework_start、safety）永不降级”），但同样没有写入规则。
- **为什么是次要**：(a) 只在大的路径集合上出现，但照 ADR-212 实现必然触发 CI 断言；(b) 是登记的取值没有写入点，实现者会各自补写或忽略，并与 “不再改写” 冲突。
- **文档位置**：`06` L383、L594–L597；`10` L207、L732、L792、L862；`13` L247、L356；`16` L184、L662、L870。
- **期望的回答形态**：
  - (a) 在 `16` L662（唯一定义）补一句：路径集合超过上限时的处置。例如整组写入 `~/.tower/goals/<G>/evidence/` 下按内容哈希命名的文件，载荷只带哈希与条数；或在 `13` §13.9.1 写明本事件的例外与上限。
  - (b) 在 `10` §10.7.1 `landmarks` 的唯一定义处：删去 `verify_pass`、`verify_fail`、`criteria_flip`（DDL 触发器与 `16` L184 同步，验证地标只来自 Fact），并写明 `submit`、`rework_start` 在回合检查点建立时按本回合是否含 `submit`、是否为返工 Run 的首个回合写入。

**R85-D6-02｜次要**（“领域表可以从 `events` 完全重建” 对 `runs`、`needs_you` 仍不成立）

- **问题**：
  - `06` L221 现在写：“领域表是事件的写穿投影，可以从 `events` 完全重建（`tower doctor --rebuild`）；`checkpoints` 表由 `checkpoint.created` 的完整载荷投影，唯一不由事件承载的列是信息性的 `in_user_repo`”。读者会理解为：其余表都能完整重建。
  - 但：
    - `runs` 表（`06` L544–L562）的 `process_token`（NOT NULL，“后台进程识别的唯一持久化依据”）、`session_id`、`adapter`、`engine_version`、`attempt_n`、`host_id`、`phase`、`submit_tool_call_id` 等列，没有事件承载。`run.*` 的载荷只有 `run.requested{kind}`、`run.started{openingIds}`、`run.ended{outcome, reason}`（`16` L649）。
    - `needs_you` 只有 `needs_you.resolved` 与 `needs_you.snoozed`（`16` L654），没有创建事件；而 `06` L241 称 Needs-You 由事件产生。
  - 照字面实现 `tower doctor --rebuild` 或投影版本迁移（`06` L63 “校验投影版本”）：
    - `runs.process_token` 的 NOT NULL 约束会失败；
    - 或者重建后无法识别未结束 Run 的后台进程（`06` L145 的重启终止范围）。
  - 这与 R84-D6-02 同类，ADR-212 只修了 `checkpoints`。
- **为什么是次要**：日常路径不受影响，只在重建或迁移时出问题；但断言与事件表直接冲突，实现者会按其中一处走。
- **文档位置**：`06` L63、L145、L221、L241、L544–L562；`16` L649、L654。
- **期望的回答形态**：在 `06` §6.2.1 写一条通则（唯一定义），二选一：
  - “建立或改写某行的事件，载荷含该行被写入的全部列”，并补全 `run.started`/`run.ended` 的载荷与 Needs-You 的创建事件（`16` §16.1.14 同步）；
  - 或收窄断言：列出不能从事件重建的表与列（`runs` 的进程与会话列、`needs_you`），以及重建时的来源或丢失的后果。

### D4 领域模型与生命周期

**R85-D4-01｜次要**（延后执行的交还 `reverify` 丢失 `returnTo`）

- **问题**：
  - **交还时**：`goal.hand_back` 第 ③ 步在同一事务中 “清除 `human_checkout` 与 `takeover_from`”（`06` L904；列注释 L504 “hand_back … 时清除”）。随后，若仍有保留原因，只写 `pending_hand_back={mode, at, decisionId}`（L480），由 `onAllReasonsCleared()` 第 1 步延后执行。
  - **延后执行时**：`reverify` 的规则是 “`returnTo` = `takeoverFrom` ∈ {`in_review`, `accepted`} 时写 `Goal.verifyFrom = takeoverFrom`，否则 `claimed`”（`16` L45，`10` L1014，`02` L188）。
  - **结果**：延后执行时 `takeover_from` 早已为空，`verifyFrom` 一律取 `claimed`。从 `in_review`/`accepted` 接管、交还时选 “直接重新验证”、但因保留原因（例如 `verify_env_error`）而延后的 Goal，验证之后不再按 “回到评审 / 验收” 的延续处理（`02` L188 “验收延续据此判定”）。
  - `pending_hand_back` 的形状没有 `returnTo`，继续目标又在执行 `pendingHandBack` 后被清除。所以没有别的字段能补回这一信息。
  - 立即执行的情形在同一命令中先读后清，不受影响。
- **为什么是次要**：结果偏保守（多走一次评审），不丢数据；但两处文字直接冲突，实现者会各自补规则（延后清除，或补字段）。这一问题早于 ADR-212。
- **文档位置**：`02` L188；`06` L480、L504、L904；`10` L1014；`16` L45。
- **期望的回答形态**：在 `16` L45（`pendingHandBack` 的唯一定义）二选一：
  - `pendingHandBack` 加 `returnTo?`（交还时由 `takeover_from` 取值），延后执行只读它；
  - 或 `goal.hand_back` 写 `pending_hand_back` 时不清除 `takeover_from`，由 `onAllReasonsCleared()` 第 1 步执行后清除（`06` L504 列注释同步）。

  - **不扣分的观察**：
    1. **`noExtensions` 连带去掉 codemode 与 tool_search**：
       - `05` L277 “与 CLI 的行为完全一致：默认加载”、L1332 “MCP / codemode / tool_search 继承用户的 Pi 配置”、G10（L1278）对清单确认之前与高风险 Goal 不再成立；
       - `00` L98 只写 “不加载任何扩展与 MCP”。
       - 宜各补半句 “（清单确认之前与 `riskTier=high` 时这三项都不加载，D46）”。不影响 M1 功能（经核实）。
    2. **残留措辞**：`11` L450 “Host 不在沙箱中，非隔离模式本来就读它” 宜改为 “Host 不在沙箱中，本来就读它”；`14` L704 K11 “高风险隔离” 宜改为 “高风险 Goal 不加载扩展”。lint (d) 的隔离 agentDir 一项可补 “非隔离模式”。
    3. **`npmCommand` 与同步查询**：
       - `npmCommand` 只来自用户级设置（不信任的项目设置整体不读，`settings-manager.ts:364-366`），Agent 不可写也不可读；用户自己的 `pi` 运行同一条命令。所以由 Supervisor 运行它可以接受。
       - 但 “只运行包管理器自身” 宜改为 “运行你在 Pi 设置中配置的 `npmCommand`（可以是包装脚本）”。
       - Pi 的查询是同步、无超时的（`package-manager.ts:2752-2765`）：包装命令挂起时，Host 的会话创建被阻塞，直到 120 s 的准备时限。Supervisor 自己的查询宜写明超时与失败时的清单表现（按 “查询失败 = 没有全局根”，与 Pi `:2143-2149` 一致）。
       - `13` 没有这一步的预算，可在冷恢复目标旁注明。
    4. **`rg`/`fd` 提示的文案**：`04` L1453 “搜索工具不可用：塑形与评审中只能逐个读文件…” 与 `05` L464 “`grep`/`find` 不可用，塑形与评审中只能用 `read`/`ls` 查看代码…” 不一致，宜以一处为准；检查只在首次运行时做，用户之后装好或删掉时没有复查，可在能力摘要中每次 Host 启动时按同一顺序重新判定。
    5. **评论关闭的参数与边界**：
       - `06` L920 三条命令共用 `{goalId, anchor, body, timing, requiresChange, confirmSecret?}`，`edit`/`delete` 缺评论 id；
       - `comment.delete` 删去一条已送达的必须修复评论，同样使它不再阻断验收，却没有 “你已关闭” 的回执，宜写明删除必须修复评论按 “关闭” 留痕，或只允许删除未送达的；
       - 远程关闭（`16` L1114 三端 ✓）与总规则 3 “改变验收依据的命令只能在本机执行” 的关系，随 `serve`（M2）复审；
       - `05` L1193 非 hunk 锚点的列举漏了 `trace`（`02` L575）。
    6. **丢失检出卡片的 “再次接管”**：`external_change` 在接管期间照常记入 `alsoApplies`（`10` L403），未解除时 `goal.take_over` 返回 `E_STATE`（`06` L903）。卡片（`06` L144、`08` L514）宜在这种情况下把 “再次接管” 置灰，提示先采纳或撤销外部改动。另外，丢失后再次接管写入的新 `human_checkout` 没有 `rebuiltTree`，`discard_human_edits` 的比较基准因此回到 pin；宜写明 “接管以来” 从第一次接管算起。
    7. **`bg_process_survived` 注记**：`10` L392、L978–L980 说检查点 “附 `bg_process_survived` 注记”，但 `checkpoints` 表与完整载荷都没有这一项。宜写明它由同一时间窗内的 `anomaly{bg_process_survived}` Fact 推导，不存储在检查点上。
    8. **多仓库事件缺 `projectId`**：`workspace.recovered{…, unusableCheckpoints?}` 与 `satellite.recovered{tree, checkpointN?, by}`（`16` L661、L662）在多仓库 Goal（`10` §10.13，检查点按仓库编号）中不能唯一指向检查点，宜各补 `projectId`。
    9. **`07` L246 的返回类型**：`worktreeTree` 的声明返回类型没有 `tempIndex`，而 L265 返回它、L262 的调用规则依赖它。
    10. **双 landmark 的时间线标签**：交还第 6 步建立的检查点 landmarks 为 `[safety, agent_bg_done]`（`10` L980）。`04` L717 与 `12` L724 每种只给一个标签，宜写明这时显示 `保护快照`，悬停列出两者。
    11. **G46 (bi) 的夹具**：C40 固定了 “夹具的全局根中没有这两个包”，G46 (bi) 没有，结果因此依赖测试机器；宜同样固定。
- **设计是否完成：ADR-212 正确地关闭了第 84 轮的全部条目。** 推迟隔离 agentDir 的决定经源码核实成立，`noExtensions` 单独提供了它在 M1 中唯一的保护。
  - 本轮有 **1 条重要条目**：
    - 新加入清单的全局根查询，与 Pi 在 Host 中的同一查询，都运行在一个含 Agent 可写包管理器配置的环境中；
    - Host 存活期间新建会话时又会重新查询，而不经清单复核。
    - 这使 “确认之前不执行扩展或包的代码” 在一个可达的配置下不成立。修正只需在 Host 环境的唯一定义处去掉这些变量，并在会话创建后比对已确认的清单。
  - 5 条次要条目分三类：
    - **全局根查询的其余问题**：R85-D5-01（环境与用户终端不同、清单与环境一对多、C40 的 pnpm 情形）；
    - **ADR-212 的连带后果**：R85-D11-02（逐项加回扩展没有机制）、R85-D6-01（载荷上限与三个 landmark）；
    - **全范围扫描**：R85-D6-02（`runs`、`needs_you` 不能从事件重建）、R85-D4-01（延后的 `reverify` 丢失 `returnTo`）。
- **下一轮建议**：
  1. **R85-D11-01**：Host 环境不含指向 Agent 可写位置的包管理器配置（只由 `bashEnv` 加入）；Host 内每次创建会话后比对已确认的清单；G46 补一组。
  2. **R85-D5-01**：写明全局根查询的环境；旧布局全局包的准确文案或取用户的包管理器；C40 不限次数。
  3. **R85-D6-01**：路径集合超限的处置；删去三个验证类 landmark，写明 `submit`、`rework_start` 的写入点。
  4. **R85-D11-02**：删去 “逐项加回” 或补字段与映射。
  5. **R85-D6-02**：载荷通则并补全 `run.*` 与 Needs-You 的创建事件，或收窄断言。
  6. **R85-D4-01**：`pendingHandBack.returnTo` 或延后清除 `takeover_from`。
