## 1. 总评

ADR-171 按第 45 轮的建议关闭了全部四条问题：
- `16` L510 的判定时机与 `seeded` 作用范围改为“任何把本地文件复制出用户检出的地方”，列举四处（含人工编辑检出），今后新增的复制点自动适用；
- “同一份内容”写成规则：每个条目只读一次，读入内存后判定再写出，`unmarked.contentHash` 的比较也取自这一份；
- `mark_secret` 对非 `isSecret` 条目写 `user` 并清除 `unmarked`，对已是 `isSecret` 的条目为无操作、不覆盖依据。`02`、`06`、`16` 矩阵与 `04` 都同步了；
- 不可读或不存在时不复制、不改写分类、不发事件，改发独立的 L1 通知；事件 producer 为 `sm`，在 `06` L391 的 producer 列表内；
- `14` L394 已改为“短于最长角色线（28.88）”，G46 加了 (af)(ag)(ah)；
- 第 45 轮 +0.03 人周的登记算术成立：WBS 121.60，各线余量与 M1 38 周、增人 33 周都成立。

M1 头号安全不变式这一条线，本轮没有发现缺口。按“谁写 `secretBy` / `unmarked`、哪些地方复制”逐项检查，四个复制点、三个写入者（复制前的判定、`mark_secret`、`unmark_secret`）与两条 DDL CHECK 相互一致。

沿 ADR-171 新开的分支（不可读 / 不存在）以及“判定与复制用同一份内容”的延伸方向复查，还有四处**次要**问题，都不触及安全不变式：
1. 自动恢复会改写 `unmarked`，但没有登记事件；“无法读取”通知没有载体（事件、Fact 或去重键都没写）。
2. `07` 中缓存键的 `envHash` 公式不含被播种文件的哈希，与同文 L482“进入 envHash”的说法矛盾；指纹 `extra` 的哈希与复制也不是同一次读取。
3. “无法读取”通知的适用范围包括本来就不会复制的条目；同时，失败卡片与返工证据的提示不覆盖“本次未复制”的已批准文件。后者是 ADR-171 相对 ADR-170 的一处小回退。
4. `14` L400 的加法式写错 0.01；依赖链中的 W9b 仍按 6.2 计。

       - 已取消标记的条目内容变化且再次命中时清除 `unmarked`，即“自动恢复为机密并通知”（`16` L510、`02` L113、`06` L234、`04` L1301）：**没有登记任何事件**。
     - 人的取消标记是 `HumanDecision{unmark_secret_file}`，Tower 自动撤销这个决定却不留事件。审计上看不到“谁、何时把它改回机密”，通知也没有可挂靠的提交对象。
  2. **“无法读取”通知没有载体**：
     - `16` L510 明确“不发上述事件”，只说“另发一条 L1 通知……按条目去重，之后成功读取时自动消失”。但没有写它是什么：事件、项目级 Fact，还是只在内存中的提示。
     - 由此也没有定义：
       - 去重键（`08` §8.4 的 `dedupeKey` 只适用于 Needs-You 条目）；
       - “自动消失”由什么触发；
       - 重启后是否还在；
       - 如何进入简报与摘要（`08` §8.1 L1 的渠道之一）。
     - `06` L219 要求通知类后效在提交之后、以幂等键执行，这也需要一个提交对象。
- **为什么是次要**：两处都不影响安全一侧（不复制的结论已经写定），也不丢用户数据。缺的是可审计与可重建：实现者需要自己发明载体，不同复制点（准备、验证调度、接管命令）可能各写一套。
- **文档位置**：`16` L284、L510；`02` L113；`06` L219、L234、L391、L407、L777；`10` L1241；`04` L1300-1301；`08` §8.1、§8.4。
- **期望的回答形态**：
  - 在 `16` 登记一条自动恢复的事件，`06` 事件注释与 `10` §10.18 同步。例如 `project.local_file_unmark_reverted{projectId, path}`，`source = system`，producer `sm`，与清除 `unmarked` 同一事务写入。
  - 为“无法读取”通知选定载体，在 `16` 一处写明。例如一个项目级 Fact `local_file_unreadable{path}`，同一条目只保留一条，下一次成功读取时失效；或者明确它不持久化、重启后由下一次复制重新产生。

### D7 诚实与验证

**R46-D7-01｜次要**（同指纹缓存的 `envHash` 不含被播种文件的哈希，与 `07` L482 矛盾；指纹 `extra` 与复制不是同一次读取）

- **问题**：
  1. **两处说法不一致**：
     - `07` L482 写“被播种文件的内容哈希进入指纹的 `extra` 部分（§7.3.2）与 envHash；未播种的含机密文件不进入”；
     - 但 `07` L706 的公式是 `envHash = sha256(canonicalJSON(生效 env 去掉 TMPDIR/端口) + toolchainVersions)`，**不含**被播种文件。
     - 同指纹缓存的键是 `(criterionSpecHash, treeSha, envHash, depsKey, profileVersion)`（L852），并声称“键覆盖全部输入”。
     - 按 L706 实现时会出现以下链条：
       - 本地文件变化后，指纹 `extra` 变化，Fact 变旧（L327），于是重新验证；
       - 重新验证时 tree 与 `envHash` 都没有变，缓存命中，复用的是旧内容下的结果。
     - 被播种的集合本身变化时（ADR-170/171 的新近命中，或本次不可读而未复制）也是同样的情形。
  2. **读取时机**：
     - 指纹 `extra` 由 `hashSeededLocalFiles` 在 `worktreeTree` 中单独读取用户检出（L259-261）；
     - pin 的指纹又在验证槽位复制之前计算。
     - 所以记在验证结果上的 `extra` 不一定对应槽位里实际写出的那一份。ADR-171 的“同一份内容”只覆盖了复制与 `unmarked.contentHash`。
- **为什么是次要**：
  - 后果属于诚实一侧：一个 `criterion_check` 可能被复用到它没有实际运行过的本地文件内容上。
  - 但 L482 有明文，按正文实现的人多半会把哈希放进去；第 2 点需要人恰好在两次读取之间改文件。
  - 这是 ADR-078 以来的旧问题，不是 ADR-171 引入的；ADR-170/171 让“被播种集合不随 tree 变化”的情形变多了。
  - 不涉及安全，不丢数据。
- **文档位置**：`07` L259-261、L327、L482、L706、L852；`16` L510；`15` ADR-171。
- **期望的回答形态**：
  - L706 的公式加上“该槽位实际播种的本地文件的 `(path, contentHash)` 列表”，哈希取自复制时的同一次读取；未复制的条目（机密或不可读）不进入，但以“未复制”标记进入，使集合变化也能改变键。
  - 在 `16` L510 的“同一份内容”中加一句：验证结果入账时记录的本地文件哈希，取自该槽位复制时的那一份。

### D8 注意力与交互

**R46-D8-01｜次要**（“无法读取”通知的适用范围过宽；本次未复制的已批准文件不进入失败提示）

- **问题**：
  1. **适用范围**：
     - `16` L510 的重新判定对“清单中**每个**条目”进行，不可读分支写的是“清单中的文件……不可读或不存在时，这次不复制……另发一条 L1 通知‘本次未复制’”。
     - 按字面，未批准的条目与 `isSecret` 的条目（例如按文件名判定的 `.env.local`）缺失时也会发出“本次未复制”。但它们本来就不会被复制，这句话暗示了一次没有发生的复制，而且会一直挂到文件恢复为止。
     - 第 45 轮 §5 的观察（未批准条目命中时，“不再播种”的文案不准确）属于同一类问题，本轮仍未处理。
  2. **失败提示不覆盖**：
     - ADR-169 规定失败卡片、返工证据与试运行红灯旁的 Claim 提示“只列 `isSecret` 的条目”（`07` L451-453、`16` L510）。
     - 已批准的普通文件本次因不可读或不存在而未复制时，验证失败的卡片与返工证据中都没有任何提示。Agent 被送去返工一个它看不见、也修不了的原因（它不能读用户检出），直到返工上限。人也要自己把项目级的 L1 通知和这次失败联系起来。
     - ADR-170 之下，不可读按命中处理，文件会变成 `isSecret`，从而出现在提示中。ADR-171 改为不改写分类后，这条联系断了，是一处小回退。
- **为什么是次要**：
  - 返工有上限，结局有界；
  - 不涉及安全，不丢数据；
  - L1 不消耗打扰预算。
  - 但第 1 点是一条不如实的陈述，第 2 点会浪费返工轮次。
- **文档位置**：`16` L510；`04` L1300；`07` L451-453；`06` L234；`14` G46(ah)、(n)(ac)。
- **期望的回答形态**：
  - **第 1 点**：在 `16` L510 把通知限定为“这次本应复制的条目”，即 `seeded` 的条目，以及 `withSecrets` 时的 `isSecret` 条目。其他条目缺失时不通知，或只在设置页该行显示 `◇ 文件不存在`。
  - **第 2 点**：在 `07` §7.4.1 的提示规则中加一句。可以是：本次验证有已批准但未复制的文件时，卡片与返工证据附一行 Claim，例如“本次验证中 `<路径>` 未复制（无法读取或不存在）；若该失败源于此，请恢复该文件后重试验证”，并说明 Agent 无法修复。也可以是：明确不提示，并说明理由。
  - **用例**：G46(ah) 补一组断言（失败时的提示，或明确没有提示）。

### D14 路线图与可验证性

**R46-D14-01｜次要**（L400 加法式错 0.01；依赖链中的 W9b 旧值）

  1. `14` L400：“全部工作（含 QA）= 28.22 + 28.88 + 28.18 + 27.92 + 安全线 14.19 = 127.38 人周”。左边五个取整值相加为 **127.39**。127.38 是未取整值（28.215 + 28.875 + 28.182 + 27.918 + 14.19）的和。

  - **其他核对**：
    - lint 全部通过（exit 0）；

    - 排期结论成立：WBS 121.60；各线 26.05 / 26.35 / 27.42 / 28.38 / 13.40；余量 0.78 / 0.12 / 0.82 / 1.08 / 0.62；38 周；增人 33 周。`14` 与 `15` 一致，只有 L400 加法式与依赖链 W9b 两处数值问题。
  - **不扣分的观察**：
    - **`mark_secret` 与已存在的副本**：标记为机密（或自动恢复）后，“此后不再复制”如实成立，但已建成的卫星中仍有先前复制的那一份。那一份是人当初批准或取消标记时同意暴露的内容，不违反 M1 不变式。若希望更彻底，可在 `04` 的标记确认中加一句“已存在的工作目录中的副本不会被删除”。
    - **对不在清单中的路径执行 `mark_secret` / `unmark_secret`**：没有像 `approve` 那样写明返回 `E_STATE`。前者即使隐式插入也只会得到一条不播种的条目，后者已被“`secretBy = null` → `E_STATE`”覆盖，不扣分。建议顺手与 `approve` 写成同一守卫。
    - **`10` L1161 的卫星重建**：可以加一句引用 `16` 的判定时机，与 L367 的写法一致。不加也不矛盾。
- **设计是否完成：在安全与领域模型上已经收敛；还剩四条次要的文字修订。**
  - ADR-171 干净地关闭了第 45 轮的四条问题。本地文件机密分类的“复制点 × 写入者 × 约束”第一次没有发现任何不一致，M1 头号安全不变式在本地文件上成立。
  - 本轮的四条问题都在安全线之外：两处载体或事件缺失、一处缓存键公式与正文矛盾、一处排期算式。修复都只需要文字，合计不足 0.02 人周。
- **下一轮建议按以下顺序修订**：
  1. **R46-D7-01**：`07` L706 的 `envHash` 加入被播种文件的 `(path, contentHash)`（取自复制时的同一次读取，未复制的条目以标记进入）；`16` L510 的“同一份内容”加上验证入账时的哈希。
  2. **R46-D8-01**：“无法读取”通知限定为本应复制的条目；`07` §7.4.1 对“本次未复制的已批准文件”给出提示，或明确不提示并写明理由；G46(ah) 补断言。
  3. **R46-D6-01**：登记自动恢复事件；为“无法读取”通知选定载体并写明去重与消失条件。
  4. **R46-D14-01**：L400 改为 127.39（或未取整的式子）；依赖链按 W9b 6.5 改为 19.7，或注明理由。

  **工时与排期**：上述修订估计合计约 0.02 人周。
