### D6 系统架构与可靠性

**R58-D6-01｜次要**（验收面板写“验收后条目随目标归档、不送达”，但 `accepted` 不是终态，`goal.accept` 也不清空 `pendingOpenings`。从 `accepted` 开始的任何 Run 都会送出这些条目）

- **问题**：
  - **新文案**（`04` L1022，ADR-185 观察 1）：目标进入待验收或已验收时队列仍非空，显示 `下次运行开场：N 条，验收后不会送达`；“验收后条目随目标归档，不送达”。
  - **验收后不会归档**：
    - `accepted` 只在“验收但不合并”或 `integrated` 宽限期满后才归档（`03` L60–61）；
    - M1 的 `branch_only` 会让 Goal 长期停在 `accepted`。
  - **验收也不清空队列**：
    - `goal.accept`（`06` L919）不涉及 `pending_openings`；
    - `16` L36：队列在“下一次任何 Run 开始时”消费，“执行 `pendingHandBack`、继续目标的改写、验证与评审都**不**清空它”。
  - **从 `accepted` 仍可开 Run**：
    - `request_changes`：`06` L920 明确允许从 `accepted` 发起；
    - `take_over` 后以 `continue_agent` 交还；
    - 修订标准或 `agent_bg` 写入使 Goal 进入 `verifying`，验证失败后走 Agent 路径自动返工。
    - 这些 Run 都会把验收前留下的条目作为开场送出，与“不会送达”相反。
  - **两种实现**：
    - 在 `goal.accept` 的事务中清空队列（文案成立）；
    - 保留队列（文案不成立）。保留时，人以为不会送达的旧指令（例如“不要动 webhook”）可能在很久之后的返工中被注入。
  - 放弃后复活（`03` L185）是否携带队列也没有写，但复活建的是新 Goal，影响很小。
- **为什么是次要**：条目在卡片上可见、可撤回（`16` L36），不越过安全边界。但新文案与队列规则直接冲突，实现会分歧。
- **文档位置**：`03` L60–61、L185；`04` L1022；`06` L855、L919–922；`16` L36；`15` L2257。
- **期望的回答形态**：在 `16` §16.1 的 `Goal.pendingOpenings` 行（唯一定义）写明 `goal.accept` 对队列的处理，二选一：
  - **清空**：同一事务把剩余条目记为 `withdraw_opening{by:"accept"}`，轨迹可查；
  - **保留**：文案改为“验收后保留，下一次运行（例如请求修改）时送出”。
  - 并说明 `abandon` 与复活时的处理。G46 或 G36 补一组“③ 中作答 → 验收 → 请求修改”。

### D7 诚实与验证

**R58-D7-01｜次要**（ADR-185 写“被覆盖的阻断命中有可重放的证据，只有人在文件系统中手动删除时才可能缺失”。本轮找到三个反例，缺失时的处理只覆盖了手动删除一种）

- **问题**：
  1. **提前返回的路径不写重放包**：
     - `verify()` 只在槽位路径上调用 `writeReplayBundle`（`07` L454）。
     - 子模块项目（L390）、没有可运行 exec 标准（L410：只有 artifact 标准，或 exec 标准全部生态未支持）、S0 被拒（L419）都在此之前返回。
     - 这些路径仍经 `decide()`：有阻断命中时同样进入 `paused(sentinel_high)`（L1616，覆盖 `pass`、`no_machine_criteria`、`exec_not_run`）。
     - 覆盖时 `06` L928 要把“最近一次以阻断结束的验证”升为决定性并写保留 ref，但这次验证从来没有重放包。
     - 同理，只有 artifact 标准的 Goal 以 `verified` 进入 `in_review` 的那次验证，按 `07` L500 是“决定性验证、永久保留重放包”，伪代码却不写。
  2. **以阻断结束的缓存命中验证**：
     - 正式验证的 exec 标准全部或部分命中缓存时，重放包中这些标准的日志“指向原验证的日志”（`07` L454、L500）。
     - 排除二只保护原验证“从命中到本次验证结束”（`10` L442）；排除一只保护“这次验证的重放包与完整日志”。
     - 本次验证以阻断结束、Goal 停在 `paused(sentinel_high)` 期间，被引用的原验证（通常是机会式验证，非永久）可以被磁盘压力清理。覆盖后升级的决定性验证因此指向已删除的日志，与“原日志与原重放包随之升为永久保留”不符。
  3. **`paused(sentinel_high)` 的范围**：
     - 人在已暂停的 Goal 上再暂停时，`human` 成为 `pauseReason`，`sentinel_high` 进入 `alsoApplies`（`03` L78）。
     - 排除一（`10` L442）与 `16` L550 写的是“`paused(sentinel_high)` 的 Goal”。只按 `pauseReason` 判定的实现，会在人暂停期间清理这次验证的包。
- **为什么是次要**：覆盖与验收的判定不受影响，seal 时的完整重哈希验证照常永久保留；第 2、3 种需要磁盘压力。但 ADR-185 把保证写成了绝对的，三种情形下实现会分歧：写不写最小重放包、保护范围是否包括被引用的原验证、按主原因还是全部原因判定。
- **文档位置**：`03` L78；`06` L928、L1114；`07` L390、L410、L419、L454、L500、L1616；`10` L442；`13` L363；`16` L550。
- **期望的回答形态**：在 `07` §7.4.1 的保留行（唯一定义）中：
  - 写明每次**正式验证**在每个返回点都写一个重放包：至少含 `manifest.json`、artifact 检查、哨兵 Fact 与环境记录，没有 exec 日志时如实写“无 exec 结果”；或者写明这些路径的重放结论是什么。
  - 把排除一的保护范围定义为“该次验证及其 `manifest.json` 引用的全部原验证”。
  - 判定条件写成“`sentinel_high` 是 `pauseReason` 或在 `alsoApplies` 中”。
  - G46(bc)(2) 补“只有 artifact 标准”与“缓存命中后以阻断结束”两组。

  - **不扣分的观察**：
    1. **`anyQualified` 的计算顺序**：`07` L1621 先算 `label`，L1625 才判定延续，而 ⑨ 依赖延续的结果。判定本身无矛盾（延续只看 ⑨ 以外的条件），但延续回到 `accepted` 时存储的标签取 `verified` 还是 `verified_qualified` 取决于实现；`12` L248 的 `●*` 不受影响。建议把“⑨ 以外的条件”写成一个单独命名的谓词。
    2. **⑦ 与跨 pin 的覆盖延续**：`07` L1528、L1534 中覆盖可随内容延续到新 pin，但没有写新 pin 上是否产生 ⑦。ADR-185 之后这决定 `accepted` 还是 `in_review`。M1 中延续基本只发生在同一树上，主要影响 M2 的 rebase。
    3. **`08` L502 与 L350 的“或停止”**：`03` L80 的 `budget_hard_cap` 出口中没有“停止”；同一行又把“放弃”定为 `informative`。建议删去或改为“放弃”。`03` L82 的按钮名“按当前状态视为提交”与 `08`、`12`、`04` 的“送去验证”不一致。
    4. **死路**：`03` L60 把 `grant_s0_exec` 列在“验证通过后按 I2 判据回到 `accepted`”的触发中。S0 下 ③ 恒成立，这一转移永远不会发生；`07` L1647 的“验收延续照常适用”同理。建议注明。
    5. **延续判据的旧复述**：`08` L712、`10` L1110（M2 合并队列）、`04` L1380（M2）仍写“contentHash 不变、无新增 hunk、标准再次通过”，没有 ADR-185 的条件，也没有引用 `07` §7.10.3。建议改为引用，并按 §3.1 补登 (D)。
    6. **未标 M2 的残留**：`13` L44（§13.1 的冲突雷达）、`13` L283（启动序列中的“冲突雷达首轮”）、`03` L60 中 `accepted` → `verifying` 的“合并队列 rebase 后内容变化”都没有 M2 标记。(z′) 不覆盖这些表。
    7. **`tool.external` 与单向门**：`11` 第 1 条硬规则把“部署、外部 API 写入”列为单向门；同样的效果经 MCP 或扩展工具发生时，`tool.external` 不是单向门，可以授予 Goal 级授权、远程批准“仅这一次”、不需要双确认。授权以工具名为单位、需要人显式给出，这是可以辩护的取舍，但没有写明。建议在 T16 或 §11.3.4 写明；或者对显式 `destructiveHint: true` 的工具只提供“仅这一次”。
    8. **工具名授权的稳定性与撤销粒度**：
       - MCP 工具名在规范化后冲突时按注册顺序加哈希后缀（Pi `mcp/tools.ts:78-92`），服务器也可以在会话中改变工具列表，同一授权名在下一个 Run 中可能指向另一个工具；
       - Goal 页只能按类撤销（`04` L354），不能单独撤销一个工具的授权；
       - 授权后带相对路径参数的调用仍因 `opaque` 而 ask（`11` L220 (3)），“相对路径”在任意字符串参数中的判定没有定义。
    9. **单向门确认的摘要与动效**：
       - `11` L106、`16` L804、`12` L345/L684、`04` L786 仍只写“按住 1.5 s 或输入目标名”，没有提到动作类名的回退；`DecisionCard` 规格没有要求在卡片上显示动作类 id，而回退依赖它；
       - `12` L761 写“`prefers-reduced-motion: reduce` 时所有时长为 0”，应写明 1.5 s 的按住阈值与 5 s 发送倒计时是交互阈值，不是动效时长；
       - `OpeningQueue` 的 120 ms 渐隐（`12` L728）不是动效令牌。
    10. **Watch 的键**：`04` L405 的 `↩ 展开`、`O 完整日志` 没有在 `16` §16.3 登记 Watch 作用域（`T`、`P` 已补）。
    11. **内存数值**：
        - `13` L193 与 `16` L765 中 Tower 自身预留 0.6 GB，小于 §13.8.1 负载列之和 650 MB；
        - 独占 Host 在 60–120 MB 之间仍按规则保持独占，此时 10 个流式 Goal 会超过 `13` L37 的 900 MB（该档属 M2 验收）。
        - 都是假设值，E6 回填时一并对齐即可。
    12. **开场消费的触发列表**：`06` L855 只列“`in_review` 中的 `request_changes`”（未列 `accepted`），`16` L36 只列 `run` 与 `continue_agent`；“任何 Run 开始”是总规则，建议补全，与 R58-D6-01 一并处理。
    13. **学习闭环的里程碑残留**：`08` L697 仍写“记忆提议与学习挖掘从 M2 起才有”，`09` L25 已改为挖掘属 M3。`07` L1737 的 `propose_project_rule`（生成 §9.6 学习闭环提议）没有里程碑标记，`04`、`12` 也没有它的界面。
    14. **`08` §8.8 剩余的未定类出口**：`verify_env` 的放弃、`stalled{crashed}` 与 `stalled{engine_error}` 只能靠通用 `stalled` 行推出；`provider_unavailable` 在 `12` L441 是 `◇`，在 `16` L194 映射为 `stalled` 类。按相邻行可以推出，建议补齐。
    15. **变更类工具调用与内置工具**：`16` L122 的只读白名单不含 `tool_search` 与 codemode 容器本身。字面实现时，`submit` 之后调用 `tool_search` 会使提交作废。建议与 R58-D11-01 一并写明。
- **设计是否完成：主干已收敛。** 第 57 轮的全部条目与观察都已落地，ADR-185 的核心规则在各文档中一致。剩下 6 条次要条目分两类：
