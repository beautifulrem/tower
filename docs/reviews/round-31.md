### D4 领域模型与生命周期

**R31-D4-01｜次要**（M1 的“base 前进”Fact 没有登记 kind）

- **问题**：
  - ADR-156 把 M1 中 base 前进时的行为定为“记 Fact‘base 前进 N 个提交’，并在卡片上提示”。出处：`10` L948、L954；`14` G45(d) 的期望；`04` L229、L1325；`12` L660。
  - `10` L111 还规定，`baseTip` 与 `baseCommit` 不相等、又不是前进时（例如上游强制推送后 `baseCommit` 不再是祖先），“只记 Fact”。
  - 这两条 Fact 在 `02` L370–397 与 `16` L127 登记的 27 种 kind 中都找不到对应项。`base_diverged` 描述的是 `refs/tower-remote` 与 `refs/user/remotes` 之间分叉，不是 `baseTip` 与 `baseCommit` 之间的关系。`conflict_forecast` 属 M2 的雷达。
  - 两条 Fact 的 `data`（N、新值、旧值）也没有定义。
  - 卡片提示何时更新、何时消失也没有写。M1 中 `baseCommit` 永不改变，N 只会增长。
- **为什么重要**：
  - 这是 M1 中新的主路径，G45(d) 要测它。
  - Fact 的 kind 是封闭枚举，`06` 以它建表。实现者只能自造一个 kind，或者塞进别的 kind。这样一来，lint (s′) 的三方一致就绕开了。
- **文档位置**：`02` L370–397；`16` L127；`10` L111、L948、L954；`04` L229、L1325；`12` L660；`14` L132。
- **期望的回答形态**：
  - 登记一个 kind，例如 `base_advanced{from, to, count}`，以及“不是前进的变化”的形状。后者可以并入同一 kind，加一个 `relation: "ahead" | "not_descendant"`。
  - `02`、`16` 同步，数量 27 → 28。
  - 写明提示随最新的一条 Fact 刷新，`integrated` 或 `archived` 后不再显示。

### D11 安全与自主度

**R31-D11-01｜次要｜M2**（pre-push 的版本前提与事实不符，退化规则绕过用户的闸门；失败去向不完整）

- **问题**：
  1. **版本前提是错的。**
     - `10` L91、L1030，`15` L1315，`16` L474，`04` L556 与 `12` L660 都写“`--to-stdin` 需要 git ≥ 2.42”。
     - 上游 `v2.40.0` 的 `builtin/hook.c` 已有 `--to-stdin` 与 `--ignore-missing`，而 Tower 的最低版本就是 2.40（`06` L1116，`15` L661）。
     - 因此“低于 2.42”的分支、卡片文案 `◇ 当前 git 版本无法在推送前运行 pre-push 钩子`，以及 G44(e) 第六组“在 git 2.41 上不运行钩子”，都是针对一个不存在的情形。第六组按文档实现后会失败：2.41 上钩子照常运行。
  2. **退化规则的方向。**
     - 即使将来出现确实不支持的环境，现行规则也是“不运行钩子、照常推送，卡片说明”。
     - 用户在项目设置中启用了“运行用户钩子”，常见用途是推送前的密钥扫描。“照常推送”意味着这道闸门被绕过，说明出现在推送之后。
     - 这类后果是“用户设置的安全闸门在 Tower 代理推送时失效”，正是补记 3 想避免的。
  3. **失败去向不完整。**
     - 卡片 `◆ 推送被 pre-push 钩子拒绝` 用的是 `◆`。按 `12` L325，`◆` 表示有需要人决定的 Needs-You 条目，但 `16` L187 的 18 种 Needs-You kind 中没有对应项，去重键与标注也没有定义。
     - “推送并开 PR”经合并队列执行（`MergeQueueEntry.mode = "push_pr"`，`10` L1002–1004）。钩子失败后，条目处于哪个 `state`，是否占住该 base 的 FIFO（并发度 1），都没有写。
     - R30 指出的一般推送失败（网络、认证）在 Q6（`10` L1018）中仍然只有 CAS 失败一种处理。
  4. **标准输入行中“远端当前提交”的来源。**
     - `10` L89 要求给出 `<远端当前提交或全零>`，同时强调这条命令“不需要网络”（L88）。
     - 但没有写这个值取自哪里：上一次推送记录的 `lastPushedSha`、镜像中的 `refs/tower-remote`，还是一律全零。
     - 钩子按 `<远端提交>..<本地提交>` 确定扫描范围。来源不同，扫描范围不同。全零会扫描整个历史，偏保守；一个陈旧的值可能让范围漏掉提交。
- **为什么重要**：
  - 第 1 项是一个可证伪的事实错误，它导出了一条错误的用例与一段不会触发的文案。
  - 第 2 项的方向与安全原则“自动化应在不确定时收缩”相反。
  - 第 3、4 项让实现者不知道队列与 Goal 停在哪里，也不知道钩子收到的范围是否正确。
  - 都属于 M2，不影响 M1 排期。
- **文档位置**：`10` L88–96、L1002–1004、L1018、L1030；`15` L1315；`16` L187、L474；`04` L542–556；`12` L325、L660；`14` G44(e)（L131）；`06` L1116；`15` L661。
- **期望的回答形态**：
  - 删去“需要 git ≥ 2.42”与低版本分支，写明“最低版本 2.40 已支持 `--to-stdin`”。删去 G44(e) 第六组与相应文案。
  - 如果仍要保留一条防御性退化规则（例如 `git hook run` 返回“未知选项”），改为：不推送，卡片提供“不运行钩子直接推送（需确认）/ 只保留分支”。
  - 失败去向：
    - 登记一个 Needs-You kind，或者明确并入现有 kind（例如 `conflict` 之外新增 `push_failed`），写明去重键与标注；
    - 队列条目进入 `needs_human`，并写明它在等待期间是否让出 FIFO；
    - 把网络与认证失败也纳入同一出口：重试推送 / 只保留分支。
  - 写明标准输入中远端提交的唯一来源。推荐：远端分支存在且 Tower 有 `lastPushedSha` 时用它，否则用全零。
  - G44(e) 增加一组：重新 seal 后的第二次推送，钩子收到的远端提交等于上次推送的提交。

### D13 隔离、git 与并发

**R31-D13-01｜次要**（“完整写法”的序列化规则不完整：空值重置、单值键的先后、`include.path` 的回写）

- **问题**：
  - ADR-156 补记规定，URL 或替换目标带密码或 token 时走完整写法：
    - 写出 `git -C <userCheckout> config --list --show-scope` 的有效配置，排除仓库级的非认证键，多值键保持顺序；
    - store helper “写在最前面”，排在全部用户 helper 之前（`10` L70–71、L80，`11` L339，`16` L474，`15` L1317）。
  - 全局或系统配置中有带 userinfo 的 `insteadOf` 时，也走这条路径（`10` L72）。
  - 按字面实现会出现三个问题：
  1. **空值重置清掉 store helper。**
     - git 按配置文件中的先后处理 `credential.helper` 与 `credential.<url>.helper`，遇到空值就清空此前积累的列表（实测）。
     - Git Credential Manager 的标准安装会在全局配置中先写一个空值、再写自己的 helper。
     - 于是 Tower 排在最前的 store helper 被这条空值清掉，URL 中的 token 用不上。fetch 与 LFS 获取要么失败，要么改用 GCM 为同一主机保存的另一份凭据。
     - 后者正是补记想排除的情形，也就是 G45(e) 期望的反面。
     - 这意味着 R30-D13-01 修复的退化，对“URL 带 token 并装有 GCM”的用户重新出现。
  2. **单值键的先后。**
     - `credential.<…>.username` 是单值键，后写者胜（实测）。
     - 如果 Tower 把用户名写在最前面的同一段，用户配置中的 `credential.username` 或 `credential.https://<host>.username` 会覆盖它，store 条目按用户名不再匹配。
     - 用户自己直接 `git fetch` 时，URL 中的用户名优先于配置，所以两者行为不一致。
     - 文档只规定了 store helper 的位置，没有规定用户名写在哪里。
  3. **`include.path` 的回写。**
     - `--list` 的输出含 `include.path` 与 `includeIf.<条件>.path` 这两类键本身，同时含被包含文件展开后的条目（实测）。
     - 原样写回时，读取临时文件的 git 会再次包含原文件。被包含文件中带凭据的 `insteadOf` 以原样重新生效（实测），与 Tower 写入的去凭据版本并存。
     - 把令牌放在单独的 `include` 文件里，恰恰是让 dotfiles 仓库不含密钥的常见做法。
     - 这类后果是“完整写法本要关闭的那一类暴露（`11` T33：带凭据的 URL 出现在传输辅助进程的参数中）在这种配置下重新出现”。
- **为什么重要**：
  - 第 1 项是常见配置下的功能退化，会被 G45(a)(e) 测出，但测试环境通常没有装 GCM。结局有定义（`prepare_failed`，或本地已知值加 Fact），所以定为次要。
  - 第 3 项让文档宣称已关闭的 T33 残余，在一类合理的用户配置下重新打开。只需一条规则就能关闭，所以同样定为次要。
  - 三项都是实现者照文档字面实现时必然遇到的问题。
- **文档位置**：`10` L59–82；`11` L339–340、L571；`16` L474；`15` L1317；`06` L239；`14` G44(d)、G45(a)(e)（L131–132）。
- **期望的回答形态**：
  - 完整写法的序列化规则写成一条：
    - **(a) helper**：对适用于该主机的 helper 先按用户配置求出生效列表，即应用空值重置之后的列表。写出时第一项为 Tower 的 store helper，其后是生效列表，不再写入任何空值。
      - 这不改变用户实际生效的 helper 集合与顺序，与“从不清除用户的 helper”的本意相同。文档应写明这一点，以免被读成“清除”。
    - **(b) 用户名**：Tower 写的 `credential.<scheme>://<host>.username` 放在文件**末尾**，以便覆盖用户的同名或更宽的单值键，与 URL 中用户名优先的 git 语义一致。
    - **(c) include**：不写出 `include.*` 与 `includeIf.*` 键，因为 `--list` 已经展开了被包含的内容。
  - include 写法的差集同样不写出这两类键。
  - G45 增加三组：
    - 全局配置为 GCM 式的“空值 + helper”；
    - 全局配置含 `credential.username = other`；
    - 带凭据的 `insteadOf` 写在被 `include` 的文件中。
  - 期望三组都使用 URL 中的凭据，取样中看不到 token。

**R31-D13-02｜次要**（M1 中远端引用 base 的前进与 `integrated` 观测没有触发点；分叉时 `baseTip` 可能取到陈旧值）

- **问题**：
  1. **没有触发点。**
     - `02` L209 的 `baseRef` 示例是 `origin/main`。G44(b) 与 G45(c) 都以远端引用 base 为 M1 用例。
     - M1 中 base 前进的检测“只在本地 base 的 `fs.watch` 与镜像从用户检出 fetch 时”进行（`10` L939）。`fs.watch` 只监视 `<commonDir>/refs/heads/<base>` 与 `packed-refs`，即本地分支 base。
     - 镜像从用户检出 fetch 只在“需要新 base 时”（`10` L22），实际上就是有 Goal 进入准备时。
     - `integrated` 的观测同样是“在每次镜像 fetch 时”（`10` L1033）。
     - 因此 base 为 `origin/main` 的 Goal 遇到 M1 的常态流程时，没有任何事件触发观测。这个流程是：用户推送分支，在托管平台上合并，再在主检出中 `git fetch` 或 `git pull`。观测要等到同一 Project 中下一个 Goal 进入准备。在此之前：
       - `◇ base 已前进` 不会出现，G45(d) 若用远端引用 base 会失败；
       - 已合入的 Goal 停在 `accepted`，14 天后只得到归档提示。
  2. **分叉时的陈旧值。**
     - `baseTip` 在分叉时取 `refs/tower-remote`，理由是它“代表远端的当前状态”（`10` L103，`15` L1314）。
     - 但 M1 不轮询远端，`refs/tower-remote` 只在 Goal 准备时更新。`refs/user/remotes` 却随用户每次 fetch 更新。
     - 设想准备之后，上游被强制推送，比如以队友经常 rebase 的功能分支为 base；用户随后 fetch 了新值。此时两者分叉，`baseTip` 取的是**更旧**的 Tower 值。
     - 结果：
       - 卡片提示“远端与本地的 main 已分叉，使用远端版本”，这句话不真实；
       - `integrated` 判定以旧值为准，用户在新上游上合入的 seal 观测不到。
     - `10` L261 写“上面的 fetch 失败时只剩 `refs/user/remotes/<r>/<b>`”，与 `baseTip`“只要存在就参与比较”的定义也不一致：上一次准备留下的 `refs/tower-remote` 仍然存在。
  3. **M2 用例。** R30 要求的“LFS 补齐进行中人点‘继续’，补齐结束后不写回”没有加入 G44(a)（见 §3）。
- **为什么重要**：
  - 第 1 项让 M1 闭环的最后一步，即观测到合入后进入 `integrated`，对远端引用 base 不会自动发生。实现者照文档实现必然如此。
  - 第 2 项让一条 `◇` Fact 提示说出不真实的话，违背诚实语法。
  - 两者的结局都有定义且安全：Goal 停在 `accepted`，人可以选“验收但不合并”，所以定为次要。
- **文档位置**：`02` L209；`10` L22、L100–111、L261、L939、L1033；`15` L1314；`16` L475；`04` L1325；`14` G44(a)(b)、G45(c)(d)（L131–132）。
- **期望的回答形态**：
  - **M1 触发**：远端引用 base 同样以 `fs.watch` 监视 `<commonDir>/refs/remotes/<r>/<b>` 与 `packed-refs`；变化时，镜像从用户检出 fetch（本地，无网络），再执行前进检测与 `integrated` 观测。`10` L939 与 L1033 同步。
  - **分叉**：
    - 为 `refs/tower-remote` 记录获取时间；
    - 分叉时取较晚更新的一方。用户一方的时间可取镜像 fetch 时观察到该值变化的时间；
    - 或者在 M1 中检测到分叉时补做一次远端 fetch，再按规则取值。
    - 二者取一，提示文字写明取的是哪一方、何时获取。
  - **`10` L261** 改为“fetch 失败时按 `baseTip` 取值（可能是上一次获取的值）”，或者明确规定失败时忽略 `refs/tower-remote`。二者取一，与定义一致。
  - **用例**：
    - G45 增加：base 为 `origin/main`，用户在主检出中 `git fetch` 得到包含 seal 的新提交，期望 Goal 进入 `integrated`；
    - G45 增加：准备之后上游被强制推送、用户 fetch，期望取用户的新值，或补做 fetch 后取远端值，提示如实；
    - G44(a) 增加 R30 要求的并发一组（M2）。
