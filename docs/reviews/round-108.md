## 1. 总评

**第 107 轮的 5 条条目都按所问关闭**（核对见 §3）。回应没有逐条加守卫，而是删除两个机制，取向成立：
- 短时探测 Host 删除之后，(a) 分组与上限、(b) 自身失败、(c) `!` 命令随新进程重新执行三支确实随之消失。扩展注册的 provider 一律不自动探测，(d) 的误报也不再出现。
- 按卷名的判别由一条 “Project 不可达” 规则取代，同名卷与符号链接不再落回丢失两行，R107-D13-02 列出的七处缺口都落在这条规则的 ③ 中。
- 第 107 轮 §5 的 13 条观察全部落地，其中观察 12 随短时 Host 删除而不再需要。

**新规则带出的分支**。“Project 不可达” 是一个新的全局判定，它的触发面与出口都比原来那一行大，带出五个分支：
- **R108-D4-01**：启动时 Project 已不可达、而 Goal 带的是真正因退出而得的 `app_quit`。§6.1.4 第 5 项的解除是照常执行还是推迟，没有写；④ 只移除 `outcome_reason` 为 `project_unreachable` 的那一种。
- **R108-D6-01**：所有检查共用一个 `worker_thread`。一个挂起的 `stat` 会使其后其他路径的检查全部超时，于是所有 Project 都被判为不可达；`~/.tower` 所在卷读不出剩余空间时也没有规则。
- **R108-D13-01**：附着点属于每个 Goal 的 binding，一个 Project 可以有多个附着点与多个 `<wtRoot>`。“附着的用户检出” 指哪些 binding、是否包括终态 Goal，没有写。
- **R108-D13-02**：卷在写回、验证或重建的文件操作中途消失时，操作先失败，可达性判定后到。失败出口照常执行，于是 R107-D13-01 要避免的 “此后不可恢复” 告知与 `human_checkout` 清除在这个窗口里仍会出现。
- **R108-D13-03**：Project 永久不可达、而仓库只在本地且已丢失时，没有能结束这些 Goal 的出口——放弃与清除都返回 `E_STATE`。被豁免的 “绑定处理” 在命令目录中也没有对应的命令。

**扫描发现的其他缺口**：
- **R108-D5-01**：每个 Run 的校验对 `retry.provider.timeoutMs` 只要求 “有限的非负数”。0 与非整数在厂商 SDK 中都变成含 `timeout` 的错误，正是这项校验要关掉的重试循环；F4b 的定义与卡片原因也没有收入这一触发。
- **R108-D12-01**：隐私清除续做在 `roots` 涉及不可达的 Project 时 “整条推迟”。这也推迟了 `~/.tower` 中本可删除的副本，而 `project`、`all` 两档写 `roots` 的同一事务已删除 Project 行，可达性无从判定。
- **R108-D7-01**：退出确认框无条件写 “下次启动自动恢复”，两处文字也不同，与 ADR-232 的规则不一致。

**对本轮重点问题的回答**：

- **探测范围：成立。** 专用模式下暂停后 Host 存活 5 分钟，按退避恰为第 60 s 与第 180 s 两次探测（下一次在第 420 s）。其余情形由人重试，如实登记。各处摘要只写专用模式下的说法，见观察 4。
- **五项设置的校验：未设置时成立，0 与非整数有缺口。**
  - “设置时” 豁免了未设置的值。Pi 的默认值：`httpIdleTimeoutMs` 300 000，`websocketConnectTimeoutMs` 未设置，`retry.provider.timeoutMs` 未设置（取空闲超时），`retry.provider.maxRetries` 未设置（按 0），`retry.maxRetries` 3。
  - `httpIdleTimeoutMs`、`websocketConnectTimeoutMs` 为 0 时在 Pi 中表示不限时，正文已写。
  - `retry.provider.timeoutMs` 为 0 或非整数的问题见 R108-D5-01。
- **“Project 不可达” 的几种情形**：
  - 人的检出都在 `<wtRoot>` 之下，成立。
  - 多个附着点见 R108-D13-01。
  - 网络卷：`stat` 慢由 13 L130 移出了事件循环，但单线程排队见 R108-D6-01；单次超过 5 s 即中止全部 Run、没有确认采样，没有登记，见观察 8。
  - 睡眠与唤醒：唤醒后没有可达性的宽限，网络卷重连较慢时会中止 Run，`resumeOnLaunch` 打开时约 30 s 内自动继续，不丢数据，见观察 8。
  - 启动顺序见 R108-D4-01 与观察 13。
- **缓存预热与凭据窗口：默认模式成立。** 默认的 `streaming` 模式在 settle 时停止预热，窗口确实止于下一次 `turn_start`。`idle` 模式在 settle 之后继续，至多 30 min 或到会话 `dispose`，这时 “下一次 `turn_start` 之前” 与 “只在对账差值中出现” 都写得过宽，见观察 1。机密的去向不扩大：扩展本就在密钥的信任边界之内。
- **偏离 “用户检出被删除时运行中的 Goal 也停下”：接受。** Run 中止而不 drain，卫星完好，下一次 Run 从卫星原样继续，不丢工作；换来一条规则的简单。
- **偏离 “删除自动查找检出”：接受机制本身，但出口要补。**
  - 依赖它的只有情形 C；`10` L38、L42 与 `04` L1522 都已改为由人迁移。
  - 被移动的仓库现在必须由人迁移，而迁移在命令目录中没有命令（R108-D13-03）。
  - 仓库连同同级的 `.tower-wt.noindex` 一起移动、迁移后走情形 F 的重建，这是 ADR-235 之前就有的路径，不是新问题。

**ADR-235 的其余写法成立**（§3.3）：

  - `06` L139 ③ 写 “本表其他各行对它的 Goal 都不执行”。`paused` 一行（`06` L144）自身 “什么都不执行”，并写明 `app_quit` 由 §6.1.4 的 `resumeOnLaunch` 显式解除——§6.1.4 第 5 项不是本表的一行。所以这次解除是照常执行，还是随本表各行推迟，有两种读法。
  - **读法一（照常解除）**：继续目标为 `run` 的 Goal 进入队列，在检查 i 处等待，可达后准入，结果正确。但继续目标为 `settle`、`verify` 的 Goal 离开 `paused` 之后 “同样等待”——在哪个状态、以什么卡片等待，没有写；`settle` 序列本属于 `running` 中的 settling 阶段，没有 Run 时无处可放。
  - **读法二（推迟）**：④ 可达后 “按本表的启动顺序执行各行”，并 “移除最后一个 Run 的 `outcome_reason` 为 `project_unreachable` 的 `app_quit`”。这两句都不覆盖 `outcome_reason` 为 `app_quit` 的 Goal，于是它在 `resumeOnLaunch` 打开时仍停在 `paused(app_quit)`，直到下一次重启。对照：F8 把 “会写数据库的中间状态检查（含第 5 项）” 明确推迟到解除时执行。
  - ③ 的例外 “启动时未结束的 Run 按三行写出暂停” 写出的 `app_quit`（`outcome_reason` 不是 `project_unreachable`）有同一个问题。
- **为什么是次要**：不丢工作，不涉及机密；最坏是 Goal 停到下一次重启或人按 “继续”。但这是 ADR-235 最常见的使用路径，两种读法下状态与卡片都不同，实现会分叉。
- **后果的类别**：
  - 读法二下，重新插上盘之后，退出前在运行的 Goal 不自动继续，卡片仍写 `已暂停 · 应用退出 · 启动后自动恢复`；
  - 读法一下，继续目标为 `settle`、`verify` 的 Goal 处于没有定义的等待状态。
- **文档位置**：`06` L101（第 5 项）、L139 ③④、L144、L147–L149、L1201（F8 “推迟的中间状态检查”）；`12` L416、L434。
- **期望的回答形态**：在 `06` L139 ④ 加一句，写明：
  - 启动时判为不可达的 Project，其 Goal 的 §6.1.4 第 5 项与本表各行一样推迟，可达时执行（同 F8）；
  - ④ 移除的是 “`outcome_reason` 为 `project_unreachable` 的 `app_quit`，以及因不可达而推迟的第 5 项”；
  - 或者反过来写明第 5 项照常执行，并给出不开 Run 的继续目标的等待状态（如留在 `paused`、继续目标保留，可达后由 ④ 执行）。

### D5 Agent 架构与 Pi 集成

**R108-D5-01｜次要**（每个 Run 的校验对 `retry.provider.timeoutMs` 只要求 “有限的非负数”：0 与非整数在厂商 SDK 中都变成含 `timeout` 的错误，正是这项校验要关掉的循环；F4b 的定义与卡片原因没有收入这一触发）

- **问题**：
  - **(a) 取值范围**：`05` L474 要求三项 Pi 不解析的设置 “设置时为有限的非负数、次数为整数”。对 `retry.provider.timeoutMs`：
    - Pi 以 `??` 取值（`sdk.ts:350`），0 被保留，原样成为厂商 SDK 的 `timeout`（`anthropic-messages.ts:641`；OpenAI 类同）。
    - 同族厂商 SDK 的 `validatePositiveInteger` 接受 0、拒绝非整数并抛出 `timeout must be an integer`（本机 0.91.1 `internal/utils/values.js:48-56`）；0 时 `setTimeout(abort, 0)` 立即中止，报 “Request timed out”（`client.js:336`）。
    - 两种错误文本都命中 Pi 的可重试模式 `timed? out`、`timeout`（`retry.ts:72-73`）。所以结果正是 `05` L474 所说 “不做这一校验时” 的循环：重试耗尽、落入 F6、探测（只查连接与鉴权）通过、解除、再失败。打包模式下只要同组 Host 空闲就一直如此，专用模式下至多两轮。
    - 对照：Pi 对经 getter 读取的两项向下取整（`http-dispatcher.ts:34`），对这一项不做处理。
    - Codex 类 provider 把 0 当作不限时，所以同一个取值在不同 provider 下含义不同。
  - **(b) F4b 的定义**：ADR-234 起 Host 启动时 `httpIdleTimeoutMs` 无效按 F4b 失败，ADR-235 起每个 Run 的校验失败也按 F4b。但 F4b 的触发列表（`06` L1197）、`03` §3.2.1 `prepare_failed`、`16` §16.1.1 `prepare_failed`（L29）都没有收入这一触发；`04` §4.8.11（L980）与 `12` L435 的 `启动失败：<原因>` 没有这一原因的写法。F4b 条目的 “重试” 在你改设置之前每次都以同样的方式失败。
- **为什么是次要**：失败可见，不计费（请求在发出前或立即中止），不丢数据，不涉及机密。但校验的目的写明是关掉这个循环，而唯一定义的取值范围放过了两类取值；卡片原因不定义，实现会各写各的。
- **后果的类别**：
  - 设置文件中该项写为 0 或带小数时，Goal 在 `provider_unavailable` 与运行之间循环，卡片写 “模型服务不可用”，而原因是本机设置；
  - 校验失败时，卡片不指出是哪一项设置，人按 “重试” 得到同样的失败。
- **文档位置**：`05` L474、L1450（D63）、L1506（C43）；`06` L1197（F4b）；`03` §3.2.1 `prepare_failed`；`16` L29；`04` L980；`12` L435。
- **期望的回答形态**：
  - `05` L474 改为：`retry.provider.timeoutMs` 设置时须为正整数（0 与非整数判为无效）；D63 补 “在所钉的厂商 SDK 版本上确认 `timeout` 的校验”；C43 补 0 一组；
  - F4b 的触发列表加一项 “Pi 设置无效（`05` §5.3.6 代理一行）”；
  - 卡片原因写 `启动失败：Pi 设置 <名字> 无效`，重试按钮旁提示先改设置。

### D6 系统架构与可靠性

**R108-D6-01｜次要**（可达性检查共用一个 `worker_thread`：一个挂起的 `stat` 使其后其他路径的检查全部超时，所有 Project 被判为不可达；`~/.tower` 所在卷读不出剩余空间时没有规则）

- **问题**：
  - `13` L130：必需路径的 `stat` 与 F8 复查的剩余空间读取 “都在一个专用的 `worker_thread` 中执行”，“每次以 5 s 为限，到时按不可访问计；同一路径上一次检查未返回时不再发起新的”。
    - 写明 “不占 libuv 线程池”，即线程内是同步调用。硬挂载的 SMB/NFS 上一次 `stat` 可以挂起很久乃至不返回，这个线程随之被占住。
    - 去重只按路径。其他 Project 的检查排在它后面：按发起时计时，它们 5 s 后全部按不可访问计；按开始执行时计时，它们永远不执行。
    - 线程被占住时怎样处理（放弃并另起一个），没有写。被系统调用挂住的线程不能被 `terminate()` 打断。
  - **`~/.tower` 所在卷**：F8 复查集合含 `~/.tower` 所在卷（`06` L1201），它的读取同样排在这个线程中。ADR-235 删去了 “求不出的卷按不足计”，而 “读不出剩余空间的卷所在的 Project 判为不可达” 只覆盖 Project 的卷。`~/.tower` 所在卷读不出时，F8 是保持只读还是视为足够，没有写。
  - **其他同步调用**：`10` L1254 的 `turn_end` 检查点前 `existsSync(path)` 与 10 分钟定期检查不经这个线程，在可达性判定通过之后、卷随即挂起时仍会占住 Supervisor 的事件循环。
- **为什么是次要**：不删除、不改名任何目录，Run 的中止不丢工作，重启 Tower 可以恢复；不涉及机密。但照字面实现时，一个挂起的网络挂载会使整台机器上所有 Project 被判为不可达、全部 Run 中止，卡片对完好的本地路径写 `Project 不可达`，直到挂载恢复或重启——与该规则 “按路径判定” 的本意相反。实现会在 “每路径一个线程”“替换挂起的线程”“单线程排队” 之间分叉。
- **后果的类别**：
  - 一个挂起的网络卷使所有 Project 停下，且可能一直停到重启；
  - 这期间 F8 若在只读状态，可能无法解除。
- **文档位置**：`13` L130；`06` L139（“5 s 内没有结果”）、L1201（F8 复查集合）；`10` L1254–L1256。
- **期望的回答形态**：在 `13` L130 加一句：
  - 5 s 从该次调用开始执行时计；调用超过 5 s 未返回时放弃该线程（不再向它派发），另起一个线程继续其他路径的检查，被放弃的线程数有上限（如每个卷一个）；
  - `~/.tower` 所在卷读不出剩余空间时按不足计（保持只读），或写明按足够计；
  - `10` §10.16.1 的存在性检查同样经这个线程，或登记它们是同步的。

### D7 诚实与验证

**R108-D7-01｜次要**（退出确认框无条件承诺 “下次启动自动恢复”；两处文字也不同）

- **问题**：
  - `06` L84：确认框 “3 个 Goal 正在运行或验证。退出会暂停它们，下次启动时自动继续。”；`04` L1423：确认 “3 个目标将暂停，下次启动自动恢复”，随后 “下次启动：自动恢复”。两处文字不同，都没有条件。
  - ADR-232 定下的规则是 “`自动恢复` 只在该 Goal 将随之自动继续时写”。卡片（`12` L434）与 `04` L1517 都按 `resumeOnLaunch` 写了条件，`04` L1517 还写明 “设置 `resumeOnLaunch` 关闭时不自动恢复”。确认框是同一事实的另一处表述，没有跟上。
  - `04` L1423 已为 “正在暂停” 的目标另起一行写 “不会自动恢复”，说明确认框本就按 Goal 区分，只差 `resumeOnLaunch` 一项。
- **为什么是次要**：只在退出时出现一次，重启后卡片如实；不丢数据。但这是对行为的承诺，与已定的规则相反，两处文字也各不相同，实现会分叉。
- **后果的类别**：关闭了 `resumeOnLaunch` 的人在退出时被告知目标会自动继续，重启后发现它们仍暂停。
- **文档位置**：`06` L84；`04` L1423、L1517；`12` L434；ADR-232。
- **期望的回答形态**：确认框文字只在一处定义（`06` §6.1.4 或 `04` F12），另一处引用；`resumeOnLaunch` 关闭时写 “下次启动后仍为暂停，需要你点继续”。

### D12 记忆与学习（隐私）

**R108-D12-01｜次要**（清除续做在 `roots` 涉及不可达的 Project 时 “整条推迟”：连同 `~/.tower` 中本可删除的副本一起推迟；`project`、`all` 两档的 Project 行已删除，可达性无从判定）

- **问题**：
  - `06` L143：“`roots` 涉及不可达的 Project 时整条推迟到可达，不记完成”。
  - **判定的对象已不存在**：`roots` 只是 `{projectId, wtRoot}` 的列表，与删除绑定、Project 行在同一事务中写入（`06` L951）。“Project 不可达” 按附着检出与 `<wtRoot>` 判定（L139），而 `project`、`all` 两档续做时这个 Project 与它的附着检出已不在数据库中，只剩 `roots[].wtRoot`。实现会在 “只 `stat` `wtRoot`”“当作不可达”“当作可达” 之间分叉。清除从不写用户仓库（`09` §9.12.4），附着检出与清除本无关系。
  - **推迟的范围过大**：“整条” 也推迟了 `~/.tower` 中与该卷无关的部分——`~/.tower/goals/<goalId>/` 下的 Pi 会话、证据、重放包，`all` 档最后还要删除数据库本身。外接盘不再使用时，这些副本一直保留；而 “续做期间该 Goal 已按事件不显示”，界面上看不出清除没有完成。`09` §9.12.4 的 “清除之后仍可能存在的副本” 没有这一项。
- **为什么是次要**：要 “清除中途崩溃” 与 “重启时该卷不可达” 两件事同时发生；副本只在你自己的机器上；可达后会续做完成。但这是隐私承诺的一处例外，而推迟的部分本可立即删除。
- **后果的类别**：你清除了一个 Goal 或全部数据，Tower 在之后崩溃，而外接盘不再插上；该 Goal 的对话记录与证据留在 `~/.tower` 中，界面上已不显示。
- **文档位置**：`06` L139、L143、L951；`09` §9.12.4（L555 起）。
- **期望的回答形态**：在 `06` L143 改一句：
  - 续做时只按 `roots[].wtRoot` 的可访问性判定（同一 `worker_thread`、5 s）；
  - 不可访问的根上的删除推迟，其余部分——`~/.tower` 中的副本、可访问的根——立即续做；全部完成才追加 `filesDone`；
  - `all` 档的数据库最后删除；
  - 推迟的部分在清除结果与 `09` §9.12.4 的 “仍可能存在的副本” 中列出。

### D13 隔离、git 与并发

**R108-D13-01｜次要**（附着点属于每个 Goal 的 binding，一个 Project 可以有多个附着点与多个 `<wtRoot>`：必需路径指哪些 binding、是否包括终态 Goal，没有写）

- **问题**：
  - `06` L139 的必需路径是 “附着的用户检出（`attach.checkoutPath`）……以及该 Project 有卫星……时的 `<wtRoot>`”，用的是单数，判定的结果是 “整个 Project”。
  - 但附着点在 Goal 创建时 “为每个 binding 选定并记录”（`10` L39，`02` L234）；同一 Project 在本机可以有多个检出——同一仓库的 linked worktree 或独立的克隆（`10` L36，`02` L87）；`<wtRoot>` 默认取附着检出的父目录（`10` L40、L239，`16` L290）。所以一个 Project 可以同时有几个附着检出、几个 `<wtRoot>`。另外 `10` L522 又写位置 “添加项目时计算一次” 并记入 Project 设置，两处不一致（ADR-235 之前已有）。
  - 没有写的有三点：
    - 哪些 binding 的附着检出算必需路径——只算非终态 Goal 的，还是包括已归档、已放弃的。后一种读法下，删掉一个旧克隆就使 Project 永久不可达。
    - 一个 Goal 的附着检出不可达时，是整个 Project 停下（字面），还是只停用该检出的 Goal。
    - 多个 `<wtRoot>` 时按哪一个判定。
  - 字面读法的后果：`git worktree remove` 掉某个 Goal 当初发起时所在的 linked worktree，同一 Project 中附着在其他完好检出上的 Goal 的 Run 也全部中止、命令全部返回 `E_STATE`。ADR-235 只登记了 “用户检出被删除而卫星完好时运行中的 Goal 同样中止”，没有登记这种跨检出的连带。
- **为什么是次要**：不删除目录，不丢工作，不涉及机密。但必需路径集合是这条规则的输入，集合不定，实现在 “按 Project”“按 binding”“含不含终态 Goal” 之间分叉，其中一种会使 Project 永久停下。
- **后果的类别**：
  - 删掉一个次要的检出或旧克隆，整个 Project 的 Goal 停下；
  - 照 “包括终态 Goal” 实现时，Project 无法恢复，只能迁移。
- **文档位置**：`06` L139；`10` L36、L39–L42、L239、L522；`02` L87、L234；`16` L290。
- **期望的回答形态**：在 `06` L139 的判定一栏写明：
  - 必需路径 = 该 Project 中**非终态** Goal 的各 binding 的 `attach.checkoutPath`，以及这些 binding 实际采用的 `<wtRoot>`（有卫星、人工编辑检出或检验目录记录时）；
  - 判定的范围：仍按整个 Project（登记跨检出的连带为取舍），或按 binding（只停用不可达附着点或 `<wtRoot>` 上的 Goal）；
  - `10` L522 与 L40 的 `<wtRoot>` 取法统一。

**R108-D13-02｜次要**（卷在写回、验证或重建的文件操作中途消失时，操作先失败、可达性判定后到：失败出口照常执行，没有 “先判可达” 的规则）

- **问题**：
  - `06` L139 ②：Project 被判为不可达时，进行中的写回、重建、接管物化停止、“不执行各自的失败出口”，验证 “照应用退出取消”。判定由 “文件系统事件、操作前检查、`10` §10.16.1 的检测” 触发；30 s 的计时只复查已判为不可达的 Project。
  - 卷在操作中途消失时，操作本身先失败（`ENOENT`、`EIO`）：
    - 写回的文件操作失败，按 `06` §6.4.3 `inspect.bring_back` 行 “写回在本进程中失败” 执行 ①②③——③ 清除 `human_checkout`、Needs-You 写 “你的改动未能保留在目录中，此后不可恢复”；
    - 验证命令在 `<wtRoot>/_verify/`（`10` L249）上失败，记为标准失败（计入返工次数）或 `verify_env_error`，写出 `verify.result` 与 Fact；
    - 卫星重建失败，升级为 `satellite_missing` 暂停原因并生成 Needs-You，之后 “重启不再自动重建”。
  - 这些结果是否先经可达性判定，没有写；只有 “操作前检查”，没有 “失败后检查”。对照：磁盘满时同一竞争如实登记（`07` L498，ADR-234）；Project 不可达既没有守卫，也没有登记。
  - 而 G35e (q)（`14` L120）“Run 中卸载” 一组断言 “没有 `stalled{write_back_failed}`、没有‘此后不可恢复’的告知、人工编辑检出未被清除”“`verifying` 的 Goal 没有 `verify.result` 与 Fact”。没有机制保证这些断言，测试结果取决于时序。
- **为什么是次要**：目录都在未挂载的卷上，Tower 碰不到，不会真的删除；不涉及机密。但这正是 R107-D13-01 要避免的告知与清除，只是缩到一个窗口里；实现会在 “失败即走出口” 与 “先判可达” 之间分叉，测试不稳定。
- **后果的类别**：
  - 写回中拔盘，人被告知改动不可恢复，交还路径被清除，而改动完好地在盘上；
  - 验证中拔盘，留下一次失败或环境错误，消耗返工次数；
  - 重建中拔盘，Goal 落入只能人工处理的 `satellite_missing`。
- **文档位置**：`06` L139 ②、L140（重建失败）、L922（写回失败出口）；`07` L498；`10` L249、L1254–L1255；`14` L120。
- **期望的回答形态**：在 `06` L139 ② 加一句：写回、重建、接管物化的文件操作失败，或验证命令以非零退出、而该 Project 有必需路径时，先经同一 `worker_thread` 判定可达性；不可达即按本行处理（不执行失败出口、不记结论），可达才照常。或者在 `07` L498 旁如实登记这一竞争，并相应放宽 G35e (q) 的断言。

**R108-D13-03｜次要**（Project 永久不可达、而仓库只在本地且已丢失时没有出口：放弃与清除都返回 `E_STATE`；被豁免的 “绑定处理” 在命令目录中没有命令）

- **问题**：
  - `06` L139 ③：作用于该 Project 或其 Goal 的命令返回 `E_STATE`，只有查询、`goal.pause` 与绑定处理（情形 C、D 的迁移与重新克隆、情形 F 的改 `worktreeRoot`）除外。所以 `goal.abandon`（`06` L941）返回 `E_STATE`；`privacy.purge` 的 `goal` 档只接受终态 Goal，`project`、`all` 档的范围内有非终态 Goal 即整笔 `E_STATE`（`09` L560）。
  - ADR-235 登记的出口是 “迁移附着检出、重新克隆或改 `worktreeRoot`，之后照丢失处理”。对一个只在本地、没有其他检出也没有远端的仓库，在它丢失之后：
    - “定位仓库” 没有可定位的；
    - “从远端克隆” 没有远端；
    - 改 `worktreeRoot` 不改附着检出，Project 仍不可达；
    - 情形 D 的 “只保留分支（从镜像导出）”（`10` L1265）导出之后，Project 与它的 Goal 怎样结束，没有写。
    这些 Goal 因此无法放弃、无法清除，一直显示为不可达。在 ADR-235 之前，情形 D “运行中的 Goal 不受影响”，放弃与清除照常可用。
  - **命令**：迁移、重新附着、重新克隆、设置 `Project.worktreeRoot`、“只保留分支” 在 `06` §6.4.3 与 `16` §16.5 中都没有命令（Project 类命令只有 `project.set_trust`、`project.merge`、`project.split`、`project.approve_docker` 等；只有事件 `binding.reattached`，`10` L1348）。迁移没有命令是 ADR-235 之前就有的，但 ADR-235 把它们定为 `E_STATE` 的例外与唯一出口：它们的参数、作用范围（按 Project 还是按 binding）、是否仅本机、对 `Project.identity` 的核对，都没有定义。
- **为什么是次要**：不丢已有的工作——检查点在 `~/.tower` 的影子中，分支可从镜像导出；不涉及机密。但这是 ADR-235 带来的死路，而唯一出口所依赖的命令不存在，实现会各自补出不同的命令与范围。
- **后果的类别**：
  - 本地仓库连同外接盘一起丢失的人，无法放弃或清除该 Project 的 Goal，它们的对话与证据留在 `~/.tower` 中；
  - 迁移的实现各异，例如是否核对同一仓库、是否远程可用。
- **文档位置**：`06` L139 ③、L941、§6.4.3、§6.4.7；`09` L560；`10` L42、L1264–L1265、L1348；`16` §16.5。
- **期望的回答形态**：
  - 在 `06` §6.4.3 补绑定处理的命令（如 `project.reattach{projectId, checkoutPath, goalIds?}`、`project.set_worktree_root`），写明作用范围、仅本机，以及迁移时对 `Project.identity` 的核对；
  - 在 L139 ③ 的例外中加 `goal.abandon`（只写数据库；人工编辑检出不可读时不做差异询问，按 “人的工作现场不自动删除” 保留），使 Goal 可以进入终态再清除；或者把情形 D 的 “只保留分支” 定义为解除该 binding 并放弃其 Goal。

### 不扣分的观察

1. **`idle` 模式的缓存预热**：默认的 `streaming` 模式在 settle 时停止预热（`cache-warmer.ts:248-250`）。你把 `cacheWarming` 设为 `idle` 时，预热在 settle 之后继续，至多到首次请求后 30 min（`:18, 252-256, 286-297`），只有会话 `dispose` 或模式改变才停止。Tower 只在 drain 或 Host 退出时 `dispose`，所以在 `verifying`、暂停后的 5 分钟、打包模式下 Host 存活期间，预热都可能继续。
   - `11` L517 的 “下一次 `turn_start` 之前” 在一个 Run 的最后一次调用之后没有终点，实际上界是 30 min 或 `dispose`。机密的去向与已登记的一类相同。
   - `06` L353 的 “只在对账的差值中出现” 对 settle 之后追加的用量不成立：它只出现在同一会话之后的某次 settle 中，Goal 进入 `in_review` 或终态后则不再出现。金额很小（有节省门槛）。
   - 宜如实改写两句，或由适配器在 settle 时停止预热。
2. **`retry.maxRetries` 的引文**：`05` L474 与 ADR-235 以 `ai/src/utils/retry.ts:198, 218` 作会话自动重试的依据，实际上那是只由压缩与摘要调用的 `retryAssistantCall`（`compaction.ts:638`）。会话的自动重试在 `agent-session.ts:1204, 3795`，遇到非数值时同样不终止，结论不变。宜改引。
3. **`!` 命令的缓存**：`06` L101 “`!` 命令的结果已在该 Host 进程中缓存，探测不使它重新执行”只对 `auth.json` 成立（`resolve-config-value.ts:208-216`）。`models.json` 中以 `!` 写的 `apiKey` 每次 `getAuth` 都不经缓存地执行（`provider-composer.ts:466-467` → `resolve-config-value.ts:221-231`），所以每次探测都会执行一次——与每次模型请求相同，`11` L517 也这样写了，后果可以忽略。宜把这一句限定为 `auth.json`。
4. **探测的摘要只写专用模式**：`03` L96、`08` L419、`12` L444、`04` L1516、`16` L29、`05` L486 写 “服务该 Goal 而仍存活的 Host”。唯一定义（`06` L101）是同组中已存活且没有进行中 Run 的 Host：打包模式下服务该 Goal 的 Host 可能正忙（不探测），也可能由同组另一个空闲 Host 探测。宜在各处摘要中写 “同组空闲的 Host（`06` §6.1.4 第 5 项）”。另外 “Host 的运行时不能代它判定” 的理由写得过强，“认证与端点由扩展决定” 已足够。
5. **F13 与 `turn_start` 出错**：`06` L1206 的 F13 仍只写 “工具被阻断（fail-safe）；连续 3 次则暂停”。`turn_start` 处理器出错时没有工具被阻断，这些出错是否计入 “连续 3 次” 只在 `05` L1006 写了。`emitError` 带 `event: "turn_start"`，可以区分。宜在 F13 一行补半句。
6. **`[重试]` 在必然失败时出现**：`12` L444 与 `06` L101 在 F8 只读期间也显示 `提供方可能已恢复？[重试]`，而这时 `goal.resume` 返回 `E_STATE`；该 Goal 的 Project 不可达时同样如此。宜在这两种情形下不显示按钮。
7. **`resumeOnLaunch` 关闭时卡片的原因过时**：`12` L434 按最后一个 Run 的 `outcome_reason` 写原因，`resumeOnLaunch` 关闭时，空间释放或盘重新插上之后，卡片仍写 `已暂停 · 磁盘已满` 或 `已暂停 · Project 不可达`，而条件已不存在。G35e (q) 关闭的一遍只核对只读期间的实况行。宜在条件消失后改写为 `已暂停 · 应用退出`，或在卡片上加 `· 已可访问`。
8. **网络卷与睡眠唤醒**：单次 `stat` 超过 5 s（转速降下的机械盘、SMB 的短暂停顿）即中止该 Project 的全部 Run，没有确认采样；唤醒后没有可达性的宽限（心跳有 60 s，`06` L109），网络卷重连较慢时会中止 Run，F16 的唤醒续跑不适用（不是网络错误的 settle）。不丢数据，`resumeOnLaunch` 打开时约 30 s 内自动继续。宜登记为取舍，或在有活跃 Run 时以第二次采样确认、唤醒后给一个宽限。
9. **Project 不可达的注意力**：`08` 没有提到它。它复用 `app_quit`，后者在 `08` 中同样只有卡片，所以实现会按 “只在卡片” 处理。拔盘会中止一个 Project 的全部 Run，宜在 `08` §8.1 写一行（例如项目级 L1 `◇` 与简报一行，不是 Needs-You），与磁盘满的横幅对照。
10. **不可达的显示细节**：
    - `12` L416 写 “不在 `ready` 的目标在原有实况行后追加 `· Project 不可达`”，可能在 `已暂停 · Project 不可达 · …` 的卡片上重复；`04` L1522 写的是 “其他目标”，宜对齐。
    - 因不可达而取消验证的 `verifying` Goal 没有对应的实况行（F8 有 `验证已取消（磁盘已满）`）。
11. **`04` L1522 的恢复一栏**：“30 s 内自动恢复” 没有带 `resumeOnLaunch` 的条件（同一行第二栏已引 `12` §12.6.5）；出口只列迁移，没有列改 `worktreeRoot` 与重新克隆。
12. **残留**：
    - `03` L97 `app_quit` 的来源写 “应用退出 / 也来自磁盘满”，没有 Project 不可达；出口中的 `abandon` 在不可达期间返回 `E_STATE`；
    - `16` L856 仍以 “外接盘未挂载” 表述，比规则窄；
    - `13` L129 “Engine Host 只在 Goal 有活跃 Run 时存在” 与同句的 5 分钟延迟退出不一致，探测现在依赖后者。
13. **启动时等待可达性**：§6.1.6 在接受界面命令之前执行（`06` L116），不可达一行最先判定，所以命令的受理可能等 5 s（R108-D6-01 下更久）。`13` 的冷启动预算只覆盖列表显示，宜写一句。
14. **lint (d) 的历史豁免窗口**：同一句 “为探测起一个短时 Host” 插在 `13` L130 时没有报出，因为匹配前后的窗口中有 “不再”（`DEL_OK` 的历史标记）。这是该检查已知的局限，宜把 “不再” 从非严格模式的豁免词中移出，或为本轮三项启用严格模式。
15. **请求时限的细节**：厂商 SDK 的 `timeout` 与 Codex 的 `AbortSignal.timeout` 只管到响应头为止；流式响应体期间只有分发器在 Host 启动时设置的 `bodyTimeout` 起作用。`05` L474 的 “先到者起作用” 宜限定为 “等待响应头时”。
16. **G35e (q) 的断言力**：“期间对该 Project 的 `goal.accept`……返回 `E_STATE`” 对运行中、写回中、验证中的 Goal 本就成立，测不出新规则；只有错误文字与 `goal.abandon` 能测出。另外，不可达期间的后台工作——在 M1 规定时机从附着检出 fetch base、定期 `fsck`、备份 bundle——是否暂停只能推出，宜写一句。

### 设计是否完成

ADR-235 以删除关闭了第 107 轮的全部五条条目：
- 探测不再另起进程，分组、上限、自身失败与 `!` 命令的重复执行一起消失；
- 校验扩到会造成重试循环的设置，请求时限的先后如实写明；
- 只读期间的实况行按 ADR-232 的条件写 “恢复”；
- 按卷名的判别由一条 “Project 不可达” 规则取代，Run 进行中卷消失、其余恢复行、清除续做、情形 C/F、命令范围、`syncing` 不变式与同名卷都落在一处。

本轮 8 条中五条是新规则带出的分支，三条是扫描发现的缺口：
- **R108-D4-01**：启动时不可达而带真正 `app_quit` 的 Goal 何时解除；
- **R108-D5-01**：`retry.provider.timeoutMs` 的 0 与非整数，F4b 的触发与卡片原因；
- **R108-D6-01**：单线程排队与 `~/.tower` 所在卷；
- **R108-D7-01**：退出确认框的无条件承诺；
- **R108-D12-01**：清除续做的推迟范围与判定对象；
- **R108-D13-01**：多附着点下的必需路径；
- **R108-D13-02**：操作中途卷消失、早于可达性判定；
- **R108-D13-03**：永久不可达时的出口与绑定处理的命令。

全部为次要：
- 没有一条会使照文字实现的人违反所述的安全不变式；
- 没有一条会删除人的工作现场——不可达期间 Tower 碰不到那些目录，告知 “不可恢复” 的一支（R108-D13-02）不伴随删除；
- R108-D12-01 的副本只在你自己的机器上，可达后续做。

每一条都能在已有的唯一定义处加一句或一条守卫关闭。
