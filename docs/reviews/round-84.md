## 1. 总评

**第 83 轮的 2 条重要、7 条次要条目中，8 条关闭，R83-D14-01 部分关闭**（G21 移到 B3，但 B3 仍早于交还的桌面一半实现，见 R84-D14-01）。§5 的 13 条观察都已落地或按理由不改；其中三条的修订带出了新的小问题（观察 6 只改了 `12`，没改 `04`；观察 8 关于 `~/.agents/skills` 的说法不准；观察 10 的事件载荷与 “从事件完全重建” 冲突），分别并入 R84-D15-01、R84-D5-02、R84-D6-02。核对见 §3。

**ADR-211 的主体成立**（§3.3）：
- **两个 Pi 开关**：
  - `PI_OFFLINE=1` 确实是关闭资源加载时自动安装的唯一开关，SDK 中没有别的安装或更新路径；
  - `PI_CODING_AGENT_DIR` 使 MCP 配置、`mcp-auth.json` 与锁、`mcp.log`、工具二进制目录都随本 Run 的 agentDir；
  - 在 `host.spawn` 时写入环境足以覆盖模块加载时的求值；崩溃日志只在交互模式写。
  - 以上经逐个调用点核实。
- **`globalPath` 按模式**：隔离模式因此不解析用户的 `packages`，R83-D11-01 与 R83-D5-01 (b) 的叠加不再出现。
- **settle 的 `agent_bg_done` 豁免去重**：只豁免 settle 第 4 步，交还第 7 步仍按 ADR-184 去重；回合入口只与回合检查点比较。I4(b) 与 Projector 断言照字面成立。`10` §10.7.2 没有检查点保留或回收规则，所以每次 settle 多一个检查点不与任何保留规则冲突。
- **检验带回**：`human_edit` landmark 与 `humanPaths` 的取法与交还第 8 步相同；`10` L415 与 L672 的 `Tower-Human-Edit` 规则都已覆盖带回。带回要求卫星树等于 T_pin，所以 `humanPaths` 之外没有需要穿透的路径。
- **忽略规则不追溯**、**丢失检出的 kind**、**评论按钮删除**：唯一定义处的改写都成立。

**ADR-211 带出或暴露的新问题**，都不触及安全不变式本身，但会使实现分叉：
- 两个开关是**进程级**的，而 Host 可以打包承载最多 4 个 Goal，且这可能成为 M1 默认。规则 “agentDir 不同就重启 Host” 在打包模式下会中断其他 Goal 的 Run，正文没有写按 agentDir 分组（R84-D6-01）；
- `bashEnv` 在三处被写成 “保留 `PI_*`”，与 “两项不进入 bash” 及 C40 字面冲突（R84-D5-01）；
- 隔离模式的实际差异没有如实写出（R84-D5-02）：
  - `rg`/`fd` 只在隔离目录的 `bin/` 与 Host `PATH` 中查找，塑形与评审阶段因此在常见环境下没有 `grep`/`find`；
  - 用户的 `shellPath`/`commandPrefix` 不再生效；
  - `~/.agents/skills` 仍会加载。
- 静态清单不知道 Pi 的 legacy 全局包路径；C40 断言的 “没有包管理器子进程” 在 v1.2.0 上必然不成立（R84-D11-01）；
- `checkpoint.created` 的载荷只有编号，与 “领域表可以从事件完全重建” 冲突（R84-D6-02）；
- `16` L196 的 `stalled` 子类型表、`04` L717 的时间线规则、`10` L774 的 `author` 注释、`06` L320 的 Host 环境拼装没有同步（R84-D15-01）；
- 影子目录被删除后的重建仍以 `baseCommit` 初始化索引，与 “不追溯” 不一致（R84-D13-01）。

**全范围扫描**在 ADR-211 之外新发现：
- 丢失的人工编辑检出：运行中与重启时两条路径的出口不一致，`goal.resume` 在运行中被 `human_checkout` 守卫拒绝；“再次接管” 会覆盖为判断去向而保留的 `takeover_from`（R84-D4-01）；
- `requiresChange` 评论的 “被人关闭” 没有命令也没有字段，却是验收闸门（含远程验收）的条件；`dropped` 的 “人选择丢弃” 同样没有命令（R84-D8-01）；
- SP6b B3（第 23 周）中有六个用例依赖第 24–29 周才完成的实现（R84-D14-01）。

**排期**：
- WBS 123.12；角色合计 Agent 26.55 / 系统 26.35 / 桌面 27.84 / 设计 28.76 / 安全 13.62。
- 余量：系统 0.12、Agent 0.23、桌面 0.36、设计 0.66、安全 0.14。

### D6 系统架构与可靠性

**R84-D6-01｜次要**（进程级的 Pi 开关与打包模式的 Host）

- **问题**：
  - ADR-211 的两个开关写在 Host **进程**环境中，`TOOLS_DIR` 在模块加载时固定（`05` L456）。规则是 “下一个 Run 选定的 agentDir 与存活 Host 的不同时，Supervisor 先让该 Host 退出再以新环境启动”。
  - 但 Host 可以打包：设置项 “打包模式” 允许每个 Host 承载最多 K=4 个 Goal（`06` L42、L284）。SP2 测得独占 Host 的 RSS p95 > 120 MB 时，打包模式还会成为 **M1 默认**（`16` L857、`13` L196）。
  - agentDir 按 Goal 选取：`riskTier=high`，或清单尚未确认（新用户的头几个 Goal 都属此类），用隔离目录；其余用用户目录（`05` L1312）。同一个打包 Host 中的两个 Goal 因此可能需要不同的进程环境。
  - 正文没有写打包时按 agentDir 分组，于是实现者只能自选：
    - 照字面重启共享的 Host：同一 Host 中其他 Goal 的活跃 Run 被中断，按 `engine_crash` 处理；10 分钟内再遇一次就进入 `stalled{crashed}`（`06` L64）；
    - 或者不重启、让不同 agentDir 的 Goal 共用一个进程环境：非隔离 Goal 在隔离环境中读不到用户的 `mcp.json`，与 C40 的断言和清单卡片不一致。
  - 另外，重启本身不在 Host 退出时机的唯一定义中：`06` §6.1.8（L169）与 `13` §13.5（L129）只列 “settle 后进入 `in_review`、`paused` 超过 5 分钟、被人中止、应用退出”。`06` L320 的准备流程拼装 Host 环境时也没有提到这两项与重启判断。
- **为什么是次要**：独占模式下规则成立；打包模式下两种取法都不越过安全边界，但一种会中断无关 Goal 的 Run，一种会使 MCP 的加载目录与清单不一致，取决于实现者自选。
- **文档位置**：`05` L456；`06` L42、L64、L169、L284、L320；`13` L129、L196；`16` L857。
- **期望的回答形态**：在 `05` §5.3.6 “Pi 运行开关” 一行（唯一定义）加一句，二选一：

**R84-D6-02｜次要**（`checkpoint.created` 的载荷不足以重建 `checkpoints` 表）

### D5 Agent 架构与 Pi 集成

**R84-D5-01｜次要**（`bashEnv` “保留 `PI_*`” 与 “两项不进入 bash” 字面冲突）

- **问题**：
  - Pi v1.2.0 的 bash 环境以整个 Host 进程环境起步，只删除并重设五个会话变量（`core/tools/bash.ts:185-206`）。所以 ADR-211 写入 Host 环境的 `PI_OFFLINE` 与 `PI_CODING_AGENT_DIR` 一定出现在 `spawnHook` 收到的环境中。
  - 能否把它们挡在 bash 之外，完全取决于 Tower 的 `bashEnv`。但它的规则在三处写成按前缀保留：
    - `05` L376 骨架注释：“白名单过滤，保留 `PI_*` 会话变量”；
    - `11` L287：“`spawnHook` 的环境白名单保留 `PI_*`（ADR-066）”；
    - 契约测试 C28a（`05` L1460）：“`spawnHook` 改写的环境对子进程生效，并保留 `PI_*`”。
  - 另一侧：`05` L456 “两项都不进入 bash 环境”，`11` L507 “只在 Host 环境中，不进入 bash”，C40（`05` L1473）“bash 子进程环境中没有这两项”。
  - 按前缀实现的 `bashEnv` 通过 C28a、不通过 C40；只保留五个会话变量的实现则相反。
- **为什么是次要**：两项变量都不是机密，泄入 bash 的后果有限。但两个契约测试照字面互斥，实现者要自定规则。
- **文档位置**：`05` L376、L456、L1460、L1473；`11` L287、L507；`15` ADR-066 相关段。
- **期望的回答形态**：在 `05` §5.3.6（`bashEnv` 的唯一定义处）写明保留的是 Pi 的五个会话变量（`PI_SESSION_ID`、`PI_SESSION_FILE`、`PI_PROVIDER`、`PI_MODEL`、`PI_REASONING_LEVEL`），不是 `PI_*` 前缀；`05` L376、`11` L287、C28a 改为引用。

**R84-D5-02｜次要**（隔离 agentDir 下的实际差异没有如实写出）

- **问题**：ADR-211 使隔离 Goal（`riskTier=high`，以及**清单尚未确认时的每个 Goal**）的整个 Pi 进程环境指向 `~/.tower/pi-agent/`，并按 `globalPath` 不读用户设置。由此产生三处与文档不符的行为：
  - **(a) `rg`/`fd`**：
    - Pi 先在 `<agentDir>/bin` 找，再在 `PATH` 中找（`utils/tools-manager.ts:83-102`），离线时不下载（`:361`），找不到时 `grep`/`find` 报 “ripgrep (rg) is not available”（`core/tools/grep.ts:121`）。
    - 隔离模式下第一处是从不会有内容的 `~/.tower/pi-agent/bin`；而 pi CLI 正是把它们下载到用户 agentDir 的 `bin/`。
    - Tower 构造的 Host `PATH`（`05` L457）只有 Tower 的 Node 与包管理器、经确认的登录 shell 目录与系统路径，macOS 系统路径中没有 `rg`/`fd`。
    - 塑形与评审阶段只激活 `read`/`grep`/`find`/`ls`（`05` L717–L718），这两个阶段在隔离 Goal 中只剩 `read` 与 `ls`。没有用过 pi CLI 的新用户，非隔离 Goal 也是如此。
    - `00` L99 只写 “也不自动下载”，没有写这一后果，首次运行检测（W16）与能力摘要也没有相应提示。
  - **(b) shell 设置**：
    - 隔离模式的 `settingsManager` 读空设置（`05` L313），`getShellPath()`、`getShellCommandPrefix()`（`05` L371、L377）因此返回默认值。
    - 这与 `00` L77 “继承用户的 `commandPrefix` 与 shell 设置”、`11` L287 “取自用户 Pi 设置”、C28a “`commandPrefix`/`shellPath` 与用户设置一致” 都不符。
    - 依赖 `commandPrefix` 准备工具链的用户，在隔离 Goal 中的命令行为会不同。
  - **(c) 技能**：
    - `09` L452（第 83 轮观察 8 的修订）说隔离 Goal 不加载用户级技能。
    - 但 Pi 恒按 `$HOME` 加载 `~/.agents/skills`（`core/package-manager.ts:2464`、`:2555-2567`），与 agentDir 无关；S2 读允许列表也含它（`05` L447）。
    - “生效上下文” 面板照 `09` 列出时会漏掉这些技能。
- **为什么是次要**：没有越过安全边界（技能只在沙箱中执行），但塑形与评审是 M1 主循环的两个阶段，它们的搜索能力在常见环境下缺失，而用户与实现者都得不到提示。(b)、(c) 会使实现与文档、契约测试分叉。
- **文档位置**：`05` L313、L371、L377、L447、L456、L457、L717–L718、L1460；`00` L77、L99；`09` L452；`11` L287。
- **期望的回答形态**：在 `05` §5.3.6 “Pi 运行开关” 与 §5.10 隔离 agentDir 一句（唯一定义）处：
  - (a) 二选一：Host `PATH` 加入用户 agentDir 的 `bin/`（Agent 在 S2 下不可写该目录）；或由 Tower 随 `$SH/tools` 提供固定版本的 `rg`/`fd`。无论取哪一种，首次运行检测与 `00` §0.5.1 都写明 “找不到时塑形与评审中的搜索不可用”；
  - (b) 二选一：隔离模式下 shell 两项仍取用户设置；或在 `00` §0.5.1、`11` L287、C28a 注明 “隔离 Goal 用默认 shell、不加 `commandPrefix`”；
  - (c) `09` L452 改为 “用户 agentDir 中的技能不加载，`~/.agents/skills` 照常加载”。

### D11 安全与自主度

**R84-D11-01｜次要**（静态清单不知道 Pi 的 legacy 全局包路径；C40 的断言在 v1.2.0 上不成立）

- **问题**：
  - `05` L1330 的不变式：静态清单的枚举根 “与 Pi 实际加载扩展的目录相同”，“确认之前不加载、不执行任何代码”。ADR-211 规定清单只列 “已安装且版本与设置相符的包（判定同 Pi）”，其余单列为 “未安装：Tower 不安装、不加载”。正文给出的包目录是用户 agentDir 下的 `npm/`、`git/`（`05` §5.3.6 用户 agentDir 一段）。
  - Pi v1.2.0 的解析多一步：用户级 npm 来源在 `<agentDir>/npm/node_modules/<name>` 不存在时，回落到 legacy 全局路径（`core/package-manager.ts:2151-2158`）。回落要同步运行用户设置的包管理器命令求出全局根目录（`:2102-2129`）。这一步发生在离线判断**之前**（`:1321-1322`），不受 `PI_OFFLINE` 控制。全局路径存在且版本相符时，该包照常加载。
  - 于是在 “包只存在于旧布局的全局目录、且 Host 的包管理器能找到它” 时：
    - 清单把它列为 “未安装、不加载”，用户据此确认；
    - Pi 却在 Host 中加载它；
    - 它的内容哈希从未进入清单，此后的改动也不会触发重新确认。
    - 这是 “确认之前不加载” 要排除的那一类后果：未列入确认清单的沙箱外代码被加载；同时 Tower 对用户的陈述不实。
  - Host 默认的 `npm` 是 Tower 自己的 Node（`05` L457），其全局目录通常是空的。所以触发需要用户设置了 `npmCommand`，或用 pnpm/bun 并有被透传的 `PNPM_HOME` 等变量（`11` L507 的工具链变量白名单）。
  - git 来源同理：用户级 git 来源的安装路径不含 ref（`:2160-2170`），Pi 只检查目录是否存在（`:1336-1340`）。若实现者把 “版本不符” 理解为 ref 不同而列为 “未安装”，Pi 仍会加载。
  - **C40**（`05` L1473）的非隔离一组断言 “没有包管理器或 git 子进程”。但它的夹具（用户 agentDir 的 `packages` 中有一个未安装的 npm 包）必然走上述回落，运行一次包管理器子进程。这条契约测试照写无法通过，**与配置无关**。
- **为什么是次要**：
  - 加载错位的触发需要两个非默认条件（旧布局的全局安装，以及能找到它的包管理器配置）；
  - 被加载的是用户自己安装、自己写进设置的包，不是外来的代码；
  - 在 S2 下 Agent 也不能写全局目录。
  - 但不变式的文字（“与 Pi 实际加载的目录相同”）不成立，契约测试必然失败，实现者需要自定取法。
- **文档位置**：`05` L456、L457、L1330、L1407（D45）、L1473（C40）；`11` L507、L607；`14` L134 G46 (bi)。
- **期望的回答形态**：在 `05` §5.10 静态清单（唯一定义）二选一：
  - 清单按 Pi 的同一顺序求包目录，含 legacy 全局路径：Supervisor 以用户设置的 `npmCommand` 求全局根，这是运行包管理器自身、不执行包代码，与安装器第 1 阶段同类。求出的目录照常哈希并列出；
  - 或写明 “legacy 全局安装的包 Tower 不支持”，并给出可执行的保证（例如 Host 环境中让包管理器的全局根指向空目录），使 Pi 与清单一致地不加载。
  - 同时：
    - git 来源的 “版本不符” 只指 npm 的版本范围，git 来源只看是否存在；
    - C40 的断言改为 “没有安装子进程（`install`/`clone`）与注册表请求”，允许并记录一次只读的全局根查询，或在夹具中固定 `npmCommand` 指向一个无全局包的包管理器。

### D4 领域模型与生命周期

**R84-D4-01｜次要**（丢失的人工编辑检出：运行中与重启时两条路径不一致；再次接管覆盖 `takeover_from`）

- **问题**：
  - **重启时**（`06` L144，唯一定义）：`syncState='idle'` 且目录不存在 → 清除 `human_checkout`、**保留 `takeover_from`**，生成 `stalled{human_checkout_lost}`，出口三个：再次接管、继续（`goal.resume`）、放弃改动。`06` L504 的列注释再次强调 “检出丢失时保留，供 `discard_human_edits` 判断去向”。
  - **运行中**（`10` L1027）：H 被外部删除时，卡片 “人工编辑检出已不在”，选项只有 `goal.resume` 与 `goal.discard_human_edits`；`10` L929 也写 “检出丢失时的 `goal.resume`（不要求检出存在）”。但：
    - 没有任何规则在运行中清除 `human_checkout`；
    - `goal.resume` 的前置守卫是 “`human_checkout` 非空 → `E_STATE`”（`06` L881）；
    - 所以运行中提供的 “继续” 照字面必然被拒绝；
    - 这条路径也没有 Needs-You kind：`08` L210 只写 “重启时”。
  - **再次接管**：`goal.take_over` 允许从 `paused(*)` 发起，`human_checkout` 已清除时守卫通过。它在同一事务中**无条件**写 `takeover_from=<源状态>` 与 `takeover_prior_reasons`（`06` L903）。从丢失检出的 `paused(human)` 再次接管时：
    - `takeover_from` 被改写为 `paused`，原来的 `in_review`/`accepted` 丢失；
    - 之后的 `discard_human_edits` 不再做 “卫星树 ≠ pin” 的判定（只在 `takeover_from ∈ {in_review, accepted}` 时做，`06` L906）；
    - 由于 `takeover_prior_reasons` 含 `human`，放弃改动后也不解除 `human`。
    - 这与 L144 “保留 `takeover_from`” 的目的相反。
- **为什么是次要**：不丢已写回的数据（未交还的改动本就随检出丢失），继续目标保持不变。但运行中提供的出口照字面不可用，再次接管后的去向判定与保留它的理由矛盾，实现者会各自补规则。
- **文档位置**：`06` L144、L504、L881、L903、L906；`10` L929、L1027；`08` L210、L514。
- **期望的回答形态**：
  - 在 `06` L144（唯一定义）写明它同样适用于运行中检测到的丢失（文件系统事件或操作前检查），`10` L1027 改为引用，出口与重启时相同；
  - 在 `goal.take_over` 行加一条守卫：`human_checkout` 为空而 `takeover_from` 非空（检出已丢失）时，保留已有的 `takeover_from` 与 `takeover_prior_reasons`，不改写。

### D8 注意力与交互

**R84-D8-01｜次要**（`requiresChange` 评论的 “被人关闭” 与 `dropped` 的 “人选择丢弃” 没有命令）

- **问题**：
  - 验收闸门要求 `requiresChange` 的评论 “为 `addressed`（只认 hunk 已变）**或被人关闭**”（`03` L141、`02` L579、`05` L1158、L1193、`16` L215）。远程验收把它作为条件之一（`06` L988、`11` L627、`16` L1081）。非 hunk 锚点的评论 “只能由你关闭”（`04` L333、L501）。
  - 但：
    - `Comment.delivery.state` 没有 “已关闭” 一值（`02` L581）；
    - `Comment` 没有关闭字段；
    - 评论命令只有 `comment.create`/`edit`/`delete`/`send_batch`（`06` L920–L921）。
  - “关闭” 可以被实现为删除（失去审计）、`edit{requiresChange:false}`（改写了人当初的要求），或新加字段，各家会不同。
  - ADR-211 使这一点更常遇到：`过期` 的 `重新发送` 以原正文新建一条评论（`04` L501）。原来那条过期的 `requiresChange` 评论仍阻断验收，只能 “关闭”，而 “关闭” 没有定义。
  - `05` L1195 的 `dropped` 定义仍含 “`abort` 后被 `clear_queue` 清掉、**且人选择丢弃**”。L1217 规定暂停流程把这些评论放回队列、保持 `queued`，ADR-211 又删除了未送达的按钮。这一分支既没有命令，也不可达。
- **为什么是次要**：与 R80-D8-02 至 R83-D8-01 同类，是界面动作没有命令。但它卡在验收闸门上，远程验收要据此判定。
- **文档位置**：`02` L579–L580；`03` L141；`04` L333、L501；`05` L1158、L1193、L1195、L1217；`06` L920–L921、L988；`11` L627；`16` L215、L1081。
- **期望的回答形态**：在 `05` §5.7.3（回执状态的唯一定义）：
  - 把 “关闭” 映射到已有命令，并写明载荷与审计。例如 `comment.edit{requiresChange:false}` 由 `comment.*` 事件留痕，回执显示 “你已关闭”。或者给 `delivery.state` 加一值 `closed`，并写明对应命令；
  - `dropped` 删去 “且人选择丢弃”，只保留 Pi 返回 `handled` 一个来源。

### D13 隔离、git 与并发

**R84-D13-01｜次要**（情形 B 的重建与 `07` 的伪代码不遵守 “忽略规则不追溯”）

- **问题**：
  - ADR-211 在 `10` L744 立了唯一定义：已收入影子索引的路径此后即使匹配忽略规则也留在快照中；“清空影子索引” 即以 `full` 的临时索引取代它。第 83 轮的期望回答也要求 “把清空影子索引之后的初始化写成同一规则”。
  - 还有两处初始化不遵守这条规则：
    - **情形 B**（`10` L1247，影子目录被删除）：“重建空影子（§10.3.1 第 3 步）……然后立即对卫星当前工作区做一次检查点”。第 3 步以 `read-tree <baseCommit>` 初始化索引（`10` L371）。于是此前收入、后来被忽略、且不在 base 中的路径从这次检查点起消失：
      - `running` 中，它们随后从 pin 与 seal 中缺失，评审 diff 中显示为删除；
      - `in_review` 中，检查点与 pin 不同，触发 I2，归因表找不到写入者。
      - 备份 bundle 中有最近的检查点（`10` L1247 同一行从中 fetch），可以用它的树初始化。
    - **`07` L262**：`worktreeTree` 伪代码在 `full` 之后 `rm(index)`，而 `07` L281 与 `10` L744 说 mismatch 之后 “以这次 `full` 的临时索引取代” 影子索引。照伪代码实现会得到空的影子索引，再从空索引 `add -A`，结果与情形 B 相同。
- **为什么是次要**：情形 B 少见；伪代码只是示意。但两处都会使同一卫星内容得到与 “不追溯” 不同的树，而规则刚刚以唯一定义的形式确立。

  - **其他核对**：

    - 排期结论成立：WBS 123.12；余量 0.12 / 0.23 / 0.36 / 0.66 / 0.14；依赖链 19.91；增人 129.06、T 23.83、33 周；M1 38 周（2027-07-30）。
  - **不扣分的观察**：
    1. **扩展子进程继承两个开关**：`pi.exec` 继承 Host 环境（`core/exec.ts:36-46`），所以用户扩展派生的进程会看到 `PI_OFFLINE=1` 与 `PI_CODING_AGENT_DIR`。若扩展再启动一个 `pi`，它同样离线、使用同一 agentDir，偏保守，无害。可在 `05` L456 补半句 “扩展子进程继承这两项”，免得有人把它当成泄漏去修。
    2. **模型目录**：Tower 创建 `ModelRuntime` 时不传 `allowModelNetwork`（`core/model-runtime.ts:251`），`createAgentSessionServices` 只做无网络刷新（`core/agent-session-services.ts:194`）。所以 Tower 中的模型列表 = Pi 内置目录 + 用户 agentDir 中由用户自己的 `pi` 最近一次刷新的 `models-store.json`，与 `PI_OFFLINE` 无关。`05` L456 “同一开关还关闭模型目录的网络刷新” 准确，但 `00` §0.5.1 可补一句 “模型列表来自 Pi 内置目录与你的 pi 最近一次刷新”，免得用户以为 Tower 会自己刷新。另外 Pi 以 `=== undefined` 判断（`:247`），设为 `0` 也会关闭，Tower 取 `1` 不受影响。
    3. **`s0.grant` 在其他暂停中**：`04` L589 写 “在其他暂停中授权只记录授权、不改变状态（`06` §6.4.3）”，但 `06` L908 的 `s0.grant` 行没有这一句。在 `verify_failed_limit` 等暂停中，文案 “验证完成后再次打开检验” 等的验证不会开始。宜在 `06` L908 补这一句，并把 `04` L589 的末句改为 “在其他暂停中，处理该暂停后再打开检验”。
    4. **Projector 断言的措辞**（`06` L267）：一个 Run 撤回到 `running` 后再次 settle 会有两个 `agent_bg_done` 检查点，宜写 “最近一个”。`claim_on_behalf` 没有 `submit`，断言的前半句应注明例外，与 `03` L115 一致。
    5. **未送达评论的送达时机**：`05` L1167 写 “恢复时作为 `opening.human` 的一部分”，`04` L501、L1356 写 “下一次运行开始时”。自动返工、交还 `continue_agent` 开出的 Run 是否同样带上队列中的评论，宜在 `05` §5.7.1 写成 “任何 Run 开始时”。
    6. **`■ 未送达` 的字形**：ADR-211 起它是 “无需操作” 的状态，但 `12` L335 仍把它列为异常与阻断类，用 danger。宜改用 `◇` 或 text-2，与暗驾驶舱原则一致。
    7. **M2 残留的通用提法**：`06` L90、L139，`04` L110、L1416、L1510，`12` L388 在 drain、崩溃恢复与文案中把 “回退” 与 “接管” 并列；`04` L626、L665 有未标的合并队列说明；`04` §4.7.2 的 M1 诊断线框画了 “尝试 2 / 回退后放弃”。这些不在 M1 中造出命令（命令行已标 M2），宜各补 “（M2）”。
    8. **`baselineCps` 的取值措辞**：`06` L906 等处仍写 “否则为 pin 的检查点”。宜引用 `10` §10.3.1 “当前 pin 的检查点（没有时为 pin 本身）”，与 `02` L169 的新类型一致。
    9. **不追溯的可见后果**：Agent 先生成、后加入 `.gitignore` 的目录（如构建产物）会一直留在 pin 与 seal 中。这与 git 的已跟踪语义一致，在评审 diff 中可见；可在 `04` 评审的提示中加一句 “已被忽略但此前已收入的文件仍会进入提交”。
- **设计是否完成：ADR-211 正确地关闭了第 83 轮的两条重要条目。** 两个 Pi 开关经逐个调用点核实，做到了它们声称的事，安全不变式在默认与 ADR-209/210 支持的配置下由构造保证。
  - 本轮没有重要或阻断条目。10 条次要条目分三类：
    - **进程级开关带出的边界**：R84-D6-01（打包模式）、R84-D5-01（bash 环境的 `PI_*` 规则）、R84-D5-02（隔离模式的实际差异）、R84-D11-01（legacy 全局包路径与 C40）；
