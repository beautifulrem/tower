## 1. 总评

**第 81 轮的 5 条次要条目全部解决，§5 的 7 条观察全部落地。** 核对见 §3。

**ADR-209 的主体成立**（§3.3）：
- **移出清单的路径按已记录的 L 回看**：
  - 判定只读 trailer 与快照树，覆盖了评审的两种情形：经 pin 收入，以及移出时仍被忽略。
  - pin 之前的 `safety` 检查点与 landmark 规则、去重、崩溃续做、I4(b) 都不冲突。它在归因窗口之内，作者推导先看 `mixedPaths`。
  - 但它带出两处原有定义没有跟上：
    - `claimed` 之后的 “归因基线 = 当前 pin 的检查点” 仍写死为 settle 的 `agent_bg_done` 检查点（R82-D13-01）；
    - 非回合检查点 “跳过第 7 步”，字面上不记 `checkpoint.created`，而窗口按事件序号取检查点（R82-D6-01）。
- **`overdraw`**：勿扰在它之前把级别压到 L2，专注放行 L4，`16` 令牌桶一行与 §8.5.2、§8.5.3 都改为引用。成立。
- **“检验打开期间”**：`10` §10.2、§10.10、§10.11 三处按各自语义同步，`inspect.closed` 补上验收或放弃的来源。成立。
- **`human_checkout.run_prepare`**：命令、前置条件、远程矩阵、`06` 禁止远程一行都已登记。但它把检验检出的沙箱档位搬到了一个**含 Tower 自建 gitdir、且人可能放入机密的目录**，档位的两条前提在这里都不成立：
  - 检验目录不含 `.git`；
  - 检验目录里的机密只经显式开关进入。
  - 由此得到本轮唯一的重要条目 R82-D11-01（H/.git 对 Agent 写的代码可写），以及 R82-D11-02。
- **用户 agentDir**：凭据路径已与用户终端一致。但非隔离模式的 `agentDir`、扩展静态清单与 S2 读允许列表仍按 Host 自己的环境或写死的 `~/.pi/agent` 求值，两者可能不是同一个目录（R82-D5-01）。

**四个自行披露的未决点**：
- **第一个快照之前移出**：可以接受。已在 `10` L742 写成已知限制，评审中文件可见。
- **`safety` 检查点用途的扩展**：取法本身可以接受，landmark 集合不变。但它要求 “当前 pin 的检查点” 有统一的定义，见 R82-D13-01。
- **环境变量只在首次运行读取一次**：可以接受。设置页显示所用路径，人可以核对。记为观察 10。
- **本地 base 下影子 `info/exclude` 的刷新时机未定义**：**不能只留在回应里**。`04` L1313 已把 “在 Tower 下一次获取 base 时生效” 写成给用户的操作说明，而本地 base 在 M1 中只用 `fs.watch` 观测，没有 “获取”；远端 base 一侧的 “每次 fetch 新 base 时” 也有两种读法。见 R82-D13-02。

**全范围扫描**在 ADR-209 之外新发现以下问题：
- 清单变化后 `in_review` 中 Fact 变旧，是否自动回到 `verifying`，三处说法不一（R82-D4-01）；

### D11 安全与自主度

**R82-D11-01｜重要**（`run_prepare` 的写允许含 H/.git：Agent 写的代码可以改写 Tower 自建的 gitdir）

- **问题**：
  - `06` L907 与 `10` L943 规定 `run_prepare` 的档位 “同 `10` §10.8.3 第 3 步（验证器档位）……写允许换为 H 与本次的临时目录”。H 是整个人工编辑检出，其中有 `H/.git`。
  - 检验目录可以直接用这个档位，前提是它 “不含 .git——它不是仓库”（`10` L877）。验证器档位因此没有对 `.git` 的写拒绝。S2 的按名字写拒绝只写给卫星（`11` L350）。
  - 而 H/.git 是 Tower 按模板新建的 gitdir（`10` L946–L948）。正文以它为不变式：
    - “该 gitdir 的全部内容来自 Tower，Agent 从未可写”（`10` L949）；
    - 人工编辑检出存在的理由就是不让人的 IDE 与 shell 对 Agent 写过的 git 元数据运行 git，“正是 R5-D11-01 的攻击面”（`10` L925）。
  - 照 `06` L907 字面实现，项目生命周期脚本与 `VerifyProfile.prepare`（正文称为 “Agent 写的代码”）就能写 H/.git 中的配置与钩子，或在 H 的子目录中造出仓库形态的目录。
  - 人的编辑器、终端中的 git 随后在沙箱外、以人的权限读取它们。这正是 T29 所列 “Agent 可写、沙箱外进程读取的 git 元数据” 这一类后果（`11` L705）。
  - 交还第 5 步排除 “H/.git 自身”（`10` L959），所以这类改动不会出现在任何差异中，人和 Tower 都看不到。
- **为什么是重要**：照正文实现即违反一条明写的不变式，后果是 Agent 影响的内容在沙箱外以人的权限执行。正文已为卫星设计了按名字的写拒绝与 watcher 兜底，`run_prepare` 是 ADR-209 新开的一条绕过路径。
- **文档位置**：`06` L907；`10` L877、L884–L890、L925、L943、L946–L949、L959；`11` L350、L381、L705、L707。
- **期望的回答形态**：在 `06` L907 的档位描述（唯一定义）加一条写拒绝，取以下之一：
  - 写允许为 H 但**拒绝 H/.git 以及 H 中任意深度、名字折叠后为 `.git` 的条目**，复用 `11` L350 卫星已有的按名字拒绝规则与等价变体的 watcher 兜底；
  - 或者把 H/.git 视为 Tower 所有：运行结束后按模板重写或比对，不一致即提示并恢复，同时做一次 §10.3.1 的全量嵌套仓库扫描。
  - `11` T31 或 T29 补一句 `run_prepare` 的缓解措施。

### D5 Agent 架构与 Pi 集成

**R82-D5-01｜次要**（用户 agentDir 只用于凭据，资源目录仍按 Host 环境或写死的 `~/.pi/agent` 求值）

  - `10` L741（ADR-207）：“没有记录可取的比较（归因基线为 `baseCommit`、运行中的观察器指纹与 Fact 新鲜度）取当时的清单，清单变化只会使 Fact 变旧”；I2 则用 pin 记录的 L，所以清单变化不触发 I2。
  - 于是在 `in_review`/`accepted` 中移出或加入一个卫星里存在的路径后，按 L741 的一种读法，Fact 变为 stale 而 I2 不触发。此后去向有两套说法：
    - **自动回到 `verifying`**：`07` L337 “任何一条变为 stale 或 expired 时，状态机执行 I2，回到 `verifying`”；`04` L1529 “过期事实……`in_review`/`accepted` 时回到 `verifying`（I2）”。
    - **不受影响，等下一次 pin**：`10` L184 “`in_review`/`accepted` 中的 Goal 在下一次生成 pin 之前不受影响”；`04` L1313 “加入与移除……不打断正在进行的评审”；G46 (bh)(6) 第八组让 E 留在 `in_review`，由人执行 `retry_verify`；`12` L276–L279 的过期示例（“需重验 ⇧V”，“示例为待验收中的目标”）也只在这条路径下可达。
  - L741 的 “运行中的” 是否同时修饰 “Fact 新鲜度”，本身也有两种读法：只修饰前者时，`in_review` 中的 Fact 按当前清单判定会变旧；同时修饰两者时，`in_review` 中按 pin 的 L 判定不会变旧。
  - 验收又要求没有过期事实（`04` L536）。
- **为什么是次要**：两种实现都不丢数据，但用户可见的行为不同：一种在清单变化后自动重新验证（ADR-209 下还会写一个 `safety` 检查点），另一种停在 `in_review`、验收被挡、等人按 ⇧V。第八组的预期只在后一种下成立。
- **文档位置**：`10` L184、L741；`07` L337；`04` L536、L1313、L1529；`12` L276–L279；`14` L134。
- **期望的回答形态**：在 `10` L741 写明 `in_review`/`accepted` 中 Fact 新鲜度用哪个 L，二选一：
  - 用 pin 记录的 L（与 I2 一致）：清单变化不使 Fact 变旧，直到下一次 pin；`12` 的示例换一个可达的情形；
  - 或用当前清单：写明 “只因清单变化而变旧” 不触发 I2，显示 “需重验 ⇧V” 并挡住验收；`07` L337 与 `04` L1529 加这一例外。

### D6 系统架构与可靠性

**R82-D6-01｜次要**（非回合检查点不记 `checkpoint.created`，而归因窗口按事件序号取检查点）

- **问题**：
  - `10` L732：非回合入口（`agent_bg_done`、`external_change_kept`、`safety`、`human_edit`）“跳过第 0 步与第 7 步”。第 7 步是 “记录事件 checkpoint.created；在 Pi 会话中 `pi.appendEntry(…)`”（`10` L758）。
  - 归因窗口以事件序号界定（`03` L74），实现为 `checkpointsAfterSeq(goal, …, windowStartSeq)`（`07` L1597）。`06` L904 也写 “`human_edit` 检查点的 seq 小于交还决定”。
  - 而 `checkpoints` 表没有序号列（`06` L577–L591），检查点的序号只能来自 `checkpoint.created` 事件。
  - 照字面实现，非回合检查点没有序号，不会被窗口取到。这会同时影响以下几类：
    - ADR-209 的 pin 前 `safety` 检查点（它的 `mixedPaths` 正是为了进入窗口）；
    - `external_change_kept` 检查点（`author:"human"`）；
    - `human_edit` 检查点的先后判定。
  - 结果是验证失败按 Agent 路径自动返工，而这正是 `03` L74 要避免的。
- **为什么是次要**：上下文清楚地表明非回合检查点需要序号，测试 `keep` 与交还的用例会很快暴露字面实现的问题，所以这是一处措辞缺口。但 ADR-209 让窗口对它的依赖又多了一处，宜在唯一定义处写清。
- **文档位置**：`10` L732、L758；`03` L74；`07` L1590–L1599；`06` L577–L591、L904；`16` L659。
- **期望的回答形态**：`10` L732 改为 “跳过第 0 步，第 7 步只跳过 `appendEntry`；`checkpoint.created` 照常记录，窗口以它的序号界定”。

### D8 注意力与交互

**R82-D8-01｜次要**（检验面板的 `[只复制文件]` 与 `授权后检验` 没有命令可表达）

- **问题**：

- **文档位置**：`04` L579、L584、L589、L734；`10` L875、L888；`06` L895、L909；`16` §16.5。

  - `授权后检验` 写明为 “`s0.grant` 成功后，对仍打开的检验补做 §10.8.3 第 3–4 步”：可以是一条新命令，也可以写明顺序 “先 `inspect.close` 再 `inspect.open`”。同时写明它在 `in_review` 中引起的重新验证与检验的关系。

### D13 隔离、git 与并发

**R82-D13-01｜次要**（`claimed` 之后的归因基线写死为 settle 的检查点，与 pin 前的 `safety` 检查点不一致）

- **问题**：
  - `10` L395（归因基线，唯一定义）：“Goal 处于 `claimed` 或之后的状态时，归因基线就是**当前 pin 的检查点**（settle 第 4 步的 `agent_bg_done` 检查点，其树 = pin 的树）”。
  - ADR-209 之后，`in_review` 中移出清单再 `retry_verify` 生成的 pin，与之同树的是 pin 前的 `safety` 检查点。`agent_bg_done` 检查点的树不含该路径 p，它记录的 L 含 p。
  - 照括注实现，基线仍是 `agent_bg_done`。此后若有来源不明的写入改动了 p：
    - 归因表第 4 行按基线记录的 L 比较（`10` L741），p 被排除，E 为空，判为 “内容未变”；
    - I2 按 pin 的 L 比较，看到 p 变了。
  - 于是指纹变了却没有任何可归属的来源，落在 `07` L1673 的 I2 分界之外：
    - 实现者可能把它送进 `verifying`，违反 “来源不明的内容不会先被验证或评审”；
    - 也可能在验收的 `full` 闸口反复不一致（`07` L280）。
  - 同样的问题在 ADR-209 之前就以较弱的形式存在：加入清单后重新生成的 pin，以及 `agent_bg` 重新生成的 pin，都没有同树的检查点。ADR-209 新增了一种 “有同树检查点但不是括注所指的那个” 的情形，使括注的写法直接与新规则冲突。
- **为什么是次要**：触发需要 “`in_review` 中移出清单 → 重新验证 → 再有来源不明的写入改动同一路径”，路径窄，也不丢数据。但两种实现给出的状态去向不同。
- **文档位置**：`10` L395、L402、L741、L742；`07` L280、L1673；`06` L906；`15` L865。
- **期望的回答形态**：把 L395 的括注改为定义：“当前 pin 的检查点 = 树与记录的 L 都等于当前 pin 的最近一个检查点”，括注只举例（settle 的 `agent_bg_done`、ADR-209 的 pin 前 `safety`）；没有这样的检查点时取 pin 本身（按它记录的 L 比较），与 L395 末句 “没有任何检查点时为当前 pin” 合并。

**R82-D13-02｜次要**（影子 `info/exclude` 的刷新时机：远端两读，本地 base 没有定义）

- **问题**：
  - `10` L183：影子创建时复制用户的 `.git/info/exclude`，“并在**每次 fetch 新 base 时**刷新”。
  - ADR-209 把 “让它不再被 git 忽略（只经 `info/exclude` 忽略的，在下一次刷新后生效）” 写成了用户操作说明：`10` L184；`04` L1313 写为 “在 Tower 下一次获取 base 时生效”。
  - G46 (bh)(6) 第八组的预期依赖 “点一次 ‘检查 base’ 即刷新”。
  - 但：
    - “每次 fetch 新 base 时” 可以读成每次获取，也可以读成获取到新提交时。远端没有新提交时，第八组的预期在后一种读法下不成立；
    - 获取之后定义的动作只有 base 前进检测与 `integrated` 观测（`10` L109，`06` L887），没有写刷新；
    - 获取按（镜像，远端，分支）合并（`10` L104），刷新作用于哪些 Goal 的影子没有写；
    - **本地 base**（M1 中常见）只用 `fs.watch` 观测引用移动（`10` L1084），不存在 “获取”；`goal.base.check` 只对远端引用执行（`06` L887）。
    - 所以本地 base 的项目照 `04` L1313 操作后，文件要等到 base 前进才可能进入，或者永远不进入。回应把这一点列为未决，但正文没有说明。
- **为什么是次要**：不丢数据，文件在人的检出中原样存在。但用户可见的结果（文件是否出现在 Goal 中）取决于各家选的刷新时机，第八组的通过与否也取决于此。
- **文档位置**：`10` L104、L109、L183、L184、L1084；`06` L887；`04` L1313；`14` L134。
- **期望的回答形态**：在 `10` L183 写明刷新时机，取以下之一：
  - 每次 `goal.base.check` 与每次 base 观测（远端获取完成，不论有无新提交；本地 base 的 `fs.watch` 事件），对该项目全部活跃 Goal 的影子刷新；
  - 或更简单：每次快照前从用户仓库读取 `.git/info/exclude`（纯数据，按 §10.1.3 的只读规则）。
  - 同步 `04` L1313 的文案；若保留只在获取时刷新，`04` L1313 写明本地 base 下的情形。

  - **不扣分的观察**：
    1. **机会式 pin 与 pin 前的 `safety` 检查点**：`10` L742 只豁免 settle 的 pin。按字面，运行中的机会式 pin（`07` L376）同样先写 `safety` 检查点，这是合理的。宜写明一句，并写明两者在同一次 `wtLock` 内以同一个 T 写出，免得实现者在中间重新 `add -A`。
    2. **`safety` 的 ref 命名**：`10` L245、L832 与 `16` L289 写 `refs/tower/<goalId>/safety/<k>`，§10.7.1 第 5 步对一切检查点写 `cp/<n>`。ADR-209 之前已有，但现在 `safety` 检查点承载 `mixedPaths`，必须在检查点链与 `checkpoints` 表中。宜统一为 “`cp/<n>`，landmark `safety`”，或写明 `safety/<k>` 只是同一提交的别名。
    3. **`run_prepare` 产物的归属**：`06` L907 规定产物 “交还时与人的修改一样” 判定。准备脚本若改动被跟踪的文件（如提交进仓库的代码生成结果），这些内容在评审中显示为 “你”，seal 写 `Tower-Human-Edit`。Tower 自己知道这些写入来自它启动的 Agent 代码。可以在运行前后各取一次 H 的树，把变化的被跟踪路径在交还时记入 `mixedPaths`（同 `07` L1671 的并发规则），或者在 `00` §0.5.1 与交还对话框中写明这一取舍。
    4. **`08` L267**：“透支期间同一 Goal 的其他 severity 2 条目一律只进收件箱”，而同一 Goal 的第二个单向门审批按 `overdraw` 可以透支。宜加 “（单向门审批除外）”，与 L251、L257 一致。
    5. **经交还首次收入的移出路径**：人在接管期间把一个播种的文件移出清单、在 H 中修改并交还时，`human_edit` 检查点是首次收入它的快照，按 `10` L742 记为 `mixed`，不是 `human`，也不写 `Tower-Human-Edit`。这是保守的一侧，但与 ADR-209 “`Tower-Human-Edit` 的既有规则不变” 的说法略有出入。可对人工决定类入口豁免，或在 L742 注明。
    6. **`run_prepare` 的其他边界**：
       - “运行中交还或放弃改动时先终止它” 没有覆盖 `goal.abandon`、退出应用与崩溃重启（`06` §6.1.6 没有对应行）。按常理应一并终止，宜写明；
       - 它的 `E_BUSY` 情形不在 `16` L293 的举例中；
       - G37 只测成功路径，没有测前置条件、S0 未授权、远程 ✗ 与写拒绝（若按 R82-D11-01 补上）。
    7. **`07` L167 的 `eligible()`**：没有 “检验打开期间” 的条件（唯一定义在 `10` L906）。`running` 中检验仍打开是可达的：检验可从 `paused(verify_failed_limit)` 打开，随后恢复。机会式验证不改动卫星，影响只是多用槽位。宜在伪代码中加一行引用。
    8. **措辞**：`05` L1317 “凭据写入用户的 `~/.pi/agent/auth.json`” 与 `04` L1453 的 `~/.pi/agent` 宜写为 “用户 agentDir（默认 `~/.pi/agent`）”，与 R82-D5-01 一起改。
    9. **其他按钮与用例**：
       - `04` L1308 本地文件建议的 `[忽略]` 没有命令或持久化，重启后会再次出现；
       - G36c (b)（`14` L123）与 `06` L914 在 M1 的预期中写 “合并队列条目移除”，M1 没有合并队列，这句是空操作，宜标 M2。
    10. **未决点的判断**：
        - 第一个快照之前移出：可以接受；
        - `safety` 用途的扩展：可以接受，需配合 R82-D13-01；
        - 环境变量只读一次：可以接受。设置页显示路径，宜在设置页提供 “重新检测”，或注明修改后需重新运行首次检测；
        - 本地 base 的刷新：见 R82-D13-02。
    11. **回看的成本**：`10` L742 的判定要知道 “此前任一快照记录过、本次不在 L 中” 的路径集合。按 Goal 增量维护即可，不必每次扫描全部 trailer。`13` 没有它的预算，宜在 §13.11 的检查点一行注明 “增量维护，O(清单大小)”。
- **设计是否完成：ADR-209 正确地关闭了第 81 轮的五条条目。** 回看判定与 pin 前的 `safety` 检查点、`overdraw`、检验打开期间的定义都成立，没有引入状态机或机密投递上的回归。
  - 本轮唯一的重要条目来自 ADR-209 新增的 `run_prepare`：它复用了检验检出的沙箱档位，而那个档位的安全性依赖 “目录里没有 `.git`、机密只经显式开关进入” 两条前提，在人工编辑检出中都不成立（R82-D11-01、R82-D11-02）。
  - 其余 8 条次要条目分三类：
