## 1. 总评

**第 110 轮的 6 条条目在所问的范围内都已改写**（核对见 §3）：
- 必需路径只有根，根之下的目录按所在的根判定；
- 失败先判可达按根，判为中断时该 Goal 同时不可达；
- 写回中断时放弃先写 `handback-t1`；
- 路径丢失确认按记录判定、`syncing` 时 `E_STATE`；
- `relocatedFrom` 只在位置改变时写入，迁回改名保留，合并取并集；
- 清除遗留清单只存 `[{wtRoot, at}]` 并先于事务落盘；
- `tool_result` 脱敏处理器 fail-closed；
- base 运行的环境错误按无结论。

第 110 轮 §5 的 10 条观察都已落地。其中观察 1 的落法带出本轮的 R111-D5-01。

**ADR-238 的 T1 保护落得太晚**。本轮唯一的重要条目：
- T1 在写回开始时写进影子对象库，但直到放弃之前，没有任何 ref 引用它（`06` L923 自己写明它在 ③ 之后是 “影子中不被引用的对象”）。
- 影子 gc 以 2 周宽限回收不可达对象（`10` L1306，`16` L879），只涉及 `~/.tower`，所以在该 Goal 不可达期间照常运行（`06` L139 ③）。
- `handback-t1` 只在放弃时写入。而它要保护的情形正是 “外接盘丢了”，你通常要过一段时间才会确认这一点并放弃。
- 不可达超过两周后：
  - T1 的对象可能已被回收；
  - 放弃时写 `handback-t1` 失败，失败时怎样处理没有写；
  - 即使盘回来，续写也会因缺对象而失败。
- 另外：
  - `handback-t1` 在放弃 180 天后随影子自动删除，确认框的 “Tower 保留一份” 没有写期限；
  - 清除该 Goal 会删除它，确认框不提；
  - 写回失败 ① 的物化也失败时，T1 照旧在 gc 宽限后丢失。
- 见 **R111-D13-01（重要）**。

**扫描发现的其他缺口**：
- **R111-D13-02**：Tower 自己会重建一个缺失的根：
  - 新 Goal 的 `git clone --separate-git-dir` 会建立上级目录；位置算法也写着 “若可创建”。这会把其他 Goal 从 “不可达” 翻成 “确实不在”，按丢失处理。
  - 情形 F 在新根上重建时，新根何时成为必需路径没有写，“没有无人续做的中断” 依赖这一未写的次序。
- **R111-D13-03**：
  - 一个写回中断的 Goal 使整个 Project 的 `project.relocate` 返回 `E_STATE`，界面却仍把迁移列为出口；
  - 迁移重建与 ③ “不重建” 的关系没有写。
- **R111-D5-01**：
  - “任一 tower-goal 处理器正常完成一次即清零” 使持续失败的单个处理器几乎永远到不了 3 次：`turn_start`、`turn_end` 与 gate 在两次失败之间照常完成；
  - 自报的 `sentinel` 没有检测器 id，去重键无定义；
  - `08` L416、L761，`06` L1199，`16` L196，`04` L980 的 `prepare_failed` 来源都漏列 F13。
- **R111-D11-01**：脱敏（含 fail-closed 占位结果）不处理 `details`。截断时其中是原始输出文本，随会话写入并被 Observer 读取；C5 的 “会话中没有原文” 照文字不成立。
- **R111-D7-01**：
  - `flake` Fact 在中断判定之前写入；
  - base 物化的确定性失败每次都按 “改动引入” 计返工，可推到 `verify_failed_limit`，与 “环境故障不计返工” 相反；
  - 准备与服务以非零退出失败时不判可达。
- **R111-D15-01**：
  - `06` L921 末句仍写 “人工编辑检出仍按原路径作为必需路径”；
  - `10` L42 无条件写 `relocatedFrom`；
  - `10` L257 “只有四处” 漏了情形 F 的改名；
  - `06` L1138、`16` L861、`09` L492 的保留期摘要漏了 `handback-t1`；
  - `14` L120 G35e 的期望 “没有 `verify.result` 与 Fact”。

**对本轮重点问题的回答**：
- **(a) 根的规则**：
  - **各类路径**（逐类核对）：
    - 附着检出与 `<wtRoot>` 是根；
    - 卫星、`_gitdirs`、验证槽位按所在 `<wtRoot>`；
    - 人工编辑检出按它所在的 `<wtRoot>`，迁移之后取 `relocatedFrom` 中的旧根；
    - 检验目录按 `inspect` 记录所在的 `<wtRoot>`；
    - 接管物化与 ① 的重新物化按卫星或 `human_checkout` 所在的根。
  - 这些根在失败时都是该 Goal 的必需路径，“判为中断时该 Goal 同时不可达” 成立。例外有两个：
    - 情形 F 的新根（R111-D13-02）；
    - 回退位置在 `~/.tower` 中的 `<wtRoot>`（观察 1）。
  - 第 110 轮的死分支都已可达：`human_checkout_lost`、① 的重新物化、写回中卫星消失、重建失败，G31 的三组新期望与之一致。
  - 新的孤儿或误判来自 “根本身是否存在由谁决定”：Tower 重建根（R111-D13-02）。
  - “被删除与卷未挂载一样由你处理” 只在 Tower 不替你重新建立根时成立。
- **(b) `handback-t1`**：
  - ref 本身在影子 gc 与镜像 gc 中都受保护：它属于 `refs/tower/<goalId>/*`，镜像 gc 前同步为 `refs/tower-live/<goalId>/*`（`10` L1319）。清除时随影子删除。Agent 不可读影子。
  - 问题在写入之前与到期之后，见 R111-D13-01。
- **(c) `relocatedFrom`**：
  - 写入条件、去重、迁回时移除与 A → B → A 的 `.kept-*` 改名都已写，合并与拆分成立；
  - 改名一处与 `10` §10.2 “只有四处” 相矛盾（R111-D15-01）；
  - 迁移整体被单个 `syncing` 的 Goal 挡住（R111-D13-03）。
- **(d) 清除遗留清单**：最小内容、写入次序、`all` 档与移除都成立。遗留根之下不属于 Goal 形状的 Tower 目录不在列出范围内，记为观察 6。
- **(e) 占位结果**：模型侧成立（见上方 “经复核不成立”）；`details` 不在其中（R111-D11-01）。
- **(f) base 无结论**：不写台账、判为 `introduced` 成立；但它计返工，并且 `flake` Fact 早于中断判定写入（R111-D7-01）。
- **(g) F13**：
  - 第三次以 `prepare_failed` 暂停，在 `02`、`03`、`12`、`16` §16.1.1 中一致，`16` L31 的 “交还即解除” 也覆盖它；
  - 但复位规则使 “第三次” 对持续失败几乎不可达，且 `08`、`06` F4b、`16` §16.1.7、`04` §4.8.11 没有同步来源（R111-D5-01）。

### D5 Agent 架构与 Pi 集成

**R111-D5-01｜次要**（F13 “任一处理器正常完成一次即清零” 使持续失败的单个处理器几乎到不了 3 次；自报的 `sentinel` 没有检测器 id；`prepare_failed` 的来源清单多处漏列 F13）

- **问题**：
  - **(a) 复位规则**：
    - `05` L1062 写 “同一 Goal 的任一 tower-goal 处理器正常完成一次即清零”，连续 3 次以 `prepare_failed` 暂停，“不会在 gate 失效的情况下继续运行”。
    - Pi v1.2.0 中，每个 turn 都经 `turn_start` 与 `turn_end`。被阻断或抛出的 gate 调用是立即结果，不经 `afterToolCall`，也就不经 `tool_result`（`agent-loop.ts:600-613, 744-776`）。于是持续失败的情形是：
      - **`turn_start` 每次都失败**：两次失败之间总有 `turn_end` 与 gate 正常完成，计数永远是 1。`05` L1006 登记的 “这一次请求可能仍带已注入的密钥，窗口延续到下一次 `turn_start`” 原本是有界的残余，在这里变为无界。
      - **gate 每次都失败**：只有一条助手消息含 ≥ 3 个工具调用时才到 3。否则 Agent 在全部工具被阻断的状态下一直运行，直到预算或停滞检测介入。
      - **脱敏处理器每次都失败**：顺序模式下下一次 gate 即复位。并行模式（默认，`agent.ts:253`）下同一消息的 gate 先跑完，所以要同一消息中 ≥ 3 个被执行的调用才到 3。否则每个结果都被隐去，Goal 不暂停。
    - 只有 “全部处理器同时失败” 或 “同一消息中 3 次失败之间没有别的处理器” 时，第三次才会出现。C5（L1467）只断言了单次抛出。
  - **(b) 自报条目没有身份**：
    - 每次自报生成一条 Needs-You `sentinel`，severity 3、L3（`05` L649、L1062，`06` L1208）。

    - 于是它是 “每次一条 L3”（与 (a) 叠加即是持续的打断），还是合并为一条，没有定义。`08` §8.8 的出口分类同样没有。
  - **(c) 来源清单**：
    - `02` L160、`03` L98、`12` L435、`16` L29 已补 “tower-goal 的处理器连续 3 次出错”。
    - 但以下几处没有：

      - `08` L761（`stalled{prepare_failed}` 的证据）；
      - `06` L1199（F4b）；
      - `16` L196（§16.1.7 `stalled` 子类型）；

- **为什么是次要**：

- **后果的类别**：

### D7 诚实与验证

**R111-D7-01｜次要**（`flake` Fact 早于中断判定写入；base 物化的确定性失败每次都按 “改动引入” 计返工；准备与服务以非零退出失败时不判可达）

- **问题**：
  - **(a) 写入次序**：
    - §7.4.6 在 `runCriterion` 内部 `recordFact({kind:"flake", …})`（`07` L874–L875），而失败先判可达在 `runCriterion` 返回之后（`07` L467）。
    - base 运行因槽位所在的根不可访问而无结论时，用例判为 `introduced`、标准为 fail，随后 L467 判为中断。这时一条 `origin:"introduced"` 的 `flake` Fact 已经写下。
    - 这与 `06` L139 ②、`07` L501 的 “不写该条标准的 Fact 与 `verify.result`” 相反（观察 4 只保留此前各条标准的 Fact）。§7.4.5 的 `flake{kind:"timing"}`（`07` L845）同此。
  - **(b) 无结论计返工**：
    - 无结论 → `introduced` → verdict `fail` → 自动返工并计次，`maxReworkCycles` 后进入 `verify_failed_limit`。
    - 无结论的来源包括 “检出或物化失败”“运行器没有给出该用例的结果”（`07` L871–L872）。这些在 base 上常是确定性的，例如 base 的依赖已无法安装。而无结论不写台账（L873、L882），所以每次验证都重复。
    - Agent 收到的是 “base 上的确认未能完成（环境错误），按改动引入处理”，它无法修复。
    - 这与 `07` L789 “安装器失败……不计入返工次数，因为问题在环境而不在 Agent 的代码”、L847 “base 上同样超时……改记 `verify_env_error`，不返工、不计次数” 的原则相反。
  - **(c) 准备与服务的非零退出**：
    - `07` L458、L462 只在 `isFsError(env.error)` / `isFsError(svc.error)` 时先判可达。
    - 生命周期脚本、`VerifyProfile.prepare`、setup 与健康检查都是子进程。卷消失时它们通常以非零退出，不是 Tower 自己的文件系统错误码。
    - 结果是 `verify_env_error`：Goal 进入需要手动重试的暂停，而不是 ② 所写的 “可达后以同一 pin 重跑”。
- **为什么是次要**：
  - (a)(c) 要求卷在验证的特定阶段消失；(b) 要求 pin 上有一个时过时不过的测试，同时 base 上的环境确定性失败。
  - 后果是多一条事实、多几次返工或多一次点击，没有错误的绿色。但 (b) 违背了 §7.3 自己写下的 “环境故障不归 Agent” 原则，会把 Goal 推到 `verify_failed_limit`。
- **后果的类别**：
  - 已中断的验证留下该条标准的 `flake` Fact；
  - Agent 因无法修复的 base 环境问题反复返工，直到 `verify_failed_limit`；
  - 卷短暂消失时验证停在 `verify_env_error`，不会自动重跑。
- **文档位置**：`07` L458、L462、L466–L467、L501、L789、L845–L847、L866–L882；`06` L139 ②。
- **期望的回答形态**：
  - `flake` Fact 与 `criterion_check` 一样，在 L467 的判定之后写入（或由 `runCriterion` 返回、由调用者写）；
  - 无结论时该标准不计返工：记 `verify_env_error{stage:"baseline"}`，或保留 `introduced` 但不计次数，并在返工消息与卡片上写明；
  - L458、L462 对非零退出同样先判可达（与 L467 对标准的写法一致）。

### D11 安全与自主度

**R111-D11-01｜次要**（脱敏，含 fail-closed 占位结果，只处理 `content` 与 `structuredContent`，不处理 `details`：截断输出的原文与 `edit` 的差异随会话写入，并被 Observer 读取）

### D13 隔离、git 与并发

  - **(a) 写入之前**：

  - 情形 F 写明：新位置的 `WorktreeRecord`（`rebuilding` 状态）与 `satellite_rebuilding=1` 在迁移的同一事务中写入，所以新根从此是必需路径，中断由 ④ 续做；`worktreeRoot` 不可访问时迁移返回 `E_STATE`。

**R111-D13-03｜次要**（一个写回中断的 Goal 使整个 Project 的 `project.relocate` 返回 `E_STATE`，界面却仍把迁移列为出口；迁移重建与 ③ “不重建” 的关系没有写）

- **问题**：
  - **(a) 被单个 Goal 挡住**：
    - `06` L921：“受影响的 Goal……`human_checkout.syncState='syncing'` 而写回已不在进行时 `E_STATE`”。命令作用于整个 Project 的一组 binding，所以只要其中一个 Goal 是中断的写回，整个迁移都失败。
    - 附着检出所在的盘永久丢失时，这组 Goal 都不可达。其中一个在写回中断，其余 Goal 就只能等你先放弃它。
    - 回应登记的是 “这个 Goal 只能放弃”，没有登记它挡住其他 Goal。
    - `12` L416 与 `04` L1522 仍把 “项目设置中的迁移” 列为不可达期间的出口；错误文字 `写回未完成：可达后自动续写，或放弃该目标` 也没有指出是哪个目标。
  - **(b) 迁移重建与 ③**：
    - ③ 写 “不可达期间……不重建”。迁移之后，若 Goal 的人工编辑检出或检验检出仍在旧根上，该 Goal 仍不可达（`06` L921 “`inspect`、`human` 角色仍在使用的照旧”）。
    - 这时情形 F 在新根上的重建是照常执行，还是按 ③ 推迟，没有写。
    - 若推迟并置 `satellite_rebuilding=1`，使该 Goal 恢复可达的路径丢失确认 `goal.discard_human_edits` 又被卫星守卫挡住（`06` L914 “`satellite_rebuilding=1` 或 `satellite_missing` → `E_STATE`”），只剩放弃。
- **为什么是次要**：
  - (a) 有出口：先放弃那个 Goal，T1 按 R111-D13-01 修订后保存；(b) 的意图大概率是照常重建。
  - 但照文字，(a) 让界面给出的出口失效、错误文字不指向原因；(b) 会让实现分叉。
- **后果的类别**：
  - 盘永久丢失后，同一 Project 的其他 Goal 在你放弃某一个之前都无法迁移；
  - 迁移后某些 Goal 停在只能放弃的状态。
- **文档位置**：`06` L139 ③、L914、L921；`12` L416；`04` L1522；`10` L1264–L1267。
- **期望的回答形态**：
  - 迁移跳过 `syncing` 的 Goal（它们保持原 binding、仍不可达，结果中列出），其余照常；或者保留 `E_STATE`，但错误文字列出这些 Goal，卡片在这时不列迁移；

### 不扣分的观察

1. **回退位置的 `<wtRoot>`**：`06` L139 写 “`~/.tower` 中的路径（影子，以及位于 `~/.tower` 之内的验证槽位）不在本行判定之内”。回退位置 `~/.tower/worktrees/<projectId>.noindex`（`10` L239）字面上也在 `~/.tower` 中，却不在括注里；写回与重建的失败先判可达也没有 “位于 `~/.tower` 时不判定” 的一句（验证一支有）。`~/.tower` 不可访问时 Tower 本身无法运行，后果为零，宜补半句。
2. **接管物化的中断**：失败先判可达把接管物化判为中断时，“可达后由 ④ 与对应的恢复行续做”，但没有接管物化的恢复行，命令的返回也没有写。§6.8 F8 一支写了（`06` L1203 “命令返回 `E_STATE`”）。中断的接管留下的目录已由 `10` L255 处理，不丢数据，宜补一句。
3. **占位结果的副作用**：
   - `isError: true` 可能使模型重跑有副作用的命令（模型不知道命令其实成功了），宜在占位文字中写 “命令已执行，结果被隐去”；
   - 若 `tower.obs` 由同一处理器写，出错时这一次的 `exitCode` 丢失。占位结果带 `structuredContent`，所以 `structured_content_dropped`（`05` L1085）不会触发，这一次的 `command_result` 只缺一条，宜登记。
4. **`handback-t1` 不进备份 bundle**：bundle 只为非终态 Goal 维护（`10` L1276），放弃时写入的 `handback-t1` 不在其中。影子被外部删除时（情形 B）这份 T1 没有第二份。宜在放弃时补一次 bundle，或如实登记。
5. **`goal.resurrect` 与带回的措辞**：
   - 误放弃的出口是复活为新 Goal（`06` L942、L944），从 `draft` 开始，`handback-t1` 不随之带入，宜在目标页的取回说明中写明；
   - 确认框写 “交还的改动”，但同一规则也适用于从 `in_review`/`accepted` 放弃的中断带回，宜写 “交还或带回的改动”。
6. **遗留根之下的非 Goal 目录**：`10` L259 的列出范围只含 `<goalId>`、`_gitdirs/<goalId>`、`_stores/<goalId>` 与 `_verify/slot-<k>`。清除时不可访问的根重新可访问后，`_stores/_shared`、`_stores/_verifier`、`_stores/_shim` 与 `README` 不在列出之列，条目在 Goal 形状的目录删完后即移除，这些目录随之不再被追踪。它们不含目标内容，只占磁盘，宜在 “清理工作目录” 中一并列出，或如实登记。
7. **`02` L160 的来源清单**：漏列 Host 启动自检、全局根查询与 “读到无效的 Pi 设置” 三个来源（`03` L98、`16` L29 有）。这在 ADR-238 之前就是如此，与 R111-D5-01 (c) 一起对齐即可。
8. **`16` L659–L660 的现行列**：第 108、109 轮两行的 “现行” 一列仍写 “必需路径（附着检出、`<wtRoot>`、人工编辑检出）” 与 “只判定该操作实际读写的路径”，没有 “由 ADR-238 改为……” 的注记（`16` L520 有这种写法的先例）。它们在历史表中，L661 已更正，宜补注记，免得被当作现行规则引用。
9. **Pi 引文细节**：`runner.ts` 的 catch 块为 `:1223-1232`；`parseHttpIdleTimeoutMs` 到 `:35` 结束。结论不变。
