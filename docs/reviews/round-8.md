>   1. 一个目录只含 `HEAD` 与一个 `commondir` 文件、本身**没有** `objects/` 与 `refs/`，git 仍把它识别为仓库（对象与 ref 按 `commondir` 指向处查找）。

>   3. 对照项（不构成问题）：上述两种目录在注入 `safe.bareRepository=explicit` 后都被拒绝——ADR-096 的主防线对它们有效。

## 1. 总评

第 7 轮的两条实测前提问题都已实质处理：

- ADR-096 让 Tower 构造的所有沙箱外 git 环境注入 `safe.bareRepository=explicit`，本轮对照核对确认它对各种裸仓库变体都有效。
- ADR-097 用垫片 exec-path 覆盖 git 派生的子进程，有实验、有备选方案、有预留工作量，G20 不再阻塞冻结。

ADR-098、ADR-100 与 ADR-092 修订注把运行器身份、安装期共享缓存、Tower 对 gitdir 的最后一处 git 调用都收口了。

本轮没有阻断级问题。新问题主要来自 ADR-096 与 ADR-099 的边角：

- **ADR-096 的嵌套仓库定义比 git 的识别规则窄**：它漏掉 `commondir` 与符号链接 `HEAD` 两种变体，而 Tower 控制范围之外的环境（用户的 shell 提示符、IDE、集成后的主检出）只能靠这道扫描兜底。同一扩展又会误伤那些在 base 中跟踪了裸仓库夹具的项目。
- **ADR-099 交还时清除 `sentinel_high`**：前提是“新 pin 会重新判定”，但并非每个阻断检测器都能从 pin 重新得出。另外，“交还后仍暂停”时人的选择没有落地。
- 第 7 轮 lint 未决项 U1 的裁决只同步到 `06`、`10`、`15`，没有同步到 `03`、`04`、`16`。

### D2 Pi 哲学契合度

**R8-D2-01｜次要**（R7-D2-01 的残留，加上新问题）

- **问题**：
  - **(a) 文档互相矛盾**：
    - `05` L387 把 settings 中的自定义技能路径列为“不在列表中、不可用”，而 ADR-100、`11` L333、`00` L89、`14` A11(c) 都写它们可读。
    - `05` 声称临时包 `~/.pi/agent/tmp/` 已登记在 `00` §0.5.1，实际没有。
  - **(b) 扩展提供的技能**：Pi v1.2.0 的扩展可以通过 `resources_discover` 事件返回 `skillPaths`（`core/extensions/types.ts` L725–733），这些技能通常位于扩展目录之内。`11` L333 同时规定了两件事：
    - Host 枚举到的已启用技能 `baseDir` 加入读列表；
    - `~/.pi/agent/extensions/**` 不可读（A11(e) 要求读取扩展的 `config.json` 被拒绝）。

    当技能的 `baseDir` 就在某个扩展目录内（甚至就是扩展根目录）时，哪条规则优先没有定义：要么这类技能失效，要么扩展的配置或密钥变得可读。
  - **(c) Pi 清单声明的技能目录**：Pi 包可以在 `package.json` 的 `pi.skills` 中声明任意子路径（`pi-manifest.ts`、`package-manager.ts` L2241–2250），目录名不一定叫 `skills`。`11` 依靠“Host 枚举 `baseDir`”覆盖了这种情况，但 ADR-100 正文与 `16` §16.1.10 只写了 `{skills,prompts}` 通配，单一来源不完整。
  - **(d) `safe.bareRepository` 的副作用范围**：注入 Host 及其派生进程后，用户扩展与 MCP 服务器在**任何**裸仓库中（不只是卫星中）以工作目录方式运行 git 都会失败。`00` §0.5.1 与 K22 只登记了“在卫星中看不到仓库”。
- **为什么重要**：“你的扩展与技能照常生效”是 README 第 8 点的承诺；能力差异必须在 §0.5.1 中如实、完整地登记。
- **文档位置**：`05` L387；`11` L30、L333；`15` ADR-100；`16` §16.1.10；`00` §0.5.1 L80–90；`14` A11、K22。
- **期望的回答形态**：
  - 改正 `05` L387。
  - 在 §0.5.1 登记临时包，以及扩展环境中裸仓库的行为变化。
  - 规定“扩展目录内的技能 `baseDir`”的处置，二选一：只加入 `baseDir` 本身、并对扩展目录中的其余文件保持拒绝；或者登记为不可用。
  - A11 增加一个 `resources_discover` 技能用例。

### D3 论证与证据

**R8-D3-01｜次要**

- **问题**：两处事实陈述比证据宽：
  - ADR-096 与 `10` L28、L74、`11` L340 把“git 会识别为仓库的目录”陈述为“同时含 `HEAD`、`objects/`、`refs/`”。git 的判定还会经由 `commondir` 查找对象与 ref，并接受符号链接形式的 `HEAD`（本轮已核对）。`10` L28 据此写出“两者合起来，S2 下沙箱外的 git 在卫星的任何子目录中都发现不到仓库”，这一结论只对 Tower 构造的环境成立。
  - ADR-099 以“新 pin 会重新判定”为理由，清除与 pin 绑定的原因。但没有逐个检测器论证“可从 pin 重新得出”（见 R8-D7-01）。
- **为什么重要**：这两条陈述都是后续安全与诚实设计的前提。
- **文档位置**：`15` ADR-096、ADR-099；`10` L28、L74；`11` L340。
- **期望的回答形态**：
  - 把“git 识别为仓库”的判定写成与 git 的实际判定等价的规则，并注明对照的 git 版本。
  - `10` L28 的结论限定为“Tower 构造的环境”。
  - ADR-099 附上逐检测器的可重算性表（与 R8-D7-01 合并回答）。

### D4 领域模型与生命周期

**R8-D4-01｜重要**

- **问题**：ADR-099 有三处转移语义没有落地。
  - **(a) “人的选择记为待执行”**：`10` L593 规定，交还后仍有保留原因时，Goal 留在 `paused(<保留原因>)`，人的选择记为待执行。但：
    - `02`、`06` DDL、`16` 中都没有对应字段。
    - 何时执行没有定义：是保留原因解除时自动执行，还是只作为下次的预选项？
    - 按 `06` L776，`budget_hard_cap` 在 `extend_budget` 之后 `resume` 会分派为 `run.requested{resume}`。如果人在交还时选的是“直接重新验证”，结果就会开出一个人没有要求的 Agent Run，而人的改动一直没有被验证。
    - 保留原因清单中有 `app_quit`。但交还本身就是人在场的显式操作，以 `app_quit` 继续暂停没有意义。
  - **(b) 合并队列的重新入队**：`10` L562、`04` L563 写“交还后重新入队”，`06` L781 写“交还或放弃后重新入队并保留原位置”。可是交还后 Goal 去的是 `running` 或 `verifying`，不是 `accepted`。只有从 `accepted` 接管后放弃改动、且树未变，才会回到可入队状态。“保留原位置”在 Goal 已经离开 `accepted` 后还是否成立，也没有定义。
  - **(c) 放弃改动时原因已经消失**：`06` L784 规定 `takeover_from='paused'` → `also_applies` 中最高者成为 `pause_reason`。若接管期间原原因已解除（例如在 `paused(human)` 期间 `extend_budget`），`also_applies` 为空，去向未定义。
- **为什么重要**：这三处都是 `transitions.ts` 必须实现的边。(a) 会在未经人要求时开 Agent Run，违背 ADR-099 自己“不在用户未要求时开 Run”的承诺。
- **文档位置**：`10` §10.8.4 L562、L579、L593；`06` L776、L781–784、DDL；`02` §2.4；`16` L27；`04` §4.6.7 L563、L582；`15` ADR-099。
- **期望的回答形态**：
  - (a) 二选一：
    - 持久化 `pendingHandBack: {mode}`，规定保留原因解除后 `goal.resume` 按它分派（`reverify` 不开 Run）；
    - 或者规定保留原因只阻挡“交给 Agent 继续”，“直接重新验证”不受预算类原因阻挡（验证不消耗 LLM 预算，`03` L70 已有此理由）。
  - (a) 把 `app_quit` 移出保留清单。
  - (b) 写明：只有 Goal 回到 `accepted` 时才重新入队，并说明位置规则。
  - (c) 写明 `also_applies` 为空时的去向，例如 `paused(human)`，由人显式继续。
  - `03` §3.2.1 同步。

### D6 系统架构与可靠性

**R8-D6-01｜次要**

- **问题**：`inspect.bring_back`（`06` L791、`10` L550–553）与 `hand_back` 一样，都是“检查点 → 逐文件写回卫星 → 检查点 → 转移”，却没有 R7-D6-01 为 `hand_back` 补上的保护：
  - **(a) 中途崩溃**：没有 `syncing` 标记与 `written` 清单，`06` §6.1.6 也没有对应的恢复行。重启后卫星处于写了一半的状态，Goal 仍为 `in_review`/`accepted`。I2 监视会把这个半成品当作 `fp_changed_human` 送去验证；而重新带回的前提“卫星树等于 T_pin”已不成立，命令只会返回冲突。
  - **(b) 与 I2 监视的竞态**：`in_review`/`accepted` 期间，Supervisor 的文件监视对任何内容变化都会触发 I2（`10` L369）。`bring_back` 自己的写入会同时触发它，两条转移（`verifyOrigin: human_change` 与 `fp_changed_human`）的先后与去重没有定义。`hand_back` 没有这个问题，因为它从 `paused(human)` 出发。
- **为什么重要**：这是一条新的写卫星路径，可靠性规则应该与 `hand_back` 一致。
- **文档位置**：`06` §6.1.6 L136、§6.4.3 L791；`10` §10.8.3 第 7 步、L369。
- **期望的回答形态**：
  - `bring_back` 复用 `hand_back` 的 `syncState` 机制，并在 §6.1.6 增加恢复行。
  - 写回期间持有 `wtLock` 并抑制该 Goal 的 I2 触发，完成后以单一事务转入 `verifying{human_change}`。

### D7 诚实与验证

**R8-D7-01｜重要**

- **问题**：ADR-099 规定，交还时 `also_applies` 中的 `sentinel_high` 一律清除，理由是“新 pin 会重新判定”。但 `07` §7.10.1 的阻断检测器分两类：
  - **可从 pin 重新得出**：`protected_path`、`dep_added`、迁移、diff 中的密钥、`nested_repo`、`lifecycle_script_changed`、`runner_tampered` 等；
  - **由运行过程产生、无法从 pin 重新得出**：`input_mutated_after_gate`（门禁放行后输入被改，severity 3，阻断）。

  `decide` 以 `openSentinels(goal, pin)` 取阻断项（`07` L1304）。如果后一类事实绑定在旧 pin 或旧 Run 上，那么只要“接管 → 任意小改 → 交还（直接重新验证）”，新 pin 上就没有这条哨兵，Goal 可以不经 `override_sentinel`（要求结构化原因，`03` L74）进入 `in_review`。
  - 对可重算的哨兵，同一 `(detector, subject)` 的已覆盖状态如何随新 pin 延续，也需要明确（`07` §7.10.2 第 3 条只按 hunkHash 处理）。
- **为什么重要**：“覆盖阻断哨兵必须留下结构化原因”是诚实语法的一部分。人工交还不应成为一条不留痕迹的旁路。
- **文档位置**：`15` ADR-099；`06` L782；`10` L591–592；`04` L582；`07` §7.10.1 L1260、§7.10.3 L1304、L1319。
- **期望的回答形态**：
  - 为 §7.10.1 的每个阻断检测器标注“pin 可重算 / 过程事件”。
  - 过程事件类哨兵按 Goal 作用域保持 open，交还后新 pin 的 `decide` 仍把它们计入 `blocking`，直到 `override_sentinel`。
  - 或者规定：`also_applies` 中含 `sentinel_high`、且其中有过程事件类哨兵时，交还对话框要求先处置该哨兵。
  - SP 增加一个用例：从 `paused(sentinel_high{input_mutated_after_gate})` 接管并交还后，Goal 不能不经覆盖进入 `in_review`。

**R8-D7-02｜次要**

- **问题**：`07` L522–529 的 (a') 以“base 的 lockfile 为参照”开头，但各条件的写法不一致：
  - “别名”条件写成“解析图中它由 `npm:` 别名引入”，没有限定为“相对 base 新出现”；
  - 补丁与覆盖、非注册表来源两条也没有明说。

  这会造成误报：base 中本来就以别名引入运行器的项目（例如以别名把构建工具换成兼容的替代实现，这是工具链团队公开推荐的用法）、或 base 中本来就为运行器打补丁的项目，每个 Goal 都会得到 `runner_patched` severity 2，结论永久降为“有保留”，人每次都要覆盖。P37 只测了“新引入别名”。
- **为什么重要**：误报会侵蚀“有保留的已验证”的信号价值（`07` §7.11 的精度目标为 0.95）。
- **文档位置**：`07` §7.4.3 (a') L522–529；`15` ADR-098；`14` P37。
- **期望的回答形态**：
  - 写明每个条件都是“相对 base 新出现或发生变化”。
  - base 中已存在的别名与补丁作为项目级信息只显示一次，例如在 VerifyProfile 中由人确认。
  - P37 增加“base 已有别名、Goal 未改动 → 无 `runner_patched`”的对照用例。

**R8-D7-03｜次要**

- **问题**：seal 消息由三部分拼接（`10` L360–361）：
  - Agent 在卫星中的提交说明（Agent 可控的文本）；
  - 人的意图；
  - Tower 的 trailer。

  seal 以用户身份提交，并可能由用户签名（`10` L366）。设计没有规定 Agent 文本与 trailer 块之间的隔离：Agent 的提交说明中如果含有形如 `Tower-Verified-At:`、`Co-authored-by:`、`Signed-off-by:` 的行，就可能被 trailer 解析器当作事实，或者以用户签名的形式成为一项声明（例如 DCO 签署）。
  - 另外，trailer 集合在三处不一致：`10` L361（Goal/Run/Model/Verified-At）、`10` L739（Goal/Contract/Verified-At）、ADR-036（Human-Edit/Co-authored-by）。
- **为什么重要**：事实与声明分离（README 第 3 点）应当延伸到写进用户仓库的持久产物；签名提交中的声明归属于用户。
- **文档位置**：`10` §10.6 L358–366、L739；`15` ADR-036、ADR-100。
- **期望的回答形态**：
  - Agent 文本作为引用段落放入，并标注“Agent 的提交说明（声明）”。
  - 对形如 trailer 的行做转义或剔除；Tower 的 trailer 永远是最后一段，由 Tower 独占生成。
  - 统一 trailer 集合并登记到 `16`。

### D11 安全与自主度

**R8-D11-01｜重要**（R7-D11-01 的残留）

- **问题**：ADR-096 把嵌套仓库定义为“名为 `.git` 的条目，或同时含 `HEAD` 文件、`objects/` 与 `refs/` 目录的目录”（`10` L74、`07` L193）。本轮已核对，git 还会识别另外两种目录：
  - **(1)** 只有 `HEAD` 与 `commondir` 文件、对象与 ref 位于 `commondir` 指向之处的目录；
  - **(2)** `HEAD` 为符号链接的目录。

  Tower 构造的环境因 `safe.bareRepository=explicit` 不受影响（本轮对照已核对），但有三处防线只靠这道扫描：

  - **集成后的用户主检出**：扫描漏判的目录不会被排除，会进入 pin 与 seal，再合入用户仓库。用户全局配置的默认值允许隐式发现裸仓库；shell 提示符的 git 集成会在进入目录时运行 git，从而读取其中 Agent 可控的配置。`00` L80 对此只是“建议”。
  - **两种检出**：信任提示“列出裸仓库布局目录”，对这两种变体失效。
  - **评审**：“被排除的路径在评审中显式列出”同样不覆盖它们。

  另外，接管时的处置各处说法不一：
  - `10` L74 写“命中任一种都在其移除前拒绝人工交接”；
  - `10` L565 与 `06` L781 只在发现 `.git` 时（`06` 还限定为 S0 下）拒绝；
  - `10` L604 与 T31 写“信任提示列出这些目录”——这意味着接管照常进行。
- **为什么重要**：ADR-096 的扫描正是 Tower 环境之外的唯一兜底。漏判的后果是用户在自己的主检出中以本人身份执行 Agent 可控的 git 配置，属于 T29 一类。
- **文档位置**：`15` ADR-096；`10` L28、L74、L199、L565、L604；`07` L193；`06` L781；`11` L340、T29 L545、T31 L547；`00` L80；`14` G27。
- **期望的回答形态**：
  - 判定规则与 git 的仓库识别逻辑等价：`HEAD` 可以是普通文件或指向 `refs/` 的符号链接；对象与 ref 按 `commondir`（若存在）解析。或者在只允许执行 git、显式关闭发现之外一切副作用的沙箱中，以真实 git 判定。
  - 统一接管时的处置。建议：从人工编辑检出的 CoW 副本中排除这类目录并在提示中列出，而不是拒绝接管（与 R8-D13-01 一起考虑）。
  - 在集成前的评审中，把“新出现的裸仓库形态目录”作为单独一项阻断或确认。
  - G27 增加 `commondir` 变体与符号链接 `HEAD` 变体。

**R8-D11-02｜次要**

- **问题**：ADR-100 用 Tower 自己的解析器读取 Agent 可控的 loose 对象与 pack（含 `.idx` 定位与 delta 解出，`10` L90）。已有的限制是：单对象 ≤ 1 MB、≤ 200 个提交、总超时 5 s。但设计没有写明：
  - 解析运行在哪个进程（Supervisor 本身，还是隔离的 worker）；
  - delta 链深度与循环的限制；
  - 解压前后的字节上限与内存上限（zlib 炸弹、超大 delta 结果）；
  - 当 delta 基对象需要经 alternates 查找时的处理（“找不到即缺失”已有，但 REF_DELTA 指向镜像对象很常见）。

  G28 覆盖了部分输入，但缺少“delta 环”与“高压缩比输入”。
- **为什么重要**：这是 Tower 进程在沙箱外处理 Agent 可控二进制格式的唯一一处；第 6 轮曾因 FIFO `HEAD` 阻塞持锁流水线。
- **文档位置**：`10` §10.1.3 L90；`15` ADR-100；`14` G28。
- **期望的回答形态**：
  - 在无网络、无写权限、限内存的 worker 中解析。
  - 规定 delta 深度上限（例如 50）与解压字节上限。
  - 或者只解析 loose 对象，pack 中的提交一律省略——失败本来就“只省略说明”，这样最简单。
  - G28 增加上述两种输入。

### D13 隔离、git 与并发

**R8-D13-01｜重要**

- **问题**：ADR-096 把“裸仓库布局”并入 ADR-071 的嵌套仓库，规则同时作用于 base 中已经存在的、被正常跟踪的目录：
  - **(a) 排除**：每次影子操作以 `:(exclude)` 排除命中路径（`10` L74、`07` L193）。
    - 以 git 实现或 git 工具为对象的仓库，常把裸仓库形态的测试夹具作为普通文件跟踪（例如 `tests/resources/<name>.git/`）。这些路径从此被排除在 pin 之外：Agent 对夹具的修改不进入 pin，也不进入验证与 seal。
    - 结果是验证判定的树与 Agent 观测轨看到的树不一致，评审中只多一行“被排除的路径”。
    - ADR-071 原本只针对 `.git`。`.git` 本来就不可能被跟踪，排除它不丢任何内容；裸仓库布局则不同，排除它会丢掉被跟踪的内容。
  - **(b) 拒绝交接**：`10` L74、L199 写“命中任一种都在其移除前拒绝人工交接”，没有区分 base 中已有的命中。这类项目将永远无法使用“我来改”与检验检出（检验检出也属于“人工交接”，L199）。
  - **(c) 依赖目录中的误报**：全量遍历“被忽略的依赖目录同样遍历但只看名称”（`13` L312）。已发布包中的裸仓库形态夹具会被记为 `nested_repo`：severity 3，阻断 Verified，精度目标 0.99（`07` L1261）。误报率没有测量计划。
- **为什么重要**：这是 ADR-096 的功能性副作用，会让一类真实项目在 Tower 中无法得到正确的 pin 与交接；而安全收益已经由 `safe.bareRepository=explicit` 在 Tower 环境中取得。
- **文档位置**：`15` ADR-071、ADR-096；`10` L74、L199；`07` L193、§7.10.1 L1261；`13` L312；`14` G24、G27。
- **期望的回答形态**：
  - 区分“base 中已跟踪”与“新出现”。base 中已跟踪的裸仓库形态目录按普通文件进入 pin，不拒绝交接，只在两种检出的提示中列出；新出现的才排除并记哨兵。或者给出其他论证过的规则。
  - 写明被忽略目录中的命中如何处理（例如只提示，不阻断；它们不进入 pin）。
  - G27 增加一个“base 跟踪裸仓库夹具且 Agent 修改其中文件”的对照用例：pin 含该修改，无误报，交接可用。
  - 在 SP 中测量样本仓库与常见依赖中的误报率。

**R8-D13-02｜次要**

- **问题**：垫片 exec-path 是 `<wtRoot>/_stores/_shim/git-core-<版本>/`，其中的符号链接指向真实 git-core，真实 git 的路径以绝对路径记录在垫片中；它“在 Tower 启动时按真实 git 版本重建”（`10` L382）。但 G20 的验收写的是“git 升级后自动重建”（`14` L70）。
  - 包管理器安装的 git，其 exec-path 通常位于带版本号的目录。Tower 运行期间升级并清理旧版本后，符号链接与垫片中的绝对路径都会悬空：Agent 的所有 git 调用（不只是嵌套调用）都会失败，直到 Tower 重启。
  - 目录名只用版本号，同一版本、不同安装位置的情况也会冲突。
- **为什么重要**：Agent 的全部 git 操作都经过垫片，它失效等于 Agent 失去 git。
- **文档位置**：`10` §10.6.1 L382；`16` §16.8.1 L863；`14` G20。
- **期望的回答形态**：
  - 每个 Run 开始前，校验真实 git 的 `realpath` 与 exec-path 是否变化，变化则重建。
  - 目录键改为（realpath，版本）。
  - 垫片发现真实 git 不存在时，给出明确错误并触发重建。
  - G20 写明“运行期间升级”的用例。
