### D4 领域模型与生命周期

**R19-D4-01｜次要**（窗口起点是“决定”，窗口内容是“检查点”，两者的先后没有定义；“通过”有两种写法）

- **问题**：
  1. **边界比较没有定义。**
     - 唯一规则以“较晚者”合并两个不同种类的点：一个 pin（提交）与一个决定（`HumanDecision`）。窗口内容则是“自起点以来的检查点”（`07` L1429 `later(lastPassedPin(goal) ?? base, lastHandToAgentDecision(goal))`、L1431 `checkpointsSince(goal, windowStart)`）。三者共用什么序（事件 `seq`、检查点序号 `n`、时间）没有写出。
     - 关键在 `hand_back{continue_agent}`。按 `06` L844，交还命令先记 `human.decision{hand_back, targetTree: T1}`，然后在第 ① 步对人工编辑检出做 `human_edit` 检查点，第 ③ 步归因为 `author:"human"`。
       - 如果按事件序比较，这个检查点晚于决定，落在窗口**内**。交还后 Agent 的下一次失败仍进入 `human_change_verify_failed`，正是 R18-D4-01 的“粘住”在最主要的交还路径上重现。
       - 如果决定记录的 T1 在检查点之后才写入，则落在窗口外。
     - 因此，结果取决于命令内部偶然的写入顺序。G33e(f) 断言“交给 Agent 的决定把窗口起点移到此处，之后只有 Agent 的检查点”，意图是第二种，但正文没有给出可以照做的定义。
     - `03` L78 的 `reverify` 说明（“交还的检查点为 `author:"human"`，窗口内有人的改动”）又说明同一个检查点在 `reverify` 时必须在窗口内。同一检查点在两种 `mode` 下必须落在边界两侧，这只能由“边界取决于决定种类”来表达，而文档没有这样写。
  2. **“通过”有两种写法。**
     - `03` L71 与 `16` L31 写“该次验证的结果使 Goal **进入 `in_review`**”；
     - `07` L1426 写“`decide` 给出 `verified`/`verified_qualified`/`not_machine_verified` 的 pin”。
     - 从 `accepted` 出发、满足验收延续的验证，`decide` 直接返回 `{to:"accepted", label}`（`07` L1457–1458），不进入 `in_review`。按 `03`/`16` 它不算“通过”，按 `07` 算。在 `accepted` 中 `keep` 后验证通过并延续、之后修订标准再验证失败时，两种读法给出不同的去向。
- **为什么重要**：这是 ADR-144 新设规则的边界，位于核心循环“验证失败 → 谁来修”上。第 1 项照字面按事件序实现，会让“交回 Agent 后恢复自动返工”在 `hand_back` 路径上失效，而这正是本规则要修复的回归。
- **文档位置**：`03` L71、L78；`06` L818、L844、L845；`07` L1426–1432、L1457–1458、L1477、L1484；`16` L31；`14` G33e（L113）；`15` ADR-144 L1117–1120。
- **期望的回答形态**：
  - 在 `16` L31 写明边界按检查点序号比较，例如：
    - 每个“交给 Agent”的决定在提交时记录 `handToAgentCp`，即该决定生效时最新的检查点序号。`hand_back{continue_agent}` 取其自身的 `human_edit` 检查点，`retry_after_human_change`/`request_changes` 取当时最新的检查点；
    - 通过的验证取其 pin 的检查点序号；
    - 窗口 = 序号**大于**两者中较大者的检查点。
  - 这样 `reverify` 不是“交给 Agent”，其 `human_edit` 检查点自然留在窗口内，两种 `mode` 的行为都由同一条定义推出。
  - 统一“通过”：采用 `07` 的标签口径（含延续到 `accepted`），改 `03` L71 与 `16` L31；或者反过来改 `07`。二选一。
  - G33e(f) 的期望写出边界依据；增加 (i)：从 `accepted` 延续通过后再失败。

**R19-D4-02｜次要**（离开 `paused` 后等待准入的状态未定义；“依赖在离开暂停时重新判定”没有转移；硬上限入口仍缺 `verifying`）

- **问题**：
  1. **离开 `paused` 后等待准入。**
     - `onAllReasonsCleared()` 的 `run` 目标“开 Run”（`03` L70）或“`run.requested{resume}`”（`06` L818），之后由准入的 a–g 检查（`06` L296–309）。
     - 槽位已满或依赖不满足时，准入写 `waitReason = slot|dependency`，但 `waitReason` 只属于 `ready`（`02` L141，`16` L67：“`ready` 中的 Goal 只可能处于 `queued`/`preparing`”）。
     - `03` 的 `paused` 出口只有 `running`/`verifying`/`claimed`/`in_review`（L23–24 图、§3.2.1）；DDL `CHECK ((continuation IS NULL) = (state <> 'paused'))`（`06` L476）又不允许清除继续目标后仍停在 `paused`。
     - 所以“三个 Goal 在运行时恢复第四个”这一常见情形，Goal 应处于哪个状态没有转移可依。
  2. **依赖重新判定。**
     - ADR-144 与 `04` L1319、`10` L268、`16` L32、G35e(j) 都写“依赖回退在离开暂停时重新判定”，但 `onAllReasonsCleared()` 与 `03` 的转移表里没有 `paused → ready{dependency}` 这条边。
     - 结果只能靠上一项的未定义路径推出。
  3. **硬上限入口。** R18-D4-02 要求的 `03` L80 入口与 L58 出口没有补上。L68 的通则（从 `verifying` 进入时写 `verify{pin}`）与 L71 的特例（继续目标 `run`）并存，未注明特例优先。
- **为什么重要**：第 1、2 项是 `03` 作为唯一状态机来源的缺边。实现者只能自行决定 `paused → ready`，或者让 Goal 以“没有原因的 `paused`”违反 DDL。第 3 项是 R18 已点名的残留。
- **文档位置**：`03` L23–24、L58、L68、L70、L71、L80；`02` L141；`06` L101、L296–309、L476、L818；`16` L32、L67；`04` L1319；`14` G35e(j)。
- **期望的回答形态**：
  - 在 `03` §3.2.1 的唯一规则 ② 中写明：`run` 目标且准入不立即通过时，同一事务转入 `ready{waitReason}`，Run 请求的类别保留为 `resume`，不受评审余量限制（与 `03` L54 一致），`pendingOpenings` 保留到 Run 开始。依赖不满足即为 `ready{dependency}`，这就是“重新判定”的唯一实现。准入第 f 项（硬上限）从 `ready` 进入 `paused(budget_hard_cap)` 时，继续目标为 `run`。
  - `03` 的图与 `ready` 行的“进入条件”加上这条边。
  - `03` L80 入口加“verifying（Agent 路径的返工因硬上限不能开始，继续目标 `run`）”，L58 加对应出口；L68 注明“L71 的硬上限分支优先于本通则”。
  - 用例：G35e(j) 的期望写出 `resume` 后的状态为 `ready{dependency}`；增加“槽位已满时 `app_quit` 后自动恢复”的状态断言。

### D6 系统架构与可靠性

**R19-D6-01｜次要**（settle 中崩溃的识别判据；drain 期间到达另一个目标；暂停中的回退前置条件）

- **问题**：
  1. **settle 中崩溃无法识别。**
     - `06` L140 同一格中有两句：“**settle 序列中崩溃**（无 drain）→ 继续目标 `settle`”；末句“`draining_for` 为空（drain 尚未开始即崩溃）→ 按‘Run crashed’处理：`paused{app_quit 或 engine_crash}`”。按 `03` L68，后者的继续目标是 `run`。
     - 两者的持久化特征相同：`draining_for` 为空、Run 未结束。区分它们所需的判据，即“本 Run 最后一次 `agent.settled` 晚于最后一次 `agent.start`、有效提交已记录、尚未 `claimed`”，没有写进恢复表。`runs` 表（`06` L522–539）也没有 settle 阶段的列。
     - R18-D6-01 第 4 项建议的持久化没有采纳，也没有给出替代判据。G35c(o) 的期望因此仍无法从恢复表推出。
  2. **drain 期间到达另一个目标**（R18-D6-01 第 3 项）。
     - `goal.pause` 写明“drain 中已有则并入 reasons”（`06` L834），但 `goal.take_over`（L843）与 `run.rewind`（L857）的前置条件都没有 `draining_for` 非空的情形。依赖回退触发的 drain 也只定义了“开始”，没有定义“已在 drain 中”。
     - 实现者可能有三种选择：覆盖 `target`、拒绝、忽略。覆盖时，`pause` 的 drain 被依赖回退改写为 `dependency`，人的暂停经 `ready{dependency}` 丢失。这正是 ADR-144 要防止的后果，只是换了一个先后顺序。
  3. **暂停中的回退（M2）。**
     - `take_over` 在 `external_change` 未解除时返回 `E_STATE`（`03` L78，`06` L843）。`run.rewind` 从 `paused(*)` 发起时不经过 drain，也没有同样的前置条件。
     - 于是在 `paused(external_change)` 中回退，会以 `restoreCheckpoint` 覆盖未处置的 E。ADR-144 只在 drain 路径上关闭了这一后果。
- **为什么重要**：
  - 第 1 项使恢复表内部自相矛盾，照“`draining_for` 为空”实现会在重启后开新 Run（继续目标 `run`），而不是按 ADR-143 完成 settle。已有的有效提交会被一次多余的 Agent Run 覆盖。
  - 第 2、3 项是同一类“人的决定或来源不明的内容被静默覆盖”的剩余入口。
- **文档位置**：`06` L90、L96、L140、L522–539、L834、L843、L857；`03` L68、L78；`10` L268；`16` L32；`14` G35c(o)、G35e。
- **期望的回答形态**：
  - 恢复表拆为两行，并写出判据：“`draining_for` 为空、本 Run 有有效提交记录（`runs.submit_tool_call_id`）且事件日志中最后一次 `agent.settled` 晚于最后一次 `agent.start`”→ 继续目标 `settle`；其余 → Run crashed。或者在 settle 第 ① 步开始时写 `runs.settle_started_at`，以该列判定。二选一。
  - 唯一规则补一句：`draining_for` 非空时，`take_over`/`rewind` 返回 `E_STATE`（“正在暂停，请稍后”）；依赖回退只在 `reasons` 中记一个 `dependency` 标记，不改 `target`。drain 结束后按 ADR-144 的规则处理，`dependency` 标记在离开暂停时由 R19-D4-02 的准入重新判定。
  - `run.rewind` 增加前置条件：`external_change` 未解除 → `E_STATE`（与 `take_over` 相同）。
  - 用例：G35c(o) 写明判据；G35e(k)：`pause` 的 drain 中发生依赖回退；(l)：`take_over` 的 drain 中再按“回退”。

**R19-D6-02｜次要**（macOS 上每 Goal 进程树的内存上限没有可执行的机制）

- **问题**：
  - `13` L190 规定每个运行中 Goal 的进程树有杀进程上限 `max(m_kill_v, 1.5 × p90_g, 2 GB)`，“超过 → 杀掉最大子进程组”。`16` L775 登记“进程树 RSS 采样：5 s（Goal）”。
  - 在 macOS 上，这需要每 5 s 知道该 Goal 的全部进程。此前靠进程组（验证器至今仍用 `ps -o rss= -g pgid`，`07` L710）；ADR-142 删除了 Agent 进程组的记录，ADR-144 又规定“不做持续扫描”（`16` L762，`10` L268，`13` L315）。
  - 两条登记互相矛盾：要么每 5 s 做一次全进程令牌扫描（不在 `13` L315 的四个时机内，也没有预算），要么这条上限在 macOS 上无从执行。“杀掉最大子进程组”在没有进程组记录的前提下也没有定义。
  - R18-D6-02 第 2 项已点出这一点，本轮回应没有涉及。
- **为什么重要**：
  - 这是 M1 平台（macOS）上防止 Agent 跑飞的测试或开发服务器耗尽整机内存的唯一单 Goal 保护；整机预留模型只管准入，不杀进程。
  - 实现者必须在两条“唯一”登记之间二选一，任一选择都会让另一份文档失真。
- **文档位置**：`13` L190、L314–315；`16` L762、L775；`10` L268；`07` L710；`15` ADR-142、ADR-144 L1124。
- **期望的回答形态**：
  - 显式选择一种，并改 `13`/`16`：
    - (a) 运行中的 Goal 每 5 s 做一次共享的令牌扫描，同时取 RSS（`proc_pid_rusage`），登记成本（≤ 50 ms / 5 s / 全部 Goal）与降级，并把它列入 `10` L268 的扫描时机；
    - (b) 以 Host 进程的后代树（按 ppid 遍历，成本低）采样 RSS，脱离父子关系的进程不计入，登记为残余；
    - (c) M1 在 macOS 上取消每 Goal 杀进程上限，只保留整机内存压力下的处置，并在 `13` 与 `11`/`14` 的风险登记中写明。
  - “杀掉最大子进程组”改写为按所选机制可执行的对象，例如 RSS 最大的、带本 Run 令牌的进程。
  - 用例：在 Agent bash 中运行一个持续申请内存的进程，断言按所选机制被处置或如实登记。

### D7 诚实与验证

**R19-D7-01｜次要**（M2 中“人的改动”的来源不可靠：Agent 可写的标签与 rebase 的措辞）

- **问题**：
  1. **`TOWER_ORIGIN=human` 可被 Agent 写入。**
     - ADR-144 补记 2 与 `10` L233 第 2′ 行规定：环境中带 `TOWER_ORIGIN=human` 的后台进程的写入归为 `author:"human"`，计入归因窗口；`11` L353 规定扫描读出该取值。
     - 但这个变量与 `TOWER_RUN_TOKEN` 一样位于普通环境中。Agent 自己的 bash 子进程可以携带任意取值，令牌本身也对 Agent 可见（`11` L350）。
     - 缺的不变式是：“人”这一层（Human）的归因只能来自 Agent 无法写入、也无法读取的通道。按现行规则，Agent 的写入可以被记成人的。
     - 后果：
       - 评审界面把这些 hunk 显示为人的改动，审查者通常不会细看自己的改动；
       - 失败去向被改为不自动返工；
       - Fact/Claim/Human 分层的“Human”可以由 Agent 生成。
     - 第 2′ 行“调用窗口内的写入”一句，在 Agent 工具调用与 `user_bash` 并发时也没有优先规则。
  2. **rebase 带入的变化被称为“你的改动”。**
     - U2 裁决（ADR-144 L1130）把 rebase（M2）带入的 base 变化计为“人的改动”，`03` L71、`07` L1430–1432 已照此修改。
     - 但 `04` L950 的失败卡片首行写“包含你采纳或修改的内容”，`12` L408 的标题是“你的改动未通过验证”，两者都没有 rebase 的措辞；`04` L946 列举的“你的改动”也不含 rebase。
     - 理由“来自人类同事的代码”也不完全成立：M2 的合并队列会把其他 Goal 中 Agent 写的代码合入 base。
     - `isRebaseCheckpoint(cp)` 所依赖的“rebase 检查点”不在 `Checkpoint.landmarks` 中（`16` L169）。
- **为什么重要**：
  - 两项都是“人”这一层的归因出错：一个可被 Agent 伪造，一个在界面上把非本人的内容称为“你的”。
  - 都只影响 M2（M1 没有 `user_bash`，也没有 rebase），因此列为次要。但它们属于产品原则层面，应在 M2 定稿前关闭。
- **文档位置**：`15` ADR-144 L1129–1130；`10` L233、L268；`11` L350–356；`03` L71、L85；`07` L1430–1432；`04` L946–950；`12` L408；`16` L31、L169；`14` G35c(s)。
- **期望的回答形态**：
  - 写入不变式：Human 层的归因不得依赖 Agent 可读或可写的值。M2 的人路径改用 Tower 侧的记录，例如 `user_bash` 实例使用独立的随机令牌，且该令牌不出现在工具路径的任何环境中；或者 M2 不区分来源，`user_bash` 的写入一律按 Agent 处理，并在 Trace 中注明“人经会话执行”。
  - 第 2′ 行补上与工具调用并发时的优先规则。
  - rebase：在 `16` L31 与 `04` §4.8.12 中单列“rebase 带入的 base 变化”，卡片文案区分“你的改动”与“base 的新变化”；给 rebase 检查点登记 landmark（如 `rebase`）；把 U2 的理由改为“不是本 Agent 的工作”。
  - 用例：G35c(s′)：Agent 的后台进程自带 `TOWER_ORIGIN=human`，断言它的写入不被记成人的。

### D8 注意力与交互

**R19-D8-01｜次要**（撤回与送出的竞争：已送出也返回成功；“消费”时点有两种写法）

- **问题**：
  1. **成功结果不区分“已撤回”与“已送出”。** `goal.openings.withdraw` 规定“该 id 已不存在（**已被消费**或已撤回）时同样返回成功”（`06` L836）。界面说明“撤回后 Agent 不会收到这一条”，“撤回立即生效……（还没有送出）”（`04` L966、L972）。人在 Run 开始的同一时刻点“撤回”时，命令返回成功，界面按成功显示，Agent 实际已经收到这段话。界面对“我的话有没有发出”给出了错误的事实。
  2. **“消费”的时点有两种写法。**
     - `02` L179、`03` L70、`06` L818、`16` L29 写“任何 Run 开始时全部消费并清空”；
     - `05` C38（L1401）写“任何一段 `disposition ≠ handled` 时 Run 终止、**未投递的条目留在队列**”，即逐段投递后才移除；
     - `05` L99 的 `details.key = OpeningRef.id` 注明“用于去重与撤回对账”，但对账规则没有写。
     - 撤回到达时，Host 已拿到的 `RunOpening` 快照中的条目（例如最后以 `prompt(human)` 发出的人写文字）是否还会发出，取决于选哪一种写法。
- **为什么重要**：这是 Fact/Human 层的诚实问题：人以为自己撤回了一段将以“你”的身份发出的话，实际没有撤回。概率低，但发生时用户没有办法知道。
- **文档位置**：`06` L818、L836；`04` L966、L972–973；`05` L99、L1401；`02` L179；`03` L70；`16` L29、L806；`14` G33d(e)(f)。
- **期望的回答形态**：
  - 统一消费时点：建议在 Run 开始的同一事务中把条目移入本 Run 的“投递中”列表（不再可撤回），逐段 `handled` 后标记已送出，失败时退回队列。C38 与 `16` L29 同步。
  - 撤回命令的结果区分 `withdrawn | already_sent | not_found`，仍保持幂等（重复撤回同一条返回同一结果）。`already_sent` 时界面显示“已送出，未能撤回”并链接到轨迹中的那一行。
  - 用例：G33d(g)：撤回与 Run 开始并发，断言结果与 Agent 是否收到一致。

### D15 文档一致性与可执行性

**R19-D15-01｜次要**
